# 全平台首轮静态核查：配置负担、工作衔接与重复决定

状态：2026-10-27 首轮静态盘点与优化排序已完成，产品实操和整改未开始。核查负责人：Codex；整改统筹待分配，各模块和在途需求保留原负责人。本记录是[治理需求](spec.md)的证据附件；需求和优化顺序由该书维护，不另建需求、状态平台或派工系统。

## 1. 证据口径

本轮对照 main `e5b173438d` 的实现与本分支已有需求补充；没有运行真实 Home、读取用户材料正文、连接真实账号、调用模型或操作桌面。源码能证明字段、跳转、条件和状态存放位置，不能证明真人任务已经复现或端到端通过。以下区分：

- **静态确认**：当前可达界面或处理分支有直接依据；影响大小和优化后的体验仍须实操验证。
- **报告待复现**：一骏实际使用报告，尚未定位当前版本根因。
- **政策待评估**：现有设计或规划可能不适合所有场景；提出差异，不视为已批准更改政策。
- **入口已定位／路径待实走**：纳入全平台范围，但本轮没有足够证据判断存在问题或已经好用。

“高级功能含技术参数”“后台做了多次校验”“有多个确认入口”本身均不算缺陷。普通任务是否被迫经过、前后是否为同一次决定、后一个检查是否要求用户重新操作，需要分别判断。源码中的 JSON、动作 id、版本和权限也不能直接算作用户看见的负担。

## 3. 具体发现与拟优化方向

批次编号引用[治理需求 §6](spec.md#6-怎样推进和交付)，不是独立严重级别或开发授权。每项都保留原主人；原需求已归档时只作为历史合同依据，实施前按仓库约定承接到现行需求，不在归档书上制造一条并行进度线。

### PF-A01 · 材料带入、生成与项目内继续之间失去连续性｜第 1 批

**报告待复现。** 一骏报告扫描/选择无反馈、代码文件缺失、返回后八千多项变 0、改范围确认无反应、生成报泛化超时、最后进入空项目且 Coding 仍要选目录。[Onboarding 服务](../../apps/local-host/src/context-onboarding-service.ts)与[客户端](../../apps/workbench/src/scripts/context-onboarding.ts)各有阶段/视图/忙碌状态，需要联合复现，当前不指定唯一根因。

拟优化：有效材料与生成结果不随视图丢失；缺模型只阻止模型步骤，修改范围只使相关结果失效；采用后读回项目内真实内容，在同一条路径接续工作目录。不能把材料读取授权扩大成任意代码执行授权。原主人：[Onboarding](../onboarding-coverage/spec.md)，已有 ONB-35～46 等具体要求，不另拆重复工单。退出证据：真实代码及混合目录，包含失败、返回、改范围和重启后能继续完成工作。

### PF-A02 · 另一条资料导入路径仍让用户处理批次与遗漏｜第 1 批

**静态确认。** [知识导入](../../apps/workbench/src/browser/knowledge/import.ts)的 `MAX_FILES = 200`，展示“一次只导入前 200 个”；拖拽遍历达到 400 项就停止，`wanted` 会过滤隐藏路径与依赖/构建目录。界面说明选中批次限制，但被发现前截断及过滤的范围没有在这段选择逻辑中形成完整遗漏说明。这是知识侧导入路径，**不能直接当成 PF-A01 的根因**。

拟优化：平台管理分批与可恢复进度，展示实际发现、忽略、待处理及已带入范围；限制确实必要时说明剩余项及继续方式，不要求用户自己拆文件夹、猜遗漏。普通读取限制与模型上下文限制分开。原主人：知识/成果库导入及 Onboarding 各自边界；[知识导入原需求](../archive/project-knowledge/spec.md)。退出证据：超过当前批次、含隐藏/忽略目录及大文件的真实集合，数量、原件与继续导入可核对。

### PF-A03 · 账号连接还没有统一交付“可以开始工作”｜第 2 批

**静态确认 + 报告待复现。** [连接引导](../../apps/workbench/src/settings-connector-guide.ts)已有准备就绪时直接登录的分支，也保留应用信息、回调和本机客户端配置；[连接说明](../../apps/workbench/src/settings-connectors.ts)还引导去 Coding、模型或 Feed 配置使用。[平台服务声明](../../apps/local-host/src/platform-connection-services.ts)明确模型、TypeSafe、图像、远程 MCP 凭据要再由消费功能选择。不能概括成“所有服务没有登录按钮”，也不能把条件分支当成每个服务已准备好。

拟优化：普通默认接入由平台准备应用、回调、能力发现及内部引用；服务页和当前任务均能完成必要登录/授权并回到可用工作。多个账号确实影响对象范围时保留选择；同账号同范围已完成的配置应读回复用。原主人：[服务接入 §8.1、ASC-45～50](../assistant-service-connections/spec.md)。退出证据：逐服务列明默认支持、自定义支持、产品未就绪，并至少完成该服务宣称的真实工作与失效重连；一个账号成功不替其他服务验收。

### PF-A04 · 模型模板后仍暴露协议表单，连接检查与保存绑在一起｜第 2 批

**静态确认。** [模型详情 `renderProviderDetail`](../../apps/workbench/src/settings-models.ts)在普通详情中展示 Base URL、API 格式、可编辑模型 ID；模板可预填部分字段，缓存/思考已经在高级项。保存说明写明地址、格式、密钥或模型变化后先检查连接，没通过就不保存。

拟优化：常用服务优先呈现账号、可用模型、用途和费用相关选择；自定义端点/协议仍可达。区分草稿保存、凭据保存、连接健康和任务可用状态，网络故障不迫使用户重填，也不把未验证模型标成可用。原主人：模型设置/agent-host；[Onboarding 模型接入](../onboarding-model-link/spec.md)及模型设置现行合同。退出证据：预设及自定义服务、临时断网、无效模型、已有有效供应商均可理解和恢复，普通预设路径无需理解协议。

### PF-A05 · 生图服务要求配置协议，再去别处准备账号｜第 2 批

**静态确认。** [Images 服务对话框](../../plugins/native/images/src/ui.ts)把 API 协议、基址、模型名称、账号选择平铺；凭据入口跳到 Connectors。生成尺寸是自由文本，提示可用值取决于服务与模型；[文案](../../plugins/native/images/src/messages.ts)还要求改变协议/基址后重新选账号。

拟优化：选服务/账号后直接得到可用模型和该模型支持的尺寸等选项；模板和已有连接组合成一个可完成的接入路径。自建兼容服务仍放高级入口；换信任目标时不能沿用不适用凭据。原主人：Images + 服务接入，历史依据[图片插件需求](../archive/images-plugin/spec.md)。退出证据：首次生成、改服务、已保存提示词、失效重连和结果未知后的恢复，不让用户猜尺寸格式或重复建同一连接。

### PF-A06 · Feed 与 Alchemist 的账号配置仍有额外接线｜第 2 批

**静态确认。** [Feed 来源设置](../../apps/workbench/src/scripts/client/navigation-feed-sources.ts)在缺连接时要求先到 Connectors，选项文字带 `auth_method`；换账号创建独立来源并暂停旧来源。[Alchemist 研究偏好](../../plugins/native/alchemist/src/ui.ts)另选跨项目 GitHub 账号，未选时匿名访问。两者有业务范围差异，不能直接强制共用一个账号。

拟优化：从“关注哪些内容/研究什么”就地补齐账号，平台显示已选账号及影响范围、带用户回原任务；必要的不同账号选择保留，协议方法不占普通选项的主要位置。换账号时解释旧内容与订阅去向并保留原数据。原主人：Feed/来源、Alchemist、服务接入；Alchemist 继续归[创作台升级](../plugin-builder-upgrade/spec.md)。退出证据：无连接、一个/多个账号、换账号和失效返回后，目标订阅及原内容都准确。

### PF-A07 · 缺配置后的跳转很多，返回原工作尚需统一验证｜第 2 批，依赖第 1 批恢复

**静态确认跳转，连续性待实走。** [Cognia](../../plugins/native/cognia/src/ui.ts)、[工作流程](../../plugins/native/workflows/src/browser/link.ts)、[创作台](../../plugins/native/plugin-builder/src/agent-studio.ts)均有模型设置入口；角色执行另选工作目录。部分插件已有 sessionStorage 草稿或工作记录恢复，不能推断所有跳转都会丢草稿。

拟优化：配置入口带回原任务、输入、选中对象与待继续动作；返回时读回事实，只有真正依赖新配置的步骤继续。不能只把链接改成弹窗，也不能新造第二份模型/账号状态。原主人：工作台导航及各消费插件，公共要求 PFG-04～06。退出证据：从上述每个消费者进入设置、失败/取消/成功返回、重开后继续；共享实现通过不替代消费者接入验证。

### PF-A08 · 记忆修改的失败重试只留在当前页面｜第 1 批记录，服从原暂停安排

**静态确认。** [记忆设置](../../apps/workbench/src/settings-memory.ts)明示“刷新浏览器或离开本页后不再保留”操作；`pendingCommands` 是页面内 Map，重试复用原 `operation_id`。当前页已有防重复提交，不能说后端完全没有幂等能力；也不能据此断言离开必然造成重复记录。

拟优化：跨返回/刷新能找回未确认结果的操作，用原主人回执先核结果，再决定重试；不要要求用户记住这次是否已经写入。原主人：[Memory 策略](../prologue-memory-strategy/spec.md)及现有记忆 UI；本轮只记录需求，不恢复已暂停的端口等待、集成或复验。退出证据：写成功但响应丢失、写失败、版本变化三种情况下离开再回来，不丢用户修改、不重复生效。

### PF-A09 · 插件通知恢复把内部交付判定交给用户｜第 1 批

**静态确认。** [插件通知恢复](../../apps/workbench/src/plugin-event-recovery.ts)要求用户先核对是否已产生结果、填写必填“处理依据”，再选跳过或“接受重复执行的可能”；[客户端](../../apps/workbench/src/scripts/client/plugin-event-recovery.ts)详情主要是事件与错误 JSON。它由插件管理和通知入口触达，属于异常路径，不是每次普通操作都会出现。工作流程[未知动作结果](../../plugins/native/workflows/src/browser/handoff.ts)也需要人工介入，但事实主人不同，不能直接合并存储。

拟优化：先由发起/接收主人按已有回执核对是否完成，给出具体对象、已知结果、影响和可安全采取的动作；仍无法确定的真实外部效果才保留用户决定，并提供可查结果入口。“接受风险”和填写理由不能替平台缺少结果信息兜底。不得以减少打断为由自动重放未知写入。原主人：Plugin Runtime 事件恢复、Workflows 各自执行记录；关联[平台插件需求](../plugin-platform-v2/spec.md)。退出证据：成功但回执丢失、确定未执行、重复请求、接收插件停用/升级；用户无需读事件 JSON 也能作出有依据的决定。

### PF-A10 · 授权文案和实际执行规则不一致；多层确认须逐边界核对｜第 3 批，文案可随相关批次先修

**静态确认。** [助理设置](../../apps/workbench/src/settings-assistant.ts)说修改类每次都需确认；[实际 `directEligible`](../../apps/local-host/src/assistant/assistant-authority.ts)允许声明且当前可用的撤销操作、未设置每次确认、非不可撤回的修改直接执行，`assistantAuthority.direct` 实际使用它；[能力读取](../../apps/local-host/src/assistant/assistant-http.ts)也返回可撤销与每次确认的选择。这里已确认的是表达/规则不一致，**没有据此证明当前每次修改都弹两次审批**。

拟优化：按实际有效授权解释哪些会直接做、哪些会确认；同一主体/范围/内容的有效批准可被相邻步骤消费，后端撤权/取消/版本核对继续执行。外部客户端授权、插件安装信任、目录访问和不可撤回效果不是一份授权。原主人：助理/agent-host、动作授权与消费者；关联[主动助理](../proactive-assistant/spec.md)、[动作架构](../action-architecture/spec.md)。退出证据：用一次普通可撤销任务、一次越范围请求、一次不可撤回操作逐步记录用户决定；实际重复时才删除对应重复门。

### PF-A11 · 个人角色使用仍要先经历保存、预览、项目发布｜第 3 批

**静态确认。** [角色编辑](../../apps/workbench/src/characters/ui.ts)区分个人草稿与固定到项目的发布版本；Coding/助理只能选已发布版本，[“现在就用它”](../../apps/workbench/src/characters/import-ui.ts)也要求先发布。工具默认继承，主动限制时才输入英文名称或另选能力。

拟优化：个人当前任务的“保存并使用”可以由系统形成可追溯固定版本并接好目标；跨项目复用、影响其他任务或扩大能力时再呈现真正差异。保留旧任务的固定版本和调用方权限，不用每轮自动升级，也不把角色选择当授权。原主人：characters、Coding/助理与[场景引导](../onboarding-coverage/spec.md)；历史依据[角色管理](../archive/characters-manager-repair/spec.md)。退出证据：首次写角色→立即做事→修改后用于新任务，旧任务版本保持准确；跨项目范围可理解。

### PF-A12 · 判断规则需要理解服务、结果映射、发布与启用｜第 3 批

**静态确认。** [判断编辑](../../apps/workbench/src/functions/ui.ts)要求选择用途、定义结果和页面动作映射；[发布说明](../../apps/workbench/src/functions/client-records.ts)明确锁定规则后还不自动启用，[使用状态](../../apps/workbench/src/functions/client-render.ts)再在当前项目启用。[账号设置](../../apps/workbench/src/functions/settings-ui.ts)另选 TypeSafe，试跑使用 Jev。已有业务说明、自动保存和高级 key 折叠，不能说全是裸 JSON。

拟优化：从“筛选消息/建议下一步”等用途带入对象和候选动作，给合理初稿；一次“试用并启用到这里”展示实际效果、所用服务与费用，并由系统固定版本/绑定用途。独立创作、高级结果映射与独立发布保留。是否替换判断服务属另一个产品决定，本轮不默认把它换成通用模型。原主人：functions、Feed/Inbox/Workflows/Home 的各消费场景；历史依据[判断产品编辑](../archive/functions-product-authoring/spec.md)。退出证据：从真实内容到该页面出现有效建议，修改规则、停用、服务失效可恢复；试跑成功不等于已经接入。

### PF-A13 · 工作流程的每条连接让人选择内部处理方式｜第 4 批，消费第 2/3 批成果

**静态确认。** [连接编辑](../../plugins/native/workflows/src/browser/link.ts)要求在判断规则、模板转换、AI、手动之间选择，模板填标题/正文占位符，判断为空时跳到规则创建。已有可读提示与“返回继续”按钮，不能当成无恢复实现。

拟优化：先问上一步内容怎样变成下一步要的结果、哪些需要用户决定；平台从当前能力给出可编辑的默认交接方式。普通直传不强迫创建判断规则；已选“手动”的业务决定继续保留，模板/规则编辑作为需要时的深入选项。原主人：Workflows 与函数/下游插件；[工作流程原需求](../archive/workflow/spec.md)。退出证据：一条直接交接、一条 AI 整理、一条确需人决定的流程，以及中途改条件、缺模型/规则、返回继续；不新增第二个编排引擎。

### PF-A14 · 自定义提示词把机器输出格式的责任留给用户｜第 4 批

**静态确认。** [提示词设置](../../apps/workbench/src/settings-prompts.ts)允许修改交给模型的说明；检测到 JSON/Schema/格式时提示用户保留格式要求，否则程序读不了。它是自定义入口，并非所有用户的开工前置条件。

拟优化：保留创作自由，把“做事方法与内容偏好”和协议必需输出要求的职责说清；能由系统承担的格式约束由系统承担。需要调整结构合同的高级能力明确其影响和验证方式，不让普通改写语气的人顺带负责解析协议。原主人：提示词/agent-host，关联[AI 交互](../ai-interaction-experience/spec.md)与[AI 开发手册](../ai-development-handbook/spec.md)。退出证据：改语气或判断依据不破坏必要结构；无效修改有针对性反馈和恢复默认，权限仍不由提示词决定。

### PF-A15 · 个人设置仍有需要专业知识才能表达的意图｜第 4 批，可独立提前处理

**静态确认。** [助理设置](../../apps/workbench/src/settings-assistant.ts)的预算只按输入加输出 tokens 填数；添加禁区应用要求输入 `com.example.app` 式标识。这两项不是所有任务的必填项，但用户表达“每天最多用多少”“不要访问这个应用”仍需自行翻译。

拟优化：预算给可理解的用量选择和当前消耗；只有价格可靠时给费用参考，不能伪造确定成本。禁区提供应用名称与可验证的应用选择，标识保留高级入口。原主人：助理预算与[Computer Use](../computer-use/spec.md)；既有真机验收安排不变。退出证据：不了解 token/Bundle ID 也能准确设置；上限、禁区及撤回仍由实际边界执行。

### PF-A16 · 规划中的统一真人批准门可能把团队发布规则扩大到个人工作｜先核规则，第 3 批落实已确定的调整

**政策待评估。** [真人批准门](../agent-approval/spec.md)仍标“尚未实现”，要求任何 Agent 代码/数据/外部状态变更取得规定人数批准，默认 2 人；[现有助理](../../apps/local-host/src/assistant/assistant-authority.ts)却已有有条件直接执行，[Goals](../../plugins/native/goals/src/policy-ui.ts)也有是否需要最终确认的项目设置。这是需裁决的适用范围，不能描述成生产中已到处要求两人审批。

建议先形成具体差异：个人同范围、可撤销的明确委托；个人不可撤回/外部效果；团队受保护发布；Goal 结果验收，分别说明谁决定、决定什么、有效到何时。GitHub 已有 review、应用内 effect 批准和任务最后验收若保护同一个决定应复用；保护不同对象时保留必要步骤。默认两人是否限团队发布、哪些个人动作可直接执行，要按既有用户决定处理，不在本次文档中自动生效。原主人：agent-approval、Coding QA、Goals/助理；退出证据是规则差异和实例，然后才实施与实操。不得把新批准门的全量落地变成所有体验修复的前置。

## 4. 检查与批准分别怎样处理

| 机制 | 此轮判断 | 拟处理与必须保留的边界 |
| --- | --- | --- |
| 用户先表达任务，随后对同范围可撤销动作再确认 | PF-A10 的实际分支已经区分一部分；剩余链路待实走 | 识别有效委托，允许后续消费；撤权、取消、对象或范围变化必须拒绝旧授权 |
| 模型“保存配置”先探测，消费者再检测可用 | 检测可以有不同目的，当前没有重复弹批准的证据 | 复用当前健康事实、保留草稿；执行前必要检查由系统做，不要求用户重复证明“已连接” |
| 角色发布、判断发布/项目启用 | 固定版本/作用范围有价值，普通使用路径仍可合并交互 | 一次有意义的“使用/启用”完成内部步骤；受影响对象与额外费用/权限差异必须可见 |
| 安装插件、外部 Runtime 接入预览 | 会修改配置、运行代码或给予新权限，不能按次数删掉 | 聚合本次相关差异；当前内容或权限变化后重新决定，不能替未来任意效果背书 |
| 调用前、效果提交前校验 | 可能保护并发、撤权与取消，不是重复人审 | 保留机器校验；只把真实新增决定交给用户，不能为了少弹窗绕过 `beforeEffect` |
| 未知结果重试与插件通知核对 | 不能盲目重复写，但 PF-A09 给人的信息不足 | 原主人先核回执和结果，必要时展示可验证事实；不把“写理由/接受风险”当恢复能力 |
| Goal 验收、PR review、真人批准门 | 分别可能面对成果、代码版本和外部效果；PF-A16 尚待定范围 | 记录各自对象，复用已有决定；不让个人任务为无关团队人数等待，也不把工程通过等同用户验收 |

没有证据证明现有所有检查都重复，本轮不设“删掉多少审批”的指标。后续用真实任务记录每次需要人作出的决定及其依据，经过相同对象但只是机器读回的步骤不记成新审批。

## 5. 已有做法中应保留的部分与未验证项

保留：Cognia 无模型时仍可阅读；Schedule 用普通时间表单；角色默认继承工具范围；Functions 自动存草稿并折叠调用 key；成果库、项目数据位置、对外能力身份的技术详情折叠；破坏性删除说明范围；知识整理到预算后停止；未知外部效果不自动重放。治理要把这些做法用到适合的消费者，不能以清理术语为由抹掉真实后果。

尚未完成：全平台真实内容路径、逐服务真实账号、已安装第三方插件、Desktop/Web 差异、启动/升级/唤醒与后台任务、性能/大量内容、响应式与键盘、模型结果质量、用户本人验收。表内入口覆盖不能代替这些证据；后续实走发现的新问题继续进入同一治理范围。

本轮文档交付的完成条件是：范围可追查、问题与推断分开、建议对应主人和真实边界、顺序与依赖明确。**这只完成盘点和排期，不完成平台治理或任何产品验收。**
