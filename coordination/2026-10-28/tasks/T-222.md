## 1. 背景

- 先答 MISC 没写、但决定单位的事：整理读一份材料、开始使用切段、进来的材料、宿主对提示语的上限，**数的都是字**，只有「一份材料占多大」这一处数单元。

  | 地方 | 数什么 | 单位 | 位置 |
  | --- | --- | --- | --- |
  | 整理读一份材料 | 前 60000 个 | 字（码点，`for (const character of text)`） | `organize-model.ts:98-108` `materialReadText`（T-163） |
  | 开始使用把长材料切段 | 每段不超过 60000 个 | 字（T-180） | `context-onboarding-service.ts:322`（`textParts`）、`:339`（`partEndByCharacters`）、`:363`（`TODO_PART_CHARS`）、`:372` |
  | `todo.organize.extract` 收的材料 | 每份最多 200000、最多 50 份 | 字（Ajv 默认 `unicode`，数码点；T-163 已核，`packages/kernel/src/action-schema.ts:41-42` 没有关它） | `organize-actions.ts:41`、`:58` |
  | 宿主对一份提示语的上限 | 180000 + 20000 + 100 | 字（注释写明「和 schema 的 `maxLength` 同口径」；先比单元数，介于一倍和两倍之间才数字） | `host-complete-text.ts:167-180` |
  | **`organizeParts` 估「一份材料占多大」** | `Math.min(material.text.length, 60000)` | **UTF-16 单元** ← 唯一不同的 | `organize-model.ts:116` |

- 链路：调用方（开始使用、助理、页面）送来最多 50 份材料 → `todo.organize.extract` 的处理器用 `organizeParts(input.materials)` 把它们分成若干组（`organize-actions.ts:117`）→ 每组一次模型调用，提示语里每份材料是 `materialReadText(material.text)`（`organize-model.ts:133`）→ 每次的回答各自解析，候选的 `ref` 加 `p<组号>-` 前缀合起来（`organize-actions.ts:118-131`）。
- 分组规则（`organize-model.ts:111-123`，本单不改）：一份一份往当前组里放，放进去会让当前组超过 `TODO_ORGANIZE_PART_CHARS`（40000）就先把当前组收起来、另起一组（`>`，所以刚好 40000 放得下）；失败的（`read === "failed"`）和空白的材料跳过，但保留它们的序号。所以**任何一份占 40000 以上的材料，前后都放不进别的材料，独占一次调用**；超过 60000 的材料也只记 60000，结果一样。
- 前提核对（MISC 那行写的）：

  | MISC 说的 | 核对 |
  | --- | --- |
  | 每份材料的长度按 `Math.min(material.text.length, 60000)` 数单元 | 成立，`organize-model.ts:116` |
  | T-180 之后一段可达 120000 个单元 | 成立：开始使用把材料切成每段不超过 60000 个字（`textParts(…, TODO_PART_CHARS, "characters")`，`context-onboarding-service.ts:372`），满是 🟢 的一段就是 120000 个单元 |

- 改成按字数以后，什么变、什么不变（`organizeParts` 的结果，起草时用独立脚本算过）：

  | 材料 | 改前 | 改后 |
  | --- | --- | --- |

  | 三份各 13000 个 🟢 | 三次调用 | 一次调用（39000） |

## 2. 目标

1. `organizeParts` 数一份材料占多大，按它的字数（码点），最多 60000，和整理实际读的字数同一口径：字数合起来不超过 40000 的材料合成一次调用，不管它们的 UTF-16 单元数是多少。
2. 其余一字不变：40000 的预算和 `>` 的比较、一份 40000 字以上的材料独占一次调用、失败与空白的材料跳过而序号不变、不含两单元字的材料分出的组和今天一样。
3. 用例钉住上面几条：预算的边界（刚好 40000 字放得下，多一个字就放不下）、码点而不是字素、混合文字、经 `organize.extract` 看到的每一次调用收到什么、一次调用最多带多少。

```ts
/** How many characters organizing reads of a material, counted as `materialReadText` cuts it: whole characters, at most TODO_ORGANIZE_MATERIAL_CHARS (a 🟢 is one character but two UTF-16 units). */
function materialReadChars(text: string): number {
  let count = 0;
  for (const _ of text) {
    if (count === TODO_ORGANIZE_MATERIAL_CHARS) break;
    count += 1;
  }
  return count;
}
```

函数怎么走：
- `for (const _ of text)` 一个码点一个码点地走，一个 🟢 走一步；`_` 不用，TypeScript 的「没用到」检查不查以下划线开头的 `for…of` 变量（`apps/local-host/src/context-onboarding-service.ts` 里 `for await (const _ of todoBatches(…))` 就是这样写的，起草时也单独用 `tsc --noUnusedLocals` 编译过）；
- 走满 60000 个、后面还有字时停下，返回 60000；走完了还不到 60000 个，返回走过的个数。所以结果是 `min(字数, 60000)`，和 `materialReadText` 取的那一段的字数相等；
- 不展开成数组（`[...text].length` 会为一份 200000 字的材料建 20 万个元素的数组，50 份就是 1000 万个）；
- 不加「单元数够长就直接返回」的快捷路径：循环最多走 60001 步，50 份材料最多 300 万步，不值得多一个分支；
- 60000 这个上限对**分组**没有可见的影响（任何一份占 40001 以上的材料结果都一样，都独占一次调用）；它在这里是为了和 `materialReadText` 一致、并且让循环有界。所以没有哪个用例能分辨「记 60000」和「记更大」，也不要为此另加用例（第 8 节第 4 条）。

## 8. 与默认不同的

1. **推翻了 T-163 第 8 节第 2 条，统筹 2026-10-29 定。** 当时 `organizeParts` 定为仍按单元估算，理由是多份材料合成的一次调用不超过 40000 个单元。现在按字数：多份合成的一次调用，字数上限不变（40000），单元数上限最多到 80000（满是两单元字时）。独占一次调用的材料（40000 字以上）没有变。没有另设单元数预算（另一种做法：字数和单元数各一个预算，较小的先到先分组）：统筹定为按字数，同切段、读、进来的材料、宿主提示语上限一个口径。
2. **加了一个新函数，只在文件内用，不导出。** `materialReadText` 导出是因为 `organize.ts` 要用；`materialReadChars` 只有 `organizeParts` 用，不导出，包的公开导出不变。它和 `materialReadText` 是两个循环，各数各的：合并成一个会改动 T-163 的函数，扩大本单的范围。两者是否一致由 `RAC-2158` 钉住（每份材料给模型的字数就是它被记的字数，每次调用带的字数加起来对得上）。
3. **浏览器用例开发不跑，交给设备 A 的验证跑。** `plugins/native/todo/README.md:35` 的必跑里有 7 个浏览器用例（名单见第 7 节）。开发不跑，验证线在最终头上跑：这是统筹定的（照 T-094、T-163 的先例），不算违反「README 必跑」。改动面很小：
