## 1. 背景

- harness 结算超时的那一段（`cdp.ts:320-333`），现在的样子：

  ```ts
          const decidedAt = performance.now();
          const settle = (profile: …, profiling: boolean) => {
            …
            // `elapsed` says how long the command actually stayed unsettled, including this optional read; `profileReadMs`
            // says how much of it was the read, so the timer's own lateness can be told apart.
            if (profiling) failure.diagnostics = { ...counters, profileReadMs: Math.max(0, Math.round(performance.now() - decidedAt)) };
            else failure.diagnostics = counters;
            failure.message += ` (elapsed ${Math.round(performance.now() - started)}ms; limit ${timeoutMs}ms)`;
            reject(failure);
          };
  ```

  `started` 是 `:304` 在 `command()` 里同步取的 `performance.now()`；`performance` 来自 `node:perf_hooks`（`cdp.ts:3`），和全局的 `performance` 是同一个对象。
- 用例 `RAC-1452`（`browser.test.mjs:370-391`）里有关的几行：

  ```js
        const started = Date.now();
        …
        await assert.rejects(harness.command("Never", {}, undefined, 100), (error) => {
          const settledAfter = Date.now() - started;
          assert.ok(settledAfter >= 100 && settledAfter <= 350, `settled after ${settledAfter}ms, outside limit..limit + 250`);
          const stated = Number(/\(elapsed (\d+)ms; limit 100ms\)/.exec(error.message)?.[1]);
          assert.ok(stated >= 140, `elapsed ${stated}ms includes the profile wait`);
          assert.ok(stated <= settledAfter, `elapsed ${stated}ms claims more than the ${settledAfter}ms the caller waited`);
  ```

- 为什么 harness 量到的等待不会比用例量到的长：
  - 用例先取 `started`，再同步调 `harness.command`，harness 的 `started` 在后（`:304`）；
  - harness 在 `settle` 里取结束读数（`:331`），然后才 `reject`；用例的结束读数在 `assert.rejects` 的回调里，更晚。

  所以只要两边用同一个单调时钟，harness 量到的就是用例量到的一段。
- 两个时钟的问题：
  - `Date.now()` 是墙上时钟，整数毫秒，会被 NTP 微调（变快或变慢）甚至跳变；
  - `performance.now()` 是单调时钟，带小数。

  只把 `:331` 改成 `Math.floor`，`Date.now()` 那一侧的差值仍可能少量不到 1 毫秒。绝大多数时候够了，但证明不了。用例改用 `performance.now()` 后才能证明：`floor(x) ≤ x ≤ settledAfter`。
- 包外没有谁读这个数：`git grep` 整个仓库（`tests/`、`apps/`、`packages/`、`scripts/`），解析 `(elapsed …ms` 的只有 `browser.test.mjs` 自己（`:295`、`:325`、`:356`、`:379`、`:407`、`:427`、`:470`）。除 `:379` 外都是 `\d+` 的格式匹配，取整方式不影响。
- `MISC.md:31` 的 ⑥⑦（同三个文件里的文字）：
  - ⑥ `README.md:40` 里「（两者相减就是定时器本身晚了多少）」不对：`elapsed − profileReadMs` 是到判定超时为止的耗时，再减 `limit` 才是定时器晚了多少。同一段里「读取期间 `close()` 会断开采样会话…」和「`close()` 自己也不被挂起的读取拖住…」说的是一件事，并成一句；
  - ⑦ 注释和 README 里的「B2」（T-036 任务书里的方案代号）改成说人话的「`profileTimeouts` 打开时」或干脆去掉；协调分支哈希 `10a24449a` 换成 `RAC-1452`。出现在 `cdp.ts:57`、`:59`、`:60`，`browser.test.mjs:374`，`README.md:40`（两处「B2 打开时」）。包里没有「B1」。

## 2. 目标

1. 超时消息里的 `elapsed` 是命令从发出到结算等了多少**整**毫秒，向下取整：只会比真正的等待少不到 1 毫秒，不会多报。
2. `RAC-1452` 的 `:381` 在任何时序下都成立，不再靠取整的运气；它的其余断言一句不改。
3. 有一个结果确定的用例（`RAC-1674`）钉住「向下取整」：改回 `Math.round`、改成 `Math.ceil`、或者从判定时刻起算，它都红。
4. README 的这段说明和注释说对：`elapsed` 怎么取整；`elapsed − profileReadMs − limit` 才是定时器晚了多少；不再出现「B2」和协调分支哈希。

## 3. 不做

- 不给 `:381` 放 1 毫秒的取整余量（`stated <= settledAfter + 1`）。那等于允许 harness 多报 1 毫秒，是放宽。
- `profileReadMs`（`cdp.ts:329`）仍用 `Math.round`。它在用例里的断言都有 100 毫秒以上的余量，换不换取整都没有测试分得出来，改了也证明不了；本单只动消息里的 `elapsed`。
- 不改任何期限、宽限（`DIAGNOSTICS_GRACE_MS`）、默认值，不改消息格式，不改 `cause` 和 `error.diagnostics` 的键。
- **不收 `MISC.md:31` 的 ⑧**（三处时间余量）。起草时逐条算过：
  - `:378` 的上界 350 就是 `RAC-1452` 的验收「`limit`～`limit + 250`」，余量约 100 毫秒，来自宽限 150。放宽上界是放宽验收，缩短宽限是改产品常数，都不在本单；
  - `:443`（`RAC-1451`，排队读取）有两处余量：
    - 宽限余量：第一次读取要在 150 毫秒宽限内读完。读取延迟是 80，余量约 70；
    - 顺序余量：第二条命令要在第一次读取重启采样段（约 30＋80＝110 毫秒）之前发出。它在 40 毫秒发出，余量也约 70。

    MISC 里的建议（延迟降到 50、第二条命令晚 20 毫秒发）：宽限余量升到 100，顺序余量降到约 60（30＋50−20），两者里小的那个反而从 70 降到 60。到现在也没见它红过，本单不动；
  - `:393` 区分力弱：`close()` 在 240 毫秒，宽限在约 250 毫秒自己就会结算，只差约 10 毫秒。要让它分得出，得加新的时间断言，会带来新的偶发红风险，不在本单。

  三条都留在 MISC，以后哪条真红了再开单（第 8 节第 4 条有建议的改法）。
- 不碰 `.github/workflows/*`、`scripts/run-tests*`、`tests/quarantine.json`、`tests/ci-product-subset.txt`。

   ```js
   test("a timeout's elapsed is the whole milliseconds the command waited, rounded down, never more (RAC-1674)", async () => {
     // merge_group run 40790882078 (#1415): RAC-1452 read "elapsed 250ms" against the 249 ms its caller had waited, because
     // the harness rounded to the nearest millisecond. Here the command starts on a whole millisecond and every later
     // reading is 0.6 ms past one, so rounding would claim a millisecond the command never waited.
     await withHarness(() => {}, {}, async (harness) => {
       const real = performance.now.bind(performance), readings = [];
       performance.now = () => {
         const reading = Math.floor(real()) + (readings.length === 0 ? 0 : 0.6);
         readings.push(reading);
         return reading;
       };
       try {
         await assert.rejects(harness.command("Never", {}, undefined, 50), (error) => {
           const stated = Number(/\(elapsed (\d+)ms; limit 50ms\)/.exec(error.message)?.[1]);
           const waited = readings.at(-1) - readings[0];
           assert.equal(stated, Math.floor(waited), `elapsed ${stated}ms for ${waited.toFixed(1)}ms measured`);
           return true;
         });
       } finally {
         delete performance.now;
       }
     });
   });
   ```

   这个用例为什么成立（写进【方案】，PR 里也写）：
   - `performance.now = …` 在全局 `performance` 上加一个自有属性，盖住原型上的 `now`；`cdp.ts` 从 `node:perf_hooks` 取的是同一个对象，所以 harness 读到的是换过的读数。`delete` 删掉这个自有属性，就恢复成原型上的。
   - 换掉之后、`harness.command` 之前没有别的代码运行（同一段同步代码），所以第一个读数就是 `:304` 的 `started`，整毫秒。
   - 后面的读数都带 0.6：`:320` 的 `decidedAt`、`:331` 的结束读数，以及这期间进程里别的代码碰巧取的读数（无害）。
   - `reject` 之后到 `assert.rejects` 的回调之间只有微任务，所以 `readings.at(-1)` 就是 `:331` 那一次。harness 算的正是 `readings.at(-1) - readings[0]`，约等于「整数＋0.6」：
     - `Math.floor` 得到那个整数，等于 `Math.floor(waited)`；
     - `Math.round`、`Math.ceil` 都多 1；
     - 从 `decidedAt` 起算得到 0 附近。
   - 没开 `profileTimeouts`，不读采样，`:329` 不跑。
   - 定时器（`setTimeout`、`setImmediate`）走 Node 内部的时钟，不读全局的 `performance.now`，所以换掉它不影响 50 毫秒的期限。

## 8. 与默认不同的

1. **这不是放宽。**
