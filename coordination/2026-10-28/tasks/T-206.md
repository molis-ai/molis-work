## 1. 背景

- Workflows 的流程是一串站点，站点之间有交接。交接有四种：人填（manual）、固定规则（function）、模型（ai）、判断规则（judgment）。每个交接（`WorkflowLink`）都带三段文字：标题模板 `title_template`、正文模板 `body_template`、说明 `instructions`。固定规则用前两段，把交过来的内容填进去；模型交接把说明当作要求；另外两种也保留着这三段，切回去时恢复（`model.ts:274` 的注释）。动作步骤把交过来的内容映射进另一个动作的输入字段，挑字段时编辑器显示每个字段的名字，名字取自那个动作的输入 schema 里这个字段的 `title`，没有 `title` 就取 `description`。
- 单位：JavaScript 字符串的 `.length` 和 `.slice` 按 UTF-16 单元数。😀 是两个单元（高代理 `\ud83d`、低代理 `\ude00`），算一个字；`"尾"` 这类 BMP 字一个单元一个字。截点落在 😀 当中，留下孤立的高代理。T-189 已经把同一个包里另外十一处同类问题改成按字（它的第 1 节有半个字存下来的样子：存进 JSON 的保留 `\ud83d` 转义，`JSON.parse` 还原成孤立代理，输出成 UTF-8 时变成 U+FFFD）。
- 本单两处，位置、切的是什么、去哪、半个字会怎样：

| 位置（main `0c7fdcc7c`） | 切的是什么 | 单位与上限 | 存在哪、谁看到 | 半个字会怎样 |
| --- | --- | --- | --- | --- |
| `model.ts:273` `parseLink` 里的 `text()`，由 `:279` 调用 | 标题模板 `title_template` | 单元，400 | 流程的链（`store.ts:210` 存成 `JSON.stringify`，读回来 `JSON.parse`）；编辑器的输入框（`browser/link.ts:22`）；交接记录里的 `rule`（`handoff.ts:89`）；固定规则填出的交接标题（`model.ts:353` 先填模板再截 200）；搜索内容（`search.ts:16`） | 模板以半个字结尾，一路带到记录和下一站的标题 |

- 这两处的上限没有别处替它们把关：`actions.ts:67` 的 `chain` 只写了 `stations` 最多 12 站，没有模板的长度；字段名来自别的插件的动作定义，长度由那个插件说了算（`description` 常是一整句话，超过 120 的机会比 `title` 大）。所以 `text()` 和 `fieldsOf` 里的这个截取就是唯一的上限。

## 2. 目标

1. 流程里每段交接的三段文字是整字：标题模板至多 400 个字，正文模板至多 8000 个字，说明至多 4000 个字；存下来、从库里读回来同样；

3. 放得下的一字不差：400、8000、4000 个 😀 的三段文字原样保留，多一个字就截掉那一个；120 个 😀 的字段名原样保留，多一个字就截掉；不是字符串的模板仍是空串，短模板的空白不动；没有 `title` 也没有 `description` 的字段仍没有名字，有 `title` 的字段不用 `description`；

### 5.1 源码，两处

每一处都是一行换一行，缩进不变，在文件里只出现一次。改完用 `git diff --stat` 看：2 个文件，2 行加、2 行减。

**1. `model.ts:273`**（两个空格缩进；`parseLink` 里，`:279`、`:280`、`:281` 三个字段都经过它）

原：

```ts
  const text = (field: unknown, max: number) => typeof field === "string" ? field.slice(0, max) : "";
```

新：

```ts
  const text = (field: unknown, max: number) => typeof field === "string" ? [...field].slice(0, max).join("") : "";
```

**2. `step-runner.ts:40`**（四个空格缩进；`fieldsOf` 里，这一行很长，只换中间那一段，行尾的 `,` 和前面的内容都不动）

原：

```ts
    return { name, type, required: required.includes(name), ...(typeof property?.title === "string" || typeof property?.description === "string" ? { title: String(typeof property.title === "string" ? property.title : property.description).slice(0, 120) } : {}),
```

新：

```ts
    return { name, type, required: required.includes(name), ...(typeof property?.title === "string" || typeof property?.description === "string" ? { title: [...String(typeof property.title === "string" ? property.title : property.description)].slice(0, 120).join("") } : {}),
```

说明：
- `.slice(0, n)` 变成先展开成字数组、取前 n 个字、再合回去，结果就是「前 n 个字」。一个两单元的字不会被拆开；
- `model.ts:273` 里 `field` 在同一个三元式里已经判过 `typeof field === "string"`，展开的类型是字符串，`tsc` 不会报；`max` 仍是传进来的 400、8000、4000，三个调用行（`:279`、`:280`、`:281`）一个字不动；
- `step-runner.ts:40` 里 `String(…)` 先把 `title` 或 `description` 变成字符串，再展开；`title` 优先、没有才用 `description` 的判断一个字不动；
- 改完以后包里剩下的按单元截的地方就是第 3 节写的那几处，用这条命令核对（应当只剩 `model.ts` 的 `:56`、`:276`、`:345`、`:367`，共 4 行，`step-runner.ts` 一行都不剩）：

  ```bash
  git grep -n -F '.slice(0, ' -- plugins/native/workflows/src | grep -v -F 'join("")' | cut -c1-110
  ```

test("RAC-1965 a template that fits is kept as it was, and one character over its limit is cut", () => {

为什么成立，期望值手算（写进【方案】，PR 里也写）：

- 记号：`over(x, n)` 是 `x` 重复 n−1 次，加一个 😀，再加 10 个 `"尾"`，共 n+10 个字、n+11 个单元，第 n 个字是 😀；`kept(x, n)` 是 `x` 重复 n−1 次加一个 😀，共 n 个字、n+1 个单元，就是按字截到 n 个字的结果。按单元截到 n：取单元 0 到 n−1，就是 n−1 个 `x` 加 😀 的高代理，结果以 `\ud83d` 结尾；
- **RAC-1964**：
  - 一个固定规则的交接，三段文字都超长：标题模板 `over("t", 400)`（399 个 `t`、😀、10 个 `尾`，共 410 个字），正文模板 `over("b", 8000)`，说明 `over("i", 4000)`。改前 `text()` 按单元取：399 个 `t` 加 `\ud83d`，7999 个 `b` 加 `\ud83d`，3999 个 `i` 加 `\ud83d`；改后展开成字、取前 400、8000、4000 个字，得 `kept("t", 400)`、`kept("b", 8000)`、`kept("i", 4000)`；
  - `w.create` 先答一遍（`saved`，三句断言），再用 `w.get` 从库里读一遍（`read`，三句断言）：存进 `chain_json` 的就是整字；
  - 流程只有两站（`feed`、`pages`）和一个交接，第一站是能挑内容的插件，第二站能接收内容，所以不触发「第一站要选能挑出内容的插件」「只能作为第一站」两种拒绝；
- **RAC-1965**（纯函数 `parseChain`，不起库）：
  - 400、8000、4000 个 😀 分别是 800、16000、8000 个单元：改前按单元取，只剩一半（200、4000、2000 个 😀）；改后原样；
  - 各多一个 😀（401、8001、4001 个）：改后多的那一个被截掉，三段正好是 400、8000、4000 个 😀，与上一句的 `full` 相同；
  - 标题模板是数字 `5`、正文模板是 `null`：不是字符串，`text()` 给空串；说明 `" 把这条 整理一下 "` 不到上限，原样（包括前后的空格，`text()` 不去空白）；这一句改前改后都绿，守的是正常路径；
- **RAC-1966**：
  - 字段 `named` 有 `title: over("t", 120)`（119 个 `t`、😀、10 个 `尾`）和一个短的 `description`：`title` 优先，期望 `kept("t", 120)`；改前取 120 个单元，得 119 个 `t` 加 `\ud83d`；
  - 字段 `described` 只有 `description: over("d", 120)`：用 `description`，期望 `kept("d", 120)`；

- **RAC-1967**：
  - 120 个 😀 的 `title` 是 240 个单元：改前被截成 60 个 😀，改后 120 个原样（`exact`）；
  - 121 个 😀 的 `title`（`longer`）和 121 个 😀 的 `description`（`described`）：改后都是 120 个 😀；
  - `title: "标题"` 加一个 `description`：用 `title`，得 `"标题"`；这一句改前改后都绿；
  - 既没有 `title` 也没有 `description` 的字段（`bare`）没有名字：`fieldsOf` 里 `...(… ? { title } : {})` 不加 `title` 键，所以是 `undefined`；这一句改前改后都绿；
- 写法都有先例：真实处理器、真实库、假的内容站点，以及 `call` 的写法，照 `tests/workflows-stop-and-token.test.ts:11-47` 和 T-189 的 `setup()`；`openWorkflowsStore` 来自 `tests/fixtures/plugin-home-stores.ts:77-80`。这里的假动作只有一个（`ticket`），`discover` 只返回它：T-189 的 `setup()` 里还有一个只写了 `action: {}` 的假判断规则，`w.actionSteps` 会在它身上抛 `TypeError`（`view.action.audiences` 是 `undefined`），所以不要把它抄进来。

## 8. 与默认不同的

1. **两处截取用 T-079、T-189 的原样写法，不先截一段再展开。**
   - 原样写法要把整个字符串展开成数组。`text()` 的输入是人写的模板，至多几千个字；字段名是别的插件的一句话，几十到几百个字；独立脚本量过，10 MB 的字符串展开约 0.46 秒（T-189 第 8 节）；
   - 等价的有界写法：先 `slice(0, 2 * n)` 再展开，如 `[...field.slice(0, 2 * max)].slice(0, max).join("")`。2n 个单元里至少有 n 个字，所以结果与不先截完全一样；T-181 的 `material-text.ts` 就这样写；
   - 选原样写法的理由：与 T-079、T-189 已合入的写法一致，输入一般不大，用例和变异都更直白。统筹觉得 `text()` 要有界写法（`chain` 的模板没有长度限制，一个很大的请求会让它展开很大的数组），在【方案】里说，只改第 5.1 节的第 1 条，别的不动，用例不变。
