# T-037 关闭项目插件时，Runtime 读不到某个插件的记录，不再跳过它的撤销和排在它后面的插件

> **这条在 main 上成立，但生产里正常用到不了；是一处防御性的收口，不是线上故障。** 项目内置插件的关闭循环把 `platform.runtime.get(...)` 放在 `try` 外（`apps/local-host/src/project-plugins.ts:97`）：Runtime 给不出记录时 `get` 抛 `plugin.definition_missing`（`packages/plugin-runtime/src/runtime-rules.ts:81-85`），这一轮的 `revoke`（`:100`）和后面所有插件的停止与撤销都不做，整个函数以原始错误失败。这是 T-035 起草时登记的「同类的另一个小洞」。起草时没有跑任何东西，下面全是读 main 的代码；标「推断」的是读出来、没有验证的。

## 1. 背景

依据都在 main `f93c1409a`：

- 循环：`project-plugins.ts:89-103`（`stopProjectPlugins`）。对 `supervisor.enabledPluginIds()`（按插件 id 排序，`supervisor.ts:325-329`）里每个插件，Supervisor 状态是 `running` 且有 `install_id`、并且 Runtime 记录是 `running`，才带 `preserve_enabled` 停（`:97-98`，注释 `:94-96`：项目关闭不是把插件关掉，停完记录仍是启用的）；停的抛错收进 `failures`；`revoke` 每个都做（`:100`）；最后抛 `AggregateError("项目插件停止失败")`（`:102`）。守卫里的第三个条件 `platform.runtime.get(active.install_id).state === "running"` 是为 Supervisor 的内存镜像可能落后于 Runtime 记录加的（例如记录已是 `uninstalled`、`disabled`、`crashed`），读在 `try` 外。
- `get` 的抛法：`PluginRuntime.get` 直接是 `requireInstall`（`packages/plugin-runtime/src/index.ts:670-672`），记录读不到就抛 `plugin.definition_missing`（`runtime-rules.ts:81-85`）。Supervisor 自己的 `revoke` 对同一个读已经设防：包在 `try`，读不到按「不在跑」处理（`supervisor.ts:286-292`）。
- 调用方怎么处理这次抛出：`releaseProjectPlugins`（`:77-87`）在调 `stopProjectPlugins` 之前已经把这个项目从 `started` 里删掉、通知已释放、停了观察者（`:81-84`），平台没有人再拿着，剩下的插件没有第二次机会被停。它的调用方 `closeProjectRuntime`（`project-host.ts:432-442`）用 `attempt` 收集每一步的失败，后面的 `store.close()` 和 `closed()` 照做，最后把失败抛出去；所以项目库关得掉、Host 也把项目忘掉（`local-host-project-line.ts:217-221`），代价是：出错插件之后的所有插件没有停（它们的停止钩子没跑，记录仍写着 `running`）、没有撤销（提供方还登记着），而库在它们脚下被关了。另一个调用方是 `startPlatform` 启动失败后的清理（`:173-181`），同样会少清理。
- 能不能真的发生：**生产里的代码路径上，我没有找到会删这条记录的地方**（读过 `apps packages plugins horizontal modules server`，推断）。仓库接口只有 `get`、`list`、`save`（`packages/plugin-runtime/src/repository.ts:29-45`，Host 用的包装 `apps/local-host/src/plugin-install-records.ts:10-16` 也一样）；卸载是把记录改成 `uninstalled` 留着（`index.ts:632-668`，`:655-659`）；删除项目是先关项目、再删库文件（`apps/local-host/src/project-deletion-service.ts:37`，端口 `:56-59`）。会让这一读抛的只剩：库被人在外面改过、`record_json` 坏了（抛的是 `SyntaxError`，不是 `definition_missing`，但同样落在 `try` 外）、连接已经被提前关掉（抛 SQLite 的错）、以及测试直接删行（`tests/installed-plugin-host.test.ts:56` 就这样造「从没装过」）。所以收益是：关闭的健壮性，不是修一个用户碰得到的故障。
- 关闭失败的后果还有一层：项目删除先 `await closeProject`（`project-deletion-service.ts:37`），这次关闭 reject 会让第一次删除在 `catalog.deleteProject` 之前失败；重试时 Host 已把项目忘掉，`closeProject` 返回 `false`，能过（推断，没跑）。本任务不改「关闭会 reject」这一点，只让它别半途停。

为什么这样修（照 T-035 对 `installed-plugin-host.ts` 关闭循环的做法）：

- 把读挪进 `try`：读不到记录是这个插件的一次失败，收进 `failures`，`revoke` 照做、后面的插件照停；关闭最终仍以「项目插件停止失败」reject，这和一次真的停止失败一致。记录读不到时 Runtime 没法停这个插件在进程里的实例（`stopOnce` 同样先 `requireInstall`，`index.ts:493-494`），悄悄吞掉会把这个异常藏起来。
- 不取的做法：像 `supervisor.ts:287-291` 那样把读不到当成「不在跑」吞掉——要新写一个带语句的 `catch`，并且让关闭对这个异常无声。这条留给统筹，见第 11 节。

有没有东西依赖「关闭会半途中止」：`git grep` 整个仓库，`项目插件停止失败` 只在源码 `:102` 和 `tests/project-plugin-startup.test.ts:76`，那一例是「一次真的停止失败，其余照停」，修后仍是同样结果；`项目插件启动及清理失败` 只在源码 `:177`。

## 2. 目标

1. Supervisor 说在跑、Runtime 里这条记录却读不到的项目插件，关闭项目时：该插件的 `revoke` 照做，排在它后面的插件仍被停（记录写成 `installed`）和撤销，关闭以 `AggregateError("项目插件停止失败")` 失败，里面只有一个 `plugin.definition_missing`（`RAC-1453`）。
2. Runtime 记录已是 `crashed`、Supervisor 仍是 `running` 的插件，关闭时不再去停，关闭不因它失败，记录保持 `crashed`，其余照停（`RAC-1454`）。
3. 在跑的插件关闭时恰好停一次、带 `preserve_enabled`，记录写成 `installed`，重新打开后又是 `running`（`RAC-1455`）。
