# T-036 Linux CI 上浏览器用例的 `CDP timeout`：修 harness 里「回复已到、定时器抢先」的一处，并让失败说出 Node 在算什么

> **现象成立，但它不是 Linux CI 的底噪：有一类只出现在含 #1295（Goals 进 Plugin Runtime）的头上，先把范围收窄再动手。** 取到的 100 个 Full 运行（10-23 至 10-28）里，36 个分片以 `CDP timeout` 失败、共 65 次超时，分两类。甲类（10-25、10-26，8 个分片、19 次）：18 次是 `plugin-frame-browser.ts` 清理步骤里写死的 1 秒限期，#1295 已经把它删了，main 上没有了。乙类（10-27 07:41 起，28 个分片、10 次运行、46 次）：限期 10～32 秒，10 次运行的头全含 #1295；10-25 起取到的 59 次运行里，含它的 19 次中 10 次出现，不含它的 40 次一次也没有。乙类 46 次的 Node 数字形状一致：事件循环空闲最多占窗口的 0.7%，进程 CPU 是窗口的 0.93～1.12 倍（中位数 1.02）。也就是说，那 12～20 秒里是**测试进程自己的 Node 在满负荷算**：不是 Chrome 慢，也不是 runner 把 Node 饿住。BL-814（T-008，#1354，10-28 12:46 已合入）记的正是 Runtime 动作调用路径上同类的同步计算成本，是眼下最像的原因，但这是推断，没有日志把占用指到某个函数。harness 里能确定地修的只有 `cdp.ts:104-110` 一处竞态（到期的定时器排在已经到达的回复前面），能救多少没有数据；要真正弄清，得让失败说出 Node 在算什么。本任务做这两件事，不放宽任何期限和断言，不替产品里的 12 秒占满打掩护。

**2. 超时在 harness 的哪里。** `packages/test-kit/src/browser/cdp.ts`：`ChromeHarness.connect` 的默认期限 `20_000`（`:73`）；`command()`（`:98-111`）每发一条命令开一个 `setTimeout`，到期时 `pending.delete(id)`、写 `cause`、拒绝（`:104-110`）；`receive()`（`:162-174`）收到一条回复时，`pending` 里没有这个 id 就直接忽略（`:168-169`）。用例的期限在 `tests/fixtures/goal-browser.ts`：`commandTimeoutMs: 15_000`（`:103`，旁边 `:101-102` 的注释说 CI 比开发 Mac 慢约 2.5 倍，这些期限是防挂住、不是测速度）；`waitFor` 的页内期限是 `timeoutMs`（默认 10 秒），CDP 命令期限是 `timeoutMs + 2_000`（`:134-138`），所以 12 秒的那 27 次，是页面里的 `check()` 到 10 秒该拒绝的时候，回复 2 秒内也没回到 Node。宿主和 web 服务器就在这个测试进程里（`:94`），与 CDP 客户端共用一个事件循环。

**3. 数字说了什么、没说什么。** `eventLoopIdleMs` 是这段时间里 Node 事件循环在 epoll 里等的时间，`eventLoopActiveMs` 是在跑回调的时间，`nodeCpuMs` 是整个 Node 进程（含线程池）用掉的 CPU（`cdp.ts:103-107`；包 README `:38` 写明它们不是 Chrome 的 CPU，也不能单独当根因）。乙类 46 次里：空闲占比 0～0.7%，活跃占比 99.3% 以上，CPU 占比 0.93～1.12（中位数 1.02），没有一次 CPU 低于窗口的 90%。读法：这段时间 Node 一直有事做，也真的拿到了 CPU（所以不是被 runner 抢占饿住），做的是主线程或线程池上的真计算。超时比期限晚到的时间（`elapsed − limit`）中位数 427 ms，最大 6788 ms，另有 4 次超过 2 秒（`shelf-dropagent-parity` 三次 `DOM.describeNode`/`Runtime.evaluate`，`ui-audit-browser` 一次），说明有过连续数秒的同步阻塞，不全是许多小任务。**它没说**：Node 在算什么。这是最缺的一环。

**4. 线索与没排除。** 已排除：Chrome 版本（上表）；runner 之间互相抢（每个分片是独立虚拟机，`full-suite.yml:46`、`:59`；同一分片里最多 2 个文件同时跑、浏览器文件同时 1 个，`:65-66`，CPU≈窗口说明 Node 没被饿）。线索：乙类只出现在含 #1295 的头上（上表）。BL-814（`specs/BACKLOG.md:242`）记着同期量到的成本：Feed、Inbox 进 Runtime 后，`tests/inbox-automatic-scenes.test.ts` 第一条在 CI 上 34 s（run 40615370984），迁移前不到 9 s；一次收进 43 个动作目录、每个约 540 行，常开插件那一读每次检查都打开 Home 插件库验表结构（一次收进 88 次），安装记录每行现读现解析。T-008（#1354，10-28 12:46 合入，晚于 `c660f1709`）把重复的计算去掉一部分，本机上该用例的收进各步合计从约 16.8 s 降到约 10.3 s，所以还剩。这些都在宿主进程里同步跑，而宿主与 CDP 客户端共用一个事件循环（`goal-browser.ts:94`），所以「Node 满负荷 12 秒、CDP 回复读不到」与它吻合。**吻合不是因果**：没有任何日志把 12 秒占满指到某个函数；含 #1295 的头里还有别的改动。没排除：（H1）上面这条，Runtime 动作路径等宿主内的重计算（命中的用例集中在 Coding、Assistant、shelf 这些要进插件 iframe 的页面，`ui-audit-browser` 与 `product-interaction` 两例都是拆成两个插件 iframe 之后）；（H2）Chrome 向 Node 发来一大批 CDP 事件，`receive()` 对每一条都 `JSON.parse` 并复制监听表（`:162-166`），把循环占满；（H3）测试进程里别的服务（假模型、SSE、node:sqlite 同步查询）在跑。这三条我**没有数据**，都是推断。

**5. 「Linux 才会」是推断。** goal-browser.ts 自己的注释说同样的操作 CI 上慢约 2.5 倍（`:101-102`）；期限按这个定的。如果 Node 在 Mac 上也要算同样多的 CPU，只是 4 秒而不是 10 秒，那么 Mac 上不触发、CI 上触发就是这个比例造成的。我没有在 Mac 上量过，不下结论。

**6. 一处确定的竞态（推断，未跑）。** Node 的事件循环每一轮里，timers 阶段在 poll 阶段之前，check 阶段（`setImmediate`）在 poll 之后（[Node 文档：事件循环](https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick)；一轮从哪个阶段进入、哪一轮的 timers 先到，要看循环被阻塞时停在哪里，这里只用「同一轮 timers 先于 poll」这一条）。Node 被占了几秒之后，回复可能已经躺在 socket 里，但这一轮先执行到期的定时器回调：`pending.delete(id)`、拒绝；随后 poll 读到回复，`receive()` 发现 `pending` 里没有它，丢掉（`cdp.ts:168-169`）。这样回复可能已经到了进程，命令仍按超时失败。A 的改法是在定时器回调里让到 check 阶段，给 poll 一次处理机会。这只是一次机会：现在的接口不知道回复到达 socket 的时刻，让出那一轮里才到的回复也会被收下。本单接受这个语义，不承诺能分辨「期限前已到达」。它不放宽任何期限，最多多一轮事件循环。能救下表里多少，没有数据（回复到没到，现有日志看不出来）；表里 `elapsed − limit` 大的几行（4.8～6.8 秒）最可能是这一类。

**7. 相邻、不在本单、要统筹知道的。**

**8. 口径是下限，以及我读的样本。** 一、前面数的是「整个分片作业失败」的日志；一个文件第一次 CDP 超时、重试通过、分片全绿的情形，不在那 265 个里。二、`--bail`（main 和 `task/*`，`full-suite.yml:135`）下，`pool.mjs:133-140` 的 `runFile` 在重试通过时只返回第二次的结果，第一次失败的输出不打印；日志里只剩 `[retry 1] ok  <文件>` 一行和结尾的「flaky」列表，看不出第一次是什么错。我读了 main 夜间与 T-019 的 95 份可读分片日志（另有 22 份已过期），0 处 `CDP timeout`，但有 5 个文件靠重试才通过（`inbox-current` 3、`stream-text` 1、`ui-audit-browser` 1），原因读不到。所以 main 与 `task/*` 上「没有」不是证据；上表里分支之间能比的只有不加 `--bail` 的承载分支。

## 2. 目标

1. 定时器到期后让出的那一轮里，一条命令的回复已经能读到，就按回复结算，不按超时失败（`RAC-1450`）。不承诺分辨回复是不是在期限前到的（第 1 节第 6 点）。
2. 超时的错误里带两样新东西：这段时间 Chrome 发来多少条消息、哪几种方法最多；以及【方案】批准的话，Node 主线程这段时间花在哪几个函数上。下一次出现，不用再猜 Node 在算什么（`RAC-1451`）。
3. 期限、默认值、消息格式、调用栈都不变，没有回复的命令仍在原期限判定超时（最多多一轮事件循环），也不多发任何 CDP 请求（`RAC-1452`）。判定之后、拒绝之前，B2 打开时只允许等一次有界的采样读取（`Profiler.stop`）：上限 150 ms，读不完就不带采样、标 `nodeSelfTimeComplete: false`，照原名、原因、格式拒绝；判定之后才到的回复照样丢掉，读的这段时间里 `close()` 停掉读取、照样拒绝。消息里的 `elapsed` 是到拒绝时的真实耗时，诊断里另记这次读取等了多久，减得出定时器本身晚了多少。B2 关着时没有这段等待。（统筹 10-28 答 T-036 的【问统筹】6473736122，选 B：B2 存在就是为了看窗口里的采样，判定已经失败的命令多等不到 150 ms 不改期限；整体仍在 `RAC-1452` 原有的 `limit + 250` ms 之内）这几种情形也照现在的语义：超时之后才到的回复照样丢掉；超时之后的下一条命令照常；连接意外断开时在途命令照现在的方式失败；让出的那一轮里调用方主动 `close()`，`pending` 照现在一样丢弃、不结算，不改成拒绝（`cdp.ts:176-185`）。
4. 在最终 head 上排两次 Full（头要含 #1295 与 #1354，main 现在就是），把第 1 节同口径的数写进【交接】，与现状对照；一次乙类也没出现就照实写，不当成已经修好。

## 6. 验收

1. `RAC-1450`：假 DevTools 回复后在同一个回调里把线程阻塞超过期限（`commandTimeoutMs: 50`，阻塞约 150 ms）；这条命令以回复的结果成功，不抛 `CDP timeout`。同进程里 `socket.write` 之后阻塞，不能静态证明回复已到客户端一侧，所以同一个用例要走完三步：没改时红、改后绿、把让出的一轮撤掉再红（第 5 节第 5 步），三次的输出都贴进【交接】。
2. `RAC-1451`：命令没有回复、期间假 DevTools 推来 200 条事件（同一方法）；超时错误的新属性里条数不少于 200、第一名是这个方法；`cause` 仍是原来的三个键、消息格式仍是 `CDP timeout: <方法> (elapsed Nms; limit Mms)`。【方案】批了 B2 的话，另一个用例在窗口里跑一个有名字的忙函数（约 200 ms），采样摘要里能看到这个名字；同一个用例里再放一个哨兵：忙函数所在脚本的 `sourceURL` 带一段查询串哨兵（如 `?token=SENTINEL-T036`），错误的消息、`cause` 和新属性序列化后都不含这段哨兵。
3. `RAC-1452`：没有回复的命令在 `limit` 到 `limit + 250` ms 之间失败，B2 打开时也一样（含采样读取的等待）；`Profiler.stop` 挂起或慢于上限时，命令仍在这个区间里拒绝，诊断标不完整（能不加新接缝造出来就加一处断言，造不出就在 PR 里写明怎样复现的）；这期间假 DevTools 收到的请求数等于测试自己发的条数（没有诊断请求）；`ChromeHarness.connect` 不带选项时命令期限仍是 20 秒（读 `commandTimeoutMs`）。第 2 节第 3 条的四种情形各有一处断言：超时后才到的回复被丢掉、不改变已经抛出的错误；超时后的下一条命令成功；假 DevTools 断开时在途命令照现在的方式失败；让出的那一轮里 `close()`，那条命令不结算（用一个短的等待确认它既没 resolve 也没 reject）。
