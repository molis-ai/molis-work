# 桌面标题栏、Light 标签与密集关系图回归修复

## 背景与目标

桌面端收起左侧目录后，布局仍保留一条由原生窗口安全区和展开按钮组成的整高侧栏。该区域继续使用目录灰底，导致正文画布没有真正铺满窗口，正文也只在剩余宽度中居中。

Light 模式的工作标签全部使用透明背景；虽然选中项有底部标记，但相邻标签缺少可见边界，长标题并排时容易连成一行。

本任务达到 Level 3「功能可用」：收起目录后内容画布占满窗口可用宽度并以整窗为基准居中；Light 标签之间具有清晰、克制的结构分隔；所有桌面页面使用同一套 Codex 式两层左侧标题区，不再把项目名称塞进 macOS 交通灯所在的一行。

真实 macOS App 的后续检查又暴露出两项回归：展开目录时项目选择器进入了原生红黄绿按钮安全区；Footballnia 的 251 个 Goal / 915 条 `depends_on` 在推进态势中形成大量跨空白、上下折返和重叠的连线。两项问题都必须在真实安装态验证，不能只依赖带 `desktop=1` 的浏览器模拟。

用户再次验收后调整了方向：左侧改为 Codex 式两层标题区。第一层只承载 macOS 交通灯安全区、目录展开/收起按钮和拖动区；第二层在交通灯下方完整展示项目选择器，通知占位与设置固定在项目行最右侧。右侧工作标签继续位于第一层，正文或上下文从第二层开始。这个结构必须由主工作台与设置页共享，不能继续用页面级偏移补丁。

## 当前行为与证据

- 收起态网格第一列为 `max(44px, safe-inline-start + 44px)`，原生窗口中约为 132px，并贯穿整个页面高度。
- 收起态目录面板仍保持目录灰色背景，只隐藏内部内容。
- Light 工作标签为透明背景、无边框，仅依赖间距和选中标签的 2px 底线。
- 真实 `/Applications/Molis Work.app` 截图中，项目图标和 `Footballnia` 文字从窗口左缘开始，和三个原生交通灯重合；当前安装态没有呈现应有的 88px 原生安全区。
- 当前密集拓扑按每个层级内部的标题顺序独立分配行号，没有使用相邻层依赖关系做对齐。251 个节点、915 条边、29 个层级下，同一条依赖的两个端点经常相隔大量行，边只能跨越空白区域并长距离折返。
- 最新 Footballnia 真实数据复测为 253 个当前 Goal、917 条 active `depends_on`、29 个层级。现有重心排序只改变列内顺序，仍把每列从第 0 行开始紧排；不同列节点数量不同时，相同的归一化位置会落在不同绝对行。结果有 59 条边跨越至少 10 行、最长跨 27 行，截图中出现了卡片区下方的大块空白、零散箭头与超长折线。
- 普通边保持接近半透明可见，且所有箭头共用灰色 marker；选中路径虽然变蓝，箭头仍是灰色，进一步削弱了端点归属。
- 主工作台、目录收起态、项目设置和全局/规划设置页混用 48px、43px、34px、30px、28px 五套高度；更根本的问题是项目选择、目录开关和交通灯被挤在同一行，长项目名只能被截断或覆盖。
- 最新原生截图按 Retina 比例复核后，项目选择、通知和设置的第二层内部已经同轴；真正的偏差位于第一层。目录按钮与右侧工作标签使用 WebView 的 24px 中线，而交通灯使用约 16px 中线，稳定相差 8 CSS px。这个偏差必须由原生壳层统一校准，不能只移动左侧按钮，否则又会破坏它与右侧标签的对齐。

## 范围

- 桌面宽度（`min-width: 761px`）下，收起目录时将主工作区网格扩展到整窗宽度。
- 将原生窗口安全区与目录展开按钮限制在标题栏覆盖层，不再形成整高侧栏。
- 工作台标题栏为窗口控制和展开按钮保留安全内边距，避免与原生交通灯重叠。
- Light 模式为相邻工作标签增加细分隔线，并保留现有选中底线和轻量 hover。
- 原生展开态和收起态都使用同一份、可由服务端 Desktop 标识直接触发的交通灯安全区；客户端 Tauri 自识别继续作为导航丢参时的兜底。
- 密集拓扑保留全部 Goal、全部 active `depends_on`、固定拓扑层级和双向滚动，不以隐藏数据换取整洁；同一分组内的层级节点通过依赖重心迭代排序，减少交叉与无意义的垂直跨度。
- 每个分组建立跨层共享的绝对行坐标：节点较少的层允许留出空槽来贴近其真实提供者/消费者，不能再把每列独立压到顶部。行分配必须保持同列节点不重叠，并以总依赖垂直跨度为优化目标。
- 普通关系边退为背景层；当前选择的一阶边、路径和箭头使用同一强调色。
- 建立唯一桌面标题区契约：每层轨道固定 48px、交互控件统一 34px。第一层只放目录开关与右侧工作标签；第二层放项目选择器、通知占位和设置。项目选择器不再消费交通灯安全区，可使用左栏完整宽度。
- 通知按钮仅作为可见占位，标明暂不可用，不接入事件、数据或未读状态。
- 将契约同时应用于主工作台（Inbox、Goals、Sessions、工作目录、Feed、来源）、Goal/Runtime 详情、关系图、目录收起态、项目设置、全局设置与规划方法页；设置页没有目录收起行为，但必须复用相同的第二层项目行。
- 更新样式回归测试。

## 非目标

- 不改变目录展开状态、持久化逻辑或键盘语义。
- 不改变目录展开态、窄屏 Companion、Dark 标签样式或标签数量上限。
- 不调整 Goal 正文自身的最大宽度、内容顺序或 Runtime 行为。
- 不改变 Goal/Relation 数据、拓扑层级、依赖方向、行动队列、全部/未完成过滤或缩放语义。
- 不引入图编辑、Canvas、虚拟化、自动写回布局或只显示局部关系的第二套图模式。
- 不实现通知中心、通知数据、未读数量、点击行为或偏好设置。

## 方案与模块边界

- `src/web/visual-foundation.ts`：维护唯一的 48px 原生控制行、48px 项目行和 34px 控件尺寸；所有桌面页面消费同一结构与尺寸，同时保留收起态网格、标题栏覆盖层和 Light 工作标签分隔样式。
- `src/web/desktop-shell.ts` / `src/web/render.ts`：用一个共享渲染结构生成原生控制行与项目行；保证 Tauri 安全区和原生垂直校准只作用于第一层，目录按钮、右侧工作标签、项目列表标题栏和设置标题栏消费同一偏移；关系图选择时继续同步路径与箭头状态。
- `src/web/icons.ts`：提供通知占位所需的 Bell 图标。
- `src/web/goal-momentum.ts`：在不改变拓扑事实的前提下，用确定性的依赖重心和无碰撞绝对行分配共同决定节点位置；不同密度的相邻层使用同一行坐标。
- `tests/visual-foundation.test.ts`：验证收起态全宽画布、安全区留白和 Light 标签分隔契约。
- `tests/goal-momentum.test.ts`：验证密集、多前置 DAG 的节点行序能减少交叉且结果稳定。
- `tests/web.test.ts`：更新收起态、原生安全区和选中箭头结构断言。

## 验收标准

1. 收起目录后，工作区网格不再保留整高的目录宽度，正文区域从窗口左缘开始并使用整窗宽度。
2. 原生窗口交通灯与目录展开按钮仍可见、可点击，不与标签重叠。
3. 正文内容以完整工作区宽度为基准居中，不因收起目录产生右偏。
4. Light 模式每个相邻标签之间都有清晰细分隔，选中标签仍使用 2px 蓝色底线。
5. Dark 模式、目录展开态和 760px 以下窄屏结构保持不变。
6. 页面不存在新增横向溢出。
7. 真实 macOS App 展开目录时，项目选择器位于交通灯下一行并能使用左栏完整宽度；目录按钮位于第一行交通灯右侧；收起时只保留第一行目录按钮且不覆盖工作标签。
8. 关系图仍完整包含所有 Goal 与 active `depends_on`，层级和提供者 → 消费者方向不变。
9. 同组相邻层的节点顺序优先跟随依赖重心；代表性密集 DAG 的连线交叉数和垂直跨度不高于旧的逐层标题排序。
10. 普通关系边不会压过节点内容；当前一阶关系的线和箭头颜色一致，缩放、滚动或调整目录宽度后端点仍贴合节点边缘。
11. 第一层目录按钮与右侧工作标签的边界框垂直中心差不超过 1px；第二层项目选择器、通知与设置的边界框垂直中心差不超过 1px；控件点击区统一为 34px 高。
12. 项目名称在第二层获得除通知与设置外的全部可用宽度，长项目名使用单行省略，不再被交通灯或其他按钮覆盖。
13. 通知占位位于设置左侧，具有明确的“暂不可用”可访问说明，不产生任何状态变更。
14. Inbox、Goals 列表、Goals 关系图、Sessions、工作目录、Feed、来源、Goal 详情、Runtime、项目设置、全局设置和规划方法页面都使用同一两层标题区；设置页复用同一项目行。
15. 原生 macOS App 的截图验收必须同时覆盖展开/收起、主工作台/关系图/设置页；不能只凭浏览器计算样式宣称对齐。
16. 原生 macOS 窗口中，第一层目录按钮、右侧工作标签以及设置/项目列表的第一层操作与交通灯中线差不超过 1 CSS px；第二层项目行不跟随该原生偏移，避免再次产生上下漂移。
17. Footballnia 当前完整数据中，关系边的平均垂直跨度、P90 与最长跨度必须显著低于旧布局；不存在因为列内独立紧排而产生的卡片区外超长折线。抽样选中顶端、中段、底端节点时，一阶关系线均从节点边缘出发并进入目标节点边缘。

## 假设与开放问题

- “白色平铺过来”理解为收起目录后正文画布真正占用整窗宽度，而不只是把原灰栏改成白色。
- “其他内容居中”理解为正文按完整工作区重新计算居中，不改变正文组件自身的宽度规则。
- “按照 Codex”以用户提供的截图为准：目录开关紧邻交通灯安全区的右侧，项目选择器位于其下一行；因为交通灯左侧没有可用窗口空间，不将目录开关放到交通灯物理左侧。
- 当前没有阻塞实现的开放问题。
