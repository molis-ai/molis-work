# 设置目录与规划方法体验

## 完成等级

内部完整：Web 与 Desktop 共用的设置页具备稳定的信息架构；规划方法库与项目工作规划职责分离，方法可以被普通用户理解、查看、调整和保存，现有方法包数据与 API 保持兼容。

## 背景与问题

- 全局设置使用“项目 / AI 与执行工具 / 诊断”，项目设置改用“工作规则 / 规划方法 / Goal Tree”。进入规划方法后整套目录跳变，用户无法判断自己仍在同一套设置中。
- 全局设置曾通过 URL 保留上一次打开的项目，并在侧栏常驻“当前项目”。这让全局设置看起来像在配置某个项目，却没有明确的项目选择动作，也无法自然切换到其他项目。
- Goal Tree 是返回工作区的动作，不是设置项；把它放进设置目录混淆了导航和操作。
- 规划方法直接暴露 `Method ID`、`area | label | question`、`consumer depends_on provider` 等内部格式。用户看不出方法解决什么问题、各字段如何影响 Runtime，也不知道怎样填写。
- 页面默认展示一份巨大的空表单，内置方法之间缺少分类和选择线索；“可配置”没有形成可理解的用户路径。
- 第一版改造仍把方法库和编辑器塞进左右双栏，导致模板、详情和编辑互相挤压；编辑器还要求用户在没有明确项目语境的页面选择“保存到当前项目”，产品对象与保存范围不一致。
- 当前全局方法库在没有项目查询参数时直接省略设置导航，只留下空白左栏；项目“工作规划”的方法卡链接也会丢弃项目上下文，进入详情并返回后同样失去一级目录。

## 目标

1. 全局设置只展示全局项；项目配置必须先从项目设置列表明确选择项目，不能沿用隐藏的“当前项目”上下文。
2. Goal Tree 仅作为顶部“返回工作区”动作，不出现在设置目录中。
3. 规划方法以用户任务为起点：卡片浏览方法库，每个方法进入独立详情页，编辑时使用结构化条目而不是内部文本格式。
4. 保持现有方法包 schema、分层覆盖规则、保存 API 与 Runtime 消费逻辑不变。
5. 全局方法与项目工作规划明确分层：全局页面只保存个人方法；用户从项目设置列表明确选中项目后，才进入该项目的工作规则或工作规划。

## 方案

### 统一设置目录

- 全局：项目设置、AI 与执行工具、诊断、规划方法。
- 设置侧栏不展示“当前项目”，也不通过查询参数把上一次打开的项目带进全局设置。
- “项目设置”页面展示全部项目。每个项目提供“工作规则”“工作规划”和“打开 Goal Tree”，用户先选项目，再进入对应配置。
- 选中项目后进入独立的项目设置空间：侧栏明确展示项目名称，只保留“工作规则 / 工作规划”，并提供“返回所有项目”。全局设置目录不得继续出现在项目设置空间里。
- 项目专用页面必须明确展示项目名称，并保留返回项目设置列表的路径；不得猜测默认项目。
- Desktop 与 Web 使用同一导航渲染函数；Desktop 的顶部返回动作继续保留 `desktop=1` 行为。

### 规划方法用户路径

1. `/settings/planning` 是全局方法库。页面用卡片展示方法的用途、适用场景、类型与内容规模，不再同时承载详情和编辑器。
2. 方法库按“全部 / 工作类型 / 专业领域 / 我的方法”筛选；点击卡片进入该方法的独立详情 URL。
3. 独立详情页以普通语言完整展示：规划路径、必须回答的问题、依赖判断、完成证据和常见误拆。内置方法提供“创建我的版本”，个人方法提供“编辑”。
4. 新建与编辑使用独立全页表单。步骤、必须回答的问题和依赖判断均为可增删的结构化条目，不要求用户输入 `|`、内部 ID 或英文依赖表达。
5. 全局方法编辑页固定保存到“我的方法库”，不出现项目范围选择；内置模板保持不变，保存后形成个人版本。
6. `/projects/:project/settings/planning` 改为“工作规划”，明确展示项目名称、全局可用方法数量和项目专用方法。只有这里进入的编辑页固定保存到当前项目。
7. 方法类型、领域标签、来源和可信度放入“高级设置”；Method ID 由系统生成或以隐藏字段保留，不作为普通设置项。

### 项目快速选用已有方法

1. 项目“工作规划”首先提供“从已有方法开始”，展示当前可用的内置方法与个人方法；用户无需从空白新建。
2. 每套方法同时展示用途、适用工作和来源范围，并提供简洁的“选用”操作。该操作只会出现在已经选定项目的“工作规划”中。
3. 选用已有方法会以相同 `method_id` 创建项目版本，沿用现有 `项目 > 个人 > 内置` 覆盖规则；不会修改原模板，也不引入第二套选择状态。
4. 保存成功后刷新为项目版本，并出现在“项目专用方法”中；用户可继续进入独立详情和编辑页调整。
5. 未选用任何方法仍是合法的零配置状态：Runtime 继续按任务类型和领域使用全局有效方法。

## 非目标

- 不改变方法包数据结构、覆盖优先级、MCP 协议或规划引擎行为。
- 不新增自动调用模型、方法市场、推荐算法、项目方法选择算法或自动改写 Goal Tree。
- 不重做项目管理、诊断或 Runtime 接入功能。
- 不引入新的前端框架或第二套 Desktop UI。

## 影响模块

- `src/web/render.ts`：统一设置导航、规划方法信息架构、表单和客户端序列化。
- `src/web/server.ts`：在全局设置路由中解析并验证可选的项目上下文。
- `src/web/i18n.ts`：新增中英文界面文案。
- `tests/web.test.ts`、`tests/i18n.test.ts`：导航稳定性、表单结构与翻译覆盖。

## 验收标准

1. 全局设置侧栏只显示全局项，不显示或暗示“当前项目”。
2. 设置目录中没有 Goal Tree；顶部始终有明确的项目列表或 Goal Tree 返回动作。
3. 项目设置页展示所有项目；每个项目都能独立进入工作规则和工作规划，返回后仍能选择其他项目。
4. 方法库首屏以卡片展示方法；卡片点击后进入独立详情页，页面不存在双栏编辑器。
5. 用户无需理解内部 ID、分隔符或英文依赖方向，就能通过结构化条目调整并提交合法方法包。
6. 全局详情页只保存个人方法；项目专用方法只能从明确显示项目名称的工作规划页创建或编辑。
7. Light、Dark、Desktop 和窄宽度下目录与规划页可读，交互不会触发意外滚动。
8. 项目工作规划可以一键把已有方法保存为项目版本；原方法不变，重复选用不会产生第二条同 ID 项目方法。
9. 现有规划引擎、Web、Desktop 与 i18n 测试通过。
10. 项目工作规则、工作规划及其项目方法详情/编辑页使用同一套项目设置侧栏；侧栏显示项目名称、“返回所有项目”“工作规则”“工作规划”，且不出现全局设置、AI 与执行工具、诊断或全局规划方法入口。
11. 方法库、方法详情、新建和编辑页始终保留一级设置目录：从项目“工作规划”进入时保持项目设置目录和项目上下文；直接进入全局方法库时显示全局设置目录，并把“规划方法”标为当前位置，不再出现空白左栏。

## 验证

```bash
pnpm typecheck
node --import tsx --test tests/web.test.ts tests/i18n.test.ts tests/planning-engine.test.ts tests/desktop-tui.test.ts
pnpm build
git diff --check
```

手动检查：在 Desktop Dark 和 Web Light 下从“项目设置”选择一个项目，确认进入独立项目设置侧栏；在工作规则与工作规划间切换并返回所有项目。选择软件开发模板，修改一条拆分步骤、一条必答问题和一条依赖判断，确认保存后重新打开仍可读。
