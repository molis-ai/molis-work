# 插件创作台 v3：全部能力、统一 Skill、按模型能力伸缩的交付流程

状态：方案已定（2026-09-27，用户拍板"全部按建议"），待执行。
上游：[`../agent-built-plugins/spec.md`](../agent-built-plugins/spec.md)（D1–D12 与 §14 执行记录继续有效）。

## 1. 背景与目标

**现在做到了什么**：一句话需求 → 主线设计给方案 → 你选 → 说明书（功能、例子、验收）→ UI Agent 从规格板（= UI 目录 `/__ui/catalog`）逐个放组件、代码 Agent 写功能 → 每项功能过关才接通 → 模拟真人验收 → 发布、安装、升级、卸载。全部 AI 调用经 Prologue。

**还差什么**：

- 插件能用的平台能力只有 5 项（调用模型、读目标、写目标进展、添加/取消提醒），由 builder 手写清单维护；官方插件只开放了 2 个动作；联网、文档成果、事件、定时执行都没接；MCP 和连接器双向不通；生成的插件也不对外提供动作。
- builder 的设计与代码规则是自己手写的提示词，和官方插件开发用的 `skills/molis-plugin-dev` 是两套，而后者不讲交付流程、也不讲生成插件。
- 流程固定，不看模型有什么能力（例如能不能出图）。
- 各项功能按顺序写，慢；"继续"基本是重来一轮。

**目标（用户原话要点）**：平台能力、用户已安装的插件（没安装的提示安装）、MCP 与连接器，都能被生成的插件使用；选择方式和前端组件同一个逻辑，由 Jev 从合法候选里挑；设计时把能力清单和组件清单一起给主线设计，出一个完整方案；方案定了以后，按动画效果绘制和接通。做插件的标准统一到一个 Skill，官方插件和 builder 共用，并且要做得很好；流程是预设的常规软件开发流程，按模型能力伸缩（能出图就给效果图让用户选）。

## 3. 范围与非目标

**范围**：W0–W8（见下）。

**非目标**：

- 不建第二套能力注册表。
- 不给插件开放不可撤销的动作。
- 不让生成插件自带前端代码（界面仍由平台用 UI 目录统一绘制）。
- 不做逐次人工批准。
- 外部市场、签名分发不在本轮。

  - 动画在真实构建中可见，e2e 断言节奏。

### W5 平台能力补齐

- 联网：宿主代理 + 域名白名单 + 密钥引用。

- 定时执行：插件的某项功能按计划被唤醒，在沙箱内运行，结果可进收件箱。
- 经统一目录调用 MCP 与连接器。
- **完成**：每项能力各有一个真实插件端到端跑通，首先是定时提醒到点进收件箱、定时执行一项汇总；联网只能访问批准的域名（越界被拒有证据）。

### W6 生成插件对外提供动作

- 安装即登记到统一目录（D16），卸载撤回，升级兼容。
- **完成**：Home 里的 AI 和外部 MCP 客户端各成功调用一次生成插件的功能；另一个生成插件也能调用它。

### W7 按能力伸缩的流程

- 能力探测：文字、出图、读图。
- 方案附效果图（经图片生成插件；失败不重试可能收费的请求）。
- 读图模型做验收截图走查。
- 没有相应能力时自动跳过。
- **完成**：配置了图片生成时，方案卡片出现效果图并能据此选择；未配置时流程不变、没有报错。

### W8 验收与度量

- 在示例项目批量试跑 10 个不同类型的需求，记录：
  - 一次成功率；
  - 平均时长；
  - 返修轮次；
  - 失败原因分布。
- 针对前三类原因修复后复测。
- **完成**：结果写进本文 §7；由用户试用验收，不自行宣布完成。

## 6. 与能力收口的接口约定（W0，2026-09-27）

**谁负责**：统一动作服务（`packages/kernel/src/action-service.ts`、`packages/contracts/src/platform/actions.ts`）的 owner 是 Codex 线程 01a0d468（见 `specs/bp-delivery-parallel/work-items/prologue-convergence/spec.md`），当前不在运行。并行会话「Codex AI能力统一至Prologue」只做"模型调用经 Prologue"收尾：改 `schedule-task-runner.ts`、`web-request.ts`（一行）、SDK 包换成 `prologue-sdk-0.0.0-rc.1-cache-breakpoint.tgz`；不碰动作服务。合并时 SDK 包以它的新包为准；本线不动 agent-host 的依赖与 lockfile。用户已授权按本方案推进，本线对动作服务只做加法，并在 `specs/action-architecture/spec.md` 留说明。

**约定**：

1. **发现**：设计时调 `ActionService.discover`，context 为 `{audience:'plugin', project_id, actor_id: 当前用户}`，结果就是能力板上"可授予插件"的动作。
2. **调用**：已安装的生成插件经 `ActionService.invoke`。context：
   - `audience:'plugin'`，`actor_id:'plugin:<pluginId>'`，`audit_actor_id:'插件「名称」'`；
   - `project_id`、`plugin_install_id`；
   - `permissions`、`allowed_actions`：安装时授予的精确引用；
   - `validate_authority`：每次派发前重查安装仍有效、授权未撤回。

   `goals.list`、`goals.note` 已按此接通。
3. **谁对插件开放**（加法，不改现有受众）：
   - `ActionMetadata` 新增可选 `effect: 'read' | 'write' | 'irreversible'`。
   - 受众检查增加一条规则：带 `agent` 受众的动作对 `plugin` 受众也可见、可调用，**除非**它是 irreversible，或明确退出（可选 `plugin: false`）。
   - 未声明 `effect` 时：query/navigation 视为读；能力 id 含 delete / trash / purge / destroy / erase / wipe / reset / uninstall / remove 的视为不可撤销（默认不开放）；其余视为写。
   - 显式带 `plugin` 受众的动作照旧可用。
   - 插件实际调用仍受第 2 条的安装授权约束：读类随安装一并授予；写类在安装清单里逐项列出。
4. **试用与验收时的写入替身**：由 builder 端通用生成——按 `input_schema` 校验输入、按 `output_schema` 生成合法结果，不要求提供方改动。提供方以后若自带 dry-run，优先用它。
5. **生成插件对外提供动作**（W6）：安装时 `registerProvider({provider_id:'plugin:<pluginId>', kind:'plugin', plugin_id, project_id})`，动作受众默认 user / agent / mcp / plugin，卸载即撤回。外部 MCP 客户端调用前，仍需用户在 `/api/settings/mcp/actions` 为该 client 授权具体动作（未授权返回 `mcp.action_revoked`，由并行会话实测）。
6. **MCP 与连接器**（W5）：已连接的外部 MCP 服务（`apps/local-host/src/connector-mcp.ts`）目前只供 Prologue Agent 直接使用，不在动作服务里。W5 把它们的工具登记为 provider kind `mcp` 的动作，进入同一目录，不建旁路清单。

**2026-09-27 补充（与 Ability Service 会话协调）**：

  - 按工具提示区分读和写（readOnly / destructive）由本线在两边合并后做：Prologue SDK 的快照不带这些提示，要补采集。在那之前，所有 MCP 工具都按"写别处"处理。

### 2026-09-27 · W4 接通、并行与续做（进行中）

- **按功能并行**：
  - 先让第一个写数据的操作单独写，由它定下记录的存法和共享模块；其余操作最多 3 个同时写，每个有自己的代码 Agent 会话。
