## 1. 目标与保留边界

**首要问题与证据：一骏 2026-10-27 明确反馈，至今还没有通过工作台完整跑通一次。** 因此工作台的真实用户端到端交付仍未通过，不能把旧文档的“已实现／已验收”、局部测试或生成答卷通过当作整条用户旅程已成立。具体卡点及根因尚未重新诊断；实施时须从真实任务复现，沿实际调用链定位，不能预设只是模型、提示词或 UI 的单点问题。

本次升级首先解决原工作台整体体验与交付能力，包括首次进入、需求澄清、设计选择、构建进展、试用反馈、修正、安装及后续使用。视觉、交互、功能闭环、稳定性、异常恢复、等待反馈与性能共同纳入范围。场景组装是在同一升级中增加的能力，不能代替原工作台的完整交付。

现有插件分别提供内容和能力，用户完成一个跨插件场景仍需逐个找到入口并手工接续。升级后的工作台同时支持两条创作路径：创建提供新能力的插件，以及把已有插件的公开能力组合为一个场景插件。两条路径可以混合：已有能力不足时，明确缺口，再创建或补充必要能力接入场景。

- **保留**旧工作台的完整产品目标：自然语言澄清、有实质差异的设计候选、UI 与功能协同构建、实际可交互预览、指着修改、真实试用、安装后独立使用及持续修订。UI 零件与业务能力分开，构建插件的流程与生成插件自身的运行流程分开。历史范围见[原工作台需求](../archive/plugin-builder/spec.md)及其子需求；本次没有将其缩减为固定模板或静态页面生成。
- **升级**为平台提供通用场景组装与运行支持，工作台提供创作体验；个人助理经同一公开动作使用这些能力，不另建生成结果或私有执行通道。场景插件可以有自己的入口、页面、步骤、状态与结果展示，在同一工作台外壳中运行。
- **保留 Alchemist 的业务价值**，按场景重新组织；不以复刻旧插件包、宿主专用服务或独立应用结构作为验收。旧迁入文档仅保留为[历史业务与证据](../archive/alchemist-plugin/spec.md)。
- **本轮不处理旧代码退场**。防腐线现有“不迁、不删、绕过”的边界保持；后续替换时再依据真正的代码与数据确定切换、保留及回退方式，不能因删除独立需求条目就删除插件或用户数据。

## 2. 平台、工作台与场景插件的职责

| 部分 | 负责什么 | 事实与边界 |
| --- | --- | --- |
| 平台 | 发现可组合的公开能力，检查依赖、输入输出与授权，提供组合所需的公共服务和正常插件运行支持 | 复用唯一动作目录、Manifest、SDK、Plugin Runtime、安装及授权路径；需要新增的共享合同对所有插件开放，不为工作台或 Alchemist 开私路 |
| 工作流程 | 表达步骤、条件、数据传递、人工介入与执行进展 | 优先扩展现有工作流程公开合同，不能为了组合场景另造一套工作流执行器 |
| 插件创作工作台 | 需求与设计、手动组合、AI 辅助生成、界面编辑、试跑、安装、修订 | 持有创作草稿与版本；手动和助理操作同一份可编辑定义，不复制正式业务数据 |
| 场景插件 | 将组合包装成完整使用路径，呈现场景入口、当前状态、操作与成果 | 通过公开合同调用原能力；对象内容和业务记录留在其主人。确需新增领域事实时显式确定 owner，不把所有中间结果另存成一份 |
| 个人助理 | 根据用户意图生成或修改场景，并解释依赖、缺口和变化 | 调用与手动创作相同的动作；生成、安装、启用与运行分清，依照当次已有授权执行 |

组合不等于把下游插件代码复制进新插件。正常调用、权限拒绝、停用、卸载、取消、安装换代及项目隔离均沿平台共同边界。场景声明所需能力不自动获得下游的全部权限，也不能绕过下游的人工决定。

## 3. 用户路径与 AI 的输入输出

### 3.1 工作台整体创作与交付

两条创作路径都必须完成以下旅程；原工作台的能力要重新做通并打磨，不能仅写为“保留”。

| 阶段 | 用户必须能做成的事 |
| --- | --- |
| 进入与准备 | 明白工作台能交付什么；模型、授权、连接或环境缺失时在对应位置完成配置，保留当前任务并继续，不让用户自己排查内部依赖 |
| 想法与设计 | 描述目标及材料，经必要澄清得到可理解的范围、差异明确的设计候选及关键状态；用户能够选择和修改，所选设计进入实际构建 |
| 构建与进展 | AI 将 UI、数据、真实能力和调用接通；用户知道当前在做什么、产出了什么、哪里需要决定。长等待有状态，失败有原因及下一步，能停止并继续 |
| 试用与修正 | 在逼真内容及真实能力上试用核心路径，直接指出视觉、交互或功能问题；反馈进入局部修订，已确认的其他行为不被随意改写。模拟预览明确标识，不能算真实交付 |
| 安装与独立使用 | 经过可理解的权限与安装流程，能找到并打开产物，真实输入得到预期结果，持久化结果可再次读取；关闭创作台及重启后仍可使用 |
| 持续迭代与恢复 | 从已安装版本回到创作，修改、验证并采用新版本，原有数据按明确合同保留；构建失败、模型超时、安装失败与中断后有继续入口，不靠重做整个任务恢复 |

工作台须对交付结果做实际验证并把发现的问题带回修正；验证失败时如实显示未完成。不得把“代码生成结束”“预览能打开”或“安装命令成功”直接显示为任务完成。端到端验收要求用户通过正常产品入口完成，不能依靠开发者在后台改源码、修数据库、补配置或补装产物才能过关；确需用户提供的授权、凭据和业务选择须有产品内入口。

AI 在原有创作路径中消费当前需求与设计选择、授权材料、构建产物、真实试跑结果和用户反馈，产出可运行插件及可检查的修订，并更新真实进展。用户可在设计、试用与采用版本时干预；低质量结果允许指出问题继续修正，停下或重启后能回到有效成果。组合路径在此基础上增加能力选择与绑定。

### 3.2 组合已有能力的创作路径

1. **确定场景。** 用户在工作台手动选择已有能力，或向个人助理描述要完成的事。两种入口都形成可编辑的场景草稿；只追问会改变输入、产出、步骤或权限的问题。
2. **形成组合。** 展示步骤、前后数据怎样相接、需要的角色／技能、人工介入点和产物去向。用户可增加、删除、重排步骤或调整绑定。无对应能力时标出缺口，不编造已存在的动作或连接。
3. **组织界面。** 基于完整旅程设计页面和关键状态；默认给用户能理解的操作与进度，技术依赖和绑定可展开检查。沿用平台组件、字体、皮肤和语言规则，不要求用户逐项编辑内部参数。
4. **试跑。** 使用隔离的试用数据走完整路径。明确哪些已接通、哪些还缺连接或能力；错误出现在对应步骤，并能查看已完成结果、修正后继续。
5. **安装并使用。** 产物走普通插件安装、信任、启用与生命周期。关闭创作工作台后仍可从工作台外壳独立进入；重启后保留应持久化的业务内容与执行进展。
6. **继续修改。** 用户可以让助理生成后手工调整，也可以从手工组合交给助理完善。修改形成草稿与可理解的差异，不让晚到的模型结果覆盖新修改；验证和采用后再改变正式使用版本。

AI 消费用户描述、明确授权的项目材料、当前场景草稿及版本、实际可用的插件与动作合同、工作流程和 UI 规范，产出场景方案、步骤与数据绑定、角色配置、页面／状态设计和局部修订。只有目录中可验证的能力才能作为已就绪依赖；不足部分是待补事项。调用模型仍经同一个 Prologue Runtime。

场景定义至少能表达：场景用途和输入输出、依赖能力及版本、步骤与数据绑定、必要角色、人工介入点、页面与状态、结果引用和恢复方式。技术设计先核对现有 Manifest、工作流程与 UI 合同能表达多少，再补真实缺口；不预设第二套包格式、注册表或安装器。

用户可查看方案、调整组合、停止生成或运行。模型超时、输出不合法或低质量时保留有效草稿，允许局部重做或手动修改；运行部分成功时保留已完成步骤和主人返回的引用。重启后先核对真实执行状态，结果未知的外部副作用不能盲目重放，继续运行不能重复创建业务记录。

### 3.3 主推角色与样例插件（建议 C5）

用户 2026-11-03 定：主推角色取[推广与用户运营](../../docs/product-operations/推广与用户运营.md) §5 的六个模板包，加 §4 的「项目经理／交付」，共七组，每组两个样例插件。样例是普通插件：与其他插件同一套 SDK、Manifest 和安装路径，不在宿主里开专用通道；工作台里可一键装上，也可以作为起点让 AI 改成自己的样子（从样例开草稿，与「从已安装版本再改」走同一条修订路径）。下表是每个样例要让用户做成的事；「用到的插件」只写目录里现有的，做样例时以真实动作目录为准，接不上的标成缺口，不写成已可用。

| 角色（模板包） | 样例插件 | 用来做什么 | 用到的插件 | 让 AI 改一次后要核对 |
| --- | --- | --- | --- | --- |
| 双 AI 开发 | 发版清单 | 每次发版前逐项勾：变更、测试、文档、版本号；未勾完的不能标「可发版」，勾过的项记下是谁、看的哪次提交 | Git、Goals | 新加一项检查后，旧清单的勾选仍在，新项在未完成里 |
| 双 AI 开发 | Bug 分诊台 | 把 GitHub 通知里像 Bug 的条目分成「是 Bug／不是／要问」，是 Bug 的进 Inbox 或升格为 Goal | Feed、Inbox、Goals | 改了分诊规则后，已分过的条目不被重分，只对新条目生效 |
| 行业周报 | 来源核对台 | 周报里的每个论断挂上出处，没有出处的标「待核」，出处更新后提示重看 | Feed、Pages、Cognia | 加一个「来源可信度」字段后，原有论断和出处都在 |
| 行业周报 | 承诺核对台 | 记下文中写的承诺与数字；无出处不能标已核，来源变了要重看 | Pages、Cognia | 改了「已核」的条件后，过去标已核的条目按新条件重新显示状态，不静默变成已核 |
| 产品经理 | 需求优先级打分 | 给需求按影响、信心、成本打分排序，排序结果可固定成一个版本 | Goals、Dataset | 换一种打分公式后，旧版本的排序仍可查看 |
| 产品经理 | 访谈整理 | 把访谈记录拆成发现、引用和待验证假设，每条引用回到原文位置 | Forms、Pages、灵光 | 加一个「受访者类型」后，已整理的引用不丢、不重复 |
| 内容创作 | 选题库 | 收选题、标状态（想法／在写／已发），从灵光或 Feed 收进来的保留来源 | Feed、灵光、Pages | 新加一个状态后，原选题的状态与来源不变 |
| 内容创作 | 素材出处卡 | 选进稿子的句子和图片带着出处，导出时出处跟着走 | 灵光、Shelf、Pages | 改了导出格式后，出处仍随每条素材导出 |
| 独立执业 | 报价前核对器 | 报价前按自己的规则核对折扣上限、必填项和付款条件，不合规的不能标「可发出」 | Dataset、待办 | 把折扣上限从 15% 改成 20% 后，旧报价按新规则重新判断并说明差异 |
| 独立执业 | 发票台账 | 记开票、收款与逾期，逾期的进待办「在等别人」 | Dataset、Shelf、待办 | 加一列「税率」后，旧记录保留并显示为未填 |
| 学生与研究 | 文献阅读卡 | 每篇文献一张卡：问题、方法、结论、我的疑问，可从 Cognia 资料直接建卡 | Cognia、Pages | 加一个「可复现性」字段后，旧卡片的内容都在 |
| 学生与研究 | 反例与反驳清单 | 对一个论点列反例、反驳和自己的回应，每条带出处 | Cognia、Jelly | 改了条目的分类后，旧条目归到对应新分类，无法归的标出来 |
| 项目经理／交付 | 例会签到与缺席跟进 | 会前导入名单，会上逐人签到，会后缺席的人记成跟进并同步建待办；历次会议可回看 | 待办 | 加一个「迟到」状态后，历次会议的签到记录不变 |
| 项目经理／交付 | 在等别人的跟进表 | 记下在等谁、等什么、哪天要催；到日子提醒，催过一次留记录 | 待办、Schedule | 改了提醒间隔后，已排的提醒按新间隔重排，已催的记录保留 |

这十四个样例同时是创作台的代表性任务：PBU-09（换一个场景仍能组合与使用）、PBU-15（用代表性真实任务复验）从中取样，第一个真实复现用的就是「例会签到」（[复现记录](reproduction-2026-11.md)）。效果按建议 C5 的口径看：样例被 AI 改造后仍能安装并正常使用的比例。本节只定角色与用途；样例的实现、上架位置和一键安装入口随第 2～3 阶段的构建、试用与安装一起做，尚未开工。

## 4. Alchemist：完整落地场景

Alchemist 作为工作台产出的创意孵化与研究决策场景，验证“组合已有能力，形成可持续使用的场景插件”。以下业务范围从旧需求承接，不再有独立重做任务：

| 使用路径 | 必须保留的用户结果 |
| --- | --- |
| 方向 → 候选想法 → Brief → 保留版本 | 可以产生、比较、修改和保留创意；研究与决策指向明确版本，后续修改不改写旧版本的结论 |
| 公开信号／Pulse → 机会 → 方向 | 从真实来源形成可追溯的机会与创意输入；支持人工补充，市场研究辅助判断，不以市场未表达需求否定创意 |
| 市场空间与实现成本两条 Lens → 证据报告 → 决策 | 两条研究独立显示状态，报告与决策对应同一创意版本；来源、支持／反向信号、未知及改变判断的条件可查看，无来源不伪造证据 |
| 研究做法与个人偏好 → 讨论／Copilot → 修改 | Research Playbook、Founder Taste、对象正文、历史讨论与选区注释进入明确的上下文；按范围启用，用户能纠正与调整 |
| 运行与留存 | 模型和预算可理解，能停止、恢复、查看活动与导出；研究失败或取消保留旧报告，旧结果和本次状态不混淆 |

设计时将每一步映射到现有插件、工作流程或平台公开服务；确实缺少的能力按通用能力或最小领域插件补齐。不得为了让 Alchemist 成立，在宿主添加按插件名分支或只供它使用的组合通道。它的创作定义应能在工作台打开、修改和试跑，不能交付一份只有开发者能改的硬编码实现。

结构化生成（BL-306）和记忆归属评估（BL-035）随这个场景处理：结构化结果按领域合同校验，错误结构不入正式业务库；哪些偏好／做法由平台记忆承担、哪些版本和研究事实归场景或原插件，设计时明确，不另造记忆系统或复制事实。旧完整迁入的本人验收（BL-010）转为本场景的完整使用验收，尚未通过，不因归并标记完成。

## 5. 承接范围、依赖与顺序

本需求是 BL-377 的唯一现行产品需求。旧 BL-376 不再是独立重做事项，其业务范围、BL-010／BL-035／BL-306 的承接和后续退场约束均在本文；编号不复用。原工作台仍待实现的方向、[harness R11 与 R12](../coding-harness-optimization/spec.md)、[产品建议 C1～C5](../../docs/product-operations/产品优化建议.md)、[字体皮肤语言 §7.2](../font-and-skin-system/spec.md)及 BL-040、055、113、114、125、132、245、373、551、712 和 BL-341 的创作台部分仍由本需求统筹，不因新增组合路径而丢弃。建议 C4 中按“官方／自建”区分待遇的旧措辞按现行插件平等原则解释：展示来源、发布者、能力依赖、权限与联网范围，同样走安装和授权。

依赖是防腐收尾后的插件公开合同与 Runtime、工作流程能力、平台 UI 以及必要的角色／技能和 Prologue 能力。字体皮肤语言 C 段先于最终生成插件的正式交付；平台组合合同和需求设计可先明确。现有合同或能力缺口在设计阶段实测后列出，不把尚未核对的机制当成已实现。

2026-10-28 按[后续演进计划](../post-anticorruption-roadmap/spec.md)调整先后：防腐收尾后阶段 1 诊断真实断点、核对公共能力并完成交互切片；阶段 2～3 做通新能力插件创作、构建试用、安装、独立使用与修订恢复；阶段 3 细化场景组装合同，阶段 4 完成手动／助理组装及 Alchemist。阶段 1 的设计同时考虑两条创作路径，前移首条路径不缩小整体范围，也不把局部完成当作 BL-377 完成。需求维护与实现待分配状态保留，C/D/E 仅表示所需协作；本轮不启动产品开发。内部顺序：

1. 用真实创作任务复现原工作台的完整旅程，记录首个阻塞和后续断点、实际产物及用户能否继续；核对公开能力与旧需求，再明确整体交互、模块职责与 Alchemist 能力映射。2026-11-03 第一次复现见[复现记录](reproduction-2026-11.md)：首个阻塞是界面验收未通过后既装不上、也改不了验收。
2. 为从想法到持续使用的主路径做高保真可交互切片，含准备、设计、构建等待、试用反馈、修正、安装与失败恢复；组合编辑和手动／助理接续在同一体验中设计。
3. 首先把新能力插件创作的完整端到端路径做通，完成体验与稳定性打磨；在同一交付链上接通平台场景组装。每条路径都要实际安装、独立使用及修订，局部通过不算整体完成。
4. 完成 Alchemist 的完整业务路径，并用一个不同的轻量场景验证组合能力通用性，不另立第二个大型产品。
5. 验证持续修订、停用／卸载、重启与部分成功恢复；确认替代路径后再制定旧实现的切换与退场方案。

**定样决定（2026-11-03，用户定）**：第 2 步的主路径切片用「对话加阶段」（定样 [`docs/design/plugin-studio-main-path/`](../../docs/design/plugin-studio-main-path/README.md) 方案 A）。左边一直是和创作助理的对话，澄清问题和构建中要定的事都在对话里问和答；右边是当前阶段（准备、想法、方案、构建、试用、安装、关掉后使用、从已装版本再改），顶上一条阶段进度，可以点回看之前的阶段；手机宽度用「对话／阶段」切换。没选：分步向导（一次只看一个阶段，助理收在抽屉里，问它要多点一下、打开时盖住页面）、规格板领头（左栏常驻这份插件的规格板，信息多、第一次进来难懂，对话不常驻）。各阶段里的内容随切片一起看过，没有要改的：只问会改变做法的问题并写明为什么问；三个有实质差别的方案各列关键状态，组合方案标出缺口、不编造已有动作；组合步骤可手动调整也可让助理调整，助理晚到的结果不覆盖你刚改的；构建每步写产出、中途要你定的事、停止先显示正在停止；试用标明试用数据和哪些能力真接通，「指着改」只改那一处并可撤回；安装前列出能做的事；关掉创作台后单独使用；从已装版本开草稿、写明差异与旧记录怎样保留，试用通过才采用；六种失败（缺配置、模型超时、构建失败、中断后重开、试用缺陷、安装失败）各在对应阶段说明保留了什么、怎样继续。真实创作台的断点由第 1 步在隔离 Home 里复现后补进切片（[复现记录](reproduction-2026-11.md)第 5 节）；场景组装的合同不在这次定样里定。做产品前把原型控件换成 `mw-*` 组件再核对一遍；功能验收照 PBU-10、PBU-15 用真实模型、构建和安装再走同一路径。 11-04 按组件板实件重做，用户确认：版面与选定的方案不变，按钮、标签、分段、状态记号、状态环、进度条和提示条换成组件板的 `mw-*`（共用的 `docs/design/kit/`）。

后续退场要保留旧备份 `backup/alchemist-plugin-builder-2026-10-21`（main `458b33059`）的参考入口，并在实际切换前另核当时的代码与数据。借旧插件验证平台边界的测试、被其他插件复用的搜索／存储服务、通用第三方插件安装与沙箱都须先有明确去处。旧创作台的专用安装通道、回放脚本／CI／语料与已生成插件怎样处理，由届时方案说明影响；本次不执行旧删除计划，不授予删除真实数据的权限。

文件／模块边界：平台合同、SDK 与 Runtime 承担共用能力；工作流程包承担流程事实；插件创作工作台承担创作体验；Alchemist 场景定义及必要领域能力承担该场景内容。精确实现文件与变更合同随阶段 1 的实际能力核对确定，组合部分在阶段 3 继续细化，当前只改需求、索引和计划，不改上述产品模块。

## 6. 验收标准

| 编号 | 完成条件 |
| --- | --- |
| PBU-01 | 用户能手动组合已有插件能力，也能让个人助理生成；同一草稿可在两种方式间继续编辑，步骤、绑定、角色和页面一致 |
| PBU-02 | 场景声明与界面只引用真实可用的能力，缺依赖、版本不匹配、输入输出不匹配均有明确位置与修正入口，不伪装为可运行 |
| PBU-03 | 组合产物经普通插件安装与 Runtime 使用；无宿主按 Alchemist／创作台名称开出的专用通道，原业务事实仍由原主人读写 |
| PBU-04 | 关闭工作台并重启后，场景插件可独立进入，业务结果和需要恢复的进展仍在；试跑数据不冒充正式结果 |
| PBU-05 | 取消、撤权、停用或安装换代后，迟到结果不能继续写入；继续执行只补未完成部分，未知外部副作用先核对，不能重复记录或越权读取 |
| PBU-06 | 助理超时、无效或低质量输出保留有效草稿，可手动修正或局部重做；旧版本输出不能覆盖用户新修改，修改草稿不破坏已使用版本 |
| PBU-07 | Alchemist 从方向、候选、Brief、保留版本到两条 Lens、真实证据与同版本决策走通；Pulse／机会、偏好／研究做法、讨论／注释、活动与导出纳入完整旅程 |
| PBU-08 | Alchemist 的两条研究独立显示运行状态，模型不可用、取消、失败及重启都有可理解恢复入口；保留旧报告，错误结构和伪造来源不进入正式结果 |
| PBU-09 | 换成一个不同的轻量场景仍能组合、编辑、试跑和使用，证明平台能力不依赖 Alchemist 名称或固定步骤 |
| PBU-10 | 原工作台新能力创作从真实想法、澄清、设计选择到 UI／功能协同构建、试用、局部修正、安装及独立使用完整走通；依照 harness R11／R12 验真实任务和持久化结果，不只验证设计答卷或截图 |
| PBU-11 | [人工] 一骏本人通过正常产品入口走完新能力插件创作与 Alchemist 场景的交付和使用旅程，无开发者后台补救；关键正常／等待／失败／恢复状态、键盘、窄屏及字体／皮肤／语言切换都可操作，技术细节不占据主流程 |
| PBU-12 | [人工] 场景／能力包设置、秘书与助理团引导、首次／项目／通用任务 Onboarding 未成为本需求的交付项或阻塞依赖；Alchemist 没有另立重做排期，旧需求归并不被解释成旧产品已验收或代码已删除 |
| PBU-13 | 生成的插件关闭创作台、重启后可真实使用；从已安装版本继续修订并采用后，核心行为与应保留的数据正确，不依赖后台手工改源码、修库或补装 |
| PBU-14 | 配置缺失、构建失败、模型超时、试用发现缺陷、安装失败和任务中断都能在产品内理解并处理，保留有效成果后继续；无效产物或未通过的验证不会被标为交付完成 |
| PBU-15 | [人工] 首次进入、设计候选、构建进展、试用反馈、安装入口及再次修改连贯可理解；使用代表性真实任务复验，两条创作路径不依赖固定演示输入或一次偶然成功。记录等待体验、缺陷和恢复结果，未解决的核心阻塞不判内部完整 |
