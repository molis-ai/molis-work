# 产品与 UX

从用户目标和关键动线验证产品行为，再扩展完整体验。

适用于：产品设计、交互设计、体验优化。

## 规划路径

1. 定义用户、时刻和现有阻力
2. 设计核心动线和状态
3. 制作真实高保真切片
4. 补齐首次使用、异常和响应式体验

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| user_problem | 用户问题 | 用户此刻真正想完成什么？ |
| core_flow | 核心动线 | 最短闭环怎样自然发生？ |
| system_feedback | 状态与反馈 | 用户如何知道发生了什么并可干预？ |
| edge_experience | 边界体验 | 首次、空、错、慢和恢复怎样处理？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| slice-after-flow | 高保真切片依赖明确的核心动线、关键状态和待验证风险。 | high-fidelity slice depends_on core flow and states |
| scale-after-slice | 全面实现依赖一个真实高保真切片验证。 | full build depends_on validated slice |

## 完成证据

- 可见可操作的关键切片
- 真实内容和关键状态

## 收口检查

- 无需解释文案也能推进主任务
- 信息层级和错误恢复清楚

## 常见误拆

- 通用 Dashboard 套模板
- 只改样式不改动线
- 靠大段文案解释交互

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
