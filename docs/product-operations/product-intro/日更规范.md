# Molis Work 产品介绍日更规范

生效：2026-10-17；2026-10-18 按用户要求补充角色与完整工作链写法。用户指定每天 **09:00，Asia/Tokyo** 更新。本文替代此前“只追 main、开头一段综合一分钟”的默认写法；历史 V0–V3 保留。

目标是维护一份可供官网取材的完整产品介绍。每天既看实际进展，也重新判断功能对谁有价值、场景是否成立、现有做法是否已经足够好。没有新功能的日子也检查五章，不为日更制造卖点。

## 产物与范围

- 正文：`daily/YYYY-MM-DD.md`，标题为 `Molis Work 产品介绍｜YYYY-MM-DD`，使用东京日期。
- 依据：`research/YYYY-MM-DD-分支盘点.md` 与 `research/YYYY-MM-DD-快照.json`；研究有实质新增时另存专题报告，不机械复制旧报告。
- 索引：更新本目录 README 的最新链接，保留旧版。
- 汇报：首行写当天日期，给正文链接、最重要变化、未核实项。自动化名称是固定名称；文档和每次汇报标题带实际更新日期。
- 同日再次执行时更新当天文档并记修订时间，保留有用的原结论与改正记录；先检查是否有人正在修改，不能整份覆盖未知改动。
- 这是文档维护：不修改产品源码、真实 Home、官网、供应商账号；不自动提交、推送、合并、发布或联系受访者。

维护目录为 `docs/product-operations/product-intro/`；历史 V0–V2 与旧介绍页保留在 `docs/product-intro/`。当前文档工作树为 `/Users/oreal/.codex/worktrees/product-intro-v3/molis-work`。读取实现时以当次远端与各工作树为准，**文档工作树的 HEAD 不代表当次最新产品基线**。若工作树位置变化，先查聊天附件及 Git worktree，找到并保留最新未提交文档，再更新路径，不在主检出盲写。

## 每次执行顺序

1. **建立边界与快照。** 读取适用 AGENTS、上一份日更与快照；检查 main、文档工作树、molis-club 的分支/HEAD/未提交改动及在途工作。记录读取时间、远端 main SHA、公开 Release、发布草稿、Club work-split SHA。必要的远端读取可用 API/连接器，不能把本地 origin/main 当已刷新；失败则保留最后成功时间并标本次缺口。
2. **枚举全部分支，再按变化深读。** 分页读取全部现存远端分支、开放 PR、本地分支和工作树。记录每条分支的 SHA、PR、相对主线状态、未提交文件；识别合并队列临时分支、已 squash 合入的旧分支、只含诊断/设计/文档的分支。全部进入清单，只有影响产品事实的差异展开。对上次以来新增或变更的路径，读代码、需求与验收记录；不能凭分支名或 spec 的旧状态句判定。
3. **补齐没有代码的需求。** 读取最新 PRODUCT、SSOT、specs 索引/BACKLOG、活跃 spec，以及各分支新增的 PRD、设计、需求、计划；对主线概述与具体实现冲突逐项求证。也读 Club work-split 新产物及用户决定。某路径缺失只表示本次没找到，不能说功能不存在。
4. **形成变更台账。** 每项记触发/用户价值、状态前后、首次出现/合入时间、事实证据、缺口、影响章节及场景 ID。PR 使用 `merged_at` 转东京时间；提交创建时间不能替代合入时间。发布另记 `published_at`。
5. **逐章复审并写完整正文。** 按下述五章顺序，保留已有框架中仍成立的内容；记录删除或降级旧卖点的理由。未变化章节也留复审结论，正文读起来应是当天的完整介绍，不能只有补丁清单。
6. **核对后落盘。** 检查口播长度、日期与基线、所有分支覆盖、状态与来源、链接、场景到 Why 的对应、官网可用范围和实际 diff。文档任务不跑产品构建/全量测试，不把历史用例通过说成本轮产品实操。

### 日期与增量不能漏一天

09:00 是截点，不是一天结束。第二章同时保留两个时间窗：

- **今日新增**：当天 00:00 至本次取证截止，按东京时间。
- **上次更新后补齐**：上次成功截止至本次截止中，发生在昨日的变化，单列日期；避免每天只看当天凌晨而漏掉昨天白天。

第一份没有昨日基线时，明确“首次建立全量基线”；与 V3 的差异是历史补齐，不能全算今天上线。中断多天就从最后成功快照补齐，并注明覆盖区间。快照之后的新提交留到下一次，不让正文不同章节各用一个“最新”。

## 固定五章

### 一、最新产品介绍

两段独立口播，各自约 180–250 个中文字符，以常速口播一分钟内为目标；检查文字长度，未真人计时就写“估算”。

- **用户视角**：产品是什么 → 谁在做什么 → 一条具体工作链 → 用户得到什么。两类角色不强塞同一痛点，写文档的人不默认有轮换 AI 的需求。
- **技术架构视角**：一 Home 一宿主 → 插件/模块各自拥有事实 → 同一动作按声明与权限供不同入口使用 → 统一 AI 运行时与本机数据/联网边界。架构解释体验，不堆包名，不说所有插件均完成 Runtime 迁移。

紧跟一句当日版本边界。开头不能把需求中的自动周报、团队协作、插件市场包装为现成能力。

### 二、今日新上功能

分“公开发布”“今日合入 main”“分支与未提交推进”“需求/设计变化”“历史补齐”。没有则明确写没有或未核实；设计和重构不能算用户新功能。按用户变化组织，带 PR/提交/文档依据、适用角色、未覆盖部分与章节影响。

章末放逐章 review 表：五章各一行，写今日证据如何改变本章，或为什么保留。不要只写“五章已看”。

### 三、功能全景

按“完成一件真实工作所必需 → 连接各步 → 复用与扩展 → 未来方向”的重要性排列。结构可沿用：工作台与助理；目标/交接/验收；材料与文档；日常执行；工作流程与插件创作；数据/模型/权限；团队与其他设计。

每项写用户能做什么、目标人群、实现/发布状态、关键依赖与来源。插件墙不能代替全景，内部工具和开发者参考入口不做官网卖点。功能总数与入口数不同，不追求一个容易漂移的“大数字”。

### 四、用户场景

保留历版“场景、麻烦、怎么做、用到”的叙事，但增加角色、交付对象、需求证据、替代做法、实际摩擦与成立条件。

1. **先枚举**：保留写代码／写文档、管事情两条大路线，按可重叠的职责 × 触发 × 交付物展开并赋稳定 ID。当前职责入口为创始人、产品、设计、研发/测试、运营增长、自媒体、销售/客户交付、研究咨询、项目协调；分组是研究假设，不是已经验证的客户画像。新功能先问改变哪个场景的一步，避免每个插件造一个场景。
2. **再抽象**：从枚举收拢少数反复出现的需求；保留具体案例，不用抽象口号替代它们。
3. **检查真实需求**：区分本团队真实经历、直接用户报告、原始调查、官方能力、推断；功能存在或竞品在做不能证明需求普遍。没有访谈就写没有，公开 issue 不计市场频率。
4. **检查解法**：完整走读触发 → 材料 → AI/人分工 → 结果落点 → 复核 → 后续，指出多余搬运、重复记账、权限/模型配置、人审、失败恢复和迁移成本。用少数重点案例写深，其他场景保持可比较的表格。
5. **检查反例**：只改一句话、原办公套件已足够、只需单次脚本、全员实时协作、严格数值计算等条件下，不强推 Work。

**2026-10-18 用户追加的写作标准：**不能以“能写文档、总结、建待办”单独构成优势。每个重点案例写清：最近发生的具体触发 → 用户原来用什么、在哪一步卡住 → Work 依靠哪个现成机制减少了哪次重讲、搬运、重配或核对 → 仍需人做的动作 → 能检查的交付物。相同机制跨角色复用时，保留角色入口，首页只选一个讲深；没有独立证据的角色不凑主案例。

**同日追加：迁移价值必须经完整工作链检验。** 每个主推案例用同一交付物对照熟练用户的现有组合，从首次设置走到实际交付、失败恢复和再次回来。不能把竞品写成每次重讲提示词、把全文搬到聊天，或只能全篇重写；已有文内 AI、模板、项目说明与自动化要计入基线。

- 按有明确产物的人类工作区分：真正消除、条件减少、只是换位置、完全不变、新增操作或能力缺口；没有观察记录不加总成“省几次点击/几分钟”。
- 分开计算首次接入、每轮操作、与旧系统并存、同事/客户协作、费用、失败恢复与退出成本。已有用户配置是沉没投入，不能只对竞品计设置成本。
- 判断 Work 是否能替掉旧记录或旧操作；若只是多一本账，不能用“都在一起”掩盖。新项目降低搬迁成本不等于日常更快，已有 Work 用户受益不等于新用户值得迁入。
- 没有足够净收益的案例继续收窄、改写或撤出主推，不要求凑满三个；相同机制跨角色同步调整，其他未验证角色不自动递补。
- “Why”只采用仍成立的子集，明确取舍与推翻条件。源码机制、可行方案、实操效率、用户迁移决定分别记录。

**继续挖掘，不能以降级旧案例作为研究终点。** 若原主推不足以驱动采用，应从当前能力重新枚举跨工具、跨多轮的完整工作链，找出具体可停用的旧操作或旧记录。分别交付“现有机制可试”“可用现有平台制作但业务样例尚不存在”“补一个关键缺口才成立”的候选；不为了留下三个案例而抬高状态。先迁入一条工作或一份对象，和搬整个工具栈分开判断。

新候选须给出主动选择它的理由、熟练替代方案、首次/每轮/并存/退出成本，以及一项足以推翻判断的真实任务。若现有能力接不住，写清最小改法、可复用的事实主人和先后依赖；先验证小范围，只读定位有用后再加持续处理状态，不因跨工具叙事先造全平台系统。迁移价值、可试性和官网可用状态分开。范例见[跨工具多轮机会研究](research/2026-10-18-跨工具多轮机会研究.md)。

本轮执行范例见[完整工作链对照与迁移判断](research/2026-10-18-工作链对照与迁移判断.md)；此前选材研究保留为历史，不覆盖新的撤回结论。

研究同类 onboarding 时，区分官方角色选项、官方个性化机制、官网任务分类和历史第三方截图；部分列表不能称完整，公开文档不能冒充实际注册。角色选项只供分类参考，不能证明 Work 的需求规模。竞争比较承认现有文内编辑、持久项目和自动化；把迁移成本、适用条件与推翻条件写进研究。角色选材沿用[10/18 前轮研究](research/2026-10-18-场景选择与验证.md)，原案例迁移判断以同日完整链复审为准，新选材以跨工具多轮研究为准；两者不互相覆盖。

示意故事不能写成客户案例。规划中的链路可作为未来场景，但标出已实现的段、缺失的段与依赖；能力都存在不等于整条用户旅程已走通。

### 五、为什么是 Molis Work？

从第四章挑最痛且与 Work 核心优势吻合的子集，逐项给出：目标用户/场景 ID → 原办法已解决什么 → 还剩什么成本 → Work 的具体机制 → 当日证据边界 → 不适用条件。

比较须刷新关键一手资料。禁止“别人都只有聊天”“只有我们跨 Agent”“引用功能只有我们有”“组合起来别人都没有”。没有实操数据就不写节省百分比。官网摘录只写类别，内部研究可点竞品名并给官方链接。

## 两个状态维度

| 维度 | 写法 |
| --- | --- |
| 实现所在 | 公开版本；main 已实现/部分实现；分支实现；本地未提交；需求/设计；待核；已撤回 |
| 证据程度 | 仓库核对；历史工程验证；历史产品实操（具体路径）；本轮产品实操；用户本人验收（明确范围） |

二者不可互相替代。main 合入不是公开发布；有测试不是体验顺畅；只有设计不是已排期；自动化运行成功不是用户验收。

官网沿用“已发布 / 开发中”简标签并标“示意”；取材清单仍须保留详细状态。需求可以演，但邻近文字要说明尚属设计，不暗示今天可下载；更新官网原句应走 Club 自己的事实源，日更不代替官网修改授权。Issue 仅在内部盘点中出现，不进入可摘录正文和截图。

## 研究与优化的持续方式

复用 [2026-10-17 审读与补研计划](research/2026-10-17-work-split审读.md) 的问题清单。每次只深化被新证据影响的关键判断，不每天重做全市场。可并行做分支核对、两类角色研究；主 Agent 核对冲突、关键源文件和最终措辞。

产品建议写成“哪个问题 → 最小改法 → 用什么真实任务验证 → 什么结果会推翻它”，明确是建议，不是新需求批准、开发承诺或排期。需登录/购买/真人访谈/外部联系的研究先保存具体脚本和待执行项，未经授权不实施。

## 完成检查

- 两段一分钟介绍、五章顺序、当日日期与取证截止齐全。
- 每个已知现存分支、开放 PR、工作树与活跃设计有去向；不可访问处明确标缺口。
- 今日与上次增量不混淆，未发布/未实现/未验收各自说明。
- 重点场景有角色、结果、替代解法、需求证据、摩擦与反例；完整链列明净减少与新增成本，弱案例有收窄或撤回决定；Why 引回仍成立的场景。
- 重要结论有固定 SHA/PR/文档/官方来源，不继承旧介绍的过时比较。
- README 链接可达，旧日稿保留，文件 diff 仅在授权的介绍目录。

只检查上述必要条件；不额外引入数据库、定制爬虫、完整竞品安装矩阵或产品测试工程。
