# Personal sync Worker — pre-deployment verification

This directory is the Cloudflare composition root, not the owner of server business logic. `src/lib.rs` registers `fetch` and `scheduled` events and forwards them to [`server/src/sync`](../../server/src/sync/README.md), built using `server/Cargo.toml`. The D1 baseline lives in `server/migrations/sync`; this App retains the build/configuration and actual-runtime integration tests. The module still uses Cloudflare APIs; this move does not make Node IM deployable on Workers or change any live resource.

Both Wrangler templates watch the App and `server/src/sync` during local development, so changing the moved source rebuilds the Worker. Existing private Wrangler configs must also update `build.watch_dir` and `migrations_dir` to match the templates; do not replace their actual resource IDs.

The Workflows collection carries definitions and run history. Imported runs remain observation-only and cannot dispatch work on the receiving device. Jelly transfers the personal calendar, notes and their links; device-specific import receipts, undo history and previews stay local.

Rust/WASM + D1 transport for space-scoped incremental replication. Auth validates the Bearer token; the server derives the space from issuer, application and user. The request cannot choose another owner. No real cloud resources are created by these instructions.

The approved scope and delivery plan are in [Personal cloud sync](../../specs/personal-cloud-sync/spec.md). Device opt-in, trusted HTTPS, shared D1/R2 quota, resumable private content, per-item isolation and record-tombstone retention are implemented for local verification. Runtime lifecycle discovery, Shelf files, Work history and Builder authoring have actual owner/Host round-trip evidence. Full Coding Runtime history, complete project lifecycle/copy/recovery and production acceptance remain outstanding. Nothing here has deployed a cloud resource.

Registered local business adapters currently cover Goals (project graph, work records and decisions), Pages, Artifacts, Form (including submissions), Dataset (including saved snapshots), PPT, Lingguang, Workflows, Jelly, Todo, Issues, Schedule conversation tasks, Character drafts, Feed capture rules/source descriptions/messages/materials/fixed Signal history and original evidence, Inbox references/dispositions/history, Images saved terminal results, Cognia knowledge graph, the Alchemist studio graph, Shelf saved files/results, Work Session history, Coding metadata/plans/unsent input and Builder complete authoring files. They share opaque transport; Rust does not import business schemas. Received Schedule tasks, Feed rules and new source descriptions remain disabled; receiving content never starts image/research generation, knowledge scans, listeners or Inbox judgments. Feed and Work evidence is re-encrypted with the receiving Home's own key; keys and connection setup never travel. This is **not all-plugin synchronization**: full Coding Runtime conversation/Run history, nested owner recovery/GC and full project/copy/recovery work remain outstanding. D1 metadata stays limited to 512 KiB; content uses owner-selected R2 projection, with domain validation and the 100 MB account admission enforced. Full coverage and remaining owners: `specs/personal-plugin-replication/spec.md`.

## Run locally

1. At repository root run `pnpm install --frozen-lockfile` and `pnpm build`.
2. Install Rust's `wasm32-unknown-unknown` target and `worker-build` 0.8.6 (`cargo install worker-build --version 0.8.6 --locked`).
3. The Rust application is not a Node workspace package. In `examples/personal-sync-tools` run `npm ci`; this directory owns only the locked Wrangler/Miniflare toolchain. `worker-build` writes the runtime bundle to `apps/sync-worker/dist`, not a second workspace package.
4. In `wrangler.jsonc` set `APPLICATION_ID` to the Auth application's ID, not its login client ID. Keep `AUTH_ORIGIN` pointing to your local Auth instance.
5. From `examples/personal-sync-tools` run `npm run build`, `npm run db:migrate`, then `npm run dev`. This starts the isolated local Worker/D1 at `http://127.0.0.1:8788`.
6. Set `MOLIS_WORK_SYNC_LOCAL=1` in the local work launcher environment and restart molis-work. Log in, enter the personal space, then open **Settings → Sync**, select the desired collections (including Goals) and save. **Retained versions → Cloud history** finds account-scoped retained keys and their paginated versions, even on a device without a local conflict journal. **Local history** remains an explicit separate view.

With no explicit endpoint or local flag the client stays disconnected. A new device asks before automatic transfer; choosing not now is remembered per account/Home. Sync Now runs one bounded cycle and never creates a timer. Saving collections does not change device consent. An opted-in device resumes when its personal space is activated; logout, account change and local-space selection cancel the old loop.

## Cloud configuration (prepare only; deployment needs approval)

`wrangler.production.example.jsonc` is an unconfigured template for an independent `molis-work-sync-production` Worker and D1 database. It has deliberately unusable placeholders. Do not point it at the Auth database or the website's database. After approval:

1. Create a separate D1 database and private R2 bucket, then copy the template beside itself to `wrangler.production.jsonc`. Set its database UUID, private `BLOBS` bucket name, `AUTH_ORIGIN` to the real HTTPS Auth origin, and `APPLICATION_ID` to the molis-work application ID (not the login client ID). Keep `DEPLOYMENT_MODE=cloud`. Do not enable a public R2 domain or development URL for user files.
2. With the locked tooling in `examples/personal-sync-tools`, use `npx wrangler d1 migrations apply DB --cwd ../../apps/sync-worker --config wrangler.production.jsonc --remote`, then `npx wrangler deploy --cwd ../../apps/sync-worker --config wrangler.production.jsonc`. The explicit working directory makes `node build.mjs` run beside the configuration, not in the tooling directory. These are instructions, not commands executed by this delivery.
3. Configure the trusted molis-work Host environment with `MOLIS_WORK_SYNC_ORIGIN=https://<the-sync-worker-address>` and remove `MOLIS_WORK_SYNC_LOCAL`. Auth configuration must use the same issuer and application as the Worker. No login-page parameter or browser request can choose the destination; redirects never receive the Bearer token.
4. Rebuild/restart the Host and explicitly enter the personal space. Existing per-device consent still applies. This does not move local-space data or reuse data from a different Auth issuer.

Use a canonical origin without a trailing slash, path, credentials, query or fragment. Cloud mode rejects HTTP Auth and non-HTTPS incoming APIs. Local HTTP is only the explicit 127.0.0.1:8788 mode. These configurations do not mean release is ready: remaining owners, complete lifecycle, operational acceptance and real Auth/two-device verification are required. Provider limits remain separate from the product's 100 MB allowance.

## D1 baseline and accounting

The current fresh D1 baseline is **v6**, recorded by `sync_schema.version` in `../../server/migrations/sync/0001_sync.sql`. It includes immutable losing-branch archives, retained-version pins, exact restore-source receipts and 30-day retention of replaced owner graphs. Requests require the exact baseline and never create or alter tables; `fixtures/baseline-v4.sql` and `fixtures/baseline-v5.sql` freeze the old schemas for refusal tests. Earlier databases require separately approved backup and maintenance; re-running an already-applied `0001` does not upgrade them. The local `sync/sync.db` is independently **v5** for parts, receipts, permanent quarantine, protected per-namespace downloads, automatically retried temporary incoming failures and stream cursors; old versions are refused and preserved. No existing user database has been maintained.

`GET /v1/quota` returns `{limitBytes:100000000,usedBytes}` for the authenticated account across projects/devices. Retained non-null canonical UTF-8 values and unique raw blob bytes count; control metadata and null tombstones do not. Completion/reuse/replay never charge twice. A smaller revision still adds bytes while history is retained. Soft deletion retains content for 30 server-clock days; unreferenced reservations become eligible after 24 hours. Capacity is not released until the corresponding persisted cleanup succeeds.

Validation, admission, event/head commit and quota increment share one SQLite statement's triggers. Concurrent writes cannot overbook; failure rolls back. Full clients still pull and send independent tombstones while preserving positive/frozen queues. Permanent format failures are quarantined by asset with durable replay and explicit retry; one bad item does not stop healthy records. Transient lifecycle unavailability is not treated as corrupt content. Explicit retry cannot overwrite a newer head.

The atomic design follows [D1's transactional execution model](https://developers.cloudflare.com/d1/worker-api/d1-database/) and is tested against Miniflare D1, not just a mocked JSON server.

## Delivered boundaries

### Private attachment protocol

`POST /v1/blobs/reserve` accepts `{namespace,digest,size}`. The authenticated space and digest identify one reservation; D1 serializes it against record admission in the same 100 MB ledger. Repeated requests return existing receipts without charging twice. `GET /v1/blobs/status?namespace=...&digest=...` is read-only; downloading never creates a reservation.

`PUT /v1/blobs/chunk?namespace=...&digest=...&part=...` sends raw fixed 4 MiB parts with exact Content-Length. Native DigestStream validates per-part and complete SHA-256. The private key includes account/digest/server generation/part/checksum: an old request cannot commit into or clean up a new generation. `POST /v1/blobs/complete` verifies at most 24 ordered parts and rechecks its generation before returning ready. Free-plan CPU/request acceptance remains a real-environment test, not a Miniflare claim.

Business uploads now include an explicit `attachments:[{digest,size}]` alongside namespace, policyRevision and mutation. D1 refuses a business event if any referenced attachment is missing, incomplete or belongs to another account. Retained events retain these references; the value and reference manifest both participate in idempotency. The authenticated chunk GET returns only ready, rechecked binary data with nosniff, never a public bucket URL.

`SyncContentCodec` is implemented by the content owner. The common engine does not guess fields or open local paths. Artifact projects `original_file.data_base64` to actual raw file bytes, and canonical version bodies to separate blobs when large or containing a file. After download it reconstructs exactly the original immutable payload and its digest; it does not overwrite the source or keep partially applied versions. Small inline values remain a current representation, not an old-format fallback. Unsupported external content references remain refused.

Every cycle permits at most 32 attachment requests. Confirmed upload prefixes and verified downloaded parts persist in the account's local sync database across coordinator restarts, so a large bundle can make progress over multiple manual cycles. The cache is not a new business owner; it is released after owner acceptance, and a revoked lease cannot write to it. An incomplete cycle reports remaining work and does not leave a new manual-mode timer.

### Retention and operations

`POST /v1/history/archive` takes the same declared-content upload envelope as `/v1/changes`. It saves and charges the losing local branch under the inspected current head, without changing that head or entering normal change downloads. Its idempotent receipt must never acknowledge an owner's pending business edit. `POST /v1/history/pin` binds namespace/key/revision/policyRevision and protects the existing current remote event without duplicating its body or byte charge. Pins protect active-asset versions from transport compaction; deletion expiry or explicit confirmed purge releases their references using the same accounting and R2 cleanup engine.

`GET /v1/history/keys?namespace=...&after=...` lists at most 20 pinned asset keys, ordered by the exact SQLite key bytes; its read-only index hides expired/purged assets before maintenance. `GET /v1/history?namespace=...&key=...&before=...` lists at most 20 versions, with pagination and the current head. `/v1/history/version` reads one version and its declared attachments. `POST /v1/history/restore` requires sourceRevision and expected current revision, operationId and policyRevision; its new normal event competes atomically with head changes and source purge. `/v1/history/purge` requires sourceRevision, expected current revision and confirm:true, and cannot delete the current head. All requests derive the account from Auth and recheck policy and server-clock expiry. The existing coordinator and authenticated Host settings routes now use these APIs. Inspection decodes full declared bytes without owner preparation or writes; restoration runs the normal receive/validation path and never directly imports a database. UI restore retries keep the same operation identity and deletion needs a separate confirmation. Semantic comparison and physical-device acceptance remain outstanding.

`GET /v1/trash?before=...` lists 20 account-scoped tombstones with server deletion/expiry times. `POST /v1/trash/restore` takes namespace/key/revision/operationId/policyRevision and restores retained content through the same CAS admission. `POST /v1/trash/purge` requires namespace/key/revision/confirm:true. Restoration and purge atomically compete on the head; expiry is checked even before cleanup. The generic tombstone protocol does not yet implement every owner's nested trash semantics.

Hourly scheduled maintenance is bounded to two heads/two GC jobs plus a five-object orphan scan. Claiming a blob blocks new references; shared live/retained references prevent collection. R2 deletion precedes an atomic metadata/accounting commit, failures persist a retryable job and keep bytes charged. A generation cursor scan collects late orphan writes without touching a replacement upload. `POST /v1/maintenance` provides the same account-only bounded pass, not an administrator clock or arbitrary-path deletion API. Pruned content leaves a minimal tombstone and compact idempotency receipt, preventing old-device resurrection and duplicate charges. Replacing a live graph retains its exact previous graph and attachment references for 30 server-clock days from replacement, including nested removals from non-null aggregates. This retention is visible in cloud history and does not grant execution authority. A pass also removes at most 20 redundant non-head transport bodies after both their age and replacement retention expire; current content and its owner-selected immutable history survive. Upload and replay responses return the committed revision; receipt acknowledgement does not advance a client's download cursor. Final operational acceptance is still pending.

Atomic rate windows bound IP digests before Auth and authenticated accounts to 600 requests/minute; maintenance to 20/minute. A 429 response has Retry-After:60. No token, raw IP, body or asset content is logged by this limiter; obsolete counters are removed after a day. Public release still requires real resource/traffic-budget and failure-recovery checks.

- Pages documents and folders use a durable, transactional per-record queue, delete tombstones, replay-safe operation IDs and remote cursors.
- The setting belongs to the personal space and is stored in D1. Local-only spaces cannot upload. Turning off a collection does not delete data.
- Concurrent edits are retained as conflicts. Explicit local/remote resolution saves both versions in the local replica resolution journal. The coordinator now requires cloud retention first: pin the existing remote version before choosing local, or archive the inspected local content through the same owner codec before choosing remote. It then passes the original inspected revision/state to the owner transaction. Failed retention must leave original, pending edits and conflict untouched; a harmless retained backup is not evidence that a delayed choice committed.
- Artifacts uses an owner-validated bundle per artifact identity containing its immutable inline versions, producer provenance, digest, supersession and archive/unavailable state. Imports use the owner's commands and journal. No producer-specific transport adapter is needed for these inline artifacts; plugin drafts remain separate.
- Goals replicates a project-consistent aggregate of facts, relations, proposals, trusted decisions, Goal-associated ContextLedger references and owned history. Stable event IDs replace local sequence numbers in transit. Receiving facts does not execute proposals or start tasks. Concurrent changes conflict at the project aggregate, not at individual Goal fields.
- The receiving device creates minimal project identity/title when needed; full project metadata, unregistered plugins' private data, installation packages and running tasks are not replicated. Attachments travel only through the explicitly connected content owners.
- References to missing Goals/Artifacts are durably held as **waiting for linked assets** and retried on subsequent cycles. They are never stripped or offered as destructive overwrite choices. Existing disabled plugins and deleted projects are not silently resurrected. An existing destination project with Artifacts disabled must be explicitly enabled before its artifact collection can be received.
- Goal and Artifact project databases have transactional, namespaced queues and receipts. The collection cursor advances only after the target project commits; a crash between commits safely replays its receipt. Host registration order places Goals before Artifacts before Pages regardless of checkbox order.
- Each uploaded D1 record is limited to 512 KiB. Incremental Pages transfer validates only the selected document/folder; the separately exposed snapshot pilot has a 1,000-record/16 MiB bound. Artifact bundles include all versions (at most 1,000); their owner projects imported raw file bytes and large immutable bodies through R2, then restores the exact original digest and local record before committing. Connected owners use content slicing up to the common 100000000-byte aggregate ceiling, still constrained by domain limits and remaining account quota. Unknown external references and over-limit content fail without truncation; permanent item errors are isolated while healthy assets continue.

Large Goal units also use the existing owner content codec: values above 64 KiB are split into 1 MiB content-addressed byte blocks, while D1 keeps the bound project/space and whole-body digest. The 100000000-byte owner bound does not bypass account quota. Every block and the full body are checked before creating a target project or atomically applying its facts. This is transport partitioning, not independent per-block conflict resolution. Other owners retain their current bounds.

Before public release: resource approval, real traffic/quota/CPU and cleanup failure acceptance, all-owner attachment integration, complete project lifecycle and independent multi-device production acceptance are still required. Local rate limiting, reservation expiry/reference cleanup and transport compaction are implemented but do not establish production readiness. This is not an all-asset personal edition.

## Operational acceptance and recovery

This is an operator procedure, not proof of a deployed service or permission to maintain a real Home. Record the exact build, Worker version, Auth issuer/application, D1 UUID/baseline, private R2 bucket and test account before a drill. Never substitute the Auth database for the sync database. Remote changes, exports of real account data and recovery need explicit approval.

### Free-plan release blocker

Official limits checked on 2026-10-19: [Workers Free](https://developers.cloudflare.com/workers/platform/limits/) has 100,000 daily requests and 10 ms CPU per HTTP invocation; [D1 Free](https://developers.cloudflare.com/d1/platform/pricing/) includes 5 million rows read and 100,000 rows written daily. A [Free D1 database](https://developers.cloudflare.com/d1/platform/limits/) is limited to 500 MB. [R2 Standard](https://developers.cloudflare.com/r2/pricing/) has a separate monthly free allowance; it is not an unlimited bucket. The application's 100 MB/account is unrelated to these account-wide limits.

The former coordinator performed `3 + N` requests in an idle round for `N` selected collections. The current `/v1/round` returns format 1 with policy, quota and the latest ordinary event revision for each selected namespace, using the existing event index. Archive-only events do not wake normal downloads; tombstones do. The client validates the entire summary before caching policy and treats heads only as hints, never as receipts or cursor advances. A server head below an already consumed cursor refuses the round rather than treating a database rollback as empty history. A policy changed during the server read refuses instead of disclosing stale selections.

An unchanged round now takes **one authenticated sync API request**, independent of the 26 selected collections; attempted writes still trigger a final quota read. At the unchanged 15-second interval, continuously idle operation is **5,760 sync API requests/day/device**, rather than 167,040. Auth introspection still happens for every request, and each admitted API request still updates two D1 rate-window rows. Tests cover 26 idle selections and actual Host/Rust/D1/R2 settled-project request counts; the isolated Worker suite passes 40/40 tests with no skips. These are code-derived budgets and local integration measurements, **not Cloudflare Free CPU or production capacity acceptance**. Repeated two-device/free-plan measurement remains necessary; authentication and rate limiting have not been disabled.

### Monitor without collecting private content

- `/health` checks the Worker entry only; a 200 does not prove Auth, D1 schema, R2 or a particular account is healthy. Use an approved dedicated account for authenticated policy/quota probes, and a disposable asset for a full upload/download/delete probe. Do not probe with a person's real content.
- Watch HTTP 401/403 (identity/scope), 409 (stale policy or CAS), 429 (rate budget), 5xx, exceeded CPU, D1 row usage/storage and R2 operations/storage. Set a named responder and notification destination before release. Alert wiring is not configured by this README.
- For cleanup, record pending job count, oldest pending age and bounded pass result from `sync_gc_jobs`; never print tokens, raw IP, payloads, keys or object bodies. Successful maintenance HTTP does not imply the backlog is empty. A failed R2 delete must retain the job and charged bytes; retry the same generation rather than manually deleting ledger rows.
- If a budget is near exhaustion, explicitly disable automatic sync on affected test devices and keep local queues. Do not silently turn a failed round into “synced”, recreate databases, increase the product quota, or switch to paid resources without approval.

### Backup and restore are a matched D1/R2 operation

1. Approve a maintenance window. Set the operator-only `SYNC_WRITE_MODE` binding to `read-only` on every serving Worker version; the normal value is `read-write` (also the default when absent). Authenticated non-GET requests, including policy updates, binary uploads, restore/purge and manual maintenance, return 503 `SYNC_READ_ONLY` with `Retry-After:60`. Scheduled cleanup skips; malformed values fail closed with `SYNC_INVALID_WRITE_MODE`. Auth and existing rate checks remain active, and read-only business downloads remain available. Request bodies cannot change the operator mode. This source/config support does not change any deployed service.
2. **Drain and verify in-flight work before taking a recovery point.** The binding affects newly admitted requests; a request or scheduled pass already admitted on an older version can still complete. Stop/observe those invocations across all versions and verify mutation refusal and no business/attachment changes before exporting. Merely updating one deployment, stopping one desktop, or receiving a `/health` 200 is not proof of quiescence. Rate-window control rows may still change during authenticated reads; business records and object generations are the paired-backup boundary. Live rollout/draining has not been rehearsed.
3. Save a D1 bookmark and export the exact sync database with the locked Wrangler toolchain. The documented [D1 export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) command is `wrangler d1 export <database> --remote --output <new-backup.sql>` with the approved config. Choose a new, explicit destination; do not overwrite an existing backup. Treat exports as private account data.
4. Pair that database point with private R2 object copies, recording complete keys/generations, sizes and hashes. Objects must survive until the paired backup expires. A D1 export or Time Travel bookmark alone cannot recover bytes already collected from R2. No R2 backup/copy job has been configured by this repository.
5. Restore first into separately approved isolated resources, never over the running production bindings. Verify exact baseline v6, account isolation, owner-validated records, attachment bytes/digests, retained histories, quota/reference accounting and idempotent receipts. Use fresh client Homes to avoid combining post-backup cursors/outboxes with older server events. Do not rewrite a real device's cursor or replay log by hand.
6. Test fresh writes and replay, interrupted uploads, conflict retention, restoration and failed GC before switching any production binding. Record object/database recovery points and the recovery time. Explicitly restore `read-write` only after approval and verify new writes and cleanup resume on the same ledger/generations. Do not clear the original resources until the isolated recovery is accepted.

[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) is automatic, but the Free retention window is **7 days**, not this product's 30-day recycle retention. Its restore overwrites a database in place; never run it casually on production. A database-only rollback is not an attachment or local-Home recovery strategy.

### Credentials, local keys and escalation

Cloudflare deployment/API credentials belong to operator secret storage, not this repository or frontend. Sync uses Auth-issued user credentials; changing an Auth issuer/application creates a different ownership boundary, not a migration. Revoke a compromised login/session through Auth and verify old requests cannot commit before reopening sync. Worker/D1/R2 operator access must be separately controlled.

For a local protection-key failure, stop that account's loop, preserve the complete affected Home and original key-store state, and surface the refusal. Do not regenerate a key beside existing ciphertext, delete a queue, clear protected history or copy another account's Home over it. A new device may fetch cloud content under its own keys after approval; it cannot recover an unsent local-only version from the cloud. Actual key-loss/backup recovery and two physical devices remain acceptance work, not a completed drill.
