## 页面录入改由 Issue 自己起标题（BL-149，2026-10-19 起草）


该项已由 [#819](https://github.com/molis-ai/molis-work/pull/819) 合入 main（`c679dc172`）。以下保留当时的问题、决定与验收要求，[命名评测原文](capture-evaluation.md)记录了当时的样本、判定与局限。

**问题。** 页面录入现在交给个人助理。页面先 `issues.prepare` 存草稿，再经 `/api/assistant/send` 发「录入草稿 <ID>」，带上方法 `issues-capture`。助理起标题、判类型，用 `change-reversible` 调 `issues.capture` 存好（`capture-client.ts` 的 `sendWork`、`watch`）。

一次调用就存好，靠的是方法正文里写死的宿主用法：
- `methods.ts` 的【页面录入】写着不要 find-capabilities 和 read-capability、直接 change-reversible、被拒就改 suggest-action。
- 【页面重新整理】写着只用 suggest-action、不调 capture 和 change-reversible。
- 【普通对话】写着 change-reversible，被拒改 change-capability。

怎样找能力、哪些动作不经确认、被拒之后怎么办，是网关和宿主的规则（手册 13.1）。宿主一改，方法就和宿主说的不一样。

页面录入也用不着助理那一层：
- 每次录入都在助理里留一条工作，页面要再把它停掉、归档（`quiet`）。
- 页面要按工作状态、卡片和提问去猜结果（`watch`）。

**决定（起草）。** 页面录入和重新整理不再经助理。Issue 在自己的动作里调一次有界模型，只要标题和类型；要写入时由插件自己写。
- **ISSUE-50** 录入：新动作 `issues.name_draft@1`。
  - 声明：command，`scheduling: "concurrent"`，权限 `issues:write` 加 `model:invoke`，只给 `user` 调。
  - 读草稿的原文和截图，经 `services.model.complete` 调一次模型，`output: "json"`。截图只在所选模型声明 `vision` 时作为 `images` 传。
  - 插件检查返回的形状：标题长度、类型枚举。依据不足时返回一句追问、不写入。
  - 只有截图、没有文字，而所选模型没有声明 `vision`：不调模型，返回固定的一句追问（写一句话说明问题，再整理），不写入。有文字时照常起标题，截图不附，传给模型的数据里写明没有附。
  - 标题用什么语言由代码定：描述里没有中日韩文字、且有英文字母，`title_language` 为 `en`，否则为 `zh`；它放在传给模型的数据里，规则要求照它写，模型不自己判。
  - 写入：`beforeEffect()` 之后，按读到的草稿版本走 `issues.capture` 的写入路径，一次写好。写入人取调用上下文里的 actor，不从输入或模型输出读（③ 10-19 的要求）。
  - 页面行为照 ISSUE-35～41 不变：输入框立刻清空、可以撤销；要补充、模型不可用、超时都留在列表顶部，点开是带原文原图的编辑器。
- **ISSUE-51** 重新整理（ISSUE-48 改走这条路）：同样调一次有界模型，只返回标题和类型，填回编辑器，不写入；由人点保存，走 `issues.update`。ISSUE-49 的「迟到结果不能写回」不变。
- **ISSUE-52** 规则只有一份：标题、类型、依据不足的规则文本放在一处。
  - 作为 Issue 自己登记的指令（`defineInstructionPrompt`，在目录条目上声明），人在「Prompt 与 Character」里看得到、改得了。
  - 方法 `issues-capture` 也从同一份文本拼出来。
- **ISSUE-53** 方法 `issues-capture` 升 v11，只留业务规则：Issue 记什么、标题、类型、依据不足时追问、普通对话里记问题用 `issues.create`、修改和删除先读版本。去掉【页面录入】【页面重新整理】两段和所有工具用法（③：页面录入改完后，方法里只留标题和类型的规则）。
- `issues.capture` 的调用方去掉 `agent`，只剩页面（手动保存 `keep` 仍用它）。这是动作合同变化：跑 `pnpm actions:update`，PR 里写影响，助理不再能调它。

「每次确认」不需要另定。用户设了 AI 改动每次确认时，现在的页面录入会落成卡片（`watch` 的 card 分支）。那是因为它走了助理的网关，不是 Issue 的规则。改成插件自己的动作后，写入是人按下「记录」那一下发起的，模型只填标题和类型，保存仍可撤销，和首期决定「记录不再等确认」一致。插件在自己的动作里调模型、写入结果，是平台现成的做法（问卷起草、Feed 规则）。这里按推荐项定，理由记在此处。

这一节取代 ISSUE-48 的「沿用现有助理建议卡…不新增后端、数据库或动作合同」和 ISSUE-36 的「标题和类型来自助理」；旧记录保留。

## 目标与依据

### 首期体验重构（ISSUE-35 至 ISSUE-41，2026-10-12）

用户目标（2026-10-12）：团队成员边用 Molis Work 边迭代它，Issue 是开发时用的。任何时候都能轻便唤起、以最短路径录入、能看到自己记过的全部 Issue；体验顺滑，界面没有冗余的按钮和字，清晰极简但不丢必要信息、不让人产生歧义。用户接受重构 Issue 与整个侧栏，要求审视助理能力与提示词，并从这个场景做全面验收。

**审视发现的问题**（V0 合入 main 的版本，在隔离 Home 实际操作与读代码得到）：

1. 唤起：只有右上角按钮，没有快捷键；打开后键盘留在按钮上，要再点一次输入框；第一次打开侧栏要等文档加载。
2. 层级与冗余：侧栏页签「Issue」里又套「记录Issue / Issue列表」两个页签，同一个界面挂载两份；录入区有「问题描述」标签、占位、一行图片说明、`0 / 6` 计数、「助理会建议标题和类型，确认后保存」、「模型设置」链接、「交给助理整理」「手动填写标题和类型」两个按钮，状态切换后还有「重试整理」「修改描述和图片」「停止整理」「补充描述」「核对保存结果」「再记一条」「刷新详情」。
3. 最短路径：交给助理整理 → 等模型（两轮：先 `find-capabilities` 再建议）→ 核对确认卡 → 确认并保存，至少两次点击加一次等待，期间描述被锁住，不能接着记下一条。
4. 信息：记录不知道在哪个页面记的——页面上下文取自 Issue 侧栏自己的地址，所有记录都写「Issue」；列表行只有标题和类型，没有时间和截图数。
5. 助理：每次整理在助理工作列表里留一条「请按 Issue 方法整理录入草稿 <uuid>…」，并发「做完了」「在等你回答」通知，底栏出现「等你 1」；问题解决后旧工作仍在等待。描述在主消息和材料里各传一遍。方法没有说明普通对话里怎样快速记一条。

**决定**（用户接受重构；以下覆盖 ISSUE-14、19、32、33 中与此冲突的旧决定，旧记录保留以便追溯）：

- 一个视图：输入框在上，「我的 Issue」在下；打开一条记录时详情替换列表，返回回到原处。去掉内层页签、整理中的各种按钮和说明文字；侧栏、整页和工作台舞台用同一个视图。
- 记录不再等确认：⌘↵ 发出后输入框立刻清空、可以接着写；Work 助理在后台起标题、判类型并直接保存。保存可撤销（新动作 `issues.discard@1`，只删记录后没改过的记录），所以按平台规则助理可以用 `change-reversible` 直接执行，工作里留「撤销」，页面提示「已记录：标题 · 撤销」。撤销把原文放回空输入框。用户在能力设置里要求这类保存每次确认时，退回确认卡，页面显示为预填好的编辑器。
- 没完成的不丢：要补充、模型不可用、超时、参数一直不对时，这条留在列表顶部并写明原因，点开是带原文原图的编辑器，可重新整理、手动保存或放弃。超时先撤销草稿，迟到的结果不会和手动保存的并存。侧栏收起时，右上角按钮用点标出整理中（铜色）和需要处理（琥珀色）。
- 编辑里不再有「让助理重新整理」：已保存的记录直接改标题和类型；`issues.prepare` 去掉 `target`，一份草稿只能变成一条新记录，撤销也只能撤回这一条。版本冲突不再并排对照：读回最新内容，把自己改过的字段放在上面，提示核对后再保存，不丢修改。
- 唤起由外壳负责：Home 工具在目录项声明组合键（Issue 为 `Mod+Shift+I`），外壳在页面和同源框架里都接得到；从视图里再按收起；按钮也是开关；打开时键盘直接进输入框；带组合键的视图空闲时预载。没发出去的文字留在本机（`localStorage`），换页面、换项目后还在；还没完成的录入也留文字和等待的原因，回来时仍列在顶部（截图要重新添加），期间已被助理保存的自动消失。截图只在当前页面保留。
- 记录位置：侧栏宿主向视图报告外壳当前的位置（地点名与项目名、地址），草稿带着它，保存为 `context.page`（`client_reported`）；详情显示「记录于 …」。
- 助理：方法 v9 一轮完成、先看依据够不够、不先发现能力；标题与类型规则更具体（语言、长度、写什么不写什么、截图与所在页面怎么用、拿不准时怎么选）；普通对话里「记个 issue：…」用 `issues.create` 直接记录（也可撤销）。页面发出的消息只说「请按 Issue 方法处理」。页面拿到结果后把这次工作归档并清掉通知；需要补充、确认卡、失败时 Issue 行是继续的唯一地方，页面显示它时就停止并归档那件工作；工作标题改为「记录 Issue：首行」。

**合同影响**（`pnpm actions:update` 的输出）：`issues.prepare` v2 → v3（去掉 `target`，加 `page`）；新增 `issues.discard@1`（受众 user、agent）；`issues.capture@1` 受众去掉 mcp 并声明撤销，`issues.create@2` 声明撤销，二者 input/output schema 不变、未升版本——`capture` 需要只有页面能准备的草稿，MCP 从来调不成；`create` 的调用方看到的输入输出不变，撤销声明只让助理可以直接执行。新增路由 `/capture`、`/discard`。插件 SDK 与 contracts 的公开 API 不变。

同一次实测发现并修好的两处问题：

- 未完成草稿的上限：插件最多留 8 份未完成的草稿，满了就拒绝新的录入。页面已经不在的草稿（换了浏览器、清了本机数据、反复测试）用户看不到也清不掉，连手动保存（也要建草稿）都会被挡住 2 小时。现在满了由最早的空闲草稿让位，它的页面若还开着，会发现草稿失效、照常可以手动保存（`tests/issue-capture.test.ts`）。
- 同一件事两处等你：要补充时 Issue 行写「需要补充」，底栏同时显示「等你 1」；在助理里回答后，Issue 行也不会自己消失。现在页面显示待处理行时就停止并归档那件工作，Issue 行是继续的唯一地方（`tests/issue-capture-page.e2e.test.ts` 断言助理里没有在等的工作和通知）。离开页面再回来，待处理行保留原来的原因（如「需要补充：…」「模型暂时不可用…」），不再一律写「上次没有完成」。

还留着的：模型偶尔多一次被拦下的读取；同一输入两轮的标题措辞不同（都可读，可编辑）；「111」约六分之一不走 ask-user，页面退回「没能自动整理」，点开同样能补充后重新整理。平台守卫不认 Issue 的「已记录」，另作后续处理。

**输入法、跨应用粘贴与桌面壳**（ISSUE-41 中能在本机验证的部分）：

- 讨论：讨论是另一个应用的框架，本机 Host 发它的脚本时附上同一段转交，在讨论里打字时按 ⌘⇧I 也会切到 Issue 并把键盘放进输入框（`tests/issue-global-navigation.e2e.test.ts`）；共享服务器上的讨论页不变。顺带修了一处：在页面没有焦点时唤起、再从 Issue 里收起，键盘原先会留在正在隐藏的侧栏里，现在离开侧栏。
- 输入法：在 Issue 输入框里用 CDP 真实的输入法组合（`Input.imeSetComposition`），组合中按 ⌘↵ 和输入法自己的回车（键码 229）都不发送，确认候选后 ⌘↵ 发出的正是输入框里的字，只发一次（`tests/issue-capture-page.e2e.test.ts`）。底栏的 `assistant-dock-ime` 用例在本机失败与 Issue 无关：同一串按键在一个不挂任何产品代码的空 `<textarea>` 上也得到 `ceshi测试`——这是 Chrome 155 收到合成的回车时自己先确认了拼音；不发合成回车时确认候选得到 `测试`。用例已改成分两段：先在组合中按回车，核对不发送且回车确实到达输入框；再另起一段组合，确认候选得到 `测试`；原有断言一条不少，去掉底栏的组合判断仍会失败。
- 跨应用粘贴：用 `osascript` 把一张 PNG 放进 macOS 剪贴板（等同别的应用复制），在有界面的 Chrome 里对 Issue 输入框按真实的 ⌘V，图片进入并显示「1 / 6 张截图」。无界面的 Chrome 用自己的剪贴板，读不到系统剪贴板，所以自动化用例里仍用合成粘贴。
- 桌面壳：Tauri 外壳只建了托盘菜单，没有给任何菜单项绑 ⌘⇧I，按键会交给页面；WebKit 没有 `requestIdleCallback` 时预载退回立即执行。桌面版本身没在本机构建（Swift 工具链坏了），按键在桌面壳里的手感仍请用户确认。

## 顺序与责任

1. 平台：复用 Runtime、Supervisor、Action Registry 和本机唯一执行进程，增加一次 Home 装配。安装身份、授予、启停、路由、数据库连接归 Host。
2. 平台：提供受当前安装与权限约束的 SQLite 服务；插件声明当前基线并拥有业务 SQL。数据库路径由可信 Host 决定，升级不自动迁移旧库。
3. Issue：在 `plugins/native/issues` 实现 schema、查询、原子增改删、动作、页面与方法说明。标识 `io.molis.work.issues`，业务数据 `{home}/issues/issues.db`。
4. 接通页面、Work 助理与 MCP 对同一 Home 动作的发现、授权与调用；用隔离 Home 验证真实链路，再交用户试用。

平台补丁和插件补丁保持可独立审阅的文件边界；不等待 Form、Todo 完整迁移，不改变它们的现有实现。

## 复杂度与范围

当前必须：Home 安装记录与生命周期、统一 provider 定位、SQLite 当前基线、授权和取消检查、条件写入版本、三入口接线及失败反馈。缺少它们会导致无项目不可用、项目切换分裂数据、旧实例继续写入或并发覆盖。

复用：已有 Runtime、Supervisor、权限检查、动作与路由适配、UI 壳及本机单进程转发。项目插件继续按安装 ID 定位；Home 内置插件以稳定插件 ID 发现，同时保留 install_id 和 installation_generation 约束执行。

延后：Form/Todo 迁移、完整统一注册表、完整方法系统、模型服务抽象、团队同步、被动环境采集、历史迁移与分析。用户自行在电脑上截图；产品内截图、屏幕共享或对截图来源的限制不在范围内。

不采用：假项目、业务 JSON KV、Issue 专用 Host HTTP 分发器、冻结的构建期动作清单、异步回调内持有 SQLite 事务、未知提交后的自动重放。

## 数据与调用约束

- 记录标题、类型（bug / experience / feature）、原始描述、上下文与来源。类型不替用户默认；保留描述空白与换行。
- Host 绑定当前 Home 所有人与入口身份，输入不接受 actor、install、provider、创建时间等可信元数据。页面上下文区分 Host 可验证值、调用方陈述与用户修改；MCP 没有 Work 页面时允许为空。
- 列表有界分页、排序稳定；修改与删除要求 expected_version，在数据库中条件写入，冲突不覆盖。
- 所有写入在事务前执行 beforeEffect，并复查当前安装授权；同步事务内不等待。停用、撤权、取消后拒绝写入，错误不得伪装成成功。
- UI 出错保留草稿和当前选择，删除先确认。助理缺标题或类型时询问，最多约两轮，不编造上下文。
