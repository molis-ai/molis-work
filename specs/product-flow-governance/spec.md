# 全平台产品与架构治理：系统性审查和优化

状态：专项需求与核查计划已整理（2026-10-27），全面核查与整改尚未开始。本轮只完善需求书与索引，不改产品、权限政策或工程门禁。需求维护负责人：Codex；专项执行负责人：待分配；各模块和在途需求保留原负责人。专项最终目标完成程度为**内部完整**：全平台各项功能及跨功能路径经过系统核查和必要优化，真实工作能够连续完成、修改和恢复，用户只承担有实际意义的决定。建立专项不代表问题已复现、根因已确认或整改已完成。

2026-10-27 用户明确：**整个平台所有地方都需要系统性审查和优化。** Onboarding 是已暴露问题的入口和首条实走路径；专项覆盖所有功能、交互、设置、入口及其背后的公共机制，既查已反馈的问题，也主动发现尚未报告的不合理设计与体验缺口。

## 1. 为什么单独立项

用户在实际 Onboarding 中已填模型、已读材料，却在选择、返回、范围确认、生成失败和进入项目之间失去连续性；真实代码文件夹只识别出部分文件，遗漏原因也看不清。问题超出了个别按钮或文案：需要核查内部模型是否被直接变成用户步骤，阶段依赖是否过严，检查与审查是否重复、过早或没有必要。

本专项以用户要完成的工作为起点，同时检查功能定位与完整性、信息组织、视觉交互、产品路径、状态与内容依赖、AI 效果、公共能力和开发约定。架构应承担内部协调，让用户能理解结果和影响；不能让用户替平台搬运材料、重建上下文、解释内部状态或反复证明已经表达过的意图。

与既有工作的关系：

- [架构防腐](../repository-anti-corruption/spec.md)继续处理事实归属、依赖和平台边界。本专项核查这些实现怎样影响实际使用；代码分层合规不能单独证明流程顺畅，新增层次或状态也不是默认解法。
- [Onboarding](../onboarding-coverage/spec.md)拥有具体引导行为。本专项以“已有文件夹 → 材料可用 → 模型整理 → 项目内继续工作”为第一条贯穿路径，找出共性原因，再由原主人修正需求和实现。[PR #1320](https://github.com/molis-ai/molis-work/pull/1320)中的场景、团队与新交互首页仍是独立需求；基础路径可靠应先于扩大这些体验，不能用新功能掩盖旧路径断裂。具体材料带入优化与 ONB 验收继续编入原 Onboarding 需求书；本专项不复制第二份功能需求，也不要求其等待全产品核查完成。
- [服务接入](../assistant-service-connections/spec.md)拥有服务连接页面和对话接入的具体行为；默认直接连接、真实可用与跨入口复用要求写回该需求 §8.1。本专项核查把技术接线转嫁给普通用户的共性问题，覆盖全部服务。
- [视觉体验](../visual-ui-experience/spec.md)、[AI 交互](../ai-interaction-experience/spec.md)、[快速创建](../quick-create/spec.md)继续拥有各自体验要求；本专项补齐跨入口、跨阶段与跨插件的连续工作核查。
- [插件创作工作台升级](../plugin-builder-upgrade/spec.md)继续拥有创作、试用、安装、持续修订和 Alchemist 场景的完整交付；本专项检查其中的流程负担和公共机制，不把它与 Onboarding 合并，也不把本专项全量结束设为该线开工前提。
- [真人批准门](../agent-approval/spec.md)、[Coding 质量保证](../coding-quality-assurance/spec.md)、[AI 开发手册](../ai-development-handbook/spec.md)均纳入适用范围复核。已经写成规范或已有测试不等于永远合理；需调整的政策提出具体替代方案，不在本轮静默修改。

## 2. 核查范围

| 方面 | 要查什么 | 应得到的结果 |
| --- | --- | --- |
| 功能价值与完整性 | 每项功能为谁解决什么、入口是否可发现、结果能否继续使用；功能重复、缺环、名实不符或长期只到切片 | 明确保留、合并、补齐或重做的方向，按完整工作交付，不只消除报错 |
| 视觉、交互与响应 | 信息层级、术语、布局、操作一致性、键盘/读屏、语言、窄窗口、大内容量、等待与反馈 | 用户找得到、看得懂、操作有效；默认配置合理，性能和异常反馈支撑实际任务 |
| 暴露给用户的内部逻辑 | 内部 id、状态码、模块名、存储分区、运行时绑定、内部前置任务；用户是否必须理解它们才能操作 | 区分真正影响选择的信息与实现细节；前者用工作语言讲清，后者由系统处理或留在按需诊断中 |
| 流程与状态衔接 | 新建、返回、跳过、修改、取消、重试、重启、切项目和外部授权返回；跨表面是否引用同一份实际进度 | 当前对象、选择、草稿、已完成结果和下一步保持一致，不因换入口失效 |
| 内容与能力依赖 | 文件发现、类型支持、读取、解析、生成、保存、索引、工作目录、模型和连接；哪些是真的前置 | 可独立完成的工作能先完成；只让真实依赖阻塞相应操作，不把后段能力缺失扩成全程不可用 |
| 检查、确认与审查 | 相同范围重复授权；可逆本机操作与对外/破坏性操作是否同等拦截；模型失败后是否重新审批；预览、确认、采用是否只是重复点击 | 每次打断都有新的、具体且必要的用户决定；已有有效委托与配置可复用，必要的自动检查继续由系统承担 |
| AI 的工作方式与效果 | 上下文是否足够、理解和结果质量是否可用、工具与能力是否真正接通；过细的固定步骤是否替代目标理解，有材料和工具仍要完成无关问卷或审查才能开工 | 遵循手册的 context over control：给足目标、事实、能力、约束与反馈，允许在授权内选方法；确定性代码负责真实边界与一致性 |
| 架构与开发约定 | 为门禁数字拆出无业务价值的层、重复校验和解析、重复状态、重复评审、重复验证；缺陷是否被“再加一道检查”补偿 | 保留能证明用户结果和边界的机制，合并或删除无收益的重复；不把工程程序转嫁给产品用户 |

### 2.1 全平台覆盖范围

以下按用户工作分组，是核查起点而非固定白名单。执行时对照 [SSOT](../../docs/SSOT-MATRIX.md)、[包登记](../../scripts/workspace-packages.mjs)、实际插件 Manifest、动作目录、导航和设置声明，展开到当前产品提供的全部功能及入口；产品中新增或发现的功能也纳入。不能只抽查几条主路径，更不能以逐页能打开、逐插件能点击替代完整覆盖。

| 领域 | 必须纳入的表面与工作 |
| --- | --- |
| 安装、启动与日常运行 | 安装/更新、首次到达、重开、休眠唤醒、后台任务、版本与数据恢复；缺环境或权限时怎样继续 |
| 工作台与项目 | Home、个人空间、项目创建/切换/管理/删除、导航、侧栏、主区、浮层、搜索、通知、快速创建和跨入口返回 |
| 全部设置与授权 | 全局、项目、角色、插件和任务配置；模型、目录、连接、权限、默认值与覆盖、保存生效与后续修改 |
| 个人助理与 AI 协作 | 对话/输入、上下文与记忆、角色/团队、工具与 Skill、委派、人工干预、结果交付、持续工作与恢复；规划能力单独核需求 |
| Coding 及开发路径 | 文件、工作目录、代码执行、Git、Diff、计划与变更审查、协作、测试和交付；从已有目录到可用成果 |
| 材料、知识与内容 | Files、Shelf、搜索/知识、Pages、成果库，以及导入、编辑、引用、生成、版本、导出和跨插件流转 |
| 目标与个人工作 | Goals、待办、Inbox/Feed、Issues、Jelly、灵光、Cognia 等当前功能；从捕捉到处理、完成、归档与再次使用 |
| 创作与数据工具 | Forms、Dataset、PPT、Images 及其他实际插件；真实内容的创建/生成、编辑、预览、保存和交付 |
| 自动执行与外部连接 | 工作流程、Schedule、规则/判断、监听和提醒、连接器/MCP/OAuth；配置、触发、运行、停用、失效与补跑 |

| 其他入口与平台支撑 | Desktop、Web、CLI、MCP 及实际存在的外部入口；动作、身份、授权、存储、同步/交换、运行时、日志诊断与发布支持对上述工作产生的影响 |

每个功能既查自身是否合理、完整和好用，也查与其他功能的组合、内容交接和切换；平台公共服务沿实际消费路径追查，不仅看模块代码是否合规。当前不存在或尚不可用的规划功能核查需求、架构与依赖，不能虚构实操；缺账号、设备或授权的实际功能标为待验证，不能悄悄从范围排除。

### 2.2 怎样证明覆盖完整

先用现有目录形成简洁的功能与路径对应关系，放在本专项的核查记录中，引用原需求和问题编号即可，不另造功能注册表、状态平台或永久流程。每个实际功能都要有核查去处，包含功能本身、相关入口、跨功能接点和已有证据；“未检查”“未验证”“已检查无问题”“待优化”“已验证”不能混为一项完成。

按功能适用性检查初次使用与日常继续、空/加载/大量内容、返回修改、取消重试、权限变化、失败与重启恢复；不机械穷举无关组合。共用机制可复用证据，但仍核对各消费者的差异和真正接入情况，不能用 Onboarding 或任一插件通过代替其余区域。核查深度按风险与真实复杂度安排，全平台覆盖范围不因此缩小。

“本机优先”意味着普通个人工作有直接路径；共享、发布、跨项目和外部服务所需的决定只在相关场景出现。真实数据位置、使用的模型、外发范围、费用和不可撤销影响可以是用户需要的信息，不能为了界面干净一概隐藏。

## 3. 每个障碍怎样判断

对遇到的步骤、阻断、检查或审查，回答四件事即可：它保护什么或解决什么；此刻缺少哪个事实/决定；用户此前是否已给出有效答案或授权；怎样在不损害目标的前提下少打断、晚询问或直接完成。引用真实失败、合同或信任边界，不以“防止万一”“规范要求”单独作为必要性证明。

| 处理方式 | 适用条件 |
| --- | --- |
| 删除 | 没有独立用户价值、没有实际依赖，也不承担真实边界；包括仅重复先前选择的确认 |
| 合并或自动完成 | 同一次意图、同一作用范围已经明确，系统能根据现有事实完成协调；机器仍可执行必要的一致性与权限检查 |
| 按需出现 | 只有特定能力或效果需要；不要求所有人先把高级配置、连接和团队流程走完 |
| 保留并改好表达/恢复 | 确实需要用户作出尚未作出的决定，或当前操作存在真实不可恢复影响；显示具体对象、范围、后果与继续方式 |
| 待核实 | 只有症状或历史记录，没有当前可达路径与根因证据；先补证据，不据此增加规则或删除保护 |

一次授权可以覆盖一串同范围的动作；进入新的权限、对象范围或效果时，再依据实际差异处理。不同信任边界的自动核对可能都必要，不能简单按“检查次数”删除；也不能因为后端需要再核对就要求用户重复点一次批准。

对 [agent-approval](../agent-approval/spec.md) 等既有方案，重点核对“任何 Agent 修改都需批准”、团队多票要求及默认值是否适用于个人本机工作，用户显式委托与后续批准如何衔接。核查可以质疑并提出修改这些政策；本需求不自动撤销已有用户决定，不授权绕过现有强制边界。需要改变规则时，交付具体规则差异、适用场景和验证证据，再按已有授权处理。

治理本身保持轻量：不新建审查平台、评分体系、总控状态机或“所有功能再过一次”的永久批准门；不设删掉多少检查、减少多少状态的数量指标；不为治理要求每项任务都生成额外报告。已有有效验证复用，只有变更或未解疑点才补验。

## 4. 对连续工作路径的要求

以下原则适用于全平台。材料导入是已有具体线索，其他功能需用自己的输入、过程、结果与恢复路径落实同样要求；不能把下面的材料例子当作核查边界。

### 4.1 从用户结果倒推依赖

先描述用户想做成什么、现有输入和预期落点，再核每个步骤是否必需。文件夹已选、模型可用、目的明确时，应能开始相应工作；运行时、来源、项目库与插件间的连接由产品协调。缺少一项能力只影响依赖它的部分，不能让草稿、已读材料或其他可用工作一起消失。

对 AI 工作，把“已读材料”“生成了摘要”“已保存进项目”等事实分别核实；一次生成失败不能把所有阶段都改成笼统失败。必要状态可以保留在实现中，用户看到的是已经得到什么、正在做什么、缺什么、能怎样继续。不要为了简化界面把事实抹平，也不要为了让状态机容易写而禁用合理的返回与修改。

### 4.2 修改、失败与恢复

更换模型、缩小范围、增补材料、改变输出要求时，只重新处理受影响的工作。未受影响的读取结果和人工内容继续有效；使用哪一份材料生成的结果应可辨认。取消、关闭与重启之后，用户无需重新选齐全部东西才能接续。

按钮触发后有进度、结果或具体缺项，不静默拒绝。错误说明失败发生在哪、已完成部分是否保留、下一步能做什么；技术细节可展开，不用一条“失败或超时”代替判断。无法确定外部操作是否已成功时先核对结果，避免重试造成重复效果。

### 4.3 真实文件夹与内容完整性

真实代码项目应覆盖常见源码、配置、脚本、文档与无扩展名文本；混合材料还包括需要解析的办公文档、图片和其他附件。核查“发现文件”“支持读取”“能够理解/解析”“带入项目”四层是否被混成一个成功数字。

默认忽略依赖目录、构建产物或版本控制内部文件可以合理，但规则、遗漏范围与影响要可查看。因类型、大小、权限、编码、损坏或数量限制未处理的文件有真实原因和后续处理方式，不静默消失、不冒充空目录。无法解析的文件是否可以保留原件/引用，应按其实际用途决定，而非一律排除或假装读懂。

材料、摘要和项目内容各有实际主人；采用必须带上此次有效材料和结果，并能在项目里打开。导入材料与 Coding 工作目录的关系在同一条路径中说明并接好：能沿用的选择沿用，需要另作决定的地方只问真正的差异，不把所有材料目录自动变成执行目录。

### 4.4 服务连接应交付可用账号与工作能力

服务连接是第二个明确的治理案例。用户要连接账号并完成工作，平台应承担默认接入方式、必要应用配置、回调、能力发现和内部接线；用户只在必要时登录、选账号、授权或提供确实不可替代的信息。普通路径要从服务名称和用途走到实际可用结果，技术配置仅在自定义接入与高级诊断中按需出现。

审查不能止于把 OAuth 等术语换成中文或增加“连接”按钮；要追查为何默认路径未就绪、连接后为何还需跳其他模块重复配置，以及这些负担由哪个事实主人消除。产品未准备好的默认接入保留为产品缺口，不转记为用户尚未完成设置，也不能用某个服务的成功掩盖其他服务仍只有技术表单。具体行为与 ASC-45～50 由[服务接入需求](../assistant-service-connections/spec.md)承接，既有权限边界继续适用。

## 5. 第一批线索与证据边界

以下是 2026-10-27 用户实际使用报告，尚未在当前版本重新复现；都是核查入口，不是已确认的代码根因。第一条是材料进入项目的完整路径，第二条是服务连接界面：技术概念过多，缺少从直接连接到开始使用的体验。两者共同说明需要全平台核查，不将专项收窄为其中一条。

| 用户观察 | 首批核查重点 |
| --- | --- |
| 各类 Connector 产品界面充满技术概念，缺少直接连接服务的路径 | 全部实际服务的默认连接、平台应用配置是否就绪、本人授权与内部接线、连接后的可用工作及失效重连；具体要求回写服务接入需求 |
| 大文件夹长时间没反馈；多个位置难以一起选；展开、文件名和下方勾选无效 | 扫描进度、选择事实、目录呈现和交互事件是否连通；完成后是否突然替换用户选择 |
| 代码文件夹只识别出一部分文件 | 发现范围、类型识别、忽略规则、读取/解析限制及漏项解释；用真实项目验证，不能只加几个扩展名就结案 |
| 连模型时仍显示文件列表；返回后八千多项变成 0 | 当前步骤与左右内容是否一致；显示状态是否与持久选择脱节；零项是真结果还是未加载/丢失 |
| 文件已读、DeepSeek 已连接，生成停在“模型请求失败或超时” | 区分读取与生成阶段，核错误来源、原始结果和恢复动作；不据泛化文案认定一定是超时 |

## 6. 怎样推进和交付

1. **先建立全平台覆盖关系。** 对照 §2 的实际功能与入口，明确每处的核查路径、证据和未验证项。全面盘点从一开始进行，不等 Onboarding 修完才开始认识其余范围。
2. **按风险和使用频率分批实走。** Onboarding 作为首条已有问题的贯穿路径，同时为其他领域安排核查批次；日常高频、跨功能依赖多、容易丢内容或恢复困难的路径优先。每批同时发现问题、提出优化并交付可独立验证的整改，不等全平台全部查完才修；也不因第一批成功就关闭专项。
3. **沿问题追到机制。** 从用户结果追到功能设计、交互、状态、数据、AI、能力、授权和规则的主人，区分功能缺口、实现缺陷、必要约束的表达问题与不必要的政策。同一机制的问题先核全部相关消费者，再确定共同整改范围，避免只修最先报错的入口。
4. **按原主人落实优化。** 功能行为回到相应需求书；修复和优化项进入现有 BACKLOG，已有编号就引用原项。优化包括补齐能力与交接、调整信息组织和交互、改善结果质量和响应、合并重复功能以及简化机制。本书保存跨路径结论与决定，不复制派工表；重要交互先给可操作切片，整改开发另按实际授权推进。
5. **逐批验证，再核全平台覆盖。** 对照修改前后的真实任务，核成功结果、人工决定、等待、上下文保留与错误恢复；每批完成后核相邻功能有无受影响。结束前回查全部实际功能与入口，补掉遗漏和新增项，保留未解问题的真实状态。测试全绿、报告写完或几条示范路径顺畅都不能单独算交付。

核查记录只保留决策需要的信息：用户目的与复现、当前版本、实际/预期、阻断的主人和依据、处理建议、验证结果。能引用已有日志、测试或工单就引用，不生成重复证据清单或为每项再造状态文件。

本轮产物只有本需求书和索引。后续专项最终应交付：全平台全部实际功能、入口及跨功能路径的覆盖与问题结论；每项不必要机制的删除/合并/按需处理或保留理由；原需求和实现中已采用的整改；关键正常、失败与恢复路径的真实验证。未检查、待优化或未验证项继续算未完成；只有用户明确调整范围，才能移出专项。专项结束须依据全平台覆盖和优化结果，不能只以 Onboarding 或其他局部修复结束。
