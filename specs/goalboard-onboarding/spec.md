# Molis Work 首次使用与版本更新 Onboarding

## 完成等级

本阶段交付 **Level 3：功能可用的生产垂直切片**。已经确认的高保真原型继续作为视觉和交互参考；生产实现必须把首次安装、新建项目初始化和版本更新 Journey 接到真实 Project、Workspace、Goal 与 Goal-bound TUI，不再用原型状态冒充领域事实。

Level 3 的完成边界是：用户能从空安装进入 Onboarding，明确确认后创建真实 Project 和根 Draft Goal；可选关联一个真实工作目录；若选择本机可用 Runtime，则不离开引导页，而是进入条件式第五步，在引导页内嵌入新项目的真实 Goal-bound TUI，并把初始化提示填入但不发送。用户完成本轮澄清与安排后，才主动进入 Molis Work。Goal Tree 的澄清、Proposal 与用户确认继续复用现有 Runtime / Coordinator 权威链路，不在 Web Onboarding 中伪造一棵“看起来完成”的树。

## 背景与目标

Molis Work 已有安全的安装、项目、Runtime 接入、工作目录、Session、Draft、Goal Tree Proposal 和用户确认能力，但这些能力目前分布在真实设置页和工作台中。首次用户完成安装后会看到项目入口，却不知道这些动作应按什么顺序发生，也没有一个明确的“第一次成功”。

本设计把 Onboarding 定义为真实产品旅程，而不是功能轮播：

- 初次安装后，用户在 3–5 分钟内建立或导入一个项目，并走到第一棵已确认 Goal Tree；
- 新建项目后，默认推荐打开一个明确绑定 Project、工作目录和 Runtime 的新 TUI Session，通过对话建立 Goal Tree；
- 版本更新后，只向受影响用户解释与其当前工作有关的变化，并把“试用”带回真实页面或 TUI；
- Onboarding 不建立第二套业务真相，实际完成情况继续从 Project、Runtime、Workspace、Session 和 Goal 事实推导。

## 当前行为与问题证据

- `src/web/render.ts` 的项目首页安全地提供“创建第一个项目”和“设置 Runtime 接入”，但两个入口平级，没有推荐顺序或第一次成功定义。
- 项目创建完成后直接进入空 Goal Tree；用户仍需自己理解工作目录、Runtime、新 Session 和 Draft/Proposal 的关系。
- Runtime 设置已经提供 detect → preview → confirm，但接入完成后的“必须新开 Session”没有形成连续交接。
- 网页新建 Goal 表单适合完整手工录入，不适合首次用户从粗略想法开始。
- `src/v1/demo.ts` 已有可重建 demo，可作为 90 秒体验退路，但当前不是一条有目标、有完成点的引导任务。

## 用户与关键结果

默认用户是已经使用 Codex、Claude Code、OpenCode、Pi Agent 或 Grok Build 推进真实项目的个人开发者、产品负责人和小团队成员。

首次使用的 aha moment：

> 一个原本只存在于聊天里的想法，已经成为用户确认的 Goal Tree；换一个 Session 后，结果、决定、下一步和完成标准仍然存在。

完整产品激活目标仍是：

1. 用户明确选择或创建了 Project；
2. 用户明确关联了工作目录，或清楚选择暂不关联；
3. 若选择 AI 初始化，Runtime 已验证接入，并新建了一个明确绑定当前 Project 的 Session；
4. 至少一条根 Goal 已由用户确认；
5. 复杂项目形成合理子 Goal，且至少一条叶子 Goal 可执行；
6. 用户能从完成页看出现在先做什么以及为什么。

本次 Level 3 的 Onboarding 交接完成条件是：

1. 真实 Project 已创建；
2. 真实根 Draft Goal 已写入该 Project；
3. 用户选择的工作目录已真实关联，或用户明确选择暂不关联；
4. 若选择 Runtime，页面停留在 Onboarding，并在第五步嵌入该 Goal 的真实 Goal-bound TUI；
5. 初始化提示只填入终端、不自动发送；
6. Runtime 成功打开且提示完成填入后，才启用“安排好了，进入 Molis Work”；用户主动确认完成后进入正常项目工作台；
7. Journey 完成或跳过状态与当前安装版本持久化在本机，刷新和重启后不重复打扰。

## 核心旅程

### A. 初次安装

`沉浸式抵达 → 说出第一个项目 → 描述想看到的真实变化 → 确认 Runtime 与工作目录 → 检查交接内容 → 新建初始化 Session → TUI 对话 → Goal Tree Proposal → 用户确认 → 第一条可执行 Goal`

首次安装不是先展示功能目录，而是进入一个全屏、一次只问一个问题的安静工作面。背景只负责提供稳定、低刺激的中性空间，不再承载 Goal Spine、线条、节点或其他“科技感”图形。科技感来自精确的步骤标识、紧凑排版、输入状态、已确认回执和页面切换；Goal Tree 只在 Proposal 阶段才成为真实内容。

对话顺序固定但允许跳过：

1. `你希望我们一起做什么？`——让用户先说想看到的变化，不要求理解 Project 或 Goal 字段；
2. `给这个项目取个名字吧。`——用自然问题获得一个之后还认得出的项目名；
3. `接下来，你想在哪里继续？`——选择可选工作目录和已探测且验证过的 Runtime；
4. `这样开始，可以吗？`——展示即将真实写入的内容与安全边界，等待最终确认。
5. `我们先把项目安排清楚。`——仅在选择 Runtime 时出现；在当前引导空间内嵌入真实 Goal-bound TUI，用户与 Runtime 完成本轮澄清和 Goal Tree 安排后再进入 Molis Work。

Molis Work 不扮演一个需要命名、建立人设的虚拟助理。温度来自措辞、节奏、回应和 Artifact 的逐步生成；产品始终清楚表明自己是在收集初始化所需事实。

入口提供三条路径：

- **用真实项目开始**：默认主路径；
- **先看 90 秒示例**：使用真实、可重建的 demo 数据；
- **导入已有数据 / 暂时跳过**：始终可见，不制造强制门槛。

### B. 新建项目后的 TUI 初始化

项目创建成功后不直接把用户留在空白 Goal Tree，也不提前把用户抛到 Runtime 工作台，而是让同一处问答空间从“提问”连续转为“嵌入式规划”：

- 主操作：`用 AI 建立 Goal Tree`；
- 次操作：`从空项目开始`；
- 弱操作：`稍后再设置`。

打开 TUI 前必须在同一视野内展示并确认：

- Project 名称；
- 工作目录；
- Runtime；
- 将创建一个新的初始化 Session；
- Molis Work 会填入初始化提示，但不会自动发送；
- 不会自动接受 Goal、改动代码或覆盖 Runtime 配置。

TUI 初始化对话分为四个可恢复阶段：

1. 理解最终结果、用户、现状与限制；
2. 补全实际流程、核心能力、基础能力和质量要求；
3. 提交根 Goal、子 Goal、叶子粒度、依赖方向与验收条件；
4. 用户采用整份提案或点名退回修改。

中途关闭后，恢复时先说明已经确认的事实、仍是假设的内容和下一件需要决定的事。

生产实现采用现有 Goal-bound TUI 作为唯一 Runtime 入口。Onboarding 不创建另一种 Session 模型：第 4 步创建真实 Project / 根 Draft / Workspace 后，把一次性恢复收据写入同源 `sessionStorage`，第 5 步通过带 `onboarding-runtime=1&onboarding-embed=1` 的项目深链接嵌入真实工作台。嵌入页只暴露 Runtime 工作面，不重复展示项目目录、Goal 详情、移动标签和工作台标题栏；它消费收据、打开用户选择的 Runtime、等待终端可写，并调用带 `onboarding=1` 的 Goal advance prompt 执行“填入不发送”。若 Runtime 先展示目录信任、Hooks 复核或类似启动确认，引导必须等待用户在真实终端中完成该确认，不能把初始化提示误写进选择界面，也不能提前回报 ready；确认完成后自动继续填入。该提示明确要求 Runtime 先读取根 Draft 与项目规划组合、一次只问一个关键问题，信息足够后按真实产出消费关系提交 Goal Tree Proposal 并等待用户确认。嵌入页通过同源 `postMessage` 回报 waiting / ready / error；父页在成功前禁用最终进入按钮，失败时允许原位重试。用户点击“安排好了，进入 Molis Work”后，进入不带嵌入参数的正常项目页面。

### C. 版本更新

版本更新使用独立 Journey，不重放初装流程：

- **当前 Level 3**：installation manifest 的版本发生变化时展示一次非阻塞更新摘要；确认后同一版本不再重复出现；
- **后续细分**：Patch 可只进入更新记录，Minor 显示 1–3 个相关变化，Major 把迁移、备份与恢复交给升级流程。版本影响分级需要真实 release metadata，本次不从版本号猜测功能影响。

更新项必须提供真实深链接：

- UI 功能进入真实工作面；
- 对话能力进入当前项目的 TUI，并填入可检查的提示词；
- 会修改 Goal Tree 的新能力只能提交 Proposal，不能静默改树。

更新 Journey 根据版本、功能使用情况、Runtime 探测、当前项目事实和是否看过该提示决定是否展示。

## 信息与交互结构

### 沉浸式 Goal Room

- 覆盖完整可用视口，隐藏工作台目录、卡片墙和功能清单；
- 不使用中央卡片或对话框外壳；问题、无边界填空和主操作直接存在于全屏空间中；
- 首屏只保留极轻的 Molis Work 标识、`迁移已有数据` 和 `跳过`，不显示功能清单或产品说明；
- 第一句固定为 `你希望我们一起做什么？`，下面只有一个 `我想……` 填空位置；
- 当前步骤根据是否选择 Runtime，以极弱的 `n / 4` 或 `n / 5` 和口语状态表达，不再绘制进度线；
- 已确认回答收拢为一行低调上下文，下一问在同一基线附近出现；
- 示例建议不出现在首屏，避免把自由表达重新变成选项表单；
- demo 始终标记为演示数据，并提供返回真实项目路径。

### 连续交接

- 用户完成问题后，问答空间逐步转成一页可检查的交接摘要，而不是跳到陌生页面；
- 摘要展示真实项目名、希望结果、工作目录、Runtime 和将创建的新 Session；
- TUI 提示词已经填入但未发送；
- 主按钮使用明确措辞：`发送给 Codex，建立 Goal Tree`；
- 用户可以返回修改任一答案，也可以选择从空项目开始。

### TUI 初始化

- 同一全屏空间收束为真实终端画布；终端通过更深的色块与内缩空间显形，不使用描边分隔；
- 终端上方保留 Project、工作目录和 Runtime 三项已确认上下文；
- 终端提示词已经填入但未发送；
- 输入、加载、断开、恢复和等待用户确认状态都可见；
- 关闭终端不等于丢失 Draft 或已经提交的 Proposal。

### Goal Tree Proposal

- 先展示整棵 Tree 的结果链和用户可读摘要；
- 每条关系说明哪个结果被谁消费，不用时间先后伪装依赖；
- 明确“采用后改变什么”和“不会改变什么”；
- 主按钮：`确认并建立 Goal Tree`；
- 次按钮：`回到 TUI 修改`；
- 确认前不写入 canonical Goal。

### 激活完成

- 不使用彩纸、烟花或虚假庆典；让暗色空间在确认后走向柔和冬日白，并留下稳定 Goal Tree，表达“事情已经清楚”；
- 展示已确认根 Goal、第一条可执行叶子和选择理由；
- 主按钮：`开始推进第一条 Goal`；
- 次入口：`查看完整 Goal Tree`；
- 说明后续 Session 会继续读取同一份事实。

### What’s New

- 标题直接说明用户能获得什么；
- 最多 1–3 条连续正文记录，不做等宽营销卡片；
- 每条变化包含：变化、对当前项目的意义、实际试用入口；
- 可关闭、可稍后、可从更新记录重新打开。

### 可访问性与原生交互语义

- Runtime 选择使用原生 `fieldset` / `legend` 和 radio，选择与“继续”是两个独立操作；
- 键盘路径保持为：标题获得初始焦点 → `Tab` 到当前 checked radio → `Tab` 到独立继续按钮 → `Enter` 确认；
- 输入错误通过 `aria-describedby` 关联可读错误文本，并同步设置 `aria-invalid` 状态；
- 项目与结果输入至少包含一个文字字符；纯数字、单个占位字符或只含符号的内容不能进入 Goal Tree Proposal，错误文案说明如何改写；
- quiet、placeholder 和 terminal 辅助文字可以维持次要层级，但对比度必须达到可交付基线；
- 滚动条跟随当前深浅表面主题，不使用浏览器默认的高反差滚动槽。

## 状态与恢复

Journey 展示状态记录在 Molis Work home 的设备设置文件中：

- `journey_id`；
- `started_at`；
- `dismissed_at`；
- `completed_at`；
- `last_presented_step`；
- `last_seen_app_version`。

文件只保存 Journey 展示和恢复信息，使用版本化结构、原子替换写入；不得复制 Project、Workspace、Goal、Session 或 Proposal 数据。安装版本来自 Molis Work installation manifest；无法确认当前版本时不弹出伪造的更新 Journey。

这些字段只控制展示。以下完成状态必须从真实领域事实推导：

- Project 是否存在；
- Workspace 是否明确关联；
- Runtime 是否验证接入；
- 新 Session 是否建立并绑定 Project；
- Proposal 是否存在及是否由用户确认；
- 是否存在可执行叶子 Goal。

用户从设置页、Runtime 或其他入口完成动作后，Journey 应自动前进，不能要求重复勾选。

## 错误与降级

- 安装不完整：停在诊断结果，提供唯一修复入口；
- 没有 Runtime：允许使用 demo、手工 Draft 或稍后接入；
- Runtime 冲突：不覆盖用户配置，保留项目与手工路径；
- 已接入但仍是旧 Session：明确要求新开 Session，不误报激活；
- 工作目录不可访问：解释路径问题并允许修复或暂不关联；
- TUI 中断：保留已写入 Draft 与 Proposal，重新进入时恢复 checkpoint；
- Proposal 无效：说明具体结构问题，只提供退回修改路径；
- 用户跳过：不重复弹出，可从系统设置重新打开；
- demo：始终标记为可重建数据，允许重置或删除。

## 视觉方向

2026-09-01 的第三次视觉修订覆盖此前“深黑冬夜”“浅色雾面 Hero”和“Goal Spine 背景”三种表达，但不改变真实写入、安全确认和一次一问的产品 Contract。

- 这是 `DESIGN.md` Calm Desktop 的首次旅程特例：保留冷静灰阶、精确排版和单一 cobalt focus，背景使用一整块平坦的中性暖灰，不再放置右侧色面、SVG、连接线、节点或模拟拓扑；
- 科技感不由背景装饰承担，而由四个真实状态组成：`01 / 04` 步骤标识、字段获得焦点、答案被记录为回执、下一步骤被装载；微型状态文字可以使用等宽字体，标题与正文继续使用平台原生字体；
- 第一屏没有中央卡片、图标墙或大 Logo。前景不做垂直居中，首屏内容的视觉中心落在视口高度约 `61.8%` 的下黄金分割点；桌面首屏前景宽度从上一版 `600–660px` 收到约 `340–380px`，视觉占比接近上一版的一半，但不机械砍掉可读字号和点击面积；
- 首屏问题控制在 `18–22px`，正文控制在 `11–12px`，主输入控制在 `13–15px`；输入是边界清楚的工作字段，不使用大型白色悬浮胶囊；
- 文案使用引导式的自然问题：`你希望我们一起做什么？`、`给这个项目取个名字吧。`、`接下来，你想在哪里继续？`、`这样开始，可以吗？`。温度来自认真回应用户说的话，不把 Molis Work 包装成有虚构人格的 AI 助理，也不使用“智能生成、开启未来、让 AI 接管”等泛化话术；
- 后续步骤继续使用同一左对齐文字基线；第一、第二步控制在约 `380px`，Runtime 与确认步骤可扩展到约 `480px` 以容纳真实信息；Review 使用连续的轻量事实行，不形成卡片墙；
- 页面不使用装饰性横线、按钮下划线或树连接线；字段边界、焦点轨迹、状态点和键盘焦点是功能反馈，不扩散为背景图形；
- 窄态 Goal 标题不在标题上方悬挂胶囊状态。状态与标题同一行，使用 5px 状态点和简短文字，不保留描边、圆角底色或独立占行；桌面宽态继续保留完整事实行；
- Hover 通过明暗和一像素位移表达；输入、Runtime 选项和按钮以平坦色块与结构线为主，不使用玻璃拟态、大面积阴影或霓虹光；
- 760px 以下仍保持一次一问，内容距视口边缘至少 20px，所有主要触控目标至少 44px；字号不因“缩半”降到不可读区间。

### 单屏步骤舞台与流程导航

2026-09-01 的第四次视觉修订解决后续步骤内容增高造成的页面滚动与导航漂移，不改变任何真实写入或安全边界。

- 首次使用的前四个问答步骤共享一个固定在视口内的内容舞台；选择 Runtime 后出现的第五步改用更宽但仍在视口内的嵌入舞台。任何步骤都不能撑高 `body`，1440×900、720×900 与 390×844 下均不需要滚动页面才能看到当前问题、当前输入、Runtime 和流程导航；
- 内容仍沿用下黄金分割点和同一左侧文字基线。较高的 Runtime / Review 步骤在舞台内部使用更紧凑的垂直节奏，只有在低高度视口下才整体上移以守住底部导航，不让短步骤跟着跳动；
- 工作目录与 Runtime 选择保持一个问题中的两个真实输入，但不形成“工具状态面板”。工作目录使用文字标签与单条输入基线；Runtime 只显示“稍后再选”和当前真正可用的工具，按截图式紧凑单列排列。每行只保留工具名，选中行出现一层浅灰底和右侧小点，不重复显示“本机可用 / 当前选择”等说明，不使用粗体、卡片边界、大行距或整块输入底色；保留原生 `fieldset`、`legend`、radio、checked 和键盘焦点语义，未检测到的工具不占据首次旅程空间；
- 第一问使用“意图选择器 + 独立文本输入”的句子编辑器：默认选择器为 `我想`，与文本框分开对齐，不把前缀伪装成输入内容；可切换为 `我想做成 / 我想设计 / 我想解决 / 我想想清楚 / 我想改造 / 我想让 / 我想讲清楚`。闭合状态是无盒子的文字触发器、必要的 chevron 和输入基线；只有展开菜单是必要容器，菜单沿用单列轻列表，当前项用浅灰底和状态点表示。选择结果作为用户提供的规划线索映射到对应 work-type method pack，但不直接锁定项目 `method_pack_ids`，也不替代 Runtime 对领域、行业和叠加层的后续判断；
- 上一步、下一步与创建 / 完成操作放在步骤内容上方，与 `01 / 05` 步骤状态组成一条轻量导航行，不固定在右下角。控件只使用真实细线箭头与简单文字，背景、描边、圆角、阴影和最小宽度全部移除；仍保留 44px 命中区、清楚的 hover / focus 与禁用状态。前三步显示 `上一步 / 下一步`，第 4 步显示 `上一步 / 创建项目`，条件式第 5 步不再允许返回修改已经写入的事实，只显示 `安排好了，进入 Molis Work`；
- 第五步只保留一段短说明、一块必要的真实 Runtime 视口和一行状态 / 重试，不增加说明卡、功能卡或第二套工具容器。Runtime 视口沿用真实终端画布与紧凑工具排版，外部引导继续保持平坦暖灰；二者以空间和一次细边界区分，不用大阴影或发光描边；
- 前进时当前内容向左收拢、下一步从右侧短距离进入；返回时方向反转。进出在同一个舞台内完成，舞台尺寸、背景和导航位置不变化；动画预算为 240–320ms、指数减速、无弹跳，切换期间避免重复触发；
- `prefers-reduced-motion: reduce` 下直接切换步骤，不执行位移或裁切，但焦点、步骤文字、按钮显隐和表单状态保持一致。

### 动效主张与预算

整个 Journey 只编排一个主叙事动作：**一句话被认真接住——字段获得焦点，答案收拢成“我们一起”的上下文，下一道问题沿同一基线出现**。

- 首次进入不制造强制等待；内容默认可见，步骤标识、问题和字段在 320–480ms 内依次就绪；
- 控件反馈 100–150ms；问答切换 220–320ms；统一使用接近 `cubic-bezier(.16, 1, .3, 1)` 的平滑减速，不使用弹跳；
- 用户确认答案后，回答收拢为带状态点的自然上下文，新问题通过短距离裁切显现；不使用大幅上移、模糊或背景联动；
- 同时运动的主体不超过两层：当前问题与当前控件。背景不运动，不做粒子、轨道、科技线或持续循环，不播放声音；
- 动效使用轻量 CSS、SVG 和少量原生脚本，不引入动效依赖；页面不可见时暂停非必要循环；
- `prefers-reduced-motion: reduce` 下跳过纯黑等待、位移、失焦和光场移动，直接显示当前问题与输入；内容默认可见，动效失败不能阻塞操作。

## 非目标

- 不在 Onboarding 内实现第二套 Goal Tree Proposal 或直接写入 canonical 子树；
- 不自动发送终端提示、不自动接受 Goal、不修改 Runtime 配置；
- 不在这次切片中安装缺失 Runtime；不可用 Runtime 只能被解释并允许稍后设置；
- 不加入原生目录选择器；Level 3 使用经过验证的绝对路径输入，文件选择器留给后续体验优化；
- 不用静态原型冒充生产完成；
- 不重新设计 Goal Detail、Runtime 设置或整个项目目录；
- 不在首次流程教学 Feed、来源、Graph、Planning Methods、Handoff 等全部能力；
- 不建立云端遥测。若未来收集完成率，默认只保留本地诊断，外发需要另行同意。

## 生产模块与调用链

- `src/web/onboarding.ts`：唯一拥有 Journey 展示状态、安装版本读取和是否应展示初装 / 更新 Journey 的判定；只读写 Molis Work home 下的本机设置文件。
- `src/web/server.ts`：拥有 `/onboarding` 和 `/api/onboarding/*` 的路由编排；在用户最终确认后调用 Catalog 创建 Project、调用 Coordinator 创建根 Draft Goal、可选调用 Catalog 关联 Workspace，再返回真实项目 / Goal 深链接。
- `src/web/render.ts`：渲染逐步表单、确认摘要、错误与恢复状态；不拥有 Project 或 Goal 事实。
- `src/web/pty-client.ts`：消费一次性初始化收据，复用现有 Panel、PTY 和 advance prompt 能力打开 TUI并填入提示；接受同源父页对嵌入页的初始化交接，并把 waiting / ready / error 状态回报给父页；收据过期、Goal 不匹配或 Runtime 不可用时安全停止，不自动发送。

输入：可选意图前缀、预期结果、项目名、可选绝对工作目录、可选且已探测可用的 Runtime、最终明确确认。

输出：真实 `project_id`、`goal_id`、项目深链接、可选 Workspace 关系，以及仅供同源下一页消费的一次性 TUI 初始化收据。

失败边界：所有可预先验证的输入在创建 Project 前完成验证；Project 创建后的 Runtime / PTY 失败不回滚业务事实，而是保留可恢复的根 Draft Goal，并允许用户从 Goal 工作台再次打开 TUI。

## Level 3 验收标准

- 空 Project Catalog 首次打开会进入生产 Onboarding；跳过后回到真实项目目录，且重启服务后不重复强制进入；
- 主路径可完整走通：项目意图 → 结果 → Runtime / 工作目录 → 交接确认 → 创建真实 Project 与根 Draft Goal → 打开真实项目；
- API 缺少最终确认、项目名 / 结果无有效文字、目录不是存在的绝对路径、Runtime 不可用时，在任何 Project 写入前拒绝请求；
- 选择可用 Runtime 时，第 4 步创建成功后页面仍停留在 `/onboarding`，进入条件式第五步并嵌入该 Goal 的新 TUI；嵌入态不显示 Molis Work 工作台目录、Goal 正文、工作台标题栏或移动标签。TUI 填入首次澄清专用的 Goal advance prompt，但不发送回车；该提示明确引导用户补全根 Draft、使用项目规划组合拆分 Goal Tree、提交 Proposal 并等待用户确认；提示填入成功前最终进入按钮不可用，失败时可原位重试；未选择 Runtime 时不创建 Panel并直接进入项目；
- 刷新或恢复不会重复创建 Project、Goal 或 TUI；过期的一次性收据会被丢弃；
- 安装 manifest 版本变化后显示独立、可关闭的 What's New Journey；确认后持久化 `last_seen_app_version`，相同版本不再重复展示；
- 页面和 API 的 Project、Workspace、Goal、Runtime 可用性都来自真实 Catalog / Store / 本机探测，不使用演示值；
- 意图选择器与结果输入拥有独立边界和共同基线；默认值与七个映射值均可通过键盘选择，选择后更新示例与回执，并把规划线索写入根 Draft Goal 的待澄清上下文，不把它写成已确认方法组合；
- 首屏在浅色静谧工作面中显出 `你希望我们一起做什么？` 与一个填空位置，没有中央卡片、功能说明或场景切换；
- 1440px 桌面首屏问题字号不超过 22px，表单主输入不超过 15px，首屏主要输入宽度不超过 `380px`；首屏内容视觉中心位于视口高度约 `61.8%`，并在上方、右侧保留明显负空间；
- 背景不包含 SVG、连接线、节点、分区图形或远程图片；无柔焦布景、织物光影、粒子、网格、神经网络、霓虹光边或持续循环；
- 所有页面均不使用装饰性横线、条目分隔线、按钮下划线或 Goal Tree 连接线；层级由留白、字号、色块、明暗和动效建立；
- 每一步只问一个问题，用户可看见上一条回答已经转化为已确认事实；
- 背景在步骤间保持稳定，Goal Tree 只在 Proposal 阶段出现；动效不代替状态文本；
- Goal Tree 在桌面与移动端都能通过空间层级读出“根 Goal → 两个分支 → 第一条行动”，不依赖连线，也不形成四散文字或卡片墙；
- 更新入口可展示一次 Update Journey，并回到真实项目目录；
- 所有主操作、返回、跳过和场景切换均可键盘操作；
- Runtime 步骤的原生单选语义、checked 状态和独立继续按钮按预期进入键盘焦点顺序；
- 输入错误文本与字段语义关联，错误状态可被辅助技术识别；
- 明确区分真实产品事实与原型演示数据；
- Proposal 面向用户统一使用“目标树、根目标、结果分支、行动”等中文表达；`Project`、`Session`、`Runtime` 只在确实指向产品实体时保留，不显示 `canonical` 或全大写 `GOAL` 等内部术语；
- 不出现自动接受、自动发送、自动改配置或自动绑定的误导；
- 1440×900 和 720×900 下无横向溢出、内容遮挡或关键操作不可达；
- 1440×900、720×900 和 390×844 下，所有可见步骤均保持 `documentElement.scrollHeight === innerHeight`；第三步的可用 Runtime 紧凑列表、提示和顶部线性导航同时可见；第五步的说明、真实终端、状态和最终进入操作也同时位于一页内；
- 步骤切换不会改变内容舞台和流程导航的位置；前进 / 返回采用相反方向的短距离过渡，并在 reduced-motion 下直接完成；
- `prefers-reduced-motion` 下主路径仍然完整可用，无强制位移动画；
- 错误、加载、恢复和已完成状态至少各有一个可检查表达；
- 视觉呈现明确的科技感与 Peace 气质，同时仍是完成任务的 Operate surface，不形成独立营销页面。

## 生产验证

- `pnpm typecheck`；
- `pnpm build`；
- 运行 `tests/web.test.ts` 中的 Onboarding 定向测试，覆盖首次跳转、跳过持久化、真实 Project / Goal / Workspace 写入、输入拒绝和版本确认；

- 在本机存在可用 Runtime 时，手动确认新 TUI 被打开且提示只填入、不发送；没有可用 Runtime 时记录该项未运行，不用伪造通过。

## 已确认决定与后续验证

- 初次安装默认进入真实项目，90 秒 demo 作为明确的次入口；
- 项目初始化 TUI 首次只推荐一个已验证 Runtime，其他 Runtime 放在可展开切换中；
- V1 只记录本地 Journey 状态和可复现测试，不外发完成率遥测；
- Level 3 先保证真实写入、恢复和安全边界；3–5 分钟完成整棵已确认 Goal Tree 仍需真实用户走查，视觉与节奏优化留到后续。
