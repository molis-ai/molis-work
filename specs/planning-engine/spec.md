# Molis Work 规划引擎

## 完成等级

内部完整：真实数据、Runtime MCP、Web 与 Desktop 共用的 Web 页面、现有 Goal 生命周期和异常路径可以在本地顺畅试用；不包含云同步、多人权限或自动调用外部模型。

## 背景与目标

Molis Work 已经能管理 Goal 的状态、确认、领取、执行、复核和验收，也能拦住部分明显过大的叶子 Goal。但“该怎么拆、为什么这样依赖、先做什么、需求变化后整棵树怎样调整”仍主要依赖 Runtime 自己判断。当前代码把固定任务清单、Proposal 校验、关系写入和 Available 排序分散在 Skill、`goal-decomposition-validation.ts` 与 `coordinator.ts` 中，缺少统一规划模型。

本任务把 Molis Work 从“记录和约束 Goal 的工具”升级为“帮助 Runtime 专业规划并持续纠偏的工作系统”：先识别工作类型和领域，选择可追溯的方法包；再依据结果和输入输出拆 Goal、建立依赖、检查整张图并排出可解释的执行顺序；用户提出新要求时，只分析和重算受影响子图，不静默改写已确认 Goal。

## 当前行为与问题证据

- `goal-decomposition-validation.ts` 有通用结果链和固定 `task_context` 清单，但清单不是可配置、可复用、有来源的方法包。
- `LeafReadiness` 能检查一条叶子是否自洽，但其专业判断由 Runtime 自报，系统不知道采用了哪套领域方法。
- `addRelation` 和 Proposal 物化只禁止 active `part_of` 环；没有统一拒绝 `depends_on` 环、同一提案内的组合环或 `part_of + depends_on` 的有效执行环。
- `checkGoalTreeProposal` 只检查对象基准是否过期，不模拟整份提案应用后的图。
- `queryAvailable` 能排除直接前置未完成的 Goal，但剩余项目只按父 Goal 确认、人工优先级和 ID 排序，没有拓扑层级、关键链长度或解锁价值。
- Skill 要求新增诉求先复用已有 Goal，但没有一个读操作返回受影响祖先、后继、依赖方、需要重新验证的范围和建议重规划顺序。

## 范围

### 1. 分层方法库

提供三层方法包，解析优先级为：

1. 项目方法包；
2. 个人方法包；
3. Molis Work 内置方法包。

同一个 `method_id` 的高层级版本覆盖低层级版本；可以停用但不物理删除内置定义。方法包具有版本、适用工作类型、领域标签、适用说明、拆分步骤、必须覆盖项、依赖判定规则、证据规则、完成检查、风险/反例、来源和可信度。

首版内置冷启方法包：

- 通用元方法：陌生领域研究与方法包生成；
- 工作类型：构建/改变、诊断/修复、分析/决策、设计/规划、迁移/重构、运营/流程、内容/传播；
- 领域：软件开发、数据分析、市场分析、产品与 UX、AI/数据产品、游戏设计、研究与内容、运营与组织流程。

冷启包是短而可执行的专业框架，不包含百科式长文。陌生领域先执行元方法：定义对象和生命周期、专业产物、证据标准、依赖模式、失败模式和完成条件；方法包达到可信门槛后才用于实际拆分。

### 2. 方法包的读取、组合与调整

- 方法包的主要 Runtime 接口是一份完整、可独立阅读的 `instructions` 正文。它按 Skill 的方式说明适用场景、规划顺序、必须回答的问题、依赖判断、完成证据、常见误拆和需求变化后的处理方式，而不是把 Runtime 留在字段名和短句之间自行补全方法。
- 现有 `steps`、`required_coverage`、`dependency_rules`、`evidence_requirements`、`completion_checks` 与 `failure_modes` 暂时保留，作为兼容数据、页面摘要和拆分门禁的来源；内置方法通过统一编译函数生成正文，避免正文和结构化摘要成为两套互相漂移的事实。
- 新建或修改个人/项目方法时，用户可以直接维护完整方法正文。旧方法没有正文时，Molis Work 根据已有字段生成兼容正文；不迁移或改写既有 Goal、Proposal 和项目方法事实。
- Runtime 可读取当前项目解析后的有效方法包，以及由多套项目方法共同形成的规划组合。
- 项目中启用的多套项目方法并列组成默认规划组合：工作类型提供主路径，领域和自定义方法共同补充覆盖、依赖、证据和完成检查；不会把各自步骤机械拼成串行任务清单。
- 方法选择还要检查主题之间的产出关系：若一个已选主题需要另一个专业主题提供产品定义、数据、证据、契约、权限、评测或其他关键结果，Runtime 必须召回对应方法并检查跨方法桥接依赖，不能只按当前讨论最显眼的主题选包。
- Runtime 只有在用户当前对话明确确认后，才能新增或修改项目方法包；写入保留来源与版本。
- Web 提供个人方法包和项目方法包的查看、创建、编辑、启停入口；内置包只读，可复制后调整。
- 表单使用普通字段和逐行列表，不要求用户编辑原始 JSON。
- Desktop 继续使用同一 Web 页面与数据，不建立第二套设置实现。

### 3. 拆分审查

- Runtime 在提出或调整复杂 Goal Tree 前必须完整阅读每个已选方法的 `instructions`。方法正文指导判断，Molis Work 继续只校验已存在的 Goal、覆盖、关系与图不变量，不新增业务语义规则引擎。
- 每条方法依赖规则都必须被判定：如果下游确实消费上游产出，则该关系是不可跳过的硬依赖；如果不适用，Runtime 要能说明不存在什么产出消费。跨主题相关性本身不构成依赖。
- `DecompositionReview` 新增 `method_pack_ids`，记录本次拆分使用的工作类型包、领域包或元方法包。
- 新的复合 Goal 提案必须能解析这些方法包；未显式指定时，历史 `task_context` 使用兼容映射选择内置包。
- 必须覆盖项从解析后的方法包统一产生；旧的固定任务清单迁移为内置包，不在校验器中维护第二份。
- 叶子粒度仍保留“一个主要可验收结果”和三项拆分信号，不按工时、文件或固定树深机械拆分。

### 4. 全图依赖校验

新增纯规划图模块，在直接关系写入、Proposal 提交、Proposal 决定和 Proposal Check 中复用。

图的执行含义：

- `part_of: child -> parent` 表示子 Goal 完成后父 Goal 才能闭合；
- `depends_on: consumer -> provider` 表示 provider 必须先于 consumer；
- 执行先后图因此使用 `child -> parent` 与 `provider -> consumer`。

校验拒绝：

- 父子环；
- 依赖环；
- 父子与依赖组合后的执行环；
- 自引用和重复 active 关系；
- 引用不存在或已回收 Goal；
- 同一 Proposal 多条关系组合后才出现的环。

返回完整、可定位的问题列表及环路径，不引入 checksum、分布式锁或额外一致性协议。

### 5. 可解释执行排序

Available 仍只是 Runtime 的可选集合，不变成强制调度器。对当前可执行 Goal 增加：

- 拓扑层级；
- 完成后直接/间接解锁的 Goal 数；
- 从该 Goal 到下游结果的最长链长度；
- 简短排序理由。

排序顺序：父 Goal 收口确认优先；随后按最长下游链、解锁数、人工优先级排序；最后使用稳定 ID。风险和 Runtime 上下文只在已有明确事实时参与，不新增模型评分。

### 6. 新诉求影响分析与局部重规划

提供只读规划分析入口。Runtime 提交本次变化说明、起始 Goal 和变化类型后，Molis Work 返回：

- 直接受影响 Goal；
- 需要重新检查的祖先；
- 消费其结果的下游 Goal；
- 可复用的现有未完成 Goal；
- 建议先检查和重新提案的顺序；
- 当前图已有问题。

分析不直接修改 Goal。Runtime 仍通过 Goal Tree Proposal 提交新增、修改、停用或依赖调整，由用户确认后进入正式事实。

### 7. 旧逻辑整理

- 方法包与覆盖规则归入独立规划模块；校验器只消费解析后的规则。
- 图构建、环检测、拓扑与排序归入独立规划图模块；Coordinator 只编排事务和权限。
- 保留 Goal Contract、Proposal、用户确认、Evidence、Claim/Run、Review、重新验证。
- 保留历史 `task_context` / `product_context` 兼容读取，不批量改写历史 Goal 或 Proposal。

## 非目标

- 不实现 Agent Orchestration、Agent 分派、远程队列或团队通信。
- 不让 Molis Work 自行调用模型或联网研究陌生领域；元方法把研究步骤和产物提供给当前 Runtime。
- 不自动接受方法包、Goal 或依赖变化。
- 不做云同步、组织级 RBAC、协同编辑或方法包市场。
- 不以预计工时、标题长度、固定树深或伪精确分数决定拆分。
- 不新增 hash/checksum 协议、分布式锁、通用工作流语言或与主链无关的抽象层。
- 不为迁移而重写已接受历史事实。

## 数据与模块边界

- `src/planning/method-packs.ts`：方法包类型、内置包、分层解析和校验。
- `src/planning/goal-graph.ts`：投影图、环检测、拓扑指标和变化影响分析。
- `src/v1/store.ts`：项目方法包持久化。
- `src/projects/catalog.ts`：个人方法包持久化。
- `src/v1/goal-decomposition-validation.ts`：消费方法包，保留叶子准备度与复合拆解门禁。
- `src/v1/coordinator.ts`：方法包项目操作、Proposal/关系事务、Available 与影响分析编排。
- `src/mcp/server.ts`：有效方法包读取、用户确认后的项目方法包写入、变化影响分析。
- `src/web/server.ts`、`src/web/render.ts`、`src/web/i18n.ts`：个人/项目方法包设置和规划诊断页面。
- `skills/goal-advance/`：先选方法再拆、陌生领域先生成方法包、需求变化先分析再提案。

## 用户流程

### 已有领域

1. Runtime 读取有效方法包和项目规划组合。
2. Runtime 先检查当前任务的目标、工作性质、专业领域、交付方式和风险。项目已有组合时将其完整作为必选下限，并补充其他确实相关的方法；没有组合时也不预设方法类型或数量，所有能补上重要检查的方法都应纳入，否则 Goal 拆分不完整。
3. 按方法包拆分并提交整份 Goal Tree Proposal。
4. Molis Work 模拟完整图，拒绝遗漏和环。
5. 用户确认后，Available 提供可解释的推进顺序。

### 陌生领域

1. 没有足够匹配的方法包时，Runtime 选择“陌生领域方法包生成”。
2. Runtime 根据项目事实和可信领域来源形成方法包草案。
3. 用户确认后保存为项目方法包；需要跨项目复用时，用户可在设置中复制为个人方法包。
4. Runtime 重新读取有效方法包，再拆实际 Goal。

### 用户新增要求

1. Runtime 调用变化影响分析，不直接追加 Goal。
2. 用户看到现有 Goal 中哪些可以复用、哪些 Contract/依赖需要调整。
3. Runtime 只提交受影响子图的 Proposal。
4. Molis Work 重新检查完整图和执行顺序；未受影响 Goal 保持原状态。

## 验收标准

1. 方法库能解析内置、个人、项目三层，并按项目 > 个人 > 内置覆盖；页面可查看来源和有效版本。
2. 至少包含元方法、7 个工作类型和 8 个领域冷启包；内容精炼且字段完整。
3. Web 可创建、修改、启停个人/项目方法包；Desktop 同页可用；内置包不可直接覆盖写入。
4. Runtime 能读取有效包，并能在用户明确确认后保存项目方法包；没有确认不能写。
5. 每个内置方法包和由旧字段生成的兼容方法包都返回非空完整正文；正文明确 `depends_on` 是消费者依赖提供者，并包含该方法适用的依赖规则、建立条件、非依赖反例、完成检查、变化处理和跨主题方法召回检查。
6. Runtime 在组合方法时检查各主题的提供者产出和消费者用途；发现缺失主题时补充召回，发现真实产出消费时建立硬依赖，同时不把一般相关性误写成依赖。
7. 新复合拆分记录所用方法包；历史 task context 仍能通过兼容映射工作。
8. 直接写入和整份 Proposal 都拒绝 `part_of`、`depends_on` 与组合执行环，并返回环路径；同一条目内多条关系也不能绕过。
9. Proposal Check 除并发基准外，还返回当前完整投影图问题。
10. Available 只返回真正可做的 Goal，并包含拓扑层级、解锁数、最长下游链和排序理由；排序有确定性。
11. 变化影响分析能返回祖先、下游依赖方、可复用未完成 Goal 和建议检查顺序，不写入 canonical Goal。
12. 旧测试通过；新增全部内置方法正文、软件开发产品→技术→基础→功能→验收依赖说明、旧项目方法兼容、依赖环和需求变更回归。
13. Web 浅色、深色、窄屏和 Desktop 页面可读，没有原始 JSON 编辑要求；方法详情优先展示完整正文，编辑页允许直接维护正文。

## 假设与取舍

- 首版“专业性”来自可追溯方法包、明确依赖规则和图不变量，不引入不可解释的模型评分。
- 个人方法包存放在 Molis Work catalog；项目方法包存放在项目数据库。内置包随版本发布。
- 方法包更新只影响之后的新拆分或主动重规划，不静默重写既有 Goal。
- 方法正文是给 Runtime 的专业判断说明，不是可执行工作流 DSL。Molis Work 不解析正文来推断业务依赖；Runtime 负责按正文提出关系，现有图校验和执行门禁负责保证关系成立后不形成非法图。
- 第一版提供规则化影响分析，由 Runtime 结合用户新诉求生成 Proposal；Molis Work 不自动改业务 Contract。
