**状态**有六种写法：

- 「待做」。
- 「待做（统筹已定，见 §4）」：统筹已经给了口径。
- 「待做（T0 已核，见 §8）」：T0 对照 main 复核过，代码位置和描述已经更新；已做完的部分和依据写在 §8。

- 「已做（#NNN）」：整行描述的缺口都已由那几个 PR 补上，统筹在合入后核过。只补了一部分的不写已做，写清还剩什么。
- 「不迁；……（用户 MM-DD）」或「不做：……（用户 MM-DD 确认）」：经用户确认不做，写理由和日期。

## 4. 统筹已定的口径

这里的 a–q 是本表采用的口径。a–k 对应 spec §10.28「统筹裁定」的条目，m–q 对应 spec §10.29「统筹裁定」的条目，原文都以 spec 为准；l 是统筹从裁定 14 推出来的。

- **a（裁定 7）删项目时清插件数据，改成声明式**。平台按插件声明的分区和文件删，删之前先经平台的后台作业服务停掉该项目的作业，不另加 Runtime 钩子。#745 的 `initialize_owner_files`（PG-103）和 #743 的 `onProjectDeleted`（PG-106）都和这一条冲突，照 m 删掉。涉及：PG-024、PG-038、PG-066、PG-103、PG-106。
- **b（裁定 8）随宿主发布的插件跟着宿主版本升降**。这算安装信任，不算特权。涉及：PG-016。
- **c（裁定 9）S-32 去掉「内置在前」**。对象种类按插件分同样的配额，按 plugin id 排序。涉及：PG-015。
- **d（裁定 10）插件经 `services.actions` 调自己的动作时，保留外层调用的受众**。`allowModelDownload` 只认宿主发的路由 control，或本人的直接调用。涉及：PG-028。
- **e（裁定 11）Cognia 读用户指定的本机目录，要有一项带同意流程的平台服务**，任何插件都走它。这是信任边界的变化，② 设计时先弹窗。#733 之后由插件自己用 `node:fs` 读，同样要换成这项服务。涉及：PG-049。
