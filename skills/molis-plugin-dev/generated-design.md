# 生成插件：怎么设计（主线设计的标准）

插件创作台生成的插件由两部分组成：沙箱里的后端代码（每件事一个"操作"），和平台用 UI 目录统一画出的界面。你设计的是说明书：做哪几件事、每件事的例子、界面由哪几块组成、怎样验收。说明书一旦定下，UI Agent 和代码 Agent 同时按它开工，任何矛盾都会在验收时才暴露，所以说明书必须自洽。输出格式以任务里的阶段说明为准，这里讲怎么判断。

## 需求与方案

- 按最小完整范围设计：用户说到的都做到，没说的不加（编辑、分类、标签、搜索、分组、导出……）。以后可以加的写进 summary。
- 只有需求含糊到"不同理解会做出不同功能"时才提问，最多一轮、1–3 个问题；不问样式、配色和示例内容。
- 2–3 个方案要在页面结构或关键行为上真正不同（例如"一页录入+列表"与"按状态分页"），各写清适合谁、放弃了什么。
- 用到平台能力或其他插件的动作时，只从任务给的能力清单里选。标着"还没启用"的插件可以用，开工前平台会请用户确认；用户不启用时，你会收到"不要使用某插件"的修改意见。

## 功能（操作）

- 一个操作只做一件事。只读用 query，会改数据用 command；query 不能写存储。
- 插件自己的操作用自己的名字前缀（`reports.list`、`water.add`），不要和能力同名。用能力是在调用它的操作的 effects 里写能力 id，不是再定义一个同名操作。
- 每条记录由插件自己生成字符串 id。
- 同一个字段在所有操作里用同一组取值（例如状态都是 `未读|在读|已读`）。给人看的叫法（"想读"）放在界面的列显示词里，不要另起一套取值。
- 可选的输入（例如筛选条件）在字段名后加 `?`；只收 id 的操作（删除、切到下一状态）由代码按记录现状计算，不要用常量去表达"下一个"。
- 合计、统计由 query 返回一个对象（数字字段 + 分类明细列表），分类的取值放进列表，不要做成字段名。
- effects 只写真正用到的：自己的存储、以及本操作真正调用的平台能力。
- 要写文档或存成果、把东西放进 Feed 时，用能力清单里对应插件的动作：写文档用 `pages.create` / `pages.update`，把文档存成成果用 `pages.promote`，读成果用 `artifacts.read`，放进 Feed 用 `feed.content.receive`。effects 里不写 `events` 或 `artifacts`。
- 要访问外部网站（天气、汇率这类公开接口）时，在那个操作的 effects 里写 `networkDomains`，列出确切域名（`api.open-meteo.com`），安装时由用户逐个批准；只能用 https。安装前（检查、验收、试用）只会真的读取（GET）批准的网站，写入由替身代答；网站的内容每天在变，例子只检查结果的结构，验收检查插件保存下来或显示出来的文字里一定会有的部分（例如"最高"）。
- 会产生费用或有配额的能力（例如调用模型）只放在由用户点按钮触发的 command 里，把结果存下来，再由 query 列出；不放在打开页面就会运行的 query 里。
- 要按时自动做的事（每天汇总、每周整理）：设计一个做这件事的 command（返回 `text` 给人看，并把结果存下来），再设计一个让用户设定时间的 command，它调用 `schedules.add` 定时运行前一个；结果要进收件箱就传 `inbox: true`。只是到点提醒用户、不需要运行插件代码的，用 `reminders.add`。

## 例子（每个操作至少一个）

例子在每次检查时，于这个操作自己的空存储上按顺序运行：

- 查询在空存储上只能得到空结果。需要已有数据的情况写进验收。
- 新增类命令的输出含随机 id，用"至少包含这些字段"检查。
- 修改、删除这类需要已有记录的命令，例子写成"找不到记录"的错误，并在 errors 里声明这个错误；成功的情形写进验收。
- 期望结果里不写依赖今天的具体日期或月份；要核对日期，就让输入给出日期。
- 期望结果只写输出里声明过的字段。
- 用到平台能力的操作，检查时由替身代答，例子只检查结构或本插件保存的内容。
- 给别处的记录（其他插件的事项、目标等）记东西时：要核对那条记录存在，就在这个操作的 effects 里用读取它的能力；不读的话，不要声明"找不到"错误。

## 界面

你只写每一块的意图，具体用 UI 目录（`/__ui/catalog`）里的哪个组件由系统从合法候选里挑：

| 意图 | 用来 | 可能的目录组件 |
|---|---|---|
| heading | 插件名与一句说明，放最上面 | Frame |
| description | 一段结果或一组数字（统计） | Card、Alert、Badge |
| input | 录入或修改的表单 | Form（页面上）、Sheet（侧边面板）、Dialog（对话框） |
| action | 对一条记录执行一件事 | Button；删除类用 Alert Dialog 先确认 |
| collection | 一组记录 | Directory、Card、Table、Accordion；记录带日期时可用 Calendar |
| reading | 分小节的原文 | Accordion、Card |
| schedule | 按日期看的事项 | Calendar、Table、Directory |
| conversation、evidence、feedback | 对话记录、证据表、状态提示 | Directory/Card、Table/Accordion、Alert |

- 每个 input 或 action 只绑定一个命令；每个操作至少被一块界面使用。
- 输入全部来自同一个列表选中记录的 action，会显示成那个列表每条记录上的按钮；按钮文字写动作本身（"删除""标为已读"），不写"删除选中"。
- 筛选和搜索是列表自己的：把查询的输入交给用户（列表上方出现筛选栏），不要为筛选另建一块界面，也不要用 action 做筛选。
- 命令的结果要让人看到时，指明结果里显示哪个字段（写在 submit 里：`"submit": {"op": "summary.run", "show": "text"}`）；表单要沿用上一步的结果或选中的记录时，用预填（用户仍可改）：上一步润色出的一句话，下一步「记录」的表单就预填它。幂等键、请求号由代码生成，不写进操作输入。
- 列表写清 id、标题、正文字段和空状态文字；布尔或枚举字段给出显示词（"已打卡/未打卡"）。
- 要在一句话里显示查询结果，给显示组件 read 那个查询，文字写成 `今天已经喝了 {{count}} 杯`：`{{字段}}` 由查询结果填入，字段必须在输出里。查询返回的是记录列表时不能用模板（要显示刚生成的那条，就让执行命令的组件显示命令结果）。不写模板时，结果显示成一组带说明的数字卡片。
- 日历按记录里的日期分天排列，今天、昨天、明天那天的标题会写出「今天」等字样；验收可以写 `expect 日历 今天 1`（今天那天的一条记录里显示 1）。
- 不设计插件自带的脚本、样式或手势；目录里没有的交互不要写。质量线见 [ui.md](ui.md#质量线所有插件)。

## 验收

- 每条验收都从空数据开始，像真人一样操作：填写、提交、按记录上显示的文字选中一条、看到或看不到某段文字、顺序、翻页、刷新。
- 至少一条"新增后能看到"；有修改、删除时各一条；有筛选时一条"筛选后只剩对的"。
- 点记录上的按钮之前，先按文字选中那条记录。"找不到记录"这类错误属于操作的例子，界面上做不到，不要写成验收。
- 期望文字写记录里真实会出现的内容，不要把列名和值拼在一起（写"在读"，不写"状态：在读"）；用到模型的，检查替身文字。
- 读取别处数据（其他插件、平台）的列表，验收时由替身代答：列表里有一条示例记录，文字字段都是「示例」，数字取最小值，取值取第一个可选值。要在这条记录上操作，先 `select 列表 示例`，再填写、提交。
- 替身不会变：写到别处之后，别处的列表在验收里看不出变化，也永远不会是空的。所以不要期望"完成后这条从列表消失"或别处列表的空状态；检查操作后界面给出的反馈（命令结果里显示的字段），或插件自己保存的内容。

## 修订

用户提修改时，没被要求改的操作和界面保持完全一致（同样的 id 和内容），已完成的代码才能复用。合同不变、只改做法（例如给模型的要求、排序细节）时，明确列出要代码改的操作和改法。

## 常见错误

| 错误 | 正确 |
|---|---|
| 同一字段在一处写成取值（`string(设计\|阅读\|产品)`）、别处写成纯文字 | 所有操作用同一组取值 |
| 例子用显示词（"想读"），取值其实是"未读" | 例子用取值；显示词放进列显示词 |
| 查询的例子返回了几条记录 | 空存储只能返回空；有数据的情况写进验收 |
| 本月合计的例子写了具体月份 | 不写依赖今天的值，或由输入给出日期 |
| 例子期望了 output 里没有的字段 | 只写 output 声明的字段 |
| 用常量 `"next:books.status"` 表达"切到下一状态" | 操作只收 id，由代码算下一状态 |
| 为筛选另建一个表单 | 把查询的输入交给列表 |
| 验收直接点记录按钮测"删除不存在的记录" | 先选中记录；错误写进例子 |
| 把验收写进页面里 | 验收是说明书的一部分，和页面并列 |
| 定义了一个叫 `goals.list` 的操作来"读目标" | 自己的操作叫 `reports.goals`，在它的 effects 里写能力 `goals.list` |
| 文字里写 `{{count}}`，但这块界面没有 read 查询 | 给它 read 一个输出含 count 的查询 |
| 表单的输入写成 `"note": "editor.note"` | 由用户填写就写 `"form"`；取自选中记录写 `"selection:列表.字段"` |
| 两页都放一个叫 `title`、`goals` 的组件 | 组件标识在整个插件里唯一：第二页写 `write-title`、`write-goals`（方案草图里宿主会替你改名，完整设计里不会） |
| 把删除、打卡按钮写在列表的 `actions` 里 | 按钮和列表并列写在 parts 里，输入写 `selection:列表.id`；界面会把它画在每条记录上 |
| 日历、列表里的记录只返回 `habitIds` 这类 id | 同时返回给人看的名字（`habitNames`），id 只留作选中用 |
| 按钮绑定了没定义的操作（`notes.remove`），或定义了没人用的操作 | 每个组件绑定的操作都在 operations 里；每个操作至少一个组件用 |
| 验收"给 Inbox 的一件事记备注"没先选中事项 | 先 `select 列表 示例`（替身给的那条），再填写、提交 |
| 验收"标为完成后这条从 Inbox 列表消失" | 别处的列表是固定替身，不会变；检查按钮给出的反馈，例如 `expect 结果 已完成` |
| 以为验收之间数据会接着用（上一条喝了 1 杯，这一条再点 3 下就期望"4 杯"） | 每条验收都从空数据开始：点 3 下就期望 3 杯 |
| 刷新后期望在按钮或表单下看到"已设定……" | 命令的结果只在点完那一刻显示在那个组件上；刷新后还要看到的状态，要设计一个 query 和一个 read 它的组件，验收检查那个组件 |
