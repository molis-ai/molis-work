## 判断与根因

**不能只将4换1并把测试期望改1。** 已知旧 schema1 linked-layout 不会被 `inspectRelease` 直接判成 valid，但会判成 repairable；`installMolisWorkHome` 随后创建当前 release 并 promote 覆盖旧目录。这条旧格式转换路径在改号后仍存在，正由 `tests/install.test.ts:459–487` 的成功演练要求保留。

现行调用证据：

- `home-contract.ts:3–9,76–95`：installer 标识为 `molis-work-home-install-v1`，schema4；release 类型仍留 obsolete schema1 的 `source_directory?`，`dependencies/content_digest` 仍是可选声明。标识中的 v1 是 owner 标记，不等于元数据 schema。
- `home-release.ts:108–115,207–233`：当前写完整 embedded 元数据；错 schema、缺 embedded 标记/摘要、缺 bundled-node 声明一律 repairable，而不是旧/不支持形状拒绝。只有这些条件及必要文件通过、摘要匹配才 valid。
- `home-files.ts:30–53,93–102`：JSON 解析后靠类型断言；installation 读写只核 installer，未核当前 schema/完整形状。`home.ts:81–104` 的 no-change 也不比较 schema，所以单改常量甚至可能把原 schema4 的 installation.json 原样保留。
- `home.ts:37–41,165–170`：先创建/准备 Home，再检查现有 release；安装元数据更晚才读。若要证明“不支持旧形状被拒且零变更”，必须把必要只读预检提前，而非在回滚中删除初始化偏好。
- `home-launcher.ts:44–48` 的 Node 启动器、`runtime-integration.ts:174–193` 也消费 installation 元数据；`uninstall-files.ts:20–23,43–50` 只凭 installer 标记认安装/release 为可删。它们不能被遗漏成仍接受旧形状的读口。
- 服务 `web-service*.ts` 用独立的 `web-service.json`、LaunchAgent/launcher 与进程健康事实，不直接读 installation schema；停/移除已归属服务的既有规则独立于新安装是否可启动。**不为本项增加服务新协议或阻断安全 stop/remove。**

同号1不是历史身份鉴别器。合同已明确不承诺拒绝所有“版本相同、形状相同”的旧内容；本项拒绝的是可识别的旧 linked-layout、错版本及不完整/非现行元数据，不加历史哈希表、格式世代或新 installer 身份来猜年龄。

## 最小行为与文件边界

1. **只认当前完整形状。** `home-contract.ts` 将常量改1、移除 `source_directory` 旧形状字段，按现行生成器明确必需的 embedded/摘要字段，保留“是否打包 Node”的当前合法分支。不改产品版本、installer 标识、字段名、动作/Manifest/SDK格式。校验以现行写入值为独立依据，不从候选输出反推允许集合。
2. **先拒元数据，再修文件。** 在同一 installer owner 内维护 release/installation 当前形状判定，复用于读口，不建通用 schema 框架。wrong schema、旧 `source_directory`/缺 embedded 等不支持形状走明确拒绝；通过完整当前元数据后，文件缺失、node_modules 意外变链接、当前程序损坏仍按既有 repair；摘要变化仍按既有 refresh；新建/idempotent/合法不同产品版本更新及失败回滚保持。**元数据格式升级不能伪装成 repair。**
3. **预检顺序。** `home-files.ts` 收紧 installation 读取/已有值覆盖；`home.ts` 在 `prepareInstallHome`、stage/promote、写 launcher/manifest 之前完成已有 installation 与目标 release 的只读预检。新 Home 无元数据继续正常初始化，原“安装中断保留完整 reviewed prefs、仅程序文件回滚”保持，不为负例清业务库。
4. **必要直接消费者同步。** `home-release.ts` 使用同一当前 release 判定并写1；`home-launcher.ts` 实际读取 installation 的 Node 分支及 `runtime-integration.ts`，须拒绝安装 JSON 或其所引用 release JSON 的旧/不支持形状，不能只验证 installation 后照样指向旧 linked release。现有版本/摘要字段的对应关系沿写入合同检查，不读取旧源码或重建额外哈希。复用同一 installer owner 判定/生成片段，保现有路径限制；bundled Node 固定路径分支不另造 JSON 依赖。`uninstall-files.ts` 不将旧/不支持形状仅凭 installer 标记归为可删，沿现有 conflicts 拒绝且不改用户数据。当前完整格式但程序文件丢失的正常卸载仍可进行。

允许生产路径仅为 `apps/local-host/src/installer/{home-contract,home-files,home-release,home,home-launcher,runtime-integration,uninstall-files}.ts`。现有 `web-service*.ts`、`uninstall.ts` 的授权、preview/confirm、快照/owner锁、stop/remove、purge边界只读，默认不改；若实际需要改，writer 先给具体调用证据与 hunk，由根纳入原书，不能顺手扩写。当前两个 manifest 类型未从 local-host 公共入口导出，不新开子路径/API。

测试范围：`tests/install.test.ts`、`tests/service.test.ts`、`tests/uninstall.test.ts`、`tests/uninstall-catalog.test.ts`、`tests/runtime-integration.test.ts`、`tests/runtime-integration-ownership.test.ts`；依赖采集若被本次实际改动触及，才补现有 `tests/installer-symlink-dependencies.test.ts`。不复制大量元数据 fixture、不拆出新测试框架。

**删除旧演练的含义：** 移除 install:459–487 的“旧 linked-layout 自动升级成功”用例及只服务该转换的旧类型/分支；保留现有完整 embedded 的真实缺文件修复用例（:442），新增/替换为“已知旧形状即使写 schema1 也被拒”的边界回归。不得只改用例名，继续走旧升级成功。此前开始方案旁注中“保留旧 linked-release 成功演练”的准备意见由本次诊断替代。

本项不改其它独立版本1的 service/Runtime/uninstall 回执、构建指纹、业务库，不顺手处理 postinstall 选择目录等不同旧逻辑，不改旧 Home 也不提供迁移命令。
