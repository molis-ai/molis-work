## 开工前检查（98-1，2026-11-18）

核现状（main `3a6f2289a0`）：

- **写入已经允许两家共用。** 记过程项只核写入方自己 Manifest 的 `process_items.produces`（`modules/artifacts/src/plugin-operations.ts` 的 `record`，项目里再由 `apps/local-host/src/declared-types.ts` 的 `projectTypeDeclared` 按本项目在用的安装核一遍，S-81）；S-82 的属主检查（`packages/plugin-runtime/src/install-rules.ts` 的 `declarationClaimRefusal`）只看 `artifacts.produces` 与 `artifacts.links`，不看过程项。生产插件由平台按运行身份写进每一份（`producer_plugin_id`、`producer_binding_signature`），输入里自带的一律丢掉。
- **缺的是接收这一侧。** `listConsumable()` 只返回引用、种类、类型与标题，不带来源，也不能带条件；接收方要么全收，要么逐条 `read` 再看 `producer_plugin_id`。Coding 现在就是这样挑自己的产出（`plugins/native/coding/src/outputs.ts` 的 `codingOutputs`：先列全部，再逐条读，读完丢掉别家的）。

### 合同设计稿

阶段一，按原版本改，一个 PR 改完所有消费者（`docs/system/CONTRACT-CHANGES.md`）：

| 位置 | 改动 |
| --- | --- |
| `packages/contracts/src/platform/plugin-artifacts.ts` | `PluginConsumableVersion` 加 `producer_plugin_id`：平台记下的生产插件（取自写入时的运行身份，不取内容）。新增 `PluginConsumableFilter { artifact_type_id?; producer_plugin_id? }`；`listConsumable(filter?)`。条件只会缩小名单：先按 Manifest 声明的消费类型、授权、本人的个人过程项、在用且可用筛，再按条件筛；不带条件就是全量 |
| `packages/contracts/src/modules/artifacts.ts` | `ArtifactListQuery` 加 `producer_plugin_id?`，在主人的 SQL 里筛（分页与读正文之前），和已有的 `artifact_type_id` 一样 |
| `modules/artifacts/src/plugin-action-contracts.ts` | SDK 动作 `sdk.artifacts.<安装>.list@1` 的输入从 `{}` 变成两个可选字段，输出每行加 `producer_plugin_id`；版本不升（阶段一），`tooling/gates/actions/host-actions.tsv` 与 API 快照同步 |

不改的：S-82 照旧只管成果类型与链接种类（两家声明同一成果类型，后装、换版本、启用的一方仍被拒）；写入照旧只核自己的声明；读单个版本（`read`）的授权不变；端口接线（输入端口接某一家的输出端口）本来就是按来源，不动。

按来源筛只认插件 id。同一 id、不同发布签名的旧版本（PG-107）不会被单独区分；接收方要分时 `read` 里有 `producer_binding_signature`。目前没有使用者需要按签名筛，不为猜测加字段。

**五个场景。** 插件：任何插件声明同一过程项类型就能共产，接收方一个条件就能挑来源，作者不用多做事；第三方与内置同一条路。平台：放在平台的成果与过程项服务里，不在某个插件里写私有过滤。助理：SDK 成果服务只给插件受众，助理与 MCP 不直接列过程项，本批不变。各类平台能力：成果库不变（S-82）；端口接线本来就按来源；资料服务（平台自己的生产者）的过程项同样带来源、可筛。后续开发：再来一个同类生产者不用改平台；以后要按签名筛，在同一个条件对象里加字段。比较过「在 Manifest 的 `process_items.consumes` 里声明只收哪几家」：那会把一次读取的选择写死进声明、换来源要升版本，且不能同时要全量与单家；调用时带条件更通用，所以选它。

### 平台能力检查（第 4.1 节）

1. 别的插件也要：Coding 已经在自己挑来源；研究、写作这类共产插件都要。2. 平台已有 `listConsumable` 与 `ArtifactListQuery`，补字段即可。3. 是插件之间协作的问题，统一放在 SDK 成果服务。4. 第三方插件同样可用。5. 助理与 Agent 不直接列过程项（受众只有插件），不变。结论：**现在收进平台**（补进现有平台能力）。

### 验收编号

- **BL375-01** 两个插件声明同一过程项类型，按两种安装顺序都装得上、都能记；每份记的生产插件是平台按运行身份写的，输入里伪造的无效。
- **BL375-02** 接收方不带条件取：两家的都在（全选），每行带真实的 `producer_plugin_id`。
- **BL375-03** 按来源取只得到那一家的（仅选其一）；按类型取同理。
- **BL375-04** 没有匹配（来源没产出、来源没装过、类型没声明消费）得到空名单，不报错。
- **BL375-05** 无权读取：没授 `artifact:read` 的被拒；别的用户的个人过程项、没声明消费的类型都不在名单里，带条件也取不到。
- **BL375-06** 固定成果仍按 S-82：两个插件声明同一成果类型，后装的一方被拒，两种顺序都一样。
- **BL375-07** Coding 只列自己的产出，经平台按来源筛，不再读别家的版本。
