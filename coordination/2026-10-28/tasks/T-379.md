## 实现合同与取舍

1. 在 navigation 的可信端给既有名单并入**仅 Mod+K、Mod+F** 的平台全局组合，按实际承载 shell 搜索的 owner 能力决定是否提供；保留原 `[data-side-keys]` 的声明工具键。不得接受 child 自报名单、任意 chord 或为搜索伪造侧栏 tab／按钮。无搜索承载的独立页不应吞键。child 和 parent 都只接受可信端同份有限名单。
2. child 沿现有 bubble 监听发送，保留 defaultPrevented/composing/repeat；仅搜索组合新增现行终端 selector 排除（包括 terminal 内 textarea）。不把所有 textarea/contenteditable 排除，否则复现问题仍在。不扩大到终端、浏览器页面、讨论应用或所有 split-pane 文档的另一套键盘协议。
3. 主区复用原接收路径；K/F 经过白名单、scope.visible 后到已有外壳 keydown／搜索处理器。父端必要时补严格键值形状校验，不能让收到的任意字符串生成任意键盘事件。不得为“真实输入”给生产合成事件伪造 isTrusted；生产既有 relay 可以合成外壳事件，测试的起始按键必须真实。
4. 侧栏插件仍是 opaque child → 可信侧栏 owner 的 MessagePort → `molis:side-key` → 外壳。外壳接收新搜索组合前必须确认 origin、**actual event.source 与仍连接的侧栏 frame.contentWindow 相同**，且所在 body 是当前打开、可见、非 inert 的页；不能只信消息里 plugin/id/visible 字段。优先复用 `scripts/client/pane-messages.ts` 已有 `SIDE_FRAME_FROM_SCRIPT`（side-panel 内的 forwarded.from 也已暴露它），再核 body/current/open；无需新增来源登记或第二个 source 解析器。
5. 搜索组合在侧栏通过来源／可见性检查后转入同一外壳 handler，已声明工具键继续 keyed。**一条按键只处理一次**，不先 keyed 再重复触发两个 handler。保留现有 Issue 的从其他 side frame／自身输入召回及关闭行为。讨论页 homeToolKeysScript 是另一既有工具键路径，本单不向它添加 K/F；若共享 source 检查会影响它，按已有实际 discussion iframe 身份维持工具键路径，不把来源范围放宽到任意 iframe/window。

取舍：只恢复既定搜索组合和现行桥的两种落点，不引入通用热键注册中心、新 DOM 事件合同、window 全键转发或插件特例。优先只改下面两个生产文件；parent/types/initialization 只有实际证据显示两文件无法复用原处理入口时才由根释放相应锁，不能默认一起改。root 可采用等效更简单方案，但须完整满足上述行为和来源边界。
