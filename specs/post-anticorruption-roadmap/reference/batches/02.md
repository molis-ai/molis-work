## 给人讲清楚

防腐整理留下几类收尾：零散的待办和风险散在几个地方，有的没人负责；几份共用的基础代码有重复，版本号也各自涨过、没有统一；以后升级要从哪个版本算起也还没定下来。这一批把它们收干净：每件遗留的事都有主人、只记在一个地方，共用代码各留一份，所有版本回到同一个起点，并写好「从此以后改结构要怎样升级」的规则。做完之后，后面每一批都在一个干净、统一的起点上开工。需要你做的：真实 Home 的清空重建要等你说开始（旧 Home 整个搬开、不删）；版本号回到 0.1.0 之前，要先在 GitHub 上删掉旧的发布和标签，这一步只能你来；对外的许可说法和几条还没定的检查规则也要你定。

### 公共合同复位 · 开工前检查

这片把当前插件格式定为第 1 版。安装级和单条记录级连接账号仍是两个不同操作，调用方能从名字区分，动作名字里不再另写版本。在插件作者示例、已安装插件校验、工作流程绑定和 MCP 名称上核同一个结果。

原合同由 contracts 声明，解析只用 SDK，Runtime、CLI、工作台和各插件消费同一现行形状。按开发流程 §4 第 1～6、8～9、14 项核对：改声明和公开快照，同时更新全部消费者；安装身份、按项目和记录的权限、回执及否定用例要保留。第 7、10～13 项沿现行机制，本片不引入存储迁移、模型调用、成果类型、界面或错误种类。N39 只收经写入方证明总会写的字段，有真实可选场景的沿用原形状。门禁继续拒绝错误的版本与不合法声明。以两个动作快照比对前后的能力、输入输出和受众，按安装／按记录的拒绝路径分开跑；核实际安装、发现与调用。真实 Home 固定引用清理由第 ③ 项在维护窗口办理。

N39 已核到当前的真实可选场景：子任务的索引写入（`prologue-run.ts`）可不写顶层工作区模式，冻结意图仍带授权目录；Agent 输入只有 SDK 提供接收时间才落时间；无场景的判断不带场景来源，只提供文本的变更不带 Git 元数据。这些字段保留可选，Memory 沿原暂停决定。

**N29 补核（2026-11-04）。** 除 Agent 动作外，宿主动作快照还有 11 个工作区、Git、写入者和运行时动作在名字末尾带 `.v1`。正式宿主传入 `workspacesFor` 时还登记 4 个：已授权目录、设置中的目录列表，以及浏览目录的读取和选择。15 个动作一起去掉名字里的版本，均以独立的 `version: 1` 注册；插件声明、文档和 MCP 工具随之更新。验收在有目录服务的项目里查新名、拒绝旧名，并核快照其它列及各入口的调用结果。创作台的历史录制保留设计者当时看到的目录。

从产品登记生成并对照了 586 个清单动作、364 个宿主动作，三项消费场景原样保留。安装槽用 `connectors.plugin_slot.read/bind`，记录槽用 `connectors.plugin_slot.record.read/bind`，授权范围仍分别是 Home 与项目。公开快照按源码重新生成；工作区、作者和 Git 动作沿原项目合同登记，不占用 05 的 `contracts/modules/functions`。

**N26 回归补核（2026-11-04）。** R2 消费者的扩大回归发现，部分 MCP、助理脚本与目录断言仍沿用复位前的动作版本；Pages、Images 等少数用例还把现行与退役版本写成了同一个值。本合同片同步修正这些测试调用：正向调用固定使用现行 `@1`，明确检查旧 `@2`／`@3` 不可用。签名正文读取仍须实际进入读取后的撤权屏障，提示注入用例仍须取得不可信正文后验证越权拒绝；不以动作缺失代替安全拒绝。正文格式、权限、对象归属、幂等和持久化断言保留。首轮失败保留，修复后逐文件复验，不能据修改预期直接记为通过。

### SQLite 第一步 · 开工前检查

项目库由 storage 打开。测试通过 test-kit 取得相同驱动的连接；造空库、只读检查、事务、文件锁和临时库的生命周期都保留原语义。项目库在持有写锁时仍用自己的驱动检查版本，服务端的严格结构检查与项目库允许插件表的区别也保留。范围按 C3、B3、B4；生产代码和测试的直接驱动引用收进 storage，Alchemist 的既有例外保留。第二次换驱动在 05。目录版本错、空库与非空无版本、锁仍被持有、读检查不建库以及插件表的差异，是本片的验收路径。

按开发流程 §4 第 1、4、5、8、14 项，数据库连接及预检由 storage 持有，业务表仍归建表的包。允许增加 storage 和 test-kit 的小入口及对应工作区依赖，约束直接导入 better-sqlite3 的新检查按 C3 的原决定实施。其余项不新增动作、界面、权限或存储格式。真实 Home 与部署另按原窗口。验证覆盖公共入口、安装载荷与结构/文件锁拒绝；最终集成候选的 GitHub CI 全量由 Codex 按一骏 11-04 的接续授权执行。

### B2／N7 · 共用工具的开工前检查

插件和平台用同一套 SDK 来声明动作。**R2-01** 判断对象时排除数组和 null，留住各调用点原先允许的对象。**R2-02** 共享对象、数组和可空字段的 schema 构造函数；默认对象封闭、所有给出的键必填，调用方可明确选择必填键。**R2-03** 共用动作工厂从操作推导种类，默认项目范围，权限和受众由调用方给出。公共定义和实际绑定仍用同一个动作。**R2-04** 能共用的转义和错误文字沿用 SDK，对非 Error 有独立展示规则的入口保留原义。每一处迁入的动作须核回原快照；签名、请求摘要和已存幂等值的排序变更归重建窗口 N4。

按流程 §4 核对，公开工具归 SDK，只有 contracts 是它的依赖。接口先交合同评审，消费者随同一集成候选核回。声明本身不授权，不改变已登记的动作、权限、调度、输入输出或数据；仓库中的工具副本以行为一致为迁入条件。验收用 SDK 公开入口、插件样本和真实动作目录比对。界面没有新入口。

**解析与签名的边界。** storage 的项目日志、成果库的存储映射和 Feed 的来源映射在 JSON 文本损坏时会返回调用方给的默认值。Goals 的两处映射对损坏文本报 `storage.record_unreadable`；安装器拒绝损坏的配置，飞书 CLI 拒绝非对象结果。B2 收口时保留这些可观察差异，有破损数据处置要求时由对应的数据主人另定。Runtime 签包按现有顺序计算且有自己的序列化规则，N4 随重建窗口办理。

**同一集成分支的交接。** 公开接口见 [#1775](https://github.com/molis-ai/molis-work/pull/1775)。R3 和 R2 的平台消费者在 `feature/roadmap-02-storage-drivers` 合起来验；Codex 在整组就绪后触发一次 GitHub CI Full（用户 11-04 接续授权），本机继续只跑定向用例。

**2026-11-04 接续。** 一骏在统筹暂停后授权 Codex 持续推进本批并更新状态，随后明确授权本批 PR 的合并也由 Codex 处理，并确认最终集成候选的 GitHub CI 全量由 Codex 接续。第 ② 项仍在实施，以下 R2 消费者由本批会话在同一集成分支顺序完成；这只是本批改动的接续，其他批次与轨道的长期归属不变。开工已核当前在途 PR：Coding 的运行目录与草稿文案、Goals 自述判定、判断规则的编辑合同另有修改，本片不改这些文件。
