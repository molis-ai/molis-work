# Molis Work 产品设计共识与研究总结

整理日期：2026-09-22。覆盖本任务从设计研究、方案与 Demo，到 9 月 21 日三场会议及随后聊天确认的推进。本文按用户要求将核心结论与方向性指引前置，完整过程放在最后。

本文是这一轮讨论的交接入口，不是生产功能验收报告，也没有直接替换正式规格。**已确认的设计方向、会议中的设想、研究者建议、实际实现是四件不同的事。** 下文分别标明；未确认的细节不会因为写进总结就自动生效。

## 1. 核心结论与阶段性设计纲领

设计结论分为六类：先说明要改善什么，再分别讨论对象怎么组织、操作怎么衔接、内容怎么呈现、AI 怎么参与，以及结果怎么让人信得过。每类下面保留具体结论及其确认状态；当前先做什么放到第 2 节说明。

| 类别 | 回答的问题 | 核心结论 |
| --- | --- | --- |
| 1.1 设计目标 | 整体体验要变好在哪里？ | 减少理解工具、寻找操作和重新拼接工作上下文的成本 |
| 1.2 对象组织与导航 | 工作放在哪里，用户怎么找到它？ | 完整对象集合是基础；重点区帮助继续；同一对象和当前范围始终可辨认 |
| 1.3 交互与工作连续性 | 进入对象后怎么做，换插件后还能否沿用习惯？ | 功能可以不同，通用操作尽可能一致；前后步骤衔接，返回后能继续 |
| 1.4 视觉与信息呈现 | 怎样看得清、读得舒服、判断得快？ | 按引用或深度处理分配空间；兼顾密度与辨识度；保持整体视觉品质 |
| 1.5 AI 协作与配置 | 怎样少配置、少重复交代？ | 插件提供真实能力，助手帮助组合与配置，上下文与动作保持清楚 |
| 1.6 状态与结果可信度 | 怎么知道发生了什么、是否真的完成？ | 区分动作后果与完成状态，保留来源和版本，不用成功提示代替实际结果 |

### 1.1 设计目标：减少两类上下文切换成本

**让用户在 Molis Work 中连续把事情做完，尽可能少花精力理解工具、寻找操作、重新拼接上下文。** 视觉与交互升级都服务于这一目标。

“眼前一亮”仍是这次设计探索的要求，但它应体现在清晰、舒服、可靠且顺手的工作体验中。单页新颖、漂亮的成果封面、不同插件各有一套精彩布局，并不能独立证明整体体验变好了。用户从一个插件进入另一个插件，如果需要重新判断从哪里看、在哪里操作、这一步会发生什么，设计就增加了工作之外的负担。

上下文切换成本有两部分，不能只照顾其中之一：

| 成本 | 真实表现 | 设计需要帮助用户保留什么 |
| --- | --- | --- |
| 产品本身的认知与操作成本 | 换一个插件就重新找入口、理解布局、猜按钮后果 | 相近的操作位置、动线、步长和反馈；已学会的习惯能继续使用 |
| 脑海里的工作上下文成本 | 忘记为什么打开这份内容、前一步选了什么、现在在哪个项目、下一步要得到什么 | 当前对象与范围、来源、工作进度、选择、输入和后续去向的连续性 |

这不是要求所有工作都少点一次按钮。必要且清楚的一步，比一次看似快捷、却让人失去位置或误解后果的跳转更省力。也不是要求用户一定从首页或 Goal 开始；真实工作可能从任一插件进入。

**依据：** 聊天中对“专业内容区允许差异”的明确补充；会议 M1 对统一模式的讨论；M2 对工作连续性的讨论；M3 02:05–09:23 的再次确认。

### 1.2 对象组织与导航：工作找得到，范围认得清

#### 以完整对象集合为基础，用重点区帮助继续

**已确认：采用 A 方向，以对象集合为插件母页的基础。** 用户应能稳定地找回完整对象集合，而不是只能接受系统挑出的几个推荐。这里的 A 是讨论中的“对象集合优先”选项，**不等于已选定 Demo 的 A「续流」外壳作为最终方案**。

同时，基础不等于最大视觉面积。后续已认可的母页方向是：稳定的标题与操作区域、完整对象集合，以及可在上方固定位置出现的重点区。重点区承载确实存在的继续工作、需要处理或最近变化；没有真实内容就不强填。列表应容易发现、进入和使用。

这个基础要同时支持三类意图：

1. 用户已经知道要找什么，可以直接定位对象。
2. 用户希望接着做，能找到上次停下的位置及变化。
3. 用户需要看全局，可以浏览完整范围，而不被推荐替代。

**尚未定死：** 重点区高度、数量、各插件首屏字段、具体列表密度、默认展开方式。会议中的“三张卡片”、自由 HTML 画布、不同人自定义首页是讨论过的可能性，不是已承诺的本期功能。插件母页的结论也不自动等于全局 Home 的最终设计。

#### 多个入口指向同一对象，当前项目或个人范围可辨认

**研究与会议共同支持的方向：多个入口应指向同一个对象，而不是产生多份互不相认的工作。** 推荐、列表、关联引用、对话可以是不同入口，用户不应因此遇到不同版本或另一套状态。

M2 21:13 起指出了具体风险：工作一段时间后忘了自己在哪个项目，可能在错误范围里继续操作。后续需要让当前项目或个人范围可辨认，并减少无意义的重新选择。不能为了省一步而静默改换项目或假设用户意图。

### 1.3 交互与工作连续性：操作习惯能复用，前后步骤能衔接

#### 功能允许差异，通用操作保持一致

**已确认：官方插件统一对象的组织、进出和通用操作；允许功能差异，但专业内容区同样需要约束。** 尽可能保持操作动线、操作步长、用户认知和操作成本一致。

落实时先看几件事：进入插件如何找对象；进入对象如何认出当前工作；从哪里理解、开始和结束一个动作；处理完成后如何知道结果；离开后如何继续。相同含义的行为应尽可能保持相近的位置和后果，不让每个插件自己发明一套惯例。

文稿、表格、幻灯片、代码当然需要不同的专业操作。差异应来自内容与任务的真实需要。例如文稿需要段落编辑，表格需要行列操作，代码需要差异检查；这些差异不意味着“保存”“返回”“当前范围”“失败反馈”也应该随意变化。

判断一个差异是否必要，可以问：**如果沿用已有习惯，会不会损害这个专业任务？如果只是为了让这一页显得特别，应优先回到共享模式。** 这是本文对已确认原则的执行解释，不是新增组件或布局规格。

#### 以完成整件工作衡量效率，保留前后步骤的联系

**会议中收敛的方向：注意力保护不仅是信息筛选，更是减少完成一件事需要付出的总成本。** 列表少显示几项，不能代替把一项真实工作推进到可结束的状态。

用户筛选材料、形成判断、写作、检查结果时，前一步的选择和理由应该能支撑后一步。长期希望避免反复切插件、重新找同一份材料、重新解释需求。但本阶段不据此规定跨插件跳转、状态移交或自动执行的具体机制。

M2 提到的 `from → do what → to` 可以用来检查一项操作是否清楚：从哪里来、做什么、到哪里去。它不是所有插件必须新增的三步向导，也不是必须摆在首页的流程图。

对整体设计而言，“从哪里来、处理了什么、结果在哪里”要能解释清楚；是否并排、是否自动带入、是否停留原页，留到真实场景中决定。

#### 返回后能继续，具体打开方式在真实场景中校准

返回时保留必要工作上下文，是应继续追求的体验方向。**但本任务尚未确认一套新的点击／预览／正式打开／固定标签协议。** 原有规格继续约束现有实现；需要改动时核对现行行为，再在具体切片中定规则，不拿聊天中的候选方案直接覆盖生产。

### 1.4 视觉与信息呈现：兼顾判断效率、阅读舒适和整体品质

#### 根据任务分配空间：对象引用与内容工作面分别处理

**会议提出的重要约束：引用报告、文稿或成果时，不必把它展示成大封面或陈列柜。** 在选择输入、查看关联、决定去向等场景中，一条清晰的对象行或入口可能已经足够；为了呈现文件类型而放大卡片，会改变页面节奏和操作距离。

当用户正在阅读、编辑或审阅这份成果时，内容需要合适的专业空间。代码可以展示 diff，正文可以显示段落与批注，表格保留行列结构。两种场景需要的空间不同。

因此，不能从“成果应可直接检查”推导出“凡是出现成果引用，都要铺开大预览”；也不能从“统一对象行”推导出“专业内容都压缩成一个按钮”。具体预览入口和打开方式尚未统一定稿。

#### 信息密度要建立在条目可辨、内容可读的基础上

**已知偏好存在张力，需要实物校准。** 王一骏重视完整信息、高密度和稳定列表；徐晶强调阅读负担、适度间距，以及未悬停、未点击时条目就应有辨识度。M3 47:31 起将这个问题说得更具体。

不能把后一个诉求直接归为“想要 Dashboard 或卡片墙”。更大的间距不是唯一解法；列对齐、文字层次、分组、边界、行节奏和可点击区域都可能改善辨识。也不能拿“专业工具要密”来合理化挤在一起、需要 hover 才认得出来的对象。

后续应使用有代表性的真实内容比较：长标题、多条记录、不同状态、空与满列表、中文正文、矮窗口。既观察一屏能判断多少工作，也观察是否容易读错、点错和失去当前位置。尚未决定新增密度切换器，也没有冻结新的行高或留白参数。

#### 用统一的层次、控件与反馈形成视觉品质

**现有偏好继续作为设计输入，但可在具体证据下调整。** 专业工具、连续工作面、克制边界、准确的颜色语义、对齐、自然的反馈，是本轮应保留的基础。不要用浮卡堆叠、无用边框、廉价阴影或大面积装饰代替层级。

M3 44:24–45:10 对当时看到的生产界面提出：深色明显比浅色成熟。这说明浅色需要同等认真地打磨，不能据此决定放弃浅色，也不能外推为全产品所有页面已经比较通过。

`taste.md` 中的字重、焦点、图标、滚动和共享控件要求仍是现有参考。Shelf 的内容气质可以保留特点，但历史上的风格例外不能解释成通用操作也可以不一致。新的具体 token、动效、行高与例外，后续在共享组件和真页面中校准；本文不悄悄改写它们。

### 1.5 AI 协作与配置：让能力转化为更低的使用成本

**M3 后段认可的方向：插件做好自身能力，并向助手暴露可调用能力；由 Assistant 帮用户组合和配置，减少重复手工设置。** 不必为了每一种组合诉求，在每个插件里不断叠加专用功能。

用户指出当前配置方式灵活，但需要配的东西太多。这个问题不能因为底层已经有 Functions 或 MCP 就视为解决。用户应能说明自己要完成什么，理解助手将使用哪些对象和能力，并能检查实际结果。可见且可修改的配置仍有价值；“助手帮忙”不能变成无法理解的黑箱。

这里有三个不同层次：插件真实能做什么；助手能否读取并配置这些能力；用户能否轻松完成自己的任务。前一个层次存在，不代表后两个已经成立。M3 演示明确提到缺失动作、尚未对齐的接线以及没有真实跑过的流程。

关于“推荐动作”，会议没有得出“永远没必要”的结论。王一骏判断当前不必做；徐晶指出推荐错误会带来成本。应保留这两个理由，现阶段不新增一套推荐系统。Taskade、Rovo 等提供的启发是上下文清楚、动作贴近对象，不是到处加聊天框。

### 1.6 状态与结果可信度：动作后果清楚，结果有据可查

**这是仓库既有语义与研究共同强调的约束，不是这次新增的工作流。** 阅读、选择、保存、采用、发送、执行、已阅和完成，后果不同，界面不能用同一种成功反馈混过去。

例如：Feed 已读不代表进入后续处理；Inbox 处理不代表关联 Goal 完成；保存工作稿不代表已经形成提交版本；查看旧版的记录不应让新版自动通过；某次运行成功也不证明业务目标已经被接受。

来源、版本和用户决定需要可追溯，但不应把原始 ID、协议和日志变成用户开始工作的前置知识。先让人看清当前事实和下一步，再按需展开依据。沿用事实所属模块提供的真实状态，不为 UI 增加另一套完成算法或业务台账。

## 2. 这次升级要解决什么、当前先做到哪里

这一节说明本轮任务的范围和顺序：要交付什么、从什么产品基础出发、现在先做哪一段。第 1 节的原则用于指导设计，这一节用于指导接下来的工作安排。

### 2.1 升级范围：Molis Work 的整体产品体验

最初要求是对 Molis Work 整体进行 UI 与视觉升级。需要一起考虑导航、信息组织、操作动线、专业内容工作面和视觉品质，并拿出可体验的 Demo 比较和校准方案。

研究应解释哪些成熟交互值得沿用、各家独特做法解决什么问题、哪些适合 Molis Work，并改变实际设计。现有规格、`DESIGN.md`、设计系统说明、开发规范和 `taste.md` 是输入；如果新设计更合理，可以提出调整，但需要把原因与具体改动说清楚。

整体体验升级仍是目标。首轮 Demo 已完成作为讨论和校准对象的作用，用户明确决定不再参考或继续优化它。后续设计从真实产品、完整研究与已确认原则重新出发；如果需要新的原型来验证设计，也不沿用旧 Demo 作为基础。

### 2.2 产品起点：以已有功能为基础，各插件先解决自己的问题

Molis Work 已有本地工作台与多个插件，但各插件的能力还不完整。下一轮设计需要以届时实际可用的功能和真实任务为基础。例如 Feed 先让用户有效收集与处理信息，Pages 先让用户完成内容工作，再观察它们之间怎样衔接最自然。

各插件可以独立使用：个人暂存材料不必先选项目，写一份文稿也不必先建立 Goal。涉及项目时，再让用户清楚自己在处理哪个项目的对象。不要为了让流程图完整，给简单工作增加不必要的前置步骤。

长期希望把专业插件、Agent 和协作连接起来，但当前不能把尚未实现的能力画成已可用。本次核对的 [SSOT 索引](../../SSOT-MATRIX.md) 仍未包含完整的团队身份、权限和同步能力；它们是未来方向，尚不能当作已可用的产品能力。

原有文档与实现的差异已记录在[产品审计](current-product-audit.md)。实际修改哪个插件，就重新核对那一部分的代码与规格；这份总结负责传递设计判断，不重新定义业务规则。

### 2.3 当前顺序：交接共识，完善插件，再验证跨插件工作

**最新阶段决定：先写好总结与交接，按共同原则逐插件完善，再用真实链路讨论跨插件流转。** M3 13:33–14:44、35:59–36:47 明确调整了此前“逐条确认所有细节再改 Demo”的推进方式。

当前必须：把核心思想和依据交清楚；使插件各自能完成真实任务；沿用稳定的对象基础与通用习惯；记录真实使用中卡住的地方。已有原则可以立即指导插件设计，不必等所有点击规则被预先穷举。

可以延后：跨插件跳转与自动带入机制、完整接续协议、统一动作推荐、自由画布、任意视图编辑器，以及依赖未来团队底座的能力。延后不意味着从愿景中删除。

应从本阶段计划移除：为了抽象完整而新增流程编排器或第二套状态；为了“覆盖研究”逐项添加竞品功能；在插件能力尚未形成时规定所有场景的交互细节；把旧 Demo 的样例流程指定为生产路线。

重新讨论跨插件设计的建议条件是：选定的一条真实链路中，各插件已能处理代表性内容，关键输入、动作与输出可用，参与者实际走过一遍并能指出具体断点。**不必等所有插件的全部功能完成**，也不能仅以框架或接口存在作为条件满足。这是交接建议，不是新增排期或验收承诺。

## 3. 完整研究资料与综合提炼

### 3.1 完整研究文档：保留观察、推导和细节

### 3.2 综合提炼：这些设计分别帮用户省掉了什么

#### 一、稳定的对象与空间，省掉每次进入都重新找路的成本

Paperclip 的工作列表、monday 的主表与对象详情、Asana 的项目和任务、OpenAgents 的线程界面，都把范围选择、对象定位和具体工作放在相对稳定的位置。**共同点是用户可以预测下一步会在哪里发生。** 不能据此归纳为所有产品都是相同三栏，更不能要求每个 Molis 插件永远保留一块空目录。

Fibery、Notion、monday 和 Multica 又展示了另一层价值：同一对象可以有多个视图，用户改变的是观察角度。Task Master 则让对话与命令都能指向同一个任务。把这些放在一起看，得到的启发是：**入口和视图可以变化，工作对象、身份与当前结果要保持连续。**

这解释了为什么 Molis 应保留容易找到的完整对象集合，为什么推荐卡片和列表入口应该进入同一件工作，也解释了为什么只统一外壳颜色还不够。对象集合基础已确认；具体打开与返回协议仍需在真实场景中校准。

回看：[平台研究的共性与 Fibery 分析](research-platforms.md)、[工作流研究的共性与 Asana 分析](research-workflows.md)、[Notion 与 Task Master 机制](research-supplement.md)。

#### 二、有理由的重点与接续，省掉重新判断“现在该做什么”的成本

Paperclip 的 Blocked Inbox 不只是标红一条记录，而是交代出了什么问题、为什么卡住、谁能解除、已经停了多久。Beads 的 ready 队列说明哪些工作没有未完成的依赖阻塞。GSD 的恢复入口则帮助用户知道上次做到哪里、有什么新变化、接下来可以继续什么。三者解决的是不同时间点的判断问题：**现在为什么需要我、什么具备继续条件、回来后从哪里接上。**

它们共同启发 Molis：重点区应该给出可理解的理由和能进入的具体工作。例如“等你确认范围，影响两条要求”比“有 3 条待办”更接近用户要做的判断；“继续修改上次有反馈的段落”比重新展示全部历史更能帮助恢复。

完整列表和重点区由此可以同时成立。前者让用户自主寻找和看全局，后者帮助接续与判断；系统挑出的内容不能让其余对象变得难找。后续会议进一步提醒：减少注意力负担还需要让工作更容易做完，不能只靠少显示几项内容。

这是母页方向的研究依据，不是已经实现智能排序的证明。哪些理由可靠、下一步如何产生，需要真实状态支持。参见 [Paperclip](research-platforms.md)、[Beads 与 GSD](research-supplement.md)。

#### 三、按工作深度安排空间，省掉不必要的进入、退出和来回比较

Linear Peek 与 Notion 的侧预览适合短暂核查：读一下关联对象，再回到当前位置。Airtable Record review 适合连续处置：队列留在旁边，切换记录后继续判断。Fibery 的不同实体视图、单栏与双栏安排，则说明长文、关系数据和不同职责需要不同的阅读空间。

这些设计放在一起，能分清三个容易混淆的场景：**快速确认一条信息、持续处理一个对象、连续处理一组对象。** 它们对空间的需要不同。统一应体现在入口、位置感和操作后果，而不是强迫三个场景占同样的面积。

这也解释了 M2 对“成果陈列柜”的批评。选择一份报告作输入时，清晰对象行加按需预览可能足够；真正审阅报告时，正文才需要成为主体。Codex 的 diff 与 Vibe Kanban 的行内反馈进一步提示：深度处理应进入适合该成果的界面，意见可以直接落到具体内容上。

我们应学习的是任务与空间的对应关系。侧栏宽度、单击行为、快捷键和持久标签规则尚未定稿，应基于真实产品和具体任务校准。参见 [Airtable、Linear 与 Codex](research-workflows.md)、[Fibery](research-platforms.md)、[Notion 与 Vibe Kanban](research-supplement.md)。

#### 四、把 AI 放回工作现场，省掉重复交代和定位问题的成本

Taskade 的 Context Pills 让用户看见 AI 此刻使用的上下文；Element Selector 允许先点选具体元素，再说要改什么，解决“这里到底是哪儿”的歧义。Rovo 根据用户正在读或编辑什么提供相应能力，Asana 将人的补充和 AI 的回应留在同一个任务中。这些做法让 AI 使用已有的对象和关系，而不是每次都从空白聊天开始。

Commonly、OpenAgents 和 ClickUp 还提供另一个角度：Agent 的身份、关联工作、对话、文件和成果需要能找到，但没有必要同时常驻在主内容里。Linear 的委托机制提醒，执行者变化不意味着人的责任消失。对 Molis，用户需要知道的是“谁在处理哪件事、使用了什么、现在需要我做什么”，而不是先理解一套 Agent 组织结构。

monday 的对象内配置与 Retool 的配置／日常操作／执行观察分工，也值得一起吸收：改规则时能看真实样本与影响，平时使用不必反复进入配置后台，出问题才深入过程。它们与 M3 的助手方向相接：**插件把能力做实，助手帮助用户理解和配置，让灵活性不再全部由用户手工承担。**

具体动作可说明用途，例如“解释这个阻塞”，上下文可供核对。是否需要常驻对话、哪些配置由助手完成、何时需要人决定，仍要依实际任务与后果设计。这些设计方向仍需通过真实 Agent 与插件任务验证。参见 [Taskade、Commonly 与 monday](research-platforms.md)、[Rovo、Asana、Retool、OpenAgents 与 Linear](research-workflows.md)、[ClickUp](research-supplement.md)。

#### 五、让判断落在实际结果上，省掉从“机器说好了”到“我知道能用了”的猜测

Multica 区分持续的 Issue 和一次 Run，执行结束后仍为人保留审阅空间。Claude Code 区分运行控制、过程和结果。Tability 将实际结果、任务活动、趋势和置信度分别表达，避免做了很多事就看起来接近目标。它们共同说明：**工作是否结束，需要看用户期待的结果，而不是单次执行的状态。**

Codex App 与 Vibe Kanban 将意见直接放在差异或内容位置上，使反馈足够具体。Retool 的执行收据说明实际写出了什么、落在哪里；Fram 的提案、讨论和结果回链则让用户能追到“我选的方向后来怎样了”。这些都是把信任建立在可查看的内容和后果上。

对 Molis，值得保留的设计包括：当前成果与尚缺依据放在附近；反馈指向明确内容；处理后能看见真实去向；必要时回看决定与过程。比如“已保存草稿”就只表达草稿已保存，不代替“已交付”；“运行结束”也不代替“目标完成”。数据驱动的 Goal 才需要真实趋势，不能给所有工作硬造百分比。

目标完成语义、生产写入与真实验收须使用各模块的正式事实，具体呈现方式在真实产品中设计和验证。参见 [Multica](research-platforms.md)、[Tability、Retool、Fram 与 Codex](research-workflows.md)、[Claude Code 与 Vibe Kanban](research-supplement.md)。

#### 六、把变化、依据和恢复串起来，省掉重新读历史、重做解释的成本

OpenSpec 将生效中的要求与正在提出的变更分开，帮助人先理解改什么、为什么改。GSD 关注恢复时的当前位置与后续动作。Vibe Kanban 保留不同执行尝试及其相关结果，避免一次重试覆盖掉此前的工作。结合来源与成果引用的研究，Molis 可以围绕同一件工作把这些机制衔接起来。

一个具体的设计机会是：用户回来时，看见新的反馈，分辨它是否已成为要求，检查会影响哪份成果，再带着依据继续修改。修改后，旧版及其反馈仍能回看，新版不会自动继承旧版的认可。用户不必靠读完聊天来还原这一过程。

这里保留的是研究提出的问题与设计机会。后续先核对真实插件能承接哪些输入、修改和结果，再基于共同操作习惯设计适合的链路；具体布局与流转方式重新判断。

参见 [OpenSpec、GSD 与 Vibe Kanban](research-supplement.md)、[工作流研究中的来源到成果与决定对照](research-workflows.md)。

### 3.3 共性之外，仍值得留下的独特探索

综合结论不应该把每家都磨平为同一种工具。还有几类不同取向值得保留，待相应问题出现时再拿出来验证：

- **参与感与长期回访。** Fram 用人员、目标和持续 Feed 增加项目的生命感；Commonly 用共享房间形成共同工作语境。这对长期协作有启发，但也可能增加消息噪音。Molis 可以研究如何让用户感到工作在持续推进，不因此立即复制社交首页或团队头像墙。
- **适应不同职责的工作面。** Fibery 的实体视图、monday 的字段与视图配置、Airtable 的专门审核界面，分别处理同一数据在不同任务中的使用需求。它们提示后续可以研究恰当的可配置程度；当前先验证默认界面，不能把设计责任全部转交给用户自由搭建。
- **用关系解释当前问题。** Paperclip 的关系图、Fibery 的关联和 Beads 的依赖可以帮助解释为什么卡住、什么会受影响。Molis 值得探索围绕当前对象展开局部关系，而不是默认展示整张图；这仍是候选设计，不是已新增能力。
- **后果与控制权的表达。** Taskade 对访问与发布方式的区分、Multica 建议先填草稿、Claude Code 的运行控制，说明相似按钮可能具有完全不同的后果。Molis 应学习怎样在真正发生影响的地方交代清楚，而不是机械复制一套确认流程。
- **视觉如何服务阅读。** monday 的固定列轨、Tability 的层级行、Fibery 为长文留出的宽度、Fram 不同的移动阅读方式，都提供了具体取舍。可以借鉴对齐、层级、按内容分配空间；不能从“好看的一张图”直接推导出颜色、密度和布局适合 Molis。

这些探索与第 1 节已确认的方向不是同一层级。完整推导和原始证据保留在三份研究中，尚未进入当前设计不等于没有价值。

### 4.1 M1：2026-09-21 15:36，23 分钟

[会议原文](https://kcn8ld2n1dh4.feishu.cn/minutes/obcn6f28f92ibw3ye6z5c85c)。主题是现有 Demo 是否真正形成统一的工作习惯。

## 5. 能力关系与真实验证场景

### 5.1 不要把“框架可以连接”写成“用户已经用通”

M3 展示了一个有价值的方向：Feed 捕捉内容，Functions 表达重复判断，Inbox 承接需要处理的对象，插件提供相应动作，Assistant 帮用户配置与调用。会议同时明确暴露出尚未对齐的行为、缺失动作与未实跑的环节。

| 项目 | 本次可以确认的证据 | 不能据此声称什么 |
| --- | --- | --- |
| Feed 规则与 Functions 选择 | M3 有现场展示与解释；仓库文档描述场景绑定 | 每种来源、规则与后续动作都能正确工作 |
| Functions 暴露给 Agent 的能力 | 会议提到 list、describe、invoke，并指出 create 尚需补齐；这是会中版本的说明 | 当前最新版一定仍是同一接口清单，或 Assistant 已能自动创建所有配置 |
| Inbox 到 Pages | 会议描述候选路径，并明确相关动作尚未写完 | 已存在可供用户使用的完整写入闭环 |
| Assistant 降低配置成本 | 双方认可方向 | 已有真实助手自动完成配置、执行、检查与恢复 |
| 页面卡住 | 会议实操时出现，并被参与者指出 | 已定位为前端问题或某组件缺陷；需要另行复现 |
| 第三方连接器更新 | 王一骏提到当晚提交及连接器能力；参与者本机版本未同步 | 本任务当前 checkout 已包含或验收了全部更新 |

初次整理交接时核对的本地 HEAD 是 `c46151e`，即设计稿 PR 的合并点。准备提交本文时，已同步到包含 PR #68 的 `8e4753f`；本次只检查文档，没有重新验收新增插件能力。会议演示与前述能力判断保留各自的时间范围，下一位实施者仍需核对实际分支、提交、Manifest 和运行版本。

### 5.2 推荐用一条真实信息处理需求作为后续验证起点

**候选场景，不是本期已冻结的设计：** 用户持续收集内容，按自己的规则筛选，把需要进一步处理的内容放到 Inbox，最终形成 Pages 中可继续使用的材料或文章。

这条场景应该回答：

1. 用户真正要收集和判断的是什么，哪一段能力已由 Feed 提供？
2. 判断、总结和整理分别应该在哪里完成？不要仅凭这次会议就把所有总结能力硬塞进 Feed，也不要提前禁止 Feed 具备合理的处理能力。
3. 规则如何创建、复用和修改？人工配置与助手帮助的分工是否让第一次使用足够轻？
4. 从选中的真实内容到输出文稿，哪些选择、来源和范围需要保留？哪些插件动作尚未存在？
5. 用户处理错误、换项目、返回或重试时，是否知道发生了什么，能否继续？
6. 结果是否真的落在目标位置、可以被使用，而不只是屏幕上显示“成功”？

可分享 SOP、预置模板、批量导入规则是讨论过的可能性。先记录真实重复负担，再决定采用最小合适做法，不把它们全部升格为待实现模块。

### 5.3 对各模块的交接提醒

| 模块 | 本阶段应该继续解决的问题 | 不应越界的地方 |
| --- | --- | --- |
| Home／插件母页 | 找已知对象、恢复工作、看全局都有明确入口 | 全局 Home 与插件母页分开设计；不另建可写业务状态 |
| Goals | 当前约定、差距、依据、下一步可读 | 不以任务勾选数、运行结束或漂亮进度条代替完成语义 |
| Feed／Inbox | 阅读、筛选、需要人处理及后续去向清楚 | 不把所有信息都变成待办；读与处置分开 |
| Shelf／项目资料 | 暂存、原件与处理副本、个人与项目归属可理解 | 不自动把个人材料归入项目或团队 |
| Artifacts／Pages | 找得到版本、实际编辑与保存、反馈能指向内容 | 对象引用不要一律做封面；草稿、提交、已阅、验收分开 |
| Functions | 真实样本、规则、输出和使用现场相互对得上 | 配置能力丰富不等于配置成本低；不把判断答案直接当已执行动作 |
| Sessions／Coding | 归属、继续条件、运行与结果可见 | 打开不运行；未来协作和完整恢复不能由演示代替 |
| Dataset／PPT／Forms／灵光 | 先完善各自真正的创作与使用闭环 | 不强制所有内容关联 Goal，不把样张或 AI stub 当交付功能 |
| Schedule／设置／插件入口 | 生效范围、时间与结果、可用条件清楚 | 不承诺服务未运行时照常执行；不增加超级总控台 |

以上是对已有研究与会议的整理，不构成新增范围或各模块完成声明。

## 6. 官网、产品站、社区与商业定位

这部分来自 M3 17:14–34:10，属于整体交接背景，不直接变成工作台 UI 的视觉规范，也不授权修改其他仓库。

王一骏喜欢会议中提到的某竞品官网，但倾向 Molis 保持克制、冷静和专业感。徐晶提醒，过于精英化可能产生距离，影响个人用户、社区成员和工作室气氛。双方随后将问题转向不同受众的入口与叙事分工。

| 入口或关系 | 会议形成的方向 | 保留的边界 |
| --- | --- | --- |
| 公司官网 | 面向潜在合作方，说明是谁、在做什么、专业能力与独立产品；帮助建立信任和合作中的平等位置 | 官网不是被认定为唯一或主要获客渠道；专业不等于对所有受众保持距离 |
| 产品站 | 面向实际用户解释产品价值；以 Molis Work 为重要主线，其他产品可集成或独立使用 | 产品页不需要复刻工作室展示站；其他产品如何分线、是否冲淡聚焦仍可调整 |
| 社区 | 承载开源产品、百科、成员介绍与活动等 | 社区气质与企业介绍的任务不同；没有完成站点实施或信息架构验收 |
| 企业服务 | 通过真实场景理解、onboarding 与咨询帮助用户用好产品，沉淀方法和产品价值 | 重点是智力与方法输出，不以不断接单本身作为唯一目标；没有形成新的服务合同或交付承诺 |
| 既有产品与新提案 | 盘点已有仓库中值得继续的产品，也听取新想法；提案需要说明研究和推导过程 | 哪些产品发布、何时发布仍未最终决定 |

会议口述站点分工为 `molis.ai` 公司官网、`molis.app` 产品、`molis.club` 社区；另提到测试／内部域名及其他备用域名。转写存在识别误差，这里仅记录讨论方向，**未核验域名配置、归属、部署或所有站点的最终分工**。会议里口述的竞品名称也不据此当作已核实品牌重新加入 23 家研究清单。
