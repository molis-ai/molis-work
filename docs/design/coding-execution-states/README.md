## 怎么打开

```bash
python3 -m http.server 4413 --bind 127.0.0.1 --directory docs/design/coding-execution-states
```

然后打开 <http://127.0.0.1:4413/>。顶上的斜纹条是原型控制，不是产品界面：先选「块」，再切「方案」A／B／C 和「状态」，中英文、浅深色都能换；「重置」回到初始。

## 复用了什么

- **03 资料与目录（D 轨 `docs/design/workbench-shared-paths`，方案 A 已定）**：「项目输出」「本轮在」「正在看 …（只读参考），Coding 仍在工作目录里做」「回到工作目录」「本轮仍在 …（开始时的设置），下一轮起用 …」「本轮在临时副本里做，完成后经你审查交回」和「输入与输出」的说法与样子照搬；临时查看是独立概念，不改执行位置。
- **04 Onboarding（[onboarding-full-journey](../onboarding-full-journey/README.md)，已批准）**：失败与恢复都用它的框架——一句话说发生了什么、一句话说为什么和怎么办、列出已经保留的东西、主次按钮加「先往下走」、「技术细节」折叠。项目没设输出时的「用引导设置」走 04 的「从 Coding 的缺项进入，再回去」。

## 统筹已定、样张照做的

- 「还没开始、在等前面」只有一种说法：**等待前一步**（BL-164），计划卡、任务板、命令列表都用它。
- 计划卡和任务板**按位置编号**（BL-161），两边同一个数字；小步写成 3.1、3.2；计划改过就重新按位置编号。
- 没拿到退出码的命令不显示成功（BL-222）：命令写「结果未知」，所在步骤写「结果未知，待核对」，进度条不把它算完成；先核对，不自动重跑。本轮结尾写「本轮结束」，不写「完成」。
- 执行目录取项目当前输出，不取浏览中的文件夹；以后接上输入／输出目录（05② 的 `roles`、07 的选择器）后，样张里的「参考 N 个（只读）」就是那份配置。

## 四块的方案

### 目录

| 方案 | 样子 | 好处 | 代价 |
| --- | --- | --- | --- |
| A 顶部位置条（做样时推荐） | 头部下面一条：项目输出 · 本轮在 · 参考 N 个（只读）；异常用整行横幅 | 和 03 已定的 Coding 头部一模一样，不用另学；本轮在哪、输出在哪一眼对上 | 多占一行高度；窄屏上参考按钮只剩图标 |
| B 输入框上的位置签 | 不占头部；输入框上方「在 website 里做」「参考 2 个」两个签，异常提示也放在输入框上 | 发之前正好看到这条消息会在哪做 | 运行中的冻结、临时副本只能写在本轮抬头里，位置信息分两处 |
| **C 文件区抬头（✓ 已定）** | 文件栏顶部就是工作目录选择，下面一行说明；窄屏文件栏收成抽屉时，对话顶上补一行「本轮在 …」 | 文件和位置在一起，最省地方 | 窄屏文件栏收起后看不到，要额外补一条；和 03 已定的样子不一致 |

状态：正常、临时查看另一个文件夹、运行中改了输出、本轮在临时副本、输出文件夹不见了、项目还没设输出。后两种发送按钮不可用，并说明原因。

### 规则和模式

| 方案 | 样子 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A 只读时常显一行提示（✓ 已定）** | 模式是讨论、规划、评审时，输入框上方一直有一行「只读：这一轮不改文件…」和「换成修改」；输入框描边变色 | 发送前就清楚，不靠猜意图，不会漏；需求 R3「发送前清楚显示只读限制并给切换入口」原样做到 | 只读模式下一直多一行 |
| B 发送时才确认 | 平时不提示；只读模式下发出像开发请求的消息时，弹一个小确认：仍按只读发／换成修改再发 | 平时干净 | 要判断「像不像开发请求」，判断漏了就静默按只读发；多一次点击 |
| C Coding 判断后自动切换 | 模式改成一排分段按钮；判断是开发请求就自动换成修改并发出，给「撤销」 | 最省事 | 模型判断改了模式，可能误判；需求写明讨论、评审不暗中升级为写入，这条贴着线走 |

规则：三个方案都在输入框底部放「规则 2」（B 另在本轮抬头写来源），点开列出本轮实际用的规则文件、适用范围和版本。状态：正常、讨论模式下写了开发请求、评审完想直接改、规则文件在运行中改了（本轮仍按旧版本，下一轮起用新版本）、项目没被信任所以规则没加载（信任只决定读不读规则，不加权限）。B、C 的意图判断在原型里用关键词模拟。

### 恢复

| 方案 | 样子 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A 行内标记 + 本轮结尾的恢复块（✓ 已定）** | 每条命令行尾写结果；命令组下面一块 04 式的恢复块（发生了什么、已保留、怎么办、技术细节） | 一眼看全部命令的结果，处理只在一个地方；和 04 的失败框架一致 | 恢复块离出问题的那行隔着几行 |
| B 出问题的那一行就地展开 | 出问题的命令行下面直接展开恢复内容 | 原因和那条命令贴在一起 | 多条出问题时会展开好几块，列表变长；和 04 的版式不同 |
| C 底部结果条 | 命令组只留行尾标记；输入框上方一条「本轮结束 · …」，点「怎么办」弹出恢复内容 | 时间线最干净，结果一直在眼前 | 恢复内容藏在弹层里；往上翻历史时看不到当时的问题 |

状态：失败（退出 1）、结果未知（没有退出码）、被你取消、超时、被系统结束、重启后接着这一轮、后面的命令在等前一步。结果未知和重启后都是「先核对」为主按钮，核对后显示「核对过：已完成」，不自动重跑。

### 计划卡与任务板

| 方案 | 样子 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A 序号与状态分开（✓ 已定）** | 每行前面是位置序号方块，行尾是状态词和图标；计划卡和任务板一模一样 | 序号一直在，口头说「第 3 步」两边都对得上；状态词始终可读 | 每行最满，窄屏上长步骤名要截断 |
| B 序号藏进状态圆点 | 没开始的显示序号，完成变勾、进行中转圈、出问题变「!」「?」；状态词只在当前步和异常步出现 | 最省地方，像清单 | 完成的步看不到序号，「第 2 步」要数；状态词少了，读屏靠 aria |
| C 只在抬头说第几步 | 计划卡行前没有数字，抬头写「第 3 步，共 5 步」；任务板左边淡色序号 | 计划卡最轻 | 两边样子不同；问「第 4 步」时计划卡上要数 |

状态：正常、第 3 步拆了小步（任务板 3.1、3.2，计划卡只提一句）、第 4 步命令结果未知、第 4 步失败、计划改过（插入的步骤标「新插入」，后面顺延一位并说明）。

## 推荐走一遍

1. 目录 C：正常 → 临时查看另一个文件夹 → 点「回到工作目录」→ 运行中改了输出 → 输出文件夹不见了 → 项目还没设输出。
2. 规则和模式 A：讨论模式下写了开发请求（看那行只读提示和「换成修改」）→ 评审完想直接改 → 规则文件在运行中改了 → 项目没被信任；再切 B、C 点发送，对比确认和自动切换。
3. 恢复 A：结果未知 → 点「先核对」→ 依次看取消、超时、被系统结束、重启后、在等前一步；切 B、C 对比。
4. 计划卡与任务板 A：正常 → 拆了小步 → 结果未知（在任务板点「核对」）→ 失败 → 计划改过；切 B、C 对比编号方式。
5. 每块切一次 EN 和「深」，再把窗口拉到 1024 和 390 宽看一次。

## 宽度、键盘、外观

- 1440：文件栏、对话、任务板三栏；1024：两侧栏变窄；760 以下：文件栏和任务板变成抽屉（头部「文件」「任务板」按钮打开，点遮罩或 Esc 关）；390：去掉外边距，横幅和提示的说明换行、按钮另起一行，按钮高 36～44px。
- 弹层（输入与输出、看哪个文件夹、模式、规则、发送确认、怎么办）打开时焦点进第一项，Esc 关闭并回到触发按钮。
- 浅色、深色共用 03／04 的 Soft Workbench 色板；减少动态效果时去掉转圈和闪烁。

## 模拟边界

- 不读文件夹、不跑命令、不调模型；文件树、命令、时间、退出信息、规则文件都是示例。按钮的后果用底部提示说明。
- 「技术细节」里的 `exit cancelled`、`exit timed-out`、`exit none (a signal ended it)` 是当前 vendored SDK 真实给出的结束说法，`exit ?` 表示什么都没收到。
- 方案、状态、语言、外观记在本机 `localStorage` 的 `molis-proto.coding-execution-states.v1`，读不到就从初始状态开始。
