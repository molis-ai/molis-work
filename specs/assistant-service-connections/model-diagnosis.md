## 可以从记录确定的共同原因

1. **错误 JSON 类型已经出现在模型供应商的响应边界。** 不是从宿主日志猜测：供应商 SSE 的 partial_json 本身就是 `version: "1"`、数组字段 `{ "item": ... }`。这足以排除 Molis 收到合法 JSON 后将它转坏；仅凭这些记录还不能进一步区分模型生成错误和供应商内部的工具编码错误。宿主正确拒绝；模型几次把参数错误描述成 Molis 网关/XML 转换错误。对已给够的数组合同继续猜测、清空参数或换接入方式，保留为模型执行问题，不写新的正则纠偏或自动参数转换。
2. **产品给模型的反馈和事实不够。** 身份校验只说“Name the capability exactly”，数字错误也被说成名字错误；本地执行回执先前掩盖意图暂缓；新消息会撤回旧等待、暂缓连接，但新一轮没有 owner 的最新状态材料。前两项可从回执与真实状态直接证实，第三项可从新轮模型请求及 `AssistantService.dispatch` 的 withdraw 路径证实。
3. **输出修饰干扰了有效入口。** 普通接入链接里有 UUID，原“内部标识”检查触发改写，部分结果被改成不带链接的模糊入口。不是全部失败的根因，但多花模型调用并损害可操作性。本轮保留链接地址，只检查显示文字中的内部编号。另有“只在预告”的既有措辞检查会误命中等待说明；它没有导致已登记等待丢失，本轮不扩改 SDK/运行循环，作为后续已有表达检查的审查项。
4. **测试阶段和错误记录有缺陷。** schema 被当成实际授权值，completed 被当成等待，提问/终止被压成五分钟超时；原本地 fetch 失败没有 cause。原始结果不改写，修正下一次测试的判定与诊断；缺证据之处明确保留未判定。离线把全部十份原始请求重新交给修正后的取值函数：六份有真实授权编号，v26-save-1、v27-save-1、v26-save-2、v26-read-only-1 均没有；这与实际准备动作结果一致，尤其不再让 v26-read-only-1 越过原等待阶段。

## 首批诊断的独立修复与验证

- `prologue-action-gateway.ts`：分别指出 capability_id/provider_id 的非空字符串要求与 version 的 JSON integer 要求，保留拒绝、当前目录核对与零派出；没有宽松转换。
- `assistant-setup-material.ts` 和现有助理装配：从接入 owner 投影本会话、操作者与项目的待办请求，只在当前授权允许读取接入状态时提供。只包含授权编号、名称、状态、意图修订和是否已收到完成材料，不复制凭据、等待表或协议状态。`previous_wait_withdrawn` 来自本轮真实撤回结果。
- assistant-base v27→v28：在原有最新意图规则中解释上述事实与 retain/等待的分工。保留/取消仍由模型按用户意图选择。没有增加某种模型错误说法的词表；诊断结束时尚未进行真实复测，后续证据见末节。
- `announce-guard.ts`：链接目标中的编号不触发改写；可见标签或正文裸编号仍受原规则约束。
- `connector-assistant-model.ts`：证据提取只接受实际成功的 tool_result，排除 schema、请求参数和用户正文，按最新有效结果取值。新增回归能复现旧辅助函数的误判。

归因分别保留：

- **模型执行问题**：恢复请求确实带着最新只读要求、等待完成事实、当前 `Inventory MCP · 读取 MCP 资源` 目录和真实网关工具。供应商 #156 原始 SSE 是纯文字、`end_turn`，没有工具调用。没有证据表明 Molis 丢失了一次正确的读取调用。
