### 3.2 工作边界与存储

助理现有 `stateFor` 的 completed 来自最后一轮的 phase，普通 work revision 也会因改标题、草稿而变化：二者都不能冒充“原工作许可已经结束”。本次工作绑定不可复用的 work_id、原 actor/project/executor 与会话身份；Coding 独立入口绑定 owner 验证的 session_id、项目/工作区和安装世代。临时 activation 只管当前调用，持久 installation_generation 管重装／升级边界；不能把重启生成的新 activation 当旧 caller 恢复。

| 变化 | 当前工作委托 | 持续委托 |
| --- | --- | --- |
| 续轮、正常重试、等待、暂停、关闭页面、Host 重启 | 同一 work/session，重新取得当前身份后可复用；未知效果先核对，不重发 | 同样复核；不恢复旧运行闭包 |
| 改标题／草稿、同一任务正常内容推进 | 不以普通 revision 作废；单次审批仍固定原对象版本 | 同左 |
| 用户停止/取消工作、归档、删除、收回被委派工作，或 owner 明确结束该工作 | 撤销并留下 tombstone；恢复归档或重新开始不能复活 | 不把持续委托改成别人的工作；该工作禁止继续，未来新工作只有在原持续委托明确包含的执行者/项目/对象范围内才可另取当前许可 |
| 用户明确结束授权、到期、撤权、收窄、换账号或安装世代改变 | 老 revision 不再可用；扩大或重新授予产生新 id | 同左；不自动关联另一个账号或安装 |

没有 owner 的明确工作结束事件时，文案写“这项工作，停止或归档后结束”，不承诺从 AI 最后一句话判断任务完成。若业务 owner 已有正式完成／验收事件，接该事件关闭许可；不新造通用任务完成状态机。当前原生助理的 `continuation_hold: stopped` 会被下一次 Send 的 `begin()` 改成 input，插件工作 stop 分支更不会保存该标记，因此不能靠这两个旧路径充当持久授权终止事实。

新存储采用同一个 secure kind `molis-work-delegation-<app hash>`、schema 1 中的**按工作聚合记录**：可信主体生成 key，正文包含 `subject`、授权 epoch、`open/ending/ended`、结束时间/原因及该工作的委托条目；单条条目仍有独立 id/revision。持续委托是该 owner 的另一种有明确执行者/项目范围的记录，不能清掉已结束工作的屏障。工作停止、归档、删除或被收回时，一次 storage CAS 把该工作记录置 ending，同时结束其中全部本次工作委托；不逐条撤销 N 个记录，也不引入跨库事务。记录还没有条目时同样允许写 ending，避免授权创建与停止穿插。

具体顺序：原入口先验证人、工作归属及 stop/archive 的有效性 → 同步阻止该工作在途许可通过最终检查 → 等授权 owner 的 ending CAS 成功 → 执行原 owner 的停止/归档/删除 → owner 确认原运行和等待已收口后写 ended 并返回。若授权持久写失败，入口报告“未完成停止”，不返回成功；本进程保持禁止旧许可，读取最新版本后只重试单向缩权的 ending 写入。CAS 成功后业务停止失败，已完成的授权终止不回滚，保持 ending 并说明工作仍需停止；用户重试先核原 owner 的真实状态，已停止只补 ended，不重复派发效果。重启即使业务 owner 尚未来得及写 stopped，ending/ended 都会拒绝旧许可；普通新一轮、Send 清 hold 或恢复归档不能重开它。

同一工作的新授权须由实际工作 owner 核实原停止/归档已收口、当前工作可继续，才允许把 ended 改成新 epoch；ending 期间拒绝授予、重开和新运行。停止、归档、重开与新运行的提交共用该工作的串行入口及持久 epoch 校验，不允许一个晚到的旧 stop 按 work_id 清掉新轮状态。归档/删除尚未完成或 owner 状态不可读时不能发新 epoch；新建工作用新的 work/session 稳定身份。扩大范围或重新授予仍是用户明确决定，旧在途调用始终绑定旧 epoch。

授予、收窄和结束在同一个工作记录上按 expectedVersion 仲裁；授权来源保留委托 id/revision 与工作 epoch，不把别的条目修改当成本条授权。结束与授予同时发生时，过期 expectedVersion 的保存失败，客户端不能读新版本后静默重试授予；结束可以读新版本重试，因为只缩权，重试期间禁止旧许可。持续授权派出前也必须同时核该工作的 ending/ended 屏障。第一次加载完成前不交出委托执行口；缺记录表示没有新增委托，坏记录阻断该主体并明确报错，不能从旧内存 standing rule 或 UI 偏好补造。持久许可加载不恢复 S-27 的旧轮次闭包：接续仍由工作 owner 在最新身份下开启新一轮。新 kind 无存量升级，不修改 session index 或 MCP 文件形状。

生命周期接入点包括 `controlAssistantWork` 的原生与插件两个分支、助理归档/删除/委派收回、Coding session 的停止/归档/删除。入口已核定“停止该工作/会话”才结束授权；仅取消一条工具或结束一轮不推断整项工作结束。实施时用这些实际入口做崩溃交错用例，不能只测授权 store 的 `end()`。

编码会话的归档由编码插件先锁住原会话的启动入口，核对它已无执行和待核对结果，再调用 Agent Host 的插件动作 `agent.session.end-work@1`。该动作只接受原会话引用，以当前插件、项目和用户核对归属，从授权 owner 扫一次找到该会话的本次工作记录，再经原结束与结算路径写入结束事实。覆盖同会话历史角色和安装世代，持续授权继续归原 owner。授权结算在编码插件保存归档前完成，任一步失败沿原入口重试，已经结束的许可不会因归档写入失败恢复。现有“停这一轮”只结束执行轮次。

## 4. 审查与来源合同

在现有审查投影上补两组事实，字段名在 C 合审后确定：

1. **当前可决定性**：`approve` 与 `reject` 分别给可用性；不可用有稳定原因及 owner 的可翻译说明。由队列与执行适配器按当前请求、存活执行方、安装、权限、版本与有效期算；页面只显示。点击时服务端仍再核，投影不是执行凭证。不能用是否有 authority 单独推断 reject 可用：`respond` 还要求 owner handler。真实 Git 恢复会撤销未派发的旧等待，Agent 历史未决定项恢复为 cancelled，均不提供决定。只有仍 pending 且 owner 确能完成原记录关闭的请求才可拒绝、不可批准；取消／到期／已决定不能再次决定。
2. **批准来源**：真人直接决定、沿用用户有限委托、独立 AI 在明确低风险委托内代批，分别带各自可信引用。来源不能仅由 `decided_by` 字符串或 note 推断。AI 的评估引用、委托引用及理由只作其 provenance；显式人审计票不接纳此类来源。执行 Agent 没有可写此来源的输入字段。

已有单次决定还要绑定当前请求内容与版本。任务委托允许正常进展，不等于旧版本的单次人工批准可以挪用。最终写入前，实际 owner 与 action service 使用相同的冻结对象／版本和当前授权检查；任一不符拒绝，既不写成功也不写失败业务记录。

AI 来源合同本批接通且测试隔离；实际 Coding 低风险独立评估器按第 64 批实施，绝不使用 mock 返回来声称 APR-12 的完整产品路径已可用。

来源形状为 `person`（可信入口 actor）、`delegation`（委托 id/revision、工作 epoch 和原 grantor）、`ai`（受限委托 id/revision、独立评估引用与模型来源），另有 `policy` 表示已经存在的可撤销等自动策略（原策略 owner/id/revision，不计真人票，也不假称一次用户委托）。只能由 Host 内部不同决定入口创建；HTTP/动作输入不接收该字段。当前 `#automatic` 按 review id 设置临时标记有串源窗口，删除它：来源随一次内部决定调用传到最终持久写入，不在共享 Map 上让另一调用借用。每条 review 的竞争通过一次串行 claim 与 storage CAS 仲裁；谁赢，谁的决定和来源一起入库，输方不消费也不执行。真人入口不能因同 id 的自动调用正在等待而被标成沿用授权。桌面控制不能自批的现行可信入口检查保留；没有新的 AI 评估器时不开放一个能自报 ai 来源的替代接口。

共同引用用 `{ owner: { kind, project_id, plugin_id, install_id }, id, version }`。Agent review 的 version 是 owner 对冻结请求的稳定摘要（含原 pending/effect 引用、文档、对象版本及操作范围），用户提交必须携带显示时的 version，服务重读后相等才接受；队列现有同 id 不可替换仍保留。Goals 验收引用由 Goals 动作重读其验收对象版本，只有 Goals 能做接受/返工。通用卡仅路由到登记的 owner 决定动作，不把 Goals 审查复制成 Agent review。

#### 来源的原子记录

使用独立 schema 1 的 secure kind `molis-review-decision-<app hash>`，以原 owner + 原 pending/effect 的稳定 id 为唯一键，正文保存**版本、决定和来源的一份完整记录**，expectedVersion=0 为唯一首次决定。version 放在值里，不允许换一个 version 键再批准同一原操作。版本哈希由冻结执行提案计算：原 effect/pending 身份、原 Session/Run/安装归属、实际 capability/工具合同与完整参数、原资源/文件预览指纹及目标版本。排序采用同一规范 JSON 写法；显示标题、翻译、当前时间、现在的权限、SDK 之后变化的 state/revision 不参与哈希。请求的展示数据可刷新，执行提案不能被替换。

它是新来源决定的事实，不是一个可在原决定之后补写的标签。Agent 待批桥、Git、checkpoint rewind 都必须先提交该记录，再消费批准或回答 SDK；现有 session index/Git 四字段记录仅保留原执行恢复需要的投影，不从它们猜测新来源。历史没有该新记录显示“来源未记录”，不会被当成真人票或恢复委托；这是新事实的缺失，不解析旧枚举、不迁移旧格式。

顺序固定为：校验 owner/版本/可决定性 → claim → 原子决定记录 → 更新队列投影 → 原执行恢复投影 → 消费一次许可 → 回答/派发 → 读实际效果。落盘失败且读回确认未提交时保持 pending、释放 claim；提交结果不确定先重读同一键，读不到确切结论则保留“决定保存待核对”，不能再批准/拒绝或消费。决定已持久而恢复投影/答复失败显示“送达待核对”；效果未知显示“执行结果待核对”，两者不混作“没有执行”。重启仅投影已保存决定，不重放答复或副作用。所有写入口和恢复读入口按此覆盖，不能只改 receipt 类型漏掉 Git/checkpoint。

claim 只是排他，不是许可：取得 claim 后、决定记录真正提交前，重新核对当前人审入口、原请求期限、取消、安装/权限与委托版本。存储提交沿现有 `effects.call`/Host action control 及同步最终检查，在任何等待之后仍拒绝失效调用；不能“检查完再任意 await，最后落盘”。决定已提交后若在旧投影保存或 SDK 送达等待中失效，保留已存在的真实决定与来源，但不再写迟到业务投影、不消费/回答/派发，依据 owner 的真实派发凭据收口。代码与用例要分别覆盖提交前拒绝、提交后未派出、派出后未知三个窗口。

平台动作在提案形成时，以已选动作和规范化实参取得原登记的持续检查；复用 Host 的异步 `beforeEffect` 与同步 `assertCurrent`，不在批准时重新发现目录。检查固定原提供方、登记 token、项目和整轮权限，MCP 固定已有授权世代；助理当前关闭该能力必须拒绝，无关能力变化不使提案失效。SDK `tool-before` 给出的原 Run/tool call 用于固定提案，执行器用本轮闭包中的同一记录和 SDK call id 核参数，不能从工具实参自报身份。决定保存、SDK 答复和实际动作调用沿用这份检查；Git 执行方也须在自身异步预检之后、真正文件或 Git 写入之前再次检查。不借用已经结束的启动调用生命周期，不新增通用场景版本系统。此细化由本批同一只读评审代理核查；最终代码仍须评审。

现有记住范围保留：`remember: session` 的原精确命令规则在内存中分配稳定规则 id，后续自动决定携带 `policy/session-rule` 来源与原设置人/时间，不用 `#automatic` 临时串源，也不假称持久委托。`remember: app-this-round` 仅由真人可信入口的明确选项产生，原 pending 确认接受后才安装到原 run，不能由 delegation/ai 来源顺带创建；撤权或 run 已结束时不再安装。这一调整需真实 SDK 的拒答、取消交错用例。

恢复顺序明确覆盖 `prologue-restored-session`、Git `restore()` 与 checkpoints：先用同一稳定键读新决定，再判断旧执行投影/SDK 的真实状态。新决定已经落盘而四字段投影尚未写入时，新决定仍生效；不能走旧的“没有决定所以 cancelled”分支覆盖它。新记录不可读/版本不符时明确阻塞该原操作，不回退为旧来源或 pending。没有新记录时才沿原四字段历史恢复，来源为未记录。若新批准保存后原 SDK 等待因重启被取消，显示“已批准，但原操作未执行”，只按真实派发凭据收口，永不重放答复。临时读取故障消失后，当前进程的 refresh 必须能重读这笔未收口的原记录（包括 Git worktree/operation），不只依赖重启，不重复扫描所有已完成的历史。

首次读取失败时只保留该原请求的历史占位。后来确认新记录不存在，才由原 owner 重读旧决定；读取期间仍不可批准或拒绝。并发刷新共用同一笔读取，回读后再次核对占位身份和原引用再投影；失败保留阻塞，重复登记不能覆盖实时提交或已经保存的新来源。历史占位未查清前，不向旧执行索引写入猜测的取消状态；解除占位后交回原 owner 核对实际 SDK 结果。

### 4.1 BL-359 生命周期

旧建议在 `decide` 中立即删除所有 authority 不适用于当前实现：`observeReviewSettlements` 必须收到原安装信息，才能发送 `host.review.settled` 和对应工作区变更。

候选处理：未执行就拒绝、取消或到期，释放队列引用；批准进入执行后保留到结算通知完成，通知后释放。同样检查 `#deciders` 捕获的 `execution.authority`，只删 Map 的一处不能证明 caller 已释放。到期现在是派生状态，释放须覆盖无人再点按钮的过期路径。未知结果仍需后续核对，不能把不确定状态等同终结；仅保留完成恢复所必需的数据，避免闭包无限留存。若需将通知身份从持权闭包解耦，只保存身份值并在投递时核当前安装，仍守 S-54；不得把历史安装当当前接收者。

验收不是增加一个“内部 Map 已删除”断言即可：要证明原 caller 可释放、成功与失败通知仍到原有效安装、旧安装不得收到，恢复历史不再发送一次，重复 settle 不重复通知。

第一片生命周期修复沿现有合同做，具体状态表如下；它不提前引入新的来源或委托格式：

| 状态变化 | decision handler | authority 与结算来源 | 后续可决定性 |
| --- | --- | --- | --- |
| pending 且未到期 | 保留原 handler | 保留 | 还须检查执行 owner 与权限；不是只看 pending |
| 拒绝／取消／到期 | 删除；正在执行的 handler 只活到当前调用退出 | 删除 | 均不可再决定 |
| 批准 | 决定落定便从 Map 删除；本次调用仍可完成持久化与派发 | 保留到实际结算；不得在 decide 删掉通知来源 | 允许当前 owner 首次消费，不可再次决定或重复消费 |
| 已消费、执行未知 | 删除 | 只保留轻量通知身份与弱引用的活性判定；不保留原 caller 强引用、execute/check 闭包 | 只可向真实恢复 owner 核对，不能重批 |
| 成功／失败结算 | 删除 | 先用原来源通知，再在 finally 删除；相同 settle 不重通知 | 终态 |
| 恢复历史 | 不创建旧执行 handler | 不创建原 activation，也不发“新执行”通知 | Git 未派发与 Agent 已中断等待按现有适配器取消；仍有效的关闭能力必须由 owner 真正提供 |

Host `reviewAuthority` 用 `WeakRef<HostPluginCaller>` 核原 issued caller，不能捕获其强引用；活性仍检查该原对象，不能按相同 install_id 找一个新实例顶替。unknown → 最终 settle 保留来源通知，进程重启后历史不通知。到期使用队列一个最近期限定时器（unref），每次状态变化重排；不用每条一条永久定时器，也不依赖用户再次点击。原 SDK 管执行等待的过期，队列只终结自己的投影和引用。关闭时停止定时器并释放 pending handlers/authorities；这不构造执行成功。
