## 1. 背景

错误模型规定：状态只由失败的种类（kind）决定，种类到状态的对应只在 `packages/plugin-sdk/src/errors.ts` 一处（`actionHttpStatus`、`actionErrorResponse`）。`pnpm health:check` 里「由错误的码或类型选出的 HTTP 状态」现在是 46 处、15 个文件，只许减少。其中宿主有一批出口还在用 `error.code === "…" ? 404 : 400` 这种写法自己选状态。这一单挑两处边界清楚的：`apps/local-host/src/web-project-deletion.ts:22`（`sendDeletionFailure`）和 `apps/local-host/src/web-mcp-action-settings.ts:93`。两处的目标行为都已经在 spec 里写明（见第 6 节），不是新决定；已经改好的同类出口可以照抄：`apps/local-host/src/web-project-settings.ts:150`。数字上这一单把那个统计从 46 降到 42。

## 2. 目标

1. 删除项目出口（`sendDeletionFailure`）和 MCP 授权设置出口的 `catch` 不再自己写状态数字，状态与正文都来自 SDK 的 `actionErrorResponse`（或同文件约定的 `respondLocalWebRefusal`），现有被测试钉住的状态一个不变。
2. MCP 授权设置里「某个能力不可用」的拒绝带上提供方声明的 kind（`state.kind`），所以真实 owner 的 409、平台的 403/404/503 能原样出来；没有 kind 的 fixture 仍然是 400。
3. `node scripts/check-health-gates.mjs --base origin/main` 里「HTTP statuses chosen by a test of an error」从 46 变成 42，`web-project-deletion.ts` 与 `web-mcp-action-settings.ts` 在这一项里不再出现。

## 3. 不做

- 同一份清单里的其他出口（`web-connector-connections.ts:105`、`web-connector-methods.ts:95/100`、`web-planning.ts:132`、`plugin-event-http.ts:27`、`side-files-http.ts:115`）：它们要先改错误码的声明（合同包里的 `PluginEventError` 与 `connector.connection.*`、Goals 包里的 `goals.planning.method_not_found` 现在都是 `invalid`），或者现在按错误码文字取状态（`side-files-http.ts:115` 用 `/not_found$/`），不是纯出口改动，不做；也不另开行，由统筹排。
- 把 `new ActionError("mcp.grant_invalid", …)`、`"mcp.grant_missing"`、`"mcp.grant_requires"` 改写成 `defineErrorCodes("mcp", …)` 声明：它们现在没有 kind，按 SDK 规则算 `invalid`，也就是 400，行为正确，不动。
- `web-project-deletion.ts:58-60` 那条直接 `sendJson(response, 400, …)`（确认没勾、删除键不合格）：它不是由错误选状态，不在统计里，也不改。
- 前端页面读这些响应的代码：正文里多出一个 `code` 字段不影响它们，不动。

## 5. 做法

已定的决定：

- 删除出口：`sendDeletionFailure(response, error)` 的签名和两处调用（`web-project-deletion.ts:71`、`web-project-settings.ts:65`）不变，函数体里用 `actionErrorResponse(error)`，再 `sendJson(response, failure.status, failure.body)`。照 `web-project-settings.ts:150-151`。
- 授权设置出口：`catch` 里同样用 `actionErrorResponse(error)`；第 88 行的 `new ActionError(state && !state.available ? state.code : "mcp.grant_unavailable", …)` 加第三个参数 `{ kind: state.kind }`（`state` 不可用且有 kind 时才带；`ActionAvailability.kind` 在 `packages/contracts/src/platform/actions.ts:361` 可选，没有就不传）。
- 不新写 Error 子类，不新增错误码。
- 状态变化只许是下面这两张表里写的几行。表外任何状态变了，停下来问。

删除出口，现在与改后：

| 失败 | 现在 | 改后 |
| --- | --- | --- |
| 运行中的终端，`catalog.project_terminal_live`（kind conflict） | 409，带 code | 409，带 code，不变 |
| 删除键冲突，`catalog.deletion_idempotency_conflict`（kind invalid） | 400，不带 code | 400，带 code |
| 项目不存在，`catalog.project_not_found`（kind not_found） | 400，不带 code | 404，带 code |
| 不是 ActionError 的失败 | 400，原文 | 见方案问题 1 |

授权设置出口，现在与改后：

| 失败 | 现在 | 改后 |
| --- | --- | --- |
| `actions.missing`（kind not_found） | 404 | 404，不变 |
| `mcp.grant_invalid`、`mcp.grant_missing`、`mcp.grant_requires`（无 kind） | 400，带 code | 400，带 code，不变 |
| 能力不可用且声明了 kind（owner 的 conflict、平台的 forbidden 与 unavailable 等） | 400 | 按种类：409、403、503 等（这是 W3-02-G4-04 写明的目标） |
| 能力不可用且没有 kind（测试夹具 `fixture.offline`） | 400 | 400，不变 |
| 请求体过大，`actions.input_too_large`（kind too_large） | 400 | 413 |
| POST 里项目不存在，`catalog.project_not_found`（kind not_found） | 400 | 404 |
| 不是 ActionError 的失败 | 400，原文 | 见方案问题 1 |

【方案】里要回答的问题：

1. 不是 ActionError 的失败怎么答。已有两种写法：`web-project-settings.ts:150` 一律 `actionErrorResponse(error)`（得到 500，`code` 为 `actions.execution_failed`，正文是原文）；`web-http.ts:40-48` 的 `respondLocalWebRefusal` 对非 ActionError 重新抛出，由 `sendUnhandledWebError` 记日志、不带原文、带诊断号。倾向后一种（`web-http.ts:40-41` 的注释把它写成了约定），但要先读调用链确认这两个处理函数的外层确实接得住重新抛出的错误，再答。
2. 在 `web-mcp-action-settings.ts:92-95` 的 `catch` 里，GET 路径抛出的错误（第 51 行专门吞掉 `catalog.project_not_found` 的那一支除外）有没有可能走到这里；如果有，GET 的状态是否也跟着变。
3. spec §10.9 的 W3-02-G4-04 写明了这个出口的目标，但现在 `grep -rn "G4-04" tests` 没有命中。查 git 历史说明这条验收当时是由哪个测试证明的，或者没证明；如果没证明，本任务补上证明，测试名带 `W3-02-G4-04`。
4. 新用例怎么造出「owner 声明了 kind 的不可用」：`tests/mcp-action-settings.test.ts:27` 的 fixture 里 `availability` 现在返回无 kind 的 `fixture.offline`，打算怎么扩（再加一个 provider，还是让同一个 provider 按开关返回不同 kind）。
