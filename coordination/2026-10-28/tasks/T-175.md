## 1. 背景

### 1.1 前两单做了什么

- **T-054**（`3fe5e45bf`，#1407）：Home 里已装同一个 ID 的插件，来的包出自另一个发布者：确认时在固定发布者和保存包之前，以 `plugin.definition_conflict` 拒。比的是同一个 ID（下面的 `present`）。
- **T-155**（`f8405728b`，#1426）：
  - 预览时 `assertNotHostId`（`plugin-install-service.ts:70-77`，`:97` 调用）拒宿主构建带的插件 ID，和它点分路径上的 ID，装进 Home 或项目都一样；
  - 确认时，Home 里已装同一个 ID、同一发布者的包也在保存之前拒，`plugin.state_invalid`（`:149`）；
  - 重写了 `:139-142` 的注释。
- 两者都只比“相同的 ID”或“宿主的 ID 表”，不读已装的别家插件的点分路径，也不看项目里同一发布者的包是不是升级。

### 1.2 `confirm` 现在的检查次序

`plugin-install-service.ts:127-162`，顺序如下（括号里是行号和码）：

1. 预览存在、没过期、同项目同人（`:130`，`plugin.preview_unknown`）；
2. 同意（`:131`，`plugin.consent_required`）；
3. 运行范围没变、范围没被别的包改过（`:133-134`）；
4. 集成 ID 没被占（`:136`）；
5. 发布者的固定没被撤销（`:137-138`，`plugin.publisher_revoked`）；
6. 同一个 ID 已装在这里，且发布者不是同一个（`:146-148`，`plugin.definition_conflict`）；
7. Home 里已装同一个 ID（`:149`，`plugin.state_invalid`）；
8. 发布者没固定又不给名称（`:150-156`，`plugin.publisher_untrusted`），给了名称就在这里**固定**；
9. **保存包**（`:157`）；
10. 交给安装宿主装（`:159-160`）；Runtime 的 `id_namespace_conflict`、生命周期的 `upgrade_required` 都在这一步之后。

`:139-146` 原样（本单只在 `:149` 和 `:150` 之间加两行，注释和这几行不改）：

```ts
    // In a project, a package of a plugin already installed there is its upgrade, and only its own publisher's: another publisher's is refused
    // before it can be pinned or kept, in a project or the Home. A Home package looks at the Home's installations of signed packages (an id of
    // the Host's own plugins was refused at the preview), a project's at the project's. The Home does not upgrade a package in place (S-80,
    // BL-628): its own publisher's is refused here too, before it is kept, with the code the Home's install answers.
    const inHome = held.runtime_scope === 'home';
    const entries = inHome ? await (this.ports.homeInstalled?.() ?? []) : await this.ports.installed(held.project_id);
    const present = entries.find(item => item.record.plugin_id === held.pkg.manifest.plugin_id && (!inHome || item.record.publisher_trust === 'pinned'));
```

`entries` 是这一侧 Runtime 里没卸载的全部记录（`installedPluginEntries` 与 `installedHomePlugins` 都不列已卸载的）：含宿主自己的、未签名的、签名包的。`present` 是同一个 ID 的那条。到 `:150` 时，`present` 若在，一定是同一发布者的（别的发布者在 `:146` 已拒），而且只可能在项目（Home 的在 `:149` 已拒）。

### 1.3 两个缺口

**缺口一：点分路径（`MISC:22`）。** Runtime 的规则（`install-identity.ts:15`、`:41-46`，原样）：

```ts
const nested = (a: string, b: string): boolean => a.startsWith(`${b}.`) || b.startsWith(`${a}.`);
```

```ts
  for (const record of installed) {
    if (record.state === "uninstalled" || record.plugin_id === id || !nested(record.plugin_id, id)) continue;
    if (trust.level !== "pinned" || record.publisher_trust !== "pinned" || record.publisher_signature !== trust.publisher_key_id) {
      throw pluginErrors.id_namespace_conflict(`插件 ID ${id} 与另一个发布者已装的 ${record.plugin_id} 在同一条点分路径上，不能安装`);
    }
  }
```

对一个签名包，`trust.level` 是 `pinned`，`trust.publisher_key_id` 就是 `confirm` 里的 `held.key_id`。所以 Host 这一侧要比的是：这一侧没卸载的记录里，有没有一条 ID 与包的 ID 不同、互为点分路径上下级、并且不是“同一个固定 key 的签名包”。同一个固定 key 的才许嵌套；宿主自己的记录（`publisher_trust` 是 `host`）、未签名的记录都不许。T-155 的 `assertNotHostId` 里内联了同一个 `nested`（`:75`），那是 local-host 里的一份，本单不再复制一份，抽出来共用。

**缺口二：项目里同一发布者的包不是升级（`MISC:23`）。** 生命周期的规则（`installed-plugin-lifecycle.ts:137-139`，原样）：

```ts
    const next = release.packaged.manifest;
    if (comparePluginVersions(next.version, record.version) <= 0) throw pluginErrors.upgrade_required('这个包的版本是 ' + next.version + '，不高于已装的 ' + record.version + '：不是升级');
    if (!(next.upgrade_compatibility?.compatible_from_versions ?? []).includes(record.version)) throw pluginErrors.upgrade_required('这个包的清单没有声明能从已装的 ' + record.version + ' 直接升级（upgrade_compatibility.compatible_from_versions）');
```

- 在这两行之前，`upgradePackage`（`:129-136`）还有几道：未固定/非签名记录 `definition_conflict`、发布者被撤销 `publisher_revoked`、被隔离 `Error`、找不到已装的包 `Error`、找不到批准记录 `Error`。这些本单不动，仍在生命周期里。
- 这条规则只认 `compatible_from_versions`。Runtime 另有一处升级判断（`packages/plugin-runtime/src/index.ts:305-311`）还认 `migratable_from_versions`，签名的沙箱包带不出它，本单不管。

**包目录为什么留着。** `SandboxPackageStore.save` 按 `[pluginId, 公钥指纹, 版本]` 的哈希建目录。同一份包再存是空操作；同一版本、内容不同会抛 `plugin.package_invalid`。没有删除的接口。所以拒绝发生在 `save` 之后，盘上就多一个目录；同一版本内容相同的包重复装，则看不出盘上多了东西，这也是 `BL623-02` 量不出来的原因。

## 2. 目标

- 另一个发布者的包，ID 与这一侧（项目或 Home）已装的某个插件在同一条点分路径上：确认时就以 `plugin.id_namespace_conflict` 拒，先于固定发布者、先于保存包。同一个固定发布者的包照样可以嵌套。
- 项目里，同一发布者的包与已装的同一个插件，不是升级（版本不高于已装的，或清单没有声明能从已装版本升）：确认时就以 `plugin.upgrade_required` 拒，先于固定发布者、先于保存包。是升级的照常装。
- 规则各只有一份：
  - 点分路径的 `nested` 在 `plugin-install-service.ts` 里只写一次，预览的宿主 ID 检查和确认的新检查共用；
  - 升级判断搬进新文件 `package-upgrade.ts` 的 `assertUpgradeOf`，确认和生命周期共用，错误码和文字一字不变。
- 六个用例证明上面几条，每个都配了变异（第 6 节）。
- S-84 行写上这两个拒绝，点名新用例。
