## 1. 背景

B 做过 T-049：作者 jing xu，#1373，提交 `3b1efc018`。本单接着它，改同一个函数，用同一个测试文件。

- 现状：`removeManagedConnectorTool`（`:77-91`）依次做这些：
  1. `:78`：校验 id 的形状，不对就抛 `invalid`；
  2. `:79-81`：安装被连接引用，返回 `"in-use"`；
  3. `:83`：目录不在，返回 `"absent"`；
  4. `:84`：目录是链接或真实路径变了，抛 `invalid`；
  5. `:85-86`：记录不在，抛 `invalid`（T-049 加的）；
  6. `:87`：`const owner: unknown = JSON.parse(readFileSync(record, "utf8"));`；
  7. `:88`：记录里的 id 对不上，抛 `invalid`；
  8. `:89`：`rmSync` 整个目录，`:90` 返回 `"removed"`。

  `:87` 抛错时，后面的核对和删除都走不到，所以已经是「什么都不删」，只是码不对。
- `:87` 抛原生错误的三种情形：

  | 情形 | 抛什么 | 本单 |
  | --- | --- | --- |
  | 记录不是合法 JSON | `SyntaxError`，没有 `code` | 收，`RAC-1640` |
  | `installation.json` 是目录 | `EISDIR`，`code` 是 `"EISDIR"` | 收，`RAC-1641` |
  | 没有读权限 | `EACCES` | 由同一个 `catch` 收下，不写用例：CI 有时以 root 跑，`chmod` 拦不住 root 读，用例会不稳 |

- 什么时候会碰上：
  - 安装成功时，`:71` 重写记录（`writeFileSync` 先截断再写）。进程在这中间被杀，记录就是空的或半截的。安装失败时 `:73` 的 `catch` 删整个目录，但进程被杀时走不到它。
  - 也可能是有人手工改坏了记录，或者备份只恢复了一半。`docs/system/HOME-DATA.md:260` 写明，这些记录要和连接库一起备份。
- 出口，和 T-049 是同一条路：
  - 内核记下失败时，原生错误有 `code` 就照记（`packages/kernel/src/action-settlement.ts:93-95`）；
  - MCP、HTTP 出口经 `action-gateway-http.ts:20-23` 走 `actionErrorResponse`（`apps/local-host/README.md:202`）。不是模型码的失败落到 kind `internal`、HTTP 500、码 `actions.execution_failed`（`packages/plugin-sdk/src/errors.ts:14`、`:62-67`、`:81`、`:86`）。
- 调用者（起草时用 `git grep -n removeManagedConnectorTool -- apps packages plugins tests` 查过）：`removeManagedConnectorTool` 有两处生产调用，导出在 `apps/local-host/src/index.ts:107`。

  | 调用者 | 怎么到 | 现在 | 改后 |
  | --- | --- | --- | --- |

## 2. 目标

1. 记录不是合法 JSON：经 `connectors.local.cleanup@1` 移除时，拒绝的码是 `connector.install.invalid`、kind 是 `invalid`，文案是「安装所有权记录无法读取，未移除任何文件」。目录里别的文件和这份记录都原样留着（`RAC-1640`）。
2. `installation.json` 是目录：同样的码、kind 和文案，目录里的东西都原样留着（`RAC-1641`）。

## 5. 做法

统筹已定的决定，照做，不另选（【方案】里不用再问这几条）：

1. **码用 `toolInstallErrors.invalid`**：和 `:84`、`:86`、`:88` 同一类，都是「这个目录不是我们认得出来的安装」。不用 `failed`（kind `unavailable`，503）：读不出来不是暂时不可用，重试也不会好。
2. **函数改成这样**，原样照抄（缩进两格；和 main 的不同只在 `:87`，原来的一行换成新的 `:87-89` 三行，后面的行号顺延两行）：

```ts
/** Only our unreferenced installation directory is removable. Working data and shared runtimes live elsewhere. */
export function removeManagedConnectorTool(home: string, id: string): "in-use" | "absent" | "removed" {
  if (!/^[0-9a-f]{8}-[0-9a-f-]{27}$/u.test(id)) throw toolInstallErrors.invalid("受管理安装标识无效");
  const referenced = withConnectorConnections(home, store => store.list()).some(row =>
    withConnectorProtocols(home, store => store.get<LocalMcpConfiguration>(row.connection_id))?.installation_id === id);
  if (referenced) return "in-use";
  const directory = join(realpathSync(home), "runtime", "connectors", "installs", id);
  if (!existsSync(directory)) return "absent";
  if (lstatSync(directory).isSymbolicLink() || realpathSync(directory) !== directory) throw toolInstallErrors.invalid("受管理安装目录已改变，未移除任何文件");
  const record = join(directory, "installation.json");
  if (!existsSync(record)) throw toolInstallErrors.invalid("安装所有权记录缺失，未移除任何文件");
  let owner: unknown;
  try { owner = JSON.parse(readFileSync(record, "utf8")); }
  catch { throw toolInstallErrors.invalid("安装所有权记录无法读取，未移除任何文件"); }
  if (!owner || typeof owner !== "object" || !("id" in owner) || owner.id !== id) throw toolInstallErrors.invalid("安装所有权记录不符，未移除任何文件");
  rmSync(directory, { recursive: true, force: true });
  return "removed";
}
```

4. 几处为什么这样写，别改：
   - 源码照同一个文件 `:64-66` 的 `let …; try { … } catch { throw toolInstallErrors.… }`。`apps/local-host/src/installer/runtime-config-backups.ts:71-72` 是同一种写法：`let parsed: unknown;`，`try` 里 `JSON.parse`，`catch` 抛声明错误，下一行用 `!parsed || typeof parsed !== "object"` 收窄。
   - `try` 同时包住读和解析：`RAC-1640` 量的是解析，`RAC-1641` 量的是读。第 6 节的 M3、M4 各拆掉一半，各红一条。
   - 文案和 `:86` 的「安装所有权记录缺失，未移除任何文件」、`:88` 的「安装所有权记录不符，未移除任何文件」并列，不带路径，也不带原生消息。
   - 用例的搭法照抄 `RAC-1494`（`:90-104`）：
     - 经 `home.host.homeActionClient().invoke(caller, connectorLocalActions.cleanup, …)` 调，量的是真实分派以后的码、kind 和文案；
     - id 是固定的小写 uuid，形状过得了 `:78` 的正则；两条各用一个，与 `RAC-1494` 的 `0e3b1d6a-…` 也不同；
     - 每条各开一个 Home。
   - 断言的顺序别调：先查 `keep.txt` 还在，再查记录。M2（`catch` 里先删再抛）红在 `keep.txt` 那一句的断言消息上。要是先 `readFileSync` 一个已经删掉的记录，红的是 `ENOENT`，不是断言。
   - `"{\"id\":"` 写出来是 `{"id":`，是截断的 JSON。`JSON.parse` 一定抛 `SyntaxError`。
   - 两个用例只用文件里已有的 `assert`、`test`、`existsSync`、`mkdirSync`、`readFileSync`、`writeFileSync`、`join`、`connectorLocalActions`、`openTestHome` 和 `:10` 的 `caller`，不加 `import`。
5. 代码里不要出现 `legacy`、`compat`、`backfill`，不加空 `catch`、`as unknown as`、`any`、`console`（这些按文件计数，只许减少）。
