# 分析与决策

从问题、证据和备选方案走到可追溯决定。

适用于：数据分析、市场判断、方案选择。

## 规划路径

1. 定义决策和成功标准
2. 确认数据与证据边界
3. 形成可比较选项
4. 记录决定、理由和复盘触发条件

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| decision_question | 决策问题 | 这次分析最终要支持哪个决定？ |
| evidence_base | 证据基础 | 数据和证据的来源、质量与限制是什么？ |
| alternatives | 备选方案 | 有哪些真正不同的选项和取舍？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| evidence-after-question | 证据收集依赖明确的决策问题和口径，避免无目的堆资料。 | evidence plan depends_on decision question |
| decision-after-evidence | 决定消费分析证据，分析不依赖预设结论。 | decision depends_on evidence |

## 完成证据

- 来源和口径
- 关键假设
- 反证或敏感性检查

## 收口检查

- 结论能追溯到证据
- 限制和不确定性可见

## 常见误拆

- 先有结论再找数据
- 堆资料但不形成选项
- 把相关性写成因果

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
