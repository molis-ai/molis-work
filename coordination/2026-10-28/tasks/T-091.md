# T-091 定时对话任务的标题与说明按 Unicode 字数数上限，与动作说明和报错一致

> **这条在 main 上成立：定时（Schedule）的对话任务说「80 字」「8000 字」，数的却是 UTF-16 单元。**
> - 动作说明（`plugins/native/schedule/src/actions.ts:34` 的 `fields`）：标题「1 到 80 字」，说明「Agent 到点要做的说明，最多 8000 字」。`schedule.tasks.create@1`（`:57-59`）和 `schedule.tasks.update@1`（`:60-62`）都用它。
> - schema 有意放得比这宽：标题 `maxLength: 200`、说明 `maxLength: 16000`。`:33` 的注释写明，空白和超长交给任务的主人去判、由它说清哪里不对。
> - 动作层用 Ajv 校验，Ajv 的 `maxLength` 按 Unicode 字符（码点）数：`packages/kernel/src/action-schema.ts:41-42` 的选项里没有 `unicode: false`。所以 81 个字的标题、8001 个字的说明都能过 schema，到主人那里才拒，这是有意的。
>
> 主人那两处却按 `string.length` 数：`plugins/native/schedule/src/tasks.ts:287`（标题）和 `:295`（说明）。一个 emoji 或扩展 B 区以后的生僻字在 JS 字符串里占 2 个单元。所以：
> - 41～80 个这样的字的标题，被拒为「请填写 1 到 80 字的标题」；
> - 4001～8000 个这样的字的说明，被拒为「请填写 Agent 到点要做的说明」。
>
> 起草时只读了代码，没有跑；第 5 节的先红就是复现。这是 T-077（Dataset）、T-079（PPT）、T-080（灵光）、T-083（Pages）、T-086（问卷）、T-090（待办）的同类问题，出在另一个插件。
>
> **不依赖别的任务，也不撞锁。**
> - 看板（协调分支 `28597504b`）没有任务锁 `plugins/native/schedule/**` 或 `tests/schedule-conversation-tasks.test.ts`。

## 1. 背景

- 合同口径（都按 Unicode 字符）：
  - `plugins/native/schedule/src/actions.ts`：
    - `:33`：注释，空白和超长交给任务的主人判；
    - `:34`：`fields`，`title` 说明「1 到 80 字」、`maxLength: 200`，`instructions` 说明「最多 8000 字」、`maxLength: 16000`；
    - `:57-59`：`schedule.tasks.create@1`，`:60-62`：`schedule.tasks.update@1`，都用 `fields`；
    - `:118`：处理器把输入整理成 `editable`；`:125`、`:126`：两个动作的处理器调端口的 `createTask`、`updateTask`。
  - Ajv：`packages/kernel/src/action-schema.ts:41-42` 的选项、`:79` 的 `new Ajv(options)`。没有 `unicode: false`，`maxLength` 走 Ajv 的 `ucs2length`，按码点数。
  - 端口：`plugins/native/schedule/src/service.ts:69-74` 的 `createTask`、`:75-84` 的 `updateTask`（后者在一个事务里改任务、重新排期）。
- 按 UTF-16 数的两处：

  | 位置 | 现在的写法 | 谁会走到 |
  | --- | --- | --- |
  | `tasks.ts:287`（`normalizeTitle`，`:285-291`） | `if (!trimmed \|\| trimmed.length > 80) {`，下一行抛 `scheduleErrors.task_invalid("请填写 1 到 80 字的标题")` | `createScheduleConversationTask`（`:104-135`，在 `:115` 调它）、`updateScheduleConversationTask`（`:162-177`，在 `:170` 调它）。会走到它们的有：`schedule.tasks.create@1`、`schedule.tasks.update@1`（页面经 `route-handlers.ts:19-20` 读表单，再调这两个动作），以及 Agent、工作流、MCP |

  - `git grep -n -e "请填写 1 到 80" -e "请填写 Agent 到点" -- tests` 没有命中；

## 2. 目标

1. 80 个非 BMP 字符（如 `🟢`）的标题经新建能收下，任务和它的闹钟都是这个标题；81 个仍以 `schedule.task_invalid`「请填写 1 到 80 字的标题」拒，新建、修改都一样，被拒时什么也不写（`RAC-1660`）。
2. 8000 个这样的字的说明经新建能收下，任务的说明和对话的第一条都是它；8001 个仍以 `schedule.task_invalid`「请填写 Agent 到点要做的说明」拒，新建、修改都一样，被拒时什么也不写（`RAC-1661`）。

上限本身不变。

```ts
test("RAC-1660 a conversation task's title is counted in Unicode characters up to 80: 80 🟢 become the task's and its alarm's title; 81 are refused on create and update", () => {
  // fields.title in src/actions.ts promises 1 to 80 characters; one 🟢 is one character but two UTF-16 units.
  const db = scheduleDatabase();
  const installation = wakeupInstallation(SCHEDULE_PLUGIN_ID);
  installation.action(SCHEDULE_TASK_WAKEUP_CAPABILITY, async () => undefined);
  const now = () => new Date("2026-09-20T00:50:00.000Z");
  const schedule = installation.scheduler(db, { now });
  const ports = createScheduleActionPorts({ db, schedule, now });
  const wide = (count: number) => "🟢".repeat(count);
  try {
    const task = ports.createTask({ title: wide(80), instructions: "读说明", hour: 9, minute: 0, notify_important: true });
    assert.equal(task.title, wide(80), "create keeps an 80-character title");
    assert.ok(task.job_id);
    assert.equal(schedule.get(task.job_id)?.title, wide(80), "the task's alarm carries the same title");
    assert.throws(() => ports.createTask({ title: wide(81), instructions: "读说明", hour: 9, minute: 0, notify_important: true }),
      { code: "schedule.task_invalid", message: "请填写 1 到 80 字的标题" }, "81 characters is still past the limit");
    assert.throws(() => ports.updateTask(task.task_id, { title: wide(81), instructions: "读说明", hour: 9, minute: 0, notify_important: true }),
      { code: "schedule.task_invalid", message: "请填写 1 到 80 字的标题" }, "update is held to the same limit");
    assert.deepEqual(ports.listTasks().map(row => row.title), [wide(80)], "neither refusal wrote anything");
  } finally { db.close(); }
});

test("RAC-1661 a conversation task's instructions are counted in Unicode characters up to 8000: 8000 🟢 become the instructions and the first turn; 8001 are refused on create and update", () => {
  // fields.instructions in src/actions.ts promises at most 8000 characters.
  const db = scheduleDatabase();
  const installation = wakeupInstallation(SCHEDULE_PLUGIN_ID);
  installation.action(SCHEDULE_TASK_WAKEUP_CAPABILITY, async () => undefined);
  const now = () => new Date("2026-09-20T00:50:00.000Z");
  const schedule = installation.scheduler(db, { now });
  const ports = createScheduleActionPorts({ db, schedule, now });
  const wide = (count: number) => "🟢".repeat(count);
  try {
    const task = ports.createTask({ title: "长说明", instructions: wide(8_000), hour: 9, minute: 0, notify_important: true });
    assert.equal(task.instructions, wide(8_000), "create keeps 8000 characters of instructions");
    assert.deepEqual(getScheduleConversationTask(db, task.task_id)?.turns.map(turn => [turn.kind, turn.text]), [["user", wide(8_000)]], "the instructions open the conversation");
    assert.throws(() => ports.createTask({ title: "说明太长", instructions: wide(8_001), hour: 9, minute: 0, notify_important: true }),
      { code: "schedule.task_invalid", message: "请填写 Agent 到点要做的说明" }, "8001 characters is still past the limit");
    assert.throws(() => ports.updateTask(task.task_id, { title: "长说明", instructions: wide(8_001), hour: 9, minute: 0, notify_important: true }),
      { code: "schedule.task_invalid", message: "请填写 Agent 到点要做的说明" }, "update is held to the same limit");
    assert.equal(getScheduleConversationTask(db, task.task_id)?.instructions, wide(8_000), "the refused update changed nothing");
  } finally { db.close(); }
});
```

3. 几处为什么这样写，别改：
   - 用 `🟢`（U+1F7E2）：一个码点、两个 UTF-16 单元，没有变体选择符。T-077、T-079、T-080、T-090 和 `tests/content-owner-regressions.test.ts:58` 用的也是它。
   - 值正好压在上限上（80、8000），多一个（81、8001）就拒，才分得清按字数和按单元。不要缩短。
   - 直接调端口，不经动作服务。schema 按码点放行到 200 和 16000，81 和 8001 都能过；经动作服务调，拒绝也只能来自 `tasks.ts`。所以直接调端口测的是同一件事，还省掉起宿主。端口就是动作处理器调的那一份（`actions.ts:125-126`）。
   - 准备部分照 `:327-333`：闹钟登记进真实的 Scheduler 服务，它按单元限标题 200（第 1 节）。断言 `schedule.get(task.job_id)?.title` 就证明了 80 个 `🟢` 的标题闹钟也收下。
   - `assert.ok(task.job_id)`：视图继承记录的 `job_id: string | null`（`tasks.ts:39`、`:47`），先断言有，下一句才能用它。
   - `RAC-1661` 看第一条对话：新建时说明同时写成第一条 `user` 回合（`tasks.ts:129-132`）。
   - 81、8001 新建和修改都试一次：两条路各调一次同一个函数（`tasks.ts:115-116`、`:170-171`）。修改在端口的事务里（`service.ts:76-82`），被拒时不写。最后一句断言库里还是原样。
   - `assert.throws` 的第二个参数比对 `code` 和 `message`：抛的是 `scheduleErrors.task_invalid`（`src/error.ts:9-16`）造的 `ActionError`。`defineErrorCodes`（`packages/contracts/src/platform/action-errors.ts:109-115`）给的码是 `schedule.task_invalid`，文案原样。
