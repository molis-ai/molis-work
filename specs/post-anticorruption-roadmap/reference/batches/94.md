## 进展（2026-11-19）

本批由一个主会话做完（决定 34），分支 `batch/94`，子分支 `batch/94-1-same-version-install`。

**复现（修前，main `3a6f2289a0`）。** 在临时的 Applications 目录（`MOLIS_WORK_APP_DIR`）与隔离 Home（`open --env MOLIS_WORK_HOME=…`）里，用现有入口 `apps/desktop/tooling/install-macos-app.sh` 装 A（构建 `07:42:18.353Z`）、打开、退出，再装同版本 0.1.0 的 B（构建 `07:49:40.943Z`）打开：`installation.json` 没动，Home 里仍是 A 的程序，新起的宿主进程也跑在 A 上。所以旧的不是 App，是 **Home 里的程序**：桌面 `embedded_version_is_upgrade` 只比版本，同版本一律不装。

**修法。** `apps/desktop/adapters/tauri/src/web_service.rs`：同版本时再比两边构建指纹 `dist/.molis-work-build.json` 的 `created_at`（App 里的 payload 与 Home 当前程序各一份，安装器原样复制），只有 App 的构建更晚才装；回退保留照旧先判，版本不同照旧比版本；读不到构建时间就不算更新（与原来同版本不装一致）。`installation.json` 的 `release_path` 只认 Home 内的普通相对路径。文档：`docs/installation.md`、`docs/installation.en.md` 写明这条规则，回退设计 §1 表格对应一行补注。

**验收与证据（DSV-01～05，修后的 App C 构建 `11:43:02.597Z`；原始输出在主会话草稿目录 `evidence/`）：**

工程：`cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml` 125/125（新增 `dsv_*` 三个、改写 `upgr05_*` 与 `only_missing_or_newer_*`）；`node scripts/affected-tests.mjs` 选出的 12 个文件（含 `desktop-shell-bootstrap`、`desktop-tui`、`action-mcp-stdio`、`install`、`runtime-payload`）`--jobs 1` 共 181/181；`check-health-gates --base origin/main` 与 `boundary:check` 通过。实操：上表五项在隔离 Home 与临时安装位置走完，没动日常 Home。本人验收：不涉及界面，不列「待你验收」；需要时照上表在开发机重装一次同版本 App 即可看到。

**偏离与说明：**

- 开发档打包随包官方包要本机开发发布者密钥（`MOLIS_WORK_DEV_PUBLISHER_KEY_FILE`，26-9），这台机器没有配置。为了这次隔离验证，在主会话草稿目录里临时生成了一把一次性测试密钥（与测试用例同法），只签这三个本地验证包，不入库、不当作开发密钥；正式密钥仍归 26-9／REL。
- 原需求只有一句验收，本批拆成 DSV-01～05 逐条举证；DSV-05（旧构建不盖新构建）是为了守住改动前代码注释里「旧 App 不覆盖同版本本地构建」的原意而加的。
- 版本号没有改：DSV-04 的 0.1.1 只是在隔离 Home 里用安装器的 `--version` 参数装的，不进仓库、不出包。

### 94-1 开工前检查（需求开发流程第 4 节）

| # | 回答 |
| --- | --- |
| 1 事实主人 | 「Home 装的是哪个程序」归安装器（`apps/local-host/src/installer`，`config/installation.json`）；「这个构建什么时候编出来」归构建指纹（`dist/.molis-work-build.json`，`format.build.manifest` 1）。桌面只读这两份，不另记一份事实。 |
| 2 插件同等待遇 | 不涉及：只改桌面外壳启动时要不要调用安装器，不碰插件。 |
| 3 能力注册 | 不涉及：没有新动作。 |
| 4 合同 | 不改。两份文件的格式与版本都不变，桌面只是多读已有字段（`installation.json` 的 `release_path`、构建指纹的 `created_at`）。 |
| 5 放在哪个包 | `apps/desktop/adapters/tauri/src/web_service.rs`，原来的判断就在这里。 |
| 6 表与存储 | 不涉及：不建表、不写新文件。 |
| 7 兼容与迁移 | 不加。读不到构建时间（文件缺失、版本不是 1、时间格式不对）就按「不是更新」处理，与原来同版本不装一致，不兜底历史取值。 |
| 8 安全边界 | 读 Home 里的 `release_path` 只认 Home 内的普通相对路径（不许绝对路径和 `..`），与回退设计 §5.1 读 `release_path` 的规矩一致；不新增可写面，不碰 S 表。 |
| 9 调用次数 | 每次启动多读两个小 JSON（App 里的构建指纹、Home 当前程序的构建指纹），不算摘要、不起进程；只有真要换时才像原来一样跑一次安装器。 |
| 10 升级与数据 | 换同版本构建走的是安装器原有的同版本刷新：上一份程序按 U3 §5.1 留作回退点，项目数据不参与替换，升级链照常随启动跑。 |
| 11 成果与过程项 | 不涉及。 |
| 12 页面、外壳与文字 | 不涉及：没有界面和新文案，用现有安装与启动入口。 |
| 13 错误 | 不涉及：没有新错误。 |
| 14 冲突面 | 只改 `web_service.rs` 与文档；#1818（签名）改打包脚本与签名，不碰这段启动判断。 |
| 15 全局最优 | 比过三种做法。①每次启动都跑安装器、由它比内容摘要：要起 Node、把整个程序算一遍摘要，每次打开多花几秒，否掉。②桌面复算安装器的内容摘要：两处各写一份摘要规则，签名重签后还会对不上，否掉。③比构建指纹里的构建时间（选用）：安装器原样把它带进 Home，读两个小文件就够，且只让「更晚的构建」生效，旧 App 不会盖掉之后 `pnpm install:local` 装的新构建。插件、助理、各类平台能力：不涉及，这是桌面外壳启动内置程序的判断，只有桌面一个使用者。后续开发：第 26 批更新器、#1818 签名都沿用同一个判断；正式发版换版本号时走原来的版本比较，不受影响。 |

平台能力检查（第 4.1 节）：只有桌面外壳一个使用者，平台里也没有现成的「比较两个本机构建」的能力；结论「暂不收」，事实仍放在安装器和构建指纹两个主人那里。
