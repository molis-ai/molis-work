# Coding 质量保证：自检、交叉评审、对抗评审

状态：已定方向，待实现（2026-10-05；2026-10-18 补充多代理 PR 评审、安全评审与真人批准门方案）。2026-10-28 对齐授权复用与显式人审，防腐收尾后作为独立任务做。

## 为什么

Goal 规则里原有「自检、交叉评审人数、对抗评审人数」三项，是旧「领取」流程的设置；事件流程里没有任何地方读取它们，设置了也不生效。用户指出这些本该是 Coding 的质量保证：Coding 有角色、委派、子任务，也能关联 Goal，由它来执行最合适。防腐目标已从 Goal 规则里删掉这几项（不搬运不生效的设置），本 spec 记录在 Coding 里重建它们的方向。

## 要做到

- 自检：一轮写作完成后，由写作的角色按关联 Goal 的要求核对自己的改动，结论写进这一轮的报告。
- 交叉评审：另外 N 个角色读同一组改动，各自给出通过、要改或说不清，意见回到会话里。
- 对抗评审：N 个角色专门找漏洞（边界、回归、越权、数据丢失），找到的问题作为待处理项。
- 结果写回关联 Goal：评审结论作为 Goal 的工作事件（进展或顾虑）记录，收尾时可被引用；不另建 Goal 状态。
- 设置放在 Coding：按项目默认、可按会话或计划覆盖；关联 Goal 时可以带上 Goal 的「需要用户验收」作为最后一步。

## 2026-10-18 补充：把评审做成一条可执行的工作流

对照 Anthropic 的 `code-review`、`pr-review-toolkit`、`claude-security`、`agent-approval-check` 与 `math-proof`，补上原方向里没有说清的四件事：**谁评、评什么、怎样算可信、什么时候必须人点头。**

### 1. 评审资格与范围

评审开始前先判断：PR 是否已关闭/草稿/明显不需要评审/已经评审过；本次评审的范围是改动行、整个 diff，还是指定路径。读根目录与修改目录的 `AGENTS.md`/项目规则；没有规则时说明“按通用标准评审”，不假装有项目标准。

### 2. 多代理评审

默认 5 个并行评审，各自独立：

1. 项目规范：改动是否违反 `AGENTS.md`/项目规则。
2. 明显 bug：只看改动本身，避免读太多上下文导致误报。
3. 历史：`git blame`/相关提交，找“过去为什么这样写”。
4. 旧 PR：以前改过这些文件的 PR 评论是否仍适用。
5. 代码注释：改动是否违反文件里的说明。

每个评审只报有依据的问题，带文件、行、触发条件、影响和最小修正方向；不报纯风格、构建/类型错误、预存问题、未改动行。评审意见先进 review 卡，不直接改代码。

### 3. 置信分与过滤

每个候选问题再由一个独立 agent 打 0–100 分：0–25 基本是误报/预存问题，26–50 小 nit，51–75 真实但不重要，76–90 重要，91–100 关键 bug 或明确规则违反。**只保留 ≥80 的问题**；没有就明确说“没有高置信问题”，不凑数。

### 4. 专科评审（可选面板）

在通用 5 个之外，按需增加：静默失败（空 catch、只返回默认值、假的 fallback）、测试（覆盖是否真的验证行为）、类型设计（类型是否表达不变量）、注释（注释与代码是否一致）、简化（只改表达、不改行为）。专科评审默认关闭，用户按项目/会话开启。

### 5. 评论产线化

- 未确认的 inline comment 先缓冲，结束后分类“真评审/测试探测”，防止子代理的测试评论发到 PR。
- 每条意见带“去修复”入口，点开带着文件、行、意见进入新一轮。
- 长评审用一条进度评论持续更新，不发多条。
- 评审只对改动行给意见；需要改未改动行时说明理由，不直接改。

### 6. 安全评审

安全评审单独一条工作流：扫描当前 diff/指定范围 → 候选 finding → 独立 verifier 挑战（复现、数据流、可达性）→ 只把确认的写进待处理项 → 生成 patch 文件，用户在审查队列里决定是否应用。**不自动应用、不 commit、不 push。** 安全评审不替代通用评审；通用评审发现的安全问题仍按原流程处理。

### 7. 真人批准门

有效授权内的工作持续执行；只有明确启用人审的项目／操作才要求规定数量的有权限真人批准。版本绑定、人员资格、撤权与恢复见 [agent-approval](../agent-approval/spec.md)。Coding 推送／合并按相应授权、人审和检查执行；可选低风险 AI 审批按 B2 的委托与 Host 判断执行，不计真人票数。质量评审通过本身不产生执行权限，执行 Agent 自述也不算批准。

### 8. 有界迭代

对“修到测试全绿”这类目标，可以用 Stop 事件做有界迭代：明确完成承诺、最大轮数、可取消；每轮仍走正常工具/审查；不取代正常一轮的停止判断，也不允许无界循环。

### 9. 对抗验证

高风险评审可以采用 judge + fresh workers + ledger + 两个 verifier 逐行核对的协议：judge 写问题、独立 worker 回答、ledger 记已证明/已反驳/未决，完整证明由两个新的 verifier 逐行检查后才算通过。它比“再找一个 agent 看一眼”更硬，但成本高，只用于高风险/高价值评审。

## 待定

- 评审角色从哪里来：现有角色库、按需生成，还是用户指定。
- 评审触发点：每轮结束、计划步骤结束，还是提交前。
- 评审不通过时：阻止提交、只提醒，还是开新一轮修改。
- 用量与费用：评审轮次计入哪个用量表、怎样让用户事先看到。
- 评审结果是否写回 Goal：现有方向是写工作事件；多代理评审的逐条意见是否也写，待定。
- 安全评审的 verifier 数量、patch 生成是否默认开。
- 真人批准门的 N 默认值、哪些团队场景启用。

## 不做

- 不在 Goal 规则里恢复这些字段；Goal 规则只保留「需要用户验收」。
- 不让执行 Agent 自审取得权限、冒充真人批准或把失败说成通过；具备授权、所需批准与检查后，可执行已委托的合并。
- 不为变绿放宽阈值；不把纯风格/构建错误/预存问题塞进评审。
- 不做无界迭代；不做没有证据的“安全已通过”。

## 验收标准

| 编号 | 用户可观察结果 |
| --- | --- |
| CQA-01 | 评审开始前能判断 PR 是否值得评审、范围是什么；不值得时明确跳过，不产生空评审 |
| CQA-02 | 通用评审覆盖规范、明显 bug、历史、旧 PR、注释五类，各自独立；意见带文件、行、依据与最小修正方向 |
| CQA-03 | 每个问题有独立置信分；低于 80 的被过滤；没有高置信问题时如实说没有，不凑数 |
| CQA-04 | 只对改动行给意见；纯风格、构建/类型错误、预存问题、未改动行不报 |
| CQA-05 | 专科评审可按项目/会话开启；静默失败、测试、类型、注释、简化各自有明确检查项 |
| CQA-06 | 未确认评论先缓冲并分类；子代理测试评论不进入 PR；每条意见能带着上下文进入修复 |
| CQA-07 | 长评审用一条进度评论更新；评审结束后状态、结论与未验证项清楚 |
| CQA-08 | 安全评审的每个 finding 经过独立 verifier 挑战；只出 patch，不自动应用、不 commit、不 push |
| CQA-09 | 明确启用人审的 PR／变更未达到所需真人票数不能合并／生效，push 后旧版本批准过期；其他工作复用有效授权；AI 低风险代批不计真人票数 |
| CQA-10 | 有界迭代有完成承诺、最大轮数、取消；达到上限或取消后不再执行 |
| CQA-11 | 对抗验证的 ledger 区分已证明/已反驳/未决；完整证明由独立 verifier 逐行核对后才算通过 |
| CQA-12 | `[人工]` 在一个真实 PR 上完成通用评审 + 一次安全评审，种子 bug 被抓到、已知误报被过滤、批准门前后的合并行为正确 |
