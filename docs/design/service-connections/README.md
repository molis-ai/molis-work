## 三块各定什么

### ① 直接连接：设置里的「连接」页长什么样

三个方案的连接过程一样：**点连接 → 在浏览器登录并同意（或只填一把密钥）→ 自动检查能做什么 → 显示「这个账号现在能做什么」**。只差在页面怎么排、过程显示在哪：

| 方案 | 排法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A 按用途分组，就地展开 | 一列，按用途分组（模型、代码与项目、邮件与日程、文档与笔记、消息）；点一行就地展开，连接过程和结果都在这一行里 | 不跳页，窄屏也是同一套；扫一眼就知道每个服务的状态 | 服务多时要往下翻（靠搜索和分组兜住）；展开的行把下面的推开 |
| B 左边列表，右边详情 | 左边是分组的紧凑列表，右边是选中服务的详情 | 宽屏信息最全，切服务快；和其他设置页一样 | 窄屏要多一层「返回列表」；右边详情常常空着一半 |
| C 服务卡片，连接时弹出 | 现在产品里的卡片格子（`settings-connector-card`），按用途分组；连接时弹出组件板的表单对话框（`mw-dialog--form`），过程在里面走完，「存在哪里」收在折叠里 | 第一次进来最好认；对话框把这一次连接和别的隔开 | 多一层弹窗；看已连接服务的详情也要弹窗 |

每个方案里都有：

- **默认只问必要的**：登录类服务一个字段都不填；只要密钥的服务（模型、图像模型）只问一把密钥，写清去哪里拿、只存在钥匙串。
- **连上以后看得见**：账号、连得上吗（含检查时间）、允许做什么（用「能读通知、看仓库」这种话，不写权限原值）、谁在用它。这四行对应需求 §5 的「配置、连接、授权、能力」四个维度。
- **还不能一键连的如实说**：Gmail（Google 还在审核应用）、飞书（要企业管理员批准）写明原因和能走的路，不摆一个点了没用的「连接」（ASC-47）。

### ② 高级配置：自己的应用、地址、权限原值和诊断放哪里

两个例子：GitHub 用自己注册的应用；MiniMax 改地址、接口格式、模型名或换密钥。

| 方案 | 放法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A 详情底部收起的「高级」 | 服务详情最下面一行「高级」，点开才看到 | 默认最干净；和现在产品里的「高级」折叠一致 | 内容多时这一段很长 |
| B 详情里的「高级」页签 | 详情分「概览」「高级」两个页签 | 高级内容有整页地方，不挤概览 | 多一个页签，普通用户也会看到它 |
| C 单独的「自定义连接」 | 列表下方一个「＋ 自定义连接」，先选种类（自己的登录应用、远程工具地址、模型地址、只要密钥的服务）再填；服务详情里只留一个链接 | 高级的东西集中一处，普通页面完全没有技术字段 | 改某个服务的高级设置要先离开这个服务 |

三个方案共同的规矩：**保存前先检查，检查不过不保存，原来的连接一直照常在用**；没保存的改动留成草稿，回来能接着改，也能放弃。

### ③ 连好回到原处：从别的地方发现缺连接时怎么走

四个来处：助理（看今天的 GitHub 通知）、Feed（加 GitHub 通知来源）、Coding（推送要多一项权限）、Images（生成封面要图像模型的密钥）。底栏输入框里都有一句用户已经写好的话，连完要还在。

| 方案 | 走法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A 在原处就地连 | 缺连接的地方出一张卡，连接过程就在卡里走完，卡收成一行「已连上」，原来的事接着做 | 完全不离开原处；最轻 | 卡里地方小，换账号这类要多解释的事挤 |
| B 去连接页，带一条「回去」 | 跳到设置的连接页，顶上一条「从哪里来 · 连好后自动回去 · 现在回去」；连好后自动回去，弹一句提示 | 连接页只有一个，各处共用；该看的详情都在 | 来回切页面；回去靠这条返回，各插件都要接 |
| C 盖在原处的侧板 | 组件板的侧板（`mw-sheet`）从右缘滑入盖在原处：上面走连接，下面一行「回去以后接着做」带你写的话和状态；连好后底部主按钮「回到原处接着做」 | 回去以后接着做什么一直看得见；原处还露在左边 | 一项连接也要盖一层，比 A 重 |

六种状态在三块里都能切：

| 状态 | 用户看到什么 | 依据 |
| --- | --- | --- |
| 取消登录 | 「没有连上，这里什么都没改」；原来失效的连接仍标「需重新授权」，在等的工作还在等；从别处来的回到原处，写的话还在 | §4.6.1、ASC-49 |
| 登录失效 | 状态改成「需重新授权」（现在产品里的词），写明从什么时候起、有几件工作在等；一键用原账号重新登录，回来接着做，不从头来 | §7、ASC-49、ASC-53 |
| 换账号 | 先问「换掉」还是「再加一个」，列出会跟着换的地方，正在做的那件先停下；从别处来时只在「两个账号能看到的东西不一样」时问用哪个 | §3.1、§8.1、ASC-49、ASC-52 |
| 服务限流 | 写明是服务那边在限流、不是你的问题；倒计时后自动再查（原型里把约 1 分钟缩成 8 秒），可以不等；密钥类服务「存好了但没验证，验证前不拿它干活」 | §7、ASC-53、PF-A04 |
| 密钥被拒 | 字段下写「拒绝了这把密钥（401），可能过期或少复制了字符」；第一次连就「还没保存」，换密钥时「旧密钥照常在用」 | PF-A04、§7 |

## 推荐走一遍

1. 块 ①、方案 A：点 GitHub 那行的「连接 GitHub」，看浏览器登录 → 检查 → 结果；再点 MiniMax 填一把密钥。点 Gmail 看「还不能一键连接」。
2. 「状态」逐个切：取消登录、登录失效（点「用 yijunw0212 重新登录」）、换账号（点「换账号」）、服务限流、密钥被拒（在 MiniMax 上）。方案 B、C 再走一遍。
3. 块 ②：切 GitHub／MiniMax；方案 A 点开「高级」，选「我自己的 GitHub 应用」，点「保存并检查」；状态切到密钥被拒、取消（上次的草稿）、登录失效（自己应用的 Secret 过期）、换账号（哪件事用哪个账号）。
4. 块 ③：「从哪里来」逐个切，三个方案各点一次主按钮；回去后看底栏那句话是否还在、原来的事有没有接着做。

- 产品样式变了要重新生成：先 `pnpm build`，再在 `apps/workbench` 里跑 `node ../../docs/design/service-connections/tools/snap.mjs <临时目录> $(git rev-parse --short HEAD)`，回到仓库根目录跑 `node docs/design/service-connections/tools/prune.mjs <临时目录>/board.css docs/design/service-connections docs/design/service-connections/board.css`，把 `<临时目录>/board.js` 拷回来。`app.js` 用了新的类名后也要重跑 `prune.mjs`。

## 和第 12 批的假设

「回到原处」要靠第 12 批的草稿与返回能力。这份样张假设第 12 批会给出：**谁发起的（哪个会话、哪个插件位置、哪个设置页）、发起时的草稿、在等这项连接的那件工作**；连好后由平台把人带回去、把草稿还原、让那件工作只接着做一次。第 12 批定样（B 轨）若定下不同的返回形状，这里的方案 B、C 跟着改，方案 A 不依赖跳转、受影响最小。

## 占位与模拟边界

- 所有服务、账号、仓库、通知、能力和诊断都是示例数据（`data.js`），用定时器模拟浏览器登录、检查和限流。没有登录任何账号、没有保存任何密钥、没有调用模型，也没有连真实 Home。
- 「再打开一次登录页」「断开」「复制」「打开 GitHub 授权设置」只演示入口；左侧设置导航不跳转。
- 原型条的下拉用的是浏览器自带的列表（原型控制，不是产品界面）；产品界面里没有用系统下拉。
- 选了哪个块、方案、状态存在浏览器的 `localStorage`（`molis-proto.service-connections.v2`），不代表产品的持久化、授权或恢复已经做好。
- `window.protoJump` 只用于截图时直接跳到某个状态，不是产品接口。
- M1 的范围还没定（路线书[决定第 18 项](../../../specs/post-anticorruption-roadmap/reference/decisions.md)），其中包括哪几家服务；这里的服务名单只为演示各种情况，不代表范围。
