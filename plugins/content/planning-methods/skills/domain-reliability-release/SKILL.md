# 可靠性与发布

围绕服务目标、变更控制、可观测性和恢复能力建立持续交付闭环。

适用于：生产服务、发布流程、稳定性治理。

## 规划路径

1. 定义关键用户旅程、服务目标和可接受退化
2. 识别容量、依赖、状态和变更风险
3. 建立构建、发布、迁移、回滚和渐进放量路径
4. 补齐可观测性、告警、值守和事件响应
5. 用故障注入、恢复演练和真实运行数据改进

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| critical_journeys_slo | 关键旅程与目标 | 哪些用户结果必须可靠，成功、延迟和可用性怎样衡量？ |
| dependency_capacity | 依赖与容量 | 哪些外部依赖、资源上限和状态会导致级联失败？ |
| change_delivery | 变更交付 | 构建、配置、迁移、放量和回滚如何保持可控？ |
| observability_alerting | 可观测与告警 | 哪些信号能在用户受损前后定位真实问题？ |
| incident_response | 事件响应 | 谁决策、如何止损、沟通、恢复和复盘？ |
| continuity_recovery | 连续性与恢复 | 数据、服务和人工流程如何恢复到可信状态？ |

## 完成证据

- 关键旅程的服务目标与监控信号
- 可复现的发布、迁移和回滚记录
- 至少一次事件或恢复演练结果

## 收口检查

- 告警对应用户影响并有明确动作
- 回滚和恢复不依赖临场猜测
- 关键外部依赖和容量上限有降级策略

## 常见误拆

- 把部署成功当成发布完成
- 监控很多但无法判断用户是否受损
- 只写正常发布不验证回滚和数据恢复

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
