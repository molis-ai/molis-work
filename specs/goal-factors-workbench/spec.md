# Goal 关键因素工作台

## 背景与目标

Goal Detail 已按“概览 / 完成要求 / 进展与阻塞 / 完整记录”分区，但关系、风险、影响范围、工作规则和人工完成依据仍混在“完整记录”里。用户既难以理解这些事实为什么存在，也很难判断应在哪里新增或修改；审计记录与操作入口混放，还会让人误以为历史数据可以直接改写。

本任务把 Goal 的日常理解、快速记录、关键因素维护和历史审计分开。用户进入 Goal 后应能快速回答：这条 Goal 还受什么影响、我要补充什么事实、保存后会改变什么、完整历史去哪里查。

Molis Work 中对应父 Goal 为 `ux-goal-factors-workbench`，依次完成三个叶子 Goal：

1. `ux-goal-factors-navigation`：五区导航、快速记录、只读完整记录；
2. `ux-goal-factors-controls`：关系、风险、影响范围和工作规则的可理解交互；
3. `ux-project-defaults-settings`：项目默认规则迁入项目设置，并通用化设置语言。

## 当前行为与问题证据

- `src/web/render.ts` 的 `renderGoalTechnicalDetails` 同时渲染原始事实、关系编辑器、Evidence 提交、Risk/Impact 新增与编辑、项目与 Goal Policy 表单和事件历史。
- “完整记录”既是审计入口又是维护入口，职责冲突；用户无法区分“改当前事实”和“查看过去发生了什么”。
- Goal Detail 只有四个顶层入口，关系、风险、影响范围和规则没有稳定位置；进展页中的风险链接仍指向旧的记录长页锚点。
- 风险表单一次要求概率、影响、区域、触发、处理、阻塞、复查、负责人和关联 Goal；Impact 与 Policy 也直接暴露内部字段，首次记录成本过高。
- 项目默认 Policy 在任意 Goal 的记录页里都能编辑，作用范围不符合用户预期。
- 设置默认围绕 Runtime、MCP、CLI 和项目存储组织；非 coding 工作也会被迫理解技术入口。

## 范围

- Goal Detail 顶层导航改为“概览 / 完成要求 / 进展与阻塞 / 关联与约束 / 完整记录”。
- Goal 标题区提供“快速记录”，可为当前 Goal 记录完成依据、风险、影响范围或 Goal 关系；取消后仍停留在原位置，保存后给出结果回执。
- “关联与约束”内部一次只展示“Goal 关系 / 风险 / 影响范围 / 工作规则”之一，并支持链接、键盘和刷新后恢复。
- 完整记录改为纯只读，按“基础信息 / 执行与检查 / 变更历史 / 技术记录”组织；不包含新增、编辑、解除、停用或保存控件。
- 四类维护表单先询问用户能直接判断的必要事实，再按需展开高级字段；关键语义不允许用不可见默认值代替用户决定。
- 项目默认工作规则迁入项目设置；Goal 只展示继承结果并允许增加当前 Goal 的要求。
- 设置首页和文案先以项目、工作规则和连接关系为中心；AI Runtime、MCP、CLI 等术语留在对应技术区域。
- 更新中英文文案、回归测试、产品与设计说明，并做桌面和移动端真实页面验收。

## 非目标

- 不改变 Goal、Relation、Risk、Impact、Policy、Evidence 的权威领域语义和权限。
- 不新增第二套状态、历史或本地存储模型。
- 不把 Risk、Impact 或 Policy 简化成失真概念，也不伪造推荐、概率、负责人、阻塞方式或项目默认值。
- 不重做 Goal Tree、Decision Center、TUI 或整个设置系统的视觉语言。
- 不在本任务中实现新的通用内容类型、富文本编辑器或自动分类系统。

## 用户场景

1. 用户进入 Goal，标题下即可看到稳定的五个任务入口；默认概览仍只负责当前状态和下一步。
2. 用户想到一条关键事实时，点击“快速记录”，选择类型后直接填写与当前 Goal 绑定的短表单，不需要先理解模块位置。
3. 用户系统检查 Goal 的依赖或约束时，进入“关联与约束”，在四个清晰区域间切换，一次只处理一种对象。
4. 用户需要审计时进入“完整记录”，可以浏览所有原始事实和历史，但不会误触维护操作。
5. 用户调整项目默认工作规则时进入项目设置；回到具体 Goal 后看到继承结果，只为例外增加更严格要求。

## 方案与关键决策

### 信息归属

- 概览：现在发生什么、下一步和目标说明。
- 完成要求：完成标准、边界、子 Goal 和前置依赖。
- 进展与阻塞：当前执行、完成依据摘要、检查和开放阻塞。
- 关联与约束：Goal 的关系、风险、影响范围和工作规则，以及对应维护入口。
- 完整记录：只读审计与技术事实。

### 写入路径

- 标题区“快速记录”是低频事实的统一快捷入口，不取代各模块的完整维护入口。
- 新增表单先显示必要字段；高级设置必须由用户主动展开。任何会改变领取、完成、失效、冲突或确认门槛的字段都要明确说明后果。
- 保存期间显示进行中，失败说明缺什么及如何修复，成功说明新增或更新了什么并保留当前 Goal 上下文。

### 视觉与语言

- 继承现有连续文档式 Goal 工作台、细分割线、紧凑控制和单一蓝色强调色；不改成卡片墙。
- 模块标题说明“它记录什么、何时需要用”；按钮直接写操作结果。
- 正文使用项目、目标、关系、风险、影响范围、工作规则、完成依据等通用词；内部对象名只在技术记录和 AI 设置出现。

## 输入、输出与依赖

- 输入：现有 `WebGoalView`、Relation、Risk、Impact、Policy binding、Evidence、Review、Event 和项目目录事实。
- 输出：五区 Goal Detail、快速记录交互、四区关键因素工作台、只读完整记录、项目规则设置及操作回执。
- 依赖：现有服务端 HTML 渲染和事件委托、现有写入 API、Molis Work 项目目录、现有 UI 状态与项目作用域路由。

## 文件与模块边界

- `src/web/render.ts`：Goal Detail 结构、表单、客户端交互、样式和设置页面。
- `src/web/server.ts`：项目设置页面所需 board 快照及现有 Policy 写入路由的作用域衔接。
- `src/web/i18n.ts`：新增双语界面文案。
- `tests/web.test.ts`、`tests/i18n.test.ts`：HTML、路由、写入路径、只读边界和双语回归。
- `PRODUCT.md`、`DESIGN.md`：最终信息架构、作用域和使用路径。

## 验收标准

- 五个顶层入口及四个“关联与约束”内部入口职责清楚，一次只显示一个对应面板。
- 快速记录始终绑定当前 Goal，四个入口可达；取消不丢上下文，保存有成功或失败回执。
- 完整记录没有写入控件，Goal、关系、风险、影响、规则、执行和事件事实仍可完整找到。
- 关系、风险、影响范围和规则的默认表单只展示必要事实，高级字段按需展开；影响门禁的字段没有静默假设。
- 项目默认规则只在项目设置编辑；Goal 页面显示继承结果且只允许增加当前 Goal 的要求。
- 通用页面不把 coding 或 AI Runtime 当作默认场景，技术术语只在技术区域出现。
- 桌面、390px 窄屏、键盘和减少动态效果下均可操作；页面无横向溢出。
- 原有领域 API、数据和审计历史保持兼容。

## 假设与开放问题

- 当前已有写入 API 足够支撑本次信息架构，不新增领域命令。
- 快速记录优先复用同一表单与保存链路，避免形成两套行为。
- 大型 Goal 的递归拆解质量已作为独立 Molis Work Draft 记录，不混入本任务。
