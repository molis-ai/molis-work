# T-049 受管理安装目录缺所有权记录时，移除报声明过的 `connector.install.invalid`，不再抛原生 ENOENT

> **这条在 main 上成立，而且不需要新码。** `removeManagedConnectorTool`（`apps/local-host/src/connector-tool-install.ts:77`）在安装目录存在、`installation.json` 不在时，`:85` 的 `readFileSync` 抛出原生 `ENOENT`。同函数里别的拒绝（`:78`、`:84`、`:86`）都用 `toolInstallErrors.invalid`（`connector-tool-process.ts:4`，kind `invalid`，HTTP 400）。只差这一种情形没走同一个码。起草时只读了代码，没有在真实路径上复现；第 5 节的先红就是复现。
>
> **和 T-013 / #1360 没有依赖。** `tests/project-deletion-service.test.ts:457-482` 的 ENOENT 不是这个函数抛的：项目删除路径（`project-deletion-service.ts:27-41`、`web-project-deletion.ts:29`）里没有连接器，它来自 `managed-project-deletion.ts:46` 的 `fs.rename(projectDirectory, stagedDirectory)`。连接器的安装目录是 Home 级（`runtime/connectors/installs/<id>`），不是项目级，也不是 `ProjectDeletedHooks` 的一个主人。本单不碰 T-013 的任何文件。

## 1. 背景

依据都在 main `5bb573455`：

- 现状：`removeManagedConnectorTool`（`:77-89`）依次：校验 id 格式（`:78`，`toolInstallErrors.invalid`）；被连接引用返回 `"in-use"`（`:79-81`）；目录不存在返回 `"absent"`（`:83`）；目录是链接或真实路径变了抛 `invalid`（`:84`）；然后 `:85` 无条件 `JSON.parse(readFileSync(join(directory, "installation.json"), "utf8"))`；记录里的 id 对不上抛 `invalid`（`:86`）；最后 `rmSync`（`:87`）。目录在、记录不在，`:85` 抛原生错误，后面的核对与删除都没走到，所以仍是「不删任何文件」，只是码不对。
- 目录在、记录不在会出现：安装流程先建目录（`:58`）后写记录（`:60`），进程在两步之间被杀；有人手工删了记录；外部工具清了半个目录。记录写入失败时 `catch` 会 `rmSync` 整个目录（`:73`），所以正常路径不留这种目录。`docs/system/HOME-DATA.md:260` 写明孤儿安装目录没有自动清理。
- 内核记错与出口：内核把失败原样记下，原生错误的 `code` 是 `"ENOENT"`（`packages/kernel/src/action-settlement.ts:93-95`）；MCP / HTTP 出口 `action-gateway-http.ts:20-23` 走 `actionErrorResponse`，不是模型码的失败落到 kind `internal`、HTTP 500、`actions.execution_failed`，消息是原生的（含绝对路径）（`packages/plugin-sdk/src/errors.ts:9-90`；`ACTION_ERROR_CODE` 正则在 `packages/contracts/src/platform/action-errors.ts:78`，`ENOENT` 不符合）。
- 调用者（起草时查了 `apps`、`packages`、`plugins`、`tests`；`removeManagedConnectorTool` 只有两处生产调用，导出在 `apps/local-host/src/index.ts:107`）：

| 调用者 | 怎么到 | 现在 | 改后 |
| --- | --- | --- | --- |
| `connectors.local.cleanup@1` 处理器 | `connector-local-actions.ts:39-42`，`beforeEffect()` 后直接返回 `{ status: removeManagedConnectorTool(...) }`，不捕获；经 MCP / HTTP / Agent 调用（受众 user / agent / mcp，权限 `connectors:management:write`，`:10`） | 500，`actions.execution_failed`，消息是原生 ENOENT 和绝对路径 | 400，`connector.install.invalid`，中文文案，不带路径 |
| `cleanupConnectorInstallation` | `connector-tool-cleanup.ts:5-12`，捕获一切，`hostLog.warn("connections", "installation_cleanup_failed", error, …)`，返回 `{ status: "retained", message }`；调用方 `connector-activation.ts:73`、`connector-authorization-presentation.ts:71`、`connector-local-submission.ts:51`（返回值丢弃）、`connector-management-service.ts:21` | 返回值不变；日志里的 `code` 是 `ENOENT` | 返回值不变；日志里的 `code` 变成 `connector.install.invalid`（`host-log.ts` 只记 `{name, code}`，不记消息） |
| 测试 | `tests/security-invariants-connector-install.test.ts:58`（所有权记录不符，`/所有权记录不符/`）、`tests/connector-managed-install.test.ts:193`（`in-use`）、`tests/security-invariants-native-cli.test.ts:36` | 都不走「记录不在」 | 不受影响 |

没有现有调用者依赖「记录不在时是原生错误」。`cleanupConnectorInstallation` 的四个调用方只看 `retained`，不看码。

## 2. 目标

1. 目录在、`installation.json` 不在：`removeManagedConnectorTool` 抛 `toolInstallErrors.invalid`（`code: "connector.install.invalid"`，`kind: "invalid"`），目录与里面的文件一个都不动（`RAC-1493`）。
2. 同一情形经 `connectors.local.cleanup@1` 调用，得到同一个码与 kind，消息不含绝对路径（`RAC-1494`）。

## 3. 不做

- 不新增错误码、不新增 Error 子类、不动 `toolInstallErrors` 的定义（`.changed` 没人用，也不是本单的事）。
- 不让孤儿目录变得可移除：「没有所有权记录就删」放宽的是安全边界（只许删自己的安装目录，`:76` 的注释），要用户定。本单只换码，仍然什么都不删。
- 不处理同一行的其他原生错误：记录内容不是合法 JSON（`SyntaxError`）、记录是目录（`EISDIR`）、无读权限（`EACCES`）；也不处理 `readManagedConnectorTool`（`:92-99`）里同样的 `JSON.parse(readFileSync(…))`，以及 `:95` 的 `realpathSync(directory)` 在目录缺失时同样抛 ENOENT。这些是同类缺陷，范围大一点，另开一张零碎单（见第 11 节）。
- 不改 `cleanupConnectorInstallation`、`connectors.local.cleanup@1` 的定义或 schema、`connector-local-actions.ts`。
- 不动 `tests/project-deletion-service.test.ts`（T-013 的）。不改 `docs/system/SECURITY-INVARIANTS.md`、`docs/system/HOME-DATA.md`。
- 不写兼容或迁移：这是同一个拒绝换一个码，不碰存量数据。
