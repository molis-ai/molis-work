# Molis Work AI 能力开发手册

状态：手册正文已写入（2026-10-16）：`docs/platform/PROLOGUE-AI.md` 第二部分（第 12–17 节）与 `skills/molis-prologue-ai/SKILL.md` 的入口，ADH-01 至 ADH-11 的工程侧核对记在 §9；真实模型前后对比的第一份记录在 §9.5（存量清理 B1，项目上手），用户验收未做。负责人：AI 能力开发手册线（Claude，由统筹会话排期与评审）；需求整理为 Codex；现有 AI 平台、各业务插件与相关 Skill 的 owner 保留原归属。

## 1. 要解决的问题

Molis Work 的开发者和开发 Agent 在实现 AI 功能时，需要共同的设计依据，尤其是 Skill、系统 prompt、上下文、工具与 Agent 协作。不能为了让某个交付案例完成，就不断增加硬编码分支、关键词路由、固定步骤、无依据阈值和 prompt 禁令，使 AI 的理解、判断和适应能力逐渐退化。

手册的核心原则是用户明确提出的 **context over control**：先给 AI 足以理解目标、环境、事实、能力、约束与反馈的上下文，使它能在授权范围内选择方法和作判断。确定性工程负责身份、权限、数据一致性、工具合同、取消、预算和恢复；二者各有职责，不能用一层代替另一层。

目标完成程度是**内部完整的开发文档与参考材料**：新开发者或接手 Agent 能找到手册，按真实场景选择实现方式，写出有理由的 prompt/Skill/context 设计，沿现有运行时接入，并用任务效果验证。手册不是新增审批系统、自动限制器或“每项都必须使用”的架构清单。

## 2. 唯一入口、交付物与范围

现有 [Prologue AI 开发手册](../../docs/platform/PROLOGUE-AI.md) 已覆盖模型接入、层次职责、调用链、提示词登记和工程验证；[AI 开发 Skill](../../skills/molis-prologue-ai/SKILL.md) 提供执行入口。**在现有手册补齐 AI 行为设计与质量迭代章节，保留已有接入合同，不另立一份重复且可能冲突的总手册。** 内容确需拆开时，保留该手册为总入口，以短链接导航到内聚章节。

最终交付包括：明确的设计原则、系统 prompt/Skill/context/tool 的分工、经源码核对的基础实现索引、贴近 Molis 的正反示例、真实任务评测和改进方法，以及 AI 开发 Skill 中的简短引用入口。正式章节应能直接指导开发，不以一份目录或本需求书代替手册正文。

覆盖内置与生成插件中的有界 AI 调用、个人助理、Coding、场景 Skill、系统 prompt 和子代理协作。手册按场景给适用做法，不要求每次单次生成都装配完整 Agent、检索、记忆和子代理。现有功能的全面改写、全量 prompt 清理、新评测平台或自动门禁不在本项内；发现具体欠账归原功能 spec，本项不借机扩成全仓重构。

## 3. 手册必须讲清的原则

### 3.1 Context over control 的实际含义

设计时先回答：AI 要做成什么，为什么；当前对象和工作状态是什么；哪些事实可靠、过期或未知；有哪些可用能力；用户已经决定什么；什么结果算有效；失败后能得到什么反馈。把这些信息组织成可读取、可更新的上下文，而不是预写它在所有情况下的下一步。

上下文不足时补资料入口、来源、对象引用和工具反馈；工具难用时改善语义、参数与返回；任务有歧义时让 AI 根据影响判断是否提问；只有真实的确定性约束才由代码强制。保留专业判断、不同合理路径与用户最新意图，不能因为单个模型或样例偶发失败，就把所有任务收窄成固定流程。

手册应给适用边界：固定格式转换、事务提交、已定义工作流等可以采用确定步骤；探索、创作、分析和复杂工作选择通常需要 AI 判断。选择依据是任务的不确定性和风险，不是对 Agent 或 workflow 的偏好。

### 3.2 系统 prompt：目标、判断依据与边界

系统 prompt 写清角色目的、结果要求、重要的判断依据、能力与真实限制，以及与用户协作的方式。语言具体、简洁、可理解；优先说明何时以及为什么采用某种方法，不堆重复命令、绝对化措辞和人为仪式。

稳定规则、场景方法、本次用户要求、资料事实及工具返回各有位置。动态对象、历史、用户资料和检索结果不混进稳定指令，不因进入上下文就取得指令权限。需要机器消费的输出遵守真实 schema；面向人的回复根据任务需要表达，不强制每次输出同一套标题、固定数量或冗长状态宣言。

示例覆盖代表性情形与合理变化，帮助理解质量，而不是把样例写成唯一正确答案。prompt 的长度由必要信息决定，不能用固定字数或“越短越好”替代内容质量；不要求展示隐藏推理，以可核对的结论、依据、产物和执行结果解释工作。

### 3.3 Skill：可复用的方法与资料

Skill 负责适用场景、工作方法、判断线索、所需资料、工具用法和质量标准；能力注册、执行权限与数据校验仍在平台和原 owner。触发描述让 Agent 判断何时有用，必要细节和资料按需读取，避免把所有 Skill 全文塞进每次请求。

Skill 可以包含适用的确定步骤和脚本，但必须说明哪些是业务必须遵循的过程、哪些是可调整的方法。场景知识优先留在可维护、可组合的 Skill 与资料中；不为每个场景同时增加一套宿主 if/else、隐藏 prompt 和专属工具流水线。复用与更新沿当前 Skill 版本、覆盖和生效机制，不新造加载器或优先级系统。

### 3.4 上下文：足够、相关、可追溯、可恢复

为任务提供目标、最新输入、工作状态、相关对象、工具目录及结果的来源；允许 AI 按需查阅更多信息。区分事实、推断、用户要求和外部材料。上下文选择依据相关性、时效、权限和实际预算，不固定把前几个对象当成完整事实，也不把全部可读内容无限堆入。

摘要、裁剪、记忆和子代理交接要保留影响任务正确性的约束、尚未解决的问题、有效引用及已发生效果；不靠每轮追加同一组禁令弥补资料丢失。上下文压缩后用户的新要求仍能生效；这些机制复用 Prologue 与已有输入回执能力，不在每个插件里再实现一套。

### 3.5 工具和运行时：让 AI 能理解并可靠行动

工具描述讲清用途、适用对象、输入输出、影响及常见失败；返回 AI 能据此决定下一步的真实状态、原因和资源引用。减少同义工具和必须猜测的参数，不让“成功”只代表请求已收下。可用性从当前声明、授权和连接事实得到，不能把开发时的固定名单当成运行时事实。

权限、来源隔离、校验、幂等、并发一致性、取消、撤权及实际预算由既有工程层强制。prompt 可以解释这些边界，但不能成为唯一防线。某类工具暂不可用应给出原因和可行路径；不以泛化限制遮住尚未接好的能力，不把错误吞掉后交给 AI 猜。

### 3.6 避免为单次交付堆控制逻辑

失败先区分目标或上下文缺失、工具问题、prompt 歧义、模型能力、运行时缺陷和真正的产品约束。改最有证据的原因；需要新增规则时说明它对应的真实问题，以及为什么上下文、工具反馈或已有机制不足。

手册要展示如何识别和替换这些做法：用关键词强制挑 Skill；任务不论大小都先拆固定数量子任务；用固定轮数或格式判定“工作完成”；每次失败都追加一条系统禁令；为了演示变绿缩小工具能力；把模型的“完成了”当成真实产物验证。这里不否定已有预算和业务约束，重点是区分其依据与效果。

这套检查以解释和案例指导判断，不生成新的自动限制评分、强制审批、阈值或所有任务必填的表格。新框架、缓存、记忆层、路由器或子代理只在具体任务受益且有证据时引入，能用已有简单路径完成就沿用它。

## 5. 正反示例与手册组织

正文至少覆盖有界调用、场景 Skill 和多步 Agent/协作这几种不同情形；可在同一组内聚例子中完成，不要求每条原则独立建一个工程。每个例子展示问题、原始设计为何失效、改进后的上下文/工具/prompt 分工，以及用什么任务证明更好。

可直接采用的示例方向：

- 工作简报不按“命中某关键词就输出固定三条建议”判断；提供工作目标、变化、来源和用户偏好，由 Skill 判断是否值得提醒，允许没有建议。排程、权限和写入仍走原服务。
- Coding 不对所有任务固定拆出几个子代理；提供目标、仓库约定、当前改动、可用工具和验收条件，让 Agent 根据真实依赖决定是否委派，权限和并发边界照常执行。
- 服务接入失败不靠“无论什么情况都反复重试”或“失败就永久禁止”处理；提供实际连接状态、错误和已发生效果，让 AI 选择可行下一步，重试幂等及授权由平台保障。

建议正式章节顺序：设计目标与分工 → prompt/Skill/context/tool 的写法 → 现有基础实现 → 正反案例 → 评测、诊断与迭代 → 开发入口及维护方式。每节讲清判断依据与实际做法，避免把本 spec 再抄成一组口号。

## 6. 如何验证与改进 AI 行为

评测直接观察真实用户任务的结果、质量、可调整性、成本与时延，而非只查字段齐全、关键词出现或固定工具顺序。根据功能选代表性任务、不同合理表达、资料不足、用户纠正、工具不可用和恢复情形；不规定一个脱离功能风险的固定 case 数。

每次重要 prompt、Skill 或 context 变化用可比较的模型配置、输入与环境记录前后表现，注明随机性和运行次数，区分“运行机制正确”与“模型表现改善”。契约与拒绝行为用确定性测试；任务质量用真实模型、实际产物和必要人工判断。替身证明调用路径，不能证明 AI 会理解场景。

案例应包含未参与设计的变化，观察是否仍能理解和适应；一次成功不等于稳定，某个样例失败也不自动证明需要加限制。回看 AI 当时实际收到的上下文、可用工具、版本与真实返回，先找根因，再决定补上下文、改工具、调整提示或修运行时。沿现有记录和测试入口复现，敏感材料不进入示例或仓库。

## 7. 实施与依赖边界

手册 owner 维护总入口和原则；各能力 owner 核对自己提供的源码示例、调用链和适用条件。Prologue 继续拥有通用执行合同，Molis Work 拥有产品行为与领域资料；本项不修改 SDK 执行语义。

预期修改范围为 `docs/platform/PROLOGUE-AI.md` 及必要的关联文档、`skills/molis-prologue-ai/SKILL.md` 的简短导航；只有关联生成插件示例确有变化时同步其 Skill 章节。使用现有链接和开发规范让开发 Agent 能发现手册，不将全文注入所有系统 prompt，不新增默认审批或强制流程。

实施顺序为核对现有参考 → 完成原则和实用正文 → 补可验证示例与评测方法 → 更新开发入口 → 用真实开发情境走读。手册中的稳定原则可供其他需求提前参考；未完成的资料不应成为所有功能的全局阻塞条件。手册迭代发现需要改产品行为时，回到对应 spec 与授权范围，不在文档任务中顺手改代码。

#### D4 模型路径上悄悄吞掉的失败（2026-10-16）
