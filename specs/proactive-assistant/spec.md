# Molis Work 主动工作助理需求书

状态：需求已整理（2026-10-15；2026-10-18 补充工作记忆初始化、每日例程、前门路由、从一次对话生成 Skill 与跨源搜索规划），尚未实现。功能目标完成程度为**内部完整**：用户在真实工作中不必反复发起请求，助理能够根据近期行为与插件内容发现值得推进的工作，按用户配置的 Skill 处理，交付可用结果，并在修改、等待、中断和重启后继续。本次交付为需求定义，不代表功能已实现。

## 1 产品目标与范围

个人助理需要持续理解用户最近一段时间在做什么、已做到哪里、正在受什么阻碍，以及平台内有哪些材料和能力可以帮助他。在用户没有发送新消息时，也能发现值得采取的下一步，准备结果或继续已受托的工作。

主动性的价值以实际推进衡量：减少重复解释和资料搬运，缩短从材料到结果的过程，让未完成的工作更容易接续，让需要本人决定的事更明确。提示数量、对话轮数、运行次数和 Agent 数量不作为成功指标。

功能集合还应让用户按日、周、月等周期理解自己的工作，通过报告中的具体选项决定下一步，并在项目首页一眼看清重点、变化与待决定事项。建议、报告和处理状态需要在工作台侧边栏中持续可见；点击建议后，主工作区能打开对应插件、定位并高亮关联内容，用户可以对照处理并返回。背后需要一套平台共用的完整工作记录，持续支撑主动理解、报告、审计，以及 Molis Work 整体端到端效果评测。

这项能力覆盖从观察、理解、判断到行动、交付、跟进的完整过程。用户给助理配置的各种 **Skill 提供这个过程中的核心做法**：决定助理关注什么、如何理解、何时值得行动、怎样推进、怎样检查结果和何时停止。用户可以查看和修改这些做法，系统提供足够好用的初始配置。

**本需求采用“通用平台能力 + 个人助理 + 可配置场景 Skill”的产品形态。** 日报周报、工作接续、提前准备、阻塞跟进、跨插件整理等场景，由个人助理按所配置 Skill 调用系统数据工具与实际业务能力完成。工程建设负责通用采集、数据与动作工具、运行控制和交互承载；场景的材料选择、判断做法、处理步骤及表达要求由 Skill 承担。本文列出的场景与用户结果，不应逐项对应成一组固化在产品代码中的专属功能。

助理应充分使用 Molis Work 的内容、搜索、记忆、角色、动作、交互与成果能力，并通过 Prologue 获得可靠的持续执行、上下文管理、协作、等待、控制与恢复体验。能力组合必须落实为用户可使用的工作结果。

范围是单个用户的个人空间、已授权项目，以及平台实际接入且用户允许使用的外部能力。保留现有助理入口、受托工作、定时、提醒、角色与插件的价值；补齐它们之间的连续工作体验。跨设备常驻、团队协同、Skill 商店和对整台电脑的默认观察不属于本次要求。

用户于 2026-10-15 确认纳入独立的**工作简报插件**，承载周期报告、专题分析、准备材料和方案对照，管理其正文、版本、来源及修订。主动判断、分析、执行和跟进仍属于同一个人助理与场景 Skill；临时提示不必生成简报，原业务事实与状态不复制。独立需求见 [工作简报插件](../work-brief/spec.md)。

2026-10-27 用户确定项目首页与 Work Brief 合并设计：Work Brief 承接综合首页及生成页面，未安装时保留插件卡片、各插件概览／建议的基础首页，统一公共来源与呈现机制。本文继续定义助理理解、判断、执行及报告质量，首页承载和生命周期由 [Work Brief §1.1～1.4](../work-brief/spec.md)收口，不另造主动助理首页或要求基础查看必须安装该插件；本次未开发。

## 2 工作理解的基本约定

助理需要区分三件事：用户正在看什么、用户可能关心什么、用户已经委托它做什么。当前页面为理解提供线索，不能覆盖另一项工作的目标；推断出的兴趣或意图也不能自动成为用户承诺。

“工作”是一个有预期结果、相关材料和当前进度的连续事项，可以属于个人空间或项目，可以跨几个插件，也可以尚未命名、尚未建立 Goal。建立 Goal、填完整计划或打开助理对话均不得成为获得主动协助的前置条件。

助理可以发现并描述尚未正式组织的工作，但不能擅自把它写成用户已确认的 Goal、待办、日程或决定。已经存在的工作应继续使用原有归属和结果，不因一个新 Skill、一次提醒或一次页面切换再建立一份。

从零散材料识别工作、判断关联和修正理解，由个人助理依照适用 Skill 调用查询与工作理解工具完成。系统保留理解的依据、候选身份与用户纠正，并复用既有工作的真实身份；不能在底层按场景名称预先拼好一份不可调整的工作结论。这里的助理理解不另建一套正式目标或业务进度。

用户应能纠正工作被错误合并或拆开的情况：说明“这是同一件事”“这份资料属于另一件事”或“这部分单独处理”后，助理调整理解、建议与后续跟进。调整的是工作关联，不自动合并或拆分插件里的正式业务对象；已有产物和发生过的操作保留原出处。相关报告和评测避免重复计数，原委托各自的权限、范围与停止条件不能因合并理解而扩大。

业务内容和完成状态以对应插件的当前事实为准。助理的理解、总结与执行进度不能代替原始内容。它必须区分用户操作、助理操作、其他自动化操作，以及有待核实的外部信息。

## 3 理解近期行为和插件内容

### 3.1 观察范围

用户能够查看和设置助理的观察范围，包括个人空间、指定项目、插件和内容范围。内容可读、允许用于主动理解、允许写入或操作，需要分别表达；用户能主动询问某份内容，不表示该内容自动纳入持续观察。

跨项目关联应符合用户设定的范围和工作需要，不因名称相近或页面切换自动混用资料。内容被排除后，后续主动判断不能通过旧的观察副本或总结继续使用它；已产生的业务成果按其现有归属与访问权限处理。

观察应包含能够反映工作进展的行为：阅读或引用材料，创建、编辑、保存、比较内容，完成或撤销操作，切换相关工作，接受、修改、拒绝助理结果，以及遇到的实际失败。普通点击或停留时长可以作为弱线索，不能单独证明任务、优先级或执行授权。

插件中的正文、资料关联、工作状态、版本变化、期限、等待事项和成果同样属于理解依据。助理应能联系多个插件里的相关内容，区分不同插件呈现的同一事实与真正的新信息，避免以出现次数误判重要程度。

2026-10-27 用户确定：在 Onboarding 配置主动助理时，由用户设置近期行为的回看范围，之后可在设置中修改。范围以近几小时、几天或几周表达；已有配置时预填当前有效值，引导与设置读写同一份配置，不再将七天定为统一默认值。跳过沿既有引导和主动启用规则处理，未选择不视为同意持续观察。

后续主动判断使用当前有效的回看范围，保存、重进设置和重启后保持一致。仍未结束的受托工作按已有委托继续接续，不因超出回看窗口自动结束；较早材料可以因当前工作的真实需要在已授权范围内引用，不能因此把全部历史持续纳入观察。

主动理解的回看窗口与平台工作记录的保留周期是两件事。修改回看范围不删除原始记录，也不截断按各自范围生成的月报和跨版本评测。平台记录、主动使用和评测使用的范围应分别清楚可查。

未发送的输入、未保存的编辑和外部应用内容必须有清楚的观察约定。默认不以逐字输入或未发送草稿启动主动工作；获准使用草稿时，必须保留其草稿身份，不能当作已保存的事实或用户指令。

### 3.2 形成和更新工作理解

助理应从行为的关系与变化中理解工作脉络，包括当前预期结果、已经完成的部分、相关材料、尚缺内容、等待条件、可能的阻塞和有价值的下一步。不能只输出最近操作清单，或把各插件摘要拼在一起。

显式诉求、当前有效决定、用户对结果的修改与纠正，优先于行为推断。需要区分可验证事实、用户表达、推断和仍未知的部分；依据不足时保留不确定性，不能编造期限、责任人、目标或进度。

不同来源对同一件事给出矛盾内容时，按对应事实的有效归属、版本与用户明确决定核对，不简单采用时间最近或重复最多的一条。仍不能解决时展示具体分歧及其影响，仅暂停依赖这项判断的处理；可以继续不受影响的准备。用户的“已在别处处理”能够结束对应提醒，但记录为用户说明，不伪装成系统已核实外部业务完成。

频繁出现不必然代表重要，近期未打开也不表示已放弃。判断重要性应综合用户表达、工作约定、实际状态、时间要求和依赖关系。

用户能查看助理认为自己在推进什么、相关依据是什么，并纠正工作归属、排除某份资料、说明已经处理或不再关注。纠正应影响后续判断和行动，不能只在当次回复里口头接受。

用户在插件中手动修改、完成、撤销、移动或删除内容后，助理应据此更新原工作。下一步以当前有效内容为起点，保留用户修改，取消已无必要的计划和提醒，不能为了符合旧理解重新制造已被删除的内容。

短期工作理解与长期偏好应分别管理。一次操作不能自动变成永久习惯；暂时不处理不能自动变成长期排除。可长期使用的偏好需要有足够依据，或由用户明确表达，且能查看、纠正和删除。

### 3.3 信息不足和首次使用

新用户没有足够行为历史时，助理仍能结合当前内容、用户已有委托和已启用 Skill 提供有依据的帮助。首次使用允许直接选用默认配置，也允许用户先限定范围；不能要求先积累很久的数据或完成复杂设置。

首次启用时，应让用户看懂默认 Skill、将观察的范围、允许准备和执行的内容，以及预期主动程度。可以直接采用一组清楚的默认设置，也可以先仅观察和提供建议；不能依靠隐藏默认值扩大委托。

缺少某个插件的数据、连接或能力时，应保留已经确认的理解，并说明对结论和下一步的实际影响。不能把未读取当成没有内容，也不能为补全理解无条件读取全部插件。

### 3.4 平台共用的完整工作记录

信息采集是平台级能力，覆盖用户手动工作、主动与被动助理、插件内 AI、工作流、定时与后台任务，以及 Web、桌面、CLI、MCP 等实际支持的入口。不能只为主动助理挑选少量埋点，也不能把未经过助理的工作排除在 Molis Work 的整体效果评测之外。

采集完整性由平台保障，不依赖某份 Skill 是否运行或主动要求记录。Skill 通过系统数据工具按任务需要读取记录、内容和关联，决定本次工作如何使用它们；停用场景 Skill 不应使其他已获准工作的审计与效果记录失去完整性。实际采集和使用仍遵循各自有效范围。

完整性以能还原一项工作当时的条件、过程与真实结果为标准。已纳入范围的工作应保留完整的关键阶段与语义信息，既包含成功，也包含失败、拒绝、取消、等待、没有行动和没有被采纳。不能只留成功样本、最终摘要或调用次数，再用它们反推整段工作。

首次接入项目、插件或资料来源时，既要了解当前范围内已有的内容、状态、关系和可用版本，也要覆盖之后发生的变化。用户能看见现有资料掌握到什么程度、完整记录从何时开始、哪些历史无法取得。首次读取、重新连接后的补读和批量导入不能被当成用户刚刚创建或编辑了全部内容；记录中断后补回的历史变化应与本次新变化区分。完整采集与每次给模型使用哪些材料分别管理，不能为了接入全量记录让每次判断都读取全部历史。

用户主动导入资料是本期真实操作，应正常记录；原内容形成时间、导入时间以及之后实际发生的修改分别表达。报告可以说明本期引入了哪些资料，但不能因此将资料中已有的历史成果全部算作本期新完成。

| 信息范围 | 必须能够回答的问题 |
| --- | --- |
| 用户意图与约定 | 原始请求、后续补充、选中对象与材料、目标和限制是什么；哪些是明确要求，哪些只是系统推断；何时改过 |
| 使用行为与交互 | 用户打开、停留、选择、编辑、保存、比较、采用、拒绝、暂缓、撤销和接管了什么；哪些内容实际进入可见区域，呈现了哪些候选、顺序和默认项；哪些只是准备展示 |
| 插件内容与业务变化 | 工作开始时相关内容和状态是什么；谁改变了什么；引用了哪个版本；变更前后与最终有效状态是什么；跨插件对象如何关联 |
| 检索、上下文与记忆 | 查找范围和查询是什么，返回了哪些材料，哪些进入实际工作上下文；读取是否完整，是否截断、压缩、缺失或过期；用了哪些记忆及其当时版本 |
| 主动判断与 Skill | 因何判断，考虑了哪些可行方向，选用或放弃什么，何时保持安静；实际生效的 Skill 正文、版本、组合、用户覆盖和简明判断依据是什么 |
| 计划与执行 | 一项工作经过哪些步骤、角色与委托；模型实际接收的消息和可获得的输出、工具参数与结果是什么；授权、调用、业务生效各处是什么状态 |
| 中断与恢复 | 何时暂停、取消、失败、超时、重试或恢复；哪些已生效，哪些被拒绝，哪些结果未知；是否重复产生效果 |
| 交付与后续结果 | 向用户交付的确切版本是什么，能否打开和使用；用户采用、修改、丢弃还是另做；后续是否返工、撤销，业务结果是否持续有效 |
| 条件、体验与成本 | 平台、插件、模型和相关配置是什么版本；连接和能力是否可用；等待、执行、呈现耗时及用量是什么；发生了哪些错误与降级 |
| 评测与人工判断 | 样本来自哪里，预期结果、判定规则与版本是什么；谁或什么评测器作出何种判断，依据何在；后续纠正有没有保留 |

工作记录应能从用户的一次操作或意图，一路关联到助理判断、Skill、执行步骤、工具调用、业务变化、页面呈现、用户反馈和最终结果。多轮、多角色、跨插件、跨入口和跨日接续仍属于同一工作脉络；一次重试与一个新的工作不能混同。真实发生时间、系统收到时间以及延迟到达的顺序需要可辨认。

Skill 的发现、被选用、有效正文进入本次工作上下文，以及对应工具取数、处理与交付过程应可核对。登记或加载了 Skill 不等于实际遵循了做法；效果评测应结合行为与结果判断，不能仅凭日志出现 Skill 名称就宣称由它驱动。

成功的检索和读取同样需要可追溯，不能只记录写入与错误；没有改变业务状态的判断、候选展示和正确不行动也属于工作过程。进入可见区域、停留和用户明确表示已读保持区别，系统不能声称知道用户是否真正理解了内容。

建议与内容联动也属于完整工作链：需要区分卡片实际呈现、选中查看、发起定位、目标加载、目标进入可见区域、精确位置高亮、退化为对象级查看、失败、返回，以及后续明确提交操作。发出了打开请求不能算定位成功，点击卡片不能算采用建议；这些阶段要能关联同一建议、内容版本和该次交互。

同一事实可以供多个用途读取，但要保留其权威来源：界面行为证明用户做过或看过什么；平台执行记录证明请求与执行状态；插件事实证明业务结果；助理与评测器提供判断。点击“完成”、工具返回成功、模型说已完成均不能独自证明业务完成。审计结论和报告中的总结不能覆盖原始依据。

为了后续效果评测，必要内容须能按当时的版本取回，包括用户已提交的请求、实际使用的材料、有效 Skill 与提示内容、可获得的模型输出、工具输入输出、交付物及相关变更。只留当前对象链接、长度、哈希或摘要不足以判断历史质量；历史证据不应因正文改写而悄悄变成新内容。保留历史证据也不产生第二份可编辑的业务事实。

图片、文件、音频等实际参与工作的内容适用同样的版本和完整性要求，不把“文本转述存在”等同于原材料可用。浏览器、桌面等能力实际提供给助理的观察和操作结果，在获准范围内也应能与该次工作关联；未获得的观察不能补造。

“完整”适用于产品范围内可观察、获准记录的工作信息。凭据只记引用；不要求或伪造模型未提供的内部思考。未发送输入、外部应用与未接入服务的活动遵循明确范围，不把完整采集解释为默认记录整台电脑。用于本机功能的记录不因此自动允许上传到集中评测或共享数据集；评测使用范围、脱敏、导出与删除要求应可设置、可核对。

真实用户工作、演示、Skill 试用、评测回放和系统检查必须能区分。它们都可以有必要记录，但不能默认混入用户成果、日周报、习惯推断或真实效果指标。用户明确将试用候选采用为真实工作时，从实际采用和生效处建立关联，不把试用期间的模拟结果补记成已发生业务。

新插件、新入口、新动作和新交互需要纳入同一完整性约定。平台能够按入口、插件、工作阶段和版本查看覆盖情况，标明未接入、暂不可用、丢失、截断、脱敏、到期清除与明确不适用；不能把缺记录解释为没有行为。关键工作链路与结果不得靠随机抽样保留；高频细节如采用汇总或抽样，须声明粒度、比例及因此无法回答的问题，不能称为逐次完整记录。

查询与呈现可以折叠重复记录，但在声明的完整保留周期内应能还原各次关键操作、不同结果及先后关系。采集异常、资源不足与保留策略造成的信息缺口应可见，不能无声丢失后继续宣称审计或评测完整。采集和评测不能明显拖慢用户工作，也不能以记录失败掩盖已经发生的业务效果。

2026-10-27 用户确定：工作记录默认在本地长期保留，不因经过固定天数自动删除；用户可在设置中选择自动清理期限或手动清理。设置清理期限或选择手动清理范围时，说明对历史回溯、报告依据与评测的实际影响；短于已启用报告周期、跨周期比较或评测所需范围时，指出可能失去的依据，不用静默延长保留期代替用户选择。配置保存与重启后保持一致，清理只作用于用户选定的记录范围。

原业务内容与已保存简报按各自主人的保留、删除规则处理，不因清理工作记录而连带删除。清理后无法取得的历史依据应明确显示缺口，不能用当前内容冒充，也不能通过旧观察副本重新纳入后续使用。长期保留不扩大采集或使用授权。

2026-10-27 用户确定容量规则：默认不设固定配额，设置中显示工作记录的实际占用，并允许用户设置、修改容量提醒线。接近或达到提醒线时提示占用与清理入口；提醒线不是存储上限，不因达到提醒线自动删除记录。用户已设置的到期清理规则照常执行，两者分别呈现。占用随新增和清理更新，提醒线保存、重进与重启后保持一致；真实磁盘不足或写入失败仍按上述采集缺口规则呈现，不能把未保存误报为已记录。

记录的有效保留周期、范围、可用体积与清除影响应清楚可查。经批准保留的评测样本应有明确用途与生命周期，不能依赖短期诊断日志是否尚未滚动删除。用户纠正或删除信息后，后续助理理解、报告与评测使用遵循对应设置，并如实标明历史证据的变化与可用性。

## 4 主动判断与工作选择

### 4.1 何时值得判断

近期行为形成新的工作脉络、相关内容发生实质变化、原工作出现可继续的条件、重要时间临近、受托工作产生结果，或用户约定的检查时刻到达时，助理应考虑是否有值得推进的事项。

平台负责提供可观察的变化、到时信号与当前运行条件；哪些变化值得关注、提前多久准备、如何判断阻塞及何时再次跟进，由适用 Skill 和已生效的用户配置决定。到时或变化信号只是判断的机会，不能由按场景写定的规则直接生成建议或决定业务下一步。通用去重、事件归并、限流及用户明确设置的范围可以由平台执行，但不得把新的 Skill 需要的相关材料按旧场景规则提前过滤掉。

判断必须同时考虑：与用户当前工作的关系、材料是否新鲜可靠、现在采取行动的价值、是否已有等价处理、所需能力与授权是否具备，以及注意力和用量是否值得。具备数据或到了检查时间，不自动意味着必须提示或启动任务。

重复变化应合并理解；助理自己产生的内容不应无条件成为再次发起同一工作的理由。已经处理、失去时效、被用户排除或仍在等待同一条件的事项，不反复提出。

### 4.2 判断结果

| 处理方式 | 对用户的承诺 |
| --- | --- |
| 暂不行动 | 没有足够价值、时机或依据时保持安静；不为展示主动性制造工作 |
| 提供下一步 | 指出具体工作、预期收益与可采取的动作，用户可以直接继续或纠正 |
| 准备结果 | 在已有授权范围内完成可审阅的整理、分析、候选稿或修改建议 |
| 继续受托工作 | 按当前有效委托推进原工作，不要求用户再次发起同一请求 |
| 请求必要决定 | 把确实影响目标、结果或授权的问题交给用户，说明为何此时需要决定 |
| 等待与跟进 | 清楚说明等待条件，在条件有效变化后接续，条件未变时保持安静 |

主动发现的下一步需要有明确对象或内容、预期结果，以及为什么现在值得做。泛泛的“建议继续完善”“可以考虑整理”不构成有效推进。

初始主动判断 Skill 优先考虑能解除阻塞、准备近期需要的结果、接上已经开始的工作，或减少用户重复劳动的事项。新的可能性也可以提出，但不默认压过用户当前重点。用户能通过 Skill 和关注设置调整这类价值取舍；用户明确的工作要求、期限约定及平台资源边界仍然有效。语义上是否同一事项、是否仍值得提示由助理按 Skill 核对，平台承担真实工作身份和重复提交不会重复生效的保障。

同一件工作涉及多个插件或 Skill 时，应形成一份连贯的处理，而非每个来源各自提示和启动。不同工作在资料、目标、权限和执行状态上保持清楚归属。

### 4.3 主动协助应覆盖的工作环节

主动能力需要覆盖工作的起点、推进、交付与复盘，而非只覆盖提醒和摘要。以下按共同工作问题划分；具体领域通过可配置 Skill 和实际插件能力扩展，不要求给每个案例做独立功能。

这些环节表达需要获得的用户价值，由个人助理选择、组合适用的场景 Skill 完成；不是要求按表逐行开发独立服务、专属 Agent 或固定流程。用户应能通过修改 Skill 改变材料取舍、优先判断、推进步骤和交付方式。

| 工作环节 | 助理应识别的变化与可交付价值 | 关键边界 |
| --- | --- | --- |
| 收拢意图与材料 | 零散行为开始指向同一结果时，联系已有材料，提出工作理解和缺口，准备可采用的整理或工作草案 | 尚未确认的意图保持候选身份，不自动建立承诺 |
| 排定下一步 | 多项工作竞争时间、期限或依赖变化时，比较先后关系，提出有理由的取舍和可执行下一步 | 不擅自改变用户目标、期限和其他工作承诺 |
| 提前准备 | 已知约定、会议、交付或阶段切换临近时，准备所需材料、问题、候选内容与检查结果 | 准备内容需与当时有效主题、参与范围和版本相符 |
| 跨插件接续 | 一处产生的材料或结果已经满足另一处工作的前提时，完成授权内的整理、转化和后续处理 | 保持原对象与来源关系，不能制造重复业务事实 |
| 解除等待与阻塞 | 新回复、新材料、依赖完成、权限或连接恢复后，识别可以继续的部分，接续原委托 | 没有新条件时不反复催促；联系他人遵循发送授权 |
| 发现偏差与补缺 | 内容与要求不符、证据冲突、资料过期、结果缺项或期限风险出现时，解释影响，准备具体修正或可选取舍 | 用事实说明问题，未知情况不夸大成失败或风险 |
| 检查交付与后续 | 候选结果完成、被用户采用或被修改后，核对可用性、剩余事项和实际效果，准备必要的接续材料 | 发布、发送和结束工作以实际要求及有效授权为准 |
| 发现相关机会 | 已授权的新资料、工具能力或外部变化可以改善当前工作时，给出相关性依据与小范围可审阅的尝试 | 新颖性不压过当前重点，不为推荐工具制造工作 |
| 周期复盘与改进做法 | 到达日、周、月或阶段回看时，梳理真实成果、反复阻塞与可调整方法，提出报告、下一周期重点或 Skill 修改草案 | 事实总结、原因推断与方法建议分开，未采用的修改不生效 |

同一工作可以自然经过其中几个环节，保留原约定、资料与结果，不要求用户逐个启动。暂不行动也是有效选择：不相关、已经完成、已有同等安排、证据不足或超出委托时，应保持安静或只提出必要问题。

发现重复劳动后，助理可以建议把有效做法整理成 Skill 或持续委托，并提供具体草案。一次处理成功不能自动升级为长期自动执行。针对真实反馈提出的改进，应能与原做法比较，由用户采用后再生效。

### 4.4 建议的暂缓、更新与退出

用户暂缓建议时，可以选择到某个时间再看、相关条件变化后再看，或仅保留由自己找回。选择应与这项工作有关，不能要求用户先配置复杂规则。到时或条件变化后，先检查建议是否仍有价值、是否已处理，再决定呈现；重新出现不等于自动获得执行授权。

用户表示“本次不需要”“已经处理”“不再跟进”时，对应建议有清楚去处与可找回记录。后续出现真正不同的事实可以形成新的判断，但需说明与此前有何变化，不能只换措辞把已拒绝的内容重新推送。被较新建议取代、失效或无须处理的内容及时退出待办视图，同时保留必要的原始过程。

在注意力或运行预算有限时，应合并同类内容、呈现当下最有价值的少数事项，并让其余内容可查；不能把所有未响应建议不断累计成用户的工作欠账。因系统预算暂缓的事项需要适时重新判断，不能无期限消失，也不能每次检查都催促用户。

## 5 由场景 Skill 驱动个人助理

### 5.1 Skill 承担什么

主动理解、机会判断、领域处理、结果检查、交付和持续跟进中的可调整做法，必须由配置给助理的 Skill 表达并真正影响行为。Skill 不能只是固定功能的一个展示名称或附加提示。用户改变做法时，不应必须修改产品代码或只能调整一段笼统的“助手人格”。

Skill 是个人助理执行工作的文字做法，个人助理依据它发现并调用当前可用的数据工具、业务动作和专业能力。不是 Skill 文本自行执行，也不是每配置一份 Skill 就创建一个独立运行的助理。场景需要的多个做法可以在同一项工作中组合使用，继续共享原资料、结果、范围和用户决定。

Skill 可以承担一项具体做法，也可以描述一段完整工作。几份 Skill 可以配合处理同一事项，不要求把每个阶段拆成独立 Skill，也不要求所有工作走固定阶段。

每份 Skill 应以用户能读懂的方式说明：用途与适用条件、什么时候不适用、需要哪些背景和材料、怎样处理、产出是什么、质量如何判断、何时继续以及何时停止。使用要求应足以判断它能否帮助当前工作，避免只有名称和一句宣传介绍。

Skill 是做法，不是权限或事实来源。正文可以说明需要的能力和适用边界，不能替用户批准操作、扩大观察范围、改变业务完成状态或让不支持的能力变得可用。

| 由谁承担 | 产品要求 |
| --- | --- |
| 场景 Skill | 说明何时适用、关注什么、怎样查询和取舍材料、如何判断价值与优先级、怎样推进和检查、报告怎样组织、给用户哪些下一步及何时继续或结束 |
| 个人助理 | 读取本次有效 Skill，结合实际工作调用工具，串起判断、准备、执行和等待，保留上下文并与用户沟通；不能只在交付文案里附一个 Skill 名称 |
| 平台与 Prologue 通用能力 | 提供工具发现、完整记录与数据访问、时间与条件触发、持续执行、权限和预算、取消与恢复、结果与用量记录，以及统一交互能力 |
| 业务插件与专业工具 | 提供自己拥有的内容、状态、真实业务操作和结果证据，保证业务约束；支持哪些读取、修改和定位能力如实可查 |
| 首页、侧边栏与内容联动 | 统一呈现助理产出的结论、引用、选择和处理状态，执行准确的打开、定位、高亮及反馈；不由每份 Skill 各造一套界面 |

在既有能力范围内，新增场景、改变报告侧重点、调整机会判断或改变跟进做法，应通过新增、配置或修改 Skill 完成，不要求修改平台源码、重新发布应用或新建场景专属插件。只有实际缺少可复用的数据、业务动作或交互能力时，才需要补齐对应通用能力；补齐后可由不同 Skill 使用。

数据工具可以提供检索、筛选、排序、统计、对比和专业处理，但不能把整项场景的取材、判断、建议与跟进全部预定好，再由 Skill 仅改标题或调用一个黑盒。已有专业工具可以复用，Skill 仍应实际决定本次目标、输入材料、使用方式、结果要求与后续处理。

Skill 可以描述关注的变化、检查节奏和继续条件；平台兑现已生效的时间或条件约定，并执行用户设置的打扰、权限与用量边界。改变 Skill 中的关注建议不自动扩大持续委托，运行控制也不能把“何时值得行动”重新固化为每个场景一套判断。

### 5.2 配置与选择

用户在一个可到达的配置入口管理助理使用的 Skill：查看、启用、停用、创建、导入、复制、修改、恢复和移除。基础操作不要求理解 Agent、模型协议或内部标识。

用户能看见 Skill 的来源、用途、有效版本、适用范围、自动使用状态和必要依赖，并能从实际工作返回查看它为什么被使用、产生了什么结果。导入或查看一份 Skill 不自动启用，也不执行其中要求。

配置需支持个人默认与项目差异。用户能看懂一份 Skill 适用于哪里，以及当前工作实际使用的是哪份做法；本次明确指示优先于一般方法，不把本次选择自动推广到所有工作。

Skill 正文表达做法，范围、周期、通知和用量等配置表达该做法本次或长期使用的条件，两者应能一起查看。同一个可调整项按本次明确要求、项目显式覆盖、个人设置、提供方默认的顺序确定，并展示实际取值和来源；明确设置优先于正文中的默认建议，未覆盖的项继续继承，不能按两个互相矛盾的值各运行一次。无法消解的方法冲突按本节要求处理。编辑器、对话和快捷设置修改的是同一份有效做法或配置，不能在不同入口各存一套；任何优先级都不能扩大权限、解除停用或覆盖平台约束。

2026-10-27 用户确定：启用 Skill 后默认允许 AI 在适用条件下自动查找和选用，用户本次点名优先，也可将 Skill 改为“仅手动点名”。已有仅手动选择不因升级或重新启用被重置；未启用的 Skill 不自动参与。自动选用不要求逐次确认选用本身，实际操作权限继续由当前有效授权决定。技能包和运行策略使用同一规则，见 [skill-packs](../skill-packs/spec.md) 与 [Skill 策略 §3.1](../prologue-skill-strategy/spec.md)。

助理能根据工作与实际可用能力选择合适的已启用 Skill，按需组合，或遵循用户点名的 Skill。不得默认把全部 Skill 同时套入每次工作。

选用依据来自当前工作、Skill 的用途与适用说明、用户设置和真实能力。通用发现可以筛掉未启用、越界或不满足运行条件的候选；场景的关注与选用做法仍应能通过 Skill 和配置调整，不能只识别预置名称或固定对应某个插件。新启用的 Skill 在已有能力足够时应能参与下一次适用判断，无需另开发专属触发或路由；不要求每次完整阅读所有 Skill 或重新采集历史。

用户点名的 Skill 不可用、不适用或缺必要能力时，应说明影响和可选处理；不能悄悄换一份仍显示原名称。自动选用也应能解释选择依据，用户可以换做法或限定本次使用范围。

没有适用且获准使用的 Skill 时，相应场景的新判断与推进应明确显示缺口，不暗中转到写死的默认流程。用户仍能查看已有结果、查询确定事实和使用停止等通用操作；其他具备有效 Skill 与授权的工作继续。用户全部停用后，不再产生依赖这些 Skill 的主动结论或新报告，首页和侧边栏仍可显示事实状态及带时间的历史内容。

多个 Skill 提出相同工作时合并处理；方法冲突时以用户当前明确要求、有效工作约定和更具体的适用规则为依据。无法据此解决且影响结果时才请求决定，不能让多个 Skill 反复竞争、互相推翻或重复执行。

### 5.3 初始场景 Skill 与扩展

交付应包含一组已经能使用的场景 Skill 及清楚的个人助理默认配置，用户首次启用时即可选用，不要求从空白编辑器开始。不能仅交付一个“支持 Skill”的框架，把完成日报、跟进或材料整理的做法留给用户自己编写。初始 Skill 的正文、用途、实际工具依赖、适用范围和试用结果都应可查看。

| 初始 Skill 需要覆盖的工作 | 助理按 Skill 取用的材料 | 必须产生的用户结果 |
| --- | --- | --- |
| 近期工作梳理与接续 | 近期行为、已有委托、相关内容、状态、工作依赖及用户纠正 | 有依据的工作理解、材料关联、当前重点和多项工作之间可以接续的下一步取舍 |
| 周期报告与复盘 | 指定周期的实际变化、交付、决定、等待和后续反馈 | 日、周、月等回顾及可选择的后续操作；周期和关注点可配置 |
| 关键事项提前准备 | 已有约定、期限、议题、当前材料与缺口 | 可审阅的资料整理、候选内容或待决定问题 |
| 阻塞与依赖跟进 | 原工作等待条件、新资料或回复、依赖状态及有效授权 | 条件变化后的正确接续，必要时请求明确决定；无变化时保持安静 |
| 跨插件整理与衔接 | 多个插件中关联的对象、来源、现状及可用动作 | 连贯的材料整理、内容转化或已授权后续处理，保留真实归属 |
| 结果核对与偏差修正 | 当前要求、候选或已交付结果、来源与业务状态 | 具体缺口、修改候选和可核对的完成结论 |
| 相关机会发现 | 当前重点、已获准的新内容、变化及实际可用能力 | 有具体依据和预期价值的尝试建议，不制造无关工作 |

这些是初始 Skill 集合需要覆盖的职责，不规定固定文件数量、名称或统一执行顺序。相关的日报、周报与月报可以共享可配置做法，也允许用户拆成不同 Skill；重点在于用户修改做法后实际行为改变。工作理解、机会选择和结果检查可作为组合中共用的做法，不要求每次都运行全部 Skill。

用户可以只启用自己需要的部分，并逐步加入领域 Skill。插件和用户导入的 Skill 在具备实际能力与授权时能够参与同一主动协助过程，不因来源不同形成另一套助手入口。

新增支持平台既有能力的 Skill，不应要求用户等待助理针对某个插件专门适配。能力或依赖缺失时，配置与工作中都能看到缺口，不能保持“已启用、可自动工作”的假象。

用户不必编排完整流程图，也不必提前选定所有专业角色，才能让 Skill 配合工作。

### 5.4 系统数据工具要让 Skill 能完成真实工作

个人助理默认根据当前任务和执行阶段，从统一目录自行查找、选择并调用已授权的系统、插件与已接入 MCP 工具，理解用途、适用范围、所需条件及可能产生的实际效果；工具说明与参数按需加载，Skill 所需能力也走同一目录。用户可以点名或限制，点名优先且限制约束搜索与实际调用；点名对象不可用时说明影响，不静默替换明确指定的做法。发现、阅读或配置 Skill 本身不调用业务写入，发现工具不扩大权限；运行时使用当前有效版本与授权，旧目录或已加载说明不能绕过停用、撤权和限制。完整选用规则归 [Tool 策略](../prologue-tool-strategy/spec.md) §3.1（2026-10-27 用户已定，尚未实施）。

| 通用工具需要支持的能力 | Skill 应能据此完成的判断或处理 |
| --- | --- |
| 按范围与时间查工作活动 | 按个人、项目、插件、对象、工作和时间读取行为、执行与反馈，区分操作者、真实工作与试用、发生时间与记录时间 |
| 检索并读取内容及历史版本 | 先找到相关材料，再读取所需正文、附件、版本或变化；知道是否完整、是否仍可用，不只拿到一段无法核对的摘要 |
| 读取业务状态与跨插件关系 | 核对目标、期限、等待条件、来源、依赖、已产生结果和当前有效状态，区分当前事实与历史情况 |
| 比较、统计与检查覆盖 | 获得明确口径的差异、计数、时间范围和记录缺口，为报告与判断提供事实；分批读取、上限或缺失不能伪装成全部内容 |
| 查看和维护助理工作理解 | 读取已有建议、委托、等待与结果；保留有依据的理解、关联、候选和用户纠正，使后续 Skill 能接续原工作；不改写插件拥有的正式事实 |
| 读取和维护允许保存的偏好 | 取得当前有效的范围、关注、用户明确偏好及其来源；在已有授权内保留纠正或提出修改草案，不把单次推断存成长期设置 |
| 安排和调整后续跟进 | 在有效委托内设置、查看、修改和取消时间或条件检查，等待回答或结果，并取得是否真正生效的反馈；缺少可观察条件时说明限制 |
| 使用实际业务与交付能力 | 在有效授权内准备、保存、修改或交付内容，取得真实效果与失败状态；仅能读取时不能伪装成已写回 |
| 关联内容与提交后续选择 | 将结论关联到真实对象和可定位位置，把可行下一步交给通用交互呈现，并将用户的选择带回原工作 |

同一份工作记录和业务事实应能被不同 Skill 复用。新 Skill 不需要先为自己重新采集一套数据；也不应为了读懂另一插件而要求用户复制正文或开发专用数据管道。工具返回的信息要保留来源、对象、版本、时间与覆盖边界，让 Skill 能判断依据是否足够并继续取数。

助理可以按 Skill 需要逐步检索、读取、比较和补充材料，不把所有插件全文固定塞进每次工作。数据不足时可以调整查询或指出缺口；没有工具或没有授权时如实说明，不能依据 Skill 中对能力的描述捏造数据、调用结果或执行成功。

系统数据工具提供事实与可复用处理能力，Skill 负责场景中怎样取用和解释这些事实。真实业务状态和写入仍由其所有者提供的能力处理，用户编辑 Skill 不能改写事实来源或绕过业务约束。

这些能力沿用平台统一的动作发现、调用与授权。工具需区分查询、保存候选、更新助理理解、安排跟进和业务写入的实际效果；即使不改插件正文，也不能把保存偏好或建立长期跟进当成无效果读取。场景 Skill 可以决定要安排什么、等待什么，平台负责让已经生效的安排在停用、撤权、取消和重启后仍遵守控制要求。不能只让助理在文字中承诺“之后再看”，却没有可查询的有效安排。

### 5.5 Skill 结果进入同一套交互

场景 Skill 应指导助理交付有明确对象的结论、依据、候选结果与可行选择，并说明哪些需要用户决定、哪些正在执行。首页和侧边栏用通用交互展示这些内容。用户提交需要分析或推进的选择后，助理带着对应工作、材料和选择使用当前适用 Skill；查看详情、打开来源、定位、返回，以及暂停、停止等通用操作直接兑现，不为这些操作重新调用模型或运行场景 Skill。明确提交继续或恢复可以接续原执行，不能与查看混同。

不同 Skill 都能使用相同的卡片、报告查看、参数补充、变更对照、进度、来源定位与高亮能力。Skill 决定“建议用户看哪份内容、比较什么、有哪些可选下一步”，平台与插件保证“打开哪个真实对象、标记哪里、点击产生什么效果”准确一致。增加一个使用现有表现形式的场景 Skill，不应再开发一套页面或为该 Skill 专门接一次定位逻辑。

Skill 可以改变报告结构、侧重点、选项内容和处理顺序，但不自行改变点击含义、执行状态、真实授权或通用返回行为。卡片的对象和位置必须来自可核对的工具结果；不能用模型生成的相似名称或虚构引用伪装真实关联。不支持的交互应说明缺口，已有的基础查看与处理仍可使用。

### 5.6 各工作环节的责任核对

下表用于约束全文的同一分工，不要求新增固定执行阶段或为每一行单独创建 Skill。

| 工作环节 | 应由 Skill 指导的做法 | 系统工具与通用能力负责 |
| --- | --- | --- |
| 工作理解与材料组织（§2–3） | 关联哪些材料、怎样解释变化、怎样纠正理解和保留适用偏好 | 提供事实与版本，保存可区分的理解和纠正，执行数据使用范围 |
| 主动选择与时间安排（§4、§13） | 何时值得检查、先做什么、何时提醒及如何调整跟进 | 提供变化与时间信号，兑现已生效安排，执行打扰和资源边界 |
| 准备、跨插件推进与接续（§7–8） | 如何取材、分步骤处理、使用专业能力、解除阻塞和准备交付 | 执行真实动作、保存结果与进度，维护权限、业务约束和恢复 |
| 质量检查与结束（§7） | 怎样核对是否满足工作要求、如何改进及提出什么完成结论 | 提供可验证的业务结果，兑现用户停止和已确认结束，避免重复效果 |
| 报告与首页重点（§9、§11） | 材料取舍、分析口径、总结结构、重点排序及下一周期建议 | 提供时间区间、确定统计、版本留存、展示和事实状态 |
| 选择项与内容关联（§10–12） | 提出哪些有意义的路径、推荐理由、处理对象与依据 | 校验真实能力和对象，呈现及提交选项，准确定位高亮与返回 |
| 复盘与做法改进（§6、§14） | 分析反馈和效果、提出 Skill 修改草案；可配置的评测分析按独立方法进行 | 提供试用、比较和隔离评测依据，保留版本与采用决定，防止改写历史评分 |

表中的可调整做法不应散落在场景专属后台、隐藏的固定提示、按钮回调或首页排序规则中。时间区间计算、可靠统计、现有业务算法、权限、记录、停止和定位则必须由相应工具或平台保证；也不应为了名义上的 Skill 驱动让模型重新计算或裁决这些确定事实。

### 5.7 工作记忆初始化与每日例程

助理需要一套可重复的“认识我的工作”例程，而不是每次从零猜人名、缩写和项目代号。

**初始化（首次或用户要求时）**：用用户真实的待办、项目、最近工作做访谈，逐条解码人名/昵称、缩写、项目代号、内部术语；可以按置信度分组请用户确认，不一次问几十个问题。结果分成两层：

- **热缓存**：约 50–80 行，放最常用的人、术语、活跃项目、明确偏好；每轮可用，保持精简。
- **冷记忆**：完整术语表、人物/项目/背景档案；需要时再查。

热缓存与冷记忆是**材料/视图**，不是第二套记忆事实；写入仍走现有记忆的候选 + 用户确认，删除/停用仍由记忆设置管理。用户明确说“记住”时按记忆规则办；一次性的选择不自动变成长期偏好。

**每日/每周更新**：同步外部任务、挑过期/长期未动/没有上下文的项、补记忆缺口；`--comprehensive` 再扫最近的聊天/邮件/日历/文档，找漏掉的承诺。默认安静：没有实质变化不打扰；提醒遵守免打扰、合并与停止规则。Todo 仍是任务事实，工作简报仍是综合结果；例程不建第二套任务或记忆库。

### 5.8 前门路由

角色包/场景包多起来之后，需要一个“前门”Skill：它不自己干活，读当前工作、项目、材料和可用技能，匹配**单一最佳**技能，说明为什么；对已启用且允许自动选用的 Skill 沿已有授权触发，不再为选用本身逐次确认。仅手动的 Skill 要有用户本次点名，用户点名优先于自动推荐。没有匹配时说明缺什么（没有技能包、没启用、缺工具/授权），不偷偷退到写死的默认流程。前门只做选择与解释，不授予权限、不扩大观察范围；需要新的决定或实际操作批准时沿原规则处理，用户仍可点名其他技能或自己操作。

### 5.9 从一次对话生成 Skill

用户经常重复做一件事，但不会写 Skill。助理应能从“看我做一遍”或“听我描述”中提取做法：

1. 优先用刚刚发生过的真实过程（用户做过的步骤、纠正、拒绝）作为规格；没有就用具体的一次经历访谈。
2. 区分固定步骤、可变参数、需要判断的点；会发送/花费/发布/删除的步骤说明所需操作授权，沿 §7.1 的有效权限方式执行；未获授权或仍需用户决定时才等待，不把已授权步骤写成固定的逐次批准门。
3. 写成 `SKILL.md`：名称、用途、适用/不适用、步骤、fallback、不编数字；判断点写清何时问人。
4. 用用户已知答案的真实案例回放，对照手工结果；不一致就改，不让用户接受“差不多”。
5. 注册到技能目录/前门，按需排期；不自动启用、不自动扩大权限、不自动创建业务事实。

生成的是技能包内容，不是运行时插件；分发、版本与启用见 [skill-packs](../skill-packs/spec.md)。

### 5.10 跨源搜索规划

助理的搜索不应只把一句话丢给一个来源。对“找那份文档/那次决定/那段讨论”这类问题：

1. 识别意图、实体、时间、来源线索与过滤条件。
2. 按当前可用来源拆成子查询，使用各来源自己的搜索语法；不假设所有来源同一套字段。
3. 并行执行；一个来源失败不阻塞其他来源。
4. 去重、按相关度/新鲜度/权威性排序；同一事实多来源时优先更权威/更完整的版本。
5. 返回来源、时间、版本与覆盖缺口；不把摘要当原文，不把部分结果说成全部。

搜索仍走现有 `search.query` 与权限；规划层是 Skill + 查询工具，不新建索引或事实源。

### 5.11 与技能包、自动化建议的关系

本节的记忆、路由、生成与搜索规划都消费 [skill-packs](../skill-packs/spec.md) 的技能目录；项目自动化建议是独立入口，见 [automation-recommender](../automation-recommender/spec.md)。三者都不新增第二套权限、任务、记忆或搜索结果。

## 6 用户修改 Skill 的完整体验

用户可以直接编辑 Skill 正文，也可以通过对话说明希望改变的做法。对话修改应给出可审阅的改动，说明保留什么、改变什么、适用范围和生效时机；用户能继续调整、采用或放弃。

草稿与正在生效的 Skill 必须可区分。未保存或未采用的修改不改变实际行为；取消编辑保留原有效版本。用户能够比较变化、查看修改历史、恢复默认做法或回到自己此前的版本。

Skill 修改应在下一次主动判断或新执行中使用新版本，不能悄悄改写正在进行的一次执行。同一轮正在运行的处理继续使用开始时可查的版本，本轮内的工具返回不构成切换版本；进入后续独立推进、跨轮等待后的接续或失败后的重新规划时，重新核对当前有效做法和已有计划。仅重试同一业务提交不等于重新规划，应先查明是否已生效。新方法与旧候选或待执行步骤有实质冲突时，说明影响并更新或暂停受影响部分，不能把旧结论与新方法混成一次无说明的执行。原目标、已完成结果和有效授权继续保留，版本固定不影响停止与撤权立即生效。

停用、移除、撤销观察或执行许可是立即生效的控制：停止新的使用和不再获准的动作。依赖该 Skill 的待执行建议及后续步骤应取消或重新判断；已经发生的效果如实保留并说明，不能显示成“什么都没做”。

已保存报告与卡片可以继续查看，但停用后提交其中依赖原 Skill 或原委托的旧操作，必须重新核对做法、委托、目标版本与当前能力。查看历史不恢复 Skill，点击旧按钮也不隐含重新启用或重新授权；复制已有内容等独立通用操作仍可使用。可用其他已启用 Skill 接续时说明做法变化；未解决的影响只阻塞依赖部分，不以静默替换掩盖缺口。

Skill 更新扩大材料需求、动作范围或成本时，不能自动扩大原授权。用户能看到新增要求及未满足部分，仍可使用不依赖新增许可的能力。

用户能够用实际工作内容预览或试用修改后的 Skill，了解会得出什么理解、提出什么下一步、准备什么结果，以及与原做法的差异。预览默认不改变真实业务内容、不对外执行；有意执行真实操作时，应清楚显示目标和已有授权范围。

试用使用的材料范围、模型与用量遵循当前设置。用户可以使用指定材料进行局部试用，不能为了验证一份 Skill 自动启动整项持续委托或全部依赖工作。

内容不完整、相互矛盾或所需能力不可用时，编辑和试用应给出具体问题，并保留用户正文。不能因保存成功宣称 Skill 已能完成工作，也不能默默替用户删改重要要求。

内置或插件提供的 Skill 更新时保留用户修改，展示与新默认的差异，让用户决定是否采用。助理可以根据反馈提出 Skill 改进，但不得在用户未采用时自改有效做法；既有明确授权的规则调整按其范围执行。

## 7 从发现到实际推进

### 7.1 行动范围与授权

用户能分别设置助理可以观察什么、可以主动准备什么、可以继续执行什么，以及哪些情况需要先征求决定。持续委托应写清目标、作用范围、允许动作、终止条件和必要的时间或用量边界，并可以随时查看与调整。

助理应从已有表达与材料中形成可理解的工作约定，说明预期产出、达到什么条件算完成，以及哪些部分需要用户决定；已有信息足够时直接使用，不要求用户额外填写任务表。执行期间改变目标、重要材料或完成条件时，应说明对已完成部分、剩余工作与原授权的影响。

没有具体执行委托时，助理可以在已获准的范围内准备分析与候选结果，提出可直接接续的下一步。行为推断不能替代执行委托，采纳一项建议也不自动授权无关操作。

已有有效同范围授权时，助理应继续必要步骤，不能每次读取、整理或执行都重复要求批准。确实需要新的决定时，应先完成已授权的准备工作，把具体可审阅结果交给用户。

**权限选项（2026-10-27 用户已定，待实现验证）**：助理使用工具与外部服务（含 MCP）时，提供以下三种方式；沿用平台同一授权与执行链，服务连接页、任务和助理入口使用同一有效选择。

| 选项 | 用户可观察的行为 |
| --- | --- |
| 只读协助 | 在已授权范围内查询、分析和准备结果，不修改业务内容，不产生发送、发布等对外业务效果 |
| 修改前确认 | 已授权读取直接进行；修改业务内容或对外操作前，展示具体结果/目标并确认 |
| 授权内自动执行 | 一次明确工作范围和允许操作，AI 在其中连续完成；已明确包含的发送、发布、删除等操作不逐次重复确认 |

连续工作推荐“授权内自动执行”，但推荐不等于已授予权限，也不覆盖用户已有的只读或逐次确认选择。授权默认仅覆盖本次工作；跨轮、等待、切换页面和重启接续不另算一项工作，仍在原有效范围内复用。工作结束、取消或授权到期后，不将这份许可带给新的工作；长期委托可由用户明确保存为持续授权，写清适用目标、范围、允许操作及结束条件，不能默认扩成整个账号或所有项目。

AI 根据用户任务和已有授权提出必要范围，用户可查看、调整后采用，不必逐个配置工具。已有委托和选择已足以明确有效授权时直接复用，不另加一次必经设置/批准；缺许可时只请求新增范围。界面用账号、资料/目标、能做的事和有效范围解释授权；本次工作与持续授权可区分，用户随时可以收窄、撤销或改回确认方式。调整后立即约束尚未派出和后续操作，不能因本轮冻结配置、已加载工具或旧待批请求继续放行；已发生或无法撤回的外部效果如实显示，未知结果先核对，不因切换模式而重做。

只有超出授权范围、授权失效或出现新的必要决定时才请求用户介入，只暂停依赖部分。权限由可信执行边界根据实际调用、对象和当前授予核对，模型、Skill 和服务声明都不能自行授予；只读性质须有可信能力依据，不能仅凭第三方自称只读。服务账号权限、项目/对象边界及平台不可覆盖的拒绝继续生效，自动检查不等于必须重复弹窗。此项确定产品行为，不表示本轮已修改运行策略，也不替代各入口的实现与拒绝测试。

主动准备和持续执行可以依据已有效的委托自动发生，卡片用于观察、干预和发起新的操作。第 10 节对“查看”和“执行按钮”的区分，不得被解释为每一步都要等用户点击；同样，用户仅查看一张新卡片也不能被解释为扩大了委托。

对外发送、发布、购买、删除等操作仍需对应的有效操作授权；账号登录或选择自动执行不独自授予这些权限。已明确包含在本次工作或持续授权中的操作，按所选方式复用，不因是外部操作而一律再问。Skill 的写法和模型的判断均不能跳过授权核对或用户保留的逐次确认要求。

### 7.2 完整结果与业务连续性

助理应使用平台真实可用的能力推进工作，可以整理材料、分析问题、准备或修改内容、更新已受托事项、委托专业处理，并核对产物质量。不能止于建议用户自行打开几个插件再重复描述。

上述取材、处理顺序、专业能力选择、结果检查和后续安排，应能在实际生效的 Skill 中找到做法依据，并由助理调用相应工具完成。已有工作流或专业执行能力可以作为步骤复用；使用它的目的、输入、结果要求和后续处理仍由有效做法与当前委托决定，不能把整项场景预设为不可调整的固定流程。

每次推进都应交代已完成什么、结果在哪里、哪些部分仍待决定或等待。准备完成、用户批准、开始执行、执行成功和业务完成需要分别呈现；执行失败或结果未知不能包装成完成。

多步骤工作有可理解的进度，已完成部分可查看和保留。用户可以继续、补充要求、改变优先级、接管、暂停或停止，不必另建一项工作。

2026-10-27 用户确定多 Skill 配合时的失败恢复规则：保留已完成结果，只暂停依赖失败步骤的部分；授权有效且互不依赖的工作继续。呈现已完成、失败、等待依赖与继续执行的实际情况，不把局部失败当成全部丢失，也不把部分成功报成工作已完成。修复、重试或重启后依据原调用记录和业务事实接续；未知效果先核对，不重复已经生效的操作，不覆盖人工后续修改。停止、停用、撤权仍按当前范围生效，运行与验收边界见 [Skill 策略 §3.4](../prologue-skill-strategy/spec.md)。

用户在插件里接手后，助理与用户围绕同一份业务内容继续。助理能根据用户的修改调整后续处理；实际冲突必须暴露，不能覆盖当前内容或把旧候选改到另一个对象上。

工作成果应能打开、检查、采用、修改和复用，并留在适合它的插件或成果位置。用于判断的临时摘要、过程材料和未采用候选，不应无条件变成正式文档、Goal、待办或成果库条目。

需要审阅或用户选择先看稿时，应能对照原内容查看具体增删、修改与影响。可独立的修改允许逐项采用、调整或拒绝；必须一起成立的变化说明依赖，不能把不完整组合显示为可用结果。提交前重新核对当前对象版本，保留用户或其他工作的并发修改；未采用部分保持候选状态，已经有效授权的自动处理不因此额外增加审阅关卡。

### 7.3 判断和执行的质量

完成依据必须对应真实结果，而非模型自述。检查应包括是否解决原问题、是否使用可靠且适用的材料、是否保留用户修改、是否满足当前要求，以及后续确实能使用。

领域质量标准、检查方法和补救取舍由适用 Skill 表达；系统工具提供内容、差异、业务状态与确定性检查的真实结果。Skill 作出的质量结论仍需依据，不能仅凭工具调用成功宣称达标；共同业务约束和用户已确认的完成条件也不能被 Skill 调低。结束委托应结合这些证据兑现第 7.4 节的要求。

低质量、空结果或部分成功应如实说明。允许在当前授权和预算内进行有界改进；无法改善时保留可用部分与实际缺口，不无限自我检查或反复启动同一工作。

### 7.4 等待、接管与结束

等待状态应说清在等什么、由用户还是助理或外部来源推进下一步、什么变化可以继续，以及是否有约定检查时间或失效条件。没有可观察的外部结果时，允许用户直接补充或说明已处理；不能假装一直能够自动得知。必要决定只阻塞依赖它的部分，答案到达后回到正确步骤，不重新做完已经完成的部分。

外部服务短暂断线时，在同一账号、地址和仍有效授权下默认自动重连，恢复后按最新要求接续原工作（2026-10-27 用户已定）。过程在原工作中可见，无须用户重复点检查或批准接续；反复失败、需重新登录或权限变化时才合并必要提醒，遵守通知设置。重试有界，主动断开/停用、撤权、取消或已结束委托不自动恢复；独立且获准的部分继续。连接恢复不代表原业务请求成功，未知写入先核对，已发生效果不重复，无法确认时只等待所需决定。连接与恢复合同归 [服务接入 §7](../assistant-service-connections/spec.md#7-失败与恢复规则)，沿原 owner 和任务机制实现。

用户接管后，应能选择让助理继续准备不冲突的部分，或暂停对应后续动作；已有明确要求时照办。一次性工作满足完成条件、被取消或明确放弃后，关联的提醒、待执行步骤和旧决定请求一并结清。新的相关变化可以提出新的可审阅建议，但不能悄悄复活已结束委托。

周期性报告和持续观察需要区分“本轮完成”和“长期委托结束”，让用户可以停止一轮或结束整个约定。项目被归档、删除或移出授权范围后，相关主动任务和提示应据其实际状态停止或失效；恢复项目或连接，不自动恢复此前已经结束的委托。

## 8 Prologue 和平台能力的产品要求

Prologue 与平台能力应成为这一集合的真实支撑。以下是需要兑现的用户能力，不预设技术方案，也不将 SDK 文档中的能力直接视为 Molis Work 已可用。

| 能力 | 主动工作中的用户结果 |
| --- | --- |
| Skill 发现与使用 | 助理知道当前可以使用哪些做法，能按工作需要真实选用；用户指定与修改实际影响工作 |
| 通用系统数据工具 | 各场景 Skill 都能让助理读取同一套工作活动、跨插件内容、版本、状态和结果证据；新增做法不依赖场景专用取数路径 |
| 会话与持续工作 | 同一工作跨多次主动推进保持目标、资料、决定和结果的连续性，不依赖用户重复发消息 |
| 规划与任务板 | 复杂工作有可理解的步骤、依赖、等待和进度；简单工作保持直接，不要求用户维护另一份任务清单 |
| 角色与协作 | 合适的专业角色或子任务能承担处理；助理汇总结果、暴露必要决定，用户不必在多个对话间传话 |
| 等待、到时检查与消息交付 | 能等待用户回答、插件结果、其他角色结果或约定条件；条件满足后接续原工作，未满足时不持续占用用户注意力 |
| 上下文与记忆 | 长工作按用户、任务阶段、执行状态和运行条件动态取材、压缩与重读；保留有效约定、关键决定、已完成效果和未完成事项，不以旧摘要覆盖新事实或人工修改 |
| 工具、动作、MCP 与资料读取 | 按任务和执行阶段从统一目录自行查找、选择并调用已授权工具，说明按需加载；用户可点名或限制，Skill 走同一目录，发现不扩权，缺能力或授权时清楚说明 |
| 多模态与专业工作环境 | Skill 所需的图片、长文、文件、浏览器或桌面操作，在平台实际支持且获准时可以使用；不足时清楚说明 |
| 控制、检查点与恢复 | 用户能暂停、继续和停止；工作中断后保留已完成部分，恢复时知道从哪里接续及哪些结果需核对 |
| 模型、用量与观测 | 与平台现有模型、凭据、预算和诊断设置一致，用户能知道近期花费、运行情况和失败原因 |
| 工作记录与效果评测 | 运行过程能关联平台行为、插件事实、实际呈现与后续反馈；足以比较不同 Skill、模型与产品版本带来的真实结果 |

周期报告应使用相同的 Skill、上下文、定时与恢复体验；首页、报告和对话中的操作应接到同一受托工作。Prologue 的运行记录与平台工作记录需要可相互定位，不能出现平台只知道“AI 成功”、AI 只知道“工具成功”，却无法确认用户最终拿到什么的断点。

运行平台负责让所配置 Skill 能被个人助理实际使用、调用工具并持续完成工作；不为日报、提前准备、阻塞跟进等场景分别建立一套助理运行体系。场景扩展应优先体现为新的 Skill 与用户配置，通用能力缺口才进入平台或插件的功能补齐。

使用专业角色、委托子任务或不同 Skill 时，原工作的资料边界、用户要求、停止指令与预算同样有效。委托不获得更大的权限，也不能变成用户需要分别监督的几套任务。

2026-10-27 用户确定长任务上下文采用“统一机制、动态适配，按真实长任务验证效果”。由 AI 按当前任务、Skill、用户和项目有效配置选择取材、保留、压缩与重读做法，并结合探索/执行/检查阶段、等待/失败/协作状态和实际模型窗口、用量限制调整；普通用户不必手动分配各类 token，可查看和纠正当前理解与重要取舍。本次明确要求优先，临时选择不自动固化为个人偏好；新增场景复用公共能力，不增加宿主场景分支。验证关注要求遗漏、旧事实误用、重复操作、人工修改保留及中断后接续，不只看压缩率或 token 节省。完整边界与验收归 [Context 策略](../prologue-context-strategy/spec.md)。

需选择并利用完成当前工作的相关能力，不为展示功能而启用所有运行方式。插件业务事实继续由原插件负责；执行情况依据真实运行和结果，助理承担跨插件的理解与协调。

用户能区分未配置、暂不可用、缺权限、运行失败和结果待核对。不能让同一能力在设置里显示可用，在实际工作中却无提示地退回普通文字建议。

插件可参与哪些环节需要分别可查：读取哪些内容与历史、能否发现变化、支持哪一级定位高亮、能够准备或执行什么，以及能提供何种结果证据。插件已安装不等于这些能力都具备；内置与外部插件遵循相同要求。缺少某项能力时保留其余有用部分并如实说明，不把只有链接跳转的插件标成已支持精确联动。

## 9 周期报告与工作复盘

周期报告由个人助理按所配置的场景 Skill 查询系统数据、核对插件内容并组织结果。下列要求约束用户可以得到什么及结果质量，报告的取材、重点、判断与表达由 Skill 决定。平台提供时间范围、事实统计、定时运行、结果留存和统一展示能力，不将日报、周报、月报的完整业务流程分别固定在代码中。

### 9.1 周期、范围与生成

用户可以让助理整理日报、周报、月报、阶段报告和自定义时间范围报告，也能查看最近若干小时或若干天的滚动回顾。个人范围可汇总已获准的多个项目；项目报告只覆盖该项目及有明确联系、允许引用的材料。切换范围不能沿用上一个范围的结论或操作对象。

日、周、月的起止按用户时区及周起始日计算。报告明确显示覆盖起止、范围、资料截止时刻和生成时间，区分“本周期进行中”与“周期已结束”。比较前一周期时说明比较范围，不把半周与完整一周当成同等长度。

用户能按需生成、约定周期自动准备、暂停某类报告，或只在有值得回顾的变化时生成。配置包括关注范围、报告 Skill、关注主题、详略、生成时机及呈现位置。默认提供可用做法，用户不必先设计模板；改变配置不擅自补生成全部历史报告。

2026-10-27 用户确定：自动报告的周期与生成时间在 Onboarding 中由用户设置，之后可在设置中修改、暂停或关闭。引导预填已有有效值并显示适用时区，两处读写同一份配置，沿原调度能力生效；不另存一份引导专用配置或重复建立定时任务。修改后后续触发使用新周期和时间，重进与重启后保持一致，原安排不再额外触发。跳过或未开启自动报告时仍可按需生成，不因完成引导自动启动定期报告。

同一范围、周期和用途的报告有可接续的身份。重复触发、重启或重试不能产生多份相同报告或重复通知。没有活动与没有数据应分别呈现；内容很少时可以给简短结论，不用固定章节和空洞文字凑成完整篇幅。

### 9.2 报告应帮助用户判断什么

| 报告内容 | 质量要求 |
| --- | --- |
| 这一周期推进了什么 | 以实际结果、关键决定和业务状态变化组织内容，链接可用成果，区分已完成、部分完成、准备好待采用 |
| 与原计划或上次相比如何 | 有有效目标或前期基准时说明变化与偏差；没有基准时不编造完成比例、计划或效率结论 |
| 什么仍未解决 | 清楚交代阻塞、等待条件、未确认信息、责任归属和影响；用户承担的承诺与助理建议分开 |
| 哪些地方需要本人决定 | 只提炼真正改变后续工作的选择，给出依据、可选路径和取舍，关联具体内容 |
| 接下来值得做什么 | 给出数量克制、可以直接接续的行动选项，说明为何现在做；保留暂缓或调整的可能 |
| 有哪些可复用经验 | 从重复出现的事实总结有效方法、返工和可改进点，区分观察与原因推断，必要时准备 Skill 修改草案 |

初始报告 Skill 默认让日报侧重当天变化和接续、周报侧重工作结果与跨日取舍、月报或阶段报告侧重趋势与目标进展。这些是可修改的默认做法，周期名称不绑定固定内容模板或处理分支。用户可以通过 Skill 修改结构、关注点、表达风格和判断标准；系统不能只替换标题和时间范围，把同一份操作流水放大成不同粒度的报告。

本节表格是初始报告 Skill 应覆盖的价值和质量要求，不要求每份报告使用固定栏目。用户可以将同一周期改为成果回顾、阻塞分析或下一步准备等侧重点；变化应体现到取材、分析与可选操作，而不只是标题和措辞。来源与状态的真实性、授权边界不能被 Skill 改写；报告的归纳和解释仍须按第 7.3 节核对，不能因工具返回了真实数据就假设分析必然正确。

报告要覆盖用户手动完成与助理完成的工作，不能将全部成果归功于助理。操作数、消息数、调用数和停留时间可作为背景，不等同于工作成果、生产力或节省时间。确需估算时说明估算方法与不确定性。

重要结论可以展开查看来源及当时版本；报告标明数据覆盖缺口。多个来源描述同一成果只计一次，较早发生但本期才收到的变化说明时间归属。对某个插件失联或材料过期的报告，仍可呈现可靠部分，但不能作出依赖缺失信息的完整结论。

### 9.3 更新、编辑、保留与分享

进行中的报告可以刷新，并说明相对上次有什么实质变化。用户能够改写、删去或补充内容；再次生成时保留人工修改，发生冲突时提供可审阅差异。修改报告里的文字不自动改写源插件的事实或完成状态。

用户已保存、导出或分享的报告保留当时版本。新资料或迟到信息到达后，可提示生成修订版或补充，不悄悄改动原版本。报告既可作为临时回顾查看，也可明确保存为正式成果；定时准备不自动向成果库灌入大量文档。

报告能打开原资料、继续相关工作、复制、按平台实际支持的形式导出，以及在明确授权下分享。为特定接收者准备分享稿时可调整范围与措辞；能读取一份材料不表示可以把它发送给接收者。生成报告与发送报告是可分别配置的行为。

## 10 可点选的决定与后续操作

助理的报告、主动建议和项目首页都应提供可以直接使用的选择项。选择项必须与当前内容和工作阶段有关，既支持“选哪条路径”的真实决定，也支持准备、继续、检查结果、暂缓等工作操作；不能只放一组每次相同的“好 / 继续 / 不要”。

场景中的候选路径、推荐理由及需要补充的问题由助理按 Skill 和当时材料提出；查看、返回、停止等通用操作由平台提供。需要继续分析的选择回到原工作及当前有效 Skill；已经明确目标、参数和效果的业务动作可在校验后直接调用实际能力，无须为了点击按钮额外运行一遍场景。平台负责选项是否真实可用及提交效果，不按报告种类或 Skill 名称另写固定业务分支。

每组选项先说明正在决定什么，选择后会得到什么。互斥方案用单选，可同时完成的独立事项允许多选；存在先后依赖或不能同时采用的项应清楚表达。推荐项给出具体依据，不替用户自动提交。用户始终可以补充文字、修改选项、提出未列出的路径或暂不选择。

选中建议卡片、勾选候选路径和提交实际操作需要有不同表现。卡片主体用于查看详情与关联内容；用户从卡片发起新的操作时，通过“准备”“采用修改”“开始执行”等明确按钮提交。勾选多项后，在用户提交前可以继续调整。查看建议不构成新的委托或批准，按钮也不能因嵌在卡片里同时误触发另一项操作；已有委托的自主推进遵循第 7.1 节。

操作名表达具体对象和结果，例如准备哪一份内容、接续哪一项工作，而非要求用户猜测“执行”会做什么。点击前能够了解重要作用范围、实际写入或对外效果；需要必要参数时，就地补充或调整，不让用户重新复制整段上下文。

选项绑定生成时的工作、对象、内容版本和适用条件。来自旧报告的操作要核对当前事实；已处理、已过期、已撤权或条件变更时说明变化，并给出现时可行处理。不能因用户换了项目，就把旧选项作用到新项目。

提交实际操作后立即给出已接收、准备中、执行中、等待、完成、失败或结果待核对等真实状态，并返回结果和继续入口。重复点击、页面刷新或恢复不重复产生业务效果。多选部分成功时逐项说明，保留用户剩余选择。

用户做出的具体选择成为原工作的新输入，可以被后续 Skill 使用；“先不做”“本次不相关”“已处理”“以后按这个做”分别生效，作用期限和范围清楚。对选项的反馈应回到原工作理解、报告和首页，避免三个地方分别要求处理同一件事。

## 11 项目首页的总览体验

本节要求适用于 Work Brief 承接的综合首页。平台基础首页与 Work Brief 的关系、可选安装、公共组件、生成页面及恢复以 [Work Brief](../work-brief/spec.md)为准；未安装时平台展示可用插件及其公开内容／建议，不能伪装成已生成的主动结论。两种首页与原插件的打开、返回、分屏和标签行为共同遵守[工作台统一规则](../product-flow-governance/spec.md#46-分屏标签右栏与底栏统一2026-10-27-用户已定)。

项目首页承担“回来就知道进展、马上能接着做”的职责。首屏应能回答：当前最值得关注什么、最近实质推进了什么、哪里在等待或需要我决定、我能直接继续什么。用户不必打开助理聊天或逐个进入插件才能理解项目状况。

首页中的主动结论、重点建议和周期回顾由个人助理依照当前有效 Skill 产生，Work Brief 组织综合首页，平台提供通用挂载、公共组件与联动，事实状态来自原主人。用户替换做法后首页的关注内容能随之改变，不要求为不同工作领域开发不同版本的项目首页。

进入首页、展开侧边栏、切换周期或查看旧报告，默认读取已有结果与事实，不因一次查看重新运行场景。需要生成或更新时，按已生效的主动安排或用户明确提交进行，并区分历史内容、当前状态与新结果。Skill 产生的重点顺序可以更新，用户固定顺序、筛选和正在交互的位置由平台保护；不能用隐藏的固定业务排序持续覆盖 Skill 和用户取舍。

| 呈现层次 | 必须看见的内容与行为 |
| --- | --- |
| 项目与时间 | 项目身份、当前观察周期和更新时刻；提供今天、本周及其他周期入口，并能区分历史回顾与当前状态 |
| 重点结论 | 用短而具体的文字描述当前重点和实质变化，关联真实结果；没有足够依据时明确表示，不以虚构百分比填满页面 |
| 需要本人处理 | 优先呈现关键阻塞与必要决定，提供少量具体选项；没有待决定事项时不制造占位警报 |
| 可以接续的工作 | 展示已经准备好的结果、适合继续的下一步及正在运行或等待的工作，允许直接查看、继续或控制 |
| 周期回顾与证据 | 可展开日、周等报告、历史变化、来源和使用的 Skill，按需要进入原插件内容 |

整体应是一份有重点、可操作的工作概览，保留日期、当前工作、事项与手边内容的有效价值，并与 Work Brief 统一组织；原首页布局不作为必须保留的表达。结论和动作优先于活动流水，不把所有埋点、插件摘要和运行日志平铺成卡片墙。数量、颜色和状态标记服务于取舍，不用装饰性图表暗示不可证明的进度。

个人主动重点可以与项目目标相关，但尚未建立 Goal 的项目也要可用。首页报告、助理入口与源插件使用同一工作归属和实际状态：在任一处处理后，其他入口应反映结果；不产生另一套需要手工维护的首页待办。

用户能固定或调整关注事项、隐藏本次不重要的内容、纠正理解、切换周期和查看更新依据。普通背景更新不抢焦点、不重排正在点击的选项、不顶走阅读位置；重要变化用可理解的更新提示呈现。

从首页点击建议或报告条目时，应在侧边栏选中同一条内容，并按其明确关联打开主工作区中的插件和对象。首页摘要、侧边栏详情与原始内容形成连续路径；返回首页时保留原周期、位置及待处理选择，不再生成一份新的建议或工作。

首次使用、无活动、无可行动事项、历史信息不全、正在生成、部分数据不可用、离线和失败分别有准确表现。上次有效结果可继续查看，但明确其时间与陈旧状态；不能用加载失败显示“今天没有进展”。

常见桌面窗口及窄窗口都要保持重点和主要操作可见，内容可用键盘到达，状态不只靠颜色区分。项目切换不得短暂显示其他项目的私有结论和操作；进入历史报告后回到当前工作，应保持清楚的时间与对象归属。

## 12 侧边栏、内容联动与用户干预

### 12.1 侧边栏是持续处理的位置

工作台必须提供可常驻的助理侧边栏，默认位于主工作区右侧。用户查看或编辑插件内容时，可以同时看到主动建议、已准备结果、报告、进行中或等待中的工作及需要本人决定的事。保留底栏的统一导航与助理入口，侧边栏作为同一助理的工作视图，不要求每个插件再提供一套入口。

侧边栏支持展开、收起和在合理范围内调整宽度；用户打开后保持可用，直到主动收起或受窗口尺寸限制。收起不暂停工作、不丢失选择和草稿；新建议以克制的状态提示出现，不能自行撑开面板。展开时恢复原查看位置，并说明内容更新。

顶部清楚显示当前个人或项目范围、内容周期，以及正在对照的插件或对象。用户能够查看本页相关、本项目或个人范围的内容，找到未处理、待决定、已准备、暂缓和历史事项；不把所有条目无差别堆在一起。默认跟随当前项目，允许固定查看某项工作，固定状态与工作归属必须明显。

切换插件、项目或窗格时，新的查看范围可以改变，进行中的委托、正在编辑的文字和已选建议的归属不能悄悄改变。用户可以退出固定查看或主动切换工作；如果草稿因此需要换归属，要保留草稿并让用户清楚选择处理方式。

首页、侧边栏、报告及对话展示的是同一建议和工作。用户从任一入口进入，都能接续已有上下文；对卡片“说一句”时明确围绕哪项建议、哪个对象和哪份材料，不要求复制原文，也不因换入口新建重复工作。底栏与侧边栏的输入均需显示实际提交对象，不能出现两个入口各自理解“当前工作”的情况。

### 12.2 卡片内容与状态

每张建议卡片首先说明具体对象、建议或已准备的结果、为什么现在值得处理，以及当前状态。相关插件、内容名称、生成或更新时刻应可辨认；长依据、关联对象、使用的 Skill 及版本、作用范围和用量按需展开。卡片可以是紧凑条目，不要求给每条内容加大面积边框。

| 状态含义 | 必须保持的区别 |
| --- | --- |
| 已呈现、已查看 | 用户是否有机会看到、是否主动展开；查看不表示采纳或完成 |
| 当前选中 | 哪张卡片正在与主区内容对照；选中样式不表示工作正在执行 |
| 建议待处理、已暂缓、已处理、已失效 | 建议本身是否仍需要决定；失效原因与可行后续可查 |
| 工作准备中、执行中、等待、成功、部分成功、失败 | 受托工作的实际状态；与卡片是否新、是否已读分别呈现 |

用户能够继续、调整、暂缓、说明已处理、拒绝、停止跟进或修改相关 Skill。拒绝一次不自动停用整个 Skill；“以后不要这样”明确针对什么、多久生效。处理后卡片更新状态并保留结果与查看入口，不能瞬间消失导致用户不知道发生了什么；用户可再将其收起或移入历史。

建议的依据、范围或目标发生实质变化时，要更新有效性并说明差异。新版本不覆盖正在输入的内容或自动替换用户即将点击的按钮；已经失效的写入操作不能继续保持可执行。用户可以刷新理解或查看新建议，保留之前的处理记录。

### 12.3 点击建议后的联动路径

卡片主体点击的默认效果是：**选中卡片 → 在侧边栏展开详情 → 在主区打开或聚焦对应插件 → 显示关联对象 → 定位并高亮具体位置**。整个过程留在同一个工作台，侧边栏保留，用户能够同时看见建议和依据。该路径用于查看，不自动修改内容、启动新 Agent 执行、接受方案或提交写入。

| 关联情况 | 点击后的要求 |
| --- | --- |
| 已有明确对象与具体位置 | 打开正确对象，将相关内容带入可见区域，并标记具体段落、条目、单元格、节点或平台实际支持的内容区域 |
| 已有明确对象，未指向局部 | 打开该对象并突出其标题或对象区域，明确这是对象级关联，不能伪造一个精确选区 |
| 只针对某个插件的整体工作 | 打开对应插件的相关视图，标明插件级关联；不随意选一条内容充当依据 |
| 存在一个主要对象及若干依据 | 默认定位主要对象，在侧边栏列出其他关联供逐项查看，并说明各自作用 |
| 多个对象同等重要，尚无明确主对象 | 先展示可辨认的目标列表，由用户选择；不能仅因为列表顺序就擅自跳到第一条 |
| 没有可定位对象的综合建议 | 展开建议和事实依据，保留主区当前内容，不制造无关跳转或虚假高亮 |

已经打开正确对象时应复用已有视图；有多个窗格时，优先使用已显示该对象的窗格，其次使用用户当前指定的工作窗格，并让目标窗格清楚可辨。不能在每次点击时不断增开标签或覆盖其他正在编辑的内容。跨项目或个人空间的关联，在卡片中预先标明归属，点击后展示实际所在位置；建议和委托仍保留自己的原始归属。

对应插件在底栏与插件切换入口中的当前态应与实际激活的窗格一致。侧边栏展示的关联对象名称与主区标题、版本保持对应，用户能分清“正在查看哪个插件”和“当前建议关联哪个对象”。

卡片内“查看依据”“查看成果”“重新定位”等入口分别到达所指内容。“准备”“采用”“执行”遵循第 10 节的明确操作约定；按按钮不同时触发卡片主体的另一轮导航。鼠标悬停或键盘经过卡片可以提供轻量预览，但不能触发插件切换、滚动或业务操作。

### 12.4 定位与高亮的可见效果

定位成功要求正确对象实际显示，目标位于用户可见区域，且建议与被标记内容的关系能辨认。只点亮插件图标、发出导航请求或滚到大致位置，不足以证明已经定位到具体内容。目标只支持插件级或对象级定位时，应如实显示到达的层级。

目标位于折叠区域、分页、长列表、筛选外或画布视口外时，应能够展示该目标并说明必要的临时查看状态。不能要求用户自己翻找，也不能为定位改写内容、持久改变其筛选偏好或移除原有选择；返回时能恢复此前的查看条件。暂时无法展示的情况进入明确的不可定位状态。

到达时给出简短的定位提示，随后保留克制的关联标记，直到用户切换建议、清除联动或离开对应内容。卡片选中态、主区关联标记和内容名称形成可辨认的对应；用户滚开后可以一键重新定位，页面不能持续把他拉回原处。

高亮属于临时查看状态，不修改原文、不进入保存内容、复制结果或导出产物，不占用编辑器的原生文字选择，也不能把“正在关联”误画成“已修改”或“已完成”。沿用平台现有视觉规范，浅深主题都可辨认；提供文字或标记说明，不能只靠颜色与闪烁。

多个关联位置需要分别可辨认，支持查看数量和逐处定位，清楚说明当前是第几处。切换建议时移除上一建议的临时标记，保留用户自己的选择与标注；重叠位置的关系可查，不能把不同建议混成无法解释的一片高亮。

同一对象改名或移动后仍应找到正确对象。内容编辑导致原精确位置失效时，能确定新位置才重新高亮；无法确定时保留原引用摘要、版本与原因，退到正确对象供查看，不能靠相似标题或相似句子把其他内容当作原依据。历史报告中的“当时内容”和“当前内容”有明确入口与版本说明。

### 12.5 多对象联动与处理后的结果

建议详情应区分处理对象、事实依据和预期或已生成成果。每个关联项说明属于哪个插件、内容是什么及为何相关；可以逐个定位，必要时按用户选择对照查看。不能一次打开全部来源、让多个插件同时滚动，或将仅作参考的内容变成写入目标。

用户在主区主动打开或选择内容时，已展开的侧边栏能够突出与其有关的建议，或明确当前卡片对应别处。反向关联只改变查看提示，不自动采用建议、重新发起处理或改绑对话；用户固定的卡片与正在输入的内容不被自动替换。

用户明确执行后，卡片显示处理进度，并关联真实生成或修改的结果。完成时提供“查看结果”，能定位新产物或修改位置；涉及修改时能够核对改变了什么，并按对应插件实际支持的能力继续调整或撤销。没有可靠撤销能力时不显示会误导用户的撤销按钮。

定位、滚动、展开与联动高亮是用户在核对建议的行为，应与新的工作意图区分。不能因为打开了一份建议的依据，就立即生成同一事项的新建议或启动另一轮自动处理，形成自我触发循环。

### 12.6 切换、失效与恢复

卡片到目标的联动需要有真实状态：正在打开、正在定位、已精确定位、已打开对象但局部不可定位、无法访问或失败。慢加载时仍能继续阅读侧边栏、取消查看或切换卡片，不能冻结整个工作台；失败保留详情、原因和重试入口。重试定位只重做查看过程，不重跑原业务任务。

用户连续点击不同卡片时，只有最后仍被选择的卡片可以改变当前主区位置与关联标记。旧请求迟到、目标加载重试或后台更新，不能把用户拉回旧对象，也不能把新卡片错误标为已定位。建议处理任务可以继续运行，但其结果留在原工作中。

定位尚未完成时，用户手动转到其他插件或窗格、返回原位置、取消查看或收起侧边栏，均结束该次尚未完成的自动定位意图；即使原卡片仍保留选中状态，其迟到结果也不能接管主区。用户可以再次明确选择“重新定位”。

目标被删除、插件被停用或卸载、权限变化、内容离线，以及局部位置失效分别说明。可访问原对象但不能精确定位时保留对象级查看；没有访问权时不通过侧边栏残留预览泄露内容。不自动改开名称相近的对象，也不因无法打开就重新创建已删除内容。

进入关联内容前保留可以返回的上下文：原项目、插件或窗格、报告周期、筛选、阅读位置、已选建议以及未提交文字。提供明确返回入口，前进后退行为一致。用户主动打开相关内容可按平台规则产生正常已读状态，但不等于采用助理建议；未提交内容不得丢失，只有确实无法保留且会造成损失时才请求用户决定。

关闭侧边栏清除其临时联动标记但不关闭用户正在使用的主区内容、不结束委托。重新打开可恢复卡片与草稿，并重新核对目标有效性；不会仅因恢复面板就在后台滚动主区。刷新或重启后恢复到可理解状态，旧的已定位标记不能冒充本次已成功显示。

窄窗口无法并排时，在建议与关联内容之间提供清楚切换和返回位置；不把主区压缩到无法阅读。键盘可以选择卡片、触发查看、转到关联内容及返回，焦点去向可预期，定位结果对辅助技术可感知；减弱动效设置下仍能识别关联。侧边栏与已有详情、设置或其他侧面板竞争空间时，保留各自草稿和返回入口，避免互相遮挡或无声销毁。

### 12.7 注意力与主动程度

用户能设置主动程度、关注重点、可打扰时段、在特定工作环境下保持安静，以及必要例外。免打扰控制通知，暂停控制工作，停止结束对应委托；三者不能混为一谈。

普通进展安静汇总；真正影响当前工作的失败或必要决定按用户规则请求关注。重复来源、同一事项的多次变化和失败重试合并呈现。用户没有回应时，不提高通知频率，也不把沉默视为同意。

“这件事是否值得现在提醒”的场景判断由助理按 Skill 提出；用户设定的通知渠道、时段、频率与例外由平台执行。Skill 可以在边界内选择更安静的处理，不能以自己判断“紧急”绕过免打扰或把一般进展标成平台故障。

后台出现的主动内容不能抢输入焦点、改绑正在处理的工作、切换插件、覆盖草稿或打断阅读。用户点击卡片后发生的定位与高亮遵循上述联动要求；其余更新不自动触发跳转、滚动或高亮动画。正在查看或即将点击的卡片保持位置稳定，新内容通过可选择的更新提示进入。

## 13 时间、用量和恢复

### 13.1 持续运行的边界

用户能了解主动功能当前是否在运行、观察范围是否完整、上一次有效检查和下一次已约定跟进，以及当前有哪些等待。缺少运行条件时，不能显示仍在持续监看。

侧边栏提供按需查看“为什么有这条建议”和“为什么最近没有建议”的入口。能够区分尚未检查、检查后没有值得行动的变化、按偏好保持安静、因用量暂缓，以及资料、Skill 或插件能力不足；依据真实检查情况说明，不能事后编造曾考虑过的机会。用户可直接调整相关设置或发起一次当前范围内的检查，日常界面保持简洁，不把每次不行动都变成通知。

关闭助理面板、切换插件或项目，不应丢失已受托工作。关闭窗口、退出应用、电脑休眠、断网和模型不可用分别可能影响运行，产品应准确说明实际后台能力；本次不承诺电脑关闭后仍由云端执行。

运行恢复后，先依据当前业务事实核对原工作。仍有价值且满足授权的事项继续，已失去时效的事项停止或重新判断，不集中补发过时提示，也不重复已经成功的操作。

### 13.2 用量与并行

用户可约束整体主动协助与单项工作的用量、频率、并行程度和必要时限。观察、判断、准备与执行的消耗应能理解，未知费用不能显示为零。

资源不足时，平台先守住用户明确的执行要求、预算和暂停约定；其余可推进事项的相对价值与取舍由助理按 Skill 和当前重点判断，不能按场景名称固定分配业务优先级。达到边界时保留已完成部分、说明暂停原因和可采取的下一步，不能持续自我唤醒消耗额度。

多个工作可以在实际支持且边界允许时共同推进；涉及同一内容或真实依赖时保持正确顺序。用户关注的是结果和冲突，不需要手动协调底层执行者。

### 13.3 失败和部分成功

网络、模型、插件或专业执行者失败时，保留输入、有效理解和已完成结果，说明当前失败对工作有什么影响，允许在合适时机继续。

重试应回到原工作，并核对哪些步骤确实发生。结果未知时先核对，不自动重发可能已生效的操作；部分成功不全部当失败重做，也不把尚未完成部分一并宣称完成。

用户停止、撤销授权或排除内容后，迟到的结果不能继续触发原定写入和新工作。恢复时不得重新激活已取消的委托、停用的 Skill 或被排除的观察范围。

## 14 Molis Work 的端到端效果评测

### 14.1 以完整工作为评价单位

工作记录必须支持从初始意图、当时资料与配置，经判断、交互、执行和用户介入，到真实交付与后续效果的完整评测。范围包含主动助理，也包含用户直接使用插件、被动请求、工作流和后台工作；一次模型回答质量或工具成功率不能代表产品端到端效果。

评测应能回答：是否理解正确、是否选对材料和 Skill、是否在适当时机行动或保持安静、是否完成业务目标、结果是否可用、用户是否需要额外纠正、结果后来是否返工，以及时间、成本和打扰是否值得。每个结论都能追到对应事实和判定规则。

| 评价维度 | 需要保留的区分 |
| --- | --- |
| 发现与时机 | 应发现而漏掉、发现正确、无关建议、重复提示、过早或过晚；识别后保持安静与根本没识别到分别统计 |
| 理解与依据 | 事实正确性、来源覆盖与新鲜度、意图识别、跨插件关联、对未知情况的处理 |
| 方法与执行 | Skill 是否适用及遵循当前要求、所选动作能否推进目标、步骤是否合理、授权与停止是否兑现 |
| 结果与持续价值 | 真正完成、部分完成、无效完成声明、后续采用、修改、撤销、返工与仍未知的效果 |
| 交互与使用负担 | 卡片与内容是否正确关联、目标是否真正可见和高亮、能否返回并接续、必要决定是否易懂、需要多少次补充和重复说明、是否造成无效打扰 |
| 可靠性与资源 | 完成耗时、实际费用与未知费用、异常与恢复、重复效果、环境缺口和记录完整性 |

质量判定可以由事实断言、人工评价或评测器完成，但来源必须明确。评测器的判断保留规则、版本和依据，争议能复查；不能只用执行助理对自己的成功宣告作为评分。用户点击、采用或暂时未反对只是一种反馈，不能单独认定正确或有价值。

### 14.2 可比较、可复查、可回放

一份有效评测样本应包含初始要求、当时可用资料与条件、相关产品和 Skill 版本、实际过程、交付物、终态证据、预期或评分标准，以及允许的合理差异。自然语言工作可以有多个合格结果，不能只与一段固定答案逐字比较。

能够比较同一类工作在平台、模型、Skill 或插件更新前后的结果，并定位差异发生在理解、检索、判断、交互、执行还是交付。比较保留共同条件和不可比部分；外部材料已经变化、模型行为不确定或运行环境不同，不能保证逐字复现，也不能把所有差异归因于版本升级。

支持查看原过程，以及在隔离、明确条件下重新评测。回放不能重复真实发送、发布、购买或删除等副作用；模拟、离线重评、隔离运行与真实环境验证必须分别标明，不能用一种结果冒充另一种证明。新的评测结论不改写当时实际发生的记录。

应能将代表性真实工作、已确认失败和关键产品路径沉淀为持续回归样本。进入样本集时保留来源与允许用途，处理不应包含的内容；用于学习或调优的样本与用于独立验证的样本要能区分，避免把已见过样本的表现当作泛化效果。

### 14.3 样本完整性与效果口径

评测集合需要包括成功、失败、中断、用户接管、拒绝建议、无响应和正确不行动，不能只筛出有最终答案的工作。用于评估“漏掉了什么”的候选机会，应有独立于助理已输出建议的依据与人工或规则判断，不能只在助理发现的事项里计算发现率。

展示指标时同时说明对象、时间窗、样本量、分母、可评测比例、缺失与排除原因。已呈现、用户已看到、已选择、已执行、业务完成和持续采用是不同阶段。没有实际曝光、尚未到观察截止时刻或记录缺失时，反馈应为未知，不能按拒绝或失败计数。

采用率、点击率、操作减少和运行次数可帮助诊断，核心目标仍是工作质量与推进效果。节省时间或效率提升需要合理基准或对照，并说明推断限制；没有比较依据时只报告实测耗时和可验证变化。按不同任务类型、插件、主动方式和版本查看差异，避免整体均值掩盖关键路径退化。

用户侧的工作报告与开发侧的效果评测使用一致的基础事实，但分别服务于工作决策与产品改进；不能把内部模型得分当成用户工作成果，也不能把用户日报的乐观总结当成评测真值。

评测中的材料审阅、语义质量判断、失败归因和结果解读，可以通过单独配置、保留版本的评测 Skill 调用平台查询、对比与评测工具完成，不为每类工作另写一套分析流程。样本用途、运行隔离、确定性断言、统计口径和证据留存由评测能力保证。被评测的场景 Skill、用户报告配置与评测方法分别管理；修改做法不会同步调高自己的评分或改写验收条件，评测方法改变后也须标明可比范围。

界面联动的评测需核对实际可见对象与标记位置是否符合卡片所指内容，并检查返回、未提交内容和后续操作。导航请求完成、插件自行报告已定位或存在某个高亮样式，都不能单独证明关联正确；应能发现定位到同名错误对象、位置被新内容替换及迟到请求覆盖当前选择等错误。

## 15 采集约定的维护与迭代

功能迭代需先区分场景做法变化与通用能力变化。材料选择、领域判断、报告结构、跟进步骤等变化，优先维护个人助理的 Skill 与配置，并用真实工作验证；实际缺少数据工具、动作、运行保障或统一交互时，再补齐相应能力。Skill 变更也需要记录版本、工具依赖、效果变化及适用范围，不能因为没有改产品代码就跳过验证。实现时应同步现有 [开发要求](../../docs/system/DEVELOPMENT-REQUIREMENTS.md)。

统一采集需要伴随产品长期维护。每项已支持能力都应有明确的记录范围、事实负责人、关键阶段、内容与版本约定、使用边界、完整性状态，以及对应验证。新增插件或功能不能等上线后出现评测缺口，再临时决定当初应该记录什么。

新增或调整入口、交互、Skill 生效方式、模型与上下文、动作、后台任务、业务状态或成果交付时，都要同时判断对采集和既有消费者的影响。改变记录含义、删去记录、降低粒度或缩短保留周期是可见的合同变化，不能伪装成无影响的日志整理。

迭代应同步更新记录约定、对应验证，以及受影响的审计、助理、报告和评测口径。历史记录继续标明当时的产品和语义版本；无法比较的范围要明确。合同变更和历史数据处理遵循仓库现行规则，本需求不额外引入一套读取兼容机制。

开发手册需将以上要求作为功能开发与交付的组成部分，给出设计、实现、验证、升级与故障修复时的检查要求。当前未接入的能力与未来接入要求分别标明；文档写了“完整”不代表系统已完整采集。实现时应同步的开发入口见 [开发手册](../../docs/system/DEVELOPMENT-REQUIREMENTS.md)。

## 16 验收标准

下列编号定义功能完成门。产品目标为内部完整，需以真实内容、实际平台能力和真实模型覆盖完整工作；模拟、结构检查或 SDK 自身支持仅证明对应局部。带 [人工] 的条目包含语义质量或真实工作体验判断。侧边栏联动在大规模实现前需用高保真可交互切片验证关键动线与状态，并明确模拟部分；功能阶段再用真实插件和内容证明对应行为。当前尚未进入功能实现与运行验收。

Skill 驱动的验证需对照第 5.6 节覆盖不同环节：保持平台、插件代码及代表性材料不变，仅调整有效 Skill 或其使用配置，检查预期的关注与选用、取材处理、跟进或选择项变化。报告文案变化不能代替整条链路的证据；也要确认相同变更没有改变权限、确定事实和通用交互。停止或缺少 Skill 的行为与正常运行一并验证。

| 编号 | 通过条件 |
| --- | --- |
| PWA-01 | [人工] 用户未发送新请求、未预建 Goal 时，助理能结合一段时间的真实行为和跨插件内容，发现与其工作相关的具体下一步，并交付可接续的建议或已获准准备的结果 |

## 17 需求边界与待验证项

### 17.1 当前范围与仍需确定的产品参数

本文将用户已提出的目标细化为可讨论的产品要求。场景由个人助理依据配置的 Skill 调用通用系统数据工具和业务能力完成，是本需求的明确产品原则。主动回看范围、自动报告周期与生成时间已定为 Onboarding 时由用户设置、后续在设置修改（2026-10-27，见 §3.1、§9.1），不固定统一天数或报告时刻。个人与项目的 Skill 配置、只读预览、版本生效规则及默认右侧的工作栏属于本草案的具体产品选择，用户调整时更新对应要求；不把它们描述成现有产品能力。完整工作记录、周期报告、可点选后续操作、项目首页总览、侧边栏与插件内容联动和平台端到端评测均属于本次需求范围。

工作记录的保留方式已定为本地默认长期保留，用户可在设置中选择自动清理期限或手动清理；容量默认不设固定配额，显示实际占用，允许用户设置提醒线，达到提醒线不自动删除记录（2026-10-27，见 §3.4）。需求书定义可观察行为、信息完整性、效果判断与维护责任，不指定采集架构、存储方式、字段协议或调度实现。正式验收前需要明确实际插件及对象类型的覆盖清单，以及首页和定位延时、主动质量、用量的评判口径与目标。这些参数应结合高保真验证和代表性真实工作确定；已有阈值需要有依据，尚无依据的不能随意填一个数字宣称达标，也不能用未定参数缩减本文要求的覆盖面。集中评测服务、跨设备采集或团队管理后台不因这些要求自动纳入本次开发。

主动作出的判断需要通过真实使用验证相关性、时机、推进价值和打扰程度。具体运行能力以 Molis Work 实际采用的 Prologue 与平台接入为准；现有能力、接入缺口与真正需要补齐的能力，不能混为已实现状态。

本需求补充已有 [系统助理需求](../archive/system-assistant/spec.md) 中的主动协助与 Skill 使用要求，不重新定义全部助理功能。术语以 [仓库术语表](../../docs/system/GLOSSARY.md) 为准；平台产品边界见 [PRODUCT](../../PRODUCT.md)，AI 能力与用户可调范围见 [Prologue AI 手册](../../docs/platform/PROLOGUE-AI.md)。上述资料约束既有边界，不替代本文的功能完成标准。

### 17.2 可选扩展方向

以下是基于当前需求值得进一步验证的产品扩展，尚未纳入本次功能验收，不因列在本文中自动成为开发任务。它们应沿用现有 Skill、侧边栏与内容联动体验。确定采用某项后，再补充其边界与验收，不另建一套助理入口。

这些方向也按相同分工扩展：比较、回看或预演的取材与分析方法配置为 Skill，助理调用通用查询、比较和评测能力完成；只有原有工具无法提供所需事实或可靠操作时才补齐工具，不能按扩展名称各建一套固定场景功能。

| 方向 | 增加的用户价值与交互要求 | 成立条件与取舍 |
| --- | --- | --- |
| Skill 效果对比 | 用户修改做法后，选择一组有代表性的历史工作，对照原版与新版会关注什么、建议什么、如何处理、漏掉什么及预计消耗。差异能定位到材料和处理步骤，用户选择采用、继续改或恢复。相较单次试用，帮助判断一种做法是否稳定适合自己 | 使用可比的当时材料与条件，结果标为离线对比；不能把已知最终答案带入当时判断，不能把离线提升保证为未来效果，也不自动启用新版本 |
| 计划变更的影响预演 | 用户试问“这项推迟、优先级调换或关键材料被替换会怎样”，助理说明受影响工作、期限、依赖和待决定项，提供少量替代安排。点选影响项能定位对应插件内容，采用后才进入实际调整 | 以已有真实关系与明确假设为依据，未知影响保持未知；预演不修改正式计划，不替用户向他人承诺，不假装预测所有后果 |
| 决定与结果的历史回溯 | 用户能够询问“当时为什么这样决定”“这个结果后来怎样了”，沿一次工作的材料、明确决定、实际操作、交付和后续修改回看，并在侧边栏对照当时版本与当前内容。帮助接续长期搁置的工作，也让完整记录直接产生用户价值 | 依据可用历史和当时记录的理由，区分用户决定、助理建议与事后解释；没有记录不编造原因，回看不复活旧任务，也不将历史事实当成当前状态 |

优先验证 Skill 效果对比：它直接帮助用户判断自己的 Skill 修改是否有效，连接现有试用、完整记录和效果评测。历史回溯适合检验工作记录是否真的可用；影响预演在跨插件关系与状态已足够可靠后再扩展，避免提前给出无法兑现的计划建议。
