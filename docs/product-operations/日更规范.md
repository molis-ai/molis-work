# 产品运营文档维护规范

生效：2026-10-18 重构版。替代 10-17／10-18 的"五章日更"写法；旧规范的取证纪律保留在本文第 4 节，旧稿在 [archive/](archive/)。用户指定的更新时间不变：每天 **09:00，Asia/Tokyo**。

## 1. 这套文档为谁、为什么

这里维护 Molis Work 面向用户的产品表达与运营研究，供官网、产品介绍、推广和用户运营取材。它要回答四件事：

1. **产品是什么、要成为什么。** 以已有 spec 和 PRODUCT.md 为准写完整的产品，不因为某项还没合入就不写；成熟度用标签标清楚。
2. **它能做的每一件事。** 全部功能（main、各分支、spec 规划）和它们怎样串起来。
3. **谁会在什么时候用它。** 按角色枚举尽可能多的使用链路，再从中选出 killer 场景。
4. **还缺什么。** 推广前要补的产品缺口与优化建议。

上一版的问题是：每段文案都塞满"不能、不承诺、未验证"，最后场景被压到只剩极窄的几条，官网拿不走。新写法把**叙事**和**证据**分层：正文按产品应有的样子讲，状态标签和成立条件跟着走；证据、反例和迁移账放进功能全景的"依据"列和 research/。

## 3. 成熟度标签

全部文档只用这一套标签，外加下面的"建议"标记。内部文档用细标签，官网摘录换成简标签。

| 细标签 | 含义 | 官网简标签 |
| --- | --- | --- |
| **已发布** | 在公开 Release 里，用户今天能取到；现在只有 v0.2.0 源码版（当时名 GoalBoard），只有它里面已有的能力能标 | 已发布 · v0.2.0（源码，当时名 GoalBoard） |
| **main 可用** | 已合入 main，主路径能走通，未公开发布 | 开发中 |
| **main 部分** | 已合入 main，但只有部分路径、或缺关键一环 | 开发中 |
| **分支** | 在分支或开放 PR 上实现，未合入 | 开发中 |
| **规划** | 有 spec 或用户确认的需求，尚未实现 | 规划中（演示须标"示意"） |
| **撤回** | 曾经规划或实现，后来被放弃或删除 | 不对外 |

**需模型**：只因要先配模型的能力不降级，标签后注"需模型"。推荐、判断这类直接决定流程走向的模型输出（浮条推荐、判断规则），没做命中率评估的标 main 部分；模型那一环自述未接通的也标 main 部分。写作、整理、问答这类输出不因没做正式评估降级。

**建议（未立项，不对外）**：只出现在产品优化建议里、没有 spec 也没有用户确认需求的项，标"建议"，不标"规划"，不进官网。只在本地分支或工作树里、还没推到远端的功能，对外按"规划"写或不写。

**路线图阶段**：[防腐之后的路线图](../../specs/post-anticorruption-roadmap/spec.md)（10-29 合入）给规划项排了阶段和轨道，写成"1·C"（阶段 1 的 C 轨）；"不排"是路线图第 8 节本轮不做、阶段 4 之后再议的。规划项和瓶颈后面可以注阶段，不写日期：防腐收尾之前都不开工，路线图也没有日历。路线图收下的建议改标"规划"；产品优化建议里每条的去向写在去向列。

团队协作内部标"规划"（10-28 起有 team-collaboration 需求草案，路线图阶段 4 交付），官网对外标"开发中"，是负责人决定的例外（见 [README](README.md#成熟度标签)）。

另有两条与成熟度无关的标记：**示意**（演示与故事是构造的，不是客户实绩）、**内部**（Issue 等内部工具，任何对外材料都不出现）。

证据程度（仓库核对 / 工程测试 / 产品实操 / 用户本人验收）只在功能全景的依据列写，不进场景正文。main 合入不等于发布，有测试不等于顺畅，自动化跑通不等于用户验收。

## 4. 每次更新怎么做

1. **建立基线。** fetch 远端（本机网络不稳时用 `git -c http.version=HTTP/1.1 fetch`）；记下 origin/main SHA、公开 Release、开放 PR、远端分支数。本地分支、工作树和未提交改动照样要核对（在途功能常在那里），但明细只记在私有采集里，公开文档只写数量和产品影响。读不到的写成缺口，不当作不存在。
2. **找变化。** 上次基线以来合入 main 的 PR（用 `merged_at` 转东京时间）、分支新提交、新增或改状态的 spec、官网仓库里已确认可公开的新决定。只深读影响用户能力的变化；CI、门禁、重构合成一行。
3. **更新功能全景。** 每项变化落到对应功能行：成熟度升降、依据、可组合点。新能力先问"它改变了哪条使用链路的哪一步"，再决定要不要新开一行。
4. **回看链路与 killer 打分。** 成熟度跨级、或新机制让某条链少了一步，就更新链路卡和打分表；打分变化写一句理由。
5. **记录建议。** 写作中发现的缺口进[产品优化建议](产品优化建议.md)，按模板写，处理过的标去向。
6. **更新 README 的更新记录**，一行：日期、基线、改了什么。没有实质变化的日子只记一行"无变化"，不为日更制造卖点。

需要更深的研究（全量分支盘点、外部补研）时，另存 `research/YYYY-MM-DD-主题.md`，主文档只引用结论。

### 公开摘要与私有采集

这个仓库是公开的，本目录里的每个字都会被外人读到（2026-10-18 #719 定）。

- **私有采集**放在仓库外的本地目录，只给当前用户读，位置由本地任务配置保存：完整 API 响应、机器快照、全量本地分支与工作树状态、文件指纹、读取清单。不放进公开同步，也不放进另一个公开仓库。
- **公开摘要**只写：日期与截止时间、必要的公开提交 SHA、PR 与来源链接、产品影响、实现状态、验证边界和覆盖缺口。没有公开依据的，写明证据有限，不拿本机文件路径冒充来源。
- **不进公开正文、附件和 PR 描述的**：本机账号与绝对路径；完整的工作树和未提交文件列表；非公开材料的文件名、哈希和摘录；未公开 Release 的草稿正文、附件和构建细节；凭据和业务私密内容。非公开来源（如官网仓库里的设计材料）只在确认可公开后提炼成产品结论；公开仓库里出现过的历史内容，也要按来源判断，不能因为出现过就默认能抄。
- 密钥扫描和"内容能不能公开"分开查：`pnpm secrets:check` 通过，不代表内容适合公开。
- 私有快照缺失或读不了时，公开摘要只给部分基线，写明缺口，不说已完成逐项核对。

## 5. 写作标准

**场景卡**（角色与使用链路、killer 场景共用）：

- **触发**：最近一次具体发生的事，有对象、有时间压力。
- **链路**：4–8 步，每一步写"在哪个插件、做什么、Work 替人做了什么"，能写动作 id 就写；编号列出或用 → 串起来都可以。
- **交付物**：能检查的结果，落在哪个插件。
- **用到的机制**：点名 M1–M8 里的哪几项（见[产品介绍第 5 节](产品介绍.md#5-八个价值支柱)），不是插件名堆砌。
- **成熟度**：按整条链里最弱的一环标，同时标出哪一环是瓶颈；只因要先配模型的不降级，注"需模型"（推荐、判断类的例外见第 3 节）。可选的步骤不拉低整条链，在卡里注"（第 N 步可选，为 main 部分）"。要另一个人确认、但只能由你代记结论的（法务、导师、客户、家人），按机制本身标，在瓶颈里写"对方进不来，由你代记（团队协作未做）"。
- **原来怎么做**：熟练用户现在的组合，以及卡在哪一步。
- **不适合**：一句话说清什么情况下不该用 Work。
- **频率 / 痛感**：高中低，加一句依据（外部调研的数据、社区原话），没有就写"推断"。

链路编号是"角色缩写-两位序号"（如 `DEV-01`），不复用；killer 场景用编号引用链路。

**说法约定：**

- 开场的顺序：先讲信念（每个人做事的一套有它的价值，Molis Work 帮你守住），再讲四句"你的"，再按角色讲怎么用；场景是证据，不是开头。每句信念后面紧跟一个今天能演的画面并标成熟度，只有信念、没有画面的段落不写。口号原文 "Work, People, AI, Tool, get connected better than ever." 是负责人 2026-10-19 定的，不擅自改写；中文副标和开场见[产品介绍第 1 节](产品介绍.md#1-口号与开场)。
- 说"可以长成你的样子""按你的做法"，不说"永远和别人不一样""你的 AI 只属于你""完全听你的"：项目说明和规则会每一轮带给助理，但模型不保证每次照办。
- 不说别的工具"控制你""绑架你"。讲"人在围着工具转"时说具体的时刻（来回切换、给 AI 重新交代背景、事情在工具之间断掉），不点名哪家产品。
- 人文的说法不代替成熟度标签：开场里最打动人的两句（你的工具、你的 AI）证据最薄，紧邻处照样标 main 部分、规划。
- 可以讲规划中的能力，紧邻处标"规划中 · 示意"，不写成今天可下载。
- 不写"只有我们""别人都只有聊天""组合起来没人做到"，也不用"没有人做全""我们没找到同类"这类论证。比较时承认对手已经做好的部分（如 AGENTS.md 共用说明、Notion / Linear / Conductor 接外部 Agent），讲 Work 在哪个具体环节更顺。
- 没有实测就不写节省时间的百分比；Agent 报告的依据写"Agent 报告"，不写"核验""证明"。
- 写文档、管事情的读者不以"换 AI 轮流干活"为卖点（负责人 10-16 决定）。
- Issue 插件是内部工具，任何对外材料不出现。
- 隐私不说"数据不出本机"，说"存在本机，调模型时发给你选的供应商"；Shelf 只有"提取文字"在本机、不调模型，"先脱敏再交给云端模型"今天不成立。
- 固定成果的"对比"只说原文改没改（未改、已改、已移走、已删除），不说能看两版差异。
- 许可证按 main 现行 LICENSE 写（Molis AI Cooperation Source License），不写"开源（MIT）""开源自由商用"；讲 v0.2.0 时可以说明它当时按 MIT 发布。
- "已发布"只用于 v0.2.0 源码版里已有的能力，对外写成"已发布 · v0.2.0（源码，当时名 GoalBoard）"，不写成能下载的 Molis Work。
- 外部内容（网页、邮件、订阅、文档）只说"按资料交给 AI、标明不可信，降低被带偏的风险"，不写"不会变成指令"这类保证。
- 外部 AI 经 MCP 连接、读连接摘要时读到项目说明，从目标打开终端时推进提示里也带着，不写"每一轮都拿到"；每一轮都带上的是内置助理和插件 Agent。
- 从目标打开终端还在，10-24 起由工作台承载（#1113），照 main 可用写。会话目录、原生会话读取和跨 Runtime 交接随 Sessions 下线（SC-4，10-23）删掉了，标"撤回"、不对外讲；重做见 BL-177，按路线图写成规划（1·C 盘点来源，2·C/F 找回历史与接续，3·C 持续跟进与跨工具交接），覆盖国内外主流的 AI 开发工具，不只 Codex、Claude Code。链路和演示里外部 AI 经 MCP 读写目标，也可以从目标打开终端。
- 成果库、角色不叫插件：成果库是平台事实，代码迁完之前界面上仍按插件出现，位置照实写；角色 10-22 起已由宿主装配（`modules/characters`，#1008），是"设置 › 角色"里的一节，原插件包已删。插件创作台和炼金术士不迁到 Plugin Runtime，也不删（10-21、10-23 定）；10-27 起整体升级并进插件创作工作台升级（BL-377，原 BL-376 并入），炼金术士是其中场景组装的落地场景。场景组装是平台能力（10-27 定），交付之前不当作现有能力讲；创作台写成"从想法到可用插件还没完整跑通过"，不写"以前生成的插件不能用"；今天能用的部分照实写。
- 插件不分官方、个人、创作台生成还是第三方，讲法一样：同一套 SDK、合同、授权规则和平台服务，只有安装信任（要不要首次确认、跑不跑沙箱）按发布者签名区分（2026-10-18 定）。今天还只给内置插件的地方照实写成现状。
- 代码还是旧样子、讲法已按 2026-10-18 的收口决定改了的句子，紧邻处标「2026-10-18 改：…」，写清原来怎么说、为什么改；依据是 `specs/repository-anti-corruption/spec.md` 第 1 节的 2026-10-18 各行。
- 不用"决定中心"：独立页面已删，说"决定请求"或目标页上的"N 项待你确认"；界面上没有的字用进演示字幕时标"示意"。
- 本地优先不等于离线：用模型、搜索、连接器时，相关内容会发给对应服务。

**产品建议**按"问题 → 建议 → 依赖的能力或 spec → 怎么验证 → 什么结果推翻它 → 优先级"写；它是建议，不是立项或排期。

## 6. 不做什么

文档维护不改产品源码、真实 Home、官网仓库与供应商账号；不自动提交、推送、合并或发布；不联系受访者、不登录或购买竞品。需要这些的研究先写好脚本和待办，等用户授权。另获提交授权时，PR 先交统筹评审，由统筹决定验证范围并入队；作者不自行合并。

## 7. 完成检查

- 每份主文档开头的"最近更新"与本次基线一致；README 更新记录已加一行。
- 所有成熟度标签来自第 3 节；每个 killer 场景标出瓶颈环节。
- 新增功能都落到了功能全景；新增或升级的场景都有链路卡。
- 链接可达（`pnpm health:check` 会查活文档断链）；`archive/` 之外不引用已删除的文件。
- 公开文件里没有原始采集、本机路径或非公开来源的明细；私有快照在仓库外，引用指向可公开的摘要。
