# Goal：情境动作——一条浮条、右栏 Shelf、左右互动、一句话新建

你负责推进这个目标，直到完成。设计已经定了，你的工作是实现、验证、合入。不要重新讨论已定的事。

## 1. 目标

把 Molis Work 里「人手上有一样东西时，能对它做什么、在哪里做」统一成一套：

- **一条情境浮条**：底部动作条取消。浮条贴着手上的东西出现：左边的选区、右栏选中的条目、助理面板的结果；拖放时出现在松手处。Pages 的格式条和写作菜单并进浮条。工具由插件声明，动作来自统一能力目录，由 Jev 排序。
- **右栏**：Shelf 不再是插件，原样（DropAgent 的全部功能与外观）成为右栏的一格。格的顺序是 Shelf · 灵光 · 文件 · 浏览器 · 讨论。右栏与左边双向互动：右栏的东西能放进左边的光标处、选区或对象（落点）；左边的东西能收进 Shelf、记下灵光。
- **一句话新建**：每个插件声明一次「创建入口」。插件页和右栏格的标题栏有「✦」；选中内容后，Jev 推荐最合适的去处，零输入，由助理起草创建。追加到已有 Item、一次提取多个、选中文字运行工作流，都走同一条路。
- **助理打通**：助理输入框上方默认带上「手上 + 落点」；助理用同一份候选出卡片；助理面板也是一个位置。
- **选区能力 F1–F13、Coding 的旁问（btw）与分叉（fork）、存量插件补齐**，按总纲的波次做完。

**完成的标准**

1. 总纲 §13 需求对照表（R1–R26、C1–C16、K1–K4）每一行都有「已实现 + 证据」，或者用户明确说过延后；
2. AC-S（side-shelf）、AC-T（context-toolbar）、AC-Q（quick-create）、AC-P（总纲 §12）全部通过并留证据；
3. 覆盖率门禁的「待补」名单清零，只剩永久不适用的几项；
4. 用户本人的验收单独记录，没做的如实写「待用户验收」。

每一波合入 main 就算一次可交付的进展，不必等全部做完。

## 3. 已定的事（别再问）

细节都在各 spec 的决策记录里，这里是最容易被重新打开的几条：

- 能力只登记一次，不另建注册表。左右关系是统一目录里的声明：side 视图的 `objects`、`places`、`ItemAttach.positions`。宿主里不出现按 `plugin_id` 的分支。
- 底部动作条整个取消，没有锚点就不显示，不留兜底、不留两套。浮条单行，窄时工具折成「格式 ▾」。打字时不自动浮出。
- 创建类候选只在推荐位出现，不进「更多」和「全部操作」。「记成待办」「记下灵光」并进创建入口，旧的删掉。
- 执行的总规则：写进人眼前正在编辑的对象，一律先预览（包括助理放进落点）；写到别处的，声明了 `undo` 的直接执行并带「撤销」「改放到」，其余出预填卡片。工作流运行、提案、只许本机本人的动作，总是出卡片。
- F2「追加到已有 Item」与「放进左边落点」合成一个 `ItemAttach`。`positions` 只用于落点目标，`find` 找到的目标放末尾或建关联。
- F8 材料篮就用 Shelf。Shelf 格里 DropAgent 的动作栏管 Shelf 自己的动作，浮条只显示去别处的动作。「文件」格与 Shelf 是两个独立功能，Shelf 材料两边都出现。
- 右栏：首次打开在 Shelf，之后回到上次那一格，某件事需要右栏时打开相关的那一格。Shelf 格窄时上下叠放，≥640px 两栏。底栏的 Shelf、灵光按钮并进侧栏按钮。
- 助理：默认带上「手上 + 落点」（可删）；助理面板是一个位置，第一期就做；放置动作不另行登记给助理。
- Coding：旁问与分叉做成平台形态（总纲 8.5）；模型操作浏览器（D3）共用右栏浏览器。
- Jev：规则先筛 ≤12 再排序，延迟预算 1.5 秒；左右互动评估的门槛是首位 ≥80%、前三 ≥95%、p95 ≤2 秒。
- 手册与 Skill 随代码一起写；覆盖率门禁用冻结名单，只许减少。

## 6. 工作方式

- **决定**：只有关键决策才用弹窗（AskUserQuestion）问用户，带方案和「（推荐）」，先做完能独立做的再攒一批问。关键决策包括：产品与合同语义、真实 Home 的数据、别人的分支与工作树、vendored、上游推送、仓库设置。其余按推荐做，写进对应 spec 的决策记录。总纲 §11 里还没定的两项（第一批放进动作清单、`web.page` 和 `im.message` 的命名），在 W0 切片时请用户看着实物定。
- **合并**：一个 PR 一个主题；分支与 main 同步、门禁全绿、CI 通过后自己合并，不用再问。每次合并记进总纲的进度。
- **协作**：开工前看 `git worktree list` 和 `ListAgents`。防腐审查会话常在跑构建、浏览器用例和全量回归，并占着 4301 端口的 QA 服务（`~/.molis-work-qa/post-merge-main`），别碰。你要整体构建、跑浏览器用例或全量回归前，先给它发消息约时段。主检出常被真实 Home 的 4207 服务使用，不在主检出里改东西。
- **子代理**：做修复类的子代理显式用 `model: "sonnet"`，effort 设 `xhigh` 或 `max`。实现与评审的提示里都写明：「不跑全量；全量回归由协调者在整合分支跑」，子代理只跑 README 里规定必跑的用例、自己的测试和门禁。
- **测试**：改过 `*/src` 后，跑全量前先整体 `pnpm build`；用 `node scripts/run-tests.mjs <文件…>` 跑测试；判断是不是自己引入的失败，用干净的基线工作树跑同一批文件对照。不为变绿而跳过、放宽或删除断言。
- **界面**：遵守 `DESIGN.md` 和总纲 §3.7；每个界面改动都在 1440、1024、800、390 宽度与深色下截图自查，也要过减少动画、读屏、触屏。预览窗格隐藏时 `document.hidden` 会停掉轮询，验证时要留意。
- **进度与证据**：写回对应的 spec，不另开进度文件。工程验证、真实场景验证、用户本人验收分开记录；模拟和没验证的部分如实写明。做完按 `specs/README.md` 归档。
