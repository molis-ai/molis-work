## 1. 要做到什么

把「从一次真实工作到一个好用的技能」走成一条完整的路：

| 环节 | 用户看到的 | 验收 |
| --- | --- | --- |
| 从真实过程生成 | 在助理里说「存成技能」，助理从刚才的过程提取固定步骤、可变参数、要问人的地方，起草成草稿；对话里一张结果回执 | SKP-11、PWA-103、PWA-104、PWA-106 |
| 编辑／参数 | 草稿就是第 41 批的那张表单，边写边存；可以「告诉助理怎么改」 | PWA-14、§6 第 1 段 |
| 校验 | 字段与长度、重名、正文行数在表单里就地报；采用时宿主按同一份检查再核 | SKP-08（沿用）、SKP-11 |
| 已知答案回放 | 从对话起草的草稿自带那次的任务和你改定的结果；采用前先回放 | SKP-11、PWA-104 |
| 试用 | 在助理与 Coding 两边、现在的版本与草稿并排回放；不调工具、不改项目、不外发 | PWA-16、PWA-83、§6 试用三段 |
| 版本采用／恢复 | 采用才生效；全部版本可看、可对照、可恢复（存成下一版），可撤销 | PWA-14、PWA-105 |
| 通用包定制 | 「改一份我的」记住来源与版本；占位符换成自己的；原来的出新版时你的照旧在用，可看差别、带进草稿 | BL-166、PWA-16、§6 末段 |
| 跨入口效果验证 | 回放在助理与 Coding 各跑一次；采用后详情里看各入口真实用过几次 | 本批交付「跨入口效果验证」 |

不做：自动启用或自动排期（PWA-105）；生成时扩大权限（自己写的技能 `tools` 恒为空，技能本身也不授权）；分步执行多个技能（第 62 批）；从项目目录导入（BL-skill-import-project-directory）；带附带文件的自写技能（第 41 批已定只写正文）。

## 2. 关键做法

### 2.1 草稿是改动的唯一形态

自己改、助理起草、恢复旧版、改一份通用技能，都先成为一份**草稿**；只有本人「采用」才走第 41 批的签名与安装路径，成为「我的技能」包的下一版。草稿：

- 属于一个范围（个人空间或项目），对象是三种之一：新技能、自己的某个技能（记下基于第几版）、改一份某个通用技能（记下来源引用与版本）。
- 边写边存（带 `revision` 防并发覆盖），所以第 41 批的「离开前未保存提示条」在技能这里不再需要，删去它在能力包页的用法。
- 不影响任何一轮：目录、选用、`skills.body.read` 都只认已安装的版本。

### 2.2 从对话生成（助理可调）

`skills.drafts.create@1` 对本人和 Agent 都开放（只是起草，不生效）。助理在用户要求或判断构成可复用做法时（[长期内容用途合同](../prologue-memory-strategy/spec.md) §13 区分技能、记忆与项目说明）调用它，输入里带：字段、提取到的三类部分的计数、以及**一个已知答案**（那次要做的事与用户认可的结果）。来源（哪一轮）从调用上下文取，不从输入读。结果经平台现有的结果回执（`ActionResultView`：一句话加「打开草稿」链接）出现在对话里，不新增对话部件。采用、启用、排期仍只给本人（防提示注入，沿第 08 批定的「启用、导入只给本人」）。

### 2.3 回放与试用：只调模型、不调工具

`skills.trials.run@1` 用宿主自己的文字模型调用（`HostCompleteText`，与第 41 批起草同一条，模型调用仍只经 `horizontal/agent-host`）：系统提示是登记的试用说明加这个入口（助理或 Coding）的角色说明与技能正文，提示是已知答案的任务与材料。没有工具、工作区或动作权限越过这条口，所以试用**按构造**改不了项目、发不出去（PWA-16）；需要工具的步骤由模型写成「会做：……」。一次回放：每个入口 × 每个版本一次调用，再一次判定调用把各结果与已知答案对照，给「一致／N 处不同／判断不了」与不同之处。整次在 `withObservationSource("trial", …)` 里跑，观测记录标 `trial`，默认查询、报告与效果指标排除（PWA-83，观测层已有）。模型按当前设置。**实现时没做到的一处：** 宿主文字模型这条口（`HostCompleteText`）只交回文字，Prologue 回执里的模型与用量没有交给调用方，平台现在也没有一处记它的用量（第 41 批的起草、信息动作同样）；只给回放单记一份会成为第二个主人，所以回放不存模型与用量，等平台给这条口补上用量记账时一起有（[BL-b42-followups](../backlog/BL-b42-followups.md) ①）。

采用门：带已知答案的草稿，当前修订没回放过就不能采用（`skills.trial_required`）；最近一次回放有不同，要本人带 `accept_differences` 再采用（界面里就地确认一次）。

### 2.4 版本、比较与恢复

自己的技能的每一版就是「我的技能」包已签名的各版发布（安装服务已保留，`packages.releasesOf`），不另存一份历史。`skills.versions.list@1` 从发布里读出某个技能的各版字段与采用时间；比较用 SDK 现有的 `compareTexts`／`renderDiff`。恢复＝从某版开一份草稿（对照现在的）→ 采用为下一版；不改写历史。

### 2.5 通用包定制（BL-166）

「改一份我的」开的草稿记下来源（技能引用与版本）；采用后这份对应关系存进宿主的技能表（见 §3），目录项多一个 `based_on`。来源出了新版时，能力包的版本信息照提示词已有的 `default_updated` 写法标出（`KitEntry.version.change`），详情顶上说「原来的有第 N 版了，你的照旧在用」，可看差别（你的 → 新版）、带进草稿（新版正文开草稿，你的占位符替换再套一遍）或先不管（记下已看过的版本）。占位符（`~~类别`，第 08 批的连接器类别写法）在定制草稿里列出来逐个换。采用时可选把原来的改成关（沿 `skills.settings.set`，同一次采用里做，失败不影响采用并如实说）。

## 3. 存储（用户 2026-11-16 已确认）

`agent-definitions` 库是技能设置与用量的主人（第 08 批），草稿、已知答案、回放与来源对应关系归它：库 **2 → 3 只新建四张空表**：

| 表 | 存什么 |
| --- | --- |
| `skill_drafts` | 草稿：范围、对象（新／自己的某个＋基于版本／定制＋来源引用与版本）、字段、修订号、来源（本人／助理＋轮次引用）、放弃时间（撤销用，过期清理） |
| `skill_cases` | 已知答案：所属草稿或技能、标题、任务、材料摘录、认可的结果、来源 |
| `skill_trials` | 回放：草稿修订、已知答案、各入口 × 版本的结果与判定（模型与用量没有存，见 §2.3） |
| `skill_lineage` | 自己的技能 ← 来源技能与版本、已看过的来源版本 |

按[合同变更流程](../../docs/system/CONTRACT-CHANGES.md)「当前保留机制」登记一行（同第 08 批 `skill_settings` 建表）：只建空表、不动已有数据，U1 升级执行，普通打开仍拒绝旧版本。用户 2026-11-16 已确认这一条，并随 #2107 合入。

## 4. 合同稿（`services/skills`，C1）

新增动作登记在 `system.skills`（技能目录的提供方）；只有 `skills.drafts.adopt@1` 登记在插件安装的提供方，因为采用要在同一提供方里签名安装「我的技能」包（实现时定，见第 42 批文件「偏离」）：

| 动作 | 谁能调 | 做什么 |
| --- | --- | --- |
| `skills.drafts.list@1` | 本人 | 这个范围的草稿摘要（目录里标「草稿」） |
| `skills.drafts.read@1` | 本人 | 一份草稿：字段、对象、修订、已知答案、最近一次回放 |
| `skills.drafts.create@1` | 本人、Agent | 开一份草稿：新技能、自己的某个技能（可带 `from_version` 恢复）、改一份通用技能；可带已知答案 |
| `skills.drafts.update@1` | 本人 | 边写边存，`expected_revision` 防覆盖 |
| `skills.drafts.revise@1` | 本人 | 「告诉助理怎么改」：一句话改草稿，返回改后的字段（等模型，`concurrent`） |
| `skills.drafts.discard@1` | 本人、Agent | 放弃，带 `restore` 可在 7 天清理前撤回；也是 `drafts.create` 回执的撤销 |
| `skills.drafts.adopt@1` | 本人 | 采用：校验、回放门、签名安装为新技能或下一版、记来源；结果带 `source`，「把原来的改成关」由页面接着调 `skills.settings.set@1`（实现时定：采用不顺带改另一个技能的设置） |
| `skills.cases.put@1`／`remove@1` | 本人 | 给草稿加、删已知答案 |
| `skills.trials.run@1` | 本人、Agent | 回放（等模型，`concurrent`，`beforeEffect()` 前按读到的修订提交） |
| `skills.versions.list@1` | 本人 | 自己的某个技能的各版 |
| `skills.lineage.dismiss@1` | 本人 | 「先不管」：记下已看过的来源版本 |

目录项 `SkillCatalogEntry` 加可选 `based_on`、`draft`（有没有草稿）与 `recent_uses`（按入口的近期次数），`KitEntry` 的版本变化对技能也给 `default_updated`。第 41 批的 `skills.authored.save` 由 `drafts.adopt` 取代（阶段一，同一 PR 改完全部消费者）；`skills.authored.read`、`remove`、`draft`（一句话起草表单）保留：新建技能时页面先用 `authored.draft` 填表，再 `drafts.create` 开草稿（实现时定，原稿写的是一并取代）。错误码用 `defineErrorCodes` 加在 `skills` 下：`draft_unknown`、`draft_conflict`、`trial_required`、`trial_differs`、`case_invalid`。

## 5. 开工前检查（需求开发流程第 4 节）

档位：大需求（一组合同、新动线、新表）；类型：横向能力（主），产品线（助理、Coding）。

| # | 检查 | 结论 |
| --- | --- | --- |
| 1 | 事实主人 | 草稿、已知答案、回放、来源对应归宿主 Agent 定义（技能设置与用量的主人）；技能内容归「我的技能」包（安装服务）；对话归助理；观测记录归观测层。没有第二个主人 |
| 2 | 插件同等待遇 | 回放、草稿、定制对任何包的技能一样（系统自带、已装、第三方、自己写的）；不点名哪个插件 |
| 3 | 能力注册 | 全部是 `system.skills` 的动作，页面、助理、Agent 用同一份；起草与回放给 Agent，采用只给本人；等模型的声明 `concurrent` |
| 4 | 合同 | 改 `services/skills`（C1）：新动作、目录项三个可选字段（`draft`、`based_on`、`recent_uses`）、错误码；阶段一按现行版本改，一个 PR 改完消费者；刷新 API 与动作快照 |
| 5 | 放在哪个包 | 合同在 contracts；实现在宿主 `agent-definitions` 与 `skill-authoring`（技能目录本来在这里，不新起服务：目录与设置的主人就是宿主 Agent 定义，第 08 批定）；界面在工作台能力包页 |
| 6 | 表与存储 | 四张新表归 `agent-definitions`，2 → 3 只建空表；只在 `apps/local-host` 里读写，不是共写的表，不登记 `table-owners` |
| 7 | 兼容与迁移 | 只建空表的升级段一条，按「当前保留机制」登记；用户 2026-11-16 已确认。不读旧形状 |
| 8 | 安全边界 | 碰提示注入面（Agent 可起草）：起草不生效、采用只给本人，补 `S-skill-authoring` 的拒绝测试（Agent 调采用被拒、Agent 起草的草稿不进目录、回放不能调工具）；试用不越过 `HostCompleteText` 口 |
| 9 | 调用次数 | 打开草稿一次读（草稿＋已知答案＋最近回放一起回）；边写边存去抖、一次一请求；一次回放 ≤ 入口数 × 版本数 ＋ 1 次模型调用、一次写库；版本列表一次读发布 |
| 10 | 升级与数据 | 已有自己的技能、设置、用量不动；第 41 批的包照常是第 1 版历史 |
| 11 | 成果与过程项 | 不涉及：技能是能力包内容，不进成果库 |
| 12 | 页面、外壳与文字 | 在能力包页与助理对话的现有位置；新文字用 `workbench.skill-*` 键；页面资源增长先量，超 10 KB 先问 |
| 13 | 错误 | 新错误码用 `defineErrorCodes` |
| 14 | 冲突面 | `services/skills` 合同（C1）；宿主 `agent-definitions`；能力包页（D 轨标本）；在途 PR 无人碰这几处（#1743 核过） |
| 15 | 全局最优 | 见下 |

**第 15 项五个场景。** 插件：第三方技能包同样能被「改一份我的」、被回放，作者不多做事。平台：不新起服务，草稿与回放挂在技能目录的主人上；试用借宿主已有的有界文字调用，按构造无副作用；观测用已有的 `trial` 来源。助理：起草、回放可被助理发现和调用，结果用平台已有回执；采用留给本人。各类平台能力：统一输入的 `/` 点名照旧只认已安装版本；评测服务（第 30 批）管真实工作记录的端到端评测，技能回放是采用前的单次对照，两者用同一套判定词（一致／不同／判断不了）但不共用存储——比较过把已知答案做成评测样本（`evaluation.samples.put`）：评测样本建在观测记录上、执行器不按需调模型，硬塞要在评测里加一条按需推理的执行路径，代价大于收益，第二个使用者（如提示词试用）出现时再看是否收进评测服务。后续开发：第 62 批的方法链、第 43 批的 Dataset 可以拿已知答案当样本来源；再加一种可试用的内容（提示词）只需换回放里的那段正文。

## 6. 平台能力检查（第 4.1 节）

1. 别的插件会不会也要做：技能来自任何包，定制与回放对所有包一样；提示词编辑（能力包）将来可能要试用——目前只有技能一个使用者。
2. 平台里有没有现成的：有，全部接上——签名安装（`plugins.local_packages.sign`＋安装服务）、发布保留（版本）、`HostCompleteText`（试用与改写）、`withObservationSource("trial")`（区分记录）、`ActionResultView`（对话回执）、`compareTexts`／`renderDiff`（对照）、`KitEntry.version.change`（来源有新版）。
3. 是不是插件之间协作的问题：不是。
4. 第三方插件能不能同样做到：能，技能包作者不用做任何事。
5. 助理和 Agent 能不能发现、调用：起草、回放能；采用、启用、排期故意只给本人。

结论：**用现成的**，缺的（草稿、已知答案、回放）补在技能目录的主人上，不另起服务；试用的回放引擎暂不收进评测服务，第二个使用者出现时再收。
