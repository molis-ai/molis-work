## 1. 背景

三例的时间都从**第一条命令创建**起算，单位 ms。名词：
- 限 = 命令自己的 `timeoutMs`；
- 宽限 = `cdp.ts:62` 的 `DIAGNOSTICS_GRACE_MS = 150`，从超时判定那一刻起算；
- 读取 = `TimeoutProfiler` 读采样（`Profiler.stop`），用例里由 helper 拖慢；
- 余量 = 两个定时器到期时刻之差。Node 按到期时刻的先后跑定时器，同一个批次里前一个回调后面的 promise 链会先跑完，再轮到下一个，所以余量是「到期时刻差」，机器卡一下不会把先后颠倒，卡住的是**之后才创建**的定时器。

### 1.1 超时路径（`cdp.ts`，只读）

- `:307-350`：限到期，`setImmediate` 让出一轮检查阶段，再决定超时（`:310-313`），记 `decidedAt`（`:320`）；
- `:339-343`：**先**建宽限定时器（`setTimeout(…, 150)`），`:348` 再调 `profiler.recent(started)`，和宽限赛跑；
- `:187-192` `recent`：读取排进 `finishSegment`（`:221-237`）的串行队列；这一步里先 `Profiler.stop`，再读 `this.segmentStarted`，再 `beginSegment()` 重启采样（`closed` 时不重启）；`nodeSelfTimeComplete` 是 `windowStarted >= read.segmentStarted`；
- `:194-203` `close()`：置 `closed`、清轮换、直接 `this.session.disconnect()`，不等读取（T-036 头 `e381756ae` 的修法；`da5d9fc16` 里这里先 `await this.finishSegment()`）；
- `ChromeHarness.close()`（`:391-401`）：清掉**还在 `pending` 里**的命令的定时器，然后 `await this.profile?.close()`。判定超时的命令早已离开 `pending`，宽限定时器在闭包里，`close()` 碰不到，所以读取期间 `close()` 以后，命令仍在宽限到期时拒绝。

核过 `cdp.ts`，没有发现产品问题：`close()` 不等读取、读取队列里读起点与停采样在同一步里，都与二审说的一致。本单不改它。

### 1.2 helper（`browser.test.mjs:248-261`，原样）

```js
/** Delays handing back the first `Profiler.stop` result, modelling a slow read of the sample. */
async function withDelayedProfileStop(delayMs, run) {
  const original = Session.prototype.post;
  let delayed = false;
  Session.prototype.post = async function post(...args) {
    const result = await original.apply(this, args);
    if (args[0] === "Profiler.stop" && !delayed) {
      delayed = true;
      await new Promise((resolve) => setTimeout(resolve, delayMs));
    }
    return result;
  };
  try { await run(); } finally { Session.prototype.post = original; }
}
```

真正的 `Profiler.stop` 在微任务里就完成了，之后**多等 `delayMs`** 才把结果交回去：这就是「读取被拖住」。`withHungProfileStop`（`:263-274`）是另一个，读取永远不回。

### 1.3 `:370` slow-read（RAC-1452），不改

原文 `:370-391`：

```js
test("a slow profile read cannot postpone the timeout past its grace, and elapsed says how long it waited (RAC-1452)", async () => {
  await withDelayedProfileStop(400, async () => {
    await withHarness(() => {}, { profileTimeouts: true }, async (harness) => {
      const started = performance.now();
      // RAC-1452: with `profileTimeouts` on the rejection still lands between the limit and limit + 250 ms, even when the
      // bounded profile read is slower than its grace. Same clock as the harness, so `elapsed` can be held to the wait.
      await assert.rejects(harness.command("Never", {}, undefined, 100), (error) => {
        const settledAfter = performance.now() - started;
        assert.ok(settledAfter >= 100 && settledAfter <= 350, `settled after ${settledAfter.toFixed(1)}ms, outside limit..limit + 250`);
        const stated = Number(/\(elapsed (\d+)ms; limit 100ms\)/.exec(error.message)?.[1]);
        assert.ok(stated >= 140, `elapsed ${stated}ms includes the profile wait`);
        assert.ok(stated <= settledAfter, `elapsed ${stated}ms claims more than the ${settledAfter.toFixed(1)}ms the caller waited`);
        assert.ok(error.diagnostics, "Chrome counters still ride along without the profile");
        assert.deepEqual(error.diagnostics.nodeSelfTime, [], "no samples without a profile");
        assert.equal(error.diagnostics.nodeSelfTimeComplete, false, "an unread profile does not claim coverage");
        assert.ok(error.diagnostics.profileReadMs >= 140, `profileReadMs ${error.diagnostics.profileReadMs} says how long the read held the rejection`);
        assert.ok(error.diagnostics.profileReadMs <= settledAfter, "the bounded read cannot outlast the settlement");
        return true;
      });
    });
  });
});
```

数：限 100，读取 400 > 宽限 150，所以命令在宽限处拒绝：
- 判定在 100（加至多一轮检查阶段），宽限到期在 100 + 150 = 250，读取要到 500，所以拒绝落在约 250；
- `settledAfter ≈ 250`：下界 `>= 100` 余量 150；**上界 `<= 350` 余量 100**；
- `stated`（`elapsed`，向下取整）≈ 250：`>= 140` 余量 110；`<= settledAfter` 恒成立（`stated` 比 `settledAfter` 先量、又向下取整）；
- `profileReadMs ≈ 150`（宽限定时器的实际等待）：`>= 140` 余量约 9，是下界，定时器至多早 1 ms 触发，晚了只会更大，不会因机器卡而红；`<= settledAfter` 余量约 100。

**上界余量 100 是产品承诺自带的**：`cdp.ts:56-61` 的注释承诺失败落在 `limit` 到 `limit + 250`，宽限 150，差 100 就是留给调度延迟的。测试一侧没有常量能改它：
- 把读取延迟 400 改小或改大，拒绝时刻都是 `限 + 宽限`，只要读取比宽限长；
- 把限 100 改成别的数，350 也是 `限 + 250`，余量不变；
- 把 350 放宽等于放宽产品承诺，不许；把宽限改小要改 `cdp.ts`，不在本单。

所以这一条不改。余量 100 ms 只在这里写明，PR 正文也照抄一句：以后这一例偶发红先看机器是不是卡了 100 ms 以上。

### 1.4 `:417` close-during-read（T-036 头的 `:393`），区分力弱

原文 `:417-439`：

```js
test("a close during the bounded profile read still rejects the timed-out command (RAC-1452)", async () => {
  await withDelayedProfileStop(400, async () => {
    const devtools = await fakeDevTools(() => {});
    const harness = await ChromeHarness.connect(devtools.url, { profileTimeouts: true });
    try {
      const command = harness.command("Never", {}, undefined, 100);
      // Past the timeout decision, while the bounded read is still waiting: closing must stop the read and keep the
      // rejection the command already earned.
      await new Promise((resolve) => setTimeout(resolve, 240));
      const closing = harness.close();
      const error = await command.then(
        () => { throw new Error("a timed-out command must not resolve"); },
        (rejection) => rejection,
      );
      assert.match(error.message, /^CDP timeout: Never \(elapsed \d+ms; limit 100ms\)$/);
      assert.deepEqual(error.diagnostics.nodeSelfTime, []);
      assert.equal(error.diagnostics.nodeSelfTimeComplete, false);
      await closing;
    } finally {
      await devtools.close();
    }
  });
});
```

数：限 100，读取 400，宽限到期在 100 + 150 = 250；睡眠 240，所以 `close()` 在 240，比宽限早 10。

「区分力弱」指的是：**断言在错误的 `close()` 下也会过**。逐个看，命令的拒绝来自宽限定时器（250），与 `close()` 做了什么无关：
- `close()` 什么都不做（M2：去掉 `this.session.disconnect()`）：`closing` 立刻完成，命令在 250 按宽限拒绝，断言全绿；
- `close()` 等读取（M1：`da5d9fc16` 的写法，断开前先 `await this.finishSegment()`）：`closing` 要到约 500 才完成，命令在 250 照样按宽限拒绝；末尾 `await closing` 多等 250 ms，断言全绿；
- 只有 `close()` 让命令永远不拒绝（M3）才红，而且是挂住，没有断言。

前提也靠时钟：10 ms 的先后差（`close` 要在宽限之前）。顺序是稳的（睡眠定时器到期 240 早于宽限 250，卡住时按到期先后跑），但**这一例没有任何一句断言能看出 `close()` 取消了读取或没等读取**。二审说得对：真正证明 `close()` 不被拖住的是 `:441` 的 hung-read 例，它在 M1 下挂住，所以红。M2 没有任何一例钉住（本单的新例钉）。

### 1.5 `:467` queued-read（T-036 头的 `:443`），余量偏紧

原文 `:467-479`：

```js
test("a profile read queued behind another times its window against the segment it was taken from (RAC-1451)", async () => {
  await withDelayedProfileStop(80, async () => {
    await withHarness(() => {}, { profileTimeouts: true }, async (harness) => {
      const first = harness.command("FirstSlow", {}, undefined, 30).catch((error) => error);
      await new Promise((resolve) => setTimeout(resolve, 40));
      const second = harness.command("SecondSlow", {}, undefined, 30).catch((error) => error);
      const [firstError, secondError] = await Promise.all([first, second]);
      assert.equal(firstError.diagnostics.nodeSelfTimeComplete, true);
      assert.equal(secondError.diagnostics.nodeSelfTimeComplete, false,
        "the second window started before the segment its profile came from");
    });
  });
});
```

它钉的是 RAC-1451：排队的第二次读取，要拿**它那一步里读到的段起点**去比窗口起点（`cdp.ts:190`）。错误写法（Q1）是在**请求时**读 `this.segmentStarted`：这时第一次读取还没重启，读到的是旧段的起点，第二个窗口（比新段早）就会被说成「完整」。

要红在 Q1 下、绿在正确实现下，三件事必须同时成立（限 30，宽限 150，读取延迟 D，第二条命令晚 S 创建）：
- **A1**：第一次读取在它**自己的宽限内**读完，否则第一次没有读到采样，`nodeSelfTimeComplete` 是 false，第一句断言红。判定在 30，宽限到期 30 + 150，读取结束 30 + D：余量 `A1 = 150 − D`；
- **A2**：第二次读取也在它自己的宽限内读完，否则第二个窗口是被宽限掐掉的，false 与实现无关，Q1 也过（空过）。第二次判定在 S + 30，宽限到期 S + 30 + 150，读取在第一次读取之后立即完成，也是 30 + D：余量 `A2 = 150 + S − D`；
- **B**：第二次读取**在第一次读取重启采样之前**被要求，否则 Q1 读到的也是新段起点，false 与实现无关，Q1 也过（空过）。第二次请求在 S + 30，第一次读取结束在 30 + D：余量 `B = D − S`。

算：

| | 算式 | 现在（D=80，S=40） | MISC 原话（D=50，S=20） | 本单（D=75，S=0） |
| --- | --- | --- | --- | --- |
| A1 | 150 − D | 70 | 100 | 75 |
| A2 | 150 + S − D | 110 | 120 | 75 |
| B | D − S | 40 | 30 | 75 |
| 最小 | | 40 | 30 | 75 |

- MISC 说的「余量约 70 ms」是 A1。真正最紧的是 B（40），二审没提。
- T-152 的任务书（第 3 节）拿第二条命令的**创建**时刻（S）去比第一次读取结束（30 + D），得 70 和 60。要比的是第二次读取**被要求**的时刻：它在限到期、让出一轮检查阶段之后才发起（`cdp.ts:307-348`），是 S + 30，所以 B = D − S，是 40 和 30。T-152 第 8 节第 4 条的「读取延迟 60、晚 5 毫秒」按这个算也只有 A1 = 90、A2 = 95、B = 55，最小 55，不如 75。
- A1 + B = 150 − S：A1 要 D 小，B 要 D 大，两个加起来被 S 吃掉。**S = 0 时两个都能到 75，是 D = 75。** 所以去掉睡眠，不是调它。
- 照 MISC 的「降到 50、晚 20」，A1 好了（100），B 反而从 40 掉到 30，最小余量更差，所以不照字面改。
- 去掉睡眠还让 B 不再依赖钟：两条命令在同一个同步段里创建，限相同、起点相同（Node 用循环开始时缓存的时间算），两个定时器在同一轮定时器阶段里先后触发，两个 `setImmediate` 在随后的同一个检查阶段里依次跑，第二次读取一定在第一次读取（一个 75 ms 的定时器）之前被要求。睡眠版本里，第二条命令是**睡眠到期之后才创建**的，卡一下就会把它推到第一次读取结束之后。

     ```js
      * Delays handing back the first `Profiler.stop` result, modelling a slow read of the sample. `run` gets `read`: `began`
      * resolves when that read starts, `over` turns true when it hands the sample back, `disconnects` counts the
      * `Session.disconnect()` calls made while `run` is going.
      */
     async function withDelayedProfileStop(delayMs, run) {
       const original = Session.prototype.post, originalDisconnect = Session.prototype.disconnect;
       let delayed = false, begin;
       const read = { began: new Promise((resolve) => { begin = resolve; }), over: false, disconnects: 0 };
       Session.prototype.post = async function post(...args) {
         const result = await original.apply(this, args);
         if (args[0] === "Profiler.stop" && !delayed) {
           delayed = true;
           begin();
           await new Promise((resolve) => setTimeout(resolve, delayMs));
           read.over = true;
         }
         return result;
       };
       Session.prototype.disconnect = function disconnect(...args) {
         read.disconnects += 1;
         return originalDisconnect.apply(this, args);
       };
       try { await run(read); } finally { Session.prototype.post = original; Session.prototype.disconnect = originalDisconnect; }
     }
     ```

## 8. 与默认不同的

1. **不照 MISC 的「降到 50、晚 20」，改成 75、不隔。** 理由是第 1.5 节的算式：`A1 = 150 − D`、`A2 = 150 + S − D`、`B = D − S`。照字面是 100/120/30，最小余量 30，比现在的 40 更差；去掉睡眠、D=75 是 75/75/75，而且 B 不再靠钟。模型里「晚 20」那一版在 100 ms 卡顿下 Q1 漏过的次数和现在的一样多（29/40）。统筹要照字面改：第 5 节第 1 条 `:467` 一例里把 `75` 改成 `50`，在两条 `harness.command` 之间加回 `await new Promise((resolve) => setTimeout(resolve, 20));`，`profileReadMs >= 50` 改成 `>= 30`，第 6 节 P1、P3 的数字跟着改。不建议。
2. **`:370` 不改。** 理由是第 1.3 节：上界 350 就是产品承诺 `limit + 250`，余量 100 来自宽限 150，测试一侧没有常量能改；放宽 350 不许，缩小宽限要改 `cdp.ts`。MISC 写的「余量约 100 ms」是一个事实的登记，不是要修的缺陷。统筹要在 `:374-375` 的注释里写这一句，也可以：加在已有的两行注释里（不加行，行号不动）。
3. **`:417` 整例重写，不是改一个常量。** 只改常量（比如睡眠）无法让它在 M1、M2 下红：命令的拒绝来自宽限定时器，与 `close()` 无关（第 1.4 节）。要红，必须看 `close()` 返回时读取有没有结束、会话有没有断开，这就要 helper 记状态。
4. **helper 多出三个字段，加一个小 helper `settledOrHung`。** `:441` 里已有一个内联的同样竞速，没有合并：它不在本单的范围，合并会让 diff 变大。
5. **读取一开始就关，不睡一段再关。** 睡一段是时钟：睡早了读取还没开始，睡晚了宽限已经到期，两种都让用例变成空过或误红。`read.began` 之后到 `close()` 之间只有微任务，顺序由事件循环保证。
6. **档乙、池。** 档的理由见表。池的依据见表：一个真 Chrome 都不起。统筹要派给 A 也行，没有区别。
7. **两个号。** `RAC-1829`、`RAC-1830` 各对应一个用例；`RAC-1451`、`RAC-1452` 原有的用例不变。统筹要合成一个号，改两个用例标题和第 6 节。`RAC-1831`、`RAC-1832` 留空。
8. **`profileReadMs >= 50` 是新增的断言**，不是放宽。它让「读取补丁没生效」从空过变成红。
9. **模型不是证据，只是预演。** 第 1.5 节、第 6 节的表来自起草线在草稿目录外写的 Node 内置模块脚本，逻辑照 `cdp.ts` 搬的。真正的证据是第 5 节步骤 4、6 在真代码上的结果；两者不一致时以真代码为准，停下贴出来（第 11 节）。
