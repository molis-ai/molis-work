## 给人讲清楚

各个插件里有不少一样的小工具各写了一份，有些页面打开一次要在背后做几万次重复检查，所以慢。这一批把公共的部分收成一份给所有插件用，再把这些重复的调用减下来，并加两道检查（一道数代码写法、一道真实打几个请求数次数），防止以后又悄悄变多。另外，那个内置的「文件」插件（浏览项目文件夹、做文件快照和选区）要退役：文件浏览、阅读、快照和引用入口搬到工作台公共界面，来源归「项目资料」，旧的过程项、快照和引用迁移后还能读。做完以后，同样的操作反应更快，插件作者不用再自己重写这些东西，所有插件的文件浏览是同一套。需要你做的：①看新文件界面和选择器的样子并定下（这次有新增界面）；②中途如果排期压不住，按方案里的止损点把「文件」退役单独挪到后面的批次。

**E. 设计稿（#1771）没有覆盖、实现前要补的缺口**

1. **浏览选择的去向。** 设计稿 §4 说「面板正在看哪里不进任何合同」，但现在 `projects.settings.browsing-workspace.read／select` 是合同，`project_browsing_settings` 是项目库表，Files、Git、Coding、助理环境（`assistant-surroundings.ts`）都在读它。设计稿 §8 存量数据只写了 `is_default`。要补：这两个动作和这张表是删、保留还是改成页面状态；Git 和 Files 之后读什么。
2. **`repair` 与引用。** `workspace_id` 由路径哈希，`repair` 换路径就换 id 并删旧关联；设计稿的 `MaterialRef.subject` 用 `<workspace_id>:<相对路径>`，`repair` 之后旧引用会指向不存在的 id。要补：`repair` 是否保持 id 不变（改成与路径脱钩），还是给旧 id 到新 id 的重映射；这直接决定 SSC-02 和「历史引用不变」（WMD-04）能不能成立。
3. **隐含单目录取法**（C 表）有十几处，设计稿只说「各插件读同一份配置」；要补：没传 `workspace_id` 时一律取输出目录，还是改成必须显式传。Schedule 的唤醒、Goals 终端、到达页都是靠这种隐含取法。
4. **Coding 把浏览和执行混在一起**（B 表 Coding 行）。设计稿把二者分开了，但 Coding 的浏览器代码要整块改；这部分归 B 轨，借 `assistant-executor.ts` 的部分归 A 轨（轨道规则 7）。
5. **`workspaceRefFor` 的注释与行为不符**：授权目录实际是「所有已验证目录」，所以现在不会因此多放权，但改 `roles` 时必须明确「输入目录能不能被 Agent 写」。设计稿 §4 已写「只有输出目录可写」，实现时要有对应的拒绝用例（开工前检查第 8 项）。
6. **没有迁移机制**：`modules/projects` 没有升级步。按设计稿 §8，如果在 U1 之前落就直接改第 1 版建表，所以 05② 的实现要等清空重建（02③）的时点定下来。
7. **Files 退役的数据维护**（D 表）：端口输出与绑定、同意记录、安装记录要重写或删除，过程项的 `producer_*` 要换成新主人；WMD §6 要求「不能连带丢失历史过程项」。承接方没有定，WMD 也写明「不提前虚构一个新文件存储包」。→ 统筹 2026-11-04 已定去向，见本节末「Files 退役的去向」。

E 表第 1～7 条已由合同台补进 #1771（`specs/shared-sources-and-surfaces/spec.md` 第 3、4、8、9 节，SSC-15～17）：浏览设置删掉、改成页面状态；目录 id 与路径脱钩，`repair` 不换 id；没写目录一律取输出目录；只有输出目录可写；Coding 的浏览与执行拆开（B 轨，`assistant-executor.ts` 的部分 A 轨）。
