## 1. 背景

批 C 把 Feed 与 Inbox 收进了 Plugin Runtime，宿主里为它们手写的装配基本删光了。`information.plan`（信息助手，起草筛选或写作方案）是平台自己的 `system.information` 提供方，按 PG-031 的裁定不算特权，但它还从 Feed、Inbox 两个插件包里 import 描述符（`apps/local-host/src/information-actions.ts:3-4` 的 `feedQueryActions`、`inboxActions`），planner 还 import 了 Feed 的类型（`apps/local-host/src/information-planner.ts:3` 的 `FeedSnapshot`）。跨模块只走公开合同：该用能力 id 和输入输出形状，不用对方的实现。门禁数字上，`tooling/gates/baseline.json` 里 `pluginOutsideMentions` 的 `feed#outside-files` 是 16，`inbox#outside-files` 是 7，这三处 import 是其中的 2 个和 1 个文件。

## 2. 目标

1. `information-actions.ts` 与 `information-planner.ts` 不再出现 Feed、Inbox 两个包的名字；`information.plan` 通过能力 id（`feed.snapshot@1`、`inbox.list@1`）读取，行为、权限、可用性判断、错误码一概不变。
2. `informationActions.plan.action.required_actions` 仍是两条只有能力 id 和版本、没有 `provider_id` 的依赖，并且 id 与两个 owner 包里现行的定义相等（有测试盯住，owner 改名时变红）。
3. `node scripts/check-health-gates.mjs --base origin/main` 里 `feed#outside-files` 从 16 变 14，`inbox#outside-files` 从 7 变 6。

## 3. 不做

- 宿主里其他还 import Feed、Inbox 包的文件：`web-view.ts:4`、`web-panel.ts:6`、`web-request.ts:3`、`native-content-permissions.ts:1`、`source-vocabulary.ts:2`、`source-pull-runtime.ts:9`、`demo-feed-library.ts`、`demo-plugin-seed.ts:2`、`index.ts:103` 等。它们不是同一种改法（有的和 Feed 客户端搬出工作台绑在一起，PG-093 的另一半），不做，也不另开行。
- 把 `information-actions.ts` 与 `information-planner.ts` 并进 Feed 包：`slices/feed-inbox-runtime-plugins.md:34` 的旧计划，被 PG-031 的裁定取代，不做；那个文件被 T-007 锁定，也不碰。
- `information.plan` 的提示词与模型调用（`information-actions.ts:27` 的 `hostCompleteText`、`:39` 的 `resolveModelPrompt`）：不动。
- `specs/repository-anti-corruption/ai-entry-inventory.md:107` 提到 `information-actions.ts`：只是列名，不改。
- 把 `FeedSnapshot` 的完整形状搬进合同包：不做，planner 只声明它自己读到的几个字段。

## 5. 做法

已定的决定：

- 取数方式：`ActionClient.invoke(context, reference, input)`（`packages/contracts/src/platform/actions.ts:546-549`）接受只有 `capability_id` 和 `version` 的引用，返回 `unknown`。现在的 `bindActionClient(client, () => nested).invoke(definition, input)` 在没有 control 参数时就是 `client.invoke(nested, definition, input)`，所以直接传引用等价。照 `apps/local-host/src/side-files-http.ts:107` 的写法（`client.invoke(caller, referenceOf(reader), …) as ActionSubjectContext`）。返回值的运行时校验由动作调度按 owner 声明的 output schema 做，宿主不重复校验。
- 引用写成本文件里的两个常量，同时给 `required_actions` 和 `invoke` 用，不要在两处各写一遍字面量：`{ capability_id: "feed.snapshot", version: 1 }`、`{ capability_id: "inbox.list", version: 1 }`。不加 `provider_id`（`plugin-query-consumers.test.ts:123` 已经要求）。
- 输入仍是 `{}`，与现在一致。
- planner 的最小输入类型只含：`sources`（`source_id`、`name`、`enabled`）、`feed_items`（`item_id`、`source_id`、`title`、`summary`）、`inbox_entries`（`entry_id`、`subject_type`、`subject_id`、`status`）。真实的 Feed 快照对象结构上满足它，`tests/feed-inbox-pages-loop.test.ts` 和 `tests/host-configured-text.test.ts` 直接把真实快照传进 `planInformationWork`，不用改。
- 结构测试断言用一个正则片段，例如 `/molis-work-plugin-(feed|inbox)/`，不必写出两个包的完整名字。`pluginOutsideMentions`（`scripts/gates/assembly.mjs:173`）只数非测试的源文件（`isSource` 排除 `tests/`）、各 `package.json` 与 `scripts/*.mjs`，且排除生成的文件，所以测试里写包名不影响数字；但这条测试要读的就是「这两个源文件里没有包名」，写法保持这个意思。
- 数字依据：在 main `0262a6d21` 上按这条门禁的口径数，Feed 在包外被点名的文件是 16 个（含 `information-actions.ts`、`information-planner.ts`），Inbox 是 7 个（含 `information-actions.ts`），与 `baseline.json` 的 494、500 行一致；这两个文件的名字去掉后是 14 和 6。`apps/local-host/package.json` 的依赖仍留着（别的文件还点名），不在这一片动。

乙档【方案】里要回答的问题：

1. 两个能力引用常量放在 `information-actions.ts` 还是单独一个小文件；`informationActions` 在 `local-owner-permissions.ts:10` 也被引用，确认引用方式不受影响。
2. `snapshot` 与 `entries` 的最小类型各写几个字段（列出来），以及从 `unknown` 转成这些类型用单次 `as`，不用 `as unknown as`（门禁数字不许涨）。
3. 取数从 `bindActionClient` 换成直接 `client.invoke` 之后，`caller.signal`、`caller.beforeEffect` 的传递（第 38-39 行 `planInformationWork` 的第五个参数 `{ signal, beforeDispatch }`）是否还完全一样；对照 `plugin-query-consumers.test.ts:92-123` 的两个阶段（dispatch、response）说明。
4. 结构测试读源文件文本，是否有更合适的现成写法（例如 `tests/` 里已有读源码文本的边界测试），先找再答。
