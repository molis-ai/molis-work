# Molis Work 的 killer 场景

最近更新：2026-10-18 · 依据 main `5f03d1e45`、全部分支与 spec、[外部补研](research/2026-10-18-外部补研.md)、[角色与使用链路](角色与使用链路.md)。成熟度标签见 [README](README.md#成熟度标签)。

这份文档从[角色与使用链路](角色与使用链路.md)的一百多条链路里，挑出最值得拿去推广和做用户运营的几条：为什么是它们、怎么演、怎么验证、推之前产品还要补什么。

---

## 1. 结论先说

**定位：Molis Work 是你用的那些 AI 之下共用的一层工作台。** 用哪家 AI 都行；目标和资料放在同一处，"做到哪、等你什么、算不算完、依据是什么、AI 能动什么"也都在这里查。

这个定位来自外部补研的判断：Claude、ChatGPT、Cursor、Notion 已经把"项目 + 记忆 + 定时 + 连接器 + 审批提示"打包进订阅，**和它们比谁更会干活没有胜算**；它们的总览、记忆和验收都只管自家的 Agent。跨厂商的中立层、把"算不算完"做成一等对象、把采用的依据固定到当时的版本，这三处没有人做全（[外部补研 §1、§6](research/2026-10-18-外部补研.md)）。

| 用途 | 场景 | 一句话 | 成熟度（瓶颈环节） |
| --- | --- | --- | --- |
| **现在主推** | **K1 多个 AI，一本账** | Agent 说做完了，Work 说还差你 | 已发布核心；瓶颈：安装包、Claude Code 原生会话 |
| **现在主推** | **K2 交出去的判断，答得上依据** | 交出去的每一份结论，都留着当时的依据 | main 可用；瓶颈：账号来源 OAuth、来源变化复核 |
| **现在主推** | **K8 你答应的、在等别人的，分开记**（新） | AI 抽了 8 件事，Work 说 3 件你已经记过、1 件在等法务 | main 可用（需模型）；瓶颈：没有按月重复、提醒只在这台电脑上 |
| 开发中演示 | **K3 一句话长出你和 AI 共用的工具** | 缺个工具？说一句，它就在工作台上，你的 AI 也会用 | main 部分；瓶颈：生成插件不是一等公民、成功率 |
| 开发中演示 | **K4 你攒下的做法，换哪个 AI 都在** | 规则和做法写一次，你用的每个 AI 都照着做 | main 部分；瓶颈：技能包只在 spec |
| 开发中演示 | **K5 第一天就有内容** | 把材料丢进来，一分钟读完你现在在做什么 | main 部分；瓶颈：正式 OAuth、首日旅程 |
| 愿景 | **K6 早上打开，工作已经理好** | 不用开口，打开就知道今天先做什么 | 规划；最小切片见建议 E0 |
| 愿景 | **K7 一封客户邮件，变成团队的一个目标** | 讨论、决定和 AI 的工作在同一处 | 规划（团队协作依赖服务端） |

另有三条**支撑场景**，不单独拉新，但每个 killer 的演示里都会用到：**S1 选中就交出去，结果回到原处**；**S2 重复的处理，存成你说了算的流程**；**S3 AI 能动手，但动不了不该动的**。

读者的主线：**写代码的人从 K1 进**，接 K3、K4；**写文档、做研究的人从 K2 进**；**管事情的人（项目、交付、自由职业、财务、人事）从 K8 进**；后两条都接 K5、K3，以 K6 收尾。K1 还有一个**约定版**，讲给不写代码、但要对客户或上级交付的人。K7 放在最后，标"开发中"。

K8 和 K1 约定版是这一轮从[角色与使用链路](角色与使用链路.md)的 136 条链路里补出来的：同一种用法在十几个角色身上反复出现，四组起草时也各自把它选成了某个角色的 killer。

## 2. 怎么挑的

### 打分维度（每项 1–5 分）

| 维度 | 问什么 | 5 分的样子 |
| --- | --- | --- |
| 痛感 P | 这件事多常发生、多疼，有没有外部证据 | 每周都发生，出错有明确代价；有调查数据或大量社区原话 |
| 契合 F | 用到几项 Work 的根本机制，替代方案要拼几样工具 | 至少两项机制叠加；熟练用户要拼三个以上工具、还得手工维护一份账 |
| 起步 T | 不搬家能不能开始，从装好到第一次"啊哈"多远 | 不迁移旧资料，从下一件事开始；十分钟内看到结果 |
| 演示 D | 60 秒能不能演出反差 | 有一个"AI 说……，Work 说……"式的反转 |
| 覆盖 B | 能跨多少角色复用 | 换个对象，五类以上角色都在用同一条链 |
| 传播 S | 产出能不能被分享、复用 | 产出本身是可分发物：插件、流程、技能包、带出处的报告 |

**总分 = 2P + 2F + T + D + B + S**，满分 40。痛感和契合加倍：不疼、或者别人一个工具就做得很好的场景，演得再好也留不住人。

**成熟度单独记，不进总分**，只决定用途：瓶颈在已发布或 main 可用的"现在主推"；在 main 部分或分支的"开发中演示"（官网可以"开发中 · 示意"全演，同时进产品优先级）；在规划的放"愿景"。

**淘汰条件**：熟练用户在一个现成工具里已经做得同样顺；价值只是"都在一个地方"，说不出少了哪次搬运、重讲或核对；要先把整个工具栈搬进来才有价值；依赖团队全员同时使用（团队协作上线前）。

**几处打分的理由：**

- **K1 契合 5**：Claude `/goal` 和 Codex Goals 只在一个会话里、由模型对着对话自判；并行桌面（Conductor、Superset）以工作区和分支为单位；Traycer 要登录、同步到云、由评审 Agent 判完成；仓库规格文件天然跨厂商，但没有一家在动作层拦住 Agent 改要求或替自己批准。"几家共享同一份目标 + 逐条要求 + 收尾看依据 + 改要求要人批"四样凑齐的，内部官网调研和本次补研都没找到。
- **K2 契合只给 3**：带引用回答已经是 NotebookLM、Readwise、Capacities 的标配。Work 能讲的只有"随成果固定当时采用的材料版本，并一路带到演示稿、待办和目标交付物"，不是"有引用"。
- **K3 痛感只给 3**：想要顺手的小工具是真的，但"个人小工具难维护"是社区里最稳定的反对声；所以 K3 的说法必须是"做出来的东西你不用自己养"，而不是"AI 帮你写软件"。
- **K4 起步 5、传播 5**：从 Claude Code、Codex 已有的规则和 Skills 导入，零迁移；做法本身就是可分享的东西。它是最好的**增长入口**，但单独作为用户故事不够有画面，所以不放首屏。
- **会议转行动项**：Granola 已经很强，Anthropic 对 120 万条 Cowork 会话的分类里"会议智能"只占 1.8%，Work 也没有会议采集。不投入。这里不做的是**会议采集**；从已有的纪要、邮件里分出"你的承诺"和"在等别人的事"是另一回事，见 K8。
- **K8 契合只给 3**：会议工具抽行动项、任务管理器记"等待"都已经成熟。Work 能讲的是一串连起来的事：和你已有的待办比对去重，"下周三"由程序换成日期，每条指回原句，等别人的单独追踪，再挂到目标上。痛感和覆盖都给 5：项目、产品、交付、销售、财务、人事、自由职业、个人事务都在用（[模式 4](角色与使用链路.md#模式-4-你答应的在等别人的分开记)）。

## 3. 主推场景

每个场景按同一结构写：一句话 → 给谁 → 触发 → 原来怎么做、卡在哪 → Work 怎么做 → 60 秒演示 → 官网文案 → 为什么是 Work → 成熟度与瓶颈 → 推广与运营抓手 → 怎么验证、什么会推翻它 → 不适合谁。代表链路编号指向[角色与使用链路](角色与使用链路.md)。

### K1 多个 AI，一本账

> **Agent 说做完了，Work 说还差你。**

**给谁：** 同时用两个以上 AI 编码工具的独立开发者、技术负责人、开源维护者。Stack Overflow 2026 年的调查里，Agent 用户中 Claude Code 占 66%、Copilot 59%，至少四分之一两个都用；约三分之一用多 Agent，而且是最活跃的那批。

**代表链路：** [DEV-01](角色链路/A-写代码与技术.md#dev-01-测试全绿了可退款在手机上我还没亲手点过)、[AIDEV-01](角色链路/A-写代码与技术.md#aidev-01-四个-agent-同时在跑我不知道哪个卡在等我)、[AIDEV-02](角色链路/A-写代码与技术.md#aidev-02-周一-claude-code-写到一半周三换-codex-接着做周二我改过接口约定)、[TL-02](角色链路/A-写代码与技术.md#tl-02-冲刺中途范围变了我派出去的四个-agent-都得立刻知道)、[QA-01](角色链路/A-写代码与技术.md#qa-01-发版前-12-条关键路径开发说好了我要亲手过其中-5-条)、[OSS-01](角色链路/A-写代码与技术.md#oss-01-周六上午清-issue30-条新的里挑出能复现的交给-agent)

**触发：** 周一 Claude Code 写前端，周三换 Codex 接后端；周五 Agent 报"全部通过"，你准备上线。

**原来怎么做、卡在哪：** 仓库里的规格文件、`CLAUDE.md` / `AGENTS.md`、PR 和 CI。每家 AI 有自己的会话、记忆和"目标"，只在自家有效；换工具或隔几天回来要重讲背景。Agent 过早宣布完成是公开记录里反复出现的失败模式（Anthropic 的长任务 harness 文章、Claude Code 有报"ALL PASSED"实际 7 个失败的 issue）。几个 Agent 停在不同问题上，你得挨个去问。

**Work 怎么做：**

1. 功能是一个目标：预期结果、几条要求，其中"手机排版"标为**必须由你验收**。
2. Claude Code、Codex 经内置接入或 MCP 读同一份目标；项目长期说明每轮自动带给每个 AI，不用各写一份。
3. Agent 往同一份里报进度和依据（写明是 Agent 报告）。
4. Agent 想换掉约好的结果、放宽要求、去掉"要你验收"，进决定中心，写明影响，由你决定。
5. 收尾时逐条对：缺依据、缺你的验收、依赖没完、有阻塞顾虑，就不生效。
6. 终端开在目标上；菜单栏显示哪个目标在等你。

**60 秒演示：**

| 镜头 | 画面 | 字幕 |
| --- | --- | --- |
| 1 | 目标"上线支付"，三条要求，第三条带"要你验收" | 一个功能，一份约定 |
| 2 | 周二，开在这条目标上的 Claude Code 报进度：前两条有依据"测试 14/14 · Agent 报告" | 哪个 AI 做的，都记在这里 |
| 3 | 周三，Codex 打开同一个目标，直接读到约定、进度和上周改过的范围 | 换个 AI，不用重讲 |
| 4 | Codex 提议"旧数据兼容改成新装可用即可"；决定中心写明影响结算页两处，你点"不同意" | 改约好的事，要你点头 |
| 5 | Codex 报"做完了"；标题从"进行中 · 1/3"变成"没算完 · 2/3"，菜单栏亮起"等你验收：手机排版" | AI 说完了，不等于完了 |
| 6 | 你在真机上看完，记一句结论，收尾生效 | 算不算完，你说了算 |

**官网文案：** 今天用 Claude Code，明天换 Codex，后天开三个 Agent 并行。它们读写同一份目标：要交什么、做到哪、还差谁确认。Agent 可以报进度、提建议；要换掉约好的结果、放宽要求、替你验收，得你点头。它说做完了，Work 会逐条对一遍。

**为什么是 Work：**

| 熟练替代 | 已经做好的 | 还剩什么 |
| --- | --- | --- |
| Claude `/goal`、Codex Goals | 单会话的完成条件，由模型对照对话自判 | 只在一个会话、一家里；没有人验收这一档 |
| Claude Code agent view、Cursor Projects | 自家 Agent 的"等你回复"总览 | 只管自家 Agent |
| Conductor、Superset、Traycer | 并行、隔离、看 diff、PR；Traycer 有跨 Agent 的规格与评审 | 单位是工作区或分支；Traycer 要登录同步到云、由评审 Agent 判完成 |
| 仓库规格（spec-kit、OpenSpec）+ CI | 天然跨厂商，走 Git 评审 | 没有一家在动作层拦住 Agent 改要求或替自己批准 |

外部证据：近一半开发者只在能自行验证时信任 AI，只有 6.6% 愿意让 AI 参与重要决定（Stack Overflow 2026）；BCG 在 HBR 发表的研究显示用到第三个 AI 工具后生产力不再上升，监督负担高的人更疲劳。

**成熟度与瓶颈：** 目标、要求、本人验收、决定中心、终端、五家接入 + MCP **已发布**（v0.2.0）；新界面与插件动作对外开放 **main 可用**。瓶颈：没有签名安装包（[建议 A1](产品优化建议.md)）；Claude Code 一侧原生会话读不全（B2）；依据都是 Agent 自报，Work 不自己核（B1）；没有系统通知（B3）。

**推广与运营抓手：**

- **入口在别人的生态里**：Work 以一个装进 Claude Code、Codex 的 Skill（`goal-advance`）和 MCP 条目出现；Readwise、Notion 都在这样做。
- **渠道**：Hacker News Show HN、Claude Code 与 Codex 社区、即刻、V2EX；演示视频就是上面六个镜头。
- **激活指标**：第一个目标被两家 Agent 写过进度，并完成一次本人验收。
- **留存回路**：每个新功能开一个目标；菜单栏每天提醒等你的事。

**怎么验证、什么会推翻它：** 找 5 位同时用两家 AI 的开发者，各拿一个真实小功能，三天里换一次 Agent、改一次约定、故意留一条需人验的项。看他们是否停掉了原来的个人追踪表，下一个功能是否还开目标。**推翻**：维护目标比收益大；仓库规格 + CI 已经同样清楚；没人在意 Agent 中间过程。

**不适合：** 只用一个 AI、一次会话就做完的改动；团队已有严格 PR 审批与 QA，且不关心 Agent 过程。

#### K1 约定版：约好的事，改了要你点头

同一套机制讲给不写代码的人。自由职业者的交付范围、律师的谈判底线、客户在方案发出后追加的需求、审稿人的 27 条返修意见、装修的每个节点：先把"交什么、怎样算完、哪几条要你本人验收"写成约定；客户、同事或 AI 想改，进决定中心写明影响，你点头才生效；约定一改，之前的验收作废。

- **一句话：** 说好的事，改了要你点头；交没交完，你说了算。
- **代表链路：** [FREE-02](角色链路/D-专业服务与个人.md#free-02-客户说不是说好包含移动端吗范围写成约定改范围要你点头)、[PM-01](角色链路/B-产品与业务.md#pm-01-评审改了范围prdgoal-约定和开发-agent-读的是同一份现行要求)、[LAW-02](角色链路/D-专业服务与个人.md#law-02-第三轮谈判把底线写成要求每次让步都留下是谁点的头)、[SALES-02](角色链路/B-产品与业务.md#sales-02-方案发出后客户追加老数据也导进来先问清再决定进不进本期)、[ACA-04](角色链路/C-研究内容与教育.md#aca-04-审稿意见回来了3-位审稿人-27-条意见45-天内返修)、[LIFE-05](角色链路/D-专业服务与个人.md#life-05-老房翻新-8-周每个节点验收我说了算付款跟着节点走)
- **60 秒演示（FREE-02）：** 约定三条，"移动端适配"不在其中 → 客户来信"不是说好包含移动端吗" → 打开当时那一版约定和它的决定记录 → 你同意加范围：新增一条要求、写明原因 → 旧验收作废，新约定下重新验收。
- **成熟度：** main 可用，机制与 K1 相同。
- **限制：** 客户和合作者进不了 Work，约定只记在你这边，不是双方签字的变更单；要让对方在同一处点头，等团队协作（建议 I8）。目标的用语偏工作，用在家庭事务上要换说法。
- **不适合：** 需要有法律效力的变更单；客户必须在线签字确认的项目。

### K2 交出去的判断，答得上依据

> **交出去的每一份结论，都留着当时的依据。**

**给谁：** 独立顾问、行业分析与投研、产品经理、研究型作者、学术研究者、法务。共同点：自己掌握一批持续积累的材料，反复向别人交付有依据的判断。

**代表链路：** [CON-01](角色链路/C-研究内容与教育.md#con-01-周五下午交客户的行业周报周一客户追问第三条是从哪看到的)、[LAW-01](角色链路/D-专业服务与个人.md#law-01-客户周三发来第二版采购合同下午五点前要给审阅意见)、[INV-02](角色链路/C-研究内容与教育.md#inv-02-业绩会结束-40-分钟内要出一页快评)、[UX-01](角色链路/B-产品与业务.md#ux-01-6-场访谈录音本机转写每条结论都带原话出处)、[DATA-02](角色链路/A-写代码与技术.md#data-02-老板晚上-9-点问为什么上周-dau-掉了-8今晚就要答)、[SALES-06](角色链路/B-产品与业务.md#sales-06-40-题安全问卷从历史答案拼初稿每条带出处版本敏感题本人验收)

**触发：** 周五交一份行业周报。下周一客户问："上周为什么建议暂缓？"周三又有一条更正消息。

**原来怎么做、卡在哪：** 阅读器（Feedly、Readwise）找材料，NotebookLM 或 ChatGPT 带引用整理，Word 或 Notion 成稿。引用在 AI 的回答里，进了交付稿就断了；"这一期到底采用了哪几篇、哪个版本"要另外手工维护一份材料包；来源后来变了，旧判断还依赖原来的条件，没人提醒你。

**Work 怎么做：**

1. Feed 订阅来源（RSS、网页查询、YouTube、Gmail），捕捉规则把值得看的送进 Inbox，写明为什么。
2. 勾 1–20 条本期材料，生成 Pages 文稿；文稿末尾附本次用到的材料快照：正文、来源、版本、摘要。
3. 在稿子里选一段，用"提反例与反驳""读者视角"让助理挑刺；只选认可的那段，放回原位置。
4. 存一版固定成果交给客户；让助理"做成 5 页给周会"，导出 PPTX；还缺证据的句子记成带来源的待办。
5. 被追问时打开那一版：当时依据了什么，都在。
6. （建议中）材料更新后，Work 列出曾采用旧版的结论，由你逐条复核。

**60 秒演示：**

| 镜头 | 画面 | 字幕 |
| --- | --- | --- |
| 1 | Inbox 里本周 6 条，每条写着为什么进来 | 只把要处理的送到面前 |
| 2 | 勾 4 条，"整理成一页"；文末出现"本期采用的材料"，每条带来源和版本 | 写进去的，就记得从哪来 |
| 3 | 选中一段，浮条里点"提反例"，助理给三条，只把第二条放回原位 | 结果回到你正在改的地方 |
| 4 | 存为固定版本，再"做成 5 页"，PPTX 导出 | 交出去的是这一版 |
| 5 | 一周后，客户问"为什么暂缓"；打开那一版，点开当时的材料原文 | 一周后，依据还在 |

**官网文案：** 订阅和邮件进来，要你处理的才送到面前，写清为什么。勾几条材料整理成稿，文末留着这一期用了哪几篇、哪个版本。改完存一版交出去，做成演示稿、记下要补的证据。下次被问"这个结论从哪来"，打开那一版就有答案。

**为什么是 Work：** 带引用的回答已经很普遍，Work 不讲"能引用"。它讲两件别处要手工做的事：**交付物固定当时采用的材料版本**，以及**出处跟着交付物走到演示稿、待办和目标**。外部证据：78.7% 的开发者认为来源标注重要或很重要（Stack Overflow 2026）；59% 的研究者说自动引用会提高信任（Elsevier）；83% 的法律从业者担心依赖编造信息（LexisNexis，二手）；42% 的知识工作者花在核实上的时间超过 AI 省下的时间（Adaptavist）。

**成熟度与瓶颈：** Feed→Inbox→Pages 带快照、PPT、成果固定 **main 可用**；Feed 与来源 **已发布**；Gmail 等账号来源依赖正式 OAuth（A3）；"以上期要求新建一期"（D1）、出处跟到 PPT（D3）、来源变化复核（D2）是建议。

**推广与运营抓手：**

- **可分发物**：一份带"本期采用材料"的周报，本身就是作品；给咨询、投研社群做"行业周报"模板包。
- **激活指标**：第一份带快照的交付，加一次回查。
- **留存回路**：每周同一专题；第二期从上一期开始。

**怎么验证、什么会推翻它：** 同一专题连做两期，中间一次客户追问、一次来源更正、一次生成失败后恢复。看作者是否停用了手工材料包。**推翻**：熟练的 Feedly + NotebookLM 组合更顺；20 条或 10 万字的上限经常不够；真正耗时的是采访和排版。

**不适合：** 只想看新闻摘要；团队 newsletter 群发；交付必须是在线共编文档。

**触发：** 客户第三次改报价清单，你又要逐行核对型号、数量和批准价；或者每次发版都要手动过一遍同一份清单。

**原来怎么做、卡在哪：** Excel 公式、脚本、Airtable 或 Retool；让 AI 写一个 Artifact（官方写明是无后端的单页）。做出来以后：要自己存数据、自己维护，接不进日常工作；AI 还是按聊天里的旧口径做一遍。

**Work 怎么做：** 在插件创作台描述需求 → Agent 先给方案，再写后端代码与测试 → 宿主类型检查、打包、沙箱试跑 → 你授权安装，底栏多一个图标 → 它的操作进同一个动作目录：你在界面里用，助理、工作流程、Claude Code 调的是同一个操作、同一份本机数据 → 改规则出新版本，在用的版本不受影响。

**60 秒演示：** 说"做个发版清单，每次发版前核对版本号、更新说明、签名" → 方案三行，确认 → 进度条走完"写代码、过检查、试跑" → 底栏多一个图标，点开就能用 → 切到 Claude Code："按发版清单检查一遍" → 它调的是同一个插件，结果出现在同一份记录里。

**官网文案：** 表格太散，专门的软件太重。描述一句，Work 把它做成一个插件：有界面、有自己的数据、装在你的电脑上。做出来以后，你在工作台里用，你的助理和 Claude Code 也用同一个操作、同一份记录。

**为什么是 Work：** 对话生成小应用已经是红海（Claude Artifacts、ChatGPT Sites、Cursor canvas），但多是单页或托管页。Work 的差别是**做出来的东西你不用自己养**：有后端和本机存储，有安装、权限和升级，进统一动作目录，所以你的 AI 和工作流程也能用。Obsidian 社区插件五个月翻倍到 8,000 多个、不得不改成自动审查，说明 AI 正在让"做插件"变成普通人的事。

**成熟度与瓶颈：** **main 部分**（预览，仍需检查与返修，仅 macOS）。瓶颈：生成的插件搜不到、成果库不认、不能当流程一站（C1）；业务数据导出与升级未验（C2）；成功率没有可信口径（C3）；没有可直接改的样例（C5）。

**推广与运营抓手：** 鼓励晒工具（"我用一句话做的报价核对器"）；每个主推角色配 2–3 个样例插件；后续做分享与导入（G3）。**激活**：第一个装上、并被 AI 调用过一次的插件。**留存**：第二次改规则后仍在用。

**怎么验证、什么会推翻它：** 四个真实小工具（发版清单、报价前核对、选题库、面试评分表），各跑四周，含一次规则变更、一次失败恢复、一次数据导出。**推翻**：每次都要作者救火；比表格更难查错；升级丢数据。

**不适合：** 一张表就够的事；必须全团队实时共用的业务系统。

**触发：** 第 N 次把同一段规则粘进另一个 AI；社区里常见的抱怨是 `CLAUDE.md` 只在 Claude Code、只在一台机器上有效，而且存得下规则、存不下"为什么"。

**Work 怎么做：** 从 Codex、Claude Code、Cursor、OpenCode、Grok Build 导入规则与 Skills，发布成固定版本的角色；项目长期说明（背景、硬约束、质量标准）带版本，每一轮自动交给助理、插件 Agent 和外部 AI；系统和插件的提示词都能看、能改，每一轮记录用的是哪一版。规划中的**技能包**是只有文字的"同事做法"，助理和 Coding 共用，`~~日历`、`~~项目工具`这类占位接到你实际用的服务，不授予任何权限。

**60 秒演示：** 选"从本机导入" → 列出 `~/.claude/skills` 里的五个 Skill，勾三个 → 发布 → 在 Work 助理里说"按我们的发版说明写法写这次的更新" → 切到 Codex，同一个项目里它拿到的是同一份项目说明。

**为什么是 Work：** Notion 的 Skills API 把 Notion 里的 Skills 同步到 ChatGPT 和 Claude，Readwise 给 Claude Code 和 Codex 发 Skills：大家都在做"做法跨 AI"。Work 的差别是本机、跨厂商、有版本、看得到每一轮用的是哪一版，并且做法不带权限。

**成熟度与瓶颈：** 导入与角色 **main 部分**；项目长期说明 **main 可用**；技能包 **规划**；纯内容技能包现在助理看不见（G1）；导入结果只能给 Coding 用（G2）。

**推广与运营抓手：** 这是**增长入口**：从用户已有的 AI 配置零迁移导入；技能包本身可分享。和 K1 一起讲给开发者，和 K2、K5 一起讲给产品与研究角色（"装一个产品经理技能包"）。

**不适合：** 只用一个 AI 且对现有配置满意的人。

### K8 你答应的、在等别人的，分开记（新）

> **AI 抽了 8 件事，Work 说 3 件你已经记过、1 件在等法务。**

**给谁：** 项目经理和交付协调、产品经理、自由职业者、会计、招聘人事、顾问：每周被会议、邮件和电话推着走，手上同时有"我答应的"和"别人欠我的"。

**代表链路：** [PMO-01](角色链路/B-产品与业务.md#pmo-01-周会纪要一出来你的承诺在等别人的事各进各的待办和日历)、[FIN-02](角色链路/D-专业服务与个人.md#fin-02-谁还欠我什么从客户邮件里理出在等别人的事每天早上一张单)、[FREE-04](角色链路/D-专业服务与个人.md#free-04-客户电话里临时加了三件事挂电话五分钟内落成待办和一条变更提议)、[TL-04](角色链路/A-写代码与技术.md#tl-04-线上事故后的复盘承诺要落到人和日期上)、[HR-03](角色链路/D-专业服务与个人.md#hr-03-新人下周一入职it行政用人经理各有一件事在等别让人第一天没有电脑)，同类用法见[模式 4](角色与使用链路.md#模式-4-你答应的在等别人的分开记)。

**触发：** 周二跨部门周会，2000 字的纪要里藏着 8 件事：有你答应的，有在等法务的，也有上周已经记过、只是改了日期的。

**原来怎么做、卡在哪：** 飞书妙记、Granola 已经能从会议里抽出行动项；Todoist、Things 管得住清单，不少人手动维护一份"等待"清单；让 ChatGPT、Claude 从纪要里列待办也很顺。卡在：抽出来的东西不知道你已经记了什么，重复和改期要自己对；"在等别人的事"没有单独追踪；"下周三"到底是哪天、出自哪句话，事后找不到。

**Work 怎么做：**

1. 纪要写在 Pages 里，或把会议工具导出的文字粘进来；邮件经信息流进 Inbox 也行。
2. 从材料整理出待办：分出"要你处理""你的承诺""在等别人""可考虑的建议"，每条的依据必须是原句。
3. 和已有待办比对：标出可能重复的，建议更新哪条的截止日。
4. 日期由程序换算，不让模型算"下周三"。
5. 你逐条采用、合并或忽略，整批可撤销；等别人的进"等待他人"，写清等谁、等什么。
6. 要动手的排进日历、挂到对应目标；每天早上的对话任务列出等了三天以上的事，起草催办话术，由你自己发。

**60 秒演示：**

| 镜头 | 画面 | 字幕 |
| --- | --- | --- |
| 1 | 周会纪要，2000 字 | 会开完了，事藏在字里 |
| 2 | 整理结果：8 条，分成四栏，每条下面是纪要原句 | 你答应的、在等别人的，分开 |
| 3 | 3 条标"可能与已有待办重复"，1 条"建议把截止日从周五改到下周三" | 已经记过的，不再记一遍 |
| 4 | "下周三"变成"10 月 29 日"，旁边是原句 | 日期不靠模型猜 |
| 5 | 第二周早上：等待清单里"法务回复合同"已等 4 天，下面是一段催办草稿 | 别人欠你的，也替你记着 |

**官网文案：** 开完会、读完邮件，事情都藏在字里。Work 把你答应的、在等别人的分开记下，和你已有的待办对一遍，日期换成具体哪天，每一条都能点回原话。等别人的事，每天早上替你列出来。

**为什么是 Work：**

| 熟练替代 | 已经做好的 | 还剩什么 |
| --- | --- | --- |
| 飞书妙记、Granola | 会议转写，抽行动项 | 不知道你已有哪些待办；不管会议以外的邮件、合同、复盘 |
| Todoist、Things、OmniFocus | 清单、提醒、"等待"标签 | 要手动录入；不记出自哪句话 |
| ChatGPT、Claude 从一段文字列待办 | 快，理解好 | 每次从零列；日期按模型理解；列完还要搬进待办 |

**成熟度与瓶颈：** **main 可用**（需模型）。瓶颈：没有按月、按季重复（建议 H10）；提醒只出现在这台电脑上，关机或服务没开时不送达（A5、I5）；读不到个人微信；邮件来源要正式 OAuth（A3）。

**推广与运营抓手：** 入口最短：粘一段纪要就能开始，不用搬任何资料。渠道是项目经理、交付和自由职业者社群，少数派一类的效率作者。**激活**：第一次整理就采用三条以上，至少一条进"等待他人"。**留存**：第二周还有"等待他人"被标完成。

**怎么验证、什么会推翻它：** 找 5 位每周开三次以上会的项目或产品经理、3 位自由职业者，连续两周把纪要和客户邮件交给它。看重复识别准不准、等待清单有没有被打开、是否停掉了原来的手抄清单。**推翻**：去重误报多到要逐条核；他们已经用会议工具接任务管理器的集成且满意。

**不适合：** 会少、事少、记得住的人；主要在个人微信里沟通的人；需要团队共享任务看板的小组（团队协作还没做）。

## 4. 支撑场景

这三条不单独拉新，但几乎每个 killer 的演示都要用到。

**S1 选中就交出去，结果回到原处。** 在稿子里选一句"周五前和编辑对结构"，点"记成待办"，不用再输入，待办带着来源；选中助理回复里的一段，在原位置预览后替换；选中一段报错，交给 Codex，背景跟着走。按 ⌃⌥W 把当前网页收进 Shelf，在右栏选一段放进中间的稿子。*成熟度：浮条、落点 main 部分；右栏放进左边 分支（#712）；语音输入 分支（#631）。* 2026 年在文档里让 AI 动手已是标配，S1 的差别在于**跨插件**：一句话能去待办、目标、演示稿、另一个 AI，带着出处。

**S2 重复的处理，存成你说了算的流程。** 每周读三份行业报告写成一页：Feed → AI 整理 → 你看过再交 → Pages → 待办。每一站是一个插件，每段交接是模板、AI 或人；判断规则拦下不该继续的一次；任何已授权的动作和接入的外部 MCP 工具都能当一步；每次运行留着当时的链和每段交接的内容。*成熟度：main 可用 / main 部分。* 比起 n8n、Zapier，它的站点就是你自己的文档和待办，人在关键处把关。

**S3 AI 能动手，但动不了不该动的。** 外部 AI 客户端逐个、逐项授权，撤销后下一次调用立即被拒；写文件、跑命令、推送进审查队列；取消或撤权后不再写入任何记录；外部内容只当资料，里面的指令不会变成命令；电脑操作把密码管理器、系统设置、支付类应用设为禁区；语音转写在本机，音频不出设备。*成熟度：main 可用；语音 分支。* OpenClaw 的传播同时伴随大量安全事件（权限过大、提示注入、国内对国企与银行的限制），**本机 Agent 的需求和对失控的担心同时存在**。Work 讲"可控"，要讲到具体拒绝了什么，而不是泛泛说"更安全"。

## 6. 不做或降级的

| 场景 | 为什么不做 |
| --- | --- |
| 会议采集与转写 | Granola 已很强且已开 MCP；Cowork 用量里只占 1.8%；Work 没有会议采集。更现实的是把 Granola 当上游来源接进来；从已有纪要里分出承诺和等别人的事归 K8 |
| 合同或法律审阅作为一个品类 | 需要行业依据库和责任界定，Work 没有；只靠"数据在本机"撑不起。律师用 K2 的链（每条意见指回自己那一版审查要点，Word 仍是交付标准，见 LAW-01）可以讲，但不做法律依据库 |
| 通用 CRM、团队知识库 | Notion、飞书、成熟 CRM 已覆盖；单机与"每项事实一个主人"不适合做团队知识库 |
| 写文档时"换 AI 轮流写" | 负责人 10-16 决定；调研也没找到这个需求 |
| 每日新闻摘要群发 | Feedly、自动化工具已覆盖；Work 不比谁会群发 |
| "AI 帮你写软件"作为口号 | 维护负担是最强的反对声；改说"做出来的东西你不用自己养" |
| "本机 Agent 能做更多事" | 那是 OpenClaw 的赛道；Work 讲可控 |
