# Work Brief：项目综合首页与工作简报

状态：需求已整理（2026-10-15；2026-10-18 补充 living page、一页式脉搏、使用回顾与交互式报告页；2026-10-27 补充风险总览接续，并按用户决定将项目首页整合进 Work Brief），尚未实现。Work Brief 升级为可选安装的项目综合信息呈现插件，保留原简报能力与 Home 级运行范围，仍由同一个人助理与场景 Skill 驱动；未安装时平台提供基础首页。目标完成程度为**内部完整**。本轮只更新需求、相关职责和演进顺序，不开发、不继续制作设计原型。需求维护：Codex；实现沿演进计划 E 轨，公共能力、工作台与助理分别由 C/D/A 轨协作，原负责人保留。

## 1. 目标与范围

项目首页与跨插件综合结果统一设计：Work Brief 组织项目概览、内容建议、变化、待关注事项、周期报告、专题分析、准备材料与方案对照，管理自己生成或采用的页面、简报正文、版本、来源和修订。首页是当前项目综合信息的入口；它展示的业务事实仍来自各插件，不再另外建设一套首页事项、日报页与简报页的业务逻辑。

例如，一份周度复盘同时引用待办、文档、代码和会议。它属于工作简报；被引用的待办、文档、代码和会议仍由原插件管理。用户从简报中选择“准备交付说明”后，由同一个人助理接续，使用适用的 Skill 和业务工具完成。

临时提示、一句建议和普通运行通知继续留在助理中，不要求每次都生成简报。本文不新增另一套助理、调度、任务板、审批或业务完成状态。

### 1.1 基础首页与综合首页（2026-10-27 用户已定）

| 状态 | 用户得到什么 |
| --- | --- |
| Work Brief 未安装、未启用或当前不可用 | 平台基础首页展示本项目可用插件的卡片表，以及各插件公开提供的内容概览、建议和继续入口；没有已打开插件时落在这里，主动返回首页时也可到达。不要求先配置模型、生成简报或安装 Work Brief |
| Work Brief 安装并启用 | 通过通用首页挂载能力承接项目综合首页，组织相同来源中的项目总览、变化、待关注事项、建议、简报及场景页面；原插件的详细工作界面保持可达 |
| 已在插件或其他窗格工作 | 保留既有标签、草稿与工作位置；安装、刷新或生成首页不自动抢占当前工作，用户返回首页时显示有效首页 |

基础首页的建议来自插件声明的可用入口、已有内容或已产生的建议；读取和展示不强制新增模型调用，不把静态入口伪装成 AI 结论。没有可用插件或内容时如实提供添加插件、带入资料或开始工作的入口；安装状态、启用状态和读取失败与“没有内容”分别表达。

综合首页默认读取已有结果与当前获准事实。个人助理按 Skill、用户关注与有效委托决定进一步取材、解释、组织和更新；访问首页不自动启动分析、持续观察、定时报告或外部操作。用户可继续打开插件处理原内容，返回后保留首页的有效阅读、筛选及编辑状态。

Work Brief 仍是 Home 级插件，可服务个人与多个项目；项目首页、页面绑定和项目简报明确关联当前项目，个人跨项目汇总仍受原授权约束。不因提供项目首页而为每个项目复制个人助理或建立另一份全局简报库。卸载、停用或首页加载失败后回到基础首页，不影响原插件的内容和可用入口；已有简报与页面按原数据保留、卸载及清除规则处理，不因首页退出自动删除。

### 1.2 共用公开来源与呈现机制

平台提供通用首页挂载、来源发现、引用／动作绑定、授权与公共呈现组件。基础首页与 Work Brief 使用同一份已安装／已启用插件目录、对象摘要、内容建议、来源状态和动作合同，复用卡片、概览、引用、状态与操作呈现；不各写一份插件名单、摘要接口或建议状态。Work Brief 经与其他插件相同的公开合同注册和挂载，宿主不按它的名称、插件 id 或某个场景名判断首页布局。

各插件只提供自己拥有的内容、可核实的概览与建议、对象引用和真实动作；Work Brief 负责跨来源的组织与页面内容，不直接查询其他插件私有表或复制它们的状态。公共组件和作者能力经 SDK 的公开入口提供，内部设计系统按现有边界复用，不能要求插件 import 工作台或其他插件的私有实现。实现前核对现有目录、起步入口、主题摘要及 UI 挂载能力，只补当前需求的公共缺口；字段、存储和动作版本随实现设计确定。

跨插件信息统一呈现不意味着全部插件界面必须依赖 Work Brief：未安装时基础首页、原插件编辑／执行界面、个人助理与公共卡片仍可工作。首页、侧栏、对话与通知引用同一业务对象、建议或简报，展示位置不生成第二份可独立修改的业务事实。

### 1.3 生成首页、当前事实与保存的简报

[Onboarding 的生成交互首页](../onboarding-coverage/spec.md#310-ai-生成新的交互首页)由 Work Brief 承接项目页面定义、有效绑定、版本、人工修改和恢复。Onboarding 负责用途澄清、预览、依赖与配置选择、采用及第一件工作；平台负责通用页面生成所需的工具、校验、隔离、挂载与动作授权；个人助理及 Skill 负责生成和修订。Work Brief 未安装时，基础引导、材料带入和原插件工作照常可用；只有采用需要 Work Brief 的综合／生成首页时才说明并完成该依赖，不因建项目自动安装或启用插件。

生成页面可以采用现有公共卡片，也允许比较、筛选、编辑、参数输入等新的交互组合和页面实现；原卡片的块合同不作为全部页面的固定模板。新页面仍在同一工作台和项目中运行，业务读写调用原主人公开动作，不获得私有数据或额外执行权限。生成失败、质量不合格、依赖停用、版本冲突和重启时保留有效内容与人工修改，能回到上一可用页面或基础首页；页面恢复不重新执行已完成的业务动作。

实时首页呈现当前可取得的事实和已有结果，保存／分享的简报保留当时版本与依据。刷新首页不暗改历史简报，编辑页面布局不修改来源对象；查阅历史时能区分当时与现在。保留[首页无感刷新](../quiet-home-refresh/spec.md)的有效体验：后台读取不先清空已有内容、不无故换掉正在交互的节点，失败保留仍可展示的有效结果与恢复入口；撤权内容不通过残留预览继续暴露。

### 1.4 Feed 与首页事项（BL-098）

Feed 的项目／个人归属从原主人和真实项目关联读取，不因它是 Home 级插件或恰好从哪个页面打开便统一标为“个人”。单纯同步到的新资料不能直接等同于用户接下的新工作或完成量，也不自动生成 Todo、Goal 或新的首页任务状态。

基础首页按公共来源合同展示 Feed 的内容概览、可用建议与打开入口；综合首页由个人助理按 Skill 判断本次范围里值得呈现的变化、依据和下一步，沿用与其他插件相同的机制。具体展示可按来源或主题组织，不为 Feed 建专用首页分支。Inbox、待办与后续执行继续引用原对象和真实操作；原始消息、跨插件引用及摘要中的同一事实不重复计为多项工作。此项产品方向已定，真实归属、展示与接续验证仍未完成。

### 1.5 团队共享范围（2026-10-28 用户已定）

按[团队协作需求](../team-collaboration/spec.md)明确共享项目。Home 级运行、项目关联及个人助理可读，不使个人简报、跨项目汇总或个人外部会话自动向成员公开。共享项目的首页、简报、引用预览和通知只呈现目标成员获准接收的材料，未共享内容也不能经摘要、统计或 AI 回答间接公开；选定个人成果的分享须有对应授权。共享收窄或撤回后，后续与在途生成、读取和展示沿最新有效范围处理，保留版本不绕过当前访问判断。原始内容、简报和共享授权仍由各自主人维护；对应验收见 TCO-01～06，当前尚未实现。

## 2. 职责与事实归属

| 承载方 | 负责什么 |
| --- | --- |
| 平台 | 统一采集、数据工具、授权、调度、运行恢复、评测记录、定位高亮；通用首页挂载、基础首页及公共来源／呈现机制 |
| 个人助理与 Skill | 发现工作、选择材料、分析判断、组织结果、提出选项、执行与跟进 |
| Work Brief 插件 | 综合首页的信息组织、页面定义／绑定／版本／恢复，以及简报正文、版本、来源和修订；保留 Home 级范围 |
| 原有业务插件 | 待办、文档、日程、代码等原始内容及业务状态 |
| 首页、侧边栏与其他呈现入口 | 使用公共组件展示同一对象、建议或简报，按统一标签／窗格规则打开对应内容；平台基础首页不依赖 Work Brief 的安装 |

插件提供创建、读取、更新、比较和展示简报的通用能力。不同 Skill 使用这些能力决定写什么、怎样分析、提出哪些下一步；不在插件代码中固化“周报流程”“会议准备流程”或“阻塞分析流程”。

源插件缺少读取、修改或定位能力时，应由对应主人补齐；工作简报不能替原插件拥有这些能力。建议处理状态、真实批准和业务完成状态沿用原有归属，简报只展示引用。

## 3. 内容、版本与修订

用户能从首页、侧边栏或助理打开同一份简报，查看正文、范围、周期或主题、材料截止时间和来源。报告中的重要结论能够对照原始依据；缺数据、资料过期和无法取得历史内容时，保留可靠部分并明确影响。

用户能查看过去的简报及其修订，区分当时版本与当前内容。刷新或重新生成不能悄悄修改已经保存或分享的版本；源内容后续改变也不能使历史依据被新内容冒充。

2026-10-27 已定：平台工作记录默认在本地长期保留，用户可设置清理期限或手动清理，完整规则归[主动助理 §3.4](../proactive-assistant/spec.md)。清理工作记录不连带删除已保存简报或原业务内容，它们按各自规则保留；简报引用的历史依据若已无法取得，应明确显示缺口，保留可用正文与来源信息，不用当前版本代替已失去的依据。

用户可以改写和补充简报。再次生成时保留人工修改，对冲突提供可对照的差异，允许继续调整、采用或放弃；不能用新的 AI 输出直接覆盖人工内容。简报文字的修改不自动写回源插件业务事实。

临时回顾、正式留存和对外分享保持清楚区别。需要留存或引用的固定版本按现有成果机制处理，不把过程候选都当作正式成果。分享和外部效果遵循原有授权要求。

### 3.1 可刷新的状态页（living page）

跨多个工作流/周期的简报可以呈一张可分享的状态页，而不是每次重写一篇长文：

- 按 tab 组织：概览与成功标准、工作流顺序、下一步，以及确有内容时的背景、计划、风险/开放问题、决定/FAQ；没有内容的 tab 不出现。
- 页面里嵌一份不可见的 `state` 块（范围、as-of、每条工作流的状态/owner/关键字段），供下一次刷新对比。
- 刷新时重新取实时状态、部署到同一地址、只报告 delta（新增/状态变化/完成/新阻塞）；取不到的数据标 stale，不编造。
- 读取的是原主人的当前事实；页面只是视图，不成为第二份业务状态。
- 页面文字与来源里的第三方内容按数据处理；实体编码，`</script>` 不能从数据里逃逸。

### 3.2 一页式脉搏

对“今天/本周怎么样”这类问题，简报可以提供一页式脉搏：

- 并行拉取可用来源，分别给出红/黄/绿或“n/a”；一个来源失败不阻塞其他来源。
- 风险项必须带具体记录、金额/天数/影响和下一步；“有些逾期”不算风险项。
- 完全没有连接/数据时，允许用户口述关键数字，结果标为 `owner-supplied`，不伪装成拉取。
- 明确 as-of、覆盖范围、缺失来源和未验证项；不把操作数、调用数当成果。

### 3.3 使用/影响回顾

简报可以提供“这一段时间做了什么、落在哪些项目、哪些结果被采用/返工”的回顾：

- 数据来自本地会话、动作记录和原插件事实；不读其他工具的私有目录。
- 不编造金额、节省时间或生产力比例；确需估算时写方法与不确定性。
- 区分用户手动完成与助理完成，不把全部成果归功于助理；重复来源不重复计数。
- 默认只给本人看；分享/导出按原有授权，敏感内容可脱敏。

### 3.4 交互式报告页

简报可以生成一张可交互的评审页，而不只是 Markdown：

- 结论按 claim 树组织，每条 claim 配一个 exhibit（界面草图、状态机、调用链、schema 或代码），决策放在它影响的 claim 上。
- 读者能展开/收起、勾选决策、评论、复制一份 response 交回助理；提交前不改业务事实。
- 页面是简报的一种呈现，不新增事实源；保存/引用仍走成果机制。

### 3.5 结合项目风险总览

2026-10-27 用户已确定提供[项目风险总览](../risk-plugin/spec.md)，并与 Work Brief 结合。总览由风险插件管理，集中查看当前项目风险；简报由个人助理按 Skill 选择本次范围内值得关注的变化、影响和下一步，结合其他来源作综合说明。风险插件通过公共读取、摘要、定位和更新能力参与，Work Brief 沿用通用引用与卡型，不增加写死的风险分析流程或第二份风险状态。

已登记风险使用风险对象引用，保留具体影响、依据与下一步，并可打开该风险详情及所属项目总览。简报里从其他业务对象分析出的潜在风险仍须引用具体来源，不能伪装成已登记风险，也不因文字出现“风险”便自动登记或创建 Goal 顾虑。登记或后续处置由对应公开工具按已有授权完成；编辑简报正文不改变风险原件。

总览的当前状态与已保存简报的历史依据分别呈现。刷新遵守 §3 的版本与人工修改规则；风险来源不可用时明确缺口或过期，其他来源仍可生成。跨项目汇总只读取已授权范围，不将无权限或未接入解释为零风险。是否纳入本次简报由助理按 Skill、当前变化和用户关注点判断，不因本次接入自动订阅通知。

2026-10-27 已定风险复查采用“按需复查、结果并入简报”：用户或 AI 在已有委托内安排时间，调度与取消仍由原调度能力负责，个人助理到期读取最新依据。普通结果并入相应范围的简报，无实质变化时安静处理，不强制每次新建一份报告；重要变化或必要决定按已有通知设置提醒。简报区分复查后的无变化、未完成复查和来源缺口；失败、重启、重试与合并展示不重复报告同一结果。安排与完整边界归[风险需求](../risk-plugin/spec.md)，Work Brief 不维护复查任务状态。

## 4. 后续操作与恢复

简报中的选项具体、可理解，保留自由补充和暂不决定的方式。查看正文、来源和历史版本不额外运行模型；需要继续分析或准备的选择交给同一个人助理及适用 Skill，明确的业务操作调用原插件真实能力。

执行前核对原工作、对象、有效版本和当前权限。旧简报、项目切换、内容变更、事项已处理或权限撤销时，不能沿用失效选项误操作。简报引用实际执行进度与产物，不维护第二份任务状态。

生成失败、中断或部分成功时保留已有有效内容和实际缺口；重试与恢复不重复生成相同用途的内容或重复执行后续操作。取消、停用、撤权后的迟到结果不能产生新效果。通用运行和恢复由平台及个人助理负责。

## 5. 验收标准

| 编号 | 用户可观察结果 |
| --- | --- |
| WBR-01 | 周期报告、专题分析、准备材料和方案对照能由个人助理按 Skill 生成并保存在工作简报中；临时提示不被强制保存为简报。 |
| WBR-02 | 首页、侧边栏和助理打开的是同一份内容及其版本；原业务内容、建议状态、批准和完成状态仍来自原主人。 |
| WBR-03 | 正文的重要结论能核对来源、范围和材料时点；缺失、过期或不可用资料的影响明确，不编造依据。 |
| WBR-04 | 保存或分享过的版本可以回看；后续刷新、修订和源内容变化不暗改历史正文或依据；工作记录清理不连带删除已保存简报，引用依据不可用时明确标记缺口。 |
| WBR-05 | 用户修改后再次生成，可以对照差异、处理冲突、采用或放弃；人工修改不丢失，正文修改不自动改写源业务事实。 |
| WBR-06 | 简报的后续选择接回同一个人助理及真实业务能力；旧版本、错误对象、项目切换和撤权不会造成误操作。 |
| WBR-07 | 中断、失败、部分成功及重试保留有效结果，不重复生效；停止或撤权后的迟到结果无新增效果。 |
| WBR-08 | 保持平台及插件代码不变，修改场景 Skill 后，取材、分析和结果随有效做法变化；插件没有按场景名称固定的生成流程。 |
| WBR-09 | [人工] 在真实跨插件工作中完成生成、来源对照、人工修订、再次生成、历史回看与后续接续，结果可用且归属清楚。 |
| WBR-10 | 状态页按有内容的 tab 组织，页面内有可对比的 state 块；刷新重新取实时状态、部署到同一地址，只报告 delta |
| WBR-11 | 取不到的数据标 stale，不编造；第三方内容按数据处理并实体编码，不能从内容里注入脚本或指令 |
| WBR-12 | 一页式脉搏并行取可用来源，按红/黄/绿或 n/a 呈现；一个来源失败不阻塞其他来源，缺失来源明确 |
| WBR-13 | 脉搏的风险项带具体记录、金额/天数/影响与下一步；没有连接时允许 owner-supplied 并如实标注，不伪装成拉取 |
| WBR-14 | 使用回顾区分用户与助理完成、不重复计数、不编造金额/节省时间/生产力；默认只给本人看，分享/导出按授权 |
| WBR-15 | 使用回顾的数据只来自本地会话、动作记录与原插件事实；不读其他工具的私有目录，敏感内容可脱敏 |
| WBR-16 | 交互式报告页能展开/勾选决策/评论并把一份 response 交回助理；提交前不改业务事实，保存/引用仍走成果机制 |
| WBR-17 | 简报可通过公共工具选取并引用风险，展示具体影响、来源和下一步，打开同一风险详情及项目总览；更新风险由原主人执行，简报正文编辑不改变风险或 Goal 顾虑 |
| WBR-18 | 风险更新后，总览读取当前事实，已保存简报保留当时版本与依据；刷新能反映新状态并保留人工修改；来源失败或无权限标明缺口，其他来源仍可用 |
| WBR-19 | 风险取材与判断由助理按 Skill 和任务范围完成，不在插件中写死分析流程；潜在风险与已登记风险可区分，提及风险不自动登记、生成顾虑或订阅提醒 |
| WBR-20 | 按需复查结果能并入相应简报，区分无变化、未完成与来源缺口；无实质变化不单独打扰，重要变化/必要决定遵守已有通知规则，重启与重试不重复报告或通知 |
| WBR-21 | 未安装／未启用 Work Brief 时，没有已打开插件的项目及主动返回首页的路径均可显示基础首页：插件卡片、可用内容概览、建议与继续入口可操作；无需模型或简报，空内容与读取失败可区分 |
| WBR-22 | Work Brief 安装启用后通过通用挂载提供综合首页；停用、卸载或页面失败后基础首页可用，原插件内容和既有工作不丢失、不被抢占，保留数据按原生命周期规则处理 |
| WBR-23 | 基础首页与 Work Brief 对至少两个职责不同的插件复用同一公开来源和呈现能力；第三方按相同合同可接入，宿主无按插件／场景命名的首页分支，不新增私有依赖、重复名单或建议状态 |
| WBR-24 | 项目首页与个人汇总按真实范围读事实；Feed 等来源的个人／项目关联正确，同一事实不重复计数，原始更新不直接等同承诺／完成工作，查看与呈现不自动创建待办、扩大授权或启动主动任务 |
| WBR-25 | 从基础／综合首页打开原对象、处理后返回以及切项目／窗格时，引用、草稿、阅读与筛选状态正确；来源失败保留有效部分，撤权内容不可残留泄露，后台刷新不清空画面或抢走编辑焦点 |
| WBR-26 | Onboarding 采用的生成首页由 Work Brief 保存页面定义、版本与有效绑定，支持新交互而不只重排固定卡片；预览、采用、人工修改、失败／冲突及重启恢复可实走，缺 Work Brief 不阻止基础引导和材料进入项目 |
| WBR-27 | 综合首页的当前事实与保存／分享简报的历史版本可区分；刷新或页面改版不篡改历史依据，恢复页面不重复业务副作用，个人与项目页面不串用绑定或资料 |
| WBR-28 | [人工] 完整工作台中实走基础首页、综合首页、原插件工作与返回、生成页及停用恢复；空数据、多来源、窄窗、深浅色、键盘／读屏均有可用表现，方向确认不代替最终实物和真实路径验收 |

当前均未进入功能验收。使用真实内容和实际入口验证；模拟结果只证明对应局部，不代表内部完整。

## 6. 关联需求与边界

[主动式助理与场景 Skill](../proactive-assistant/spec.md) 定义主动理解、周期报告质量、权限、运行恢复与评测的完整要求；本文收口基础／综合首页的关系、公共呈现及 Work Brief 的内容和页面生命周期，不另建助理或执行体系。[Onboarding](../onboarding-coverage/spec.md)消费首页能力完成场景采用和第一件工作；[工作台统一机制](../product-flow-governance/spec.md#46-分屏标签右栏与底栏统一2026-10-27-用户已定)继续拥有分屏、标签、底栏和导航行为。现有平台和插件边界沿用 [事实归属](../../docs/SSOT-MATRIX.md) 与 [插件开发约定](../../skills/molis-plugin-dev/SKILL.md)。

本次明确扩展为综合首页与简报的统一产品范围，没有指定新的存储协议、动作名称或框架。实现时沿用现有公开合同和 Plugin Runtime；需要确定的技术细节不得被当作已经完成的产品能力。按[演进计划](../post-anticorruption-roadmap/spec.md)，先交付公共来源／呈现及基础首页，再接 Work Brief 的综合首页与简报核心，随后接生成页面和主动报告；这些依赖不阻塞普通材料进入项目。WBR-21～28 当前无实现与验收证据，后续测试须引用相应编号，本轮只运行文档检查。

卡片与简报页的设计稿（统一卡片记录、块语法、卡型配方，以及用户 2026-10-26 拍板的命名、范围、摘要读取与先做卡型四项）见 [design.md](design.md)，可视规格板见 [docs/design/assistant-cards](../../docs/design/assistant-cards/README.md)；除这四项外，设计稿里的协议与动作名是提案，随分期实现时再定。
