## 1. 判定口径

### 1.1 什么算状态机
一个实体或流程同时满足三条才算候选：① 有一个有限、可命名的状态集合（SQL 列、类型 union、CHECK、JSON 字段、文件、内存、UI 步骤）；② 代码在某个地方判断「当前状态 → 发生某事件后变成另一个状态」，不是纯派生投影；③ 当前状态决定接下来允许发生什么，或被多个写入点改变。

### 1.2 什么算「隐式」
**没有唯一声明的「状态 + 合法迁移」定义**，至少表现为一种：
- **散落**：合法迁移由多个写入点各自的 `if (x.status === …)`、SQL `WHERE status = …` 或方法级守卫决定，没有共享迁移表或唯一的 `assertTransition`；
- **只枚举不约束**：SQL `CHECK` / 类型 union 只列出取值，代码并不拒绝非法迁移（同一次 UPDATE 无 from-state 条件、任意写者都能覆盖）；
- **多字段乘积**：有效状态是若干个状态列 / 标记 / 时间戳 / 计数器的组合，没有任何一处声明哪些组合合法；
- **状态藏在自由结构里**：状态存在 `*_json` 文档、`record_json`、`body_json`、两段提交的意图字段或无 CHECK 的裸列里；
- **双写**：同一状态同时存在两处（库 + 内存、库 + 文件、宿主 + 页面/sessionStorage），同步靠约定。

### 1.3 不算状态机（不进入隐式清单）
- 纯展示的 tone / icon / 色板（`MwStatusTone`、`StateRingState` 等）；
- 纯派生投影：状态由其它事实即时算出、自身没有迁移（如 `AssistantWorkState`、`ModelProviderStatus`、`MCP` 授权视图、`PluginInputPortState`）；
- 一次性/单向终止标记且不参与后续守卫（如只写一次的发布指针）；
- 普通枚举（`kind`、`mode`、`scope`、`transport`、`provider` 等）；
- 已经显式的状态机（有迁移表 + 唯一校验入口），见 §6；外部 vendored 的 Prologue SDK 状态机按外部实现处理，只记录本仓在调用点的二次判断。

### 1.4 分类与风险
- `implicit-machine`：满足 1.1 且按 1.2 属隐式——本次要找的主体；
- `semi-explicit`：有局部迁移表 / 校验函数，但只覆盖部分入口，或迁移表与写入点不一致；
- `explicit`：完整迁移表 + 唯一校验入口（§6，不计入清单）；
- `derived` / `not-a-machine`：§7，不计入清单。
- 风险 `high` 不表示代码难看，只表示：持久化或跨模块、非法迁移无拒绝、崩溃/取消/重试/并发下可能写错账或显示错事实。`low` 表示单表、单入口、影响面小。

1. **这次审计在全仓只找到 4 个真正显式的状态机**：Attention 条目状态、SQLite 存储升级链/带版本文件、外部 Prologue SDK 的 board/node/effect/wait/continuation 状态机、Gmail live-sync 游标协议。其余生命周期（144 条候选里绝大多数）都是手写 `if` 守卫、SQL `WHERE` 或页面变量在推进。§6 有对照。
2. **89 条隐式里，非法迁移「完全拒绝」的只有 2 条，「部分拒绝」69 条，「不拒绝」14 条，「没有任何守卫」4 条**（半显式 55 条：yes 20 / partial 34 / no 1）。也就是说常见形态是「每个写入点各自挡住一部分」，新增入口或旁路 UPDATE 一出现就绕过，没有任何一处能回答「这个状态机允许哪些迁移」。完全不拒绝的 18 条见 §2.1。
3. **状态被当事实读、但从来没有生产写入点的「死状态」成片**：Goals 的 `definition_state`/`decomposition_state`/`validity_state` 多列声明值（T1-01）、`goal_relations.proposed`（T1-05）、`policy_bindings.withdrawn`（T1-06）、Alchemist 的 `interrupted`/`partial`（T2-02/T2-01）、Shelf 的 `pending`（T5-31）、Feed listener `quarantined` 无解除入口（T1-10）、`mw_commands.state` 写而不读（T4-30/T6-16）等。它们被规划、排序、StatusRing、导航或界面当事实用，未来任何写入点出现都会立刻改变行为，却没有迁移口径。
4. **两段提交普遍缺持久中间态**：成果固定版本（T3-04）、Alchemist 计划确认/输入清空/委派派发（T2-13/14/16）、Home 升级单元（T4-01）、项目删除收据与 owner 步骤（T4-03）、安装器「预览→确认」的一次性计划（T4-06）、跨分区移动补偿（T5-21）、插件安装确认（T4-05/T4-06）、页面授权等待（T7-03）。中间态只在内存/一次响应里，崩溃或并发时只能靠重做或人工判断。
5. **同一状态机被抄成多份**：成果固定两段提交 4 份且已经分叉（T3-04，pages 的删除多一个缺口）；页面侧授权等待 3 份、计时/截止规则各不相同（T7-03）；Run/会话相位至少 3 套（T5-01/T2-12/T4-10）；连接账号状态跨宿主与 connector-host 两半（T4-22/T5-09）；`once` 幂等 6 份、复制后状态重置 5 种（T3-18）。

## 8. 覆盖范围、方法与未覆盖

### 8.1 方法
7 个领域并行审计（T1–T7，范围见 §2 表与各 §4 小节标题），每个领域按四步：① 用仓库级检索枚举所有「有状态取值」的实体——48 张含状态列/状态枚举的 SQL 表、124 个导出的 `*Status|State|Phase|Stage|Lifecycle` 类型、31 个 contracts 命名状态类型 + 38 个内联状态联合、`PAGE_STATE_OWNERS` 与事件表、以 `_at`/标记编码的状态、文件（`ledger.json`/`state.json`/sessionStorage）与内存 Map；② 对每个候选找全写入点（`SET status/state`、`INSERT`、对象构造、`mutate`）、读取/guard 点（`===`、`switch`、SQL `WHERE`）与拒绝点（`invalid_transition`、CAS、CHECK）；③ 判断合法迁移定义在哪里、非法迁移是否被拒；④ 分类并写证据。
Lead 的反查：把 48 张 SQL 表、124 个导出状态类型、31 个 contracts 命名状态类型逐一对照全部 findings——全部至少被某个条目或附录覆盖；跨领域条目（§5）由 Lead 归并并抽查原文。高风险条目由 Lead 二次读代码核对（T1-01/T1-08、T2-12、T3-04、T4-01/T4-03/T4-06/T4-10/T4-21、T5-20/T5-21、T6-01 等）。

### 8.2 未覆盖与边界（诚实说明）
- **T4（宿主）**：`apps/local-host` 约 400 个低风险入口文件只按 grep 命中筛过，未逐行读；`packages/storage` 升级链的完整实现、`plugin-runtime` 的完整迁移实现、connector-host 其余 store、agent-host 任务图节点状态、`server/src/sync` 的 Rust 删除写入点没有逐行读，相关条目标了「推断/存疑」。
- **T7（页面）**：浏览器脚本是模板字符串，做了 grep + 关键流程通读，未逐行读 `parent.ts`/`account.ts`；未运行 `dom-events --report`（需要 git 操作），PAGE_STATE_OWNERS 的死路靠手工核对。
- **T2/T3**：Alchemist 浏览器端计划编辑/合作面板的 UI 步骤只做了抽样；Pages 编辑器 1.7 万行按生命周期抽查；catalog 1,012 行只 grep 抽查。

### 8.3 怎样用这份清单
- 先看 §3 的 32 条高风险；多数是「跨模块 + 无唯一迁移定义」，改造收益最高。
- 再做 §5 的归并：同一业务事实的多份实现，先定唯一主人（仓库规则：每项事实只有一个主人，见 `docs/SSOT-MATRIX.md`），再收口；只改某一份会立刻漂移。
- 把「只枚举不约束」「状态藏在 `record_json`」「两段提交无持久中间态」三类挑出来，它们最容易在崩溃/并发下写错账；§4 的「拒非法」列是初筛。
- §6 的 4 个显式状态机可作为写法参照；§7 说明哪些「看起来像状态」的字段不用管。
