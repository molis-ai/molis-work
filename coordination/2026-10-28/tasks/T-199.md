## 1. 背景

- 竞态：`tests/ci-product-subset.test.ts` 在临时仓库里放假的测试文件，让真的运行器 `scripts/ci-product-subset.mjs` 去跑，用来验「CI 取消一次运行」。假文件的内容（`:274`、`:320`）是：

  ```ts
  test("never finishes", async () => {
    writeFileSync("<hang 文件>", String(process.pid));
    await new Promise((resolve) => setTimeout(resolve, 60_000));
  });
  ```

  `writeFileSync` 先 `open(O_CREAT|O_TRUNC)` 建出空文件，再 `write` 内容。外面的用例每 50 毫秒看一次 `existsSync(hang)`，恰好落在这两步之间就读到 `""`。
- 同一条竞态在 `tests/ci-linux-probe.test.ts` 已经修过：#646（`b3c549aa8`，2026-10-17，"the Linux probe test waits for the pid itself, not just the pid file"）。现在的写法在那边是：
  - `:114-116` 的 `pidIn`：`existsSync(file) ? Number(readFileSync(file, "utf8")) : 0`，要 `Number.isInteger(pid) && pid > 0` 才算有，否则返回 0；注释写明 `0` 会被 `ps -p 0` 当成本进程的组；
  - `:254-256` 的 `cutOff`：`await until(() => pidIn(hangPid) > 0, …)`，再 `const pid = pidIn(hangPid)`，再 `ps -o pgid= -p String(pid)`。

  本单把产品子集这边改成同一个读法，所以 `until` 的签名和 50 毫秒轮询都不动（两边的 `until` 是同一段）。
- CI 里的样子：run 40826819385 的 Gates 作业，`ci.yml:118` 那一步（"Gate rules reject what they claim to"）跑到 `[2/13] FAIL tests/ci-product-subset.test.ts 62.5s 18/19 tests`，失败的是 "a report exists from the start: a run killed while its first file is running still leaves one"，抛 `Command failed: ps -o pgid= -p`。Gates 是挡合并的作业，每个 PR 都跑这一步，所以任何 PR 都可能撞上；窗口很窄，所以平时是绿的。
- 同文件里别的读，逐个看了，都不是这一类（读之前，写的那一方已经结束，或写的是原子替换）：

  | 位置（`a3f5fd7ed`） | 读什么 | 为什么读不到半截 |

  | `:289`（`cutOff` 的 `before`）、`:328`、`:333` | 运行器还在跑时读 `report.json`、`summary.md` | 每次写都是先写 `.tmp` 再 `rename`（`scripts/ci-linux-probe/report.mjs:75` 的 `replace`，`scripts/ci-product-subset/report.mjs:86-94` 调它）；第一个文件开始前 `keepCurrent()` 就写过一份（`scripts/ci-product-subset.mjs:134-135`），之后每个文件结束写一份（`:167`），读到的是完整的旧份或新份 |
