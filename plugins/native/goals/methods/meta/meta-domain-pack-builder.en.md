# Build a method for an unfamiliar domain

## Planning path

1. Define the domain boundary, task outcome and main users
2. Identify objects, roles, lifecycle and value flow
3. Collect authoritative sources, professional standards and representative cases
4. Identify typical outputs, evidence thresholds, dependencies and failures
5. Check at least two typical cases and one counterexample
6. Record source, applicability, confidence and review triggers

## Required coverage

| area | label | question |
| --- | --- | --- |
| domain_objects | Objects | Which objects change state and who owns them? |
| domain_lifecycle | Lifecycle | Which phases lead from input to result? |
| domain_artifacts | Professional outputs | What usable and verifiable output does each phase produce? |
| domain_evidence | Evidence | What warrants confidence in the result? |
| domain_dependencies | Dependencies | Which outputs must come first and what can run in parallel? |
| domain_failure_modes | Failure patterns | What is often split, missed or sequenced incorrectly? |

## Dependency rules

| rule_id | statement | direction_hint |
| --- | --- | --- |
| decomposition-after-method | Real task decomposition requires evidence that the domain method works; do not use an unverified method to guide real Goals. | task decomposition depends_on validated method pack |

## Completion evidence

- At least one authoritative or primary source
- At least one traceable practice source
- Recorded typical and counterexample checks

## Closeout checks

- Applicability is explicit
- Dependencies are explained by consumption
- Unknowns and low confidence are visible

## Common mistakes

- Copying a nearby domain's template
- Defining terms without a lifecycle
- Decomposing real Goals before research
