# Molis Work 产品介绍｜2026-10-17

## 一、最新产品介绍

### 用户视角 · 一分钟

Molis Work 是一张装在电脑上的 AI 工作台，把资料、文档、任务和代码放在同一个工作环境里。写报告时，你可以从材料起草文稿、核对来源，再把后续事项记成待办；做产品时，你和 Claude Code、Codex 可以接着同一份目标、要求和进度工作，隔几天回来，也看得见还差什么。工具按项目需要组合，助理就在手边。它想帮你把一件事从材料推进到成果，让过程看得见，重要取舍由你决定，需要你验收的地方也留下明确结论。

### 技术架构视角 · 一分钟

Molis Work 采用本地优先架构：一个 Home 由一个常驻宿主管理，桌面、浏览器和外部 Agent 接入同一套服务。目标、文档、待办等事实分别归对应插件和模块保存；一项动作登记一次，界面、助理、工作流程和 MCP 按各自的权限调用。模型执行统一经过 Prologue 运行时，搜索、记忆和内容放置由平台衔接。这样新增工具可以接入已有工作，结果也回到负责保存它的地方。工作数据主要留在本机；使用联网模型和服务时，相关材料仍会发给对应服务。

排序依据是完成真实工作的贡献与两类首批用户的相关性，不是开发量。**“main”均指开发版，不能与公开可下载混用；“设计”也不是排期。** 表中每项先写人的工作，再列工具。源码、合同和未验收项的出处集中在[盘点](../research/2026-10-17-分支盘点.md)，后续按项更新。

| 把重要判断写成有版本、可检验的规则 | 维护流程的人；能力中的 Functions | main；#616 修复同毫秒连续写入的版本检查；不是独立插件，判断也不是可靠性的自动保证 |
| 描述缺少的小工具，选方案、预览检查、授权后放进工作台 | 高频自定义需求者；插件创作工作台 | main 预览；生成成功率、功能正确性与用户验收要分别看；不等于任意应用都能一次生成 |
| 导入、调整规则与 Skill，查看/修改 AI 的做事方式 | 两类角色，开发者更常用；角色与提示词设置 | main；现有导入支持的本机格式要逐项核对，不是所有工具配置的无损互转 |
| 形成主稿、各平台稿和作者批准后的下载结果 | 多平台作者；CGS 创作 | 分支试验；研究、选题、平台发布和回执未形成完整当前闭环 |

### 6. 支撑这些体验的公共底座

一 Home 一常驻宿主；业务事实各有 owner；插件通过公开合同交互；动作声明一次，按声明的调用入口和权限开放；模型调用经唯一 Agent Host/Prologue 接入；预算、连接、调用记录、个人/项目记忆统一管理。搜索索引可以重建，不能变成第二份业务事实；长期成果与插件之间的过程数据分别处理。[架构依据](https://github.com/molis-ai/molis-work/blob/958946e224/docs/system/ARCHITECTURE.md)

09:00 新合入的 #621 让能力收到模型原样填写的参数，错的格式明确拒绝并返回合同；#616 让记忆导出在无法完成筛查时停止。它们让失败与边界更明确，不代表模型从此理解正确，也不证明所有数据外发都被同一导出筛查覆盖。

这些机制的价值在于减少重复接入与互相矛盾的状态。它们不表示所有插件已迁到同一生命周期路径，也不表示任意外部 Agent 的独立文件操作都被 Work 控制。工作数据本地保存，模型、搜索、连接器等仍有网络请求；本地优先不是离线 AI。当前无现成的第三方插件安装/分享市场；SDK 与生成插件预览不能代替市场交付。

### 7. 已进入仓库、仍要继续建设的方向

| 方向 | 想解决的工作问题 | 截止本次的状态 |
| --- | --- | --- |

| Coding 自检、交叉/对抗评审，后续编程体验 | 更好发现遗漏，衔接代码、验证与人的判断 | 需求与部分前置实现；不宣传成独立验收者，后续清单逐项追踪 |

## 四、用户场景

### 先枚举：谁在什么情况下需要它

首批画像是待验证的产品判断。开发者优先考虑**跨多次会话交付、能自己决定范围并承担验收的人**；知识工作者优先考虑**持有本地材料、周期性向别人交付有依据成果的人**。小团队负责人是后续人群，当前不能默认完整多人产品已经可用。

### 再抽象：这些场景背后的四个需求

1. **交付的含义保持清楚。** D1、D2、K2、T2：这次答应什么、哪些只是报告、哪部分还需要判断。
2. **中断以后能继续，材料变成结果时有据可查。** D3、D4、D7、K1、K3、K4：继续工作不靠重新讲全部背景，也不把来源和交付版本混掉。
3. **把注意力留给真正要自己处理的事。** D5、K6、K10、T1：提醒要有明确触发和处理出口，不能多造一个收件箱。
4. **把高频做法留下来。** D6、K5、K9；K7、K8 只在重复发生且方法稳定时加入：先把人工路径做顺，再将稳定步骤变成工具或流程。X1 是这些路径的输入与操作辅助。

### 官网优先讲的四个案例

从上面的 20 个候选里，先选写代码两条、写文档/管事情两条。这个顺序是根据问题代价、Work 的具体作用和实现边界作出的编辑判断，不是已验证的市场排名。完整官网短卡与三幕脚本见[官网场景稿](官网场景案例-2026-10-17.md)，取舍、替代方案、摩擦与可推翻条件见[场景研究记录](../research/2026-10-17-官网场景取舍.md)。

以下均为**开发中 · 场景示意**。实际功能状态沿用 09:00 基线；需要记录要求、选择材料、确认动作和核对结果的地方，都保留人的步骤。

### D1 / D2 · 上线前，看清还有哪一步没验过。

适合：独立开发者、亲自负责产品交付的工程师。

周五准备上线支付功能。Agent 已经交了代码和测试报告，早先约定的旧订单兼容、失败后重试和手机体验，却还需要逐项核对。越到最后，越怕一句“做完了”掩盖没检查的地方。

在 Work 里，把这些要求留在同一目标中，将手机体验设为需要本人验收。Agent 按要求留下改动与测试报告；如果想把旧订单兼容挪到下一版，就提出具体变更，交给你决定。收尾时，缺少你的手机验收结论，这项缺口仍会挡住目标完成。

你在对应版本上走完支付与失败恢复，再留下结论。发布前，已有的依据和还需亲手检查的地方，都能对着当前确认的要求核对。

**Work 接上的一段：**同一份交付记录里，看清原来答应什么、后来改了什么、现在还差什么。

**使用前提：**先记录关键要求，并明确哪些需要本人验收；Agent 的测试报告仍需核对。

**实现与验证：**基础机制随 v0.2.0 源码公开；当日 main 有后续加强。官网整段建议标“开发中 · 场景示意”，不要把新版画面标为公开安装包。

### D3 · 周三回来，接着已经改过的要求做。

适合：功能跨多天、多次会话推进的开发者。

周一，你让 Agent 做一个订单导出功能。周二决定只导出当前筛选结果。周三新开会话，旧聊天还停在“导出全部订单”，你得先弄清哪份要求算数，才敢继续。

把范围变化和上次进展记回 Work 的同一目标。从这个目标继续工作，让 Agent 先读取现行要求、最近决定和未完成项，再核对仓库与工作树。上次做了哪些部分、为什么改范围、空结果提示还缺什么，都有记录可查。

这次就从“补好筛选为空时的提示”开始。继续使用原来的 Agent，或在需要时换一个，工作的要求与进度都留在这条目标上。

**Work 接上的一段：**会话会结束，当前要求、关键决定和交付记录继续属于这件工作。

**使用前提：**接入的 Agent 需要持续写回进展，续做时仍须核对代码状态；不会自动搬运全部聊天。

**实现与验证：**Goals、Sessions 和目标终端的基础机制已公开；当前实现与增强按 09:00 main 核对。整段标“开发中 · 场景示意”。

### K1 / K4 · 交稿前来了新材料，接着这份稿子改。

适合：持有本地材料、亲自交付建议的顾问与研究作者。

明天要给客户交一份推广建议。初稿写着“下月全面推广”，今天补来的文字访谈却提到：试点团队的旧数据导入还没跑通。结论要改，原稿里已经确认的内容还要接着用。

把这份文字材料带进 Work，打开原来的文稿，对照相关段落。让助理整理新材料对这一段的影响，你将建议改为“先完成旧数据导入，再扩大试点”，并检查、补齐出处。没有证实的部分，就在稿子里明确留下待核问题。

交稿前，把审阅后的文稿保存为固定成果版，核对导出内容后交给客户。以后继续修改时，你仍能回到这次交出的版本，核对当时写了什么、留下了哪些疑问。

**Work 接上的一段：**新材料、人工判断和正在写的稿子在同一工作台接上；交付的一版也能留住。

**使用前提：**示例使用已整理成文字的材料；你选择材料、检查改写与出处，并通过现有渠道交付。

**实现与验证：**Pages、材料读取、助理与固定成果等组成能力在 main；这套代表性材料的完整旅程未实操。标“开发中 · 场景示意”，不标真实客户案例。

### K2 / K6 · 下次评审前，把上次答应补的事带回来。

适合：自己跟进交付、向客户或负责人汇报的项目牵头者。

上次客户评审，你答应确认历史数据能否导入，再补一份试用安排。几天后，一件已经收到回复，另一件还在等。下次评审临近，得把这些零散进展重新交代清楚。

会后，在 Work 的纪要中选中自己要跟进的内容，确认记成待办，安排哪天由自己跟进。处理时回看来源，知道当时为什么要做；收到回复，就由你把结果补进当前文稿。没拿到答案的继续列为待核。

评审前，围绕这两件事整理出“确认了什么、还差什么、这次要决定什么”，需要时让助理帮你组织表达。保存本次说明，再用原来的沟通渠道交给对方。下一轮从这些进展继续。

**Work 接上的一段：**一条跟进带着来由，处理后的结果接回下一次交付。

**使用前提：**这里跟进的是你自己的事项；收到他人的回复后由你补入记录，不自动派单或汇总所有聊天。

**实现与验证：**Pages、选句转 Todo、来源/日期与固定成果在 main；周期简报自动生成仍属设计。此处是本人组织的路径，完整旅程未实操，标“开发中 · 场景示意”。

其余场景仍保留在枚举与全景中。重复方法和自建工具作为延展；团队派单、完整主动工作与自动简报仍按设计/在途状态表达。本次不将它们强塞进四条主案例。原 09:00 的六条深案例已保存在[取舍记录的历史附录](../research/2026-10-17-官网场景取舍.md)，供后续继续研究。

## 五、为什么是 Molis Work？

适合考虑 Work 的时刻，是工作跨过了几天、几份材料和几个入口，你开始花很多精力核对“答应什么、做到哪、结果在哪、还差谁判断”。它的价值要在这条具体工作链上成立。

### 1. 同一件事做了几轮，交付标准仍然清楚

对应 D1、D2、D3。Work 将当前要求、报告、缺口、关键决定与人的有效验收留在同一目标中。对有真实交付责任的开发者，这比一句“完成了”更容易核对。它允许普通工作继续推进，同时把放宽承诺和指定验收交回有权的人。

这不是首创验收门禁：[Conductor 待办](https://www.conductor.build/docs/reference/todos)、[Claude Code 完成钩子](https://code.claude.com/docs/en/agent-teams#enforce-quality-gates-with-hooks)、[Factory QA](https://docs.factory.com/software-factory/automated-qa) 都有相应机制。Work 应争取的差别是直接提供跨会话、与约定版本对应的人机交付记录。是否更省维护，还要与“规格文件 + CI + PR review”实操比较；不替代测试或代码审查。

### 2. 材料、稿子和后续行动放得近，交付以后还能回查

对应本轮官网的 K1/K4 改稿、K2/K6 跟进案例，以及候选 D7。Work 把材料处理、文档、待办和固定成果版放在同一环境；助理通过这些工具的原有动作工作，结果留在用户继续工作的地方。它更适合本地资料较多、需要自己掌握交付版本、又会继续追后续事项的人。

引用、原位 AI 和多工具处理已有成熟产品。Work 的候选优势是这类输入条件下更少搬运、版本更清楚；不能保证所有跨插件引用自动保持语义正确，也没有测得效率提升。只有改写一段字，或者团队资料都在现成办公套件，原工具可能更合适。

### 3. 作为延展：人和 AI 共用工具，重复的方法能留下来

对应 D4、D6、K9。能力按合同登记与授权，页面、助理、流程、外部 Agent 在允许范围内调用同一操作；高频做法可先串流程，缺少的环节再试做插件。这有机会减少“给人做一份界面、给 AI 再写一套脚本、各记一份状态”的维护。

自动化与应用生成并不稀缺。Work 的区别要落在“接着已有材料和目标使用”的体验上；当前创作台仍预览、第三方市场尚未交付。外部连接覆盖、成熟 CI 或一次性脚本更合适的事，就沿用它们。并非每种工作都值得生成一个插件。

### 4. 工作积累主要由自己掌握，模型与工具可以选择

贯穿 D3、K1、K3、K6。工作数据主要在本机，内容由各自 owner 保存；模型与权限集中管理，提示词和规则有可查看、调整的入口。选择哪家模型不必成为重新建立整套工作记录的理由。

本机保存、自带模型、开源都已有替代，不能单独推导“更安全、更便宜、更自由”。使用网络服务仍会外发材料；模型需要配置和费用；当前旧版数据也不是无损一键升级。长期可掌握性要靠可读导出、可回查版本与实际升级路径证明，不能只靠一句本地优先。今天记忆导出筛查失败会明确停止，是一个具体边界修正，不能扩张成所有信息均不会外发的承诺。

**今天最值得讲清楚的，是前两条的具体案例，再用第三、四条解释它们为什么有机会持续成立。** 完整团队协作、自动准备简报和通用电脑操作可作为产品方向展示，但不进入“今天已经更好”的结论。

### 给官网与产品迭代的输入

官网优先取第一章两段与[四个已精修案例](官网场景案例-2026-10-17.md)：D1/D2 交付核对、D3 隔天续做、K1/K4 新材料改稿、K2/K6 两次评审间的跟进；按“写代码 / 写文档、管事情”分别呈现。D6/K9 方法复用保留为延展。内部的实现状态映射为“已发布 / 开发中”，演示标“示意”；只有设计的步骤就近说明，不能用开发中掩盖尚未实现。主线发布以后也需核对 Release 实际包含的切片，不能把所有开发中标签一起改已发布。

优先验证的产品方向是：**让验收来源与对应版本看得清；让材料到交付的引用能经过真实改写和导出；减少规格/目标双份记账；让首次安装和模型配置能走到第一份真实结果。** 先借现有能力完成真实任务比较，看到哪步仍然费力再改；不先增加一层新系统。详细的最小实验、反例与待做访谈见两份补研及[审读记录](../research/2026-10-17-work-split审读.md)。这些是建议，未变成开发排期。
