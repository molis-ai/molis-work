## 1. 背景

- 送达的位置（`operations.ts:185-240` 的 `runScheduledOperation`）：
  - `:218-223` 的事务把本次记成 `running`，再调执行入口；
  - `:227` 算出 `text`；`:228-238` 的第二个事务里送通知（`:230`）、记本次的终态与 `detail: text`（`:232-233`）、结果未知时把操作改成 `needs_review`（`:234`）、一次性的做完时把操作的 `detail` 也记成 `text`（`:236`）；
  - `:230`：`outcome.state !== "unknown"` 且（失败，或这个定时操作勾了 `inbox`）才送。**失败的一定送，成功的看 `inbox`，结果未知的不送；**
  - `:239` 返回给 Scheduler 的说明，失败时是「运行失败：」加 `text`，Scheduler 截到 500 个单元（`index.ts:413`、`:418`，不在本单）。
- `text` 是 `operationResultText(outcome.value)`（`:242-251`）：
  - 字符串：整串（`:243`）；
  - 对象：`text`、`summary`、`message` 里第一个非空字符串（`:246`），没有就取第一个非空字符串的值（`:247-248`）；
  - 都不是（数组、数字、对象里没有字符串值）：`JSON.stringify(value)` 的前 2000 个单元（`:250`）；
  - 失败时是错误信息（`runtime-wakeups.ts:73` 的 `error.message`），结果未知时也是错误信息（`operations.ts:226`）。
- 送达（`runtime-wakeups.ts:77-79`，本单只读）：标题是「插件名：」加结果文字前 80 个（或操作名），摘要是 `text` 的前 280 个，正文是 `text || "操作已结束"`。T-162（#1435）改标题与摘要，正文不动。
- 通知服务（`plugin-notification-service.ts:39-41`）逐个字段查：`key` 300、`title` 200、`summary` 1000、`body` 100000，都按 `.length`（UTF-16 单元）；`title` 与 `body` 还不许 `trim()` 后为空（`summary` 可以）。不合格抛 `actions.input_invalid`「通知字段无效：<字段>」。它在 `joinPluginTransaction` 里同步执行，Schedule 的 `notify`（`runtime-database.ts:40-42`）在写事务里调它，一抛事务就回滚（`runtime-database.ts:42-51` 的 `write`）。
- 下游：
  - Feed 的接收动作（`plugins/native/feed/src/notification-actions.ts:21-22`）：`body` 是 `{ type: "string", maxLength: 100000 }`，AJV 数的是码点，服务放行的它一定放行；`summary` 没有下限，空串也收；
  - Feed 入库时正文原样存（`plugins/native/feed/src/store/items/ingest.ts:85`），读回是 `FeedItemRecord.body`（`rows.ts:50`；`packages/contracts/src/modules/feed.ts:45` 是 `string | null`）。
- 同一个插件里已有的「按整字截到 N 个单元以内」写法（`runtime-wakeups.ts:14-23`，T-099）：

  ```ts
  /** The notification service takes a title of at most 200 UTF-16 units; a longer one is cut at a whole character and ends with 「…」. */
  function notificationTitle(title: string): string {
    if (title.length <= 200) return title;
    let cut = "";
    for (const character of title) {
      if (cut.length + character.length > 199) break;
      cut += character;
    }
    return cut + "…";
  }
  ```

## 2. 目标

1. 定时操作的结果文字不超过 100000 个单元时，与现在一字不差（通知正文、本次记录的 `detail`、操作的 `detail`）。
2. 超过 100000 个单元时，按整字截到不超过 99999 个单元，加「…」，一共不超过 100000 个单元；通知送得进收件箱，本次记录是 `succeeded`（或 `failed`），不再停在 `running`。
3. 结果文字 `trim()` 后为空时当作空串：通知正文是「操作已结束」，成功通知的标题用操作名，送得进收件箱。
4. 结果不是字符串、对象里也没有字符串值时，取 `JSON.stringify` 的前 2000 个字（原来是前 2000 个单元），不劈开两单元字。
5. 用例钉住上面几条：去掉上限、上限差一、改回按单元截、去掉「…」、边界改成小于、去掉空白判断、JSON 改回按单元截，各自都红。

1. **`operations.ts`**：三处，其余一个字不动。

   - `:227`，原：


     新：


   - `:250`，原：


   - 文件末尾，`:251` 的 `}` 之后空一行，加：

     ```ts
     /**
      * The result text is also the notification's body, which the notification service takes only non-blank and at most 100000 UTF-16 units: a blank
      * one becomes empty (delivered as 「操作已结束」), and a longer one is cut at a whole character and ends with 「…」.
      */
     function notificationBody(text: string): string {
       if (!text.trim()) return "";
       if (text.length <= 100_000) return text;
       let cut = "";
       for (const character of text) {
         if (cut.length + character.length > 99_999) break;
         cut += character;
       }
       return cut + "…";
     }
     ```

   说明：
   - 包在调用点而不是 `operationResultText` 里面：`operationResultText` 有三个 `return`，包在外面只动一行，`:250` 的 2000 个字（最多 8000 个单元）也一起过这道上限，不另写；
   - 先判空白再判长度：100001 个空格也是空白，给空串；
   - `for (const character of text)` 按码点走，`character.length` 是 1 或 2，累加到第 99999 个单元为止，不劈开两单元字；加「…」（1 个单元）后不超过 100000；
   - `text` 同时是本次记录和操作的 `detail`（`:233`、`:234`、`:236`）与给 Scheduler 的说明（`:239`），所以这三处跟着变：只在超长或全是空白时才变（第 8 节第 4 条）；
   - `[...x]` 按码点展开，`slice(0, 2000)` 取前 2000 个字，同 T-079 的写法；
   - 两个新写法都只在本文件，不导出。

2. **`tests/schedule-runtime-delivery.test.ts`**：在文件末尾（`:54` 的 `});` 之后）空一行，原样加下面两个用例。`parkFeedClock`（`:12`，同一文件）、`scheduleRuntimeFixture`、`scheduledOperationActions`、`listScheduledOperationOccurrences`、`assert`、`test` 文件开头已有，不加 `import`。

   ```ts
   test("RAC-1803 a timed operation's result past the 100000 units a notification body takes is cut at a whole character and still reaches the Inbox", { timeout: 60_000 }, async t => {
     // 50000 🟢 (U+1F7E2, two units each) are 100000 units, which the notification service takes as a body; 50001 are one character past it
     // (apps/local-host/src/plugin-notification-service.ts:39-41), which it refused, rolling the delivery back with the occurrence left running and
     // nothing in the Inbox. Whole characters within 99999 units are 49999 🟢 (99998 units), then 「…」. A cut by units would keep half of the 50000th 🟢.
     const f = await scheduleRuntimeFixture(t), at = new Date(Date.now() + 1000).toISOString();
     await parkFeedClock(f);
     f.execute(async (_caller, input) => ({ text: "🟢".repeat((input as { text: string }).text === "over" ? 50_001 : 50_000) }));
     const over = await f.sdk.invoke(scheduledOperationActions.add, { at, operation: "summarize", input: { text: "over" }, inbox: true });
     await f.sdk.invoke(scheduledOperationActions.add, { at, operation: "summarize", input: { text: "edge" }, inbox: true });
     assert.equal((await f.tick(at)).failed, 0, "neither notice is refused");
     const bodies = (await f.inbox()).map(item => item.body ?? "");
     assert.deepEqual(bodies.map(body => body.length).sort((a, b) => a - b), [99_999, 100_000], "both notices reach the Inbox, the longer result cut within 100000 units");
     assert.ok(bodies.includes("🟢".repeat(50_000)), "a result of exactly 100000 units is delivered whole");
     assert.ok(bodies.includes("🟢".repeat(49_999) + "…"), "a longer one keeps its whole characters within 99999 units and ends with 「…」");
     const store = await f.store();
     assert.equal(listScheduledOperationOccurrences(store.db, f.project.project_id, over.scheduleId)[0]?.state, "succeeded", "the longer result's run is recorded as done");
   });

   test("RAC-1803 a timed operation whose result is only blanks still reaches the Inbox, named by its operation", { timeout: 60_000 }, async t => {
     // The notification service refuses a body that trims to nothing (plugin-notification-service.ts:39-41), and " \n " is not empty, so
     // `text || "操作已结束"` (runtime-wakeups.ts:79) kept it and the delivery rolled back like an overlong one. A blank result is now empty: the body
     // is 「操作已结束」 and the success title falls back to the operation's name.
     const f = await scheduleRuntimeFixture(t), at = new Date(Date.now() + 1000).toISOString();
     await parkFeedClock(f);
     f.execute(async () => ({ text: " \n " }));
     const created = await f.sdk.invoke(scheduledOperationActions.add, { at, operation: "summarize", input: { text: "x" }, inbox: true });
     assert.equal((await f.tick(at)).failed, 0, "the notice is not refused");
     assert.deepEqual((await f.inbox()).map(item => [item.title, item.body]), [["定时笔记：汇总", "操作已结束"]], "the notice names the operation and says it finished");
     const store = await f.store();
     assert.equal(listScheduledOperationOccurrences(store.db, f.project.project_id, created.scheduleId)[0]?.state, "succeeded", "the run is recorded as done");
   });
   ```
