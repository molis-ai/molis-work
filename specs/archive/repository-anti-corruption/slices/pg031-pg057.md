## 2. PG-057：Shelf

- **工作台电脑侧栏**（`apps/workbench/src/side-panel-computer.ts`）：原来把一轮的操作记录直接 POST 到 Shelf 的插件路由 `/api/plugins/io.molis.work.shelf/items`，失败时再调它的 `/items/<id>/delete`。现在界面把写好的标题与正文 POST 到宿主的 `/api/computer/records/<id>/shelf`（`apps/local-host/src/computer/computer-http.ts`）。宿主以本人身份经 Shelf 的公开动作做：
  1. 先用 `shelf.items.admit@2` 放进文字；
  2. 再放记录里最新的一张截图；
  3. 截图读不到或放入失败时，用 `shelf.items.delete@1` 取回文字，第一次删除失败会再试一次。

  动作从 Home 的动作目录按 `capability_id@version` 找，不钉提供方。截图字节从宿主自己的记录里读，不经过页面。
- **桌面壳**（`apps/desktop/adapters/tauri/src/shelf_http.rs`、`drop_wheel_macos.rs`）：POST 的是 Shelf 在 Manifest 里声明的路由。那是插件自己声明的对外接口，不是宿主私有 HTTP，不算本行要清的对象。这里不新开「桌面令牌调动作服务」的路，也不另记 BL（统筹 2026-10-25 裁）。
- `/api/shelf` 在 main 上已经不存在（Shelf S3 起改成插件路由）。

## 3. PG-057：助理

- **相关的助理工作**：新加宿主动作 `assistant.works.related@1`（`apps/local-host/src/assistant/assistant-related-action.ts`）。
  - 登记在助理自己的提供方 `io.molis.work.assistant.rules` 下，和提醒规则、评论回复的动作同一处登记。
  - 谁能调：`audiences: ["user", "plugin"]`。插件来调时，处理器只认调用插件 Manifest 里自己的 subject reader，且这个 reader 要的权限已授予；读的是调用所在的项目，和原来页面的 HTTP 读法一样。别的 owner 的对象一律拒绝（`actions.forbidden`）。
  - 返回：只有工作的状态和结果链接，不含对话与材料。
- **页面侧**：
  - Todo 的详情改经 `invokeAction` 调这个动作，`todoManifest.capabilities.consumes` 声明 `assistant.works.related`。
  - `plugin-page-authority.ts` 删掉给隔离页面开的 `GET /api/assistant/related` 例外：页面再直接请求，一律 403。这是收窄。
  - `/api/assistant/related` 的 HTTP 只留给平台自己的界面（助理 island、成果库详情里的「被谁引用」）。成果库是平台能力，它的客户端跑在工作台文档里，不算插件。
- **评论回复（threads）**：按方案 A 做，见第 5 节。
- **助理自己的界面**（island、设置、电脑侧栏的「停止这项工作」）属于平台本身，继续用 `/api/assistant`。

## 5. 评论回复：交给助理面板（方案 A）

统筹 2026-10-25 裁：不给 `assistant.threads.*@1` 加 `plugin` 受众（插件页面会成为替人发起 AI 回复的代理），由外壳画按钮，人点了才以本人发起。

- **合同**：`AssistantPluginMessage`（`packages/contracts/src/services/assistant.ts`，`molis:assistant-message`）加可选的 `thread: { thread_id, message_id, draft? }`；`source` 加 `plugin_id`，只由外壳填。`dom-events.ts` 的条目同步写明。
- **外壳**（`apps/workbench/src/browser/plugin-frame/presentation.ts`）：转发页面的 `assistant-message` 时，`source` 整个由外壳按 frame 写（`surface`、`title`、`plugin_id`），页面写的不用。没有手势时照旧去掉卡片、把 `delegate` 降成 `suggest`。
- **助理**（`assistant-island.ts`、`assistant-step-row.ts` 的 `ASSISTANT_THREAD_REPLY_SCRIPT`）：收下消息时检查 `thread`（id 至多 160 字；草稿要么完整在宿主上限内，要么整条线程不算）。建议在下一步那一行画成「让助理回复{来源}的评论」；人点了，`replyToThread` 以本人调 `/api/assistant/threads/start`（`assistant.threads.start@1`），目标是 `source.plugin_id`、`object` 与 `thread`，然后打开那项工作。跟进、重试、停止都在助理面板里。没有 `source.plugin_id`（不是从 frame 来的）就只当普通建议放进输入框。
- **Pages**（`plugins/native/pages/src/comment-side-client.ts`）：评论照旧经自己的插件路由保存；勾了「请助理回复」时，保存后发一条带 `thread` 的 `suggest`，状态行提示去助理面板点「让助理回复」。侧栏里原来的状态轮询、重试、停止都删了（它们调的 `/api/assistant/threads/*` 在隔离页面里一直被拒）。消息大小与失败保留按下面的窄工单处理。
- **信任**：按钮是助理画的、在工作台文档里，页面碰不到；插件身份来自 frame；处理器 `assertPerson` 不变。工作台文档本身的脚本是平台代码，能自己写 `plugin_id`，但仍要人点。
- **本机验证**：下列窄工单覆盖普通评论、完整建议与真实侧栏恢复路径；原 PAS-01 等其他浏览器场景本单未重跑。

### 2026-10-25 窄工单：完整评论建议的转发上限

状态：已实现并通过定向工程与实际浏览器路径验证，候选待独立评审；资源增长尚待按现行政策评审处理。基于 `6a2d59cef4a57a04c506a938de5bfb002c019717`；修正 #1311 评审第 2 节的两条非阻塞项。目标是让超限有可见、准确的结果，评论和待交给助理的内容可恢复；不改变方案 A 的授权与启动方式。

旧的「未保存正文超过 90,000 字就不保存评论」规则改为完整消息检查：用与外壳相同的 `JSON.stringify(detail).length`（含转义、对象、线程、评论和未保存正文）与 100,000 比较，等于上限可转发。发送前构造唯一一份 detail；尚未保存时，服务端消息 id 暂为空串，先检查这个已知大小的下界，超限就报「评论未发送」，不保存。保存返回真实消息 id 后，填回同一份 detail，再检查最终准确大小；这一步超限就显示「评论已保存，尚未交给助理」，保留原评论草稿、`request_id` 和已保存的 `message_id`，不发事件、不显示已交给助理、不清草稿。缩短或保存文档正文、取消附带草稿后重试，同一条未改正文的评论复用已保存 id，不重复保存；修改评论正文仍按现有规则成为新的评论意图。

Pages 范围是评论客户端、内部 host 类型、浏览器装配、双语错误文案，以及下面三份相关测试。删除没有消费者的 `CommentSideHost.route` 与装配参数。不增加 ACK、队列、公共合同或 API，不改不透明 frame 桥接的上限、身份覆盖、目的名单、手势处理、受众和助理按钮。普通非 AI 评论不受这项转发大小检查影响。验证先整体构建，再跑有限离线回归，最后在隔离 Home / 专用测试浏览器里验证实际评论 frame → 外壳 → 助理下一步；不跑全量。
