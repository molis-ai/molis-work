# 游戏设计

围绕核心循环、系统内容、玩家旅程和反馈建立可玩闭环。

适用于：游戏设计、玩法系统、游戏内容。

## 规划路径

1. 定义幻想、玩家动机和核心循环
2. 建立系统规则与内容供给
3. 设计玩家旅程和反馈
4. 制作可玩切片并测试节奏与平衡

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| core_gameplay | 核心玩法 | 玩家反复做什么，为什么愿意继续？ |
| game_systems_content | 游戏系统与内容 | 规则、资源和内容怎样支持循环？ |
| player_journey | 玩家旅程 | 学习、成长、挑战和长期目标怎样展开？ |
| interaction_ui | 交互与 UI | 输入、反馈和信息怎样保护可玩性？ |
| audiovisual | 视听表现 | 视听怎样传达状态并强化情绪？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| systems-after-loop-intent | 系统规则和内容供给依赖已经明确的玩家动机与核心循环假设。 | systems depend_on core loop intent |
| production-after-loop | 大规模内容和视听生产依赖已验证的核心可玩循环。 | production depends_on playable loop |

## 完成证据

- 可玩切片
- 玩家行为观察
- 规则和数值检查

## 收口检查

- 核心循环实际可玩
- 内容与系统服务同一体验

## 常见误拆

- 堆设定不做循环
- 先生产大量内容
- 只拆技术层不拆体验结果

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
