## 1. 背景

### 1.1 命令的定时器怎么走（`cdp.ts`，只读）

- `:304` 取 `started = performance.now()`；`:307` `setTimeout(…, timeoutMs)`（右花括号和 `timeoutMs` 在 `:350`：`      }, timeoutMs);`）；定时器到期后 `:310` 先 `setImmediate` 让出一轮检查阶段，再在 `:331-332` 写消息、`reject`。
- 这个用例的 harness 没开 `profileTimeouts`（`withHarness(…, {}, …)`），`this.profile` 为空，`:335` 的 `if (!profiler) { settle(undefined, false); return; }` 立刻结算，没有任何等待。
- 所以从用例的 `started` 到结算，只有定时器自己的等待，加上到期之后的 `setImmediate` 与微任务。**后面这些只会让它更晚，不会更早。** 量到 118.7 ms，说明 Node 的定时器比 120 ms 早触发了约 1.3 ms（按 `performance.now()` 算）。

### 1.2 Node 怎么数这 120 ms

- `lib/internal/timers.js` 的 `insert(item, msecs, start = binding.getLibuvNow())`（本机 Node v24.14.0 用 `node --expose-internals` 打出来核过）：起点取 libuv 循环的毫秒时间 `getLibuvNow()`（整数毫秒），到点是 `start + msecs`，同一时长的定时器放在同一条链 `timerListMap[msecs]` 里，`L.append(list, item)` 按建的先后追加。触发时 `listOnTimeout` 每次先看链头（`L.peek(list)`）：链头还没到期（`now - timer._idleStart < msecs`），整条链就等，排在它后面的定时器也不会先跑。所以排在后面的定时器不可能先于排在前面的触发（同样核过 v24.14.0 的 `listOnTimeout`）。
- 到期的判断也是循环的整数毫秒时间。起点、到点各向下取整，在精确时钟上真实等待大于 `limit − 1`（T-152 的算式，对）。本机（macOS）300 个 20 ms 定时器，最短的 19.256 ms，吻合。
- 118.7 小于 `limit − 1 = 119`，所以 runner 上还有别的因素把窗口拉宽了。**没有证实**，最可能的候选：libuv 在 Linux 上，内核报告 `CLOCK_MONOTONIC_COARSE` 的分辨率不大于 1 ms 时，循环时钟就读这个粗钟（比精确钟最多落后一个节拍）。那样真实等待只保证大于 `limit − 2`（118），118.7 在范围内。这是凭对 libuv 源码的印象写的，起草时没有核；runner 内核的节拍也没法从这里查。**修法不依赖它是不是真因。**
- 统筹原先猜的「定时器从当前循环迭代缓存的旧时间起算，旧了好几毫秒」**不成立**：本机 v24.14.0 上，在定时器回调里空转 40 ms 再建 100 ms 的定时器，它在 102.3 ms 后触发（在 `setImmediate` 里同样试：101.9 ms），不是 60 ms 左右。`getLibuvNow()` 会刷新循环时间。

### 1.3 为什么不是别的修法

- **把 119 再放宽到 118 或更低**：仍是猜。118.7 刚好过 118，下次 runner 抖一点就红；每放宽 1 ms，真缩短 1 ms 的定时器就多漏掉一点。
- **拿 harness 自己的起点或消息里的 `elapsed` 当下界的参照**：`cdp.ts:304` 的 `started` 与用例的 `started` 是同一个钟（`performance.now()`），`elapsed` 是同一个差向下取整（118），量出来一样早。
- **去掉下界**：命令的限被缩到 1 ms 也过，等于删掉 `RAC-1452` 的核心。
- **本单的参照定时器**：下界不用钟的数字，用 Node 自己对同一时长定时器的承诺（先建的先触发）。命令的限没被缩短，它就一定不早于参照；被缩短了，才会早。

### 1.4 这条下界要守的是什么

`RAC-1452` 在这个用例里说的是：调用方给 `harness.command` 的限（120 ms）就是定时器的时长，超时发生在限上，不提前。提前的做法有：定时器时长被减小（`timeoutMs - 5`、`Math.min(timeoutMs, 60)`），或结算走了别的路径。参照定时器对这些都敏感，对毫秒怎么数不敏感。

## 2. 目标

1. 在合并队列所在的 Linux runner 上，`RAC-1452` 这一例不再因为定时器比 `performance.now()` 早到 1 ms 以上而红；它的下界用的是「同一时刻起、同一时长的普通定时器已经触发」，没有毫秒数。
2. 下界仍拦得住被缩短的命令定时器：定时器时长改成 60 ms，这一例红，红在新的参照断言上；连跑 10 次，10 次全红。
3. 这一例的其余断言一字不动：消息格式、上界 `<= 370`、迟到的回复不结算任何命令、请求数 3、断线、`close()` 那两段。

1. **替换块。** 把 `browser.test.mjs:517-525` 这九行（从 `    const started = performance.now();` 到 `    assert.ok(elapsed >= 119 && elapsed <= 370, …);`，含中间的两行注释）整段换成下面这些。缩进 4 个空格，其余各行（`:516` 的 `await harness.command("Ping");` 以前，`:526` 的 `// The late reply settles nothing…` 以后）一个字不动：

   ```js
       // The limit is not a number of milliseconds on `performance.now()`: Node counts a timer on its own whole-millisecond loop
       // clock, and a correct 120 ms timer has settled the command 118.7 ms after this clock said it began (merge_group run
       // 40850221824). What the limit promises is that the command gets the timer the caller asked for, and Node answers that
       // exactly: timers of one duration share a list and fire in the order they were armed. A plain 120 ms timer armed just
       // before the command has therefore fired by the time the command's own 120 ms timer has run and settled it; a shorter
       // command timer lands in an earlier list and can settle first. Arm the reference before the command, never after it.
       const started = performance.now();
       let referenceFired = false;
       const reference = setTimeout(() => { referenceFired = true; }, 120);
       await assert.rejects(harness.command("Never", {}, undefined, 120), (error) => {
         assert.match(error.message, /^CDP timeout: Never \(elapsed \d+ms; limit 120ms\)$/);
         return true;
       });
       const elapsed = performance.now() - started;
       clearTimeout(reference);
       assert.ok(referenceFired, `timed out after ${elapsed.toFixed(1)}ms, before a plain 120 ms timer armed just ahead of it had fired`);
       assert.ok(elapsed <= 370, `failed after ${elapsed.toFixed(1)}ms`);
   ```

   这段里与原来逐字相同的有 6 行：`const started = performance.now();`、`await assert.rejects(…, (error) => {`、`assert.match(…)`、`return true;`、`});`、`const elapsed = performance.now() - started;`。新写的 11 行是 6 行注释、`let referenceFired`、`const reference`、`clearTimeout(reference)` 和两条 `assert.ok`；去掉的 3 行是原来的两行注释和 `assert.ok(elapsed >= 119 && …)` 那一条。
   - **参照定时器必须建在命令之前**，两条语句之间不许有 `await`。起草时试过相反的顺序（先发命令、后建参照）：400 次里有 3 次误红，因为参照落在了更晚的一条链上。顺序对，400 次 0 次误红；
   - 参照的 `120` 和命令的 `120` 是同一个数，必须保持相同：时长不同就不在同一条链上，顺序保证不成立；
   - `clearTimeout(reference)` 在断言之前，是为了断言失败时不留一个悬着的 120 ms 定时器；
   - `referenceFired` 在命令结算（`setImmediate` 之后）时检查：此时它已经是 `true`（正确的实现），或者仍是 `false`（命令的定时器比参照早）。命令的拒绝回调与读 `referenceFired` 之间只有微任务，参照不可能在这中间触发。

## 8. 与默认不同的

1. **这不是放宽。**
   - 老断言要的性质是「命令的定时器不比调用方给的限短」。`elapsed >= 119` 拿 `performance.now()` 的毫秒数去量它，而 Node 不按这个钟数毫秒（第 1.2 节）：同一个正确的定时器，量出 118.7；T-152 已经为同一个原因放宽过一次（120 → 119）。再放宽一次仍然是猜；
   - 新断言没有容差：正确的实现不可能红（按 Node 的实现，同一条链上后建的不会先于先建的触发），定时器被缩短就红；
   - 检测对比（第 7 节「起草时的试验」第 4 条的表）：每个被缩短的档位，新规则红得都不比老的少；
   - 其余断言一字不动：`assert.match` 的消息、上界 `<= 370`、迟到的回复、`received.length === 3`、断线、`close()`。第 5 节步骤 4 用 `git diff -U0 | grep` 核；
   - 失去的只有一样：老的绝对下界在「整个 Node 的定时器都一起偏早」时能看出来。那不是 harness 的问题，也不是 `RAC-1452` 要守的。
2. **原因没有查到底，修法不依赖它。** 第 1.2 节说清了哪些是核过的（`insert` 的实现、起点不旧、macOS 上最短值）、哪些是候选（Linux 粗钟）。参照定时器两个都在同一个循环钟上数，所以不管 runner 上是哪一种，都不受影响。统筹要查，办法只有一个：在 `.github/workflows/*` 里加一步打印内核节拍（`getconf`、`/boot/config-*` 里的 `CONFIG_HZ`），那是 CI 改动，不在本单。
3. **参照必须在命令之前建。** 第 5 节第 1 条的末尾和代码注释最后一句都写了；试验里相反的顺序 3/400 误红。
