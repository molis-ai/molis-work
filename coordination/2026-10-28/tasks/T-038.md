## 1. 背景

T-019 加了 `tests/ci-install.test.ts`（RAC-1183），守着 CI 里每个装依赖的步骤都有超时、都先用本机 Node 的头文件。二审在 #1341 里（找「【二审 T-019】@c022cd60f 可合」那条的 [建议] 1、2）指出守卫会漏判，并用改写后的 `ci.yml` 实跑验证过。下面的行号都在 main `df9635d7b` 核过：

1. 块头认得太窄。`commands()` 把单独的 `|` 或 `>` 当块头（`tests/ci-install.test.ts:74` 的 `inline !== "|" && inline !== ">"`，`:79` 的 `(?!\|$|>$)`）。`run: |-`、`|+`、`>-`、`|2`、`| # 注释` 都被当成一条单行命令，块里的内容丢了。`blockCommands()` 还要求块内行缩进恰好 10 格（`:62`）。
2. 命令认得太窄。`INSTALL = /^pnpm install\b/`（`:24`）只认行首。`pnpm i`、`CI=1 pnpm install`、`corepack pnpm install`、`cd x && pnpm install` 的新步骤抓不到。
3. 开头的注释（`:5-17`）说得比实际能拦的多：「新步骤或未守卫的安装会失败」只对认得的写法成立。
4. 超时的正则锚在行尾（`:21` 的 `/^ {8}timeout-minutes: (\d+)$/m`）。写成 `timeout-minutes: 5 # 说明`、带行尾空格、或整份文件 CRLF，正确的写法会被报成「没有 timeout」。这一条是报红，不会漏，影响小。
5. 守卫没有计数哨兵。`:117` 只断言「至少有一个安装步骤」。步骤悄悄掉出守卫、或有人整段删掉一个安装步骤，测试照绿。
6. 守卫只读 `ci.yml` 和 `full-suite.yml`（`:110-113`）。以后新增的工作流文件里的 `pnpm install` 不受约束。现在只有 `release-macos.yml:42` 一处，T-019 任务书明令不动。这一条来自二审同一条 [建议] 的第三项，统筹的 T-038 清单没列，我并进了 `RAC-1458`；统筹不要可删（第 11 节）。

今天 main 上三份工作流里的 `pnpm install` 数：`ci.yml` 7 处（`:63 :150 :191 :308 :490 :555 :629`），`full-suite.yml` 1 处（`:88`），`release-macos.yml` 1 处（`:42`）。我用一条宽松的正则逐行数过，数字对得上。三份里都没有 `|-`、`>` 这类写法。

## 2. 目标

1. 下面这些写法的安装步骤，守卫都认得出来，缺超时或缺头文件就红：`run:` 块头 `|-`、`|+`、`|2`、`|2-`、`|-2`、`>-`、`>+`、带行尾注释的块头；命令写成 `pnpm i`、带环境变量或 `corepack` 前缀、在 `&&`、`||`、`;`、括号、`then` 之后。`timeout-minutes` 带行尾注释、带空格、整份文件 CRLF，都按正确写法放过；写成非整数、表达式、带引号，报红并说清是哪种（`RAC-1456`、`RAC-1457`）。
2. 守卫认得的安装数，等于文件文本里「宽松地数」出来的安装数，也等于写死的预期数（`ci.yml` 7、`full-suite.yml` 1）。认漏一种写法、或删掉一个安装步骤，都会红，而不是悄悄少检查。`.github/workflows/` 下出现任何不在名单里的、含 `pnpm install` 的文件，也红（`RAC-1458`）。
3. 开头的注释与测试一一对应：注释里写的每一种「认得」和「不认得」，都有一条测试名对着（评审人核）。

## 3. 不做

- 不改 `.github/workflows/*`，哪怕是临时改一下再还原。`release-macos.yml:42` 那一处没有超时和头文件，要补是 CI 改动：不做，已记入观察一天后的 CI 方案，用户批了再改。
- 「Install pnpm」步骤（`npm install --global …`）没有超时，`gates` 等 5 个作业没有作业级 `timeout-minutes`：同上，CI 方案，不做。
- 不认 `pnpm add`、`pnpm update`、`pnpm dlx`、`pnpm fetch`：它们不是现在要守的「装依赖步骤」，加了会对无关命令误报。要认再另开。
- 不认 `pnpm --filter x install` 这类「`pnpm` 和 `install` 之间还夹着带值选项」的写法，也不认流式映射 `- { run: … }`、缩进不是 6 格的步骤列表。这些交给计数哨兵：宽松计数会数到、认得的数不到，测试就红。不为它们写更复杂的解析。
- 不解析 shell 引号和变量，不引入 YAML 解析包（会动 `package.json` 和锁文件）。
- 不改 `ci.yml:117` 的测试清单（`tests/ci-install.test.ts` 已在里面），不改 `tests/ci-product-subset.txt`。
- 不删、不改写 `tests/ci-install.test.ts` 里现有七条测试的断言；不放宽任何一条。现有的错误文案（`no timeout-minutes`、`timeout-minutes is N, not 1..10`、`npm_config_nodedir is not set before the install`、`npm_config_nodedir is not the approved export line`）一个字不改，旧测试按它们匹配。

## 5. 做法

改的都在 `tests/ci-install.test.ts`。函数名保留：`steps`、`commands`、`installs`、`installSteps`、`violations`、`isApprovedExport` 现有测试在用，签名不变。

1. 先写测试，不动实现。把第 6 节每个编号的测试按下面第 3 到第 5 步的描述写好，用 `node scripts/run-tests.mjs tests/ci-install.test.ts` 跑，预期红的列在第 7 节。红的原始输出贴进【交接】。

2. 行与块头。
   - `steps()`（`:38-54`）把 `text.split("\n")` 改成 `text.split(/\r?\n/)`。行号、缩进规则不变。
   - 加 `BLOCK_HEADER = /^[|>](?:[-+]\d?|\d[-+]?)?[ \t]*(?:#.*)?$/`。它认 `|`、`|-`、`|+`、`>`、`>-`、`>+`、`|2`、`|2-`、`|-2`、`| # 注释`、`|- # 注释`。二审建议的 `^[|>][-+]?\d*\s*(#.*)?$` 不认 `|2-`（缩进数字在前、符号在后），用这条。我对这两条各跑过上面这些值，这条全认，`|x`、`|--` 不认。
   - `commands()`（`:69-82`）改成只有一条路径：找到 `run:` 行（第一行 `      - run:` 或任一行 `        run:`，键所在的列都是第 8 格），取冒号后面的值。值匹配 `BLOCK_HEADER`、或值为空：读块。其余：单行命令，值两端成对的引号去掉，一个命令。
   - 读块：后面缩进大于 8 格的行都属于它，遇到缩进不大于 8 的非空行结束（`blockCommands()` 的 `/^ {10}/` 改成这个）。空行和 `trimStart()` 之后以 `#` 开头的行跳过（shell 注释里写着 `pnpm install` 不能算安装）。块头以 `>` 开头时按 YAML 折叠：相邻的非空行用一个空格连成一条命令，空行把它们断开；连成一条的行号取第一行。折叠后 `export …` 和 `pnpm install` 连在同一条里，不再等于批准写法，会被报「not set before the install」，这是对的（真跑起来 `export` 会把后面的词当变量名），不要为它放宽。
   - 现有「行首不含 `trimEnd`」的规矩不变：`isApprovedExport` 仍是 `command.text === APPROVED_EXPORT`，行尾多一个空格仍然不行（现有测试 `:191-206` 钉着）。CRLF 切行之后 `\r` 没有了，不影响这一条。

3. 命令。
   - 把 `INSTALL`（`:24`）换成一条全局正则，在一行命令文本里找出每一个装依赖命令：命令词位置是行首，或 `&&`、`||`、`;`、`|`、`(`、`)`、`{`、`}`、反引号、`$(`、`then`、`do`、`else` 之后；前面可以有若干 `NAME=值` 赋值和 `env`、`corepack`、`time`、`exec`、`command`、`nohup`；然后是 `pnpm`，若干个以 `-` 开头的选项，再是 `install` 或 `i`，后面是空白、行尾或 `;&|)`。我试过的一版：

     ```ts
     /(?:^|&&|\|\||[;|(){`]|\$\(|\b(?:then|do|else)\b)\s*(?:(?:[A-Za-z_][A-Za-z0-9_]*=\S*|env|corepack|time|exec|command|nohup)\s+)*pnpm\s+(?:-\S+\s+)*(?:install|i)(?=\s|$|[;&|)])/g
     ```

     对 `pnpm i`、`CI=1 pnpm install`、`corepack pnpm install`、`cd x && pnpm install`、`(pnpm install)`、`if x; then pnpm install; fi`、`pnpm --frozen-lockfile install` 各数到 1，`pnpm install || pnpm install` 数到 2，`npm install --global pnpm`、`pnpm run build:install`、`echo pnpm install`、`pnpm test # pnpm install` 数到 0。不必逐字用它，但这些值要是同样的结果。
   - `installs(step)` 改成：对每条命令，按这条正则每匹配一次返回一个 `Command`（行号取命令的行号，`text` 取整条命令文本）。同一条命令里有两个安装就是两个。
   - `violations()`（`:91-108`）的逻辑不变：每个安装，前面（行号更小）的命令里要有逐字等于批准写法的 export。结果是：`export … && pnpm install` 写在同一行，不算（同一行没有「前面」）。这是故意的严格，和「export 是单独一行、逐字」一致，加一条测试写明（第 6 节 `RAC-1457`）。

4. 超时与哨兵。
   - 超时（`:21`、`:94-97`）：在步骤文本里找 `^ {8}timeout-minutes:` 那一行（第一行是 `      - timeout-minutes:` 的写法也算，读之前把第一行的 `      - ` 换成 8 个空格）。取冒号后的值，去掉行尾的 ` # 注释`，两端去空白。没有这一行：`no timeout-minutes`（文案不变）。值不是纯整数（`5.5`、`"5"`、`${{ … }}`）：新文案 `timeout-minutes is not a plain number: <值>`。整数但不在 1..10：原来的文案。
   - 加 `EXPECTED_INSTALLS = { "ci.yml": 7, "full-suite.yml": 1 }`，和 `UNGUARDED_INSTALLS = { "release-macos.yml": 1 }`（后者旁边写一句理由：release 作业，T-019 任务书明令不动，另案补）。
   - 加 `mentions(text)`：宽松数。逐行，先去掉行尾注释（`/(^|\s)#.*$/` 换成 `$1`），再用 `/(?<![\w./-])pnpm\b[^\n]*?\s(?:install|i)(?=\s|$|[;&|)])/g` 数匹配，全文件求和。它故意比第 3 步宽：`pnpm` 和 `install`、`i` 之间可以夹别的词，不看 `run:`、不看缩进、不分步骤。我对三份工作流的真实文本跑过，得 7、1、1，与上面的预期一致。
   - 加 `recognised(text)`：`steps(text).flatMap(installs).length`。
   - 加 `problems(file, text, expected)`：`recognised !== mentions` 或 `recognised !== expected` 时返回说明，写出两边的数和各自的行号，方便定位。

5. 变异验证（必做，输出贴进【交接】）。
   - 全部写完后跑 `node scripts/run-tests.mjs tests/ci-install.test.ts`，全绿。
   - 逐个临时改回，各看相应的测试变红，贴红的测试名和第一行失败，再还原：
     1. 把 `BLOCK_HEADER` 换成 `/^[|>]$/`：`RAC-1456` 的块头表和对真实工作流的改写测试红。
     2. 把安装正则换回 `/^pnpm install\b/` 的行首匹配：`RAC-1457` 的写法表红。
     3. 把超时的值解析换回行尾 `(\d+)$` 的正则：`RAC-1456` 的超时表和 CRLF 例红。
     4. 把 `problems()` 里 `recognised !== mentions` 那半句删掉：`RAC-1458` 里 `pnpm --filter x install` 的例红。
     5. 把 `EXPECTED_INSTALLS["ci.yml"]` 改成 8：对真实 `ci.yml` 的断言红。
   - 「构造一段 `run: |-` 里藏着没超时的 `pnpm install` 的工作流文本」就是第 6 节 `RAC-1456` 的块头表：每一行用 `violations()` 得到恰好两条（`no timeout-minutes` 和 `npm_config_nodedir is not set before the install`）。改前的实现对这些行返回空数组，这是先红的依据。
   - 「对现有工作流仍然是绿」：对真实 `ci.yml`、`full-suite.yml` 的原有断言（`violations` 为空）与新的哨兵断言都绿，且 `git status` 里除两个测试文件外没有别的改动，工作流文件没动过。

6. 读目录。`workflowFiles()` 返回 `{ file, text }[]`，按文件名排序，路径写法照 `tests/fixtures/ci-workflow.ts:8-14`（`fileURLToPath(new URL("../../.github/workflows/…", import.meta.url))`）。`RAC-1458` 的目录测试：每个 `mentions(text) > 0` 的文件必须在 `EXPECTED_INSTALLS` 或 `UNGUARDED_INSTALLS` 里，名单里的文件数要等于 `mentions`。

7. 开头的注释。重写 `:5-17`：写清认得什么（上面第 2、3 步列的写法）、`>` 折叠怎么算、export 必须单独一行逐字等于批准写法、哨兵数的是什么；写清不认得什么（第 3 节「不做」的最后几条）和它们怎么被哨兵拦。每一句话都要有一条测试名对着；没有测试的句子就删掉。删掉原来的「A new unguarded install appears, this fails」这类说过头的话。

不写 `legacy`、`compat`、`backfill`，不加空 `catch`、`as unknown as`、`any`、`console`（按文件计数只许减少，这个文件现在都是 0）。
