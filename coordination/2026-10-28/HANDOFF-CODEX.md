**用户已经定过的长期规则**（以前记在 Claude 的记忆里，这里抄给你）
- **合并前**先读 PR 上的评审意见和评论，答复了或修完了再合。
- **合并顺序：** 碰同一批路径的 PR 合成批 PR 一起落；叠成链的 PR 整条落地。共用文件的冲突由统筹一次解，不让每个作者各自去同步。
- **main 红了：** 某个 PR 只红在 main 自己那一个用例上时，等 main 修好、再合 main，然后走「只合 main」的沿用，不重跑全量。修好之前不合。
- **偶发的超时：** CI 失败只是负载导致的超时、不是逻辑问题，可以重跑失败的作业后入队。测试时限按慢机放宽（例如 30 秒改成 90 秒）不算放宽断言。
- **页面资源：** 字节数不是硬上限。必需的增长要在 PR 里写明理由，审过后用 `APPROVED_CEILINGS` 一次性放行。单个资源涨超 10 KB，或者新增资源，先问用户。
- **巨大单元：** 不硬拆。只做一件事的单元，在 `giant-exceptions.json` 里登记理由；职责混杂的才拆。
- **模型能力问题不打补丁：** MiniMax 能力弱造成的坏效果，不加措辞禁令、正则或特例开关；后果严重的，靠工程层的事实核对兜住。评测时可以直接用 MiniMax，不用问；但必须在一次性的隔离 Home 里跑，密钥只内联读取，跑完就删 Home。

  - 发版；
  - 凭据；
  - 取消 CI；
  - 删创作台或炼金台；
  - 产品语义上的取舍。

  问的时候一律弹窗，带方案和「（推荐）」。先把能独立做的做完，再把要问的攒成一批问。
