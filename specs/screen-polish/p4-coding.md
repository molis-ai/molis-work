# 逐屏打磨 P4 前半：Coding 逐屏里不依赖壳层的六处

状态：已实现，分支 `feat/screen-polish-p4-coding`（2026-11-18），随统一 PR #2142 合入（原 #2139 已关）。评审台 2026-11-19 退回一次，四个挡合并的点里三个已改完；剩余的调用次数预警卡与「做的时候定下的」六处判断已于 2026-11-20 经用户全部确认（见下文）。

这一片属于[逐屏打磨第一轮](spec.md)第六节和第九节的 P4。方案写明 P4 不需要用户另外拍板；样稿是 `docs/design/screen-polish/` 第 1 屏（`?only=coding`）。

分档：独立片（只动 `plugins/native/coding` 一个包，不改合同，不加服务或表；出了几种新的界面状态，所以不算小修）。类型：体验与效果，产品线 Coding。要人决策：没有开工前要定的事；做的过程中碰到的六处判断与第 3 处预警卡已于 2026-11-20 经用户逐项拍板确认（见「做的时候定下的」）。页面资源增长按实测报给用户。

## 给人讲清楚

1. **这批做什么**：把 Coding 这一页收拾干净。左边的会话列表让名字说话，状态只留一个小点；对话里的两张「准备」大卡在没事的时候收成一行；一轮结束只用一行说清「改了什么」并给一个「看改动」；头部和右边的结果面板按人看的顺序排。
2. **解决什么问题**：现在会话名被截到六个字，状态词和时间却完整；每一轮的回答被两张准备卡压到屏幕下面；结果面板一打开先看到的是绝对路径和能力编号。
3. **做完能看到什么**：打开 Coding，列表里能认出每个会话；发一句话，回答就在第一屏；一轮结束后一眼看到改了几个文件。
4. **为什么排在这里**：这些都在 Coding 自己的页面里，不用等底栏和顶部栏重做。输入框底排、对话栏和输入框对齐要等底栏第十三版落地，留给 P4 后半。
5. **需要用户做什么**：看浅色、深色各一遍截图；页面资源有增长时点头。

## 做的时候定下的

方案没写死、按方案第二节的原则定的六处。**已于 2026-11-20 经用户逐项拍板**：第 1、2、5 项认可；第 3 项先按甲方案随 #2142 显示 `+a −b`，只传行数的轻量接口（乙方案）放到 Coding 后半（36A-4b）；第 4 项保留现状（目录行留灰色「优先」与五种状态短词）；第 6 项沿用「修改 N 个文件」与「看改动」：

1. **「空台」指没有打开会话的台面。** 台面上的「开始新会话」只在没有会话打开时出现（现在就是这样），目录列的新建收成列头的 ＋ 以后，同一屏不再有两个新建。
2. **准备信息什么时候展开。** 环境里有要人处理的行（依赖没装、缺环境变量、工作树有问题、仓库有冲突）就展开并带琥珀；否则只在这一轮还没写出第一句回答时展开（方案说「运行中展开」「回答先出」）；回答一出来就收成一行。人自己点开或收起以后，以人的为准。材料被截断不算要人处理的事（Agent 可以按需续读），不展开，卡片里的状态照旧。
3. **「+24 −6」的来源。** 一轮的增减行只有读这一轮的变更才知道（`GET …/runs/<轮>/changeset`）。只对最新的、已经结束且改了文件的那一轮读一次，按轮记在页面里，不轮询；读不到就只写「修改 N 个文件」。更早的轮在打开过「看改动」以后才有增减行。**成本照实写**：这一次读取在宿主那边是三次动作调用（读会话、读这一轮、读这一轮的写入审查），回来的内容带每次写入前后的全文，页面只用其中的增减行；页面刷新或重新挂载后会再读一次；还在等「核对中断结果」的一轮不读（那时读不到），核对完再读。**口径**和变更阅读器的合并视图一致：只算真正落盘的写入，被拒的不算；同一文件多次写入用服务给的净增减（第一次写入前对最后一次写入后），不把每次相加；有一次写入失败或结果不明、或者净增减说不准，这一行就不写增减。这一处属于「调用链与调用次数」，见下面的预警卡。
4. **「优先」留在目录行上，以及哪些状态出短词。** 「标为优先」进了头部的 ⋯，但人自己标过优先的会话，目录行的状态点旁仍写一个灰色的「优先」，否则标了看不出来（合入 P0 之前的 main 上，目录行一直写「优先 · 状态词」）。出短词的是五种状态：等你回答、等你批准、暂停、失败、需要核对——和 P0（#2110，已合入）窄列规则里「保留状态词」的那五种是同一组；方案 6.1 的括号里只写了「等你、失败」。已于 2026-11-20 经用户拍板保留现状。
5. **结果面板里方案没提到的分区。** 待你决定的审查和中断恢复紧跟在「改了什么」后面（它们在等人）；计划、子任务、协作、后台命令排在检查点后面；「运行详情」在最后，默认收起。
6. **回合结束卡的用词沿用现有词条。** 方案的例子写「改了 3 个文件」，页面上工具行一直写「修改 N 个文件」，这一行沿用同一个词；按钮按方案改成「看改动」，底栏「下一步」里的同一个按钮跟着改。已于 2026-11-20 经用户拍板沿用「修改 N 个文件」与「看改动」。

## 预警

按需求开发流程第 6 节补的预警卡（评审指出第一版没有发）。Agent 只起草，由负责这一片的人发到团队讨论群；结论写回这里。

**预警卡：Coding 回合结束卡的「+a −b」多一次变更读取**

1. 一句话：回合结束卡要写「修改 3 个文件 +24 −6」（方案 6.3），增减行只有读这一轮的变更才知道，所以最新一轮结束且改了文件时，页面多发一次 `GET …/runs/<轮>/changeset`。
2. 情形：底层逻辑调整里的「调用链与调用次数」。
3. 影响：只有 Coding 的会话页。每个页面、每个打开过的会话、每个「最新且改了文件」的轮一次；宿主那边是三次动作调用（读会话、读这一轮、读写入审查），回来的内容带每次写入前后的全文，页面只用增减行。不改合同，不影响别的插件。
4. 方案：
   - **甲（现在的做法，推荐先这样）**：读一次完整的变更，页面只取增减行；口径和变更阅读器的合并视图一致，说不准就不写增减。好处是不动合同、不加动作；代价是大文件的一轮会多传一次全文。
   - **乙**：给「读取变更」加一个只回统计的读法（按文件给已落盘写入的净增减）。回来的内容只有几十个字节；代价是动作 `coding.changesets.read` 的输入要加一个字段，是合同改动，要走合同流程，放进后面的批更合适。
   - **丙**：不多读。回合结束卡平时只写「修改 N 个文件」，人打开过「看改动」以后才有增减行（阅读器本来就读了）。没有任何新增请求；代价是方案 6.3 例子里的「+24 −6」第一眼看不到。
5. 要谁回答：Coding 线的负责人；选乙涉及合同，要用户点头。
6. 卡住什么：不卡别的。甲已经实现并有用例；换乙或丙都只动 `change-tally.ts` 一处的读取。
7. 时限：1 个工作日；到时没人回，由本批主会话按推荐（甲）定，用户可以推翻。
8. 链接：本任务书「做的时候定下的」第 3 条；统一 PR #2142。

结论：选甲方案随 #2142 先合入（保留第一眼看到 `+a −b`），只传行数的轻量接口（乙方案）放到 Coding 后半（36A-4b）推进。用户拍板，2026-11-20。
