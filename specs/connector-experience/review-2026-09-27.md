# Connector 端到端复查（2026-09-27）

修复更新：用户已授权“全修”，以下保留最初审查证据。当前修复与最终验证见 [verification.md](verification.md)。原失败复现已迁至 `tests/connector-reconnect-regressions.test.ts`，纳入默认回归。

结论：连接目录、授权协议和凭据边界已有基础，但尚未达到“内部完整”。发现 2 项 P1 和 4 项 P2；主要缺口是授权后的实际使用与异常恢复，而非视觉重做。本轮保留生产逻辑，交付审查及可执行失败复现。

范围：目录/引导、Workbench 客户端、Host OAuth/MCP 与连接生命周期、Cloudflare Broker 合约、Feed 和 Agent 消费入口。依据当前工作树与原 spec；没有注册新应用、执行真实账户授权或部署 Worker。

## 必须处理

### R1 · P1：通用 OAuth 重连成功，Feed 来源仍然断开

- 位置：`apps/local-host/src/web-connector-api-methods.ts:19–30`；`apps/local-host/src/connector-api-oauth.ts` 的 `completeApiOAuth`。
- 路径：已有 OAuth 账号绑定 Feed → 断开（来源变为 disconnected）→ 对同一账号重新授权成功。
- 实际：连接库恢复 connected；Feed 来源仍为 disconnected，`inspectSourceAuthorization` 仍拒绝使用它。
- 证据：`tests/connector-reconnect-regressions.test.ts` 第二例执行失败，实际 disconnected，期望 active。HTTP 自动回调与手动完成分支均未调用来源状态同步；专用 OAuth 路由和 Token 更新已经有此同步。
- 调整：在 Host 的授权完成协调层统一传播连接状态变化，覆盖自动/手动回调；保留用户主动暂停、已删除的来源及原绑定。将来源同步从 HTTP 文件移到 Host 业务协调模块，避免 OAuth 业务层反向依赖 Web 路由。

### R2 · P1：官方 MCP OAuth 连接没有接到 Agent 的正常使用路径

- 位置：`apps/local-host/src/system-agent-service.ts:41–53`；`apps/workbench/src/settings-connector-guide.ts:57`。
- 实际：Agent 的连接解析限定 `mcp-bearer`；官方服务的 `auth_method=mcp` OAuth 连接未纳入该路径。`getMcpConnectionDescriptor`、`resolveMcpConnectionToken` 的生产导出尚无 Agent 消费方；工具调用接在连接设置页的手动 API 中。
- 影响：可授权、发现工具和手动调用，不能据此宣称已接通 Agent 使用。Figma 的“供 Agent 读取和处理”文案超出当前正常连接链路。
- 调整：通过 Host 已有 MCP 描述/令牌解析端口接入 Agent，并提供明确的选择连接和工具权限入口；令牌刷新和断开仍由 Host 管理，不让 UI 或 Agent 持有应用密钥。接入前修正文案。这属于实际使用能力缺口，不能靠改按钮完成。
- 证据等级：静态调用链核查；未执行模型侧真实远端工具调用。

### R3 · P2：部分已配置 OAuth 在断开后重连时向用户索要 Client Secret

- 位置：`apps/local-host/src/connector-api-oauth.ts:67–89`；`horizontal/connector-host/src/connection-store.ts:301–307`。
- 实际：断开删除保存的 client secret；重连沿用旧 clientId，但产品配置回填限定没有 connectionId。直接 confidential OAuth 随后报“请填写此应用的 Client Secret”。
- 证据：失败复现第一例，使用产品配置的 Asana、同一连接 ID，全部远端请求为受控 fixture；没有触碰真实凭据。
- 边界：此问题不等同于所有 Broker 连接均失败，Broker 分支不依赖这份本机 secret。
- 调整：区分产品配置和用户自定义应用。只在身份匹配时重新解析产品凭据；自定义应用明确提示重新配置，不能任意回退到另一应用的秘密。

### R4 · P2：官方页面拒绝授权后，原窗口仍等待到超时

- 位置：`apps/workbench/src/scripts/connectors-settings.ts:102–119`；`apps/local-host/src/web-connector-api-methods.ts` 回调错误分支。
- 实际：原窗口只轮询 connection ID；新授权失败时没有连接记录，返回 404，和“尚未完成”不可区分。取消信息仅出现在回调浏览器页。重授权失败时旧连接 revision 不变，同样无法结束原窗口等待。
- 证据：现有 `connector-api-oauth.test.ts` 已验证取消回调跳转及随后 GET 404；客户端明确吞掉 404 并持续等待。
- 调整：为授权尝试提供可查询的终态（成功、拒绝、失败、过期），原窗口据此呈现原因和重试；不要以连接记录有无替代授权结果。

### R5 · P2：授权成功后的页面刷新失败会留下无法继续检查的等待界面

- 位置：`apps/workbench/src/scripts/connectors-settings.ts:52–59,113–119`。
- 路径：轮询发现成功 → reload 先 stopWaiting → HTML 获取失败/非 200/缺少目标节点。
- 实际：异常被 poll 的空 catch 吞掉；session 已停止，页面仍显示等待，“我已授权，检查结果”也立即返回，且超时回调不再执行。
- 调整：区别授权状态与页面刷新状态，显示“已授权，但页面刷新失败”及重新加载操作；不要将刷新异常当作可忽略的轮询网络抖动。
- 证据等级：确定的代码控制流；未在浏览器中注入网络故障。

### R6 · P2：“下一步”与连接方式不匹配

- 位置：`apps/workbench/src/settings-connectors.ts:87–94,121`。
- 实际：`nextStep` 只接收服务 ID，多数服务统一呈现“选择项目，添加来源”；Notion 默认推荐官方 MCP，页面同时声明它不用于 Feed。尚未配置/尚未连接也显示相同下游按钮。
- 证据：隔离本地服务中实际查看 Notion、Gmail 页面，AX 与截图均确认；Feed 的 `feed-source-service.ts:53` 明确拒绝 MCP/CLI 来源。
- 调整：按实际连接方式和状态显示下一步。API 账号进入来源设置；MCP 进入工具选择/使用；未连接页说明连接后用途，不把无法完成的下游操作作为下一步。

## 代码结构判断

- 保留现有分层：Workbench 渲染/引导/样式、Host 协调、协议/提供商配置、通用连接存储、Worker 秘密边界。没有必要为每个提供商再建一个类。
- 优先调整两处职责：连接变化传播从 `web-connector-connections.ts` 移至 Host 协调层；332 行字符串形式的 `CONNECTORS_SETTINGS_CLIENT_SCRIPT` 将授权等待与页面刷新分开，并采用项目已有客户端模块方式取得类型检查与行为测试。文件长度本身不是缺陷，R4/R5 是拆分依据。
- Host 与 Worker 的 token request 存在协议规则重复。后续可共享无 Node/平台依赖的纯请求构建逻辑；Worker 的加密、回调验证和本机 SecretStore 仍各自负责。不为消除几行重复强行合并运行时。
- `nextStep` 应使用已有方法/能力元数据与连接状态，不再扩充一串服务 ID 特判。
