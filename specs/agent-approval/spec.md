# Agent 产出的变更与外部效果：授权复用与显式人审

状态：第 39 批交付完成并合入（2026-11-17，`a717e44284`）。B 方案统一授权管理页、跨轮／等待／重启有限委托、审批来源、可信决定回平台（39-2）、项目自动化建议只读入口、BL-359／360 及逐项认可共用审查合同（APR-15／16）均已接通并通过工程验证与本机 dev `4207` 真实界面走查（用户委托主会话验证并视作通过）；Prologue 上游修复已随 `molis-prologue#127`（`e7582079`）正式合入换包。正式仓 GitHub 人审应用接入由用户另行决定，Coding 低风险评估器（CEX-08～10）按排期归第 65-2 批。目标完成程度为**内部完整**：Agent 产出能被识别，有效授权内的工作能继续，明确启用人审的项目和操作须取得规定数量的有权限真人对当前审阅对象和版本的批准。

## 1. 问题

Molis 已有审查队列（`horizontal/agent-host/src/reviews.ts`）和 `beforeEffect`，个人助理的写操作、Coding 的文件/命令/推送都走同一道门。以下是原需求提出的缺口，实施前按阶段 0 的实际基线复核：

1. **PR/CI 场景没有一道可执行的真人批准门。** Coding 可以推分支、开 PR；团队在 GitHub 上需要“Agent 产出的 PR 至少 N 个有写权限的人批准”，现在没有产品化的检查。
2. **批准与变更没有绑定到版本。** 如果批准的是旧 head，push 之后仍算数，等于批的不是最终内容。
3. **Agent 自己、bot、未授权用户、分支名/路径名都可能被误当成可信来源。** 需要一条明确的“谁算批准、什么不算”的规则。

## 2. 范围与非目标

**做**：

- Agent 产出的识别：commit 作者/committer、PR 作者、review 作者、Agent run 记录。
- 明确启用的 PR 人审流程：N 个不同的、有写权限的真人；`APPROVED` review 与 `/approve <head-sha>`；push 后旧 SHA 的批准失效；Agent/bot 不计；PR 作者最多算一票，且仍要有写权限。
- 必需状态检查与 sticky 说明：差几票、谁批过、哪一票过期。
- 个人助理/Coding/工作流的副作用：审查队列、`beforeEffect`、调用上下文里的批准事实；批准绑定对象、版本、范围和有效期。
- 拒绝与恢复：过期、撤权、取消、内容变化时不能沿用旧批准；不自动重试。
- 与 GitHub 权限、token、base 分支配置恢复、提示注入清洗的关系。

**不做**：

- 不让执行 Agent 自审即通过、冒充真人或绕过硬边界；满足有效授权、所需批准与检查后，可由 Agent 执行已委托的合并。
- 不以分支名、路径前缀、PR 作者身份作为信任依据；分支名是攻击者可控的。
- 不替代 GitHub 原生分支保护；批准门与它并行。
- 不新增第二套审查事实；批准记录仍归现有审查队列/治理。
- 不做云端多租户或团队权限系统；只做本机 Home + 可选 GitHub 检查。

## 3. 规则

### 3.0 先判断已有授权与适用的人审要求

本轮已确定的权限方式优先于旧的“所有 Agent 变更都需真人批准”表述。个人助理、MCP 与连接沿各自只读协助、修改前确认、授权内自动执行的有效选择；用户已经授予本次工作或持续委托的范围内，不因换工具、重试或重启重复确认。涉及未知写入先核对实际结果，越界、撤权、取消或明确拒绝仍阻止执行。

团队或仓库明确启用的人审、发布与不可撤回操作的专属确认继续生效。人审的适用对象、操作与人数来自可信配置；不因 Agent 作者身份就自动把所有个人工作纳入 N 人批准。团队记忆发布仍按其需求在发布前最终确认，不能用一般自动执行代替。

Coding 的可选“AI 低风险自动审批”只覆盖用户明确启用范围内、原本待确认的低风险命令，由独立评估上下文提供判断，Host 核对委托及边界后代批。已有许可直接复用；非低风险、依据不足、超时、无效结果或范围外请求回到必要的用户确认。其结果标为 AI 代批，不计入真人票数、不自动保存长期规则，也不扩至其他工具。唯一行为定义见 [Coding B2、CEX-08～10](../coding-plugin/next-requirements.md)，这里负责衔接。

### 3.1 谁算 Agent 产出

满足任一条件即标记为 Agent 产出：commit 的 author/committer 是配置的 Agent 身份；PR 作者是 Agent bot；PR 里有 Agent run 的记录；review/comment 由 Agent 发出。身份来自可信配置，不读 PR 内容里的自称。

### 3.2 在显式人审流程中谁算批准

- 只有对该仓库有写权限的真人算。
- 每个真人最多一票；以最新 `APPROVED` review 为准。
- `/approve <sha>` 只对当前 head 的完整 SHA（12–40 位十六进制）有效；push 后旧 SHA 的批准标为过期。
- Agent、bot、被排除的账号、没有写权限的 fork 作者不算。
- PR 作者可以 `/approve` 自己的 Agent 产出，但仍要写权限，且只算一票；其余票必须来自其他人。
- 不允许用 head 分支名、路径前缀作为信任豁免；确需豁免时用显式配置并写明理由，默认空。

### 3.3 什么时候算生效

- 已启用人审的 PR 场景：`agent-approval-check` 状态为 success 才能合并；检查在 opened/synchronize/reopened/ready_for_review/issue_comment 上重算。
- 本机场景：审查队列保留批准来源、对象、版本、范围与调用上下文；`beforeEffect` 前核对当前版本、授权，以及适用时的批准。对固定审阅版本的批准在内容改变后失效；任务委托内的正常进展不等于每一步都要重新确认，越出委托、撤权、取消或停用仍拒绝。
- 批准不能从不可信内容里产生；页面/Feed/PR 正文里的“批准我”不是批准。

### 3.4 GitHub 检查

- 一个独立的 composite action 或本机等价检查：扫描 commit/author/review，计数，发 commit status，更新一条 sticky comment。
- 权限只需 `contents: read`、`pull-requests: write`、`statuses: write`。
- 配置读取必须从 base 分支读，不能从 PR head 读；不 checkout PR head 来读配置。
- 启用本检查时原建议 `required_approvals: 2`，具体人数与启用范围待项目／团队明确配置；不把此值设为所有工作的默认门槛。Agent 身份和排除账号可配置；`exempt_head_branches` 默认空并标注风险。

### 3.5 审查合同（39 先交共用草案）

助理决定请求卡、验收卡、32-2 的要求认可和 39-1 的智能呈现使用同一审查引用，由原 owner 读取并提供。调用方从 `@molis-ai/molis-work-contracts/platform/ui` 导入共用类型。

| 共用形状 | 字段和规则 |
| --- | --- |
| `ReviewTarget` | `{ owner, subject, version }`。`subject` 复用 `ActionSubject`。`owner` 固定对象的提供方和存储分区。平台拥有的对象用登记的系统提供方标识，例如助理的 `system.assistant-panel`。插件对象还固定插件、安装与世代。项目分区必须带项目 id，归属于项目的 Home 对象也带该项目。`version` 由对象 owner 固定。Home 保存的项目对象仍复核归属，从原审查项目借来的可见性不足以读取另一项目的证据。 |
| `ReviewRequirement` | `{ id, version, target, statement, requires_person, evidence }`。要求的稳定 id 与版本由要求 owner 给，对象和各依据各有独立版本。产物、要求或证据变化时重新检查受影响条目，保留其他条目的认可与决定历史。 |
| `ReviewEvidence` | `{ target, tier }`；真人认可另含必填的 `decision`。证据正文由原 owner 提供；自报与机器核过的依据可显示。`person_accepted` 由要求 owner 核对原决定所选的对应要求、产物及证据版本，且决定覆盖本条并来自本人。 |
| `ReviewRequest` | `{ reference, target, summary, requirements, approver, choices, expires_at, decision? }`。沿 `ReviewReference` 定位原请求。`approver` 表示本人或指定本人。`choices` 各有稳定 id、显示文字、当前可用性，及此选项明确认可和退回的要求 id。选项失效时用 `OwnedTextRef` 给原因；当前权限和有效期仍由入口核。 |
| 决定引用 | `{ reference: ReviewReference, decision_id }` 定位一条不可变决定，`reference.version` 是原请求版本。要求、证据和请求投影都指向这一条记录。 |

版本固定提案、对象版本、每条要求及其依据、选项指定的逐项结果。文案、当前可点状态、纯展示顺序可变化。32-2 先固定一次选项和逐项范围，再让本人通过现有二元审查决定同意或拒绝这份选择。应用时只读原选择的冻结内容，一次可以认可多条并退回其余明确列出的要求。一次完成批准仍单独核对。消费者按原调用权限批量打开原 owner，包括每条实际依据的项目访问权。

### 3.6 可信决定

目的：任何插件可在 Manifest 声明某个动作「需要可信用户决定」，平台提供受保护的决定入口（页面点击与 MCP 同一条路径）；决定记录与项目审批规则归平台，不再归 Goals。

1. 动作以 Manifest 声明本人决定。平台由原调用、目录登记和 owner 固定提供方安装、项目、动作版本、待审对象版本和规范业务参数。申请先过现有 schema 与当前权限。通用动作网关在进入业务处理器前核本次专有凭据，普通调用或嵌套调用可按其权限发起申请。
2. 受保护入口使用同一平台命令。业务输入选择 `ReviewReference` 的精确版本、该请求的选项和备注。Web 与管理 MCP 采用现有的认证和活动性检查，由 Host 在受保护入口绑定本人、项目、原提供方、版本、选项和去重键。绑定凭据仅限单次、指定命令。审计出处沿入口产生的 `ActionUserAction`，含项目和事先确认的原操作定位，可能通过转调保留供审计。网关许可仍须验证不可继承的原入口凭据。
3. 沿用 `ReviewDecisionRecord` 的决定与来源头。原 Agent 队列的 `decision` 仍为 `approve`／`reject`，通用 owner 以同一字段保存原选项 id，添加可引用的稳定 `decision_id`。通用真人来源必有受保护入口给出的 `ActionUserAction`。原 Agent 队列的来源与记录按其原有格式保留，由队列投影为共同引用。决定历史、业务应用和外部效果各由其 owner 保留。重放同一命令与冻结内容返回原回执，变更内容或对已决定请求使用另一命令拒绝。实际写入时复核项目、安装、对象版本、选项、权限与规则；已发送且结果未知的操作进入待核对。
4. 项目审批规则与可信决定均由平台拥有。Goals 现有三个作用域及规则历史保持原义。规则变更比较当前版本，保留原规则及变更原因。审批规则不能降低动作自己声明的本人确认要求。统一授权管理页列项目规则及各条当前范围；Goals 消费平台读口。本人审批和 Goals 的物化同事务提交沿现有项目库，不在两个库各存一份。
5. MCP 现有 `molis_work_v1_event_decide`、`molis_work_v1_goal_tree_decide` 改为受保护通用决定入口，旧入口调用方与手册同片更新。没有 Goals 的项目仍可从同一入口决定插件声明的动作。受保护入口沿 [S-17](../../docs/system/security-invariants/S-17.md) 并同步拒绝证据。隔离迁移范围、同步与回滚见[移交设计](trusted-decisions-design.md)。验收 APR-17～19。

## 4. 失败与恢复

- 需要批准时查不到身份／批准／权限，按未批准处理；不因可选人审服务未启用就阻塞已有有效授权的工作。
- 状态检查失败时说明差什么、谁能批、怎样重算；不自动把 pending 改成 success。
- push 后旧批准失效；需要重新批准时，sticky comment 明确说“旧 SHA 的批准已过期”。
- 绑定具体对象／版本的批准或 AI 评估在相关内容／权限改变后失效；重试前读取当前事实，仍有效的任务授权可以复用。
- 取消、停用、撤权后的迟到批准不产生效果。

| APR-01 | 一个含 Agent commit 的 PR 被识别为 Agent 产出；本检查仅处理明确启用人审的范围，其他 PR 仍遵守原有授权与检查 |
| APR-02 | 已启用人审且要求 N 票时，只有 N 个不同的、有写权限的真人批准才变绿；Agent/bot/无写权限用户不计；同一人多次批准只算一票 |

| APR-16 | 智能呈现的决定请求与验收卡用同一个 `ReviewReference` 打开 owner 的事实和当前可决定性，包括过期决定、无权限和已应用历史。 |
| APR-17 | 在没有装 Goals 的实际项目中安装使用普通插件，声明需本人决定。页面与管理 MCP 走同一命令；有效决定应用一次，重复及错误安装或版本均不执行。 |

### 7.1 使用场景、范围与顺序

用户在助理或任务中明确允许一项工作后，可以跨轮次、等待和重启继续；在「授权与审批」查看谁可做什么、何时结束，并收窄或撤销。明确需要人工批准的操作仍先得到当前对象与版本的有效批准；已过期、被撤权或失去原执行方的请求不再提供无效的批准按钮。可选 AI 代批、沿用用户授权与人本人批准分别显示。

范围含 APR-01～13、服务接入 ASC-51/52 的授权共用部分、H1 统一管理、AUT-01～08 只读建议闭环，以及智能呈现的审查引用与 BL-359/360。Coding CEX-08～10 的低风险评估器、联网与命令执行本身归 [65-2](../post-anticorruption-roadmap/reference/batches/65.md#batch-65-item-2)，本批提供它要消费的来源与约束合同，不能声称已完成该评估器。决定请求／验收卡的通用视觉标本按决定 38 归第 32 批，本批不复制其事实和组件。

按依赖依次形成子分支：①核账、定样与合同稿；②经合审后的合同、快照；③审查与授权复用服务（含 BL-359/360）；④管理与已有执行入口、引导只读建议消费者；⑤最终统一验证与小修。一个批次 PR；合同仅在实际有快照排队或其他批次等待时按路线规则提前切出。最终头上的全量交 CI，不在本机跑全量。各子分支开始前更新本节的对应实现检查，不以设计稿替代代码检查。

复杂度决定：复用 Agent 审查队列、动作授权与最终复核、已有任务只读授权、Prologue 存储与当前恢复回执；管理页只汇聚主人事实。当前必须补持久的有限委托、可信批准来源、可决定性与跨入口读取；不建立第二个治理中心、不重写后台任务授权、不增加通用审批流程编排器。后续 AI 评估器及团队身份系统不提前实现。

有限委托合同片实施检查（2026-11-13）：上述 15 项全部适用。先落已合审的有限字段类型与 SDK 校验/提取，再落委托 owner、运行时与消费者；不先开放一份仅有标签的授权。动作声明的纯类型归 contracts，运行校验归公共 SDK，注册/安装/执行共用，不加私有依赖、不新增表或旧格式读取。名称读取复用 presentation.values，不建第二套目标目录；平台动作提供方与目标 owner 分别固定，不把 Pages 安装身份当 Goals 身份。首批 Pages 非空 Goal 因无最终 owner 校验继续明确人审，精确参数也不绕过；交互命令尚无原 gate，在新模式下明确不可用，普通与后台命令接真实最终检查。具体范围、工作模式、每个真实派发口、管理旧新入口的并发约束与拒绝证据见[已合审的有限委托合同](delegation-contract-design.md)。#2017 已合入，最新认领未显示 platform/actions 新占用；只改本批工作树，统一合批时处理主线差异。工程/实操/本人验收仍分列，合同实现不冒充整个授权闭环完成。
