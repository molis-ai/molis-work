## 1. 背景

- **谁在读那两行输出。** `.github/workflows/ci.yml` 的 `queue-check` 作业（`:38-62`）跑 `node scripts/ci-queue-verified.mjs`，作业的 `outputs`（`:46-48`）读 `steps.check.outputs.verified` 和 `steps.check.outputs.run_url`，也就是命令往 `$GITHUB_OUTPUT` 那个文件里追加的两行（`scripts/ci-queue-verified.mjs:75`）。九个挡合并的作业和 `Verify` 都靠 `needs.queue-check.outputs.verified == 'true'` 决定跳过，所以那两行的名字、顺序、值错了，整个「走队列进 main 的提交不重跑」就悄悄失效（`verified` 读成空，结果是全跑，不会少跑，所以不会红，只会白白多跑一遍挡合并的作业，约 5 分钟）。这正是第 1 条要钉住的。
- **现在的测试为什么看不见。** `tests/ci-queue-verified.test.ts:91-99`：`environment` 里 `GITHUB_OUTPUT: ""`（`:93`）。命令里是 `if (process.env.GITHUB_OUTPUT) appendFileSync(…)`（`scripts/ci-queue-verified.mjs:75`），空串为假，整行不执行。同文件第一个 test（`:46`）测的是 `queueVerified()` 这个函数的返回值（`verified`、`runUrl`、`reason`），不经过命令行入口和输出文件。Codex 的验证（[6493584627](https://github.com/molis-ai/molis-work/pull/1460#issuecomment-6493584627)）在本机用替身核过输出文件，但没有留成常驻断言；合入后的真实 push（[6494652400](https://github.com/molis-ai/molis-work/pull/1460#issuecomment-6494652400)）里 runner 记了 `Set output 'verified'` 和 `Set output 'run_url'`，下游 `Verify` 收到了 `true` 和网址，所以现在的行为是对的，缺的只是常驻的断言。
- **`runStep` 是什么。** `tests/ci-queue-verified.test.ts:106-113`：把 `ci.yml` 里一个 `run: |` 步骤的脚本写进临时文件，用 `bash --noprofile --norc -eo pipefail <文件>` 跑（`:112`），环境变量由调用方加，`bin` 放在 PATH 最前（给 `git` 放替身）。`RAC-1902`（`:152-179`）和 `RAC-1903`（`:181-211`）用它。`ci.yml` 没写 `shell:`，runner 的默认是 `bash -e {0}`（上面第 2 条的日志）。
- **文档那一段。** `docs/system/PARALLEL-DEVELOPMENT.md:68` 是第 3 节「合并」里「合并队列」那一条，讲了 `queue-check` 的全部做法，是一整行很长的文字。起点比较的部分已经写了（「`Verify` 里名为 `Merge queue base <sha>` 的一步记下 `merge_group.base_sha`，要等于推送的 `before`……叠在别的组上的组起点可能不同」），缺的是把它的一个直接后果说白：几个组一起落地的那次推送，`after` 是最后一个组的头，最后一个组的起点是前一个组的头，不等于 `before`，所以全跑，这是有意的。依据在 `scripts/ci-queue-verified.mjs:55`（只认 `step.base === before`）。
- 同样的三个问题在别处还有没有（起草时逐个 `git grep` 了 main）：
  - `bash --noprofile --norc -eo pipefail` 和 `pipefail` 在 `tests/`、`scripts/`、`docs/`、`.github/` 里，只出现在 `tests/ci-queue-verified.test.ts:106`、`:112`、`:168`；另外 `tests/native-checks.test.mjs:162` 的 `set -euo pipefail` 是它造的一个 shell 脚本样例，与 runner 无关；
  - 「as the runner」一类说法：`git grep -i -E "as the runner|the runner's|runner does"` 在 `tests`、`scripts` 里只有 `tests/ci-queue-verified.test.ts:5`、`:106`、`:168` 是讲 shell 的，其余是别的意思（`tests/ci-product-subset-plan.test.ts:15` 等讲运行器的行为）；
  - `queue-check` 的 `outputs` 只有 `scripts/ci-queue-verified.mjs:75` 一处写；
  - `docs/` 里讲 T-129 的地方只有 `PARALLEL-DEVELOPMENT.md:68`（和 `:69` 里一句「needs 里另有只在 push main 上运行的 `queue-check`」），`PACKAGE-BOUNDARIES.md`、`CALL-CHAINS.md` 都没有讲它；
  - `.github/workflows/ci.yml` 里讲 `queue-check` 的注释（`:28-37`）已经写了「a group built on another one has another base」，不需要改，也不能改（#1481 在改这个文件）。

## 2. 目标

1. `tests/ci-queue-verified.test.ts` 里名字带「writes both outputs」的那个 test，真的断言了输出文件：
   - 不验证时，在已有内容之后追加 `verified=false`、`run_url=` 两行；
   - 验证成功时，写 `verified=true` 和那次运行的网址；
   - 去掉 `scripts/ci-queue-verified.mjs` 里任何一处（改名、删行、不追加、写错值），这个 test 红（第 5 节 6 个变异）。
2. 文件里不再有「runner 用 `-eo pipefail`」的说法（`:5`、`:106`、`:168`）；`RAC-1902` 开头多一条断言，`ci.yml` 里出现 `shell:` 或 `defaults:` 时它红，提醒回头看这些注释和 `runStep` 的参数。
3. `docs/system/PARALLEL-DEVELOPMENT.md:68` 说明：几个组一起落地的那次推送，目前总是全跑，是有意的保守做法，不是故障。

## 3. 不做

- 不把 `runStep` 的参数改成和 runner 一样的 `bash -e`：二审说「测试比实际更严，只是注释措辞不准」，更严的测试是好事，门禁和 CI 只许变严；不做。
- 不改 `scripts/ci-queue-verified.mjs`（含它的头注释，已经讲清了起点比较）：不做。第 5 节为了弄红测试会临时改它，一个变异一个变异地改，每次改完还原，最后 `git status` 里不许有它。
- 不碰 `.github/workflows/ci.yml`、`tests/ci-timeouts.test.ts`（#1481 在改），不碰 `tests/fixtures/ci-workflow.ts`：不做。前提「ci.yml 不写 shell」用测试里的一条断言钉住，不靠改 workflow。
- 不改 `PARALLEL-DEVELOPMENT.md` 的其他行，尤其不碰 `:72`（#1481 在改）：不做。
- 不做「让 `queue-check` 也认一串连续的队列组」（沿 `head_sha` ← `base_sha` 链从 `after` 走到 `before`，[6494450067](https://github.com/molis-ai/molis-work/pull/1460#issuecomment-6494450067) 提出）：它放宽「起点相等」，是改 CI 行为的设计决定，由统筹定要不要另开单；不做。
- 不去数「几个组一起落地」有多常见，也不把 18% 这类数字写进文档：数字是会过时的，文档只写规则；不做。
- 不把 `verified=true` 的断言做成起一个本地 HTTP 服务器：`spawnSync` 会阻塞当前进程的事件循环，同一进程里的服务器接不了请求；用 `node --import` 预装替身 `fetch` 够用；不做。
- 不改同文件第一个 `RAC-1900` test（`:46-89`）和 `RAC-1901`、`RAC-1903`、`RAC-1904`：不做。
