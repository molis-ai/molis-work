生产实施由当前 Codex Session 负责计划、调度、审阅与验收，直接调用本机 Grok CLI（`grok-4.6`、`xhigh`）执行，不经过 ForkLight。工作项与进度见 [implementation.md](implementation.md)。下文“本轮原型”是已经完成的设计阶段边界；生产实施权限与完成等级以本段及 implementation.md 为准。

最新方向：Goal 以有类型的事件承载工作事实；工作规划提供事件定义和默认要求，当前 Goal 保存采用版本及局部扩展。Runtime 可在已有授权内为没有适用规划的 Goal 动态设计事件。本文统一替代前两版“只组合现有写入、不改变业务模型”的保守方案。

## 目标与已完成的原型阶段边界

用户方向：Molis Work 越来越擅长保留事实、呈现差距、协调责任和承接下一步；越来越少强制规定模型如何思考、如何拆解、必须经过多少步骤。GoalDetail 的五个 tab 全部重新组织，以时间流呈现处理结果与相关材料。

已完成的设计阶段等级为 **2：可交互原型**。该阶段交付当前问题证据、新的信息与流程设计、独立 HTML 原型和实施边界。原型使用明确标注的示例内容，交互仅影响当前浏览器会话，不调用 Molis Work API，不改变真实 Goal、规则、数据库或 Runtime。后续生产改造已按 implementation.md 达到等级 **4：内部完整**，真实 SQLite/Host/MCP 与桌面/窄屏浏览器路径已验证。安装发布、真实用户项目迁移、性能收益与真人长期试用尚未验收。

保留：目标身份、事实来源、结果与要求的对应关系、历史更正、明确的责任、真实依赖、授权范围、用户已做决定、跨 Session 恢复。

替换：五个分类 tab、术语先行的信息组织、以模型步骤组织的主界面、强制拆解格式、同一事实反复抄写、无影响范围的阻断、已授权动作重复确认。

忽略：五个 tab 的位置与名称、现有表单数量、既有规划模板的步骤数。这些不作为新体验验收约束。现有数据仍需完整保留。

## 核心体验

用户回来后能直接回答：要得到什么？最近做成了什么？现在还差什么？谁在处理？我是否需要做决定？

### 整体进展在上，纯时间线在左，事件内容在右

2026-09-09 第二版按一骏反馈替代第一版布局：提升时间线密度，左侧只放时间与事件入口，点击后在右侧展示该事件及内容。保留事实、决定及处理流程方案，忽略第一版在流中铺开长文、把差距固定在右侧的结构。

- **顶部整体进展**：紧凑目标标题和一句结果目标之后，常驻显示当前判断、已做成的结果、下一步及负责人、风险/阻塞/待决定事项。它表示当前 Goal 的总体事实，不随用户选中的历史事件变成过去状态。
- **左侧纯时间线**：新到旧、按日期分组，只显示时间、短事件标题、类型和作者。行高适合连续扫描，同屏可看多条；不在列表放正文、附件、检查表或决策表单。选中项清楚可辨，键盘上下键也可切换。
- **右侧事件内容**：显示所选时刻的完整事件、结果、过程说明、产物、相关要求、检查范围及来源；在该事件中处理决定。查看材料或目标说明使用同一阅读区，提供明确的返回所选事件入口。
- **当前完成要求**：从顶部“完成要求”入口读取；每项可定位并选中对应时间点。要求仍区分已验证、未知、不符合和需重查，不用材料数量代替完成。
- **「目标说明」**：按需在右侧阅读目的、范围、有效决定、相关 Goal、依赖与长期参考；时间线保持原来的选中位置。
- **「补充一条」**：用户直接写事实、想法或要求；先保留原话及来源。普通备注直接记录；会改变承诺、授权或完成要求的内容形成可审阅的变化，不能因为写在输入框里就偷偷生效。

桌面左右两区独立滚动，整体进展保持可见。窄屏采用时间线→事件的往返阅读，保留顶部整体进展的紧凑摘要，可展开查看全部；不把两个窄列硬塞在手机屏幕上。

时间流回答“怎么走到这里”；当前概况回答“现在以什么为准”。有效要求与决定不能仅藏在历史中。两处读取同一份正式事实，不各存一份状态。

### 时间流条目

左侧一条只作为时间定位与选择入口。右侧先展示完整标题与业务结论，再展示产物、验证结果、剩余差距或需要的决定；作者、时间、来源是次级信息。标题例如“首次使用已走通，重启恢复还差一次验证”，不用“Run completed / Evidence submitted”。

按需展开：做了什么、依据说明、实际附件、对应要求、检查的范围、相关执行记录。一个成果可支撑多条要求，多份材料也可一起支撑同一要求，不能为满足一对一格式复制内容。

区分事实种类：直接观测、模型报告、模型建议、用户决定。AI 生成的归纳要可追溯，不能把“建议”压缩成“已决定”。展示必要的解释、结果和工作记录，不要求保存或展示模型隐含思维过程。

关键变化以新事件追加：旧结论标“已由后续结果更新”，仍能追溯。新检查失败可覆盖旧的当前结论，不能改写过去。新消息不抢阅读位置；用户在旧内容中时提示“有新进展”，由用户跳转。

### 原五个 tab 的去向

| 现有内容 | 新位置 |
| --- | --- |
| 当前：下一步、状态、完成要求 | 顶部整体进展 + 完成要求入口 |
| 上下文：目标、要求、边界、说明 | 当前有效的「目标说明」；变化进入时间流 |
| 进展：结果、依据、检查、阻塞与风险 | 左侧选择时间点，右侧查看内容；未解决事项在顶部整体进展中持续可见 |
| 关系：上下级、依赖、影响范围 | 相关事项与目标说明；真正影响当前动作时出现在差距摘要 |
| 记录：原始事实、历史与执行记录 | 可展开的时间流来源与「查看更早记录」；保留稳定定位入口 |

### 核心场景

1. 有新结果：默认选中最新事件；左侧连续扫时间点、右侧阅读成果。点击完成要求可选中对应结果；查看历史时顶部仍反映当前状态。
2. 部分受阻：写明受阻的是哪个动作，原因、谁能解决、何时恢复；其他已授权工作继续。不能笼统把整个 Goal 变成“等你”。
3. 需要决定：原位给问题、原因、推荐、差异与后果。决定后该条原位成为“已决定”，当前有效说明同步更新，下一步随之变化。
4. 用户先前已决定：复用其适用范围和来源，不再次提问。只有条件或权限发生实质变化才提出新的差异。
5. Runtime 中断：保留最后一次实际结果，显示接续所需信息。准备好交接摘要不等于已启动 Runtime；真实连接状态必须来自 Host。
6. 新 Goal：可以先保存一句意图；允许调查、澄清等已获授权的工作。不要求先填完整树、假设的输入或非目标。尚无完成要求时不能宣称完成。
7. 已完成：展示最终成果及各项完成结论，保留未覆盖的范围；如已要求人工验收，不能由 AI 自行替代。
8. 父 Goal：聚合子项产生的实际成果和未覆盖结果；不搬运全部子项日志，不用子项数量证明父目标完成。允许直接归属于父目标的整合或验收工作。

## 工作规划、Goal 与事件的统一模型

### 分工与事实来源

- Goal 保留稳定身份、原始意图、当前有效的结果约定、相关 Goal 与实际授权。
- Timeline 保存有类型的事件；Goal 当前约定、完成要求、未解决事项由有效事件更新。允许保存读取用投影，但不能在 UI 与 MCP 各维护一套业务真相。
- 当前进展的自然语言归纳由 Runtime 汇报，并关联所依据的事件游标。新事实到来而归纳尚未更新时显示其时效，失败不能被旧摘要遮住。
- Runtime 自主选择工作路径、设计局部记录格式、报告实际成果与判断。Molis Work 不把填表完整或附件可读当作内容真实。
- Host 提供可证明的操作者、Session 与连接状态；Runtime 报告的下一步不等于执行已经启动。用户的决定与 AI 的建议分别保留来源。

### 工作规划

现有 PlanningMethodPack 的内置、个人、项目来源及版本机制保留。补充 Goal 专属配置；作者与作用范围分开记录。

规划包含三类内容：

1. 推进建议：领域问题、可选方法、真实依赖和常见遗漏。它不自动成为强制阶段。
2. 事件定义：类型名、用途、领域字段、字段类型、必填项、可选的通用语义分类。
3. 默认要求：什么情况下需要哪些记录、对应什么结果、谁作结论。具体 Goal 保存实际采用的要求。

采用规划与登记事件类型不等于自动启用全部要求。按当前 Goal 的范围解析条件性要求；记录适用或不适用的结论及原因，不引入任意可执行规则引擎。多个规划一起使用时，去重等价要求并保留来源；实际冲突在采用时处理，不能把方法中的所有“必须”机械累加。

系统预置和个人模板作为可选起点。用户明确不使用模板时，从空白开始；不暗中补选默认规划。已明确适用于项目的约定仍应说明，其调整复用已有授权规则。

Goal 保存采用的规划版本、类型版本、有效要求和局部修改。模板升级不改变已有 Goal 的约定或旧事件含义。保存为个人/项目模板是扩大复用范围的单独操作；本次 Goal 的动态类型无需先晋升到模板库。

### 动态事件定义

定义的数据边界：

| 字段组 | 含义 |
| --- | --- |
| identity | 类型 ID、版本、名称、用途、作用范围、来源 |
| fields | 稳定字段 ID、标签、说明、受支持的数据类型、是否必填；选项类型的合法取值 |
| semantic_family | 可选的进展、交付、验证、Concern 等通用语义；未分类类型仍可记录 |
| presentation | 使用通用字段阅读器展示；不提交 JavaScript、任意 HTML、外部渲染代码或可执行验证器 |

文本、长文本、数值、日期、选项、列表、材料与正式对象引用按产品实际需要逐步支持，不先做完整的 schema/表单平台。原型只验证文本和长文本字段、必填/可选、事件名称与用途的动态定义。

在已有规划与执行授权内，Runtime 可以直接为当前 Goal 登记类型、扩充字段、设计与用户目标一致的完成要求。改动已承诺结果、降低用户指定验收或扩大权限仍按其实际影响处理；不能通过注册一个“用户批准”类型获得批准权限。

类型修改产生新版本；历史事件保持原类型版本。字段名称变化不能让历史数据丢失。类型注册与改变完成承诺独立；生产实现不开放任意覆盖历史类型的操作。

### 事件与完成要求

事件共同具有：系统生成 ID、Goal 归属、服务器接收顺序与时间、来源、类型版本、简短标题、领域数据，以及按需提供的材料、关联要求、所依据约定版本、被解决/替代事件引用。

事件类型最小职责：

| 类型 | 内容与作用 |
| --- | --- |
| 目标定义/调整 | 结果约定、变化与原因；正式生效按既有授权和有效版本处理 |
| 进展 | 实际工作与当前判断；接续需要时记录下一步及责任人 |
| 交付 | 可使用的结果、内容或入口、已知缺口 |
| 验证 | 检查对象、方法、实际观察、结论、适用范围；材料按需关联 |
| Concern | 问题或风险、影响对象；通过后续事件表达解决、接受或反证 |
| 决定请求/决定 | 问题、选择与影响；决定来源与适用范围可追溯 |
| 收尾 | 完成、取消等结论及原因；完成说明对应结果与支持，取消不需伪造交付 |
| 自定义 | 按已登记的领域结构保存；映射已支持的通用语义才影响对应投影 |

一条事件可以支持多项要求，一项要求也可由多条事件共同支持。一个工作更新可一次提交交付与验证；不要求模型重复上传同一材料。普通事件没有领取角色、创建 Run 或完成某个阶段的前置条件。

要求包含：具体结果对象、为何需要、来源、适用条件、需要的事件类型/语义、可接受的判断来源、当前支持及缺口。不能用“存在一种事件”或记录数证明满足。

生成与收尾有必要记录；其他必需性取决于 Goal 的约定。例如工程行为变化需要适当验证，迁移才需要迁移演练，视觉验收仅在当前范围或用户要求中生效。全新创意任务可由 Runtime 设计局部类型；没有结果约定时可以工作与记录，但不能宣称完成。

完成是对当前约定的显式结论，不是事件数量触发的副作用。系统检查引用、来源及明确要求是否支持该结论；内容质量由对应 Runtime、工具观察或用户判断承担，并区分“Runtime 报告满足”“独立检查”“用户验收”。失败与未知不会成为通过。之后反证指向相关要求，更新当前差距，保留历史完成结论及其被更新原因。

### 两个具体场景

**工程开发**：使用工程开发规划，变更交付与适当行为验证支撑本次结果。界面检查、数据迁移、发布验收按是否涉及而启用。现有示例的三项要求仍是创建项目、首个真实目标、重启接续；新增事件类型不会清除重启缺口。

**全新互动故事**：用户明确不用已有模板，并允许 Runtime 为当前 Goal 设计记录方式。Runtime 登记故事交付、规则实验、玩家观察三种类型；前两种承接可体验片段与选择反馈的完成要求，玩家观察可选。同一次配置保存在当前 Goal，随后上报按这些定义生成的数据，不先修改全项目方法库。

## MCP 与 Runtime 推进协议提案

以下是行为契约；名称为候选，不是现有可调用 API。

| 能力 | 输入 | 输出与边界 |
| --- | --- | --- |
| planning_read | 需要的规划/目录筛选 | 简要目录，选中后读取方法、事件定义与默认要求 |
| goal_configure_events | Goal、基础版本、采用模板或局部类型、要求变化 | 保存当前 Goal 配置及变化来源，返回生效内容与需要决定的差异 |
| goal_read | Goal | 当前约定、实际采用类型与要求、概况、未解决事项、最近游标；不要求重读全项目 |
| timeline_read / event_read | 游标/分页或事件 ID | 增量摘要与按需详情，含历史类型版本和材料 |
| report_events | Goal、请求幂等键、有类型事件及其数据 | 记录回执、状态效果、当前差距、最新游标；不要求 Run/角色阶段 |

动态类型作为数据登记，上报工具按已登记版本校验，不为每一种类型创建 MCP 工具。用户决定和正式变更由有相应权限的入口承接，普通报告工具不能自填可信用户身份。

一轮合法工作更新原子保存相关事件并返回实际结果。结构错误或非法归属在写入前指出具体字段；材料不可访问作为访问状态保留，不把整轮实际成果丢掉。完成要求不满足时可以保存完成报告，但其完成效果不生效，回执必须分开说明“已记录”和“仍未完成”。请求重试复用幂等键；只在修改正式约定或正式状态时检查所基于的版本，普通历史报告可以按其原版本保存。

Runtime 正常循环：读取当前 Goal → 在授权内选择和执行工作 → 实质变化时上报 → 消费更新后的差距继续工作。新 Session 读取当前约定、类型和最后结果即可接续。失败、部分受阻和未知随时记录；只暂停真正依赖缺失条件的动作。Host 负责实际运行占用、重试和连接信号，不把续租变成日常用户流程。

## 现有规则与模块的重整

保留身份、归属、可信用户来源、授权、路径边界、事务、幂等及正式并发变更保护。移除默认固定阶段、强制角色序列、非空规划数组、固定拆分阈值、补齐 Evidence 才释放执行等普遍流程约束。已有明确用户验收不能静默降级。

| 模块 | 重整职责 |
| --- | --- |
| modules/goals / planning | Goal 当前约定、采用的规划与局部类型、实际完成要求；去除按规划步骤控制推进 |
| Goal 事件应用服务（具体落位在实施时确定） | 定义登记、事件验证与追加、明确的状态效果、回执；沿用存储事务，不新增编排器 |
| evidence-verification / artifacts | 材料与观测、读取边界、更正引用；复用文件能力，不保留为通用上报而强制的独立生命周期 |
| governance-collaboration | 决定来源、约定调整与要求变化；已授权动作复用来源 |
| execution / Host | 真实连接、占用与冲突恢复；与普通事实记录脱钩 |
| native goals / workbench | 同一投影上的顶部概况、时间线、动态字段阅读器与介入入口 |
| apps/mcp / skills/goal-advance | 当前上下文读取、配置与事件上报；删除固定方法召回、角色领取与重复确认流程 |

现有 Run、Evidence、Review、Decision 的真实历史按原 ID/来源映射；映射不可靠的记录保持中性历史记录，不编造新的验证或批准。业务记录不再由新旧两套状态机分别决策：按 Goal 分阶段切换 owner，旧写入要么明确适配同一事件服务，要么拒绝并指向新版入口。

实施顺序：

1. 本轮：完整需求书与可体验切片（工作规划 → 动态类型 → 上报 → 时间线 → 完成要求）。
2. 一个新 Goal 的真实登记、上报、读取、恢复闭环；建立事件存储及唯一状态效果入口，接入 MCP 与 Runtime Skill。
3. 接通授权决定、局部阻塞、失败/更正、收尾与父目标整合；不按子项数量推断完成。
4. 映射历史、处理旧入口、模板采用与版本升级；验证后再替换生产 GoalDetail 和旧协议。
5. 完成替换后的无用代码清理，移除失效入口、重复实现和临时过渡代码，同步清理测试、依赖与文档；验证新链路及历史读取后，才算本次改造完成。

生产验证必须覆盖合法部分结果可保存；动态定义在新 Session 可恢复；错误类型数据有明确字段错误；跨 Goal/项目引用拒绝；同次重试无重复记录；旧类型修改不破坏历史；模板升级不改变既有约定；失败/未知不假完成；已有授权不重复提问；反证只更新相关要求；并发正式变更不覆盖；中断接续无重复副作用。完整运行性能用代表任务实测，不预设固定调用数或 token 收益。
