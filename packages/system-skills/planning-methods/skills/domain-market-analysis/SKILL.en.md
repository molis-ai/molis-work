# Market analysis

Deliver market structure, differences, options and testable assumptions.

For: Market research, Competitor analysis, Entry strategy.

## Planning path

1. Define market boundaries and decision
2. Identify users, alternatives and value chain by layer
3. Compare differences and evidence
4. Offer directions and a verification plan

## Required coverage

| area | label | question |
| --- | --- | --- |
| market_boundary | Market boundary | At what level do alternatives compete to solve what problem? |
| customer_moment | User moment | Who chooses or abandons the current option, and when? |
| alternatives_competition | Alternatives | What are real alternatives and structural differences? |
| strategic_options | Directions | Which choices does this give the current project? |

## Dependency rules

| rule_id | statement | direction_hint |
| --- | --- | --- |
| comparison-after-boundary | Comparisons need agreed market boundaries, user moments and dimensions. | comparison depends_on market boundary |
| recommendation-after-landscape | Recommendations need evidence about the market, users and alternatives. | recommendation depends_on market evidence |

## Completion evidence

- Primary or authoritative market sources
- Real user or product evidence
- Method to test key assumptions

## Closeout checks

- Give options rather than a single arbitrary answer
- State what it means for the project

## Common mistakes

- Substituting a feature grid for analysis
- Treating unexpressed demand as proof against innovation
- Collecting links without a decision

## How to use this method

- Think the work through along the planning path first, then list each result that can be delivered and accepted on its own as one item; do not mix several main results into one.
- Every required-coverage question that bears on the task needs an answer; a key question without one is listed as open, not hidden behind a vague item.
- A dependency means consuming a result: B depends on A only when B cannot start or finish without A's accepted output. Order of discussion, timing, the same owner or the same file are not dependencies; work with no such relation stays parallel. Judge each dependency rule, and say which output is missing when one does not apply.
- State for each item what proves it is done (completion evidence), and run the closeout checks before finishing.
- Describe finite changes that can be completed; ongoing operation is not an item that never ends.
- When used with other planning methods, put their key results side by side, see which consumes which, and bring in the method that provides anything missing.
- Show the breakdown to the person first. When they want it in a tool (for example an installed Goals plugin), write it with that tool's own actions, with their confirmation.
