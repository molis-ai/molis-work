## 1. 分档、分类与决策

### 1.1 分档

| 档 | 是什么 | 要走的步骤 |
| --- | --- | --- |
| 小修 | 一条 BACKLOG 或一个缺陷：只动一个包；不改合同（Manifest、SDK 出口、`packages/contracts`、动作 schema、MCP 工具名、库结构）；不出新界面；不加服务或表 | 不写 spec。在 PR 里按第 4 节逐项过一遍，只写涉及的项和结论。照组件板已有控件改的界面不用定样。碰到第 6 节的预警情形照样发预警 |
| 独立片 | 在一条轨道里做得完：可以改一处合同，或加一种界面状态，但不借别的轨道独占的文件 | 写 spec（或在已有 spec 里加一片），带第 3 节的产品检查和第 4 节的开工前检查；统筹审过再开工。碰到第 5 节的界面先定样 |
| 大需求 | 跨轨道、新的平台服务、新插件、新页面或新动线、一组合同改动，或要上游 Prologue 的能力 | 独立片的全部步骤，再加三样：相关轨道的主人一起定合同与边界（共同设计）；合同先行（[轨道与冲突规则](tracks.md#section-5)规则 1）；spec 里先列 PR 序列和每片的验收（[并行开发](../../../docs/system/PARALLEL-DEVELOPMENT.md)第 4 节） |

几条小修随本批 PR 合入（第 8.4 节）后，每条仍按小修走，不因为在同一个 PR 里就升档；但每条都要各自满足小修的条件。

拿不准归哪一档，按高的那档走。做着做着超出了原来的档，停下来补齐那一档的步骤再继续。

### 1.2 分类与决策

需求常常由几个人分头做，每个人只看到自己分到的那一片。所以每项需求、每一片都先标清两件事：属于哪几类，要不要人决策。路线书里全部未完成的需求已经标好（[需求映射](requirements.md#section-3-9)）；新需求立项时一起标（第 2 节）。

**四类。** 一项需求常常跨几类，几类都标，主要的写在前面；产品线要写明是哪条线。

| 类 | 是什么 | 例子 |
| --- | --- | --- |
| 产品线 | 用户感知得到的一条场景或功能线：助理、Coding、引导、首页与简报、工作台、Sessions、创作台、团队、同步、发布，以及各个插件 | Coding 下一阶段、风险插件 |
| 体验与效果 | 界面打磨、文案、AI 效果、性能与可靠性 | 体验债、Coding harness |
| 横向能力 | 被几个插件或几条线共用的平台服务、合同、SDK、公共组件 | 统一输入框、技能包、观测和采集、智能呈现 |
| 底层与架构 | 存储与升级、运行时、授权与安全边界、门禁与工程流程 | 升级链、显式人审、防腐线 |

**两种决策标记：**

- **直接做**：需求和关键方案已经定了，照 spec 做。做的过程中碰到第 6 节的预警情形，照样发预警。
- **要决策：〈什么〉**：开工前或某一片之前要人定的事，写出是哪件事；谁来定按第 6 节「要谁回答」。要界面定样的也算（第 5 节）。

**交给别人做的片，** 任务书或 spec 的开头写清下面几行。接手的人不用通读全仓，也知道这一片在整体里的位置：

- 属于哪几类、哪条产品线；
- 用到哪些横向能力，可能产出或改动哪些；
- 相邻的线：谁在用它的结果，它在用谁的；
- 已有的决定和红线（第 4 节）；
- 哪些情形要发预警（第 6 节）。

**拆片。** 跨几类的需求拆给不同的人时，横向能力和底层的那一片由能力的主人（轨道主人）做，产品线的片叠在它后面（[轨道与冲突规则](tracks.md#section-5)规则 1、规则 7）。体验与效果的片可以和功能片并行，但不改功能片定下的合同。一条轨道独占的文件同一时间一个写手，轨道之间并行（[排期原则](dependencies.md#section-2)「冲突」，用户 2026-11-03 定，11-05 按[决定 26](decisions.md#decision-26)只管文件）；同路径、合同快照、换包和机器额度按路线书与并行开发规则串行。

## 2. 立项

1. **先查有没有。** 查 [BACKLOG](../../BACKLOG.md)、[在做的 spec](../../README.md)、同名的已归档 spec，以及用户已经定过的事：各 spec 的决策记录、[决策记录](decisions.md#section-7)、`AGENTS.md` 里写着「用户某日定」的条目。已有的接着写，不另起一份。
2. **写 spec。** 按 [specs/README.md](../../README.md) 写状态句、范围、验收编号和决策记录。需求决定及验收证据写回这份 spec。防腐后各项交付的认领和实时进展按第 2.2 节记在 GitHub。
3. **排进路线书。** 重要度按[排期原则](dependencies.md#section-2)的三条（工作接得上、体验、易用），依赖看[依赖图](dependencies.md#section-4)，按所改文件归到对应[轨道](tracks.md#section-5)；在[执行目录](../spec.md#execution-batches)的对应批次更新一行，在该行链接的批次详情写清交付、原需求、前置、可并行项和 UI 要求，同步需求来源与类型；目标或退出条件变化时再更新阶段总览，不另起排期（[维护规则](maintenance.md#section-9)）。复核近期需求时按[PR 来源对照](requirement-prs.md#recent-requirement-prs)查实际差异与交付去处，包含在途需求；未合入的标明固定头和状态，不能把排进批次记成已实现。
4. **写明负责人。** 需求维护和实现可以由不同的会话做，spec 里分开写。
5. **标类型与决策。** 按第 1.2 节标，写进[需求映射](requirements.md#section-3-9)的表。

### 2.1 每一项开始前先讲清楚

每项需求、每个批次里的每一片，**实际开始前先在执行会话向用户说明要做什么**，再进入对应工作；一批一个 PR（第 8.4 节），每批讲一次，每项都要讲到。接手已有任务也一样；不能只报批次号、标题或“继续推进”。说明分两步：先用大白话给人讲清楚，再给技术说明。

**说明之前先认领。** 在[认领板 #1743](https://github.com/molis-ai/molis-work/issues/1743)确认该项待认领、同轨独占文件上没有别的在途写手，按第 2.2 节登记会话并留评论。

**先给人讲清楚（用户 2026-11-03 定）。** 每个批次开工前，先用用户听得懂的话讲五件事：

1. **这批做什么**：一两句话说清楚要做出来的东西。
2. **解决什么问题**：现在哪里不顺，用户实际碰到的是什么。
3. **做完能看到什么**：用户在哪里、能用它做什么。
4. **为什么排在这里**：它要先等哪些东西做好，做好以后又让后面哪些事能开始。
5. **需要用户做什么**：看样定下、亲自验收、办账号或凭据、做某项决定；没有就说没有。

不用包名、合同、schema、轨道、验收编号这类词；非用不可时顺带一句说明它是什么。讲完以后，用户应当能用自己的话转述这批做什么、为什么做。每个批次文件（`reference/batches/NN.md`）开头的「给人讲清楚」一节是底稿：开工时先按当时 main 的实际情况核对、改准再讲；讲出来的和底稿差得多时，顺手改批次文件。批内每一片开工前也照样先讲，小片两三句话即可。

例如第 15 批：

> 现在同一个东西（比如一个 Goal）在首页、插件里和对话里长得不一样，能点的也不一样。这批先做一层公共的「展示」，让它在哪儿都按同一套样子显示、给同样的操作，再做一个不装别的插件也能用的首页。做完你会看到首页清楚了，同一个东西在各处是一样的。它排在字体和文字规矩（第 14 批）之后，因为显示的文字要按那套规矩写；后面的风险、Work Brief 都要用它。需要你先看几种展示的样子，定下来再做。

**再给技术说明。** 讲清楚以后，按下面五点说明这一片的技术安排，小修用两三句话，跨模块的片用短段落或清单；内容直接取自同一份 spec／工单，不另建说明书。技术说明包含：

1. **为什么做、做到什么程度**：当前哪里不顺，完成后用户或调用方能观察到什么；目标是方案、可交互原型、功能可用、内部完整还是可发布，沿既定要求，不自行降级。
2. **这片具体交什么**：属于哪个大需求和批次、需求／验收编号；真实场景、入口、输入、处理及结果，正常路径和相关失败／恢复。已有成果先核回，只实现缺口。
3. **怎么做、谁拥有**：主要模块和允许修改范围、事实主人与公共能力；保留什么、替换什么，本片不包含什么；负责的会话／writer 与需要交接的角色。
4. **先等什么、按什么顺序**：前置成果是否实际就绪，未决事项卡住哪一部分；先合同再服务再消费者，或本片实际顺序。可并行的明确写设计、只读核查或等待期间的独立工作，不能把后续依赖项当成已可开工。
5. **怎样证明完成**：对应验收的命令、真实操作或可操作样，预期结果及尚缺的账号／设备／数据；分别记录工程、实操和本人验收，UI 定样沿第 5 节。

第 15 批服务片的技术说明：

> 本片交智能呈现的确定组合服务，让同一对象在不同位置按同一声明显示并提供获准操作。先核 05 的公开合同和 14 的文字读取；在独立 horizontal 包实现组合，Host 只装配，SDK 复用共用校验，再由后续四种形态和三个插件接入。这片不做模型组合。验同一输入结果一致、无模型可用、越权与无效声明被拒，再用真实组件核对应位置的降级。前置缺口只暂停对应接入，设计审阅可继续，实现由 C 轨写手落。

**说明是同步，不是新增审批。** 讲完就继续，不等用户回话：已有授权、原要求已满足且没有关键待决，就讲清后继续；第 4～7 节确实要求的决定仍按原范围等待，不重复问已经定过的事，也不把沉默当作批准。发生影响交付、合同、前置或并行范围的变化时，先更新原 spec 和路线书对应行，再说明变化；不必为每条命令重讲。

### 2.2 在同一个 GitHub issue 认领和更新

防腐后 01～89 和服务端批共用[路线书认领板 #1743](https://github.com/molis-ai/molis-work/issues/1743)。正文每行对应一项交付，显示当前负责人、分支或 PR、状态和更新日期。评论按时间记录发生了什么，正文与评论不一致时，以该项最新的评论为准。

| 什么时候 | 负责人在 #1743 记录什么 |
| --- | --- |
| 开工或接手续做前 | 读最新正文和该项评论，核对前置与同轨独占文件上的在途写手。首次认领先确认该项「待认领」，在自己的交付行填会话、设备、分支和日期，改为「已认领」，再评论“认领 批次号／交付项”。继续自己已认领的工作时，从最近的进展接着做。 |
| 有实质进展或状态变化时 | 定样有结果、开始实施、范围或前置改变、验证通过或失败、开 PR 或收到需处理的评审意见时，当次更新自己的行并留评论。即使仍是「实施中」，也要写清本次结果、证据链接和下一步。开 PR 后改为「待评审」，分支栏换成 PR 链接。 |
| 受阻、暂停、恢复、放弃或交接时 | 写清受影响的项、阻塞原因、所需决定或恢复条件。恢复时记录新依据和下一步。暂停期间保留原负责人。明确放弃时记录原因和释放的交付项。交接经确认后，记录原会话、接手会话和剩余工作，再更新认领行。 |
| PR 合入或验收有结果时 | 记录 PR、实际合入范围，以及工程验证、真实操作和本人验收各自的结果。只合入一部分时，该交付行保持「实施中」并写明余项。整项合入才改「已合入」，列出仍待验收的部分；批次详情按第 11 节写回。 |

一批一个 PR（第 8.4 节），每项仍各占一行，分支栏写本批分支和子分支、开 PR 后换成 PR 号，并写明这批要碰的枢纽文件和合同快照。每次改正文前重新读取，只改自己的交付行，状态沿用认领板已有选项。评论写明批次号和交付项，让接手的人能顺着找到证据。超过三天没有更新可在评论里询问，改派按认领板的规则办理。

## 3. 产品检查

独立片和大需求写在 spec 里，小修有涉及的才写。

- **从用户的结果倒推。** 写出用户从哪里进来、走哪几步、在哪里拿到结果、中途中断后怎样接上（[产品治理](../../product-flow-governance/spec.md)第 4.1 节，[排期原则](dependencies.md#section-2)第 1 条）。
- **每一步都要站得住。** 每个确认、检查、设置项都回答产品治理第 3 节的四件事：它保护什么或解决什么、此刻缺哪个事实或决定、用户此前给过答案或授权没有、怎样少打断。能删的、能合并的、能按需出现的，就不留成固定步骤。
- **已有的授权和选择接着用。** 不让用户为同一个意图重复确认（产品治理第 3 节、第 6.2 节第 3 条）。
- **AI 的部分。** 资料、工具和约束各放在 [Prologue 手册](../../../docs/platform/PROLOGUE-AI.md)说的位置。模型能力不够造成的坏效果，不按症状打补丁（手册第 16.3 节）；后果严重的，用事实核对兜住。
- **归谁。** 这项能力属于哪个插件或平台服务；以后别的插件也会用的，做成平台能力（第 4 节第 2 项）。
- **别漏掉的路径。** 设置、空状态、失败与恢复、第一次和第二次进入、中英文两种界面。

## 4. 开工前检查

在 spec 里加「开工前检查」一节，逐项回答。不涉及的写「不涉及」，并给一句理由。

| # | 要回答的 | 依据 |
| --- | --- | --- |
| 1 | **事实主人**：每项新事实归谁（插件、Module 还是平台服务）；读别人的事实走哪个公开合同；不出现第二个主人 | [SSOT](../../../docs/SSOT-MATRIX.md)、[系统架构](../../../docs/system/ARCHITECTURE.md)第 3 节 |
| 2 | **插件同等待遇**：经 Plugin Runtime 装配、用同一套 SDK；缺的平台能力补进平台，不给某个插件在宿主里开私路，不新增构建期接线 | `AGENTS.md` 硬约束、[插件开发 Skill](../../../skills/molis-plugin-dev/SKILL.md) |
| 3 | **能力注册**：能力在自己的声明里注册一次，页面、工作流、Agent、MCP 都用这一份；可信身份取自调用上下文；等模型或外部服务的动作声明 `scheduling: "concurrent"` | [动作架构](../../action-architecture/spec.md)第 3 节 |
| 4 | **合同**：改不改合同、改哪几项；按现在所处的阶段做（M1 之前不留兼容期，一个 PR 改完所有消费者；M1 之后带读取兼容）；要不要先单独开一个只改合同的 PR | [合同变更流程](../../../docs/system/CONTRACT-CHANGES.md)、[轨道与冲突规则](tracks.md#section-5)规则 1 |

**第 15 项的五个场景（用户 2026-11-07 定）。** 方案还能改的时候逐个比一遍，选全局最优，不选只对手上这一片最省事的。回答要点名具体的插件、批次或能力，写「已考虑大局」不算回答；不涉及的场景写一句理由，小修只答涉及的场景。

| 场景 | 要看什么 |
| --- | --- |
| 插件 | 别的插件、第三方插件能不能用同一个办法；作者要多做什么；有没有只有内置才有的路 |
| 平台 | 该归平台还是归插件；有没有现成服务可接；外壳、运行时、授权要不要跟着变 |
| 助理 | 助理和 Agent 能不能发现、调用这项能力；没有界面时能不能完成；结果和授权说不说得清 |
| 各类平台能力 | 统一输入、技能包、公共呈现、资料与目录、观测采集、连接器、成果库、工作流程、MCP、同步与团队：该接哪些，有没有重叠 |
| 后续开发 | 后面哪几批碰这一块；再加一个同类的要改几处；合同和升级以后怎样走 |

三条配套的话，避免这项被读成「多做点」：

- 全局最优不等于提前做后面的事。默认只把事实主人、合同和放置位置做对，让后面接得上。
- 手上这一片多花一点、其他场景少付很多的，选全局更优的；代价相同时，选让平台能力往前走一步的做法。
- 只算真实的使用者：已有的和已排定的算，猜测的不算，不为猜测造抽象。

**谁审。** 统筹审这一节，把结论写在 spec 的 PR 或评论里；审出问题先改设计再开工。审查也按产品治理第 3 节保持轻量：只追问真正缺的决定，不为「规范要求」另加步骤。

**红线项弹窗问用户**，由统筹或负责的会话问，不自己定：

- 动真实 Home 的库或数据（[发版规则](../../../docs/releases/POLICY.md)）；
- 换 vendored 的 Prologue 包，或改上游；
- 发版、改版本号，用到账号、证书或凭据；
- 放宽门禁或改门禁本身（脚本、`limits.json`、CI）；
- 新增兼容或迁移逻辑（第 7 项）；
- 某个页面资源一次涨超过 10 KB，或新增一个资源；
- 改变产品语义，或推翻用户已经定过的事。

## 5. 界面先定样

**要求有多高（用户 2026-11-04）：** 用户对整个项目的界面、设计、交互、视觉和使用体验要求很高。凡是碰到界面的改动，不论是新做、复用、改文案还是修缺陷，都要在空间、光影与阴影、动效与曲线、反馈、留白、内容布局、色彩上逐项做到位，中英文、浅深色、1440／1024／390 都要看过。「能用」「测试过了」不算完成：界面与体验类以用户本人看实物验收为准（[决策记录](decisions.md) 第 12 项）。统筹审界面相关的 PR 时，照这几项逐一看截图或预览；有一项没做到位的，退回去再做。

**体验维度（用户 2026-11-04 补）：** 上面是看得见的做工；下面六个维度看的是「用起来怎么样」，同样逐项过，一项不到位就退回，不以「功能可用」交差。**做不到「用得爽」就退回。** 每个界面相关的 PR 由做的人自检、评审的人逐条看（评审怎样记见第 10.1 节）。

- **交互：** 步数少，能一步做完的不拆成两步；可预期，点之前看得出会发生什么；可撤销，删除、覆盖这类动作能撤回或至少确认一次；反馈即时，点了马上有回应，慢的操作有进度；键盘能走通，主路径不碰鼠标也能做完，焦点顺序合理；出错就地修好，错误出现在出错的地方，说清下一步怎么办，已经填的内容不丢。
- **动效：** 有目的，用来说明变化、指向焦点或确认结果，不为好看而动；用令牌，时长和曲线只取 `--dur-*`、`--ease-*`（[DESIGN.md](../../../DESIGN.md)「Motion」），不手写数值；有退路，`prefers-reduced-motion` 下去掉位移和到达，信息不靠动效才传达得到。
- **布局：** 内容的先后和分组跟着用户的任务走，不照数据结构排；主次分明，空间、对齐、留白一致；长文字、多条目、空状态、窄屏下仍成立，不出现折行错位、横向滚动和内容被截。
- **注意力控制：** 一屏一个主焦点，主操作一眼找得到；只在必须时打断用户，能内联的不弹窗，能晚点说的不现在说；提示分级，错误、警告、提醒、成功的分量和位置各不相同，不让每条都一样响；不让人找、等、猜：要的东西在手边，等待有说明，状态有交代。
- **认知心理学：** 让人认出来而不是回想，选项、对象和状态直接摆出来，不要求记住上一屏；渐进展开，先给常用的，高级的按需出现；分块，一组一组地给，一组的条目数在人容易扫读的范围内；默认值合理，大多数人不改就能往下走；不露系统内部的词和 id，用用户自己的话，术语照 [GLOSSARY](../../../docs/system/GLOSSARY.md)。
- **行为心理学：** 少摩擦，能省的步骤、确认和重复输入都省掉，已有的选择和授权接着用（第 3 节）；有完成感，做完看得到结果并知道下一步；尊重自主，让用户自己选、能跳过、能回头，不替人做决定；不用暗黑模式，不用诱导点击、制造紧迫、藏退出和默认勾选来推用户。

**界面通用规则（用户 2026-11-03）：** 按钮有边界，看得出能点；多项内容要分区；行不折行，状态与条目同一行；文件和文字放进容器，不散在背景上；不同内容用搭配的不同颜色区分。

**什么时候要定样：** 新页面或新动线；新的交互方式；组件板上还没有的控件或状态；视觉方向变了（皮肤、字体、色彩、密度、动效语言）。照组件板已有的控件和版式改、改文案、修缺陷，不用定样。

**怎样做：**

- 共享的控件、状态和动效，做成组件板 `/__ui/catalog` 上的标本（[DESIGN.md](../../../DESIGN.md)「Where the rules live」，[界面工艺底线](../../ui-craft-floor/spec.md)第 5 条）。整段动线做成能点的预览页：能用产品代码的就用产品代码，模拟的部分在界面上逐处标明（例：[情境动作](../../context-program/spec.md)第 16.2 节的 W0 原型）。
- 给 2～3 个方案，各写取舍。浅色和深色都要，宽度看 1440、1024、390，中英文两种界面也都看。
- 样遵循组件板和整体设计规格（用户 2026-11-04 定）：先用组件板 `/__ui/catalog` 上已有的控件、状态、令牌和版式；配色、字号、间距、圆角、动效和界面通用规则，按 [DESIGN.md](../../../DESIGN.md)、[界面设计规范](../../craft-finish/spec.md)和[界面工艺底线](../../ui-craft-floor/spec.md)。组件板上没有的控件或状态才新做：在样里逐处标出「组件板新增」，写明现有的为什么不够；定下后先补成组件板标本，再进产品。
- 原型用组件板的实件做：空间、阴影、动效、反馈和色彩与组件板上的 `mw-*` 控件一致。能挂进产品预览的，直接用 `mw-*` 控件和令牌；只能写在产品之外（如 `docs/design/<目录>/`）的，样式取自组件板现行的令牌和控件样式，不拷旧原型的令牌表另起一套。统筹审定样 PR 时逐项核对这两条；定样跟实现同一个 PR 的（第 8.4 节），在写产品代码之前的走查上核对。

**谁定：** 用户本人看实物拍板，截图说不清的就开预览给用户点。定下的方案连同理由、否掉了哪些和日期，写进 spec 的决策记录，然后才写产品代码。

**之后：** 按 [DESIGN.md](../../../DESIGN.md)、[界面设计规范](../../craft-finish/spec.md)和[界面工艺底线](../../ui-craft-floor/spec.md)实现。实现时发现定下的方案走不通，回到定样再问，不在实现里悄悄换方向。

## 6. 预警与讨论

不是每个人都看得到整体。迭代时只盯着手上的功能，容易把本该收进平台的能力各写一份、把底层的规矩悄悄改掉，或者让别的线的体验跟着变了。第 4 节的检查是开工前答一遍；这一节是全程盯着：评估方案时、开发中、评审时，碰到下面的情形就发预警，拉团队讨论。

**什么时候发：**

| 情形 | 信号 |
| --- | --- |
| 界面变化 | 新页面或新动线、新控件或新状态、视觉方向变化（皮肤、字体、色彩、密度、动效）。第 5 节的定样也在这里讨论 |
| 可能沉淀成横向能力 | 第二个插件或第二条线也会用到；别处已经有类似的实现；正在给某个插件写本该由平台提供的东西 |
| 底层逻辑调整 | 改合同、存储与升级、运行时、授权与安全边界、调用链与调用次数 |
| 改产品语义或影响别的线 | 推翻或绕开已有的决定；改变别的产品线的体验或数据；要借别的轨道独占的文件 |

拿不准算不算，就发。多问一次的代价，比各写一份、事后返工小。

**预警卡写什么**，几行就够：

1. 一句话：哪里要变、为什么；
2. 属于上表哪种情形；
3. 影响到哪些线、插件、横向能力；
4. 2～3 个方案，标出推荐和各自的取舍；
5. 要谁回答：产品线负责人、能力的主人（轨道主人）、统筹；涉及红线或产品语义的，要用户回答；
6. 卡住哪一部分，其余是否继续；
7. 时限；
8. spec 或 PR 的链接。

**在哪里发：** 团队 IM 的固定讨论群。Agent 起草预警卡，由负责这一片的人发出去；Agent 不代人发消息。

**发了之后：**

- 只停受影响的那部分，其余照做。
- 时限默认 1 个工作日。到时没人回，由统筹按推荐定，并记下来；用户可以推翻（用户 2026-11-03 定）。红线项（第 4 节）和第 5 节要用户拍板的定样，照旧要等用户；已明确批准的内容不重复询问。
- 讨论的结论写回 spec 的决策记录：结论、谁定的、日期、讨论的链接或摘要。IM 里的讨论不算记录，以 spec 为准。
- 定下要收进平台的，按[轨道与冲突规则](tracks.md#section-5)规则 7 由能力的主人落，原来那一片叠在后面。定下先不收的，写明理由；以后第二个要用的人再提。
- 影响分类或排期的，同步改[需求映射](requirements.md#section-3-9)、[执行目录](../spec.md#execution-batches)及其链接的批次详情；目标或退出条件变化时再改[阶段总览](stages-and-acceptance.md)。

## 7. 要用户定的事

- 先把能独立推进的部分做完，再把要用户定的事攒成一批，用弹窗问。每项给 2～3 个方案并标出推荐，写明它卡住哪一步。
- 定下的写进 spec 的决策记录，记日期和用户的选择；影响排期的同步到[决策记录](decisions.md#section-7)。
- 用户已经定过的不再问。要推翻的，写明有什么新证据，再问。

## 8. 开发

- 每片开工先按第 2.2 节认领，再完成第 2.1 节说明。按这片实际前置和[执行目录](../spec.md#execution-batches)推进，每次进展有变化就在认领板更新。
- 开工、工作树、枢纽文件、PR 体量、构建与测试的时段，按[并行开发](../../../docs/system/PARALLEL-DEVELOPMENT.md)第 1～5 节。
- 改某个包之前，先读它 README 里的「开发要求」（[写法](../../../docs/system/DEVELOPMENT-REQUIREMENTS.md)）。写插件看[插件开发 Skill](../../../skills/molis-plugin-dev/SKILL.md)，调模型看 [Prologue AI Skill](../../../skills/molis-prologue-ai/SKILL.md)。
- 一批一个 PR（第 8.4 节），一批算一个主题。合同在本批分支上先做；改门禁、脚本、CI 的并进本批 PR、单独一个提交，而且先问用户。
- 全批写完测完才开 PR（第 8.4 节）；子分支不开 PR，也不开草稿 PR 占位（用户 2026-10-25 定，PR 多了占 CI 槽位；2026-11-07 从一项扩到一批）。提前切出小 PR 的几种情况见第 8.4 节。

<a id="better-plan"></a>

### 8.1 有更好的方案就换

批次文件里的方案、拆片和顺序是默认做法，不是死要求（用户 2026-11-07 定，[决定 27](decisions.md#decision-27)）。看清现状后有更好的做法就可以换，判断标准三条：用户拿到的结果不比原来差，综合第 4 节第 15 项的各场景更优，总代价说得过去。不能借此降低完成程度、去掉或降低验收。

| 谁定 | 什么事 |
| --- | --- |
| 批次主会话自己定，记下来 | 实现方案、拆片、顺序、PR 怎么分；把后面批次的一小块并进本批；把一项挪到相邻批次（验收有人接） |
| 发预警（第 6 节）后定 | 影响别的产品线、别的批次的前置，或改变合同走向 |
| 先问用户 | 第 4 节的红线；推翻用户定过的事；改产品语义；已定样的方向；减少或降低原需求的验收 |
| 不在可换的范围内 | `AGENTS.md` 硬约束；独占文件一次一个写手；合同默认单独开 PR（例外只有第 8.4 节那一种）；机器额度；本批没合完不开下一批的实现（按批推进，第 55 批第 3 项 N22 是写明的例外，[决定 29](decisions.md#decision-29)） |

最后一行是防冲突、防腐的规矩，不是批次设计，放开了会互相踩。

**怎样换。** 在本批文件的「交付与前置」里改成新做法，并写一条偏离记录：原来怎样、现在怎样、为什么更好、影响谁。后面批次受影响的，同一个改动里改那一批的文件。然后跟用户说一声，不等回话。后面批次的内容默认不提前做；提前做一小块能明显少返工，或本批设计离不开时，可以并进本批。评审看第 10.1 节第 7 行。

<a id="cleanup"></a>

### 8.2 边做边清理

清理是这一片的一部分，不留到收尾：到收尾时 PR 已合、写手已收，多半就不会再清了（用户 2026-11-07 定）。范围以这一片碰的模块为界，不另留大扫除的片。

| 碰到的情况 | 怎么办 |
| --- | --- |
| 这一片让它变多余：旧入口、被替换的实现、不再用的导出、依赖、测试、文档 | 必须同片删 |
| 这一片碰的模块里已有的重复或无用代码，删了不改行为 | 应当顺手清；清不动就写明原因 |
| 在别的轨道独占的文件里 | 按[轨道规则 7](tracks.md#section-5) 由那条轨道落 |
| 要改合同、改行为，或量大到成了另一个主题 | 单开 PR 或记 BL，写清主人和理由 |
| 不确定还有没有人用 | 不删，列为候选 |

- 删之前按[系统性整理 Prompt](../../../docs/prompts/repository-systematic-review.md) 第 11 节核对动态加载、插件注册、构建脚本、迁移、公共 API 和外部消费者。
- 不为变绿放宽或删除断言；只删验证已删代码的测试，并在 PR 里写明。
- 小的清理跟这一片同一个 PR、单独提交，评审能分开看；不为每次清理单开 PR。
- 这项靠人看（仓库现在没有查无用导出和重复代码的工具，也不为此加门禁），会有漏网，收尾检查再看一遍。

<a id="elegant-code"></a>

### 8.3 写法要优雅

门禁过了不等于优雅（用户 2026-11-07 定）。判断标准四条：

- **结构直接：** 读的人顺着看得懂，概念少，一个名字一件事。
- **改动面小：** 再加一种同类情况，只改一处。
- **不绕：** 没有只为绕开问题的特判、多余的转发层和标记参数。
- **不炫技：** 简单写法够用就不加抽象。

评审可以因此退回，但要写出更简单的写法长什么样，不能只说不喜欢，也不按口味重写。

<a id="batch-grouping"></a>

### 8.4 一批一个 PR

**为什么（用户 2026-11-07 定，[决定 28](decisions.md#decision-28)、[决定 31](decisions.md#decision-31)）：** 防腐之后这一大批需求周期紧，产品还没有用户，现在是集中攻坚。决定 28 让同批的小任务合成一组，但仍有文件数、包数和多种单独开 PR 的限制，实际一批还是好几个 PR，每个都要同步 main、重测、排队，互相冲突。所以改成**一批一个 PR**：批内各项在本批分支上一起开发，开发途中不和 main 反复合并，整批写完统一测一次、统一解一次冲突，合成一个 PR 合入 main。提速只省开发过程里的重复，验收、评审、用例、门禁和本人验收一项不减，质量不能降；不考虑回退（第一个版本装到开发机之外时再重新看）。

**分支怎么开。**

1. **本批分支。** 主会话开工时从最新 main 切出 `batch/NN`（服务端批是 `batch/srv-N`），一个批次只有这一条集成分支。
2. **子分支。** 批内各项按依赖和冲突面分成子分支，从本批分支切出，做完合回本批分支，**不开 PR**、不同步 main。同轨或有依赖的按先后叠；两个写手不碰同一批文件；别的轨道独占的文件仍按[规则 7](tracks.md#section-5) 由那条轨道的写手在本批分支上接力写。批次文件的「粒度」写的是子分支怎么分，是开工前的建议，主会话按当时情况改准，和建议不一样的记在认领板和 PR 的「偏离」（第 8.1 节）。
3. **合回不重测。** 子分支途中只保证能编译，只跑刚写的用例确认写对了，不跑受影响用例和浏览器批次；合回本批分支时也不重测。用例照写，不因为最后才测而少写。
4. **开发中不同步 main。** 本批分支在开发途中不合 main；main 上的改动在开 PR 前统一合一次。只有本批真要用到 main 上新合入的东西（例如提前切出的合同），才在那时合一次。
5. **谁合。** 子分支交回主会话，由主会话合回本批分支，有冲突交回那个写手解。全批写完后，同步 main、解冲突和统一测试由主会话派一个写手做（冲突跨模块的用 Opus 5.5 high），主会话核对后开 PR。
6. **交回前过门禁。** 写手交回子分支前跑一次 `node scripts/check-health-gates.mjs --base origin/main`，门禁数字的问题当场改，不留到最后。它几分钟就完，不算重复测试。
7. **推送备份。** 本批分支和子分支照常推到远端（推送前 `pnpm secrets:check`），只是不开 PR。名字用 `batch/`，不用 `integration/` 开头：推到 `integration/**` 会触发 CI 全量（[并行开发第 7 节](../../../docs/system/PARALLEL-DEVELOPMENT.md#7-集成分支上跑全量)）。

**PR 怎么开。**

- **一批一个 PR，不限文件数和包数。** PR 里一项一组提交，提交说明写交付项和验收编号；机械改名、大段删除、生成文件各自单独提交；描述按项分节，按验收编号列每个编号对应的用例或走查，缺一项不合。
- **文档不单独开 PR。** spec、决策记录、BACKLOG 删条、批次文件的进展与合入记录、收尾检查结论、定样记录，都写在本批分支上，随本批 PR 合入。合入的提交号随下一批的 PR 补。不属于任何批的文档改动，并进当时在做的那一批。
- **门禁、脚本、CI 并进本批 PR。** 单独一个提交，PR 描述单列「门禁改动」一节，写清改了什么、有没有放宽；改门禁仍是红线，先问用户。
- **合同随本批 PR。** 设计稿先评审、合审，提交到本批分支，再写合同代码，实现叠在后面；公共合同台的合审在最终的头上，本批跑全量。
- **定样随本批 PR。** 定样记录不单开 PR；组件板新增部件由 D 轨在本批分支上补成标本，D 轨合审过了才写产品代码。用户拍板前不写产品代码；评审走查在写产品代码之前做完，结论连同原型路径和提交号记在认领板该项。
- **小修随本批 PR。** 本批的 BL 小项、评审里不挡合并的意见，在本批分支上开一个小修子分支攒着做。

**只有这几种提前切出一个小 PR 先合：**

| 什么 | 为什么 |
| --- | --- |
| 别的批、服务端批或别的片确实在等的合同或能力，或有人排队改同一份快照 | 等整批合完会挡住别人 |
| main 红了、安全缺陷的修复 | 不能等 |
| 有固定窗口和授权的事：真实 Home、换 Prologue 包、发版、第 16 批的一次切换 | 时段由窗口定 |
| 要等外部账号、凭据或服务、等不到批次结束的 | 等待不可控，就从本批移出，记进下一批 |
| 原需求要求单独验证的，如第 72 批业务数据导出回读 | 合并不能模糊证据 |

切出时把它和依赖它的提交一起移到从 main 切出的小分支上，合入后本批分支再合一次 main。某项卡住（等用户定、设计被退回、前置没到），从本批分支上拿掉它的提交，留给后面的批，其余照做，整批不等它。

**测一次。** 全批写完后：

1. 本批分支同步最新 main，解一次冲突，整体构建一次。
2. `node scripts/affected-tests.mjs` 按全批改动挑用例，加上各包 README 的改动后必跑，一次跑完，不抽样；浏览器用例另外跑（`--include-browser`，排时段）。脚本不提示的也要跑：动共用样式跑 `pnpm visual:compare`，改创作台 Skill 跑 `pnpm studio:replay`，macOS 专有用例在本机补。门禁跑一次，页面资源按全批合计。有界面的按三种宽度、深浅色、中英文统一截图，每处界面都走一遍。
3. 失败按提交看属于哪一项，在本批分支上修，重跑失败的文件和相关用例；是否自己引入的照旧用干净基线比对；不为变绿跳过或放宽断言。
4. 测完才开 PR。全量在 CI 上跑，放在改完评审意见之后的最终头上，全批只跑这一次。

**评审。** 本批 PR 开出后，评审台按子分支同时开几个评审，各审一个子分支的提交范围（这些评审也算机器上的并发数，多了就分两轮）；另开一个审全 PR：整合、冲突的解法、跨项的一致性，同时做本批的收尾检查（第 11.1 节）。结论照第 10.1 节七行逐条写在 PR 评论里，每行写明覆盖哪些交付项。意见尽量一次提全，写手一次改完再推。评审结论、合审、相关用例、全量，以及 `pnpm health:check`、`pnpm boundary:check`、页面资源、`pnpm secrets:check` 都必须在最终的头上；再推就重跑受影响的部分。开 PR 后没有冲突不再同步 main，交合并队列；别的 PR 合入了本批碰的枢纽文件，同步 main 并重跑相关用例。

**认领板。** 仍是每项一行，分支栏写本批分支和子分支，并写明这批要碰的枢纽文件和合同快照：开 PR 之前，别人只能从这里看到。子分支合回本批分支仍是「实施中」，评论记一笔；本批 PR 开出后各项改「待评审」、分支栏换成 PR 号；合入改「已合入」。开工说明每批讲一次，每项都要讲到；开工前检查可以按子分支答，写在一处，其余原需求放链接。要用户本人看的，全批列一张清单，一次看完，每项结果分开记。

**不变：** 每个验收编号都要有证据；工程、实操、本人验收三级分开记；评审逐条写；界面做工和体验逐项看；安全改动带拒绝测试，不变量表和拒绝测试同一个提交；CI 要通过；红线照旧问用户；按批推进不变，本批没合完不开下一批的实现。

**代价有两个：** 问题发现得晚，最后一次冲突可能较大；PR 大，评审难。所以一项一组提交、按子分支分头评审、卡住的项移出去、提前切出的几种情况都不能省。

**在途批次（2026-11-07 起）：** 已开的 PR 不重开、照原样走；剩下的项立即按本节做，在认领板发一条公告。

## 9. 验证

下面这些按全批统一做一次，做法见第 8.4 节。

- 用例：按改动用 `node scripts/affected-tests.mjs` 挑，全量什么时候跑、在哪里跑按并行开发第 6、7 节；判断失败是不是自己引入的，用基线工作树比对（第 8 节）。
- 门禁：`node scripts/check-health-gates.mjs --base origin/main`；改了样式或客户端脚本，再跑页面资源检查；推送前跑 `pnpm secrets:check`。
- 界面：跑浏览器用例，截浅色、深色，1440、1024、390 三种宽度的图；对照定下的样走一遍真实路径。
- 分三级记录：工程通过、实操（自动化或人工走查）、用户验收。下一级不能从上一级推出来。

## 10. 评审与合并

- PR 按[模板](../../../.github/pull_request_template.md)填，其中「开工前检查」一节写档位和类型，贴 spec 里的检查、定样决定，以及发过的预警和结论。
- 合并之前先读评审意见，答复了或改完了再合。
- 改到共享核心的，在最终 head 上跑全量；由统筹入合并队列。
- 本批 PR 的描述按验收编号列明每个编号对应哪个用例或哪次走查，缺一项不合（第 8.4 节）。

<a id="review-quality"></a>

### 10.1 评审时的防腐与代码质量

每个 PR 的评审（评审台或统筹）在 PR 评论里把下面七行**逐条**写出结论，每条只能是三种之一：

- **过**：看过 diff，没有问题；
- **不涉及（理由）**：这个 PR 碰不到这一条，写一句为什么；
- **问题**：写清哪里、违反了什么、怎么改。

**有一条是「问题」就挡合并**，改完回到同一条再看一遍。看不出来的当「问题」提出来，不默认过；纯文档的 PR 多数条是「不涉及」，也要逐条写。不能只写「LGTM」或只挑几条写。界面相关的 PR，另按第 5 节的做工和体验维度逐项看，结论一并写在评论里。

| # | 逐条看什么 | 依据 |
| --- | --- | --- |
| 1 | **开工前检查**：第 4 节的 15 项，对照 spec 里的回答和实际 diff 是否一致，不涉及的项有没有理由；红线项有没有问过用户 | 本文第 4 节 |
| 2 | **仓库硬约束**：diff 碰到的每一条都符合，包括插件同等待遇、能力只注册一次、模型调用只经 agent-host、可信身份不从输入读、一张表只由建它的包读写、安全边界登记、合同只认现行取值 | [`AGENTS.md`](../../../AGENTS.md)「硬约束」 |
| 3 | **系统整理的审查面**：模块划分与调用链（第 3 节）、开发契约与能力注册（第 4 节）、自动发现（第 5 节）、插件实现完整性（第 6 节）、数据状态事件生命周期（第 7 节）、AI 与 Prologue（第 8 节）、前端质感与动线（第 9 节）、配置安全性能升级发布（第 10 节）、无用重复过时（第 11 节）、测试与预期行为对齐（第 12 节） | [系统性整理 Prompt](../../../docs/prompts/repository-systematic-review.md) 第 3～12 节 |
| 4 | **调用次数**：一次用户操作发出几个请求、每个请求做几遍目录发现、授权核对和开库；有没有重复读同一份数据、按条目逐个请求、后台轮询；一次请求一份上下文，嵌套调用共用 | [对抗式审查台账](../../../docs/reviews/adversarial-review-2026-11-01.md) N42～N56 |
| 5 | **门禁只许变小**：跑 `node scripts/check-health-gates.mjs --base origin/main`，下列数字不能比 merge-base 大——`any`、`as unknown as`、空 `catch`、没处理的 promise、`console`、兼容标记、`Error` 子类、测试引用包内部、巨大单元；放宽门禁本身是红线项，先问用户 | `AGENTS.md`「构建与测试」，[`tooling/gates/README.md`](../../../tooling/gates/README.md) |
| 6 | **代码质量**：平台已有的能力不另写一份；不留死代码和重复代码，这一片让它变多余的都删了（第 8.2 节）；写法优雅（第 8.3 节）；函数内聚，一个函数做一件事；注释写为什么，不复述代码；命名照 [GLOSSARY](../../../docs/system/GLOSSARY.md)，不造同义新词；改安全边界的带「拒绝」测试，且断言的确是拒绝；不为变绿而跳过、放宽或删除断言；界面文字与外观按第 4 节第 12 项看：不拿译文做判断、不存译文、不拼半句，HTML 插值里没有 `t.text`、`say.text`，样式里没有局部色值 | `AGENTS.md`，[安全不变量](../../../docs/system/SECURITY-INVARIANTS.md) |
| 7 | **偏离**：和批次文件不一样的地方都记了吗，理由站不站得住，有没有借此降级或绕开红线；该发预警、该问用户的问了没有 | 本文第 8.1 节 |

评论的写法，一行一条：

> 1 开工前检查：过
> 2 仓库硬约束：不涉及（只改文档，没碰代码）
> 3 系统整理的审查面：问题——新文件里自己写了一份目录过滤，平台已有同样的能力，改用平台的
> …

本批 PR 按子分支分头评审、另有一个全 PR 评审（第 8.4 节），各自七行写一遍，每行结论写明覆盖哪些交付项，某一项有问题就单独写出来，不让一句「过」盖住；界面逐处写。

作者在 PR 描述里先按这七条自查，评审时有疑问的地方先看作者写的理由；评审结论以评审者自己看 diff 的为准。

## 11. 收尾

按第 2.2 节逐行收尾。某个 PR 只交了其中一片时，在认领板记录这片的结果和余项，整行继续由原负责人推进。

- 收尾检查（第 11.1 节）由本批 PR 的全 PR 评审做，结论和本批合入记录在开 PR 前后写在本批分支上，随本批 PR 合入（第 8.4 节）。
- 做完的条目从 BACKLOG 删掉，在提交说明里写编号。
- 按 [specs/README.md](../../README.md) 归档 spec；只差用户验收的，列进 BACKLOG 的「待你验收」。
- 在[执行目录](../spec.md#execution-batches)链接的批次详情记录日期、PR、验证与剩余项：主会话攒着，开 PR 前、暂停或交接时一次写在本批分支上（第 8.4 节），平时看认领板。整项合入后，把[认领板](https://github.com/molis-ai/molis-work/issues/1743)对应行改为「已合入」。整段完成后更新阶段总览，原需求完成后才从[需求映射](requirements.md#section-3-9)删行。
- 清掉用完的工作树和分支（并行开发第 10 节）。

<a id="batch-closing-check"></a>

### 11.1 批次收尾检查

本批 PR 开出后、合入之前，由评审台的全 PR 评审把全批改动合起来看一遍，回答下面五问（用户 2026-11-07 定；一批一个 PR 后从「全部合入后」挪到合入前，决定 31）。它不重复第 10.1 节按子分支的评审，只看合起来才看得出的东西；不新增会话，也不加门禁。每批一次，不按交付项做。

| 问 | 要回答什么 | 证据 |
| --- | --- | --- |
| 防腐 | 合起来有没有单个 PR 看不出的问题：同一件事写了两份、事实多了一个主人、调用次数叠加变多、留下没接上的半成品 | 本批全部 diff，点名文件或 PR |
| 平台能力 | 有没有值得沉淀的。结论三选一：已沉淀（在哪）、现在收（BL 或加片）、不收（一句理由）。不强求，「不收」是正常结论 | 已有第二个使用者，或点名已排定的批次 |
| 代码质量 | 整体变好、持平还是变差，结构更简单还是更绕；变差写为什么值得、谁什么时候还 | 门禁数字前后、净增减行数、巨大单元 |
| 清理 | 删了什么；本批让什么变多余却没删、为什么；候选记到哪条 BL | 文件或导出名，BL 编号 |
| 全局 | 开工时的场景判断还成立吗；做出来的结果让插件、助理、别的平台能力和后面哪几批更顺或更难；批次文件要不要改，改了没有 | 点名场景与批次，改动的链接 |

不是每条发现都挡完成，分界是这个问题是不是本批带来的：

| 发现 | 挡不挡本批完成 |
| --- | --- |
| 本批带来的防腐问题 | 挡，在本批 PR 上修完再合 |
| 本批让它变多余却没删 | 挡，除非写明理由并记 BL |
| 质量变差且说不出理由 | 挡，给理由或改掉 |
| 旧代码的问题 | 不挡，记 BL |
| 平台能力候选 | 不挡，不强求 |

**怎样写。** 每问一到三句，要点名文件、数字或 PR，结论写进本批文件的「收尾检查」一节，放在本批合入记录之前。只有设计或核账、没有代码改动的批次，代码质量和清理写「不涉及」并给一句理由。数字对照本批第一个 PR 合入前的 main（`node scripts/check-health-gates.mjs --report` 前后各一份）。只有一个 PR 的批次，写在那次评审评论里，本批文件链过去。写法示例（编号是占位）：

> 防腐：问题已修——#A 和 #B 各写了一份目录过滤，#C 并成一份。
>
> 平台能力：不收——只有一个插件在用，已排的批次里没有第二个使用者。
>
> 代码质量：变好——空 catch 5→3，净减 420 行，巨大单元无变化。
>
> 清理：删了旧入口 X 和导出 Y；Z 不确定，记 BL-NNN。
>
> 全局：第 NN 批可直接用本批的 W，已改它的前置；助理和插件走同一个动作。

**怎样生效。** 规则合入前已开的 PR 不回头补第 15 项和评审第 7 行；还没收尾的批次都做收尾检查，批次已完成的不补。
