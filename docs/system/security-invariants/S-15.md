### S-15 插件权限

S-15 的规则与代码位置按主题展开；本文件的表保留全部测试引用，仍由现有门禁逐项核对。

可信双实例的可选权限取项目自身 grant 与匹配 Home 现行授权的交集。Home 缺失、停止或换代拒绝可选能力，必需能力与项目生命周期独立；原 Home 激活的撤销检查随实际动作、scene 回调、保留作业、后台执行、route 和 SDK 消费调用保留，等待后、效果前及结果交付前重验，关→开不能复活旧调用，撤权后的失败记账同样拒绝。Home 只提供只读捕获函数，不暴露 context 或复制授权账。

#### 调用者

动作网关只认宿主发出的插件调用者（PG-110，① 10-19）：插件受众的调用、带 `host_plugin` 的调用，都要带一个宿主发出、还没收回的调用者（Runtime 会话的，Home 会话进项目时另发的一份，成果 SDK 复用的同一会话的，沙箱代理为这一次调用发的），它的人、项目、安装与这次调用一致；
没有、复制或伪造的、已收回的（停用、卸载、撤权、项目关闭、宿主重启）一律 `host.plugin_caller_invalid`，对不上的 `host.plugin_caller_mismatch`；
插件的权限收窄到声明与授权的交集，动作要的超出它就 `actions.plugin_permission`，每次写之前再查一次，执行中被撤权的调用不再写业务记录。
插件在自己的动作里经 SDK 调它消费的动作时，被调动作每次写之前还要问插件这次所在动作的原调用者（插件调用时记下的那一份，同 S-18）：原调用被取消或撤权，被调动作就不写（PG110-11）。
宿主发出的插件调用者只用于插件受众的调用：人、Agent、工作流的调用带着它，即使人、项目、安装都对得上，也是 `host.plugin_caller_mismatch`（PG110-12）。
调用者在调用等待中被记下、会话随后停止的，直接拿去调网关是 `host.plugin_caller_invalid`，等待中的那次调用也不写（PG110-13）。
动作、动作可用性与全部场景回调交给插件的上下文不含 `host_plugin`，Runtime 内部保留原调用者；
A 调 B 时 B 拿不到 A 的签发对象，B 自己的 SDK 服务仍可用（PG110-17）。
B 要知道是哪个插件调的它（例如 Feed 的 Home 一半只收 Feed 自己的项目实例），读上下文里的 `calling_plugin_id`：它由宿主按签发的调用者在每次调用时给出，只在插件受众的调用上有，人、Agent、工作流的调用带着它也被去掉（PG110-18）。

Goals 不再有自己的内置插件名单，插件调 Goal 动作和调别的动作一样只过这道网关（PG-006）。

公共后台 Agent 只在本插件获准的 concurrent command 或保留 job 内启动；
项目、角色与安装由当前激活确定，原调用取消、插件停止和超时均取消所创建运行，迟到结果不写插件数据（SYS-15-A1～A3）。

#### 权限交集

插件权限：清单声明和安装授权**两样都要**才能用一项能力；

权限只算声明与授权的交集。

本地用户在网页里调插件动作时，授权读自登记里 `plugin_install_id` 指的那份运行中的安装：宿主手写装配、与插件同名的提供方拿不到该插件的任何安装授权（`actions.forbidden`），已停止的插件的授权立即失效。页面路由给人的调用一律经 `bindLocalWebActions`，路由写下的权限不直接交给动作网关（PG-008）：宿主自己登记的提供方以它为上限、按人对该提供方持有的到达，运行时插件的动作只按它的安装授权到达，路由写下什么都不给它加授权；成果库（含各类型主人的预览、比较、继续与引用方查询）、项目内引用、Goal 页与片段里的成果读取、置物架设置、项目上手都是这样，运行时插件的动作只按它的安装授权到达，撤掉的在路由这一层就是 `actions.forbidden`；还留着手写权限的：Goals 自己的动作（`bindGoalsWebActions`、个人计划），随 Goals 的 S12 改；Alchemist 不迁、要删（BL-376）；插件创作台不迁（BL-377）。
Plugin Runtime 登记的提供方（带 `plugin_install_id`），不论内置与否、清单 `kind` 是什么，都只按这份授权：本人对宿主自有插件的权限（`LOCAL_OWNER_PERMISSIONS`）只对宿主自己登记、背后没有安装的提供方起作用，目录里带 `runtime` 的条目也不算进这份权限；
插件路由自己声明的权限只对照路由背后那份安装的授权（`plugin-route-operations.ts` 派发时现读），不论谁来调、调用者自己带着什么权限；
经路由调到的动作，调用者能不能调由动作层照常判断。
撤掉安装的授权后，网页路由与已经建好的调用上下文的嵌套复查（`validate_authority`）都拒绝（`actions.forbidden`）。

插件的模型服务 `services.model` 同样两样都要，读和发分开：Manifest 声明了只读的 `model:read` 或 `model:invoke` 才有这项服务；
列模型（`choices()`）、问能不能用（`availability()`）要二者之一既声明又由安装持有，两样都不持时 `choices()` 被拒（`plugin.grant_denied`）、`availability()` 答 `actions.plugin_permission`；
`model:read` 发不出请求。
发请求（`complete()`）只认 `model:invoke`，并且只在插件自己的动作里放行：动作声明了 `model:invoke` 且 `scheduling: "concurrent"`、安装持有 `model:invoke`、实例在运行，宿主按它自己记下的“正在执行的动作”判断，插件不传调用上下文；
在启动、路由、定时器、别的插件的动作、串行动作、没声明权限的动作里调用，在发出之前被拒（`plugin.model_*`），动作返回之后的调用得到 `actions.expired`；
发出前、返回后各问一次这次调用的 `beforeEffect()`，取消、撤权、停用的调用拿不到结果；
沙箱插件没有这项服务；
指令只收插件自己登记的；
同一套模型与安装授权规则用于 Home 和项目执行器。

宿主的模型起草 `agent.draft-text` 是动作（PG-035）：要 `model:invoke`，受众只有插件。
人、Agent、工作流、MCP 即使持有 `model:invoke` 也看不到、调不了（`actions.forbidden`），没有宿主发出的调用者的插件受众调用是 `host.plugin_caller_invalid`；
插件经 `services.actions.invoke` 调：Manifest 没把它列进 `consumes` 的是 `actions.forbidden`，列了却没持有 `model:invoke` 的由插件自己的动作客户端在问宿主之前拒绝（`plugin.grant_denied`），它的调用者直接拿到网关，自称带不带这项权限都是 `actions.plugin_permission`；
插件没有第二个客户端够到它（PG035-01、02：写测试时曾发现 typed 通路下没声明 `model:invoke` 的插件也能让模型起草，先补了拒绝，R8 随后把 typed 的 `services.capabilities` 整个删掉）。
指令按宿主给的插件身份查，输入里带 `plugin_id`、自带指令、空白或超过 60000 字的材料都是 `actions.input_invalid`；
被取消、撤回、插件停止的调用不问模型（PG035-04、05）。
Coding 的 `model:invoke` 是可选的，关掉以后只有提交说明与历史摘要这两处起草不可用：提交说明的路由答带码的 400，历史摘要退回 Coding 按记录整理的那一份（PG035-07）。

插件经清单的 `capabilities.consumes` 调动作时，宿主的和别的插件的都可以（用户 2026-10-14 定）：只放行清单列出的那一个动作，以插件受众、插件自己的授权去调，提供方钉在项目目录里唯一的那一个；
没列出的、受众够不到插件的、缺授权的一律拒绝，缺授权先说缺授权（`plugin.grant_denied`），不说找不到。

Runtime invokeQuery 只在当前同安装动作中沿原 caller 委托 query；
consumes/声明/grant/原允许引用任一不足拒绝，嵌套 query 不扩权，直接或替换后的 command 与后代 command 均零执行，过期 scope 及撤权/停用后不交付结果。

插件经平台调 Characters 的 `characters.list` 与 `characters.runnable`（插件受众，Coding 经它们读角色，C2）也只过这一道：Manifest 没把 `characters.runnable` 列进 `consumes` 的插件是 `actions.forbidden`，只给本人的 `characters.execution` 列进去也够不到（`actions.dependency_missing`，在插件看来没有这个动作），授权被收回之后的列了的动作是 `plugin.grant_denied`，几种都不会问到 Characters（W5-01-CODING-29、30）。

公共安装查询限定当前项目和激活，缺声明、撤权及跨安装/项目借用拒绝。

公共通知与插件业务共用精确的当前事务：通知是平台自己的队列行（`plugin_notifications`），与业务记录同事务提交或回滚；
回滚、撤权、失效句柄和只读调用不入队，来源身份由平台派生。提交之后由平台交给项目里 Manifest 声明了 `notifications.receive` 的插件（D6-2）：
调用身份是平台自己的通知身份（工作流受众加 `PLUGIN_NOTIFICATION_DELIVERY_ACTOR`），接收方拒绝其他任何调用者（工作流、Agent、人都不能冒充插件发通知）；
没有接收方、接收方没装或停用时，通知留在队列里，不丢、不写别处；投递失败也留在队列并记错误码（不记内容）。

#### 内置与信任

随宿主发布的插件（`host` 信任）与其他插件同一规则（用户 2026-10-18）：必需的权限总有，可选的按人留下的给；
它只在全新安装时拿到清单声明的全部权限（可选的默认打开），条目写了什么 `grants` 都一样；
人关掉的可选权限（设置里的开关是下一片，现在只有 `runtime.grant` 能收窄），之后的启动和跟随新构建都不打开（新构建新声明的才默认打开，记录自己那个构建声明过什么读发行物存档，读不到就不打开任何可选的），关着时用到它的动作不可用；
不是 `host` 信任的插件只拿到必需的（或安装的人确认的），需要可选权限的动作保持不可用。
**只有宿主自己的启动名单能给插件 `trust: HOST_BUILD_TRUST`**，清单和安装记录里的任何字段都不行；
`host` 信任也只给宿主自己运行的代码：`PluginRuntime.install` 对 `host` 信任 加沙箱定义一律以 `plugin.grant_denied` 拒绝，不论带不带 `grants`，所以沙箱插件的授权始终是人确认的那一份。

Home/project 重复声明、沙箱 Home 条目和冒充内置身份在开库前拒绝；
Home 的提供方、库归属只认宿主实际定义对象，网页从该条目正在运行的安装读取当前 grant，不从前缀、query 或 provider 名字推身份。
Runtime 与 supervisor 持有的是平台对该对象的视图（`platformDefinition`）：同一个对象，只有 Manifest 换成平台在交付时深冻结的副本（Manifest 不是纯数据时不换，栅栏照旧比较序列化）。宿主认身份时按视图反查出的原对象（`definitionOrigin`）；对视图或原对象做的拷贝都不算，进程内准入照样以 `plugin.in_process_denied` 拒绝。调用方之后改自己手里的 Manifest，对运行中的实例没有作用；改平台副本当场抛 TypeError（`tests/platform-manifest-snapshot.test.ts`）。

插件的 `services.ownerFiles` 只给 Manifest 声明了 `owner_files`、又在宿主启动名单上的定义（声明了却不在名单上的启动被拒，`plugin.declaration_invalid`），根必须已登记为该插件所有，条目只有声明的顶层文件与目录；
无 Home、沙箱、错误 owner 或未声明读写权限拒绝；
符号链接、硬链接、特殊节点和越出声明条目的路径不允许，创建不覆盖原文件，升级预检没有文件服务。

可信 Home ownerFiles 只从实际 definition 的冻结声明取得已登记主人根，跨 scope 共根、错 owner/权限、project/sandbox 在受管 IO 前拒绝；
严格相对路径、软硬链接、特殊节点及坏子树均拒绝。

#### 沙箱

沙箱进程没有环境变量、不能读写宿主文件、不能起子进程、不能直连网络；
超时、内存、CPU、队列、消息大小有界；

沙箱代理为一次调用发的调用者，只持有插件声明了、人也批准了的能力所要的权限（`installed-plugin-host.ts` 的 `sandboxGrants`），所以 broker 放过的调用，网关按同一份授权再核一次；
目录板在发出调用者之前，也按这次调用的那一项能力核对它在不在批准里（`catalog.ts` 的 `catalogCapabilities`），批准了一项不等于批准了要同样权限的另一项（PG110-14）；
创作台的目录板只按动作声明列出插件能申请的动作和它们要的权限（Goal 的四个动作也在其中），没开放给插件的动作列出来但不可申请，调了也被拒。
