## 1. 背景

## 2. 目标

1. Home 的 Goals 库里任一个人方法包的 `pack_json` 读不出来，`goals.planning.personal.list` 整个被拒，码 `goals.storage.record_unreadable`、kind `internal`，不返回少一个的列表；错误不带存的文本、方法 id、列名、表名（`RAC-1495`）。
2. 同样的库里，`goals.planning.personal.save` 无论存的是坏行的 id 还是新 id 都被拒，同一个码，库里每一行逐列不变（`RAC-1496`）。
3. 报错不动数据：人工把坏行改回合法 JSON 后，`list` 读回全部个人方法包，没坏的那些与保存时返回的相同（`RAC-1497`）。

- 不改项目库的读取（`repository.ts` 里除了 `parseJson` 前加 `export` 之外一个字不动）和治理一侧的 `governance/mappers.ts:14-29`：T-025 的。
- 不改项目侧把 Home 的任何读取失败都报成 `personal_unavailable`（`runtime-ports.ts:110-112`）：那是另一份合同，要定「原样透出」还是「带上原因」。记 BL-819。
- 不加删除、修复、隔离坏行的动作或页面，不写维护脚本：修就是维护人员直接改库里那一行。去向：不做；用户要产品内修复再另开。

- 不让 `save` 只读自己那一行：它读全表是现状，本单不改读法（理由见第 5 节）。去向：不做。
- 不校验方法包的形状（字段是否齐全）：本单只管 JSON 读不读得出来，合法 JSON 但形状不对的，和项目方法包一样照旧放过。去向：不做。

## 5. 做法

统筹已定的决定，照做，不另选：

1. **读到一行读不出来，整个 `list()` 抛 `goals.storage.record_unreadable`，不跳过那一行。** 跳过就是悄悄丢掉一个方法，正是 T-025 改掉的；项目方法包（`repository.ts:195-201`）已经是这样。
2. **读取口径与项目方法包完全一样，用同一个 `parseJson`，不开第三份。** 一条规则只写一处；`repository.ts` 与 `governance/mappers.ts` 里已经各有一份，不再多一份。合法 JSON 文本 `null` 仍被 `.filter` 去掉，和项目方法包一致。若 `export` 让 `pnpm boundary:check` 或 `check-health-gates.mjs` 的数字变大，改成在 `personal-methods.ts` 里写一个同口径的本地函数，抛 `goalErrors["goals.storage.record_unreadable"]`（`module/planning/engine.ts:1` 与 `event-adoption.ts:1` 同样从 `../errors.js` 取 `goalErrors`），PR 里写明，不必停下问。
3. **`save` 读全表的写法不变。** 它要读旧版本才能算下一版，读不出来就不能当它不存在，所以任一行坏了，保存任何个人方法都被拒；今天这样保存会把版本号重置并覆盖坏行。改成只读自己那一行是另一件事，不在本单。
4. **修复是维护，不是产品。** 坏行由维护人员改库，本单不加入口、不写脚本；存量数据由维护改成现行形状，读取不兜底，是 AGENTS 的现行规则。副作用要在 PR 正文写明：今天重新保存同一个方法会「顺手修好」坏行（并重置版本号），改后不会，修复只剩改库这一条路。
5. **错误码与文案沿用 T-025。** 不带位置信息；`internal`。
6. **用户可见的后果接受（统筹 10-28 定：与 T-025 给项目方法包定的同一口径，AGENTS「读取时不兜底」），写进 PR 正文，不做缓冲：** 读坏后，个人规划设置页答 400 带那句固定文案，项目里读个人方法的规划调用被拒（报 `personal_unavailable`），直到维护人员修好那一行；以前是悄悄少一个方法，用户看不出来。
7. **测试放新文件，不放进 `goals-stored-json.test.ts`，也不改 `ci-product-subset.txt`。** 前者靠「纯内存、几秒」进了子集，这里要起 Host；后者 T-041 锁着。
