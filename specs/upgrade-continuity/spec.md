# 升级后持续可用

状态：需求已整理（2026-11-02），尚未实现。用户装上新版本后，旧的 Home、库、插件和保存的引用都接着能用，只感觉到功能变多了。代码照样会迭代、会有不兼容的改动，但不兼容由平台在升级时消化掉，不交给用户。排进[路线书](../post-anticorruption-roadmap/spec.md) 3.5 节。

验收编号见 §9，前缀 `UPG`。

## 1. 要解决的问题

对照 main `2a582a2e9` 的现状：

- **库的版本不对就拒绝。**
  - `packages/storage/src/sqlite-baseline.ts` 的 `applySqliteBaseline` 见到别的版本就抛 `SqliteSchemaVersionError`，提示「不就地升级……备份后移走这个库让它重建」；
  - 25 个文件里有 55 处调用 `applySqliteBaseline` 或 `openBaselineHomeSqlite`，全部照此办理；
  - 目录库、会话库等自管版本的库也一样（[C 端就绪方案](../repository-anti-corruption/c-end-readiness.md) F5）。
  - 所以开发期间，任何改了库版本的构建，对旧 Home 都是「打不开」。用户说这种事经常遇到。
- **合同一改形状，旧引用就失效。**
  - 工作流程步骤、Characters 草稿、MCP 客户端、Skill 里固定的 `capability@version`，在动作改形状后要么找不到，要么报错；
  - 插件按 `host_api_version` 声明自己要哪一版宿主，宿主不再认旧的，插件就起不来。
- **更新没有演练。** 桌面端只在内置版本比 Home 里的新时，才把运行时装进 Home（c-end-readiness F3）。新程序装上以后才发现库升不了，这时旧程序已经被换掉了。
- **已经有的部分：**
  - 插件自己的表被拒绝时，只停这个插件在这个项目里的实例，不拖整个项目（`packages/contracts/src/platform/plugin-database.ts:214`）；
  - 有离线快照命令 `molis-work home snapshot`（`apps/cli/README.md`）；
  - 有插件回放工具 `scripts/replay-plugins.mjs`：存量插件样本能加载、按 `upgrade_compatibility` 升级、能调用；
  - 合同的读取兼容流程已经写进[合同变更流程](../../docs/system/CONTRACT-CHANGES.md)第 4 节，从「阶段二起点」生效；
  - [C 端就绪方案](../repository-anti-corruption/c-end-readiness.md) C-2 设计了库的升级链，C-3 设计了自动更新。

本书把这些合成一个用户能感觉到的承诺，补上缺的几块，并把库的起点提前。

## 2. 承诺

1. **升级永远往前走，不需要用户动手。** 任何一个发布过的版本（从统一起点算，§3），都能直接升到最新版，中间不要求用户导出、重装、移走库或重建项目。
2. **新程序在确认能升之前，不替换旧程序。**
3. **升不了的，只影响它自己。** 一个库或一个插件升级失败，只有它的主人暂时不可用，并说明原因、给出出路；其余照常。
4. **保存的东西不悄悄坏。**
   - 固定的引用、工作流程、Skill、外部 Agent 的 MCP 调用：能自动接上的就接上；
   - 接不上的，在用到时、在原处告诉用户要重选什么，不会悄悄换成别的，也不会悄悄失败。
5. **随时能回到上一版**：一条命令，或设置里的一个按钮，回到升级前的程序和数据。
6. **用户感觉到的只有新功能。**
   - 升级在启动时完成，耗时长的显示一行进度；
   - 需要用户做的决定（重选模型、确认新授权），放到用到时再问，不挡启动；
   - 更新说明只写新功能和要知道的变化。

## 3. 起点：库从统一起点开始升级链

**用户 2026-11-02 同意。**

- 对抗式审查第五遍定了：所有版本收敛到初始，阶段一里动作与 Manifest 改形状时不升版本，直接在原版本上改（[报告](../../docs/reviews/adversarial-review-2026-11-01.md) §18.6）。
- 库不走这条：库的结构变了而版本不升，旧库会被当成新库打开，比拒绝更糟。

所以分开：

| 对象 | 从什么时候起不再让用户卡住 | 规则 |
| --- | --- | --- |
| Home 里的库与带版本的文件 | **统一起点**：真实 Home 清空重建、各库回到第 1 版的那一次 | 改结构必升版本，并带一段 `n → n+1` 的升级；不再「拒绝后重建」。开发用的 Home，包括用户自己的，从此也是升级，不再重建 |
| 动作、Manifest、MCP 工具名、`host_api_version` | **阶段二起点**：第一个装到开发机之外的版本，即 M1 | 阶段一在原版本上直接改，旧引用按现行 schema 明确失败；阶段二起按 §5 的过渡期 |
| 插件自己的表 | 跟随插件自己的版本：内置插件从统一起点算，装上的插件从它第一次安装算 | 插件声明自己的升级，平台执行（§4.4） |

落地时同一批改：
- [合同变更流程](../../docs/system/CONTRACT-CHANGES.md) §3 第 4 条（「改建库基线并升结构版本，版本不符的库被拒绝……不写迁移链」）；
- `AGENTS.md` 的「存量数据由维护改成现行形状」；
- c-end-readiness C-2 第 1 条的起点。

## 4. 库与数据怎样升

### 4.1 升级链

- 每个库的基线从「版本 + 建库语句」扩成「版本 + 建库语句 + 按序的升级段」。这是 c-end-readiness C-2 第 2 条的机制。
  - 版本低于当前：在一个事务里依次执行升级段，再写版本号；
  - 版本等于当前：照旧检查结构；
  - 版本高于当前：见 §4.3。
- **升级段只往前**，每段说清自己做什么：加表、加列、回填、改约束、删表。
- **破坏性的改动先扩后收：**
  - 这一版加新列或新表，读写都转到新的，同时回填；
  - 下一版再删旧的。
  - 这样任意一版回到上一版时，上一版的程序仍然能读。
- **带版本的文件**，比如 MCP 工具偏好、Shelf 目录、密钥文件、安装清单，走同一个接口。
- **密文与密钥跟着数据一起升**：换密钥派生或命名空间时，升级段用旧钥匙读、新钥匙写，不留下读不出的块。正是对抗式审查 N36、N37 那类恢复层要消灭的情况。
- **几个库之间的顺序**：
  - 写一份升级记录：要升哪些库、升到哪一步；
  - 中断后，从记录接着做，或者整体回到快照（c-end-readiness C-2 第 4 条）。

### 4.2 保护

- **先快照，再升级。** 只快照要动的库，用离线快照的同一套做法（SQLite 备份接口，带清单与摘要）。
- **升级后先检查，再交出去：**
  - `integrity_check`、外键检查；
  - 结构与新基线逐表一致；
  - 主人插件声明的业务检查，比如关键计数不减少。
- **失败自动回到快照。** 这个库的主人显示「暂不可用」，写明原因，并给两条路：「回到上一版」和「发送诊断」；其余照常。插件表现在已经只停这个插件，本书把同一做法推广到平台自己的库。
- 升级由常驻宿主在维护态做：一个 Home 只有一个执行进程，其他入口等它做完。

### 4.3 遇到比程序新的库

用户退回旧程序，或者两台机器的版本不同步时，会遇到比当前程序新的库：

- 只拒绝这个库，不拒绝整个程序；
- 主人显示「这份数据来自更新的版本」，给出「更新到最新版」；
- 不尝试读，也不改写它。

### 4.4 插件的数据

- **声明升级段。** 插件在 Manifest 的 `databases` 声明里，给自己的表写升级段；平台按 §4.1、§4.2 执行。插件不自己开库升级。
- **跨版本升级。** 插件包的版本跨越时，走已有的 `upgrade_compatibility`：
  - `compatible_from_versions` 直接接上；
  - `migratable_from_versions` 加 `validateUpgrade` 检查，再执行升级段。
- **装上的第三方插件**同样适用，不分来源（插件同等待遇）。

### 4.5 不由我们控制的存储

- Prologue SDK 自己的存储（会话、记忆条目），它的格式变化由上游保证能往前升。
- 每次换 Prologue 包，都要用金样 Home 回放（§6）；回放不过，就不换包。

## 5. 合同与保存的引用

从阶段二起点起：

- **过渡期，新旧并存**（合同变更流程第 4 节）：
  - 动作的新形状用新版本，旧版本继续可调用到过渡期结束；
  - 旧输入由平台映射到新形状，写入只产生新形状。
- **保存的引用自动接上：**
  - 工作流程步骤、Characters 草稿、保存的操作面里，固定的 `capability@version`，过渡期内照常工作；
  - 平台能证明映射无损的，在升级时直接改写成新版本，写一条记录，用户不用动手；
  - 不能证明的，在用到时提示重选，并说明哪里变了。
- **外部 Agent 与 Skill：**
  - MCP 工具名与参数在过渡期内保持旧形状可用；
  - 工具描述里写上「将在某版停用」，更新说明的「升级须知」写一条。
- **插件与宿主：**
  - 宿主至少接受上一个 `host_api_version` 的插件；
  - 更旧的插件，在插件列表里显示「需要更新」，并给出更新入口，不在启动时报错。
- **门禁：**
  - 阶段一的「版本全是 1」检查（对抗式审查 N41），到阶段二起点改成「过渡期登记表里有的才许大于 1」；
  - 每段过渡期有删除条件（合同变更流程第 4 节第 5 条）。

## 6. 证明：金样 Home 与回放

- **每个发布版本留一份金样 Home：**
  - 发版时用那一版的代码和种子数据，生成一个 Home：所有库、带版本的文件，以及一个装上的第三方插件样本；
  - 数据是合成的，不含真实内容；
  - 和发布物一起存，带清单与摘要。
- **统一起点就留第一份**，从此每次发版加一份。开发期间的大改（每次升了某个库的版本）也可以留一份中间样本。
- **CI 回放：**
  - 每份金样都升到当前代码；
  - 跑一组读写用例：现在 `tests/action-read-compatibility.test.ts` 的做法，扩到全部库和全部金样；
  - 再跑插件回放（`scripts/replay-plugins.mjs`）；
  - 金样数量多了，挡合并的作业只回放最近几份，全部金样交给定时作业。
- **门禁：**
  - 改了建库语句却没有升版本、没有升级段的 PR，失败；
  - 升了版本却没有对应回放通过的，失败。
  - 发布检查单 §3 的版本表由代码生成和核对（`scripts/verify-release-versions.mjs` 已做了表与代码一致这一半）。
- **换 Prologue 包与发布前**，都用全部金样回放。

## 7. 更新与回退

- **先演练，再切换**：
  - 下载新版后，新程序在后台对当前 Home 的一份副本跑完整升级和检查，不碰正在用的 Home；
  - 全部通过，下次启动才换上新程序、对真 Home 升级；
  - 没通过，就留在当前版本，记下诊断，等修好的版本。
- 自动更新本身照 c-end-readiness C-3：Tauri 的更新器，提示「重启以更新」，可以延后。演练是加在它前面的一步。
- **回到上一版**：
  - 保留上一版程序和升级前的快照，一条命令或设置里一个按钮恢复两者；
  - 回退后，按 §4.3 处理比程序新的库：这时快照已经恢复，所以不会出现这种库。
- **长时间不更新的用户：** 从任何一个发布过的版本都能一次升到最新，升级链依次执行；不要求先装中间版本。
- **最后的兜底：**
  - 一份稳定、带版本的整份导出格式，任何版本都能导出，新版本都能导入；
  - 它和定时在线备份（c-end-readiness C-4）是两件事：导出是给人的，跨机器、跨大版本都能用。

  - U2 与 U1 同时做：先留金样、写回放，等机制合入再开门禁；

- **冲突面：**
  - U1、U3 动宿主启动和打开库的地方，是规则 4 的热文件，与别的宿主改动一起落；

  - 个人同步（G 轨）的两台机器可能版本不同，同步协议要接受上一版客户端；按 §4.3 处理更新的数据；
  - 换 Prologue 包的窗口（规则 2）要先过金样回放。

## 9. 验收标准

1. **UPG-01** 统一起点之后，改了任何库的建库语句，必须升版本并带升级段，否则门禁失败。
2. **UPG-02** 版本低于当前的库，打开时在一个事务里依次升级到当前版本，结构与新基线逐表一致。
3. **UPG-03** 升级前对要动的库拍快照；升级或检查失败时，自动回到快照，库的内容与升级前逐字节一致。
4. **UPG-04** 一个平台库或插件库升级失败时，只有它的主人显示「暂不可用」，说明原因并给出「回到上一版」「发送诊断」；其余插件与页面照常工作。
5. **UPG-05** 遇到比程序新的库，只拒绝这一个库，显示「这份数据来自更新的版本」，不读、不写；程序其余部分照常。
6. **UPG-06** 几个库一起升级时中断（杀进程），下次启动从升级记录接着做，或整体回到快照，不会出现一半新一半旧还被当成可用。
7. **UPG-07** 带版本的文件（MCP 工具偏好、Shelf 目录、密钥文件、安装清单）走同一个升级接口，有同样的快照与回退。
8. **UPG-08** 换密钥派生或命名空间的升级段，用旧钥匙读、新钥匙写，升级后没有读不出的密文，也不留第二套恢复层。
9. **UPG-09** 插件在 `databases` 声明里写的升级段，由平台执行；装上的第三方插件与内置插件走同一条路。
10. **UPG-10** 统一起点的金样 Home 存在，以后每次发版加一份；CI 把每份金样升到当前代码，读写用例与插件回放都通过。
11. **UPG-11** 换 Prologue 包的 PR，必须过全部金样回放。
12. **UPG-12** 新程序在副本上演练升级，通过之前不替换旧程序；演练失败时留在当前版本，并记下诊断。
13. **UPG-13** 「回到上一版」恢复上一版程序与升级前快照，回退后程序能正常打开全部数据。
14. **UPG-14** 从最早的金样一次升到最新，不要求先装中间版本。
15. **UPG-15** 阶段二起，动作改形状升了版本，旧版本在过渡期内照常可调用；旧输入映射到新形状，写入只产生新形状。
16. **UPG-16** 平台能证明映射无损的已存固定引用，升级时自动改写到新版本并留记录；不能证明的，在用到时提示重选并说明变化，不悄悄失败。
17. **UPG-17** 宿主接受上一个 `host_api_version` 的插件；更旧的插件在列表里显示「需要更新」，不在启动时报错。
18. **UPG-18** 阶段二起点当天，版本门禁从「全是 1」换成「过渡期登记表里有的才许大于 1」。
