# Molis Work 人类友好信息与操作体验

## 背景与目标

Molis Work 已能保存完整的 Goal、关系、风险、执行和复核事实，但默认页面仍要求用户理解
Contract、Claim、Run、Evidence、Review、Candidate、Rewire、Policy 等内部对象。Goal 详情的同级模块过多，
待决定事项先展示类型而不是用户要回答的问题，终端与所属 Goal 的边界也不够持续、明确。

本任务让用户进入 Goal Tree、Goal 详情、待决定或终端后，先看懂三件事：现在要做什么、具体怎么做、
这代表什么。所有说明都从既有事实派生，不建立第二套状态，不替用户决定，也不删除完整记录。

Molis Work 中的父 Goal 是“让 Molis Work 清楚说明当前要做什么、怎么做和意味着什么”，按已确认依赖依次完成：

1. 统一的人话状态与行动说明；
2. Goal Detail 信息架构；
3. 待决定完整流程；
4. Goal 绑定终端与父 Goal 子项入口。

## 当前行为与问题证据

- `src/web/render.ts` 的工作状态名称、详情下一步、待决定标题和终端提示分别硬编码，同一事实可能出现不同说法。
- Goal Detail 曾把概览、目标说明、完成要求、进展和技术记录连续铺开；页面又长，模块边界和当前任务都不清楚。
- 默认正文直接出现 Claim、Run、Evidence、Review、Policy 等词，技术记录与用户任务争夺注意力。
- 待决定记录以 Contract Proposal、Candidate、Rewire、Human Review、Risk 为主标题，按钮与后果说明不足。
- 待决定表单依赖浏览器原生 `required` 校验；必填理由为空时，提交事件不会执行，页面也没有内联说明，用户会看到“点击保存没有反应”。
- 风险决定表单会默认选中风险的当前状态（通常是“暂不处理，继续跟踪”），并允许直接保存。真实操作中服务器因此成功收到一次 `open → open` 的无变化更新：记录更新时间改变，但风险仍留在待决定列表，用户会误以为自己确认的“已处理”没有保存。
- 项目作用域页面的决定成功回执曾把已经包含项目路径的 Goal 链接再次加上项目路径，形成重复的 `/projects/.../projects/.../goals/...`，导致“返回 Goal”这个闭环入口失效。
- Runtime 已整理好的原生 Goal Tree 提案没有进入“待决定”统计和列表；对应 Draft 仍提示“继续回答关键问题”，用户看不到其实只差确认方案。
- 原生 Goal Tree 提案已经进入待决定后，父 Goal 的权威数据仍应在采用前保持 Draft；但 Web 继续把它标成“目标待澄清”，并展示“这条 Goal 还没说清楚”和多项空字段。用户因此无法区分“还要继续和 Runtime 澄清”与“方案已经整理好，只等我确认”。
- 原生 Goal Tree 提案进入待决定后，默认展开全部关系和变更，长方案会把理由输入和选择按钮推到首屏之外；用户看懂问题后还要继续寻找操作入口。
- 所有 Goal 默认都渲染可开终端的第三栏；复合父 Goal 曾只在 `waiting_children` 时禁止直接开工，子 Goal 全部完成后父 Goal 转为“已完成”，门禁随状态消失，又错误地允许添加终端。
- Goal Detail 的“子 Goal 进度”对任何有子 Goal 的父级都声称“子 Goal 全部完成后自动完成”，没有区分已经确认由子 Goal 共同完成的 `closed_compound`，与仍在拆解的 `abstract / frontier_open`。真实项目因此出现“现有子 Goal 全部完成，但父 Goal 仍待澄清”，页面又同时承诺会自动完成的矛盾信息。
- 终端标签保存了 `goal_id`，但栏头和连接状态没有持续显示 Goal 名称与状态，也没有明确的父 Goal 只读表现。
- TUI 外层虽然占满工作区，但隐藏父 Goal 提示后，黑色终端被自动排到固定高度行，最后的剩余空间成为大块空白。
- 执行结果已经提交、但执行占用尚未释放的短暂交接窗口，会被错误解释成“这个 Claim 没有未结束的 Run”。这既不是工作失败，也不是用户可处理的阻塞，却把 Claim、Run 和 Runtime 直接暴露在 Goal 详情中。

## 范围

- 为全部可见工作状态提供中英文的名称、含义、下一步、行动方法和主操作文案。
- 为五类待决定事项提供用户问题、建议完整性规则、选择及后果的统一表达。
- Goal Tree、Goal Detail、Decision Center 和 TUI 复用同一只读解释模块。
- Goal Detail 改为四个职责清楚的任务入口，一次只展示一个：
  1. 概览：下一步、状态和目标说明；
  2. 完成要求：完成标准、工作边界、子 Goal 和前置事项；
  3. 进展与阻塞：执行、依据、检查、阻塞和风险摘要；
  4. 完整记录：ID、关系、执行记录、风险、规则和历史。
- Decision Center 按所属 Goal 和阻塞影响组织，每项先问问题，再给原因、建议依据、前后变化、选项后果和结果回执。
- 风险决定不再预选当前状态；用户必须明确选择一次处理结果。保持现状的选项要直接说明仍会造成的阻塞，没有选择时在表单内提示并聚焦选择框。
- 原生 Goal Tree 提案归入“目标说明”：展示整份方案的结果、关系变化和完成条件，并允许用户明确采用整份方案或退回修改；Draft 的下一步同步改为处理这项决定。
- Draft 已有待确认的目标说明或 Goal Tree 方案时，Web 从现有提案事实实时显示“等待你确认”；Goal Tree、Goal Detail 和终端上下文使用同一解释。该展示不改写 Draft，也不新增可持久化状态；提案采用、退回或失效后自动回到真实工作状态。
- “等待你确认”的详情首屏不再同时声称目标没说清楚，也不把原草稿的空字段伪装成当前方案内容；它明确说明正式 Goal 尚未更新，并把用户直接带到待决定中的整理后方案。
- 长 Goal Tree 方案默认只展示结果和变更数量，具体变更、范围与完成条件按需展开；发生冲突时自动展开冲突项，避免隐藏阻塞。理由和选择因此紧跟在方案摘要之后。
- 终端持续显示所属 Goal；任何由子 Goal 共同完成的复合父 Goal 都不新建执行终端，改为子 Goal 选择器；历史父级终端始终只读。该规则绑定 Goal 的拆分结构，不依赖“等待子 Goal”这一临时状态。
- 父 Goal 使用一套明确的完成规则：只有用户已经确认 `accepted / closed_compound` 的父 Goal 才在所有生效子 Goal 完成后自动完成；`abstract / frontier_open` 表示拆分仍可能有遗漏，即使当前子 Goal 全部完成也只进入“待确认父目标”，需要确认现有子 Goal 已覆盖整个目标后才能收口；标记为独立叶子却仍有子 Goal 时显示结构需要修正，不猜测完成。
- “待确认父目标”的主路径是在该父 Goal 中核对现有子 Goal 是否覆盖结果、范围和完成要求：覆盖完整则提交复合父 Goal 收口方案，仍有遗漏则继续补子 Goal。它与已有待确认提案的“待你确认”是两种不同状态。
- “待确认父目标”也是 Runtime 的优先续办项：Available 必须明确标记并排在普通工作前。用户下次说“继续推进/领取下一份”时，Runtime 优先领取该父 Goal 的 clarifier 工作，先确认现有子 Goal 是否覆盖整个父目标；确认完整后再提交 `accepted / closed_compound` 收口方案，否则继续补充遗漏子 Goal。
- 用户或 Runtime 发现会让完成结论不成立的异常时，Skill 必须先查关联 Goal 和现有工作：当前验收失败则保持 Goal 未完成并记录失败依据或真实阻塞；已有 Goal 已覆盖则更新其下一步；需要独立交付或验收则提出纠正 Goal 并关联原 Goal；已经发生的问题不能只登记为未来 Risk。规则要覆盖设计、内容、研究和运营等非代码任务。
- 执行、复核和重新验证的交接窗口必须按最近一次真实结果解释：结果已提交时显示正在进入检查，失败或放弃时说明工作已经停止及下一步；只有从未开始推进的异常占用才显示需要恢复或结束。默认文案不出现 Claim、Run、Runtime。
- 工作台和黑色终端区域占满视口剩余高度；终端默认展开/收起逻辑保持不变。
- 更新产品和设计说明、自动化测试，并进行桌面和移动端浏览器验收。

## 非目标

- 不修改 Goal、Decision、Risk、Review 或权限的权威语义。
- 不新增 Runtime 协议字段，不重绑已有终端，不自动领取、发送或执行。
- 不静默改写用户或项目已经保存的正文。
- 不替换现有视觉语言，不把页面改成卡片墙，也不删除审计数据。
- 不开发本次体验闭环之外的新功能。

## 用户场景与主要路径

1. 用户在 Goal Tree 选择一项，详情第一屏直接说明当前情况、唯一下一步、如何操作和为什么还没完成。
2. 用户从 Goal Detail 的待决定提示直达该 Goal 的具体事项，理解问题、依据和每个选择的后果；提交后看到结果和下一步，并能回到原 Goal。
3. 用户点击由子项共同完成的父 Goal，只看到子 Goal 的完成、可开始、被挡住或待决定状态；无论父 Goal 正在等待还是已经完成，都要进入具体子 Goal 后再查看或打开它自己的终端。
4. 用户在任意终端中始终看到所属 Goal；切换页面不会改绑终端，跨 Goal 推进会被拒绝并指向正确入口。
5. 需要审计时，用户进入“完整记录”，仍能找到原始类型、ID、策略来源、执行记录、证据、复核和事件账本。

## 方案与关键决策

### 统一解释来源

新增无状态的 Web 展示模块，只消费 `GoalWorkState`、现有阻塞理由、Goal 标题和决定事实，输出：

- 人话状态名；
- 这代表什么；
- 用户现在要做什么；
- 如何继续；
- 结果导向的操作文字。

它不保存状态，也不猜测建议。建议只有在记录含有可追溯理由或证据时显示；否则明确说“现在没有足够依据推荐某个选择”，并指出缺什么。

### 信息归属与渐进展开

- “概览”是默认入口，承载下一步、当前状态、一个主操作、阻塞和目标说明。
- 验收、范围、子 Goal 进度和硬依赖只在“完成要求”完整展示。
- 当前执行者、最近进展、证据、复核、风险和规则摘要只在“进展与阻塞”展示。
- 原始内部对象、ID、策略编辑、关系管理、完整历史和事件账本进入“完整记录”。关键阻塞和风险摘要仍在日常入口可见。
- 状态名使用简洁、专业的短标签，例如“目标澄清中”“执行受阻”“待复核”；解释和操作方法在需要时使用完整句子。
- 阅读态与编辑态分开；默认层只有一个最重要的主操作，管理动作保持次要。

### 待决定与终端

- 五类决定的主问题分别是：Goal 是否已说清楚、新工作是否加入 Goal Tree、Goal 关系是否调整、结果是否达到完成标准、风险要处理/接受/暂缓。
- Runtime 一次整理出的 Goal Tree 方案仍属于“Goal 是否已说清楚”这类决定，不另造一套用户概念；页面把整份方案及其中的 Goal、关系、依赖和规则作为一个可理解的决定呈现。
- 选择按钮写结果，不使用脱离对象的“确认、处理、继续”；提交后回执说明改了什么、没改什么、下一步和返回入口。
- 终端栏头、标签和连接/只读状态显示所属 Goal。服务端仍以现有 `panel.goal_id` 为边界，写入目标不一致时拒绝。
- 复合父 Goal 的第三栏始终变为子 Goal 导航。历史父级面板只允许查看，不允许推进、填入、重新打开或新建；父 Goal 自动完成后规则不变。

## 输入、输出与依赖

- 输入：现有 Goal、派生工作状态、阻塞理由、关系、子 Goal、风险、决定、执行记录、证据、复核、终端面板绑定和当前语言。
- 输出：同一套中英文解释、重组后的 HTML、决定结果回执、Goal 归属终端状态和回归证据。
- 依赖：`src/v1/types.ts` 的权威状态与记录、`src/web/server.ts` 的 Web View、现有项目作用域路由、现有 PTY 面板和控制令牌。

## 文件与模块边界

- `src/web/human-language.ts`：统一工作状态和决定类型的人话说明；无持久化、无副作用。
- `src/web/render.ts`：Goal Tree、Goal Detail、Decision Center、TUI 的结构和样式。
- `src/web/server.ts`：只补足渲染需要的现有事实、父 Goal 终端门禁和决定回执上下文；不改变领域状态机。
- `src/web/pty-client.ts`：展示终端所属 Goal、只读父级状态和客户端操作门禁。
- `tests/i18n.test.ts`、`tests/web.test.ts`、`tests/desktop-tui.test.ts`：中英文、页面结构、操作路径和边界回归。
- `PRODUCT.md`、`DESIGN.md`：记录最终信息归属、主要路径和终端规则。

## 验收标准

- 全部工作状态在中文和英文下都有非空的“代表什么、现在做什么、如何继续”，四个主要界面使用同一来源。
- 按钮说明操作结果；错误、空状态和冲突同时说明发生了什么及下一步；文案短、直、具体，不使用口号、隐喻、咨询术语或名词堆叠。
- 待决定缺少必填理由时，在表单内明确指出缺什么、把焦点放到对应输入框并允许立即重试；有效提交期间显示正在保存，成功后显示回执。
- 风险决定首次打开时显示“请选择处理结果”，不得把当前状态当作用户的新决定；未选择时不能发送请求，并明确提示“请选择风险处理结果，再保存”。选择“保持待处理”时，文案说明它会继续跟踪以及是否继续阻塞 Goal。
- Goal Detail 提供“概览 / 完成要求 / 进展与阻塞 / 完整记录”四个任务入口，一次只展示一个；每个模块只有一个职责和一句用途说明；常见状态只有一个明显主操作。
- 默认“概览”不以 Contract、Candidate、Rewire、Policy、Claim、Run、Evidence、Review、原始状态或 ID 作为唯一说明；完整事实仍可在“完整记录”查看。
- 执行结果已提交但占用尚未释放时，概览显示“结果已提交，正在进入检查”，不会把正常交接误报为技术阻塞，也不会出现 Claim、Run 或 Runtime；真正没有推进记录的异常状态同样使用用户可行动的人话说明。
- 五类待决定以用户问题为主标题，展示为什么现在决定、可靠建议及来源或证据不足、前后变化、每个选择的后果；成功、退回、冲突、过期和空状态均给出下一步并保留原 Goal 上下文。
- 决定成功回执的返回链接在项目首页和项目作用域页面都只拼接一次路径，并能回到原 Goal。
- 原生 Goal Tree 提案计入“目标说明”和总待决定数，显示在所属 Goal 下；存在待确认提案时，Goal 概览不再错误提示继续补充信息，而是直达该提案。
- Draft 存在待确认的目标说明或 Goal Tree 方案时，Goal Tree 状态和 Goal Detail 状态均显示“等待你确认”，下一步只指向该决定；页面不再出现“目标待澄清”“这条 Goal 还没说清楚”或空白目标说明。采用、退回或提案失效后，展示立即回到最新真实状态。
- 有生效子 Goal 的父级必须显示自己的完成方式。`accepted / closed_compound` 明确说明“全部子 Goal 完成后自动完成”；仍为 `abstract / frontier_open` 且现有子 Goal 全部完成时显示“待确认父目标”，明确说明不会自动完成及下一步；叶子状态与子 Goal 结构冲突时显示需要修正，不能继续给出自动完成承诺。
- 终端所属 Goal 持续可见；当前终端不能静默推进另一 Goal；切换 Goal 不改绑已有终端。
- 复合父 Goal 无论正在等待还是已经完成，都不能新建、重新打开或写入执行终端；第三栏显示子 Goal 状态与入口，历史父级标签只读。
- 工作台和终端栏占满视口；黑色终端区域占满栏内剩余高度，底部只保留设计内边距；终端默认展开逻辑不变。
- 桌面、窄屏、键盘和减少动态效果下保持相同阅读顺序和可操作性。
- 原始 Goal、关系、风险、策略、证据、复核、ID 和事件记录没有丢失。

## 假设与开放问题

- 现有 `GoalWorkState` 仍是唯一工作状态；人话说明只是派生视图。
- 既有 Decision API 的实际结果和权限语义保持不变，回执根据真实响应生成。
- 风险建议只有在记录里存在可追溯处理理由时才显示；没有依据时不伪造推荐。
- 目前没有必须在编码前由用户补充的产品选择；视觉和内容取舍以“更快找到下一步且不丢关键事实”为准。
