# T-032 安装不在 running 时，停用和曝光失败清理不再被 `plugin.state_invalid` 拒绝

> **先看：任务来源的说法在 main 上只对一半。**
>
> - 停用成立。`apps/local-host/src/installed-plugin-lifecycle.ts:163` 的 `runtime.stop` 遇到 `crashed`、`quarantined`（`installed` 也一样）会抛 `plugin.state_invalid`（`packages/plugin-runtime/src/index.ts:496-498`），后面的 `registerPrompts(…, 'disabled')` 不执行，`lifecycle('disable')` 以这个错误拒绝。
> - 曝光失败清理不成立到「安装本来就崩了」。`apps/local-host/src/installed-plugin-exposure.ts:47` 的 `current()` 要求安装是 `running`；安装事先已经不是 `running`，进不了 `:50`，走 `:51` 抛 `actions.provider_replaced`。`:50` 的 `stop` 只在安装「`current()` 判过 running 之后才变成非 running」时抛 `state_invalid`，盖住原来的曝光错误。我读代码得出两条路，**没有跑过**：一是同一把安装锁上先排着的 `reportCrash`；二是 `supervisor.revoke` 自己排的那次 `stop` 在插件的停止钩子里失败、把安装记成 `crashed`（#1340 在 `project-plugin-enablement.ts` 的注释写的就是这种）。能不能稳定造出来，由【方案】回答，造不出来按第 11 节停。

## 1. 背景

#1340 修了项目启停刷新里的同一个缺陷：`apps/local-host/src/project-plugin-enablement.ts:36`（main 上）无条件 `runtime.stop`，安装已不在 `running` 时 Runtime 抛 `plugin.state_invalid`，一次刷新带着整个页面请求失败。它的修法是只放过这一个码：`.catch` 里 `error instanceof ActionError && error.code === "plugin.state_invalid"` 才吞，别的照抛（`gh pr diff 1340`）。二审登记 3 指出 Host 里还有两处同样的无条件 `stop`，就是这个任务的两行。

核下来的事实：

- Runtime（只读，不改）：`stop()` 先同步撤掉激活上下文，再在安装锁里跑 `stopOnce`（`packages/plugin-runtime/src/index.ts:442-445`、`:493-537`）。状态 `disabled` 重放回执（`:495`）；不是 `running` 抛 `pluginErrors.state_invalid`（`:496-498`）；停止钩子自己抛则存成 `crashed`、抛 `plugin.executor_failed`（`:515-527`）。Runtime 里只有 `stopOnce` 会写 `disabled`（`:504`、`:531`），`stop` 没法把 `crashed`、`quarantined` 变成 `disabled`。
- 监督器的 `revoke`（`packages/plugin-runtime/src/supervisor.ts:267-296`）在监督器不忙、安装是 `running` 时自己再排一次 `runtime.stop`，错误吞掉（`:285-294`）。所以 `:163`、`:50` 的 `revoke` 之后，那行 `await runtime.stop` 是同一把锁上的第二次：第一次成功，状态 `disabled`，第二次重放，没事；第一次的停止钩子失败，状态 `crashed`，第二次抛 `state_invalid`。
- 停用：`apps/local-host/src/installed-plugin-lifecycle.ts:163` 依次 `c.withdraw`、`revoke`、`stop`、`registerPrompts`。`stop` 抛了，动作和授权已经撤下，提示词没有被改成 `disabled`。该文件 import 的是 `pluginErrors`（`:8`），没有 `ActionError`。
- 曝光：`apps/local-host/src/installed-plugin-exposure.ts:46-53`，`catch` 里先 `current()`（`:47`），为真才记 `recoveryErrors`、清理（`:50`），最后 `throw error`（`:52`）。`ActionError` 已 import（`:2`）。`expose` 的调用方：安装（`apps/local-host/src/installed-plugin-lifecycle.ts:112`）、启用（`:176`）、启动恢复（`apps/local-host/src/installed-plugin-host.ts:202`）；版本切换传 `'caller'`，不走 `:50`（`apps/local-host/src/installed-plugin-version.ts:32`、`:48`）。
- 两个函数不只服务项目：Home 版 `apps/local-host/src/home-installed-plugins.ts:126`、`:144` 用的是同一份 `installedPluginExposure` 与 `installedLifecycle`，改一次两边都变。
- 其余的 `runtime.stop` 调用：`apps/local-host/src/installed-plugin-host.ts:183` 关闭 Host 时只在 `state?.status === 'running'` 时调，包在 `try/catch` 里收集失败，已有保护；`apps/local-host/src/home-plugin-http.ts:111` 是 Home 插件停用路由里的同一个缺陷，被 T-005（#1345）锁着。
- 没有测试覆盖这两行。disable 的用例都从 `running` 起（`tests/installed-plugin-host.test.ts:108`、`:181`）；`:305-328` 的隔离用例只测升级、回滚被拒，状态是直接写进仓库的（`:310`），最后走卸载，没有停用。#1340 的 RAC-1120 两条只覆盖 `project-plugin-enablement.ts`。
- 重启时的处理不对称：`apps/local-host/src/installed-plugin-host.ts:195-198` 把 `disabled`、`quarantined` 当作保持关闭、提示词 `disabled`；`crashed` 走 `:201` 的 `platform.start`。读代码我判断不了「停用时留在 `crashed` 的安装，Host 重启后会不会又起来」，没跑过，见第 5 节问题 3。
- `tests/installed-plugin-host.test.ts` 整份是 `mac`（`:29`，`process.platform !== 'darwin'` 就跳过），Linux 全量和 CI 都跳过。这个任务的红和绿只在 macOS 上看得到。

## 2. 目标

1. 安装在真实 Runtime 里是 `crashed` 或 `quarantined` 时，`lifecycle('disable')` 成功返回：提示词标成 `disabled`，动作撤下，Runtime 记录的状态不被改动（`RAC-1150`）。
2. 曝光失败清理里，`stop` 因安装已不在 `running` 而抛的 `plugin.state_invalid` 不再盖住原来的曝光错误：原错误照旧抛出，`recoveryErrors` 里记的也是它（`RAC-1151`）。
3. 只放过 `plugin.state_invalid`，别的错误（含停止钩子失败的 `plugin.executor_failed`）照旧抛出（`RAC-1152`）。

## 5. 做法

**已定**

- 写法与 #1340 一致：只放过一个码，别的照抛。`:163` 的 `await platform.runtime.stop(record.install_id)` 改成
  `await platform.runtime.stop(record.install_id).catch((error: unknown) => { if (!(error instanceof ActionError && error.code === 'plugin.state_invalid')) throw error; });`
  之后 `registerPrompts(…, 'disabled')` 照常执行。`:50` 同样写，`:52` 的 `throw error` 不动，`:47-51` 的判断不动。
- 每处留一到三行英文注释，写为什么只放过这一个码：Runtime 不停不在运行的安装，别的错误是 `stop` 自己的。照 #1340 在 `project-plugin-enablement.ts` 里的注释。
- `installed-plugin-lifecycle.ts` 从 `@molis-ai/molis-work-contracts/platform/actions` 加 `ActionError`（`pluginErrors` 现在从 `…/platform/plugin` 来，`:8`）。
- 改完 `apps/local-host/src` 后，跑测试前先构建，测试读的是 `dist`：`node scripts/machine-slot.mjs run build --label "<谁> T-032" -- pnpm --filter @molis-ai/molis-work-app-local-host run build`（`--filter` 在 `run` 前）。
- 测试全部追加在 `tests/installed-plugin-host.test.ts` 末尾，用现有的 `mac` 选项、`publishedFixture`（`:33-59`）、`hostWithProject`（`:232-238`）。该文件的相对内部引用现在是 7（`tooling/gates/baseline.json:213`），只许减少。
- 状态要真，从 Runtime 里走出来：`crashed` 用 `platform.runtime.reportCrash(installId)`；`quarantined` 用恢复上限走到，照 #1340 的 RAC-1120 第二条（`gh pr diff 1340` 里 `tests/project-plugin-enablement-refresh.test.ts`）：`reportCrash` 加 `recover` 连做三次（默认上限 3，`packages/plugin-runtime/src/index.ts:570`），再 `reportCrash`，第四次 `recover` 抛 `plugin.quarantined`，状态是 `quarantined`（`:571-578`）。不要把 `:310` 那样直接写仓库的状态当 `quarantined` 的证明。
- `RAC-1150` 的断言：`await installed.lifecycle('disable', release)` 不抛；提示词状态 `disabled`（照 `:177-182`，`agentDefinitionsFor(home, builtinRegistrations)` 加 `registry.prompt(key).source.state`）；`(await installed.catalog()).some(entry => entry.id.startsWith('generated.'))` 为假（照 `:109`）；Runtime 记录仍是原来的 `crashed` 或 `quarantined`。`crashed`、`quarantined` 各一条。
- `RAC-1151` 用 `enable` 触发曝光（`:176`，`onFailure` 不传）：照 `:118-130` 直接用 `ensureInstalledPlugins` 并在 `actions.inspect` 里放钩子，让 `catalog()` 抛一个认得出的错误。

**【方案】里要回答的问题**（先在本机把用例写出来，在 main 的构建上跑到红，把结果写进去，再等批）

1. **真状态与耗时**。`crashed`、`quarantined` 各怎么造，`quarantined` 那条每次 `recover` 都会真的去启动沙箱吗；写出新增用例整体的耗时（这份文件每条用例都开一个 Home）。`installed` 状态同样被拒（`packages/plugin-runtime/src/index.ts:496`），但我没找到活着的 Host 里怎么让它停在那个状态；找到了就补一条，找不到写一句。

   **统筹预裁（10-28）**：两条都造不出稳定的红，这一次就不改 `:50`，范围缩到停用这一处，`RAC-1151` 不做。【方案】里写出你试过什么、结果如何，统筹会把 `:50` 记进零碎单。这种情况不用停下来等。

4. **`RAC-1152` 怎么证明**。把真的 `plugin.executor_failed` 送到 `:163` 或 `:50` 的 `stop` 上，要同时满足：`revoke` 没替它排停止（监督器忙，或安装已不在 `running`），且停止钩子抛错——走沙箱 Host 很难不 mock 做到。三个选项，选一个并说理：（a）找到不 mock Runtime 的办法就用它；（b）把那段 `.catch` 抽成 `apps/local-host/src` 里的小函数，用真的 `PluginRuntime`（照 `tests/security-invariants-plugin-regrant.test.ts:47-58`，停止钩子可配成抛错）证明——但测试要从包入口取它，不能新增相对 import，要动 `apps/local-host/src/index.ts` 的导出，门禁数字会变；（c）这一半不写测试，靠这三行判断本身的评审，PR 里直说。我的倾向是（a），做不到再（c）；（b）要先说清门禁怎么过。
   **统筹预裁（10-28）**：（b）不接受，因为要动 `apps/local-host/src/index.ts` 的导出。（a）做不到就用（c），PR 正文直说「这一半没有测试，靠评审」，仍按 #1340 的写法只放过一个码。
