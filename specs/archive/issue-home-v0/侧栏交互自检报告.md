### 根因证据

- 日常 Home 原工作 `work-dd917fe3-249f-4164-850d-2243578909f1` 的输入为「111」、无图。读取其 SDK 加密运行记录，六次 `ask-user` 入参的 `questions[].options` 都是只有 `description` 的对象；六次回执均为 `TOOL_ARGUMENTS_INVALID`，没有成功生成提问或确认卡。
- 当前实际 SDK 广告合同为 `options: string[]`；自由文本提问只需 `why`，省略 `questions`。Anthropic 适配器直接发送 `input_schema: tool.parameters`，拼接 `input_json_delta` 后用 JSON.parse 生成工具入参；执行器拒绝 description 对象。历史原始网络帧没有留存，因此不能声称逐帧对照过旧请求；本轮 HTTP 模型回放已核对实际收到的 schema、原对象进入后续工具记录及一次正确参数修复，未发现这条转换路径把字符串变成对象的证据。

- 补充图文的实机复测另外捕获四次相同 `suggest-action` 失败，实际 `input` 为 `""`，不是空对象。通用网关的 input 当时仅有 description、未声明 JSON 类型；原样经过 SDK 到达合同校验，没有被补成草稿字段。添加显式 JSON 类型后，同一图文和独立短描述均一次生成确认卡。该证据说明本次端到端样本改善，不推断供应商内部如何使用 schema。

### 最小修复

- 方法 v7 明确自由文本提问结构，只问缺少的一个事实，不让用户选处理方式，不要求在页面不存在的对话框中回复；不设字数门槛，明确「点保存没反应」可以生成确认卡。

## 发现与修复

1. **列表页签恢复了旧详情。** 显式点击或键盘进入列表时只隐藏详情；侧栏收起重开不执行这个跳转。修复前的回归用例确实在“列表未显示”断言失败。
2. **异步结果可能抢回详情。** 返回列表后，迟到的详情读取被忽略；已完成的保存正常落库，但不会把用户强行带回详情。再点原记录可看到最新只读内容。
3. **迟到保存的删除后续不完整。** 当新建保存期间用户切走，结果会留在录入页。从此处删除应回到空白录入，原实现会出现列表，且新整理按钮没有恢复可用。现在删除结束后可以立即继续记录，另一页签的编辑仍保留。
