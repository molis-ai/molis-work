## 给人讲清楚

界面的字体、皮肤和中英文文字现在写死在各处，想换外观或补翻译，要到处改，还容易漏。这一批先把规矩定下来：界面文字、字体、皮肤怎样登记、怎样引用，并给出完整的基础清单，同时量清楚页面加载的开销，确保换了以后不变慢。除了规矩和基础文件，还有两件事一并做：个人助理按你选的界面语言回复，选了英语，助理就回英语；再把这套写进插件开发手册和开发流程，后面新写的插件有规矩可循。做完界面基本看不到变化，但助理的回复语言会跟着你选的语言走，后面换外观、补语言也有了统一的做法。需要你做的：外观选择的样子已经定了（方案 C），页面加载的预算也定了（第一屏总字节只许变少）；还要你定的有两件：圆润字体用哪一款；`AGENTS.md` 和开发流程里新加的文字，写进去之前先给你看。

- 测一次：子分支途中只跑刚写的用例确认写对了，不跑受影响用例和浏览器批次，合回本批分支时不重测。全批写完后先同步最新 main（开发途中不同步），解一次冲突，统一构建，按全批改动挑用例，加上各包 README 的改动后必跑，一次跑完，不抽样；脚本不提示的也要跑（动共用样式跑 pnpm visual:compare，改创作台 Skill 跑 pnpm studio:replay）；页面资源按全批合计。每个验收编号都要有证据，PR 描述按编号列明，缺一项不合（需求开发流程第 8.4 节）。
- 证据分三级：工程通过、实操、本人验收，分开记。界面与体验类以我本人看实物为准；行为和工程类由统筹在隔离 Home 里走一遍，不记为「本人认可」。要我本人验收的列进 BACKLOG「待你验收」，不代我验收。
- PR 粒度：一批一个 PR。子分支不开 PR，也不开草稿 PR 占位，全批写完测完才开；本批分支和子分支照常推到远端备份（推送前 pnpm secrets:check），名字不用 integration/ 开头，推上去会触发 CI 全量；不限文件数和包数，PR 里一项一组提交、描述按项分节。只有这几种提前切出一个小 PR 先合：别的批、服务端批或别的片确实在等的合同或能力；main 红了或安全缺陷的修复；有固定窗口和授权的事（真实 Home、换 Prologue 包、发版、第 16 批的一次切换）。文档不单独开 PR：spec、决策记录、BACKLOG、批次文件的进展与合入记录都随本批 PR。门禁、脚本、CI 的改动也并进本批 PR，单独一个提交，PR 描述单列「门禁改动」一节，写清改了什么、有没有放宽（改门禁仍是第六节的红线，先问我）。依据：需求开发流程第 8.4 节、轨道规则 1。
- 最终的头：评审结论、合审、相关用例和要跑的全量，以及 health:check、boundary:check、页面资源、secrets:check，都要在最终的头上；再推就重跑受影响的部分，所以全量放在改完评审意见之后，全批只跑这一次。评审意见尽量一次提全，写手一次改完再推。开 PR 后没有冲突不再同步 main，交合并队列；别的 PR 合入了本批碰的枢纽文件，同步 main 并重跑相关用例。
- PR 按模板填，「开工前检查」一节贴检查结果和定样决定；推送前先 git fetch origin main 再跑 pnpm secrets:check；合并交统筹，你不合。
- 各项进展按下面「上报进展」更新认领板 #1743，记日期、分支或 PR、证据和剩余项；子分支合回本批分支后删掉它的工作树和分支。用户决定和 BACKLOG 删条写在本批分支上，随本批 PR 走；影响别的批的决定也写在本批分支上，只有那一批已经在等时才切出来先合。批次文件的进展与合入记录由你攒着，开 PR 前一次写进去，合入的提交号随下一批的 PR 补。本批 PR 的全 PR 评审同时是本批的收尾检查（需求开发流程第 11.1 节）：把全批改动合起来看防腐、平台能力、代码质量、清理、全局五问，结论写进本批文件；平台能力不强求，本批带来的问题在本批 PR 上修完再合。本批 PR 合入，本批才算完成，然后删掉本批分支和工作树。
- 上报进展：
  - 认领板 #1743 是进度的唯一记录：正文一项一行，评论是时间线，两者对不上以最新评论为准（需求开发流程第 2.2 节）。开工前读最新正文和该项评论，确认是「待认领」、同轨独占文件上没有别的在途写手，再改自己那一行（认领写会话与设备、状态「已认领」、更新日期），并评论「认领 NN-项名」。之后每有实质进展，当次改这一行并留评论，写本次结果、证据链接和下一步：开始定样改「定样中」，开始实施改「实施中」，子分支合回本批分支仍是「实施中」，评论记一笔；本批 PR 开出后各项改「待评审」、分支栏换成 PR 号；评审退回或卡住时状态不动，评论写清等什么、等谁；只合入一部分保持「实施中」并写余项，整项合入才改「已合入」；暂停、放弃写原因。状态只用这几种。改正文前先重新读，只改自己那一行：gh issue view 1743 --json body -q .body > board.md，改完 gh issue edit 1743 --body-file board.md。不在 01～89 行里的小修和插队，记进「小修与插队」表。超过 3 天没更新的行会被点名问。
  - 评审意见、给评审的答复、统筹的裁定都写在 PR 评论里，带上看过的提交号；PR 描述写「开工前检查」和「防腐与代码质量」两节，评审照这两节逐条看 diff。
  - 只在这几种时候给统筹发会话消息，一两句话，附 PR 号或文件位置：评审台已审过、PR 等入队（附 PR 号和头）；我定了样或拍了板；要别的轨道先落地它独占的文件；卡在要我定的事上（攒成一批）；本批全部合入。消息只发给要接手的一方，不发例行汇报，不在消息里重复认领板已有的内容。
  - 要我拍板的按第九节问，先把能独立做的做完再攒成一批；定了写进决策记录，并在 #1743 该项下评论记一笔。
  - 会话标题写成「批次｜台名·当前事项、状态」，状态变了就改名。
  - 评审退回的挡合并的点在本批 PR 上改完，写手一次改完再推；不挡合并的交小修台在本批分支上改，或记进「小修与插队」留给后面的批。

九、什么时候停下问我

十、会话、写手和模型
本批由你这个主会话独立安排（用户 2026-11-05 定，会话不再按轨道跨批）：独立的任务由你开子会话去做，写手一律用子代理，不借别的批次或旧的公共会话。任何档位都不用 max。你开的每个会话标题写「批次｜台名·当前事项、状态」，状态一变就改名。
- 你自己（Opus 5.5 high）：开本批分支、分子分支、开子会话、派写手、对账、按第八节上报进展；子分支交回后由你合回本批分支（有冲突就交回那个写手解），全批写完后同步 main、解冲突和统一测试派一个写手做（冲突跨模块的用 Opus 5.5 high），你核对后开本批 PR；把审过的 PR 号交统筹入队。批次文件的进展与合入记录由你在开 PR 前、暂停或交接时一次补（第八节），写手不改批次文件。不写产品代码，不做长走查。
- 写手一律用子代理（isolation: "worktree"），一个子分支派一个，本批可以同时有多个写手。按子分支里最难的一项挑模型：
  - 安全、沙箱、共享核心、跨模块、合同代码：Opus 5.5 high；
  - 范围清楚、跨几个文件的：Opus 5.5 medium；
  - 一般实现：Sonnet 5.5 xhigh；
  - 小而清楚的：Sonnet 5.5 high。
  写手只做派给它的那个子分支，一项一个提交，提交说明写交付项和验收编号；子分支从本批分支切出，做完合回本批分支，不开 PR、不同步 main；合同随本批 PR（tracks.md 规则 1，例外见第四节）；合同文件归 C1 独占，同一时间只有一个写手在改，改之前在 #1743 认领这份合同，已有写手在改就交它落、你的片叠在后面（轨道规则 7）；别的轨道独占的文件同样按规则 7；目标用例走 machine-slot、--jobs 1；只跑刚写的用例，不跑全量、不定样；交回前跑一次 node scripts/check-health-gates.mjs --base origin/main，门禁数字的问题当场改掉，不留到最后；做完把分支交回你。
- 子会话：本批用得上哪几台就开哪几台，各开一个，做完就收：
  - 设计台（Opus 5.5 high；新的视觉方向和大页面，即首页、Onboarding、工作台外壳，用 xhigh）：本批和下一批要定样的项；不写产品代码，不审自己的样。
  - 本批的合同台（Opus 5.5 high，只出设计稿）：本批和下一批的合同、SDK、存储、动作 schema 设计稿；不定样，不写合同代码（交写手），不做合审（合审归公共合同台）。
  - 评审台（Opus 5.5 high 审实现、合同、界面；纯文档用 Sonnet 5.5 xhigh）：本批 PR 开出后，按子分支同时开几个评审，各审一个子分支的提交范围，另开一个审全 PR：整合、冲突的解法、跨项的一致性，并做第八节的收尾检查。都照第七节审，结论按需求开发流程第 10.1 节七行逐条写，界面部分另按第五节走一遍体验；全部过了在 PR 上写「【评审台】审过（头 <sha>）」，退回写清挡合并的点，不挡合并的写成小修条目；不改被审的 PR，不入队。你不审自己派的片。收尾检查的结论由你写进本批文件。
  - 小修台（Sonnet 5.5 high）：本批的 BL 小项、评审里不挡合并的意见、文案和单文件缺陷，在本批分支上开一个小修子分支攒着做，随本批 PR 合，记进 #1743「小修与插队」；不改别的写手正在改的文件，不改合同。
