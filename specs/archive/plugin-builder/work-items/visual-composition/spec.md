# Plugin Builder：整页设计与视觉复查

状态：2026-09-29 核心功能可用：冻结前体验规划、按问题来源修复、整页呈现、独立视觉修订、隔离截图、受证据约束的视觉复查和版本兼容已实施并验证。目标仍为内部完整，尚未达标：当前真实模型的首次生成仍可能卡在合同/代码检查，视觉建议仍存在误判与未解决项，用户尚未验收。工程、真实模型和人工视觉检查的证据见末尾。工作树 `plugin-ui-composition`，分支 `feature/plugin-ui-composition`；2026-09-29 已获合入并推送 main 的授权，真实 Home 未部署。

## 当前优先级：优化 Builder 的生成机制（2026-09-29 调整）

一骏明确纠正：不要为了修 UI 而修，主要看 Plugin Builder 本身怎么优化。保留已验证的共用能力和修复，停止围绕阅读样例逐项美化。后续改动必须能解释它改善了哪个生成决策、阶段交接或失败恢复；截图用于发现跨插件的问题，不作为追求某一张画面的目标。以下是机制改造的方向；本轮已实施的范围、验证结果与剩余问题分别见执行合同和末尾记录。

当前实现与真实生成共同指出三个问题：

- **体验决定得太晚。** `detail → adopt → compose` 先冻结操作、部件、绑定和验收，再让 UI Agent 调整布局、组件 kind 和 props。后者无法减少不合理的部件拆分或操作步骤。体验规范已经进入模型请求，但原始任务、journey 和 purpose 尚不能证明这些决策做对了。
- **修复容易找错对象。** 视觉复查返回字符串意见，非空意见即可触发一次修改；实际意见多次误读截图状态或建议不存在的能力。另一侧，查询的部分匹配示例绕过空存储检查，把矛盾合同交给代码 Agent，造成持续返工。继续添加禁止条款不能替代边界检查和正确的失败归属。
- **验证内容不足以判断生成质量。** 主线的短样本可以通过功能验收，却不足以判断阅读和比较体验；长正文后来由人工补入，模型自动评审没有看过。单一样例被反复指导后的改善也不能证明新插件首次生成更好。

### 下一阶段的顺序与边界

1. **先调整设计交接与冻结时点。** 用户选定产品方案后，先围绕主任务明确入口、常用路径、主内容、主操作、完成/失败后的去向及代表性状态，再落到部件和绑定。UI 的体验判断进入完整设计确认之前；操作权限与数据合同仍由主线和宿主负责。等部件、绑定和验收引用一致后再冻结并进入代码/装配。用户选中的是产品行为，不应被解释成选定了每块表单的位置。优先复用已有设计通道和存储；是否拆分模型调用要以输入复杂度、实际耗时和质量对比决定，不默认增加常驻 Agent 或无条件多轮评审。
2. **按证据与责任修复。** 确定的合同矛盾在设计接收处拒绝，反馈具体操作及原因；实现错误回代码，组合错误回 UI，宿主能力缺口如实保留。视觉意见必须区分可定位、当前能力可实施的问题与证据不足的推断；后者不直接成为自动修订指令。结构错误仍须修复，风格偏好不增加硬性通过门槛，也不在纯视觉修订中偷偷改变业务合同。
3. **用任务覆盖验证 Builder。** 沿用阅读/浏览、频繁操作、数值比较三种需求，以相同原始需求和模型配置观察首次生成。内容须能暴露对应任务的问题：完整正文、连续操作、可比较的数值；通过正常验收路径准备数据，不直接制造预览结果。分别记录生成是否完成、主路径是否完整、首轮设计的任务适配、修复来源与次数、总耗时，以及仍需人工判断的体验问题。不规定某种布局才算好，不用字段存在、提示词已挂载或模型 reviewed 代替质量证据。

Impeccable 继续作为设计判断的来源：动线影响部件拆分，信息层级影响内容主次，动效原则影响状态连续性；不把它扩成每轮追加一份通用形容词清单。只有不同需求暴露了同一种表达缺口时，才把补齐组件能力列入本任务；单一样例的外观偏好不驱动设计系统扩展。

预计实现边界：先看 `agent-workflow.ts` 的设计接收/冻结与调用顺序、`agent-authoring.ts` 的合同输入检查、`agent-presentation.ts` 的 UI 交接和复查输入，以及对应阶段规范与生产路径测试。初始设计的部件调整必须发生在引用冻结前；既有草稿、已发布设计与「只调整界面」仍保持原有合同、后端复用和恢复语义。具体行为变更实施前在本节补齐确定的输入输出与验收，不借此改创作台外壳或重做全部渲染器。

### 本轮执行合同（2026-09-29，已获开工授权）

首次生成在用户选定方案及平台能力之后、detail/adopt 之前，增加一次有界的 `experience` 模型任务。输入为原始需求、已选产品方案、操作输入输出和实际组件能力；输出 summary、journey、pages（可增减/重组草图部件，只能引用现有操作）与 scenarios（任务、代表性内容、应观察到的结果）。主线 detail 使用这份草图建立最终绑定和验收；宿主在设计中保留 summary/scenarios 作为后续 UI 和评审的上下文，不把草图 id 当作永久合同。初始调用增加一次模型成本，仍复用已有设计 Runtime、取消和格式修复机制；旧草稿、恢复已冻结构建和纯视觉修订不补跑本步骤。

视觉复查改用结构化问题：截图、页面/部件、证据、任务影响、责任范围及改法。宿主区分当前呈现范围内的可定位意见与设计/宿主/待确认意见；后者保留给人查看，不触发自动修订。宿主验证引用与可调整属性，并不假装能验证模型的审美判断或截图描述真伪。继续保留一次集中修订、一次确认以及结构失败不放行的规则。历史 visualResult 的字符串意见继续可读。

已知合同缺陷的最小修复：本地存储 query 的非空列表期望在 output/includes/outputIncludes/expect 的所有写入形式上使用同一检查，错误交回现有主线设计修复循环；平台能力与网络读取继续按现有替身/结构合同处理。不可为通过验证造记录或改断言。

验收：生产编排证明体验草图可改变初始部件拆分、进入 detail 与 UI/评审，原操作/能力不被体验任务改写；暂停后旧结果不提交；已冻结恢复和视觉修订不重跑体验规划。合同反例须在 prepareBuild/代码调用之前被设计修正。待确认、宿主问题、无效截图/目标/属性不得触发自动修改，有效呈现问题仍进行一次修改及确认，结构失败仍阻断。整体 build 与包 README 必跑回归，以及 authoring/workflow 测试；使用相同三类需求做一次隔离真实生成，记录成功和失败，不针对每个样例追加布局指导或连续美化。

完成程度仍以内部完整为目标；本节工程验收和真实模型质量结论分别记录，不把新增字段、更多模型调用或 reviewed 状态当成体验已达标。

让生成插件围绕具体任务形成有主次、有空间组织、可持续操作的界面。阅读摘记、待办清单和收支记录应有不同的信息组织，同时保持 Molis Work 的控件、字体、主题和操作习惯。

## 方案选择

推荐扩展平台的声明式界面能力：设计 Agent 决定整页表达，Jev 在该表达允许的候选中选控件，宿主渲染并检查。

| 路线 | 能解决什么 | 代价与判断 |
| --- | --- | --- |
| 只改提示词和默认 CSS | 改善当前模板的局部观感 | 布局和交互上限不变，不足以满足本任务 |
| 整页设计 + 可组合布局 + 视觉复查 | 保留统一控件，同时按任务组织空间和交互 | 需要扩展界面合同、渲染器和编排；推荐 |
| 生成独立前端代码 | 更自由的视觉和复杂交互 | 增加前端隔离、依赖、发布和兼容负担；遇到声明式方案确实无法表达的已选需求时再评估 |

保留：现有组件目录和主题、平台渲染器、后端沙箱、功能合同、权限、动作桥接、可见构建过程、试用与正式数据隔离。

替换：整页单一区域、逐块独立选择却无人负责整体、只以功能验收结束构建。

本期范围：页面组合、语义化呈现属性、选中内容的详情展示、响应式安排、截图与有限修订、旧插件兼容。暂不扩展任意 HTML/CSS/JavaScript、拖拽画布、插件自有主题、复杂图表或图片生成流水线；不重做创作台外壳。

## 用户会看到什么

1. 用户表达需求；主线设计给出 2–3 个真正不同的任务方案。现有方案预览使用真实组件和逼真示例内容；示例有明确标记，不进入正式存储。无需逐个方案调用生图服务。
2. 用户选定产品方案，体验阶段先给出使用路径、部件草图与代表性场景，主线细化绑定与验收、校验一致后冻结。UI Agent 根据整页意图组织空间，代码 Agent 同时实现功能。画布继续呈现真实的放置、接通与修改步骤。
3. 全部接通后执行功能验收。宿主准备典型内容状态，检查实际布局并截图；UI Agent 在有看图能力时检查画面。
4. 发现问题后集中修一次，复查一次。修改记录保存上一版；同一业务合同下可以只读查看上次界面、返回当前界面和撤回。修改理由保留在协作记录中。用户可以继续试用或暂停。
5. 发布沿用原流程。功能结果、结构检查、视觉复查分别如实展示，不把“能点击”写成“视觉已通过”。

例如同一个「阅读摘记」需求，假设范围只有浏览、筛选、新建、编辑与删除：

- 首页首先呈现可浏览的摘记，而不是展开所有录入字段；工具栏放筛选和一个新建入口。
- 点开一条后，宽屏形成紧凑目录与宽正文区，正文有适合阅读的行长，来源和日期退为辅助信息；未选中时不自动替用户打开第一条。
- 新建在已有 Sheet 中完成，编辑失败保留输入；保存后新记录进入目录，使用已有到达反馈。
- 窄屏先看目录，打开后进入详情，返回保留滚动和筛选。插件不重画工作台外框，不重复显示宿主已有的插件名。

这些是可组合出来的结果，不把「阅读摘记模板」写死成所有插件的新默认。

## AI 职责和输入输出

不增加一个常驻服务。复用当前 designer 运行通道，新增明确的界面设计与复查阶段，在产品里仍称 UI Agent；每个阶段有自己的提示词和输入范围。

| 参与者 | 输入 | 输出与责任边界 |
| --- | --- | --- |
| 主线设计 | 用户需求、已有方案、冻结前的体验草图与代表性场景、平台能力目录 | 业务操作、数据合同、用户旅程、验收场景，以及页面应突出什么；不指定 CSS |
| 体验设计 | 用户原始需求、已选产品方案、操作输入输出、实际组件能力 | 在冻结前重组部件草图、决定主任务路径和信息主次，提供具体合成场景；不修改操作或扩权 |
| UI Agent | 已选方案、冻结的操作、体验上下文、整页现状、组件能力及组合示例、主题规则、逼真样本；复查时加截图和结构检查结果 | 页面组合与呈现属性、有限的呈现修订；不改业务操作、权限或验收期望 |
| Jev | 页面主次、所在区域、相邻组件、局部意图、合法候选 | 选择局部组件；不独立推翻整页设计 |
| 代码 Agent | 冻结操作与已有开发材料 | 后端实现与测试，不因为视觉修订而重写功能 |
| 宿主 | 页面设计、组件实现、真实预览、功能结果 | 校验、渲染、截图、版本提交和恢复；决定检查是否真正通过 |

Jev 不可用时优先使用 UI Agent 已给出的合法偏好，记录为设计选择；不再无条件以固定候选顺序决定整页。不存在合法表达时报告缺失能力并保留草稿，不悄悄换成一个意思不对的表单。

组件目录仍是唯一来源。用于生成的元信息、预览与组合示例从同一目录导出，避免维护第二份名单。UI Agent 可以看到哪些组件可用、适用数据、支持的状态和组合方式，而非只有组件名称。

## 最小完整的界面表达

在已有 design 中增加有版本的可选呈现描述，继续引用已有页面、区域和稳定 part id。功能操作、数据绑定和节点定义不复制到另一份模型；页面树只拥有组合关系和呈现信息。

首期开放四类能力：

| 能力 | Agent 可以决定 | 平台负责 |
| --- | --- | --- |
| 空间组合 | 上下排列、左右分区、网格、分组；主区与辅助区比例；内容最大宽度 | 用现有 Frame 等原语组合，必要的布局能力先进入同一目录；拒绝任意坐标、代码和 CSS |
| 信息层次 | 标题/正文/辅助信息角色、紧凑/常规/阅读密度、语义化间距、主次操作位置 | 映射现有 token，保持浅深色、可读性与键盘焦点 |
| 内容组织 | 字段优先级、次要内容折叠、单行操作、选中记录的详情展示 | 使用明确的字段引用和宿主拥有的选中状态，不执行表达式或用户脚本 |
| 视口与状态 | 窄屏堆叠或目录→详情；空态入口；加载、失败和成功反馈位置 | 固定的可验证状态转换、返回恢复、减少动效、焦点与输入保留 |

目录→详情是此次需要补齐的呈现能力：已有列表的选中记录作为详情数据来源，详情只能读取同一合同允许的数据；已有数据足够时无需新增后端查询。组件之间的移动不能改变原有操作授权或绕过页面/区域的绑定检查。

主操作、导航标题等信息只能有一个权威配置位置，渲染器从它派生。树引用不能重复、悬空或成环；不允许把关键功能移到无法到达的位置。

组件选型与属性修订都须适合所在槽位，并保留交互语义。比如把表单变为 Sheet 时，打开入口、关闭方式、错误提示和焦点归还必须一起成立。

## 业务修订与视觉修订分开

- 纯视觉变更只更新呈现描述及必要的组件种类/属性；操作 schema、副作用、数据、业务验收保持不变，不重新调用代码 Agent、安装依赖或打包后端。
- 部件 id 和绑定不变时，移动真实 DOM 节点并保留输入、光标、选中和滚动；需要替换控件时按当前字段映射恢复合法输入。
- 视觉修订碰到新增数据或新操作的需求，回到已有的主线设计修订流程，说明功能变化；不能在视觉阶段暗改合同。
- 复用已有构建 revision、取消令牌、历史和 before-effect 机制。暂停、撤权、停用或新版修改发生后，旧截图和旧模型结果不能写回。
- 宿主重启保留最后一版已校验设计、已通过功能和未完成阶段；恢复时检查当前版本再继续，不从旧截图直接提交。

## 视觉复查怎样落地

先执行原 G1–G7 功能检查。通过后在隔离预览里准备典型内容，捕获与当前呈现版本关联的画面和布局结果；最终复查对象必须是正式渲染器生成的界面，生图 mockup 不作为通过证据。

自动结构检查目前覆盖页面横向溢出、可见操作超出视口或被遮挡；合法的表格局部滚动不按整页溢出处理。焦点、输入、窄屏返回和失败恢复由定向浏览器操作验证；通用文字裁切和所有对话框键盘退出尚未成为自动检查器能力，不能标为已覆盖。

视觉模型负责层次、密度、阅读节奏、重复标题、无意义卡片、主次操作冲突等判断。每条建议指向页面/组件和具体画面证据，不输出一个没有解释的审美总分。截图里的内容按待检查材料处理，不能成为模型的新指令。

一次批量检查覆盖代表页面的桌面浅色、深色和窄屏，以及按实际风险选择的空态、长内容、加载或失败场景；不机械展开所有排列组合。预算为首次检查、集中修改、最多一次确认复查。只复查被修改的页面和相关功能路径；不为视觉样式重复跑全部后端测试。

模型及失败处理：

- 优先使用当前已配置且已验证支持图片输入的模型，不自动切换供应商或新建模型设置。图片输入须经同一 Home Prologue Runtime；现有 Builder 文字请求需要补齐附件传递，实施前以本机替身协议和实际支持模型验证。
- 截图仅取构建预览画布，默认使用不含真实私人内容的验收/示例数据；不截整个工作台，不带令牌，不让截图触发真实的外部写入或收费动作。
- 没有看图能力、超时或失败时保留可用结果，显示“功能已验证；视觉未复查”。结构检查仍执行，发布遵循原功能和授权条件；不额外强制用户找一个模型或进行人工审批。
- 确定的交互/结构故障必须修复；审美建议集中修改后仍有分歧就展示未解决项，允许用户继续调整，不无限循环，也不静默回到旧模板。
- 记录真实调用数、耗时和用量；视觉闭环不要求生图调用。实际成本由配置模型和截图体积决定，本提案不给未经测量的金额或时延承诺。

## 切换、兼容与回退

1. 先让渲染器读取可选的新呈现版本；缺少该字段的旧草稿和旧发布继续走原布局，读取时不改存储。

## 设计标准进入生成流程（2026-09-29 追加范围）

本轮目标是让审美、UI、动效、用户动线和信息呈现成为实际模型输入，达到这条提示链路功能可用；不以写入规范或单次模型回答宣称生成质量已经稳定、达到内部完整。参考本机 Impeccable 4.1.1 的 Operate/Read、animate、craft-floor 和 critique 中的设计原则，按 Molis 现有视觉系统改写，不引入其营销页风格、评分流程、子代理编排或运行时依赖。

- 唯一内容源为 `skills/molis-plugin-dev/generated-experience.md`，设计和 UI 阶段共同挂载；代码阶段不携带审美提示。主线设计把入口→动作→结果→继续/返回写进已有 journey，部件目的写进 purpose；UI 阶段在已有 summary 中说明主内容、主操作和空间取舍，不新增协议字段。
- 标准覆盖任务气质、视觉层级、阅读/扫描/比较、渐进呈现、命名与空态、窄容器、失败恢复、动效的反馈与连续性。原则须能映射当次目录中的布局、组件与字段；不机械要求每页分栏、弹窗、卡片或动画。
- 动效实现仍归宿主；本轮不开放动画脚本、时长或第二套 token。强调真实到达/完成、短反馈、减少动效、不中断操作。静态截图不能证明时序、焦点、键盘、动画或未展示状态，复查不得据此报告缺失。
- 视觉复查沿用同一质量标准，补充实际渲染节点、用途、绑定和字段映射，使模型区分目录摘要/正文、同一命令入口/提交、不同截图状态。建议须含截图标签、页面/部件、可见证据、对任务的影响和当前表达能力内的改法；仍最多五条、一次集中修订和一次确认。无需新增运行阶段或评分门禁。

范围：Builder prompts 与呈现任务、Local Host Skill 挂载、生成规范和相关测试。保持合同、权限、渲染器、业务代码与现有恢复行为。验证沿生产编排检查阶段挂载与真实 Prologue 请求内容、评审获得实际节点；整体构建后跑两包要求和相关编排回归，再用既有阅读样本做一次有限真实模型界面修订/复查。已有宽窄屏渲染测试不因纯提示文案重复扩大；实际模型质量和未观察状态单列证据。
