## 3. 看板与领取

`BOARD.md` 只写不会变的：派给、顺位、依赖、锁定的文件。任务走到哪一步不记在看板上，`next.mjs --role status` 从分支、PR 和评论推出来；统筹合入后不改看板。

| 任务 | 标题 | 档 | 派给 | 顺位 | 依赖 | 锁定的文件 |
| --- | --- | --- | --- | --- | --- | --- |
| T-012 | assistant 监听失败记 hostLog | 丙 | A | 1 | — | `apps/local-host/src/assistant/assistant-store.ts` |

- 统筹预先派好，每台设备一个按「顺位」排的队列；「派给」写「池」的是公共池，A、B 谁空谁领，先领自己的，再领池里的。
- 领哪一项由 `next.mjs` 给出：派给自己或池、没人领、依赖都已合入、锁定的文件没被在途任务占着。
- **领取就是推一个分支，不开 PR**（推分支不触发 CI；PR 一开，每推一次就跑一遍约 20～25 分钟、带 macOS 作业的 CI）：

  ```bash
  git fetch -q origin main
  git worktree add -b task/T012-a ../mw-T012 origin/main
  cd ../mw-T012
  git commit --allow-empty -m "T-012 开工"
  git push -u origin task/T012-a
  ```

- 分支名 `task/T<三位号>-<后缀>`：设备 A DeepSeek 用 `a`，设备 B DeepSeek 用 `b`，Codex 自己的任务用 `cx`，本机线用 `m`。
- 池里的一项被 A、B 同时领了：后缀字母序靠后的（`b`）删掉自己的分支，去领下一项；`next.mjs` 会提示。
- 开发中的分支可以随时推，备份进度，不花 CI。**开发中每 60 分钟至少推一次**：没有新代码就推一个写明做到哪里的空提交；卡住了贴【阻塞】。`next.mjs` 到点提醒。
- 一台设备同一时间只开发一项（第 11 节）。两项的【方案】都批了，先做先领的那项，开了 PR 再做下一项。
- **收回。** 认领以后 2 小时既没有推送、也没有评论（在等【方案】批复、【问统筹】答复的不算；同一台设备 2 小时内推过别的分支的，算排队，也不算），`next.mjs` 提醒统筹在 #1332 问一声；问后 1 小时仍没回音，统筹在看板把这一项的「派给」改到别的设备或本机，这就是收回。收回后原开发不再推那个分支，在 #1332 说一句推到了哪个提交，分支不删；接手的人从 main 新开自己的分支，用得上的提交自己 cherry-pick。
- 自己的队列空了：`next.mjs` 会提示在 #1332 贴【空闲】，一次就够，统筹补派后再领。统筹的目标是每台设备、公共池各常备 3 份能领的（依赖还没合入的不算），少了 `next.mjs` 提醒统筹补。

## 5. 一个任务的流程

```text
统筹：写任务书，派
  ↓
开发：领取（只推分支）
  乙档：在 #1332 贴【方案】 → 统筹【统筹答】 → 再写代码
  ↓
开发：自测、自审 → 开 PR（直接 ready，不开 draft） → 马上贴【交接】，不等 CI
  ↓
Codex：一审 + 验证（验证结论等 Verify 出来；Verify 红就退回开发）
  全是小问题 → 自己修 → 贴【一审 已小修 @新头】
  有大问题   → 贴【一审 要改】 → 开发修 → 贴【修复】 → Codex 只看增量
  ↓
二审会话：自己领走，贴【二审】；统筹同时给 full=true 的排 Full
  二审要改 → 开发修 → 【修复】 → Codex 增量一审与验证 → 二审增量
  ↓
统筹：合并 → 贴【合入】；远端分支由 GitHub 自动删，开发删本地工作树
```

**接力棒。** 一个分支任一时刻只有一方能推，由最后一条阶段评论决定：

| 最后一条阶段评论 | 谁能推 |
| --- | --- |
| 领取、【统筹答】、【一审 要改】、【验证 失败】、【二审 要改】 | 开发 |
| 【交接】、【修复】 | Codex，只做小修 |
| 【一审 可进二审】、【一审 已小修】、【验证 通过】、【二审 可合】 | 没有人；要合 main 时由统筹在【统筹答】里指定 |

**小修的边界。** 下面几条全满足才算小问题：
- 不改行为、断言和合同；
- 不改门禁文件和数字；
- 只动这个 PR 已经改过的文件；
- 合计不超过 30 行。

例如：错别字、注释和文档措辞、测试名里漏的验收编号、lint 告警、PR 正文缺的节。有任何一处大问题，就整单退回开发，Codex 不动手，小问题也列在里面让开发一起修。

**加急。** 看板「加急：」一行列出的任务（挡着别人的，例如 CI 装依赖）：开发先修它，Codex、二审先看它，统筹先给它排 Full。`next.mjs` 把它排在最前，并标「加急」。

**二审的 [建议] 去哪里。** 不为每条建议开一份新任务：
- 只动本 PR 已改的文件、是措辞、注释或小改的：开发在同一轮【修复】里一起改。PR 已经可合、只剩这类建议的，照合，建议记进统筹的零碎单。
- 指向别的文件或要另外查证的：统筹每天收一次，攒成一份丙档的「零碎」任务。
- 像是别处还有同样缺陷的：原开发在【修复】里只读核一下，写出结论；是缺陷，统筹再开任务。

**交接前自查**（所有开发都做，本机线甲档尤其；写进【交接】）：
1. 同一种写法别处还有没有：grep 你改的那个模式，范围内的都改了，范围外的列出来。
2. 测试真能证明验收：去掉产品改动测试会红（贴先红的输出）；断言打在验收说的那件事上，不是旁证。
3. PR 正文、spec、注释里每一句讲行为的话，都在代码里核过；涉及状态的，每种状态都过一遍（running、crashed、quarantined、disabled……）。没核的写「没核」。
4. 改的文件有没有在途 PR 也在改：文件多的 PR 用 `gh api --paginate repos/molis-ai/molis-work/pulls/<号>/files` 查，`gh pr list --json files` 每个 PR 最多只给 100 个文件，会漏。
5. 本机线：交接前用本机的 heavy.sh 把任务书第 7 节的测试文件和 affected-tests 给出的非浏览器文件跑一次（本机一个槽，排队），结果写进【交接】；浏览器用例和全量留给 Codex 和 CI。

**推一次就重跑一次 CI。** 每推一次，PR 上正在跑的 CI 会被取消重来（约 20～25 分钟）。修复攒齐了一次推，不一条一推。

**合 main。** main 有合并队列（squash，最多 5 个一起建、一起验），PR 不用追 main。只在两种时候合：有冲突，或统筹在【统筹答】里要求。合法：`git merge origin/main`，不 rebase 已推的分支，不 force push。`tooling/gates/baseline.json` 冲突时重跑 `node scripts/check-health-gates.mjs --update --base origin/main`；`tooling/gates/api/`、`tooling/gates/actions/` 冲突时先 `pnpm build` 再 `pnpm api:update` / `pnpm actions:update`；不手合。合完重跑门禁和任务书的测试，推上去后贴【修复】，注明「只合 main」。

**评审沿用。** 一审、验证、二审都写明头。合 main 之后 PR 自己的补丁没变（`git patch-id` 相同，`next.mjs` 自动比），原来的结论照样算，只等新头的 Verify；补丁变了（解了冲突）就只看变的部分。

**防打转。** 一个任务的「要改」（一审、验证、二审合计）到第 3 次时，统筹介入：改任务书、拆小，或收回本机做。

## 6. 评论格式

第一行是抬头，`next.mjs` 靠它认；最后一行是署名。设备 A 的 DeepSeek 和 Codex 共用 `yijunw0212`，设备 B 的 DeepSeek 和本机 Claude 共用 `jingxusandra-gif`，所以每条评论都要署名，PR 正文第二行写 `开发：<署名>`。全部用中文。

| 抬头 | 谁 | 必写的内容 |
| --- | --- | --- |
| `【方案 T-012】` | 开发（乙档） | 每个要改的文件怎么改、测试怎么写、任务书第 5 节要回答的问题、拿不准的点 |
| `【交接 T-012】@<头> 开发→一审` | 开发 | 改了什么；自测的命令与结果，逐条；一行 `full=true` 或 `full=false`；自审清单里没过的；没验证的 |
| `【一审 T-012】@<头> 可进二审｜要改｜已小修 @<新头>` | Codex | 问题逐条编号，标 [大] [小] [建议]，写 `文件:行`、问题、怎么改 |
| `【验证 T-012】@<头> 通过｜失败` | Codex | 命令与结果；一行 `full=…`；浏览器用例；红的逐个归因：本 PR、main 也红、偶发（重跑过） |
| `【修复 T-012】@<新头> 对应 一审/二审 @<旧头>` | 开发 | 逐条：编号 → 怎么改的，或不改的理由 |
| `【二审 T-012】@<头> 可合｜要改` | 二审 | 同一审的写法，[必修] [建议] |
| `【问统筹 T-012】` | 任何人 | 一句话问题、选项、推荐和理由 |
| `【统筹答 T-012】` | 统筹 | 裁定；要合 main 时写明谁来合 |
| `【合入 T-012】main @<sha>` | 统筹 | — |
| `【空闲】`、`【阻塞】`、`【main 红】`、`【设备】` | 任何人，在 #1332 | 设备、原因；main 红写文件、第一个红的提交、归因 |

署名：`— DeepSeek（设备 A）`、`— DeepSeek（设备 B）`、`— Codex（设备 A）`、`— Claude 二审`、`— Claude 统筹`。

`@<头>` 一律写 PR 头的 9 位短 sha（`git rev-parse --short=9 HEAD`）。

## 7. 二审看什么

一审看任务书有没有做到、代码对不对。二审在一审之上再看：

1. 任务书本身对不对：统筹写错的地方在这里抓。
2. 防腐后果：每项事实只有一个主人；没有兼容层；数字只降不升；没有给某个插件开私路。
3. 与其他在途 PR、刚合入的 main 有没有相互影响：撞文件、撞号、撞语义。
4. 一审的意见都落实了；豁免的有理由。
5. 验证的证据和当前头一致；`full` 的判断对。
6. 账目：spec 状态句、BACKLOG、PR 正文的各节。

本机线和 Codex 自己的任务、丙档没有一审，二审连一审的清单一起看（前两种用 Opus，丙档用 Sonnet）。

## 8. 合并

只有统筹合并。下面几条要在同一个头 H 上都成立（`next.mjs --role coord` 逐条核，齐了给出合并命令）：

- CI `Verify` 绿；
- 【一审】可进二审，或已小修且新头就是 H（没有一审的档位除外）；
- 【验证】通过；
- 【二审】可合；
- `full=true` 时，Full 在 H 上通过；
- 碰了安全不变量的测试或登记表时，不挡合并的 `security-invariants` 作业在 H 上绿，统筹手查过；
- 没有未答的【问统筹】。

第 5 节「评审沿用」认的结论，算在 H 上。

```bash
gh pr merge <号> --match-head-commit <H 的完整 sha>
```

合并方式由合并队列决定，不加 `--squash`。入队后回读 main 上的合并提交，再贴【合入】。LINES 一天记一次，不逐个记。

用户 2026-10-28 在统筹会话里授权：「二审可合、第 8 节条件都齐的任务 PR，统筹可以直接合并」。只在统筹会话里合；工具层的拦截不绕开，被拦时统筹告诉用户，由用户就那一个 PR 点头。

## 9. 测试与全量

| 谁 | 在哪 | 跑什么 |
| --- | --- | --- |
| 开发 | 自己的设备 | 任务书第 7 节的测试文件（含点名的浏览器用例）、affected-tests 给的用例、门禁 |
| Codex | 设备 A | 第 4 节「验证」那一列 |
| CI | GitHub | 每个 PR 的 `Verify`；`full=true` 的跑 Full |
| 本机 | — | 只跑门禁 |

- `full` 由 `node scripts/affected-tests.mjs --base origin/main --json` 的 `full` 字段定。
- CI Full 只由统筹排。PR 上加 `full-suite` 标签跑一次（同一个头要再跑，先去掉标签再加），最多占 6 个 runner、约 30～35 分钟；同时最多两个，给 `Verify` 和合并队列留够 runner。几个 PR 一起时进一条 `integration/**` 承载分支，占 10 个 runner，同时只一条；它在排队或在跑时不再往承载分支推（会取消它）。取消任何 CI 都要用户本人同意。
- `full=true` 的，一审过了就排，和验证、二审并行，不等到最后。
- Codex 在本机跑全量会把设备 A 占住约一小时，只在统筹点名、而且 Codex 队列空的时候跑；它只是提前发现问题，不替代 CI Full。
- 设备 A 上 DeepSeek 和 Codex 共用一台机器：构建、浏览器用例包在 `node scripts/machine-slot.mjs run <build|browser> --label "<谁> <任务>" -- <命令>` 里排队；全量只由 Codex 跑。

## 11. 上限

上限卡的是瓶颈前排队的长度，不是每人手上有几个 PR。瓶颈是 Codex：一个人给两台 DeepSeek 做一审和验证，一单约 30 分钟。

- 每台 DeepSeek 在 Codex 队列里（贴了【交接】或【修复】、还没有一审和验证结论的）最多 2 个乙、甲档 PR；到 2 个就不领新的。丙档只要轻验证，不算。两台各 2 个是 4 单，Codex 约 2 小时排完，交接到一审的等待不超过 2 小时。
- 开发中最多 1 项。在等【方案】批复或【问统筹】答复的不算，可以先领下一项。
- 等统筹的（待二审、待合）不算：那是统筹要尽快清的。
- 修复永远先于领新的。
- Codex 的顺序：先看【修复】（增量），再按交接时间看新的【交接】，然后是 main 变红，最后才做自己的任务。
- 同一枢纽文件同一时间只给一个在途任务，写在看板「锁定的文件」列。枢纽名单见 `docs/system/PARALLEL-DEVELOPMENT.md` 第 2 节。追加行的文档（`specs/BACKLOG.md`、spec 进度行）例外：只加、删自己的行，合 main 时两边都留。
- 一个 PR 一个主题，不超过约 50 个文件，最好不超过 15 个。
- 第一天之后按数据调：Codex 常空就放到 3；交接到一审常等过 2 小时就收到 1。2026-10-28 下午：Codex 队列常有 4 单、不空，上限仍是 2；改为丙档不走一审、不占名额。

## 12. 怎样知道该做什么

每个角色都不读全部评论，只跑 `next.mjs`，它按角色列出「现在轮到你做的」：

```bash
git fetch -q origin coordination/handoff-2026-10-14
git show origin/coordination/handoff-2026-10-14:coordination/2026-10-28/next.mjs > "${TMPDIR:-/tmp}/next.mjs"
node "${TMPDIR:-/tmp}/next.mjs" --role dev-a     # dev-b、codex、review、coord、status
node "${TMPDIR:-/tmp}/next.mjs" --role dev-a --wait --max 25
```

- 做完一件事就跑一次，按它列的顺序做。只读它给的那条评论和那个 PR。
- 没事可做时跑 `--wait`：它在 shell 里每 3 分钟查一次，有事才返回，等的时候不花模型的 token。harness 的单条命令有时限的，把 `--max`（分钟）设在时限以内，返回「无事」就再跑一次。
- 每天开工、换任务前重新取一次 `next.mjs`，它也可能改。
- 状态全在 GitHub 上，会话可以随时换：DeepSeek 每个任务开一个新会话；Codex 和二审上下文用过一半就重开，从 `next.mjs` 接着做。
- 统筹用 `--role coord --wait --new <文件>` 在后台挂着，只有新事才醒；最多 4 小时醒一次兜底。
