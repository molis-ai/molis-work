## 1. 背景

SYS-15-S1（`tests/installed-plugin-host.test.ts:133-166`，整份是 macOS 才跑，`:29`）：装一个沙箱插件，调它的 `schedule` 操作（里面 `schedules.add`，到点 `Date.now() + 1500`，没给 `repeat`，是一次性的，`:148`、`:47`），关掉 Host、重启，再在 `:158-159` 用 `clock.tick(new Date(at + 1000))` 触发时钟，断言回执 `{ invoked: 1, failed: 0, skipped: 0 }`，失败信息打印 `JSON.stringify(clock.list())`。

核下来的事实：

- `tick` 只回汇总：`runTick` 对时钟上所有已启用、到期的任务逐个 `claim`、执行，数 `invoked`、`failed`、`skipped`（`horizontal/scheduler/src/index.ts:239-258`，`list` 在 `:217`，`tick` 在 `:316`）。每个到期任务一次 tick 里只被 `claim` 一次，所以「到期的集合恰好是 N 个」加「回执 `invoked` 是 N」，就等于每个跑了一次。
- 这个测试自己的任务：`schedules.add` 登记的是 `plugin_id: SCHEDULE_PLUGIN_ID`（`"io.molis.work.schedule"`，`plugins/native/schedule/src/manifest.ts:14`）、`capability_id: SCHEDULE_OPERATION_WAKEUP`（`"schedule.operation.wakeup"`，`plugins/native/schedule/src/operations.ts:9`）、`object_ref: projectId + "|" + id`（`:121`）。
- Feed 的任务：`feed.sources.wake`，`plugin_id` 是 `FEED_PLUGIN_ID`（`"io.molis.work.feed"`，`plugins/native/feed/src/identity.ts:1`），`object_ref` 是 `"sources"`，30 秒一次的循环任务，到期点是它登记那一刻的挂钟时间（`plugins/native/feed/src/runtime-wake.ts:8-9`、`:41-49`）。它由后台任务 `keepFeedWakeup` 登记，最多重试 25 次、每次隔 200 毫秒，约 5 秒（`:52-64`）。
- 别的测试已经按这个事实写：`tests/schedule-resident-runtime.test.ts:72-76` 断言项目时钟上唯一启用的循环任务是 `[FEED_PLUGIN_ID, "feed.sources.wake"]`，并断言一次性任务 tick 后 `!job.enabled && job.last_wakeup?.status === "ok"`；`tests/feed-sync-authority.test.ts:28-34` 最多等 5 秒等 Feed 把任务登记上；`tests/feed-runtime-plugin.test.ts:585` 按 `capability_id` 过滤。所以是 SYS-15-S1 的断言过期，产品行为是对的。
- 一次性任务 tick 后行还在，`enabled` 变假，`last_wakeup` 填上（`horizontal/scheduler/src/index.ts:435-441`）；循环任务 `enabled` 保持，`next_due_at` 往后推。
- 测试里 tick 的时刻是写死的 `at + 1000`（离安排那一刻约 2.5 秒），而 Feed 任务的到期点是挂钟时间：如果重启比这长，Feed 的任务在 tick 时还没到期，回执又会是 1。这是读代码得出的，没有复现；改法顺手去掉这个依赖，见第 5 节。
- 这个文件不在 `tests/ci-product-subset.txt`，也不在 `tests/quarantine.json`（`entries` 为空）。CI 在 Linux 上跳过它，所以绿只能在 macOS 本机见到。

## 2. 目标

1. SYS-15-S1 只对自己的任务下结论：tick 前，时钟里恰好有一个 `SCHEDULE_PLUGIN_ID` / `SCHEDULE_OPERATION_WAKEUP` 的任务，已启用、到期；tick 后它的 `last_wakeup.status` 是 `ok`，操作的副作用（`:164` 的 `read` 回 `'scheduled'`）还在（`RAC-1170`）。
2. 回执仍然全部算清：tick 前到期的启用任务恰好是自己的和 Feed 的 `feed.sources.wake`，回执是 `{ invoked: 2, failed: 0, skipped: 0 }`，Feed 的任务 `last_wakeup.status` 是 `ok`，tick 后启用的任务只剩 Feed 的（`RAC-1171`）。

## 5. 做法

1. 先复现：在 macOS 上 `pnpm build`（用 `node scripts/machine-slot.mjs run build --label "<谁> T-033" -- pnpm build`），再 `node scripts/run-tests.mjs tests/installed-plugin-host.test.ts`。SYS-15-S1 红在 `:159`，失败信息里的 `JSON.stringify(clock.list())` 是此刻时钟上的全部任务。把它贴进【交接】，核对：恰好两条，一条 `io.molis.work.schedule` / `schedule.operation.wakeup`，一条 `io.molis.work.feed` / `feed.sources.wake`。多于或少于两条，停，见第 11 节。
2. 顶部加三个 import，从包入口取，照 `tests/schedule-resident-runtime.test.ts:10-11`：`SCHEDULE_PLUGIN_ID`、`SCHEDULE_OPERATION_WAKEUP` 来自 `@molis-ai/molis-work-plugin-schedule`，`FEED_PLUGIN_ID` 来自 `@molis-ai/molis-work-plugin-feed`。「测试引用包内部」只数以 `.` 开头的相对路径（`scripts/check-health-gates.mjs:380-383`），所以这个文件的数字仍是 7（`tooling/gates/baseline.json:213`）。`'feed.sources.wake'` 写字符串，照 `tests/feed-runtime-plugin.test.ts:585`。
3. 把 `:158-159` 那一段改成下面的形状，名字和断言消息自己写：

   ```ts
   const clock = scheduleServiceFor(runtime.store.db);
   // Feed asks the clock for its wakeup in the background (runtime-wake.ts:52-64); wait for it as feed-sync-authority.test.ts:32 does.
   const feedJobs = () => clock.list(FEED_PLUGIN_ID).filter(job => job.capability_id === 'feed.sources.wake');
   for (let waited = 0; !feedJobs().length && waited < 5_000; waited += 25) await new Promise(resolve => setTimeout(resolve, 25));
   const own = clock.list(SCHEDULE_PLUGIN_ID).filter(job => job.capability_id === SCHEDULE_OPERATION_WAKEUP), feed = feedJobs();
   assert.equal(own.length, 1, JSON.stringify(clock.list())); assert.equal(feed.length, 1, JSON.stringify(clock.list()));
   const tickAt = new Date(Math.max(at + 1000, Date.parse(feed[0]!.next_due_at) + 1));
   const due = clock.list().filter(job => job.enabled && Date.parse(job.next_due_at) <= tickAt.getTime());
   assert.deepEqual(due.map(job => job.job_id).sort(), [own[0]!.job_id, feed[0]!.job_id].sort(), JSON.stringify(clock.list()));
   assert.deepEqual(await clock.tick(tickAt), { invoked: 2, failed: 0, skipped: 0 }, JSON.stringify(clock.list()));
   assert.equal(clock.get(own[0]!.job_id)?.last_wakeup?.status, 'ok'); assert.equal(clock.get(feed[0]!.job_id)?.last_wakeup?.status, 'ok');
   assert.deepEqual(clock.list().filter(job => job.enabled).map(job => [job.plugin_id, job.capability_id]), [[FEED_PLUGIN_ID, 'feed.sources.wake']]);
   ```

   其中等待那一行是在等一个后台登记，不是为了变绿：上限取 `keepFeedWakeup` 自己的重试预算；5 秒内没等到，上面的断言会带着时钟全貌失败。`tickAt` 取「原来的时刻」与「Feed 任务到期点之后」中较晚的，去掉对重启快慢的依赖。`:160-162` 里其余的断言（`builder.get`、`manifest_digest`）和 `:164` 的 `read` 原样保留。
4. 在断言上面各留一行英文注释，分别写 `RAC-1170`（自己的任务）和 `RAC-1171`（回执全部算清）。
5. 不要为了「看起来干净」把 `due` 里不认识的任务过滤掉：多出任何一个任务，`deepEqual` 要红，这是这条测试要继续数的东西。
