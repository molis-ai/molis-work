# T-186 图片的下载名与演示稿的文件名按整字截到 80 个字，不再截出半个字

> **可领，依赖无。成立：Images 下载图片时可以带 `name=`，路由把它按 UTF-16 单元截到 80；截点落在两个单元的字（如 😀，U+1F600）中间，名字就以半个字结尾，路由随后对它做 `encodeURIComponent`，抛 `URIError: URI malformed`，下载请求回 500。PPT 的 `.pptx` 文件名同样按单元截到 80，半个字留在文件名里，不抛错，下载名里多一个乱码字。**
>
> - 截取发生在两处（main `5a88022f7`）：
>   - `plugins/native/images/src/routes.ts:42`，函数 `downloadName`（`:40-45`），原样：
>
>     ```ts
>       const name = (request.query.name ?? "").replace(/[\u0000-\u001f\u007f"\\/:*?<>|]+/gu, " ").trim().slice(0, 80);
>     ```
>
>   - `plugins/native/ppt/src/pptx.ts:165`，函数 `pptxFilename`（`:164-166`），原样：
>
>     ```ts
>       return (clean(title).replace(/[\\/:*?"<>|]/gu, "_").trim() || "演示稿").slice(0, 80) + ".pptx";
>     ```
>
> - 来源：起草线代码扫描一（按 UTF-16 单元截人看得见的文字）的书一（图片与演示稿的下载文件名），仓库里没有对应的 MISC 行和 BACKLOG 行。扫描给的是「按代码读出，没跑」。起草时逐处核了下游，**结论比扫描说的轻一些**：Images 的页面自己带的名字最长 47 个单元，够不到路由里的 80，所以今天页面点下载撞不上这一处（第 1 节）。修的是路由和 `pptxFilename` 自己的契约：上限按字数，不切开字。
> - 这两处是 T-079（`bc20f3667`，#1404）漏掉的：它把 PPT 的 `store.ts`、`content-actions.ts` 改成按整字，文件名这一行留着。
>
> **修法起草时定、写死：** 两处都照 T-079 的原样写法 `[...x].slice(0, 80).join("")`，不先截一段再展开。`routes.ts:42` 改成 `[...(…).trim()].slice(0, 80).join("")`，`pptx.ts:165` 改成 `[...(… || "演示稿")].slice(0, 80).join("") + ".pptx"`，各在前面加一行英文注释。不先截的理由和另一种选择见第 8 节第 2 条。用例四个：Images 的两个写成一个长 test 里的子例，加在 `tests/images-plugin.test.ts` 的下载断言之后；PPT 的两个加在 `tests/ppt-actions.test.ts` 末尾。

## 1. 背景

- 谁用 Images 的 `downloadName`：
  - 只有 `routes.ts:27`，路由 `images.images.read`（`manifest.ts:21`，`GET /jobs/:id/images/:image_id`）的处理器。函数不导出（`index.ts:10` 的 `export * from "./routes.js"` 只带出 `imagesRoutes`），所以测试只能走 HTTP；
  - 只有 `?download=1` 时才用 `name`：控制字符和 `"\/:*?<>|` 换成空格，`trim()`，再 `.slice(0, 80)`；扩展名取存下来的文件名（`<uuid>.png`、`.jpg`、`.webp`，`service-job.ts:47-48`），名字已经以它结尾（不分大小写）就不再补；
  - 结果最长是 80 个单元加扩展名。
- 字节响应怎样用这个名字（`apps/local-host/src/plugin-route-operations.ts:154-160`，#1449 合入后行号会移）：
  - `result.bytes !== undefined` 时，`response.writeHead` 的参数里求值 `encodeURIComponent(result.filename ?? "material")`（`:158`）。求值先于 `writeHead`，抛错时没有任何头发出；
  - 调它的 `home-plugin-http.ts:148` 外面只有 `try … finally`（`:139`），没有 `catch`；外层 `web-server.ts:188-190` 的 `catch` 交给 `sendUnhandledWebError`（`web-http.ts:59-64`）：500，`actions.execution_failed`，句子是「请求未能完成，请重试。」。
- Images 页面怎样用：
  - 结果页的下载链接在 `browser/result.ts:63-82`：`download.href = …&name=${encodeURIComponent(name)}`，`download.download = name`（`:77-78`）；
  - 点击在插件框里被 `child.ts:112-116` 截下，转成 `link` 消息，宿主的 `parent.ts:169` 交给 `downloadFrameFile`（`browser/plugin-frame/links.ts:4-11`）：用 `molisWorkRequest` 取路由，非 2xx 就抛路由的错误句，页面弹提示，没有文件；2xx 就从 `content-disposition` 的 `filename*=UTF-8''…` 取名；
  - 页面自己的名字（`fileNameOf`，`result.ts:6-11`）：提示词压成单空格后 `.slice(0, 40)`，一次出多张时加 ` N`（最多 4 张，`providers.ts:39`），再加扩展名：**最多 40 + 2 + 5 = 47 个单元，够不到路由里的 80**。仓库里别的 `download=1` 只有 `list.ts:5-6` 的 `imageUrl`（页面用）、`tests/images-plugin.test.ts:53` 和 `tests/images-plugin.e2e.test.ts:52`（都不带超长的 `name`）。所以今天没有调用者能让 `name` 超过 80 个单元；半个字要靠直接带 `name` 的 HTTP 调用才进得来，不过路由是公开的本机接口，上限按字数、不切开字是它自己的契约。
- PPT 怎样用 `pptxFilename`：
  - 源码里只有 `actions.ts:160`（动作 `ppt.pptx`，`:157-161`）；`index.ts:9` 导出，没有别的源码或测试用它，没有文档提它；
  - 动作 `audiences` 是 `user`、`workflow`、`agent`、`mcp`（`actions.ts:31`）；路由 `ppt.pptx`（`manifest.ts:39`、`plugin.ts:130`，`GET /ppt/:id/pptx`）回的是 JSON 不是字节，所以没有 `encodeURIComponent`，不会抛；
  - 页面（`browser/record-commands.ts:72-75`）拿 `filename` 调 `page.host.download`（`files.ts:14-16` 经 `port.postMessage` 交给宿主，`parent.ts:156` 的 `downloadPageBlob`，`links.ts:13-16` 的 `link.download`），并用它写操作回执 `page.placed({ file: { name } })`。
- 演示稿标题的上限：`create`、`update` 的 schema 是 `maxLength: 80`（`actions.ts:45`、`:46`；Ajv 按码点数），`normalizeTitle`（`store.ts:255-259`）也按 `[...title].length > 80` 拒绝。所以标题至多 80 个字；`clean`（`pptx.ts:25`）、禁用字符换 `_`、`trim` 都不会让它变长。改前的 `.slice(0, 80)` 按单元：标题含两单元字、超过 80 个单元（41 到 80 个字之间就可能）时，在第 80 个单元处切；改后按字，**至多 80 个字的标题永远不会被切**，这一刀只剩给直接调 `pptxFilename` 的人当保险。
- 半个字怎样进下游，一张表：

| 下游 | 位置（main `5a88022f7`） | 数上限的单位 | 半个字会怎样 | 受影响 |
| --- | --- | --- | --- | --- |
| Images 路由的 `Content-Disposition` | `plugin-route-operations.ts:158` | — | `encodeURIComponent` 抛 `URIError: URI malformed`，宿主答 500，没有文件（独立脚本验过抛错；500 与句子是读 `web-server.ts:188-190`、`web-http.ts:59-64` 推出来的，没跑） | 是，下载失败 |
| 宿主的下载器 | `links.ts:10` 与 `:15` | 单元，200 | 本单的名字最长 80 个两单元字加扩展名，165 个单元，截不到 | 否 |
| Images 页面自己的名字 | `result.ts:8`、`:77-78` | 单元，40 | 页面自己 `.slice(0, 40)` 提示词，可能留半个字，再在 `:77` 自己 `encodeURIComponent` 时抛错。不经过路由的 80，本单改不到（第 3 节） | 否，另一处 |

| PPT 页面的下载与回执 | `record-commands.ts:72-75` → `files.ts:14-16` → `parent.ts:156` → `links.ts:13-16` | 单元，200（`links.ts:15`） | `link.download` 和回执卡片都带着半个字；浏览器保存时怎样处理没在浏览器里试，按常识是换成 U+FFFD | 是，文件名显示成乱码 |

- 更长的名字会不会撞上更严的限：本单让名字从「至多 80 个单元」变成「至多 80 个字」，最长 160 个单元加扩展名。逐个看过：宿主下载器的 200 个单元（上表）够；响应头里 `encodeURIComponent` 后最长 80 × 12 = 960 字节加扩展名，没有响应头上限问题。**一处没法在代码里确认的**：80 个表情的名字 UTF-8 下是 320 字节，超过常见文件系统的 255 字节；改前最多 40 个表情 160 字节。浏览器保存时会不会自己缩短没试（第 8 节第 5 条）。
- 写法的先例（`[...x].slice(0, n).join("")`，T-079，main `bc20f3667`）：`plugins/native/ppt/src/store.ts:279`、`plugins/native/ppt/src/content-actions.ts:52-53`、`plugins/native/pages/src/content-actions.ts:42`、`plugins/native/dataset/src/store.ts:147`。

## 2. 目标

1. Images 下载带 `name` 时，保存的文件名是整字，至多 80 个字（一个两单元的字算 1 个）；名字落在第 80 个字是两单元字时保留它；响应是 200，不再是 500；
2. `ppt.pptx` 动作和 `pptxFilename` 给出的文件名是整字，至多 80 个字加 `.pptx`；
3. 放得下的名字、已带扩展名的名字、禁用字符换成的空格和 `_`、没有名字时的备用名（`演示稿`）与现在一字不差；
4. 用例钉住上面三条：撤销任一处、改错截点，各自都红。

2. **两处都用 T-079 的原样写法，不先截一段再展开。**T-181 的第 8 节第 2 条遇到的是没有上限的标题，先截 1000 个单元再展开；这里的输入都有界：
   - Images 的 `name` 来自请求的查询串，受 Node 的请求头上限约束：本机 Node 24 量到 `http.maxHeaderSize` 是 16384，`apps/local-host` 里建服务器处（`web-server.ts:122`）没有改它，`git grep maxHeaderSize` 只在四处出站请求里出现（`anysearch-transport.ts:92`、`mcp-resident-health.ts:17`、`packages/plugin-sandbox/src/https-proxy.ts:91`、`plugins/official-integrations/rss/src/pinned-request.ts:27`）。独立脚本量过：展开 4000 个单元的串再取前 80 个，1000 次共 25 ms；
