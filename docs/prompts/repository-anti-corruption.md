# 第二步：系统性代码与架构防腐整理

第一步（全部需求合入后的功能审查、合并缺陷修复与 spec 梳理）完成之后做这一步：按仓库系统整理要求和上一轮《Molis Work 代码与架构防腐体检报告》，对全仓的代码与架构做防腐处理，**完成必要的修复、重构、清理、验证和规范沉淀**。只出报告不算完成。

## 目标

这一步要让仓库达到三件事：

1. **后续容易扩展**：新增插件、服务集成、AI 能力、设置、界面入口等，按声明和扩展点接入，只改自己的包，不改宿主与工作台里的名单。
2. **多人并行开发不出大问题**：每块代码的职责和归属清楚；并行的需求各改各的文件，很少有大家都要改的热点；公共合同的变更有流程；CI 能在合并前拦住回归；协作规则写在仓库里，不只在某个会话的记忆里。
3. **调用链清楚、改得动**：每个能力只有一条实现路径，从界面或入口一路能追到领域、存储和模型；改需求、修 bug、调交互时，改动范围小、可以预期，有测试兜底，出错能定位到具体环节。
4. **不留兼容逻辑**：假设没有旧用户。本轮结束后，代码里不再有为旧数据、旧定义、旧行为保留的逻辑：每个库只有一份当前 schema 的建库代码，旧身份、旧接口、旧名称、旧格式和只为历史存在的模块全部删除。

仓库系统整理要求的 15 节和体检报告回答"查什么、怎么做"；这四条回答"做到什么程度算到位"，第 7 节用可度量的标准验收。

## 0. 启动条件、范围与授权

**启动条件**：第一步的总 spec `specs/post-merge-review/spec.md` 写明完成，里面有行为基线（回归基线、能力快照、跨功能场景清单）、spec 梳理结果和交给第二步的清单；统一待做清单 `specs/BACKLOG.md` 已经建立。没有完成时先问我。开始前查开放 PR、`git worktree list` 和正在运行的会话，与在途工作协调文件范围；共享核心与有依赖顺序的修改串行做。

**范围**：全仓，不只本轮新增的代码。每个 workspace 包都至少完成一次结构审查，交出第 4.4 节的包级清单，不能只登记名字；深入程度按风险决定，未深入或无法验证的范围必须标明。

**授权**（可按需改这一段）：

- 常规、可逆、证据充分的修复、清理与重构自主完成：在自己的分支提交，可以推送分支、开 PR。每个 PR 只做一个主题，CI 通过。
- 体检报告已经列出的结构性收口方向，视为认可的方向：内置插件统一走 Plugin Runtime、MCP 旧适配退役、宿主瘦身、巨大单元拆分、浏览器脚本打包与类型检查、删除旧皮肤、收敛错误类型。每项先交方案和一个样板片，样板片合入后按片推进。
- 合入 main、删除他人分支或工作树、丢弃主检出的改动、删除 vendored 文件、向 Prologue 上游推送、修改仓库设置（分支保护、合并队列、评审要求），先问我。
- 本轮没有旧用户：清除兼容逻辑，以及对外公共合同（Manifest 字段、动作合同、MCP 工具名、插件 SDK 导出、事件）的破坏性修改，都不需要兼容期，已获授权。改变合同语义或产品行为，以及其他重大迁移策略，先给具体方案、取舍和推荐，等我决定，同时继续其他独立工作。
- 涉及我和同事正在使用的真实 Home 的数据操作（备份、升级、重建），先问我。
- **怎么问我**：需要我拍板的事，一律用 AskUserQuestion 弹窗问，不用纯文字提问，也不把问题埋在汇报里。每个问题给 2 到 4 个选项，推荐的方案放第一个、标签末尾加「（推荐）」；每个选项的说明写清做法、影响和代价；需要对比代码、界面或数据方案时，用选项的预览展示。先把不依赖这些决定的工作做完，再把问题攒成一批弹窗问，一次最多 4 个；等我回答期间，不推进依赖这些决定的改动。问题和我的回答都记进总 spec 的决策记录。

## 4. 工作内容

整理要求的 15 节全部要做。以下是围绕四个目标必须覆盖的重点，不代表只做这些。

### 4.1 清除兼容逻辑

假设没有旧用户。目标是本轮结束后，代码里不再有为旧数据、旧定义、旧行为保留的逻辑。这一项先做：兼容代码删掉之后，后面的分层、巨大单元和调用链整理要面对的代码会少很多。

**要删除的**（编写时找到的；开始时全仓重新清点，不限于这些）：

- **数据迁移与升级链**：项目库、目录库、Feed、会话、Goals（事件工作流迁移、指导迁移、修订回填等）、治理、执行、证据、Artifacts、炼金术士的 SQL 迁移与迁移前备份。每个库改为只有一份当前 schema 的建库代码，带版本号；打开版本不符的库时明确拒绝并说明怎么办，不尝试迁移。
- **只为历史数据存在的模块与读取路径**：执行模块、证据模块、治理模块里只保留历史职责的部分、Goals 里旧规则、风险、验收与覆盖账的历史读取、旧提案视图。依赖它们的逻辑（例如项目删除前的历史活动检查）一并简化。
- **旧身份与旧名称**：`board_id` 与 `project_id` 合并为一个身份；识别、拒绝或迁移旧产品名 GoalBoard 的代码（目录、App、钥匙串、环境变量、浏览器存储键）。
- **旧接口与别名**：0.1.x 根 SDK 兼容出口（`apps/local-host/sdk`、`tsconfig.sdk.json`、根包的导出）、MCP 旧工具名与别名、插件的 `legacyMcp` 适配、旧路由与重定向、旧格式导入（v3 看板导入、Pages 旧项目）、浏览器存储键的迁移、插件里为旧动作保留的入口（例如炼金术士的旧动作）。
- **合同里的历史取值**：结果合同里只为已存历史保留的枚举值、可选字段，以及"读取兼容"的特殊处理。
- **内置插件里为过去版本写的兼容声明**：版本号按新的版本策略重置。
- **为兼容存在的测试与样本**：历史 SQL 样本、迁移测试、读取兼容测试、旧名拒绝测试等，随代码删除；只留守住"当前 schema 建库正确"和"拒绝版本不符的库"的测试。
- **文档、工具与规则**：`docs/system/MIGRATION.md` 归档；架构文档里关于 `board_id` 与历史模块的段落、SSOT 里的历史模块行、`tooling/migrations/`、兼容白名单 `tooling/boundaries/compatibility-allowlist.json`、`AGENTS.md` 的"读取兼容"硬约束，按本节结论修改或删除。

**不算兼容、要保留的**：

- 产品功能里的"历史"：Goal 事件与时间线、Artifact 的版本、撤销、运行记录、通知记录等。
- 面向未来的版本机制：Schema 与合同的版本号字段、插件升级声明（`compatible_from_versions`、`migratable_from_versions`）与发行物留存。它们是以后发布插件新版本时要用的机制，不是为旧数据留的：保留机制，删掉只为过去版本写的声明。是否连机制一起简化，给方案交我决定。

**真实 Home 的安全**：

1. 删除迁移代码之前，先列出我和同事正在用的 Home，问我哪些数据要保留。
2. 要保留的：先完整备份，再用删除前的代码把它升级到最新版本。
3. 逐表比对"新基线建出的库"与"升级后的库"：表、列、索引、约束和版本号都一致，才删除迁移代码。
4. 不需要保留的：按新基线重建；示例数据由种子脚本重新生成。
5. 删除之后，用旧版本的库启动时明确拒绝并说明怎么办，不静默损坏数据。

**以后的规则**：在有真实用户之前，Schema 改动直接改基线并提高版本号；开发用的 Home 用一次性脚本升级或重建；产品代码里不再写迁移链。有了真实用户以后，再按第 4.7 节的合同变更流程引入迁移，每段兼容都写明删除条件。加门禁防止兼容逻辑回流：例如迁移只允许出现在建库基线里，源码里不再出现旧名称与兼容标记；确有必要的写进允许名单并说明理由。

### 4.2 调用链

逐条追以下主链路，写明每一环的 owner、输入输出、权限与错误、事件与结果，整理成文档放进 `docs/`：

1. 界面操作 → 工作台客户端 → 宿主 HTTP → 动作服务 → 插件或模块 → 存储 → 事件 → 界面刷新；
2. 外部 Runtime 经 MCP → 逐客户端授权 → 动作服务 → 同一条业务路径；
3. 助理与 Agent：对话 → Agent Host → Prologue → 工具调用 → 动作服务 → 副作用前复查 → 结果与运行记录；
4. 插件生命周期：安装或启用 → 校验 → 注册 → 加载 → 目录与发现 → 停用、卸载、升级时能力与界面同步撤下；
5. 后台：调度与监听 → Feed 与信号 → Inbox → 提醒与通知；
6. 搜索、@ 引用与放置：来源声明 → 索引 → 对象读取器 → 权限 → 打开位置；
7. 记忆：写入门 → 存储 → 召回 → 使用回执 → 在设置里查看与撤销；
8. CLI、安装与升级。

验收：每个能力只有一条实现路径；同一能力从界面、MCP、助理进入时，权限、错误和事件一致；一次调用有贯穿全链的调用标识，从界面上的报错能追到具体环节与原因；绕过统一入口的私有捷径删除，或登记理由与删除条件。

### 4.3 分层与边界

逐层核对 `docs/system/DEVELOPMENT-REQUIREMENTS.md` 的分层要求和 `docs/system/PACKAGE-BOUNDARIES.md`，每个包给出结论。至少处理这些已知问题：

- **横向服务承载业务规则**：`horizontal/memory` 负责写入门与自动写入决策，`horizontal/placement` 记录对象与工作的业务关系。按 `docs/system/ARCHITECTURE.md` 的定义，业务事实与规则归 Module；给出迁移方案，或修正分层定义并写明理由。
- **合同包里有运行时逻辑**：contracts 只放类型、Schema 和无副作用的小工具，其余移到对应的实现包。
- **宿主入口导出面过宽**（含多处 `export *`）：分清 Host 装配接口与普通消费者接口；模块不再把 Repository 当作公共出口。
- **工作台按包名引入所有插件**：能由声明得到的，不再硬编码。
- **两套能力机制并存**：旧的宿主能力注册表（`HostCapabilityDefinition`、`registerCapability`）与统一动作服务同时在用。给出收敛方案：对外能力只经动作服务注册、发现与调用；旧注册表退役，或只留宿主内部装配用途并写明边界。
- **宿主瘦身与 AI 层**：插件专属的业务逻辑移回插件包；每个插件各写一份的 AI 适配，收敛到宿主统一的推理端口；Agent Host 的合同保持精简；哪些能力下沉 Prologue、哪些留在业务层，按整理要求第 8 节判断。
- **留在工作台的 Goals 界面**，以及**实验线**（`server/`、`apps/server`、`packages/im-ui`）：给出归位或移出主线的判断。
- **测试大量直接引用包内部源码**：重构时测试先坏。改为经公共入口或测试端口，测试保护行为而不是内部结构。
- 依赖方向、循环依赖与深层引用用门禁守住；`pnpm boundary:check` 缺的规则补上。

### 4.4 类、方法与放置

逐包审查，交一张包级清单：公共入口、负责与不负责、主要文件及各自的变化原因、放错位置的类和方法、重复实现、建议的移动。判断标准：

- 一个文件、一个类只有一个变化原因；插件专属逻辑在插件包里，宿主只做组合与本机 IO；
- 方法放在拥有那份数据或规则的 owner 里，不在调用方另写一份；
- 路由、HTTP 处理器、界面渲染里不写业务决策；Store 和 Repository 里不发网络请求、不调模型；
- 一次性的逻辑不建抽象；三处以上的重复，判断是不是缺了抽象；没有第二个使用者的抽象，考虑删除。

文件长、层次多或代码相似，不能单独成为重构理由；避免万能 Service、无实际复用的抽象和只搬代码不改善职责的拆分。

### 4.5 巨大单元控制

1. **列清单**：超过 800 行的源文件、超过 300 行或超过 25 个方法的类、超过 150 行的函数。阈值可以按证据调整，写明理由。
2. **逐个按变化原因审查**：有多个变化原因的，按职责拆成可以单独测试的单元；单一职责但必然很长的（文案表、样式表、静态数据、生成代码），登记理由。
3. **先处理增长最快、被最多 PR 修改的**：例如助理服务、平台记忆服务、Prologue 节点适配器的初始化函数、Coding 的路由绑定、Pages 编辑器的挂载函数。
4. **门禁**：新增单元不得超过阈值；已登记的超标单元只减不增，变大即失败；接进 CI。现有的大文件门禁只统计已经退役的根目录 `src/`，要替换掉。
5. **文档**：重写 `docs/system/HUGE-CLASS-MIGRATION.md`，只记当前的单元、owner、判定与计划；历史记录移到归档。

### 4.6 扩展点与插件平台

- **装配统一**：构建期组合的内置插件逐个迁到 Plugin Runtime，按 Coding 一组的样板。先迁一个作样板（建议 Todo 或 Form），迁一个就删掉对应的宿主 `<插件>-actions.ts`、`<插件>-native-plugin-http.ts` 和工作台目录条目，同步缩减 `tests/builtin-plugin-assembly-gate.test.ts` 的冻结名单。
- **声明代替名单**：内置插件目录、导航、HTTP 路由（统一挂在 `/api/plugins/<plugin_id>/`）、翻译词典、样式、设置分区，尽量由 Manifest 推导；保留必要的装配与授权，不机械追求零配置。
- **MCP 旧适配退役**：`legacyMcp`、`LEGACY_FUNCTIONS_MCP`、`LEGACY_GOALS_MCP` 直接删除，不留兼容期；同步更新 goal-advance Skill、Runtime 接入说明和插件开发 Skill 里的工具名。
- **扩展点清单**：按方向列出「怎么加、现在要改几处、目标几处」：内置插件、第三方插件、服务集成、AI 能力与 Agent 角色和提示词、动作与消费场景、设置分区、底栏与侧栏与标题栏入口、搜索来源、记忆作用域、新 Module、新横向服务、新 Agent Runtime、界面插槽、界面语言、操作系统平台。目标：新增一个内置插件只改它自己的包和声明，不改宿主和工作台；其他方向各自写明合理的目标。
- **扩展性演练**：从 `PRODUCT.md`、`specs/BACKLOG.md` 和尚未实现的目标包（团队与权限、交换与同步、自动化、可观测性）里，选五到六个有代表性的下一个功能，推演在当前架构下要改哪些位置；超过目标的，补上扩展点或给出方案，再推演一次。用一个可移除的测试插件走一遍正式扩展路径：安装、发现、调用、升级、停用、卸载。
- **第三方插件**：用户自行安装插件的路径目前不存在。给出方案（安装命令、签名信任、市场入口、沙箱边界），不在本步实现。

### 4.7 多人并行开发

- **热点治理**：把每条需求线都要改的聚合文件改成各自登记：翻译词典、样式、外壳入口（底栏、标题栏、侧栏）、页面初始化、HTTP 路由、目录名单、设置分区，都由各自的包声明，外壳只读取登记结果。公共合同文件按领域拆分，减少无关改动挤在同一个文件里。验收看第 3 节的热点表是否明显下降。
- **归属**：在 SSOT 里给每个包或区域写明负责人或负责角色；共享核心（合同、内核、动作服务、Agent Host、外壳）的改动需要谁评审，给出方案（例如 CODEOWNERS），交我决定。
- **合同变更流程**：目前没有旧用户，本轮的破坏性变更不留兼容期。流程写清有了真实用户之后怎么做：合同版本、兼容期（读取兼容、写入严格）、消费者迁移、删除条件与合同测试，并用门禁守住。
- **公开 API 快照**：插件 SDK 与 contracts 的导出清单入库；导出一变就必须显式更新快照，并在 PR 里说明兼容影响。
- **已发布插件的回放**：本轮不为现有的生成插件和已安装插件保留兼容。把"合同或运行时变更时，用存量插件样本回放，确认仍能加载、升级和运行"写进以后的合同变更流程，并准备好回放工具。
- **CI**：在边界与合同检查之外，加一组稳定的产品用例子集，以非浏览器用例为主，加少量浏览器冒烟，写明时间预算。偶发失败进隔离名单，带负责人和期限。是否启用合并队列、要求 PR 评审，给方案交我决定。
- **协作规则入库**：多会话并行时形成的规则，例如合并顺序与冲突枢纽、Prologue SDK 合成包的打包与替换、构建与浏览器用例排时段、基线工作树比对、工作树清理，现在只在各会话的记忆里。写进仓库文档（例如 `docs/system/PARALLEL-DEVELOPMENT.md`），`AGENTS.md` 指过去。
- **PR 体量**：给出拆分规则；体量大的需求按包与层分 PR，先合合同与扩展点，再合实现。
- **反馈速度**：量出全量构建与全量测试的时长；能按包增量构建、单独跑某个包的测试。测试执行器现在是串行的，逐个消除必须串行的原因（共享端口、共享 Home、共享浏览器），给出时间预算。
- **新成员上手**：从零安装到跑起预览和测试的步骤与耗时写成文档并实际走一遍；只在 macOS 上能用的部分写明。

### 4.8 改需求、修 bug、调交互的便利

- **前端**：浏览器代码接入打包与类型检查，先用一个插件跑通再逐个迁移；每个界面有自己的客户端模块；页面里的状态归属和自定义事件名统一登记；共用设计系统的原语与 token；删掉被覆盖的旧皮肤，用多宽度、浅深色的截图对比守住视觉不变；组件板 `/__ui/catalog` 是组件的唯一展示处。
- **可诊断**：结构化日志与调用标识贯穿主链路；错误统一类型与错误码前缀，保留原因；不吞错、不假成功，空 `catch` 改为有处理或有记录。
- **测试可改**：测试经公共入口；合同测试守模块边界，端到端测试守用户动线；重复的测试工具收进 `packages/test-kit`；快照只用于确实要冻结的输出。
- **需求可追溯**：spec 的验收编号能在测试名或测试说明里查到，改需求时知道要改哪些测试。
- **页面资源预算**：每张页面下发的样式与脚本体积、首屏时间设上限，在 CI 检查，防止每加一个插件页面就变重。
- **文案与翻译**：翻译词典以中文原文为键，改一处文案就会让译文失配。改为稳定的键，或加检查保证改文案时同步译文。

### 4.9 体检报告与第一步清单逐项闭环

### 4.10 本轮新合同的全链路

Manifest `methods`、撤销声明、到期提醒、后台任务回报、放置协议、搜索来源与对象读取器、页面操作卡、情境片段推荐、记忆、侧栏文件来源与浏览器、插件通知等，每一项沿「定义 → 注册 → 发现 → 调用 → 授权 → 执行 → 返回」走一遍，并验证停用、卸载、升级与撤权。每项都要有至少一个真实消费者、有守住它的测试、写进插件开发 Skill；没有消费者的合同删掉或标明未启用。动态交互对动作合同与内核的改动，按 `specs/action-architecture/spec.md` §3 基本合同复核，并同步那份合同文档。

- **数据库**：每个库、每张表只有一个 owner；只有一份当前 schema 的建库代码，带版本号；版本不符时明确拒绝；不跨 owner 直接读写表。迁移的处理见第 4.1 节。

### 4.13 门禁

把稳定、重要、适合自动验证的要求纳入门禁并接进 CI，至少包括：兼容逻辑不回流、静态检查的最小规则集、公开 API 快照、页面资源预算、巨大单元只减不增、内置插件装配名单只减不增、分层与依赖方向、测试不得新增对包内部源码的引用、vendored 包数量、`specs/` 根目录的 spec 必须有状态句、contracts 不得有占位 subpath、浏览器脚本必须经打包与类型检查、Skill 里引用的路径与接口真实存在。每道门禁都做一次突变验证，证明它真的会拦。依赖业务判断的规则写清方法与示例，不变成脆弱的字符串检查。

### 4.14 开发手册与 Skill

开发者和编码 Agent 都按 Skill 与手册写代码；它们落后于代码，就会把旧做法复制到新代码里。

- **清点**：`skills/` 下的全部 Skill（goal-advance、molis-plugin-dev 及其各分册、molis-prologue-ai）及其 `agents/` 配置、Coding 的方法包、`.cursor` 下的规则与链接、`AGENTS.md`、`docs/system/DEVELOPMENT-REQUIREMENTS.md` 与各包 README 的「开发要求」、`docs/platform/` 手册。
- **运行时消费者**：插件创作台在运行时挂载插件开发 Skill，改这份 Skill 就是改生成插件的做法，要用创作台的离线回放或真实生成验证；goal-advance 随安装发到用户的 Runtime；方法包由 Agent Host 加载。
- **一致性**：Skill 里写的接口、字段、路径和命令在当前代码里真实存在，示例能编译或运行；稳定的部分做成检查，接进门禁。多份 Skill 之间不矛盾。
- **覆盖**：本轮的新合同、新分层、新门禁、第 4.5 节的巨大单元规则、第 4.7 节的协作规则，都有对应的章节。
- **补缺**：按开发场景补指南：新增 Module、新增横向服务、宿主组合、前端界面开发（设计系统、客户端模块、组件板）、测试与回归、多人并行开发。手册解释架构与示例，Skill 指导执行，互相链接，不复制。
- **给编码 Agent 的护栏**：Skill 里"照着抄"的样板只指向已经整改过的插件，否则旧做法会继续被复制；`AGENTS.md` 保持简短，每条硬约束都有对应的门禁或测试；PR 模板与评审清单与本次的规则一致。
- `AGENTS.md` 的"先读哪里"覆盖以上全部场景；路径、链接与触发说明用代表性开发场景走查；`skills/` 在全量回归期间不改。

### 4.15 概念与命名

- **术语表**：动作、能力、判断函数、方法、Skill、消费场景、行为、Character、角色、Agent；Project 与 Board；插件 id 与显示名不一致的情况。每个概念一个名字、一个定义，写进 `docs/` 的术语表；同义概念合并，代码命名随之统一。

### 4.16 代码规范与静态检查

- 仓库没有统一的格式化与静态检查工具。引入一套，先用最小规则集覆盖确定的问题：未处理的 Promise、空 `catch`、新增 `any` 与 `as unknown as`、遗留的调试输出；接进 CI，按包逐步开启，不一次性大改格式。
- TypeScript 已开严格模式，所有包继续继承同一份基础配置。
- 非 TypeScript 代码同样纳入：桌面端的 Rust 用 clippy 与 rustfmt，原生素材处理的 Swift 和各类脚本也要能构建、能检查。

### 4.17 依赖与 Prologue SDK

- **第三方依赖**：清点未使用的、重复版本的、过期的和有安全公告的依赖；Node 与 pnpm 的版本在本地、CI 和发布中一致。
- **SDK 补丁漂移**：当前用的是打了二十多个补丁的预发布版，每条需求线还会再叠一个补丁包。给出收敛方案：补丁合回 Prologue 上游，以上游版本为基础，合成包只有一个流程、一个负责人。向上游推送先问我。
- **公开仓库里的私有包**：仓库是公开的；vendored 的私有包能否随仓库分发，交我决定。

### 4.18 安全不变量

把安全边界写成不变量，每条写明代码位置，并有测试守住：本机控制入口（只绑回环、控制令牌、Origin 校验、一次性操作键）、MCP 逐客户端授权、插件权限与沙箱、密钥只给引用、浏览器与 Computer Use 的站点策略与确认、记忆与网页内容的提示注入防护、外部输入的路径与 URL 校验。推送前做密钥扫描。

### 4.19 C 端就绪：只出方案

自动更新、崩溃上报与可观测性、在线备份、公证签名、跨平台桌面、生成插件沙箱不依赖 `sandbox-exec`、减少私有 vendored 依赖，都是新能力，不在本步实现。给出方案、成本、依赖和建议顺序，交我决定。

## 5. 执行顺序与验证纪律

**顺序**：先止血，再治理。

1. **门禁先行**：静态检查的最小规则集、公开 API 快照、巨大单元与装配名单只减不增、分层与依赖方向、测试不新增内部引用、vendored 包数量、spec 状态句，先接进 CI，防止边整理边恶化；
2. 真实缺陷与权限、状态问题，契约与接入遗漏；
3. 清除兼容逻辑（第 4.1 节）：先处理真实 Home 的安全，删完接上防回流的门禁；
4. 冲突热点与调用链；
5. 分层与边界迁移；
6. 巨大单元拆分与插件装配统一，按片推进；
7. 共享与 SDK 提取、清理；
8. 手册、Skill 与协作文档。

**每一片**写明真实问题、证据、新边界、兼容成本、受影响的行为与测试；改完重跑受影响的跨功能场景与用例，并更新第 3 节的度量。

**分支与 PR**：从最新 main 开分支，一个 PR 一个主题，不积累大量未验证的重构。合并前变基到最新 main，并重跑相关用例。

**测试**：不跳过、不放宽、不删除关键断言来换取通过。测试保护行为与协议，不冻结偶然实现。迁移代码时同步迁移测试的入口，不让测试继续调用退役的实现。

**回归纪律**（仓库已经踩过的坑）：

- 改过任何 `*/src`、`scripts`、`package.json` 之后，跑全量前先整体 `pnpm build`。单包构建写成 `pnpm --filter <包> run build`，`--filter` 放在 `run` 之前。
- 全量回归期间不改源码、脚本、`package.json` 和 `skills/`，只改 `docs/`、`specs/`。不并发构建。
- 保留完整输出。判断是否新引入，用干净基线工作树（`git worktree add --detach`）跑同一批文件对比。
- 停进程只按 pid，不用 `pkill -f scripts/run-tests.mjs`。
- 浏览器用例在 macOS 本机 Chrome 上跑，加 `--lang=zh-CN`。
- 有其他会话同时在跑时，构建与浏览器用例串行排时段。

**环境与协作**：用隔离 Home（`MOLIS_WORK_HOME` 指向临时目录，`MOLIS_WORK_SECRET_BACKEND=file`），不占用真实 Home 4207/4208 的 Agent 运行锁。跨仓修改 Prologue 前确认 SDK 工作区和其他负责人的范围。不重置、不覆盖别人的未提交改动。

## 附录 B：仓库系统整理要求要点

全文见 `docs/prompts/repository-systematic-review.md`，以全文为准。第 12 节关于保留历史迁移样本的要求，以及其他要求保留历史的条款，由本步"不留兼容逻辑"取代。

1. **现场与归属**：读规则、协议、spec 与 Skill；查分支、工作树和他人任务；保护他人成果，不提交混杂改动；一份简洁总 spec；产品语义、公共契约、重大迁移先给方案。
2. **清单与预期行为**：清点全部 App、Host、Plugin、Module、共享包、后台任务、外部协议与 SDK；每项的场景、入口、成熟度、owner、注册与发现、调用链与测试、重叠关系；区分生产、实验、部分实现、弃用；新旧实现是否并存、消费者是否迁移完。
3. **模块划分与调用链**：职责是否清晰，是否切得过碎或混了不同生命周期；沿「输入 → 身份与权限 → 编排 → 领域 → 存储或外部 → 事件 → 反馈」追踪；包、文件、类、方法和函数是否属于正确 owner；查 App/Host 混入业务、UI 做状态转换、Store 混入网络与模型、插件重复通用能力、跨模块 SQL、循环与反向依赖、无意义包装、入口之间行为不一致。
4. **契约与注册**：每项要求的来源、范围、验证方式；应开放的能力是否注册、有入口、Schema 与错误和权限准确、能被发现调用、与 UI 共用路径，停用、卸载、升级、权限变化后状态正确；Manifest 与真实行为一致。
5. **自动发现与扩展**：沿「安装 → 校验 → 注册 → 加载 → 目录 → 发现 → 筛选 → 调用 → 结果」验证；权威来源唯一，没有重复静态名单；刷新与缓存失效；项目与账号隔离；重名、版本不兼容、部分失败；单个插件失败不阻断其他。
6. **逐插件**：用户任务闭环；占位与半实现；协议与入口；持久化与产物；越界依赖；重复能力；生命周期；撤权、失败、取消、并发、恢复；空数据、首次、无模型；同类插件横向比较；组合场景；平台接点（导航、搜索、命令、设置、连接、权限、通知、活动、执行历史、产物预览、后台任务、取消、恢复）。
7. **数据、状态、事件、生命周期**：每类事实唯一 owner；状态机；身份传递；多窗口与多进程；事务、幂等、部分成功；取消与完成、删除与执行、撤权与副作用之间的竞争；重试与恢复；孤儿数据；事件命名、载荷、时序与消费者响应；订阅、定时器、进程的创建、释放与恢复。
8. **AI 与 Prologue**：清点全部生产 AI 入口，核对真实调用链；模型与凭据、上下文、工具、身份、权限、审批、副作用前检查、预算、usage、事件、超时、取消、持久化、恢复；查供应商直连与旁路；工具能被理解和正确选择、按需发现；自动发现不绕过授权。
9. **前端质感与动线**：层级、布局、一致性；主次与危险操作；弹窗、抽屉、标签与页面的选择；窄屏、长文本、焦点、键盘、可访问性；加载、空、失败、部分成功、无权限、离线；闪烁、跳动、输入丢失、重复提交；用户路径与引导；跨页面保留上下文；前后端状态一致；用真实界面与截图验证。
