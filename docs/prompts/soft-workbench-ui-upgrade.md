## 2. 不可偏离的体验方向

**全局结构必须保留底部统一对话栏和菜单栏。** 不得改成全局左侧导航，也不要产生多个相互竞争的全局对话入口。以现有 `renderWorkbenchBar` 的真实能力为基础：左侧菜单与插件入口，中间插件上下文及统一输入，右侧会话、项目和账户等控制。具体分区可打磨，功能和可达性必须保留。插件内部的目录、树、列表与详情可以采用适合其任务的分栏。

设计重点是“组合起来依然精致”，不能只让单个按钮好看：

- 珍珠灰背景、连续白色工作面、石墨色主操作，正文和辅助信息有清楚的层级。通过间距、字重、表面色和有限的分隔线组织内容，减少重复外框、嵌套卡片和装饰性标签。
- 温暖与冷色的柔和光感集中用于 Onboarding 和适合的抬升表面；不要把整个业务系统铺成渐变。阴影表达浮层与深度，边框表达边界，避免每个容器同时使用重阴影、描边和底色。
- 字体以获认可原型的系统无衬线与中文观感为基准，建立正文 400、控件与条目 500、标题 600 的角色层次，并统一字号、行高、字距、数字和等宽文本。视频的确切字体尚未确认，不得声称已识别或已获指定某个字体品牌。
- 统一圆角、控件高度、图标尺寸和线宽、触达面积、间距、内容最大宽度、分栏比例、层级、滚动区域与底栏避让。缩略预览中的微小字体不是正式产品字号规范；正式界面以可读性和可操作性为先。
- 微交互需要服务操作结果：悬停、按压、选择、输入聚焦、菜单展开、浮层进出、状态切换、加载与完成应有一致反馈。参考原型约 130ms 的按压、250ms 的状态变化、420ms 的内容进入，以及 Onboarding 的方向性转场，按正式场景调整，不机械复制时长。
- 保留键盘与可见焦点、可访问名称、合理的焦点返回和减少动态效果设置；满足适用的 WCAG AA 对比度要求。动效不能阻塞输入、造成晕动、丢失上下文或让高频操作变慢。
- 保留当前支持的浅色、深色、跟随系统、密度和语言能力，建立语义一致的对应方案，不能只完成浅色中文版本。

效率型页面保持必要的信息密度，编辑器、阅读页、树和画布、时间表、文件与代码工具保留各自适合的结构。统一设计语言不等于把所有插件改成同一套卡片列表或 Dashboard。

## 3. 全覆盖：所有存量插件，所有页面

这是一条硬性范围和验收条件：**所有存量插件都必须适配，所有页面都必须适配。** 首页、Goals 和 Feed 是视觉参考与早期验证切片，不是本次交付范围的上限。

先从插件目录、manifest、实际注册表、UI Contribution/Slot、路由、客户端入口及生成插件渲染链路交叉建立完整清单，不能只按照菜单当前显示的项目盘点。覆盖内置插件、仓库维护的 app/integration 插件，以及现有生成插件和已安装插件的可适配 UI。没有独立页面的插件也要核对其设置、授权、配置、状态、错误与贡献界面；确实没有 UI 的条目标注事实和原因，不虚构页面。

逐个插件盘点并升级：主页面、子页面、详情、创建和编辑、设置、搜索与筛选、历史、预览、弹窗、抽屉、上下文菜单，以及通过深链接、权限变化、内容类型或二级操作才出现的界面。正常、空内容、加载、错误、禁用、权限不足、断连、重试和恢复等状态，按实际功能覆盖。不能因为页面少用、入口深、插件不常启用或样式独立，就将其排除。

范围包括且不限于：

- 项目首页与项目管理、底部菜单和统一对话栏、插件切换、会话与历史、全局搜索、偏好设置、账户与权限、集成配置、通知和后台状态等现有全局界面。
- Goals、Feed、Inbox、Pages、Shelf、Functions、Schedule、Workflows，以及文件、产物、表单、数据集、图片、PPT、Coding、Runtime、Git、Diff、终端等当前实际存在的插件与相关页面。
- Plugin Builder、插件管理/市场/升级、生成插件的预览和正式运行、个人工具及其他实际注册插件。以上举例不是白名单，实际清单必须完整。
- Onboarding 的全流程、分支和返回用户路径，以及当前支持的桌面和 Web 界面中受此次升级影响的部分。

对于已有生成插件，应由共享渲染器、组件目录和兼容机制让存量定义获得新外观，不能仅修改未来生成的提示词。保留原 manifest、用户配置、数据、动作和授权；确需兼容迁移时，先说明必要性和可恢复方案。外部不可控页面或受隔离边界约束的嵌入内容，应升级宿主界面并明确记录可控范围，不能绕过沙箱，也不能冒称已改造其内部 UI。无法访问的存量插件需列为具体缺口，不得从分母中删掉。

在同一份迁移清单中记录「插件/模块 → 页面或视图 → 现有能力与关键状态 → 适配位置 → 验证证据 → 剩余问题」。清单要可核对、可继续推进，避免为了流程重复建立多份状态系统。任何页面未适配或关键路径未验证，都必须如实列出；不能宣称“全量完成”。

## 4. 建立正式设计系统与可操作组件板

沿用现有 `@molis-ai/molis-work-design-system`，将获认可的方向落在共享实现中。先核对这些当前入口，再按实际代码调整：

- `packages/design-system/src/palette.ts`：配色与语义色。
- `packages/design-system/src/visual-foundation.ts`：主题、密度和表面层次。
- `packages/design-system/src/typeface.ts`、`fonts/`：字体与资源。
- `packages/design-system/src/primitives/`、`src/styles/primitives.ts`：共享控件和组合。
- `packages/design-system/src/primitives/catalog.ts`：组件板，开发入口 `/__ui/catalog`。
- `packages/design-system/src/icons.ts`：现有图标体系。
- 共享动效样式及 `src/styles/craft-finish.ts`：检查、整合现有反馈与动效。
- `apps/workbench/src/page-assets.ts`：样式注入与最终层叠关系。

已发现的冲突必须实际解决：`typeface.ts` 中 `html body * { font-weight: 400 !important; }` 会压平字重层次；旧 README 仍规定“一律纯色，不用渐变”和默认 400 字重。请协调代码、字体资源、设计规范和消费者，替换冲突规则。不要通过新增一层 `!important` 或每个插件私写覆盖样式来对抗旧规则。

字体需验证中英文混排、真实字重覆盖、回退、离线加载与布局稳定性。系统字体按平台使用；需要打包的字体核对许可并维护资源说明，不把受限系统字体直接复制进仓库。代码、终端和 diff 保留合适的等宽字体。

组件板必须使用真实生产组件，覆盖现有按钮、输入/文本域、搜索、选择器、复选/单选/开关、标签页/分段控件、列表/树/表格、表单校验、工具栏、菜单、提示、Popover、Dialog/Sheet、Toast、进度/加载/空态/错误态，以及日期、颜色、范围、上传等实际存在的控件。补齐相关变体和交互状态，不为凑数量发明没有使用场景的组件。

组件板还要展示组合后的效果：列表与详情、工具栏与筛选、带错误的表单、对话框内的菜单、长内容和嵌套滚动、底栏与浮层、窄窗口与密度切换。组件和组合都可以实际操作，避免成为静态样式陈列。组件板是开发工具，不增加到普通用户的产品导航中。

保留当前 HTML Slot/string renderer、`render*` helper、`.mw-*` 和 `data-slot` 等架构约定。Design System 管视觉和控件，Workbench 管全局壳与装配，UI Host 管挂载、隔离和生命周期，插件维护自己的业务视图与能力。不要借 UI 升级重写成另一套前端框架，也不要把插件业务搬进共享组件包。

## 5. Onboarding：还原体验，接上真实流程

重点复现获认可原型和视频的体验：横向窗口、问题与选项、联动的小型产品预览、石墨色选中态和明确勾选、克制的进度提示、柔和光感、前进与返回有方向感的转场，以及完成后自然进入工作台。

正式步骤必须由当前真实 Onboarding 的目标与依赖决定。先核对语言/外观、项目创建或选择、Runtime 连接、授权、通知、其他必要配置等已有步骤与分支，再将该交互语言应用到它们。不要把原型的演示步骤顺序、假连接或脚本状态直接当成正式业务流程。

保持真实的返回、跳过、重试、取消、继续未完成流程、偏好保存与完成状态；验证刷新和重启后的恢复。已完成引导的老用户不能因换 UI 被强制重来。OAuth、系统权限、Runtime 和真实连接状态必须来自原有能力，不能用好看的成功页掩盖尚未完成的操作。

统一对话栏继续使用真实上下文与执行状态，清楚表达当前项目/插件范围，以及已有的等待、流式输出、停止、失败和重试。升级不能重建组件时丢失草稿、选区、滚动位置、会话、运行任务或终端状态，也不能把真实 AI 替换成演示回复。

## 6. 功能无损的具体含义

开始前建立现有功能基线，升级后逐项证明对应能力仍然存在且有效。外观和信息组织可以变化，但必须保留：

- 现有入口及等价可发现路径、操作、快捷键、路由/深链接和跨插件跳转。
- API、Action/Capability、权限和确认语义、插件契约、Manifest/SDK 兼容性以及业务 owner 边界。
- 用户数据、标识、历史、草稿、偏好、已有连接与凭据、导入导出、持久化和升级行为。
- 现有真实业务结果、错误反馈和恢复能力，以及跨插件、后台执行和重启后可观察的状态。

不得用删除入口、隐藏复杂功能、禁用按钮、占位实现、假数据或吞掉报错换取整洁界面。比如记录普通进展不能顺带将 Goal 标成完成，换 UI 也不能改变执行回执、幂等或权限语义。

优先保持业务与数据契约不变。确有必要调整接口或状态时，先在需求书中说明具体原因、影响、兼容和验证，再按已有授权范围实施；与 UI 无关的架构重构和新业务功能不夹带进入。无需数据迁移时，不额外建迁移框架。

使用真实代码路径和隔离测试数据验证读写、持久化及后续结果。需要外部账号或副作用的集成，遵守实际授权；依赖缺失时列出未验证项并继续其他工作，不能伪造通过。外观截图、mock、构建成功和测试数量都不能单独证明功能无损。

## 8. 实施顺序与工作边界

1. 检查工作树、分支和已有修改，读取适用规则与当前实现。保护用户及其他任务的成果，不重置或覆盖无关改动。核对当前启动实例与构建方式，避免清理共享产物或重启服务干扰正在使用的产品。
2. 建立正式升级的独立需求书，例如 `specs/archive/soft-workbench-rollout/spec.md`，并在同目录维护全量页面/插件迁移清单。原型 spec 继续记录原型，不将它混作正式升级验收。写清目标、范围、功能基线、模块责任、验证与真实开放问题。
3. 在正式实现中先打通字体与 token、基础控件、底部全局壳和一个完整业务切片，实际观察组件组合与真实行为。这个切片用于及时发现系统性问题；验证后继续剩余全部范围，不新增等待我确认的默认关卡。
4. 按依赖顺序迁移所有插件与页面，包括独立样式、动态注入、弹层及生成插件。每完成一组就核对清单与回归，不能单凭全局 token 改变便认定所有页面适配成功。
5. 完成正式 Onboarding、组件板、开发 Skill、生成链路和文档；收敛过时样式与相互覆盖规则，只清理本次替换且已确认无消费者的实现。
6. 进行全量范围复核与真实场景验证，处理本次引入的回归，最后交付可体验版本、证据和确实剩余的缺口。

使用实际适用的设计/前端 Skill，但本任务已明确的用户方向与授权优先于其默认流程。常规可逆取舍自主推进；仅对会实质改变功能、范围、成本或权限且无法从现有信息确定的事项提问。不要因为任务长就主动缩减范围。

本任务目标是完成本地正式升级及验证，不自动扩展为对外发布、远程部署、替换用户已安装应用或发送消息。

## 9. 验证与完成标准

验证分为工程、功能和体验三个方面，缺一不可：

- **工程**：依据当前 package scripts 与模块 README，执行相关类型、包边界、构建和回归检查。现有根命令包括 `pnpm typecheck`、`pnpm boundary:check`、`pnpm build`、`pnpm test:run`；选择和编排时核对其真实作用，避免并发清理同一构建目录。验证运行页面实际消费的新产物，不能只修改源码却继续截图旧版本。
