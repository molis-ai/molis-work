## 5. 一个任务的流程

```text
统筹：写任务书，派
  ↓
开发：领取（只推分支）
  乙档：在 #1332 贴【方案】 → 接着写代码；要先问的那一部分等【统筹答】
  ↓
开发：自测、自审 → 开 PR（直接 ready，不开 draft） → 马上贴【交接】，不等 CI
  ↓
Codex：一审 + 验证（验证结论等 Verify 出来；Verify 红就退回开发）
  全是小问题 → 自己修 → 贴【一审 已小修 @新头】
  有大问题   → 贴【一审 要改】 → 开发修 → 贴【修复】 → Codex 只看增量
  ↓
二审会话：自己领走，贴【二审】；统筹同时给 full=true 的排 Full
  二审要改 → 开发修 → 【修复】 → Codex 增量一审与验证 → 二审增量
  ↓
统筹：合并 → 贴【合入】；远端分支由 GitHub 自动删，开发删本地工作树
```

**接力棒。** 一个分支任一时刻只有一方能推，由最后一条阶段评论决定：

| 最后一条阶段评论 | 谁能推 |
| --- | --- |
| 领取、【统筹答】、【一审 要改】、【验证 失败】、【二审 要改】 | 开发 |
| 【交接】、【修复】 | Codex，只做小修 |
| 【一审 可进二审】、【一审 已小修】、【验证 通过】、【二审 可合】 | 没有人；要合 main 时由统筹在【统筹答】里指定 |

**小修的边界。** 下面几条全满足才算小问题：
- 不改行为、断言和合同；
- 不改门禁文件和数字；
- 只动这个 PR 已经改过的文件；
- 合计不超过 30 行。

例如：错别字、注释和文档措辞、测试名里漏的验收编号、lint 告警、PR 正文缺的节。有任何一处大问题，就整单退回开发，Codex 不动手，小问题也列在里面让开发一起修。

**加急。** 看板「加急：」一行列出的任务（挡着别人的，例如 CI 装依赖）：开发先修它，Codex、二审先看它，统筹先给它排 Full。`next.mjs` 把它排在最前，并标「加急」。

**二审的 [建议] 去哪里。** 不为每条建议开一份新任务：
- 只动本 PR 已改的文件、是措辞、注释或小改的：开发在同一轮【修复】里一起改。PR 已经可合、只剩这类建议的，照合，建议记进统筹的零碎单。
- 指向别的文件或要另外查证的：统筹每天收一次，攒成一份丙档的「零碎」任务。
- 像是别处还有同样缺陷的：原开发在【修复】里只读核一下，写出结论；是缺陷，统筹再开任务。

**交接前自查**（所有开发都做，本机线甲档尤其；写进【交接】）：
1. 同一种写法别处还有没有：grep 你改的那个模式，范围内的都改了，范围外的列出来。
2. 测试真能证明验收：去掉产品改动测试会红（贴先红的输出）；断言打在验收说的那件事上，不是旁证。
3. PR 正文、spec、注释里每一句讲行为的话，都在代码里核过；涉及状态的，每种状态都过一遍（running、crashed、quarantined、disabled……）。没核的写「没核」。
4. 改的文件有没有在途 PR 也在改：文件多的 PR 用 `gh api --paginate repos/molis-ai/molis-work/pulls/<号>/files` 查，`gh pr list --json files` 每个 PR 最多只给 100 个文件，会漏。
5. 本机线：交接前用本机的 heavy.sh 把任务书第 7 节的测试文件和 affected-tests 给出的非浏览器文件跑一次（本机一个槽，排队），结果写进【交接】；浏览器用例和全量留给 Codex 和 CI。

**推一次就重跑一次 CI。** 每推一次，PR 上正在跑的 CI 会被取消重来（约 20～25 分钟）。修复攒齐了一次推，不一条一推。

**合 main。** main 有合并队列（squash，最多 5 个一起建、一起验），PR 不用追 main。只在两种时候合：有冲突，或统筹在【统筹答】里要求。合法：`git merge origin/main`，不 rebase 已推的分支，不 force push。`tooling/gates/baseline.json` 冲突时重跑 `node scripts/check-health-gates.mjs --update --base origin/main`；`tooling/gates/api/`、`tooling/gates/actions/` 冲突时先 `pnpm build` 再 `pnpm api:update` / `pnpm actions:update`；不手合。合完重跑门禁和任务书的测试，推上去后贴【修复】，注明「只合 main」。

**评审沿用。** 一审、验证、二审都写明头。合 main 之后 PR 自己的补丁没变（`git patch-id` 相同，`next.mjs` 自动比），原来的结论照样算，只等新头的 Verify；补丁变了（解了冲突）就只看变的部分。

**防打转。** 一个任务的「要改」（一审、验证、二审合计）到第 3 次时，统筹介入：改任务书、拆小，或收回本机做。

## 7. 二审看什么

一审看任务书有没有做到、代码对不对。二审在一审之上再看：

1. 任务书本身对不对：统筹写错的地方在这里抓。
2. 防腐后果：每项事实只有一个主人；没有兼容层；数字只降不升；没有给某个插件开私路。
3. 与其他在途 PR、刚合入的 main 有没有相互影响：撞文件、撞号、撞语义。
4. 一审的意见都落实了；豁免的有理由。
5. 验证的证据和当前头一致；`full` 的判断对。
6. 账目：spec 状态句、BACKLOG、PR 正文的各节。

本机线、设备 A 的 Claude 和 Codex 自己的任务、丙档没有一审，二审连一审的清单一起看（前三种用 Opus，丙档用 Sonnet）。

## 8. 合并

只有统筹合并。下面几条要在同一个头 H 上都成立（`next.mjs --role coord` 逐条核，齐了给出合并命令）：

- CI `Verify` 绿；
- 【一审】可进二审，或已小修且新头就是 H（没有一审的档位除外）；
- 【验证】通过；
- 【二审】可合；
- `full=true` 时，Full 在 H 上通过；
- 碰了安全不变量的测试或登记表时，不挡合并的 `security-invariants` 作业在 H 上绿，统筹手查过；
- 没有未答的【问统筹】。

第 5 节「评审沿用」认的结论，算在 H 上。

```bash
gh pr merge <号> --match-head-commit <H 的完整 sha>
```

合并方式由合并队列决定，不加 `--squash`。入队后回读 main 上的合并提交，再贴【合入】。LINES 一天记一次，不逐个记。

用户 2026-10-28 在统筹会话里授权：「二审可合、第 8 节条件都齐的任务 PR，统筹可以直接合并」。只在统筹会话里合；工具层的拦截不绕开，被拦时统筹告诉用户，由用户就那一个 PR 点头。

- `full` 由 `node scripts/affected-tests.mjs --base origin/main --json` 的 `full` 字段定。
- CI Full 只由统筹排。PR 上加 `full-suite` 标签跑一次（同一个头要整份再跑，先去掉标签再加），16 片、同时占 6 个 runner、约 30～35 分钟。几个 PR 一起时进一条 `integration/**` 承载分支，占 10 个 runner。取消任何 CI 都要用户本人同意。

**runner 预算**（2026-10-28 晚起）。组织一共 20 个并发作业，至少留 8 个给 `Verify` 和合并队列：

- 所有 Full 合计不超过约 12 个 runner。要么一条承载分支，要么最多两个 PR Full，两种不混：承载分支在排队或在跑时，不排 PR Full。
- 承载分支同时只一条。同一批的子分支（`…-c`、`…-c2` 这类）也占这一条的名额。它在排队或在跑时不往它推（会取消它）。
- PR 的 CI 有 3 轮以上在排队（`gh run list --workflow ci.yml --status queued`，一个作业都还没开始）时，也最多一个 PR Full，先把 runner 让给 PR 的 CI（2026-10-29 加：10-28 晚上两个 Full 占 8 个 runner，PR 的 CI 一轮约 20 分钟、排着 67 个作业）。已经在跑的 Full 不取消，跑完不补第二个。
- 晚高峰（本机 18:00～23:00，即 UTC 10:00～15:00）最多一个 PR Full。这段时间两台设备都在推，合并队列也最忙；不急的承载分支挪到这段之外。
- 什么时候排：`full=true` 的 PR，一审过了、同头 `Verify` 绿了就排，和验证、二审并行。`Verify` 红的头不排；一审「要改」的，等改完的头。
- `next.mjs --role coord` 按这几条给「排 Full」，或者「待排 Full：等…」。

**Full 红了，先归因再动手。** 合并标准不变：`full=true` 的，Full 要在 H 上通过。

1. 先看红的文件和本 PR、本批的改动有没有关系：affected-tests 的列表、改了哪些文件、错误信息。有关的，回给作者修，修完攒成一次推。
2. 无关、像偶发的（重试才过、超时、`CDP timeout`、`Navigation did not finish`），只重跑失败的作业：`gh run rerun <run> --failed`。不去掉标签再加，那会把 16 片整份重跑。
3. 同一个无关的文件第二次红（同一个 PR 或别的分支上），不再重跑第三次。统筹开加急的零碎单修这个文件（像 BL-806、BL-807 那样）；这个 PR 等它合入，合一次 main 再跑。
4. 「main 也红」以 main 的夜间 Full（`schedule` 那次）为准。只在承载分支或 task 分支上红、main 夜间不红的，先怀疑分支里的内容，不当作底噪。T-036 量到的 `CDP timeout` 多数出在几条承载分支上。不过 main 夜间跑 `--bail`，重试才过的那次失败日志里看不见，所以「main 夜间没有」只说明下限。

**承载分支。** 推之前，上一次 Full 红的文件先在设备上修好、跑过（设备 A 的浏览器用例在 `machine-slot` 里跑），一轮修复只推一次。连着两次红在本批没碰的文件上，先按上面第 4 点归因，不接着推。

**其他。**

- 任务书里写「留给设备 A 的验证」「设备 A 实跑浏览器」的，2026-10-29 起都由设备 B 上的验证线（Codex）跑；开发自己要跑的浏览器用例仍按派给的设备。

## 11. 上限

等评审、等验证的 PR 数不挡开发领下一项。按 2026-10-31 本机 Codex 接续规则，作者、一审、验证、二审分别由独立上下文承担；会话按职能线组成可复用池，每线可有多个会话；阶段结束后接下一单，不再为每个任务新建会话。每会话同时一单，同一 PR 不兼任作者/一审/验证/二审；增量优先回原阶段 owner，需转交由根明确。不同 PR 可以并行，独立 session 与子代理均可用；根会话核结果后统一发布，按 §8 合并。旧设备/模型分工见历史，不能覆盖本节现行规则。

留下来的上限：

- 每台设备开发中最多 4 项（用户 2026-10-29 定 3–4 项，原为 1 项）。在等【方案】批复或【问统筹】答复的不算，可以先领下一项。

- 修复永远先于领新的。
- Codex 的顺序：先看【修复】（增量），再按交接时间看新的【交接】，然后是 main 变红，最后才做自己的任务。
- 同一枢纽文件同一时间只给一个在途任务，写在看板「锁定的文件」列。枢纽名单见 `docs/system/PARALLEL-DEVELOPMENT.md` 第 2 节。追加行的文档（`specs/BACKLOG.md`、spec 进度行）例外：只加、删自己的行，合 main 时两边都留。
- 一个 PR 一个主题，不超过约 50 个文件，最好不超过 15 个。
- 整台机器的构建、浏览器用例各一个槽（`node scripts/machine-slot.mjs`），CI Full 的并发照第 9 节；去掉的只是等评审的 PR 数，不是同时开更多重型进程。


- 做完一件事就跑一次，按它列的顺序做。只读它给的那条评论和那个 PR。
- 没事可做时跑 `--wait`：它在 shell 里每 3 分钟查一次，有事才返回，等的时候不花模型的 token。harness 的单条命令有时限的，把 `--max`（分钟）设在时限以内，返回「无事」就再跑一次。
- 每天开工、换任务前重新取一次 `next.mjs`，它也可能改。
- 状态全在 GitHub 上，会话可以随时换：DeepSeek 每个任务开一个新会话；Codex 和二审上下文用过一半就重开，从 `next.mjs` 接着做。
- 统筹用 `--role coord --wait --new <文件>` 在后台挂着，只有新事才醒；最多 4 小时醒一次兜底。
