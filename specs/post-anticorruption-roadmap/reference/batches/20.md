## 给人讲清楚

后面要让 AI 为你配好场景、甚至生成新的交互页面，前提是平台先有一套公共规矩：角色、设置、场景怎么描述，生成的页面怎么运行、保存、恢复，插件又允许被怎样配置。这一批先把这套规矩定下来，也包括官方场景包（Molis Work 自带的几套现成做法）怎样声明。你基本看不到界面变化。需要你做的：如果规矩影响到交互方式，会做样给你看。

### 二、「只有声明的插件」形态（第 08 批）的现状

[技能包需求](../../../skill-packs/spec.md) §3、§4 和 [插件平台 v2](../../../plugin-platform-v2/spec.md) S1（PLP-01）都写好了：没有运行时的插件，走同一条安装路径。代码还没跟上：

- **一定要有入口**：SDK 解析时拒绝空的 `entrypoints`（`packages/plugin-sdk/src/manifest.ts:51`）；Runtime 安装时也拒绝没有本部署入口的插件（`packages/plugin-runtime/src/index.ts:203-206`）。
- **签名包只认沙箱包**：签名包安装走 `readKeptSandboxPackage`（`apps/local-host/src/plugin-install-service.ts:111`）。沙箱包必须带 `plugin.mjs` 等四个文件，`kind` 只能是 `app`（`apps/local-host/src/sandbox-package.ts:76-104`），入口由 `sandboxPluginManifest` 写死（`packages/plugin-sdk/src/sandbox-manifest.ts:137-141`）。
- **方法跟着进程走**：Manifest 里的 `methods` 只在实例启动时登记（`apps/local-host/src/plugin-instructions.ts:38-89`），最后一个实例停了，就变成「不在运行」（`apps/local-host/src/agent-definitions/agent-definitions.ts:356`）。
- **助理看不见没有动作的插件的方法**：助理只保留「同一个提供方有可用动作」的方法（`apps/local-host/src/assistant/assistant-work-reads.ts:137-156`）。技能包需求 §4 写的是改成「已安装且在本项目启用」。需求里写的旧位置 `assistant-service.ts` 已经搬到这个文件了。
- **已有可以接上的**：签名包里带纯文本的角色和方法正文（`SandboxAgentBodyDeclaration`，`packages/contracts/src/platform/plugin-package.ts:10-31`），只是今天必须和运行时一起出现。

### 三、签名与信任（ONB-53），和第 26 批的签名准备怎么接

**今天的两条路**：

- **签名包**：`verifyPluginPackageSignature` 用包里带的公钥验 Ed25519 签名，这把公钥要和 `manifest.publisher.signature` 对得上（`packages/plugin-runtime/src/package-verification.ts:107-114`）。首次安装一定要用户同意；发布者没固定过的，还要先固定（`apps/local-host/src/plugin-install-service.ts:160-199`）。信任分 `host`、`pinned`、`unsigned` 三档（`packages/contracts/src/platform/plugin-trust.ts:5`），只有 `host` 跑在进程里（`packages/plugin-runtime/src/trust-rules.ts:56-61`）。签名工具已经有了：`tooling/plugin-cli/src/package-signing.ts`，可以接外部签名器。
- **随宿主发的插件**：只有 `plugins/native/*/src/registration.ts` 会被生成进目录（`scripts/generate-plugin-registry.mjs:47`）。目录里的插件直接拿 `HOST_BUILD_TRUST`（`apps/local-host/src/project-plugins.ts:181-184`），同意项自动给，**不验签名**。

**结论**：套组要是写成 `plugins/native` 下的登记，就会拿到宿主信任，跳过授权确认。这正是 §3.8.1 和 ONB-53 不许的：不按「官方」开分支，不跳过确认和依赖检查。所以套组应当做成**随安装包带上的签名插件包**，走签名包的验签、同意和固定发布者。代码里没有任何地方按套组名或「官方」判断。

**和第 26 批的关系**：这是两把不同的钥匙，管的是两件事。

- **Apple 的 Developer ID 签名与公证**（26 第 1 项）：保证整个 App 和 Resources 里的文件没被改过，是 Gatekeeper 查的。
- **插件包的 Ed25519 发布者签名**：决定这个插件包「是谁发的、要不要首次确认」，是 Plugin Runtime 查的。

套组包放在 App 的 Resources 里，会被 Apple 签名一起封住，但这代替不了发布者签名。第 26 批要另外补三件事：

1. Molis Work 的插件发布者密钥：生成、保管、轮换和撤销。这是凭据，要用户本人办，工程只写步骤。
2. 发布工作流（`.github/workflows/release-macos.yml`、`apps/desktop/tooling/build-macos-release.sh`）里加一步：用这把密钥给套组包签名。
3. 开发构建用什么钥匙签：开发钥匙和正式钥匙分开，不能混。

### 四、版本升级差异，和「随包带上但未启用」

- **签名包能升级，但只看两样差异**：升级是一次新的预览加确认（`apps/local-host/src/plugin-install-actions.ts:112`）。新版本必须更高，并且在 `compatible_from_versions` 里列着（`apps/local-host/src/package-upgrade.ts:9-18`）；会丢授权的升级会被拒（`packages/plugin-runtime/src/index.ts:297-335`）。升级前**只**对角色和方法正文标出新增、改动、删除（`apps/local-host/src/plugin-install-service.ts:124-133`）。用户改过的提示词另存在 `prompt_overrides` 里，默认值变了会提示（`apps/local-host/src/agent-definitions/agent-definitions.ts:24-31,138-139,190`）。
- **随宿主发的插件不能拒绝升级**：带宿主信任的记录会自动跟着新构建走（`packages/plugin-runtime/src/install-rules.ts:214-231`）。ONB-55 要的「可以不升级」，这条路给不了，这又是套组不能走宿主登记的一个理由。
- **ONB-55 还缺两样**：
  - 整份场景声明的差异，不只是角色和方法正文；
  - 采用之后的东西已经交给各自的主人（项目设置、Characters、首页），套组升级不会自动改它们。所以差异要说清「新版建议改哪些」，由用户挑着重新采用。另存为个人场景包后，和官方版本分开演进。
- **「随包带上但未启用」现在没有这个状态**：
  - 随宿主发的插件，每个项目的 Runtime 都会启动，只是没加进项目的就停用（`apps/local-host/src/project-plugins.ts:153-158`、`apps/local-host/src/project-plugin-enablement.ts:10-45`）；
  - 签名包只有「装了」和「没装」两种；
  - 插件市场只列随宿主发的目录（`apps/workbench/src/plugin-catalog.ts:244-266`）；
  - 代码里还没有引导里挑套组的地方。

  缺的是：一份「安装包里带了、还没装」的只读清单，挑选处和助理推荐都读它。选中以后，才走签名包的安装确认，再加进项目，按 §3.12 采用。没选的套组不装、不启动、不进工作台。

### 五、给第 08 批合同稿的输入

1. **地基先做**：允许 `entrypoints` 为空，Runtime 按「只有声明、不起进程」装配；签名包不再只认沙箱包；方法登记不跟着进程走；助理按「已安装且在本项目启用」取方法。
2. **套组是普通插件加一块场景声明**：在 Manifest 里加一个**可选**的场景声明，把一里「缺什么」那一列放进去：目的、角色模板、依赖和受影响的步骤、需要的账号、运行条件的建议值、首页与示范任务的引用。官方、个人、AI 生成的方案共用这一份。
3. **起名避开「消费场景」**：判断规则里已经有 `action_scenes`、`scenes:use`、`services.scenes`（`packages/contracts/src/platform/plugin-scenes.ts`），英文键名别再用 `scene`。中文名和英文键名要在 [`GLOSSARY.md`](../../../../docs/system/GLOSSARY.md) 里登记。
4. **依赖照轨道规则按能力声明**：依赖按能力合同写，`optional` 表示缺了只挡一部分；再加上「挡第几步」和「需要哪家服务的账号」。采用时由平台找到提供方并加进项目，不直接写插件 id。
5. **采用的去向**：声明本身不保存用户数据。采用时把角色交给 Characters、把设置交给各自的主人、把首页交给页面合同；移除套组时只解除它拥有的绑定（ONB-56）。这部分要和第 20 批第 1 项的角色、设置、页面合同一起定。

### 统筹裁定（2026-11-04，见 #1793 评论）

1. **套组包的形态**：做成随安装包带上的签名插件包，内容只有声明，不写进 `plugins/native` 的宿主登记。它和第三方插件走同一条路：先预览，再确认安装，平台验签名（依据 ONB-53 与插件同等待遇）。插件发布者密钥和给包签名的那一步，并进 11-05 第 26 批的签名问题一起问用户。
2. **首次挑套组时照常确认**：不在安装包里预先固定 Molis Work 这个发布者，和别的发布者一样，第一次由本人确认。
3. **个人场景包、AI 生成的方案、从外部导入的 Skills，都用这个 Home 现有的发布身份签名**：和创作台发布的插件同一档。这把 Ed25519 钥匙的私钥存在 SecretStore 里，见 `apps/local-host/src/plugin-builder/publisher-identity.ts`。首次安装照常预览内容、由本人确认；不另造钥匙，也不另开 `unsigned` 一档。
