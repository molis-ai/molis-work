# Goal Tree 状态多选过滤

## 背景与目标

左侧 Goal Tree 的过滤图标当前只把焦点移到关键词输入框，不会给出可见反馈或状态选择。用户点击后容易认为页面卡住，也不能按 Goal 当前派生工作状态缩小列表。

本 Work Item 把该入口改为一个轻量、可关闭的状态过滤面板：用户可同时选择多个状态，并与现有关键词搜索共同过滤 Tree。

## 当前行为与问题证据

- `data-focus-filter` 的点击处理只执行 `treeSearch.focus()`。
- 浏览器复现没有报错，但焦点变化没有可见结果，Tree 与页面也没有任何反馈。
- Goal Tree 节点已有 `status` 这一派生事实；不需要新增 Goal 状态或写入数据库。
- 在真实 Goal `MOLIS_WORK-DRAFT-DIALOGUE-CLARIFICATION` 上，当前页面可打开筛选面板且控制台没有异常；但触发器仍落在覆盖写入、导航和折叠操作的全局异步点击委托中。为避免真实数据更新或图标事件目标进入该宽泛路径而让入口表现为卡住，筛选触发改为独立、无网络副作用的监听器；焦点恢复使用 `preventScroll`，且只有面板仍打开时才执行。

## 范围

- 过滤图标打开/关闭一个可见的状态多选面板，并有明确的展开语义、Esc 与点击面板外关闭行为。
- 面板仅列出当前集合中实际存在的工作状态，显示人类可读标签与数量。
- 多选状态采用“满足任一已选状态”的语义；与关键词搜索同时生效。
- 匹配子节点时保留其祖先节点和树层级，便于理解它属于哪个 Goal；祖先不计入直接匹配数。
- 过滤条件在本次页面会话中保存；清除操作恢复全部状态。
- 成功筛选不刷新页面、不改 Goal、关系、Claim、Run 或 canonical 状态。

## 非目标

- 不新增第二套 Goal 状态、服务端筛选 API 或数据库字段。
- 不按 Runtime 角色、优先级、Risk 等新增其他过滤维度。
- 不改变归档/回收站的独立视图语义。

## 用户场景

1. 用户点击 Tree 顶部过滤图标，立即看到“按状态筛选”的面板，而非无反馈地被送入搜索框。
2. 用户同时勾选“待执行”和“执行中”；Tree 仅显示这些节点及其必要的父层级。
3. 用户输入关键词后再选择状态，两个条件共同收窄结果；清除状态选择后关键词搜索仍保留。
4. 用户按 Esc 或点击面板外关闭面板，不会丢失已经选定的状态。

## 方案与关键决策

- 复用 `WebGoalView.status` 和现有 `STATUS_LABELS`，在每个 Tree 节点写入 `data-goal-status`；这是派生展示事实，不创建新状态。
- 由当前 `visibleGoals` 集合计算可选状态与计数，所以正常 Tree、归档和回收站各自只展示有意义的选项。
- 客户端维护 `selectedStatuses`；`filterTree` 统一计算关键词与状态条件、直接匹配数和祖先可见性。
- Tree footer 用“显示 N / 总数”反馈结果。面板保持可操作，不因每次勾选而关闭。
- 点击事件以 `Element` 防御性收窄，避免非 Element 事件目标让委托处理器中断。

## 文件边界

- `src/web/render.ts`：过滤面板、Tree dataset、客户端状态与样式。
- `tests/web.test.ts`：渲染结构与状态过滤客户端契约回归。
- `DESIGN.md`、`.impeccable/design.json`：记录可多选状态过滤的 Tree 交互。
- `specs/goal-tree-status-filter/spec.md`：本 Work Item 的唯一需求源。

## 验收标准

- 点击过滤图标能打开可见面板，且不会只发生不可见的焦点跳转或阻塞页面交互。
- 连续打开/关闭或自动更新邻近发生时，筛选触发器不会进入全局异步点击路径；面板关闭后不会再把焦点滚动到隐藏的复选框。
- 可同时选择两个或更多状态；Tree 以 OR 语义筛选，并与关键词条件共同生效。
- 匹配子 Goal 时父级层次仍可见；无筛选结果时有明确反馈。
- 状态筛选不写入 SQLite、不改变任何 Goal lifecycle/work state、也不触发页面导航。
- 键盘可操作：触发器有 `aria-expanded` / `aria-controls`，Esc 关闭并恢复触发器焦点。
- 受影响 Web 测试、类型检查、完整测试与 `git diff --check` 通过。

## 假设与开放问题

- 多选状态的自然含义是“任何一个被选中的状态”，而不是同时满足多个互斥状态。
- 当前只需要 Tree 内的即时前端过滤；规模化服务端过滤与更多筛选维度属于未来需求。
