## 已确认问题

### 1. P1 — 返回缓存话题会漏掉中间消息，且无法分页补回

位置：`packages/im-ui/src/client.ts:164–168`，`selectThread`。

复现：进入只有第 000 条回复的话题，再回主群。第二个测试成员通过真实 API 连续发送第 001–065 条。重新进入该话题，DOM 只有 51 条：000、016–065；没有“加载更早的消息”按钮。真实服务 `reply_count` 为 66，数据没有在服务端丢失。

原因：切换只请求最新一页，与缓存消息直接合并；分页状态继续采用 `cached.page`。原缓存的 `has_more=false` 被保留，最新页与旧缓存间的 15 条消息没有补齐。随后 refresh 的边界已经是最新消息，也不会再发现中间空洞。

调整：进入缓存话题时使用可证明连续的历史窗口，补齐到旧缓存边界后再合并；分页游标必须对应当前已连续加载的窗口，不能直接复用旧 page。补一个浏览器回归：离开期间新增超过一页，返回后完整读取且分页仍可达。

### 2. P1 — 较早话题的发送响应会删除较新的未发送草稿

位置：`packages/im-ui/src/client.ts:263–268`，`newThread` 提交回调。

复现：在隔离浏览器中只延迟话题 A 的 POST 响应，真实服务已提交 A；发送中点击顶部“＋”，输入草稿 B。释放 A 响应后，B 仍暂时显示在输入框。点“留作草稿”再打开“＋”，B 的标题与正文都变空。已恢复原有测试草稿，临时 fetch 延迟已撤销。

原因：成功回调无条件先将整个群的 `topic-draft` 存储写为 null，之后才检查 room/epoch；它会清掉期间创建的另一份草稿。

调整：清理时比较被提交草稿的稳定 ID/版本，只移除已提交那份；发送操作独立持有目标与内容快照。版本检查也必须覆盖存储副作用，不能只保护 DOM。回归需要实际交错 A 响应与 B 编辑，而不是只断网重试同一份内容。

### 3. P1 — 原会话丢失后，项目讨论没有身份恢复路径

位置：`packages/im-ui/src/client.ts:340–351`；`apps/local-host/src/im-server.ts:55–58`；`server/src/identity.ts:10,48–65`。

证据：会话有效期为 30 天，失效后 ensure 发匿名新会话；当前界面只提供填写名字，name 会为匿名会话创建新 member。使用新 Cookie 再填写原测试用户名字“一骏”，命名接口 200，而同一真实项目接入 403：`此项目的访问已撤回或没有操作权限`。本地宿主 `/continuity/api/session` 实测 404，IM 挂载也不提供配对路径。

影响：清除 Cookie、换浏览器或全部会话过期后，用户有本地项目和控制凭证，却不能通过当前产品流程恢复原项目讨论身份。反复点击重新连接不会解决。

调整：接入现有稳定账户/设备配对机制，提供恢复原 member 的明确路径。不能以同名匹配成员，也不能把此处 403 改成自动授权；拒绝陌生身份的边界应保留。补会话失效后恢复原身份、恢复草稿命名空间和重新连接项目的端到端测试。

### 4. P1 — 短屏下输入框完全超出讨论区

位置：`apps/workbench/src/discussion-split.ts:19–21`；`packages/im-ui/src/styles.ts:9–10,16`。

复现：实际工作台设为 390×400 CSS 像素，打开带来源上下文的 Thread。讨论 iframe 高约 207px；项目头和标签已占约 151px。输入容器在 iframe 内 top≈240、bottom≈345，完全不在 iframe 可见范围内，外层 overflow:hidden 将其裁掉。只能看到标签和部分来源，无法输入或发送。

对照：390×843 时 iframe 高约 437px，输入框 bottom≈429，正常可达。截图分别为 [短屏缺陷](short-screen-390x400.png)、[正常窄屏](narrow-390x843.png)，均已打开检查。此为真实视口实测，不等于手机软键盘实机验证。

调整：按可用高度设计组合收缩策略：输入区始终可达，头部/标签/上下文按需折叠或并入可滚动区；宿主上下分屏不能只固定使用 52dvh。保留工作上下文，不用默认全屏聊天绕过问题。覆盖短屏、有来源、较多标签与长草稿组合。

### 5. P2 — 在搜索中切换话题会丢失原阅读位置

位置：`packages/im-ui/src/client.ts:139–153,158`；`packages/im-ui/src/views.ts:37–40`。

复现：在长话题中阅读旧消息，打开搜索，再点击另一个话题标签，随后返回原话题。原阅读位置被替换为底部（实测 scrollTop≈1843，与 scrollHeight−clientHeight 相等）。搜索期间原 stream 的 clientHeight、scrollHeight、scrollTop 均为 0。

原因：openSearch 已保存有效锚点，但 selectThread 再次调用 rememberPosition 时，原消息流已被 display:none 隐藏。captureScroll 把全零几何状态判断为 bottom:true，覆盖有效锚点。搜索时收起宿主也走同类路径。

调整：隐藏/搜索状态不采集会话几何；切换前恢复可测布局或沿用进入搜索前的锚点。补“读旧消息→搜索→切换/收起→返回”的回归。

## 模块、类和方法边界

可以保留的边界：Workbench 管宿主分屏与 iframe 生命周期，im-ui 管会话 UI，Server 管正式消息、权限、事务和事件，contracts 管 DTO。UI 没有导入 SQLite 或复制一套身份数据库。`ImReads`/`ImWrites` 的基本职责清楚，消息写入、幂等回执与事件同事务是正确基础；不必为了形式把每个函数都改成类。

需要随修复调整的三处：

| 现状 | 建议 |
| --- | --- |
| `client.ts` 的约 410 行 String.raw 同时管理身份、请求、SSE、缓存、草稿、搜索和 DOM，TypeScript 只检查字符串外层 | 将会话/历史状态、草稿与提交、传输与重连拆为少数有类型的模块，保留页面控制器做编排；不要再增加并列全局变量。浏览器代码应经过真实类型检查或构建，而非仅字符串语法检查 |
| `server/src/im/project.ts` 同时承载项目主群创建、消息搜索和已读写入 | 项目文件保留项目主群行为；`readPositions`/`searchMessages` 归读职责，`markRead` 归写职责。沿用现有 Reads/Writes，避免再造无实际需求的通用层 |
| read/search 协议只在 contracts 注释里描述，客户端直接接收无类型 JSON | 补 `ImReadState`、已读输入和搜索结果 DTO，与有类型客户端一起使用；让群/Thread 目标、游标与请求结果能在编译期校验 |

另一个已知产品边界：当前工作台固定走同源本地 `/im/api`，使用 `<home>/server/server.sqlite`。同一服务上的两个测试成员互通，不等于两台独立工作站已经接入同一个远端 Server。跨工作站接入须与共享 Server/身份 owner 联调，本轮未把它扩写成新的后端或宣称已验证。

## 交互与信息布局判断

保留：右侧分屏、固定主群首标签、自然宽度话题、单会话、明确发送目标、来源定位和按需展开操作。中性浅色/石墨深色与接受图方向一致，无需重做视觉世界。

优先调整：短高度的空间分配、隐藏视图的状态保存、发送中切换新话题的操作生命周期。入口、标签等触摸目标多为 32–36px，可作为后续触摸优化；这不是本次 P1 的根因。大量话题与超长历史尚需性能测量，不能把当前小规模预览当作性能验收。
