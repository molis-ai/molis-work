## 给人讲清楚

防腐整理留下几类收尾：零散的待办和风险散在几个地方，有的没人负责；几份共用的基础代码有重复，版本号也各自涨过、没有统一；以后升级要从哪个版本算起也还没定下来。这一批把它们收干净：每件遗留的事都有主人、只记在一个地方，共用代码各留一份，所有版本回到同一个起点，并写好「从此以后改结构要怎样升级」的规则。做完之后，后面每一批都在一个干净、统一的起点上开工。需要你做的：真实 Home 的清空重建要等你说开始（旧 Home 整个搬开、不删）；版本号回到 0.1.0 之前，要先在 GitHub 上删掉旧的发布和标签，这一步只能你来；对外的许可说法和几条还没定的检查规则也要你定。

```text
你在 Molis Work 仓库里推进路线书第 02 批「需求、版本与工程收口」。完成程度按本批每项交付写的来（定样、合同、实现或验收），不停在方案、原型或几个样例，也不自行降级。PR 按第八节的粒度开，交统筹审和合并。

四、前置与顺序
按本批文件的「前置／待决」和每项的「该项前置」逐条核；没就绪的只停那一项，其余照做。合同先单独一个 PR（轨道规则 1），服务再接，消费者最后。可并行项只做设计、只读核查或等待期间的独立工作，不把后续依赖当成已经能开工。

五、界面
本批文件的界面要求是「无需」。一般没有新界面，普通文案、已有控件与缺陷修复直接做；真要改变操作路径或出现新界面时，按下面的「定样怎么走」先出样，我确认、定样合入后再写产品代码。
定样怎么走：
1. 出 2～3 个方案，用组件板实件；1440、1024、390 三种宽度、中英文、深浅色都出图或给能打开的实物，正常与异常状态都有。
2. 先拿给我看，再弹窗请我选；没确认的方案不进实现。
3. 我确认后，把选定的方案连同理由、否掉了哪些写进这一项原需求的决策记录，开定样 PR。
4. 评审走查、D 轨合审组件板新增后合并；定样合入后才写产品代码。

凡是碰到界面的部分（新做、复用、改文案或修缺陷都算），都要做到让我用得爽，不以「功能可用」或「测试过了」交差，做不到的不合入（需求开发流程第 5 节）：
- 交互：主路径步数最少，结果可预期，能撤销；每个操作都有即时反馈；键盘能走通；出错能就地修好。
- 设计与美学：用组件板实件和 DESIGN.md 的令牌；空间、光影与阴影、留白、色彩都做到位；不同内容用搭配的不同颜色。
- 动效：每个动效都有目的，交代从哪来、到哪去、状态变了；时长和曲线用令牌；不挡操作；减少动态效果时有退路。
- 布局：一屏能看懂；按钮有边界，多项要分区，行不折行；文件和文字放进容器；1440、1024、390 三种宽度、中英文、深浅色都成立。
- 注意力：一屏一个主焦点；只在真需要我时打断；提示按轻重分级；不让我找东西、干等、猜状态。
- 认知：降低认知负荷——让人认出来而不是回想；渐进展开，信息分块；默认值合理；用我的话，不用系统内部的词和原始 id。
- 行为：减少摩擦，让下一步自然发生，给完成感；尊重我的自主，不用暗黑模式，不制造焦虑。
样和产品代码都用组件板 /__ui/catalog 的实件，守 DESIGN.md、specs/craft-finish/spec.md 和 specs/ui-craft-floor/spec.md。组件板上没有的部件标「组件板新增」，定下后先由 D 轨补成组件板标本再进产品。界面与体验类的完成，以我本人看实物验收为准。

六、边界
- 一条轨道同一时间一个写手；要改别的轨道独占的文件，由那条轨道落，你的片叠在后面（轨道规则 7）。

- 只做本批的交付，后面批次的内容不提前做；发现本批范围要变，先改本批文件和原需求，再跟我说。
- 红线，一律先问我：动真实 Home；换 vendored 的 Prologue 包或改上游；发版、改版本号、用到账号证书或凭据；改门禁或 CI；新增兼容或迁移逻辑；页面资源一次涨超过 10 KB，或新增资源；改变产品语义，或推翻我已经定过的事。别的取舍按推荐直接定，写进本批文件或原需求的决策记录。
- 并行：两个写手不碰同一批文件；tooling/gates/api/ 下同一个子路径，同一时间只有一个 PR 在改；合同 PR 请合同台合审一次。

七、防腐与代码质量
防腐整理定下的规矩一条都不能再违反。PR 描述里写一节「防腐与代码质量」，逐条写「过」「不涉及（理由）」或「问题」；评审照同一张表看，有一条是「问题」就退回，不入队（需求开发流程第 10.1 节）：
- 开工前检查 14 项（需求开发流程第 4 节）：事实主人、插件同等待遇、能力注册一次、合同、放在哪个包、表与存储、不加兼容与迁移、安全边界、调用次数、升级与数据、成果与过程项、页面与外壳、错误码、冲突面。
- AGENTS.md 的硬约束。
- docs/prompts/repository-systematic-review.md 第 3～12 节：模块划分、调用链、自动发现、数据与生命周期、无用与重复内容、测试与预期行为对齐。
- 对抗式审查台账 N42～N56 的调用次数：一次操作发几个请求、每个请求做几遍目录发现和授权核对、开几次库；不重复读、不按条目逐个请求。
- 门禁数字只许变小（node scripts/check-health-gates.mjs --base origin/main）：不新增 any、as unknown as、空 catch、没处理的 promise、console；不新增兼容标记、Error 子类、测试引用包内部；巨大单元不变大，混了几件事的按职责拆，合理的大单元登记理由。
- 代码本身：平台已有的能力不另写一份；不留死代码和重复代码；函数内聚，命名照 docs/system/GLOSSARY.md；注释写为什么；安全边界的改动配上断言「拒绝」本身的测试；不为变绿跳过、放宽或删除断言。
查出旧代码里的违规，记一条 BL 交给对应的轨道，不顺手扩大本片范围。
```
