# Feed 捕捉成果跨产品版本重放

状态：本地验证通过，待合入（2026-11-23）。

目标为功能可用。Feed 的捕捉线按消息和规则确定，已保存的 `origin.revision` 是捕捉内容的指纹。现有重放尝试重写最新版本，成果库的 `sameVersion` 会比较整份记录，包括生产插件版本。产品升版后，Feed 把 `version_conflict` 当作内容变化，于是追加了一版。

在现有捕捉事务内，成果库给 `PluginArtifactWriter.head` 补充原始 `origin_revision`。它只投影当前插件自己成果线的最新版本。Feed 比较现有指纹，匹配即完成本次捕捉，否则在该线上追加并指向前一版。成果库继续按完整记录判定精确版本重放。

另一个方案是给 Feed 及捕捉动作授予 `artifact:read`，再读取固定版本。事务写入者已有成果线归属和实时授权检查，补一个字段即可完成本次比较，可以避免扩大读取授权。生产路径涉及 Contracts、成果库的插件服务与 Feed 捕捉逻辑，`PluginArtifactClient.head` 及动作 schema 沿用现有合同。范围限于此后的重放和新写入。

## 开工前检查

送审时补记。此项是独立片，涉及 Feed 产品线和公开合同。用户继续通过原来源拉取或重新执行捕捉规则，在成果库查看相同的固定版本。捕捉内容变化时可以打开新版本，旧引用仍指向原版。

| 检查项 | 结论 |
| --- | --- |
| 1 事实主人 | Feed 决定捕捉内容和指纹，成果库持有版本事实，经公开的 `PluginArtifactWriter.head` 返回已存修订。 |
| 2 插件同等待遇、3 能力注册 | 沿用 Plugin Runtime 与成果库事务写入者。动作与调用身份沿用现有注册和上下文。 |
| 4 合同、5 包归属 | Contracts 扩充已有写入者的返回类型，成果库提供投影，Feed 消费。公开 API 快照与消费者同片更新，按当前阶段原位变更。 |
| 6 表与存储、7 兼容与迁移、10 升级与数据 | 直接比较成果原有的固定修订。数据库形状、现有成果版本和引用沿用，重放修复从此后的捕捉生效。 |
| 8 安全、9 调用次数 | 项目事务、写权限与发布者签名仍由原入口核对，S-100 带拒绝断言。同内容执行一次成果线读取，内容变化时执行一次发布。 |
| 11 成果与过程项 | 捕捉结果继续作为已有类型的固定成果留存。 |

| 14 冲突面 | 开工查过 #1743 和在途 PR。同步 main 时保留上游合同说明，并用源码重生成共享 API 快照。 |
| 15 全局方案 | 在两种已授权方案中选用成果库事务写入者的修订投影。Feed 需要比较的只有自身捕捉指纹，已有写授权足够。 |

平台能力检查结论为用现成的事务写入者，在同一份合同补字段。目前只有 Feed 需要字符串指纹，Pages、Form、Dataset、PPT 等固定成果路径继续走各自已有的版本判断。此次比较发生在同一生产者自己的成果线上。凡宿主已提供 `join` 的插件，都使用同一份写入者合同。助理和 Agent 仍可通过原有 Feed 动作入口使用修复后的捕捉行为。

## 验收

1. **FVR-01** 发布版本字段不同、捕捉内容相同时，手动重放及来源重送都沿用已有版本，旧版本记录保持原样。
2. **FVR-02** 发布版本变化后，捕捉内容改变仍追加一版，指向前一版并记下当前生产插件版本；再重放同样的内容时版本数稳定。
3. **FVR-03** 事务中的有效写入者可通过 `PluginArtifactWriter.head` 读取自己成果线的原始修订，包括同一事务刚写的版本。该入口拒绝其他生产者的成果线。`PluginArtifactClient.head` 继续返回数字修订投影。
