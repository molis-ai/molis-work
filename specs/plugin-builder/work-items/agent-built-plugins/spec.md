# 插件创作工作台：Agent 编写的真实插件与平台沙箱

状态：2026-09-26 用户授权端到端实现完整生产级 Plugin Builder，实施中。本文是这项工作的唯一需求与验收依据；目标为可发布，工程、真实模型/产品实操与用户体验验收分别记录，不将阶段完成当作全部完成。

- 取代旧的"固定解释器 + 受控设计"路线（`model.ts` 的 Design / 字段 / 计算、`records.ts`、`generated.ts`、`formula.ts`、behavior 角色）。旧路线只是演示版本，没有存量用户，**不做兼容和数据迁移**。
- 保留并沿用 [看得见的协作构建](../live-collaboration/spec.md) 的做法：`steps` 是画布与左栏的唯一真相源；规格板 + Jev 逐个选零件；逐个接通；指着画布修改。
- 对"由创作台生成的插件"，本文取代 [Plugin Platform v2](../../../plugin-platform-v2/spec.md) 第 55 行"不做不可信插件沙箱"的约定。内置插件的运行方式不变。

## 1. 要做成什么

我们要把插件创作工作台升级为一条"界面由 Jev 装配、功能由 Agent 写代码"的插件生产线。

用户用自然语言描述需求后，主线设计先给出基础思路：用户旅程、页面与区域结构、可执行的验收用例，以及前后端共同遵守的**功能合同**（每个操作的名称、输入输出、数据结构和错误）。所需能力只能从平台能力目录和本项目已启用插件的对外能力里选。

随后两条线并行：
- **前端**：宿主按规格板从平台组件池算出每个位置的合法候选，Jev 从中选出下一个组件，属性由规则和设计补齐，画布即时渲染，未接通的操作明确标"待连接"。
- **后端**：写代码的 Agent 在宿主创建的构建目录里按合同实现各项操作并编写测试。每个操作依次通过宿主门禁后，宿主把绑定它的组件逐个接通；失败时原文交回 Agent 修正，轮次有上限。

全部接通后由浏览器自动执行验收用例。"能用"的判据是通过这些用例并经用户试用确认。左侧每一步都对应真实发生的组件选择、代码修改、检查与结果。

通过后插件打包签名；用户安装时一次确认权限、能力、其他插件的能力和联网域名；插件进入主插件平台和项目左侧栏，可以升级、回滚、撤下。

隔离要求：
- 后端在独立进程中运行，受系统沙箱约束，不能直接访问文件、网络和环境变量。
- 联网经宿主代理，按已批准域名放行；密钥只传引用。
- CPU、内存、调用和存储都有上限，调用单独排队。
- 界面不执行插件自己的前端代码，组件只能绑定本插件合同里的操作，接触不到控制令牌和其他插件。

## 2. 用户看到的完整过程

1. **表达**：一句话需求，可附文字或 CSV 资料。
2. **理解与澄清**：主线设计分析谁用、怎么用、留下什么结果；只追问会改变合同或能力的问题，最多一轮。
3. **比较方案**：2–3 个方案在页面结构和关键行为上有实质差异，右侧用组件池真实渲染第一个方案的骨架。每个方案列出它要用的平台能力、其他插件的能力和联网域名，让用户在选择时就知道代价。
4. **确认主线**：用户选定方案后，宿主冻结第一版功能合同，生成 Manifest 草稿和项目骨架。
5. **双线构建**：UI 指针按 Jev 的选择逐个放入组件；代码指针按操作逐个写代码、跑检查。某个操作的检查全部通过后，绑定它的组件打勾"已接通"，可以在画布上真实试用。
6. **随时介入**：暂停、继续、停止、撤回；Jev 给不出合法组件时由用户挑；指着组件提修改；某个操作多轮修不好时，交给用户决定改需求、降范围还是停止。
7. **验收**：全部接通后，宿主在沙箱里跑一遍验收用例（浏览器自动操作真实界面），结果逐条显示。
8. **安装**：一张授权清单列出权限、平台能力、其他插件的能力、联网域名和密钥引用，用户一次确认。插件出现在项目左侧栏。
9. **继续修改**：再次编辑产生新草稿，不影响正在使用的版本；发布新版本时，新增的权限或域名需要重新确认。

## 3. 参与者与编排

| 参与者 | 实现 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 主线设计 | Prologue 角色，只读，不带工具 | 用户旅程、页面与区域结构、功能合同、验收用例、能力清单；修订时交回整份修订版 | 选具体组件、写代码 |
| UI 装配 | 宿主规格板 + Jev（TypeSafe choice） | 在合法候选里逐个选组件；属性由规则和设计补齐 | 发明组件、改合同 |
| 代码 Agent | **新的 Prologue 角色**（D6） | 按合同在构建目录里实现操作、编写测试、根据检查结果修正 | 改 Manifest 能力清单、改合同、自称通过检查 |
| 宿主 | 创作台编排代码 | 生成骨架、执行门禁、逐个接通、验收、打包、安装 | 替 Agent 写业务代码 |
| 用户 | — | 选方案、回答澄清、授权、试用与最终验收 | 逐个批准可逆的组件装配 |

### 3.1 代码 Agent 的编排（D6）

Agent Host 的 `host_tools` 只能从宿主的固定集合里选（读写文件、搜索、运行命令、询问用户等），插件不能给自己的角色定义新工具。所以本场景的特殊编排放在**宿主侧的循环**里：

- 一次运行只处理**一个操作**（或一组互相依赖的操作）。任务里包含：合同片段、骨架里对应的文件、SDK 类型与能力目录的相关部分、上一轮的检查结果。
- 角色的执行级别是 `text-edit`（读文件、搜索、写文件、改文件），**不给 `run-command`**，Agent 不在用户机器上跑任何命令。
- **检查工具（D10）**：Agent Host 新增一个宿主工具（暂名 `plugin-checks`），只开放给这个角色。Agent 可以在运行中调用它，对当前构建目录执行 G1–G6（可以只跑指定的操作），拿到和宿主门禁同样格式的结果。工具的实现和执行位置都在宿主和沙箱里，Agent 只拿到结果。
- 运行结束后，宿主**仍会自己再跑一遍**门禁，以宿主这次的结果为准；Agent 在运行中自查"通过"不算数。宿主把结果原文交给下一轮运行。每个操作最多修 3 轮，还不通过就把问题交给用户。
- 不同阶段的提示词分开版本化（写实现、写测试、按失败修正、按修订调整），为定向调优留接口。
- 每次运行的输入、输出和检查结果都保存在本机，作为以后调优的评估样本。不上传。

## 4. 功能合同：前后端的唯一对接点

主线设计产出、宿主校验并版本化的一份数据：

- **数据**：插件自己持久化的实体及字段类型（含日期、枚举、关联等常用类型）。
- **操作**：`operation_id`，输入 schema、输出 schema、可能的错误；**副作用声明**（读写自己的存储、调用哪些平台能力或其他插件的能力、访问哪些域名、用哪些密钥引用）。
- **示例**：每个操作至少一组示例输入和期望输出，既是后端测试的起点，也是接通后的冒烟用例。
- **验收用例**：按用户旅程写的端到端步骤与期望结果，由浏览器自动执行。

规则：
- 组件的数据来源和事件只能绑定合同里的操作。后端实现的操作必须与合同一一对应，schema 一致。宿主检查两侧，不一致不接通。
- 副作用声明是 Manifest 能力、权限和域名清单的**唯一来源**。Manifest 由宿主从合同生成，Agent 不能直接改。
- 合同变更（修订）时，宿主计算受影响的组件、操作和用例，只重做这些部分。旧版本的结果不能覆盖新版本。

## 5. 前端：规格板 + Jev + 平台渲染器（D2）

### 5.1 组件池
- 以设计系统现有组件为基础（`packages/design-system/src/primitives/`，约 60 个：按钮、表单字段、表格、卡片、布局、导航、标签页、浮层、反馈、日历等）。
- 每个组件补上生成用的元信息：用途、适用条件、属性 schema、可以放进哪些区域、能接收什么数据（对应合同类型）、能发出什么事件（可以绑定哪类操作）、示例。
- 首阶段只开放"首个真实插件"用得到的子集，按验收场景扩充。池里没有的组件**报告缺失**，本次不允许插件自带前端组件。

### 5.2 选择
- 主线设计给出页面与区域结构；宿主按"当前区域、已放入组件、合同"算合法候选。
- Jev 的 choice 一次最多 32 个选项（`modules/functions/src/store.ts:869`），所以候选按区域收窄，每次选择都不超过这个上限。
- 选择规则沿用 live-collaboration：只有一个候选时按规则选、不调用模型；Jev 未配置时按规格板顺序；Jev 答出候选之外的值或出错时，不放组件，交给用户选；暂停、停止或界面已变化后才到的答案作废。每次选择记录来源、候选数、模型、耗时和置信度。
- 属性分开处理：Jev 只选组件；属性由规则、设计默认值或主线设计补齐，选择、配置、定位分开校验。

### 5.3 渲染
- 渲染器由平台提供，是可信代码：按组件树渲染，用户可见的文字一律转义，链接和图片只允许安全协议。
- 组件事件经宿主桥接，只能调用**本插件合同里已接通的操作**，桥接令牌只属于这个插件；界面接触不到工作台的控制令牌和其他插件的接口。
- 增量更新：保留用户输入、焦点和滚动位置。指标：100 个组件的代表页面，本地修改到可见反馈 P95 ≤ 200ms，记录设备和采样方法。
- 创作台画布和安装后的插件用同一个渲染器。

## 6. 后端：Agent 写代码与门禁（D1）

### 6.1 构建目录与可见材料
- 宿主为每次构建创建专用目录，不使用用户的项目工作区。Agent 只能读写这个目录。
- 目录里只有宿主生成的骨架（Manifest、入口、每个操作的空实现、按示例生成的测试桩）、合同、开发者材料（§9）。**没有平台和其他插件的源码。**

### 6.2 门禁（宿主执行，不以 Agent 的说法为准）

| # | 检查 | 失败时 |
| --- | --- | --- |
| G1 | Manifest 可解析，且与合同的副作用声明一致 | 交回 Agent（通常是实现越界） |
| G2 | 只针对 SDK 类型定义做严格类型检查 | 交回 Agent |
| G3 | 打包：只允许导入 SDK、JS 内置能力和按 §6.3 安装的 npm 包；不允许导入 Node 的文件、网络、进程等模块；产出单个包 | 交回 Agent |
| G4 | 合同一致：每个操作都已实现，输入输出与 schema 一致 | 交回 Agent |
| G5 | 在模拟宿主里跑 Agent 写的测试和合同示例 | 交回 Agent |
| G6 | 沙箱试运行：真实宿主服务、预览数据空间，用合同示例冒烟 | 交回 Agent；沙箱拒绝的越界调用单独标出 |
| G7 | 全部接通后，浏览器自动执行验收用例 | 定位到对应操作或组件，交回相应一方 |

- G1–G6 按操作执行；某个操作全部通过后，宿主把绑定它的组件写进 `connected`，预览接口按接通状态放行。未接通的操作不会假装成功。
- G6 和 G7 使用预览数据空间，与正式安装的数据分开。

### 6.3 第三方 npm 包（D9）
- Agent 只在构建目录的 `package.json` 里声明依赖，自己不能安装（它没有运行命令的权限）。
- 宿主负责安装：只从官方 npm 源获取，版本写进锁文件并固定；**禁用安装脚本**；安装过程本身也在沙箱里进行。
- 不接受原生扩展（`.node` 文件）；单个依赖和依赖总量都有大小上限；记录每个包的许可证。
- 依赖最终打进插件包里。运行时照样受沙箱约束：依赖如果试图读文件、联网或启动进程，会在 G6 被拦下并如实报告。
- 升级插件版本时，依赖的变化在授权界面列出。

## 7. 平台沙箱（D3、D4）

### 7.1 谁进沙箱
- 由宿主按插件来源决定：创作台生成的、未经官方签名的插件一律进沙箱。Manifest 不能声明自己退出。
- 内置插件继续在宿主进程内运行，代码不改。

### 7.2 进程与系统沙箱
- 每个安装实例一个 Node 进程，以空环境变量启动。
- Seatbelt 配置：禁止网络；文件只允许读插件包和 Node 运行时；禁止写文件；禁止启动子进程。
- 资源上限：内存（启动参数）、单次调用时长、CPU 看门狗。超限时终止进程，按现有崩溃恢复与隔离规则处理。
- Node 自带的权限模型只作为附加保护，不作为安全边界。

### 7.3 宿主侧代理
- 宿主提供一个实现 `PluginDefinition` 的代理：`start()` 拉起沙箱进程；路由、动作、事件等处理器转成跨进程调用（这些接口本来就允许返回 Promise）。平台的启停、升级、隔离逻辑不需要知道对面是进程。
- 视图不由插件渲染：宿主按组件树用 §5.3 的渲染器输出。
- 插件身份由通道绑定，调用参数里的身份一律忽略。

### 7.4 沙箱版 SDK（异步）
- 现有的 `PluginPrivateStorage`、Artifact 服务是同步接口（`packages/contracts/src/platform/plugin.ts:47`），跨进程做不到同步，沙箱插件改用异步版。现有插件继续用同步版，合同只增不改。
- 提供：私有存储、Artifact 读写、调用已授权的平台能力和其他插件的能力、发布已声明的事件、联网（经代理）、密钥引用。
- 调用单独排队并有超时，不进入项目共用的队列（`apps/local-host/src/local-host.ts:451`），不会堵住其他插件。
- 存储容量、调用频率、事件发布频率有上限。

### 7.5 联网代理（D4）
- 新增一项平台能力：只允许 HTTPS，只放行安装时批准的域名；拒绝本机、内网、链路本地地址，以及解析到这些地址的域名（防止借代理访问宿主或内网）。
- 请求和响应有大小与时长上限。
- 密钥：插件只拿到引用，由代理注入请求；插件读不到密钥值。

## 8. 安装、授权与生命周期（D5）

- **授权清单**：权限、平台能力、其他插件的能力、联网域名、密钥引用，由合同的副作用声明生成，安装时一次确认。沙箱插件**不适用**"省略即授予全部必需权限"的默认规则，必须显式授权。
- **进入左侧栏**：项目插件 id 的合同已经是开放字符串（`packages/contracts/src/modules/projects.ts:33`），但实现仍是编译期列表（`apps/workbench/src/plugin-catalog.ts:160`）。改成"内置 + 已安装"合并；生成插件可以用现有的"撤下"启停和移除。
- **升级**：新版本如果新增权限、能力或域名，需要重新确认。升级预检期间，宿主锁住该安装的写入（取代旧路线"同一调用栈内校验再激活"的做法）。
- **回滚**：回退代码版本，不回退数据，界面上如实说明。
- **卸载**：停止进程，撤销授权与代理放行，不留运行中的残余。

## 9. 开发者材料（D7）

随产品发布，Agent 只能看到这些：
- SDK 类型定义（仅 `.d.ts`）和沙箱版 SDK 的运行时入口。目前 `contracts`、`plugin-sdk` 都是 `private: true` 的工作区内部包，需要单独打包出这份材料。
- 能力目录：从运行中的宿主能力表生成，只列本项目可授权的平台能力和已启用插件的对外能力，带 input/output schema 和说明。
- 组件池说明（给主线设计和 Jev 用）。
- 写插件的文档与示例。
- 模拟宿主：在构建目录里运行测试用。

## 10. 实时可见

- `steps` 继续是唯一真相源。新增步骤类型：冻结或修订合同、写某个操作、某项门禁的结果、接通、验收用例的逐条结果。
- **构建由宿主驱动**：每份构建在宿主侧有一个常驻的推进循环，关掉页面也继续，宿主重启后接着跑。不再由浏览器每 900ms 调一次 `advance` 来推进。
- **推送**：宿主通过 SSE 把步骤变化推给页面，页面不再轮询。当前仓库没有推送通道，属于本次新增。
- 代码 Agent 的每次文件修改在左栏显示摘要，可展开查看改动。模型输出的流式展示不在本次范围内：Agent Host 目前只提供读取运行状态，不提供运行事件订阅。

### 对抗用例（S0 起始终保留）
沙箱插件尝试以下行为，每一项都必须被拒绝并留下记录，同时其他插件的功能和数据不受影响：
读宿主或用户文件、读环境变量里的密钥、直接联网、访问未批准的域名、经代理访问本机或内网、读写其他插件的存储、调用未声明或未授权的能力、冒充其他插件身份、死循环、内存耗尽、反复崩溃、大量调用挤占队列。

### 首个真实插件：重做知识库（D12）
验收目标是用创作台从一句需求开始，造出新的学习型知识库插件，产品需求见 [Cognia 2 spec](../../../cognia-plugin/v2/spec.md)。它对本文提出的要求，需要在对应阶段先准备好：
- **模型调用**：沙箱插件经 Agent Host 能力调用模型（只读、不带工具），费用走用户配置的模型服务。S0 的异步 SDK 要覆盖。
- **其他插件的能力**：读取 Goals、给 Goal 记进展；读取已导入的文档 Artifact。
- **提醒**：复习到期提醒，使用平台的调度能力（`schedule.register` 等）。
- **npm 包**：间隔复习调度库（FSRS）、简繁转换库。
- **起步包**：《论语》二十篇原文作为只读资源随插件包分发（由我们准备，不由代码 Agent 生成），创作台要支持把这类资源放进构建目录，且 Agent 不能修改它。
- **组件池**：设计系统目前没有对话流和原文阅读组件，S2 要补上。
- **修改已使用的插件**：插件用过一段时间后，再加一个功能并发布新版本；已有学习记录保留，新增的授权重新确认。

| 修订后保留下来的零件排到了页面最前（节点按放置顺序，保留的先放） | 节点始终按设计里的零件顺序排列（放置与安装页面都按设计顺序）；渲染器按视图顺序摆放、已在位置的零件不移动（输入与焦点保留） |
| 只有一个页面也显示页面切换条 | 单页面不显示切换条 |
| 删除要"选择 → 另一个区块里的删除选中"两步 | **记录级操作**：一个零件的输入全部取自同一集合的选中记录时，它直接显示为该集合每条记录上的按钮（标签取动作本身，如「删除」），不再单独占一块；结果显示在集合下方；没有其他零件用到这个选择时不显示「选择」。验收语法不变（`select notes 文字` + `submit remove`），验收执行器记住所选记录并点它上面的按钮。`designer/2.3` 写明这一点 |
| 已安装插件只能从创作台的链接打开 | **进入工作台**：项目里已安装（且未停用/隔离）的生成插件出现在左侧栏"更多"里，与内置插件并列；点开是工作台里的一个页面（框住它的正式页面，打开时才加载），标签页显示插件名。创作台内嵌时"打开插件"直接切到这个页面；刚安装的插件工作台重载一次后打开；卸载后入口立即移除 |

**测试**：组件（真实浏览器：记录级操作、视图顺序、单页）；创作台端到端扩到 3 个操作（含删除用例在真实验收执行器上通过、已安装页面点记录上的删除、工作台页面列出与卸载后移除）；左侧栏渲染（名称作为文本转义、没有目录面板）。旧构建器两个端到端测试缺少动作服务装配（执行器要求 `actions`）而失败，已补上与产品相同的装配。

### 14.4 平台能力目录：调用模型（2026-09-26，Claude）

**能力目录**（`plugins/native/plugin-builder/src/agent-capabilities.ts`）：宿主定义的平台能力，每项有给设计师与代码 Agent 的说明、输入输出 schema、给用户看的授权说明、最长耗时，以及**固定替身**。第一项 `model.generate`：`{instructions, input} → {text}`，用用户配置的文字模型（创作台所选，否则第一个已配置的），一轮、无工具、看不到插件存储以外的数据。

| 场合 | 能力怎么回答 |
| --- | --- |
| 代码 Agent 的测试、合同示例、G4–G6 门禁 | 替身：`［模型替身］` + input 前 40 字（可重复、零费用） |
| 界面验收（G7） | 替身（验收期间该构建的试用身份切到替身） |
| 用户在创作台试用、已安装插件 | 真实模型（经 Agent Host 新的 `model` 角色：plan 模式、无工具、单轮；记录写在该插件自己的目录） |

宿主侧（`apps/local-host/src/plugin-builder/capabilities.ts`）：调用前后按目录 schema 校验输入与输出；每个安装身份每分钟最多 20 次真实调用；声明了慢能力的插件，操作与服务时限按一次调用放宽（否则沙箱默认 15 秒/10 秒会先超时）。broker 仍按"操作声明 ∩ 安装授权"放行。

设计与界面：设计师只能从目录里选能力，查询（query）不能调用模型（打开页面就会自动调用、产生费用）——宿主静态拒绝；方案卡片显示"调用模型"；安装授权写"用你配置的文字模型生成内容（费用计入你的模型服务）"；提交时显示"模型正在生成，可能要几十秒…"；模型回答里的 `**强调**` 显示为加粗、标题符号去掉，一律按文字节点渲染。

**真实模型实跑**（MiniMax-M3，"概念自测"）：设计师 3 个方案里 2 个用模型、1 个刻意不用；选定后代码 Agent 接通 3 个操作（含调用模型的出题）；验收首次失败——出的题没有出现在回答表单里。据此补上：

| 现象 | 处理 |
| --- | --- |
| 命令结果（出的题）不显示、回答表单拿不到题目；设计协议里没有教过怎么把一个组件的结果带给另一个组件 | 设计简写新增 `"show": "字段"`（显示命令结果）与 `"prefill:组件.字段"`（表单字段沿用另一个组件的结果或选中记录，用户仍可改）；输入表单只写一个字段时其余字段仍由用户填写；`designer/2.5` 给出"先出题再回答"的写法 |
| 失败交给了代码 Agent（它改不了界面接线），白耗一轮 | 分诊新增两类交给设计师：**接线**（期望文字出现在一个不读取任何操作的组件上）与**表单**（提交时必填字段是空的）；验收执行器提交前先检查表单，直接报"表单还有必填字段是空的：concept"，不再等 20 秒超时；不读取操作的组件不再去读数据 |
| 设计师让回答表单的 concept 预填自出题组件，但出题命令的结果里没有 concept | 宿主校验：预填/选择的字段必须存在于来源组件列出的记录或命令结果里，否则在写代码之前退回设计师并说明"把 concept 加进 concepts.generatequestion 的 output" |
| 验收写成 `expect 组件 包含 文字` | 「包含」「显示」当作步骤关键词；`expect` 也看表单字段里的值（预填的内容算显示） |

结果：自动恢复后验收 2/2 通过 → 创作台试用时真实模型出题、题目与概念预填到回答表单、保存后列表显示 → 发布 → 安装（授权列出调用模型）→ 已安装插件经 Plugin Runtime 与沙箱调用真实模型（约 1 秒返回）。

**已知限制**：沙箱一个通道同时只跑一个操作，调用模型期间同插件的其他读取要排队；真实调用记录会随使用增长，保留策略待定；生成插件自己写的给模型的要求质量取决于代码 Agent（本次模型一次给了 6 个问题而不是 1 个），下一步在能力说明里给出"要求写法"范例。

### 14.5 更多需求类型的实跑与修正（2026-09-26 夜，Claude）

用真实 MiniMax 跑了三类新需求（概念自测的修订、习惯打卡、读书清单），逐个修掉暴露的问题；全部修正先在工作区克隆里验证，再应用到 main。

| 现象（真实实跑） | 处理 |
| --- | --- |
| 修订"每次只出一个问题"：合同不用变，改动在代码里给模型的要求，代码 Agent 不会被叫到 | 设计师修订可以写 `rework: [{op, why}]`；宿主把这些操作当作需要改代码，即使旧代码仍能通过检查也让代码 Agent 按 why 改一次 |
| 代码 Agent 53 次工具调用是搜索且多为空 | 代码角色去掉 search 工具（任务里已给出全部路径）；之后同规模插件 0 次搜索、未再用完轮次 |
| 协作记录看不到代码 Agent 读了哪些文件 | Prologue 的工具参数在 `ToolCall.input`（适配器原来读 `args`），读写路径现在都会记录 |
| "按状态筛选"：组件池没有筛选，设计师自造 schedule 零件 + `fill filter.status`，宿主只说"验收输入字段不存在" | **筛选栏**：collection 的 read 可以带 form 字段，列表上方出现筛选控件（可选枚举多一个「全部」，改动即重读，打字时标记等待）；独立的"筛选零件"如果只是在读同一个查询，宿主把它并入列表；验收报错点名用例、步骤、组件和它有的字段 |
| 合同错误只有 `$: missing status`、`$.status: value is outside enum`、"缺少必需输入的绑定：status" | 宿主报错点名操作和示例、给出允许的取值、提示可选字段写成 `"status?"`；零件错误带上零件 id 和改法；设计师修正从 2 次放宽到 3 次（一次回答只要几秒） |
| 设计师把"推进到下一状态"写成常量 `"next:books.status"`，宿主运行时才拒绝，代码 Agent 修不了 | 常量必须是该输入能接受的值，设计时就拒绝，并说明"让操作只收 id，在代码里算" |
| 布尔字段显示成 `false`；验收写成"今日 未打卡"（列名连值），UI Agent 选了表格就对不上 | 列可以写 `values`（`{"true":"已打卡","false":"未打卡"}`），没写时布尔显示是/否；期望文字里含列名的失败交给设计师；列表上的多词期望按"同一条记录里都出现"匹配 |
| 表格只显示 columns，标题字段不见了 | 表格在前面补上 titleField/textField 列，列名取合同里的字段说明 |
| 单页插件已不显示页面切换条，验收的 `page home` 找不到目标 | 单页时 page 步骤视为已完成；失败原因去掉 "Error:" 前缀 |
| 构建选择器停在"需要处理"；修订期间一次读取失败的报错一直挂着 | 选择器跟随实时推送；读取成功后清掉上一次读取留下的错误（保存失败的提示不动） |
| （14.4 的已知限制）调用模型期间，同插件的其他读取要排队 | 声明了慢能力的操作在同一安装的第二个沙箱进程（慢车道）里运行，两个进程共用按安装串行化的存储；端到端测试在模型慢 3 秒时确认列表读取 1.5 秒内返回 |
| （14.4 的已知限制）真实模型调用记录会一直增长 | 每个插件只保留最近 50 条调用记录（记录里有用户内容） |
| 记账本：合计是对象（总额 + 分类合计），组件池只有列表能显示数据，设计师得到"没有合法组件"而没有原因 | 正文组件把对象显示成一组带说明的数字（说明取合同字段描述），嵌套列表显示成小表格；"没有合法组件"会说明查询返回的不是列表、合计该用正文 |
| 类型写成 `number(>0)`、`string(YYYY-MM)`、`enum`；`"form.category?"` 被当成常量 | 简写接受大小限制（成为 minimum/maximum）与格式提示（成为字段说明）；`form.x`、`form?` 都是表单字段；看起来像引用的常量会说明引用的写法 |
| 示例写了 `month: "1970-01"`（或 `month: "string"`），代码 Agent 只能把月份写死，本月合计永远是 1970-01 | 部分匹配的示例里依赖当天日期或写成类型名的字段由宿主去掉并记录（设计师在修订里会原样照抄，退回无效）；精确输出里的仍退回；代码 Agent 指令与开发者材料写明"今天用 new Date()（沙箱里是真实时间），测试不断言当天日期" |
| 另一种筛选写法：一个表单"提交"列表正在读的查询，列表不变 | 宿主把这个表单的字段并入列表的筛选栏，并去掉验收里"提交筛选"的步骤 |
| 进度文字写的是操作 id（"要改代码：books.updatestatus"、"「books.updatestatus」已接通"）；手机上模型选择器被截成 "Mi" | 修订摘要与接通提示改用功能说明（"「把一本书切到下一状态」"）；模型选择器先显示模型名，窄屏给它固定宽度 |

结果：记账本验收 5/5（本月合计按当前月份、分类合计小表格、按分类筛选、最新在前、删除）；习惯打卡验收 4/4（今日显示"已打卡"、每条记录上"打卡"）；读书清单验收 4/4（筛选栏按状态过滤、每条记录上"下一状态"与"删除"），修订一次即改对。
