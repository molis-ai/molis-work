# 第二步：系统性代码与架构防腐整理

第一步（全部需求合入后的功能审查与合并缺陷修复）完成之后做这一步：按仓库系统整理要求和上一轮《Molis Work 代码与架构防腐体检报告》，对整个仓库的代码与架构做防腐处理，**完成必要的修复、重构、清理、验证和规范沉淀**。只出报告不算完成。

仓库在很短时间里经历了大量并行迭代。第一步保证了功能正确；这一步要让代码与架构重新满足：模块职责合理，代码归属清楚，开发契约落实，能力能被正确发现和使用，跨功能行为一致，失败可恢复，测试表达当前有效预期，文档与代码一致，后续开发和新插件接入有可执行的依据，并且离向 C 端开放更近一步。

## 0. 启动条件、范围与授权

**启动条件**：第一步的总 spec `specs/post-merge-review/spec.md` 写明完成，里面有行为基线（回归基线、能力快照、跨功能场景清单）、spec 梳理结果和交给第二步的清单；统一待做清单 `specs/BACKLOG.md` 已经建立。没有完成时先问我。开始前查开放 PR、`git worktree list` 和正在运行的会话，与在途工作协调文件范围；共享核心与有依赖顺序的修改串行做。

**范围**：全仓，不只本轮新增的代码。完整清点，按风险深入；未深入或无法验证的范围必须标明。

**授权**（可按需改这一段）：

- 常规、可逆、证据充分的修复、清理与重构自主完成：在自己的分支提交，可以推送分支、开 PR。每个 PR 只做一个主题，CI 通过。
- 体检报告已经列出的结构性收口方向，视为认可的方向：内置插件统一走 Plugin Runtime、MCP 旧适配退役、宿主瘦身、浏览器脚本打包与类型检查、删除旧皮肤、收敛错误类型。每项先交方案和一个样板片，样板片合入后按片推进。
- 合入 main、删除他人分支或工作树、丢弃主检出的改动、删除 vendored 文件、向 Prologue 上游推送，先问我。
- 改变对外公共合同（Manifest 字段、动作合同、MCP 工具名、插件 SDK 导出）或定兼容期，涉及产品语义或重大迁移策略的实质变化，先给具体方案、取舍和推荐，等我决定，同时继续其他独立工作。

## 3. 本轮必须覆盖的重点

整理要求的 15 节全部要做。下面是结合体检报告和本轮新增内容、必须覆盖的重点，不代表只做这些。

### 3.1 体检报告逐项闭环

附录 A 每一项给出结论：已修复（附证据）、仍然成立（附方案与顺序）、不再成立（附依据）。报告第 5 节的防腐顺序和第 7.5 节的在途线建议，逐条说明执行情况。第一步交来的清单同样逐项闭环。

### 3.2 插件平台能否持续扩展

- **装配统一**：构建期组合的插件逐个迁到 Plugin Runtime，按 Coding 一组的样板。先迁一个作样板（建议 Todo 或 Form），迁一个就删掉对应的宿主 `<插件>-actions.ts`、`<插件>-native-plugin-http.ts` 和工作台目录条目，同步缩减 `tests/builtin-plugin-assembly-gate.test.ts` 的冻结名单。
- **发现与入口统一**：内置插件目录、导航、HTTP 路由（统一挂在 `/api/plugins/<plugin_id>/`）、翻译词典、设置分区尽量由 Manifest 推导，清理多处手写名单。保留必要的装配与授权，不机械追求零配置。
- **MCP 旧适配退役**：`legacyMcp`、`LEGACY_FUNCTIONS_MCP`、`LEGACY_GOALS_MCP` 给出退役条件与兼容期方案，交我决定后迁移消费者、删除旧路径。
- **第三方插件**：用户自行安装插件的路径目前不存在。给出方案（安装命令、签名信任、市场入口、沙箱边界），不在本步实现。
- 沿「安装 → 校验 → 注册 → 加载 → 目录 → 发现 → 筛选 → 调用 → 结果」，用一个可移除的测试插件走正式扩展路径验证，包括升级、停用和卸载。

### 3.3 分层与归属

- **本轮新增的包与目录**：`horizontal/placement` 记录的是业务关系；平台记忆的事实在宿主 `apps/local-host/src/memory/`；宿主里还有 `assistant/`、`contextual/`、`browser/`。按 `docs/system/ARCHITECTURE.md` 对 Module、横向服务、插件、App 的定义判断归属，需要时迁到 Module 或独立包，并更新 SSOT 与包的「开发要求」。
- **宿主瘦身**：`apps/local-host/src` 只做组合与本机 IO。插件专属的业务逻辑移回插件包；每个插件各写一份的 AI 适配，收敛到宿主统一的推理端口。
- **Goals 界面**：留在工作台里的十几个 `goals-*.ts` 是否该进 Goals 插件包。
- **实验线**：`server/`、`apps/server`、`packages/im-ui` 保留在主线还是移出，给出判断。
- **公共合同**：删除 contracts 里只有占位的 subpath；本轮 subpath 数量的增长逐项说明理由；动态交互对 `packages/contracts/src/platform/actions.ts` 与 `packages/kernel` 的改动，按 `specs/action-architecture/spec.md` §3 基本合同复核，并同步那份合同文档。

### 3.4 本轮新合同的全链路

Manifest `methods`、撤销声明、到期提醒、后台任务回报、放置协议、搜索来源与对象读取器、页面操作卡、情境片段推荐、记忆、侧栏文件来源与浏览器、插件通知等，每一项沿「定义 → 注册 → 发现 → 调用 → 授权 → 执行 → 返回」走一遍，并验证停用、卸载、升级与撤权。每项都要有至少一个真实消费者、有守住它的测试、写进插件开发 Skill；没有消费者的合同删掉或标明未启用。

### 3.5 前端代码与设计系统

- **浏览器代码**：工作台与插件里以模板字符串交付的脚本，接入打包与类型检查，先用一个插件跑通，再逐个迁移；空 `catch` 改为有处理或有记录。

把稳定、重要、适合自动验证的要求纳入门禁并接进 CI，例如：vendored 包数量、`specs/` 根目录的 spec 必须有状态句、contracts 不得有占位 subpath、内置插件装配名单只减不增、宿主不得新增插件专属文件、浏览器脚本必须经打包与类型检查。每道门禁都做一次突变验证，证明它真的会拦。依赖业务判断的规则写清方法与示例，不变成脆弱的字符串检查。

## 4. 执行顺序与验证纪律

**顺序**沿用整理要求第 14 节：真实缺陷与权限、状态问题 → 契约和接入遗漏 → 模块边界 → 共享与 SDK 提取 → 清理 → 手册和 Skill。结构性收口在前两类处理完之后按片推进。

**每一片**写明真实问题、证据、新边界、兼容成本、受影响的行为与测试；改完重跑受影响的跨功能场景与用例。文件长、层次多或存在相似代码不能单独成为重构理由；避免万能 Service、无实际复用的抽象和只搬代码不改善职责的拆分。

**分支与 PR**：从最新 main 开分支，一个 PR 一个主题，不积累大量未验证的重构。合并前变基到最新 main，并重跑相关用例。

**测试**：不跳过、不放宽、不删除关键断言来换取通过。测试保护行为与协议，不冻结偶然实现。迁移代码时同步迁移测试的入口，不让测试继续调用退役的实现。

**回归纪律**（仓库已经踩过的坑）：

- 改过任何 `*/src`、`scripts`、`package.json` 之后，跑全量前先整体 `pnpm build`。单包构建写成 `pnpm --filter <包> run build`，`--filter` 放在 `run` 之前。
- 全量回归期间不改源码、脚本、`package.json` 和 `skills/`，只改 `docs/`、`specs/`。不并发构建。
- 保留完整输出。判断是否新引入，用干净基线工作树（`git worktree add --detach`）跑同一批文件对比。
- 停进程只按 pid，不用 `pkill -f scripts/run-tests.mjs`。
- 浏览器用例在 macOS 本机 Chrome 上跑，加 `--lang=zh-CN`。
- 有其他会话同时在跑时，构建与浏览器用例串行排时段。

**环境与协作**：用隔离 Home（`MOLIS_WORK_HOME` 指向临时目录，`MOLIS_WORK_SECRET_BACKEND=file`），不占用真实 Home 4207/4208 的 Agent 运行锁。跨仓修改 Prologue 前确认 SDK 工作区和其他负责人的范围。不重置、不覆盖别人的未提交改动。

## 附录 B：仓库系统整理要求要点

全文见 `docs/prompts/repository-systematic-review.md`，以全文为准。

1. **现场与归属**：读规则、协议、spec 与 Skill；查分支、工作树和他人任务；保护他人成果，不提交混杂改动；一份简洁总 spec；产品语义、公共契约、重大迁移先给方案。
2. **清单与预期行为**：清点全部 App、Host、Plugin、Module、共享包、后台任务、外部协议与 SDK；每项的场景、入口、成熟度、owner、注册与发现、调用链与测试、重叠关系；区分生产、实验、部分实现、弃用；新旧实现是否并存、消费者是否迁移完。
3. **模块划分与调用链**：职责是否清晰，是否切得过碎或混了不同生命周期；沿「输入 → 身份与权限 → 编排 → 领域 → 存储或外部 → 事件 → 反馈」追踪；查 App/Host 混入业务、UI 做状态转换、Store 混入网络与模型、插件重复通用能力、跨模块 SQL、循环与反向依赖、无意义包装、入口之间行为不一致。
4. **契约与注册**：每项要求的来源、范围、验证方式；应开放的能力是否注册、有入口、Schema 与错误和权限准确、能被发现调用、与 UI 共用路径，停用、卸载、升级、权限变化后状态正确；Manifest 与真实行为一致。
5. **自动发现与扩展**：沿「安装 → 校验 → 注册 → 加载 → 目录 → 发现 → 筛选 → 调用 → 结果」验证；权威来源唯一，没有重复静态名单；刷新与缓存失效；项目与账号隔离；重名、版本不兼容、部分失败；单个插件失败不阻断其他。
6. **逐插件**：用户任务闭环；占位与半实现；协议与入口；持久化与产物；越界依赖；重复能力；生命周期；撤权、失败、取消、并发、恢复；空数据、首次、无模型；同类插件横向比较；组合场景；平台接点（导航、搜索、命令、设置、连接、权限、通知、活动、执行历史、产物预览、后台任务、取消、恢复）。
7. **数据、状态、事件、生命周期**：每类事实唯一 owner；状态机；身份传递；多窗口与多进程；事务、幂等、部分成功；取消与完成、删除与执行、撤权与副作用之间的竞争；重试与恢复；孤儿数据；事件命名、载荷、时序与消费者响应；订阅、定时器、进程的创建、释放与恢复。
8. **AI 与 Prologue**：清点全部生产 AI 入口，核对真实调用链；模型与凭据、上下文、工具、身份、权限、审批、副作用前检查、预算、usage、事件、超时、取消、持久化、恢复；查供应商直连与旁路；工具能被理解和正确选择、按需发现；自动发现不绕过授权。
9. **前端质感与动线**：层级、布局、一致性；主次与危险操作；弹窗、抽屉、标签与页面的选择；窄屏、长文本、焦点、键盘、可访问性；加载、空、失败、部分成功、无权限、离线；闪烁、跳动、输入丢失、重复提交；用户路径与引导；跨页面保留上下文；前后端状态一致；用真实界面与截图验证。
10. **配置、安全、性能、升级、发布**：默认值与覆盖顺序；凭据轮换与撤销；敏感信息不进日志、事件与产物；外部输入、路径、URL 在真实边界校验；阻塞、重复查询、无界扫描、资源增长；超时、取消、背压生效；不吞错、不假成功；旧数据迁移；源码与产物一致；不依赖开发机特有的路径。
11. **清理**：死代码、重复实现、旧入口、废弃配置、冗余依赖、过期兼容层、失效测试、旧文档；删除前核对动态加载与外部消费者；统一术语。
12. **测试与预期**：测试调用当前生产入口；Mock 符合真实接口与时序；不因过度 Mock 绕过注册、权限、持久化；fixture 保留真实旧数据；查只断言不抛错、用被测算法生成预期、只测内部方法、过度绑定实现、持续放宽断言；复核 skip 与排除项。
13. **手册与 Skill**：Prologue AI 手册与 Skill、插件开发 Skill 覆盖 owner、协议、注册、发现、对外入口、权限、事件、数据、生命周期、前端、测试、文档与发布资产；路径、链接与触发说明经代表性场景走查。
14. **实施顺序与验证**：真实缺陷与权限问题 → 契约遗漏 → 模块边界 → 共享与 SDK → 清理 → 手册；通过正式扩展路径验证，不在测试里直接注入对象；并发要制造真实交错；区分源码审查、Mock、真实集成、产品实操与用户验收。
15. **交付与完成标准**：可追溯的结果；区分已确认、推断、未验证与已完成、在途、待决；持续完成已授权且证据充分的工作，不在首次扫描或部分修复后提前结束。
