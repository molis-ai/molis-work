## 1. 背景

- 先答「到底哪里不一致」。同一个上限，四层各数各的：

- 对着数字看（提示词为例）：32000 个 🟢 是 32000 个字、64000 个单元。schema：收下；Images 服务端：`64000 > 32000`，拒；这是 MISC 说的那一处。我在草稿目录量过 Ajv：`maxLength: 32000` 对 32000 个 🟢 返回通过，对 32001 个返回不通过；`maxLength: 128` 对 128 个 🟢 通过，对 129 个不通过。
- **平台端口把事情变复杂了（起草时才看到的，MISC 没写）。** Images 的 `start`（`service.ts:91-138`）受理任务以后，后台的 `runImageJob`（`service-job.ts:22-65`）在 `:37-43` 调 `run.imageGeneration.generate(request, …)`。这个 `imageGeneration` 是平台给的，进去先过 `copyRequest`（`image-generation.ts:103-109`）：`text(request.prompt, 32_000)` 里 `value.length > max` 按单元数，超了抛 `plugin.image_input_invalid`。按代码推断（没跑）：
  - 只改 Images、平台不改：一条 16001～32000 个两单元字的提示词，`start` 受理成功（返回 `running` 的任务），接着 `generate` 抛 `plugin.image_input_invalid`；`runImageJob` 的 `catch`（`service-job.ts:54-63`）把任务记成 `failed`，信息经 `failureMessage`（`:67-74`）：这个错误不是 `images.*`（`isImagesFailure` 看码以 `images.` 开头，`error.ts:35-38`），码也不是 `host.image_*`，`kind` 不是 `timeout`，落到最后一行「生成失败：无法连接厂商、下载图片或保存结果。请检查网络、API 基址及磁盘空间……」。厂商一次都没被调用，人却被告知是网络问题；
  - 现在（两边都不改）同一条提示词是入口就被 `images.invalid` 拒，句子虽数法不对但清楚，没有任务、没有计费。所以只改 Images 是**倒退**，必须平台先改；
  - 平台一半改成按字数数以后，Images 这一半放宽才是一致的：schema、Images、平台端口、库，提示词的上限都是 32000 个字。
- 放宽的面有多大：只放宽「字数不超过、单元数超过」的内容，最多放宽到原来的两倍单元数，且数据库、厂商这边没有按单元数的限制（库是 `TEXT` 没有 `CHECK`）。id 类字段放宽也不会让库里出现新的长 id：服务的 id 是服务端 `randomUUID()` 生成的（`service.ts:57`），改服务时 `input.id` 必须是已有的（`:59`），删除、读任务按已有的找；只有请求号是调用方自己给的，库里按文本存，没有长度限制。
- 谁能碰到这个不一致：页面碰不到（页面的提示词框 `maxlength="32000"` 数单元，永远不会送来超过 32000 个单元的提示词；见第 8 节第 2 条）；MCP 工具 `images.jobs.start__v3`、助理、工作流步骤、别的插件的调用，都直接面对 schema，能送来 16001～32000 个两单元字的提示词。实际极少见（一条提示词里要有一万六千个以上的 emoji 或同类的字），所以影响小；做它的价值是「一个上限只有一个单位」，以及信息里写的「字符」名实相符。
- 这个项目里同类的前例：T-077～T-094 把各插件的库一侧改成 `[...x].length`；T-185 把文字模型端口（`host-complete-text.ts`）改成按字数；本单是 Images 的服务端一侧，平台一半是生图端口。
- 数法对不对：新函数不能直接 `[...text].length`，因为 `connection_id`、`size`、`aspect_ratio`、保存服务的三个字段没有 schema 上限，调用方（MCP、工作流）能送来很长的串。T-197 在同一类输入上量过：拍平的 3600 万个单元的串，`[...x]` 约 2.7 s 到 6.4 s、多占 1.0 到 1.7 GiB（那台机器，数字随机器变）。所以先用两个 O(1) 的比较挡掉不用数的（`text.length <= limit` 一定放得下，`text.length > limit * 2` 一定放不下），只有中间那一段（最多 `2 × limit` 个单元，提示词最多 64000）才展开数。
- 页面一侧（不做，写在这里是让评审知道看过）：`ui.ts` 的五个 `maxlength` 都按单元，但**只会比服务端更严或相等，不会更松**：提示词 32000 个单元 ≤ 32000 个字；名称 100、模型名 200 同理。所以它们造不出「页面收下、服务端拒绝」。唯一更松的是尺寸（`:68`，100 对服务端 64）和宽高比（`:69`，100 对服务端 32），那是数字本身不一样，不是单位问题，也不在本单（第 3 节）。浏览器脚本里没有长度上限（`browser/compose.ts:14-16` 直接送 `.value.trim()`），页面发送失败时显示服务端的话（`messageOf`，`browser/dom.ts:29`）。

## 2. 目标

1. schema 收下的提示词，Images 服务端也收下：16001 个和 32000 个两单元字的提示词，`jobs.start` 返回 `running` 的任务，任务里和库里的提示词一字不差，任务跑到厂商（本机厂商夹具被调用一次）并成功（`RAC-2115`，要平台一半已合入）；
2. Images 自己查的别的长度同样按字数数：128 个两单元字的请求号收下且仍按请求号去重（`RAC-2116`）；64 个两单元字的尺寸、100 个两单元字的服务名称收下，多一个就回 `images.invalid`、话里写「最多 64 个字符」「最多 100 个字符」（`RAC-2117`）；
3. 普通文字一字不差：64 个一单元字的尺寸收下、65 个拒；前后空白先去掉再数；全空白拒；空串表示没有尺寸（`RAC-2118`）；schema 的上限不动：提示词 32001 个字、请求号 129 个字仍在 Images 之前被 `actions.input_invalid` 拒，没有任务、没有厂商调用（`RAC-2119`）。

   ```ts
   function textField(value: unknown, name: string, maximum: number): string {
     const text = typeof value === "string" ? value.trim() : "";
     if (!text || !withinCharacters(text, maximum)) throw imagesErrors.invalid(`${name}不能为空，且最多 ${maximum} 个字符。`);
     return text;
   }
   /**
    * Whether `text` has at most `limit` characters: the unit the action schemas' `maxLength` counts. A character is one or two UTF-16 units.
    * The two cheap answers come first, so a long text is never spread into an array: at most `limit * 2` units are ever counted.
    */
   function withinCharacters(text: string, limit: number): boolean {
     if (text.length <= limit) return true;
     if (text.length > limit * 2) return false;
     return [...text].length <= limit;
   }
   ```

   说明：
   - 和原来的 `textField` 逐项对照：不是字符串、`trim` 以后为空 → 仍抛同一句（`!text`）；`trim` 以后放不下 → 仍抛同一句；返回值仍是 `trim` 以后的串。唯一变的是「放不下」怎么判断；
   - `withinCharacters` 的三步各自成立：一个字至少一个单元，所以单元数 ≤ 上限，字数一定 ≤ 上限；一个字至多两个单元，所以单元数 > 2 × 上限，字数一定 > 上限；中间才展开，`[...text]` 按码点切，孤立的高、低代理各算一个字，与 Ajv 的数法一致（起草时在 48000 个随机串上比过，0 个不同）；
   - 第一步 `text.length <= limit` 和第二步 `text.length > limit * 2` 都只是为了快：去掉任何一个，结果都不变（循环到最后一步仍是对的），所以是等价变异，第 6 节不钉它们，只钉它们的边界数；
