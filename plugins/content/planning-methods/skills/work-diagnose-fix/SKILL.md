# 诊断与修复

先复现和定位根因，再修复、回归并恢复可信状态。

适用于：故障诊断、缺陷修复、质量问题。

## 规划路径

1. 固定症状与复现条件
2. 缩小影响面并提出可证伪根因
3. 实施最小完整修复
4. 回归原场景和相邻边界

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| symptom | 症状 | 什么输入、环境和动作稳定产生问题？ |
| root_cause | 根因 | 哪个契约或状态转移导致症状？ |
| regression | 回归 | 如何证明修复且没有破坏相邻路径？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| fix-after-cause | 修复依赖已验证的根因，不依赖未经证实的猜测。 | fix depends_on root-cause evidence |
| regression-after-fix | 回归验证消费已经完成的修复产物和原始失败基线。 | regression depends_on fix and failure baseline |

## 完成证据

- 修复前失败证据
- 修复后通过证据
- 相邻路径回归

## 收口检查

- 根因能解释全部关键症状
- 修复没有靠补丁互相补偿

## 常见误拆

- 看到报错就加条件
- 只消除表面症状
- 缺少修复前后对照

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
