## 1. 问题与范围

同发布者的新 Home 签名包当前被 `PluginInstallService.confirm` 与 `openHomeInstalledPlugins.installPackage` 两处提前拒绝，提示先卸载重装；项目包已走共用 `installedLifecycle('upgrade')`。设置页只在项目 `data.plugins` 中找旧版本，无法显示 Home 升级预览。接受方案要求同发布者、版本递增、范围不变时原地升级，数据与安装身份保留，新批准、密钥、提示词归新版本。两个范围仍不提供用户回滚。

仅完成 BL-711，不实现 T-145 的逐项目同意、T-143 模型设置/生图、T-144 Agent/方法、T-149 创作台签名，也不借此放开沙箱权限、改包信任或打开真实 Home。BL-916、PG-011整体不因本片完成而全部销账。

## 2. 已定语义及实现要求

1. `plugin-install-service.ts:confirm` 去掉 Home 一律拒绝的分支，保留预览绑定actor/project/时限与一次性消费；仍先检查范围、发布者、ID命名空间、版本，再 pinPublisher / save / 切换。另一发布者、相等或更低版本、范围改变，拒绝时旧安装、授权、文件、密钥和调用能力都不变。
2. `home-installed-plugins.ts:installPackage` 根据本 Home 当前有效安装决定 install/upgrade，调用同一 `installedLifecycle`，不能新增第二份升级算法。查询仍由 Host 当前记录决定，不能用输入声称“这是升级”。禁用安装升级后仍禁用、不得自动运行；running安装升级后使用新定义与提示词；quarantined/包不可读/撤销发布者按共用生命周期现行拒绝，不顺手扩恢复语义。
3. 共用 `installed-plugin-version.ts` / 生命周期已经拥有版本切换、批准/密钥、提示词与失败补偿，先复用。失败补偿恢复原版本属于内部一致性恢复，不能因为D1“不做用户回滚”删掉它；用户主动rollback仍按原断言拒绝。
4. 设置页读取Home列表后保留该列表，按预览 `runtime_scope` 选Home或项目旧记录，再显示已有中英文“已装的是x，装上后升级到y；数据保留”。同一 review 对初次安装和 Home 升级均展示本次签名预览的服务及精确 HTTPS origins；复用现行 preview 返回值，不新增端点或来源授权规则。新权限/声明仍显示，来源改变时让人重新看见并明确确认；取消不安装、不升级。只改现有设置流程，不新增页面资源。当前 API 有 origins 而实际设置页尚未展示，这是既有 BL-530/BL-691 合同缺口，与 T-122 核收交接在本单统一补齐。
5. 本片的“Home包”包括已支持的integration包，不能只删app两处拒绝却留下集成旧声明。开工方案必须逐步核对integration升级：`assertIntegrationsFree`是否只忽略同一真实owner；旧`withdraw/detach`与新`expose/attach`同队列的先后；改服务/来源后登记是否刷新；T-134的连接声明者钉住是否继续拒别的发布者。当前`IntegrationRegistry.attach`的“已attached只换contribution”依赖不升级旧前提，`IntegrationDeclarations.declare`已有记录直接返回；需证明新版本不会仍使用旧来源/声明。若确需改登记，先根放#1672文件锁，范围仍限本次升级必经链。
6. 签名集成来源变更仍按BL-530/BL-691现行预览逐项展示并确认，不能自动沿用旧来源批准。范围仍是已支持source，不加document_import或新OAuth声明能力。
7. 升级、取消/撤权/关闭并发沿现行世代和beforeEffect检查：旧实例晚回执不写新版本业务；失败不留混合批准/密钥/提示词。安装ID延续必须从实际Runtime记录验证，不能仅比较plugin_id；新安装/其他发布者不得接管T-134连接。
