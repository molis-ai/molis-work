# work-split 审读与研究结论｜2026-10-17

这是产品介绍的取材与研究结论摘要。对应[当日正文](../archive/产品介绍-2026-10-17.md)，写法遵循[日更规范](../日更规范.md)。本次完成分支产物审读、仓库事实核对和公开资料补研；未做真人访谈、付费竞品试用、最终 App 全旅程实操或用户验收。

## 1. 读了什么，证据到哪里

本轮审读了内部官网需求与设计、已有决定、两类角色研究、历史场景稿和演示方案。这里保留可用于产品表达的研究结论；原始材料、非公开文件清单及本地取证数据不在本文展开。

审读区分方案获认可、官网已实现与 Work 产品已实现。读取了方案正文、比较表、场景脚本、历史截图和相关实现差异；截图与动画只作叙事参考，不能证明当前 App 功能。未运行方案交互或官网，未对全部内嵌图片重新验收。

Work 的远端、主线、分支、工作树与活跃设计由另一子 Agent 盘点，主 Agent 对 Release、关键代码和冲突独立核对。具体覆盖和缺口见[分支盘点](2026-10-17-分支盘点.md)。两类角色的补研结论分别保存在[开发者场景](2026-10-17-开发者场景.md)和[知识工作者场景](2026-10-17-知识工作者场景.md)。三份报告是依据，不自动等于产品验收。

## 2. 应继承的是写法与判断，不是旧卖点

**产品总纲继续是“你和 AI 在同一张工作台做事，工具可以按自己的方法组合”。** Goals 的要求与验收是开发者的重要切入点，但不足以定义整个 Work。文档、材料、日常安排、流程与工具创作同样需要在全景里有位置。

两种入口应分别回答不同问题：

- **写代码的人**：几天、多个会话以后，还按原来认可的要求交付吗？Agent 报告、工程依据和本人的体验结论能分清吗？重点是跨次交付、范围变化与验收责任；换 Agent 只是一种情境。
- **写文档、管事情的人**：几份材料怎样变成能交给别人的判断，引用查得回去吗，修改会不会丢，交完以后谁跟进？重点是材料、人工判断、交付版本与后续行动；不强行套“换 AI 接着写”。

保留旧稿“场景—麻烦—怎么做—用到”的具体叙事，每个例子增加目标用户、交付对象、真实需求证据、原办法和不适用条件。全景负责防遗漏，场景负责判断人是否需要，Why 只选少数最有根据的场景。官网可以省去内部证据表，但不能省掉会改变用户预期的条件。

## 3. 本次纠正的事实与比较

| 原材料中容易沿用的结论 | 本次处理 |
| --- | --- |
| Coding 已有共享工作板，就等于完整团队协作 | 区分 Agent 协作、本机讨论、多人的共享项目；后两者的通知、同步、助理进群等不能由前者推导 |
| PPT 只有内容列表、还不能导出 | 回查 main：已能导出基础 PPTX，且早于 V3；范围是标题、要点、备注与颜色，不是复杂图片图表排版 |
| Workflows 仅三类衔接、四个内容站 | 回查声明与处理器：模板、AI、人工、判断四类；九个内容 owner。成果只读，Jelly 接的是笔记，各站接收/创建能力不同 |
| 语音、CGS、工作简报统一叫“开发中” | 内部细分分支实现、本地修补、需求设计；CGS 主创作切片不代表研究、选题、正式发布也完成 |
| 0.3.0 发布草稿已经可以下载使用 | 公开最新正式版仍是 v0.2.0 源码；0.3.0 是草稿，不能当公开新版安装包。安装和首次模型配置仍是首批用户路径的关键问题 |
| 测试数字打勾，目标就已经可靠做完 | 区分 Agent 提交的报告、可信产物、目标记录和本人验收；Work 也不控制所有外部 Agent 独立文件写入 |
| 只有 Work 能跨 Agent 接力、记规格、设完成门禁 | 当前 Superset、Codex plugin、Traycer、Conductor、Claude Code hooks、Factory 都有相关机制。比较改成具体任务的维护成本与剩余缺口 |
| 知识工具只有聊天，引用和导出需要自己搬 | NotebookLM 等已有引用、报告/表格导出与部分来源同步；Work 要证明其特定本地材料与后续行动场景更省事，不能先宣称对方没有 |
| 本地优先自然意味着不外发、更便宜、更安全 | 本机事实保存与联网模型外发分开；模型配置、费用、权限与升级成本都进入用户体验判断 |
| 旧演示里的首屏视频时长、稿子逐句来源、一次点击全接通 | 视为示意。跨插件来源、改写后关联和导出要实际走通；不会因为动画画出了出处就认定产品保证语义正确 |
| 旧小样里的一个修复示例 | 示例内部的时间与数值互相对不上，修复方法也未证实。新案例不沿用这个装饰性技术细节 |

以上修改只进入产品介绍和内部研究，没有修改 Club 官网或其事实源。

## 4. work-split 九项研究需求的完成程度

以下九项问题来自前轮内部调研的问题框架，这里按主题列出。按“拿到什么证据”报告，不把桌面研究包装成真实用户研究。

| 问题 | 本轮得到什么 | 仍缺什么，下一步怎样做 |
| --- | --- | --- |
| 真实用户访谈/调查 | 两类角色各有候选画像、任务链、反例与访谈问题；开发者直接 issue、知识工作者原始使用讨论提供问题线索 | 尚未联系或访谈任何人。各找 3 位近期完成过相应任务的人，带最近一次材料/记录回放，而不是问“喜欢这个概念吗” |
| 同类产品实操 | 更新官方能力，准备对照路径，消除“对方没有”的错误前提 | 未安装或登录竞品。拿同一任务分别用原工具和 Work，记录配置、重输、复核、恢复成本；需要账号/付费时再按权限执行 |
| 完成、验收与承诺机制 | 已补研共享规格、门禁、QA、会话状态等官方机制，并与 Work 现行边界比较 | 机制比较不等于体验比较。实操“要求变更→新会话→报告完成→本人未验收”，观察是否误收尾、如何恢复 |
| 团队协作模型 | 核查 Work 当前本机讨论、Agent 工作板与完整多人方向的差别；主流办公/项目工具已有分派通知 | 未做多真人协作。先验证两个人对同一项变更怎样确认、知道对方收到，别先设计完整组织/权限系统 |
| 社区真实抱怨 | 开发者报告与知识工作者原始讨论已分类，记录年代、来源角色、偏差；闭合的旧问题不当当前故障 | 小样本不能给频率/市场份额/付费意愿。下一轮只围绕优先场景追近期反例，不能堆抱怨条数证明需求 |
| 安装分发与第一次使用 | 核对公开 Release/草稿、官网入口与模型配置依赖；明确源码版和新版 App 的区别 | 未让新用户从下载走到真实结果。先在可交付安装物上记录第一份结果路径，再决定是否需要额外引导；不以本机开发环境替代 |
| 国内产品与使用条件 | 已读原始国内产品报告；补研引用飞书等一手能力，识别“已有办公套件足够”的反例 | 未系统验证中国区账号、访问、支付、模型服务与数据条件。旧报告价格/品牌判断未全面刷新，不进入正文事实 |
| 定价与商业模式 | 识别自带模型、配置、维护和迁移成本；未据此推导更便宜 | 本轮没有定价研究结论。先问用户现在为这件事付出什么、谁有购买决定权，再核同日价格和方案限制；不直接给出价格建议 |
| 提示注入、权限与外发 | 读取现行授权/事实 owner/材料角色边界；正文明确本地保存仍可能联网外发 | 未做对抗实操。后续用无敏感资料验证来源中嵌入的指令、拒绝授权、取消后的迟到结果；需要实际拒绝与无副作用证据 |

开发者补研的 D1–D8、知识补研的 K1–K10 是各自报告里的研究分类；正文的 D/K/T/X 是产品场景编号，不能按相同数字自动合并。引用时同时写名称：知识补研的“本地知识资产问答”对应正文 K1/K4 的一部分，“项目/周报”对应正文 K2；正文不会把研究文档中的十条都宣布为核心用户。

## 5. 优先验证什么产品方向

下面是本轮建议，尚未批准实现或排期。每项先用现有对象和动作做真实任务，发现确切缺口后才增功能；不新建研究平台、业务数据库或另一套任务系统。

| 顺序 | 用户问题与最小改法 | 可观察的实验 | 什么结果会推翻建议 |
| --- | --- | --- | --- |
| 1 | **首次交付能否开始。** 把下载/版本、模型连接、第一件事入口连成准确说明，先复用现有配置 | 一位新用户拿自己的非敏感任务，从实际安装物到第一份可保存结果；记录卡住和需代操作的位置 | 全程主要卡在核心功能本身，则先修核心任务，不继续堆教程 |
| 2 | **开发交付是否少误会。** 在现有目标里看清当前要求、变更授权、报告来源和本人验收，减少与 spec 双份录入 | D1/D2 场景换成真实小功能；中途改一条要求、换会话，最后故意保留一个需人判断的缺口；与规格文件 + CI + PR 对照 | 维护目标比收益更大，或原流程已同样清楚，应收缩到特定复杂交付人群 |
| 3 | **资料变稿子的链条能否保持。** 复用现有来源、Pages 和固定成果；先暴露缺失引用与实际放置位置 | K1 用本地文件、网页和一条未证实说法出一页简报；本人改写，再导出，交给另一人追查一个判断 | 引用只在演示中成立，或主要成本仍在输入整理，则先补这一步，不能宣传“来源一路跟随” |
| 4 | **周报能否保住当时的事实。** 先保存一份经过审阅的固定交付；不要先实现全自动工作简报 | K2 下周改变任务状态，再打开上周交付；重生成本周内容时检查人工说明是否保留、变更是否可见 | 人工维护两份反而更累，或原工具已经完成，则重新找更窄输入条件；自动增量合并仍需设计 |
| 5 | **第四次复用是否仍省事。** 先将一条已手工稳定执行的流程存下来，复用原插件动作 | K9 连续四次整理同类客户材料；第四次新增一字段、替换一来源、让一次 AI 失败，观察用户能否改规则、恢复且不重复交付 | 每次都要改内部 ID/修提示/清重复结果，则暂缓“工具越用越顺”，先改善维护与恢复 |
| 6 | **提醒是否真值得打断。** 先复用现有定时/事件提醒，不新增自动派单 | 记录一周实际提示：哪个需要决定，哪个重复，哪个缺材料；每条能否返回原工作 | 大多没有明确行动，或用户更愿意固定时间处理，则降低主动性，改成可查汇总 |

研究成功不以用户说“看起来不错”计，而看他们是否能用自己的材料完成原本要做的事，知道结果边界，且愿意在下一次继续用。公开资料只帮我们缩小要验证的问题，不能替代这个结果。

## 6. 官网如何使用这份输入

1. 首屏从当天第一章取短句；按两类角色各演一条工作，不把所有未来功能放进同一个“顺滑完成”的故事。
2. 功能全景保证覆盖；用人物任务组织动画，内部仍回链到分支/需求/发布证据。
3. “为什么”先用正文 D1/D2 与 K1/K2；方法复用和本地架构解释其成立条件，不用竞品弱化表制造优势。
4. 所有数字、名字和动画是示意时明确标注；没有实际产物接入的“测试通过”只写报告来源。内部 Issue 不出现在官网正文或截图。
5. 官网简标签可以是“已发布 / 开发中”，但只有需求的步骤要就近说明尚在设计；正式下载入口只取真实公开 Release。新版草稿不等于公开发布。
6. 官网事实文档仍按其所属仓库的事实源规则维护。本文给出输入，不自动修改、批准或发布官网。
