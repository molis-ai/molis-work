## 1. 背景

- 先答 MISC 没写、但决定单位的事：说明和错误信息下游有没有按字数的上限。没有。
- 链路：到点的任务 → `fireScheduleWakeup` 调唤醒动作（`index.ts:410` 起的 `try`）→ 动作回 `{ detail?, status? }`，或者抛错 → 在 `:413`、`:418` 截到 500 → `:428-431` 写进 `schedule_wakeups.detail` → 读回时 `toWakeup`（`:530-540`）原样交出。
- 受影响的下游：

| 下游 | 位置（main `a3f5fd7ed`） | 长度怎么管 | 半个字会怎样 | 受影响 |
| --- | --- | --- | --- | --- |
| 库表 | `index.ts:111`：`detail TEXT`，没有 `CHECK`（同表的 `status` 有）；写入 `:428-431` | 无 | SQLite 把孤立的高代理存成 U+FFFD，读回来最后一个字符是 `�`，长度还是 500 | 是 |
| 读回 | `toWakeup`，`index.ts:530-540`，`detail: row.detail` | 无 | 乱码一路带出去 | 是 |
| 日程页详情「上次的说明」 | `plugins/native/schedule/src/ui.ts:182`，`job.last_wakeup.detail` 只 `p.escape`，不截 | 无 | 说明末尾一个 `�`，用户看得到 | 是 |
| 宿主的 Scheduler 服务 | `apps/local-host/src/plugin-scheduler-service.ts:31-36`，`view()` 把 job 记录（含 `last_wakeup`）整个展开 | 无 | 同上，交给插件的就是这个值 | 是 |
| 唤醒动作的回执 | `apps/local-host/src/plugin-scheduler-owner.ts:42-59`，只查 `detail` 是不是字符串、`status` 是不是三个值之一 | 无 | 到 Scheduler 的是动作回的原串，截的地方只有 `index.ts` 这两行 | 截点只在 Scheduler |
| 合同 | `packages/contracts/src/services/scheduler.ts:30`（`detail: string \| null`）、`:70-74`（`ScheduleWakeupReply` 的 `detail?: string`） | 无 | 不变 | 否 |
| 唤醒动作的输出 schema | `plugins/native/feed/src/runtime-wake.ts:22`、`plugins/native/schedule/src/background-actions.ts:15`：`detail: { type: "string" }` | 无 `maxLength` | 不变 | 否 |
| 动作合同快照 | schema 不变 | — | 快照不变 | 否 |

- 所以单位只能由 Scheduler 自己定：包里自己的长度判断都按单元数（`index.ts:472`、`:480` 的 `> 200`，`:507` 的 `> 512`）；库、合同、schema、页面都不限字数；T-162、T-166 在 Schedule 插件里对同类截点的写法也是「整字，且不超过 N 个单元」（`plugins/native/schedule/src/job-title.ts:7`、`runtime-wakeups.ts:18`、`operations.ts:262`，main `1ebf09a8d`）。本单照这个：整字，总长不超过 500 个单元；
- 输入没有上限：唤醒动作回的说明、抛出的错误信息都是动作自己的字符串，Scheduler 和 `plugin-scheduler-owner.ts` 都不限长，一个插件可以回几 MB。所以截点不能先把整串展开成数组。独立脚本量过（拍平的 3600 万个 UTF-16 单元的串，这台机器，数字随机器变）：

| 写法 | 耗时 | 多占内存 |
| --- | --- | --- |
| `[...text].slice(0, 500).join("")`（T-079 的写法） | 约 2.7 s 到 6.4 s | 约 1.0 到 1.7 GiB |
| 本单的循环（`wholeCharactersWithin`） | 约 0.02 到 0.17 ms | 无 |

  每次唤醒都过这一行，所以代价是每次。循环最多走 501 个字（超出就停），不建数组；
- 日程插件自己的唤醒动作也回 `{ status, detail }`（`plugins/native/schedule/src/operations.ts` 里的 `return { status, detail: … }`），说明会经过这里；抛错的路径则覆盖别的插件的唤醒动作。两条路径都要钉住（第 6 节）。

## 2. 目标

1. 唤醒动作回的说明，记下来的是整字：保留前面能放下的最长一段，总长不超过 500 个 UTF-16 单元，不以半个字结尾；
2. 动作抛出的错误信息同样（`Error` 取 `message`，其余取 `String(error)`）；
3. 放得下的原样留下；`reply.detail` 缺省或为 `null` 记 `null`，空串记空串；`status` 的选择一个字不动；
4. 用例钉住上面三条：撤销任一处、改错截点或上限，各自都红。

## 5. 做法

统筹已定之外的决定都是起草线定的，照做；觉得不对在【方案】里说，不要自己换（第 8 节写了理由）：

1. **`index.ts`**：三处，其余一个字不动。

   1. `:413`。原（六个空格缩进）：

      ```ts
            detail = reply?.detail?.slice(0, 500) ?? null;
      ```

      换成两行（同样缩进，后面的行号顺延 1）：

      ```ts
            const replied = reply?.detail;
            detail = replied == null ? null : wholeCharactersWithin(replied, 500);
      ```

      `== null` 把 `undefined` 和 `null` 都记 `null`，空串仍走函数、记空串，和原来 `?.slice(…) ?? null` 的结果一样；`status = reply?.status ?? "ok";` 在下一行，不动；
   2. `:418`（新 `:419`）。原：

      ```ts
            detail = (error instanceof Error ? error.message : String(error)).slice(0, 500);
      ```

      新：

      ```ts
            detail = wholeCharactersWithin(error instanceof Error ? error.message : String(error), 500);
      ```

   3. `function iso(value: Date): string {…}`（原 `:466-468`，新 `:467-469`）之后，空一行，插入下面这个函数，再空一行接 `function normalizeIdentity`（新文件里它在 `:472-481`）：

      ```ts
      /** The first characters of `text` that fit in `limit` UTF-16 units: a character of two units is never cut between them. */
      function wholeCharactersWithin(text: string, limit: number): string {
        if (text.length <= limit) return text;
        let cut = "";
        for (const character of text) {
          if (cut.length + character.length > limit) break;
          cut += character;
        }
        return cut;
      }
      ```

   说明：
   - `for…of` 按字（码点）走，一个两单元的字的 `character.length` 是 2，放不下就停，所以不会在两个单元之间截；
   - 每一轮只多一个字，最多走 `limit + 1` 个字，不建数组；
   - 第一行的 `text.length <= limit` 只是快路：短串（绝大多数）直接返回。去掉它结果不变，是等价变异，不钉（第 6 节）；
   - 文件里的注释都是英文，保持；不新增中文，界面翻译的门禁不会动。

## 8. 与默认不同的

1. **单位：整字，且总长不超过 500 个 UTF-16 单元；不是「500 个字」。**统筹觉得要「500 个字」，在【方案】阶段说，起草线改书（用例的输入和期望值要重算），不要自己换。理由：
   - Scheduler 之后的每一环都不按字数管（第 1 节的表）：库是 `TEXT` 没有长度，合同和输出 schema 不限，页面直接 `escape`。要一个字数上限，就是新加一条规则；
   - 包里自己的长度判断都按单元数（`> 200`、`> 512`），Schedule 插件里 T-162、T-166 对同类截点的写法也是「整字，且不超过 N 个单元」；
   - 存进库的串不会比今天更长（最多 500 个单元）；「500 个字」的写法（`[...x.slice(0, 1000)].slice(0, 500).join("")`）最长 1000 个单元，是另一个存进库的值；
   - 代价：第 500 个单元落在两单元字中间时，现在少一个字（499 个单元）。这就是整字截的意思。
2. **截点用本包里一个 9 行的循环函数，不是 T-079 的 `[...x].slice(0, n).join("")`。**统筹觉得要原样，在【方案】阶段说。理由：
   - 说明和错误信息没有上限（第 1 节），原样写法要把整串展开成数组：拍平的 3600 万个单元的串，约 2.7 s 到 6.4 s、多占 1.0 到 1.7 GiB，每次唤醒都这样；循环最多走 501 个字，约 0.02 到 0.17 ms，没有额外内存（独立脚本，这台机器，数字随机器变）；
   - 循环的写法本来就是房子里的写法：`plugins/native/schedule/src/job-title.ts:7`、`runtime-wakeups.ts:18`、`operations.ts:262`；
   - 另一种：先 `slice(0, 1000)` 再展开（T-190 的做法），仍按「500 个字」，见上一条；
   - 再一种：`.slice(0, 500).replace(/[\uD800-\uDBFF]$/u, "")`（去掉结尾的半个字）：不用循环，也不会更长，但只对「结尾恰好是孤立高代理」有效，起草线要多一条正则；没选，因为循环更直白。
3. **函数放在 Scheduler 包自己的 `index.ts` 里，不放 `packages/plugin-sdk`。**同样的循环现在在 Schedule 插件里已有三份；Scheduler 不能 import 插件，放进 SDK 是公开 API 的改动（`pnpm api:update`、对插件作者的影响），另派。统筹要收成一份，在【方案】阶段说。
4. **`full` 预计 `[]`，不进集成批。**第 7 节写了「指定文件名」与 `--base` 两种写法的差别；开发用 `--base`，结果不是 `[]` 就停。
