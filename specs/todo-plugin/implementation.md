## 2. 实现决定（按推荐（用户授权））

1. **个人插件，Home 级提供方**：Todo 在 catalog 标 `personal`（每个项目都可用）。数据在 `{home}/todo/todo.db`，一张待办表，每条带 `project_id`（个人或暂未归类时为空）。动作由一个 Home 级提供方登记（同 Jelly），所有动作 `scope: "home"`：没有项目时（项目列表页、个人工作）也能用。
2. **作用域在处理器里强制**：调用方带着某项目时只看到“个人＋暂未归类＋这个项目”的待办；不带项目时只看到个人和暂未归类。跨所有项目的“全部”视图只对 `audience: "user"`（用户本人界面）开放，助理、工作流、MCP 调不到（spec 5.4）。改归属：个人、暂未归类、当前项目三种；移到别的项目留到后续。
3. **状态与历史**：五种状态＋归档标记；每次修改记一条历史（修改前后、由谁：用户本人／助理／其他），用户本人改过的字段记入“手动改过”（spec 6.5 的保护依据）。
4. **撤销**：按历史撤销（单条修改、批量修改、完成、新建）；撤销前核对版本，之后被改过就拒绝并说明。**删除不可撤销**：删除是“不可撤销”效果，执行前确认（与动作效果分类一致，助理侧也会逐次确认）——spec 5.8“删除可以撤销”据此改为“删除需确认、不可撤销；批量修改与完成可以撤销”。
5. **日期**：截止日期＋可选截止时间、计划处理日期、提醒时间（带时区的时刻）三者独立；“今天”按本机时区。快速记录的日期识别在浏览器端用规则完成，不调模型，保存前以可改的标签显示。
6. **提醒（第一阶段）**：提醒约定、到期判断、稍后／关闭／知道了、错过合并都由 Todo 自己保存；到期后在 Todo“今天”顶部和首页事项里出现。**暂不做推送**：助理的插件推送入口做好后，到期改为经它送达底栏提醒（受勿扰规则），避免两套提醒。关闭应用期间不会按时提醒，设置提醒处如实写明（D09）。
7. **重要标记**只能由用户手动设置；动作对 `audience: "agent"` 不开放这个字段的写入。
8. **对后续助理接入的准备**：对象读取器 `todo.item.subject.read`、搜索来源、`result_subject`、`expected_revision`、页面 `data-assistant-context`。
9. **从 Inbox、灵光转为待办（D02）由 Workbench 组合**：两个插件只在详情里放一个带数据的按钮（`data-make-todo` 及标题、对象、打开位置），Workbench 点击时调 Todo 的新建接口，所以 Inbox、灵光都不依赖 Todo；页面上没有 Todo 时按钮不显示。原条目作为待办的来源保留（Inbox 条目 `inbox_entry`、灵光 `lingguang_spark`，与灵光动作声明的对象种类一致，可点回原处），不改原条目的状态；同一条再转一次找到原来的待办（请求号 `inbox:<id>`、`lingguang:<id>`），删掉待办后可以重新转。转成的待办归属当前项目。

**Todo 侧做了什么**：
- **撤销声明（D08）**：下面这些写动作在用户明确要求时由助理直接执行，工作面板给“撤销”。删除仍然不可撤销、每次确认。
  - 新建、修改、状态、归档、关联：按 `change_id` 撤销。
  - 批量、采用整理结果：按 `batch_id` 撤销。
  - 整理材料：撤销就是收起那份整理结果。
- **详情接入助理**：
  - “交给助理推进”：把这件待办作为对象、它的细节作为材料交给常驻助理。已有未完成的相关工作就接着同一项做。
  - “助理工作”一栏：列出相关工作及状态，可以“继续推进”。
  - Todo 内的修改会通知相关工作重读。
- **给助理的方法**：“整理待办”“推进待办”。后者要求状态只提议，做成的草稿挂回待办。改状态动作的说明也写明“推进不等于改状态”。

- **放置**：
  - Home 作用域的 `todo.placement.move`：身份不变、记入修改记录、可撤销。
  - 个人空间里 Todo 按个人视图。
  - 对象读取带 `project_id`；已归档的待办读取时报 `todo.not_found`。
  - 详情标题行留了位置槽。

### T6 第一片：Inbox、灵光转为待办（D02，2026-09-28）

**做了什么**：Inbox 条目详情（待处理和历史里的都有）和灵光编辑页各加“转为待办”。点一下就在当前项目记下一件待办，标题取原条目标题（灵光取屏幕上正在写的标题，没写标题取正文第一行），来源写明“你从 Inbox／灵光转为待办”，灵光的正文作为依据原文保留。结果就地显示“已转为待办，这里的状态不变”和“打开待办”；再点一次显示“这条已经转为待办”，不会重复。待办详情的来源可以点回原条目。Inbox 条目的处理状态、灵光本身都不变——“处理了 Inbox 条目不等于完成待办”，反过来也一样。待办的提醒不进 Inbox。灵光被丢掉后，待办照旧；点它的来源时灵光提示“这条灵光已丢掉或不存在”，不再打开一个空页面（Inbox 条目只改状态、不会被删，来源总能打开）。事先在来源上标“无法访问”需要 Host 的对象可用性核对，助理分支正在做同一套对象读取（读取器对不存在的对象报 not_found），届时接上，不另建一套。

**实现中发现并修掉的问题**：灵光页面代码里的换行转义写错，导致整个工作台脚本在浏览器里语法错误（Inbox、首页都打不开）；新增的单元测试会解析灵光页面脚本，防止再发生。Inbox 成功提示原本沿用错误提示的红色 10px 样式，改为正常文字并给“打开待办”加下划线；之后 Inbox 自己的操作失败时仍按错误样式显示。

**真实场景通过**：`tests/todo-from-inbox.e2e.test.ts`（真实 Host、Chrome，1440 与 390）：链接打开 Inbox 条目 → 转为待办 → 条目仍是待处理 → 再点不重复 → 打开待办看到来源 → 点来源回到 Inbox 条目；灵光里记下一条、未等保存就转为待办，正文进了依据、灵光还在；丢掉这条灵光后待办不变，点来源得到“已丢掉或不存在”；不横向滚动。截图在 `.impeccable/qa/review/specs/todo-plugin/verification/todo-from-*.png`。

**工程通过**：`tests/todo-from-inbox.test.ts` 3 项（按钮携带的数据与转义、灵光脚本可解析、来源种类与重复转换、删除后可重新转、未知来源种类被拒）；相关单元测试 88 项、相关浏览器测试 12 项（Inbox 3、灵光 3、Todo 4、Onboarding 2），另加本片的 2 项、typecheck、边界与工作区检查通过。

### T4 第二片：Onboarding 待办草稿与真实模型校准（2026-09-28）

**做了什么**：Onboarding 读完材料后，与工作概览并行调用 `todo.organize.extract`（来源标“开始使用时”，请求号绑定这轮整理，重试不重复整理）；草稿失败不影响概览。审阅页在概览下方列出草稿（类别、原句依据、截止与原文说法、负责人是否确定），默认勾选“要你处理／你的承诺／在等别人”，建议不勾；主按钮写明“采用，加入 N 项待办并开始”。采用时建项目、存资料与概览后，把勾选的草稿加入新项目的待办（重试安全），没勾的留在 Todo“待你确认”；有待办加入时直接打开待办页。

**用真实模型（MiniMax-M3，经 Prologue；隔离 Home，密钥进程内拷贝不打印）校准整理方法**，材料是自拟的邮件、会议纪要、聊天导出，无个人数据：
- 第 1 轮：模型输出偶尔带额外文字导致解析失败 → 解析改为按括号配对找含 candidates 的 JSON，失败再请模型重来一次。
- 第 2 轮：主要事项“发送新版方案”因为已有同名待办被模型省略，冲突提示丢失 → 提示要求“已有的也要列出并写关系”；“周四上午10点”被算成 9/29 → **日期不再采用模型的换算**：原文说法能用规则读懂的，按那句话写下时的时间确定性换算（聊天行的时间戳、邮件头、材料开头的日期，按写信人的当地钟点）；周日说的“下周X”、不同材料对同一说法读法不一、材料没有时间，都只给建议日期并写明原因。
- 第 3、4 轮：模型把与已有待办日期不同的事判为“同一件事” → 材料写明的截止日期与已有待办不同，按规则列为“更新”；你手动改过的列为“冲突”，默认保留你的。
- 最终：Onboarding 全流程约 9–18 秒；草稿日期正确（周五前→10/2、周四上午10点→10/1 10:00、今天下班前→9/28），有歧义的只给建议；采用后 5 项进入新项目待办，来源标“开始使用时”。另外把“不确定”里夹带的内部字段名改为要求用用户读得懂的话写。

**工程通过**：`tests/todo-organize.test.ts` 此时 9 项（新增：带说明文字的回复、写下时间的推断、确定性日期换算与歧义、日期差异按规则判为更新或冲突）；`tests/context-onboarding-todo.test.ts` 2 项（概览加草稿、采用勾选的进入新项目待办、重试不重复、其余留在待你确认；草稿失败不影响概览与采用）；既有 Onboarding 测试 26 项通过。

**真实浏览器走通**（`tests/context-onboarding-todo.e2e.test.ts`，1440 与 390，截图 `onboarding-drafts-*.png`）：预置一轮已整理完的记录（草稿是经替身模型生成的真实整理结果），审阅页显示三项草稿（两项预选）、原句、“采用，加入 2 项待办并开始”；取消一项后按钮变为“加入 1 项”，采用后跳到项目并打开待办，只加入了那一项，“待你确认”里留着其余的。发现并修正：手机宽度下底部固定的采用栏挡住草稿最后一行的勾选框（加了滚动留白）。

**尚未做 / 边界**：概览与草稿对“其他已有项目”的归属（D11）只能放到新项目、个人或暂未归类；Gmail 等来源的真实账号材料没有测（本轮只用自拟材料）。


### T4 第一片：整理结果与审阅（2026-09-28）

**实现决定（按推荐）**：整理结果是 Todo 保存的对象（D03）；助理或 Onboarding 调 `todo.organize.extract` 把读好的材料交给 Todo，由登记的整理方法（指令 `todo.organize.basic`，在“Prompt 与 Character”里可见可改）经 Host 文字模型整理，结果存为待确认的整理结果，**不直接新建或修改待办**；用户在 Todo 的“待你确认”里勾选、改写、采用或忽略——这一步是用户亲手的确认，不依赖 D08。整理结果有对象读取器 `todo.batch.subject.read`，助理可把它作为工作成果挂上，打开位置是 Todo 的“待你确认”。助理侧的 Skill 与待办整理师接通后，改由 Skill 提供同一方法。

**对模型输出的核对**：依据必须能在对应材料里找到（容忍空白和标点差异），找不到的候选略去并写进说明；截止日期只有在原文说法出现在材料里时才算截止，否则改为“建议日期”并注明是推测；负责人没写明时标“不确定”；与已有待办的关系只接受真实存在的待办；用户手动改过的字段只作冲突提示，采用时由用户勾选才改；已结束的待办再出现要求时提示“重新打开”。

**记忆**：按“材料＋事项”记下处理过和忽略过的；同一材料再次整理时，忽略过的和已经在待办里的不再列出，并在说明里写出数量。撤销采用后，由它加入的候选回到待确认。

**工程通过**：`tests/todo-organize.test.ts` 5 项（依据核对；规格 6.6 的例子：编造的依据被略去、“今天催小李”只作建议且不预选、依赖关系、参考信息单列；采用：来源与原句、等待状态、依赖关联、忽略记忆、再次整理不复现、整批撤销并回到待确认；已有待办：同一件事补来源、手动改过的日期默认保留、疑似完成只在选择时标完成；没有模型不可用、请求号不重复、项目范围与对象读取）。Prompt 登记门禁通过。

**真实浏览器走通**（`tests/todo.e2e.test.ts` 第 4 项，替身模型）：以助理身份发起整理后待办数为 0；Todo 出现“待你确认 3”，列出三项（两项预选、建议不选）、原句依据、不确定之处、“另有 1 条仅供参考”，主按钮“加入 2 项待办”；改写一项标题后采用，提示“已处理：加入 2 项待办”；“忽略没选的 1 项”后清空。
