# Goal 推进态势：内部完整实现

## 背景与目标

现有“关系图”以当前 Goal 为中心做放射状展开，同时绘制 `part_of` 与 `depends_on`。它能证明关系存在，却不能回答内部使用时最重要的三个问题：项目最近是否持续推进、哪个 Goal 正在形成瓶颈、现在优先行动什么。

本任务把该入口替换为“推进态势”，完成等级为 **4：内部完整**。视图只读取 Molis Work 的权威 Goal、关系、Claim、Run、Risk、Review、Evidence 与事件事实；不创建第二套进度、优先级或状态写入。

已确认的交互方向以 [`../goal-momentum-hifi-slice/spec.md`](../goal-momentum-hifi-slice/spec.md) 和其高保真原型为视觉与行为基线。

## 保留、替换、忽略

- 保留：列表/详情入口、当前 Goal 深链、项目范围、状态筛选、缩放、键盘操作、主题与真实事实源。
- 替换：旧“关系图”入口、以选中节点为中心的放射/轨道布局、`part_of` 连线与关系类型开关。
- 忽略：通用图编辑、跨项目图、团队容量/工时估算、对 Goal/关系/风险的写入、可配置图表系统。

## 用户场景

1. 内部成员打开“推进态势”，先看到近 7 天或近 30 天的启动、完成、新阻塞与停滞变化。
2. 在完整拓扑中从左到右读取“前置提供者 → 消费者”；完成 Goal 仍保留但弱化，`part_of` 只作为分组带和标题。
3. 选择任一节点时，一阶依赖边、行动队列与详情同步；可直接打开该 Goal 正文。
4. 在行动队列中看到可追溯的排序原因，不显示无法由事实证明的工作量或综合分数。
5. 在空数据、历史不足、关系异常、慢加载、窄屏、深色主题和密集数据下仍能理解当前状态并恢复操作。

## 派生模型与口径

### 输入

- Goal：`goal_id`、标题、状态、优先级、创建/更新时间、完成标准及通过情况。
- 结构：所有 active `depends_on` 与 `part_of`。
- 推进事实：Claim、Run、Evidence、Review、Risk、Decision reasons 与相关事件。

### 拓扑

- 存储方向为“消费者 `from_goal_id` depends_on 提供者 `to_goal_id`”；视觉方向必须反转为“提供者 → 消费者”。
- 对所有 active `depends_on` 做确定性的拓扑分层：无前置为 L0，消费者层级为其所有提供者最高层级 + 1。
- 多前置/多下游保留为 DAG，不强行变成单父树。
- 循环或悬空关系不伪造层级：保留可见节点，显示数据完整性提醒，并用确定性降级层级防止页面不可用。
- `part_of` 不画箭头，只决定分组带；无父级 Goal 进入“项目级独立事项”。
- 瓶颈影响值只统计该节点可触达的未完成下游 Goal 数；只有已阻塞或停滞且仍影响下游的节点使用瓶颈标记，不把“高影响但可开始”误报为问题，也不生成虚假健康分。

### 节奏

- 时间窗口支持近 7 天与近 30 天。
- 启动：窗口内首次 executor Run 开始。
- 完成：窗口内首次 `goal.satisfied` 事件。
- 新阻塞：窗口内首次出现 completion-blocking Risk 或明确 blocker 事件/原因。
- 停滞：未完成 Goal 在整个窗口内没有 Run、Evidence、Review、Contract 或关系更新活动。
- 缺少足够历史时明确显示“历史不足”，不把缺失数据算作停滞。

### 行动队列

只包含未完成、仍需直接推进的叶子 Goal；`waiting_children` 复合父 Goal 与已替换/失效 Goal 不进入行动队列。其余按以下稳定层级排序；每项显示来自真实事实的理由与影响范围：

1. 等待用户决定且正在阻塞下游。
2. 已执行/接近完成，完成后可解锁下游。
3. 无未满足前置且可解锁较多下游。
4. 其他可开始 Goal。
5. 长期无活动且影响较小的 Goal。

同层级依次按下游影响数、Goal priority、标题和 ID 排序，保证相同快照结果稳定。

## 模块与调用链

- `src/web/goal-momentum.ts`：纯派生模型；消费规范化后的 Goal/关系/事实，产出拓扑层级、分组、影响、节奏与行动队列。
- `src/web/render.ts`：把 `WebGoalView` 映射为派生模型输入，输出“推进态势”服务端 HTML；客户端完成依赖边布线、7/30 天切换、全部/未完成过滤、选择联动、缩放与键盘行为。
- `src/web/server.ts`：懒加载 endpoint 从 `/api/board/graph` 替换为 `/api/board/momentum`。
- `src/web/visual-foundation.ts`：新工作台、拓扑、分组带、队列、窄屏、深色主题和降级样式；删除轨道/放射定位。
- `tests/goal-momentum.test.ts`：验证方向、拓扑、多前置、循环降级、影响数、节奏口径、历史缺口和行动排序。
- `tests/web.test.ts` / `tests/visual-foundation.test.ts`：验证真实页面替换、懒加载、关键交互、无旧放射结构与响应式契约。
- `PRODUCT.md` / `DESIGN.md`：把推进态势、口径与视觉语义写回唯一产品和设计事实源。

## 体验与异常边界

- 空项目显示解释性空状态，不渲染空坐标系。
- endpoint 失败保留原位错误与重试；加载时使用 `aria-busy` 和可读状态。
- 历史不足、循环、悬空边分别显示数据诚实提示。
- 密集数据使用横纵双向滚动、固定层级标题、可缩放视图；不删除节点来换取整洁。
- “仅未完成”过滤只是显示范围，不能改变原拓扑派生或行动排序。
- 节点和队列项使用原生 button，可聚焦、可用 Enter/Space 激活；视口本身可键盘滚动。
- 深链保持 `/goals/:goal_id`，选择节点同步当前 Goal，但不破坏浏览器历史恢复。

## 性能与降级

- 派生模型目标为 `O(V + E + V·reachable)` 的小项目可解释实现；代表性 300 Goal / 900 关系 fixture 在本机单次派生应低于 100 ms。
- SVG 只画当前可见的 `depends_on`；选中态仅更新 DOM class 和路径，不重新请求数据。
- 超密集数据继续完整渲染，但默认使用更紧凑节点和滚动；不引入 canvas 或虚拟化作为本次范围。

## 验收标准

1. 页面只从 Molis Work 权威事实派生节奏、拓扑、瓶颈和队列；fixture 可逐项对账。
2. 所有 Goal 与 active `depends_on` 在完整模式可见，方向为提供者到消费者，`part_of` 仅作分组。
3. 7/30 天切换、全部/未完成、节点/队列选择、打开 Goal、缩放与重试可工作，并给出排序理由和数据缺口。
4. 旧“关系图”文字入口、放射轨道、环形坐标、`part_of` 图边和 `/api/board/graph` endpoint 均移除。
5. 列表、详情、项目深链、主题、键盘与窄屏回归通过。
6. 300 Goal / 900 关系代表性测量达标；循环、悬空、无历史、空项目与加载失败有明确降级。
7. `PRODUCT.md`、`DESIGN.md` 与实现一致，没有第二套状态或写入口。

## 假设与开放项

- 当前数据库事件历史可能晚于部分 Goal 创建，因此“停滞”只对有足够历史的 Goal 计算；其余作为缺口展示。
- 一项 Goal 若存在多个 active `part_of`，本次按稳定排序选择首个分组并报告完整性提醒，不静默合并层级。
- 本任务不改变 Molis Work 对 `depends_on`、Risk、Review 或完成判定的领域语义。
