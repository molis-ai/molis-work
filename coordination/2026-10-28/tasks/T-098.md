# T-098 提醒的「插件名：文字」超过 200 个单元时到点送不进收件箱：补用例确认，钉住现状

> **这条按代码推断在 main 上成立，起草时没有跑；本单就是确认。**
> - `reminders.add` 收提醒文字，上限 200 个单元：
>   - schema 在 `plugins/native/schedule/src/reminder-actions.ts:17`；
>   - 主人在 `plugins/native/schedule/src/reminders.ts:67` 检查。

## 1. 背景

- 登记：`reminders.add`（`plugins/native/schedule/src/reminder-actions.ts:17`），文字 `maxLength: 200`。主人 `reminders.ts:61-81` 的 `add`：
  - `:67`：`input.text.length > 200` 就拒，按单元数；
  - `:75`：登记闹钟，闹钟名称是 `input.text.slice(0, 120)`。与本单无关，不碰；
  - `:76-78`：存提醒记录，`pluginTitle` 是登记者的插件名，`text` 是整段文字。
- 送达：`deliverScheduleReminder`（`reminders.ts:97-111`）。一个事务里做完：
  - 读记录；
  - 核对安装；
  - `:106` 调 `ports.deliver`；
  - `:108` 删掉一次性提醒。
- `ports.deliver` 在 `runtime-wakeups.ts:37-38`，main 上的原样（4 个空格）：

  ```ts
      deliver: (reminder, dueAt) => runtime.notify({ key: reminder.id + ":" + dueAt, title: reminder.pluginTitle + "：" + reminder.text,
        summary: reminder.text, body: reminder.text, open_plugin_id: reminder.pluginId }),
  ```

- `runtime.notify` 是 `plugins/native/schedule/src/runtime-database.ts:40-41`，调平台的 `notifications.deliver`。平台实现在 `apps/local-host/src/plugin-notification-service.ts:35-43`：
  - `:39` 给 `title` 的上限是 200；
  - `:40` 按 `.length` 数，超了就在 `:41` 抛 `new ActionError("actions.input_invalid", "通知字段无效：" + field)`。
- 抛出去以后，没有人接：
  - `runtime-database.ts:42-51` 的 `write` 只有 `try … finally`，没有 `catch`，这次写入整个回滚，提醒记录留着；
  - 闹钟一侧（`horizontal/scheduler/src/index.ts:415-418`）把这次唤醒记成 `failed`，`detail` 是错误的消息，截到 500；
  - `:436` 按 `recurrence_kind` 写 `enabled`：一次性的写 0，闹钟停了；每日、每周的仍开着，下次到点再失败一次。本单只量一次性的。
- 收件箱一侧放得下 200 个单元的标题：Feed 的接收动作 `feed.notifications.receive` 的 schema 里 `title: text(200)`（`plugins/native/feed/src/notification-actions.ts:22`）。所以 195 个字的那条整条路都走得通。
- 「投递失败并记下原因，提醒保留」是 README 写明的不变量（`plugins/native/schedule/README.md:64`），本身不是缺陷。缺陷在于：
  - 登记时收下的文字，到点必定送不出去；
  - 登记的人当时不知道；
  - 插件名越长，能送出去的提醒越短。
- 现有用例没有量到：`tests/agent-built-plugins-reminders.test.ts` 里的提醒文字都很短（`:16-17`、`:40`、`:53`、`:55`、`:72`、`:78`）。
- 夹具（`tests/fixtures/schedule-runtime.ts`）：
  - `:20` 插件名是「定时笔记」；
  - `:40` 的 `tick(at)` 让闹钟在 `at` 之后一秒走一次，返回 `{ invoked, failed, skipped }`；
  - `:37` 的 `inbox()` 只取 schedule 发出的通知在 Feed 里的条目。
  - Feed 自己也在这只闹钟上有一个定时任务，所以 `invoked` 不只数提醒。用例只断言 `failed`，`:61` 也是这样写的。

## 2. 目标

1. 在 main 上，同一时刻到点的两条提醒（`RAC-1670`）：
   - 195 个「提」的那条：送进收件箱，标题是「定时笔记：」加 195 个「提」，提醒记录已删；
   - 196 个「提」的那条送不出去：
     - 这次走闹钟只失败这一条；
     - 提醒记录留着，文字完整；
     - 它的闹钟停了，最后一次唤醒是 `failed`，原因里有「通知字段无效：title」；
     - 通知队列里没有给它留的行；
     - 再走一次闹钟也送不出去。
2. 用例在 main 上全绿，就是确认了 `MISC.md:57` 那条疑似缺陷。

```ts

test("RAC-1670 a reminder whose 「plugin name：text」 passes 200 UTF-16 units is taken but never delivered: the wakeup fails, its one-shot job stops, the reminder stays (known defect, pinned until its fix is chosen)", { timeout: 60_000 }, async t => {
  // reminders.add takes up to 200 UTF-16 units of text (plugins/native/schedule/src/reminders.ts:67), delivery titles the notification
  // 「plugin name：text」 (runtime-wakeups.ts:37), and the notification service refuses a title over 200 units
  // (apps/local-host/src/plugin-notification-service.ts:39-41). 「定时笔记：」 is 5 units, so 195 fits and 196 does not.
  // The fix (cut the title, or tighten the text) turns the second reminder's assertions around.
  const f = await scheduleRuntimeFixture(t), store = await f.store(), clock = scheduleServiceFor(store.db), at = next();
  const fits = await f.sdk.invoke(reminderActions.add, { at, text: "提".repeat(195) });
  const over = await f.sdk.invoke(reminderActions.add, { at, text: "提".repeat(196) });
  const job = getScheduleReminder(store.db, over.reminderId)!.jobId;
  assert.equal((await f.tick(at)).failed, 1, "only the reminder whose title would be 201 units fails");
  assert.deepEqual((await f.inbox()).map(item => item.title), ["定时笔记：" + "提".repeat(195)], "a 200-unit title reaches the Inbox");
  assert.equal(getScheduleReminder(store.db, fits.reminderId), null, "the delivered one-shot reminder is consumed");
  assert.equal(getScheduleReminder(store.db, over.reminderId)?.text, "提".repeat(196), "the refused reminder stays");
  assert.deepEqual([clock.get(job)?.enabled, clock.get(job)?.last_wakeup?.status], [false, "failed"], "its one-shot job has fired and stopped");
  assert.match(clock.get(job)?.last_wakeup?.detail ?? "", /通知字段无效：title/, "the notification service refused the title");
  assert.equal(new PluginNotificationQueue(store.db).pending(f.project.project_id).length, 0, "nothing is left queued for it");
  await f.tick(new Date(Date.parse(at) + 60_000).toISOString());
  assert.equal((await f.inbox()).length, 1, "a later tick does not deliver it either");
});
```

2. 几处为什么这样写，别改：
   - **用「提」。** 一个字一个单元，按单元数和按字数数一样。证明缺陷与 emoji 无关，只在于「插件名：」占了位置。
   - **195 和 196 放在一起。** 195 证明 200 个单元的标题整条路都收得下（通知服务、Feed 都是 200）；196 证明多一个单元就送不出去。两条同一时刻到点，一次 `tick` 走完。
   - **只断言 `failed`，不断言 `invoked`。** Feed 自己的定时任务也在这只闹钟上（`:49-50` 的注释），`invoked` 会多数。
   - **闹钟从 `clock.get(job)` 读。** 它返回的记录由 `scheduleRecord`（`horizontal/scheduler/src/index.ts:349-365`）拼出：`enabled` 是布尔值，`last_wakeup` 带 `status` 和 `detail`。`:58` 也用同一个 `clock.get`。
   - **原因用 `assert.match`。** 闹钟一侧把错误消息原样记下（`horizontal/scheduler/src/index.ts:418`），本单只认里面有「通知字段无效：title」。
   - **队列断言是 0。** `pending` 只数还没送达的行（`packages/plugin-runtime/src/notification-queue.ts:72-74`，`delivered_at IS NULL`）：195 的那条送进 Feed 后标为已送达；196 的那条在入队之前就被字段检查拒了（`apps/local-host/src/plugin-notification-service.ts:39-41` 在 `:48` 的 `enqueue` 之前），根本没写进去。
   - **最后再走一次闹钟。** 一次性闹钟已停，提醒不会再送；收件箱仍只有 195 的那一条。
   - **测试名和注释写明 known defect。** 修的那一单要把后半段翻过来，读的人一眼知道这不是想要的行为。
   - 只用文件里已有的 `assert`、`test`、`scheduleServiceFor`、`getScheduleReminder`、`reminderActions`、`PluginNotificationQueue`、`scheduleRuntimeFixture`、`next`（`:1-12`），不加 `import`。
3. 代码里不要出现 `legacy`、`compat`、`backfill`，不加空 `catch`、`as unknown as`、`any`、`console`（这些按文件计数，只许减少）。
