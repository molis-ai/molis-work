## 1. 背景

- Workflows 在许多地方把一段文字截到前 N 个字：流程名、运行名、交接的标题、判断规则读到的文字、模板、步骤名……截点要落在字与字之间，不能落在一个两单元的字（如 😀，U+1F600）中间，所以 T-079、T-189 起，这个包里按字截的写法是 `[...x].slice(0, n).join("")`：把字符串展开成「一个字一个元素」的数组，取前 n 个，再合回去。T-189 已把十一处改成这样，T-206 又加两处。
- 这个写法有一个毛病：展开的是**整段**文字。数组的每个元素是一个独立的字符串，一个字要占二三十个字节（独立脚本量过，见下），文字有多长数组就有多长，再取前 n 个只是把绝大部分扔掉。独立脚本（不在仓库里，在一份空进程里）量到的：

  | 文字（汉字 `尾`，每个一个单元） | 改前：`[...x].slice(0, 8000).join("")` | 改后：`[...x.slice(0, 16000)].slice(0, 8000).join("")` |
  | --- | --- | --- |
  | 100 万个 | 约 20 毫秒，进程多占约 43 MB | 不到 1 毫秒，多占约 3 MB |
  | 1000 万个 | 约 300 毫秒，进程多占约 385 MB | 约 2 毫秒，多占约 20 MB |
  | 5000 万个 | 约 3 秒，进程多占约 1.6 GB | 约 6 毫秒，多占约 97 MB（主要是那段文字本身，两字节一个字；不是数组） |

  同一台机器上各跑一次的数，会随机器和负载变；用例不量它们（第 1 节最后一条、第 8 节第 4 条）。

  真实的正文有多大，起草时没有量（没有读真实 Home）；二审说的「极大的 CJK 正文」是估算，上表是机器上的实测。结论是：输入大到几百万字，这个写法才开始吃力；在那之前它不出错，只是白占。本单把它改成与输入长度无关。
- 先截 2N 个单元再展开，**结果相同**，推理如下（第 6 节用用例钉住，起草时另用独立脚本对 52,400 个随机和边界字符串比过）：
  1. 一个字占一个或两个单元（BMP 字一个，😀 这类两个；孤立的半个字也算一个字、占一个单元，`[...x]` 就是这样数的）。所以前 `n` 个字至多占 `2n` 个单元，它们全在前 `2n` 个单元里；
  2. `x.slice(0, 2n)` 的末尾可能把一个两单元的字从中间切开，但那个字在第 `n` 个字**之后**（前 `n` 个字已经整个在里面了），随后的 `.slice(0, n)` 把它丢掉，不会进结果；
  3. 文字不足 `n` 个字时，它不超过 `2n - 2` 个单元，`x.slice(0, 2n)` 就是整段，与改前完全一样；
  4. 「是否超过 `limit` 个字」同理：超过 `2 * limit` 个单元的文字，字数一定超过 `limit`（一个字至多两个单元），不用展开就能答；不超过的，展开至多 `2 * limit` 个元素。

## 2. 目标

1. 十一处截取（含一处只数不截）给出的结果与改前一字不差：任何输入，含两单元的字、孤立的半个字、上限前后、空白；
2. 每一处所花的「步数」（引擎从字符串里取出的字数）至多是上限的两倍加几步无关的，不随文字变长：40 万字的文字截到 8000 字、4000 字、400 字、200 字、120 字，都在上限的 4 倍以内；判断规则读 100 万字的正文约 16,000 步，100 万字的运行名约 240 步；
3. 固定值的上限不变：8000 个字放行（8000 个 😀 是 16000 个单元，放行；16000 个汉字拒绝），多一个字拒绝；超过 16000 个单元的固定值不展开就拒绝；

```ts
/**
 * Cutting a text to its first characters without spreading all of it: the pieces of text Workflows keeps (titles, templates, names,
 * the text a judgment reads) come from other plugins, a model or a request, and the text may be a whole document.
 * A character is one or two UTF-16 units (an emoji is two), so `limit` characters never take more than `2 * limit` units.
 * Only those units are spread into characters, and the result is the same as spreading everything: the work and the memory
 * are in proportion to the limit, not to the text.
 */

/** The first `limit` characters of `text`, whole: a character of two units is never cut in half. */
export function firstCharacters(text: string, limit: number): string {
  return [...text.slice(0, 2 * limit)].slice(0, limit).join("");
}

/** Whether `text` is longer than `limit` characters. More than `2 * limit` units is already more than `limit` characters (a character is at most two), so such a text is not spread to be counted. */
export function exceedsCharacters(text: string, limit: number): boolean {
  return text.length > 2 * limit || [...text].length > limit;
}
```

说明：
- 两个函数都是纯函数，不依赖任何导入，所以浏览器脚本和别的包不会因它多打进东西；
- `firstCharacters`：`text.slice(0, 2 * limit)` 先把长文字砍到至多 `2 * limit` 个单元，`[...]` 再把这一小段展开成字，`slice(0, limit)` 取前 `limit` 个，`join("")` 合回去。`limit` 为 0 时得到空串，与改前相同；
- `exceedsCharacters`：`text.length > 2 * limit` 为真就不再展开（超过 `2 * limit` 个单元，字数一定超过 `limit`）；为假时 `text` 至多 `2 * limit` 个单元，展开至多 `2 * limit` 个元素。
