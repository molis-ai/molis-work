# PG-049：本机目录读取的同意流程（设计稿）

状态：设计稿，待用户拍板，不含代码（2026-10-25）。负责人：ac-kernel。按 `privileges.md` §5 第 6 条，定稿前由统筹弹窗问用户；第 5 节列出要定的几点，每点带推荐。

## 1. 要解决什么

裁定 11（`privileges.md` §4 e）：插件读用户指定的本机目录，要经过一项带同意流程的平台服务，任何插件都走同一个入口，不能有后台静默读。

main 上已经有这项服务的底子（PRR-03，用户 2026-10-20 选 B，`specs/pr-review-remediation/spec.md`）：

- **入口**：`POST /api/host/directory-grants`（`apps/local-host/src/plugin-directory-http.ts`）。页面只能说是哪个插件在请求，目录由系统选择器选；插件页面不能替别的插件或项目请求。
- **授权**：`apps/local-host/src/plugin-directory-service.ts` 的 `directoryForHome`。授权绑定在这一次安装（安装 id 与世代）、这个人、这个项目上，30 分钟后过期，只存在内存里，一个 Home 最多 32 个。插件停用、卸载、换代或项目删除都会撤掉。
- **读取**：插件只拿到 `PluginDirectoryService.read`（合同 `platform/plugin-directory`），按 `grant_id` 加相对路径读。宿主每次都核对安装的 `directory:read`、调用身份和授权是否仍有效；逐段 realpath/lstat，拒绝符号链接，只读，目录、文本、字节各有上限（`plugin-directory-read.ts`）。
- **Cognia**：已经不用 `node:fs`，只经这项服务读（`plugins/native/cognia/src/directory.ts`）。

所以 PG-049 剩下的不是“有没有服务”，而是同意流程本身。现在有四个缺口：

1. **只有 30 分钟。** 授权在内存里，重启就没了。用户想让插件以后再读同一个目录（例如 Cognia 重新扫描、增量同步），每次都要重新选；而这时也没有“这个目录以后都行”可以选。
2. **没有“只在你在场时读”。** 30 分钟内，这个安装以同一个人、同一个项目的身份发起的任何调用都能读，包括 Agent 的自主轮次、定时任务和工作流步骤。宿主没有区分这次调用是不是人当场发起的，这就是裁定说的后台静默读的空子。
3. **看不到，撤不了。** 没有地方列出哪些插件被授权读了哪些目录、上次什么时候读的。只有停用插件或删除项目才撤得掉。
4. **安全不变量表里没有登记。** PRR-03 的拒绝测试在 `tests/security-invariants-directory.test.ts`，但 `docs/system/SECURITY-INVARIANTS.md` 里没有对应的行。

## 2. 设计

在现有服务上补，不另起第二套。

### 2.1 两种授权

- **本次授权**（现状）：选目录后 30 分钟、只读，在内存里，绑定这次安装、这个人、这个项目。
- **记住的授权**（新增）：选择器确认之后，人在同一个宿主对话框里勾选「以后也允许『插件名』读这个目录」。
  - 写进 Home 库，宿主自己的表，表的主人是 `apps/local-host`。
  - 一行记：插件 id、安装 id 与世代、项目（或 Home 级）、人、目录的 realpath、设备号与 inode、授权时间、上次读取时间、读取次数。
  - 每次读都重新核 realpath 与设备号/inode。目录被换掉、被移走或变成符号链接，就返回 `changed`，这条授权作废，要人重新选。
  - 插件只拿到不透明的 `grant_id`，记住的授权也一样，绝对路径永远不给插件。

### 2.2 只在人发起的调用里读（推荐，见第 5 节第 2 点）

`read` 除了核对授权，还要核对调用来源（宿主从可信的调用上下文取，不从输入读）：

- **放行**：人在页面上的操作，以及人在确认卡上点了确认的那一次动作。
- **拒绝**，返回 `denied` 并说明「需要你在场时操作」：Agent 自主发起的、定时任务、工作流自动推进的步骤、MCP 客户端。
- 本次授权与记住的授权都守这条规则。

### 2.3 看得见、撤得掉

- 设置里加「本机目录」一页（平台设置，不是哪个插件的页面）。按插件列出每条授权：目录、项目、本次还是记住、上次读取、读取次数。每条可以撤回，也可以「撤回这个插件的全部」。
- 撤回立即生效：进行中的读取在下一次核对时失败，不再写出结果（同现有的 `check`）。
- 插件卸载、项目删除照旧自动撤回。插件升级换代时，记住的授权要人再确认一次，见第 5 节第 3 点。
- 每次读取只记谁、哪条授权、什么时候、成败，不记文件名和内容。这条记录供设置页显示，不进动作调用日志的内容字段。

### 2.4 任何插件同一个入口

- 入口仍是一个宿主路由加一个系统选择器，再加一个宿主自己的确认对话框，插件不能自绘。
- Manifest 声明 `directory:read` 权限，安装确认里照常列出。
- 官方、个人与第三方插件待遇一样（10-18）；签名只决定安装信任，不决定能不能读目录。
- 插件 SDK 不新增 API：`PluginDirectoryService.read` 不变；`grant_id` 由页面经宿主路由拿到后交给插件动作，和现在一样。

### 2.5 不在本稿

- 写入本机目录：另一项服务，另一次决定。
- 监听目录变化后自动重扫：要后台读，与第 2.2 节相反，若要做另外再定。
- 项目工作区目录：已由 S-41 一类的规则覆盖，不并进来。

## 3. 安全边界

实现时要占一个 S 号，并且先问统筹。同时补表行与拒绝测试，至少断言这几种拒绝：

- 非人发起的调用读取被拒。
- 别的安装、别的人、别的项目拿同一个 `grant_id` 被拒。
- 撤回后被拒，进行中的读取不写出结果。
- 目录被换成另一个 inode 或符号链接后返回 `changed`。
- 页面请求别的插件的目录被拒（现有）。

PRR-03 的现有拒绝测试顺带登记进同一行。
