# Coding 插件：UI 与交互设计

状态：**设计稿**。本文设计用户能做什么、界面怎么组织、按钮何时出现，**不是开发合同，也不代表任何功能已实现**。
实现前需要据此另立实施 spec。平台侧依据 [`specs/plugin-platform-v2/spec.md`](../plugin-platform-v2/spec.md)，
视觉依据 [`DESIGN.md`](../../DESIGN.md)。

参考来源：FlyLeaf 仓库（本机 `~/code/flyleaf`）的 `specs/coding-app/design-brief.md` 与已跑通的
`plugins/coding-agent`；执行语义参考 Prologue（本机 `~/code/prologue`）。两处都在本仓之外，链接不会解析，
查阅需切到对应仓库。两者都只借鉴**工作方式**，不照搬布局，
也不因为它们有某项能力就宣称 Molis Work 已具备。

## 1. 边界

- Coding 是一个 **project-scoped 的 app 插件**，走 Plugin Platform v2：有自己的 Manifest、端口、事件、视图、命令和路由。
- 它**组合**已有能力，不吞并别的插件：Goal 事实归 Goals，终端归 Sessions，Artifact 存储归 Artifacts，
  材料归 Shelf，审批归宿主。Coding 只拥有「编码任务意图、会话元数据、呈现偏好、未提交草稿」。
- 它是**第一个完整跑在 Plugin Runtime 里的 app 插件**：启动、隔离、崩溃重启、端口投递、事件订阅都走真实运行时。
  这也是存量六个内置插件后续迁移的样板。
- 不引入 React，不引入第二套图标族，不新建 Coding 私有设计规范。

## 2. 和 FlyLeaf 不同的地方

FlyLeaf 的 Coding App 是在一个纯编码工作台里组织项目/会话。Molis Work 有 FlyLeaf 没有的资产，
设计必须用上它们，否则就是把 FlyLeaf 原样搬过来：

| Molis Work 已有 | Coding 怎么用 | 为什么重要 |
| --- | --- | --- |
| **Goal 与事件工作流** | 一条编码会话可以挂在一个 Goal 下；执行产生的进展、交付、阻塞按既有 Goal 事件协议回写 | 编码不再是孤立的对话，而是目标推进的一部分。这是本产品的核心 |
| **Artifact 真持久** | ChangeSet 与 Report 直接是项目库里的 Artifact 版本 | 成果可被 Artifacts 插件浏览、被其他插件按类型消费、重启后仍是同一版本 |
| **工作台标签与分屏** | 会话与变更并排用宿主的分屏树，Coding 不自建工作面管理 | 少一套布局代码，且与全产品的标签/恢复行为一致 |
| **Shelf 材料** | Shelf 里的文件/文本可作为固定材料喂给任务 | 已有的收集链路直接接上 |
| **Sessions 终端** | 真实终端仍归 Sessions；Coding 只显示命令回执 | 不造第二个终端 |

**不做**：不把 Goal 变成会话的必填项；没有 Goal 也能开一条编码会话。

## 3. 界面里只保留四个概念

- **工作区**：已授权的项目目录。宿主事实，Coding 只读取和显示。
- **会话**：可找回、可继续的一段任务讨论，承载多轮执行。列表里用用户的任务标题表达。
- **本轮执行**：一次提交之后的实际执行与结果。内部 Run id 是次要事实，不作为主文案。
- **成果**：变更集、报告、命令输出、文件。都有来源和版本。

「任务」只作为会话的用户语言，不另造一套与 Session/Run 竞争的状态机。
会话分支与 Git 分支在操作名和影响说明上必须分开。

## 4. 它在壳里的位置

Molis Work 的桌面壳是：32px 标题栏 / 48px 图标栏 + 240px 目录栏 + 一个工作台（32px 标签条 + 分屏树）。
Coding 占用其中四处，全部由 Manifest 声明，宿主不为它写分支：

- **图标栏**：一个 Coding 入口，`code` 图标（Lucide Braces，已在图标库内）。
- **目录栏**：顶部用标签页在 Coding 自己的五个导航面之间切换——会话、TaskBoard、目标、产物、文件。
- **工作台中部**：对话与报告正文。标签条上是**打开的会话**，像编辑器的文件页。
- **工作台右栏**：结果预览与结果动作，同时是工具面——结果 / 浏览器 / 终端 / Canvas，可上下分屏。

三段的分工是固定的：**左边找东西，中间谈，右边看结果并对结果动手**。
变更、报告、TaskBoard 不再各占一个工作台标签——它们要么是左栏的一个导航面，要么是右栏的一页。

### 目录栏

```
┌ 会话 │ 任务 │ 目标 │ 产物 │ 文件 ┐   ← 34px 标签页行：五个导航面，图标 + 选中态
├────────────────────────────────────┤
│  会话                      ＋  🔍  │   ← 28px 标题行：当前面的名字 + 动作
├────────────────────────────────────┤
│  全部 │ 进行中 │ 需要我处理        │   ← 段控（segmented），不是三个按钮
├────────────────────────────────────┤
│ ▾ 让首次使用不再卡在连接            │   ← Goal 分组（有 Goal 的会话）
│     修好 runtime 连接提示      2h   │   ← 36px 两行行：标题 + 状态/时间
│     补充失败时的下一步文案     昨天 │
│ ▾ 未关联目标                        │
│     看看 shelf 的抽取为什么慢  3天  │
└────────────────────────────────────┘
```

- 分组按 **Goal**，不是按目录——因为一个项目就是一个工作区，按目录分组没有信息量。没有 Goal 的会话进「未关联目标」组。
- 行高 36px（两行目录行的现行密度），标题 13px/400，时间与状态 12px/`--muted`。
- 状态用共享 `mw-status` 标记：进行中用不定弧（现行「运行中 Goal」的处理），等待回答用 attention clay，
  失败用 red，已完成不加标记。
- 「需要我处理」是**筛选**，不是第二个收件箱账本——它筛的是「有待回答的问题」「有待批准的操作」「失败待处理」。
- 会话行的更多菜单：重命名、关联/取消关联 Goal、归档、删除。归档只整理列表，不停止执行。
- 搜索范围始终显示（标题 / 标题+正文），结果显示命中片段与所属 Goal。

### 工作台：会话标签

一个会话 = 一个标签，标签标题是任务标题（12px，超长有 tooltip）。

```
┌ 32px 工具条 ────────────────────────────────────────────────┐
│ 修好 runtime 连接提示   · 让首次使用不再卡在连接 · ~/code/gb │
│                                        [停止]  [查看变更 3] │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   对话流（内部滚动，76ch 阅读宽度）                          │
│                                                             │
│   ▸ 读取 12 个文件、搜索 3 处            ← 工具活动折叠摘要  │
│   助手回答（Markdown，代码可复制）                           │
│   ┌ 需要你决定 ───────────────────┐    ← 结构化问题就地出现 │
│   │ 连接失败时应该…              │                          │
│   │ ○ 重试三次  ○ 立刻报错       │                          │
│   └──────────────────[提交回答]──┘                          │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│ ＋ @ /        [讨论 ▾]  [claude-opus ▾]            [执行 →] │  ← 输入区
└─────────────────────────────────────────────────────────────┘
```

- **工具条**：会话标题、所属 Goal（有才显示，可点进 Goal）、工作区目录尾段。右侧动作**按状态出现**，不常驻。
- **对话流**：正文按共享 Markdown 规则排版，76ch 上限（与 Feed 阅读一致）。流式更新时已有节点稳定；
  用户上翻后停止自动贴底，出现「回到最新」。
- **工具活动**默认折叠成一行摘要（「读取 12 个文件、搜索 3 处」），展开才看输入范围、输出与错误。
  原始协议、内部推理、日志不作为主阅读内容。
- **输入区**：`＋` 加文件/图片/Shelf 材料，`@` 引用对象，`/` 选方法。意图选择（讨论 / 规划 / 执行 / 评审）
  用段控，**不暴露 Reader/Builder/Coordinator 这些内部角色名**——角色由意图映射。
  模型入口显示当前模型，改动明确作用于下一轮。

### 工作台右栏：结果与工具面

右栏常驻，有四页，页签在顶部，右上角可上下分屏：

- **结果**：本轮成果的预览与对成果的动作。变更集在这里看：上面是文件列表，下面是差异，
  行上可留意见，若干条一起「发回任务」。底部动作条是「发回意见 / 应用」，
  **应用在只读档下是真不可用**，不是藏起来。
- **浏览器**：把跑起来的东西打开看。地址栏、后退、刷新，用来复现和验收。
- **终端**：本轮执行自己跑过的命令**回执**，只读。见下面的边界。
- **Canvas**：让本轮执行把结论画出来（流程图、状态机、分流图）。画完可以「让它重画」或「存为产物」，
  存下来就是一个 Artifact，有来源和版本。

两条不能含糊的规则，和原来一样：

- 标题栏标明当前范围：**本轮固定变更** 还是 **工作区当前改动**——这两者是不同事实，不能混。
- 反馈不是批准；AI 说「检查完成」不是交付。

**终端的边界**：这一页只读**本轮执行自己跑过的命令回执**，来源是 Agent Host 的 `AgentCommandOutput`，
**不在这里重造一个可输入的 PTY**。用户要真终端就去 Sessions——那是用户自己的终端，和这页不是一回事。
放宽这条就等于在 Coding 里开了一条绕过宿主审批的副作用通道。

命令执行今天在两个 Runtime 上都申报为不支持，所以这一页在 C5 接通审批之前**显示为真实不可用**。

## 5. 按动作路径显示能力

默认视图只承担三件事：**看懂当前任务、继续输入、进入真实结果**。其余能力挂在它作用的对象上。

| 用户意图 | 入口 | 打开后 | 关闭后 |
| --- | --- | --- | --- |
| 继续任务 | 对话与输入区 | 已有消息、当前必要状态 | 留在同一任务 |
| 加文件/材料 | 输入区 `＋`；`@` 是引用快捷方式 | 作用域明确的选择器（项目文件 / Shelf 材料） | 引用进草稿，不自动发送 |
| 用方法 | 输入区 `/` | 可用方法搜索与说明 | 插入选择，保留输入 |
| 换模型 | 输入区旁的当前模型入口 | 真实可用模型与运行参数 | 明确作用于下一轮，保留草稿 |
| 关联 Goal | 工具条的 Goal 位；无 Goal 时是「关联目标」 | Goal 选择器 | 回到原会话 |
| 看执行细节 | 运行中就地状态；完成后「查看执行记录」 | 本轮工具与命令详情 | 收回摘要 |
| 审查变更 | 成果区单一「查看变更」 | 变更标签 | 反馈发回原任务 |
| 看报告 | 成果上的「打开」 | 报告标签（同时是一个 Artifact） | 返回原任务 |
| 整理会话 | 会话行 / 标题的更多菜单 | 重命名、关联 Goal、归档 | 保留导航语境 |
| 配置方法/MCP | 全局设置里的 Coding 页；故障旁的修复动作 | 有返回路径的配置页 | 回到原会话与草稿 |

阻塞、审批、错误、失败、停止**必须出现在相关任务里**，不能为了简洁藏进设置。
选择器支持空结果、取消和键盘返回；读取失败就地重试，回到原草稿而不是新任务。

## 6. 审批：宿主拥有，插件不碰

Agent 要改文件、跑命令、调 MCP 工具、回退检查点，都必须经过**宿主的统一审查面**。

- 会话里出现的是一张摘要卡 + 「查看并处理」，点开进宿主审查面。
- Coding **不**保存批准状态，**不**提供快捷放行，**不**把「模型说完成了」当成已批准。
- 拒绝后不得换个入口重做。
- 未批准时零写入——这条是硬边界，不是配置项。

结构化提问（AskUser）显示在会话当前推进位置：单选、多选、自由输入都支持，并说明「这个选择会影响什么」。
不代填答案；离开不等于取消；失败保留已填内容；后台问题在目录栏标「需要我处理」，**不抢焦点**。

## 7. 四条动线

**继续昨天的任务**
图标栏 → Coding → 目录里选「修好 runtime 连接提示」→ 恢复阅读位置和草稿 → 看上次验证失败 →
补充说明 → 执行 → 检查本轮成果。目录授权失效时仍能读历史，就地重新授权后继续。

**两条任务并行**
任务 A 执行中 → 新建任务 B → B 规划时 A 提出问题 → 目录栏 A 那行出现「需要我处理」→
用户自己决定何时回 A → 回答后继续 → 回到 B，草稿和阅读位置不变。后台请求不抢前台焦点。

**检查、修改、交付**
会话产出修改提案 → 开变更标签，拖到右边与会话并排 → 在某处留反馈 → 发回当前任务 →
检查更新后的提案 → 经宿主审查面统一批准 → 真实落盘拿回执 → 批准跑一条检查命令 →
结果回到同一轮 → Agent 给结论 → 保存固定 Report。

**编码推进一个 Goal**
从 Goals 里某个 Goal 的「用 Coding 处理」→ 新建会话且自动关联该 Goal →
完成后按 Goal 事件协议回写一条进展或交付事件 → 回到 Goal 能看到这条编码记录及其成果引用。
（这条是 Molis Work 独有的动线，FlyLeaf 没有对应物。）

## 8. 按钮出现时机

| 场景 | 保持可见的主要动作 | 次要动作与连续性 |
| --- | --- | --- |
| 首次进入 / 无会话 | 新建会话 | 历史可浏览；说明执行需要工作区授权 |
| 草稿就绪 | 按意图命名的提交（讨论 / 规划 / 执行 / 评审） | 上下文与配置靠近输入；空输入不给误操作 |
| 正在执行 | 停止、补充要求 | 草稿可继续编辑；子任务在存在时出现 |
| 等待回答 | 在问题上提交回答 | 草稿保留；离开不取消；已答收起表单 |
| 等待批准 | 查看并处理 | 前往宿主审查面，完成后自然返回 |
| 执行完成 | 查看变更 / 打开报告 / 继续输入 | **有变更才出现差异动作**；不同时常驻停止/恢复/重试 |
| 失败 | 对当前失败有效的重试或重新授权 | 保留已完成部分与输入；无确定结果时先核实 |
| 已停止 | 继续讨论或发起下一轮 | 不把已停止当作未产生过修改 |
| 浏览历史 | 继续该会话、更多菜单 | 历史的批准与回答按钮不可再操作 |

状态变化后动作消失时，焦点回到同一任务的稳定位置，不跳页首。
菜单 Escape 关闭，弹层恢复触发位置，输入法回车不误提交。

## 9. 窄窗口

- ≤760px：只显示聚焦的那一格，用窗口选择器切换，分屏关系保留。输入区字号 16px。
- ≤600px：图标栏与目录栏合并为抽屉；选择后关闭。标题栏标签与搜索保留。
- 缩窄不丢对象、不改任务、不重置滚动；恢复宽窗回到原布局。

## 10. 视觉决定

全部沿用现行设计系统，本节只记 Coding 需要定的几处：

- **插件色**：建议 **cyan**。已占用：blue(Goals)、brown(Feed)、purple(Sessions)、mint(Inbox)、
  slate(Shelf)、pink(Artifacts)、steel(Settings)、gray(Home)。剩余里 green/red/orange 是状态色，
  indigo 与 `--focus` 撞，只剩 cyan 与 yellow；yellow 作为编码工具的身份色不合适。
  **风险**：`--tone-hold` 也用 cyan。二者出现在不同表面（插件色在图标栏/目录字形，状态色在 `mw-status` 标记），
  但这需要你确认。见 §12。
- 目录标题 13px/400，说明 12px；标签 12px；对话正文 13px/1.6，76ch。
- 状态一律 `mw-status`（Lucide 图标 + 家族色文字），不加边框，不做胶囊。
- 运行中用现行的不定弧，且**只在工具条和会话头**出现；目录列表保持静态标记，不把列表变成一排转圈。
- 控件 28px、10px 圆角；变更标签内的差异用等宽字体，属于「技术证据」范畴。
- 深浅主题都完整；减弱动效偏好下去掉位移。

## 11. 它怎么落在 v2 平台上

Manifest 草案（**设计意图，不是最终声明**）：

```
plugin_id   io.molis.work.coding      kind app      schema_version 2
permissions artifact:write / artifact:read / storage:private / ui:register
capabilities.consumes
            agent.runtimes.v1 · agent.roles.v1 · agent.session.create.v1 · agent.session.read.v1
            agent.run.start.v1 · agent.run.read.v1 · agent.run.control.v1 · agent.reviews.list.v1
            projects.workspace.read.v1 · goals.event.append.v1
requires    agent.run.start.v1（必需）· projects.workspace.read.v1（必需）
            goals.event.append.v1（可选，缺失则不写回 Goal）
ports
  inputs    goal      goals.goal@1            optional   ← 关联的目标
            materials shelf.material@1        optional   ← Shelf 材料
  outputs   change-set  coding.change-set@1
            report      coding.report@1
events
  publishes io.molis.work.coding.file-changed@1      ← 真实落盘后，Sessions/Shelf 据此刷新
            io.molis.work.coding.session-updated@1
  subscribes（首版为空，不订阅别人）
views       directory  navigator  Coding   icon code
            session    stage      Coding   accepts_objects
            changes    stage      变更
            settings   settings   Coding
commands    open-session / open-changes / open-report
routes      GET  /sessions · POST /sessions · POST /sessions/:id/submit
            POST /sessions/:id/stop · GET /sessions/:id/runs/:run
agent       roles  reader / planner / builder / reviewer（对应四种用户意图）
            prompts + skills + mcp + subagents + compaction
            （工作区目录不在这里：它由宿主授权，见下）
```

两处在平台侧已经有答案了：

1. **Coding 不持有 Agent Host，只通过 Capability 调用它。** 这八个 Capability 已经定义并可注册
   （`agentHostCapabilities`）。**批准动作刻意不是 Capability**——那是用户在宿主审查面里的动作，
   开成插件可调的能力就等于让插件批准自己的副作用。
2. **工作区目录不是端口，也不在 agent 块里。** 项目的授权目录是宿主事实（`project_workspaces`）。
   起跑时由宿主校验「目录是否授权给这个插件、realpath 是否核过」，插件只是把它带进
   `AgentStartRequest.directory`；不合格的请求到不了 Runtime。
   FlyLeaf 那个 `directory_input_port` 字段在 Molis Work 不适用，本设计不使用它。

仍待实施时定死的一处：

3. **Coding 是第一个真正运行时托管的 app 插件。** 它除 Agent 之外还要用到的 Module 能力
   （Projects 的工作区读取、Goals 的事件写回）**尚未注册**进 Kernel Capability Registry——
   目前只有 Goals 的约 30 个能力在册。这是实施前的硬前置，也是存量六插件后续迁移的同一条路。

### 角色与执行档位怎么落

用户在界面上选的是**意图**（讨论 / 规划 / 执行 / 评审），不是内部角色名。意图映射到 manifest 里的角色，
角色的执行档位由 manifest 冻结、由宿主校验：

| 意图 | 角色 | execution | 在哪个 Runtime 上可用 |
| --- | --- | --- | --- |
| 讨论 / 规划 | reader / planner | `read-only` | Prologue 与 CLI 都可用 |
| 执行 | builder | `workspace-write` | **两个 Runtime 目前都不可用**——审批桥未挂到 Runtime 上 |
| 评审 | reviewer | `read-only` | Prologue 与 CLI 都可用 |

执行这一档现在会被宿主明确拒绝，而不是降级成只读悄悄跑。界面上它应当显示为**真实不可用**并给出原因，
这正是 §5「不可用的命令仍然显示，带上原因」那条规则的具体一例。

## 12. 复用与缺口

| 来源 | 已有 | Coding 需要补的 |
| --- | --- | --- |
| Plugin Platform v2 | Manifest、依赖解析、隔离重启、事件流、输入图、视图/命令/路由装配 | 已就绪 |
| Agent Host | 启动授权、角色冻结、越权复核、Review 队列、8 个可注册 Capability | 已就绪 |
| Prologue adapter | 会话、Run 的启动/观察/控制、事件流投影、**审批桥已可挂载**（挂上才申报 `text-edit`） | `command` 的回执来源；真实模型端到端验证（需凭据）；产品装配尚未构造 Agent Host |
| CLI adapter | 只读 Run 真实执行、`stream-json` 投影、停止、用量 | permission-prompt 工具，把 CLI 的询问转回宿主队列 |
| Artifacts | 版本、类型、producer 身份、端口发布已接通 | ChangeSet / Report 两个 Artifact 类型定义 |
| Goals | 事件协议、Goal 树，**16 个事件类 Capability 已注册** | 不用新增：Coding 在 Manifest 里声明消费即可 |
| Projects | 工作区目录与授权 | 面向插件的受限只读 Capability——**未注册** |
| Sessions | 用户自己的交互终端 | 不借用：右栏终端页读的是 Agent Host 的命令回执，两者不是一回事 |
| Agent Host 命令回执 | `readCommandOutput` 契约在，两个 adapter 都实现 | 暴露成 Capability；在审批接通前仍申报不支持 |
| 浏览器页 | 桌面壳自带 WebView | 一个受限预览 Capability：只开 localhost 与本项目产物，不做通用浏览器 |
| Canvas 页 | Artifacts 已有版本与来源 | 一个「执行画出来的图」Artifact 类型，以及它的渲染面 |
| Shelf | 材料收集 | 材料作为 Artifact 输出到端口 |
| 宿主审查面 | Review 队列与回执语义已具备 | 用户可操作的审查界面本身 |

**没有的东西不要在设计里假装有**：PR/CI 跟踪、云端执行、定时任务都不在首版。
它们在能力全景里保留位置，单独决定投入。

**2026-09-19 第二轮调整**：右栏工具面把**运行预览（浏览器页）**和**命令回执（终端页）**拉进了首版——
这两样在第一轮里是明确排除的。改的是范围，不是判据：终端页仍然只读，浏览器页仍然受限，
两者都要先有上面那两个 Capability 才算接通。在它们注册之前，这两页在 UI 上必须显示为真不可用，
而不是画一个空壳。

## 13. 已定的四件事（2026-09-19）

1. **插件色用 cyan。** 接受它与 `--tone-hold` 的重叠：身份色只出现在图标栏与目录字形，状态色只出现在
   `mw-status` 标记上，两者不共处同一控件。已落进 `MW_PLUGINS`。
2. **Goal 关联非必须。** 没有 Goal 也能开一条编码会话；目录里分「按目标分组」与「未关联目标」两组，
   §4 的设计不变。
3. **行级反馈首版就做。** 变更标签里可在具体行留意见，若干条一起发回原任务。反馈不是批准。
4. **CLI adapter 首版进。** 与 Prologue 并行支持，两者实现同一 `AgentRuntimeAdapter`，各自如实申报
   能力矩阵；CLI 做不到的能力显示为真实不可用，不降级伪装。
