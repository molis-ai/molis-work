# Molis Work 代码质量与实际体验审查

状态：执行中（2026-11-15）。负责人：Codex。本轮基线 `efdaa3376`，已拉取 `origin/main`，独立工作树 `codex/quality-experience-audit`；代表入口检查与三批本地定向验收完成；首屏路径批准和CI Full尚未完成。

## 目标、范围与完成标准

根据本轮用户要求，独立检查六个方向：隐式状态机、过度防御、用户干扰、冗余实现、职责与调用链、平台化机会；同时检查逻辑缺陷、整体需求实现度和可清理的 BL。检查范围按 `scripts/workspace-packages.mjs` 的 73 个包、SSOT 与公开合同确定，另覆盖 Rust 同步服务的入口和边界。旧审查报告只作线索，每项判断以本基线源码和实际调用方重新核实。

交付目标是审查闭环及纳入本轮改造的内部完整：正常入口的操作、持久化、反馈与相关失败恢复均有证据。工程通过、隔离 Home 实操和本人验收分别记录。包成熟度不代表整份产品需求完成，不将未实现或待本人验收的 BL 当作可删除项。

范围不含未经授权的推送、PR、发布、真实 Home 数据变更、Prologue 换包、门禁修改及新兼容机制。确需这些动作时先做完可审阅的准备，再说明具体差距。本地定向验证使用机器槽、`--jobs 1`；共享核心的 Full 按仓库规则在 CI 执行，不擅自改成本地全量。

## 执行路径与取舍

1. 核对注册、包入口、事实 owner、主要调用方和已有测试，逐包登记实际审查深度；沿 UI、HTTP/动作、后台、Agent、CLI/MCP 到存储追踪关键路径。每个方向独立检查，不以旧报告的条数作为完成标准。
2. 在同目录报告中记录代码位置、触发条件、影响、反证、处置和优先级。优先解决可复现的正确性和用户中断问题；低风险、语义一致的重复实现优先复用现有 SDK。公开导出没有仓内调用方不自动等于死代码。
3. 审查得到证据后在本 spec 追加实际分批范围及编号验收，再改行为。每批完成正常入口、失败/取消/重试、实际写入与相关消费者验证。UI 使用公共 test-kit 和隔离 Home、独立测试浏览器；不碰个人浏览器资料。
4. 核对所有活跃 spec、路线书状态与 BL 的来源。仅当原验收已经满足或事项确已合并才列为可清理；“待本人验收”保持原归属。报告记录证据，不另立第二份待办事实来源。

平台化选择沿用现有动作目录、Plugin Runtime、SDK 与 SSOT：状态和业务规则归原 owner，平台负责声明兑现、授权、执行和通用呈现；不以统一写法为由强迫业务生命周期相同，也不凭单个布尔字段就引入状态机。

## 第一批：资料导入队列与结果对应

发现：`apps/workbench/src/browser/knowledge/import.ts` 的 `importFiles` 先截 200 个，最后却用截断队列替换完整选择；它还把 DOM 的 `is-failed` 当作下一轮队列事实。重试未重画行，导致文件和行号错位；运行中选择新文件也会被最后的赋值覆盖。目录拖入另有 400 文件静默截断。

保持每批最多 200 份、逐个调用既有成果导入的行为；由此客户端唯一持有待导入队列，用成功条目移除已完成项，重试前由队列重画结果行。处理中可追加选择但不重画当前批；结束时说清剩余数量。目录只遍历允许的目录，不读取文件正文、不增加新的存储或平台抽象。事实写入仍归成果服务，复用既有幂等导入；界面不重新解释服务端成功结果。

最终失败边界检查补充：失败条目若始终排在队首，整批200份失败会永久挡住后面的正常文件。批次完成后，尚未处理的尾部（含处理中追加）优先，失败条目保留并移到它们后面；不增加新状态或自动重试。先用200个稀疏超限文本文件加一个正常文件复现，再验下一次点击确实保存正常正文；已有部分失败测试同时核对新的实际行顺序。

允许修改：上述客户端、工作台中英文对应词条、该路径浏览器测试和本任务文档。无合同、库结构、权限变化；不改变模型下载同意流程。验证：先用真实隔离 Home 浏览器复现，再构建并运行定向用例及工作台 README 必跑、相关界面回归、边界/健康/资源检查。界面沿用已有对话框，不新增布局组件。
