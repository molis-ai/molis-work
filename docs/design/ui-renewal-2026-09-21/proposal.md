# Molis Work UI 与视觉升级提案

2026-09-21 · 候选方案，待体验校准 · 分支 `codex/ui-visual-renewal`

**建议把 Molis Work 设计成围绕同一件工作持续推进的工作台：新反馈影响要求，要求指导内容，修改形成版本，审阅回到具体内容，下一步随这些变化更新。** 用户每次回来，都能看清发生了什么、哪些判断仍然成立，以及现在可以继续做什么。

这也是本轮视觉升级的重点。工作台应该安静、清楚、适合长时间使用；鲜明之处来自材料、内容与动作之间准确的联系。用户采用一条反馈后，眼前的要求、文稿、版本和下一步应该一起作出可理解的回应。

本轮提供交互原型和逐模块升级方案。生产界面、数据库、正式规格和现有 `taste.md` 未因本提案被修改；样例中的编辑、决定、版本与审阅只影响浏览器本地数据。

## 1. 先体验一件完整的工作

样例围绕“让新成员理解 Molis AI，并知道如何参与”。当前要求是“先阅读社区指引，再选择参与”；一条明确标注为本地演示的访谈提出“直接报名参加一次活动”。用户需要决定是否在本轮采用。五类导航保留，仅首页参与按钮与加入指引受影响；这些关系是为原型明确给定的样例。方向稿、加入指引和反馈因此属于同一件持续的工作。

| 时刻 | 用户眼前的内容与动作 | 操作后应发生什么 |
| --- | --- | --- |
| 回来继续 | 上次的文稿与一条尚未采纳的反馈；能看见为什么现在值得处理 | 打开变化判断，保留原工作的入口；阅读反馈本身不改变要求 |
| 判断变化 | 当前要求与候选要求并排；说明影响什么、哪些部分保持有效 | 选择采用或留到下轮，也可以重新打开；采用后改变本轮要求与后续工作提示，留后则保留当前依据 |
| 带着依据写作 | Pages 样例有三段真实可编辑的正文，旁边可看本轮要求和反馈 | 用户直接修改原始 v1 文稿；采用反馈不会自动替用户或 AI 改稿 |
| 保存一版 | 草稿保存与成果提交有不同动作；自动／手动保存先保住编辑内容 | “保存为成果 v2”才产生一份内容固定的本地成果版本；之前的稿件与依据保留 |
| 对照与审阅 | 上版和本版逐段对照；选择具体段落留下返工意见 | 记录“已阅”只针对眼前版本；意见能把用户带回对应段落的草稿 |
| 继续修订 | 回到原稿和相关问题，修改后再次提交 | 成果依次形成 v3、v4；旧版的已阅与意见仍绑定旧版，不自动覆盖新版 |

这些动作构成一条返回路径：**反馈 → 要求 → 文稿 → 版本 → 审阅意见 → 文稿**。首页据此呈现真正可推进的工作：最新成果有返工意见时引导修改，尚未查看且没有返工意见时引导审阅；延期反馈和等待事项安静保留，普通草稿不会被说成新成果。A、B 使用同一组数据和同一条路径，布局切换不应把采用的变化、草稿或意见重置。

此前原型更擅长展示当前成果、记录范围选择和阅读来源，但要求、成果及后续会话大多是固定样例。新主线使“关系会随动作变化”成为可以亲手操作的体验：采用反馈与暂缓反馈有不同后果，保存与未保存有区别，新版本与旧版审阅记录不会混为一谈。

## 2. 这如何服务 Molis 的整体愿景

Molis 的长期价值是让个人拥有自己的材料、上下文和专业应用，并能把选定的结果交给后续工作或团队。日常体验需要先解决三件事：

- **回来时接得上。** 不用翻完历史，就能知道工作停在哪里、发生了哪些变化。
- **制作时有空间。** 文稿、代码、数据、幻灯片使用各自合适的专业工作面，相关要求和来源随时可查。
- **交回时说得清。** 结果是哪一版、使用什么依据、还有哪些问题、谁看过什么，都能回到具体内容。

因此，Goal 负责“希望得到什么”，专业应用负责“把内容做好”，Session 负责“这段执行在哪里继续”，成果与审阅负责“结果现在怎样”。界面可以把这些信息放在一起，但不能把一次执行结束、保存一稿或记录已阅解释成工作已经完成。

这条样例用于验证共同交互，不要求所有工作先进入 Goal 或经过一次批准。用户可以独立写文稿、整理资料、建数据表、设计问卷和演示稿；这些应用拥有自己的对象库与工作面，关联 Goal 是明确选择。Functions 也应从具体来源和判断问题进入，不能被缩减成一条通用自动化流程。

当前落地仍是本地工作台。未来团队路径必须保留完整设计：**个人产出 → 选择披露哪些内容与版本 → 接收方审阅 → 明确接受 → 实际落地及结果反馈**。每一步都能回看发生了什么；接受不自动等于已经应用。团队身份、权限、交换与同步需要真实能力支持，本轮不使用在线头像或团队统计暗示这些远期能力已经接通。

## 3. 关键设计取舍：研究如何改变产品

以下取舍来自全部 23 个参照的综合比较。研究帮助选择适合 Molis 的工作方式；不同参照并不需要各自对应一个新增功能。

### 决策一：首页优先呈现“从哪里继续”，并解释原因

**问题。** 最近打开、最近更新、运行中、等待人判断，是不同的事。只按时间聚合，用户仍要逐项打开才能知道该做什么。

**竞品之间的差异。** Beads 从依赖中筛出当前可做项；GSD 强调恢复进度、决策与阻塞；Paperclip 的 Blocked Inbox 直接说原因及解除责任。Tability 则提醒我们，做了多少任务和目标是否取得进展需要分开观察。这些机制共同说明：首页要能支持选择下一步，排序本身还不够。[Beads](https://github.com/gastownhall/beads) · [GSD](https://github.com/gsd-build/get-shit-done/blob/main/docs/USER-GUIDE.md) · [Blocked Inbox](https://docs.paperclip.ing/guides/day-to-day/blocked-inbox/)

**我们的选择。** 首页用短回顾和工作行连接“上次停在哪”“现在出现什么变化”“下一步入口”。待采纳反馈、待修改文稿、待审阅版本保持不同含义；用户操作后，同一工作的摘要随之更新。原因在行内可读，必要时就近查看依据。

**舍弃什么。** 不增加全局优先级评分、成本卡片墙、虚构完成率和自动派单。无法确定下一步时，直接呈现已知缺口，不假装已经安排好。

**Demo 位置。** `#home` 直接回到上次文稿，也能进入当前可推进的变化／审阅工作；等待项降低强调。处理后返回首页，观察提示是否与实际选择一致。

**生产落地边界。** 优先聚合现有 Goal、Inbox、Session 和成果事实；排序及原因必须来自可读取的信息。“可继续”表示前提满足，不表示已获授权启动 Runtime。

### 决策二：变化先被看清，再成为当前要求

**问题。** 一条新反馈往往只影响部分工作。用户需要同时知道“这次改什么”和“原来哪些成果还可以保留”。

**竞品之间的差异。** OpenSpec 将提议变化与当前规格分开，再把采用后的变化带进后续工作；Notion、monday 的同对象多视图擅长提供不同观察角度；Fram 强调提案、人的判断与结果之间的接续。Molis 应吸收变化的明确前后关系，同时让用户沿用熟悉的对象详情。[OpenSpec](https://github.com/Fission-AI/OpenSpec) · [Notion 视图](https://www.notion.com/en-gb/help/views-filters-and-sorts) · [Fram](https://forwardby.io/)

**我们的选择。** 在变化工作面并排显示当前与候选要求，下面分清受影响的内容和仍有效的内容。采用、留到下轮有不同结果；原始反馈一直可查。采用后进入的文稿应带着新依据，原有保存版本仍保留当时依据。

**舍弃什么。** 不新增独立规格中心、通用审批链或全局影响图；也不声称系统能自动判断每个相关结论是否失效。范围不明的影响明确保留为待判断。

**Demo 位置。** `#change`。这张工作面是本轮原型的主要判断场景，替代只改变状态文案的取舍演示。

**生产落地边界。** 原型中的影响关系为明确样例，不是 AI 自动推断结果。正式产品应复用现有变更、要求与决定能力，逐项核对如何表达采用及其实际生效；UI 不另外维护一份可写的“当前要求”。

### 决策三：专业内容占主位，依据紧贴实际编辑

**问题。** 用户已经知道要改什么，却还得从聊天里复制交代、再去文档里定位内容，会在切换中丢失判断。

**竞品之间的差异。** Commonly、OpenAgents 将讨论和 Agent 协作作为主要工作场所；Taskade 强调指向具体对象后修改；Fibery 通过不同实体视图和收起空字段让当前职责更突出。Molis 包含多种专业应用，需要根据正在完成的工作决定主内容，而不是全站固定采用聊天或字段表。[Taskade 上下文交互](https://help.taskade.com/en/articles/11967139-a-guide-to-the-new-ui#h_f5fd2b6bff) · [Fibery 实体视图](https://the.fibery.io/@public/User_Guide/Guide/Entity-View-335)

**我们的选择。** 进入 Pages 就把正文放在中心，允许实际输入和修改；当前要求、引发变化的反馈与返工意见在旁边按需查看。草稿保存保护进行中的工作，提交成果形成可检查的版本，两者在动作和反馈上分清。用户应直接感到“我正修改这份稿”，而非在一个通用 Goal 表单里编辑附件。

**舍弃什么。** 不让常驻大 Chat 占据全部应用，不为了统一而把表格、代码和长文压成同一种卡片。不为本次样例先建设通用布局编辑器。

**Demo 位置。** `#writing` 提供三段正文编辑、草稿保存与成果版本提交；从变化判断和审阅意见均能进入同一份工作稿，后者定位到相关段落。

**生产落地边界。** 当前样例编辑器验证布局与交互，不代表生产 Pages 已接好全部版本能力。正式接入时沿用 Pages 的内容保存与草稿机制，再连接已有 Goal、材料及成果引用；不以浏览器样例存储替代产品数据。

### 决策四：审阅绑定具体版本，意见回到具体内容

**问题。** “我看过了”和“这版解决了问题”不同；对旧版的认可也不能自动沿用到新稿。笼统的聊天意见又很难定位返工。

**竞品之间的差异。** Vibe Kanban 把任务、执行尝试及代码评论分开；Codex 将成果检查放进独立审阅面；Multica 区分持续的 Issue 与某次 Run；Retool 将结果和执行记录连接起来。Asana、ClickUp 的对象活动流则有助于追溯人和 Agent 的参与，但活动流本身不能替代检查正文。[Vibe Kanban 审阅](https://vibekanban.com/docs/reviewing-code) · [Multica Issues](https://multica.ai/docs/issues#issues-and-runs) · [Retool Agents](https://retool.com/build-enterprise-apps/agents)

**我们的选择。** 前后稿对照与段落意见出现在同一工作面；点意见返回原稿修订，提交后得到新版本。已阅和返工意见均绑定被查看的版本；新版本不会自动继承旧版已阅，更不会因此完成 Goal。对研究、代码、文稿、数据分别使用适合内容的检查方式。

**舍弃什么。** 不引入统一的万能批注平台，不把 Agent 空闲、保存成功或评论已处理显示成整项完成。原型不模拟自动运行或虚假的生成进度。

**Demo 位置。** `#workreview`，与 `#writing` 形成可返回的修改路径；重点体验修改后旧版审阅记录如何保留、新版如何呈现。

**生产落地边界。** 原型以本地稿件版本表达机制。正式版本必须绑定精确的内容与成果标识，尊重各插件实际支持的格式；“已阅”与产品已有的批准、验收、收尾语义分别接入。

### 决策五：查看依据不打断正在做的事

**问题。** 用户在编辑或判断时需要查资料，返回后若丢了位置、草稿或选中对象，就会承担重复定位的成本。

**竞品之间的差异。** Notion side peek 保留原数据库语境；Linear Peek 适合快速核查；Airtable 的 Record review 强调队列与当前记录相邻。它们适用于不同阅读深度：短暂查看、持续编辑和连续审核，需要不同空间。[Notion 数据库](https://www.notion.com/help/intro-to-databases) · [Linear Peek](https://linear.app/docs/peek) · [Airtable Record review](https://www.airtable.com/guides/collaborate/interface-designer-record-review)

**我们的选择。** 引用以短预览查看，持续编辑进入完整工作面，成批判断保持队列语境。返回时保留对象、草稿、选择与滚动位置。A 日常布局和 B 对照布局围绕同一对象切换，不复制稿件或产生另一套状态。

**舍弃什么。** 不让每次查看都新增一个持久标签；不永久保留无用目录；小屏不硬缩三栏。没有对照需要时，把宽度交还内容。

**Demo 位置。** `#change`、`#writing`、`#workreview` 之间的返回，以及原有 Goal／资料预览。具体哪些位置状态已经实现，以最终交互验证为准。

**生产落地边界。** 复用 Workbench 现有 pane、tab 与对象身份。预览和正式打开的规则需在当前实现及规格冲突中统一，不另造导航系统。

### 决策六：Agent 在当前工作现场介入，用户先看清将交代什么

**问题。** 从文稿或审阅切回 Agent 时，用户不应再次重述目标、版本和修改意见，也不应因一次查看而触发执行。

**竞品之间的差异。** Rovo 依当前页面提供能力；Taskade 把感知到的上下文放在输入附近；Asana 与 ClickUp 将 AI 行为归回工作对象；Task Master 通过对话和任务 ID 指向同一工作；Claude Code、GSD 则提供面向执行与恢复的明确入口。Molis 可以综合这些做法，但不能默认拥有相同的团队知识、访问权限或恢复能力。[Rovo 入口](https://support.atlassian.com/rovo/docs/the-rovo-button/) · [Task Master](https://github.com/eyaltoledano/claude-task-master) · [Claude Code 交互模式](https://code.claude.com/docs/en/interactive-mode)

**我们的选择。** 当用户确实需要交给 Agent 时，展示将携带的目标要求、精确版本、选区与未解决意见；先形成可修改的交代，再使用对应 Runtime 的真实入口。当前工作内容仍是中心，Agent 能力靠近需要它的动作。

**舍弃什么。** 不增加全站默认聊天框，不把关联 Session 等同启动执行，不承诺所有 Runtime 都能无损恢复，也不承诺所有外部动作都能撤销。

**Demo 位置。** 新写作与审阅路径主要检验人的修改；原有 `#sessions` 及接续预览表达向执行工具交代的方式。本轮不调用 Agent。

**生产落地边界。** 只携带实际可读、被允许使用的内容。Runtime、Session、目录及准备／发送／执行状态按现有能力呈现；团队分享另行实现。

## 4. A 与 B：同一工作，两种阅读重点

**A · 续流，面向日常长时间使用。** 窄插件轨与当前目录分工，保留熟悉的入口和稳定工作区；首页用少量工作行帮助恢复，制作时以正文为主，依据在需要时展开。轻冷灰外壳、白纸内容、中性主动作和少量身份色，让真实内容形成层次。

**B · 对照台，面向变化判断与成果审阅。** 带文字的石墨导航提高入口可见性；在变化判断时并排当前与候选，在审阅时并排前后稿。比较对象本身占主要面积，旁边只留当前相关的影响、意见和动作。局部关系用于解释眼前工作，不能变成所有目标都必须经过的阶段图。

顶部保留 A／B 切换，作为导航与布局候选供比较：A 是窄插件轨＋目录，B 合并为带文字的导航。两种布局都走完整的新主线。原有静态三栏 Atlas 保留为布局样张，不再承担核心体验。比较时应关注找到入口是否容易、文字是否读得下去、判断前后差异是否省力、返回是否连续。

**建议生产采用一套外壳和一套状态，让“编辑 / 对照”成为同一工作中的阅读方式。** 当前保留 A、B 两个全局方向是为校准导航与密度。若 B 的文字导航更合适，可以选它作为外壳；无需长期维护两套皮肤。窄屏优先保留当前对象，比较内容按顺序切换或展开。

## 5. 逐模块升级安排

统一的是导航、控件、状态表达、保存与返回，以及来源和版本的可读性。专业工作面保留各自的操作方式。个人 Shelf 可以先轻放与处理材料；明确选用于项目或分享时，再核对目标与范围，不把日常暂存变成层层确认。

| 模块 | 首屏优先回答的问题 | 升级方式 | 本轮原型与落地边界 |
| --- | --- | --- | --- |
| Home | 上次停在哪？现在什么变化需要我？ | 简短回顾＋有理由的工作行；处理后更新提示；日期辅助 | 新主线入口；本地样例，不建设独立任务数据库 |
| Goals 母页 | 要得到什么结果？当前缺什么？ | 稳定列轨、搜索筛选、状态原因；列表与关系视图保留同一对象 | 原有列表与本地创建可体验；真实状态由 Goals 提供 |
| Goal 工作面 | 当前要求、成果与下一步是什么？ | 内容和未解决问题先出现；变化、来源、历史逐层展开 | 与新变化／写作路径衔接；不新算完成率 |
| Inbox | 为什么现在需要我，处理后影响什么？ | 问题、来源、取舍与影响相邻；保留决定及返回入口 | 范围决定、Feed 去向和失败示例；已处理不等于 Goal 完成 |
| Feed／项目资料 | 发生什么？哪些来源值得在当前项目保留？ | 紧凑行、就地读正文；已读、存项目资料、加入待决定分开；保存去向在 Feed 现场可查 | 阅读与保存进入项目资料视图；新主线用未采纳反馈说明阅读和采用的差别；不写入个人 Shelf |
| Artifacts | 当前是哪一版，用过什么依据？ | 内容预览、精确版本与使用位置；前后版检查；旧记录仍可查 | 样例成果＋写作版本对照；未接正式导出或全部 renderer |
| Shelf | 个人散落材料怎样先放下，再处理？ | 轻量暂存；原件与处理副本清楚；本机抽字和副本任务沿材料呈现；选中后动作靠近材料 | 个人置物架的处理面，与项目资料分离；不是每次暂存都要求选择项目或分享范围 |
| Sessions | 这段执行属于哪里，怎样继续？ | 上次摘要、当前 Goal、Runtime、目录与恢复条件；原始过程按需看 | 接续预览；不执行终端、不创建真实 Session |
| Coding | 当前改了什么、等我什么、结果在哪里？ | 对话与 diff／预览并存；回答、批准、审查有不同入口 | 设计安排与会话示意；C12/C13 和真实问答续跑不列为已完成 |
| Pages | 我正在写哪份稿，依据什么，是否保存？ | 文稿主位、上下文按需；真实编辑；草稿保存与成果提交分开；意见回到段落 | 新主线的 `#writing`；本地文本编辑不等于生产 Pages 完整升级 |
| 审阅工作面 | 这版改变了什么，哪些意见还需处理？ | 前后稿与段落意见；查看、已阅、返工分别表达 | `#workreview`；已阅绑定版本，不替代正式验收 |
| Dataset | 哪张表需要处理，记录、字段及版本怎样修改？ | 独立数据对象库；表格主位；列定义现场编辑；导入预览；差异可查；Goal 可选关联 | 设计说明，未接真实数据编辑 |
| PPT | 正在做哪份演示，当前页怎样组织？ | 独立演示对象库；缩略图、大纲、专业画布与当前页属性；Goal 可选关联 | 页面样张；准确区分 JSON 与 PPTX，未提供正式导出 |
| Forms | 哪份问卷正在设计、填写或收集答复？ | 独立问卷对象库；三种工作状态明确；原始答复在统计前可达；Goal 可选关联 | 设计说明；AI 生成尚未接通的部分保持原成熟度 |
| 灵光 | 怎样先留下念头，再决定是否展开？ | 少字段、轻输入、最近记录；转为目标是独立动作 | 本页草稿样张，不自动形成正式承诺 |
| Schedule | 何时做什么，上次结果怎样？ | 紧凑时间行；对话任务与插件闹钟分清；失败能回源处理 | 固定时间样例，未创建真实提醒 |
| Functions | 这条内容为什么被捕捉，怎样改进判断？ | 从 Feed 来源进入规则；原文样本旁编辑；试跑显示理由；草稿／发布版分开；返回来源看使用版本 | 当前仅固定试跑样张，不调用模型或发布函数；这条现场编辑闭环需要后续深化，三步流程图不作为最终方案 |
| 应用／插件 | 它能帮什么忙，在当前范围是否可用？ | 用途与条件优先；个人／项目、安装／启用／连接分清 | 应用入口及安排说明；不安装插件 |
| 项目与全局设置 | 改动影响哪里，何时生效？ | 独立设置文档；分类轨＋约 760px 内容；明确保存／即时偏好 | 外观偏好可体验；完整项目配置未接 |
| 团队空间／Casebook／Exchange | 哪些个人结果可以交给谁，接收后怎样推进？ | 个人产出→选择披露→接收审阅→接受→实际落地；分别留下可回看的结果，后续工作能使用被接受的版本 | 必须保留的长期设计；身份、权限与同步具备后接入，不画成当前在线能力 |

## 6. 视觉与工艺

**让用户一眼分清正在读什么。** 外壳提供位置感，正文提供阅读感，对照提供差异感。主内容以连续纸面组织，分隔线只在对象或职责发生变化时出现；少用浮卡套浮卡。

- **色彩。** 延续冷中性壳、插件身份色和带文字的状态色。A 壳 `#f1f3f5`、纸 `#ffffff`、墨 `#262a30`；B 导航 `#252d38`。靛用于链接、选区与进行中；主按钮保持中性。候选变化和当前内容通过标签、位置和文本差异共同区分，不能只靠红绿。
- **字体。** 复用自托管 Inter 与 Noto Sans SC。桌面 UI 13px、文档正文 14px 起，长篇正文可按实际阅读提高；标题 22–28px，常规字重 400。重要文字不藏在缩略图小字里。正式接入前统一检查小字号与对比度。
- **密度。** 列表和目录保持工具密度；编辑与判断面留出阅读宽度。28–32px 视觉控件、44px 触控目标。不能靠开启“紧凑模式”才能正常工作，也不能为三栏布局把中文正文压成窄条。
- **动作。** 一个工作面保持一个清楚的当前主动作：采用变化、保存版本、返回修改。动作旁说明实际后果；已读、已阅、采用、保存、执行、完成使用不同措辞。
- **选择与焦点。** 选中状态采用稳定底色与文字，不叠加边条、描边和高亮。保留键盘可见焦点，使用仓库 Lucide sprite；触屏入口不依赖 hover。
- **动效。** 约 90ms hover、180–190ms 到达作为候选；用于帮助看见打开位置与状态变化，避免全页淡入和所有卡片浮起。正式接回共享 motion token，并遵循减少动态效果偏好。
- **滚动与返回。** 固定外壳、内容内部滚动；正文、意见与动作在矮窗口仍可达。查看来源关闭后回到原位置，返工返回对应稿件；多栏只在有足够空间时并列。
- **失败与未保存。** 输入先保住，再解释失败；重试贴着失败动作。未保存修改、成功保存和已阅记录各有可见反馈。示例中的故障演示不能代表真实后端恢复已经通过。

作品本身可以有丰富排版与色彩。工作台的视觉个性来自克制的层次、稳定列轨，以及一次修改后准确出现的差异和关联反馈。

## 7. 哪些规格建议调整

下面记录候选变化，便于之后校准和落实；本提案没有直接覆盖已生效规格。

| 现有偏好或规则 | 建议调整 | 需要保留的边界 |
| --- | --- | --- |
| 插件轨约 48px＋目录约 240px | A 继承；B 比较带文字导航；母页和深度编辑不强留空目录 | 稳定入口与对象身份，不为几何一致牺牲内容宽度 |
| Home 以日期、日历、快捷入口组织 | 把恢复工作及当前需要人介入的变化前置 | 日期仍可用；首页不成为第二套业务状态 |
| Goal 中执行内容占较大空间 | 按工作需要在制作、看要求和审阅之间切换焦点 | Runtime 归属及打开不执行保持不变 |
| 版本与依据主要作为元信息 | 升级为可参与操作的上下文：采用变化、保存、对照、返工 | 固定引用不被 latest 静默替换；真实缺失的信息不伪造 |
| 预览、母页与持久标签规则存在旧文档冲突 | 明确短暂查看、正式打开、返回原稿的区别 | 先核对当前 Workbench 行为，再校正规格，不按旧文档反向改实现 |
| 状态、原因与历史分散 | 当前问题及下一步在首屏可读；历史逐层展开 | 只聚合已有事实，不新增一套可写状态 |
| 所有页面希望共享一致视觉 | 统一导航、控件与版本表达；保留 Shelf、文稿、表格、代码的内容气质 | 不以统一为由削弱专业编辑能力 |
| 字重、焦点、图标、系统控件等工艺要求 | 校准必要字号／字重变化，保留焦点、主题、原语与可访问性要求 | 探索不降低已有工艺底线 |
| 完成与验收、打开与执行各有不同含义 | 保留，并在新版本审阅路径中明确呈现 | 已阅不能完成 Goal，保存不能假称已交付 |

`PRODUCT.md` 旧执行术语、`DESIGN.md` 标签与目录行为等漂移详见[当前审计](current-product-audit.md)。正式改造时，在对应切片内校正具体差异，避免把本轮视觉研究扩大为无关架构改写。

## 8. 实施顺序与依赖

当前授权交付是方案与原型。下面描述设计被采纳后，生产升级应按什么顺序推进，不预设工期。

1. **先验证这条修改路径。** 让用户亲手采用或暂缓反馈、编辑正文、保存、对照、留下意见、返回修订；比较 A/B 的发现性、密度与返回。先确认动作是否好用，再锁定外壳和视觉规格。
2. **核对真实内容与关系。** 明确当前要求、变化、文稿保存、成果版本、意见分别由哪里提供；不足之处单独列出。能复用现有能力就直接连接，不能因 Demo 有按钮就承诺生产能力已经存在。
3. **建立共享表达与控件。** 在 design-system 的 Catalog 中落实被采纳的字体、颜色、按钮、列表、预览与对照组件；Workbench 接导航和连续工作面。沿用当前 HTML Slot，不为视觉升级迁框架。
4. **先落一个专业内容闭环。** 以 Pages 文稿或仓库中最成熟的内容类型连接 Goal／Inbox／精确版本与审阅：变化可判断、修改可保存、旧版可回看、意见能回到内容。Home 随真实结果更新。
5. **再扩上下文入口。** 接 Feed、Shelf、Session 的来源、保存去向与接续；覆盖取消、跨模块返回、未保存草稿、失败和重试。Runtime 能力按实际 adapter 逐项接入。
6. **扩到其余专业应用。** Coding 用 diff，Dataset 用记录和字段差异，PPT 用页面比较；Forms 保留原始答复与填写流程。深化 Functions 的来源→规则编辑→样例试跑→发布版本→来源使用这一闭环；Schedule 保留时间安排与本次结果。各应用可独立使用，已有未完成的 AI 能力保持诚实的可用状态。
7. **完成真实桌面使用校准。** 用最终 App、代表性内容、13 英寸及矮窗口、多标签／分屏、中文输入法、键盘与连续使用检查体验，再决定发布。团队身份、分享和同步后续单独落地。

每次改造范围应能独立回退。纯布局与 token 切片不需要数据迁移；若精确版本或意见关联确实缺少能力，应先说明必要性、数据影响及最小实现，再安排相应修改，不用 UI 临时状态补出第二份真相。

## 9. 怎样判断这版值得继续

用同一任务检验以下问题，先观察操作，再讨论审美偏好：

- 刚打开首页，能否说清上次停在哪里、为什么这次反馈需要处理？
- 采用前，能否指出哪条要求会变化，以及哪些内容保持有效？
- 选择留到下轮后，当前文稿是否仍使用原要求，而不是悄悄更新？
- 编辑时能否看见当前依据，清楚区分未保存内容和已保存版本？
- 对照时能否找到具体变化，针对段落留下可操作的意见，并顺利返回修改？
- 提交新版后，能否理解旧版已阅仍保留、而新版仍需检查？是否误以为 Goal 已完成？
- 返回、刷新、切换 A/B 与窄屏后，是否仍在同一件工作上？草稿、版本、意见与选择有没有丢失？

可以记录完成时间、误操作和需要提示的次数，但目前没有用户实测数据，不声明效率提升百分比。

证据分开记录：语法、构建和自动检查只能说明工程情况；浏览器点通说明这份原型的局部交互；最终 App 实操才覆盖生产路径；用户亲自体验后才能确认质感与适合程度。中文输入法候选、VoiceOver 连续使用、真实设备手感及长期负担目前仍为 `UNVERIFIED`。新增主线以最终运行与验证记录为准，不沿用旧原型测试结果宣称它已经通过。

## 10. 研究索引与覆盖范围

研究是上述取舍的依据，覆盖数量不决定产品要增加多少功能。当前可暂缓的共性能力包括组织图、成本面板、任意视图配置、所有对象的看板、多 Agent 自动调度、常驻全局 Chat；它们没有成为这次个人工作闭环的必要条件。

多家产品反复采用左侧范围导航、稳定对象列表、原位详情、当前内容与历史分层、输入旁的上下文、成果审阅等模式。因此可以把这些作为“用户可能熟悉”的假设，把新的学习重点留给 Molis 的变化、版本与完成含义。**这不等于已经证明目标用户学会了这些交互。**

| 研究分组 | 名单 | 数量与证据深度 |
| --- | --- | --- |
| [平台型参照](research-platforms.md) | Paperclip、monday.com、Taskade Genesis、Fibery、Commonly、Multica | 6；官方资料，部分官方界面、导览与公开工作面观察 |
| [工作流参照](research-workflows.md) | Asana、Atlassian Rovo＋Forge、Airtable、Retool、OpenAgents、Tability、Fram | 7；官方交互资料，部分实际查看官方产品图 |
| [成熟交互参照](research-workflows.md) | Linear、Codex App | 2；交互文档与已知宿主能力，用于预览、责任与成果审阅 |
| [历史机制参照](research-supplement.md) | Beads、Task Master、OpenSpec、GSD、Claude Code、Vibe Kanban、Notion、ClickUp | 8；当前官方源码／文档机制研究，非视觉工具不作视觉评分 |

合计 **13 个主名单＋2 个成熟参照＋8 个历史参照＝23 个独立参照**。各家的具体布局、独特机制、为什么有用、不能照搬之处与精确链接在研究文档中。没有完成 23 个产品的登录实测，不能据此证明其完整可靠性、用户效果或商业成熟度；未见公开证据的能力仍写未证实。

截至研究日，Vibe Kanban 官网已经公告 sunset、继续开源与社区维护，因此这里只吸收已公开的交互机制。Beads 的官方仓库重定向、Task Master 的当前品牌入口、OpenSpec 的现行工作流和 Tability 的产品更新也已按本次来源处理，不沿用历史任务的旧状态作为现状结论。

本次设计研究最终应能在三个地方被看见：**改变如何被采用，内容如何被修订，以及人回来时如何接着做。**
