# 构建与改变

从可观察结果反推能力、基础和交付闭环。

适用于：开发产品、建立能力、改变现有系统。

## 规划路径

1. 定义最终结果和使用流程
2. 分离核心能力与支撑基础
3. 按独立交付和验收划分 Goal
4. 补齐验证、发布与恢复

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| final_outcome | 最终结果 | 最终交付什么、由谁使用、成功后发生什么变化？ |
| operating_flow | 实际流程 | 结果如何被产生、使用、维护，关键角色怎样协作？ |
| core_capabilities | 核心能力 | 完成主任务必须具备哪些业务或专业能力？ |
| foundation_infrastructure | 基础能力与基建 | 核心能力消费哪些数据、资产、工具、权限或环境？ |
| quality_continuous_delivery | 质量与持续交付 | 如何验证、交付、监控、恢复并持续改进？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| capability-after-foundation | 核心能力只有在真实消费基础设施、数据、权限或契约时才依赖对应基础 Goal。 | capability depends_on consumed foundation |
| delivery-after-capability | 交付、发布和验收依赖可运行的核心能力及其验证证据。 | delivery depends_on validated capability |

## 完成证据

- 可运行或可使用的产物
- 完成条件对应的检查证据

## 收口检查

- 用户结果可观察
- 每条叶子只有一个主要验收结果
- 基础结果被核心能力真实消费

## 常见误拆

- 按文件或技术层机械拆分
- 只列功能不列运行和交付
- 把讨论顺序当执行顺序

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
