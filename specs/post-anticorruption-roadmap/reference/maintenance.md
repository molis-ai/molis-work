## 怎样维护这份路线书

- `spec.md` 只维护批次顺序、每项独立交付一行的内容和 reference 分类入口。完整交付、来源、前置、并行、UI、进展与证据只写在对应批次详情，不把长说明重新堆回目录。

- 每批及每片开工前先按[开发流程 §2.1](development-workflow.md#kickoff-brief)用大白话讲清楚做什么、解决什么问题、做完能看到什么、为什么排在这里、需要用户做什么，再说明交付与验收、边界和前置；范围或依赖变了先同步同一份 spec 与执行表，再继续受影响部分。
- 每批一个[批次文件](execution-rules.md)（`batches/NN.md`、`batches/srv-N.md`）：新增批次时同时写好「给人讲清楚」和「Goal Prompt」（Goal Prompt 的通用部分照现有批次原样写：第一节的「开发要求」、第四节的按批推进与合同顺序、第五节的定样流程和七项体验要求、第六节的红线与并行、第七节「防腐与代码质量」、第八节的证据三级、收尾与「上报进展」（认领板 #1743 的行与评论、PR 评论、发消息的场合、拍板、会话标题）；用户 2026-11-05 定，统筹提示里统筹以外的开发要求都进每批的 Goal Prompt）；交付、前置、顺序或 UI 要求变了，在同一个改动里同步这两节；移到服务端批的编号留一个只写去处的文件。调整顺序时，批次之间的上一批／下一批链接一起改。
- 每批按原需求记录实现、工程验证、真实操作和本人验收，不能互相替代；只完成同批一部分时保留其余交付。做完的条目从 BACKLOG 删掉（在提交说明里写编号），归档做完的 spec，在[执行目录](../spec.md#execution-batches)链接的对应批次详情补日期、PR 和剩余项；整段完成后再更新阶段总览。
- 新需求先进 BACKLOG 或原 spec，再按[排期原则](dependencies.md#section-2)的三条和[依赖图](dependencies.md#section-4)的依赖并入[执行目录](../spec.md#execution-batches)对应批次：目录增加或调整交付行，批次详情更新来源、前置、并行和 UI 要求，需求映射补来源／类型／未决入口；阶段总览只在目标或退出条件变化时更新。需要调整顺序时在这张完整表内调整，并核对所有批次引用，不另起补充编号或聊天排期；要服务端的需求进[服务端批](server-batch.md#server-batch)，片号接着编（用户 2026-11-03 定）。一项需求从立项到收尾怎样走，见[需求开发流程](development-workflow.md)。原需求完成后才移除[需求映射](requirements.md#section-3-9)对应行。
- 「谁正在做哪一项」只记在[认领板](https://github.com/molis-ai/molis-work/issues/1743)（置顶 issue，用户 2026-11-03 定），用法写在它的正文开头：开工前认领、状态变了就改、合入后改「已合入」。执行目录增删或改名交付行时，在同一时间同步认领板的行；认领板不记排期，排期仍以执行目录为准。
- 轨道独占文件或交接变了就更新[轨道表](tracks.md#section-5)，交付行增删或改名时同步[批次与轨道对照](tracks.md#section-5-2)；为判断冲突而重测的热点记入历史，不在执行规则里累计旧统计。
- 全部阶段及已纳入交付的服务端批都走完，或者本文被新的排期取代时，按 [specs/README.md](../../README.md) 的规则归档。
