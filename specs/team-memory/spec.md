# 团队记忆：持续理解团队、积累经验并辅助协作

状态：独立需求草案（2026-10-28）。用户已确定团队记忆像一个 24 小时在线的 PMO：持续观察获准的团队项目、沟通和工作，选择能长期复用的决策、风险、知识、偏好与协作经验，减少人与人、人与 AI、AI 与 AI 之间的上下文传递，并支持主动协作、工作习惯和交付质量改善。成员仍可主动发布个人记忆，发布前再次确认并告知不能撤回；团队管理员维护团队记忆，个人与团队可采用不同策略。具体形成／融合策略、管理交互及技术合同待细化，尚未实现或验收。本轮只整理需求，不开发。需求维护：Codex；实现待分配。承接 BL-022，沿原 3·C／阶段 4 的设计和实施安排，不改变现有记忆 P0 的负责人、依赖或暂停边界。

## 1. 目标与范围

团队记忆像持续在线的项目协调者（PMO），逐渐理解团队在做哪些项目、为什么这样决定、工作如何衔接，以及哪些做法影响交付。它从团队获准观察的项目、沟通和实际工作中主动积累，也接收成员愿意分享的个人经验。目标是让每次工作留下的认知在以后继续有用，减少反复讲背景、找决定、解释约束和交接遗漏的成本。

例如，团队几次交付都在最后一天补齐验收口径，造成返工。记忆应保留具体原因、有效的改进办法和适用条件；下次类似项目启动时，助理可据此提前准备验收清单。另一名成员或 AI 接手时，也能知道已做的决定、不能遗漏的检查和仍待核实的风险，无需重新读完所有讨论。是否真的减少返工，要看后续工作结果。

本需求覆盖持续观察、价值筛选、形成和融合、成员发布、管理员维护、按任务使用，以及基于使用反馈的修正。目标完成程度为**内部完整**：多个真实成员和 AI 能完成观察／贡献、积累、交接使用、主动辅助、纠正与异常恢复的完整路径。成员贡献、观察记录与最终记忆不要求一一对应，记忆可融合多个来源，也可按主题拆分。

“24 小时在线”表达持续主动工作的目标，运行承载与调度方式待方案确定。来源未接入、未获准、主机休眠、连接中断或历史缺失时，须显示实际覆盖和补读状态，不宣称已持续观察全部工作，也不据此假定已经决定云端常驻部署。

不自动公开个人记忆，不为发布建立成员逐条撤回／删除机制，不复制另一套记忆运行时，也不将团队记忆当作项目长期说明、业务事实或执行授权的替代品。

## 2. 成员发布：确认后不可撤回

成员选择有权向目标团队分享的内容，形成可审阅的发布预览。预览明确展示实际发布正文、目标团队、可见范围及来源说明，避免把选定摘要误认为发布整段会话或整个个人记忆库。

发布前必须再次取得成员对这份预览的明确确认，并在同一处告知：**内容发布后可能被整合进团队记忆，不能撤回，无法保证消除它已经产生的影响；内容有误时可补充更正，由团队管理员处理。** 具体文案随交互设计打磨，但不能只藏在帮助页，也不能把发布按钮伪装成可随时撤销的普通保存。

成员说“发布到团队”、使用 AI 准备发布、个人记忆的形成／候选批准、通用自动执行许可，都不能省掉本次最终确认。已有一份对相同正文、团队和范围的有效最终确认可在同次发布的重试中复用，不因重连或重试重复询问；内容、目标或共享范围发生变化后须展示新预览并重新确认。预选、沉默、关闭界面与超时不算确认，AI 不能替成员确认。

确认前可以修改或取消，取消不产生团队可见内容，也不进入团队召回或融合。最终确认后由同一授权服务再核对成员与分享权限，按本次确认完成一次发布；成员发布不额外要求管理员逐条批准。页面、对话、工具和其他实际支持的入口遵守同一条件，不能从某个入口绕过。

发布成功后，成员可以补充新信息或提出更正，不提供撤销已发布贡献的承诺。发布者退出团队、删除个人原文或失去访问权，不会自动把已发布内容及其融合影响从团队中抹除；退出和撤权仍限制该成员之后的访问与操作。管理员维护当前团队认知也不等于收回成员已经看过、导出或用于工作的内容。

个人原文继续归个人管理。一次发布不授予持续同步整个个人记忆的许可，团队内容变化不反写个人原文。来源文件和原会话仍按各自权限访问，不因发布了摘要就向团队开放。

### 2.1 发布结果与失败恢复

发布是否已被团队接收，与是否已经参与融合、是否已经用于任务分别显示。接收成功不能冒充融合完成；融合失败也不能把已经发布的内容说成仍可撤回的私人草稿。

确认前失败保留私人草稿；提交失败、结果未知或回执丢失时先核对真实发布状态。重试、重连和重启不重复发布、不覆盖管理员后续维护结果。已确认但尚未生效的请求在执行前遇到撤权必须拒绝；已经成功发布的内容按上述不可撤回规则处理，不能伪称已撤回。

## 3. 团队如何整合和使用

### 3.1 持续观察与成员发布是两类输入

观察范围覆盖团队所有已获准接入的项目，以及相关沟通、讨论、任务过程、交付物、评审和反馈，包含人与 AI 的工作。通过平台共用的采集和公开数据工具理解已有材料及后续变化，不依赖成员每次手动挑选或说“记住”。接入外部工具仍沿各自连接与有效范围；未接入或不可读的来源列为覆盖缺口。

| 输入 | 如何进入团队记忆 |
| --- | --- |
| 获准用于团队记忆的项目内容、沟通和工作记录 | 按团队启用的形成策略持续筛选、提出候选或吸收；不把每次提炼都变成成员个人记忆发布流程 |
| 成员未共享的个人记忆、私人会话或个人材料 | 仍由成员选择可分享内容，按 §2 审阅并最终确认后发布；个人助理能够读取不等于团队可接收 |

团队管理员能查看来源覆盖、开启或暂停形成、调整有效范围和纠正结果；其操作限于原本有权管理的来源。“团队所有项目”不授予访问未共享项目的权限。来自受限项目或沟通的提炼保留来源的访问限制，融合、摘要和跨项目引用不扩大可见范围；无法安全分离不同权限来源时不向更宽范围输出。来源撤权后，相关观察记忆的后续召回和在途输出遵守新的有效访问，不能套用成员主动发布的不可撤回规则继续读取。已确认发布的个人贡献按该次发布范围与 §2 处理。

首次理解、持续变化和断线补读复用同一来源及进度。历史导入不当作新发生的工作，重复采集和 AI 反复转述不算多份独立证据。形成、融合失败或重启后保留此前有效记忆，核对实际进度再继续；未处理的材料不冒充已理解。

### 3.2 从后续复用价值选择记什么

优先保存能在后续任务改变判断或做法、减少解释与查找、避免重复错误的内容。选择时考虑适用范围、来源可靠性、可能有效多久、与已有认知的关系，以及带入上下文的成本；不以存入条目数、摘要长度或记录频率作为成功指标。一次重要决定可以立即有价值，不要求重复发生才记；短期状态与一次性噪声继续留在工作记录中按需取用。

| 值得积累的内容 | 需要保留的含义 |
| --- | --- |
| 决策与背景 | 做了什么选择、为什么、放弃了哪些方向、当时的约束，以及何时需要重看；明确区分决定和提议 |
| 风险与经验 | 风险发生的条件、早期信号、实际影响和有效处理办法；当前风险状态引用原风险记录 |
| 知识与方法 | 项目／客户背景、领域知识、验证过的做法和失败教训，以及可回看的材料 |
| 偏好与质量要求 | 团队及相关成员在什么场景偏好怎样沟通、评审和交付；区分明确表达、实际采用和系统推断 |
| 工作与协作模式 | 任务如何拆分、谁在什么阶段介入、怎样交接、常见等待与返工点，以及团队已经尝试的改进 |

长期观察应逐步补充和修正这些认识。一个项目的习惯不直接推广到全团队，一次失误不成为成员的永久标签；工作模式改变后旧结论要更新或停止使用。来源互相矛盾时保留分歧和条件，不凭多数、时间较新或 AI 总结宣称已经形成共识。

### 3.3 融合、管理与任务取材

个人与团队共用已有记忆底层能力，产品策略分别设计。个人围绕自己的偏好、经历与当前工作整理；团队需要处理多人来源、重复、互补信息、分歧、适用范围和集体维护。不能把个人的一套形成／召回配置直接复制给团队，也不能因为共用存储机制就要求两者采用相同管理界面。

团队融合应保留能解释当前认知的来源、条件和变化依据。融合可以归纳已有贡献，不得把推断伪装成成员明确表达，不以重复提交或同一来源的多次改写增加独立支持。新贡献是否补充、替换或形成分歧，由后续明确的策略处理；不默认“最后写入的人获胜”。发布确认允许团队接收和按有效策略使用本次内容，不等于批准 AI 随后产生的每个新结论。

成员和 AI 按有效团队权限、当前任务和实际适用范围取用记忆。团队记忆不必每轮全量带入，也不因发布到团队就强制用于该团队的所有项目；个人偏好与团队认知同时相关或相互冲突时，需要明确的使用策略，不预设谁永远覆盖谁。用户能知道本次用了哪些团队认知、依据和限制，必要时回到原始贡献核对。

管理可以围绕主题、当前认知及来源展开，不预设逐条 CRUD 列表。团队管理员负责查看团队理解、纠正内容、处理分歧、调整适用范围和停止使用失效认知；这些操作只作用于获准团队，不扩展到成员未发布的个人内容。更正应能影响后续实际召回与回答，不能只改管理页展示；管理员维护不承诺从所有历史输出中消除某一贡献的影响。具体清理、保留和过期策略随方案细化。

AI 负责持续筛选、提炼、去重、关联、融合和按任务取材；输入限于获准观察的团队工作及有效发布内容，输出是可核对的候选、团队认知或本次任务的相关上下文。管理员在形成和维护入口干预，成员在个人发布前干预，使用者可查看依据并反馈错误。模型生成的推断须有明确标识，不能自行批准自己的候选；自动吸收按团队已启用的形成／晋升策略执行，具体策略在实现前确定。融合失败、冲突未决、模型超时或低质量结果保留已接收贡献与此前有效认知，显示未完成状态；重启后不重复发布或把未完成结果当成正式认知。

### 3.4 在交接、主动协作与交付中使用

| 场景 | 记忆应提供的帮助 |
| --- | --- |
| 人与人交接、新成员加入 | 按接手的工作带出相关背景、决定及原因、协作约定、风险和资料入口，让接收者知道哪些已确定、哪些仍待核实 |
| 人与 AI 开始或继续任务 | 自动取用相关团队偏好、历史经验和质量要求，减少重复输入背景；用户能看见并纠正用到的理解 |
| AI 与 AI 分工、跨会话或跨工具接续 | 提供一致的相关团队认知和来源，实际任务状态从原主人读取，减少反复压缩转述造成的丢失或误传；记忆不转移执行权限 |

主动助理根据当前工作和团队记忆，在有用的时机准备材料、提示风险或建议改进。例如，启动类似项目时提示过去遗漏的依赖；交接时发现缺少决定依据；提交前结合既有质量要求指出缺失验证；复盘时识别反复出现的等待、返工和低效交接。提醒应说明当前证据、相关经验和可采取的下一步，并沿既有通知偏好控制打扰，不因记住了一件事就持续推送。

建议、执行与效果分别记录。建议被采纳不等于工作习惯已经改变，任务被标记完成也不等于交付质量达标；后续要结合真实结果、成员反馈和反例判断是否修正记忆。有效做法如需变成可重复执行的 Skill 或持续遵守的项目说明，由各自公开能力和生效规则承接。风险仍由[风险插件](../risk-plugin/spec.md)拥有，记忆保留经验与引用；团队记忆不另建任务、风险或绩效台账。

效果验证同时看少传了多少上下文和工作是否变好：重复解释／查找与交接耗时、关键背景遗漏、AI 实际上下文用量及形成／维护成本、风险提醒的相关性、返工与质量缺陷。用相近任务的基线和后续结果比较，区分相关性与可归因的改善，不预先承诺节省比例。团队习惯和协作模式需要跨时间、跨任务验证，一次演示不能证明长期学习已经成立。

| [现行记忆方案](../prologue-memory-strategy/spec.md) | 已有写入口、候选、版本、状态、作用域、授权、召回与用量能力；新增通用缺口由原主人补齐，不另建运行时 |
| [主动助理](../proactive-assistant/spec.md)、场景 Skill 与 [Work Brief](../work-brief/spec.md) | 消费当前事实和团队记忆，判断何时准备、提醒或执行；工作台与简报承载用户查看和干预，动作沿原授权，记忆层不再做一个助理 |
| 评测（[主动助理 §14](../proactive-assistant/spec.md#14-molis-work-的端到端效果评测)） | 使用同一工作记录验证上下文成本、建议效果与交付质量；记忆提供其形成和使用依据，不自行宣告效果达标 |
| 个人同步与 [Sync & Replication](../../docs/modules/sync-replication.md) | 传输、重连、冲突和真实同步结果；不决定哪些私人内容被发布，不从传输成功推导融合完成 |
| 原业务插件与项目长期说明 | 原始事实、来源和持续规则；团队记忆只保留必要提炼与引用，不制造另一份业务状态或规则主人 |

实现前先完成个人／团队策略对照与高保真切片，覆盖观察范围及覆盖状态、值得记住的候选、贡献预览与最终确认、团队认知和来源、管理员纠正、三类交接及一次主动质量提醒；再冻结必要合同并接入。发布门与身份依赖就绪之前不开放真实发布。具体字段、融合算法、运行承载与界面布局不在本轮预定；共享底层不代表现有实现已经支持团队融合。

待细化：观察来源接入和持续运行方式，哪些内容自动吸收、哪些形成候选，冲突和失效如何处理；个人与团队记忆共同使用的条件和优先关系；管理员如何观察和干预形成／融合；观察、贡献、认知、历史版本与纠正之间的关系；容量、保留、同步及效果比较口径。持续理解团队、减少三类上下文交接、支持主动协作与质量改善，以及个人发布前再次确认、发布后不支持撤回、管理员维护已经确定，不再作为未决方向。
