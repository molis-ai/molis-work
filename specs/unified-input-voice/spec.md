# 统一输入体验与本地语音输入

状态：第 10 批已实现并合入 main（2026-11-09，[#1991](https://github.com/molis-ai/molis-work/pull/1991)，合入提交 `ecdfe102d2`）：K0／K0b／K0c／K1／K2／K3 与 H4 用词已实现，首页与助理已换上统一输入组件；第 11 批（分支 `batch/11`，一个 PR，待合入）已实现 K4 Coding 换上统一输入组件与 K5 第一个真实来源「待办」，见[第 11 批进展](../post-anticorruption-roadmap/reference/batches/11.md#batch-11-progress)；K6 其余入口与语音待后续批；本人验收待 [BL-unified-input-acceptance](../backlog/BL-unified-input-acceptance.md)、[BL-unified-input-coding-acceptance](../backlog/BL-unified-input-coding-acceptance.md)。此前状态（2026-11-04）：需求已整理（2026-10-15），2026-10-27 用户确定统一输入组件由平台负责，并增加开放注册与插件通用扩展要求（§2.1～2.2）；2026-11-04 用户定下第 10 批定样（§10），实施方案与开工前检查见[第 10 批实施方案](implementation-plan.md)（当时待审），尚未实现，当时只更新需求书、不代表功能验收通过。目标完成程度为**内部完整**。

## 1. 目标与完成标准

用户在首页、助手、Coding 中，都能用熟悉的方式输入、补充上下文、口述和发送内容，不需要在不同入口重新学习操作。

目标完成程度为“内部完整”：文字和语音的主要路径、首次使用、异常恢复、页面切换及窄屏体验均可顺畅使用。语音识别效果和等待时间需经过真实使用验证。

## 2. 范围

首期覆盖三个主要输入入口：

| 入口 | 共同行为 | 保留的场景差异 |
|---|---|---|
| 首页 | 文字、语音、草稿、发送与反馈 | 轻量表达，以及明确内容将交给谁、进入哪里 |
| 助手 | 文字、语音、草稿、发送与反馈 | 当前助手及关联上下文 |
| Coding | 文字、语音、草稿、发送与反馈 | 当前会话、Character、执行方式及任务上下文；底层模型沿统一运行配置 |

统一基础体验，同时保留各入口必要的功能。搜索框、名称字段、普通表单和文档正文编辑器不纳入首期统一范围。

首期不包含语音通话、语音播报、唤醒词、后台持续监听、系统级跨应用听写和会议录音整理。

### 2.1 平台统一负责整体体验（2026-10-27 用户已定）

本文是统一输入组件整体交互与 UI 的唯一需求入口，由平台按[迭代路线](../post-anticorruption-roadmap/spec.md) A 轨统筹：输入区、布局、共同控件、语音、附件入口、草稿隔离、键盘与提交反馈形成一套公共组件。首页、助理、Coding 是首批消费者，组件本身面向所有适用的插件页面和组件开放，不写死三个入口或插件 id。

各场景保留必要差异，通过公开注册接入共同组件。统一组件不合并不同会话的草稿，不成为模型运行、输入回执或领域数据的新主人。相关需求按以下边界接入；既有实现负责人保持不变，输入回执与用户纠正继续归原 Claude 工作线。

| 内容 | 唯一主人及与公共组件的关系 |
| --- | --- |
| 送达方式、输入身份、读到／处理回执、排队与纠正 | [AI 输入回执](../ai-input-receipts/spec.md)；组件消费现有合同并负责呈现和操作入口，不另建输入账 |
| 待回答目标、问卷、操作卡与推荐动作 | [AI 交互](../ai-interaction-experience/spec.md)；注册目标提示、相关操作与视图，不另起输入区 |
| 接收者与子代理目标 | [子代理交互](../subagent-interaction/spec.md)；显式目标由原合同校验，组件展示有效接收者 |
| 上下文、资料与下一步 | [情境计划](../context-program/spec.md)、[项目资料与目录](../product-flow-governance/workspace-and-materials-design.md)；使用真实来源引用，公共组件提供选择和展示位置 |
| 视觉细节与布局 | [视觉体验](../visual-ui-experience/spec.md)提供共用设计要求；输入组件的最终布局、密度及控件冲突由本文统一收口 |

### 2.2 开放注册与插件扩展（2026-10-27 用户已定）

各插件及其组件可以通过公开合同和 SDK 注册自己的输入扩展，也可以在自己的页面中使用统一输入组件。内置、个人、创作台生成与第三方插件使用相同的注册、挂载、生命周期和权限规则。平台根据注册内容装配，不为某个插件加宿主分支或另一份扩展名单。

首批支持的扩展形态围绕实际输入路径组织：

| 扩展形态 | 例子与职责 |
| --- | --- |
| 资料来源与选择器 | 选择项目文件、插件对象或选区；交付原主人可验证的引用，不复制正文形成另一套资料库 |
| 目标与上下文展示 | 注册接收者、当前任务、资料引用等组件；让用户知道发给谁、使用什么内容 |
| 场景控件与操作 | 注册模型／模式选择、领域选项、工具按钮、命令及必要的自定义控件；服从统一布局、可访问性与窄屏规则 |
| 当前目标的校验与提交适配 | 在所挂载的输入实例内校验必要字段，并调用目标已有公开动作；显示具体缺项，沿用统一发送中、成功、失败与结果未知反馈 |

注册应能确定扩展身份、所属插件／组件、适用场景、挂载位置、需要的上下文与权限，以及渲染／交互和释放方式。实现先核对现行 Manifest、UI 贡献和 SDK 机制，补齐缺失合同；准确字段与版本随实现设计确定，不预先造第二套插件框架。需要复用的客户端组件与注册能力通过公共 SDK 提供，不要求插件 import 工作台私有实现或别的插件。

公共组件掌握草稿、当前接收目标与最终提交生命周期。插件只接触本次挂载实例明确提供且获准的上下文；注册扩展不会自动获得所有会话草稿、全部资料、其他插件状态或执行权限。组件注册不等于自动发送、换目标或批准副作用，实际动作仍经现行授权与取消边界。扩展可以提供场景行为，不覆盖全局基本键位、默认送达语义和中文输入法规则。

同一扩展重复挂载不产生重复按钮、监听或提交；多个插件的扩展可同时存在且来源可辨，冲突有确定的排列与可理解的反馈。切页、切会话、停用、卸载、撤权或升级后按原生命周期释放；迟到结果不得写进别的会话。非必要扩展失败时保留基础输入与草稿；当前提交依赖的扩展不可用时明确阻止该次提交，保留已输入内容和恢复入口，不能静默丢掉所选资料或参数后发送。

公共组件与插件扩展一起纳入高保真交互切片，至少用两个不同插件的扩展验证可组合、可移除和状态隔离，再做真实接入。本文不改变本地语音的处理承诺，也不授权本轮开始开发。

## 3. 统一输入框与 UI 表现

三个入口使用一致的视觉语言和操作位置：

- 文字字号、行距、内边距、边框、圆角、背景和焦点表现一致；亮色、暗色主题均清晰可读。
- 输入区随内容增长，到达合理高度后内部滚动，长内容不挤走主要操作。
- 麦克风、发送、取消等共同操作保持一致的位置、图标含义和提示方式。
- 附件、上下文等操作在适用入口出现；同类操作表现一致，不展示当前场景无用的控件。
- 模型、执行方式等场景选项与输入内容有清楚的层次，不挤占主要书写空间。
- 空白、聚焦、已有草稿、不可用、处理中、失败等状态有一致表现；不能只靠颜色区分。
- 窄屏下可以调整排列，但保留输入、停止录音、取消和发送等核心操作。
- 所有主要操作支持键盘访问，并提供明确名称和状态提示。

占位提示可以随场景变化，但只帮助用户开始表达，不承担说明当前会话或发送目标的职责。

## 4. 统一文字输入与发送行为

- 支持多行输入、粘贴长文本、选中修改和正常撤销。
- 默认 Enter 换行，Command/Ctrl + Enter 发送；中文输入法选词、确认候选时不触发发送。
- 空白内容不能发送。仅附件等非文字内容能否发送，按对应入口已有能力决定。
- 发送前，用户能明确识别当前会话或接收目标，以及影响本次处理的关键选项。
- 发送过程中提供明确反馈，连续点击或按键不产生重复提交。
- 内容确认提交成功后才清空对应草稿；失败保留文字和上下文，允许修改或重试。
- 无法确定是否提交成功时，明确显示状态待确认，避免引导用户盲目重复发送。
- 各入口可以保留“停止 AI 当前任务”的操作，但它必须与“停止录音”清楚区分。

运行中的默认“补充”、立即打断改向、排到下一轮等送达语义沿用[输入回执 §4.1](../ai-input-receipts/spec.md#41-发送方式)。2026-10-27 用户已确定以下统一映射，不由某个插件自行改写：

| 操作 | 统一入口 | 行为 |
| --- | --- | --- |
| 换行 | Enter | 编辑文字；中文输入法组合或确认候选不触发发送 |
| 正常发送／运行中补充 | Command/Ctrl + Enter，或发送按钮 | 运行中在当前回复或工具批次结束后的模型边界读到；不立即打断 |
| 本轮结束后再做 | Command/Ctrl + Shift + Enter，或发送方式菜单 | 进入会话排队；沿用输入回执 D4，由人开启的下一轮携带，不因此自行新开一轮 |
| 打断并改向 | 明确的“打断并改向”按钮或发送方式菜单 | 不设新增直接触发快捷键；已发生的操作不撤销 |

Tab 保持焦点导航；Esc 用于退出局部菜单等交互，不直接停止 AI。以上运行控制只在当前目标支持且状态允许时可用，不可用时说明原因，不把排队或打断静默改成另一种发送。待回答问题的目标选择仍沿用原交互合同，快捷键不绕过当前目标或审批。中文输入法、录音／转写中的防误发要求同样覆盖新增快捷键。

个人助理的[主对话与后台任务](../proactive-assistant/spec.md#75-主对话持续可用任务在后台执行)使用同一组件：主对话输入发给个人助理，由其区分新工作、原任务补充和即时问答；不会因后台 A 正在执行，就把新输入默认排到 A 后面或改发给 A。明确进入某任务／子代理对话时显示对应接收者，返回后恢复主对话目标与草稿；仅查看或固定任务不换发送目标。以上键位与 D4 的显式消息排队语义保持不变，任务执行排队单独展示。

## 5. 草稿与上下文归属

草稿属于具体入口及对应会话，而不是全局共用一份。

- 切换页面、会话或项目，再返回时，恢复对应的文字和已选上下文。
- 刷新或重启后，恢复已保存的文字草稿；不能宣称恢复尚未转写的录音。
- 语音结果始终回到开始录音时的草稿，不能填入后来切换到的会话。
- 转写期间允许继续编辑文字；识别结果不能覆盖用户新增或修改的内容。
- 用户主动清空或删除草稿后，迟到的转写结果不能自动把内容填回来。
- 上下文已经失效或不可访问时，应明确提示，不能静默以不同上下文发送。

## 6. 本地语音输入

语音输入用于把口述转成可编辑文字，是文字输入的另一种方式。

完整路径为：

**点击麦克风 → 开始录音 → 用户停止 → 本地转写 → 文字进入草稿 → 用户检查、修改并发送。**

具体要求：

- 录音只由用户主动开始，不在后台自动开启。
- 开始录音前明确目标输入框；同一时间只录制一段语音。
- 录音中持续显示录音状态、时长和声音输入反馈，并提供停止与取消。
- “停止”结束录音并开始转写；“取消”放弃本次录音，保留原草稿。
- 录音中及转写中不发送对应草稿，避免发送缺少口述内容的半成品。
- 转写完成后插入文字，保留原有内容；默认接在原光标位置，插入不会覆盖已有文字。
- 若转写期间草稿发生编辑，导致原插入位置不再明确，应提供可确认的插入方式，不猜测并覆盖。
- 连续多次口述可以补充同一份草稿。
- 首期要求停止后获得完整文字；边说边出字不作为首期必备条件。
- 识别内容应尽量忠实于原话，支持中文、英文及中英混说，提供基本标点；不擅自总结、扩写、改写意图或执行口述中的指令。

## 7. 首次使用与本地处理承诺

首次使用时，用户需要知道为什么暂时不能录音，以及怎样完成准备：

- 麦克风权限未开启时，解释用途并提供清楚的开启指引。
- 本地识别资源需要准备时，展示下载大小、进度、完成状态，以及失败后的重试入口。
- 下载由用户明确发起；用户可以取消，稍后继续准备。
- 准备完成后，语音识别在断网情况下仍可使用。
- “本地识别”表示音频在当前使用设备上处理，不发送到远端服务器；不满足这一条件的使用方式，不能标成本地识别。
- 本地识别不可用时明确说明，不静默切换为云端转写。
- 默认不长期保存原始录音；取消或成功完成后清除本次临时音频。
- 转写失败时可暂时保留本次录音供重试，并允许用户主动丢弃。
- 本地转写与发送给 AI 是两个阶段：用户发送后的文字，按所选 AI 服务处理，界面不能让人误以为后续处理也必然离线。

## 8. 异常与恢复

| 情况 | 用户应看到和能够做的事 |
|---|---|
| 麦克风权限被拒绝 | 看到原因与开启指引，继续使用文字输入 |
| 没有麦克风或设备断开 | 明确提示录音不可用或已中断，保留原草稿 |
| 没有检测到有效语音 | 提示未听清，允许重新录音，不插入虚构内容 |
| 转写耗时较长 | 看到仍在处理及取消入口，不显示虚假的剩余时间 |
| 转写失败 | 保留原草稿，提供重试和丢弃本次录音 |
| 切换页面或会话 | 持续可见当前录音或转写状态，结果归属不变 |
| 刷新、关闭或应用意外退出 | 已保存文字可恢复；未完成录音或转写如无法恢复，明确告知 |
| 达到录音时长限制 | 提前提示，到达限制时结束录音并处理已有内容，不静默丢弃 |
| 当前入口不能发送 | 说明原因，保留草稿和已完成转写文字 |

## 9. 验收标准

- **UIV-01**：首页、助手、Coding 的共同控件、状态和键盘行为一致，场景差异可辨认。
- **UIV-02**：中文输入法、多行编辑、长文本粘贴及撤销正常，不误发送。
- **UIV-03**：发送成功、失败及结果不确定三种情况均有明确反馈，无草稿丢失或重复提交。
- **UIV-04**：切换入口、会话、项目及刷新重启后，已保存草稿正确恢复，互不串写。
- **UIV-05**：首次准备、权限申请、录音、停止、转写、修改、发送全流程可完成。
- **UIV-06**：取消录音或转写不破坏已有草稿，也不产生后续自动填入。
- **UIV-07**：转写期间编辑、切换会话或清空草稿，不发生覆盖、误填或被清空内容重新出现。
- **UIV-08**：识别资源准备完成后，断网仍可转写；音频不因识别被发送到远端。
- **UIV-09**：[人工] 中文、英文、中英混说、技术词、停顿和静音经过代表性实测，记录准确性、等待时间及已知不足。
- **UIV-10**：权限拒绝、设备断开、转写失败和中途退出均有明确恢复路径。
- **UIV-11**：亮暗主题、桌面与窄屏下，关键状态清楚，主要操作始终可用，键盘可以完成核心路径。
- **UIV-12**：首页、助理、Coding 通过同一公共组件呈现基础输入；布局冲突由统一合同解决，回执、上下文及领域事实仍从原主人读取，草稿互不串写。
- **UIV-13**：至少两个不同插件通过公共合同／SDK 注册并使用各自的资料选择器、场景控件或提交适配；平台不增加按插件 id 分支，不新增私有依赖或重复名单。
- **UIV-14**：内置与外部插件扩展走相同注册与授权路径；无法访问其他输入实例的草稿或未获准资料，无法借注册自动提交、换目标或批准动作；拒绝本身有实际用例。
- **UIV-15**：重复挂载、多个扩展共存、切会话、停用、卸载与迟到结果不产生重复提交或串写；必需扩展失效阻止当前发送并保留草稿，非必要扩展故障不使基础输入不可用。
- **UIV-16**：扩展前后基本键盘、中文输入法、窄屏与可访问性一致；高保真切片和真实接入分别覆盖资料选择、目标提示、提交失败与恢复。
- **UIV-18**：工作台只有底栏一个输入框：插件页面（含沙箱框架里的 Coding）不再挂自己的输入框，而是把自己登记为收件人（标签、场景控件、命令、`@`、必需项、送达方式、停止与暂停、提交），底栏的框在它在前台时发给它；框里写的字按收件人分草稿，换收件人不串写。（§10.2）
- **UIV-19**：底栏输入框与前台页面的对话栏同宽、同一条左右边，以工作区（不是整个窗口）居中；「发给」是框里脚条上的标签，点开换收件人（这一页的会话、助理新对话或最近的、别的会话），框外不再悬一行。（§10.2）
- **UIV-20**：发给插件会话时，＋ 的来源由工作台以本人身份列出与选取，交给插件的只有选中引用（`MaterialRef`），插件页面列不出结果；收件人登记不能自行换收件人、自动提交或读别的收件人的草稿，拒绝有实际用例。（§10.2）
- **UIV-21**：沙箱框架里的页面用 `window.molisComposer` 挂 AI 输入框时，页面里不画框（它给的根留在页里、隐藏，里面的文本框是底栏框的副本）；这一页在前台时底栏换成它：发给标签是它的名字，提示语、场景控件、命令、送达方式、停止与暂停都是它的；回到别处，底栏回到助理，助理的草稿还在。（§10.3）
- **UIV-22**：底栏发给页面时，人做的事只以数据经框架桥到页面：改一个场景控件、选一条命令、写字（页面的草稿适配器收到）、发送（页面的提交收到）；页面往自己文本框里放字（预填），底栏框里看得到。（§10.3）
- **UIV-17**：所有接入入口按 §4 映射换行、补充、排队与显式打断；实际回执和队列与所选方式一致，排队不自行新开轮次；中文输入法、录音／转写及不支持的状态不误发、不降级为其他方式，Tab 与 Esc 保持原交互职责。

识别准确率、等待时间和单次录音时长上限的具体数值，留待代表性设备与口述样本实测后确定；在这些指标明确并验证前，不宣称语音体验已达到内部完整。

上述新增项均为待实施、待验证的验收要求。实现用例在测试名或注释中引用相应编号；本次只运行文档检查，不以需求落盘代替组件实现或产品实操。

### 10.1 第 10 批定样（用户 2026-11-04）

用户看过可点定样 [`docs/design/unified-input/`](../../docs/design/unified-input/README.md) 后定下，七块都照推荐。前提是统筹 2026-11-04 定的五条（[第 10 批本批核账](../post-anticorruption-roadmap/reference/batches/10.md#batch-10-audit)「已定的点」）；现状盘点见[输入框盘点](input-inventory.md)。

| 块 | 定下的方案 |
| --- | --- |
| 编辑器层 | 附件在框里、写字区上方，每个附件一项，读取中、读完、附不上（带原因与移除）各有样子；恢复的草稿在框里一行写「已恢复没发出的草稿」和时间，带「清空」。长高到上限后在框里滚动（§3、VUX-16） |
| 对 AI 的送达菜单 | 运行中发送按钮写「补充」，旁边 ▾ 菜单列补充（默认）、打断并改向、下一轮再做，各带一句说明和快捷键；从菜单选一种只改这一次的按钮，发出后回到补充，所以打断总要两步。创作台也走这个菜单，不另加按钮（用户 2026-11-04 选定；需求 §4 允许按钮或菜单，统筹 11-04 第 3 条「明确的按钮」按此落实） |
| 新键位的一次提示 | 不在升级时弹说明；只在有人按老习惯在一行字后按 Enter 时，发送键上方出现一次「回车已改为换行。要发送请按 ⌘↵」，用 ⌘↵ 发过一次或点「知道了」后不再出现。发送键的提示里一直写 ⌘↵ |
| 发给谁 | 框上方一行「发给：对象」，切到某项任务或子任务时这一行换名字，带 × 回到默认接收者（与第 03 批连续对话定样一致）。手机（≤ 600px 宽）和矮窗口（≤ 560px 高）里没人写字、没有附件也没有状态时，整个输入框收成一行：＋、对象缩成框内左侧的小标签、输入框、发送；一开始写、有附件或有状态就长回多行（用户 2026-11-08 定） |
| 状态 | 发送中、运行中、失败、待确认、被丢弃、离线写在框里、发送键上方一行，图标加整句，能做的事给按钮；不只靠颜色，也不只靠会消失的提示 |
| 插件扩展的入口 | 左下角一个 + 菜单，按附件、资料、插件提供分组，写出是哪个插件给的；/ 和 @ 在框里随时可用，弹出同一套分组；Esc 只关菜单 |

### 10.2 一个输入框（用户 2026-11-10 定「甲」）

第 11 批走查时用户看过 Coding 的页内输入框与底栏助理输入框上下两个框、底栏框以整个窗口居中不与任何东西对齐，要求「Coding 里的对话框和助理入口合并」，看过定样稿 [`prototype/one-input.html`](prototype/one-input.html)（在 Coding 会话里静止一行、写字时长高与换收件人、深色）后选了**甲：共用一个输入框**——Coding 会话仍是 Coding 的（任务记录、审查、任务图归 Coding），只是不再有自己的输入框；**不是**乙（把 Coding 会话并成助理的会话，那会改事实主人）。本条取代 §10.1「发给谁：框上方一行」的写法。

| 块 | 定下的方案 |
| --- | --- |
| 一个框 | 底栏中间的输入框是工作台唯一的输入框；插件页面不挂自己的输入框，登记为收件人，前台是它时框就发给它 |
| 对齐 | 框与前台页面的对话栏同宽、同一条左右边，以工作区居中；页面没有对话栏时用工作区的阅读宽度 |
| 发给 | 框里脚条上的标签（图标与名字），点开列这一页的会话、助理（新对话、最近的）与别的会话；静止时一行：＋、发给、提示语、场景控件、发送 |
| 场景控件 | 跟着收件人：发给 Coding 会话时是任务方式与模型（运行中加暂停、停止）；发给助理时是助理自己的 |
| 下一轮带上 | 插件会话选过的材料、方法等在脚条上以小标签（如「材料 2」）出现，点开是原来的选择 |

做法分四步，每步可单独合入：

1. **O1 对齐与发给入框**（只动工作台外壳与输入组件）：底栏框按前台工作区与对话栏定位与定宽；「发给」从框外一行改为脚条上的标签。
2. **O2 页面收件人合同**：页面（含沙箱框架，经框架桥）登记收件人与它的场景控件、命令、`@`、必需项、送达方式、停止、暂停与提交；底栏框按前台页面换收件人，草稿按收件人分；＋ 的来源由工作台列与选，只把选中引用交给页面。公开合同与安全不变量（`S-composer-source-call` 第 5 条）随这一步改。
3. **O3 Coding 换成收件人**：删掉 Coding 页内的输入框，改为登记收件人；下一轮带上的选择在脚条上以小标签出现。同一步删掉 Coding 页里重复的会话列表：工作台侧栏已经列出 Coding 的会话时，页里不再画自己那一栏 240px 的列表（`plugins/native/coding/src/ui.ts` 的 `renderCodingDirectory` 在页内的那一处）；侧栏收起、窄屏与手机上仍要能回到列表（用户 2026-11-10 定并入 O3）。
4. **O4 发给菜单**：列这一页的会话、助理新对话与最近的、别的会话。

第 11 批之后做的框架桥（分支 `batch/11-frame-sources`，框内输入框经父页列来源）在 O2 之后用不上：Coding 不再在框里挂输入框，来源由工作台的框直接列。它暂不合入，O2 定稿时决定删掉还是留给以后在框里挂输入框的插件。

### 10.3 O2 落地：页面收件人经框架桥（2026-11-10）

不新加公开合同：页面照旧调 SDK 的 `window.molisComposer(root, options)`、拿到同样的句柄。框架里（工作台窗格中、不是侧栏视图与目录）的 AI 输入框由框架桥接到底栏，桥的两头在 `apps/workbench/src/browser/plugin-frame/composer-child.ts` 与 `composer-parent.ts`，消息形状在 `composer-bridge.ts`：

| 方向 | 过桥的是什么 |
| --- | --- |
| 页面 → 底栏 | 页面此刻的状态（收件人名字与图标、提示语、送达方式、暂停的字、场景控件与命令——不带函数、必需项、运行中、等待原因）；页面往自己文本框里放的字；页面要聚焦、插入、加文件、按发送 |
| 底栏 → 页面 | 人在底栏做的事：改控件、选命令、停止、暂停、发送、`@` 查询、读文件，草稿经页面自己的适配器读写；底栏框的字（给页面那个隐藏的文本框） |

- 底栏只在**前台**有这一页时换给它：聚焦窗格里看得见的那个框架；助理的对话面板开着（或助理在自己的标签页里）时底栏仍是助理的。分屏里另一个窗格是独立的工作台文档，没有底栏，那里的页面照旧画自己的框（已知限制）。
- 页面的字只当文字画（底栏的输入组件逐字转义），图标只认平台图标名，页面缺的字由底栏的补上；页面的「当前对象」一律算这个插件自己的。
- 来源仍不对框架里的页面开放：底栏发给页面时 ＋ 不列来源（`S-composer-source-call` 第 5 条不放宽）。§10.2 第 2 步写的「来源由工作台列与选、只交选中引用」与 UIV-20 留到「Coding 接平台来源」那一步（第 11 批之后紧接着做，用户 11-10 定）一起开。
- 用对话 id 记草稿（`draft: { conversation }`）的 AI 输入框暂不过桥，照旧画在页里；今天框架里只有 Coding 用 AI 输入框，它用自己的适配器。
- 分支 `batch/11-frame-sources`（框内输入框经父页列来源）用不上了：工作台窗格里的页面不再画框。不合入，等用户同意后删。
