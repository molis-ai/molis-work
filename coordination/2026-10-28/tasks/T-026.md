## 1. 背景

长会话的下一轮从摘要起跑时，摘要由模型写；写不出来，宿主用自己的记录式摘要顶上，六条仍然有效的补充都得带着（`specs/ai-input-receipts/spec.md:1581` 的 RCPT-102，证据列要求「故障注入生产摘要接缝」）。`tests/coding-history-requirements.test.ts` 已经在真 HTTP、真 Agent Host、装好的 SDK 上证明了两种失败：provider 回 400（`:30`）、回空正文（`:32`）。摘要真的超时没有用例：`Summary` 只有 `"model" | "error" | "empty"`（`:20`）。相邻的 `tests/coding-history-summary-http.test.ts:34-40,94-97` 的「超时」是桩让起草动作直接抛 `ActionError("actions.timeout", …)`，也没有走生产的计时器。BL-311 要的就是让生产的两分钟截止时间真的到点。

BL-311 只写了一个计时器；main 上有两个，以代码为准：

- `apps/local-host/src/model-draft.ts:19`：`createExecutionLifetime` 设两分钟，到点以 `ActionError("actions.timeout", "起草超过两分钟，已停止，可重试")` 中止；计时器是 `packages/plugin-sdk/src/execution-lifetime.ts:38` 的 `setTimeout`。
- `model-draft.ts:28` 又把 `timeoutMs: 120_000` 交给 `apps/local-host/src/host-complete-text.ts:174,180`，那里是 `AbortSignal.timeout(timeoutMs)`，由 `waitForText`（`:234-241`）在信号上拒绝。

两者同为 120 000，`setTimeout` 先建、先到。生产里用户看到的是第一句；只补第二个，`digest.problem` 会变成 `host-complete-text.ts:222` 一带的「模型请求失败或超时，材料已保留，可重试」，证明的就不是生产的路径。

到点之后的链：`plugins/native/coding/src/history-digest.ts:144` 等 `draft`，失败时 `:145` 先 `beforeWrite()`，`:146` 转 `fromRecords`（`source: "records"`），不记用量（`:148` 只在有答案时记，写入在 `start-round.ts:205`）。`POST …/runs` 的响应带 `digest: { source, problem }`（`start-round.ts:250`）。会话读取的 `usage_total.digests` 只在 `calls` 大于 0 时才有（`plugins/native/coding/src/session-window.ts:86-88`），读法见 `tests/coding-history-summary-http.test.ts:101-102`。

缺口在 main 上仍在：`git grep -n "timeout" tests/coding-history-requirements.test.ts` 只有两处用例的 `{ timeout: 60_000 }` 选项。

## 2. 目标

1. `RAC-1340`：第二轮的摘要请求被挂住，直到生产的两分钟截止时间（用例里把它缩短）到点，这一轮用备用摘要起跑：响应 `digest.source` 是 `"records"`；本轮的 provider 请求是一次摘要尝试加本轮自己的一次调用，没有更多；本轮第一次请求带齐六条补充（来源、顺序同 `assertCarried`，`:72-81`），并写明「的记录由宿主根据执行记录整理」。
2. `RAC-1341`：provider 在到点之后才回的摘要什么也不改：等过迟到的时间后，请求总数不变，没有请求带那份摘要的标记，`usage_total.digests` 不存在。
3. 补丁只在这个用例里生效，用例结束后原函数回来。

## 5. 做法

**已定（main 上核过）**

- 形状照现有的 `twoRounds`（`tests/coding-history-requirements.test.ts:22-70`）：在摘要分支（`:29-33`）里加 `"timeout"`：返回一个 Promise，等一段「迟到时间」后才解析成 `cogniaModelResponse(…)`，正文带一个只在迟到摘要里出现的标记（例如 `LATE-SUMMARY-MARKER`）。夹具的 `respond` 可以是异步的（`tests/fixtures/coding-product-host.ts:17`）；夹具的 fetch 桩不把 `init.signal` 交给 `respond`（`:40-48`），所以截止时间不靠 fetch 被中止，而靠 `waitForText` 在信号上拒绝（`host-complete-text.ts:234-241`）。迟到的响应没人读，这正是 `RAC-1341` 要的。
- 补丁装在 `round = 2`（`:61`）之后、第二次 `start(…)`（`:62`）之前，用 `t.mock.method`（`TestContext` 已 import，`:5`），用例结束自动还原。只改参数恰好是 `120_000` 的调用，其余原样转给原函数：夹具的 `ended()` 用 15 000（`coding-product-host.ts:72`），用例自己的轮询用 20（`:47`），都不能动。
- 断言顺序照 error 用例（`:94-101`）：`summaries.length === 1`、`later.length === 2`、`reviews.length === 1`，再加 `digest`、`assertCarried`、记录式摘要的开头。
- 响应里的 `digest`：`start` 辅助函数（`:42`）的泛型要加上 `digest?: { source: string; problem?: string }`。
- 用量：`f.call(project, coding + "/sessions/" + id + "?window=20")` 读 `usage_total`，形状读 `tests/coding-history-summary-http.test.ts:101-102`。
- 文件头注释（英文）写明 `RAC-1340`、`RAC-1341`、RCPT-102、QA-010 和 BL-311。测试名以编号开头。

**【方案】里要回答的问题**（先把用例写出来在本机跑一遍，把结果写进去，再等批）

1. 哪几个调用要补：在 `Summary = "timeout"` 的运行里，把参数为 120 000 的 `setTimeout` 与 `AbortSignal.timeout` 调用都记下来（谁调的，栈顶两三帧）。报告补丁要覆盖哪几个，才和生产一样让 `model-draft.ts:19` 的那个先到点；写出补丁的规则（按参数、按调用次数、还是按时间窗）和理由。`digest.problem` 在你的补丁下实际是哪一句。
2. 到点值与迟到值：BL-311 写 300 ms。机器慢时摘要请求可能还没走到 fetch 桩、到点就先到了，「恰好一次摘要尝试」会偶发。写出你量到的摘要请求到达桩的延迟，和你选的到点值、迟到值；或者让到点计时从「桩看见摘要请求」之后才起。连跑 5 次的结果。
3. `digest.problem` 要不要写进断言：稳定才写，写出实际字符串。
4. 两个编号各一个 test（各跑一次 `twoRounds`），或一个 test 名里含两个编号：选一个并说理由。
5. 把用例弄红一次的办法：例如把迟到时间缩成 0，让摘要先答，`digest.source` 变成 `"model"`，看第一条新断言红；写出你打算怎么做。
