# 仓库系统性整理 Prompt

请对当前仓库开展一次系统性的架构、功能、实现与体验整理，完成必要修复、重构、清理、验证和开发规范沉淀。

仓库已经经过多轮功能迭代。本次不仅检查“代码是否遵守现有架构”，还要判断现有架构是否合理、各功能是否完整、开发契约是否落实、测试是否仍对应当前预期，以及真实用户使用是否顺畅。

本次需要回答并处理：

- 模块划分本身是否合理？
- 包、文件、类、方法和实现逻辑是否放在正确的位置？
- 调用链、数据、状态、权限和事件是否清晰一致？
- 各插件是否实现完整，并遵守规定的协议与接入要求？
- 新能力是否能按机制被宿主、用户、MCP 和 AI 发现并使用？
- 哪些能力应共享、抽取或下沉 Prologue？
- 前端是否有质感、简约合理、动线清晰、引导到位？
- 历史代码、重复路径、失效测试和过时规范是否清理到位？
- 单测、集成测试和端到端测试是否表达当前有效的预期行为？
- 如何通过手册、Skill 和必要门禁，减少后续开发再次偏离？

交付必须包含实际修复与验证，不能只给建议清单。完整清点全仓，按风险深入检查；不做无依据的大重写，不以目录更整齐、抽象更多或测试全绿代替任务完成。

## 1. 确认现场、授权范围和任务归属

读取适用的仓库规则、架构规范、协议、已有 spec 和开发 Skill，检查分支、工作树、已有修改及其他正在进行的任务。

已有任务负责的范围，与负责人交接具体问题、证据和验收要求，避免重复修改；无人负责的部分由你完成。交接不等于已修复，记录实际状态与负责人。

保护现有成果，不重置工作树，不覆盖无关修改，不提交混杂的全量改动。遵循当前协作规则安排并行，共享核心和存在依赖顺序的修改串行处理。

建立或复用一份简洁总 spec，记录目标、范围、事实来源、模块 owner、实施顺序和验收。不要新增大量重复的进度文件和清单。

常规可逆修复自主完成。涉及产品语义、公共契约或重大迁移策略的实质变化，先提供具体方案与取舍，同时继续其他独立工作。不自动扩展到发布、部署或无关产品开发。

## 2. 建立完整清单与当前预期行为基线

清点全部 App、Host、Plugin、业务 Module、共享包、后台任务、外部协议和 SDK 接入。

对每项能力明确：

- 用户场景、实际入口和当前成熟度；
- 所属模块、主要依赖和数据 owner；
- 注册、开放、发现和调用方式；
- 关键调用链及已有测试；
- 与其他能力的重叠、替代和依赖关系。

区分生产使用、实验、部分实现、已弃用和待确认能力。特别检查新旧实现是否并存、消费者是否完成迁移、旧路径是否仍有真实用途。

结合当前已接受的需求、有效 spec、产品协议和公开契约，明确功能现在应该如何工作。

当前实现、测试和历史文档都是证据，任何一方都不能自动成为唯一正确答案。发生冲突时，区分实现回归、测试落后、文档过时和需求不明确。

清点要完整，深查按风险安排。未深入或无法验证的范围必须明确标注。

## 3. 审查模块划分、代码放置与调用链

不要默认现有架构正确。结合业务能力、变化原因、生命周期、数据归属和协作成本，检查：

- 每个模块是否职责清晰；
- 是否把完整能力切得过碎，产生过量透传和协调；
- 是否把不同变化原因或生命周期的能力混在一起；
- 是否存在名义独立、实际无法独立理解和验证的模块；
- Plugin、Module、Host、基础设施和 SDK 的边界是否合理；
- 是否需要合并、拆分、移动、下沉或删除某些模块。

沿真实 UI / CLI / MCP / HTTP / 后台任务入口追踪：
输入 → 身份与权限 → 用例编排 → 领域逻辑 → 存储或外部服务 → 事件与结果 → 消费者反馈。

检查包、文件、类、方法和函数是否属于正确 owner，尤其关注：

- App/Host 混入业务规则；
- UI 承担领域状态转换；
- Store/Repository 混入网络、模型调用和产品决策；
- Plugin 重复实现通用运行能力；
- 跨模块直接 SQL 或绕过公共接口；
- 循环依赖、反向依赖、内部实现泄漏；
- 无意义的包装、透传、重复转换和重复校验；
- 同一能力不同入口的行为、错误和权限不一致。

每项调整说明真实问题、影响、新边界和兼容成本。文件长、层次多或存在相似代码不能单独成为重构理由。

避免万能 Service、无实际复用的抽象和只搬代码不改善职责的拆分。架构规范过时的，同步修正规范。

## 4. 核对开发契约、能力注册与协议遵循

从有效规则、协议定义、类型与 Schema、注册机制、开发 Skill 和测试中，提取必须遵守的开发要求。

每项要求明确来源、适用范围、行为、实现位置和验证方式。区分强制要求、场景性要求和建议，不把偶然实现当作全仓规范。

检查每项应开放的能力是否：

- 注册到规定的能力目录、Action 或工具系统；
- 按要求提供 MCP、HTTP、CLI 或其他入口；
- 具有准确的描述、输入输出 Schema、错误与权限声明；
- 能被真实发现、选择和调用；
- 与 UI 共用核心业务路径和授权规则；
- 在禁用、卸载、升级或权限变化后正确更新可用状态。

沿“定义 → 注册 → 发现 → 调用 → 授权 → 执行 → 返回”验证。注册表中存在记录不代表接入完成。

检查 manifest、协议、版本和生命周期声明是否与真实行为一致，是否通过私有捷径绕开统一入口，协议变化是否同步消费者。

项目要求通过 MCP 等渠道开放的能力不得遗漏，但内部 helper 和所有类方法不应机械暴露。

## 5. 审查自动发现与平台扩展机制

检查新增插件是否通过规定机制接入，还是需要在多个互不关联的位置手工维护名单、路由和映射。

追踪：
安装或启用 → 校验 → 注册 → 宿主加载 → 目录更新 → 消费者发现 → 上下文与权限筛选 → 调用 → 结果与事件进入产品。

检查：

- 插件与能力元数据是否有明确权威来源；
- 是否存在重复静态清单和遗漏风险；
- 哪些入口应自动生成，哪些需要有意设计；
- 运行中安装、启用、升级是否正确刷新；
- 禁用、卸载后旧能力是否消失；
- 描述、Schema、版本或权限变化后缓存是否失效；
- 不同项目、账号和权限下目录是否隔离；
- 重复名称、版本不兼容、加载失败和部分加载如何处理；
- 单个插件失败是否不必要地阻断其他插件；
- 发现失败是否能定位环节。

如果项目承诺“注册后自动发现”，就验证实际消费者可见、可调用。明确可发现、可调用和被合理选用是不同验收点。

不要机械追求所有内容零配置；保留必要的装配和授权，清理无必要的重复接线。

## 6. 逐插件审查实现完整性与组合使用

对每个插件检查：

- 用户任务是否形成完整闭环；
- 是否有占位、半实现、不可达或失效功能；
- 注册、协议、事件和对外入口是否落实；
- 输入、输出、持久化和产物是否一致；
- 是否越过领域 owner 或依赖其他插件内部实现；
- 是否重复已有能力，或遗漏应共享的技术能力；
- 安装、初始化、配置变化、升级、禁用和卸载是否正确；
- 权限撤销、失败、取消、并发和恢复是否完整；
- 空数据、首次使用、依赖缺失和无模型配置时是否有合理路径；
- 测试是否覆盖真实行为。

横向比较同类插件，找出重复框架、语义和行为不一致，同时保留合理的业务差异。

按真实用户场景组合多个功能，检查上下文、数据和产物能否继续流转。逐模块通过不能代替组合使用验证。

根据适用范围核对平台接入：
导航、搜索、命令入口、设置、连接管理、权限、通知、活动记录、执行历史、产物预览、后台任务、取消和恢复。

不是所有功能都必须接入全部位置，但需要的接点必须完整。

## 7. 审查数据、状态、事件和生命周期

明确每类业务事实的唯一 owner，检查数据库、内存、缓存、文件、事件投影和 UI 是否形成多个冲突的权威来源。

检查：

- 状态机及合法转换；
- 用户、账号、项目、工作区、会话和插件身份传递；
- 多窗口、多进程和并发任务下的一致性；
- 事务、幂等、重复请求和部分成功；
- 取消与完成、删除与执行、权限撤销与副作用之间的竞争；
- 重试、重启和恢复是否重复执行或丢失状态；
- 删除、卸载后的孤儿数据、文件、凭据和任务；
- 缓存失效、历史引用和产物读取。

根据业务需要审查事件：

- 哪些变化必须产生事件，由谁发出；
- 事件是业务事实、进度还是诊断信息；
- 名称、载荷、标识和版本是否规范；
- 数据提交与事件发布的时序是否正确；
- 回滚、重试、乱序和恢复时是否符合契约；
- 消费者是否实际响应；
- 订阅是否正确清理和恢复。

验证“操作 → 状态 → 事件 → 消费者结果”，不能只断言 emit 被调用。按实际需要设计可靠性，不为每个函数造事件或无依据引入复杂消息系统。

明确订阅、定时器、连接、进程、后台任务和缓存的创建、持有、释放与恢复责任，验证重复启动、退出和重启。

## 8. 专项整理 AI 能力与 Prologue

清点全部生产 AI 入口：AI 对话、单次文本、结构化输出、图片、OCR、音频、工具调用和 Agent 执行。

核对实际使用的 Prologue 版本、源码和公开 API，区分：

- SDK 已支持但没有正确使用；
- 适合模块内部整理；
- 适合产品内共享；
- 与业务无关、契约稳定，适合下沉 Prologue；
- 属于产品身份、领域语义、权限政策或体验决策，应留在业务层。

项目要求经 Prologue 的 AI 能力，必须检查真实生产调用链，不能只看 import。

核对模型与凭据、上下文、工具、身份、权限、审批、副作用前检查、预算、usage、事件、超时、取消、持久化、恢复和产物发布。

检查供应商直连、旧执行器和绕过约束的 fallback；检查 Runtime 结束、权限撤销或配置变化后是否仍产生副作用。

能力被注册成 MCP 或工具，还需验证 AI 能否理解和正确选择：

- 名称、描述、约束及副作用是否清楚；
- 输入输出是否稳定、可组合；
- 工具是否严重重叠；
- 项目、账号和权限上下文是否正确；
- 是否支持合适的按需发现，避免无差别塞入全部工具；
- 失败结果是否可处理；
- 结果是否关联真实产物和执行记录。

自动发现不能绕过授权。按场景使用 SDK，不强行把所有 AI 请求套进同一种 Agent 循环。

每项共享或下沉说明消费者、契约、依赖方向、迁移顺序和验证。完成消费者切换，清理替代路径，避免两套执行框架长期并存。

跨仓修改前确认 SDK 工作区及其他负责人范围。

## 9. 审查前端质感、交互和用户动线

读取项目设计规范及适用的前端 Skill。以真实页面和操作判断，不以“能打开、能点击”作为完成标准。

检查：

- 信息层级、布局、字体、间距、色彩、图标和动效是否协调；
- 是否简约而不隐藏必要信息；
- 信息密度是否适合场景；
- 主次操作和危险操作是否明确；
- 是否有重复卡片、过多边框、无效留白和不必要层级；
- 页面、组件、术语及交互是否一致；
- 弹窗、抽屉、标签页和独立页面是否使用合理；
- 窄屏、长文本、滚动、焦点、键盘及基本可访问性是否正常；
- 加载、空状态、失败、部分成功、权限不足和离线状态是否完整；
- 是否存在闪烁、布局跳动、输入丢失和重复提交。

按用户路径验证：
找到功能 → 理解用途 → 完成前置条件 → 开始操作 → 确认结果 → 继续下一步。

检查首次引导、示例、默认值、空状态行动提示，以及配置或授权完成后能否返回原任务并保留上下文。

验证跨页面、跨插件时项目、账号、选择和草稿是否保留；检查返回、取消、关闭、撤销和再次进入是否符合预期。

熟练用户应有合理快捷路径。引导不等于堆说明文字，质感不依赖装饰，不能把所有功能都改成卡片或 Dashboard。

检查前后端状态是否一致，明确区分“请求已接受”“执行中”“完成”和“产物已发布”。验证乐观更新失败、多窗口、刷新和事件重连后的状态。

通过真实界面、截图和交互验证视觉与动线，纯结构断言不能证明体验质量。

## 10. 审查配置、安全、性能、升级和发布

配置与安全：

- 默认值、来源和覆盖优先级是否统一；
- 配置变化如何影响当前和后续执行；
- 凭据轮换、撤销、删除和账号切换是否一致；
- 敏感内容是否泄漏到日志、事件、错误或产物；
- 外部输入、路径、URL、重定向、进程参数和文件访问是否在真实边界校验。

性能与诊断：

- 启动、常用页面和关键路径是否明显阻塞；
- 是否存在重复查询、重复初始化、无界扫描、队列或全量刷新；
- 大数据、长会话和长期运行是否造成资源增长；
- 超时、取消和背压是否实际生效；
- 错误是否保留原因和必要关联信息；
- 是否通过吞错、假成功或无限重试掩盖故障。

升级与发布：

- 使用真实旧数据和旧配置验证迁移及失败恢复；
- 检查源码、构建产物和发布包是否一致；
- 必需资源、Schema、迁移、脚本和运行时依赖是否齐全；
- 开发缓存、历史归档和重复依赖是否误入产物；
- 新安装、升级和启动是否使用正确版本；
- 是否依赖开发机特有的全局工具或路径。

所有优化和保障机制必须对应实际问题，不能先引入复杂设施解决假想风险。

## 11. 清理无用、重复和过时内容

检查死代码、重复实现、旧入口、废弃配置、冗余依赖、过期兼容层、失效测试、旧文档和重复发布资产。

删除前核对动态加载、插件注册、构建脚本、迁移、公共 API 和外部消费者。没有普通 import 不等于无用，有测试引用也不自动说明必须保留。

明确可删除的直接清理，同步导出、依赖、引用、测试和文档；证据不足的列为候选并说明原因。

整理重复术语、概念和接口命名，避免同一能力多种名称。检查已删除或未完成的功能是否仍被文档和界面宣称可用。

## 12. 系统审查测试与预期行为是否对齐

审查单测、集成测试、端到端测试、fixture、Mock 和快照本身，不只是运行测试并修到全绿。

发现实现与测试不一致时，区分：

- 实现违反有效契约，属于产品回归；
- 需求已经明确改变，测试尚未更新；
- 测试设计错误；
- 新行为缺少覆盖；
- 预期行为不明确，需要决定。

不能默认测试错了，也不能把旧断言当成永远正确的需求。

检查：

- 测试是否调用当前生产入口，还是退出使用的旧实现；
- Mock 是否符合真实接口、事件、错误和时序；
- 是否因过度 Mock 绕过注册、发现、权限或持久化；
- fixture 是否具备相关生产约束；
- 是否依赖旧默认值、旧标识、旧状态或静态插件列表；
- 是否读取过期构建产物；
- 快照是否只是在保存历史输出；
- 当前生产路径是否反而缺少保护。

历史迁移 fixture 必须保留真实旧数据，不能为适配当前默认值改写历史样本。

检查测试是否真正验证返回、错误、持久化、事件、副作用、权限、隔离和恢复。识别：

- 只断言不抛异常、字段存在或 Mock 被调用；
- 用被测算法生成预期结果；
- 只测内部方法，绕过真实入口；
- 实现明显错误仍能通过；
- 过度绑定实现细节；
- 为适应代码而持续放宽断言；
- 测试名称声称覆盖全流程，实际只验证局部结构。

处理失败前先区分产品回归、预期变化、测试缺陷、环境问题和时序不稳定。不得通过跳过、吞错、无依据延长超时或删除关键断言获得全绿。

检查 skip、todo、隔离名单、暂停测试组和 CI 排除项，判断原因是否仍有效。具备稳定执行条件的重要回归应恢复。

每项改动明确哪些行为保留、哪些允许改变、哪些测试更新或删除、哪些关键覆盖需要补充。测试保护行为与协议，不冻结偶然实现，也不为机械低影响改动凑数量。

## 13. 编写 Prologue AI 开发手册和配套 Skill

以 Coding App 为具体参考，先审查并修正其实现，再提炼可复用实践，不把现状自动当作标准。

开发手册基于最终代码，包含：

- 产品、Host、Plugin、领域模块和 Prologue 的职责；
- 用户触发、AI 执行、工具副作用和产物落地的调用链；
- 新增 AI 能力的最小完整示例及实际文件位置；
- 模型、凭据、上下文、工具、权限、审批、预算和 usage；
- 能力注册、MCP 等入口与事件接入；
- 流式结果、结构化输出、错误、取消、超时和恢复；
- SDK、宿主和业务分别承担什么；
- 常见错误、测试方法和验收要求。

区分通用要求、Coding 专属逻辑和其他 AI 场景。示例应与实际 API 一致并经过适当验证，未支持能力不能写成已实现。

查找现有 Skill，优先整合，按适用编写规范创建或完善 Prologue AI 开发 Skill。

Skill 写清触发条件、必读材料、能力归属判断、实施步骤、契约、验证与验收。手册解释架构和示例，Skill 指导执行，通过链接关联，避免复制导致漂移。

更新实际使用的插件开发 Skill，使其覆盖：
模块 owner、协议、注册、发现、对外入口、权限、事件、数据、生命周期、前端体验、测试、文档和发布资产。

新增或修改 AI 能力时，明确要求读取 Prologue AI Skill。纯非 AI 功能不加载无关内容。

核对路径、链接和触发说明，使用代表性开发场景走查。

## 14. 按依赖实施，并用真实路径验证

按影响和依赖顺序推进：
真实 bug 与权限/状态问题 → 契约和接入遗漏 → 模块边界 → 共享与 SDK 提取 → 清理 → 手册和 Skill。

每项改动对应具体问题、证据和验收，优先完成小而完整的路径，不积累大量未验证重构。

按风险执行类型检查、架构门禁、定向回归、构建和真实集成；重大跨模块调整完成后执行必要整体回归。

代表性端到端场景包括：

- 首次安装、配置、授权、发现和使用；
- 同一能力通过 UI、MCP 等入口调用；
- 跨插件协作、事件传递和界面反馈；
- AI 发起、工具选择、审批、执行和产物读取；
- 中途取消、失败、重启和恢复；
- 权限撤销、账号或项目切换；
- 历史数据升级和插件生命周期变化。

选择现有代表性插件，或可移除的测试插件，通过正式扩展路径验证注册、加载、发现、调用、事件、升级、禁用和卸载。不能在测试中直接注入对象，绕过需要验证的机制。

并发问题制造真实交错，重试验证无重复副作用，失败和取消验证不会继续发布结果。

将稳定、重要且适合自动验证的要求纳入现有门禁或必要回归；依赖业务判断的规则写清方法和示例，不把所有要求变成脆弱的字符串检查。

明确区分源码审查、Mock、真实集成、产品实操和用户验收。已有有效证据不机械重跑，未验证范围不得隐藏。

## 15. 最终交付与完成标准

交付一份可追溯的结果，包含：

- 功能、插件和模块清单及审查状态；
- 按严重程度列出的问题、证据、根因与处理结果；
- 模块划分判断和修复后的关键调用链；
- 逐插件的实现、契约、接入与体验结论；
- 数据、状态、事件、权限和生命周期结论；
- 已下沉 Prologue、产品内共享、保留业务层和暂缓的能力及理由；
- 新旧实现切换、代码与依赖清理结果；
- 测试预期修正、回归修复、覆盖补充及仍未验证范围；
- 前端体验改进与真实操作证据；
- 开发手册、Prologue AI Skill 和插件开发 Skill 链接；
- 验证结果、限制、未关闭事项及明确负责人。

区分“已确认、推断、未验证”和“已完成、在途、待决”。建议不冒充修复，交接不冒充关闭，测试全绿不冒充产品完整。

持续完成已授权且证据充分的工作，不在首次扫描、建议清单或部分修复后提前结束，也不无限扩展建议性重构。

最终标准是：
模块职责合理，代码归属清楚，开发契约落实，能力能被正确发现和使用，跨功能行为一致，用户动线顺畅，失败可恢复，测试符合有效预期，文档与代码一致，并且后续开发有可执行的依据。
