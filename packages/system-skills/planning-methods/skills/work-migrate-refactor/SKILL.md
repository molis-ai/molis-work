# 迁移与重构

先建立兼容和回退边界，再分段替换并验证。

适用于：数据迁移、架构重构、系统替换。

## 规划路径

1. 盘点现状和兼容契约
2. 定义目标状态与迁移批次
3. 准备回退和双向验证
4. 分段切换并清理旧路径

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| baseline_contract | 现有契约 | 哪些行为和数据必须保留？ |
| migration_path | 迁移路径 | 每一批如何进入、验证和退出？ |
| rollback | 回退 | 失败时怎样恢复到可信状态？ |

## 依赖规则

| rule_id | statement | direction_hint |
| --- | --- | --- |
| cutover-after-proof | 切换依赖迁移验证和可用回退。 | cutover depends_on validation and rollback |
| cleanup-after-cutover | 旧路径清理依赖新路径已经切换、观察并确认可回退边界。 | legacy cleanup depends_on proven cutover |

## 完成证据

- 迁移前后对账
- 回退演练或可复现步骤

## 收口检查

- 旧路径明确退出
- 没有静默丢失兼容行为

## 常见误拆

- 边改边迁没有基线
- 只迁成功路径
- 旧逻辑永久并存

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
