## 主干基线复现的问题（以下保留原反例）

### P1：工作流把执行中的拒绝误认为“从未执行”，导致重复写入

位置：[actions.ts:329](../../plugins/native/workflows/src/actions.ts)。

`runActionStep` 仅凭 `actions.forbidden`、`actions.provider_changed` 等错误码就清除 `attempted_at`。这些错误也可能由已经执行的处理器或其下游动作抛出，并不能证明之前没有副作用。

复现：通过正式 PluginRuntime 安装陌生工单插件，工作流动作先创建工单，再以 `actions.forbidden` 报告下游拒绝。第一次调用失败后，持久化的 `pending.attempted_at` 被清空；第二次普通“继续”（没有 `retry_action: true`）再次执行，工单从 1 条变为 2 条。

建议：执行核心提供可信的“尚未进入处理器”结果标记，或保守地保留已经发起的调用状态。处理器返回的错误码不能解除结果未知状态；部分成功须要求核对结果和明确重试。

证据：复现脚本（`/tmp/action-main-review/workflow-partial.test.ts`）、结果日志（`/tmp/action-main-review/reproductions.log`）。

### P1：MCP 调用准备期间撤权，工具仍被实际调用

位置：[connector-mcp-actions.ts:69](../../apps/local-host/src/connector-mcp-actions.ts)、[connector-mcp.ts:368](../../apps/local-host/src/connector-mcp.ts)。

动作只在进入连接层之前执行 `caller.beforeEffect()`。后续还会等待连接、认证和 `tools/list`，最终 `tools/call` 前没有再次检查该动作的当前授权。连接仍有效不代表下游调用者仍有权限。

复现使用正式 `authorizeMcpActions` 和持久化 MCP grant：本地真实 MCP 服务处理 `tools/list` 时撤销该客户端的精确授权，随后仍收到一次 `tools/call`，调用返回成功。

建议：把原调用的检查传到连接执行层，在异步准备结束、发出实际工具请求之前再次执行，并保持撤权错误的分类。资源读取也需按同一原则核对当前读取权限。

证据：复现脚本（`/tmp/action-main-review/mcp-boundaries.test.ts`）、正式授权复现日志（`/tmp/action-main-review/mcp-grant-reproduction.log`）。

### P1：上游 MCP 工具合同变更，旧版本引用仍可执行

位置：[connector-mcp.ts:369](../../apps/local-host/src/connector-mcp.ts)。

目录登记时计算 schema 指纹并分配版本，但调用时只检查当前列表中是否还有同名工具，没有把当前 schema 与登记的准确版本比较。只有再次显式发现工具才会更新目录版本。

复现：登记 `echo@1` 并授予精确权限，上游随后改变输入 schema；调用旧引用时虽然重新取得了新列表，仍以 v1 成功执行一次。保存的工作流、Agent 选择和客户端授权因此可能悄悄执行已经变化的合同。

建议：调用时携带已登记合同的指纹与连接身份，在实际派发前比对当前定义；变更必须使旧引用失效，重新登记新版本，不能继续以旧授权执行。

证据与上一项共用脚本；日志中 `scenario: schema change`、`refVersion: 1`、`callCount: 1`。

### P2：不支持的 MCP schema 被静默替换成“任意对象”

位置：[mcp-tool-actions.ts:29](../../apps/local-host/src/mcp-tool-actions.ts)。

`mcpInputSchema` 捕获编译错误后返回 `{ type: "object" }`，丢掉必填项、字段和约束，目录仍可显示可用。两类 MCP 适配器均使用此函数。

复现：带 Draft 2019-09 声明、要求 `message` 的合同进入适配器后只剩 `type: object`；注册到真实 ActionService 后可用性为 true，空对象成功到达处理器。工作流的字段发现也会因此缺失。

建议：保留原合同，明确显示不支持原因并禁止调用；或实现经过验证的方言支持。不能以静默放宽输入的方式兼容。

证据：脚本（`/tmp/action-main-review/schema-fallback.test.ts`）、日志（`/tmp/action-main-review/schema-fallback.log`）。

### Feed 与自动拉取闭环（同日后续）

在原 owner 中贯通 Action dispatcher 的 `beforeEffect`，并同时检查来源是否暂停、删除、改配置或换账号。首个拒绝在该次尝试内保持拒绝，后续 catch 不能将它改写为一次失败状态提交。公开来源在网络返回后检查；研究库在真实 Git 拉取、包校验及判断等待后检查；账号来源在 Listener 接收 raw delivery、提交 Signal、Feed、游标、run 与错误收尾前检查。来源指定的账号连接同时核对 Home 中原连接记录，断开不能靠旧凭据引用继续提交。释放自己持有的 Listener lease 仍执行。

生产定时器现在只触发插件声明的 `feed.sources.tick`，查询目录、调用记录、权限及插件生命周期与其他动作一致；Host 的默认私下直调同步已删除。tick 使用原 concurrent 调度合同，来源的已有 inFlight 集合跨该处理器的 tick 保留。同一 Host 的暂停与配置动作可在定时拉取等待时完成，重复 tick 跳过正在拉取的来源；失败提醒与下次拉取时间也受同一持续检查约束。多个来源并行时等待全部已发起尝试退出，避免提前结束调用上下文。

新的真实调度测试查出原有故障：`scheduled:<source>:<ISO 时间>` 含小数点，真实同步入口的幂等键合同不允许小数点，导致自动拉取直接失败却仍推进计划。原调度测试用 fake dispatch，未触及入口合同。现复用 owner 的 `stableId` 以来源与计划时间生成稳定合法键；真实 RSS 与账号拉取都已执行，并验证恢复同一计划后不重复产生材料或 Signal。

恢复保持原事实：来源换账号产生独立来源身份，不复用旧账号的 Signal 去重空间；上游已存取消/失败回执时重新拉取使用新请求键；已获授权创建的 Signal 不回滚，但拒绝后的 delivery 状态和游标不得继续推进，恢复用原 receipt 去重。不声称撤回已派发的网络请求，也没有删除原缓存、材料或历史。

### Coding MCP 的 SDK 最后派发边界（同日后续）
