## 1. 背景

Goals 把很多字段存成 JSON 文本列（目标的范围与约束、验收的证据、项目规则、方法包、事件配置、治理提案的条目……）。读出来时，有两份一模一样的宽松解析函数：文本读不出来、是空串、或者不是字符串，一律悄悄换成备用值（`{}`、`[]` 或 `null`），不报错。

- `plugins/native/goals/src/module/repository.ts:378-384` 的 `parseJson`：`typeof value !== "string" || value.length === 0` 返回备用值，`catch` 里也返回备用值。`:273-275` 的 `rowJson` 原样转出它。
- 同一份在 `plugins/native/goals/src/governance/mappers.ts:13-20`（`parseJson`）。
- 直接调用：`repository.ts:190`（项目规则）、`:198`（方法包）、`:285-290`（目标）、`:315-316`（验收）、`:345`、`:364`（项目指引）；`governance/mappers.ts:44`、`:56-59`、`:62-63`、`:82`；`governance/event-decisions.ts:81`、`:87`。
- 经 `rowJson`：`module/event-state-outcome-records.ts:186`、`event-state-concern-records.ts:83`、`event-state-decision-records.ts:157-161,175-178`、`event-facts-config-records.ts:75,155,156`、`event-facts-requirement-records.ts:111`、`event-facts-work-event-records.ts:185`、`query-facts-repository.ts:25`。

最重的后果有两条，都在代码里核过：

1. 项目规则「完成前必须你点头」存在 `policy_bindings.policy_json`（`project-database-goals.ts:99`，`NOT NULL`）。这一行读不出来，`listActivePolicyBindings`（`repository.ts:173-192`）给出 `policy: {}`；`resolveGoalPolicy`（`module/query.ts:177-193`）只在 `policy.human_approval != null` 时覆盖默认值，默认是 `{ human_approval: false }`（`query.ts:22`）。收尾检查读的就是它：`module/event-facts.ts:144` 算出 `human_approval_required`，`module/event-state-completion.ts:81-88` 据此决定要不要拦。结果：规则行一坏，规则悄悄失效，Goal 不用你点头就能完成。
2. 治理提案的条目带着「提出时各对象的版本」（`goal_tree_proposal_items.baseline_versions_json`，`project-database-governance.ts:42`）。检查冲突时逐条拿它和现在的版本对比（`goal-tree-check.ts:47-52`，`proposal-baselines.ts:19-26` 同理）。这一列读成 `[]`，一条对比都不做，过期的提案条目被当成没有冲突。

写入这些列的地方都用 `JSON.stringify`（`repository.ts:265-267`、`governance/mappers.ts:9-11`），规则写入还校验形状（`module/policy-commands.ts:15-18`）。所以正常运行不会产生读不出来的文本；读不出来就是库坏了，该报，不该猜。`AGENTS.md` 的规矩是存量坏数据由维护处理，读取不兜底。

## 2. 目标

1. 库里 JSON 列的文本读不出来（空串、非字符串、解析失败），读取抛 `goals.storage.record_unreadable`（kind `internal`），不再换成备用值。SQL 的 NULL 仍然读成备用值（可空列的「没有」）。Module 与 Governance 两边都是。
2. 抛出的错误不带库里的任何内容。
3. 上面两条严重后果各有一条用例钉住：规则行坏了，收尾不会被放过；提案条目的版本列坏了，读提案会报错。

## 5. 做法

**已定（main 上核过）**

- 规则两边一样：`value == null` → 备用值；否则必须是字符串且 `JSON.parse` 成功；空串、数字、损坏文本都算读不出来。不动函数签名，不动 `rowJson`。
- 错误文案固定，写成「Goals 存的一条记录读不出来（JSON 已损坏），读取已停止，没有按空值处理」这个意思。**不要**把 `JSON.parse` 抛出的 `SyntaxError` 的 `message` 拼进去：V8 的这条信息会带一段原文。`catch` 里不绑定错误对象。
- 一行坏了，整个读取抛错，不逐行跳过：`snapshot`、`listGoals`、`getGoalTreeProposal` 都是整体失败。读不全比读错好。
- `listPlanningMethodPacks`（`repository.ts:194-199`）的 `.filter` 不动；方法包也走同一个严格的 `parseJson`。
- 码的声明照 `plugin-sqlite.ts:4-10` 的 `goals.storage` 族：`internal` 类。两边声明同一个码字符串。若 `pnpm health:check` 或测试因同一个码在两处声明而报错，Governance 一侧改成 `goals.governance.record_unreadable`，并在 PR 里写明。
- 门禁口径：新写的 `catch` 里有 `throw`，不算空 `catch`；不要写 `as unknown as`；不加 `any`。
- 测试只用公开入口，照 `tests/goals-query-facts.test.ts:1-16`：`new LocalProjectDatabase(":memory:")`、`new GoalProjectApplication(store)`、`new GoalsModule(pluginLegalSql(store).db, store, {})`（来自 `./fixtures/goals-modules.js`），用 `store.db.prepare("UPDATE … SET …_json = ?")` 把一行改坏，同一个文件里就有这种直接写库的先例（`:25-32`）。**不要** import `plugins/native/goals/src/…` 或 `dist/…`：「测试引用包内部」与「同一个包不得同时从源码和构建加载」两项都按文件只许减少。Goals 的 `dist` 是测试加载的东西，改完源码先 `pnpm --filter @molis-ai/molis-work-plugin-goals run build`。
- 每条抛错断言写成：`error instanceof ActionError && error.code === "goals.storage.record_unreadable" && error.kind === "internal"`，照 `tests/governance-collaboration-module.test.ts:152`。
- 对照用例（`RAC-1268`）要证明没有读坏：同一批数据未损坏时读到的值，和损坏前一样；NULL 的可空列（`goals.decomposition_review_json`、`acceptance_criteria.target_json`、`goal_tree_proposals.narrative_json`）读成 `null`。
