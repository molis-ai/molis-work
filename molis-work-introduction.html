MOLIS WORK / PRODUCT ESSAY2026.09 · 第四版

让工作，
在人与工具之间继续。

Molis Work 是一个面向个人与团队的插件化工作平台。
在这里使用工具、积累成果、与他人协作，也可以从 Codex、Claude Code 等外部 Agent 直接调用指定插件。

01从交接处出发

一件工作，
通常不只发生在一个工具里。

设想一个小团队准备发布新产品：有人调研，有人写方案，有人制作内容。每个人都在产出，但下一步开始前，仍可能需要重新找文件、确认版本、补充背景。

即使文件传过去了，也不一定知道它为什么产生、依据是什么、哪些结论已经确认。隔几天回来，或换一个人接手，还要从聊天里重新拼出事情的来龙去脉。

Molis Work 的出发点，是把这些交接处连接起来。不仅让工具出现在同一个平台，更让前一步的结果，成为后一步可以直接使用的输入。对个人如此，对团队也如此。

贯穿全文的例子

“团队准备一次产品发布”是用于解释机制的目标场景，不是已有客户案例。它会经过不同成员、不同工具和多次交接。

我们关注的不是让所有工作变成对话，而是让工作不被某一次对话困住。

放在一起，是入口统一。
接得下去，才是工作连续。

要让交接可靠，先要让每一步留下可以被识别、引用和继续使用的成果。

02成果与上下文

插件负责能力。
Artifact 负责成果。

平台里的业务能力以插件提供。一个插件可以用于对话、文档、数据分析或内容制作，也可以只是一个解决具体问题的小工具。它不必都使用 AI，也不必都围绕任务看板工作。

当插件产生了可以独立使用的结果，这份结果便可以成为 Artifact（成果对象）。它不仅保存内容，还记录类型、版本、来源和访问范围，让别的兼容插件能够找到并使用它。

因此，插件之间对接的不是彼此内部的实现，而是共同认可的成果。今天由一个插件生产，明天也可以由另一个遵循相同约定的插件接手。

已经有的技术基础：仓库已实现 Artifact 的身份、固定版本、类型兼容检查和跨插件输入机制。全平台互通仍需逐条链路接入。[1][2]
成果，不只等于文件

一份 Excel、一个视频、一份报告或一组结构化代码变更，都可以成为成果。能否被其他插件消费，取决于内容类型、格式约定与访问许可。

上下文可以通过关系关联到成果，不必把所有历史都塞进同一个对象。

传过去的，不只是一份文件。

下一步真正需要的，往往还有这份结果背后的工作背景。平台希望把相关的目标、来源、约束和进展保留下来，让接手的人或插件按需取得，而不必靠用户逐次复述。

结果是什么
哪一份成果、哪一个版本，是否仍然可用。
为什么产生
服务什么目标，采用哪些材料，有哪些已确认的约束。
怎样继续
已经完成什么，仍需确认什么，下一步要接过什么。

对个人，上下文的目标范围覆盖整个个人空间，已有积累可以跨项目复用；对团队，共享内容在权限范围内连接成员。项目是组织工作的方式，不该成为重复解释背景的原因。

当成果可以跨工具接续，同一套机制也应该连接不同的人。

共享，不等于全部灌入

按当前工作选取相关信息，不把所有文件与聊天一次性塞给每个模型。引用可见，也不代表正文已获授权。

关系查询与指定上下文重建已有实现；个人全域、跨项目的统一体验仍需补齐。[3]

03 / 工作从一个人，走向一群人

同一个目标，
不需要同一种工具。

回到那次产品发布。团队可以在 Goal 插件里拆分和领取任务，成员各自选择合适的插件执行，再把成果带回共同目标。不同的人，沿着同一份共享背景推进。

01 / 拆分与领取

先说清共同结果，
再让成员认领任务。

负责人用 Goal 插件拆出调研、方案和内容任务，说明预期结果、完成条件与依赖。团队成员领取自己负责的部分，协作不是把一段模糊指令丢进群聊。

领取的是责任，不只是看板上的一张卡片。
02 / 分别执行

成员选择合适的插件，
做出自己的成果。

调研成员在研究或对话插件里整理材料，形成调研表；其他成员可以先做不依赖该结果的准备。协作不要求所有人使用同一个工具，也不把所有步骤锁成一条串行流水线。

工具由成员选择，成果仍回到同一件工作。
03 / 带着背景交接

下一位接过成果，
不再从空白开始。

方案成员在文档插件中引用获准的调研表及相关约束，形成发布方案。内容成员再取用所需的确认版本，制作素材。各自留下来源与版本，而不是复制出一组无法追溯的“最终版”。

交接的是可用结果，以及理解它所需的背景。
04 / 汇总与验收

各项结果回到目标，
最后形成共同交付。

负责人查看成员提交的成果、未完成项与待确认问题，完成汇总和验收。“生成成功”“成员已提交”“目标已验收”是不同状态。下一次迭代继续使用有效积累，而不是重新开一段失去历史的对话。

工作可以分开做，交付仍然需要一起对齐。
一个人的成果，
成为另一个人的起点。

人与人之间、插件与插件之间，都围绕可引用的成果及获准的上下文交接。协作因此不只发生在聊天里，也落实在工作本身。

↳平台与插件的边界

协作不属于 Goal 一家。
它应该是平台的共同基础。

Goal 插件提供的是一种协作方式：围绕目标拆分、领取、提交和汇总。文档插件可以组织评论与审阅，资料插件可以支持分工采集，其他业务插件也可以定义自己的合作过程。

平台的方向，是把成员、权限、共享成果、变更同步与操作记录做成通用服务。插件按需接入，再实现自己的业务规则和界面。它不必为了多人使用，重新建设整套协作基础设施。

平台支持多人，不等于每个插件都必须多人化

个人工具仍可以保持简单。只有需要协作的插件才接入对应服务；用户也不必先建立 Goal，才能在其他插件里共同工作。

个人与团队不是彼此割裂的两套产品。一个人可以先积累资料和成果，再选择把需要的部分用于团队工作；成员退出或权限改变后，访问边界也应随之调整。

任务领取、评论审阅与多人实时编辑不是同一种能力。接入协作服务不自动代表插件具备实时共同编辑；具体支持范围需要逐插件实现和验证。

平台内部已经能够围绕成果与协作连接起来。但现实中的工作并不会全部发生在 Molis Work 里：下一步，是让外部 Agent 也能进入同一个业务世界。

04从平台外部进入

工作不一定发生在 Molis Work 里。
但结果可以回到同一个地方。

很多真实工作本来就发生在 Codex、Claude Code、Cursor 或其他 Agent / IDE 里。Molis Work 不应该要求用户为了“统一”而离开这些工具，再把内容复制回来。

更自然的方式，是让插件声明自己允许外部调用的能力，由平台通过 MCP 统一、安全地暴露。外部 Agent 因此可以把内容写入指定插件，也可以在获得授权后读取已有成果和上下文。

UI、内部 Agent、外部 Agent 和自动化，只是不同入口。进入插件以后，仍然遵守同一套业务规则、权限、Artifact、Context 与协作体系，不再产生第二份事实。

不是每个插件各开一个 MCP Server

目标形态是：插件声明 mcp_exports，由 Molis Work Host 统一组成一个 MCP Gateway。外部 Runtime 不需要理解插件数据库和内部实现。

仓库已有统一 MCP 导出机制的工程基础，但并非每个插件都已经开放完整 MCP 能力。[10]

入口可以无限增加，
事实只有一份。
Codex → Goal完成一次架构分析后，把结果和来源写回指定 Goal，团队下一位成员继续使用。
Claude Code → Pages在外部完成研究，将成稿直接保存到 Pages；需要时再发布成 Artifact。
外部 Agent → Artifact读取获准的精确版本继续处理，新结果仍能被平台里的其他插件消费。
为什么这一层重要

Molis Work 不必成为用户唯一停留的界面。它更像一个持续的工作底座：外部世界不断变化，成果、关系、权限和团队事实仍能留在同一个地方。

这也让未来插件商店的价值扩大：一个插件不仅能被人在 Molis Work 里点击，也可以成为外部 Agent 可组合的能力。

当平台既能接住内部插件，也能接住外部 Agent，用户就不必等待官方预设所有工作方式：缺少的能力，可以进一步由用户自己创造。

05从使用到创造

需要的工具不存在，
就把它做出来。

那支准备产品发布的团队，可能还需要一个专门的素材验收工具：按渠道整理内容，让负责人审阅，再把确认版本交给发布环节。一个通用文档不够合适，一整套新软件又太重。

Molis Work 希望插件像平台里的“小程序”：可以使用，也可以创建、修改和分享。创作不只属于官方，用户可以把自己的工作方法变成一件持续可用的工具。

为此，平台提供两条互补的创作方向。它们的自由度不同，但不应走向两套互不相通的生态。

不是只生成一段代码

真正的结果应是一个能在平台内使用、保留数据、继续修改的插件。是否调用 AI，是插件的选择，不是“成为插件”的前提。

下方描述创作的目标体验。当前受控创作范围与验证边界见第八章。

A / AI 辅助创建

从一句需求开始。

“做一个素材验收工具，按渠道收集内容，允许负责人审阅，并交出确认版本。”

用户说明场景，AI 协助形成方案、界面和功能。通过试用发现缺口，继续调整。需要多人协作时，接入平台的相应服务，而不是另起一套账号和权限体系。

描述需求→试用调整→留下插件
B / 人工开发

从一段实现开始。

有开发能力的创作者，可以实现更专业的业务逻辑和交互。通过平台接口声明输入、产出、权限、所需服务以及可选的 MCP 对外能力，把自己的专业能力接到共同的成果、协作与外部 Agent 体系中。

不必把插件做成所有功能的集合；把一件事做好，也可以成为别人工作中的一环。

实现能力→接入契约→验证维护
两条入口，同一套平台规则。输入与产出 · 成果类型与版本 · 访问权限 · 按需协作

无论由 AI 协助还是人工开发，新插件的价值都不只在于“多一个功能”。它还应该接得过已有成果，留得下后续可用的结果，必要时让不同成员一起参与。

到这里，平台的核心机制和创作方式已经讲清楚。下一步不再讲抽象概念：直接看这些能力在真实工作里怎样组合起来。

06完整案例

从一个人的小事，
到一群人的复杂协作。

前面讲的是平台为什么需要 Plugin、Artifact、Context、协作基础和 MCP。下面不再把这些词拆开解释，而是看六件真实工作怎样从头走到尾。

案例按复杂度递进：单插件 → 跨插件 → 外部 Agent → 自己创建插件 → 小团队协作 → 多团队、多插件、多 Agent 的完整发布。

这些案例怎样读

每个案例都回答同一组问题：工作从哪里开始？谁在参与？用什么入口？哪些过程只属于插件内部？什么时候形成 Artifact？下一步如何拿到足够的上下文？最后少掉了哪些重复工作？

它们描述目标体验与产品逻辑；并不表示每条链路今天都已完整验收。

CASEBOOK / 01—06

复杂度增加时，核心规则不变：过程可以分散，结果要能被引用；入口可以变化，事实不能分叉；协作可以多人并行，权限与版本必须说得清楚。

01
单人 · 单插件 · 最简单成果

对话里做出一份 Excel：聊天结束，成果没有跟着消失。

场景

运营负责人刚结束一次活动，需要把订单、渠道和投放数据整理成复盘表。他在一个对话型数据插件里上传 CSV，并说：“按渠道统计转化、成本和退款，最后给我一份可继续分析的 Excel。”

这件事并不复杂，但很能说明 Artifact 的边界：模型的推理、临时清洗表、重试记录都只是过程；真正值得留下的是最终可以独立使用的 Excel。

  1. 01 / 输入用户说明业务口径并上传原始数据。

    插件知道本次统计为什么做、哪些字段要保留，以及最终需要什么形式的结果。

  2. 02 / 插件内部清洗、计算、修正异常值。

    临时表、缓存和模型中间推理仍属于插件内部状态，不需要为了“可追踪”而全部变成 Artifact。

  3. 03 / 成果形成生成「9 月活动复盘.xlsx」并登记为 Artifact v1。

    平台记录成果类型、版本、来源插件、必要元数据与访问范围。用户不需要再点一次“上传到平台”。

  4. 04 / 再次使用一周后，用户直接从这份成果继续。

    无论重新进入原插件，还是交给一个兼容的数据分析插件，引用的都是同一份确定版本，而不是重新从聊天记录找附件。

留下什么可复用 Excel Artifact、版本、来源与本次业务背景。
不留下什么无价值的每一步模型推理、临时缓存和渲染中间态。
少掉什么导出 → 找文件 → 再上传 → 解释“哪个才是最后版”。
核心机制Plugin → Artifact。
02
单人 · 跨插件 · 上下文接续

先做市场研究，再写产品方案：换了工具，不重新做准备工作。

场景

一个创业者准备做新的 AI 产品。他先在研究插件里整理竞品、用户反馈和价格信息，随后要在 Pages 写正式产品方案。普通工具链里，第二步通常从“上传报告 + 解释背景 + 指明哪些结论可信”重新开始。

Molis Work 的目标不是简单把报告文件塞给 Pages，而是让 Pages 按权限拿到这次写方案真正需要的那部分背景。

  1. 01 / Research研究插件形成研究报告 v3。

    报告关联采用的原始材料、关键判断和“尚未验证”的部分，前两个草稿仍保留为历史版本。

  2. 02 / Context用户选择“基于这份研究写产品方案”。

    平台不用搬运整个个人空间，只重建当前任务需要的报告、选定材料、目标和已确认约束。

  3. 03 / PagesPages 接过结果与上下文，继续写。

    用户不必重新解释“为什么更关注企业市场”“这三个竞品为什么被选中”“哪些数据只是估算”。

  4. 04 / New Artifact产品方案定稿后成为新的 Artifact。

    这份方案又可以成为下一步 PPT、预算、研发拆解或团队评审的输入。

共享的不是“把我全部聊天历史给 Pages”。
共享的是当前任务需要、且获准读取的研究成果与相关上下文。
少掉什么重复上传、重新概括、在多个工具里维护不同“最终版”。
核心机制Artifact + Context → 跨插件接续。
03
单人 · 外部 Agent · MCP

人在 Codex 里工作，进展和成果却已经回到团队能继续使用的地方。

场景

开发者正在 Codex 里排查一个架构问题。他不想为了“记进展”不断切回 Molis Work，更不想在一天结束后再手写一份总结。Codex 已经知道代码现场，于是直接通过 MCP 调用平台中的 Goal、Pages 和 Artifact 能力。

关键不是“支持 MCP”四个字，而是 MCP 不能建立第二套事实：从外部写回来的内容仍然由目标插件按同一规则保存。

  1. 01 / Codex分析代码、运行只读检查，得到架构结论。

    工作完全发生在用户本来就在使用的 Codex 会话中。

  2. 02 / MCP GatewayCodex 调用 goals.report_progress。

    把“已经确认什么、下一步是什么、有哪些风险”写回指定 Goal，而不是复制一段纯文本到另一个数据库。

  3. 03 / Pages完整架构说明保存到 Pages。

    若这份说明达到可独立复用的程度，用户可以进一步发布为 Artifact，保留精确版本。

  4. 04 / Next Runtime第二天换 Claude Code，仍然能从平台事实继续。

    Claude Code 不需要访问昨天那条 Codex 私有会话，只读取获准的 Goal 进展和已发布成果。

入口Codex；下一次可以是 Claude Code、Cursor 或其他 MCP Client。
事实所有者仍然是 Goal / Pages / Artifact，而不是 MCP 网关。
少掉什么切应用、复制总结、重新同步团队进度。
核心机制External Agent → MCP → Plugin → 同一业务事实。
04
单人 · 创建插件 · 从需求到长期工具

平台没有“素材验收”工具？先用 AI 做一个，再让它真正进入你的工作流。

场景

内容负责人每周都要检查几十条短视频素材：看标题、封面、渠道、发布时间和审核意见。表格勉强能用，但没有“待审 / 退回 / 已确认”的专门流程，也无法方便地把确认结果交给后续发布工作。

她没有等待官方做一个“短视频素材验收插件”，而是在插件创作工作台里说：“帮我做一个素材验收工具。”

  1. 01 / 描述需求用户先讲工作，而不是讲数据库字段。

    “每条素材需要标题、封面、渠道、负责人、审核状态和意见；被退回后要保留历史；确认后能交给发布环节。”

  2. 02 / AI 辅助设计AI 给出候选界面和数据结构。

    用户选择卡片式素材列表，补充“负责人必须能批量筛选待审内容”，并删掉不需要的统计组件。

  3. 03 / 真实试用在预览数据里跑一轮完整审核。

    发现“退回理由”必须是必填项，于是修改规则；确认数据和交互都符合真实习惯后再发布插件版本。

  4. 04 / 接入平台声明输入、产出、权限与可选 MCP 能力。

    它可以读取指定素材 Artifact，确认后发布 approved-material-set；如果以后要让外部 Agent 批量导入素材，再开放相应 MCP 工具。

  5. 05 / 日常使用下周继续用同一个插件，而不是重新生成一次。

    插件有自己的稳定身份、数据和版本；创作过程结束后，它成为真正的工作工具。

  6. 06 / 继续成长需求变化时升级，而不是推翻重做。

    团队后来需要按品牌分组，用户在兼容规则允许的范围内发布 v2；历史审核记录仍可读。

创建的不是一段一次性 HTML 或一个只能演示的 AI 页面。
创建的是有身份、有数据、有版本、能接入 Artifact / MCP / 协作能力的长期插件。
用户获得“没有合适工具 → 自己做一个 → 真正反复使用”的闭环。
核心机制AI Builder / SDK → Plugin → Platform Capabilities。
05
小团队 · 自建插件参与协作

四个人准备一次功能发布：有人领任务，有人用自建插件，成果最后回到同一个 Goal。

场景

一个四人产品团队准备发布新功能。负责人在 Goal 插件中拆出：用户调研、发布方案、宣传素材、上线验证。刚才创建的“素材验收插件”第一次真正进入团队协作。

这里的重点是：Goal 不是所有协作的唯一容器。它负责目标和任务关系；素材审核发生在素材插件；文档评审发生在 Pages；平台负责成员、权限、共享成果与变更记录等共同基础。

  1. 01 / Goal负责人定义共同结果并拆分子任务。

    每个任务说明期望产出、完成要求和真正的前置依赖。

  2. 02 / Claim成员按专长领取，而不是由系统假装“自动派单”。

    A 负责调研，B 负责方案，C 负责内容，D 负责最终验证。

  3. 03 / Parallel Work没有依赖的工作并行开始。

    B 可以先搭方案结构，C 可以准备视觉方向；等 A 的研究 Artifact 确认后，再补上需要真实结论的部分。

  4. 04 / Custom PluginC 把素材送进团队自建的素材验收插件。

    负责人在插件里审阅、退回、确认。确认版本作为 Artifact 留下，而不是只在群里说一句“这版可以”。

  5. 05 / Handoff各项结果沿明确版本交给下一步。

    发布方案引用研究 v3，宣传素材引用方案 v2，验证清单引用最终发布候选。

  6. 06 / Acceptance负责人最后回到父 Goal 做整合与验收。

    “每个子任务都有产物”不自动等于“产品已经发布成功”；最终集成和验收仍是单独事实。

团队共享目标、获准成果、必要上下文、决定与状态。
成员仍可私有个人草稿、失败尝试、未发布的工作过程。
少掉什么群里问进度、反复找附件、口头确认“到底采用哪一版”。
核心机制Goal + Collaboration + Custom Plugin + Artifact + Context。
06
复杂团队 · 多插件 · 多 Agent · 多入口

十个人、多个外部 Agent、几个自建插件，同时推进一次 AI 产品正式发布。

场景

团队包含产品、研发、设计、增长和运营。研发主要留在 Codex，研究人员习惯 Claude Code，设计使用图片插件，运营有两个内部自建插件；负责人需要知道真正影响发布的结果，而不是监控每个人的每一步操作。

这时 Molis Work 的价值不再是“少切一次应用”，而是为高度分散的工作提供一层共同事实。

  1. 01 / Shared Goal团队先建立发布目标与关键交付链。

    只建立真实依赖：例如“上线文案必须消费已经确认的产品定位”，而不是简单按时间顺序把所有任务串起来。

  2. 02 / External Runtime研发在 Codex 里完成实现与评审。

    关键报告和进展通过 MCP 回到 Coding / Goal；未发布的开发过程仍可以留在个人或执行上下文中。

  3. 03 / Research & Content研究和内容团队在不同插件中并行工作。

    Claude Code 写回研究结果，Pages 形成正式说明，图片插件生成视觉成果，自建插件负责内容审核。

  4. 04 / Artifact Graph真正需要交接的结果进入成果网络。

    每个消费者读取精确版本和必要上下文；一个新版本出现，不会悄悄改写已经基于旧版本完成的历史工作。

  5. 05 / Team Boundary新成员加入，只拿到足够继续的共享内容。

    他能看到团队确认的 Artifact、Goal 和决定，却不需要读取原成员的全部私人 Prompt、失败尝试和未发布草稿。

  6. 06 / Release & Resume发布完成后，整套积累继续服务下一次迭代。

    三周后重新启动 v2，不从空白会议开始：既有结果、采用原因、历史版本和未解决问题仍能被找到。

分散的是工具、成员、会话、执行地点和专业流程。
统一的是可共享的事实、成果身份、权限边界、版本与因果关系。
平台价值让复杂协作不退化成复制文件、转发消息和反复开会。
核心机制Goal + MCP + Plugins + Artifact + Context + Collaboration。
六个案例，复杂度不同，但平台做的事情始终一致。

当一份结果值得后续工作继续使用，它就以清楚的身份留下；当工作换了插件、成员或 Agent，新的参与者得到足够继续、但不过度暴露的上下文；当现有工具不够，用户还能创建新插件并把它接回同一体系。

当一个自建插件不只被自己使用，而是在真实工作里被反复采用，它自然会出现下一个问题：这件工具能不能交给更多人？这正是插件生态开始的地方。

07从工具到生态

一个人的工具，
可以成为更多人的能力。

当这个素材验收插件在团队里反复使用、逐渐成熟，作者可以选择把它分享出去。另一个团队无需从头创造同样的工具，就能在自己的空间里使用，再提出新的需求与改进。

这就是插件商店的意义：让经过使用验证的工具，被需要它的人发现、采用和维护。发现、安装、权限说明、版本升级与质量反馈，应连成完整体验，而不只是把插件名字放进一个列表。

共享成果使已有工具能够接续，通用协作服务让新工具更容易进入团队，MCP 让这些能力被外部 Agent 调用；开放创作再把新的能力带回来。它们共同构成我们想建立的生态。

一个需要验证的判断

插件越多，不必然越有价值。真正重要的是：有人持续使用，成果被其他插件接过，作者愿意维护，其他用户愿意采用。

这些是产品验证方向，不是已有增长数据或已经成立的网络效应。

共享能力，不等于公开所有数据。

形成 Artifact
把可独立使用的结果纳入成果体系。可以自动登记，也可以主动发布；不等于向团队或互联网公开。
共享给协作者
在明确范围内授予团队或成员相应权限。个人资料不会仅因参与团队工作，就自动成为所有成员可读的内容。
公开分享插件
让别人使用同一种工具能力。作者的文件、对话、密钥和私人工作成果，不随插件一起发布。

这三条边界要同时成立，用户才可能放心积累，团队才可能可靠协作，创作者才可能安全分享。
