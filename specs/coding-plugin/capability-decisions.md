## 第 1 块：中断与恢复（2026-09-25，按对照清单第一项）

**做了什么**

- **从断点继续**：最新一轮停下（你停止、出错、被取消）后，完成卡上有"从断点继续"。
  - 服务端新增 `coding.continuation`（Coding 1.33.0），按宿主的事实拼出继续说明：原任务；哪些已写入、被拒绝（附意见）、结果未知；哪些命令已运行（附 exit）、被拒绝、未运行；读过的文件；没结束的操作；计划步骤。
  - 不让模型凭记忆推断；不回放任何操作，新的写入和命令照常审查；"继续的继续"仍指回原任务。
  - 并行分工轮次不提供一键继续，说明原因。
- **核对并继续**：服务被中断的一轮，完成卡上显示"核对并继续"。点击后先核对：结果全部明确才关闭中断轮次并继续；有未知结果时打开右侧核对区说明原因。
- **暂停 / 恢复**：执行中可以暂停，当前这一步做完后停下，可随时恢复。会话列表与底部提示都显示"已暂停"，"需要你"筛选也包括暂停的会话。
- **失败说明**：常见失败码翻成人话并给下一步，原始错误码保留，例如 MODEL_NETWORK_FAILED 显示为"连不上模型服务：检查网络或代理后，从断点继续即可"。
- **筛选计数**："进行中 / 需要你"筛选带计数，0 时隐藏。
- **顺带修复**：
  - `coding-workbench.e2e` 的偶发失败：文本已到、布局晚一帧，改为等待可见，读区一直不可见仍会失败。
  - 会话状态里两个不存在的图标名。

**真实任务证据**（MiniMax-M3，coding-sandbox）

- **你停止 → 一键继续**：会话"给 src/report.ts 增加一个 monthlyReport…"。
  - 批准一条命令后按 Esc 停止；继续说明如实列出：`ls src test` 未运行（被停止取消），`ls -la` → exit 0，读过 3 个文件。
  - 继续轮只补跑了未运行的命令，然后实现 monthlyReport 和两个测试并运行 npm test；沙盒 16/16 通过。
- **服务强杀重启 → 核对并继续**：会话 `5c43912a…`。
  - 模型先提问，按"只更新 name"回答；批准 `src/habits.ts` 写入后，在下一次写入待审时停掉服务并重启。
  - 重启后显示"这一轮需要核对结果"，并列出已修改的文件；点"核对并继续"后，模型核对到 `src/habits.ts` 已包含 renameHabit，只补写测试文件并运行 npm test。
  - `src/habits.ts` 与中断前 SHA-256 相同，没有重复写入；沙盒 18/18 通过。
- **暂停 / 恢复**：一个 7 个文件逐个读取的只读任务，约 1 秒进入已暂停；暂停 8 秒内没有新内容（仅计时变化）；恢复后约 1 秒继续，正常完成。

**测试**

- 新增 `coding-continuation` 4 项、时间线 DOM 测试（继续按钮与失败说明）。
- 相关 322 项中 321 通过、1 跳过（最后一轮的偶发失败已按上面修正，Coding e2e 再跑通过）。
- workspace:typecheck 通过。
- 本块没有跑全仓回归。

**还没做 / 未验证**

## 第 2 块：计划与 TaskBoard（2026-09-25）

**做了什么**

- **对话里的计划进度卡**：执行确认计划的一轮，在任务下方显示整张任务图，按执行顺序列出每一步。
  - 每步显示状态标记（完成 / 进行中 / 受阻 / 失败 / 你跳过了）、最近一次模型回报和你的验收，点步骤可以打开原有的回报与验收弹窗。
  - 状态只来自模型对任务图的回报，不从回答正文推断。
- **执行中调整计划**：进度卡上可以提前 / 推后（只限未开始的步骤）、跳过（需写原因）、在某步后插入（需写完成条件）、对受阻的步骤给出决定、越过失败的步骤。
  - **宿主**：新增 Host 能力 `agent.run.step-board.amend.v1`（2026-10-17 P4-C2 换成动作 `agent.collaboration.revise.v1`，形状不变，见 `specs/prologue-adoption` §6.0j），全部使用 SDK TaskBoard 的 report / addNode / rewire，带版本号防并发。
  - **只动涉及的步骤**：每次调整只重接受影响的步骤，不会因为别处的改动自动越过失败。
  - **记录**：调整以报告形式记在图上。
  - **告知这一轮**：Coding 经原有的补充要求通道把调整告诉执行中的这一轮，要求它先 board-read。
  - **权限不扩大**：模型只能回报本轮图上已有的步骤（包括你插入的），仍然不能自己加节点。
  - **确认计划不改写**：确认计划 Artifact 保持不变。
- **跨轮次继续同一张图**：`AgentStartRequest.continue_step_board_of`。
  - 宿主要求使用同一版确认计划、那一轮已结束、图未结束，并把这一点冻结进新一轮；Node 运行时复用原图，不再新建。
  - 你插入 / 跳过的步骤跨轮保留。
  - 以前执行同一计划会被"已执行过"拦下，只有明确的继续才绕过。
- **完成卡如实反映计划状态**：计划还有步骤时显示"这一轮结束，计划还剩 N 步"（琥珀色），并提供"继续计划"。之前会显示"这一轮完成"，是误导。
- **左栏 TaskBoard 与步骤弹窗改按图的顺序和 id 取步骤**：插入的步骤带自己的标题与完成条件，你跳过的显示"你跳过了"。
- **提示**：图的执行说明补充"只要还有 ready 的步骤就不要结束这一轮"；计划的继续说明改为"把剩下的步骤依次做完"。
- **时间线**：board-read / board-report 显示为"查看任务图 / 回报步骤"。
- Coding 1.35.0。

**真实任务证据**（MiniMax-M3，coding-sandbox，会话"为 coding-sandbox 规划这个功能…"）

- **规划与执行**：规划轮产出 5 步计划（第 5 步是可选的 README 说明）；确认后按计划执行。
- **执行中调整**：第 1 步进行中时，在第 2 步后插入"为 yearlyReport 补一个闰年边界测试"，并以"这次不改 README"跳过第 5 步；两次都显示"已告诉执行中的这一轮"。模型随后 board-read，复述了新顺序。
- **第一次暴露的问题**：该轮做完第 2 步后，模型在一次上下文整理后自行结束。完成卡原本显示"这一轮完成"，已改为如实显示"还剩 3 步"。
- **第 3 轮**：点"继续计划"，在同一张图上完成你插入的那一步后又自行结束。原因是继续说明里写了"完成后说明做了什么"。已按上面的提示修改。
- **第 4 轮**：再次继续，一轮做完剩下两步（补测试、`npm test` exit 0）。
  - 最终图：5 步完成，其中含你插入的 1 步；README 那一步显示"你跳过了"，并附跳过原因。
  - 完成卡显示"这一轮完成"；沙盒 21/21 通过。

## 第 3 块：子代理（2026-09-25，第一部分）

**做了什么**

- **对话里的子任务卡片**：父任务派出子任务后，卡片显示在派出那一步下面，每个子任务一张。
  - 显示角色、实时状态、用量和分工首行。
  - 子任务自己的工具过程用与主对话相同的时间线展示，进行中实时更新。
  - 子任务的待审操作直接出现在自己的卡片里，仍由宿主决定。
  - 结论默认折叠，带一行预览。
  - 进行中可以单独停止；结束后"评价结论 / 评价并整合成果"跳到结果面板原有的评价入口（带版本校验的逻辑不重复实现）。
- **重试**：失败或已停止的子任务可以"重试"。父任务仍在执行时，经补充要求通道请它重新派出；已结束时，把请求放进输入框，由你决定是否发送（新一轮会产生费用）。
- **并排对比**：两个及以上子任务时，可以切到并排对比，结论并列展开。
- **派出子任务的审查卡改为可读**：宿主按冻结的子角色给出"子任务角色 / 分工 / 可用工具 / 工作目录"，分工按原文换行显示，完整参数折叠在下方备查。审查历史标题为"派出子任务：角色名"。
- **时间线**：dispatch-subagent / await-subagents / steer-subagent 显示为"派出子任务 / 等待子任务 / 补充子任务要求"。等审查时派出子任务算作"等你批准"。父轮完成卡写明"派出 N 个子任务"。
- **修复真实缺陷：子任务派不出去**。
  - **现象**：MiniMax 派子任务时漏掉了子角色声明中的 `context-remaining`，SDK 以 CHARACTER_ESCALATION 拒绝（子角色的工具必须落在父任务派出时给的清单内）。模型拿到英文错误后原样重试 4 次，全部失败，最后没有子任务就自己汇总。

  - 回归测试改为派出时不带 context-remaining。
  - Coding 1.36.0：manifest 改动必须递增版本，否则平台会以"同一版本不能对应不同 Manifest"拒绝加载，这条保护在真实运行中触发过一次。
- **新增 `coding-client-scripts` 测试**：客户端脚本由模板字符串拼成，里面的转义错误会让整个页面（不只 Coding）失效。本块开发中出现过两次，这项测试直接解析拼好的脚本，第一时间报错。

  - 卡片显示在派出那一步下面，结论折叠带预览；并排对比时两列并排展开。
  - 父任务读取完整报告后独立核对，再合并清单。
- 卡片宽度限制在阅读列内（修正了长预览撑宽卡片的问题）。

## 第 3 块：子代理（2026-09-25，第二部分：成果整合与冲突）

**做了什么**

- **按文件看差异**：整合对话框里，每个文件显示子任务版本与主工作区的差异，与"结果与审查"用同一种差异视图（未改变的行可展开）。对话框加宽到 1040px，差异和合并编辑器在对话框内部滚动；窄屏时占满宽度。
- **两边都改过的文件可以三方合并**。以前遇到这种文件直接拦下（"主工作区在子任务开始后也改了这个文件"），现在由宿主做三方合并（`git merge-file --diff3`，原基线取自独立工作树创建时的提交）：
  - 没有冲突：显示自动合并的结果，确认后用它整合。
  - 有冲突：在合并编辑器里处理。每处冲突旁边有"用主工作区 / 用子任务 / 两边都保留"三个按钮，也可以直接编辑。冲突标记还在时不能勾选整合。
  - 准备审查时宿主再核对一遍：必须带版本号（内容已变就拒绝，要求重新读取）；结果里不能有冲突标记；不能与主工作区现状相同。审查卡上显示的就是将要写入的文本。
- **为什么用 diff3 样式**：默认样式会把两边共有的行（比如函数末尾的 `}`）移出冲突块，这时"两边都保留"会丢掉这一行，得到语法错误的代码。真实运行中遇到了，已改正并加了回归测试。
- **子任务失败原因改成白话**：先说原因和下一步怎么做（例如"用完了可用的执行轮次"），原始错误码保留在下方。

**真实任务证据**（MiniMax-M3，coding-sandbox，独立工作树写入）

- 流程：在对话框里准备独立工作树 → 审批 → 填写分工（longestStreak 加测试）→ 选"并行写入"发送。子任务在自己的工作树里实现、提交，npm test 通过。
- 制造冲突：在主工作区同一文件末尾另加了 `checkInCount`。
  - 整合对话框标出"三方合并有 1 处冲突"。
  - 点"两边都保留"→ 勾选 → 准备整合审查 → 批准。
  - 主工作区得到两个完整函数，npm test 29/29 通过。
- 第一次点"两边都保留"得到的代码缺一个 `}`（即上面说的默认样式问题）。改用 diff3 后，同一场景重跑通过。

**这次发现的问题（需要你决定）**

- **写入子任务跑满 8 个模型轮次就被 SDK 停下**（TOOL_FAILED "too many tool turns"）。父任务派出时如果没给轮次，子任务就用 SDK 默认的 8 轮。这次 4 个子任务里有 2 个因此失败，父任务自己重新派出才完成。提高这个上限会影响费用，按约定由你决定。
- 5 次派出审批只产生了 4 个子任务：有一次派出已经批准但没有执行，结果面板里如实显示为"已批准，但执行未完成"。

**测试**

- 新增 writer-integration-conflict，覆盖：
  - 无冲突时的自动合并；
  - 冲突标记的格式（两边完整，中间是原基线）；
  - 两边都在文件末尾追加函数时，冲突块里两边各自完整；
  - 四种拒绝：没有给结果、结果里还有标记、与现状相同、内容已经变了。
- 相关 329 项中 328 通过、1 跳过。workspace:typecheck、boundary:check 通过。

## 第 4 块：长任务与上下文（2026-09-25）

**先发现的两个真实缺陷（基准测试里暴露）**

- **长会话第 10 轮就用不了了。** SDK 每开一轮，都会把之前所有轮次的原文（包括每次读文件的完整输出）当作"必需上下文"重新带入，而且只在一轮内部整理，不跨轮整理。所以累计超过窗口（默认 12 万 tokens）后，新一轮直接被拒绝（CONTEXT_BUDGET_EXCEEDED）。基准会话每轮读两个文件，第 10 轮就停了；真实编码会话只要反复读大文件，也会碰到。
- **一次被拒绝的启动会把会话锁死。** 宿主在调用 SDK 之前就记下了"启动意图"，SDK 拒绝后这条记录没有对应的执行。重新读取会话时，它被当成"结果未知"，之后每一轮都提示"需要核对"。

**做了什么**

- **跨轮自动整理（类似 Claude Code 的自动 /compact）**：新一轮开始前，宿主看上一轮结束时的上下文用量。
  - 超过窗口的 60%、你手动要求整理、或会话已经整理过一次时，这一轮不再带入原文历史，改为带入宿主写的**前面对话摘要**：每轮的要求、结局、结论、改动文件。
  - 摘要明确告诉模型："工具输出的原文没有带入，需要文件内容请重新读取，不要凭记忆"。
  - 摘要有上限（2.4 万字）：最近三轮保持详细；更早的先缩成一行；还放不下就写明"更早的 N 轮从略"，不会悄悄丢掉。
  - 如果 SDK 仍然拒绝，就自动改用摘要重试一次。
  - 摘要从执行记录现算，不另存任何账本；SDK 没有改动。
- **被拒绝的启动不再锁死会话**：打包上下文阶段就被拒绝时（此时 SDK 还没有创建执行），记为"已拒绝"，不算"结果未知"，重启后也一样。
- **按模型窗口打包**：模型标明的窗口比运行时默认值小时，按模型的来（只会更小，不增加费用）。每轮都记下用的是哪个窗口。
- **上下文用量**：宿主把最近一次主调用的完整提示（按服务方计数）记为这一轮的上下文用量；整理调用不计入。缓存部分没报全时标"约"。
- **读取与会话长度无关**：
  - 每次刷新只带最近 6 轮的完整内容。更早的轮次只发一行摘要，而且摘要有变化才发；未变的轮次只发指纹。
  - 工具输出只发时间线会显示的行（其余只记行数）。
  - 往上翻时自动按页加载更早的轮次（每页 10 轮，每帧画 2 轮，从近到远），正在读的位置不动。顶部也有"显示更早的 N 轮"按钮，可以用键盘或读屏操作。
- **审查列表按会话读取**：以前每次刷新都带上全部轮次的 id，并返回全部审查历史。现在按会话查：待处理的全部返回，已结束的只返回最近 30 条，其余一键展开；而且只在结果面板打开时才读。
- **上下文与用量面板**（发送按钮左边的圆环和百分比，类似 Cursor 的上下文圆环、Claude Code 的 /context 和 /cost）：
  - 上下文用量和窗口；
  - 下一轮是否整理及原因；可以"下一轮整理上下文"，也可以取消；
  - 本会话的输入、输出、缓存读取用量；
  - 费用：服务方没有返回价格时写"未知"，不写 0；
  - 预算：按万 tokens 设置。达到 80% 和 100% 各提示一次，圆环显示"超预算"，**不会停下**（按你的拍板）。
- **摘要轮次的显示**：你看到的是自己写的那句话，上方折叠一行"带入了前 N 轮的摘要 · 工具输出原文没有带入"，点开可以看完整摘要。计划、报告、任务板、继续上一轮这些地方都只取你自己写的那句。

## 第 5 块：会话之间（2026-09-25，方案 A + B + C，不开 D）

按你的拍板：模型拿不到任何跨会话工具；委派出去的任务不会自动执行。三种关系沿用 FlyLeaf 的协作协议：**谁执行、谁写入**。

**A 引用其他会话的固定成果**

- "固定材料"里新增"其他会话的固定成果"和"本会话的固定成果"，包括固定报告、固定变更、确认计划。每一项都标明来自哪个会话。
- 选中后按固定版本带入这一轮，和其他材料一样冻结在这一轮的记录里。正文会写明："只读引用固定版本：记录的是那一轮当时的情况，不代表当前工作区，也不授权任何操作。"
- 固定变更按文件列出差异。原记录没有保存 diff 时，由原审查的改前、改后内容算出（带 3 行上下文），并写明审查结果是否已写入。第一次实测只带出了 219 字的标题，模型拿不到改动正文，已经修正。
- 来源被归档或不可读时，会明确显示"材料已归档或不可读"，不会拿当前内容顶替。

**B 相关会话（只读）**

- 结果面板新增"协作与相关会话"：列出你委派出去的、委派给你的、以及你引用过其成果的会话，显示各自的状态，可以一键打开。
- 这是宿主的只读投影，不交给模型。

**C 委派与交付**

- **委派**：在"+"菜单里选"委派给新会话"，填写任务，并勾选要一起交给对方的固定成果。
  - 宿主新建一个会话：任务放进它的输入框，勾选的成果作为它的材料，模型和工作区沿用发起的会话。
  - 对方接受并发送后才开始执行，不会自动运行。
- **状态机**（沿用 FlyLeaf）：已收到 → 已送达 → 已接受 → 执行中 → 已完成；另有拒绝、取消、失败三种结束方式。
  - 每一步都有回执，不能跳级。
  - 在接收的会话里直接发送第一轮，记为"发送第一轮即视为接受"，再进入执行中。
  - 结束之后才到的操作（比如完成后又点取消）只记录为"在结束之后到达，只记录"，不改变结果。
  - 最多转交 3 层。
  - 每次写入都是对原记录的原子替换：内容已被别人改过就拒绝，不会覆盖。
- **双方各有权限**：只有接收方能接受或拒绝（拒绝必须写原因）；只有发起方能取消，也只有发起方能决定是否收下交付。
- **交付**：接收的会话完成一轮后，可以把这一轮的报告（交付时自动固定）或已固定的变更交回，附一句说明。
  - 发起方可以"收下并作为下一轮材料"：委派完成，交付的成果自动加入下一轮材料。
  - 也可以"不收下"并写明原因：对方看得到原因，可以修改后再交付。
- **显示**：
  - 接收的会话顶部有一条委派横幅，显示来源、内容，以及接受 / 拒绝 / 交付操作和回执。
  - 发起的会话在结果面板里显示每个委派的状态、交付记录和回执。
- **存储**：委派记录存在插件自己的存储里，宿主或 SDK 都没有新增账本；重启后状态和回执不变。

**实测中发现并修正的问题**

- **委派出去的会话用错了工作区。** 新会话默认用项目当前选中的目录，而当时选中的是第 3 块测试留下的独立工作树，所以 C 在那里找不到要测的函数。模型没有编造，而是停下来问人。已改为沿用发起会话的模型和工作区。
- **收下交付后，发起方页面上的材料选择还是旧的**，下一轮发送时会把刚收下的成果覆盖掉。已改为收下后重新读取材料。
- **会话列表不能滚动。** 列表内容溢出后，较早的会话压在"新建编码会话"按钮上，而且滚不到。这是之前就有的问题，已修正。
- 协作卡片里较长的会话名撑宽了结果面板，已改为自动换行。

**真实任务证据**（MiniMax-M3，coding-sandbox）

- **A 引用 B 的固定变更**：新建会话 A，在材料里选中会话 B（"给 createHabit 加输入校验的单元测试"）的固定变更。模型据此说出 test/habits.test.ts 新增了哪些用例、各测什么（例如 createHabit("Read", [3, 7]) 应该报错），并且注明这是那一轮的固定版本，不代表当前工作区。

- **修正后的第二次委派**：A 委派"为 checkInCount 补 3 个边界测试"。
  - C 的横幅显示"已送达，等对方接受"；点"接受并放进输入框"后，用执行方式发送。
  - 审批了 2 次写入、1 次 `npm test`：补了 3 个测试，24 项全部通过。
  - C 交付第 1 轮的报告，附一句说明。

- **重启**：重启服务后，A 和 C 两边的状态与 6 条回执都没变（已提交 → 已送达 → 已接受 → 开始执行 → 交付 → 收下）。
- **用上交付的成果**：A 下一轮带着 B 的固定变更和 C 交付的报告，重新读取 test/streaks.test.ts，逐条核对报告里说的三个测试都在；同时如实说明自己是只读，没有重新运行测试。

**测试**

## 第 6 块：体验（2026-09-25）

**做了什么**

- **语法高亮**：
  - 覆盖回答里的代码块，以及变更阅读器、整合对话框里的差异行。
  - 支持 TS/JS、JSON、Python、Shell、CSS、HTML、SQL、Go、Rust、Java/Kotlin、C 和 diff。颜色取自主题色，深浅色都能看清。
  - 高亮只把文本切成带种类的片段，再用文本节点拼出来，模型写的内容不可能变成页面标记。
  - 富文本净化原来会去掉代码块的 `language-*` 类，所以代码块的语言信息丢了；现在只放行这一种类名。
  - 差异按文件扩展名逐行着色。跨行的块注释和字符串会按行断开，这是有意的取舍。
- **逐字推送**：新增宿主能力 `agent.run.wait.v1`。
  - 页面持有某个版本时，宿主一直等到这一轮的内容出现变化（或超时）才回答，并把 40 毫秒内到达的增量合成一次。
  - 页面收到后只重画这一轮。常规刷新在执行中从 350 毫秒放慢到 1.2 秒。

  - 不可用的命令不会出现在列表里（例如没有执行中的一轮时，不显示 /stop）。

- **@ 引用文件**：在词首输入 `@`（或全角 `＠`）弹出工作区文件列表，文件名匹配的排在前面，选中后插入 `@路径`。
  - 发送时，宿主通过只读的文件读取能力（Coding 新声明使用，只读、不带任何批准权）读取提到的文件，附在任务后面，标明是"发送这一刻的内容"。
  - 每个文件最多附 2.4 万字，一轮合计最多 6 万字；超出的写明只附了前多少行。读不到的文件会写明原因。

  - ⌘⇧P / Ctrl+Shift+P 打开命令面板：同一套命令，外加"切换到某个会话"，支持模糊匹配。

  - 输入框下方显示提示："/ 命令 · ⇧⌘P 面板 · ⌘ / Ctrl ↵"。

## 第 7 块：Git 与工程流程（2026-09-25，push 与 PR 按你的拍板做，每次经宿主审查）

**做了什么**

- **Git 面板新增"提交与分支"**（Coding 左栏的"文件"视图里，和 VS Code、Cursor 的源代码管理一样）：
  - 显示当前分支、远端跟踪分支、领先 / 落后几个提交；
  - 提交说明框，可以"按暂存内容生成"草稿；
  - 按钮：提交 N 个已暂存文件、推送（没有远端分支时一并建立）、建 PR，以及分支的新建 / 切换；
  - 最近 6 次操作的结果，例如"已提交 a14330d …"、"已推送到 origin：* [new branch] …"。
- **每个操作都是一次宿主审查**，沿用 SDK Effects 的审批、执行与核对机制。新增操作类型 git-operation，工具限定为 git-commit、git-branch-create、git-branch-switch、git-push、git-pr-create。
  - 审查卡列出：仓库、当前分支、提交说明原文、暂存的文件、远端地址、推送哪些提交、执行范围（会运行仓库的 hooks；不强制推送；不推送远端等）。
  - **准备时锁定仓库状态**：HEAD、分支、远端跟踪分支、暂存内容。审批后执行前会再核对一次，只要变了就拒绝执行。实测中审查期间多暂存了一个文件，提交被拒绝，没有把别的内容提交上去。
  - 命令不经过 shell，也不会停下来要求输入：使用这台电脑上已有的 Git 凭据和 GitHub CLI 登录，宿主不保存、不读取任何密钥；超过 2 分钟就停止。
  - 审查标题写明是什么操作（"Git 提交：…"、"推送：…"），不再是笼统的"工具操作"。
  - 操作结果（提交号、推送范围、PR 地址）在执行成功后记下，显示在操作记录里。
- **建 PR 前先检查条件**：没装 gh、gh 没登录、远端不在 GitHub、分支还没推送，都会先说清楚，按钮保持不可用。
- **从 Coding 一轮直接提交**：改过文件的一轮完成后，卡片上有"提交这些改动…"。
  - 点击后，用这一轮你写的要求、结论要点和改动文件拼成提交说明草稿，把 Git 面板切到这一轮的工作区并放入草稿。你暂存、修改说明后再提交，每一步仍经过审查。
  - 草稿标题取你自己写的要求。如果这一轮是"让它继续"或"从断点继续"，会先去掉产品拼出的那层说明。
- **"只说了下一步就结束了"的一轮**：MiniMax 实测中出现过，回答"我先读 README.md 确认……"之后就结束了，一个工具都没调用，但这一轮显示为"完成"。
  - 现在这种情况的卡片写"这一轮只说了下一步就结束了：模型说了要做什么，但没有调用任何工具就结束了，所以什么都还没做"，并提供"让它继续"。
  - 继续需要你点击，不会自动发送。直接作答的讨论不会被误判。
- **修正第 3 块的一个回归**：主工作区里已暂存的文件，整合时应该拒绝（暂存的改动是你的工作），第 3 块的三方合并误把它也纳入了合并。已恢复为拒绝，只有未暂存的偏离才走三方合并。这次扩大测试范围后才发现。

**真实流程证据**（MiniMax-M3；coding-sandbox 的独立工作树；远端 origin 是本机的一个 bare 仓库）

1. Coding 一轮修改 README.md（审批写入）→ 点"提交这些改动…"→ Git 面板切到这个工作区，草稿里有要求、结论和改动文件。
2. 暂存 README.md（审查"暂存文件"）→ 提交（审查卡显示提交说明和暂存的文件）→ 得到"已提交 09112ff"。
3. 新建分支 feature/checkin-docs 并切换过去（审查）→ 完成。
4. 推送并建立远端分支（审查卡显示远端地址、"整个分支（远端还没有这个分支）"、不强制推送）→ 远端出现 feature/checkin-docs@09112ff，面板显示"↑0 ↓0 · origin/feature/checkin-docs"。
5. 建 PR：远端是本机路径，面板说明"不在 GitHub 上，目前只支持经 GitHub CLI 建 PR"，按钮不可用。
6. 又一轮只说了"我先读 README.md……"就结束，卡片如实显示；点"让它继续"后下一轮改好 README，再从草稿暂存并提交 → "已提交 a14330d"，领先 1 个提交。

建 PR 没有在真实 GitHub 上实测：那需要一个 GitHub 仓库，而且是对外可见的操作，要你来决定。已用测试里的替身 gh 核对传给 gh 的参数和返回地址的解析。
