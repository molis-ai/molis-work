## 1. 最值得保留的结论

**写代码的人最可能为 Work 留下来的原因，是跨多次工作之后，仍然知道“答应交什么、已经交了什么、还差谁确认”。** “能同时开几个 Agent”“能把 Claude 的上下文交给 Codex”已经有现成解法，不能单独承担定位。

先验证三种场景：

1. **代码说做完了，但产品还没验收。** 把每条要求的支持记录和人的验收分开，让未完成项继续可见。
2. **做着做着，交付条件变了。** 改约定需要对应授权；人能看见改了什么、影响什么，后续会话读到同一份现行约定。
3. **隔几天或换个 Agent 继续一个较长的交付。** 接着同一份要求、进度和缺口工作；不用依赖某一段聊天总结作为唯一依据。

三者都不是市场独占。更值得检验的是：Work 能否把这些步骤做得比“GitHub/Linear + 规格文件 + CI + 手动交接”更顺，而且不用维护第二套互相矛盾的任务账本。

**最重要的产品边界：Goals 控制的是目标记录和完成生效，不等于控制外部 Agent 的全部代码操作。** 外部 Agent 若持有独立文件写权限，Work 的约定门禁不能被写成“它绝不会改错代码或越界”。同样，Agent 报告是来源之一，不是 Work 已独立验证结果。

| D5 中 | 维护者并行处理文档、测试补齐、依赖升级，但只想看真正等自己的几件事 | 多窗口与 PR 容易分散注意力；审查能力才是瓶颈。Willison 的直接经验支持这一点，但不是总体统计 [U6] | 目标与会话关联、当前缺口/待决定、条件提醒；潜在减少“挨个问做到哪” | 不能由“有通知”推导通知有用。并行桌面已有完善状态与待办；若 Work 仍要求重复抄进展，就可能增加负担。需观察实际提醒命中率与人工回查次数 |

| D7 中低 | 独立开发者兼写技术文章，做完功能后想从具体版本整理发布说明和演示素材 | 代码 PR、产品约定、文档和素材分散；读到新的文档却误当作当时交付版本 | 固定成果版本、Pages、资料引用、目标结果关联，有机会覆盖开发之外的交付 | 本轮没有直接用户访谈证明这一步足够痛；当前导出、引用粒度、版本回看链路须实操。应作候选，不凭“工具多”列为优势 |
| D8 未来 | 开发者、产品负责人、客户支持围绕同一问题讨论，确认需求，Agent 实现，产品验收 | 信息经群聊→工单→PR→验收，在各处重复同步；成熟团队已有 GitHub/Linear 等方案 | 项目讨论、目标、Agent、成果在同一工作环境内衔接是清楚的产品方向 | 人与人的共享项目、@ 通知、助理进群不能从 Agent 间共享项目板推导；10/17 审查已指出这些层次不同。按 main/分支/需求逐步标记，演示不能伪装当前团队产品闭环 |

八个场景可收拢为四个底层需求：

- **交付含义稳定**：D1、D2。人、Agent、测试与正式验收各自说的“完成”能对应起来。
- **跨工作片段继续**：D3、D4。带走的是当前约定和来源，不只是最近聊天。
- **把注意力用在需要判断的地方**：D5、D8。减少找状态与重复解释，而不是多产生通知。
- **把反复用的方法留下来**：D6、D7。工具和资料能在后续工作里复用，但只有高频重复时才值得新增系统。

旧框架里按用途划分的一级章节可以保留；上述具体案例放进相应章节。每个场景必须给到角色、触发与结果，不能只写插件串联。

## 4. 三个优先深案例

### 案例 A：上线支付，测试过了，手机体验还没有验收

**角色**：独立开发者，既实现也决定产品是否可交付；也可扩展成有明确验收负责人的产品工程师。不是“所有程序员”。

**起因**：原约定包含支付成功、失败恢复、旧订单兼容、手机完成支付四项。Agent 交了自动化测试记录；最后一项需要真人设备判断。

**现在的办法**：任务清单 + CI + PR review。它不是无效办法；若团队一直严格执行，而且要求与检查已有一一映射，Work 的额外价值可能很小。痛点发生在“CI 绿了/Agent 说完了”被复制成“全部交付”时。

**Work 的最短场景脚本**：

1. 人确认结果和四条要求，把手机体验标为本人验收。
2. Agent 回报代码与自动化检查，只为覆盖的要求提供支持。
3. 收尾显示还差手机验收；保留已交的结果，不让用户把全部过程再走一遍。
4. 人在实际构建上体验后给结论；若失败，记录具体缺口，继续同一个目标；若认可且其他条件满足，再正式完成。

**最关键的设计点**：结果页必须让普通读者一眼区分“Agent 报了测试”“机器结果可查”“本人已看过”。当前协议只证明第一类报告与人的有效结论分开，不证明独立机器核验已存在。人工验收不该塞进每个微小任务，否则系统会制造批准疲劳。

**为何可信**：Kiro 的一个 2026-10-05 报告提供了运行停止却标完成的具体故障，维护者次日确认应调查；spec-kit 3/16 报告给出任务勾选与实现不符的例子 [U1][U2]。两者支持这类故障存在，不能推导出现比例或新版本仍普遍失败。

**竞争反例**：Conductor 的 todos 可拦合并、Claude 的 TaskCompleted hook 可阻止任务完成、Factory QA 可设 required check [F5][F6][F7]。Work 不应声称首创完成门禁；应比较是否已给用户做好“哪些必须由人判断、哪条还缺、结论属于哪个约定”的整套体验。

**可以验证/推翻的方向**：在一个真实发版里放入一项自动化无法代替的验收。比较原流程与 Work：双方能否都稳定留住未验项，找到缺口要翻几处，用户是否愿意第二次继续用。如果原流程同样清楚、更少记账，停止把它包装成独占优势。

### 案例 B：兼容旧数据太难，Agent 想把承诺改小

**角色**：对交付范围有最终决定权的独立开发者或项目负责人。

**起因**：Agent 实施后发现成本高，提议取消兼容旧数据。真实问题是“重要取舍谁来做、按哪版约定验收”，不只是“Agent 有没有照步骤走”。开发中合理调整方案完全可能；不能把一切偏离计划都认定为错误。

**Work 的最短脚本**：保留现行要求 → 提出“取消兼容”的具体变更及影响 → 人拒绝或同意 → 更新后的要求供之后每个会话读取。拒绝就继续原承诺；同意也保留旧约定和原因。新 Agent 不能拿一段“用户同意了”的聊天摘要自行批准另一项变更。

**已经核对的协议事实**：初始结果、普通记录和权限内新增要求不机械增加批准；替换既有结果、修改/退掉要求、去掉人验收需要该具体变化的授权；版本冲突先读差异，不能偷偷换版本号重试。出处是当前本地协议文档第 23–35 行。

**不能跳过的边界**：如果外部 Agent 绕开 Goals 直接改代码，Goals 不会因此自动防住代码改动。官网应演“约定变更被交回人手里”，不演“所有越界修改都被全局防火墙拦住”。真正生产落地仍需要代码评审和运行权限。

**现有替代**：仓库规格 + PR review 让变更可审阅；计划模式、hooks 和受保护分支可以组合出更强约束。Work 的候选价值是让这件事不依赖每次重新写提示词/找散落记录，但是否更轻便仍需实操。

**可证伪优化**：决策卡展示“原要求→新要求、受影响结果、为什么现在要改”，一处回复即可回到原任务。拿三种真实决定验证：放宽验收、修改实现方式但不改结果、无关小补充。若三种都被挡成大审批，说明边界和体验不合理，应先改粒度而非增加更多确认。

### 案例 C：周一写到一半，周三换一个会话继续

**角色**：任务常跨天、经常中断的产品开发者；可以一直用同一家 Agent，不强行要求多 Agent。

**起因**：周一完成后端，周二人改了接口约定，周三新会话只拿到周一的总结。代码文件能恢复，但“今天该按什么做、什么仍不算完”容易不一致。

**Work 的最短脚本**：打开原目标 → 读当前约定和未完成项 → 看到周二的决定及影响 → 确认本次工作目录与版本 → 从下一步继续 → 将部分结果留回原目标。必要时跨 Runtime 开新会话，仍引用同一份 Goal 事实。

**价值重心**：不是让 Agent 记住每句话，而是让它读取可更新、有明确负责方的工作状态。保留有用背景，但不给旧聊天高于现行代码和约定的优先级。

**竞争反例**：Superset 会向另一 Agent 传最近上下文；OpenAI 官方插件提供 Claude→Codex 的持久线程转移；Traycer 的 artifacts 本来就跨对话存活 [F2][F3][F4]。这些必须在比较里承认。

**仍然可能有的差别**：接着已有要求的验收状态工作，且人作过的关键决定不靠新 Agent 重述。为此用户需要持续记录；若必须每回话手工同步，价值会被维护成本抵消。

**可证伪优化**：交接预览只显示当前结果、变更后的要求、未完成项、相关成果版本、工作目录和已知顾虑，并让用户删去不想外发的材料。用一次真实隔日接续做比较：新会话是否重复已做工作，是否遗漏周二的变更，准备交接花了多少人工操作。只测同厂商，再测跨厂商；不把换模型当成功本身。

## 5. Why Work：应该留下哪些，暂时不要拔高哪些

| 候选说法 | 推荐写法 | 何时它有说服力 | 反例与不适用对象 |
|---|---|---|---|
| 完成有依据 | **每条要求做到了哪、还差谁确认，都留在同一个目标里。** | 交付跨会话，且有真人验收或多个结果需要汇合 | “自己记一个 checklist 就够”的微任务；已完备落在 CI/PR 里的团队 |
| 改约定由人决定 | **AI 可以推进工作；要放宽约好的结果，先把取舍交给你。** | 确实有范围、成本、体验的实质取舍 | 不等于所有实现细节都须审批，不等于阻止所有代码越界 |
| 人、工具与 Agent 继续 | **换会话以后，接着的是同一份要求、进度和未完成项。** | 长任务反复切换且有最新变化必须继承 | 同一个会话内的几分钟工作；只求跨模型聊天转移者已有方便替代 |
| 工具按方法长 | **把反复要做的那套检查做成工具，下次你和 AI 都能用。** | 高频、有固定输入输出、多入口会调用 | 一次性脚本、现有 CI 已足够、生成后维护比手工更麻烦 |
| 主动且有分寸 | 先作场景内细节：**有新材料与当前目标相关时再提醒，内容变了旧建议也失效。** | 提醒有可观察的真触发，并能减少漏事 | 本轮没有足够直接证据说明用户愿意接受更多主动提醒；不能提前宣称“懂你的工作” |

优先放前面三个；后两个留在场景或全景里继续验证。**“本机 + 多模型 + 插件 + 权限”是重要实现条件，但“四样合起来别人没有”不是用户购买理由**。应说这组条件在某件事上让用户少承担什么，而不是拼稀有功能组合。

## 6. 旧调研里需要纠正的推断

1. **“没有跨厂商交接”不能保留。** 五份原报告彼此矛盾；本轮打开的 Superset 与官方 Codex 插件已构成直接反例。
2. **“并行产品只管窗格、没有长期共享任务”过强。** Traycer 明确有跨对话保存的 spec/ticket/review；Linear 也不是只有一个临时聊天。没有在某页找到某项字段，不能推导整个产品不存在。
3. **“只有 Work 有完成门禁”不成立。** 已有 hooks、阻止合并的待办与必过 QA；应该比较门禁对象、谁能改变条件、结论对应哪一版，而非有/没有二分。
4. **“改约定/收尾必须全部由人点头”不准确。** 当前 Work 允许权限内记录和新增；只有指定的验收与实质变更需要对应授权。
5. **“安全”不能从 Goals 授权推到任意外部 Agent 的文件权限。** 目标事实控制与执行环境控制是不同边界。
6. **公开 issue 是具体事件，不是市场规模。** #3476 由记忆产品创始人提出，有自荐动机，本轮降为设计线索；不能拿它独自证明大量普通开发者有同样痛点。
7. **不要靠星数、品类占比推付费需求。** 多厂商有人用，尚不能证明愿意另装 Work 维护状态。必须看真实任务中重复解释、遗漏验收的代价。
8. **供应商资料证明机制，不能代替用户证据。** 本轮把“厂商提供 transfer”和“用户因此持续痛苦”分开，后者还要访谈。

## 7. 继续补研与产品优化：按能推翻假设的实验来排

以下是建议，不是已排期/已实现。

| 优先级 | 假设与最小实验 | 观察什么 | 停止或调整条件 |
|---|---|---|---|
| 1 | 找一个真正跨天的交付，用现有工具与 Work 各走一次，不换任务标准 | 要求遗漏、被误判完成、找当前状态的步骤、维护两套记录的次数 | Work 没减少回查/遗漏，反而引入重复记账：先解决导入、引用与回写，不堆新 Agent 功能 |
| 1 | 把支持来源明确区分为 Agent 陈述、可打开的机器产物、本人验收；先做现有页面的标记与跳转评审 | 用户是否误以为“有报告=已核验”；能否找到对应版本和失败项 | 标签仍被误读，或机器结果没有可信来源：不叫“核验”，不允许状态自动升级 |
| 1 | 决策卡试三类真实变更：承诺缩水、实现路径改变、普通记录补充 | 是否在真正要取舍时出现，授权范围是否清晰，批准后是否顺畅接回 | 日常小事被频繁挡住：调整边界；仍能用无关批准放宽承诺：先修权限与作用域 |
| 2 | 借已有规格文件/PR 为目标提供引用，先试一个格式，不做多系统双向全同步 | 用户能否只维护一份要求；版本漂移能否被发现 | 无法明确谁是事实主人，就暂停双向写入，保持单向引用/导入 |
| 2 | 用原有发版脚本试做一个 Work 动作，不先生成复杂插件 | 人、助理、外部 Agent 是否调用同一检查；输出可否回到原目标 | 只能多一个按钮但没有复用价值：保留脚本即可 |
| 2 | 从一次日常工作观测“需要你”的提醒 | 真正需要人行动的比例，是否打断专注，同一事是否重复出现 | 用户关闭它或靠人工刷新更可靠：先调触发与合并，不增加提醒渠道 |
| 3 | 访谈两组各 4–6 位作为小样本：单 Agent 但跨天交付；多 Agent/多厂商重度使用 | 要求展示上周真实任务，找最后一次漏验收/改约定/重讲背景，不问“你喜不喜欢这个功能” | 受访者没有近期实例，只认同概念：降低场景优先级，不把愿景当已验证需求 |

这组样本量只是建议的探索规模，不能做总体发生率统计。亲手竞品对照建议先选 Traycer、Superset 与“GitHub + 原有 Agent + CI”的组合，不必把十几家都装一遍；真正的基准是用户已经在用且不愿放弃的流程。

## 8. 日更如何逐章 review，避免只追功能名字

每个新增能力除 main/分支/需求状态外，再回答五个问题：

1. 改变了上面哪个场景中的哪一步？目标用户是谁？
2. 带来新的完整闭环，还是只完成一个入口/协议/视觉演示？
3. 之前真实痛点的证据有没有因此变强，还是只是“技术上能做”？
4. 竞品/现有工作法是否已经覆盖；Work 的额外维护成本是什么？
5. 官网今天可说什么、只能示意什么、仍要现场证明什么？

例如“新增输入回执”不能只写成更可靠：应在 D2 里检验用户中途补一句“不改数据库”后，是否能看见这句话被何时采纳、哪些已开始动作不受它影响、还需何处检查。它也不能直接推出“AI 已理解并遵守全部要求”。“Coding 能等外部 CI”应看 D1 是否只是节省轮询模型消耗，是否真正把 CI 对到本次代码与要求；这两层不能合并成“已验证完成”。

## 10. 旧演示思路：应保留、应重写

补充阅读范围：完整阅读既有场景框架，以及历史介绍小样的可见正文和场景脚本。没有做浏览器视觉或交互验收；旧演示的动画用硬编码文字推进，不是后台动作跑通的证据。这些旧材料不是公开文件，此处只保留叙事与产品边界的判断，不引原文，不列文件名与章节。

### 应保留的思路

1. **从一件事讲到底，而不是每个插件发一张功能卡。** 旧开发者线始终围绕同一件事：从报错、修复、复核，到手机上验收和发版清单，一步指向一步。这比十个互不相关的小演示更有说服力。新版可以把一个实例贯穿“今日变化→场景→Why Work”，并明确当天只改善了哪一站。
2. **同一机制给两类角色不同的具体收益。** 保留“写代码 / 写文档、管事情”的入口，但按各自实际任务选案例。写代码的人可能需要多 Agent 交接；写文档的人更可能需要来源可回查、观点与依据分开、修改回到稿子里。不要仅替换名词，强行让两边都有同样的“换模型”情节。
3. **“你和 AI 用同一个工作台，工作台按你的用法长”仍应是产品总纲。** 旧框架里负责人的决定已经把插件创作、流程和越用越顺手放在核心位置。本报告把验收/约定列前，是写代码人群的 Why Work 候选排序，不是把整个产品重新定义成目标管理或验收管理器。
4. **先呈现端到端体验，再解释技术为什么能接起来。** 旧框架把页面按钮、浮条、助理、流程、MCP 的真实连接列出，并单列缺口，这种写法可直接用来约束新文档：统一动作目录解释“同一个动作不同入口”，单一事实主人解释“改动回到原处”，插件契约解释“新工具也能接入”。不是先讲技术名词后补应用想象。
5. **“收、想、写、排、推进”适合功能全景，实际场景另按目标来分。** 场景不能写成 Feed→Cognia→Dataset→Pages 的图标串；要说用户拿到什么、下一步为什么发生、需不需要人判断。比如技术写作的终点是可交付且能核查的稿子，插件数量本身不是结果。
6. **保留“人把精力留给判断、创造和生活”的收束，但当愿景写。** 旧结尾的时间轴可以表达方向；没有观测数据，就不暗示已经每天节约几小时、必然早下班。

### 应重写或重新核对的内容

| 旧演示的写法或情节 | 问题 | 更可靠的写法/演出 |
|---|---|---|
| 用“递 / 接 / 长”这组词作章节标题 | 后续 work-split 已要求去掉这套标题；但底层体验仍有价值 | 直接写动作与结果：资料带着来源进稿子，隔几天继续同一个交付，把每周重复的检查做成工具 |
| 把“换个 AI 接着写”作为文档人群的中心情节 | 负责人已明确不认同为此人群强塞换 AI 需求 | 改成同一篇稿子经历找资料、插引用、本人修改、交稿，内容与依据一直找得到；换模型只在真实用户有此需求时出现 |
| 暗示背景和提示词都不用写，每一步点一下就行 | 演示刻意隐藏初始配置、目标选择、错误关联和检查成本 | 说明已接入项目，选中报错后可先检查带上的背景再交给 Agent；演示一次关联错误如何修正，否则不能称丝滑 |
| 测试数字出现后目标自动变完成 | 把 Agent 陈述演成独立核验；读者可能误读为代码质量保障 | 标“Agent 提交的测试记录”，点击可看对应产物；人的体验验收独立保留。没有可信产物接入时，不画“已验证” |
| 改约定、算完成都要你点头，Agent 只能提 | 忽略了权限内新增、普通记录和不要求人验收的完成 | 放宽约好的结果、或需要本人验收的项，必须有对应授权或结论；把需要决策的条件讲清楚 |
| 周五自动跑完发版清单并把草稿写进 Pages | 旧框架自己注明定时任务当时只能只读，不能从有流程推导定时可写闭环 | 由主 Agent 核当前 schedule/workflow 能力；未核实前可作为需求示意，并标明具体缺口，不混写已可用 |
| 一句话就得到可用工具，马上能串进流程 | 创作台仍有设计、生成、检查、修订与安装；历史小样不能证明稳定的生成质量 | 把需求交给创作台，检查、调整后装进工作台，下次从页面或 AI 调用。历史小样不能代替当前质量验证 |
| 固定示例里的修复时间与数值互相对不上 | 动画内部技术细节不自洽；而且改容忍窗口不是已证明正确的修法 | 不把修法细节当装饰。改用已核实的故障和修复过程，或明确只展示“定位并修复验签失败”的概念流 |
| 竞品对比写成“对话助手都要手搬、文档 AI 只认当前工具、别的 AI 用不了你做的工具” | 把功能边界写成了全市场绝对判断；与当前集成、MCP、transfer、共享规格等机制冲突 | 比较一个具体任务里用户要维护哪些资料、哪步仍要人工、Work 多了什么成本；产品名与版本可查，不用“其他都不行” |
| 支持 MCP 的 Agent 都能调用你做的插件 | 统一动作不代表每个动作都暴露给每个 Agent；还受声明、启用、作用域和授权约束 | 按插件声明和授权，可供页面、助理、流程或外部 Agent 调用，正文用可验证的一个实际调用例子 |
| 团队案例里选一个方案，所有目标、Agent、待办自动跟上 | 决策被记录、受影响项被标记、外部 Agent 实际采纳、团队成员收到是四个层次 | 分别演示已保存决定、哪些事项受影响、哪些已确认采纳、哪些还等人；主 Agent 核对分支/需求，不能用一段飞线替代完整闭环 |
| 没实现和分支都叫开发中 | 旧文粗粒度状态不能支撑日更与官网输入 | 内部每项分“发布 / main / 分支实现 / 需求或设计 / 演示假设”，补证据和待核项；官网可简写，但链接回内部出处 |

旧框架有一个值得改进的研究顺序：先看插件密度，再推“适合哪些人”，容易反过来为库存功能找人。新日更应先保留用户上周实际在做的任务和失败证据，再看哪个新增功能改变了它。两条都可保留：功能全景保证不遗漏，用户场景负责判断是否值得讲，Why Work 只选其中已经有证据和成立条件的少数案例。

建议写代码人群的连续场景顺序是：**发现一个值得修的问题 → 携带已确认要求交给 Agent → 跨天继续且看见变化 → 复核未覆盖的情况 → 人验收关键体验 → 把可复用检查留下来。** 主角是完成一件工作；多模型、插件、目标和流程在需要时出现。每一幕写明“今天新增后少了哪一步/少漏哪件事”，而不是把全部未来能力集中演成已经顺畅完成。
