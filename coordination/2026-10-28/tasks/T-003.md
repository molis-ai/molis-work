## 5. 做法

**已定（main 上核过）**

- 文件的形状照 `tests/shipped-plugin-lifecycle-content.test.ts:1-33`：文件头注释（英文，写明 `RAC-1200`、`RAC-1201` 与 w6-02 文档），一个 `Record<string, Shipped>`，`const walked = "added, removed and added back in a project, revoked, upgraded and uninstalled"`，每项一个 `test`：名字以编号开头、以 `${walked}` 结尾，第三个参数是 `{ timeout: 180_000 }`，函数体是 `walk(…)`。
- 两个插件都不在新项目的默认名单里（登记上没有 `default_enabled`，`apps/local-host/src/plugin-registry.ts:199` 只取有它的），都不是个人插件：所以都写 `joins: true, stops_when_removed: true`，例子在 `tests/shipped-plugin-lifecycle-coding.test.ts:43-46`。
- 两者的项目键和 id：`feed`／`io.molis.work.feed`，`inbox`／`io.molis.work.inbox`。
- 伙伴规则（`modules/projects/src/project-service.ts:108-165`，Feed 登记上 `companions: ["inbox"]`，`plugins/native/feed/src/registration.ts:17`）：加入 Feed 会带入 Inbox；从项目移出 Feed，Inbox 留着；移出 Inbox，Feed 一起走。所以 Feed 这一项移出、加回都只动 Feed，不需要 `removed_by`；Inbox 这一项的项目里不加 Feed，它的移出也就只动它自己。
- 撤的权限用默认 `storage:private`：Feed 的权限全是必需（`plugins/native/feed/src/permissions.ts:21`），Inbox 的 `storage:private` 也是必需（`plugins/native/inbox/src/manifest.ts:44`）。
- Feed 是双实例（`registration.ts:12-15`）：Home 一半只是引用账（`plugins/native/feed/src/home-plugin.ts:7-12`），人写下的数据在项目一半。所以 Feed 写 `scope: "project"`，走查跟着项目一半的安装。Home 一半的三个动作只给插件调用（`plugins/native/feed/src/content-ledger-actions.ts:17,23,29` 的 `audiences: ["plugin"]`），不应进人的目录；`callable()` 里要是出现了它们，这是夹具要不要认识「双实例」的问题，停下来问。
- Feed 的写入与读回：写 `POST ${routes}/sources`，body `{ kind: "custom_rss", name: title, feed_url: "https://example.com/feed.xml" }`（`plugins/native/feed/src/source-route-handlers.ts:13-18`、`route-input.ts:9`；登记不联网的例子见 `tests/connector-consumer-usages.test.ts:97`）；读 `GET ${routes}/snapshot` 的 `sources[].name`（`route-handlers.ts:15-23`，形状见 `query-actions.ts:30-36`）。不调 `sync`，不联网。新项目的来源应该是空的；不空就在 `titles` 里按名字过滤，例如只留以你写入的名字开头或结尾的（`.filter(name => name.endsWith(…))` 一类）。
- Inbox 没有「人写一条带标题的东西」的路由：`plugins/native/inbox/src/actions.ts:59-90` 只有读列表、改状态、生成文稿、绑定判断规则，事项由 Feed 的消息和来源故障生成（`plugins/native/inbox/src/content-actions.ts:74-75`）。它自己存的只有判断规则的绑定（`POST ${routes}/judgment`，要一个已发布规则的 `function_key`）。所以 Inbox 这一项按「没有自有数据」写，照 Diff、Text Stats（`tests/shipped-plugin-lifecycle-coding.test.ts:58-63`）：`write: async () => undefined`，`kept: []`，`titles` 读 `GET ${routes}/entries` 的 `entries[].entry_id`。文件头注释和测试名要写明：读回一个空列表不是留存的证明（w6-02 文档第 17 行），这一项有意义的是撤权、升级、卸载、重启。除非【方案】找到一条只走路由的、能让 Inbox 有一条带标题事项的办法并经统筹批准，才改成有数据的写法。

**【方案】里要回答的问题**（先把两项写出来在本机跑一遍，把结果写进去，再等批）

1. Feed 一项跑完整遍的结果：过了，或停在哪一步、实际答什么、期望答什么。尤其这几处：
   - `POST /sources` 与 `GET /snapshot` 在没有模型、没有连接的临时 Home 里的状态码与字段；`snapshot` 路由还读规则、建议和连接状态，它们在这个 Home 里能答吗；
   - 移出之后路由答 `403 actions.plugin_disabled`：Feed 是双实例，Home 一半先把路由交给项目那条链，是哪一层答的；
   - 卸载：`uninstall(…, { retain_private_data: false })` 对 Feed 项目一半成不成，Home 一半的引用账在，会不会拦；卸载后路由答 `404 actions.missing`。
2. Inbox 一项同样的结果。单独加入 Inbox（项目里没有 Feed）能启动、`GET /entries` 能答吗，读回是不是 `[]`。
3. Inbox 有没有只走路由、不直接写库的造条目办法？有就写出来并给出理由，没有就写「没有，按没有自有数据写」。
4. 把夹具弄红一次的办法：例如临时去掉 Feed 的 `write`，看第一个读回断言红，确认用例真读了东西；写出你打算怎么做。
