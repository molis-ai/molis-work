## 1. 背景

时间顺序，依据都在 main `df9635d7b`：

1. 有一次启动或恢复正在跑。起点有两类：人点「重试」或「解除隔离」（`apps/local-host/src/plugin-route-operations.ts:76-79` 调 `supervisor.restart`）；页面、事件、路由第一次用到一个还没在跑的插件（`supervisor.ts:433-453` 的 `ensureStarted`，不在跑就 `restart`）。两条都落到 `PluginRuntime.start` 或 `recover`，在 `startOnce`（`index.ts:456-491`）或 `recoverOnce`（`:567-613`）里，等着 `executor.start(...)`（`:466`、`:587`）。这时插件的启动代码手里拿着本次的 activation 上下文（`activateContext`，`:727-732`，由 `activation-context.ts:6-25` 造）。
2. 项目的启用名单变了，某个请求里的刷新（`apps/local-host/src/project-plugin-enablement.ts:28-44`，每个项目请求都先跑，`project-plugins.ts:117`）把这个插件判为「关」：先 `supervisor.revoke`（`:35`）。Supervisor 看到这个插件忙（`#pending > 0`），只记撤销、不排停止（`supervisor.ts:267-296`，忙的分支在 `:285`）。接着刷新自己调 `runtime.stop(state.install_id)`（`:39`）。只有 Supervisor 状态里已经有 `install_id` 才会走到这一步，也就是说这个插件以前启动过。
3. `PluginRuntime.stop` 在拿生命周期锁**之前**同步撤销当前上下文：`index.ts:443` 的 `revokeContext(installId, true)`。这是写明的做法（`packages/plugin-runtime/README.md:87`「在返回 Promise 前撤销」），`tests/plugin-model-service.test.ts:367` 靠它。停止本身排在锁后面，等第 1 步那次启动结束才跑（`:444`）。
4. 第 1 步里的启动代码接着用上下文：任何一次 `requireGrant` 都抛 `plugin.grant_denied`（`activation-context.ts:17-19`）。启动函数收到这个错：
   - `startOnce` 的 `catch`（`:477-490`）撤上下文、把记录写成 `crashed`，`last_error_code` 是 `plugin.grant_denied`，再抛 `plugin.executor_failed`「已记录为 crashed」。
   - `recoverOnce` 的 `catch`（`:599-612`）同样写 `crashed`，并且 `recovery_count` 加 1（`:605`）；到了上限（默认 3，`:570`）或是「解除隔离」那一次（`releaseQuarantine`），写成 `quarantined`（`:601-604`）。解除隔离前一步还把记录先改成 `crashed`（`:586`），失败才恢复隔离，所以被停用打断的解除隔离也会重新隔离、并且 `recovery_count` 加 1。
5. 排在锁后面的停止这时跑 `stopOnce`：记录已是 `crashed` 或 `quarantined`，不是 `running`，抛 `plugin.state_invalid`（`:496-498`）。刷新里的 `.catch` 把它吞掉（`project-plugin-enablement.ts:39-41`，T-007 加的）。T-034 之后，`crashed` 的停止会记成 `disabled`，但此时记录是第 4 步写的那条，`last_error_code` 和 `recovery_count` 已经错了。
6. Supervisor 一侧是对的：`restart`、`#activate` 每次 await 之后都查 `#revoked` 和 `#epochs`（`supervisor.ts:455-493`、`:542-570`），返回 `plugin.revoked`（`:607-631`）。所以界面上看到的是「插件已撤销启用」，Runtime 记录却写着崩溃。

用户看到的后果（推断，没跑）：这个插件被关掉之后，Runtime 里是 `crashed`（或 `quarantined`），带着一个其实是自己被停用造成的 `plugin.grant_denied`；之后名单把它加回来，`#restart` 因为记录是 `crashed` 走恢复（`supervisor.ts:480-488`），花一次恢复预算；每被打断一次花一次，三次就被隔离，要人手动解除。

为什么修在 Runtime，不在刷新里：「撤销再停止」这个组合有五处调用（`project-plugin-enablement.ts:35-39`、`home-plugin-http.ts:126-127`、`installed-plugin-lifecycle.ts:165-167`、`installed-plugin-exposure.ts:51-53`、`installed-publisher-standing.ts:41-42`）。问题出在 Runtime 把「被停用打断」当成「插件崩溃」，改刷新只盖得住一处。

可选的做法：

- 不改：留着错的记录，代价上面已写。
- B（默认）：Runtime 在 `startOnce`、`recoverOnce` 的 `catch` 里认出「本次上下文已被撤销」，这次失败是被取消，不是崩溃：不写 `crashed`，不加 `recovery_count`，解除隔离的那一次把隔离恢复原样，抛 `plugin.state_invalid`（Supervisor 已经按 `#revoked` 报 `plugin.revoked`）。保留「stop 同步撤销」这一条写明的行为。
- C：停止发现有激活在进行时不立刻撤销，等启动结束。否决：一个挂住的启动会让「马上收回授权」不成立，`README.md:87` 和 `plugin-model-service.test.ts:367` 都靠立即撤销。
- D：只改刷新：吞 `plugin.grant_denied` 或先等 Supervisor。否决：见上，只盖一处，而且记录已经写错，吞错误不撤回记录。

选 B 的取舍：它认的是「上下文被撤销」，不是「错误码是 `plugin.grant_denied`」。插件可能捕获 `grant_denied` 再抛别的错，或根本不再用上下文就失败；按撤销认，覆盖得全，代价是启动本来就会失败、恰好又被停用时，记录不写崩溃（停用在先，用户要的就是关，这条失败不再有意义）。哪个判法见第 11 节。

## 2. 目标

1. 启动被停用打断：`Runtime.start` 以 `plugin.state_invalid` 失败，记录保持启动前的样子（`installed` 或 `disabled`），`last_error_code`、`recovery_count` 不变，没有写 `crashed`；排在后面的停止照常把它记成 `disabled`（`RAC-1465`）。
2. 恢复被停用打断：`Runtime.recover` 同样失败，记录仍是 `crashed`，`recovery_count` 不加，不会因为这次打断被隔离（用 `maxRecoveryAttempts: 1` 钉：现在一次打断就隔离）；之后排着的停止把它记成 `disabled`（`RAC-1466`）。
3. 解除隔离被停用打断：记录回到 `quarantined`，`recovery_count` 与 `last_error_code` 和打断前一样；排着的停止仍被拒（隔离不被一次停止绕过，T-034 保留的行为）（`RAC-1467`）。
4. 启动、恢复自己真的失败（没有人停用）：行为不变：启动失败写 `crashed` 并抛 `plugin.executor_failed`，恢复失败 `recovery_count` 加 1、到上限隔离（`RAC-1468`）。
5. 项目刷新那一串（`supervisor.revoke` 再 `runtime.stop`）打断一次 `supervisor.restart`：Supervisor 报 `plugin.revoked`，Runtime 记录是 `disabled`、`recovery_count` 没动（`RAC-1469`）。

## 3. 不做

- 不改 Supervisor（`supervisor.ts`）：它每个 await 之后都查撤销，是对的。
- 不改这五处调用，包括 `project-plugin-enablement.ts` 和 `home-plugin-http.ts:127`（Home 停用没有 `.catch`，隔离中的插件被停用会抛 `state_invalid`，那是 T-034 之后仍存在的另一件事；不做，不开行）。
- 不改「stop 在拿锁之前同步撤销」，不改 `README.md:87` 那条的意思，只补一句。
- 不改 `stopOnce`（T-034 的）和 `reportCrashOnce`。
- 不新增错误码、不新增 Error 子类：抛现有的 `plugin.state_invalid`。新码要动合同、错误模型主人表和公开 API 快照，不值得。
- 不处理「启动代码挂住不返回」，也不处理「启动代码根本不再用上下文」（那种启动成功，之后排着的停止走正常的停止，不在这里）。
- 不新增 `private` 方法：`PluginRuntime` 在 `giant-exceptions.json` 里的 `methods` 要保持 29，见第 4 节。
- 不新增 S 号。撤销的语义没变，授权仍然立刻收回；变的只是失败记账。AGENTS 硬约束 3 说被撤销的调用不再写业务记录，这里的 Runtime 安装记录不属于「业务记录」，但方向一致；要不要把它升成 S 条目，见第 11 节。
- 不写兼容或迁移：不读存量数据，已经被错记成 `crashed` 的记录不回补（它们和真崩溃分不开）。
