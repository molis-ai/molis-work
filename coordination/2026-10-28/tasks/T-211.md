# T-211 Goals 项目说明的单条上限与总长上限按字数数，含两单元字的说明不再被多拒，错误信息里的「个字符」成真

> **可领，依赖无。成立：项目长期说明（用户确认过、长期交给 Agent 遵守的项目规则，`goals.guidance.add` / `goals.guidance.update` 写的那几条）有两个上限——单条 4000、项目里生效的合计 32000。代码对两者都用 `.length` 数，数的是 UTF-16 单元；错误信息却写「个字符」，归档的 spec 也写「字符」。一个字（码点）可能占两个单元（如 `😀`，U+1F600），所以含这类字的说明两千多个字就超单条上限，合计也一样早到顶。超限不是截，是整条拒绝：单条超限抛 `goals.project_guidance.entry_too_large`，合计超限抛 `goals.project_guidance.total_too_large`（种类都是 `invalid`），什么都不写。起草时按 MISC 的要求核了动作 schema 和下游：它们都不数这段文字（见下），只有这三个文件在数，所以改成按字数（码点）数。**

**修法起草时定、写死：**
- 判断：`module/guidance.ts` 里 `normalizeProjectGuidanceContent` 之后加两个函数（模块内部用，`module/index.ts` 不转出，包入口看不到）：
  - `projectGuidanceLength(value)`：`[...value].length`，数字数；
  - `withinProjectGuidanceEntryLimit(value)`：`value.length <= PROJECT_GUIDANCE_ENTRY_MAX_CHARS * 2 && projectGuidanceLength(value) <= PROJECT_GUIDANCE_ENTRY_MAX_CHARS`，单条上限的判断；
- 调用方：单条两处（`guidance-add.ts:46`、`guidance-update.ts:69`）的条件换成 `!withinProjectGuidanceEntryLimit(content)`，错误信息一个字不动；合计两处（`guidance-add.ts:89`、`guidance-update.ts:136`）里的 `.length` 换成 `projectGuidanceLength(…)`，数字 4000、32000 留在 `guidance.ts` 原处；
- 单位：字（码点），上限数 4000、32000 不变。放宽，不收紧：旧规则放行的（单元数不超过 4000），字数一定不超过 4000，新规则也放行；合计旧规则放行的（单元合计不超过 32000），字数合计一定不超过 32000，新规则也放行。所以没有任何说明因此变成被拒，库里已有的说明不需要处理；
- 有界：一个字最多两个单元，所以单元数超过 `4000 * 2` 的串，不用数就知道超限，直接拒，不展开；只有不超过 8000 个单元的串才展开（最多 8000 个元素）。理由：`content` 在动作 schema 里没有上限，调用方能送任意长的串，展开一个几百万单元的串要占几百 MB（T-197 第 1 节量过，拍平的 3600 万个单元的串展开约 2.7 s 到 6.4 s、多占 1.0 到 1.7 GiB）；
- 合计不需要这层界：合计里展开的只有两样——库里已有的生效说明（每条都过了单条检查，至多 8000 个单元；合计只数生效的，字数合计不超过 32000）和这次要写的 `request.content`、`next.content`（它们在单条检查之后才进合计；停用与恢复用的是库里的原文）。所以 `projectGuidanceLength` 只给已经过了单条检查的串用，函数的注释写明；
- 拒绝不是截取：内容、分类、原因、确认摘要、幂等回执的写法一个字不动；归一化（换行统一成 `\n`、去首尾空白，`guidance.ts:24-26`）仍在数之前；空白、未确认、未知分类、重复、`no_changes` 等检查一个字不动；
- 不抽常量、不改错误信息文字：四句「…个字符」信息现在名副其实；
- 用例：新文件 `tests/goals-guidance-characters.test.ts`，31 个 test，全部通过 Goals 的公开命令（`GoalProjectApplication.goals.commands.addProjectGuidance` / `updateProjectGuidance`，`readProjectGuidance`，夹具 `tests/fixtures/goal-application.ts`）调用，不直接 import 被改的函数（它们没有从任何包的入口导出，门禁也不许），也不点名 Goals 的包名。

## 2. 目标

## 8. 与默认不同的

1. **单位：字（码点），上限数仍是 4000 和 32000；不是「把数改成 8000 和 64000」。**统筹觉得要保持按单元（只把数翻倍），在【方案】阶段说，起草线改书。理由：
   - 信息说「个字符」，归档 spec 说「字符」，房子里同类的上限都按字数数（T-093、T-094、T-096 已合入），动作 schema 的 `maxLength` 也按码点数；一个字最多两个单元，翻倍会让只有一单元字的说明放到 8000 个字，比原意宽一倍；
   - 放宽不收紧，没有任何说明因此变成被拒（见开头「修法起草时定、写死」）；
   - 代价：含两单元字的串要数字数，所以有第 3 条的有界写法。
2. **范围多收了合计两处**（MISC 那一行只点名单条）。理由见开头；代价是多改两行、多三个 test（RAC-2113）和三个变异。统筹不要这一半：把 `guidance-add.ts:89`、`guidance-update.ts:136` 和 RAC-2113 去掉，其余不变，在【方案】里说。
3. **有界写法只给单条：先比 `value.length <= 4000 * 2`，再展开；不是循环数到 4001 个字就停，也不是无条件 `[...value].length`。**统筹对 T-200 的指示就是「单元数超过上限两倍的先拒、不展开」，本单照同一个思路。另外两种，统筹可以裁：
   - 循环（T-197 的 `wholeCharactersWithin` 的写法，逐个字取、超出就停）：也有界，但会迭代超长串的开头；那里要截取，这里只要判断，一行比较更直白；
   - 无条件 `[...value].length <= 4000`：就是变异 M6，`content` 没有 schema 上限，几百万单元的串会占几百 MB。
4. **用例走公开命令，不直接调被改的函数；RAC-2112 靠改写 `String.prototype[Symbol.iterator]` 计数。**
   - 两个函数在 `module/guidance.ts`，不从包入口导出（`module/index.ts` 不转出它）；新测试文件 `import "../plugins/native/goals/src/…"` 会让「测试引用包内部」的数字 0 变 1，点名 `@molis-ai/molis-work-plugin-goals` 会让「插件包名在自己的包之外被点名的文件数」加一（`tests/fixtures/goals-modules.ts` 文件头写了这条规矩），都不许；所以走 `GoalProjectApplication`，同 `tests/goals-command-module.test.ts`；
   - 代价：31 个 test 各开一份项目库（临时目录里的 SQLite），比纯函数用例慢，但仍是秒级；
   - RAC-2112 的计数是一个只在这一次同步写里生效的全局改写，数「超过 8000 个单元的串被展开或迭代」的次数。起草时看过命令到 `readAddRequest` / `readUpdateRequest` 之间的路径，单条检查之前只有 `normalizeProjectGuidanceContent` 的 `replace`/`trim`，没有展开，所以正确写法下计数是 0；**但没有在真实仓库里跑过**。若修好之后 RAC-2112 红在 `iterated`（不是 0），先确认函数顺序没写错（第 5 节第 1 条的第一条说明），写对了仍红，说明应用链路别处也迭代了长串：停，把 `iterated += 1` 那一行临时加上 `console.log(new Error().stack)`（只在本地，不提交）看是谁，贴到 #1332 问统筹，不要放宽断言；
