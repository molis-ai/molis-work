# Operations and organizational workflow

Connect roles, permissions, tools, exceptions and measurements into an operation that can continue.

For: Organization processes, Service operations, Cross-role work.

## Planning path

1. Define service outcome and trigger
2. Assign roles, permissions and tools
3. Design handoffs and exceptions
4. Separate setting up the capability from operating it
5. Run, record evidence and propose finite improvements

## Required coverage

| area | label | question |
| --- | --- | --- |
| roles_responsibilities | Roles | Who can own each task with the available commitment? |
| permissions | Authority | Who approves which action? |
| tools_workflow | Workflow | Where are facts recorded and handed off? |
| exception_handling | Exceptions | How are blocks, conflicts and failures handled? |
| measurement | Measurement | How are efficiency, quality and outcome observed? |

## Dependency rules

| rule_id | statement | direction_hint |
| --- | --- | --- |
| workflow-after-ownership | Workflow and tooling depend on agreed roles, permissions and actual capacity. | workflow depends_on roles and permissions |
| improvement-after-measurement | Improvement uses real operations, exception records and measured outcomes. | improvement depends_on operational evidence |

## Completion evidence

- Confirmed roles
- Real process walk-through
- Outcome metrics

## Closeout checks

- Runs with available commitments
- Exceptions have an owner and a recovery action
- Recurring operations do not keep the setup Goal open

## Common mistakes

- Copying a large company's process
- Responsibility without capacity
- Records disconnected from work
- Permanent open Goals for recurring work

## How to use this method

- Think the work through along the planning path first, then list each result that can be delivered and accepted on its own as one item; do not mix several main results into one.
- Every required-coverage question that bears on the task needs an answer; a key question without one is listed as open, not hidden behind a vague item.
- A dependency means consuming a result: B depends on A only when B cannot start or finish without A's accepted output. Order of discussion, timing, the same owner or the same file are not dependencies; work with no such relation stays parallel. Judge each dependency rule, and say which output is missing when one does not apply.
- State for each item what proves it is done (completion evidence), and run the closeout checks before finishing.
- Describe finite changes that can be completed; ongoing operation is not an item that never ends.
- When used with other planning methods, put their key results side by side, see which consumes which, and bring in the method that provides anything missing.
- Show the breakdown to the person first. When they want it in a tool (for example an installed Goals plugin), write it with that tool's own actions, with their confirmation.
