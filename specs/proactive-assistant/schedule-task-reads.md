## 1. 用户的决定

2026-11-04，经统筹转达：

1. **按任务勾选**：建定时任务时，由用户勾选它能读哪几类（待办、Inbox、日程、目标）。这份授权只给这一个任务，可以随时撤回，不跟助理共用。
2. **「日程」的口径**：Jelly 日历加 Schedule 的提醒；待办的日期算在待办查询里。

## 2. 产品检查

**从结果倒推。** 用户在 Schedule 里新建或打开一个定时任务，写「每天 8 点，列出跟进日已到的在等事项，以及今天的日程和卡住的目标」，在「能读的数据」里勾上待办、日程、目标，确认一次。第二天 8 点任务自动跑，用户在这条任务的对话里看到结果。中途撤回某一类，下一次运行就读不到那一类，结果里如实说「没有授权读日程」。

**每一步站不站得住**（产品治理第 3 节）：

| 步骤 | 保护或解决什么 | 缺哪个事实或决定 | 之前给过没有 | 怎样少打断 |
| --- | --- | --- | --- | --- |
| 勾选能读的数据 | 无人值守的 Agent 只能读到用户同意的那几类；用户决定的范围 | 这个任务要读哪几类 | 没有：授权按任务，不借助理的 | 只在建任务或改范围时出现一次；不勾就是原来的「读项目文件」任务，不多一步 |
| 确认 | 写入授权的必须是本人（安全不变量 S-17） | 本人的确认 | 没有 | 勾选与确认在同一个平台面里一次完成，不先在插件里勾、再到平台确认一遍 |
| 插件改了读取能力后再确认 | 不在用户不知道时扩大可读范围（「发现不扩权」，§5.4） | 新的能力要不要读 | 只确认过旧的 | 只在任务卡片上标「有一类需要重新确认」，下次打开时处理，不弹窗 |

**已有的授权接着用。** 任务停用后再启用、Schedule 停用后再启用、版本升级而读取能力没变，授权都还在，不重新问。

**AI 的部分。** 角色提示词不写动作 id 和版本，Agent 经目录查找（Prologue 手册的工具位置）。读不到就如实说读不到；模型漏查、误读不按症状补丁，结果的依据在回复里列出所读的来源。

**归谁。** 「按任务的授权主体」是平台能力：以后工作流程、场景 Skill、别的插件的后台任务都会要（第 4 节第 2 项）。Schedule 只是第一个用的。

**别漏掉的路径。** 没有可读的来源（项目里没装这些插件）；勾选后插件被停用；撤回一类；归档任务；卸载 Schedule；删项目；第一次和第二次进入任务表单；中英文两种界面。

## 3. 设计

### 3.1 授权主体怎么标识

新的主体是一个**任务主体**，客户端 id 写成

```
agent:task:<project_id>:<plugin_install_id>:<subject_key>
```

- `project_id`、`plugin_install_id` 由宿主从当次调用上下文取（S-17），插件给不了；`subject_key` 由插件给（Schedule 用自己的 `task_id`），宿主只接受 1～120 个 `[A-Za-z0-9_-]` 字符。
- 前缀 `agent:` 让它沿用 Agent 受众（`apps/local-host/src/mcp-action-grants.ts:17` 的 `actionClientAudience`），所以只能用 `audiences` 里含 `agent` 的动作。
- 同一个插件的不同任务、不同项目里同名的任务、别的插件用同样的 key，得到的都是不同的主体，互不相借。
- 一个插件只能为**自己的安装**发起和使用任务主体：插件给的只有 `subject_key`，前面三段宿主填。

### 3.2 记在哪、谁写、谁读

**记在哪。** 沿用逐客户端动作授权的那份记录（`config/mcp-tools.json`，`apps/local-host/src/mcp-settings-store.ts`）：一条授权就是一个 `McpActionGrant`（客户端、项目、动作、版本、提供方、接受的权限、启用），带 `generation`。不新建表、不改记录形状，所以没有库结构变化，也不需要升级步骤。选它的理由：逐次核对、撤权后排队调用被拒、权限变了就不认这些规矩（S-08）都已经在这份记录上，换一处存就要再写一遍。

**按什么粒度记。** 用户勾的是「类」，记下的是**这一刻**目录里这一类的每个只读动作各一条：

- 「类」就是提供这些动作的插件：目录里本项目可见、`audiences` 含 `agent`、`operation` 为 `query` 的动作，按提供方分组。名单从目录来，宿主里不写插件名（硬约束：不另写名单）。待办 = Todo，Inbox = Inbox，日程 = Jelly 与 Schedule，目标 = Goals；装了别的、有只读查询的插件，也会作为一类出现。
- 界面上每一类写明包含什么（例如 Jelly 写「日历与笔记」），用户知道勾了什么。
- 只读动作才收：宿主建授权时拒绝 `operation` 不是 `query` 的动作。
- 以后提供方新增或改了只读动作，已勾的类**不自动扩大**：新动作没有记录，读不到；版本或权限变了的动作，原记录不再匹配（`matches` 的现有规则），读不到。宿主在读授权时报出「这一类有未确认的读取能力」，任务卡片上标出来。

**谁写。** 只有本人，经平台自己的确认面：

- 平台动作 `agent.task_grants.set@1`：受众只有 `user`，输入是任务主体（插件安装与 key）和勾选的类；宿主在执行时重新读目录、展开成动作记录、整体替换这个主体的记录。插件、Agent、MCP 客户端、工作流都调不到（S-17 的同一条规矩）。
- 平台动作 `agent.task_grants.clear@1`：受众 `user` 和 `plugin`；插件只能清**自己安装下**的主体。只减不增，所以给插件是安全的（Schedule 归档任务时调）。
- 平台动作 `agent.task_grants.list@1`：受众 `user` 和 `plugin`，插件只能列自己安装下的主体；一次返回这个安装在本项目的全部主体与各类状态（已授权、需重新确认），任务列表打开时调一次，不按任务逐个请求（开工前检查第 9 项）。
- 「对外接入」一页（`apps/local-host/src/mcp-action-access.ts:54`）目前把授权里出现过的客户端 id 都列成可编辑的客户端：任务主体要从那份列表里排除，改在「授权与放行」一页按任务列出，可撤回（D 轨）。

**谁读。** 只有宿主：插件 Agent 服务启动这一轮时把主体交给动作客户端；每次 Agent 调动作时由 `authorizeMcpActions` 重新读。

### 3.3 运行时怎么用

1. Schedule 到点调 `services.agents.run({ role_id: "brief", title, task, grant_subject: task_id })`。
2. 插件 Agent 服务（`apps/local-host/src/plugin-agent-service.ts`）：
   - 只有 `workspace: "business"`、`execution: "read-only"` 的角色才接受 `grant_subject`；别的角色带了就拒（`actions.input_invalid`）。
   - 带了 `grant_subject` 的，启动请求设 `action_gateway: true`，动作客户端的身份换成任务主体（`preparePlugin(caller, subject)`，`apps/local-host/src/agent-host-composition.ts:263` 的 `actor_id` 从固定的 `agent:${runtimeId}` 改为由这里传入；审计作者照旧 `agent:<runtime>:<会话>`）。
   - **没带的业务角色不给网关**：插件启动的 Agent 不能借内置 Agent（`agent:prologue`）那份共用授权。这是今天的行为，写成不变量钉住。
3. 网关（`horizontal/agent-host/src/run-start.ts` 的 `frozenGateway`）：角色只读，`operate` 为 false，写类工具一律回「只能读」（`adapters/prologue-action-gateway.ts:243`、`250`、`368`），这一层不用改。
4. 目录：`find-capabilities` 只列这个主体被授权的动作（`resolveMcpActionContext` 按 `client_id` 过滤）。任务主体**没有默认放开的动作**：`openByDefault` 对任务主体一律 false，连项目资料也要勾（最少权限；项目资料作为一类出现、默认不勾，统筹 2026-11-04 定）。

### 3.4 撤权、停用、删任务之后

| 发生了什么 | 结果 | 由谁做 |
| --- | --- | --- |
| 本人撤回一类或全部 | 下一次动作调用起就被拒（`mcp.action_revoked`）；已在排队的调用也被拒 | 平台确认面或「授权与放行」调 `set`／`clear`；每次调用重新读记录（3.5） |
| 任务停用 | 不再到点运行，授权留着；再启用照旧能读 | Schedule 现有逻辑 |
| 任务归档 | 授权清除 | Schedule 归档时调 `clear`；宿主另在读取时核对：插件的 `list` 结果里找不到对应任务的主体，由 Schedule 在对账作业里清（防止漏清） |
| Schedule 停用 | 插件 Agent 服务拒绝启动（安装不是运行中、`agent:run` 不在授权里，`plugin-agent-service.ts:35` 的 `check`）；授权留着，再启用照旧能读 | 现有 |
| Schedule 卸载 | 这个安装下全部任务主体的授权清除 | 宿主卸载插件的动作（`plugins.installed.uninstall@1`，`apps/local-host/src/plugin-install-actions.ts:123`）按 `agent:task:<project>:<install>:` 前缀清 |
| 删项目 | 这个项目的任务主体授权清除 | `ProjectDeletionService`（`apps/local-host/src/project-deletion-service.ts`）按 `agent:task:<project>:` 前缀清 |
| 提供方停用或卸载 | 那一类的动作不在目录里，调用被拒；记录留着，提供方回来、形状没变就恢复 | 现有目录与授权规矩 |
| 动作版本或权限变了 | 旧记录不匹配，读不到；任务卡片标「需要重新确认」 | 现有 `matches` 规矩 + `list` 报状态 |

### 3.5 无人值守只能读，每次调用都重新核对

- **只能读**有三层，任一层都够：角色 `execution: "read-only"`（网关不给写）；`agent.task_grants.set` 只收 `query` 动作；到点的一轮一旦需要人确认就被取消（`plugin-agent-service.ts:110`）。
- **每次调用都重新核对**：任务主体的动作客户端走现有的 `authorizeMcpActions`（`apps/local-host/src/mcp-action-client.ts`），每次 `discover`／`invoke` 都重新读授权记录和目录、按调用开始时钉住的记录比世代（`pinMcpActionGrants`），执行前的最后一次同步检查（`assert_authority_current`）再读一次。插件安装与 `agent:run` 授权由插件 Agent 服务的 `check` 每 100 毫秒及每次调用前核对。

### 3.6 Schedule 一侧

- **新角色** `brief`：`workspace: "business"`、`execution: "read-only"`、`host_tools: []`（业务角色可用的宿主工具都不需要），提示词 `schedule-brief`：说明手边是经目录查到的只读能力、读不到就说读不到、回复第一行的 IMPORTANT 标记沿用。原 `reader` 角色不变。
- **任务种类不存表**：有任务主体授权的任务用 `brief`，没有的用 `reader`。到点时 Schedule 用一次 `agent.task_grants.list`（或按单个主体读）决定。所以 Schedule 的表、动作输入输出都不变，不碰 05 批的升级链（「首次改库结构前 U1 必须就位」）。
- **就绪检查按种类**：`tasks.readiness` 的输出不变（`model`、`workspace`）；页面按任务种类解读：读数据的任务不要求工作区，要求至少一类已授权；读文件的任务照旧要工作区。
- **归档清授权**：`tasks.archive` 成功后调 `agent.task_grants.clear`；对账作业（现有 `SCHEDULE_RECONCILE_JOB`）顺手清掉已归档或不存在任务的主体。
- **界面**（用户 2026-11-04 定样，见 3.7 末）：任务详情里「能读的数据」一段，放平台区域（3.7）；任务列表的每行标出种类（读文件／读数据）和「需要重新确认」。新建任务改在详情里直接写，不再弹对话框；能读的数据在任务建好后选。

### 3.7 勾选与确认放在哪（要定样，并发预警）

插件页面的代码不能代表本人写授权：插件页面调的是插件自己的路由和动作，受众是 `plugin`，不是 `user`；如果插件页面能直接写，插件就能悄悄给自己的任务加权限。所以**勾选并写入**要在平台自己的确认面上完成。方案：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A（推荐）** | Schedule 表单上的「选择能读的数据」按钮请平台打开确认面；勾选框就在平台确认面里，本人勾完点确认，平台写入；回到表单显示结果 | 一次操作完成，可信；确认面由 D 轨做，Schedule（E）只做入口和状态显示。别的插件以后要按任务授权，用同一个确认面 |
| B | 勾选框在 Schedule 表单里，保存时平台确认面列出所勾的类，本人再确认一次 | 勾选和插件表单在一起，但本人要看两遍；插件预填的勾选可能和本人想的不同，确认面要逐类再显示，实际是两套勾选 |
| C | 只在「授权与放行」一页里按任务管理 | 最省开发，但建任务时找不到入口，用户要换页面，违背「建任务时勾选」 |

平台确认面怎样被插件打开（登记的 DOM 事件，还是插件调一个返回「需要本人确认」的平台动作，由工作台接住），在定样时和 D 轨一起定；无论哪种，写入都只走 `agent.task_grants.set` 的 `user` 受众。

**定样结果（用户 2026-11-04）**：不弹窗，选 **F 开关即生效**（[原型](../../docs/design/schedule-task-grants/README.md)）。「平台确认面」落成**插件页面里的一块平台区域**：

- Schedule 只决定它放在任务详情的哪里，给出任务主体的 key；区域里的内容（类别、开关、说明、撤销）由平台画、平台写，插件读不到也改不了。
- 一类一个开关，拨一下就是一次 `agent.task_grants.set`（`user` 受众），平台只认真实的点按（`isTrusted`）；下面一行写刚才的变化，可撤销；有新的读取能力时那一行给「允许」。
- 这是新的平台能力：区域怎样挂进插件页面（DOM 事件或声明的挂点）、怎样防止插件在上面盖一层假的、点按怎样核实，P3 由 D 轨定，作为一条新的安全不变量过评审，测试先在没有保护的代码上红过。
- 「授权与放行」一页照旧按任务列出、可撤回（D 轨）。

## 4. 安全不变量的变化

按 [SECURITY-INVARIANTS](../../docs/system/SECURITY-INVARIANTS.md)第 3 节加一行、改两行。测试都要先在没有保护的代码上红过。

**新增 S-108（暂编，落地时按表顺延）：按任务的授权主体。** 拒绝什么：

1. 别的任务（同一安装、同一项目的另一个 key）拿不到这份授权：用 A 的授权以 B 的主体调，目录里看不到、调用被拒（`actions.missing` 或 `mcp.action_revoked`）。
2. 助理（`agent:prologue`）和外部 MCP 客户端都拿不到：给任务主体授权后，内置 Agent 与 MCP 客户端的目录里没有多出这些动作。
3. 别的插件、别的项目拿不到：同一个 key 由另一个安装或在另一个项目里使用，得到的是另一个主体，没有授权。
4. 撤回后立即读不到：撤回后下一次 `invoke` 被拒；撤回时已在排队的调用在最后一次检查被拒；被拒的调用不写业务记录。
5. 只有本人能写：`agent.task_grants.set` 以 `plugin`、`agent`、`mcp`、`workflow` 受众调，都按没有这个能力拒（`actions.missing`），不留记录；插件调 `clear`／`list` 只作用于自己的安装，给别的安装的主体被拒。
6. 只收只读：`set` 里含 `operation` 不是 `query` 的动作，整次被拒。
7. 不默认放开：任务主体在没有记录时目录为空，项目资料也不例外。
8. 插件启动的 Agent 不借共用授权：不带 `grant_subject` 的业务角色没有网关；带了 `grant_subject` 的非只读或非业务角色被拒。
9. 外部 MCP 客户端的身份不能以 `agent:` 开头（若现有规则已经保证，写出是哪条并加用例钉住；若没有，就是补洞）。
10. 卸载 Schedule、删项目后，对应前缀下的授权记录不在。

测试文件暂定 `tests/security-invariants-task-grants.test.ts`，进 `test:security`（不依赖浏览器，Linux 上能稳定跑）。

**修改 S-08**：授权的客户端多一种「任务主体」，写明它的标识由宿主组成、规矩与 MCP 客户端相同（逐次核对、撤销后排队调用被拒、权限变了不认），并加上「任务主体没有默认放开的动作」。

**修改 S-17**：插件 Agent 一轮的动作身份只从宿主来：任务主体的项目与安装取自调用上下文，插件只给 key；Agent 的工具输入里带主体被拒。
