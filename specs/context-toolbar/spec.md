# 情境浮条：动作出现在用户动作发生的地方

状态：设计已定，未开工（2026-10-02）。三处取舍用户都按推荐拍板（§9），下一步是 S0 高保真切片给用户看。同日与右栏需求（side-shelf）、创建入口（quick-create）合并设计：交叉的部分（浮条也贴着右栏条目与助理面板的结果、落点、`ItemAttach`、分期）以[情境动作总纲](../context-program/spec.md)为准，总纲第 8 节是全部能力的索引。分支 `feature/context-toolbar`（从 origin/main a4e246e0），只有本文件，没有代码改动。

## 1. 用户的话与要解决的事

用户的话：现在的动态动作栏一直在底部，能不能出现在用户动作发生的地方？Pages 里选中文字本来就有一个浮窗工具栏，两者应该合并；综合设计一个方案，把这个浮窗工具栏做成系统级的通用能力：动态行为的逻辑不变，外观用 Pages 选中文字后的那种浮窗，由系统定义通用 UI 结构和协议，各插件填自己的行为。

现状的三个毛病（均已对照代码核对）：

1. **离动作太远。** 情境动作条是输入框上方的固定一行（`apps/workbench/src/assistant-dock.ts:72` 的 `[data-assistant-context-actions]`，`craft-finish.ts:1010` 起的样式）。人在文档中间选了一句话，眼睛要跳到屏幕底部才看得到「改写 / 找依据」。助理面板打开时它还会整个隐藏（`craft-finish.ts:1012`）。
2. **Pages 里同一件事有三个入口。** 选中文字时：①底部动作条；②选区上方的格式条 `pages-format-bar`（`plugins/native/pages/src/editor-browser.ts:2990`，14 个格式按钮 + 一个「AI」按钮）；③点「AI」弹出的写作菜单 `pages-pop`（`openAi`，:3248），它是把底部动作条的方案再抄一遍（`menuActions` / `watchMenuActions` / `chooseMenuAction`，经 `molis:assistant-context-actions` 与 `…-choose` 来回转），底部还有一段只有 Pages 才有的「助理」小节。
3. **只有 Pages 有就地的浮层，也只有 Pages 有成套的选区动作。** 其余 17 个声明了对象的插件（Todo、灵光、Goals、Feed、Cognia、Dataset……逐个见 §10.1）选中文字后，底部一行里只有跨插件的通用动作（查找、记成待办、记下灵光、拆成目标步骤、助理）；它们想加自己的快捷操作没有地方放；Inbox、Artifacts、Characters、Sessions 等还没有声明对象，选中文字什么都不出。

## 2. 方案一句话

做**一个**系统级浮条（`ContextToolbar`），在拥有选区的那个文档里、贴着选区出现，外观取 Pages 现在的格式条。浮条里有两类内容：

- **工具**：插件自己带的、确定的、只作用于当前打开内容的命令（Pages 的加粗、标题、列表、链接、评论）。插件**声明**它们，系统负责画；
- **动作**：目录派生、Host 排序的动态动作（现在底栏上的那些）。逻辑一行不改，只换陈列的地方。

底部动作条和 Pages 的「AI」按钮 / 写作菜单随之取消。

```
选区上方 8px，居中，放不下翻到下方；选区高亮不变，焦点不离开编辑器

   ┌──────────────────────────────────────────────────────────────────────┐
   │ B I U S ‹›│H1 H2 H3│• 1. ☑│A 🔗 💬  ┃ 找依据 │ 提反例 │ 拆步骤 │ 更多▾ │ ✦助理 │
   └──────────────────────────────────────────────────────────────────────┘
     └──────── 工具区：插件声明，位置固定 ────────┘ └──── 动作区：Host 排序，最多 3 个 ────┘
```

- 工具在左、固定不动（肌肉记忆）；动作在右、随内容变化（只淡入、不挪位置，规则沿用 contextual-interaction §3.4）；
- 没有工具的插件（只读页面）浮条只有动作区；
- 「更多」沿用现有菜单（推荐 / 按意图分组 / 整篇 / 全部操作），底部固定一段「助理」：带到助理（只放进输入框）、说出要做什么再交给助理——这是把 Pages 现有的两种交法上收成所有插件共有。**「更多」里没有「发送到」**：创建 Item 类的去处（待办、炼金术士、灵光……）不在菜单里，由 Jev 按当时的上下文推荐最合适的，直接出现在动作区（§10.2）；
- 底栏上的「选区标签」去掉（选区本身的高亮就是范围）；依据点（Jev / 按规则）移进「更多」菜单底部；「助理：有一条建议」变成动作区末尾的「✦助理」，点开是面板槽里的一行输入：说一句话，由助理决定创建什么、放到哪个插件。

## 3. 什么算工具、什么算动作

这条边界决定协议怎么分，也守住仓库硬约束「能力注册一次，由共同目录供页面、工作流、Agent、MCP 使用，不另写名单」。

| | 工具 | 动作 |
| --- | --- | --- |
| 作用 | 当前打开的这份内容的版面与标记，用它自己的撤销 | 读写别的对象、产出新内容、需要预览或批准 |
| Agent / 工作流能调吗 | 不能，也没必要 | 能，是目录里的能力 |
| 谁排序 | 插件（固定顺序） | Host 情境服务（规则 + Jev） |
| 谁执行 | 插件自己的页面 | 动作服务 invoke；页面能接的交回页面（`…-action-chosen`），其余走助理卡片 |
| 例子 | 加粗、标题、列表、链接、评论、颜色 | 改写、总结、找依据、拆解步骤、记进展、翻译成新文档 |

判断口诀：**Agent 会不会也想调它？会就是动作，进目录；只是编辑器里的一个按键，就是工具。** 这条靠评审和插件手册，不做门禁。外壳里不出现任何按 `plugin_id` 的分支。

## 4. 通用 UI 结构（共享件）

- **组件**：`packages/design-system/src/primitives/` 新增情境浮条（DOM 构建 + 样式）。外观就是 `pages-format-bar`：`--paper` 底、8px 圆角、`--shadow-raised`、无描边、4px 内边距、28px 按钮 / 6px 圆角、悬停与开启态 `--nav-hover`、130ms 升起（`pages-rise`）。落地时写进 `DESIGN.md` 与规格板 `/__ui/catalog`（规则：共享控件的改动必须与规格板一致）。
- **定位**：把 `plugins/native/pages/src/floating.ts`（`placeFloating`、`scrollShouldFollow`）和 `editor-browser.ts` 里的 `placeOverlay` / `pinAt` / `followScroll`（含「窗格本身成了 fixed 的参照盒」的校正）上移到设计系统，Pages 改为引用它。
- **谁画在哪**：浮条画在**拥有这段选区的那个文档**里（总纲 §5：右栏的 iframe 格、助理面板同样适用，手上的东西可以在 `main`、`side`、`assistant`）。主文档：画进当前插件舞台的浮层根（舞台已 `isolation: isolate`，层级 z 40，低于助理面板 50）；分屏窗格（iframe）：画在窗格自己的文档里。这样不需要跨 frame 换算坐标、不需要追踪窗格内滚动，焦点和选区也不会跨文档丢失。
- **大脑只有一个**：外壳的情境总线（`context-actions.ts` 里的 `bus`）仍在顶层：收情境、请求候选与判断、保存方案。窗格仍把情境转发上来（`workbench-surface-focus`）、方案仍转发回窗格（`workbench-context-plan`）、选择仍经 `workbench-context-action-choose` 回到总线——这三条现成的消息就是浮条在窗格里工作所需的全部。
- **不抢焦点**：浮条上的 `mousedown` 一律 `preventDefault`，点它不改变选区与焦点；键盘用 ⌘. 进入（现有快捷键）、←→ 移动、Esc 回到原处；`role="toolbar"`，每项有无障碍名称；「可以做：…」的读屏播报保留。

## 5. 协议

沿用 contextual-interaction 的事件与合同（`packages/contracts/src/services/contextual.ts`），只新增下面四处。已有的 `molis:surface-focus`、`molis:assistant-context-actions`、`…-action-choose`、`…-action-chosen`、`molis-work:place-changed`、冻结与失效核对、`prepare()` 全部不变。

**5.1 锚点：浮条贴在哪。** `SurfaceFocus` 加可选字段：

```ts
anchor?: {
  rect?: { left: number; top: number; right: number; bottom: number };  // 本文档视口坐标；编辑器用 coordsAtPos 给，选区形状特殊时（表格单元格选区）必须给
  element?: Element;                                                     // 同文档内的元素；多选的列表行、刚完成的条目
  placement?: "above" | "below";                                         // 默认 above，放不下自动翻转
}
```

缺省规则（插件什么都不写就能用）：`activity: "selecting"` 取当前 DOM 选区的矩形；其余情况没有锚点就不出浮条。现有的「通用 DOM 选区」分支（`context-actions.ts` 里那段）继续生效，所以只写了 `data-assistant-context` 的插件选中文字就有浮条。

**5.2 工具：插件声明。** 插件在情境变化与工具状态变化时，在自己的根元素上派发 `molis:context-tools`：

```ts
interface ContextTools { context_id: string; groups: readonly ContextToolGroup[] }
interface ContextToolGroup { id: string; items: readonly ContextToolItem[]; collapse?: "never" | "overflow" }
interface ContextToolItem {
  id: string;                  // 组内唯一、稳定
  label: string;               // 无障碍名称 + 悬停提示（已翻译）
  icon?: string;               // 设计系统图标名
  glyph?: "B" | "I" | "U" | "S" | "H1" | "H2" | "H3" | "A";  // 字形按钮，限这几个
  pressed?: boolean;           // 开关态（aria-pressed）
  disabled?: boolean;
  shortcut?: string;           // 显示在悬停提示里
  opens?: "panel";             // 点击后由插件打开面板（见 5.4）
}
```

数据是有限的、可清洗的（≤6 组、≤24 项、标题 ≤24 字，其余丢弃），不带函数，所以能原样跨 iframe、能写单测、能在规格板上列出来。`context_id` 对不上当前情境的丢弃（与动作方案同一条规矩）。

**5.3 工具被点：** 浮条在插件的根元素上派发 `molis:context-tool-invoke`，`detail: { context_id, group, id }`。插件自己执行（Pages 调编辑器命令），再重发一次 `molis:context-tools` 更新开关态。外壳不知道这些命令是什么。

**5.4 面板槽：浮条下面的小表单。** 链接要输入地址、评论要写字、改写候选要预览并「替换 / 插到后面」——这些是插件自己的内容，但位置属于浮条。插件派发 `molis:context-panel-open`，`detail: { context_id, node, label, onClose? }`，浮条把 `node` 放在自己下方（同一个定位、同一个层、一次只开一个）；Esc、点别处、情境变化时关闭并调 `onClose`；选区在面板打开期间保持冻结高亮（现有冻结范围机制不变）。Pages 今天的 `pages-pop`（链接、评论、候选预览、颜色）整体搬进这个槽。

> 事件名沿用 `molis:` 前缀，常量与现有的放在同一份合同文件里；落地时 `skills/molis-plugin-dev/` 加一节「选区浮条」：声明锚点、发布工具、接收调用、开面板，并写明 §3 的口诀。

## 6. 行为规则

继承（不改）：规则先出、判断（Jev）后到且只改顺序 / 重点 / 分组；同一情境内悬停或聚焦的按钮不移动；判断到达时若指针在浮条上则暂存、离开后更新；忽略过的动作降权；冻结快照与失效核对；写入类走助理卡片；记忆信号。

新增（浮条特有）：

- **何时出现**：选区稳定 350ms 后；拖选过程中、输入法组合中、选区在 `input / textarea / select` 里时不出现；Pages 现有的 `dragSelecting` 逻辑上收成通用规则。没有任何可用动作、也没有工具时不出现。
- **不跳**：浮条的左缘在一个情境内固定，规则 → 判断到达导致变宽时只向右长；动作区在判断到达前用现有的 pending 淡化占位，不整体重排。
- **何时收**：Esc（记「忽略」信号）、选区折叠、点浮条外、滚出视口、`place-changed`、窗格隐藏、情境换了。滚动期间跟随（`followScroll`）。
- **不遮字**：默认在选区上方；上方放不下翻到下方；触屏（`pointerType: touch`）固定放下方，让开系统选区菜单。
- **让位**：同文档里其他浮层（斜杠菜单、块菜单、链接预览）打开时浮条收起，关闭后回来。
- **窄屏**：单行不换行。舞台放不下整条时，先把工具区里的格式类（加粗、斜体、标题、列表……）折成一个「格式 ▾」菜单，链接、评论这类高频的留在行内；动作区始终保留，≤ 480 时只留 2 项，其余进「更多」。折叠由设计系统按宽度统一算（工具组用 `collapse: "overflow"` 声明哪些可折），插件不管。
- **与助理面板**：不再互斥，面板打开时选区动作照常可用（现状是整条隐藏）。
- **关闭开关**：沿用记忆线的「界面推荐」开关；关闭后只剩插件自己的工具区。

**不留两套**：S2 与 S3 必须同一个 PR（分提交）：只换外壳而不动 Pages，Pages 选区上会同时出现两层浮条。

- 触屏选区与系统菜单重叠 → 固定放下方。

## 9. 取舍（用户 2026-10-02 已按推荐拍板）

1. **浮条版式：单行，窄舞台时工具折成「格式 ▾」。** 工具在左固定、动作在右；折叠规则见 §6「窄屏」。不做两行（会遮住选区上方两行字），也不把工具整个折进「Aa ▾」（Pages 的加粗、斜体要多点一次）。
2. **正在写字（`activity: "editing"`）时：不自动浮出。** 打字时不出任何浮层；选中文字、按 ⌘.、或点段落旁的把手时才出。底栏「正在写的这段」的改写建议随之改成：⌘. / 把手唤出的浮条里显示同一份方案。Pages 仍然上报 `editing` 情境（供判断与开场建议用），只是不据此自动画浮条。
3. **底部动作条：整个取消，没有锚点的情境不显示。** 不留兜底、不留两套；「全部操作」在浮条的「更多」里。

## 10. 各插件：现状与可扩展的场景

浮条主体（§2–§8）解决「放在哪、怎么协议」；这一节回答「各插件放什么」。浮条上线后，插件的价值全在这一节：每多一项声明，所有插件的选区上就多一个动作，外壳不写名单。

### 10.2 创建类动作：Jev 推荐去处，一句话由助理创建

用户的话：选中文字发送到炼金术士、发送到 Todo 只是举例；这就是「一句话新建」，由助理创建对应内容；更多里不用出现，在浮条里由类似 Jev 的选择模型根据当时的上下文推荐最合适的 Item。

- **每个声明了「创建入口」的插件，自动成为一个候选**（登记簿派生，插件启停就增减，外壳没有名单）。它和别的动作一样进同一份候选集，由同一个 Jev 判断排序；
- **推荐直接出现在动作区**：比如选中「周五前把方案发给 Lee」，动作区首位是「记成待办」；选中一句「也许可以把留存拆成三个队列」，首位是「记成炼金术士想法」或「记下灵光」。拿不准时不强推，该动作不加重点；
- **点了之后不用再输入任何东西**：助理按选区的上下文（选中的文字、所在对象、标题路径、周围文字、所属 Goal、记忆）自动填好目的地创建接口的字段，直接创建；结果提示里有「改放到 ▾」，下拉是这一次判断排出的前几个去处，推荐错了一键换，不用回头找菜单；创建前要不要再确认，按插件分（用户拍板）：声明了撤销动作的（待办、灵光、新文档这类删得掉的）直接创建，结果提示里带「撤销」；没有撤销的（Goals 提案、Coding 会话、工作流运行等）出一张预填好的卡片，一键确认，也不用打字（quick-create §8 问 3）；
- **想自己说**（可选，不是流程的一部分）：点「✦助理」，在面板槽的一行输入里说一句话（「记到炼金术士里，作为下周的优先方向」），由助理从登记簿里选目的地并起草；没说去处就由它按上下文判断；
- **只在推荐位出现**：创建类候选不进「更多」，也不进「全部操作」。这是对「全部操作不依赖推荐」那条规矩的唯一例外，理由是去处会随插件数量线性增长，列出来就是一堵墙；够不着的去处有两条路：「✦助理」里的一句话，和那个插件页面里的「✦ 一句话新建」；
- 同一条路径也是每个插件页面里的「一句话新建」，区别只是去处已经定了。

现在已有的「记成待办」「记下灵光」是它的特例，落地时并入，不留两套。怎么推荐、怎么起草，见 [quick-create §6](../quick-create/spec.md)。

### 10.3 旁问、分叉与「Side Talk」

核对结果：仓库里没有叫 Side Talk、Side Chat、btw 或 Fork 的功能；Coding 现在不支持。它们在 Coding 的下一阶段需求书里，状态是：

- **C1 会话分叉**（`specs/coding-plugin/next-requirements.md`）：Pi、Codex、Claude Code 都有；Prologue SDK 已有 `forkSession`，Coding 还没接，状态「◐ 接上」；
- **C4 旁问**（同一文件）：Codex 的 `/btw`，借当前会话的上下文问一个问题，答案不进会话历史、不打断正在跑的一轮，实现要点是「开一个只读的临时一轮来答，答案显示在旁边」；状态「✗ 新做」，不在统一待办清单里。

浮条正好是它们的落点，而且这是一个**平台级**的形态，不只属于 Coding：

- **旁问 = 一个 `apply: "result"` 的动作 + 面板槽里的内联答复。** 选中一段话，点「问一下」，答案就出现在选区下面的面板槽里，不写任何记录、不进任何历史。面板里三个出口：继续问、放进会话（写入类，出卡片）、复制。关闭就消失；
- **谁提供**：Coding 提供「问问这一轮 / 这个会话」（只读临时一轮，带会话上下文，Coding 家族）；助理提供「问一下（不记入工作）」（轻量一问一答，不开工作）；两者在「更多」里按提供方区分；
- **分叉 = 对象级动作**：Coding 的一轮或一条回复旁出现「从这里分叉」，调 `forkSession` 建新会话，可选回到那一轮的检查点；会话列表显示分叉关系（C1 的验收要求）；写入类、只许本机本人；
- 手上的东西在右栏或助理面板时，旁问同样可用（总纲 8.5）；
- 边界：只读、不带工具、不改文件；答案进不了判断、不进记忆，除非用户点「放进会话」。

这三项都依赖面板槽（§5.4）和「面板里的内联答复」，所以排在浮条主体之后。

### 10.5 守则

- 每个动作由目的地或所有者在目录里**声明一次**，外壳不写名单；插件启停，浮条上的去处自动增减；
- 创建类（创建入口）默认是写入类（`apply: "record"`）：先出卡片、确认才创建；放进输入框的（带到助理、带到项目讨论、放进 Coding 的输入框）不写任何记录，由用户自己发送；
- Coding 这类只许本机本人的动作，只在本机界面里由人点击触发，不进 Agent / MCP 受众（沿用 `LOCAL`）；
- 去处多了也不会让浮条或「更多」变长：创建类候选**只在推荐位出现**，不进「更多」，也不进「全部操作」；够不着的去处用「✦助理」里的一句话，或到那个插件页面用「✦ 一句话新建」；候选总数膨胀的处理见 10.7 末尾；
- 仅本人可见的来源（Shelf）：选中文字不进判断模型，只在用户点了具体动作之后才用于起草；
- 选区文字进模型前先 `redactText`、`screenInbound`，像指令的文字当数据（沿用 contextual-interaction §4.2）。

### 10.6 排期建议

1. **先让浮条「出得来」**：补 Inbox、Artifacts、Characters、Sessions 的对象声明；G1 文本框选区；
2. **创建入口及其在浮条里的推荐**（quick-create）：先 Todo、灵光、Pages、Inbox、Goals，再其余；
3. **旁问**：先助理的「问一下」，再 Coding 的旁问与分叉（依赖面板槽）；
4. **各插件专属动作**：Todo、Feed、Inbox、Goals 先；Pages 再加；其余按使用情况；
5. **对象级工具**（`anchor.element`）：Todo、Inbox。

每一项都是独立的小 PR，不阻塞浮条主体（S1–S3）。存量插件逐个补齐的计划、每个插件的完成标准和波次见 11.6。

**选区家族的先后**：①F1 创建 + F2 追加 + F3 批量（同一套起草与卡片，一起做）；②F4 文本框写作助手（依赖 G1）；③F8 材料篮 + F13 运行工作流；④F6 识别、F7 复制引用、F10 记住；⑤F9 批注。每一族是一个独立的小 PR 序列，不阻塞浮条主体（S1–S3）。

**一个新概念：系统工具。** 复制为引用这类（加入材料已改为 Shelf 的创建入口，见 F8 行），不依赖任何插件、也不需要模型排序，由外壳自带，固定放在「更多」底部。它和插件工具（§3）的区别：插件工具由插件声明、显示在工具区；系统工具由外壳提供、每个选区都有。外壳里仍然没有按 `plugin_id` 的分支。

**候选膨胀怎么办。** 家族多了，一次选区的候选可能有四五十个。处理办法：规则先按粒度、角色、识别器、可用性筛到 12 个以内，再交给 Jev 排序；评估集（contextual-interaction §5.4 的方法）加一类标注「这段选区最合适的去处 / 动作是哪个」，每加一个家族重跑，目标值等第一轮测量后再定，不先拍数字；延迟预算沿用 1.5 秒，超时退回规则。

## 11. 开发手册、Skill、模板与门禁：让每个插件默认就有

用户的话：理论上大部分插件都应该有这些，所以开发手册和 Skill 里要声明，并且尽可能提供。

### 11.1 原则

- **默认都做，不做要有理由。** 每个有用户内容的插件默认做三件事：①声明当前对象（已有）；②声明创建入口（[quick-create](../quick-create/spec.md)）；③需要时贡献选区动作与浮条工具。第①②件是必做，第③件按需；确实不适用的（Git、Diff、Text stats 这类工具型插件）在门禁的豁免名单里写明理由；
- **平台尽可能替作者做**：能从已有声明派生的，就不让作者再写一遍（11.2）；
- **手册全部随代码一起写**（用户 2026-10-02 拍板）：Skill 描述的是「现在是什么」，所以手册随各阶段的代码 PR 一起合，不先于代码，也不单独先补；已经在 main 上、手册里却缺的那部分（11.4）并进 S1 的第一份 `contextual.md`。

### 11.5 覆盖率门禁（冻结的豁免名单，只许减少）

仿 `tests/builtin-plugin-assembly-gate.test.ts` 的做法，新增一个测试（拟名 `tests/plugin-context-coverage.test.ts`）：

- 每个 native / app 插件：有用户可创建的对象（有创建类动作）→ 必须有创建入口（自声明或由内容站派生），否则必须在豁免名单里并写理由；
- 每个展示用户内容的插件：必须能得到对象声明（自己写或工作台按搜索来源命名），否则同样要在名单里；
- **名单分两类**：「待补」（存量缺口，每项写明波次，见 11.6，补完就删）和「不适用」（永久，每项写理由）。永久不适用的只有：Text stats（无用户内容对象，它是纯计算动作的提供方）、插件创作台、市场，以及 `integration` 家族（GitHub、Gmail、RSS、YouTube……不展示用户内容对象，内容经 Feed 进来）；
- **名单只许减少**：新插件不能加入名单，只能声明；每补完一个存量插件，那一个 PR 里把它从「待补」里删掉；
- 测试输出一张覆盖率表（对象声明 / 创建入口 / 选区动作 各覆盖多少个插件），进度一眼可见；
- `molis-work plugin validate` 对第三方与生成插件给**提示**（不拦截），说明缺什么、用户会因此少什么。

### 11.6 存量插件补齐计划（用户 2026-10-02：存量的应该尽可能补上）

目标：**「待补」名单清零**，最终只剩上面几个永久不适用的。不靠一次大改，靠按波次的小 PR，每个 PR 只动一个插件。

**一个插件算「补齐」要做到五项**（Pages 已全部做到，当作对照）：

1. **对象声明**：打开一个对象时对象可被读到；文本框里的选字也能触发（依赖 G1 助手）；
2. **创建入口**：声明或由内容站派生，带 `examples`；
3. **至少一个有用的专属选区动作**（或对象级动作），不是只靠通用那几项；
4. **工具**：只有编辑型、或有对象级操作的插件才需要（Todo、Inbox 的对象级工具；其余没有就写「无」）；
5. **验证**：该插件的 README「开发要求」写明现状；单测证明声明进了目录、插件停用时去处与动作同时消失；一条真实场景（选一段真实文字 → 看到动作 → 执行 → 结果落在对的地方）的证据写进本 spec 的进度节。

**波次**（按价值与代价排；每一波可以由不同会话并行做，插件目录互不重叠）

| 波次 | 插件 | 主要工作 | 前置 |
| --- | --- | --- | --- |
| 0 共享件 | — | 浮条 S1–S3、G1 文本框选区助手、起草服务 Q1、覆盖率门禁（带完整「待补」名单） | — |
| 1 只需声明 | Todo、灵光、Pages、Inbox、Goals | Todo、灵光并入「记成待办」「记下灵光」；Inbox 补对象声明、创建入口由 `receive` 派生；Goals 加事件类动作与 `proposes` 入口；Pages 补创建入口与几项新动作 | 波次 0 |
| 2 派生加小补 | Jelly、Feed、Dataset、Form、PPT、Schedule、Cognia、Shelf、炼金术士、Coding、Files | 内容站的 6 个只补 `examples`；Jelly 分事项、笔记两个入口；Feed 分加入 Feed、建规则；Schedule 要理解时间；Coding 做「放进下一轮」「补充给这一轮」；Files 把「选区引用给 Coding」收进浮条 | 波次 1 的起草服务与卡片已经稳定 |
| 3 先补声明 | Artifacts、Characters、Sessions、Git、Diff | 只做对象声明与一两个动作（引用到 Pages、作为 Goal 证据、评论一处改动） | 波次 0 |
| 4 先设计 | Images、Workflows、Experiments、Characters「一句话拟人设」、Sessions 终端 | Images 是生成不是建 Item；Workflows 画布与 Sessions 终端要自己上报焦点（G2）；Experiments 样例标注 | 各自出小设计 |
| 5 旁问与分叉 | Coding、助理 | §10.3 | 面板槽 |

**每个补齐 PR 的形状**：只改一个插件目录加它的测试与 README，加一行把它从「待补」里删掉；跑它自己的测试、覆盖率测试、`boundary:check`，一条选区送去该插件的真实场景；不动别的插件，不改共享合同（共享合同的改动在波次 0）。

**存量的生成插件**（用户已经在创作台里做出来、装在 Home 里的）：界面由平台绘制，所以平台升级后自动得到对象声明和「✦」，不要作者或用户重新生成（落地时核对绘制处，核对不通过就在波次 3 前补一个平台侧的统一声明）。

**怎么知道进度**：门禁测试输出的覆盖率表；每波结束把「已补齐 / 待补」的数字写进本 spec 的进度节，并更新统一待办清单里 BL-038、BL-039 的进展。
