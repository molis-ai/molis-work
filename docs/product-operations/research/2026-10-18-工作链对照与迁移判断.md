## 怎么比较才公平

比较的是同一份可检查交付物，连同开始、收尾、失败与下次回来。现有用户的已完成配置算沉没投入；Work 新增的配置、学习和双重维护不能略掉。新用户从零开始，另算一套账。

“一步”指一项有明确产物的人类工作，例如确认需求、核对出处、接收修改；不是点击数。把一个按钮拆成三个点击、把三个插件合称“交给 Work”，都会扭曲比较。下表用五种判断：**不变、换位置、条件减少、新增、能力缺口**。没有把所有行加成一个“少 X 步”的虚假精确数字。

| 比较对象 | 选它的理由 | 公平前提 |
| --- | --- | --- |
| 研发：Claude Code + 仓库规格/验收记录 + GitHub PR/检查/审批 | 已有跨会话上下文与真实代码门禁，适合本例的成熟开发流程 | 不把全部要求散在聊天当成默认；必要时可写轻量脚本/CI，但把新增维护算成本 |
| 研究：Craft 文内 Assistant + 文内任务 + 交付文件；Notion/Word 作反例 | 原位修改、恢复会话、带上下文待办已存在 | 不强迫现有用户先粘到独立聊天再搬回来；团队协作已在原工具时算迁移损失 |
| 运营：模板 + 保存提示词 + 人工审改；较重需求再用 Notion Custom Agents/n8n | 普通摘要不必先搭自动化；确需触发、跨服务和审批时已有可行方案 | 保存规则不是每次重写提示词；“批准工具执行”与“人直接改正文”分别核对 |

依据：[Claude Code 项目记忆](https://code.claude.com/docs/en/memory)、[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Craft 文内编辑](https://support.craft.do/en/ai-assistant/editing)、[文内任务](https://support.craft.do/en/plan-and-do/tasks)、[保存提示词](https://support.craft.do/en/ai-assistant/custom-prompts)、[Notion Custom Agents](https://www.notion.com/help/custom-agents)、[n8n 人工批准工具](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md)。官方能力不等于我们完成了这套组合的实操。

## R04：研发交付——核对当前约定能少一点手工，代码交付链没有被替掉

**相同任务：**支付功能跨多天推进，兼容范围发生变化。交付物是当前代码、执行与测试依据、本人体验结论，以及明确的剩余缺口。两条路径都要知道实际验的是哪个构建；不能只拿到一个绿色状态。

| 阶段 | 熟练的现有组合 | Work 路径 | 差额 |
| --- | --- | --- | --- |
| 首次设置 | 已有仓库规格、Agent 项目说明、PR 模板与所需 GitHub 规则 | 配置 Home/项目、Agent 或模型/MCP 权限；建立目标与关键要求，选本人验收条件 | **新增** Home/MCP 接入与目标配置；沿用外部编码工具时不必另配 Work 模型，使用内置 AI 才另计模型配置 |
| 记录承诺 | 在规格/验收表写支付失败、旧订单兼容、手机体验；PR 引用它 | 在 Goal 中写当前要求及本人验收项；技术资料仍留仓库 | **换位置**。若团队仍要求原规格，两份事实还要同步 |
| 中途改范围 | 改规格、记录决定；执行前读取新版本，必要时停下旧任务 | 确认 Goal 变更，继续前读取有效约定；仍要处理正在跑的旧任务 | **增加系统授权校验**：Runtime 未引用有效具体授权的受保护约定修改会被拒绝；人的决定、外部通知与同步仍要做 |
| 换会话开工 | 项目指令与已存规格可重读，继续/恢复原会话；检查代码现场 | 接入者读取同一 Goal 和进展；仍检查 HEAD、分支、未提交内容 | **不变/换位置**。持久背景不是独有，不证明所有 Agent 自动写回 |
| 写代码与测试 | Agent 实现，跑测试，检查差异与失败 | 同样执行；把报告写回 Goal | 核心步骤**不变**，新增或替换一份结果记账 |
| 真实手机体验 | 人对代表性构建操作，记录条件、结果和缺口 | 人做同样的事，从可信入口给对应要求留下结论 | **不变**。这一步不能用 AI 报告省掉 |
| 判断结论仍适用 | 人对照规格/变更、构建、PR；GitHub 可令变动后的旧 review 失效 | Goal 按其合同核对要求与本人结论；启用项目完成规则时另检查整份约定/轮次 | **条件减少**部分“Goal 是否满足完成规则”的手工比对；不替代构建核验 |
| 显式收尾 | 按原流程更新验收表、PR/交付状态，确认实际结果 | 提交 Goal 收尾，再确认是报告已保存还是完成已生效 | **新增或替换一次状态维护**；有报告不等于目标已完成 |
| 绑定实际代码 | PR/检查与提交关联；必要时在验收记录写构建链接 | 仍需明确记录/核对验收针对的代码或构建 | **不变**。本次未发现 Goal 的人审承诺自动硬绑定 commit SHA/build ID |
| 合并、部署、发布 | GitHub 与部署系统执行本身的规则 | 仍回原系统按规则完成 | **不变**。Goal 完成门槛不是外部发布门禁 |
| 下周再做一轮 | 打开规格与交付记录，识别哪些有效、哪些要重验 | 读取同一 Goal；完成/取消后新一轮需显式恢复并写明原因，接入者持续写回 | **条件减少**从分散记录拼回目标状态；若原记录集中则主要换入口，另有显式恢复及 Home/授权故障处理成本 |

### 真正省下什么，增加什么

没有消除写需求、写代码、测试、本人实操、核对构建、合并与发布中的任何必需阶段。候选收益集中在一处：**把已定义的目标完成条件交给系统核对，减少人为拼接当前要求与有效结论**。这是有条件减少核对负担，不是减少一次验收。

同时增加目标建模、要求更新、Agent 接入与写回、理解验收语义的成本。若已有仓库验收表与 PR 状态还要继续维护，Goal 很容易成为第二本账。GitHub 已有检查、review 与旧批准失效；它不理解所有业务条件，但也不能被写成没有门禁。

**必须分清两种规则：**单条要求指定本人验收，与项目 `human_approval` 完成规则不同。后者默认关闭；启用后，才有针对当前目标约定与相应重开/继续轮次的整体匹配。两者都不能自动证明“眼前运行的构建就是验过的那个”。具体字段、失效与可信身份见本轮代码核对补记。

### 迁移判断与改写

对已把规格、人工验收和 GitHub 规则维护顺畅的团队，**不建议仅为这条场景迁移**。唯一值得保留的试用入口是：本人负责、任务跨多轮、当前依靠自己拼接要求与结论的一个小项目；先接入一个新 Goal，保留仓库和发布流程，验证它能否替掉原先的一份个人追踪表。

新案例标题改为：**「上次说验过了，这次的条件还一样吗？」** 文案重点是当前约定和缺口可核对；删除“Work 因此保障上线”“换会话必然少交代”“验收自动绑定代码版本”的暗示。若试用后仍要两边重复更新、仍需逐条重查才能信任状态，则撤下这一迁移理由。

## R07：研究修订——原位写作有价值，但不足以让熟练文档用户搬家

**相同任务：**已审阅的推广建议临近交付，新访谈表明旧数据导入尚未完成。只修订有关判断，补出处与后续核对，交出正确版本。最终交付若要求 Word 批注或多人在线协作，两边也必须满足这一要求。

| 阶段 | Craft 等已有文内助手的路径 | Work 路径 | 差额 |
| --- | --- | --- | --- |
| 首次进入 | 原稿、来源与协作关系已在现有工具 | 安装/配置，导入或新建稿，检查转换结果，安排原系统与 Work 谁为当前稿 | **新增**。从新项目开始可降低历史搬迁，但不是已证明收益 |
| 回到原稿 | 打开稿件及已有 Assistant 会话 | 打开并保存稿件，找到助理工作并明确加入该对象 | 原稿定位**不变**；对象加入与工作归属可能**新增** |
| 带入新证据 | 加入/指出新访谈与目标段落，说明修订范围 | 选择材料、选区与落点，交给助理 | **不变/换位置**。两边都不能略掉判断相关性 |
| 局部修订 | 文内 Assistant 提议后批准，或直接编辑后查看；可撤销 | 选择认可的回复文字，在原位置预览、确认写入 | 双方都有把局部修订写回原稿的能力；质量和省事程度未比较。Work 的选段路径可能增加选取/落点操作 |
| 核查事实与相邻段落 | 人核对原文、结论与未改处 | 人做同样核对 | **不变**；“原位”不证明修改语义正确 |
| 补出处 | 在段落中保留来源链接或文字，核对对应内容 | 补来源，引用或固定材料须按实际路径处理 | **不变**；固定快照不是自动逐句保真引用 |
| 留补证事项 | 在文档里建任务，保留相关内容/日期；任务视图可汇总 | 选句准备带来源 Todo 卡，补清内容并确认 | **换位置**；Craft 已有与文档相连的任务，Work 未消除这个阶段 |
| 留交付版本 | 按需版本记录/保存副本/导出；核对交付文件 | 显式固定成果，再导出并核对 | **不变或增加归档动作**；需记录哪份是交出的版本 |
| 交给客户 | 沿既有共享或文件交付方式 | 发交付文件；如客户需原套件协作，还要搬回并检查 | 对共享审稿用户存在**新增成本/能力差异** |
| 下次回来 | 回原稿和任务；在保留期与对应客户端内重开会话 | 同一 Work 对象、工作及来源待办可以继续 | **换位置**；熟练原工具用户同样可接续 |

### 对照后还剩哪两项可能收益

如果用户确实仍用“独立聊天 + 无 AI 的文档编辑器”，Work 可能减少**把背景再复制进聊天**与**把回答再复制回正确段落**这两类搬运。然而先开启现有工具的文内助手，也可能消除它们；这不是 Work 相对成熟文内工具的净收益。

Craft 会话当前保留 30 天，Web 会话在当前浏览器，不与 App/其他浏览器同步；对照不假设无限记忆。其已有导出与共享仍需考虑平台和使用条件。

相比当前 Craft 组合，本轮没有找到可确定删除的必需工作阶段。Work 可以演示对象、位置和动作在自己工作台里的组织方式，但不能把偏好写成明显省步骤。

迁移成本有具体内容：Pages 文件导入不持续同步来源；评论、权限和历史版本不随导入迁移；当前导入转换器会把媒体转为链接或说明、部分布局需重整。当前直接导出 Markdown/HTML，PDF 走打印，未提供原生 DOCX 导出；导出读当前编辑稿而非固定成果快照，仍需核对两者。这是**导入路径**的边界，不是断言 Pages 编辑器完全不支持图片。若客户仍在 Word/原共享空间审稿，往返和“哪份是最新”的问题可能比原来的 AI 搬运更大。Word 已有共享共编、修订审阅；相应订阅和组织设置允许时，也能选段用 Copilot 改写并审阅采用，不能把客户原稿默认成没有 AI 的编辑器。

### 迁移判断与改写

**撤回“研究修订足以驱动成熟文档用户迁移”的主张。** 将其改为一个低迁移成本的试用场景：独立顾问开一项新研究，材料主要是本地文字，客户接收文件，个人决定用 Work 作为本次原稿；先完成一次从新证据到段落修订和补证任务的循环。

新案例标题改为：**「新项目开始，把材料、修订和补证接在一起。」** 它是产品体验入口，不是从原办公套件迁移的理由。已有共同编辑、评论链、复杂格式和长期资料库的用户，不因一次局部修改而搬家。R06 自媒体变体也同步降级，不能换个角色把同一个弱主张重新放回首页。

## R05：运营审改——运行记录是增益，自动化与业务判断没有替掉

**相同任务：**收到一条渠道新规，准确写出改变了什么；人对照正在运行的活动条件，决定是否调整；保留自己核对后交出的说明。不能把“AI 总结了规则”当成“已识别实际业务影响”。

| 阶段 | 最小现有做法：模板/保存提示词 | Work：Feed → AI → Inbox → 人工 → Pages | 差额 |
| --- | --- | --- | --- |
| 首次设置 | 保存说明模板和固定提示词；已有文档工具继续用 | 配置模型和材料入口，建站点/衔接与指令，试跑交接 | 相比简单模板**新增**结构配置与排障 |
| 获得一条规则 | 从已有订阅/网页打开，必要时留原文和链接 | 来源接入 Feed，再明确选一条材料进入实例 | **换位置**；不能把另建来源入口算免费 |
| 整理改变的条件 | 选保存提示词处理，在原页保留候选 | 推进 AI 交接，将候选送到 Inbox | 规则复用**等价**；不省每次重写提示词，因为原方案本来就不用重写 |
| 判断实际影响 | 人查当前活动规则/数据，核实哪些条件受影响 | 人仍查这些信息，在手动交接时补判断 | **不变**。这是案例最关键的业务难点 |
| 审改正文 | 人在原页改，确认未知项、出处与结论 | 在手动交接里改标题正文，再确认继续 | **换位置**；人审不消失 |
| 形成可交付说明 | 原页已是可编辑文稿，按需求共享/导出 | 交到 Pages 自动建可编辑文稿，再核对/交付 | 原页可直接交付时没有搬运可省；Work **新增一次交接** |
| 记录当次输入与 AI/人工稿 | 如确有回看需要，模板分区/副本/历史可留存；不同方式需核是否足够 | 实例保存当时输入、AI 输出、人工交出内容及已发生交接的要求 | **条件减少**专门手抄阶段快照；但只有业务真需要这些记录时才是收益 |
| 中断回来 | 从原页状态/记录继续 | 从实例步骤继续 | **换位置**；是否更好找待实操，不由“有状态”直接推出 |
| 失败与重试 | 检查原稿是否已改，再撤销/重试；自动化另有错误处理 | 同一次 Pages 交接重试复用既有文稿；动作结果未知时仍需查看再决定 | 特定恢复机制有价值，不代表整链不用排障 |
| 下一条 | 复用模板与保存提示词 | 再选单条、再推进各段 | 两边都复用；Work 的每段推进仍是经常性成本 |
| 调整渠道活动 | 人在实际渠道后台执行并确认 | 仍去实际渠道执行并确认 | **不变**，未打通业务执行 |

另有两项首轮成本不能跳过：内置示例是先人工、后 AI，本例需改配；动作站的返回结果只进记录，不自动成为下一段 AI 的材料，所以不能靠加一个“读活动库”动作就声称本链已自动核对业务影响。记录界面也不等于已有逐句差异审阅器。

较重的自动化需求另比：Notion Custom Agents 已有事件/定时触发、既有资料与应用权限、运行记录；需要相应套餐和用量投入。n8n 能在具体工具执行前暂停让人批准/拒绝，需搭建连接与凭据；它的“批准”不等于已自带可编辑的全文审稿器，若要改正文必须另设计。不能用最轻的 Work 手动链去证明胜过一个从未配置的自动化系统，也不能用强自动化逼普通用户承担不必要的配置。

### 迁移判断与改写

对“读一条规则、写一份影响说明”的用户，模板与现有文内 AI 通常已覆盖关键步骤；Work 并未省掉核实活动条件、审改或业务执行。对已经用成熟自动化的团队，当前逐条、逐段手动链又没有替掉无人值守、批量和组织接入。**R05 撤下首页迁移主案例。**

只保留更窄的使用说明：材料与稿件本来就在 Work，并且这个人确实需要回看“AI 候选”和“自己确认交出稿”的差别。标题改为：**「每条材料，留下一份我确认交出的说明。」** 不再声称“省去每次重找提示词”“自动知道哪个活动受影响”。如果用户不需要阶段回看，连这条流程也可能不如直接在 Pages 写。

## 迁移账：把首次、每轮和退出成本分开

| 成本 | R04 研发 | R07 研究 | R05 运营 |
| --- | --- | --- | --- |

| 每轮额外操作 | 更新要求与结论，保证接入者写回；核对构建身份 | 明确对象/选区，接受写入，准备 Todo 卡，必要时固定成果 | 选单条、推进两段、查看/编辑人工交接、核对 Pages |
| 并存的重复维护 | Goal 与原规格/PR 验收表若同时成为事实源 | 原协作文档仍在更新时，导入稿与原稿发生分叉 | 既有内容库/状态表和 Work 实例若都需更新 |
| 人与组织迁移 | 同事仍在 GitHub/原项目系统，原门禁保留 | 客户批注、权限、共享链接与格式不能视作可无损搬迁 | 团队权限、渠道数据、外部触发和后台可用性需要继续解决 |

| 退出与回退 | 可保留代码仓库，但 Goal 的结构状态不能假定已同步回原规格 | 导出内容不等于恢复原评论、权限和历史；回原套件需再核 | 交出稿可导出，运行状态/流程规则迁回其他平台需重建 |

当前公开发布成熟度也要算：本次产品基线的新体验属于开发版，v0.3.0 尚为草稿。试用准备、升级与恢复成本未实测，不作“零成本迁移”或“免费替代”承诺。本地优先是部署与数据偏好，只有用户明确需要且接受相应限制时才产生价值；联网模型仍涉及材料外发。

迁移值得做的条件是：**反复任务中减少的重复劳动与错误恢复成本，大于首次设置、每轮新增操作、双份维护及回退成本。** 这里没有数据可以算出回本次数，更不能编一个“每次省 5 分钟”。

## 三条改稿决定与最低验证

| 案例 | 原主张处理 | 新位置 | 最小完整验证与推翻条件 |
| --- | --- | --- | --- |
| R04 | 去掉“已有代码验收工具还要迁 Work”的默认推销 | 一项个人项目的增量试用；待验证 | 同一任务跨三轮：增加要求、放宽范围、重开交付；检查旧结论如何失效，以及代码变了而约定不变时谁发现。保留 GitHub。若仍要双重记账或误认构建已验，则不主推 |
| R07 | 撤回原位改稿带来独立迁移优势 | 新项目体验入口；既有用户可用 | 同一份非空稿和新访谈分别走 Craft 与 Work，直到交付文件及补证事项。记录定位、复制、确认、格式修复、返回与版本混淆；若 Work 更费事或共享损失更大，保留在原工具 |
| R05 | 撤下首页主推 | 已有 Work 用户的可选流程例 | 连续处理三条材料，一条信息不足、一条中途停止。比较简单模板与 Work 的阶段记录是否真被用来继续/复核；若不看运行记录或逐段推进更费力，直接用原页模板 |

“新项目试用”降低的是一次性迁移成本，并没有证明每轮更快。“已有 Work 用户适用”说明留存/深入使用价值，不能循环论证为什么新用户要迁入。九类角色入口继续保留，但不因角色多就产生更多已验证卖点。

## 后续产品改进只追这几个具体问题

1. **研发是否真的减少一本账。** 先选一项个人项目，明确 Work 目标事实与仓库技术说明的边界，观察每次更新是否仍需重复抄。没有对照记录之前，不先加大同步系统。实际构建身份是当前明确缺口，文案不宣称已自动绑定。
2. **文稿接续是否比现成原位助手更费事。** 先测已有对象加入、选区、落点和卡片条件；如果恢复一次任务需要更多识别操作，就在现有入口上改可见性和操作顺序，不新增一套“全自动上下文”来掩盖摩擦。
3. **流程记录是否值得每段推进。** 先让实际使用者回看一次中断的记录。如果阶段快照对决策没有帮助，就不要用保存记录当卖点；如果明确有用但操作过多，再考虑复用现有能力减少无判断的推进步骤。自动批量/服务接入是另一项需独立验证的需求，不写成已有功能。
