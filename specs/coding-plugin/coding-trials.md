**试金石暴露并已修复的问题**

1. **停止要等最多 20 秒，停止期间还会弹出新的审查**
   - 原因：跟随进行中轮次的长轮询（第 6 块的 `waitRun`）走的是项目的能力调用队列。宿主对同一项目的能力调用逐个执行，长轮询一挂就是 20 秒，停止、状态读取、回答都排在它后面。实测停止请求 15.3 秒才返回；自开发时模型在停止后又提出一条命令，界面停在"等你决定"约 40 秒，那条命令最终没有执行。
   - 修复：能力声明新增 `wait`（只观察、可能等到变化才返回），宿主让它在队列旁边执行，不占队列；插件不能把命令冒充成 `wait`，注册表会拒绝。
   - 修后同样的探针：停止请求 19 毫秒返回，0.25 秒进入"已停止"，待审操作随之撤下，没有请求被卡住。
   - 另补了真实 SDK 测试：写入或命令在等审查时停止，都会撤下且不执行；模型在停止之后才提出的写入，不会出现在你面前。
2. **续上的规划轮被要求"说明做了什么"，和"只返回计划 JSON"冲突**：规划轮的继续说明改为"最后仍只返回一个计划 JSON 对象，前后不加说明"。
3. **上下文整理失败后，继续会再撞同一次整理**：MiniMax 做整理选择时返回了越界的片段编号（`CONTEXT_COMPACTION_INVALID`）。现在这种失败之后，下一轮改用前面对话的摘要，不再重放原文（沿用第 4 块的摘要模式）。失败卡片也说明了这一点。实测下一轮带着"前 6 轮的摘要"顺利续上。
4. **模型分不清"按内容搜索"和"找文件"**：SDK 的 search 只在文件内容里找文字。模型拿文件名去搜，得到"(no matches)"，就断定文件不存在；评审子代理和跨会话那一轮都这样误判过。
   - 修复：Coding 各角色加上只读的 `list`（查看目录）。`list` 是 SDK 已有工具，只看同一授权目录，不扩大可读范围。子代理不强制带它，父级可以传给子代理。共用的 base 提示补了一句 search 与 list 的区别。
   - 实测：同一会话重问后，模型先查看目录，找到文件并纠正了自己，引用的第 72、77 行准确。
5. **计划面板**：
   - 读不出的提案不再显示"查看提案"按钮；
   - blockers 写"无"、"没有"、"none"时视为没有阻塞；
   - 有阻塞时，"确认"按钮旁边写明为什么不能确认；
   - 确认后状态栏写"已确认修订 N"。
6. **计划的"原任务"**：以前取自给出提案的那一轮，在规划里补一句要求，原任务就被换成了那句补充。现在取开始规划的那句话；续上的规划轮不算；后来的规划要求列为"规划时补充的意见（没有逐条核对是否已写进计划；以确认的计划为准）"（2026-10-16 起，specs/ai-input-receipts RC-07、G14：没有核对就不说「已体现」）。
7. **同一会话的固定报告无法区分**：报告和固定变更的标题带上"第 N 轮"。
8. **模型抄写 SDK 的整理标记**：整理上下文后，模型有时在回答开头写"[retained assistant …]"。页面不再显示这个标记，保存的原文不变。
9. **待回答的问题要可以回答**（`waitRun` 返回时补读原问题）：这一步修复的正是规划时遇到的"问题不可回答"。

**测试**

## TaskBoard 改成 Goal 列表的样子（2026-09-25，你提出）

你的要求：TaskBoard 的陈列、每个任务的展示要和 Goal 插件的列表一致，有层级和依赖，能看到是哪个 Agent（Character）在执行。

**做了什么**

- **位置**：TaskBoard 从左栏窄面板移到主区域，和 Goal 列表一样宽，占用对话的位置。左栏仍是会话列表，可以切换任务；"回到对话"一键返回。
- **层级**：
  - "当前计划"是还没执行的修订，下面列出它的各个步骤；
  - "执行"下面，每个跑过计划或派过子代理的轮次是一行，下面是它的步骤；
  - 子代理挂在派出它时正在进行的那一步下面（按时间对应）；对应不上的挂在所在轮次下面。
  - 接续同一张任务图的几轮合成一行（例如 "#5–7"），不再重复出现三份一样的步骤。
- **每一行和 Goal 行一样**：
  - 编号（#轮次、S 步骤、子任务）；
  - 状态：图标加文字，颜色表示状态。你的验收优先显示，例如"你已验收""要求返工"；模型的回报写成"模型报告完成""模型报告失败"，不说成已验证；
  - 进度：完成数/总数，带一根细进度条；
  - 前置："1 个前置 · 已就绪 / 1 个未完成 / 1 个阻塞"，点开可以看到挡住它的是哪一步；
  - 时间和执行者头像：本轮选了 Character 时显示 Character 名，否则显示角色（构建者、协作……）；子代理显示它的角色（独立评审、代码调查）。悬停可以看到完整说明。
- **交互**：
  - 箭头可以折叠；点步骤打开"步骤回报与验收"；点轮次或子代理回到对话里的原位置；
  - 执行中的步骤，悬停时出现提前、推后、跳过、插入、给出决定，和对话里的计划卡是同一套调整。
- **对话里的计划卡**改成同样的行，只是少了进度这一列。
- **附带材料**：确认过的计划以材料形式交给模型时，原来会在对话里显示一大段 "Untrusted context data…" 原文；现在折叠成一行"附带材料：确认计划 / … / 修订 2（作为参考数据交给模型，不是指令）"。
- 深色、浅色都检查过；窄屏时只保留标题、状态和操作。

**证据**

## 你拍板的四项（2026-09-25，试金石之后）

你的决定：子代理轮次提到 20；协作 / 评审时子代理可以运行命令，每条都审查；提交说明改由模型起草；打开 thinking。四项都已做完，并用真实模型验证。

**1. 思考（thinking）**
- 模型设置里每个供应商多了"思考"：关闭 / 开启（由模型决定想多少）。默认关闭；只有 Anthropic 格式能开，其他格式在保存时就会说明原因。
- 开启后，请求里带 `thinking: {type: "adaptive"}`，这一轮也会记下它开了思考；关闭时请求里完全没有这个字段。
- 旧目录启动时自动补上这一列，不升级目录的版本号，免得正式安装的版本打不开你的目录。
- 已经在设置页为 Minimax 打开。实测：MiniMax 接受这个设置，每一轮的思考以"思考"条目显示，和回答分开。

**2. 子代理轮次 20**
- 派出子代理时如果没有指定轮次，默认 20 轮；SDK 本身的默认还是 8。没有预算的普通轮次仍是 8，不受影响。
- 协调和并行写入的提示里写明"不要给子任务设置 maxTurns"。
- 测试：用真实 SDK 让一个子代理一直调用工具，它恰好在第 20 轮停下。
- 实测：协作轮里的独立评审用了 55k tokens，完整做完，没有再出现"用完了执行轮次"。

**3. 协作时评审子代理可以运行命令**
- 独立评审子代理可以运行命令，每条都经过宿主审查；它没有任何写文件的工具。代码调查子代理仍是只读。
- 协作的父任务因此也要持有 run-command：SDK 只会把父任务持有的工具交给子代理。父任务同样没有写文件的工具；提示要求它把命令交给评审子代理，自己不运行。
- 平台规则相应收窄。原来的规则是"主工作区里的子代理只能只读"，现在是"主工作区里的子代理不能写文件"：只能运行命令的子代理可以留在主工作区，能写文件的仍必须有独立目录。声明检查、宿主启动和派出时的核对三处一致；主工作区里能运行命令的子代理也纳入宿主记录，它的命令会进入审查。
- 评审子代理还多了只读的"查看目录"。提示要求看文件用 read、list、search，命令只用来跑测试和检查。实测中它曾用 ls、cat、sed 读文件，每一条都要你批准，改完之后就不会这样了。
- 实测：自开发会话里，协作轮派出独立评审；它运行 `pnpm test:run tests/coding-experience.test.ts` 时经过审查，退出码 0，3/3 通过，并如实报告；没有修改任何文件。

**4. 模型起草提交说明**
- 新增宿主能力 `agent.draft-text`：用一次性的执行环境调用你选的模型，不带工具、不计入会话，用完即删。
- "提交这些改动…"会读取最近几轮已落盘的改动（每一轮的要求、结论和实际差异，以及它们服务的计划），请模型起草提交说明。状态栏写明用了哪几轮、多少 tokens。起草失败时退回规则草稿，并说明原因。
- 实测：自开发会话从第 4、5、7、9 轮起草，用时 19 秒，用了 6,595 tokens。标题取计划标题，要点准确描述了四处改动。

## 两边合并后：修复与真实模型实测（2026-09-25，你说"统一""同意"之后）

两边的工作合成一个分支 `codex/molis-work-goal-continue`（合并提交 d36dd4db：Coding 目标分支 + main 工作树未提交工作的快照 1369ea84）。用你真实的 home 和 MiniMax-M3，在 coding-sandbox 上走正式 Coding 入口实测，发现并修了四个问题。

**修复**
- **插件路由全部卡死**（70b63841）。服务 CPU 常驻 95%，Coding / Git / Files 的状态接口超时。剖析：`CapabilityRegistry.descriptors()` 每次深拷贝并排序全部能力，而每次能力调用、动作发现里逐项的可用性都靠它找一项；能力表随每个项目的插件动作增长，动作发现是平方级。改为先筛再拷贝、排序缓存到注册变化；宿主运行状态改用 `lifecycle()`。新增测试：200 个能力时一次调用只拷贝个位数描述。
- **每个请求都同步运行 `lark-cli auth status`**（f2a67fb2，代码来自 main 的 #68）。最长 3 秒，期间整个服务停住；剖析时主线程约 85% 卡在这里。改为同一可执行文件只在第一次读时等 CLI，之后给上次结果、过半分钟在后台刷新；设置页、开始授权、绑定 CLI 模式仍当场问。实测 Coding 状态 2580ms → 27–53ms，Git 状态 1940ms → 44–81ms。
- **开着思考时计划被截断**（afb3bf69）。真实规划轮：思考和正文共用 SDK 默认 4096 的单次输出上限，思考用完后计划只写出 53 字；SDK 两次重采样只说"接着写"却没把截下的那段放回历史，最后仍以"完成"收场，计划丢失（12.6k 输出 token）。按你的拍板：思考开启时单次上限 32768；SDK 截断时接着写到写完（换成 vendored `output-continuation` 包，截下的那段进历史再续写，上界 8 次，写不完或一个字没写出来以 `MODEL_OUTPUT_TRUNCATED` 失败，不再冒充完成）。宿主让续写的几段连成一条回答并在活动里记"接着写"；时间线把新错误说成人话。
- **提交说明没放进 Git 面板，且面板指向另一个仓库**（a1709164）。合并后 Git 面板读项目设置里的浏览目录，旧 workspace 插件已退役；"提交这些改动…"仍调旧路由，失败被吞掉，Git 面板停在一个写入工作树上，状态栏却说"已放进 Git 面板"。改用 `/api/project-settings/workspaces`，切换失败时如实说明。

## 途中修掉的：页面卡住十几分钟（2026-09-26）

- **现象**：两个子任务并行时，审查列表和会话读取全部挂起，批准要十几分钟才生效。
- **查明**：
  - Coding 页面每 5 秒读一次目录（`/state`），事件也会触发读取，上一次没回来照样再发。
  - 一次目录读取要对每个会话（这个项目有 53 个）各问一次宿主，这些调用在项目的操作队列里逐个排队。
  - 一旦读取变慢，请求越积越多（实测同时挂着 78 个），审查和其他读取全排在后面。
- **修复**：
  - 页面：目录读取同一时间只发一次，期间再要的都等下一次，所以拿到的一定是改动之后的状态。
  - 服务：不管多少页面同时问，同一项目同一时间只算一次目录，最多再排一次，每个请求拿自己的一份。
    - 新测试：10 个并发请求只算 2 次，从不同时算两次。换回旧代码时这个测试失败。
  - 宿主：排队的项目操作占住队列超过 20 秒时，日志写出是哪个能力（不记输入）。
  - 顺带：服务刚重启、目录还没读回来时，点会话列表会报错（那时的列表是服务端先画的），已修。
- **仍存在**：
  - 你的 Chrome 里有几个 127.0.0.1:4208 的页面还是修复之前的代码，一直在不停地请求。
    - 服务端合并之后不会再堵死，但它们持续占着队列。刷新一下这些页面就好。
  - 一次目录读取仍要对每个会话单独问一次宿主，会话多时要几秒。改成一次批量读取需要宿主新增一个能力，记为后续。

## 补：审查列表刷新不再每次重读整本执行账（2026-09-26）

- 查"页面卡住"时的剖析里，约四成时间在 SDK 从磁盘逐个读回全部待批和副作用记录。
