## 3. 完整行为链

```text
真实CLI home restore --from / --recover
→ 原canonical Home的同一排他lease
→ archive + target + 原key + 各owner当前资格零写预检
→ 必要的真正空态reviewed账本在Home外准备
→ 同一durable journal：原件保存、受控发布、全owner复核
→ 成功commit/清pending，或回滚/保留pending并由recover续作
→ 正常Host重开与事实回读
```

**入口。** 扩展现有 `runLocalHomeCli`，提供 `home restore --from DIRECTORY [--home PATH] [--json]` 和 `home restore --recover [--home PATH] [--json]`；闭合参数、重复/冲突参数在获锁前拒绝。actor、目录检查、Memory所需key及owner端口来自可信产品装配，不接受CLI自选inspector、allowFresh或模拟成功回调。原snapshot命令保持。

**集合与预检。** 唯一集合来自当前Home登记、归档中的已装库owner及各现行声明，不能从归档授予写权限或在CLI列库名单。读archive/目标身份、当前版本/完整结构、全部必要payload、安装引用、原key与SDK认证；归档/目标后续变化须在效果前复查。目录路径用当前项目owner推导，不能读回旧catalog.database_path。任何不完整、未知或不符输入均不进入发布，不伪称每个同号历史形状都可识别。

**Memory只读资格。** storage作为表owner新增窄inspection：只读当前账本、可信actor的个人/project-default完整偏好，复用contracts的 `isCompleteMemoryPrefs`，不复制校验、SQL到Host或密码学。缺文件只报告absent；存在但损坏、版本/结构/偏好不完整直接拒绝。不调用可写 `openMemoryLedger/applySqliteBaseline`，不切WAL、不创建源库/目录/key、不开SDK/Host/模型；源、归档及侧车保持不变。

**源事实与真正空态。** absent不是恢复资格。现有snapshot inventory必须在同一owner lease下记录实际源根、必要嵌套容器及当前排除路径的存在状态，区分不存在、存在的节点种类与被排除；必要事实连同store/SDK现行owner事实由现有snapshot编排带入归档并复核。排除理由和“未备份”不能表示源中不存在；不新建快照器、密码学或独立库名单。记录采用实际枚举/检查结果，不写归档自报的empty/allowFresh布尔。

Host恢复以这些完整事实和当前owner合同共同推导真正空Home/允许的锁与技术文件状态；业务非空缺账本、已有不完整偏好、遗漏/unknown、必要源事实缺失或排除路径无法证明的归档均拒绝空态资格，不能默认为不存在。实际含bin/releases而业务stores均absent的源仍为非空，不得生成默认Memory。缺源事实的归档不因此丧失完整现行账本的正常恢复资格，但不能走空态初始化；不添加猜测旧归档的兼容路径。

**准备与发布。** 仅在完整预检后，于目标Home外本次700私有空暂存目录调用现行 `prepareMemoryHome` 生成reviewed账本，关闭并只读验证；已有完整账本恢复归档原件，不生成默认。生成产物与普通恢复文件一起纳入同一journal/目标计划，记录原目标身份、原件位置和预期内容，在任何目标变更前durable prepared。准备失败不写目标；不另建Memory恢复表、第二发布器或私有任务图。

**状态与收尾。** 发布后先复核文件与全部owner资格（含Memory），再记committed/清pending。未committed失败按同一journal回滚；失败不能完整回滚时保留原件/pending并明确未完成。committed未clear的recover只复核/收尾，不重置偏好；状态变化或与预期不符则保留现场报changed。同一journal重试复用已准备节点，不重新写默认；无pending的recover无写入。另一次明确完整restore仍按原快照替换范围，不暗加跨操作保留所有后续修改的新语义。

公开结果严格对应实际：`restored`须发布/owner复核及解除阻断均成功；`unchanged`也须完成资格/key/当前性检查；`rolled_back`只证明回到操作前；`finished`只证明committed收尾；`no_recovery`表示没有待续作。部分发布、未确认清pending或回滚失败不能返回成功；沿现有CLI错误模型报告，不静默跳owner。

**互斥与公开Catalog寿命。** pending存在时正常Host/Catalog/SDK借用及已有同Home写入口必须在业务写前拒绝。公开 `MolisWorkProjectCatalog.open` 与桌面包装入口须在首次 `prepareMemoryHome`、mkdir或目录库写入前受同一排他lease/pending检查保护，连接整个寿命保持该保护，不以无锁exists检查代替。

已有Host通过最小公开options/可信装配复用属于同Home的真实opaque capability，不二次acquire、不按samePID放行，也不占SDK专用的单borrow槽。Host在Catalog关闭后才释放其父owner；Catalog自身失败/close只清理自己的连接/持有，不误释放Host父owner。独立Catalog由同一核心取得同锁，并向现行初始化传真实owner，保留“仅技术锁”fresh条件；初始化失败及close完成后释放自持lease。桌面/Web直接调用方只适配这些必要options/资源寿命，不在外层内层各获一次锁；不向IPC/CLI传可伪造的owner标志。显式recover仍用同一底层inode排他锁，不能借它启动SDK、绕过真正busy或用samePID通行。恢复不在线quiesce/resume，不重构全Catalog或制造第二把锁。
