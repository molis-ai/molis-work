## 1. 问题与范围

同发布者的新 Home 签名包当前被 `PluginInstallService.confirm` 与 `openHomeInstalledPlugins.installPackage` 两处提前拒绝，提示先卸载重装；项目包已走共用 `installedLifecycle('upgrade')`。设置页只在项目 `data.plugins` 中找旧版本，无法显示 Home 升级预览。接受方案要求同发布者、版本递增、范围不变时原地升级，数据与安装身份保留，新批准、密钥、提示词归新版本；公开确认无密钥值输入，密钥值替换及失败恢复由同一生产 Home lifecycle 受控输入层单列证明，不把该层冒称设置 DOM 输入。两个范围仍不提供用户回滚。

仅完成 BL-711，不实现 T-145 的逐项目同意、T-143 模型设置/生图、T-144 Agent/方法、T-149 创作台签名，也不借此放开沙箱权限、改包信任或打开真实 Home。BL-916、PG-011整体不因本片完成而全部销账。

## 2. 已定语义及实现要求

1. `plugin-install-service.ts:confirm` 去掉 Home 一律拒绝的分支，保留预览绑定actor/project/时限与一次性消费；仍先检查范围、发布者、ID命名空间、版本，再 pinPublisher / save / 切换。另一发布者、相等或更低版本、范围改变，拒绝时旧安装、授权、文件、密钥和调用能力都不变。
2. `home-installed-plugins.ts:installPackage` 根据本 Home 当前有效安装决定 install/upgrade，调用同一 `installedLifecycle`，不能新增第二份升级算法。查询仍由 Host 当前记录决定，不能用输入声称“这是升级”。禁用安装升级后仍禁用、不得自动运行；running安装升级后使用新定义与提示词；quarantined/包不可读/撤销发布者按共用生命周期现行拒绝，不顺手扩恢复语义。
3. 共用 `installed-plugin-version.ts` / 生命周期已经拥有版本切换、批准/密钥、提示词与失败补偿，先复用。公开 confirm 保持 preview_id/consent/pin_label；公开升级核新批准、secretRef 授权及原密钥无非预期改写，不能用空 secrets 数组证明 stage/apply/restore。真实 Home 生产 lifecycle 的受控输入层另核 replacement/fresh 值、生效、失败原值恢复/新增值撤销及较新状态保护。失败补偿恢复原版本属于内部一致性恢复，不能因为D1“不做用户回滚”删掉它；用户主动rollback仍按原断言拒绝。
4. 设置页读取Home列表后保留该列表，按预览 `runtime_scope` 选Home或项目旧记录，再显示已有中英文“已装的是x，装上后升级到y；数据保留”。同一 review 对初次安装和 Home 升级均展示本次签名预览的服务及精确 HTTPS origins；复用现行 preview 返回值，不新增端点或来源授权规则。新权限/声明仍显示，来源改变时让人重新看见并明确确认；取消不安装、不升级。只改现有设置流程，不新增页面资源。当前 API 有 origins 而实际设置页尚未展示，这是既有 BL-530/BL-691 合同缺口，与 T-122 核收交接在本单统一补齐。
5. 本片的“Home包”包括已支持的integration包，不能只删app两处拒绝却留下集成旧声明。现行 Home 升级链不会调用 registry detach；attach 已有 entry 时只换 contribution，故必须补声明刷新。最小方案在 registry 既有 attach 队列任务内先 parse/live 并调用完整 `this.assertFree`（含 Host id、OAuth 和当前 Declarations 检查），检查失败时旧占用/entry 不变，成功后才同步 release/declare 与替换 entry，中间不加 await。复用 Declarations 的现有方法，当前不必改它。Home 单独拆成 detach→attach 会先释放旧占用，不能只凭“同一队列”宣称失败补偿安全。此最小方案须先由根逐文件释放/串行交接 #1672 registry 及 T143 Home 重叠文件；另有更小方案须交根核保留旧占用、补偿与关闭/取消证据。T-134 真实安装声明者钉住继续保留，不放宽其他发布者。
6. 签名集成来源变更仍按BL-530/BL-691现行预览逐项展示并确认，不能自动沿用旧来源批准。范围仍是已支持source，不加document_import或新OAuth声明能力。
7. 升级、取消/撤权/关闭并发沿现行世代和beforeEffect检查：旧实例晚回执不写新版本业务；失败不留混合批准/密钥/提示词。身份/版本/scope 确认预检拒绝要求零新 pin/save；合法 v2 已保存后才发生的启动/切换/expose 失败，要求旧运行、数据和授权一致恢复，不要求删除已合法保存的 v2 包。安装ID延续必须从实际Runtime记录验证，不能仅比较plugin_id；新安装/其他发布者不得接管T-134连接。

旧编号逐条映射，PR必须解释预期变化，不整体删除快照或拒绝：

- RAC-1505：签前构造同 publisher compatible v2，公开升级成功；核原安装身份/数据和真实 v2 操作，不再断言 afterNewer 等于旧安装。
- RAC-1506：再次提交当前 v2（或独立 v1→v1），精确 plugin.upgrade_required，同版后当前完整快照不变；升 v2 后再提交 first(v1)只能算降级，另由 RAC-2617 证明。
- RAC-1507：成功前后及同版拒绝后都取完整快照；成功允许版本/批准的预期变化但身份/数据保留，拒绝后对成功后的当前快照逐项不变，后续真实写读可用。
- RAC-1683 与 RAC-1500/1501/1504：自己的 compatible 新版成功另核；未 pin 的 b 与已 pin 的 c 两个别 publisher 仍精确拒绝、零新 pin/save/数据/连接变化且候选未启动，先核 v1 原身份/数据/真实动作，不能混成所有尝试后仍 v1。
- RAC-1682：service harness 对 running/disabled 合法新版核正确 Home 安装端口和保存合法包；非法版本/身份/scope 预检零副作用仍保留。harness 不证明真实 disabled 未启动，后者必须在真实 Home 用例核。

预检拒绝与已 save 后的补偿失败分层。公开主成功/公开失败补偿/source/真实设置 DOM 仍各自必需，不能全部换成直接 lifecycle。v2须在签名前声明正确的 `upgrade_compatibility.compatible_from_versions`，不得用缺compatibility或改签后manifest制造假首败。至少新增主成功路径与一个失败补偿场景先在当前main失败，失败应是目标Home升级缺口。登记回归须直接调生产 registry，不能手动detach替产品补刷新；新声明冲突时断言旧占用/entry不变。mock只证明局部；主流程用临时Home、真实签名包与Host/Runtime；模型可用本机替身，不用真实凭据。
