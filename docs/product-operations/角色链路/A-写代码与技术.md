- 要另一个人确认、但只能由你代记结论的（法务、导师、客户、家人），按机制本身标，不因此降级，瓶颈里写"对方进不来，由你代记（团队协作未做）"。

## DEV 独立开发者 / 一人公司

**角色画像**：一个人做一个付费 SaaS 或 Mac 小工具，上午写代码、下午回用户邮件、晚上发推。工具是 Claude Code 或 Codex 加 GitHub、Stripe、Notion/Obsidian、一个邮件客户端，偶尔 Linear。AI 是主力劳动力，经常两个 Agent 同时开。最在意三件事：上线时没漏掉自己答应过的东西，切换上下文少花时间，每月 AI 账单可控。

### DEV-01 测试全绿了，可退款在手机上我还没亲手点过
- 触发：周四晚上准备上线 Stripe 退款，Claude Code 说"已完成，测试 42 个全过"；周五早上要发公告。
- 链路：
  1. Goals 新建 Goal "退款上线"，用 `goals.agreement.set` 写当前约定：四条要求（全额退款、部分退款、失败重试、手机 Safari 完成退款），最后一条标"必须由人验收"。Work 替人把"什么算完成"落成一份所有 AI 都读同一份的账。
  2. 项目设置写项目长期说明（`goals.guidance.add`）："金额一律用整数分；不改 `/api/v1` 公共接口"。内置助理和 Coding 每轮都带上当前版本；外部 Runtime 在经 MCP 读连接摘要（`context_resolve`）时拿到，读不读由它决定，Work 不往外部 Agent 的每一轮推送。
  3. Claude Code 经 MCP 连上这个项目，读连接摘要拿到这条 Goal、四条要求和项目说明（也可以从这条 Goal 打开 Claude Code 终端（F-011），推进提示带着目标和项目说明；从 Goal 打开的绑定终端还在，10-24 起由工作台承载（#1113））。
  4. Claude Code 经 MCP 调 `goals.events.report` / `goals.progress.record`，只为自动化覆盖的三条要求报支持。
  5. 它调 `goals.closure.submit` 时被 `goals.event_closure.human_decision_required` 拦下：Goal 页写明"还差手机 Safari 本人验收"，已交的三条保留。
  6. 本人用手机试，在目标页的决定表单里记结论（`goals.decisions.record`，只有本人入口能写）；并在结论里手写当时的构建号。之后若改约定，这次点头作废、要重新验收。
- 交付物：一条已完成的 Goal，时间线上分开显示"Agent 报的测试"和"本人验收结论"。
- 机制：M2、M1
- 成熟度：main 可用；瓶颈：结论不自动绑定代码 SHA 或构建号（要人注明），goal-closure-identity 待本人验收；只标了"必须由人验收"的要求不会点亮菜单栏，要 Agent 发起验收请求（`requirement_acceptance`）才会，平时靠 Goal 页和收尾被拦来提醒。
- 原来怎么做：GitHub issue 里的 checklist + CI + 自己审 PR + `CLAUDE.md`。纪律好时足够；卡在"Agent 说完成""CI 绿"被顺手当成整件事完成，手机那一项没有一个"必须我看过才能关"的地方挂。Claude 的 `/goal` 由另一个小模型读对话来判定完成，Codex Goals 由 Agent 自己判定，两者都只看会话内容，不看你亲手点过没有。
- 不适合：几分钟的小修；已有严格 QA 清单且每条都映射到 CI 的团队。
- 频率/痛感：中高。Stack Overflow 2026 调查近一半人只在能自行验证时信任 AI，仅 6.6% 愿让 AI 参与重要决定（外部补研 §2.2）；旧研究 D1 引的 Kiro、spec-kit 公开报告证明"标完成但没做完"的故障存在。

### DEV-02 早上 37 条 GitHub 通知，真正要我动手的只有两条
- 触发：每天 8:30 打开 GitHub，通知里混着 Dependabot、别人的评论、付费用户提的崩溃。
- 链路：
  1. 「设置 › 服务连接」用设备授权码连 GitHub；Feed 加 GitHub 账号来源（F-098），设每 30 分钟自动拉。
  2. 建捕捉规则（`feed.rules.create`）：关键词 "crash / regression / refund" 加一条判断规则；先 `feed.rules.preview` 看最近 5 条原消息会怎么判，不调模型、不入箱，再保存，设 `admission: "inbox"`。
  3. 命中的进 Inbox；`inbox.next` 场景只给四种建议：先核查、整理成稿、做完了、忽略。要不要复现、是不是重复、并进哪个 Goal，由你自己判断。
  4. 那条付费用户的崩溃点"升格为 Goal"（`feed.items.promote`），消息以 sha256 摘要记为 Goal 的已确认输入。
  5. 让 Codex 接这条新 Goal：它经 MCP 读到目标和消息出处，开始处理（也可以从新 Goal 打开 Codex 终端，推进提示带着目标和出处；从 Goal 打开的绑定终端还在，10-24 起由工作台承载（#1113））。
  6. Dependabot 那条"转为待办"（`todo.items.create`，来源 `inbox:<id>`），排到周五。
- 交付物：一条带原始消息出处、Codex 已接手的 Goal，一条待办；Feed 里其余消息保持已读。
- 机制：M4、M1、M3
- 成熟度：main 部分；瓶颈：GitHub 通知的真实账号联调待验（F-098 自述）；`inbox.next` 要绑一条判断规则，要先连 TypeSafe，只用关键词时可以入箱，但没有"建议下一步"这一环。
- 原来怎么做：GitHub 通知页加邮件过滤器，看中一条就复制链接和报错贴进 Claude Code 重讲一遍背景。过滤本身 GitHub 做得不错；卡在"贴给 AI"这一步每次都是手工搬运，而且事后找不到哪条通知变成了哪次修复。
- 不适合：一天只有三五条通知的项目；已经用 GitHub 自带的 Copilot coding agent 直接 assign issue 且满意的人。
- 频率/痛感：高（每天）。HN 多位作者描述在 CLI 与聊天之间手工搬提示（agentifysh、kaydub，外部补研 §2.2）。

### DEV-03 周五要发 changelog、一条推文、给 50 个付费用户的邮件
- 触发：周五下午 4 点，本周关了 5 条 Goal，合了 9 个 PR，晚上要发版本 0.8.3。
- 链路：
  1. 底栏对助理说"把本周完成的 Goal 和 Coding 报告整理成 0.8.3 发布说明"。助理用 `find-capabilities` 找到 `goals.list`、`coding.reports.list`，先读后写，`pages.create` 走操作卡，人点了才建。
  2. 在 Pages 里选中"技术细节"一段，浮条上选"读者视角"/"改写·更口语"（`pages.ai`），候选出现在旁边，确认才写入。
  3. 从 Pages 再生成一版 280 字的推文稿和邮件稿，助理回复里选一段，用落点"替换选区"放回（`pages.landing.replace`），先在落点处预览。
  4. （可选）图片插件按提示词出一张版本配图（`images.jobs.start`）。
  5. `pages.promote` 把发布说明固定成 v1，`goals.deliverables.pin` 记为"0.8.x 维护"Goal 的交付物。
  6. 规划：工作简报插件把"本周交付"做成可刷新的状态页，只报和上周相比的变化，取不到的数据标"过期"（work-brief §3.1–3.4）。
- 交付物：一份固定版本的发布说明（成果库可回查"当时发的是哪一版"），一张配图，两份分发稿。
- 机制：M4、M3、M6
- 成熟度：main 部分（第 4 步配图可选，第 6 步工作简报为规划）；瓶颈：代码若是在外部 Claude Code 里写的，就没有 `coding.report.v1`，助理只能读 Goal 进展记录；配图的付费厂商账号未验收。
- 原来怎么做：release-please 或 GitHub 自动 release notes 出 changelog（这部分已经很好）；推文和邮件在 ChatGPT 里另写，再贴回 Mailchimp。卡在三份稿子各改各的，下周想查"上次邮件里承诺了什么"要翻发件箱。
- 不适合：只发 changelog、不做面向用户的说明的项目。
- 频率/痛感：中（每周到每两周）。Anthropic 的 Cowork 用量分类里，最大的一类是"业务流程与运营"（33.4%），"把零散更新整合成报告"只是这一类下举的一个例子（外部补研 §2.6，用量证据，不是痛点证据）。

### DEV-04 用户说"扣了两次钱"，我要在对话里把 Stripe 接进来查
- 触发：周日晚上一封愤怒邮件，说被重复扣款；Stripe 后台能查，但我想让助理顺着查完并记下要跟进的人。
- 链路：
  1. 对助理说"帮我接入 Stripe 的 MCP"并给出地址。助理先查已有连接，选远程 MCP 方式，配置、连接、验证（`connectors.setup.prepare/execute`）。以后连接时还要选三种权限之一：只读协助、修改前确认、授权内自动执行；默认只授权这一次工作，查扣款选只读协助就够（MCP 策略，规划 3·C）。
  2. 需要登录授权时，助理停在受保护的接入链接；本人在那个表单里完成，密钥不进对话、不进截图。完成后原任务按最新意图自动续办（#661）。
  3. Stripe 的工具作为"MCP 提供方"的动作进了项目动作目录（F-136），助理用 `read-capability` 查这位用户近 7 天的扣款。
  4. 助理用提问卡（`ask-user`）请你选"退哪一笔"；问题卡在 Molis 重启后仍在，回答时按那一刻的权限重核（#695）。
  5. 退款这类写操作由你在 Stripe 后台自己点；助理只用操作卡建待办"周一回信给 X"并 `todo.items.link` 到 Goal "支付稳定性"。
  6. 给那条待办设"在等"并填跟进日（`waiting.follow_up_on`）：到日子首页出现跟进提醒，再让助理照第 3 步查一遍。每天自动巡检今天做不到：Schedule 的对话任务只读得了项目工作目录里的文件，调不了 Stripe 的工具，也读不到 Molis 的数据；"打开就有一页"的巡检属于主动助理（规划：交办的后台执行 2·A，主动发现 3·A；不承诺电脑关机或睡眠时还在跑）。
- 交付物：一条带出处、带跟进日的待办，Goal 上的一条问题记录。
- 机制：M5、M7、M6
- 成熟度：main 部分；瓶颈：#661 整功能全量与真实账号 OAuth 验收未完；每天自动巡检做不到（现为跟进日提醒，本机服务没在运行时提醒不送达）。
- 原来怎么做：Stripe Dashboard 查 + Claude 桌面版接 Stripe MCP 问，后者已经能查得很顺；Claude Routines 还能定时跑每日只读巡检，也带得上账号下的 connectors，这部分它做得更直接。卡在查完要另开 Todoist 记跟进，而且这次查的结论没挂在任何项目记录上。
- 不适合：不想让 AI 碰任何支付数据的人（即使只读）。
- 频率/痛感：中（突发，但一出就是付费用户）。推断。

### DEV-05 下个季度做团队版还是做 Windows 版
- 触发：等候名单里 40% 是团队用户，另一批人在推上要 Windows；只有一个人，下个季度只能做一个。
- 链路：
  1. 炼金术士写探索方向"团队协作 vs Windows 客户端"，启动炼化（`alchemist.explorations.start`）得到候选卡，保留两张成 Idea。
  2. Forms 建问卷，AI 拟题（`form.questions.draft`）要求不具体时先回问三道选择题；`form.fillpage` 导出独立 HTML 填写页随邮件发给 40 个等候用户，答卷文件发回后 `form.answers.import`（同一份只算一次）。
  3. 在 Form 界面点「存成数据表」，把现有答卷做成一张数据表，做分组计数并 `dataset.snapshot`；之后再到的答卷不会自动并进这张表，要再存一次。
  4. 炼金术士对两个 Idea 各跑双 Lens 研究（`alchemist.research.plan/start`）：市场空间与实现成本，设模型调用上限；预算不够只得部分报告并标出来。
  5. 两个 Lens 都齐后记 Build/Hold/Drop 决定（`alchemist.decisions.create`），带理由和报告引用。
  6. 对 Build 的那个，在 Goals 新建 Goal，用规划方法库读"开发者工具"行业包和"构建变更"工作类型（`goals.planning.read/apply`），由 Runtime 提结构提案，本人逐条确认进树（`goals.tree.decide`）。
- 交付物：一条有理由与报告引用的决定，一份固定快照的答卷表，一棵确认过的 Goal 树。
- 机制：M4、M2、M5
- 成熟度：main 可用（需模型）；瓶颈：炼金术士包仍标 partial；Forms 只出本机填写页文件，答卷靠对方用邮件、微信等发回，内容会经过这些通道（只是不经问卷平台）；新答卷不会自动并入已存的数据表。
- 原来怎么做：Tally 或 Google Forms 发问卷，导进表格，再把结果贴进 ChatGPT 问"该做哪个"。问卷工具本身很成熟；卡在决定和依据各在一处，三个月后回看"当时为什么不做 Windows"找不到。
- 不适合：已经有明确付费客户合同指定方向的人；问卷需要公网链接、几百份回收的场景（Forms 只出本机填写页文件）。
- 频率/痛感：低频高痛（每季度一次）。推断。

### DEV-06 每次发版都要核的 6 件事，我想做成一个我和 AI 都能用的小工具
- 触发：0.8.2 发版时漏改了 `Info.plist` 里的版本号，审核被拒，损失两天。
- 链路：
  1. 插件创作台用一句话描述："发版核对台：每个版本一张清单，6 项（三处版本号一致、CHANGELOG、签名、迁移脚本、截图、价格页），每项记结果、证据链接、谁核的"。Agent 设计、在 macOS 沙箱写后端和测试、宿主类型检查、打包、试跑后安装（F-044）。
  2. 插件的动作进动作目录：界面、内置助理、外部 Claude Code（经 MCP，逐项授权）调的是同一个处理器。
  3. 发版时 Claude Code 在终端里跑完版本号检查后，调插件动作记"三处一致"并附命令输出摘要；截图、价格页两项由人在界面里勾。
  4. Goal "0.8.3 发版" 的要求里写"核对台 6 项全绿"，并把那一项标为本人验收。
  5. 每周五用插件里登记的 `reminders.add` 把"核对台还有未完成项"放进 Inbox。

- 交付物：一个装在项目里的插件；每个版本一张有证据的清单。
- 机制：M5、M1、M2
- 成熟度：main 部分；瓶颈：创作台生成的插件不自动声明成果类型、搜索对象和工作流内容站（搜不到、进不了成果库，产品介绍 2026-10-18）；"业务样例"尚未做；仅 macOS。
- 原来怎么做：仓库里一个 `RELEASE.md` checklist 加一个 shell 脚本。这条路零成本、很多时候就够；卡在脚本只在终端里，AI 和人各勾各的，勾没勾不会挂到任何"这次发版算不算完"上。
- 不适合：一次性检查；已经在 CI 里做完全部检查的项目。
- 频率/痛感：中（每次发版）。旧研究 D6；HN 上也有"个人小工具难维护"的强反对声（外部补研 §2.2），所以讲法是"做出来不用自己养"，不是"AI 帮你写软件"。

**这个角色最可能的 killer**：DEV-01。它是独立开发者每次上线都会遇到的"AI 说完了 vs 我还没看"，而我们读到的竞品官方页面里还没有把"本人验收"做成目标级一等对象（外部补研 §1 读法第 4 条）；Claude `/goal` 和 Codex Goals 都只看会话内容，由小模型或 Agent 自己判定完成。

## OSS 开源维护者

**角色画像**：维护两三个中等流行的库，业余时间或半职。每天面对 GitHub issue/PR/Discussions、偶尔邮件列表和 Discord；用 Copilot 或 Claude Code 修 bug、审外部贡献。最在意：时间碎片里不漏重要的事，外部 PR 的质量（尤其 AI 生成的），每次发版不出错，别被倦怠吞掉。

### OSS-01 周六上午清 issue：30 条新的里挑出能复现的交给 Agent
- 触发：一周攒了 30 条 issue，一半没有复现步骤，有两条带最小复现仓库。
- 链路：
  1. Feed 的 GitHub 账号来源拉通知；捕捉规则用关键词 "bug" 加一条判断规则（score：是否附了最小复现），预览最近 5 条后保存。
  2. 命中的进 Inbox；`inbox.next` 场景只给"先核查 / 整理成稿 / 做完了 / 忽略"四种建议，需要复现、疑似重复、可交 Agent 这三类由你自己判断。
  3. 对"可交 Agent"那条，⌃⌥W 把 issue 页抓进 Shelf，再把复制的 stack trace 从剪贴板历史放进去；Shelf "提取结构化信息"出要点。
  4. 升格为 Goal，要求里写"维护者本人复现过"并标本人验收。
  5. Codex 经 MCP 读到这条 Goal 和 issue 出处，写修复和回归测试，经 MCP 报进展（也可以从 Goal 打开 Codex 终端，上下文填入、不自动发；从 Goal 打开的绑定终端还在，10-24 起由工作台承载（#1113））。
  6. 其余没复现步骤的，用一条 Inbox 事项"转为待办"提醒自己周日统一回"请补充复现"。
- 交付物：每个被处理的 issue 对应一条 Goal 或一条待办，带原始通知出处。
- 机制：M4、M1、M2
- 成熟度：main 部分；瓶颈：GitHub 通知真实账号联调待验；判断规则需 TypeSafe；Shelf 热键需桌面 App 与辅助功能授权，真实时段实操未做。
- 原来怎么做：GitHub 通知 + label + 保存的搜索，再把 issue 贴给 Claude Code。GitHub 的分拣界面很成熟，Copilot coding agent 可以直接 assign；卡在"哪条交给了哪个 Agent、修好后谁复现过"没有统一记录。
- 不适合：已经用 GitHub Copilot 直接 assign issue 并满意的仓库；issue 量极少的项目。
- 频率/痛感：高（每周）。旧研究 D4；外部补研 §2.2 的复制粘贴证据。

### OSS-02 外部贡献者的 AI 生成 PR 越来越多，我只想看值得看的问题
- 触发：一周来了 8 个外部 PR，其中 5 个明显是 AI 生成，改动大、描述空泛。
- 链路：
  1. 在 Coding 里对 PR 分支准备独立工作树，用"评审"方式检查现有改动给意见。
  2. 再派一个只读"独立评审"子任务交叉看，结果区显示它实际读了哪些文件。
  3. Diff 看变更集，对行写意见；意见追加到原草稿，由你自己发到 GitHub（Coding 不代发）。
  4. 规划：多代理评审只保留置信分 ≥80 的问题，安全评审只出补丁不自动应用（CQA）。
  5. 规划：显式人审——维护者明确启用 PR 人审时，无写权限的 fork 作者、Agent、bot 的批准不计，分支名不作为信任依据，`/approve` 绑定 head SHA（agent-approval，10-28 改）。
  6. 把要合的 PR 记进 Goal "v3.2 发版"的输入，作为发版的依赖。
- 交付物：每个 PR 一份固定评审报告和逐行意见草稿。
- 机制：M2、M7
- 成熟度：规划（第 1–3、6 步为 main 部分）；瓶颈：多代理评审与显式人审只有 spec；Coding 下一阶段的 Q1～Q8 已定，GitHub PR 跟进在 D 期，排在路线图阶段 4。
- 原来怎么做：GitHub review + CodeRabbit/Copilot review + CI。机器人评论覆盖面广；卡在噪声多，维护者还是得把每条读一遍。
- 不适合：只接受少量、可信贡献者 PR 的项目。
- 频率/痛感：中高。Obsidian 官方承认编码 Agent 让插件投稿激增、审核队列变长（外部补研 §4）；HN 多位作者说评审是瓶颈（§2.2）。

### OSS-03 第五次有人提同一个功能请求，我要找出三年前拒绝它的理由
- 触发：周三晚上有人在 Discussions 再次提"支持全局配置单例"，你记得以前讨论过但找不到在哪。

  1. Cognia 导入仓库 `docs/adr/` 和导出成 Markdown 的旧 Discussions（`cognia.import.directory_preview` → `commit`），保留路径与每次变更的版本，源文件不被改。
  2. 在"设计决定"领域提问（`cognia.knowledge.query`），回答必须带合法的固定来源引用；上下文超过 100,000 字符直接拒绝，不截断。

- 原来怎么做：GitHub 搜索 + 记忆 + 翻旧 issue。issue 标题写得好时 GitHub 搜索够用；卡在理由散在长评论线程里。
- 不适合：没有 ADR、讨论也很少的年轻项目。

### OSS-04 发版周：changelog、迁移指南、社区直播讲稿要同源
- 触发：v3.0 有破坏性变更，周五发版，下周二社区直播。
- 链路：
  1. Git 看 v2.9..HEAD 的变更集；Coding 用"讨论"方式按变更类型归类，产出固定报告。
  2. Pages 用"技术方案"模板起迁移指南；外部 Claude Code 经 MCP `pages.get` / `pages.update` 写同一篇：顶层 Agent / MCP 调用必须带读取时的整篇版本，缺了或旧了都被拒、要求重读；Agent 的改动还会记成可撤回的变更。

  5. 发版后改了一处错，再 promote 成 v2；成果库里能看到"直播讲稿引用的是 v1"。
- 交付物：固定版本的迁移指南、一份 `.pptx`，二者的引用关系可查。
- 机制：M4、M1
- 成熟度：main 可用（需模型）；瓶颈：Coding 与 Pages AI 要配模型；PPT 不含图片与图表。
- 原来怎么做：release-please 自动出 changelog（做得很好），迁移指南写在 docs 仓库，讲稿在 Keynote。卡在三份内容改了一处不知道另两处是否跟上。
- 不适合：只发补丁版本、没有迁移成本的项目。
- 频率/痛感：中（每个大版本）。推断。

  4. 规划：代码现代化工作流——评估 → 地图 → 业务规则作为候选由你确认 → 计划批准 → 工作树内增量改造 → 行为等价证明（"测试通过"不算完整证明）→ 一页式报告（code-modernization）。
  5. 结论记进 Goal；若暂不升级，在目标页的决定表单里记"暂缓"和理由。
- 交付物：一条有决定和依据的 Goal；若升级，一份固定变更集与报告。
- 机制：M4、M2、M5
- 成熟度：规划（第 1–3、5 步为 main 部分）；瓶颈：代码现代化只有 spec；网页查询来源的集成工厂是骨架，实际通路在宿主（F-102）。

- 不适合：依赖很少、升级无破坏的项目。
- 频率/痛感：低频高痛。推断。

**这个角色最可能的 killer**：OSS-01。每周都发生，GitHub 通知 → Inbox → Goal → Agent 经 MCP 接手是现有能力最完整的一条（最后一环也可以是从 Goal 打开的绑定终端），且维护者要的正是"哪条交给了谁、谁复现过"。

- 交付物：一份复盘文档、一批有出处有日期的待办、日历上的复查日。
- 机制：M4、M3、M5
- 成熟度：main 部分（风险插件为规划）；瓶颈：#661 整体验收未完；Todo 整理要配模型；右栏放进左边的落点只有 Pages，本人验收未做。
- 原来怎么做：Google Doc 复盘模板 + Jira 建 action item。模板很成熟；卡在 action item 建了没人跟，下次复查时找不到它们出自哪次事故。
- 不适合：已有成熟事故管理平台（如 incident.io）且流程跑通的团队。
- 频率/痛感：低频高痛。推断。

### TL-05 新人入职，把团队的做法装进他的 AI
- 触发：下周一来了一位新工程师，他用 Codex，团队的评审规范和测试约定都在 TL 的 Claude Code Skill 里。
- 链路：
  1. TL 用 Characters 从自己的 Claude Code 导入"团队代码评审"规则和 Skill，发布成项目角色。
  2. 平台记忆导出"记忆包"（`memory.export`，密钥与本机路径已去掉），新人在自己机器上导入。
  3. 项目长期说明里"质量标准 / 协作约定"两节由 TL 写清，新人的 Codex 接入 Molis 后经连接摘要读到当前版本（Work 不往外部 Agent 的每一轮推送）。
  4. 规划：把评审做法打成技能包（`pack.json` + `skills/*/SKILL.md`），签名、固定版本，安装前展示要用的连接器，用 `~~project tracker` 类别占位符让同一包适配 Linear 或 Jira（skill-packs、ASC-38–44）。
  5. 新人第一周的 Goal 里写"按团队规范完成一次评审"，TL 本人验收。
- 交付物：新人机器上的一份角色、一份记忆、一份项目说明；第一次评审有 TL 的验收记录。
- 机制：M5、M1、M8
- 成熟度：规划；瓶颈：技能包只有 spec；Characters 与项目说明目前不跨机器同步，新人要自己导入；团队空间未做。
- 原来怎么做：Notion 入职手册 + 仓库里的 `CONTRIBUTING.md` + 把 Skill 文件夹打包发给他。手册很成熟；卡在新人的 AI 不读手册，Skill 格式在 Codex 那边还要转。
- 不适合：团队已统一用一家 Agent 且规则都在仓库文件里的。
- 频率/痛感：低（每次入职）。推断。

**这个角色最可能的 killer**：TL-02。范围变更"一处改，内置助理和 Coding 下一轮按新范围，外部 Agent 下次读约定或收尾时按新范围，旧验收作废"是 Goals 最独特的组合，且是 main 可用；演示时说明外部 Agent 不会被实时通知。

## QA 测试与质量

**角色画像**：测试工程师或小团队里兼职质量的人。工具是 TestRail/Xray 或表格、Jira、Playwright、Charles、录屏和截图工具。用 AI 写用例、造测试数据、读日志。最在意：缺陷能稳定复现，回归不漏关键路径，"测过"有证据，发布门不被一句"开发说好了"绕过去。

### QA-01 发版前 12 条关键路径，开发说好了，我要亲手过其中 5 条
- 触发：周四发版，Playwright 跑了 7 条自动化路径全绿，另外 5 条（支付、导出 PDF、离线同步、iPad 横屏、首次引导）需要人看。
- 链路：
  1. Goal "4.2 发版回归" 写 12 条要求，5 条标"必须由人验收"。
  2. 外部 Agent 跑完 Playwright，经 MCP `goals.events.report` 只为 7 条自动化路径报支持，附报告引用。
  3. `goals.closure.submit` 被人工验收拦下，Goal 页列出还差的 5 条。
  4. QA 逐条亲测，在目标页的决定表单里记结论并手写构建号；一条不过就记缺口，Goal 继续而不是重来。
  5. 开发改了一处，约定随之更新，之前对那条的验收作废，需重测。
  6. 规划：明确启用人审的操作，本机审查队列的批准绑定对象、版本、范围，生效前重核；有效授权内的照常执行（agent-approval 本机场景，10-28 改）。
- 交付物：一条已完成的回归 Goal，自动化支持与人工结论分开可查。
- 机制：M2、M1
- 成熟度：main 可用（第 6 步为规划）；瓶颈：结论不自动绑定构建号或 SHA。
- 原来怎么做：TestRail 测试运行 + Jira 发布门。测试管理工具已经很强；卡在 TestRail 的"通过"和开发那边的"完成"是两本账，开发的 AI 不读 TestRail。
- 不适合：已有完整测试管理平台且开发流程强绑定的团队。
- 频率/痛感：高（每次发版）。微软 2026 Work Trend Index：50% 把质量把关列为最重要的人类技能（外部补研 §2.1）。

### QA-02 探索性测试一下午记了 9 个问题，晚上要变成能交给开发的报告
- 触发：下午 2–5 点探索新版编辑器，边点边截图边嘟囔。
- 链路：
  1. 每发现一处，⌃⌥A 把 Finder 里的截图加进 Shelf，或复制截图进剪贴板历史；灵光记一句话描述（自动保存）。
  2. 录了一段口述的录屏，用灵光读文件（`lingguang.material.read`）在本机转写成文字，需要先下载本机语音模型时先问你。
  3. 晚上对助理说"把今天 9 条灵光和 Shelf 里的截图整理成缺陷报告草稿"，助理读灵光与 Shelf 材料，`pages.create` 走操作卡。
  4. Pages 里逐条核对，选中一条"记成待办"给自己明天复测。
  5. 若团队用 Jira：对助理说"接入 Jira"（#661），用 Atlassian 的远程 MCP 由助理逐条建单，写入前每次确认。
- 交付物：一份缺陷报告文档、9 条带截图出处的记录、若干复测待办。
- 机制：M4、M3、M5
- 成熟度：main 部分；瓶颈：灵光转写依赖原生组件（缺失时报 `native_unavailable`）；Jira 写入取决于外部 MCP 服务端与 #661 的真实账号验收。
- 原来怎么做：截图工具 + 一个 Markdown 草稿 + 晚上逐条贴进 Jira。截图工具很顺手；卡在截图和描述对不上号、口述内容要重新打一遍。
- 不适合：缺陷直接在 Jira 里实时记的团队。
- 频率/痛感：中（每个迭代几次）。推断。

### QA-03 用户说"导出 PDF 中文乱码"，我要在桌面版 App 里按他的步骤走一遍
- 触发：客服转来一封邮件，只在某台 Mac 上的桌面 App 复现。
- 链路：
  1. 在「设置 › 助理 › 使用电脑」打开 Computer Use（默认关），系统授权屏幕录制。
  2. 让助理按邮件里的 6 步在目标 App 里操作；每步先问你，或"本轮内允许在这个应用里操作"，导出、删除这类不可撤回动作仍逐步问。
  3. 过程在右栏"电脑"标签实时可见，你动鼠标它自动暂停；终端、IDE 只能看和点、不能打字；银行、支付、密码管理器按名单列为禁区，证券、基金按应用名识别，识别不到的可自己加。
  4. 每轮操作记录进"文件"标签，存在本机：截图 30 天后自动删，文字步骤和回执保留，可随时整份删除；截图放进 Shelf 本机 OCR 抽出乱码文字。
  5. 复现步骤落进 Pages，升格成 Goal 交给 Coding。
- 交付物：一份可复现的步骤记录与截图证据。
- 机制：M3、M7
- 成熟度：main 部分；瓶颈：Computer Use 收尾 #721 已合，二十步整格与带截图的 Shelf 放入要等真机验收（负责人决定推后）；仅 macOS 14+；产品介绍明确不宣传任意 App 自动化。
- 原来怎么做：自己照着邮件点，QuickTime 录屏。自己点最可靠；卡在步骤长、要反复试不同字体设置时很耗时，录屏也不好检索。
- 不适合：Web 应用（用浏览器标签更合适）；涉及支付或银行类 App（在禁区内）。
- 频率/痛感：中（突发）。推断。

### QA-04 需求文档改了一版，我要知道哪些用例要重跑
- 触发：PRD 从 v3 改到 v4，产品只说"小调整"。
- 链路：
  1. PRD 在 Pages 里，每次评审后 `pages.promote` 固定；`pages.artifacts.compare` 只判断固定版与原文当前是否一致（一致 / 已改 / 已移走 / 已删），不对比两个固定版，两版内容分别打开、人工对看（Diff 插件能逐行比较文件快照与变更集，可作以后做固定版差异的基础）。
  2. 用例矩阵在 Dataset（≤40 列、≤2000 行），每次回归前 `dataset.snapshot`，改错可回滚。
  3. Goals 里每条要求对应一组用例；用 `goals.planning.impact` 算这次需求变更的受影响子图。
  4. 只对受影响的要求重建验收；Dataset 里标出要重跑的行，`dataset.promote` 固定为本轮用例版本，记为 Goal 输入。
- 交付物：一份"这次要重跑什么"的固定用例表，和它对应的需求版本。
- 机制：M4、M2
- 成熟度：main 可用；瓶颈：没有两个固定版之间的逐段差异视图（建议 D6，未立项）；Dataset 的行不能直接关联到 Goal 要求，对应关系靠人维护；影响子图只覆盖 Goal 树，不读 Dataset。
- 原来怎么做：TestRail 的需求追溯 + 手动 diff 两版 PRD。追溯矩阵在成熟工具里很好；卡在 PRD 在 Notion 里改了没人通知，diff 靠肉眼。
- 不适合：需求和用例都在同一个测试管理平台里的团队。
- 频率/痛感：中（每个迭代）。推断。

### QA-05 把"修复 → 回归 → 验收"做成一个我和测试 Agent 都写得进去的回归记录台
- 触发：团队开始让 Claude Code 跑 Playwright，结果散在终端输出里，没人能说清"4.2 的第 3 次回归结果"。
- 链路：
  1. 插件创作台描述"回归记录台：每次回归一张单，每条用例记版本、结果、证据链接、执行者（人或哪个 Agent）"，生成、沙箱试跑、安装。
  2. 它的动作进动作目录；在「设置 › 对外接入」给 Claude Code 授权"写回归结果"这一个动作。
  3. Claude Code 跑完 Playwright，调这个动作逐条写结果；人亲测的几条在界面里写。
  4. 工作流程：动作步骤调回归记录台的写入动作、AI 整理衔接汇总失败项、Pages 站收成测试报告；结果未确认时由你选是否重试，避免重复写。
  5. 报告 `pages.promote` 固定，记为 Goal "4.2 发版回归" 的交付物。
- 交付物：一个装在项目里的回归插件；每次回归一张单和一份固定报告。
- 机制：M5、M1、M2
- 成熟度：main 部分；瓶颈：生成插件不自动声明工作流内容站与成果类型，只能经"动作步骤"进流程；工作流动作步骤不能用查询类动作（BL-043）；创作台业务样例尚未做。
- 原来怎么做：Playwright HTML report + TestRail API 脚本上传结果。脚本能用；卡在人工测试结果和 Agent 跑的结果进不了同一张表，脚本也只有写它的人会维护。
- 不适合：已用 TestRail/Allure 且集成跑通的团队。
- 频率/痛感：中（每次回归）。外部补研 §2.2 的"个人小工具难维护"是反面证据，讲法要落在"人和 AI 写同一张表"。

**这个角色最可能的 killer**：QA-01。和 DEV-01 是同一条机制，换成 QA 的对象后痛感更直接：发布门不能被"开发说好了"绕过去。

## DATA 数据分析师 / 数据科学家

**角色画像**：每天写 SQL 和 Python，Jupyter、dbt、Metabase/Looker、Excel；AI 用来写查询、解释口径、出初稿结论。最在意：口径一致、数字能追溯到哪张表哪次查询、结论可复现、敏感数据不乱发。

### DATA-01 周一例会的指标周报，口径每周都得一样
- 触发：每周一 9:30 前交"增长周报"，上个月因为有人改了"活跃用户"定义，两周的数字对不上。
- 链路：
  1. 指标口径文档（Markdown）导进 Cognia，每次改口径都形成新版本。
  2. Codex 在 notebook 仓库里经 MCP 读 Goal "周报自动化"，跑 SQL（也可以从这条 Goal 打开 Codex 终端；从 Goal 打开的绑定终端还在，10-24 起由工作台承载（#1113））；项目长期说明写"活跃用户按 Cognia 口径 v5"。
  3. 结果 CSV 导入 Dataset（每次导入新建一张表，不往旧表追加行），`dataset.snapshot` 留本周快照。
  4. 助理按 Pages "周报"模板起草，口径引用 Cognia 的固定版本；Dataset 的数字由人核对后贴入。
  5. `ppt.create` 后用 `ppt.outline`（给 `page_id`）从周报出大纲，删到 3 页，导出 `.pptx`；`pages.promote` 固定周报。
  6. 规划：工作简报把周报做成只报变化的状态页，口径版本或数据过期时标 stale。
- 交付物：每周一份固定周报，能追到口径版本和 Dataset 快照。
- 机制：M4、M1、M6
- 成熟度：main 可用（第 6 步简报为规划）；瓶颈：每周导入都新建一张表，不往旧表追加，周周对比要自己并；Dataset 上限 2000 行，只适合汇总表。
- 原来怎么做：dbt metrics/semantic layer + Metabase 仪表盘 + Google Slides。语义层已经很好地管住口径；卡在周报文字部分在 Slides 里，引用的是哪版口径没人记。
- 不适合：已有完整语义层与自动周报的团队。
- 频率/痛感：高（每周）。外部补研 §2.1 Adaptavist：42% 的人复核时间超过 AI 省的时间。

### DATA-02 老板晚上 9 点问"为什么上周 DAU 掉了 8%"，今晚就要答
- 触发：Slack 里一句话，明早 9 点要回。
- 链路：
  1. 对助理说"接入我们的 Metabase"（或给本机的 BigQuery MCP 启动方式），助理登记本机 MCP 的程序、包来源、参数与环境变量名，安装固定版本，连接验证（#661）。
  2. 助理用接进来的工具查分渠道 DAU；Coding 用"讨论"方式（只读）翻 dbt 仓库，Git 看上周的模型变更，发现 `is_active` 条件被改。
  3. Pages 起草答复，选中"原因"一段，浮条"找依据"和"提反例"；助理回复里的查询结果段用落点插入。
  4. `pages.promote` 固定答复，链接发给老板；同时在 Goal "指标口径治理" 记一笔"问题与风险"。
- 交付物：一份有查询依据和代码变更出处的固定答复。
- 机制：M3、M4、M7
- 成熟度：main 部分；瓶颈：#661 的本机 MCP 接入整体验收未完；浮条 Jev 排序未做真实评估。
- 原来怎么做：自己在 Metabase 和 dbt 仓库之间来回点，结论写进 Slack。熟练的人很快；卡在第二天有人问"你怎么算的"时，查询和截图已经散了。
- 不适合：数据权限不允许任何 AI 读取生产库的公司。
- 频率/痛感：中高（突发、每月数次）。推断。

### DATA-03 用户调研：问卷 → 数据 → 一页结论
- 触发：产品要在两周内知道 50 个试用客户对新定价的反应。
- 链路：
  1. Forms AI 拟题，要求不具体时先回问；`form.fillpage` 导出填写页文件，随邮件发给客户。
  2. 答卷文件导回（同一份只算一次），在 Form 界面点「存成数据表」做成一张数据表（之后到的答卷不会自动并入，要再存一次）。
  3. Coding 在分析仓库用 Python 读 Files 里的 CSV 快照做交叉分析，产出固定报告（Coding 的"图"是节点连线结构，属于过程项，不进成果库，画不出统计图；统计图要另做）。
  4. Pages 写一页结论，PPT 出汇报稿；`pages.promote` 固定并记为 Goal "新定价验证" 的交付物。
- 交付物：一份固定答卷表、一份分析报告、一页结论。
- 机制：M4、M5
- 成熟度：main 可用；瓶颈：新答卷不会自动并入已存的数据表；Forms 没有公网链接，回收要靠对方用邮件、微信等发回文件（BL-045），答案内容会经过这些通道，只是不经问卷平台。
- 原来怎么做：Typeform + Google Sheets + Jupyter + Slides。每一环都成熟；卡在问卷版本、数据快照、结论版本之间没有引用关系。
- 不适合：需要几百份以上公网回收的调研。
- 频率/痛感：中（每月一两次）。外部补研 U8 证据弱，只作演示。

### DATA-04 客户名单不能发给云端模型，但我还想让 AI 帮我清洗
- 触发：拿到一份 3000 行带手机号的客户 CSV，公司规定个人信息不出机器。
- 链路：
  1. 「设置 › 模型设置」用"OpenAI / Anthropic 兼容"格式添加本机模型端点：回环 http（填 127.0.0.1）可以接，保存前连通性检查；Work 没有专门的 Ollama / LM Studio 模板，也没做过本机模型的质量验收。
  2. 项目长期说明可以写下"本项目只用本机模型；个人字段不进任何提示"提醒同事，但它只是提示词，不路由也不过滤；要守住靠在模型设置里选本机模型，并自己决定交给 AI 的内容。
  3. Shelf 放进 CSV 副本（原件不动），用本机模型跑"敏感信息脱敏"配方，结果是一份新文件。
  4. 脱敏后的 CSV 导入 Dataset（超 2000 行需拆分）；之后的分析才允许用云端模型。
  5. 助理每日 token 上限设好；「设置 › 调用记录」可查哪次调用用了哪个模型。
- 交付物：一份脱敏后的数据副本；只要全程选的是本机模型，原件内容不会发给云端模型。
- 机制：M7、M4
- 成熟度：main 部分；瓶颈：我没有核到"按项目绑定模型"的设置，靠人自觉选模型；本机模型的脱敏质量未验证；Shelf 配方本身会把材料发给"所选模型"。
- 原来怎么做：Python 脚本 + 正则脱敏，或本机 Ollama + 自写脚本。脚本很可靠；卡在每次换数据格式都要改脚本。
- 不适合：没有能跑本机模型的电脑；合规要求连本机模型都不许用的场景。
- 频率/痛感：中。Stack Overflow 2026：13% 因隐私避免用 AI，但只有 2.2% 因此换工具（外部补研 §2.10）——是少数人的硬门槛。

### DATA-05 指标异常时，我想第一个知道而不是老板先问我
- 触发：DATA-02 那种事一个月来两次，想做个"异常雷达"。
- 链路：
  1. 插件创作台描述"指标雷达：读指定 Dataset 的最新快照，和 7 日均值比，超过阈值就提醒"，安装时授权它调 Dataset 的读取动作（插件间只走动作目录）。
  2. 插件用 `schedules.add` 每天 9 点跑一次，超阈值用 `reminders.add` 把提醒放进 Inbox。
  3. Inbox 里的提醒升格成 Goal "调查 DAU 异常"，让 Codex 经 MCP 接这条 Goal 查原因（也可以从这条 Goal 开 Codex 终端；从 Goal 打开的绑定终端还在，10-24 起由工作台承载（#1113））。
  4. 外部 Claude Code 经 MCP 也能调"指标雷达"的查询动作。
- 交付物：一个每天自动检查的插件，提醒落在 Inbox，调查落在 Goal。
- 机制：M5、M6、M1
- 成熟度：main 部分；瓶颈：创作台业务样例未做；本地 Web 服务没开时闹钟不响（BL-030）；Dataset 只存小表。
- 原来怎么做：Metabase alert / dbt test / Airflow 告警发 Slack。告警平台很成熟；卡在告警进了 Slack 就沉了，调查过程没有落到任何"这件事做完没"上。
- 不适合：已有成熟数据可观测性平台（Monte Carlo 等）的团队。
- 频率/痛感：中。推断。

**这个角色最可能的 killer**：DATA-02。突发、时间紧，"接入数据源 → 只读查代码变更 → 带依据的固定答复"一晚上能演完，而且第二天被追问时能拿出依据。

## DEVREL 技术写作 / 开发者关系

**角色画像**：写文档、教程、示例代码、博客、演讲，经营 Discord/论坛社区。工具是 Docusaurus/Mintlify、GitHub、Notion、Keynote、OBS、YouTube。用 AI 写初稿、改写、翻译、检查示例。最在意：文档和代码版本一致、示例真能跑、社区问题有闭环、一份内容多处复用。不以"换 AI 轮流写"为卖点。

### DEVREL-01 API 改了，文档里 14 处示例过期，三篇关键教程我要亲手跑一遍

  4. 报告回写进展；`goals.closure.submit` 在三篇教程没有本人结论前不完成。

- 交付物：一份固定变更集和报告，一条有本人验收记录的 Goal。

- 不适合：示例全在 CI 里被测、教程很少的项目。
- 频率/痛感：中（每个大版本）。推断。

### DEVREL-02 一篇教程变成博客、演讲和视频脚本，三份要跟着同一个版本走
- 触发：写完一篇"用 SDK 做实时协作"的教程，下月要在两场 meetup 讲，还要录视频。

  4. 成果库里"被谁引用"显示第二场的讲稿还指着 v1，用"从这一版继续"更新讲稿。
  5. 图片插件为博客出封面图。
- 交付物：教程 v1/v2、两版讲稿、封面图，引用关系可查。

- 不适合：一次性内容、不复用的写作。
- 频率/痛感：中（每月）。Epidemic Sound 2026：44% 的创作者用 AI 想点子写脚本（外部补研 §2.7，创作者人群，非 DevRel 专属）。

### DEVREL-03 论坛和 Discussions 里同一个问题被问了 20 遍，我要写成 FAQ
- 触发：每周一看社区，发现"怎么在 Next.js 里初始化客户端"又被问了五次。
- 链路：
  1. Feed 加论坛的 RSS（Discourse 有 RSS），可选再加 GitHub Discussions 通知；捕捉规则关键词 "initialize / Next.js"。

- 交付物：一份带来源快照的 FAQ 固定版本，和 docs 仓库里对应的 PR。
- 机制：M4、M1

- 频率/痛感：中（每周）。推断。

### DEVREL-04 我写文档，Claude Code 改示例代码，我们改的是同一份说明
- 触发：写"迁移到 v3"指南时，你在 Pages 里改文字，Claude Code 在仓库里改示例，经常把对方刚改的内容覆盖掉。
- 链路：
  1. 项目长期说明写风格指南："第二人称、每个代码块必须可运行、版本号写全"，内置助理每轮都带上，Claude Code 经连接摘要读到。
  2. Claude Code 经 MCP 授权 `pages.get` / `pages.update`；顶层 Agent / MCP 的写入必须带读取时的整篇版本，你刚改过这篇文档，它手里的旧版本写入就被拒、要求重读（版本按整篇算，不按段落）；它的改动记成可撤回的变更。
  3. Cognia 里的 API 参考（固定版本）作为它的补充材料，经 `cognia:read` 只读检索。
  4. 你在 Pages 评论里 @助理 问"这段和 API 参考 v3.0.2 是否一致"，答复回到评论线程，不改正文。
  5. 定稿 promote，记为 Goal 交付物。
- 交付物：一篇双方都改过、没有互相覆盖的固定版本指南。
- 机制：M1、M4
- 成熟度：main 可用；瓶颈：Pages 对象之外的聊天内容不会自动回传；两端都要接通并授权 MCP。
- 原来怎么做：文档也放仓库，人和 Agent 都改 Markdown，靠 git 合并。git 处理冲突很成熟；卡在写作者不想在编辑器里处理合并冲突，Notion 里的稿子 Agent 又读写不了。
- 不适合：所有文档都在仓库 Markdown、写作者熟悉 git 的团队。
- 频率/痛感：中。外部补研 U10：Readwise、Notion、Capacities 各开自家 MCP，HN 多人自写 MCP 桥（§2.2）。

### DEVREL-05 三个会议的 CFP 截止日、提案和差旅，别再错过
- 触发：收藏了三个会议的 CFP 链接，上个月错过了一个截止日。

  1. 把三个 CFP 链接丢进灵光，`lingguang.source.read` 读网页正文，你把要点记成灵光。

  4. 提案在 Pages 起草，评论 @助理 用"读者视角"看评审会怎么读。
  5. 截止前 3 天的提醒用待办提醒（`todo.reminders.due`），出现在首页。

- 成熟度：main 部分；瓶颈：灵光读网页依赖原生组件构建；提醒只在本地服务开着时送达（BL-030）。

## A 组共性与 killer 候选

### 反复出现的四个模式

1. **"AI 说完成"与"我认可完成"分成两本账。** DEV-01、QA-01、DEVREL-01、OSS-01、TL-02 都在用同一组机制：要求可标本人验收，`goals.closure.submit` 被拦，约定一改旧验收作废。这是本组 main 可用程度最高、我们读到的竞品官方页面里最少覆盖的一条（外部补研 §1 读法第 4 条；Claude `/goal`、Codex Goals 都只看会话内容）。共同缺口：结论不自动绑定构建号或 SHA，显式人审（agent-approval）仍是规划。
2. **一份说明，所有 AI 都读得到。** 项目长期说明、Characters 导入、记忆包、规划中的技能包，在 AIDEV-03、AIDEV-06、TL-02、TL-05、DATA-01、DEVREL-04 里反复出现。内置助理和 Coding 每轮都带上，外部 Runtime 在经 MCP 读连接摘要时拿到。技术角色的真实痛点是"改一处规则，四个工具各要改一遍"；`AGENTS.md` 已被二十多家工具支持，共用规则本身有现成办法，Work 的差别在说明之外，目标、要求、依据、进度、谁验收过也是几家都读写、带版本的记录。共同缺口：跨机器共享和纯内容技能包的可见性（技能包随路线图 1·C 一起改）。
3. **外部来源进来，变成挂在 Goal 上的工作，再交给经 MCP 接进来的 Agent。** GitHub 通知 / RSS / Gmail（只取主题和摘要片段）→ Feed 捕捉规则 → Inbox → 升格 Goal → Agent 经 MCP 接手，或从 Goal 打开绑定终端，出现在 DEV-02、OSS-01、OSS-05、TL-03、DEVREL-01、DEVREL-03。共同瓶颈：真实账号联调与判断规则依赖 TypeSafe。
4. **缺工具就在对话里接进来或长出来，长出来的人和 AI 共用。** #661 接入 Stripe/Sentry/Metabase/Jira（DEV-04、AIDEV-06、TL-04、DATA-02、QA-02），插件创作台做核对台、回归台、指标雷达（DEV-06、QA-05、DATA-05）。共同缺口：生成插件不自动声明成果类型、搜索对象、工作流内容站；工作流动作步骤不能用查询类动作（BL-043）；#661 整体验收未完。

### 最可能成为 killer 的三条

1. **DEV-01 测试全绿了，可退款在手机上我还没亲手点过**：每次上线都发生、main 可用、能演出"AI 说完成 → Work 说还差你看一条"的反转；换对象即覆盖 QA-01、DEVREL-01、OSS-01，跨角色复用最高。
2. **AIDEV-01 四个 Agent 同时在跑，我不知道哪个卡在等我**：research 里证据最一致的开发者方向（U1），厂商自带的总览主要管自家 Agent；Work 的位置在跨工具一层，但覆盖面只限 Agent 主动上报的决定请求和受阻事件。瓶颈是"权限确认""一轮结束等输入"这两种最常见的等待不经 MCP 上报；读外部会话的进展随 Sessions 下线删掉了，排在 Sessions 重做（BL-177，路线图 3·C 持续跟进）。
3. **AIDEV-03 我在 Claude Code 里攒的 Skill 和规则，想让所有 AI 都按它做**：不用搬家就能开始（导入本机已有目录）；产出本身可分发（角色、将来的技能包），也是从 Claude Code/Codex 用户拉新的现成入口（产品优化建议 已指出它没被当拉新入口讲）。
