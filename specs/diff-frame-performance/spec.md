# 大型代码变更的逐帧高亮性能

状态：修复已实现、待合入（2026-10-22），负责人 Codex。目标为功能可用；独立 PR #1010 通过代码评审，Linux 的 diff 着色与插入断言通过；全量仍因同一用例后续的长对话断言失败。一骏已决定将长对话问题另开 PR 继续修复，#1010 保留 diff 范围。工程验证不代表一骏本人验收。

## 问题、范围和方案

CI Full suite 39745490860 的 `code-diff-scale.e2e` 两次失败，逐帧最长 518 ms、中位数 215 ms，原门槛为 200/80 ms。本机可用 CPU 降速复现。当前证据显示测试构造整份参考结果、反复序列化 DOM 与页面逐次高亮后的 grid 布局都贡献开销。缩小批次不能单独解决，不作为结论。

保留首帧完整纯文本、顺序渐进着色、超长压缩行纯文本、复制与选择、统一/并排布局、行号对齐和横向滚动。诊断后只减少高亮引起的重复工作，测试的参考构造移到计时前、完成检查改为最后一行并在完成后逐行全量比较。禁止降低性能阈值、跳过测试、修改 CI 或引入截断/删除屏幕外 DOM 的虚拟列表。公共 API、动作、数据与模型调用不变。

修改边界为 Coding 高亮客户端及必要的 Diff 行布局、对应浏览器测试和本 spec。输入是既有变更行与 token；输出仍是同样的文本、token 节点和行布局。帧任务沿用现有生命周期，卸载后取消。布局方案以浏览器测量为依据，不固定像素宽度或字体假设。现已测得着色前后列表宽度 867096 px、高度 79868 px 和行高 20 px 均不变：采用浏览器 `contain-intrinsic-size: auto` 记住首次纯文本的自然尺寸，再由 `content-visibility: auto` 跳过屏幕外行的重复布局；全文与 token DOM 始终保留。首次纯文本布局后再启动高亮，容器宽度、字体度量或行高改变时重新记尺寸；压缩纯文本行持续渲染，保持最宽行的实测尺寸；可着色长行也跳过屏幕外的重复布局，须检查滚到该行后的显示与响应。若需改变产品语义，先补充决定。

## 验收标准

- **DFP-01** 2,000 行输入的 3,993 行变更完整可读，120,000 字符压缩行始终完整纯文本，30,000 字符行完成着色；每行结果与独立构造的完整参考相同。
- **DFP-02** 着色跨至少 3 帧且进度单调，沿用最长低于 200 ms、中位数低于 80 ms，以及变更/长对话单节点插入低于 50 ms 的原门槛；测试自己的参考构造不混入帧计时。
- **DFP-03** 统一与并排布局、缩放、缺失字体、中文/表情/Tab、行号对齐与长行横向滚动不回退。
- **DFP-04** 大型列表关闭后重新打开，替换掉的列表主动释放尺寸、折叠和字体监听，不依赖已隐藏列表再次发出尺寸变化；连续替换只保留当前列表的监听。
