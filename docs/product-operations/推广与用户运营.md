## 1. 口号、开场与三句「不」

对外口号、开场原文与成熟度标注规范以[产品介绍 §1](产品介绍.md#1-口号与开场)与 [README 成熟度标签](README.md#成熟度标签)为准（不在此重复长开场）：

- **口号**：`Work, People, AI, Tool, get connected better than ever.`（人、AI、工具与工作，前所未有地连在一起。）
- **副标题**：工具和 AI 围着你转，你还是你。
- **讲述顺序**：先信念 → 再四句「你的」（每句紧跟对应画面与官网简标签）→ 再按读者分流（写代码 / 管项目与跟进 / 写文档与研究）→ 最后以 killer 场景作证。
- **三句「不」**（借鉴 Granola 否定式差异打法，与开场互为两面）：
  1. **不把你的工作锁在某一家 AI 里**：目标、文档、待办留在本机，换 AI 仍接得上。
  2. **不把「AI 说做完了」当成做完了**：每条要求有依据，需要你验收的由你拍板。
  3. **不替你派单，也不替你点头**：AI 可以记录、提议；改约定、替你确认，留给你。

## 4. 分角色上手路径

每类角色的「十分钟 — 第一次变成你的 — 第一周 — 第一个月」转化路径（`specs/plugin-builder-upgrade/spec.md` §3 参照本节「项目经理 / 交付」与 §5 六个模板包设计样例插件）：

| 角色 | 十分钟内看到什么 | 第一次「变成你的」 | 第一周做成什么 | 第一个月留下的理由 |
| --- | --- | --- | --- | --- |
| 双 AI 开发者 | 装好 Work，一键把 MCP 条目写进 Claude Code / Codex，在按需启用的 Goals 建首个目标并让 Agent 上报进度 | 把自己的 `CLAUDE.md` 和 Skills 导入成角色或写入项目指导 | 换一次 Agent 接着做；一次改约定由本人拍板；一次收尾被拦 → 本人验收 | 每个新功能开一个目标；工作台「等你」与决定请求汇集待决事项；外部会话服务随时回看历史上下文 |
| 技术负责人 | 导入团队规则，写入带版本的项目长期指导（`modules/projects`） | 把质量标准写入项目指导，每次修改留版本 | 多个外部 Agent 读同一份指导与目标要求；风险插件与工作简报跟踪交付风险 | 质量标准写一次，每个 AI 照着做 |
| 独立顾问 / 分析师 | 新建项目带入客户本地文件夹，拿到项目摘要与来源文稿 | 把「每周读报告写一页」存成工作流程 | 第一份带「本期采用材料」快照的周报存固定版，修订后用逐段对比复核 | 第二期接着做；被追问时一键回查当时依据 |
| 项目经理 / 交付 | 粘一段周会纪要，看到「你的承诺」与「在等别人」分开，已记过的被识别出来 | 把客户交付范围写成约定，标出哪几条必须本人验收 | 在等的事设跟进日，到日首页提醒并起草催办；风险条目挂 Schedule 复查 | 范围变更走决定留痕，承诺与等待不漏跟进 |
| 产品经理 | 用 Pages 模板起草 PRD，选中段落让助理挑反例 | 把评审反复下的判断写成判断规则 | 一个目标的要求与验收；Forms 问卷转存 Dataset、输出 PPT | 需求、决定、风险与验收在一处；范围不被悄悄改动 |
| 内容创作者 | 灵光收集网页与素材摘句，选中句子带出处放进 Pages 草稿 | 把选题标准与语气写入项目长期指导，助理每轮带上 | 一篇带出处的稿子 + 固定成果版本 | 每周选题、素材与改稿链条固定 |
| 一人公司 / 自由职业者 | 在平台插件创作台描述「报价前核对」并预览构建 | 按自己的规则修改一次工具逻辑或待办模板 | 客户改单时在界面和助理两处共用同一套规则与记录 | 数据留在本机、规则随业务微调仍能继续用 |

> **首日旅程演进（规划，onboarding-coverage）**：后续支持从一句用途直接起步，预览需新建/复用/修改的插件、角色、技能与首页，采用后即做第一件真事；上线前对外只讲上表今天可走通的路径。

## 7. 指标

- **北极星（建议）**：**每周被两个以上入口读写过的工作对象数**（入口指人、内置助理、外部 AI、工作流程），直接衡量「人、AI 与工具对着同一份事实协作」。备选：每周收尾生效且带依据的交付数。
- **开场信号（建议）**：**第一次「变成你的」**——首次导入角色、写项目指导、存工作流程、写判断规则或安装自建插件。
- **采集边界**：本地优先产品不默认上报遥测（可选本机汇总与自愿导出统计见 `BL-169` 与路线书规划）；上线前在内测访谈中与用户共同回看其目标、待办与成果记录，不作全量推算。

| 场景 | 激活信号 | 留存信号 | 流失信号 |
| --- | --- | --- | --- |
| K1 | 一个目标被两家 Agent 写过进度并完成本人验收 | 第二个、第三个功能继续开目标 | 建目标后 Agent 不回写 |
| K2 | 第一份带快照交付被回查或做过固定版逐段对比 | 第二期从上一期继续 | 交付后不再打开 |
| K3 | 生成插件被界面和 AI 各调用一次 | 改过一次规则后继续用 | 装完不用第二次 |
| K4 | 导入规则或写项目指导并在两个入口生效 | 项目指导经历版本修订 | 导入后从未生效 |
| K5 | 首次带入材料生成带内容项目 | 第一周回来处理草稿待办 | 建议未被采用 |
| K8 | 首次整理采用 3 条以上且至少 1 条设为「在等」 | 第二周仍有「在等」项结清 | 跟进提醒被忽略或误报过多 |
| K6 | 连续三天看首页简报并点击下一步 | 两周后仍保持查看 | 一周后弃用或视为噪音 |

## 8. 用户运营节奏与三轮验证协议

1. **内测招募**：用 Forms 独立填写页做招募问卷，按角色与「当前使用几家 AI」分组，先从第一波双 AI 开发者与第二波研究/交付角色起步。
2. **三轮用户访谈与四周留存验证协议**（自 2026-10-17 知识工作者研究 §8 抽提并扩展为全场景标准协议；先在 K8 / K1 约定版与 K1 / K2 上执行，见[killer 场景 §7](killer场景.md#7-下一步)）：
   - **样本起点**：先从 **5–6 位有近期真实交付的用户**开始，至少覆盖独立顾问、内容作者、交付/项目负责人（开发者组另配 5 位双 AI 开发者）；属可执行的小样本验证，不作统计代表性推论。
   - **第一轮（复演原办法，不推销概念）**：让用户展示上一次真实交付物与原始材料，现场复演其现有工作方法；追问具体触发事件、接收者、发生频率、最近一次出错与返工成本，以及已有替代方案。**绝不先展示 Work 再问「你喜不喜欢」**；沉淀匿名事件卡，不记礼貌赞同。
   - **第二轮（同材料交错对照）**：只选两条最强场景，用用户自己的同一批材料与验收要求对照「原办法 vs Work」，交错演示次序减少熟悉偏差。实测记录：首次可交付用时、人工修正与查证时间、手工搬运次数、配置成本，以及**接收者在不打开 Work 的情况下能否独立复核交付物**；语气、信任感与顺畅度由用户本人判断，不以自动化测试替代。
   - **第三轮（短期连续使用与四周留存）**：周期报告类场景（K2 / K6 / K8）**至少连续覆盖 2 个真实周期**，自建小工具类场景（K3）**至少连续使用 4 周**（包含一次字段/规则变更、一次重复输入或失败恢复）；唯一硬迁移信号是**用户主动回来用、停掉了原来的手工追踪表或材料包，且维护成本未抵消收益**。
   - **官网主案例五项入选硬条件**（测试前钉死）：① 有真实工作事件与明确接收对象；② 需求重复发生；③ 现有替代方案确有未满足环节；④ Work 覆盖可观察的交付链；⑤ 目标用户与接收者均认可结果。时间改善阈值按实测基线算，不预编百分比。
3. **反馈回收与社区节奏**：内测反馈进 Feed/Inbox 按场景归类并驱动路线书迭代；工作室内部实战经验经同意后连载；插件与技能包分享先在内测群验证权限披露与审查机制后再公开。

## 9. 待授权事项

以下操作均须获得用户明确授权后才可执行，本目录仅维护方案与底稿：

- 对外发帖、投稿、录制和发布演示视频。
- 招募内测用户、发出问卷、执行访谈或联系任何外部人士。
- 登录、试用或付费购买竞品做对照实操。
- 修改官网文案、许可页或下载页。
