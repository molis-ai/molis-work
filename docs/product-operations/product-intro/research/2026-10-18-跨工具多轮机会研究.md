## O01：每周交简报，交出去的判断还带着当时的依据

**具体任务。** 独立顾问每周给客户写一个细分行业的观察简报。周五选用数条发布说明、报道与评论，写明哪项变化值得试、哪项只是厂商自述；周一客户追问某条判断，周三又出现修正信息。交付物包括经本人核对的简报、本期实际采用的材料、补证事项。不是无人值守新闻摘要。

**用户可能卡住的地方。** 阅读器擅长发现和收藏，研究工具擅长带来源回答，编辑器擅长交稿；但这位用户仍需维护“本期到底采用了哪些内容”的材料包，下一轮不能只凭一个会变化的网页链接重建过去。这个痛点须在试点本人工作中确认，不能从工具数量推定存在。

| 工作环节 | 熟练现有方案 | Work 当前路径 | 省掉、转移或增加什么 |
| --- | --- | --- | --- |
| 1. 配置持续来源 | 阅读器的订阅/过滤；或 Feedly AI Feeds。使用 NotebookLM 时可配 RSS 批量导入器 | 在 Feed 配可用来源；需要时试跑并绑定已发布判断，把候选送到 Inbox | 双方均有设置成本；不声称 Work 独有筛选或导入 |
| 2. 本人选择本期材料 | 从 Board/阅读列表/笔记本勾选；核实正文、来源和日期 | 在 Inbox 选 **1–20 条可读 Feed 材料**，核实本次能读取的内容 | 选择和核实不消失；不是所有外部资料都能直接走这个批量入口 |
| 3. 整理可编辑稿 | 研究工具出初稿，再在文档中审改；Feedly 自身也能生成带 AI 内容的 newsletter | 生成到 Pages；程序附上采用材料快照、来源标签、材料 revision 和返回入口；已有截断标记随附录显示 | **程序完成这份采用材料附录的组装；旧流程确实手工拼装时才算省掉这段劳动**；不等于免核来源、获得网页全文或逐句引用已正确 |
| 4. 核验与交付 | 对照原文；写自己的判断；保存/导出约定格式；需要留底则固定本期 | 原页审改、核对附录和原文，另存固定成果；Markdown/HTML 导出或打印 PDF，与留存版核对 | 审稿、留存、导出仍做；Work 不自动保证固定成果与当前稿导出一致 |
| 5. 回来回答追问 | 查当期文档及已保存的资料包；若只留网页链接，可能需找旧内容 | 打开当期稿或固定成果，回看随稿保存的采用材料；具体判断为何采用仍要在正文写清 | 可减少重建本期材料包；附录不是不可篡改审计，当前稿可被人编辑，正式留底用固定版 |
| 6. 下一期有新证据 | 新材料与上期结论比较，更新研究、重新交付 | 新一批材料另成稿，人工打开上期对照；也可显式选段修订 | **没有自动比较旧新简报、标出受影响结论或一键续期**；此处仍有明显成本 |
| 7. 失败与退出 | 工具的重试/导出；人工确认未丢稿 | 相同生成请求完成后重试返回原文稿，保留已发生的人改；要求或材料选择变了须新请求。退出可导出稿件，完整资料库搬出另算 | 防重复生成有代码依据；外部收件人不能靠导出的本机返回链接访问 Inbox，要保留可读附录或原始公开链接 |

**当前差别的强度。** 若用户每期确实要交一份可追问的个人判断，并额外手工保存采用材料，这条链有可检查的价值。若只想看新闻摘要、发团队 newsletter，或已经在现有工具里完整留底，Work 未证明更顺。它首先是“从下一期开始试”，不是要求全量迁库。

**最小采用条件。** 一期材料在 20 条以内，材料正文合计不超过 100,000 字符；主要是可读文字；交付格式允许 Markdown/HTML/PDF；作者本人掌控审稿；来源能通过已支持的路径进入 Feed。不要把客户邮件、所有 PDF、私有网页、全站抓取预设成已接通。材料 body 可能退回节选或摘要，捕获时间也不等于原文发布时间。

**直接需求线索。** 一位 [n8n 用户](https://community.n8n.io/t/ideas-for-implementing-human-review-in-workflow/81096)已完成 RSS 聚合，却卡在人工选材、排序与跨天汇集，曾另搭审阅页失败。同帖已有原生 Form 解法；这是 2025 年的具体经历，只支持人需要参与取舍，不证明当前 n8n 缺此能力，也不直接证明“材料附录”需求。后者仍需试点核实。

**强对照。** [Feedly 的 AI newsletter](https://docs.feedly.com/article/753-guide-to-using-ai-in-automated-newsletters)已能将筛选内容整理进简报；[NotebookLM Web Importer](https://github.com/eluchansky10/notebooklm-web-importer)声明支持 RSS/OPML 批量选入。后者是第三方实现，本轮未安装，不采用其“原生只能一次加一个”的宣传。Work 要验证的是采用材料随稿留存和后续核查的总成本，不能仅比摘要按钮。

## O02：常用的业务核对，不再分别教给表格和每一个 AI

**具体任务。** 小服务商反复收到客户改过的清单，需要按批准的数据核对哪些行可处理、哪些缺信息，自己要打开界面改记录，也希望 AI 能帮忙按相同规则检查。先选一个边界小、输入结构清楚的“报价前核对器”：已整理的品项与数量、批准的目录和价格、未匹配项清单。识别 PDF、发正式报价、写 ERP 都不属于首个样例。

公开有一位分销业务需求方为 [RFQ 到报价原型](https://community.n8n.io/t/seeking-estimates-n8n-developer-for-a-small-rfq-to-quote-prototype/312281)征询方案，明确要从认可目录取价、不确定项给人审。它支持这种工作需求存在；仍在询价，不能算 Work 客户、付费成交或已证实频率。我们收窄为其中的核对环节，完整原需求当前没有被 Work 满足。批准目录和价格仍由原业务系统或负责人维护；首个样例只接收带来源、版本的只读快照，由人提供更新，不另建一份可独立编辑的正式价格账，也不承诺实时同步。

| 工作环节 | 熟练现有方案 | 用 Work 验证的链 | 迁移账 |
| --- | --- | --- | --- |
| 1. 定义规则 | Excel/Sheets 公式，或 Python + SQLite；低代码工具也能共用查询与逻辑 | 在创作台明确输入、确定性匹配规则、人工待核项及记录结构，再生成并试跑 | 业务建模和正确性检查不能省；生成通过不证明报价正确 |
| 2. 给本人一个可修改入口 | 表格本身就是界面；脚本另配表单；Retool/Appsmith 已提供界面和数据能力 | 装进 Work 的同一插件，平台提供界面装配、安装、私有存储和运行宿主 | 相对纯脚本可能少搭宿主/界面；相对熟练表格不必然更轻 |
| 3. 让 AI 调用同一规则 | 编码 Agent 可直接运行脚本；也可另接 MCP；Retool 已有 MCP 能力 | 插件操作在共同动作目录中向已授权 Agent/MCP 暴露，调用同一安装的业务实现和数据 | **若原流程确有重复规则可以合并；通常待省的是工具暴露接线，已有共享脚本则未必减少规则实现**；不会自动让所有 AI 获得授权 |
| 4. 客户第二次改数量或型号 | 改原表/记录，重跑同一公式或函数 | 本人从界面修改，或让获授权 AI 调同一操作，再从界面查看结果 | 这是共用事实的潜力；记录修订、价格版本、并发控制须在具体插件合同中实现和验收，平台不会自动补全 |
| 5. 审核、发送和后续 | 人核例外，用原渠道给客户；ERP/财务保留权威记录 | 同样核例外并通过原渠道发送；只有核对工具被替换 | 不得多造另一份正式订单账，也不承诺外部系统写回 |
| 6. 规则升级、失败和退出 | 改公式/脚本、测试回归；已有表格易查看和导出 | 插件重建、试跑、确认权限和升级；结果未知时先查记录；数据导出需样例明确提供 | Work 新增版本和运行成本。安装包导出不等于业务数据已可带走 |

**为什么值得做一次真样例。** Work 当前提供的是个人工具的共同运行底座：操作、可视界面、安装存储和 AI 入口有现成连接。这与“AI 写出一段代码后，还要自己把它变成日常软件”之间存在可验证的距离。适合同时需要本人界面与 AI 调用、愿意确认业务规则的个人负责人；只需一张表，或必须全团队实时共用 ERP 的人不适合先迁。

**严格状态。** 报价前核对器并不存在；本轮没有生成。现有平台支持构建此类工具，不是承诺一句话得到可商用报价系统。生成插件目前没有自动声明成果类型和可搜索业务对象，不能顺口说它的记录会自动进入全局搜索、Pages、成果库或任意流程下一步。

**强对照。** [Retool MCP](https://retool.com/blog/retool-mcp-server)已有外部 AI 入口，[Appsmith Packages](https://docs.appsmith.com/packages/overview)可复用业务逻辑。Work 的待证空间是单人的本机安装、共用动作和日常维护是否更省，而非“只有我们能复用”。模型或网络操作仍有服务成本，本机数据不代表材料从不发给模型。

## O03：分析、编码、回看，直接改同一份本地研发说明

**具体任务。** 独立开发者先研究某个导入流程，再在惯用编码工具里实现；体验后发现一类文件不完整，需要把实际结果交回分析侧，重新定下一轮。真正卡住时，是人在两种工具之间反复搬正文、重写结果和解释自己刚改过哪句话。

| 环节 | 熟练现有链 | Work 可采用的链 | 差别与成本 |
| --- | --- | --- | --- |
| 初次接入 | 仓库内/外 Markdown + 编辑器，双方直接读写；或同一 Notion 页 + MCP | 两端明确连接同一 Home/项目并授权 Pages；只创建一份研发说明，需要固定来源时再用 Cognia | 增加接入；代码、Git、PR、历史文档不搬 |
| 分析→实施 | Agent 更新并读取共享文件/页面 | 分析 AI 写 Pages，人改；编码 AI 读取同一文稿及明确选择的材料版本 | 相对手工搬聊天可省转述；共享文件早已顺畅时只是换位置 |
| 实施→反馈 | 编码 Agent 把结果写同一文档 | 编码 AI 明确写回本轮变化、实际文件/命令结果与缺口；分析侧重新读取 | 需要操作约定；不自动采集证据，不自动回传所有原生对话 |
| 人改后再来一轮 | 文件 diff/编辑器、Notion 编辑历史等 | Agent 更新 Pages 须带读取版本，旧版覆盖被拒；重读后继续 | 有陈旧写入防护，仍需处理冲突和判断模型是否理解 |
| 结束与恢复 | 原工具测试、PR、人审；下轮读说明和当前代码 | 原流程照常；需要留底时另保存文稿固定成果；下一会话主动读取 | Work 不替代发布门禁，也不会恢复从未保存的推理 |

需求线索来自[公开的讨论与开发交接报告](https://github.com/openai/codex/issues/32519)。后续评论已提到新桥接能力，所以只采“逐轮搬运”的经历，不声称当前 ChatGPT/Codex 仍没有桥接。当前 [Notion 官方 MCP](https://developers.notion.com/guides/mcp/get-started-with-mcp)已支持 Codex、Claude Code 等读写同页；本地 Markdown 也是真正强对照。

**选用决定。** 作为研发二级入口：仅适合重视本地可视编辑、需要固定文字材料版本、当前确有人工搬运的人。先试三轮一篇说明，只有停掉原来的交接副本才考虑扩大。不能以不同工具间能传文字就认定值得迁移。

**高痛但未接住的部分。** 当前原生 Session 适配只注册 Codex，其他 Runtime 的登记 fallback 不等于已把消息送进 Claude Code；Handoff 也不搬完整原生历史。任意 Runtime 故障后无缝续做不在本案例承诺中。

## O04：最值得补的缺口——来源变了，先知道哪些采用过它的知识要重审

**目标故事。** 顾问上周据客户材料写了三条建议。本周材料更新，最费力的不是再总结一次，而是找出哪条旧建议需要重看、哪条与这次更新无关。当前 Work 能保存旧来源版本，尚未把它变成用户可逐项处理的复核入口。

一位 [Obsidian 用户的原始提问](https://forum.obsidian.md/t/title-how-you-keep-research-notes-clean-when-source-change-later/115963)描述了来源数周后变化、笔记是否应更新难以分清的问题。回复也给出元数据、Bases 审查队列与版本笔记的办法；[Chamber Drift](https://github.com/abm9111/chamber-obsidian)声明可显示依赖段落变化，另需外部 ingest/verify。需求有具体线索，解决办法也已存在；Work 要比的是减少维护最初采用版本索引和查找复核候选的劳动，不能声称独创。

**已有起点。** Cognia 导入保留不可变 revision；AI 草稿保存固定材料引用，采纳后仍能读回这些引用。关键限制是：这些是最初采用草稿的来源关系，知识正文后来可人工改动，不能把它们当成当前每句话的精确依赖图。PPT 从 Pages 取得标题/正文也不能推出已持久保存完整的来源版本依赖。

**建议的最小改进方向（未实现、未排期）：**首轮仅限 Cognia 当前可读取的文本/Markdown，以及有草稿采纳记录的知识。客户 PDF、Word、图片的提取与转换成本另计，不能默认已接通。先验证只读候选清单和旧新回看是否有用；随后若确有重复复核负担，再补处理回执形成持续闭环。

1. 只做 Cognia 内部。用户明确重导入后，由 Cognia 查询已有采纳关系，列出“最初采用过旧版材料的知识”；附本次导入成功/失败和检查范围。不是监控所有文件或全网。
2. 一行展示知识、当初采用的材料版本、当前材料版本；能打开旧版与新版并返回知识正文。内容没变、只改元数据的情况要分清，删除/读取失败不能显示“无需复核”。
3. 第一轮由人用现有知识编辑/待办记录处理；只读定位确有价值、重复提示成为负担后，再让人选择“需要修改”或“此变化不影响这条知识”，留下简短理由。复核回执至少绑定本次知识 revision 与来源 revision；任一再次变化后重开待核。**不自动把旧引用改成新引用来消除提示。**
4. UI 明说它只覆盖有采纳记录的知识，来源关系可能因后续人改而需要复核。直接写的无引用笔记、任意 Pages/PPT 和外部文件不显示虚假的“已检查”。

**复杂度判断。** 当前必须复用 Cognia 的版本和草稿采纳记录，先验证只读定位。后续如需保存复核决定，由 Cognia 自己拥有最小回执。可以延后自动语义影响分析、跨插件依赖传播、整段自动重写和定时抓取。应当删除“为这个实验另造一套通用知识图谱/第二资料库”的方案。实验若成立，再讨论 Pages/PPT 的显式采用关系，而非先铺全平台。

**真实任务验证与推翻条件。** 用一份真实研究里的 8–12 条已采用知识，重导入包含实质变化、仅格式变化、无关变化和缺失来源的新材料。让作者完成复核，比较其熟练 Obsidian/Bases 或原来手工索引法。第一阶段必须能找到已登记关系，旧版可读、无关项可说明；若进入回执阶段，再检查改后再次变化会重新待核；漏掉应复核项、误报多到仍需全读、手工维护引用比旧方法更重，就不扩成主卖点。数量是建议实验规模，不是已获得数据。

## 从“值得试”到“值得迁移”，各用一个明确决定

以下是建议的对照任务，尚未执行；不预设省时比例，也不因新建项目成本低就判胜。

| 候选 | 完整对照任务 | 真正的采用信号 | 停止或改方向的条件 |
| --- | --- | --- | --- |
| O01 | 同一专题连续做两期，一次交稿后追问，一次来源更正，一次生成失败后恢复 | 作者可以停用手工拼材料附录/本期依据文件；下次核查不再另找旧内容；总负担接受 | 仍需在别处重建同一材料包；现有 Feedly/NotebookLM 组合更顺；20 条或 100,000 字符上限、格式、正文范围经常不足 |
| O02 | 用同一组真实、可获授权的业务数据，先做最小核对器，再由界面、一个 AI 和另一个 AI 连续处理四次；含规则变更和退出导出 | 若原有重复，能停用旧副本；若原有共享脚本，界面/MCP/安装接线与维护的总负担确实降低 | 每次需作者救火；比表格更难查错；升级丢状态；换客户端仍重建规则；业务数据带不走 |
| O03 | 一个实际小功能三轮分析→编码→回看，加一次人改与陈旧 AI 写入冲突 | 一份共享说明替掉人工回传的正文副本，资料版本和当前事实能分清 | Markdown/Notion 本就同样顺；MCP 不可达；仍逐轮复制正文；结果只是多一本账 |
| O04 | 新材料引发一次完整人工复核，再更新一次材料 | 用户不用全库扫读，愿意停止维护旧版采用索引；覆盖边界可理解 | 关系不可信、误报过多、重要漏项、需要维护第二份关系库 |

共同计入：首次安装/授权/模型费用、每轮核查、并存维护、失败恢复、实际交付格式和退出。试验前确认用户目前真用什么，不拿一个故意松散的流程当对照。主张迁移至少应有使用者愿意把某条重复工作留在 Work 的行为证据；本轮没有这个证据。
