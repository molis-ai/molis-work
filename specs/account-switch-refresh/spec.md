## 1. 本次要做什么

在已有账号分区机制上，把切换账号做完整：A 使用 A 的数据区域，B 使用 B 的数据区域；代码中把这样的数据区域称为 Home。切换时由平台结束旧账号的工作环境，选中新账号区域，刷新工作台。应用进程、桌面窗口和本机服务入口保持运行。

普通插件继续使用平台给它的存储和服务，业务功能保持原样。插件实例可以按既有生命周期卸载、重新加载，不要求插件识别“切账号”，也不向每个插件新增账号参数。

本次交付只有四项：

- 把各入口的账号选择收口为同一安装的一个当前账号。
- 补齐平台刷新：旧凭证失效、旧任务停止、旧页面退出，再加载新账号内容。
- 清理旧显示和运行状态，按账号区域隔离持久草稿与浏览器缓存。
- 修复 PR #1877 诊断中的重复开库、重复读取插件目录和重复构造检查基准。

本文是本次开发的唯一任务说明。[个人云同步规格](../personal-cloud-sync/spec.md)保留原同步规则及历史记录；其中旧阶段的测试结果不代表本次切换已验收。

## 4. 一次平台刷新具体怎样发生

### 4.1 正常切换

平台掌握这次切换的全过程，插件无需分别订阅账号变化。

1. **先处理旧工作。** 主动切换或退出前，依据已有页面未保存标记、草稿通道和任务状态处理 A 的工作。已交给草稿通道的写入完成后留在 A；未提交的编辑沿用原页面保存能力，可返回保存、取消切换或明确放弃。确有未保存内容或运行任务才提示，保存失败可重试。平台不代替插件提交业务，也不新增每个插件必须实现的切号/保存钩子。
2. **沿用登录流程。** 在上述处理完成后发起现有登录，准备期间阻止旧页面继续新增需要保存的编辑和业务操作，取消或失败时解除限制、继续使用 A。`PersonalAuth.complete()` 已先校验目标身份再使 A 失效，保留这个认证顺序；不预先增加第二套待提交身份或登录服务。B 的认证完成与 B 的业务就绪是两个阶段。
3. **撤销旧授权。** 沿用认证成功或主动退出时的旧登录代次撤销，补齐会话、附加票据及区域交接的关联。A 的页面权限、CLI/MCP 连接和服务句柄继续经已有授权检查拒绝；同步、后台任务和在途操作经原取消与关闭路径停止。等待中的结果不能再写入业务记录、文件或通知。
4. **释放旧环境。** 复用现有区域释放流程，关闭旧页面通信、流连接、计时器和插件实例，等数据库及其他资源释放完成。已经保存在 A 区域的数据保留。
5. **打开新区域并刷新。** 用现有空间映射和装配逻辑打开 B，按 B 的设置加载功能，再让工作台刷新。显示的项目、内容、插件启用状态和外部授权都来自 B。

这里的“刷新”允许重新加载工作台页面、释放并创建账号区域的内存服务实例；桌面进程、常驻宿主进程、窗口和公共监听入口不退出、不重启。

同一安装中的旧页面都必须退出旧状态。可信桌面页面通过已有原生连接流程取得新授权；普通浏览器、CLI 和 MCP 的旧凭证只会失效，需重新连接，不能凭原凭证自动获得 B 的权限。刷新通知只用于更新界面，服务端仍独立拒绝旧请求。

已有草稿接口只保存调用方交给它的内容，`unsaved` 只表示页面已声明的状态；二者不是所有插件输入的自动快照。保留现有页面关闭动作，但不得依赖页面已销毁后的关闭请求补存撤权前草稿，也不得为此给旧页面保留业务写权限。若回归发现某一编辑器未接既有机制，单列其证据和边界，不把本任务扩大成所有编辑器重做。

### 4.2 退出、失败和再次进入

主动退出采用同一套保存、撤销与释放流程，最后显示登录入口，不进入可匿名编辑的工作区。关闭一个窗口继续沿用原后台任务规则，不触发账号退出；退出应用的进程关闭规则不在本次重做。

账号被明确撤权时立即拒绝操作，不等待草稿确认。单纯断网不当作切号或撤权；已登录账号的本机工作及已有离线规则保留。

如果准备失败，A 继续可用；如果已经撤销 A，后续释放或 B 初始化失败，页面显示明确失败和重试入口，保持旧权限失效，不暗自恢复 A 或回退到匿名区域。B 未就绪时不显示“切换完成”。重复点击只推进同一次切换，不能同时打开多个活动账号或重复启动任务。

A→B→A 时，重新取得 A 的授权和服务。A 原有数据、已保存草稿及设备同步选择仍在；旧 A 会话不能因账号相同而复活。

### 4.3 清理的是哪些状态

| 状态 | 切换时的处理 |
| --- | --- |
| 当前页面内容、选中项目、搜索结果、预览、待返回的页面消息 | 清除旧显示，废止旧消息，再从新区域加载 |
| 草稿和浏览器持久缓存 | 已保存及经既有通道完成保存的内容按区域隔离；返回 A 可读取 A 的内容，不把它迁给 B；未提交输入按 §4.1 处理 |
| 无法确认账号归属的旧缓存 | 不自动认领给当前账号，也不删除原件；停止按无区域前缀自动加载 |
| 账号会话、控制连接、插件服务句柄 | 撤销后不能继续使用；新区域重新发放 |
| AI、同步、终端及后台任务 | 旧账号工作停止；不迁移到新账号，不因页面刷新自动重放中断的执行 |
| 模型配置、外部账号授权、工具权限 | 随所属区域选择，B 不能沿用 A 的授权；不改变各外部服务自己的登录协议 |
| 数据库、附件和已经保存的内容 | 留在原账号区域，不因切换或退出删除 |
| 程序代码、公共静态资源、非私密设备偏好 | 继续复用，不随账号复制一套 |

已发往外部服务的操作可能无法收回。平台负责阻止撤权后的新副作用和迟到本地写入，并按已有结果核对机制显示实际状态，不能把“本机停止”等同于“外部一定没执行”。现行安全不变量中已明确批准的有限例外继续按原合同处理。

## 6. PR #1877 的性能修复

[第 10 批增量诊断](https://github.com/molis-ai/molis-work/pull/1877#issuecomment-6691053364)报告：页面请求重复查询常开插件，一次请求约打开 Home 插件库 41 次；`/api/home/events` 约 1.1 万次 SQLite 调用，`/api/board/refresh` 约 1.06 万次。浏览器用例在原 15 秒 CDP 时限下超时，Node 进程同期几乎没有事件循环空闲。

重复发现插件、重复开库与实际结构检查原本就存在。PR 又让 `expectedHomeStoreShape` 每次打开都创建内存库重建期望结构，单次测试报告重建 3928～5645 次，加重已有瓶颈。以上数字来自诊断作者；本说明书核对了调用链，未重新测量。

本次采用两个直接改动：

1. **不变的检查基准只计算一次。** 在定义 Home 插件库基线的位置，复用当前代码声明的期望结构；区分带/不带 storage-space 的形态，并与对应版本、声明一致。只缓存期望结构，不缓存“某个磁盘库曾经合法”的判断。
2. **同一次只读汇总复用常开插件目录。** `ProjectService.pluginMembership()` 已在单次成员判断内复用结果；缺口在 `homeProjectPlugins().alwaysOn()` 每次被调用仍重新发现，`runningPluginDirectory()` 与 `builtinMarketDirectory()` 也分别读取。沿 home/events、board/refresh 的实际汇总调用链传递同次发现结果，避免项目枚举和目录拼装反复开库，复用已有参数而不重做 Projects API。本次不预先建设长期缓存和额外失效系统。复用只限同一 Home 的当前只读汇总；不得跨请求或跨账号复用，更不能取代受保护读写、异步等待后和提交前的当前授权检查。

优化后仍须拒绝错版、结构篡改和错误空间，安装/同意/停用变化在后续请求生效。按相同数据、请求与浏览器负载记录改前改后的开库、SQL、基准构造、CPU、事件循环与耗时；原超时预算不变，不靠减少页面功能或跳过检查通过。
