4. **「当前约定」：看见 AI 自己说记住了哪些补充，并且不被当成事实**（#713 + #714，基线时来源为 PR，现已合入 main）。价值：中途补充的要求有处可查、可更正，且诚实标注"AI 自己说的，未核对"。成熟度：基线时实现完待合入，之后已合入。依据：`specs/ai-input-receipts` §9.2、RCPT-358–363。
5. **两个窗口同时答一个问题也安全**（#708，来源：PR；与 main 的"问题跨重启仍可回答 #695"合起来）。价值：AI 的追问不会因重启、多窗口丢失或重复生效。成熟度：实现完待验收。依据：`specs/ai-interaction-experience` AC-08/AC-11。
6. **技能包：把"角色做法"当内容安装给助理和 Coding**（#718，来源：设计；spec 现已在 main）。价值：工程、产品、数据、设计、法务各有一包"同事做法"，无需写插件；卸载只删内容、技能不授权；`~~calendar` 这类占位符让同一包适配任何同类服务。成熟度：仅 spec（SkillPack、PLP-01–08、ASC-38–44）。依据：`specs/skill-packs`、`specs/plugin-platform-v2`。
7. **多代理代码评审 + 置信分过滤 + 只出补丁的安全评审**（#718，来源：设计）。价值：评审结果只报 ≥80 分的高置信问题，安全 finding 要独立 verifier 复核，补丁在审查队列里由人决定是否应用。成熟度：仅 spec（CQA-01–12）。依据：`specs/coding-quality-assurance`。
8. **Agent 产出的变更必须真人批准（绑定 head SHA、Agent 不能自批）**（#718，来源：设计）。价值：把"人决定"落成可执行门——PR 需 N 个有写权限的真人批准，push 后旧批准过期，也适用于本机审查队列。成熟度：仅 spec。依据：`specs/agent-approval`。

## 9. 分支设计里给我的产品启发

1. **平台定位可以从"本地优先的插件平台"扩成"工作方法的分发平台"。** #718 的判断很锋利：Molis 插件太重（Manifest、Runtime、actions、views、storage），适合 app，不适合"角色包"。Skill Pack（纯 Markdown + 技能声明，不授权、不写事实）是供给侧杠杆最高的一步，配上 `~~类别` 占位符，同一份"产品经理做法"换一个连接的项目工具仍可用。这意味着产品介绍的第二层叙事可以是"装一个角色 = 装一个同事的做法"，而不是"装一个应用"。
2. **"人决定 + AI 说的不等于事实"正在被做成一整套可检查的机制，这是差异化主线。** 回执把"送达 / 排队 / 读到"（事实）和「AI 说」（自述）分开画；「当前约定」用虚线加"Molis 没有核对"；真人批准门绑定 head SHA；记忆是"候选 + 确认"。Anthropic 方案里自主团队、自动开 PR、自动写记忆被明确列为"不照搬"。可以把定位讲成"可信 AI 同事：它说它做了什么，和系统证明它做了什么，永远分开显示"。
3. **Killer 场景候选：Shelf → Pages 的"拿起—预示—放下"。** 资料在右栏，选段或拿起助理结果卡，悬停时左边落点闪一下，确认才写入，版本过期会拒绝。它把助理产出从"复制粘贴"变成"放到我选的位置并可撤"，比聊天式 AI 更像工作台。
4. **"AI 的工作可中断、可接续、可重问"是被低估的卖点。** 问题跨 Host 重启仍可回答（#695）、已关闭的问题可"请 AI 重新问"（#669）、两窗口答同题只收一次（#708）、补充可撤回可更正。对依赖 AI 做长任务的人，这比"多聪明"更影响信任。
5. **本地优先可以落到最具体的承诺：音频不出设备。** #631 把语音转写做成本机 helper，下载模型需明确同意，不静默回退云端，并区分"本地转写"与"发送给 AI"两个阶段。这是隐私敏感用户、会议口述场景里一个能一句话讲清的差异点。
6. **"做一遍，让它学会，用你已知的答案回放验证"**（#718 N2 build-agent）。把重复工作变成 Skill 的入口，强调固定步骤 / 变量 / 判断点，判断点和会发送 / 花费 / 发布 / 删除的步骤做批准门，再用已知结果回放，对不上就改。与 Plugin Builder 互补：Builder 造"应用"，这个造"做法"，门槛更低。
7. **工作简报应该是"可刷新的状态页"，而不是"生成一篇周报"。** living page 内嵌 state 块、只报 delta、取不到标 stale、一页红黄绿脉搏且风险必须带具体记录。这能让简报变成每天会回来看的东西，并避免"AI 写了一篇漂亮但不可核对的周报"。
8. **垂直创作链（CGS）证明"垂直行业 = 插件 + 助理 Skill + 精确批准"可以走通，但也暴露风险。** 作者旅程里最有价值的是"比较并采用候选、平台稿精确批准、下载"这类人决定的节点；同时模型仍会"只解释不执行、超篇幅、带历史占位链接"，质量要靠人工校对。产品介绍里宜把它写成"一条受控的作者流水线"，不要承诺"一键成稿"。
9. **用户自己的体验清单（#156）提示的需求：看懂插件之间的依赖。** 区分官方 / 自建插件，能看到自建插件依赖哪些能力，哪项能力被哪些插件使用。这与 #718 的"目录元数据与安装前详情"（安装前展示命令 / 技能 / hooks / MCP / 权限 / 发布者）是同一个需求的两侧，值得合并成"插件透明度"叙事。
