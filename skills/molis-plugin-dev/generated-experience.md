# 生成插件：体验与审美标准

此章供主线设计、整页 UI 生成和视觉复查共同使用。用户明确的任务与偏好优先；Molis 的现有控件、主题和本次提供的能力目录决定可实现边界。目标是让人轻松完成自己的事，并愿意继续使用。

## 先形成一个适合任务的设计

先判断人在这里主要是操作、阅读还是比较；混合任务要分清当前主次。写摘记的安静感来自正文和节奏，处理待办的利落感来自紧凑行与就近动作，比较收支的清晰感来自同单位、可对照的数据。不要只换标题就套同一个布局，也不为了显得不同增加装饰。

冻结前的体验阶段可以重组部件草图，用 `scenarios` 给出任务、具体内容和可观察结果；不改操作或权限。主线设计据此建立绑定和实际验收，用 `journey` 写清「从哪里开始 → 做什么 → 看到什么结果 → 怎样继续或返回」，用 `purpose` 说明每块内容为哪一步服务。首次使用的「新建」排在旅程第一步，不代表每次打开都应让录入表单占据首屏；有内容后的常用任务同样要顺手。UI 阶段用已有 `summary` 简短说明主内容、主操作、布局取舍及窄屏顺序。只交当前阶段要求的 JSON，不额外输出设计报告、打分或任务未要求的字段。

## 用户动线与状态

- 首次打开就能辨认核心内容和下一步；空态指出当前界面里真实可用的入口。不要让用户先阅读功能介绍或配置无关选项。
- 围绕内容安排行为：筛选靠近受影响列表，记录操作靠近记录，提交结果靠近触发位置。已经能直接操作时，避免额外的选择、展开、确认步骤；真正危险的操作沿用目录提供的确认组件。
- 按频率和输入负担选择呈现：频繁的一两项录入适合内联；偶发的多字段编辑可用 Sheet；只有需要中断并集中判断时才考虑 Dialog。不要把所有表单铺在首屏，也不要一律藏进弹窗。
- 一次任务有清楚的结束：保存后看得到结果，失败说明问题与下一步并保留输入，返回回到原来的内容位置。使用已有结果、预填和选择绑定；缺少能力时说明限制，不靠文案承诺不存在的自动保存、撤销或导航。
- 设计需要的空态、加载、失败、成功和长内容场景；主题、键盘焦点、禁用和错误恢复由宿主控件承接。UI 阶段不能通过新增操作或修改验收来补功能。

## 信息呈现与视觉层级

- 先定用户最需要看的内容，再给它空间。正文、当前任务或比较结果居主位，来源、日期和说明退为辅助。主操作可以醒目，但不意味着表单应占最大面积；危险和低频动作不争夺注意力。
- 用分组、对齐、留白和文字层级表达关系：组内紧、组间松。连续工作面优先，必要的边界才分隔；不要把每个字段、数字和段落都包成等重卡片。密度由任务决定，不等于内容越少或空白越多越高级。
- 阅读要有完整正文、可辨认的小节和合适行长，来源不抢正文。扫描列表只放识别条目和做决定需要的字段；内部 id 留作绑定。比较数据用可对齐的行列和一致单位；有理由时用 Table，不强行禁表格，也不把一段文字拆成数字卡片。
- 目录摘要帮助寻找，详情正文帮助阅读，两者同屏不自动等于重复。应去掉的是同一位置、同一用途的重复信息。独立正文和集合内置 detail 选一种；不能把摘要当作全文。
- 控件、字体、颜色、圆角、状态与动效沿用宿主。通过布局节奏和内容表达气质，不另创字体、渐变、阴影或图标体系。阅读用 `measure: reading`，操作用合适的 `density`，分区用 `gap` / `ratio`；具体值以本次 vocabulary 为准。

## 文案与响应式

- 标题说内容，按钮说动作，标签用用户熟悉的词。展示命令结果时说明实际发生的事；不暴露字段名、内部状态码或系统机制。空态不只写「暂无数据」，也不虚构入口；说明文字只在有助于决定时出现。
- 窄屏是任务顺序的变化：优先保留核心内容和动作，辅助信息随后，目录与正文用已有返回路径衔接。考虑嵌入工作台后的窄栏，不能只看整窗宽度；不要用缩小字体来塞下桌面布局。
- 长标题、长正文、多条记录和窄屏操作仍应可读可达；筛选、选择和返回不能因重新布局而失去上下文。仅凭截图看不到的行为应交浏览器操作验证。

## 动效：解释发生了什么

每个动效应能回答：确认了哪次操作、解释了哪种状态变化、保持了哪里的空间连续性？允许真实保存后的到达反馈、完成反馈和详情展开；不在首次加载时把已有内容当作新到达，不让每个区域轮流入场，不用装饰性跳动拖慢高频操作。

动效执行、时长、曲线与减少动效偏好由宿主统一提供。选择合适的现有组件即可，不输出动画配置、CSS 或脚本，不要求用户等待动画结束才能继续。减少位移时仍保留可理解的状态反馈；缺少所需行为要说明，不能假装已实现。

## 复查：同一标准，按证据判断

先看用户能否完成核心任务，再看信息主次、阅读/扫描/比较、空间节奏和文案。按任务影响排序，最多五条有用的问题；不为凑数挑风格偏好，不输出审美总分。

每条写「截图标签 · 页面/部件：可见证据 → 对任务的影响 → 具体改法」。结合实际部件用途、绑定、字段映射和当前渲染 kind，改法须在本次目录与冻结合同内；不能建议删除必需部件、新增业务能力或编造配置。标准是判断依据，不是每条必须找出缺陷的清单。

分别判断每张截图所处状态：预览没有宿主标签栏；Sheet 的打开入口与内部提交可属于同一个命令；未选择、已展开、浅深色不是同时出现的界面。不能把摘要与全文的共同词句当作冗余，也不能把未捕获的确认框、加载或错误状态当作不存在。静态截图不能证明动画时序、减少动效、焦点恢复、键盘路径或触控命中范围；证据不足就不下结论。

复查只返回当前阶段规定的结构化 issues JSON。区分当前可调整的 presentation、需回设计的 design、宿主能力 host 与证据不足 unverified；只有真实截图/目标和受支持属性对应的 presentation 意见进入自动修改，其余保留待确认。一次集中修订、最多一次确认；仍有争议保留建议，不以无限改动换取空问题列表。

## 来源与取舍

提炼自 Impeccable 4.1.1 的 Operate/Read、`operate.md`、`animate.md`、`craft-floor.md` 和 `critique.md`：任务优先、认知负担、信息层级、状态连续性、目的明确的动效和有证据的评审。这里按 Molis 的连续工作面与声明式渲染器改写，作为随发行物提供的独立规范；运行时不依赖本机 Impeccable。未引入营销页视觉套路、固定动画参数、全套评分、访谈或子代理流程。
