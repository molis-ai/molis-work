## 1. 背景

公开来源拉取（`PublicSourceSync.sync`）在 `try` 里先 `executeExact`，再 `commitPublicResult`；后者在提交里把来源行的 `updated_at` 推到 `completedAt`（`plugins/native/feed/src/source-sync.ts:239-256`），提交后才 `flushPendingJudgments()`（同文件 270 行）。判断以调用者身份跑，失败会抛出来，进 `catch`（91 行）。`catch` 第一件事是 `await beforeEffect()`（98 行），守卫按拉取开始时的来源修订核（`source-sync-guard.ts:37-40` 的 `[updated_at, name, description, enabled, status, schedule]`），于是把拉取自己的写入读成别人改了来源，抛出 `feed.source_changed`，原来的错误（例如场景里读证据被 S-97 拒）对外看不见。终态 run 的判断在后面（102 行 `if (current?.phase === "terminal") throw error`），已经太晚。

C（#1327）为这个只改了测试走 Runtime 的 `feed.sources.sync`，没有改这个 `catch`（`specs/BACKLOG.md:217`）。

## 2. 目标

1. 拉取已提交（run 为终态）、其后判断抛出带码的错误时，`sync` 以那个错误拒绝，不是 `feed.source_changed`；来源、条目、终态 run 保持提交时的样子，没有多出 interrupted 记录。
2. 拉取没提交的失败路径一个行为都不变：来源被人改、暂停，调用被取消、撤权、停用，仍按现行顺序先过守卫，不写业务记录。
3. 调度器（`FeedSourceScheduler.tick`）遇到同样情形，行为与第 5 节写的一致，并有一条测试钉住。

## 3. 不做

- `source-sync-guard.ts` 的修订签名和选项：不做，守卫本身没错。
- `connector-sync.ts`、`research-library-sync.ts` 的 `catch`：不做。读代码的结论是它们没有这个缺口——连接器同步的 `catch`（`connector-sync.ts:81-82`）进来时来源行还没被本次拉取写过（写在 148 行之后），研究库同步（`research-library-sync.ts:98-99`）的判断在终态写入之前。你读完发现不是这样，在【方案】里说，不顺手改。
- 场景里读证据被 S-97 拒的规则本身（`runtime-judgments.ts`、`services.sourcePull`）：不做。
- 调度器 `source-scheduler.ts` 的守卫换法：不做。第 6 节 `RAC-1214` 红了，停下来问。
- `slices/feed-inbox-runtime-plugins.md` 的历史记录：不改。

## 5. 做法

已定，照做：

1. 只改 `catch`。进来先读 `this.feed.getSourceRunByOperationId(this.projectId, operationId)`；`phase === "terminal"` 就 `throw error`，在任何 `await beforeEffect()`、`await input.beforeEffect?.()`、`input.signal?.throwIfAborted()` 之前。这个分支不写任何东西，守卫在这里唯一的作用就是把错误换掉；而拉取自己的提交已经动了来源行，守卫会把它读成别人的修改，并且把 `refused` 置上。
2. 调度器路径里 `input.beforeEffect` 就是调度器按拉取前来源核的守卫（`source-scheduler.ts:49,53`），终态分支同样不许调它，否则同一个缺口换个地方出现。
3. 终态分支之外一字不动：`beforeEffect.refused` 时丢弃（95-97 行）、`await beforeEffect()`、`input.beforeEffect`、`signal.throwIfAborted()`、写 interrupted。95 行条件里的 `!== "terminal"` 在新顺序下恒成立，可以去掉，只读一次 run。
4. 不动守卫，不给守卫加「终态」的概念。`write()` 里的 `beforeEffect.check()`（28 行，FI-C-05）、`commitPublicResult` 里 89 行的 `await beforeEffect()`，都是正确性所需，原样保留。

照着写的例子：`plugins/native/feed/src/source-scheduler.ts:58-65`——同样是「失败来自自己已经写过的东西」，先分清是什么失败，再决定过哪个守卫，注释把理由写在代码旁。

调度器后果（已核，读代码，未跑）：今天提交后判断失败，`tick` 以 `feed.source_changed` 拒绝，`next_pull_at` 不前进（槽没花掉），下一轮用同一个 key 重放终态 run。修后，错误是判断的错误，调度器 `catch`（58 行）走 `result.failed += 1`、换成 `afterOwnFailure` 的守卫（63 行）、通过、`advanceSchedule` 花掉槽，`tick` 返回 `failed: 1` 而不是拒绝。这是对的（拉取确实发生了），但是行为变化，写进 PR 正文，`RAC-1214` 钉住。`recordActionableFault`（`source-scheduler.ts:90-94`）只对 `auth`、`configuration`、`stale_cursor` 且不可重试的错误建 `source_fault` 收件条目；判断失败不该落进去，`RAC-1214` 要断言没有新条目。

【方案】要回答：

1. 终态分支里，已被取消或撤权的调用对外报哪个错？默认：报原错误。理由：判断以调用者身份跑，取消或撤权时第一个失败本来就是那条拒绝（`judgment-queue.ts:134-152` 的 `judgeEach`，取消立即停止）；`catch` 只有在有东西抛出时才进来，没抛出就谈不上。请用 `RAC-1213` 证明，并说明有没有找到「原错误不是拒绝、而调用已无权」的情形；找到了写出来，等【统筹答】，不要自己再加守卫。
2. `RAC-1210`、`RAC-1211` 怎么造：store 级让 `captureJudgment` 抛 `ActionError`。码用哪个（错误码门禁按 `<主人>.<原因>` 写法数，见第 8 节）；要先确认这次拉取真的拉到至少一条新条目，否则没有判断可排（`judgment-queue.ts:35-37`）。
3. `RAC-1215` 怎么造 S-97 拒绝：`runtime-judgments.ts:31-34` 注释说 `evidence.read` 在场景回调里被拒。在 `judging(t)`（`tests/feed-runtime-plugin.test.ts:926-948`）上怎么让这条拒绝走到 `feed.sources.sync` 的调用方，写出来。造不出来，停下来问（第 11 节），不要退成别的断言。
4. 对 `connector-sync.ts`、`research-library-sync.ts` 的结论（第 3 节）你读完同意吗，一句话。
