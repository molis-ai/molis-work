**五个场景与平台能力检查（第 4.1 节）。** 插件：别的插件要知道「某轮的成果整合回主工作区时删了什么」也走同一个动作，不必各自记一份。平台：审批队列是唯一事实来源，只补了按来源读取，不新建能力。助理：读的是同一动作，不受影响。各类平台能力：观测采集已有审批结算事件，不重复。后续开发：上游命令回执若将来带上实际路径，可在同一处补「命令确认的删除」（BL-coding-command-path-receipts）。结论：**在主人处补读取，插件只消费**。

**比较过的做法。** ① Coding 自己在整合时记一笔删除：重复了审批队列的事实，且人在 Coding 以外批准时会漏；② 对比轮前后工作区：只能看到文件不在了，用户定过不足以归给本轮；③ 宿主读一轮审批时带上以它为来源的整合审批（选定）。

<a id="decisions"></a>

## 决策记录（99-1）

- **证据从哪来。** 能证实「本轮删掉了某个文件」的只有整合审批：它的文档逐个文件写出整合前后的内容（删除是「之后」为空），回执由执行方确认生效，来源写明是哪个会话的哪一轮。命令回执只有命令文字、退出码和输出，不含它动了哪些文件；Prologue 自带的「删一条路径」也没有开放给 Agent。所以普通命令直接在主工作区删文件，按 11-18 的决定保持未知、不列。要让这种删除也能证实，得由上游命令回执带上实际变动的路径，记为 BL-coding-command-path-receipts，不在本批做（动上游是红线）。
- **宿主一处补读取。** 整合审批是人在这一轮结束后发起的，没有自己的轮次，原来 `agent.run.reviews` 只按轮次筛，读不到它。现在同一个动作也带上「来源是这一轮、同一插件发起」的整合审批，事实仍归审批队列这一个主人；输入输出形状和版本都不变（合同阶段一，按原版本改），快照无变化。其他读这个动作的地方（继续上一轮、提交说明）只认文本写入和命令，不受影响。
- **工作树里跑了多轮。** 一个独立工作树可以接着用好几轮，整合时宿主以其中最新一轮为来源。删除记在整合审批写明的那一轮，不再往前猜是哪一轮的命令删的。
- **不改存储格式。** `deleted` 本来就在合同取值里，固定变更版本不升：删除项的 `after_text` 写空串、`kind` 写 `deleted`，原文只放整合前的内容，不编造；`coverage` 取值不变，注释写明也包括整合确认的删除。旧清单读法不变，不加兼容读取。
- **只收删除。** 整合里的新增和修改不进本轮变更：子任务的文本写入本来就以写入审批列在本轮里，再列一次会重复。
- **界面。** 复用固定清单原有的状态标：种类写「删除」（与新建、修改并列），状态写「已执行」（不说「已写入」）；打开是整份删除，复制补丁写 `/dev/null`。表头改为「N 个文件 · N 处改动」，下方说明补上「以及整合成果时确认删掉的文件」。
