**Molis Work：四人团队后续开发分工与架构拆解建议**

2026-09-25｜讨论稿，尚未作为开发需求书接受。根据当前工作树的源码、既有需求书与静态检查分析；本轮不修改业务实现，也不沿用旧文档中的测试通过状态作为当前验收结果。

建议保留现有 Module、Horizontal Service、Plugin、App 分层，以四位稳定负责人推进。七个产品方向会共享身份、动作、AI 执行和工作状态，不能直接划成七条独立开发线。Character 与 Prologue 应前置统一；插件优化和体验改善随产品路径一起交付。

**当前架构可以支撑分工，但需要先补三个明确的衔接处。**

一是本机能力如何成为受授权的远程能力；二是 Character、Prologue 与动作服务如何贯通到不同 AI 入口；三是 Builder 生成的工具如何注册真实动作并参与后续工作。团队协作还需要明确共享项目的业务状态由谁决定。

| 方向 | 当前可复用基础 | 当前缺口及证据 |
| --- | --- | --- |
| 手机、桌面、云端互联 | Workbench、Desktop、本机动作网关 | 未发现正式 apps/server、apps/mobile、packages/exchange、modules/sync-replication 实现；网关明确只允许数字 loopback HTTP，不是远程接口 |
| 团队协作 | Projects、Goals、Artifacts、Governance 的本地规则与私人工作上下文 | Identity/Team 与 Sync 目前只有描述符级 Contract；没有完整认证、团队权威状态、设备交换与冲突处理 |
| Builder | Prologue 设计/行为角色、受控零件、计算、试用、独立发布、版本与数据保护 | 当前生成物是固定解释器上的本地数据应用；生成 Manifest 无公共动作，不能直接成为助理可调用的通用工具；图片输入尚无正式 AgentStartRequest 通路 |
| 个人助理 | 信息助理入口、动作发现与调用、判断函数、Schedule、Attention、私人 Session | 现有 assistant-http 仅能建议 configure_filter / draft_pages，两类动作由前端继续处理；尚非持续的个人任务执行与恢复体系 |
| 插件优化 | 多个插件已接入共同动作目录和内容交接 | 动作迁移进行中，不能按旧索引判断所有插件成熟度；应沿选定业务路径分批完成 |
| 操作体验 | Workbench、UI Host、Design System 与插件各自 UI | 手机窄屏截图不等于跨设备产品；首次使用、工作接续、权限与故障状态需要整条路径验收 |
| Character / Prologue | Character 草稿、Artifact 固定版本、AgentHost 冻结与执行、Coding 消费 | Builder 未声明 Character 消费；Cognia/Alchemist 的 Host 适配单独创建 Prologue adapter；助理和部分工作流仍经 hostCompleteText 调模型，入口尚未统一 |

重要补充：Builder 较新的工作项记录了真实 MiniMax-M3 的读书清单、库存账本两个场景，不能继续依据更早文档说“从未测过真实模型”。但两个场景不能证明任意搭建需求的成功率，其真实环境发布、图片输入和广泛质量仍有缺口。[较新验证记录](../../specs/plugin-builder/work-items/live-collaboration/spec.md)

当前工作树有大量已有修改，不能直接从旧 HEAD 分出四条开发线并假定包含这些成果。正式启动前应由团队整理一个包含所需工作成果的共同集成基线，再创建各自分支或工作树。本轮没有提交、清理或覆盖这些修改。

只读静态检查读取到 66 个 package、50 个 Contract subpath。workspace 检查失败于 Dataset README 缺状态、Contract 入口和迁移 Goal 三项；源码依赖检查另报 Local Host 的 connector-connection-store.ts、web-connector-connections.ts 直接导入 node:sqlite。这是需要归还正确存储/服务 owner 的具体问题，不意味着应重写整个仓库。检查使用现有 test-kit 构建产物；本轮未运行全量构建和产品验收。

**四人的长期责任如下，人数相同不意味着每条线工作量相同。**

| 负责人 | 主责任 | 主要代码范围 | 第一份可验收交付 |
| --- | --- | --- | --- |
| A：AI 与能力底座、个人助理 | 统一 Character、AgentHost、Prologue 与动作调用；随后负责助理产品闭环 | horizontal/agent-host、modules/characters、packages/kernel 的动作部分、相关 Contracts/SDK；助理后续从 Host 薄接口进入独立产品 owner | 同一 Character 固定版本用于两个不同入口，调用同一真实动作，取消、撤权、结果与历史可核对 |
| B：云端与团队协作 | Server、身份、设备、交换、同步、团队业务状态 | 新建 apps/server、modules/identity-team-access、modules/sync-replication、packages/exchange；团队应用层和服务端存储适配 | 手机请求经 Server 到桌面，结果返回；断线重连不重复执行；随后两人共用同一团队项目 |
| C：Builder 与场景插件 | 需求理解、生成、修订、验收、发布；按场景补足插件能力 | plugins/native/plugin-builder；选定插件及其动作/内容合同；必要的 Host 专属装配文件 | 新需求生成可使用插件，修改后保留数据；生成插件的动作能被助理发现并实际调用 |
| D：跨端客户端与体验 | 手机客户端、桌面连接体验、公共操作动线、设计系统 | 新建 apps/mobile；apps/desktop 的配对/状态/通知适配；Workbench Shell、UI Host、Design System 的公共部分 | 手机上查看桌面工作、提交一个操作、看到真实状态与结果；恢复失败时知道下一步 |

A 作为技术集成负责人，管理共享架构决定与公共接口版本；B 决定认证与团队访问语义；C 决定 Builder 与插件业务语义；D 负责公共交互约定。各负责人都承担自己功能的界面和验证，D 不成为全项目所有页面的代写者，A 也不代写每条线的接线代码。

A 的前期主要交付是公共执行链，个人助理的完整多步骤能力随后推进；B 先完成设备互联所需服务，再扩展团队；C 先提高现有生成质量，再接新能力；D 先完成公共动线与手机薄客户端，再补团队界面。这样四人可以同时有成果，而不会假装所有方向都能同时达到完整产品水平。

**共享接口需要先做小范围统一，不能演变为长期平台重构。**

| 需要先约定的接口 | 明确什么 | 负责人和首批消费者 |
| --- | --- | --- |
| 身份、项目与执行位置 | 谁发起、属于个人还是团队、在哪台设备或云端执行；凭据由可信 Host 注入 | B 提供身份和设备语义，A 接入动作/Agent；D 消费 |
| 动作发现与执行 | 继续使用已有能力 ID、版本、Provider、输入输出、可用性和权限；远程与 AI 使用同一业务处理器 | A；C 的生成插件和 B 的远程调用消费 |
| Character 与 AI 启动 | 选择的固定 Character 版本、上下文来源、角色能力、模型、预算、取消与恢复；不得由人格取得额外权限 | A；Builder、助理及现有 AI 插件消费 |
| 跨端操作与成果引用 | 请求标识、目标端、对象版本、状态与结果引用；传输收到、业务生效、用户接受分开表达 | B 与 A；D 展示，C 提供真实业务结果 |
| 公共工作状态呈现 | 等待、运行、待决定、失败、结果不明、已完成；给出对应的可用操作 | D 制定，其他负责人在自己功能内实现 |

即时查询和短操作保持现有轻量调用。只有需要断线恢复或后台追踪的操作才建立持久执行记录。引用已有 Session、Run、Artifact 和业务对象，避免创建另一套拥有所有状态的总 Manager。

ActionContext 中的回调、AbortSignal 等进程内能力不能直接当作网络协议发送；Server 和接收 Host 根据认证、授权和请求重新构造可信上下文。远程请求中的 actor_id、目录、权限列表和 Character 都不能自行成为授权证据。

**手机互联可以先独立交付，团队业务和云端执行分开增加。**

推荐首条路径为：手机 → 已认证的 Server → 桌面主动建立的连接 → Local Host 动作服务 → 原插件 → 结果返回手机。手机首版提供查看进度、补充输入、处理关键决定和读取成果，先以适合手机的 Web/PWA 形态验证路径；原生能力按实际通知、后台与系统集成需求另行增加。

当前仅限 loopback 的网关继续服务本机进程，不通过去掉校验或把控制 token 放到手机上实现公网访问。新增远程适配复用核心动作服务，并拥有独立认证、设备配对与撤销机制。桌面离线时，界面明确显示等待桌面；是否允许离线排队由操作性质决定，重连后再次验证权限与对象版本。

云端 Server 保存已授权上传的工作摘要、成果和远程请求。手机看到的是该范围内的内容，不宣称看到了离线桌面的最新全部状态。文件型成果需要可授权下载的内容或 Blob 引用，不能把桌面绝对路径返回给手机当作可读结果。

手机、桌面执行、云端自主执行是三个不同交付层次。桌面关机后仍要完成任务，需要配置云端执行 Host/Worker、模型与工具凭据、工作材料和执行环境。建议在设备往返路径稳定后，先为不依赖本机文件的单一场景接通云端执行。Server 控制进程不直接接管所有本地业务与 Runtime。

验收采用一部手机和一台真实桌面：提交任务、桌面完成、手机读到成果；然后实际断网、重启桌面、撤销设备、重复发送同一请求。结果未知时先核对既有操作，不盲目重放副作用。远程批准必须对应准确的待决定项和当前版本，过期请求不能继续生效。

**团队协作需要一个明确的共享事实 owner。**

现有架构将 Server Core 定义为认证、路由、Envelope、版本与传输服务，不解释插件私有内容，也不判断 Goal 完成。这适合交换，但仅增加消息中转还不足以组织团队工作。

建议保留 Server Core 的轻量边界，在其旁边设置团队项目应用层，可按 Team Plugin/应用装配实现。它负责成员参与、分派、共享进度与决定，通过同一套 Goals、Artifacts 等业务规则产生团队权威状态。存储部署不同可以更换适配，不复制一套完成算法。该服务端业务装配是需要补写架构决定的扩展，目前并不存在。

个人未分享的草稿和 Session 继续留在个人端；选择发布到团队的成果和工作状态进入 Team Project。桌面持有副本与待提交意图。离线修改携带原版本，联网后由权威端接受或返回冲突；第一版优先采用服务端序列与明确版本检查，先不建设通用多人文档实时合并。

最小团队路径是两位成员、一个项目：创建/分派工作 → 成员在自己的桌面执行 → 提交进度和固定成果 → 另一位成员查看或作出决定 → 各端看到一致的共享状态。负责人变化、成员移除、提交冲突与断网补交必须纳入这条路径。团队管理员身份不会自动取得私人会话访问权限。

组织、项目、成员权限属于 Identity/Team；Character 表达行为与专业方式。两种“角色”必须在代码与界面上区分，选择一个高级 Character 不会获得团队管理权。

**Character 与 Prologue 统一，应当先覆盖真正的执行入口。**

保留 Characters Module 的草稿与启用状态、Artifact 固定版本以及 AgentHost 已有的冻结机制。补充 Home、项目和本次任务的选择规则，每次执行明确使用哪个版本；角色更新影响后续选择，已经运行的任务和历史报告保留当时的版本。

迁移顺序建议为：共用 Host 的 Prologue 执行入口 → Character 解析与适用范围 → 动作目录到 Agent 工具的授权适配 → Builder 和助理 → Cognia、Alchemist、工作流等已有入口。Cognia 的 Home 作用域和 Builder 的项目作用域需要都能表达，不能为了复用接口伪造项目或强制要求本地仓库目录。

现有 startAuthority 从 Workbench 的内置插件目录获取角色授权信息，生成插件则没有该入口。应让 Host 根据实际安装与 Manifest 提供可信角色/能力声明；Workbench 消费这些信息来展示界面。这样云端和无界面执行也能得到相同授权语义。

统一的是身份、Character、上下文、动作权限、调用记录与恢复。多步骤 Agent 和内容生成可进入共同 Prologue 服务；Jev/TypeSafe 等结构化判断通过同一能力治理调用，保留明确的输入输出，不让全局人格覆盖分类规则或固定 schema。Character 在专业判断中只使用该场景允许的偏好，在纯规则判断中可以明确不适用。

原生 CLI 路径可以保留为显式外部 Runtime Adapter，沿用其真实权限机制，并记录固定 Character 输入。不能把 SDK 执行与原生终端执行说成完全相同的可控能力。宿主始终检查实际支持的操作。

验收重点是两个不同产品入口使用同一固定 Character，调用相同的授权动作；停用角色、撤销动作、换模型、取消与重启后得到符合约定的行为。角色文字成功传入模型只是局部证据，还需要用同一任务对照输出质量和人工纠正成本。

**Builder 的下一步是扩大可兑现的能力，而不只是让生成过程更热闹。**

当前实现的优势是受控数据、真实存储、可见构建过程和兼容发布，应当保留。要达到用户所说的“Manus 时刻”，交付标准应为：用户提出一个事先没有专门适配的真实需求，得到能执行关键流程的插件；用户提出局部修改后，系统保留正确内容与已有数据；发布后第二天仍然可以使用。

建议分三层增加能力。第一层提高现有本地数据工具的理解与修订质量，并按真实需求补足缺少的数据类型、状态和页面表现。第二层让生成插件声明并注册公共动作，通过现有动作服务调用其他插件及已授权的外部能力，保存成果引用，参与助理和工作流。第三层才讨论任意代码、独立后端或更自由的 UI。

当前 PluginRuntime 是受信进程内执行，UI Host 也不等于任意代码沙箱。因此第三层需要单独设计执行隔离、网络/文件权限、资源限制和包升级恢复。四人团队首期应优先交付前两层；如果业务必需任意代码生成，则明确置换一个当前产品阶段，不能悄悄塞进 Builder 迭代。

参考图片同时影响 Builder 和手机输入，先由 A 补齐可授权读取的材料合同、模型能力检测与 Prologue 适配，再由 C/D 增加入口。不能只做上传按钮，让图片最终仍然无法进入模型。

质量验证从用户真实需求中形成任务集，检查需求覆盖、首次可用、纠正次数、到达有效成果的时间、修订保留与次日实际使用。测试应使用独立预期结果和真实操作，不能只让生成模型评价自己的设计是否通过。

**个人助理先完成一条持续工作路径，再扩展主动性。**

建议选择“发现值得处理的信息 → 结合当前目标判断 → 调用插件整理成果 → 提醒待决定事项 → 下次继续”作为第一条路径。它能复用当前 Feed、Inbox、Pages、Goals、Schedule 和动作服务，也比先造一个覆盖一切的聊天框更容易验收。

助理需要从明确的上下文来源读取当前项目、选定材料、未完成事项和允许使用的个人偏好；根据可用动作目录选择工具；将执行结果保存到原业务 owner；保留 Session 和恢复引用；向用户呈现真实结果和需要判断的内容。不可读取的数据与无法调用的动作应当如实说明。

持续的委托需要一个稳定的产品 owner。可以将现有 assistant-http 保留为薄传输，把助理用例放进独立插件/应用服务；Session 继续归 Private Work Context，唤醒继续使用 Scheduler，业务成果继续归对应插件或 Artifact。若新增持久 Action Request，则先更新已有 Actions 的定位，避免与 Agent Run、工作流实例重复保存同一状态。

主动执行分步增加：先手动请求，随后是用户启用的规则，再是明确时间或事件触发的持续委托。每一步都需要有效结果、可中断性和预算边界。对外动作超时应返回结果未知并核对，不能自动重试造成重复发送或重复记录。

效果评估包括任务实际完成率、需要用户纠正的次数、重复解释的负担、漏掉和误报的重要事项，以及打断是否有价值。用户说“帮我整理”之后出现一句合理建议，不能算个人助理已经完成工作。

**插件和体验通过同一条业务路径持续改善。**

C 首期只集中处理 Builder 和当前共同验收场景必需的插件。比如助理路径采用 Feed → Inbox → Pages，就先把这条路径的动作、内容交接、权限、错误和恢复做顺。插件各自保存自己的领域数据，通过公共动作和成果引用协作。其他插件的持续迭代按影响排序，不在同一阶段承诺全量优化。

D 制定首次进入、工作进行中、成果阅读、关键决定、失败恢复和移动端接续的公共交互约定，维护 Shell 与公共组件。A/C 在助理和 Builder 内实现这些约定，B 提供足以准确表达状态的数据。产品实操由两人交叉使用，避免只有作者自己知道怎么操作。

**并行批次按依赖放行，每批都有真实可用结果。**

| 批次 | A：AI/助理 | B：云端/团队 | C：Builder/插件 | D：跨端/体验 | 共同验收 |
| --- | --- | --- | --- | --- | --- |
| 启动 | 冻结动作/AI 公共合同与迁移范围 | 明确身份、个人/团队 owner、请求与同步合同 | 整理当前能力边界与真实搭建任务，改进本地生成质量 | 给出手机关键路径高保真切片，改善已有本地动线 | 共同基线、文件归属、合同样例与失败语义明确 |
| 第一批 | Character/Prologue 统一执行、动作工具适配 | 最小认证、设备配对、传输、授权成果读取 | 生成插件动作接入与发布后可调用 | 手机薄客户端与桌面连接，接真实接口 | 手机发起一个现有动作，桌面执行并返回真实成果；Builder 新动作可被目录发现 |
| 第二批 | 个人助理多步骤执行、取消与继续 | 团队项目业务层、成员/分派/共享进度 | 从新需求生成并迭代可供助理调用的插件 | 手机工作接续、关键决定、团队进度界面 | 助理使用 Builder 产物完成工作；两位成员的桌面与手机读到一致共享进度 |
| 第三批 | 选择一个主动助理场景并验证质量 | 不依赖本机的云端执行或更完整团队恢复，按优先级选择 | 按实际失败案例补能力，优化所选插件链 | 异常恢复、首次使用与端到端可用性收口 | 四人自己连续用产品做真实工作；原始结果、故障与人工成本可核对 |

表格是依赖批次，不是固定工期承诺。建议每两周检查一次真实可用产物，具体交付量按首批吞吐调整。单条线达到公共接口门槛后即可进入下一项，不要求所有模块重构完才做产品。但团队权威状态不能用传输成功替代，手机演示也不能代替真实桌面执行。

代码冲突需要靠明确归属减少：A 负责 actions/agent-host 的公共类型及核心执行；B 负责 identity/exchange/sync 的类型与实现；C 负责 Builder 和已分配插件；D 负责公共客户端和设计系统。同一公共文件在一批工作中只有一个编辑者。Host 的各功能装配文件由对应负责人提交，local-host.ts、project-host.ts、web-server.ts、统一目录和总样式等共同热点指定当批集成人串行修改。

所有人每日向集成分支提交可构建的小批次，跨模块请求以具体 Contract 变更提出。既有动作架构 spec 继续是该范围的需求来源，新增工作项补充依赖、允许路径、验收与交接；本讨论稿被接受后再转成总 spec 与必要子项，不另起互相竞争的架构文档。

四条线的终局验证可以用同一个真实任务串起来：用户在桌面用 Builder 创建专用工具，个人助理用选定 Character 调用该工具完成工作，用户在手机上查看并处理一个决定，再把选定成果交给团队成员继续。桌面离线时状态如实显示，恢复后能够继续；已经分享的内容可见，私人草稿仍然保持私人范围。每条线都有独立验收，同时共同证明 Molis Work 的工作接续价值。
