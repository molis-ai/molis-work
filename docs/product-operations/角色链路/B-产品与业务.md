读卡须知：
- 成熟度按整条链最弱一环标。链路几乎都用到 v0.2.0 之后才合入 main 的能力，本次也没有逐环核对哪些已在发布版里，所以链路一律不标"已发布"；"main 部分"多数是真实账号联调、本机原生组件或本人验收没做，瓶颈一栏写明是哪一环。
- 只因要先配模型的环节不降级，写"需模型"：配模型是首次设置的一步。但推荐、判断这类直接决定流程走向的模型输出（浮条推荐、判断规则）没做命中率评估，这一环标 main 部分。
- 可选的步骤不拉低整条链，卡里写明"第 N 步可选"；做不到的步骤要么改成今天能做的做法，要么标"第 N 步为规划"并相应定标签。
- 要另一个人确认、但只能由你代记结论的（法务、导师、客户、家人），按机制本身标，不因此降级，瓶颈里写"对方进不来，由你代记（团队协作未做）"。

## FND 创始人 / 独立产品负责人

**角色画像**：一到五个人的公司，产品、部分开发、销售、融资都自己扛。想法和决定记在 Notion 或飞书，开发用 Linear 或 GitHub Issues，对外靠 Gmail 和微信，研究用 ChatGPT/Perplexity，代码交给 Claude Code 或 Codex。AI 用得最重，也最清楚它的报告写得漂亮、下周回看时却说不清当时凭什么。最在意：有限的时间押在对的方向上，答应过用户和投资人的事不掉。

### FND-01 两个方向这周只能验一个：市场和成本都查齐了，才记下 Build 或 Hold
- 触发：周五晚上，"独立作者素材工具"和"小团队评审工具"各有一份深度研究，结论都是"市场有机会"；下周二要跟天使投资人说清先做哪个。
- 链路：炼金术士 `alchemist.directions.create` 写下两个方向 → `explorations.start` 后台炼化出候选卡，各保留一张成 Idea（`cards.keep`，形成初始版本）→ 对每个 Idea 版本 `research.plan` 选模型、设调用次数上限，`research.start` 跑"市场空间 + 实现成本"双视角研究，证据经宿主搜索层带真实网址，缺口单列；预算不够只出部分报告并标明 → 在报告选区写注释"这个用户数是厂商自述"（`annotations.create`），由注释提出研究方法校准（`alchemist.memory.propose`），确认（`alchemist.memory.apply`）后方法出新版本，下次研究沿用 → 两个视角都齐才能 `decisions.create`：作者方向 Build、团队方向 Hold，理由引用两份报告 → 在 Goals 里手动建"两周内 5 位作者带真实稿子试用一次"，把"试用结论"设为必须本人验收 → 下周新证据来了，打开上次决定和当时的缺口对照。
- 交付物：炼金术士里两条带报告引用的正式决定；Goals 里一条带本人验收要求的验证目标。
- 机制：M2、M4、M7
- 成熟度：main 可用（需模型）；瓶颈：炼金术士包仍标 partial；报告还不能固定成成果挂到 Goal 当依据（固定研究成果的生产端口未接线，`alchemist.reuse.publish` 不在这条链里）；从决定到 Goal 靠人手建。
- 原来怎么做：两轮 ChatGPT/Perplexity 深度研究 + Notion 决策页 + 一张比较表。研究本身已经很强；卡在两份报告口径不一、调用花费不可控，下周回看只剩结论，看不到"当时缺什么证据"，新研究又从头比。
- 不适合：已有真实试点数据、决定靠用户行为而不是桌面研究的时候。
- 频率/痛感：中 / 高——每月几次，押错方向代价是几周；只有旁证：Stack Overflow 2026 仅 6.6% 愿意让 AI 参与重要决定（开发者样本），其余为推断。

### FND-02 每周一早上 20 分钟扫一遍市场：信号变成机会，值得追的变成方向
- 触发：周一 8:30，听说一家竞品上了 GitHub Trending，Product Hunt 又冒出两个同类工具；你不想再开五个标签页手翻。
- 链路：炼金术士 `pulse.sources.configure` 启用 Toolify、Watcha、GitHub 来源；GitHub 账号另用 `alchemist.pulse.github.configure` 选「服务连接」里的（令牌留在宿主，插件拿不到；只有本人能选，选定后整个 Home 的项目共用）→ `pulse.start` 按规则综合（不调模型）出报告与机会 → `opportunities.save` 暂存两条，`opportunities.convert` 把一条转成探索方向 → 对那家竞品在 Feed 加更新日志 RSS 和网页查询"<竞品名> pricing"，建关键词捕捉规则，`feed.rules.preview` 先看最近 5 条怎么命中，再保存为命中进 Inbox → 每天早上想看"哪三条值得看"时，对助理说一句，让它读 Inbox 里昨天命中的竞品动态、列出三条；Schedule 的对话任务做不了这件事，它只读得了项目工作目录里的文件，读不到 Inbox，"打开就有一页"属于主动助理和工作简报（规划）。
- 交付物：脉搏报告与新方向；Inbox 里按规则筛过的竞品动态；助理按需列出的"值得看的三条"。
- 机制：M4、M6
- 成熟度：main 部分；瓶颈：市场脉搏要联网访问三个站点，盘点标部分可用；网页查询来源的集成工厂是骨架、实际走宿主路径；每天早上自动列出"要我看的三条"今天做不到。
- 原来怎么做：Feedly、Product Hunt、GitHub Trending 订阅 + Notion 想法清单。订阅工具抓得全；卡在信号和想法清单是两处，两周后说不清某个方向是被哪条信号引出来的。
- 不适合：只盯一两个竞品、手动看官网更快的人。
- 频率/痛感：高 / 中——每周；Feedly 已在做 AI 归类（外部补研 U7，个例），差异只在"信号到方向"的留痕。

### FND-03 投资人今晚要一页进展：数字从 Goals 和待办里来，不让 AI 编
- 触发：周二 22:00 投资人来信："明天 10 点前发一下 10 月进展和 11 月计划。"
- 链路：Gmail 来源把这封信拉进 Feed（只带主题和摘要片段，够看出是谁来的、要什么），加入 Inbox，"转为待办"带来源 → 对助理说"按周报模板起一份 10 月进展"：助理用 `find-capabilities` 找到并读取 Goal 状态、交付物列表（`goals.deliverables.list`）、待办的已完成与等待他人视图、Coding 固定报告列表，写入前出操作卡给你确认 → Pages 周报模板成稿 → 对"本月新增用户"一句评论 @助理"这个数出自哪"，答复只回到评论线程、不改正文 → `pages.promote` 固定这一版 → `ppt.create` 后用 `ppt.outline`（给 `page_id`）从这篇出大纲、删到三页，导出 `.pptx`（讲者备注保留）→ 两个固定版本记为 Goal"Q4 融资沟通"的交付物。
- 交付物：固定版进展文稿与三页演示稿，挂在 Goal 下，下个月可对照。
- 机制：M1、M4
- 成熟度：main 部分；瓶颈：Gmail 真实账号 OAuth 验收被暂缓；"周报有固定的家、只报变化"的工作简报插件是规划，现在是一篇普通 Pages。
- 原来怎么做：翻 Linear、GitHub、Notion 拼数字，贴进 ChatGPT 润色，再进 Google Docs。润色很快；卡在每个数字要回原处再核一遍，下个月又从零拼。
- 不适合：已有 BI 看板、投资人更新就是截看板的公司。
- 频率/痛感：中 / 中——每月一次，临时催稿时高；Anthropic 对 Cowork 会话的分类里，"把零散状态更新整合成报告"所属的业务流程类占 33.4%（用量证据，不直接证明痛）。

### FND-04 定价改版：用"定价 + 企业 SaaS"方法拆目标，改一条要求只重议受影响的那几块
- 触发：免费用户占比太高，决定 11 月 15 日上付费档；周三晚上要拆清楚，周四给两位兼职开发派活。
- 链路：Goals 建"11/15 上线付费档"，项目说明写硬约束"不做免费无限额、价格页文案本人定"（`goals.guidance.add`；内置助理和插件 Agent 每轮都带上，外部 AI 在读连接摘要时拿到，Work 不往外部 Agent 的每一轮推送）→ `goals.planning.catalog` 选"定价与变现"领域、企业 SaaS 行业、支付资产叠加层，`planning.read` 读正文 → 让 Claude Code 经 MCP 按方法提结构提案（`goals.tree.submit`），系统做整图检查（缺端点、循环、重复关系）→ 你逐条确认（`goals.tree.decide`，只有本人能调）→ 把"价格页文案"设为必须本人验收 → 周五改主意：先对 10% 新用户灰度，`goals.planning.impact` 算出受影响子图，只对子图重新提案、确认。
- 交付物：一棵确认过的 Goal 树、带本人验收的要求、一次有影响范围的变更记录。
- 机制：M2、M1、M5
- 成熟度：main 可用；瓶颈：外部 Runtime 写提案要先接入、授权并新开 Session；方法不会自动成树，拆分质量取决于模型。
- 原来怎么做：Linear 项目 + Notion 定价文档 + 跟 Claude 聊拆解。Linear 管任务很顺；卡在改成灰度后哪些任务要重做靠记忆判断，下一次对话的 AI 也不记得"文案我定"。
- 不适合：只改个价格数字、不牵动流程的调整。
- 频率/痛感：中 / 高——每季度几次；推断。

### FND-05 早期用户承诺台：答应过谁什么，界面、助理和 Claude Code 查的是同一份
- 触发：这个月第三次忘了答应设计伙伴"下周加 CSV 导出"；承诺散在微信、邮件和 Notion 评论里。
- 链路：插件创作台写一句需求"记录早期用户的请求与我的承诺：用户、原话出处、答应日期、状态，到期提醒" → Agent 设计、在沙箱写后端与测试，宿主类型检查、打包、试跑后安装 → 插件用 `reminders.add` 到期把提醒放进 Inbox → 你在界面里录；也把一张微信截图交给助理，助理 `find-capabilities` 找到这个插件的"新增承诺"动作，出操作卡确认后写入 → 写代码时 Claude Code 经 MCP 读同一份承诺，交付后改状态为"已兑现" → 工作流程：起点站 Inbox（设计伙伴邮件的正文由你贴成一条事项；Gmail 来源只带主题和摘要片段，不够整理）→ AI 整理出"请求/承诺" → 动作步骤（`workflows.steps.actions`）调这个插件的新增动作。
- 交付物：装在本项目的承诺插件和它的记录，到期提醒进 Inbox。
- 机制：M5、M1、M6
- 成熟度：main 部分；瓶颈：创作台预览里的外部写入是替身，装好后才真写；生成插件不自动进 ⌘K、不能声明成果类型；沙箱仅 macOS；这个业务样例还没做过；插件动作要面向流程、输入平铺才能当流程的一步。
- 原来怎么做：Notion 数据库 + Zapier 提醒 + 在 Claude 里粘贴。数据库很灵活；卡在 Notion AI 和 Claude 按各自口径记，Zapier 改一次字段就断，自己维护不动。
- 不适合：承诺不到十条，一张表加日历提醒就够。
- 频率/痛感：中 / 中——每周新增；外部补研 U4："个人小工具难维护"是最稳定的反对声，价值要落在"平台替你养、AI 共用同一操作"，不是"AI 能写工具"。

### FND-06 散步时想到的点子，到家已经在方向卡里
- 触发：晚饭后散步冒出"作者工具可以先做'素材到大纲'"，手机录了 90 秒语音。
- 链路：录音拖进灵光，`lingguang.material.read` 用本机语音模型转写（首次下载模型前先问你），记成一条灵光 → 选几条相关灵光开头脑风暴（`lingguang.conversation.message`），追问"最小验证是什么" →（可选，规划）在 Work 输入框点麦克风口述补充，文字先进草稿、你检查后再发；这一步现在用打字代替 → 选中整理好的那段，浮条推荐"记成炼金术士想法"，一点就成方向 → 下次炼化时这条和上周的 Idea 一起比较。
- 交付物：一条带原始转写的灵光，一个炼金术士方向。
- 机制：M3、M4、M7
- 成熟度：main 部分（第 3 步可选：输入框口述是规划，先前的实现 PR 关闭未合，交互要重新设计）；瓶颈：灵光转写依赖原生组件，未构建时报不可用；"一句话新建"到炼金术士的覆盖面未逐插件核实。
- 原来怎么做：手机语音备忘录或 Otter + 微信发给自己 + 隔天整理进 Notion。录得很顺；卡在一半语音再也没被整理，想法和后来的方向研究接不上。
- 不适合：不录语音、习惯手写的人。
- 频率/痛感：高 / 低——几乎天天有，丢了也不疼；推断。

**这个角色最可能的 killer**：FND-01。"AI 说市场很大，Work 说成本那一半还没查完、不让记 Build"是 60 秒能演的反转；研究预算、双视角和决定记录连成一条，熟练用户现在要拼三样工具还得自己记口径。它现在是 main 可用（需模型），但炼金术士包整体仍标 partial，报告固定成成果还没接线，所以只适合小范围试用，不当主推。

## PM 产品经理

**角色画像**：在 20–200 人的公司管一两条产品线：写 PRD、开评审、分诊反馈、和研发设计对范围。文档在飞书或 Notion，任务在 Jira 或 Linear，稿子在 Figma，调研用问卷星或 Google Forms，初稿交给 ChatGPT。AI 用来起草和总结，但对"开发那边的 AI 是不是按最新范围在做"没底。最在意：范围变化有据可查，研发拿到的是现行要求，结论背后有用户证据。

### PM-01 评审改了范围：PRD、Goal 约定和开发 Agent 读的是同一份现行要求
- 触发：周四评审决定"订单导出这期只导当前筛选结果，历史归档下期做"；开发同事的 Claude Code 会话昨天还在按"全部导出"做。
- 链路：Pages 打开 PRD（PRD 模板起的），改"范围"一节，评论 @助理"按新范围列出受影响的验收条件"→ Goals 里 `goals.agreement.set` 更新当前约定，把"空结果提示"设为必须本人验收；约定一改，之前的本人结论自动作废 → 开发侧 Claude Code 经 MCP 提 `goals.decisions.request`"归档导出的接口已经写了，要回滚吗"，目标页的决定表单列出问什么、依据、各选项的影响（Agent 自己写的一行，Work 不计算），你 `decisions.record` 选"保留接口、不对外暴露"→ 下一轮新开 Session，Agent 先 `goals.contract.read`、`pages.get` 读现行要求；它经 MCP 写 PRD（`pages.update`）必须带读取时的整篇版本，旧了被拒、要求重读 → 交付时 `goals.closure.submit`：空结果提示没有你的结论就不算完成 → 选中 PRD 里"通知设计改空状态"记成待办，带出处。
- 交付物：PRD 现行版、Goal 的当前约定与一条决定记录、本人验收结论。
- 机制：M2、M1、M3
- 成熟度：main 可用；瓶颈：开发侧要接入 Work 的 MCP 并逐项授权 Goals/Pages 动作；本人结论不自动绑代码 SHA，版本由人注明；只管 Goal 完成，不拦外部合并与发布。
- 原来怎么做：飞书/Notion PRD + Jira 改单 + 群里 @开发。改 PRD 很快；卡在 AI 编码会话里残留旧范围，收尾时没人对着最新约定核，"做多了"或"做错了"到演示才发现。
- 不适合：研发不用 AI Agent，或团队已有严格的需求变更与测试门禁。
- 频率/痛感：高 / 高——每个迭代都有范围变化；Stack Overflow 2026 近半开发者只在能自行验证时信任 AI；研究 6.1：读到的竞品官方页面里没有把"验收"做成目标级一等对象。

### PM-02 每天的用户反馈自动筛，周五合成一份每条都能点回原话的综述
- 触发：周五 16:00 要交本周"用户声音"；反馈来自支持邮箱、社区论坛、应用商店评价。
- 链路：Feed 加 Gmail（支持邮箱；只取主题和摘要片段，默认只看收件箱未读）、论坛 RSS、网页查询"<产品名> 评价"三类来源，各设拉取间隔 → 建捕捉规则：关键词 + 一条判断规则"是不是可执行的产品反馈"，先预览最近 5 条再保存为命中进 Inbox → Inbox 里 `inbox.next` 给每条"先核查 / 整理成稿 / 做完了 / 忽略"的建议，bug 类你自己"转为待办" → 周五在 Inbox 选 20 条，`inbox.pages.generate` 要求"按主题分组，每条保留原话"（邮件只有主题和摘要片段，要原文就把正文贴进来），生成带材料快照（正文、修订号、来源、摘要）的 Pages → 你改结论，`pages.promote` 固定 → 用 `goals.artifact_inputs.pin` 记为 Goal"Q4 留存"的输入。
- 交付物：一份附本期材料快照的反馈综述固定版；对应的待办。
- 机制：M4、M6
- 成熟度：main 部分；瓶颈：判断规则要 TypeSafe 连接；Gmail 真实账号验收暂缓，且只带主题和摘要片段；快照可能是节选；两期之间的比较仍靠人。
- 原来怎么做：Productboard/Dovetail 或 Notion + Zapier 汇集，ChatGPT 归类。专业反馈工具归类做得好；卡在三周后负责人追问"这条结论是哪几封邮件说的"，原话已沉在邮箱里。
- 不适合：每周上千条、需要专门标签体系和团队共享的公司。
- 频率/痛感：高 / 中——每周；外部补研 U8 证据弱（厂商博客），按推断写。

### PM-03 30 位老客户的付费意愿调研：从出题到评审会演示稿
- 触发：要不要做"团队版"，下周三评审要数据；你不想把客户答案存到外网问卷平台。
- 链路：Forms 新建问卷，`form.questions.draft` 写"了解团队版付费意愿"——要求太泛，它先回两道选择题追问（目标人群、要比较的方案），再生成 10 道题 → 人改题、预览 → `form.fillpage` 导出独立 HTML 填写页，自己用邮件发给 30 位客户 → 客户在自己浏览器填完，把答卷文件用邮件、微信等发回，`form.answers.import` 导入（同一份只算一次；答卷内容会经过这些通道，只是不经问卷平台）→ 在 Form 界面点「存成数据表」做成数据表（之后到的答卷不会自动并入），`dataset.snapshot` 存一版再清洗 → Pages 用竞品分析模板写结论 → `ppt.create` 后用 `ppt.outline`（给 `page_id`）出大纲，改讲者备注，导出 `.pptx` → 问卷、数据表、演示稿各自 `promote` 固定，挂到 Goal"团队版决策"。
- 交付物：问卷固定版、可回滚的答卷数据表、结论文稿、评审用 `.pptx`。
- 机制：M4、M7
- 成熟度：main 可用；瓶颈：新答卷不会自动并入已存的数据表；数据表最多 40 列 2000 行；PPT 不含图表，盘点里也未见 Dataset 的公式与图表，图要另做。
- 原来怎么做：问卷星/Google Forms + Excel + PowerPoint。投放和图表都成熟；卡在答案存在第三方，改过题后新旧答卷混在一起，结论页和原始数据断开。
- 不适合：要公开投放上千份、配额抽样或外网托管链接（未做，BL-045）。
- 频率/痛感：中 / 中——每季度几次；推断。

### PM-04 线上事故两小时内出复盘：截图、日志、群聊整进一份文稿，承诺拆成待办
- 触发：周一 11:20 支付回调超时 40 分钟，老板要 14:00 前看到复盘初稿。
- 链路：对助理说"接入我们的 Sentry"，助理查已有连接、选方式，停在受保护的授权链接让你本人登录，回来续办并读出错误摘要（`connectors.setup.*`）→ 把 Slack 导出的聊天记录和三张监控截图拖进右栏 Shelf，`shelf.jobs.extract` 本机提取文字，"整合多份材料"配方出时间线 → Pages 复盘模板打开，选中助理回复里的时间线，预览后"插入到光标处"（落点）→ 对"根因"一段用浮条"提反例与反驳"→ `todo.organize.extract` 从复盘里找出"你的承诺 / 在等别人的事"，与已有待办比对后采用 → `todo.items.link` 关联 Goal"支付稳定性"。
- 交付物：复盘文稿（可固定版本）、一批带出处的待办，等待他人的单列。
- 机制：M3、M4、M1
- 成熟度：main 部分；瓶颈：Sentry 等目录连接器多为只读、真实账号未逐项验；#661 整体本人验收未完；落点与浮条在本人验收前。
- 原来怎么做：Slack 搜消息 + Sentry 截图 + Google Docs 复盘模板 + Jira 建单。每样都熟练；卡在两小时里大半在复制和对时间线，复盘里的"后续行动"会后没人追。
- 不适合：已有事故管理平台自动生成时间线的团队。
- 频率/痛感：低 / 高——一个月一两次，时间压力最大；推断。

### PM-05 每条新需求走同一套处理链：判断重复、补齐信息、落进需求池
- 触发：销售、客服、老板每周往你这儿丢十几条"客户想要……"，一半重复，一半缺关键信息。
- 链路：工作流程新建：起点站 Inbox（需求由 Feed 规则或手动加入）→ "AI 整理"衔接：按保存的要求整理出"谁要、要解决什么、现在怎么绕" → "判断规则"衔接（Choice 型：新需求 / 疑似重复 / 信息不足），信息不足的这次运行被拦在这一步，原因记下 → "手动"衔接：你看完决定交不交、改几个字 → 终点站 Pages：每条需求落成一篇带来源的文档，放进"需求池"文件夹（一次交付一篇，不是往一张表追加行）；再加动作步骤 `todo.items.create`，给提需求的人建"等待他人：补数据量" → 每周一从需求池挑 5 条进 PRD。
- 交付物：一条可重复运行的流程，每个实例保留当时的链和每段交接；需求池里的需求文档。
- 机制：M5、M4
- 成熟度：main 部分；瓶颈：判断规则需 TypeSafe 连接，发布后不能改，改标准要新建并重绑；流程一次推一条，不是批量；动作步骤不能用查询类动作（BL-043），没法在流程里先查需求池去重；能当一步的只有面向流程、输入平铺的命令。
- 原来怎么做：Jira/Linear 的需求表单 + 自动化规则 + 人工分诊。表单和自动化成熟；卡在 AI 整理在 ChatGPT 里做、结果再复制回 Jira，判断标准每次看当天心情。
- 不适合：需求量大到要多人分诊、或已用 Productboard 一类专用工具。
- 频率/痛感：高 / 中——每周；推断。

**这个角色最可能的 killer**：PM-01。"AI 说做完了，Work 说约定改过、上次验收已作废、空结果提示还没你的结论"，一个画面就讲清范围变化在人和 AI 之间怎么不走样。

## UX 设计师 / 用户研究

**角色画像**：在产品团队里做交互与研究：排访谈、做可用性测试、写研究报告和设计说明。常用 Figma、Dovetail 或飞书妙记、Notion、问卷工具；用 AI 转写和归纳，又怕它把原话"总结没了"，也怕参与者的隐私外流。最在意：结论能回到原话，设计改动有依据，研发交回来时真按稿实现。

### UX-01 6 场访谈录音本机转写，每条结论都带原话出处
- 触发：一周做完 6 场 45 分钟访谈，周三要给团队讲"注册流程到底卡在哪"。
- 链路：录音逐个导入灵光，`lingguang.material.read` 本机转写，音视频不上传，每场记成一条灵光 → 你在转写稿里手动去掉姓名、公司和手机号（Shelf 的"敏感信息脱敏"配方也能做，但它会把原文发给你选的模型，确认页写明）→ 脱敏稿导入 Cognia"访谈"领域（先预览再提交，每份有版本）→ `cognia.knowledge.synthesize` 选 5 份综合成草稿，输出必须带固定来源引用；第 6 场单独 `cognia.knowledge.query` 问"谁提到了价格" → 草稿点"保存到知识库"→ Pages 用户访谈模板写报告，引用段落带出处 → `pages.promote` 固定交付版。
- 交付物：6 份带版本的转写、一份每条结论带固定引用的研究报告固定版。
- 机制：M4、M7
- 成熟度：main 部分；瓶颈：灵光转写依赖本机原生组件（未构建时报不可用）；Cognia 综合每次最多 5 份、上下文 10 万字，超了拒绝而不截断；综合与问答会把脱敏后的转写文字发给你选的模型（音频留在本机，文字不一定）；"新材料出来后复核旧结论"（旧稿 O04）未实现。
- 原来怎么做：飞书妙记/Otter 转写 + Dovetail 打标签 + Notion 写报告。Dovetail 的高亮和标签很强；卡在录音要上云、团队对第三方存敏感访谈有顾虑，引用点到 Notion 报告里就回不到 Dovetail 里的原段。
- 不适合：要多人协同打标签、做大规模亲和图的研究团队。
- 频率/痛感：中 / 高——每个研究周期；Elsevier：59% 研究者说自动引用会提高对 AI 工具的信任；LexisNexis：53% 担心保密数据泄露（法律样本，作隐私旁证）。

### UX-02 一句原话推翻了注册方案：右栏选那句话，放进说明的那一段
- 触发：评审前一晚写注册流程设计说明，回看访谈时看到一句"我只是想先看价格，为什么要先填资料"。
- 链路：中间 Pages 打开设计说明，光标停在"方案二"下；右栏 Shelf 打开那场访谈的转写 → 在右栏选中那句原话，选区条出现在侧栏里，用"插入到光标处"把原话放到左边，写入前先预览落点、确认后写入（带出处标记的"引用"落点在侧栏标签里是否可用，未核）→ 选中"方案二"整段，评论 @助理"对比价格前置和现状，各自要验证什么"，答复回到评论线程 → 选中答复里认可的一段，"替换选区"，预览后确认 → 选中"价格前置是否提升继续率"，浮条"记成待办"，带出处 → 说明固定一版交研发。
- 交付物：一段带原话引用的设计说明修订、一条待验证的待办。
- 机制：M3、M4
- 成熟度：main 部分；瓶颈：右栏插件标签里的选区进入统一情境、悬停时在左边预示落点都已在 main（#712、#720）；落点只有 Pages，本人验收未做；浮条推荐没做命中率评估。
- 原来怎么做：Dovetail 找原话 → 复制 → 粘进 Notion，ChatGPT 另开窗口分析。复制粘贴不难；卡在原话、分析、说明三处来回定位，粘过去的引用丢了出处。
- 不适合：说明主要是 Figma 里的标注、文字不多的团队。
- 频率/痛感：高 / 中——写说明时天天遇到，每次几分钟；Figma 2026 报告设计师参与开发从 21% 升到 41%，UserTesting 称仅 15% 设计师对 AI 产出质量明显更有信心（二手）。

### UX-03 下周约 6 位重度用户：筛选问卷、名单、日程、访谈提纲一条线
- 触发：周四、周五要排满 6 场访谈；客户成功同事只肯帮你转发一封邮件。
- 链路：Forms `questions.draft` 写"筛选每周导出 3 次以上的用户"，它先追问"排除哪些行业"再出 5 道题 → `form.fillpage` 导出填写页，交同事邮件转发，回来的答卷文件 `form.answers.import` → 在 Form 界面点「存成数据表」，加一列"是否邀请"手工勾 → 选中的 6 人在 Jelly 日历各建一个事项，附一条笔记 → 在笔记里选中提纲草稿，`jelly.plan.generate` 拆出"会前一天发确认、准备原型链接"等待采纳任务，采纳后排进日历（`jelly.task.schedule`）→ 每场一份 Pages 用户访谈模板，`goals.inputs.bind` 挂到 Goal"注册流程研究"的资料。
- 交付物：筛选答卷数据表、6 个日历事项与笔记、6 份待填访谈稿。
- 机制：M4、M3
- 成熟度：main 可用；瓶颈：新答卷不会自动并入已存的数据表，答卷文件靠对方转发的邮件等发回；Jelly 不发会议邀请，邀请仍走你的邮箱和日历；拆计划需模型。
- 原来怎么做：Google Forms + Sheets + Calendly + Google Calendar。Calendly 约时间比这里顺；卡在筛选结果、日程、提纲分在四处，访谈当天找提纲要翻邮件。
- 不适合：已用招募平台、要付参与激励的研究。
- 频率/痛感：中 / 中——每个研究周期一次；推断。

### UX-04 竞品新版注册流程：侧栏浏览器里让助理走一遍，步骤和截图进竞品分析
- 触发：竞品昨天改了注册流程，产品负责人问"他们现在要几步"。
- 链路：右栏浏览器打开竞品注册页（登录状态和你自己的浏览器分开）→ 给这个网站开"助理可操作"权限，"把这一页交给助理" → 助理按"用测试邮箱走到首页为止，每步记字段"操作，画面实时可见，要提交表单时弹确认，遇到验证码由你接手 → 走查记录和截图放进 Shelf 提取文字 → Pages 竞品分析模板，选中助理整理的步骤表"插入到光标处" → `pages.ai`"比较异同"把我们的流程与竞品对照 → 固定一版，记为 Goal"注册改版"的输入。
- 交付物：一份带截图与步骤的竞品走查文稿固定版。
- 机制：M3、M4、M7
- 成熟度：main 部分；瓶颈：侧栏浏览器"待更多代表性实操"，真实网站登录（BL-017）待验；按网站设"允许 / 禁止 / 每次问"，没有"付款不碰"规则，只在截图里遮住信用卡字段。
- 原来怎么做：自己录屏 + 截图拼进 Figma 画板 + Notion 记步骤。录屏最真实；卡在每次改版都要重走一遍，截图和文字分家。
- 不适合：要走查 iOS/Android 原生应用——侧栏只是网页，Computer Use 也不宣传任意 App 自动化。
- 频率/痛感：中 / 低——每月一两次；推断。

### UX-05 研发说"按稿做好了"：设计验收由你点头才算完成
- 触发：开发同事的 Agent 在 Goal 里报告"注册页改版完成，测试通过"；周五要上线。
- 链路：Goal"注册改版"的当前约定里，"390px 宽键盘不遮挡按钮""错误提示文案与稿一致"早就设为必须本人验收 → 打开 Goal 时间线，看 Agent 用 `goals.events.report` 报的事实和附的 Coding 固定报告 → 在右栏浏览器打开预发环境，逐条看；第二条不对，`goals.note` 记"问题与风险"附截图 → Agent 提 `goals.decisions.request`"文案差异能否下版改"，你在目标页的决定表单看各选项的影响，选"本版必须改" → 改完再看，给出本人结论 → `goals.closure.submit` 通过；之后约定若再改，这次结论自动失效。
- 交付物：Goal 上两条带本人结论的要求、一条决定记录、一次显式收尾。
- 机制：M2、M1
- 成熟度：main 部分；瓶颈：侧栏浏览器待更多实操；完成确认的身份规则已在 main 但待用户验收；结论不绑定构建号，预发版本由人注明；只标了"必须本人验收"的要求不会点亮菜单栏，要 Agent 发起验收请求才会。
- 原来怎么做：Figma 评论 + Jira 设计验收子任务 + 群里截图。Figma 标注很成熟；卡在"测试通过"一来，验收子任务就被顺手关掉，没人对着最新约定核。
- 不适合：有专职 QA 和视觉回归测试流程的团队。
- 频率/痛感：高 / 中——每次上线；微软 2026：50% 把"对 AI 产出做质量把关"列为最重要的人类技能。

**这个角色最可能的 killer**：UX-01。本机转写、固定版本引用、报告固定版连在一条链上，回答"原话在哪"和"录音去哪了"两个研究员最常被追问的问题；但要讲准：音频留在本机，综合时脱敏后的转写文字会发给你选的模型。

## PMO 项目经理 / 交付协调

**角色画像**：同时管 3–8 条交付线（内部项目或客户项目），每天在会议、周报、风险和"谁在等谁"之间来回。常用 Jira/Asana/飞书项目、Excel 风险表、会议纪要工具、邮件和群聊；AI 主要用在纪要和周报。最在意：答应的事有人追，风险早暴露，周报的数字对得上。

### PMO-01 周会纪要一出来：你的承诺、在等别人的事，各进各的待办和日历
- 触发：周二 15:00 跨部门周会，纪要 2000 字，藏着 8 件事：有你答应的，有在等法务的，也有上周已经记过的。

### SALES-02 方案发出后客户追加"老数据也导进来"：先问清，再决定进不进本期
- 触发：周三方案评审后客户来信："试用时能不能顺便把老数据也导进来？"
- 链路：Gmail 来源把信拉进 Feed（只带主题和摘要片段，要引用客户原话就把正文贴进来），加入 Inbox，把这条消息绑为 Goal"星河试点交付"的资料（`goals.inputs.bind`）→ 在方案 Pages 的"交付范围"一节选中相关句子，浮条"记成待办"，类型"等待他人：确认数据量、格式、时间"，带来源 → 客户回信后，你或助理提一个决定"导入纳入本期 / 另行报价"，目标页的决定表单列出各选项的影响 → 你记决定，当前约定随之更新 → 方案改完 `pages.promote` 出 v2，v1 与 v2 分别打开对看（`pages.artifacts.compare` 只判断固定版与原文当前是否一致，不对比两个固定版）→ 你自己发给客户。
- 交付物：方案 v2 固定版、一条带依据的范围决定、关掉的等待项。
- 机制：M2、M4、M3
- 成熟度：main 部分；瓶颈：Gmail 真实账号未验且只带主题和摘要片段；浮条推荐的真实 Jev 评估未做；Work 不发邮件、不替客户确认。
- 原来怎么做：邮件 + Google Docs 方案 + CRM 备注。改方案很快；卡在"可以看看"在邮件里一来二去成了默认承诺，交付时才发现没人记得是否纳入。
- 不适合：有正式报价配置与合同变更流程的大单。
- 频率/痛感：中 / 高——每个项目几次，误承诺直接伤利润；推断。

### SALES-03 季度业务回顾（QBR）：用量数据、工单和成功计划拼成一份演示稿
- 触发：下周给前 5 大客户各做一次 QBR，每份要讲用量趋势、问题和下季度计划。
- 链路：Goals 给每个客户一棵"成功计划"目标，参考规划方法库的客户成功与服务领域、企业 SaaS 行业 → 后台导出用量 CSV 和工单 CSV，`dataset.import` 各成一表并 `snapshot` → Pages 复盘模板写回顾，`pages.ai`"要点"压摘要，"读者视角"按客户高管视角挑问题 → `ppt.create` 后用 `ppt.outline`（给 `page_id`）出大纲，调到 8 页，改讲者备注，导出 `.pptx` → 演示稿和数据表固定，记为该客户 Goal 的交付物 → 下季度打开上季固定版，对照承诺是否兑现。
- 交付物：每个客户一份固定版 QBR 演示稿、数据表快照、更新后的成功计划。
- 机制：M4、M1、M2
- 成熟度：main 可用；瓶颈：PPT 不含图表，趋势图要在别处做再贴；数据表 2000 行上限；工单系统不在连接器目录里，靠导 CSV。
- 原来怎么做：Gainsight 或表格 + BI 截图 + PPT 模板。图表工具强得多；卡在每季从零拼，上季答应的事兑现没有要翻旧 PPT。
- 不适合：已有客户成功平台自动生成 QBR 的团队。
- 频率/痛感：中 / 中——每季度；研究未找到客户成功的独立数据，推断。

### SALES-04 客户发来第二版报价清单：型号、数量、折扣按批准目录核一遍，AI 也按同一套规则
- 触发：客户周三发来第二版报价单 PDF，60 行，改了 11 处型号和数量；折扣上限按区域不同。
- 链路：PDF 拖进 Shelf，本机提取文字，"提取结构化信息·全量 JSON"配方出逐行数据 → 插件创作台做"报价核对台"：批准目录和折扣上限作为带来源、版本的只读快照，逐行核对，缺信息的列为"待确认" → 装好后你在界面里用；也可以对助理说"核一下这份"，助理调同一个插件动作 → 不确定的 4 行记成"等待他人"待办 → 核完由插件经安装时的授权调 `pages.create` 出一份核对说明 → 说明固定一版交内部审批。
- 交付物：一个报价核对插件和每次核对记录、一份核对说明固定版。
- 机制：M5、M4、M1
- 成熟度：main 部分；瓶颈：业务样例未做；创作台预览阶段对外写入是替身，装好后才真写 Pages；PDF 抽取质量看原件；不做正式报价、ERP 写回和自动发送。
- 原来怎么做：Excel VLOOKUP + 人工核 + 让 ChatGPT 比两版。Excel 核对已经可靠；卡在规则一半在公式、一半在聊天提示词，换人或换 AI 就走样。
- 不适合：一张表加两个公式就够的。
- 频率/痛感：中 / 高——每个商机几轮，错一处折扣就是钱；对应旧稿 O02，尚无业务样例。

### SALES-05 每天早上的跟进清单：哪些客户该回、哪些承诺快到期
- 触发：周一 8:30，周末进来 37 封客户邮件，上周答应的 4 件事分散在三个客户那里。
- 链路：规划：主动助理按"阻塞跟进"场景 Skill 读 Feed（Gmail）、Inbox、等待他人的待办和各客户 Goal 的事件，没有实质变化就保持安静 → 工作简报生成"今日跟进"状态页：每项带依据（哪封信、哪条待办），取不到的标过期 → 首页"需你处理"里每条可点开到原对象 → 你点"起草回复"，助理在 Pages 写草稿，发信仍由你在邮箱里做 → 你说"以后报价类邮件排前面"，助理记为候选偏好，你认可才生效。今天的手工版：Inbox + 待办"等待他人"视图和跟进日提醒（首页显示）；Schedule 的对话任务读不到这些。Gmail 来源只带主题和摘要片段，主动助理读到的也只有这些。
- 交付物：每天一页带依据的跟进清单。
- 机制：M6、M1、M4
- 成熟度：规划；瓶颈：主动助理与工作简报都只有需求书；后台运行受 Work 是否开着限制，不承诺电脑关闭后仍执行（BL-030）。
- 原来怎么做：CRM 任务队列 + Gmail 星标 + 晨间翻邮件。CRM 任务队列已能提醒；卡在客户在邮件里新提的事不在 CRM 任务里，要自己读一遍才知道。
- 不适合：客户不到 10 个、邮件不多的人。
- 频率/痛感：高 / 中——每天；ChatGPT Pulse、Tana 都在做每日简报（外部补研 U2），差异只能是"每条能回到原信和待办"。

### SALES-06 40 题安全问卷：从历史答案拼初稿，每条带出处版本，敏感题本人验收
- 触发：大客户采购发来 40 题安全问卷（Excel），周五截止；类似问题去年答过 3 次，答案散在不同文件里。
- 链路：把历年问卷答案和安全白皮书目录导入 Cognia"安全问答"领域（预览后提交，保留版本）→ 问卷另存 CSV，`dataset.import` 成一题一行 → 对助理说"逐题起草"：助理把 40 题分 4 组委托为子任务，每组用 `cognia.knowledge.query` 找依据，答案必须带固定来源引用；子任务回来后助理对照"每题都有引用"的验收标准核对再汇总 → 草稿进 Pages；加密、数据驻留类 8 题在 Goal 里设为必须本人（安全负责人）验收 → 助理报告找不到依据的 5 题，评论 @助理"列出需要找谁确认" → 本人结论齐了再固定、导出。
- 交付物：一份每题带出处版本的问卷答案固定版，8 题的本人验收记录。
- 机制：M4、M2、M1
- 成熟度：main 部分；瓶颈：子任务委托只有一层；Cognia 每问最多 5 份资料；导出回 Excel 格式要人手；安全负责人进不了 Work，由你代记他的结论（团队协作未做）。
- 原来怎么做：Loopio/Responsive 答案库，或共享盘 + ChatGPT。专业问卷工具的答案库很成熟；卡在小团队没有答案库，每次从旧文件里抄，答案是否仍成立没人核。
- 不适合：已用专业问卷工具且答案库维护良好的团队。
- 频率/痛感：中 / 高——大单必遇；Stack Overflow：78.7% 认为来源标注重要（开发者样本旁证）；Elsevier：59%。

**这个角色最可能的 killer**：SALES-06。"AI 起草了 40 题，助理报告其中 5 题找不到依据、系统记着 8 题还没有本人结论"，正是销售最怕的"答错一题丢一单"，而小团队没有专业答案库；已有 Loopio、Responsive 这类答案库的团队不是目标。

## B 组共性与 killer 候选

### 反复出现的四个模式

1. **决定和范围要留下依据，改了要能让旧结论作废。** 炼金术士的双视角决定（FND-01）、Goals 的当前约定 + 本人验收 + 决定表单（PM-01、UX-05、PMO-05、SALES-02、SALES-06、MKT-04）、规划方法的影响子图（FND-04）。这 6 个角色都在为"AI 说做完了 / 说可以 / 说市场大"和"谁拍板、凭什么"之间的落差付钱。对应 M2，是我们读到的竞品官方页面里没做成一等对象的那一维；但跨厂商的中枢已经有（Linear 委派、Conductor 并行跑几家 Agent），Claude `/goal`、Codex Goals 又只看会话内容，所以 Work 能讲的差别只限目标级的要求、本人验收，并绑定到约定版本。
2. **材料到成稿，出处跟着走，追问时找得回当时那一版。** Inbox→Pages 的材料快照（PM-02、OPS-01、MKT-02；Gmail 来源只带主题和摘要片段，要原话得把正文贴进来）、Cognia 固定引用（UX-01、MKT-04、SALES-06）、成果固定版与"原文已改"提示（FND-03、OPS-02、SALES-03、MKT-01）。"能引用"已是各家标配，B 组真正用到的是"固定到当时的版本 + 挂在目标下"。对应 M4。
3. **从一段材料里抽出承诺、等别人的事和下一步，落到待办、日历和目标上。** `todo.organize.extract`（PMO-01、PM-04、OPS-02）、Jelly 拆计划与排期（UX-03、OPS-05、MKT-05）、浮条"记成待办"（UX-02、SALES-02）。与已有待办比对、"等待他人"单列、日期不让模型算，是熟练工具组合里最常缺的一步。对应 M3 + M1。
4. **重复的处理链自己固化，人和 AI 用同一套规则。** Feed 捕捉规则 + 判断规则、工作流程四种衔接与动作步骤、插件创作台生成的小工具、从 Claude Code 导入的角色（FND-05、PM-05、PMO-05、OPS-03、SALES-04、MKT-03）。共同瓶颈也在这里：判断规则依赖 TypeSafe，创作台还没有一个做完的业务样例，生成插件进不了搜索和成果库。对应 M5。

另一条横向观察：B 组 40 条里有 25 条卡在"main 部分"，最常见的三个瓶颈是 **Gmail 等真实账号 OAuth 未验**、**判断规则需要 TypeSafe 连接**、**创作台业务样例未做**；这三件补齐后，FND-03、FND-05、PM-02、PM-05、PMO-05、OPS-03、SALES-04 的主要瓶颈就会消失（其余限制仍在，是否升到 main 可用要逐条再核）；其中用到 Gmail 的几条还有一个补不掉的限制：Gmail 来源只取主题和摘要片段，要整理长邮件，得把正文贴进 Pages 或交给助理。主动助理与工作简报（SALES-05、PMO-02 的升级版、SALES-01 的后半段）是这一组"打开就有东西"的关键，目前都是规划。

### 最可能成为 killer 的 3 条

按 [killer 场景 §2](../killer场景.md#2-怎么挑的) 的总分（2P + 2F + T + D + B + S，满分 40）粗评，再用该节的淘汰条件过一遍（成熟度不进总分，只决定放哪）：

| 编号 | 标题 | 粗评 | 成熟度 / 放哪 | 一句话理由 |
| --- | --- | --- | --- | --- |
| **PMO-01** | 周会纪要一出来：你的承诺、在等别人的事，各进各的待办和日历 | P5 F3 T5 D4 B5 S2 = 32 | main 可用（需模型）/ 现在主推 | 换个对象（纪要、复盘、客户邮件）六个角色都在用，不搬旧资料，下一次会议就能开始；"AI 抽了 8 条，整理结果标出 3 条可能重复、1 条在等法务"是一眼可懂的反差。 |
| **PM-01** | 评审改了范围：PRD、Goal 约定和开发 Agent 读的是同一份现行要求 | P4 F5 T3 D5 B4 S2 = 32 | main 可用 / 现在主推（需先接 MCP） | 把"约定一改、旧验收作废、没你点头不算完成"演成一个画面，是 B 组最独有的机制，也是产品、设计、销售、交付共用的交接点。 |
| **FND-01** | 两个方向这周只能验一个：市场和成本都查齐了，才记下 Build 或 Hold | P3 F4 T4 D5 B2 S3 = 28 | main 可用（需模型）/ 现在主推（按最弱一环；炼金术士包整体仍标 partial，对外先找几位创始人试） | 创始人是最可能先试用的人群；"预算内双视角研究 + 两边齐了才许记决定"我们没找到现成工具把它连成一条，演示反转最强。 |
