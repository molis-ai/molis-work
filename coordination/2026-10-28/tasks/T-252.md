## 1. 背景

来源：T-228 二审（#1499 评论 6504032319）的建议。`plugins/native/pages/src/actions.ts:301`（`pages.generate` 的处理函数）：

```ts
if (input.inputs.reduce((sum, item) => sum + item.body.length, 0) > 100_000) throw pagesErrors.invalid("材料过长，请减少所选条目");
```

`item.body.length` 是 UTF-16 单元数，所以含 emoji 等两单元字的材料，只要总共不超过 50,000 个这样的字就够 100,000 个单元，再多就被拒，而信息写的是“材料过长”。这条是整个动作唯一的材料总长检查：`snapshot` 的 `body` 在动作 schema 里只是 `text = { type: "string" }`（`actions.ts:26`、`:44`），没有 `maxLength`；`inputs` 最多 20 条（`:136`）。T-228 刚把生成文稿**输出**的上限改成按字数，输入一侧是同一类问题。

## 2. 目标

1. 总长上限按字数数：所选材料的正文合计不超过 100,000 个字就收下，超过就拒，信息不变。
2. 不展开整段材料：先看单元数，超过 200,000 个单元的一定已经超过 100,000 个字；只有不超过时才按字数数。
3. 有用例：一个 😀×60,000 的材料（120,000 个单元、60,000 个字）被收下；总共 100,001 个字被拒。

## 3. 不做

- 不改材料条数上限（20）、不改 `snapshot` 的 schema、不改信息文字。
- 不加兼容或迁移逻辑。

## 4. 范围

`plugins/native/pages/src/actions.ts`（只 `:301` 那一行，必要时在文件里加一个小函数）、对应测试（现有的 pages 动作测试文件，或新文件；`git grep -ln "pages.generate\|pagesActions.generate" -- tests` 找一个最近的）。

锁定：无（2026-10-29 核：没有在途 PR 和 `task/*` 分支改着这个文件）。

## 5. 做法

先在当时的 main 上核第 1 节的行。把检查改成（形状，名字自定）：

```ts
const units = input.inputs.reduce((sum, item) => sum + item.body.length, 0);
// 一个字最多两个单元：超过 200,000 个单元一定超过 100,000 个字，不必展开。
if (units > 200_000 || (units > 100_000 && input.inputs.reduce((sum, item) => sum + [...item.body].length, 0) > 100_000)) throw pagesErrors.invalid("材料过长，请减少所选条目");
```

注意：单元数不超过 100,000 的一定不超过 100,000 个字，所以只在 100,000 < 单元数 ≤ 200,000 时才展开去数。

再查两件事并写进【方案】：① 材料之后会进模型提示（`generate.ts` 里拼 prompt），提示的总长有没有自己的检查（`apps/local-host/src/host-complete-text.ts` 的 `PROMPT_MAX_CHARS`，T-185 起按字数），100,000 个字的材料加指令、固定部分会不会超；会超就停下来问；② 材料的来路（Inbox 条目快照）有没有自己的上限，是不是已经按单元或字数截过。

## 6. 验收

- `RAC-2280`：一个 😀×60,000 的材料（120,000 个单元）被收下，不报“材料过长”。
- `RAC-2281`：材料合计 100,001 个字被拒；合计 100,000 个字被收下。
- `RAC-2282`：超过 200,000 个单元的材料被拒，且没有把整段展开成数组（可用一个超大字符串加计时或检查调用次数，也可只在【方案】里论证）。
- 余下号备用。
