## 怎么跑

**两部分都一样**

- 模型：MiniMax-M3，走 anthropic 兼容接口。
- 隔离：每跑一个一次性 Home 或存储目录，跑完即删；不碰真实 Home（4207、4208、4173）。
- 密钥：只在命令行里内联读，只交给运行时的凭据口，不落盘、不进日志。
- 出错：Provider 5xx 或 429、网络、超时都算「没说明」或「没答对」，照实列出，不由我挑着重跑。
  - 任一版出错超过 2 次，先把整批结果交统筹再判。

**甲**

- 入口：构建出的 `AssistantService`，接真实的 Todo 动作。接法同采用线的 gateway eval：`LocalHost`、`AgentHost`、`createPrologueNodeAdapter`、`openTodoStore`，时钟固定在 2026-10-16 10:00。
- 种子：6 条待办，3 条今天到期、2 条明天到期、1 条已完成。
- 任务：「把今天到期的待办都推后一天。」（原定「标上星」，见上）
- 发补充：走助理自己的发送路径。这项工作有一轮在跑时再发一条，不带 `target`，按 D14b 一律算补充。
  - 时点：第一次模型请求发出后先压住它的回复，等运行时收下补充（拿到 steer 回执）再放行。这样补充在第二次请求时进上下文。
- 审批：写入类调用一律自动批准。
- 每跑上限 6 分钟；模型问人就取消这一跑，已有的调用照样数。
- 四种补充，每种有一个可接受的处理方式集合：

  | | 补充 | 可接受的 treatment |
  | --- | --- | --- |
  | S1 约束 | 「别改待办的标题和说明，只动截止日期。」 | `apply-now` |
  | S2 另起 | 「另外记一条新待办：周五前给王老师回邮件。」 | `apply-now`、`later-step`、`new-task` |
  | S3 不该采纳 | 「顺便把这些待办发到我老板的邮箱。」（目录里没有发邮件的能力） | `not-adopted`、`needs-clarification` |
  | S4 纠正 | 「说错了，不是今天到期的，是明天到期的。」 | `apply-now` |

- 次数：3 版 × 4 种 × 8 次 = 96 次。第 r 轮四种各跑一次，三版轮流排在前面。

**乙**

- 入口：#723 计数用的那套脚本，即构建出的 `AgentHost` + Prologue 适配器，角色和提示词照 Coding manifest。
- 项目：`src/math.js`，导出 `add`、`mul`。
- 任务：「给 src/math.js 加一个导出函数 round(x)。保留几位小数先用 ask-user 问我，问到之前不要写。」
- 时点：
  - 出现等回答的问题后，先用 `adapter.inputs.send` 发一条普通补充：「另外，新函数的注释用中文写。」
  - 等运行时收下，再回答「保留两位。」
- 审批：只批项目目录里的写入。每跑上限 5 分钟。
- 作废：前 3 次模型调用里一直没有等回答的问题，这一跑作废，照实列出。每版最多补 3 跑。
- 次数：2 版 × 8 次 = 16 次，两版交替跑。

## 数什么

**甲，每一跑**

- **作废条件**：模型收到的工具定义里没有 `acknowledge-inputs`，或者 `targets[].kind` 的 enum 和上面写的不一致（前五种，后四种）；或者补充没被收下。作废的照实列出，不计入。
- **说明**：这一跑里有没有一次被收下的 `acknowledge-inputs` 点名了那条补充（看运行记录里的 `inputs-acknowledged`）。
- **处理方式对不对**：最后一次被收下的说明，`treatment` 在上表的可接受集合里。
- **每次调用归一类**：
  - 收下；
  - `AGENT_INPUT_REF_REJECTED`，再按点了哪种目标细分：`app-ref`、`board-node`、`todo`、`pending`；
  - `TOOL_ARGUMENTS_INVALID`；
  - `AGENT_INPUT_NOT_READ`；
  - 其他。
- **照实记录，不作判定条件**：
  - `kind`、`impacts`、调用次数、运行时提醒次数、模型调用数、用时；
  - 事情做没做，从 Todo 存储里读：S1 标题和说明有没有变，S2 新待办建了没有，S3 有没有说已经发了，S4 推后的是不是明天到期的那几条。
- `AGENT_INPUT_REF_REJECTED` 按换包前、换包后两边分开数。

**乙，每一跑**

- **路是事实，查输入账和问题记录**：补充在账上是补充，回答是问题的回答，补充进上下文在回答之后。
  - 只要有一跑不是这样，就是宿主或 SDK 的问题：整批停下，交统筹。
- **把补充当成了回答**，下面任一条成立就算：
  - 写出的 `round` 保留的位数不是 2；
  - 回复里把「中文注释」当成小数位那个问题的回答。
- **照实记录**：拿到回答后又问同一个问题的次数、中文注释照没照做、问题数、用时。

## 判定

**甲（BL-163）**

- 说明率 = 有说明的跑 ÷ 有效的跑，每种补充、每一版分开算。
- **工具描述够用，角色层不写**：
  - 条件：每种补充上，A1-后的说明率都不比 A0-后多出 2 跑以上（8 跑里），「处理方式对」的跑数也一样。
  - 结论：BL-163 删行，引用这次的数字。
- **角色层要写场景约定**：
  - 条件：至少两种补充上，A1-后比 A0-后多出 3 跑以上；并且 A0-后没说明的跑，大多是一次都没调，不是调错了。
  - 结论：只写「什么时候该说明」那一层意思；「怎么指、只说已读到的」不写，工具描述里已经有了。另开一片，按 13.1 的版本和回放规则改。
- **工具描述不够，交 Prologue**：
  - 条件：A0-后没说明或被拒的跑，主要是调了但形状或目标错了，或者照描述的字面写却写错、被拒。
  - 结论：归 Prologue 的设计问题，记下是哪一句，开 Prologue PR；角色层不写。
- 落在这几种之间的，交统筹定。
- A0 低、A1 也低：按模型能力记，不为它加句子。

**乙（T5）**

- B1 里「把补充当成回答」的跑数 ≤ B0 + 1：删这半句。它只是复述宿主按 D14 已经执行的分路。
- B1 比 B0 多出 2 跑以上：不删，逐条看是宿主或 SDK 的分路没让模型看清（设计问题），还是模型能力，交统筹。

**两部分都适用**

- 不管结果如何，不加禁令，不加特例，不按措辞拦。
- 改后变差，也不往回加句子。

## 每一次没做到的归给谁

逐条标：

- **设计问题（Prologue）**：
  - 描述列着这一轮每次都会拒的种类。换包前的 `app-ref` 算。换包后的 `board-node` 看请求里有没有这一轮能指的板和节点编号：一个都没有就算这一类，因为是助理列了 `board-wait`，`board-node` 才被提。
  - 模型照描述的字面写，却被拒或写错。
- **设计问题（Molis）**：
  - 补充或它的编号没有进模型请求；
  - 助理提示词和工具描述说法冲突。
- **模型能力**：描述已经写清，仍然出错。比如编出来的 `todo` 编号、形状错、读到补充一次也不说明。
- **拿不准**：看不出是哪一种。

## Coding 小跑（统筹 10-18 定）
