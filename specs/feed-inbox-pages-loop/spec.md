# 研究信息从 Feed 到 Pages 的真实闭环

状态：本地实现与指定真实路径已实操；工程记录、实操范围与未验证项见 [验证记录](validation.md)。用户尚未验收。基线 `f25ea17`，分支 `codex/feed-inbox-pages-loop`。

## 用户任务与授权

承接设计共识 5.2：用户要求从 `molis-ai/research-library` 选一个真实来源，收集、按规则筛选、进入 Inbox、形成可继续使用的 Pages 文稿，并调通助手配置与调用。首个来源选 `twitter-ai-observation`；读取已发布的研究成果，不接管上游研究任务。用户已同意上一轮五步推进方案。本地实现、配置和实操属于本次范围；不提交、推送或发布版本，不修改研究库。

## 最小完整方案与职责

- GitHub integration 读取固定提交上的 sources/catalog/manifest/research，校验发布哈希；Feed 持有来源、条目及同步历史。每条研究发现保留原文、证据、限制、包版本与修订关系。
- 沿用 Sources 的计划、Listener 的同步收据、Feed 的去重；为仓库来源补适配，不建采集平台。
- Functions 继续仅判断；来源规则显式选择仅建议或自动入箱。旧规则默认仅建议，不改变其 Artifact 捕捉语义。失败与待复核不会伪装为筛选通过。
- Inbox 保持 Attention 引用。用户选择材料及写作要求，由 Host 读取 Feed、调用真实模型、通过 Pages 的公开能力写文稿。文稿和输入快照由 Pages 保存；生成成功不自动标记 Inbox 已处理。
- 同一个写作请求有稳定回执，重复请求返回原文稿；失败可重试，项目隔离；不能覆写用户修改。
- Pages 复用现有编辑、保存、打开路径；正文附来源，模型输出与原材料区分，保留 BOUNDED/RESEARCH_ONLY/DEFER 与阅读范围。
- Workbench 助手通过同一套公开 HTTP 动作查询来源、编辑并试跑规则、配置绑定、读取材料和生成文稿。只支持规则方案和写作方案两种有类型的动作；显式按钮才执行。复用已有凭据与插件用例，不建立第二套业务状态；没有新增外部 MCP 或通用 Agent 编排。

当前必须：来源接入、规则执行设置、选择与写作动作、真实模型、助手接线、失败恢复和来源追踪。延后：通用编排器、SOP 市场、批量规则导入、团队权限同步、全产品视觉改造。重复需求出现后再评估。

## 依赖顺序

1. 固定真实研究包及使用边界，接收来源并验证重复同步。
2. Inbox 选择真实材料，生成 Pages 文稿、回读及编辑保存。
3. Functions 真实试跑与来源规则自动入箱，保留人工方式。
4. 助手配置、调用和可见结果；工具与界面共用用例。
5. 验证错误、重试、切项目、返回和重启后继续，同步规格与证据。

## 验收与回滚

- 工程：适用包构建、类型与边界检查；真实来源解析、哈希失败、幂等、隔离、模型失败、旧规则兼容的定向测试。
- 产品实操：最终构建在持久的隔离 Home 中使用真实研究数据、真实 Functions/生成模型；浏览器走收集、筛选、入箱、生成、编辑、返回、重试及恢复。保留可供用户继续使用的入口。
- 用户验收：中文输入法候选、主观手感和文稿质量由用户确认，未确认前标为 UNVERIFIED。
- 数据采用增量兼容字段，旧规则默认行为不变；停用新增来源与规则即可停止后续采集。回退代码保留已生成文稿与原有数据，不删除或覆盖用户成果。

## 创建、复用与修改规则

助手起草 Functions 草稿，真实样本试跑后由用户启用。人工可到 Functions 修改尚未发布的草稿，再试跑与发布。已有发布函数可在任一来源的「任务配置 → 捕捉规则 → 判断」下拉框复用；每条来源规则单独选择仅建议或自动入箱。

沿用已有发布不可变语义：已发布函数不能就地改写，修改判断时创建新草稿并发布，再在来源中停用旧规则、绑定新函数。没有引入函数版本升级或分享 SOP 系统。已有消息不会因绑定规则悄悄重跑；需要明确点击「对最近 20 条消息运行当前规则」。
