# 银行与支付

围绕资金流、账本、授权、清结算、争议和持续可用性建立可信交易闭环。

适用于：支付产品、银行服务、资金基础设施。

## 规划路径

1. 明确参与方、资金来源去向、产品承诺和市场边界
2. 映射授权、记账、清算、结算、退款与争议生命周期
3. 固定账本、余额、幂等、对账和最终性契约
4. 补齐身份、权限、风控、合规、审计和人工运营
5. 用异常交易、失败恢复、资金对账和高峰容量验证

## 必须覆盖

| area | label | question |
| --- | --- | --- |
| payment_participants | 参与方与资金流 | 谁付款、收款、持有、路由或担保，资金在哪些节点改变责任？ |
| transaction_lifecycle | 交易生命周期 | 授权、记账、清结算、退款和争议经过哪些可追溯状态？ |
| ledger_reconciliation | 账本与对账 | 哪个账本是权威余额，重复、延迟和差异如何发现并修复？ |
| identity_risk_controls | 身份与风险 | 身份、权限、限额、欺诈和合规判断在哪发生？ |
| disputes_exceptions | 争议与异常 | 拒付、退款、超时、部分成功和人工调整如何处理？ |
| resilience_audit | 连续性与审计 | 高峰、依赖故障和恢复时如何保持资金与审计一致？ |

## 完成证据

- 资金流、账本与交易状态契约
- 成功、重复、超时、退款和争议的对账记录
- 权限、风险、审计和恢复演练

## 收口检查

- 每一笔金额都能追溯到权威记录和责任方
- 重试不会重复记账或静默丢失交易
- 已按目标市场另行确认牌照与监管要求

## 常见误拆

- 只按接口成功判断支付成功
- 混淆订单、支付意图、账本分录和结算
- 把人工对账当成长期架构

## 怎样用这份方法

- 先按「规划路径」把事情想完整，再把每个能独立交付、独立验收的结果列成一项；一项里不混入几个主要结果。
- 「必须覆盖」里与当前任务有关的每个问题都要有答案；答不上来的关键问题列为待确认，不用含糊的条目盖过去。
- 依赖只表示结果消费：乙开始或完成时必须用到甲的可验收产出，乙才依赖甲。讨论顺序、时间先后、同一个人负责、改同一份文件都不算依赖；没有结果消费关系的保持并行。逐条判断「依赖规则」，不适用的要说得出缺了哪一种产出消费。
- 每一项写明完成时拿什么证明（见「完成证据」），收尾前过一遍「收口检查」。
- 只描述有限、能完成的改变；持续运行的事不写成永远做不完的一项。
- 和别的规划方法一起用时，把各自的关键结果放在一起看谁消费谁，缺了提供方的再补上相应的方法。
- 拆出来的结果先给用户看。用户要落到某个工具里（例如已装的 Goals 插件）时，用那个工具自己的动作写入，由用户确认。
