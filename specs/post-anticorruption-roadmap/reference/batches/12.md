## 给人讲清楚

一件真实的工作从「放进资料」到「交给 Coding 去做」再到「看到结果」，现在中间有好几处断开：Coding 的计划卡和任务板编号对不上，命令没有给出退出码也会显示成功，材料放进项目后接不到 Coding。这一批把这条基本路径从头到尾打通，并把这些明显的错修掉。做完你可以拿一份真实材料，一路交给 Coding 做完、看到可靠的进度和结果。需要你做的：看一下目录、规则和出错恢复这几处的界面样子并定下。

## 交付与前置

- **阶段／类型**：1；产品线（引导、Coding）；体验与效果
- **需求来源**：[Harness A／R7][CHO]、[Onboarding §3.14][ONB]、[治理 PF-A01／02／09][PFG]
- **前置／待决**：04、06、07、09、11
- **可并行项**：13 的服务资格与当前接入能力核查
- **UI 要求**：先定样：目录／规则／恢复；复用 03、04

| 交付项 | 做什么、产出什么 | 该项前置 |
| --- | --- | --- |
| <a id="batch-12-item-1"></a>Coding 执行、委派与可见状态 | Coding 目录执行、委派、规则／模式、渲染、计划／TaskBoard 与命令状态。TaskBoard／计划卡编号与状态一致（BL-161、BL-164）；无退出码的命令不能显示成功（BL-222）。 | 共用本批前置 |

```text
你在 Molis Work 仓库里推进路线书第 12 批「基础工作路径贯通」。完成程度按本批每项交付写的来（定样、合同、实现或验收），不停在方案、原型或几个样例，也不自行降级。PR 按第七节的粒度开，交统筹审和合并。

一、先读
- 本批文件：specs/post-anticorruption-roadmap/reference/batches/12.md。交付、前置、可并行项和界面要求都以它为准；它和这段 prompt 对不上时以它为准，并顺手改正这段。

- 原需求（行为与验收以它们为准）：specs/coding-harness-optimization/spec.md；specs/onboarding-coverage/spec.md；specs/product-flow-governance/spec.md

二、开工前先跟我讲清楚（大白话）
先核对现状：main 上已经有什么、前置批次是否真的合入、有没有在途 PR 在做同样的事。然后用大白话跟我讲：这批做什么、要解决什么问题、做完我能看到或用到什么、为什么排在这里、需要我做什么。不用包名、合同、schema、编号这类词，非用不可时顺带解释一句。本批文件「给人讲清楚」一节是底稿，按核对结果改。讲完就继续做，不用等我回话。

三、本批交付
1. Coding 执行、委派与可见状态（本批文件 #batch-12-item-1）
2. 材料进入项目与 Coding 接续（本批文件 #batch-12-item-2）
每片开工前先在认领板（GitHub issue #1743）认领，再按需求开发流程第 2.1 节说明这一片，再在原需求里答第 4 节的开工前检查。已经做了的先核回，只做缺口。

四、前置与顺序
按本批文件的「前置／待决」和每项的「该项前置」逐条核；没就绪的只停那一项，其余照做。合同先单独一个 PR（轨道规则 1），服务再接，消费者最后。可并行项只做设计、只读核查或等待期间的独立工作，不把后续依赖当成已经能开工。

五、界面
本批文件的界面要求是「先定样：目录／规则／恢复；复用 03、04」。写「先定样」的部分，先做可操作的样（组件板标本或预览页，2～3 个方案，正常与异常状态都有），我看过定下、记进原需求的决策记录后再写产品代码（需求开发流程第 5 节）；写「复用」的部分沿已定交互。

六、边界
- 一条轨道同一时间一个写手；要改别的轨道独占的文件，由那条轨道落，你的片叠在后面（轨道规则 7）。
- 不碰真实 Home（4207／4208 端口、~/.molis-work）；不换 vendor/prologue-sdk；不放宽门禁、不删断言、不为变绿跳过用例；不加兼容读取或迁移，除非已写进 docs/system/CONTRACT-CHANGES.md 的「当前保留机制」并经我确认。
- 只做本批的交付，后面批次的内容不提前做；发现本批范围要变，先改本批文件和原需求，再跟我说。

七、验证与完成
- 每项按原需求的验收编号验：用 node scripts/affected-tests.mjs 挑相关用例，node scripts/run-tests.mjs 跑；浏览器用例按机器槽位排，一台机器同时一个构建、一个测试；全量由统筹在集成分支跑，你不跑全量。
- 工程验证、真实操作和本人验收分开记；要我本人验收的列进 BACKLOG「待你验收」，不代我验收。
- PR 粒度：一项交付完整做完，或者别的片真要先用到它时，才开 PR；同一项的后续步骤叠在同一个分支上，不为每一步各开一个，也不开草稿 PR 占位；合同改动先单独开小 PR（需求开发流程第 8 节、轨道规则 1）。
- PR 按模板填，「开工前检查」一节贴检查结果和定样决定；推送前先 git fetch origin main 再跑 pnpm secrets:check；合并交统筹，你不合。
- 每片合入后在本批文件补日期、PR 和剩余项，并在认领板改状态；全部交付都验过，本批才算完成。

八、什么时候停下问我
碰到我没定过的事、红线（需求开发流程第 4 节）、界面定样、要动真实 Home／账号／费用／对外发布，或本批文件和代码现状对不上、要改范围时。问的时候给 2～3 个方案，标出推荐和各自的代价。
```
