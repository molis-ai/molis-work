## 二、开工前先跟我讲清楚（大白话）

先核对现状：main 上已经有什么、前置批次是否真的合入、有没有在途 PR 在做同样的事。然后用大白话跟我讲：这批做什么、要解决什么问题、做完我能看到或用到什么、为什么排在这里、需要我做什么。不用包名、合同、schema、编号这类词，非用不可时顺带解释一句。本批文件「给人讲清楚」一节是底稿，按核对结果改。讲完就继续做，不用等我回话（需求开发流程第 2.1 节）。

## 三、交付与认领

每片开工前先在认领板（GitHub issue #1743）认领，再按需求开发流程第 2.1 节说明这一片，再在原需求里答第 4 节的开工前检查；同一个子分支的按子分支做，每项都要讲到，认领板仍是每项一行，开工前检查写在一处、其余原需求放链接（第 8.4 节）。已经做了的先核回，只做缺口。

## 四、前置、顺序与分支

- 按本批文件的「前置／待决」和每项的「该项前置」逐条核；没就绪的只停那一项，其余照做。合同先做，服务再接，消费者最后，都在本批分支上按这个顺序叠。可并行项只做设计、只读核查或等待期间的独立工作，不把后续依赖当成已经能开工。
- 按批推进：本批 PR 合入 main、证据记好，才开始下一批的实现；准备工作（开工前检查、核账、定样、合同稿）只领先一批。批内谁依赖谁看 [依赖图](dependencies.md)。某项在等我定或等别批时，先做批内其他项和下一批的准备，不开下一批的实现；要我定的攒成一批问。
- 一批一个 PR（决定 28、31）：开工从最新 main 切出本批分支 `batch/NN`（服务端批 `batch/srv-N`），各项分成子分支，从本批分支切出，做完合回本批分支，不开 PR；全批只在最后开一个 PR。本批文件写的「粒度」是开工前的建议，看清现状后按需求开发流程第 8.4 节自己判断，和建议不一样的记在认领板和 PR 的「偏离」里。
- **每天同步一次 main**（用户 2026-11-14 定，[决定 44](decisions.md#decision-44)，取代决定 31 的「开发途中不同步 main」）：本批分支每天合一次 `origin/main`；另外，main 上合入了改本批要碰的枢纽文件、合同快照或生成文件的 PR，当天就合。同步后只整体构建一次（`pnpm build`），确认能编译、门禁数字没变大，不重跑用例；整批测一次（第八节）不变。正在做的子分支在合回本批分支时一起带上。同步出冲突的生成文件不手解，按[并行开发第 3 节](../../../docs/system/PARALLEL-DEVELOPMENT.md#3-合并)重新生成。
- 合同怎么走：先出设计稿，评审后提交到本批分支，再写合同代码，实现叠在后面，合同和实现一起随本批 PR 合入。只有别的批、服务端批或别的片确实在等这份合同，或有人排队改同一份快照时，才把合同切成一个只改合同的小 PR 先合（轨道规则 1）。首个外部安装之前是合同阶段一：按原版本改、不留兼容期，一个 PR 改完所有消费者（`docs/system/CONTRACT-CHANGES.md`）。

## 五、界面

Goal Prompt 写了本批的界面要求。写「先定样」的部分，按下面的「定样怎么走」先出样，我确认后再写产品代码；写「复用」的部分沿已定交互；出现已定之外的新页面、新控件或新动线时，同样先定样。

定样怎么走（已经定下的不重新出样：先查本批文件、原需求的决策记录和 `docs/design/`，照定样做，只补没定的）：

1. 出 2～3 个方案，用组件板实件；1440、1024、390 三种宽度、中英文、深浅色都出图或给能打开的实物，正常与异常状态都有。
2. 先拿给我看，再弹窗请我选；没确认的方案不进实现。
3. 我确认后，把选定的方案连同理由、否掉了哪些写进这一项原需求的决策记录；定样记录随本批 PR 走，不单开定样 PR。组件板有新增部件的，在本批分支上先补成组件板标本，再进产品；只有别的批也在等这个部件时，才单开定样 PR 先合。
4. 写产品代码之前做完走查，结论连同原型路径和提交号记在认领板该项，本批 PR 贴链接。

凡是碰到界面的部分（新做、复用、改文案或修缺陷都算），都要做到让我用得爽，不以「功能可用」或「测试过了」交差，做不到的不合入（需求开发流程第 5 节）：

- 交互：主路径步数最少，结果可预期，能撤销；每个操作都有即时反馈；键盘能走通；出错能就地修好。
- 设计与美学：用组件板实件和 `DESIGN.md` 的令牌；空间、光影与阴影、留白、色彩都做到位；不同内容用搭配的不同颜色。
- 动效：每个动效都有目的，交代从哪来、到哪去、状态变了；时长和曲线用令牌；不挡操作；减少动态效果时有退路。
- 布局：一屏能看懂；按钮有边界，多项要分区，行不折行；文件和文字放进容器；三种宽度、中英文、深浅色都成立。
- 注意力：一屏一个主焦点；只在真需要我时打断；提示按轻重分级；不让我找东西、干等、猜状态。
- 认知：让人认出来而不是回想；渐进展开，信息分块；默认值合理；用我的话，不用系统内部的词和原始 id。
- 行为：减少摩擦，让下一步自然发生，给完成感；尊重我的自主，不用暗黑模式，不制造焦虑。

样和产品代码都用组件板 `/__ui/catalog` 的实件，守 `DESIGN.md`、`specs/craft-finish/spec.md` 和 `specs/ui-craft-floor/spec.md`。组件板上没有的部件标「组件板新增」。界面与体验类的完成，以我本人看实物验收为准。

## 九、评审与合并（主会话负责）

1. **开 PR。** 全批写完测完才开，按模板填，「开工前检查」贴检查结果和定样决定；推送前先 `git fetch origin main` 再跑 `pnpm secrets:check`。
2. **评审。** 起一个只读的评审子代理（Opus 5.5 high；纯文档 PR 用 Sonnet 5.5 xhigh），提示里给 PR 号、本批文件和本手册第七节，写明不改代码、不跑测试和全量。它先按子分支逐个审各自的提交范围，再审全 PR：整合、冲突的解法、跨项的一致性；有合同改动的另审一遍合同（形状、版本、快照、对固定引用和消费者的影响），有组件板新增的另审一遍标本。结论按需求开发流程第 10.1 节七行逐条写在 PR 评论里，界面部分另按第五节走一遍体验；全部过了写「【评审台】审过（头 <sha>）」，退回写清挡合并的点，不挡合并的写成小修条目。你读完意见，挡合并的一次改完再推，让同一个子代理接着看改动的部分；PR 太大就分几次交给同一个子代理。你不替评审写「审过」。
3. **全量。** 评审意见改完后，你在最终的头上加 `full-suite` 标签，全批只跑这一次。要求是**不比 main 多红**（用户 2026-11-14 定，[决定 44](decisions.md#decision-44)）：允许红的只有当时「main 的夜间全量红了」issue 里列的文件，以及 `tests/quarantine.json` 里登记了 owner 和到期日的条目，PR 里逐个写明；其余都必须绿。本批引入的红在本批 PR 上修。
4. **入队。** 当前头上有「【评审台】审过」、CI 全绿、全量满足上一条，你自己用 `gh pr merge <号> --squash` 放进合并队列。合并前先读一遍 PR 上的全部评审意见，答复了或改完了再合。有页面资源许可的，最后一次同步 main 之后重新量一遍（`pnpm workspace:build` 再 `pnpm page-assets:check`），许可按新基点的实测写：同样的源码在新的 main 上可能多出几十字节，许可按旧基点写的会在队列里被拒（#2056，11-14）。
5. **出队了。** 合并队列失败，先看是哪个作业、哪个文件：时序类的偶发失败（作业摘要列为 Flaky，或与本批改动无关、重跑即过）直接重新入队；别的 PR 合入后的真冲突或门禁数字，同步 main 后修好再入队；本批引入的回归修好再入队。别的 PR 合入了本批碰的枢纽文件，同步 main 并重跑相关用例。
6. **不开「合后审计」PR。** 收尾检查（第十节）在合入前做完，本批的问题在本批 PR 上修完再合。合入后才发现的，除了 main 红了和安全缺陷要立即单开小 PR 修，其余记进下一批的小修子分支，随下一批的 PR 合。

## 十、收尾（主会话负责，合入前做完）

1. **收尾五问。** 你自己把全批改动合起来回答需求开发流程第 11.1 节的五问（防腐、平台能力、代码质量、清理、全局），每问一到三句，点名文件、数字或 PR；评审子代理的全 PR 评审结论作为输入。结论写进本批文件「收尾检查」一节。本批带来的问题在本批 PR 上修完再合。
2. **代码清理。** 按第七节和需求开发流程第 8.2 节再过一遍全批：本批让它变多余的旧入口、实现、导出、依赖、测试和文档都删了；没删的写理由并记 BL。
3. **需求映射与依赖。** 本批做完的需求，在[需求映射](requirements.md#section-3-9)里改状态或删行（原需求整项完成才删）；本批改变了别的批次的前置、交付或顺序的，同一个改动里改[依赖图](dependencies.md)、[执行目录](../spec.md#execution-batches)对应行，以及后面受影响、还没开工的批次文件；那一批已开工的，在 #1743 该项下评论，由它的主会话改。目标或退出条件变了，再改[阶段总览](stages-and-acceptance.md)。
4. **记录。** 批次文件的进展、合入记录和收尾检查写在本批分支上，随本批 PR 合入；合入的提交号随下一批的 PR 补。用户决定写进决策记录，做完的条目从 BACKLOG 删掉，提交说明里写编号。
