# 第一步：全部需求合入后的功能审查、合并缺陷修复与 spec 梳理

所有并行需求合入 main 之后，先做这一步：

1. 以最近三天合入 main 的全部 PR 为范围，结合各自的 spec，核对每个需求在 main 上实际做到了什么程度；
2. 找出合并带来的缺陷与跨功能断点，**修复并验证**，让 main 回到功能正确、回归干净的状态；
3. 梳理 `specs/`：已经实现的归档，还没实现或已经明确后续要做的事项统一抽取到一份清单。

只给问题清单不算完成。

这是两步中的第一步。第二步是系统性的代码与架构防腐整理（`docs/prompts/repository-anti-corruption.md`），以本步交付的 main、行为基线和 spec 梳理结果为起点。**本步不做结构性重构**：审查中发现的架构与代码质量问题，写进交给第二步的清单。

背景：多条需求线在不同会话和工作树里并行开发，各自验证后先后合入 main。每条线"本线通过"，不代表合在一起的产品是对的：合并可能丢掉修复，同一能力可能被做了两遍，跨功能的动线可能断开，旧数据升级可能没人走过。与此同时，`specs/` 里堆积了大量 spec，很多已经实现却没有归档，还没做的事项散落在各份 spec、实施记录和 PR 描述里。

本步需要回答并处理：

- 最近三天合入的每个 PR 对应哪份 spec？每个需求承诺的功能，在 main 上实际做到了什么程度？哪些已实现、部分实现、未实现、与需求不符，或合并后退化？
- 合并带来了哪些缺陷：丢失的修复、互相覆盖的改动、用户能看到的重复功能、初始化与样式冲突、跨功能流程断开、旧数据升级问题？
- `specs/` 里哪些 spec 已经实现、可以归档？哪些事项还没实现，或已经明确要后续做？
- 修完之后 main 的全量回归是什么状态？哪些需要我决定，哪些需要我亲自验收？

完整清点，按风险深入。不以测试全绿、文档更新或建议清单代替完成。

## 0. 启动条件、范围与授权

**启动条件**：所有需求线都已合入 main。开始前用开放 PR 列表、`git worktree list`、各分支相对 `origin/main` 的超前提交核对。仍有未合入的需求线时，列出线与负责会话，不碰它们改动的文件，请我决定等待还是排除出本轮，并写进总 spec。

**范围**：

- **PR**：最近三天合入 main 的所有 PR，以开始执行的日期往前推三天。执行晚了也不要漏掉这一轮集中合入的需求，起点最晚取 2026-09-28。同一条需求线在起点之前还有合入的 PR，一并纳入。
- **spec**：这些 PR 涉及的 spec 做逐条验收（第 3 节）；`specs/` 根目录的全部 spec 做梳理（第 6 节）。
- 更早的功能只在被本轮改动影响时复查。

**授权**（可按需改这一段）：

- 功能缺陷、合并缺陷与已接受需求范围内的缺口，修复时自主完成：在自己的分支提交，可以推送分支、开 PR。每个 PR 只做一个主题，CI 通过。
- spec 的状态句补写、归档、链接修改与统一清单的整理，自主完成。
- 结构性重构、目录与包的搬迁、公共合同的重新设计，不在本步范围，写进第二步清单。
- 合入 main、删除他人分支或工作树、丢弃主检出的改动、删除 vendored 文件、向 Prologue 上游推送，先问我。
- 涉及产品语义的实质变化（例如两个功能该保留哪一个），先给具体方案、取舍和推荐，等我决定，同时继续其他独立工作。
- 我已验收的需求，不重新讨论产品决定，只核对合并后是否仍然成立。

## 1. 事实来源

| 问题 | 先看 |
| --- | --- |
| 产品承诺与当前范围 | `PRODUCT.md`、`DESIGN.md` |
| 每个需求要什么 | `specs/<任务>/spec.md`（含已归档到 `specs/archive/` 的）、`goal-prompt.md`、`implementation.md`、决策记录与用户拍板 |
| 合入了什么、声称验证了什么 | 范围内各 PR 的描述、合并提交、spec 的验证小节 |
| spec 怎么归档 | `specs/README.md` 的归档规则 |
| 修复时必须遵守的规则 | `AGENTS.md` 硬约束、各包 README 的「开发要求」、现有门禁（例如 `tests/builtin-plugin-assembly-gate.test.ts`） |
| 实际行为 | 代码、测试、真实界面操作、真实模型调用、MCP |

实现、测试、spec、PR 描述和历史记录都只是证据，没有哪一方自动正确。冲突时区分：实现回归、合并丢失、测试落后、测试设计错误、文档过时、需求不明确。

上一轮《Molis Work 代码与架构防腐体检报告》（`docs/prompts/code-health-report-2026-09-30.md`）是第二步的输入；本步只用到其中与功能相关的几项（见第 5 节）。

## 2. 清单与基线

### 2.1 PR 与需求清单

1. 列出范围内合入 main 的全部 PR，连同合并提交、分支名与描述，例如：

   ```bash
   gh pr list --repo molis-ai/molis-work --state merged --search "merged:>=<起点日期>" --limit 300 --json number,title,headRefName,mergedAt,mergeCommit,body
   ```

2. 把每个 PR 对应到 spec：看 PR 描述、它改动的 `specs/` 文件和分支名。一条需求线是一份或几份 spec 加上若干 PR。没有 spec 的 PR（测试修复、小修）单列，核对它说的问题确实修好了。
3. 反向核对：范围内被修改过的 spec 都要找到对应的 PR；spec 承诺了、却没有任何 PR 实现的部分，记为未实现。
4. 逐条需求线建表：spec 位置、PR 与合并提交、声明的完成等级（功能可用、内部完整等）、spec 状态句、验收项、用户验收状态、spec 与 PR 写明的"未做"、负责会话。

没有验收编号的 spec，按其范围与验收小节逐条编号（例如 `SEARCH-01`），写明出处小节，再逐条判定。

### 2.2 能力快照

导出当前真实宿主的动作目录、MCP 工具目录、设置分区、标题栏与底栏元素、侧栏标签、插件清单与各自的装配方式。这份快照既用来核对需求，也作为第二步重构前后对比的依据。

### 2.3 回归基线

在当前 main 的干净工作树上整体构建，跑全量非浏览器与浏览器用例，保存完整输出。每一个失败都要归类处理。"main 上本来就失败"不是结论：要么修复，要么写明原因、负责人和期限。

## 3. 需求实现程度

对每条验收项，从真实入口（界面、MCP、HTTP、CLI、后台任务）在隔离 Home 中验证，留下证据（截图、请求记录、测试名），判定为：

- 已实现并验证；
- 部分实现，说明缺什么；
- 未实现；
- 实现与需求不符；
- 合并后退化：之前验证过，现在不成立；
- 需求不明确，需要决定。

同时核对：

- spec 状态句、"未做"清单和 PR 描述的说法，与 main 上的实际行为是否一致；
- spec 决策记录里的用户拍板是否都已实现，且没有被后合入的线改掉；
- 声明的完成等级是否真实达到，包括首次使用、空数据、无模型或模型失败、权限撤销、插件停用、离线、窄屏、英文界面、键盘与读屏；
- 需求要求真实模型的，用真实模型（MiniMax）在隔离 Home 实测，不用替身冒充。

处理方式：已接受需求范围内、规模可控的缺口，直接补齐并验证；大的缺口给出方案与工作量，请我决定。不悄悄缩小需求，不把没有证据的项记为完成。最后为每个需求整理一份给我的验收清单：我需要亲自看什么、在哪里看、预期是什么。

## 4. 合并后的缺陷

### 4.1 合并丢失与互相覆盖

- 范围内每个合并的 PR：列出它新增或修改的测试文件，在当前 main 上重跑。失败说明合并破坏了它，追到具体提交。
- 每个 PR：核对描述里的关键行为在当前 main 上仍能观察到。
- 范围内被三条及以上需求线同时修改的文件，读最终版本全文，不只看 diff。编写时已知的热点包括 `apps/workbench/src/immersive-shell.ts`、`i18n/en.ts`、`scripts/client/initialization.ts`、`scripts/client/navigation-presentation.ts`、`page-assets.ts`、`goals-page-renderer.ts`、`builtin-plugins.ts`、`apps/local-host/src/web-request.ts`、`web-catalog.ts` 和各设置页文件。检查重复的事件监听与 DOM id、初始化顺序、样式层叠覆盖、翻译键冲突、设置分区重复、路由重复。
- 搜索残留的冲突标记与被注释掉的整段代码。

### 4.2 用户能看到的重复与语义冲突

并行开发很容易把同一件事做两遍。本步确定唯一的用户可见路径，修好行为与数据；只剩代码层面的旧路径删除时，可以交给第二步，但要写明位置和删除条件。至少检查：

- **通知入口**：标题栏插件通知铃铛与底栏助理「需要你看看」铃铛并存；助理提醒、Todo 到期提醒、Schedule、插件通知、后台任务回报之间的边界。
- **记忆**：助理第一版记忆（`<Home>/assistant/assistant.db` 里的偏好与候选）与平台记忆系统；旧数据是否迁移，用户在设置里看到的是不是同一份。
- **推荐与操作**：情境动作、首页 Dock 判断、页面操作卡、底栏建议条之间，是否只有一套推荐。
- **文件与预览**：侧栏文件、Files 插件、助理附件与材料。
- **讨论分屏**：被侧栏取代后，旧入口是否已经消失。
- **Characters**：角色收进「设置 › 角色」后，与插件目录、市场、导航和文档描述是否一致。
- **搜索、@ 引用、放置的相关资料**：是否读到同一个对象、遵守同一套权限。

### 4.3 Prologue SDK 合成包

各需求线对 SDK 的补丁（助理 intake 与 app 模式、记忆作用域与缺口、侧栏 surface、动态交互等）是否全部进了当前使用的合成包，相关功能是否都能用到。`scripts/workspace-packages.mjs` 与 `horizontal/agent-host` 的依赖是否指向同一个包。vendored 包的数量清理留给第二步。

### 4.4 跨功能场景

在隔离 Home、真实浏览器、真实模型下走通以下组合场景，可以补充。截图与记录作为证据，并把场景清单写进总 spec，供第二步每次重构后重跑：

1. 全新安装、无模型 → 配置模型 → 助理第一轮 → "记一下"按内容分到待办、日程或灵光 → 撤销。
2. Pages 选中文字 → 底栏出现情境动作 → 选择 → 预览并写回 → 结果出现在侧栏文件 → 用到的记忆能在设置里看到并撤销。
3. Feed 新资料 → Inbox → 转为待办 → 放置到项目 → 项目首页的相关资料 → 系统搜索找到并打开准确位置。
4. Coding 委派与助理交接 → 侧栏浏览器里助理操作 → 审批 → 中途停止与撤权。
5. 底栏、设置、Shelf、灵光的开关与返回；标签页增删与暂存；刷新、后退、多窗口、分屏。
6. 插件停用、卸载、升级 → 目录、搜索来源、助理能力、MCP、记忆、情境动作同步更新，没有残留的可调用项。
7. 项目切换，个人空间与项目之间移动 → 权限与可见范围隔离。
8. 重启与崩溃恢复：定时跟进、后台任务、到期提醒、侧栏会话、未完成的写入。
9. 旧数据升级：用范围起点之前 main 的构建创建并使用一个隔离 Home，再用当前 main 打开。验证助理、记忆、Todo、放置、搜索索引等迁移不丢数据、可以重复执行。需要拷贝我的真实 Home 做演练时先问我。

### 4.5 轮询、并发与性能退化

清点各需求线新增的定时器与轮询（通知铃铛、助理提醒、到期提醒、后台任务回报、定时跟进、Feed 调度、搜索索引等），量合在一起的空闲负载、启动时间、首页与常用页面的打开时间。明显的退化在本步修；需要改结构的写进第二步清单。检查"一个 Home 一个执行进程"和 Agent 运行锁在新功能下是否仍然成立。

### 4.6 界面回归

后合入的需求线是否沿用 Soft Workbench 的 token 与原语。检查 1440、1024、390 三档宽度，浅色与深色，中文与英文，减少动效。检查 390 宽度下底栏与标题栏有没有被各线新加的入口挤出格子。

## 5. 已知的功能相关问题

编写时观察到的，开始时逐项复核：

- main 上已知失败的用例：Shelf 设置页 Grok 文案、Shelf DropAgent 对照、Feed → Shelf 动作流程、SDK 打包样例离线安装、plugin-event-recovery、workbench-pane-feed。编写时有一条修复分支在处理其中一部分，核对它是否已经合入、问题是否修好。
- 两个铃铛同时在 main 上：`immersive-shell.ts` 的 `data-plugin-notifications` 与 `assistant-dock.ts` 的 `data-assistant-attention`。
- Characters 已收进「设置 › 角色」，但仍是插件目录条目。
- 主检出落后 main 一百多个提交，真实 Home 4207 跑的是旧代码；用户第一次升级时走的就是第 4.4 节场景 9 的路径。
- 编写时尚未合入的修复与需求线，合入后行为是否成立。

## 6. spec 梳理：归档已实现的，统一抽取未实现和后续要做的

对象是 `specs/` 根目录下的全部 spec，不只本轮的。依据 `specs/README.md` 的归档规则；规则与这里不一致时，按这里做，并同步更新那份规则。

**逐份判定**，写明依据：

- **已实现**：正文要的行为在 main 上成立。本轮相关的 spec 用第 3 节的验收结论；其余对照代码与真实行为核对，不只看状态句。
- **部分实现**、**未实现**；
- **已被取代**或**已作废**：写明被哪份 spec 或哪个决定取代；
- **现行规范**：仍被 `AGENTS.md`、SSOT、Skill、包 README 引为现行规则的 spec，例如动作架构的基本合同、craft-finish 设计规范、架构重组需求书。这类不归档；
- **判断不了**：写明缺什么证据，列为待我决定，不擅自归档，也不当成已完成。

**处理**：

1. 已实现的（包括只差我验收的）：补状态句，写明依据与日期，移到 `specs/archive/`。只差我验收的，把验收项列进统一清单的「待你验收」一节。
2. 部分实现、未实现、以及明确写了后续要做的：逐条抽取到统一清单。抽取来源包括 spec 正文、`implementation.md`、决策记录、PR 描述里的"未做""未包含""后续""下一期""暂缓""不在本期""待用户定"等。原 spec 已没有其他在做的内容时，归档，并在开头注明剩余事项移到了统一清单的哪几条；仍在做的保留在根目录。
3. 已取代或作废的：写明被谁取代，归档。
4. 现行规范：保留原位，在 `specs/README.md` 单列。
5. 正在被在途会话使用的 spec，先问负责会话再动。

**统一清单** `specs/BACKLOG.md`，作为未做事项的唯一来源。每条写：编号、事项、来源 spec 与小节（链接）、类型（未实现、部分实现、明确后续做、已知缺口、待我决定、待你验收）、为什么还没做、依赖、建议优先级、已知负责人。按产品区域或需求线分组，同一件事在多处出现的合并成一条。只抽取与归并，不在清单里重新设计需求；几处说法冲突的，列出来源请我定。

**收尾**：

- `specs/README.md` 改为只列在做的 spec、现行规范和统一清单的链接；
- 归档时同步修改仓库内所有指向它的链接，包括代码注释、README、`docs/`、`skills/`、包 README 的「开发要求」和测试；
- 跑全仓断链检查和 `pnpm boundary:check`（它会检查包 README 里的链接）。

## 7. 修复方式与验证纪律

**顺序**：数据丢失、安全与权限问题 → 用户可见的回归与断开的动线 → 需求缺口 → 用户可见的重复与语义冲突 → 性能退化。spec 梳理可以与修复穿插进行，但每份 spec 的判定要用最新的验收结论。

**每项修复**写明问题、证据、根因、改动、受影响的需求线，以及修复前失败、修复后通过的测试或真实操作证据。修复只改到能修好问题的范围；看到结构问题，写进第二步清单，不顺手重构。

**分支与 PR**：从最新 main 开分支，一个 PR 一个主题。spec 梳理单独成 PR，不与代码修复混在一起。合并前变基到最新 main，并重跑相关用例。

**测试**：不跳过、不放宽、不删除关键断言来换取通过。先分清产品回归、合并丢失、预期变化、测试缺陷、环境与时序。偶发失败单独连跑确认，并记录。

**回归纪律**（仓库已经踩过的坑）：

- 改过任何 `*/src`、`scripts`、`package.json` 之后，跑全量前先整体 `pnpm build`。单包构建写成 `pnpm --filter <包> run build`，`--filter` 放在 `run` 之前。
- 全量回归期间不改源码、脚本、`package.json` 和 `skills/`，只改 `docs/`、`specs/`。spec 归档需要改 `skills/` 里的链接时，也不要在全量回归期间改。不并发构建。
- 保留完整输出。判断是否新引入，用干净基线工作树（`git worktree add --detach`）跑同一批文件对比。
- 停进程只按 pid，不用 `pkill -f scripts/run-tests.mjs`。
- 浏览器用例在 macOS 本机 Chrome 上跑，加 `--lang=zh-CN`。Linux 容器缺原生资产，结果不能与本机基线直接比较。
- 有其他会话同时在跑时，构建与浏览器用例串行排时段；同时跑多个全量会全部超时。

**环境**：用隔离 Home（`MOLIS_WORK_HOME` 指向临时目录，`MOLIS_WORK_SECRET_BACKEND=file`）。真实模型把模型配置拷进隔离 Home，不打印密钥。不占用真实 Home 4207/4208 的 Agent 运行锁。

**协作**：开工前看 `git worktree list` 和正在运行的会话。不重置、不覆盖别人的未提交改动。主检出里的无主改动由我决定怎么处理。

## 8. 交付

1. **总 spec** `specs/post-merge-review/spec.md`，作为本步唯一的进度与证据记录：
   1. 范围：起点日期、范围内的 PR 清单、基线提交、未纳入本轮的线；
   2. PR 与需求清单：每个 PR 对应的 spec，每条验收项的判定与证据；
   3. 问题表：编号、严重程度、证据、根因、处理、状态（已完成、在途、待决）、负责人；
   4. 合并缺陷与用户可见重复的处理结果；
   5. 跨功能场景清单、结果与截图；
   6. 全量回归结果与基线对比，失败逐项归类；
   7. **行为基线**：最终的回归基线（提交、用例数、通过数、已知失败及负责人）、能力快照、跨功能场景清单，供第二步每次重构后对照；
   8. spec 梳理表：每份 spec 的判定、依据和去向（归档、保留、现行规范、待我决定）；
   9. 待我决定的事项：方案、取舍与推荐；
   10. 未验证的范围与原因；
   11. 给我的逐需求验收清单；
   12. **交给第二步的清单**：审查中发现的架构与代码质量问题，每项写明位置、证据和为什么留给第二步。
2. **统一清单** `specs/BACKLOG.md`。
3. **更新后的** `specs/README.md` 与归档后的 `specs/archive/`。

最终汇报区分"已确认、推断、未验证"和"已完成、在途、待决"。建议不冒充修复，交接不冒充关闭，测试全绿不冒充产品完整。

## 9. 完成标准

- 范围内每个 PR 都对应到 spec 或单列为无 spec 的修复；每条验收项都有判定与证据。部分实现与未实现的项已经补齐，或有我确认过的方案与负责人。
- 合并丢失与互相覆盖已修复；用户能看到的重复功能只剩一条路径，涉及的数据已迁移。
- 跨功能场景在真实浏览器与真实模型下通过。
- 全量非浏览器与浏览器回归没有未归类的失败；`pnpm build`、`pnpm typecheck:all`、`pnpm boundary:check` 与 CI 通过。
- `specs/` 根目录只剩在做的 spec 和现行规范，每份都有状态句；已实现的已归档；未实现与后续要做的事项全部在 `specs/BACKLOG.md`，每条可追溯到来源；仓库内没有断链。
- 行为基线与交给第二步的清单已写进总 spec。
- 不在首次扫描、建议清单或部分修复后提前结束。
