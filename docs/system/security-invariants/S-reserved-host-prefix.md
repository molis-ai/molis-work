**随包放行：来源在预览核，签名者在安装与每次启动核（第 44C 批 P-13，用户 2026-11-26 定「绑签名者」）。**

- 来源核在预览（`apps/local-host/src/plugin-install-service.ts` 的 `preview`）：只有经 `{ bundled: { plugin_id, version } }` 进来、由宿主自己从本次发布的随包文件夹读出并验过签的包（`bundledBundle`），才带「来自本次发布」的标记（`assertNotHostId(…, 'bundled' in input)`）；调用方直接交来的 `bundle`，哪怕 id 与随包的一样，也按前缀拒。确认（`confirm`）只认内存里持有的那份预览（`preview_id`），不接受新的包体。
- 签名者核在 Runtime 安装与每次启动、恢复、换版（`packages/plugin-runtime/src/install-identity.ts` 的 `assertInstallIdentity`，`ReleasePackages.signedBy`）：id 在本次发布的随包文件夹里还不够，记录的发布者签名必须是那份包的签名者——文件夹里签好的包（`<plugin_id>.json`）认它验过的签名密钥，待签包（`<plugin_id>.draft.json`）认本 Home 自己的发布者密钥（安装时正是它签的）。这样绕过预览进了 Runtime 的记录（别的密钥签、或未签名标签）在启动前就以 `plugin.id_namespace_conflict` 拒，进 crashed，不注册任何动作。宿主按 `apps/local-host/src/host-plugin-ids.ts` 的 `releasePackagesFor` 读同一个文件夹（测试给宿主的随包文件夹时读那个）。
- 绑的是签名者、不是精确摘要：随包文件夹换了新版后，用户已装的旧版仍是同一签名者，照常启动，等用户确认换版；绑精确摘要会让旧版在换版前一律起不来（用户 2026-11-26 选了前者）。
