## 1. 背景

来源：统筹 2026-10-30 的高优先级一行。症状：`tests/code-scale.e2e.test.ts` 约 :88 的 RAC-2072（`Math.max(...steps) < 50`，每个着色帧含它强制的布局与观察器）在 T-131 #1575 的 Full（run 41094251737，第 1、2 次尝试各带重试）里连续失败 4 次，最长帧 50.2～58.4 ms；超出的部分总是**第一个着色片**的强制布局（47～51 ms），js 只有 3～5 ms。与具体 PR 无关：main 在 CI 的 Linux runner 上本身就贴着线；T-298 #1597 加了用例后更糟。代码：`plugins/native/coding/src/code-paint-client.ts`（`createCodingCodePaint`）约 :63 `SLICE = 16000`、`BLOCK_SLICE = 4000`、`CAP = 400000`，约 :125-135 的切片循环与 :135 的 `ResizeObserver` 等首次布局；大块的第一次布局已经单独占一帧（T-281，RAC-2070/2071），之后每帧一片。测试里 `steps` 是各着色帧的总耗时，`sliceCosts` 有 js、layout、observers 分项（`t.diagnostic("code-scale slices: …")` 会打印）。可能的原因（**未证实，要你量**）：(a) 第一片本身太大（16000 字一片，生成的 span 多，强制布局要把它们全排一遍）；(b) 整块第一次布局的残留成本落进了第一个着色帧；(c) 前面几个用例（`display:none`、`content-visibility:auto`）遗留的布局成本带过来。T-281 的实测：Apple 芯片开发机 16～20 ms，4× CPU 降速 55～57 ms，6× 74～95 ms；CI Linux 约比开发机慢 4～5 倍。行号以 `origin/main` 为准，开工先核。

## 2. 目标

先在 #1332 贴【方案】（乙档）：你量到的数据（见下）、判断的原因、打算改什么、新增什么用例、先红的预期。
1. **先量**：用 `Emulation.setCPUThrottlingRate` 4× 和 6×（T-281 的做法，看 `tests/code-scale.e2e.test.ts` 与 `tests/fixtures/code-colouring.ts`），把 `sliceCosts` 的 js/layout/observers 逐片打出来，至少跑 5 次，找出“第一片”的 layout 随什么变：片大小、前序用例是否在同一页、整块首次布局是否刚结束。把原始数字贴进方案，不要只贴结论。
2. **再改**：只改着色的调度或片的大小策略（例如第一片比后面小、第一片之前先让出一帧、按已排版的块大小调整片），让 4× 降速下最长着色帧稳定低于 50 ms 且留出余量（目标：4× 下最长不超过 35 ms，6× 下不超过 50 ms；做不到就在方案里写明能到多少）。**不改 `tests/code-scale.e2e.test.ts` 里的 50 ms 上限、不改 RAC-2071 的 150 ms、不跳过用例、不降 `steps.length >= 15` 的要求**；着色完成的结果必须不变（`matchesColour` 仍通过，增长、重来、离页停止三段照旧）。
3. **新增用例 RAC-2440**：钉住你找到的原因，最好不依赖 CI 机器的快慢——例如断言第一片的字数不超过某个与布局成本挂钩的上限，或第一个着色帧的 layout 在降速下低于某值（用 CDP 降速，和 T-281 一样）。先对旧代码证明红。
4. **RAC-2441**：在 4× 降速下连跑，`steps` 的最长帧低于 50 ms（可并进 RAC-2440 同一用例，各自断言要分开写明）。
5. 在 CI 上只有 Full 才跑这条（`code-scale.e2e` 是浏览器用例）：本机用降速代替；PR 里写明本机 4×/6× 的前后数字，统筹排 Full 验证（你不加 `full-suite` 标签）。
