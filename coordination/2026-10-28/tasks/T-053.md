## 1. 背景

- 写：`source-sync.ts:164-190` 一带，`write(() => { … this.feed.ingestItem({ … }) })` 里，`:179` 是 `tags: [latest.kind, \`feed-source:${latest.source_id}\`]`，`:180` 是 `author: material.sourceName`。仓库里写 `feed-source:` 开头标签的只有这一处（在 `plugins`、`packages`、`apps`、`modules`、`tests` 的 `.ts` 里搜过）。
- 读：`application-projection.ts:7-8` 的内部常量 `FEED_SOURCE_TAG_PREFIX`，`:28` 的 `tags: item.tags.filter(tag => !tag.startsWith(FEED_SOURCE_TAG_PREFIX))`。常量只在这个文件里用。`feedItemRecord` 的调用方是 `application.ts` 的 `:41`、`:54`、`:58`、`:63`、`:282`、`:388`、`:392`、`:396`、`:406`。
- 下游都读投影后的 `tags`，所以不用动：详情页 `ui.ts:387`，搜索摘要 `content-actions.ts:43`，规则匹配 `out-rules.ts:140`，捕捉产物 `out-rules.ts:157`。
- 为什么重拉去不掉库里已有的：`store/items/ingest.ts:31-35` 只在 `refresh` 或更新的 Signal 版本时走 `UPDATE`，`:40` 才重写 `tags_json`；同一条再拉一次只会去重。所以 T-053 之前拉进库里的条目，`tags_json` 里仍有那个标签（第 5 节第 2 条）。
- 现有测试：`tests/feed-item-tags.test.ts`（231 行，T-028 写的，`RAC-1270`～`RAC-1273`）。它的第一例（`:87-114`）靠读出的 `tags` 断言，读出走过滤，所以量不到库里写了什么；第四例（`:191-231`）和第一例的后半（`:100-110`）断言的正是「人写的 `feed-source:` 标签被滤掉」，这条行为本单要去掉。

## 2. 目标

1. 来源拉取写进库的条目，`tags_json` 里只有来源类型（如 `custom_rss`），没有 `feed-source:` 开头的项（`RAC-1185`）。
2. Feed 读出时不再改写标签：一个人写的、恰好以 `feed-source:` 开头的标签，原样原顺序读出（`RAC-1186`）。
3. 详情页和搜索摘要对拉取来的条目仍然只露出来源类型，不含 `feed-source:`；没有标记的条目的摘要不变（`RAC-1187`，护栏）。

## 5. 做法

统筹已定的决定，照做，不另选：

1. **停写和删读出过滤放在同一个 PR。** 读出处的注释就这么要求；AGENTS 写明合同读写只认现行取值、读取时不兜底历史取值，留着过滤等于永久留一条兼容读。库里已有的是存量数据，该由维护改，不由读取兜。
2. **不做维护，接受存量条目会露出标记。** 新迁移要用户确认，不在本单；上面第 1 节说了重拉去不掉它。代价是 T-053 之前拉进库的条目在详情页和搜索摘要里又会看到 `feed-source:feed-source-…`，直到维护去掉；BL-096 的行把这件事记下来，不丢。
3. **`tags: [...item.tags]`，不直接 `tags: item.tags`。** 原来 `filter` 给的是新数组；读出的条目不与模块记录共用一个数组，行为不变，一行的代价。
4. **三个读出的下游一个都不改。** 它们只读投影后的 `tags`，标记不再被写就够了；改它们是在范围外补第二层保险。
5. **测试从库里读原始值。** `RAC-1185` 用 `data.store.db.prepare("SELECT tags_json FROM feed_items WHERE project_id = ? AND item_id = ?").get(DEMO_PROJECT_ID, item.item_id) as { tags_json: string } | undefined`，再 `JSON.parse(row.tags_json)`，写法同 `tests/desktop-tui.test.ts:1292-1296`（单次 `as`，不写 `as unknown as`）。测试不在表主人门禁的扫描范围（`scripts/gates/table-owners.mjs` 开头注释：不扫 tests、fixtures）。过滤删掉之后，读出的 `tags` 就是库里的，读 SQL 的价值在 main 上：那里读出的 `tags` 被滤过，只有读库才红。
6. **改写 `tests/feed-item-tags.test.ts`（就地，不另起文件）。** 沿用 `MATERIAL`、`harness()`、`close()`（`:22-83`）：
   - 第一例（`:87-114`）改名 `RAC-1185`：拉一次，`snapshot` 里找到该来源的条目，读库里的 `tags_json` 断言恰好 `["custom_rss"]`，再断言 `item.tags` 与 `getFeedItem(...).tags` 同样是 `["custom_rss"]`；后半（`:100-110` 人写标签）搬到新例。
   - 新例 `RAC-1186`：`ingestItem` 写 `tags: ["zeta", "feed-source:handmade", "alpha"]`（沿用 `:100-108` 的参数），断言 `ingestItem` 返回的 `item.tags`、`getFeedItem(...).tags`、`snapshot().feed_items` 里同一条的 `tags` 三处都等于 `["zeta", "feed-source:handmade", "alpha"]`。
   - 原 `RAC-1271`（`:117`）、`RAC-1272`（`:135`）只换编号为 `RAC-1187`，断言一个不动。`:136` 那句 `assert.equal(FEED_CAPTURE_ARTIFACT_TYPE_ID.length > 0, true)` 只是为了让导入被用到，随导入一起删。
   - 原 `RAC-1273`（`:189-231`）整例删：它的对象是被删掉的过滤；捕捉产物的 `tags` 与规则匹配读的是同一个投影后的数组，标记不再被写，`RAC-1185` 的库里断言已经守住。删完之后没人用的导入（`FEED_CAPTURE_ARTIFACT_TYPE_ID`、`feedCaptureArtifactId`、`openProjectVersionStores`）和 `harness()` 里的 `app`（`:11`、`:13-14`、`:55`、`:77`）一起删。
