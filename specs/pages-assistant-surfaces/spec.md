## 2. 交互方案

### 2.1 一个侧栏，常驻工具与情境内容共存

右侧沿用现有工作台 sheet：与主区等高、8px 分隔、可调整宽度；窄屏沿用底部 sheet。Shelf 是插件，不把这个通用容器归给 Shelf。

- 顶栏保留现有常驻工具；当前插件声明的情境视图按 Manifest 出现。Pages 提供「评论」「备注」两个内容模式，均属于 Pages 的一个侧栏视图，不为每条评论增加工作台标签。
- 激活 Pages 文档 A，评论显示 A 的线程；换到文档 B，显示 B。分屏时以有焦点的主区窗格为准。草稿按对象与线程保存。
- 切换主区只更新上下文，不自动打开已收起的侧栏，不抢走用户正在看的讨论/浏览器/文件。点正文评论或「评论」按钮才明确打开并选中对应视图。
- 主区离开 Pages 时情境入口撤下，旧视图保留草稿但不冒充当前内容；侧栏若正在显示它，则回到上一次常驻工具（无常驻工具时显示无相关内容）。返回 Pages 恢复文档自己的状态。
- 只有显式点击引用才跳到原文并短暂高亮，不因收到回复自动滚动正文。侧栏载入失败保留正文和草稿，提供仅重载视图的入口。

### 2.2 助理展开到主区

- 底部对话面板提供「在主区展开」。当前 work 成为现有主区标签的一项，标题取工作标题，带助理身份；不打开浏览器新标签、不盖住主区标签栏。
- 每个 work 最多一个主区标签。重复展开聚焦已有标签；同一个编辑输入区不会在两个位置同时出现。主区标签切换不改变 work 的作用域、材料和授权。
- 「收回底部」恢复之前的主区标签，并把同一对话视图移回底部；消息、草稿、滚动、待答问题和运行状态连续。关闭主区标签只收起展示，底栏可再次打开；停止执行用独立的「停止」操作。
- 助理在主区时，底栏助理入口负责聚焦该会话；不出现两个可并发提交的输入框。其他插件标签仍可正常访问，助理后台运行可见状态点。
- 全局 work 与评论 work 不自动混为一条。评论内提供详细运行入口时，打开绑定的同一 work，并明确「回复到 Page / 线程」；即使在主区接续，回复目标仍固定。切片先覆盖全局 work 展开与评论内回复，不实现评论运行详情入口。

### 2.3 Pages 中就地讨论

正文工具栏的「评论」可针对整篇 Page；选中正文时提供「评论所选内容」；已有评论线程内始终能回复或「请助理回复」。引用旁显示所针对的片段/全文。每条消息有稳定身份，可以选「回复这条」明确回应哪一条；助理默认读取该线程，不读取其他无关评论。

输入框默认发普通评论。点击「@个人助理」后出现选中态与「发送并请助理回复」，发送才开始执行；只输入提及文字或收到别人的提及不会自动运行。用户的这条请求作为普通用户消息留在原线程，助理以明确身份回复。之后普通跟帖仍不自动召唤，需要再次选择。

发送前显示上下文范围：Page 标题、当前锚点、整条线程；正文按当前可读版本取用。若有未保存正文，允许用户明确选择带上本页草稿并标记为草稿；默认等待正文保存成功再发起，保存失败留在原处重试，不偷偷使用旧正文。长文需裁剪时显示范围说明，不声称已读全文。

正在回复、已停止、失败、重试均在原线程。发送后可换页、收起侧栏或查看其他线程。原线程的状态可见但不抢焦点。相同线程运行中允许普通评论，第二个 AI 请求先提示等待或停止当前回复，不隐式并发或排队。

回答/建议不获得正文修改权；本轮不设计自动采用和改写正文。文档评论中要求改正文时可给建议，真实修改必须走既有独立动作及授权流程。

备注仍是附着块的短文字，在「备注」模式编辑；不默认把所有备注转为多人线程。需要讨论可显式从该块新建评论。

## 3. 合同、事实与调用边界

下列合同随 P1–P4 实现冻结，并在同一工作树更新生产方、消费方与快照。2026-10-13 核对最新主干 `2cb35d4e8`：在途 #472 改动 Assistant 服务、存储、HTTP 与界面；#411 是情境动作交接，涉及 UI 合同和 Pages 编辑器。当前从主干实现，不依赖未合并的候选包，不复制在途工作的交互卡或输入回执。

### 3.1 侧栏上下文

在现有 UiViewDeclaration 的 side 视图上增加可选上下文声明（拟名 `context_binding`），取值为常驻工具或跟随本插件主区对象；未声明的既有工具按当前静态行为工作。不是按 Pages 名字在宿主写分支。

上下文载荷包含 `pane_id/tab_id`、`view_id`、`object_ref`、`revision`、`selection_ref?`、单调递增的 `context_epoch`。对象采用现有对象引用形状，选区由 owner 解释；不把编辑器实例、Store 或整篇正文送进平台状态。

宿主根据已挂载且有焦点的实例建立绑定，side 客户端 ready 后补发最新上下文；后续切换显式更新/清空。旧 epoch 的加载结果不得覆盖新对象。iframe 消息同时校验 origin、source 与实际挂载实例；project、actor、installation 不信任消息输入。DOM 事件需在既有登记表中声明生产者、消费者与载荷。

侧栏可以请求聚焦稳定对象/锚点，实际导航与访问校验归宿主和 owner。跟随焦点是 UI 语义，绝不授权读写其他对象。

### 3.2 展示状态与执行状态

| owner | 唯一事实 |
| --- | --- |
| Workbench | 主区标签/窗格、当前焦点、侧栏模式与尺寸、work 的展示位置、各视图滚动位置 |
| Pages | 正文与版本、评论线程、消息、锚点、备注、用户评论草稿、已提交的助理评论 |
| Assistant | work 与 thread 绑定引用、round/run 生命周期、请求上下文快照、待答/待审状态、结果投递状态 |
| Agent Host / Prologue | 模型调用、工具执行、会话运行事实；沿用 Home 唯一 Runtime |

助理标签标识基于 work_id，不能把个人助理伪装成已安装业务插件。主区沿用现有标签布局操作，增加有 owner 的系统视图挂载入口。共享对话控制器负责轮询、提交、问题回答和草稿；展示挂载不创建 session、不重新发送请求。

### 3.3 评论线程与锚点

拟议 Pages 线程：`thread_id/page_id/revision/anchor/messages`；消息：`message_id/author/body/reply_to?/created_at`，助理消息带 `work_id/run_id/request_id` 作为来源引用，不允许浏览器自称 assistant 作者。线程历史与助理运行日志是不同事实，Pages 保存最终发布的评论，执行轨迹仍归 Prologue。

核对生产 schema 后修正原先假设：Pages 尚无通用稳定块 ID，已有评论 mark 的 id 可随 ProseMirror transaction 映射。首轮生产锚点使用全文或带稳定 mark ID 的文本范围；从块备注发起讨论时标记该块文字。引用快照供人辨识，不以纯字符偏移或文本搜索当唯一身份。正文编辑时经编辑器 transaction 映射；原文删除则显示「原文已变更，保留引用」，不能猜一个相似段落重新挂接。切片只演示显式引用和选区，不证明 ProseMirror 映射。

存量 comment mark 的 text 和块 note 必须保留，继续作为现行正文注释。新增讨论由 Pages 的独立 page_comments 表拥有；用户显式回复一条正文注释时才创建讨论，并把当时的注释保存为标记作者未知的引用消息。这是用户动作，不在读取时回填或猜测原作者。新线程与正文版本独立提交，防止模型回复覆盖正文。Pages SQLite 基线升至 v2，新 Home 直接建现行结构；旧库版本明确拒绝。**本轮不迁移真实 Home**，没有新增自动迁移/兼容机制；已有 Home 的离线维护仍需单独授权。

### 3.4 原地召唤与结果交付

1. 用户显式提交：Pages owner 幂等保存用户消息，确定线程/消息引用；保存失败不派出 AI。
2. 通过共同动作服务调用助理发起/接续能力，传请求 ID、对象/线程/消息引用与期望版本；可信身份取调用上下文。宿主解析 owner 声明的上下文读取动作和回复提交动作，不在助理里 import Pages 实现。
3. Assistant 给该线程创建或复用独立 work，冻结该轮上下文与回复目标。UI 焦点之后变化不影响绑定。对话可跟踪为 work，但不自动弹开全局助理。
4. 经 horizontal/agent-host 使用当前 Home 的 Prologue Runtime；本场景只允许必要读取和原线程回复，不继承全局 work 的正文写入工具权限。正文、评论内容按不可信材料处理。
5. 终态回复由宿主调用 owner 的提交动作，携带运行来源和固定目的地；模型不能任意指定另一个线程。异步等待声明 concurrent，提交前 beforeEffect 复查取消、授权、安装和目标存活，再按版本与事务保存。
6. Pages 以 request_id + run_id 做幂等投递；成功落库后才展示为已回复。进度/流式文字仅作临时显示，不伪装成已存评论。

建议最小动作集合：读取线程、追加用户消息、发起线程回复、提交助理回复（仅受控 Host 调用）、读取/控制已绑定运行。最终名称按同一能力定义生成 Manifest 与动作快照，不加平行工具目录。第三方消费走 contracts + plugin-sdk；平台和插件共用的运行检查放 SDK，不转出私有包。

版本变化分类：普通跟帖不改这一轮已冻结输入，回复注明基于发起时上下文；目标删除/权限变化拒绝投递；正文或锚点变化则保留旧引用，结果不得自动改正文。提交线程时只追加到已验证的同一线程，不以整篇正文版本冲突覆盖新跟帖。

## 4. 失败与恢复

| 情况 | 用户看到与允许的恢复 |
| --- | --- |
| 评论已保存、AI 未启动 | 用户消息保留，原处显示「助理未能开始」，重试复用请求身份，避免重复评论 |
| 模型失败/超时 | 明确失败原因、保留请求；重试由人点击，不自动付费重跑 |
| 结果已生成、评论提交失败 | 标为等待投递；先查同一运行的已存结果与投递回执，重试只投递，不重复调模型 |
| 停止/撤权/插件停用 | 旧运行不得再写任何业务记录；用户停止的状态通过独立授权的控制动作处理，不由已取消的调用补写 |
| Host 重启、状态不明 | 读已有 run 状态与投递记录后恢复；无法确认则显示待核对，不当失败直接重跑 |
| 原文或线程已删除 | 不转投当前页面；可查看运行说明，不提供失去授权的旧正文 |
| 草稿保存失败/存储不可用 | 保留当前输入，明确告知未保存；不把空输入替换回来 |

实现范围：

- 由 Manifest 的 `context_binding: "focused-object"` 接入侧栏，绑定实际焦点窗格的对象与单调 epoch，验证 iframe 来源。切页立即恢复对应草稿，再异步读线程，避免标题已经切换而旧草稿仍短暂显示。

- Pages 拥有持久线程、稳定 mark 锚点、消息与块备注。正文注释保持原样；只有显式讨论才复制为原批注消息。新 Home 使用 v2 基线，旧库明确拒绝，真实数据维护另行授权。

- dispatcher 保留原授权和动作注册实例用于后台投递，投递前再次校验。停止、撤权或注册实例替换后拒绝旧回复。Host 重启后只读取已有运行状态，由人明确重试投递，不自动重复调用模型。
