# 技术项目的 SSOT 与正交模块拆解

## 完成等级

内部完整：Molis Work 的内置软件开发方法和共享 Runtime Skill 会在复杂技术项目进入实现拆解前，先建立或核对项目级 SSOT、横纵模块地图和模块级 SSOT，并用产出消费关系与 Impact 写入面判断依赖和安全并发。现有可信文档可以复用，小型局部修复不被迫重建整套文档。

## 背景与目标

当前软件开发方法已经包含“产品计划 → 技术方案 → 基础能力 → 功能 → 验收”的结果链，也能通过 `depends_on` 表达真实产出消费，通过 Impact Binding 阻止两个 active Goal 同时写入同一权威区域。

但现有拆解仍缺少一个正式的“文档与边界落盘”阶段：

- 技术方案可能只存在于对话或某条 Goal 正文中，换 Session 后难以恢复完整上下文。
- Runtime 可能直接按前端、后端、数据库或文件夹拆 Goal，多个 Goal 实际共同决定同一状态或契约。
- 即使 Goal 标题看起来互不相同，也没有先说明各模块拥有的状态、公共契约、读写面和禁止修改范围。
- 共享基础的实现容易被设成所有功能的串行前置；实际上在契约稳定后，提供者和消费者通常可以用 test double、fixture 或兼容层并行实现，最后再集成。

本任务把技术项目的拆解顺序调整为：先形成可追溯的项目契约，再定义正交模块及各自 SSOT，最后从这些稳定边界派生实现 Goal。目标不是多写文档，而是减少共享决策和共享写入，让不同 Runtime 能安全并发。

## 真相边界

“SSOT”在本任务中不是再造一份 Molis Work 数据库：

- Molis Work 继续是 Goal、关系、决定、工作状态、Evidence 和 Review 的权威真相源。
- 仓库中的项目与模块 SSOT 是产品、架构、模块边界和公共契约的权威文档；它们由 Goal 作为可验收产物引用。
- 代码、测试、迁移和运行证据证明当前实现行为。文档与实现不一致时不能假装完成，必须修正文档、实现或提出 Rewire。

根项目文档只保存全局事实和模块索引，不复制每个模块的全部细节；模块特有事实只写在对应模块 SSOT，避免两个文档同时声明同一契约。

## 适用边界

必须使用完整流程：

- 新技术项目或重大产品能力；
- 涉及多个可独立交付模块的架构、迁移或重构；
- 多个 Runtime、Agent 或 Work Item 需要并发执行；
- 现有文档互相冲突、缺少明确边界，或实现需要改变跨模块契约。

可以复用现有 SSOT 并只做差异核对：

- 项目已有可信、当前且可追溯的项目与模块文档；
- 变更只影响一个已定义模块，没有改变公共契约或共享状态所有权。

局部诊断、机械修改或范围明确的小修复不强制新建全项目文档。若执行中发现跨模块影响、契约变化或写入冲突，立即回到本流程。

## 拆解流程

### 1. 建立或核对项目级 SSOT

项目级 SSOT 至少回答：

- 项目结果、用户或调用主路径、范围与非目标；
- 当前系统上下文、全局约束和必须维持的不变量；
- 关键状态、数据和跨模块决定的唯一权威位置；
- 模块目录、每个模块的横纵类型、职责、SSOT 引用和依赖方向；
- 跨模块公共契约、关键决策、迁移/发布/恢复规则；
- 文档如何被代码、测试和 Evidence 验证。

若这些内容已经存在，Runtime 读取并核对来源、时效和互相一致性，不能为了形式重复创建第二份 SSOT。

### 2. 用横纵两条轴建立模块地图

模块类型不是文件夹标签：

- **纵向模块**：负责一条可观察的端到端用户或调用结果，可以从入口走到结果并独立验收。例如“用户完成账号恢复”，而不是“账号页面”。
- **横向模块**：向多个纵向模块提供稳定、可复用的能力或契约，例如身份、权限、事件、存储、评测或发布能力。只有确实被多个消费者使用时才独立成横向模块。

每个重要状态、公共契约、决策面和可变数据只能有一个权威模块。一个模块可以读取另一个模块的产物，但不能绕过公共契约共同维护同一状态。无法明确唯一所有者的重叠必须在实现 Goal 创建前解决或显式串行化。

不要机械地把 UI、API、数据库、测试、平台目录或团队分工各自变成模块。它们可以是同一个纵向结果内部的实现层，也可以在确有多个消费者时成为横向能力。

### 3. 分别撰写模块级 SSOT

模块地图和全局不变量稳定后，各模块 SSOT 可以并行撰写。每份模块 SSOT 至少包含：

- 模块结果、消费者和不负责的内容；
- 独占拥有的状态、数据、决策和公共契约；
- 输入、输出、接口、事件及兼容承诺；
- 消费哪些其他模块产物，以及下游如何消费本模块产物；
- 允许读取、写入、决策或独占的 Impact surfaces；
- 主路径、异常、迁移、恢复、测试与验收；
- 未决问题、来源引用和需要重新核对的触发条件。

模块 SSOT 是实现 Goal 的输入，而不是实现本身。文档 Goal 的完成证据必须包含可读取的产物引用和正交性核对结果。

### 4. 做正交性与并发审查

在实现 Goal 进入 Goal Tree 前，逐项检查：

1. 每个状态、数据、公共契约和决策面是否只有一个写入或决定所有者；
2. 模块间依赖是否都能说清“提供者产出 → 消费者用途”；
3. 是否存在循环依赖、双向内部知识、共享可变状态或两个 SSOT 声明同一事实；
4. 并行 Goal 的 Impact 写入面是否互斥；若重叠，能否通过重新划界消除，否则必须建立真实依赖或显式独占；
5. 每个纵向模块是否仍能独立完成一条真实主路径，而不是被技术层切碎；
6. 横向模块是否有至少一个真实消费者，且没有成为“所有公共代码”的垃圾桶。

“文档已经分开”不等于正交。正交的证据是唯一所有权、稳定契约、单向消费和无冲突写入面。

### 5. 从 SSOT 派生执行 Goal

- 项目级 SSOT 或其差异核对先于模块边界决定。
- 模块地图稳定后，各模块 SSOT Goal 可以并行。
- 每个模块实现 Goal 依赖自己的模块 SSOT，以及它实际消费的公共契约。
- 提供者实现和消费者实现只要共享契约已稳定，并且消费者能使用 test double、fixture 或兼容层，就保持并行；不要把“提供者实现完成”机械设成消费者实现的前置。
- 集成与端到端验收 Goal 同时依赖提供者和消费者的可运行产物。
- 实现 Goal 的 Impact surfaces 来自模块 SSOT；Claim 时继续使用现有 Impact 冲突门禁。

## 文件与模块边界

- `PRODUCT.md`：把技术项目的 SSOT、模块正交和并发规则写入产品 Contract。
- `src/planning/method-packs.ts`：更新内置“软件开发”方法的步骤、覆盖项、依赖规则、证据、收口检查与误拆提醒。
- `skills/goal-advance/SKILL.md`：在核心 planning loop 中增加技术项目的文档架构关口。
- `skills/goal-advance/references/planning.md`：提供完整的项目/模块 SSOT、横纵模块和并发派生规则。
- `tests/planning-engine.test.ts`：验证内置方法暴露新的覆盖项、依赖语义和完整 Runtime 指南。

本任务不新增数据库表、Goal 状态、第二套 Plan 实体或文件生成器。现有 `decomposition_review.coverage` 可以记录新增覆盖项，Goal 的 `required_inputs`、`promised_outputs` 和 Acceptance Criteria 可以表达 SSOT 产物，现有 Impact Binding 继续承担运行时冲突门禁。当前 Runtime MCP 不直接开放 `impact_add`；能随 Contract/Candidate 提议的 Impact 继续走用户确认路径，其余 Impact 由用户在现有 Web/管理入口确认登记，未登记前相关 Goal 不得按“已证明正交”并发领取。

## 非目标

- 不规定所有仓库必须使用同一目录名或 Markdown 模板文件名。
- 不自动生成整套项目文档或扫描代码后自行认定架构事实。
- 不把项目级 SSOT 变成复制所有模块细节的巨型文档。
- 不用“横向/纵向”标签自动推断依赖；依赖仍由真实产出消费决定。
- 不保证所有工作都能并行；存在同一决策面、不可分割迁移或真实运行前置时必须串行。
- 不把写完文档当作产品功能完成。

## 验收标准

1. 内置“软件开发”方法明确要求在复杂技术实现拆解前建立或核对项目级 SSOT、横纵模块地图、模块级 SSOT 和正交性审查。
2. 方法的必须覆盖项分别包含项目 SSOT、模块地图、模块 SSOT 与并发写入边界，能够进入现有 `decomposition_review.coverage` 门禁。
3. 方法明确区分纵向端到端结果与横向共享能力，并拒绝按 UI/API/数据库/文件夹机械拆模块。
4. 依赖规则表达：实现消费模块 SSOT；消费者消费提供者契约；契约稳定后提供者与消费者实现可以并行；集成验收再依赖双方实现。
5. Runtime Skill 明确要求先复用现有可信文档，只有缺失或失效时才创建/更新；小型局部修复不被迫重建全项目文档。
6. Runtime Skill 要求模块 SSOT声明唯一所有权和 Impact surfaces，并在并行前解决两个 Goal 的写入/决策重叠。
7. Product Contract 清楚区分 Molis Work 工作状态、仓库 SSOT 和代码/测试三类真相，避免第二套状态源。
8. 既有方法包组合、依赖图和 Goal 生命周期保持兼容；定向测试、类型检查、完整测试与构建通过。

```bash
pnpm test

git diff --check
```

人工核对一个包含共享身份能力和两个端到端用户流程的样例：项目 SSOT 先固定全局边界；身份、流程 A、流程 B 的模块 SSOT 可以并行；三份实现消费同一稳定契约后可并行；集成验收等待三份实现；任意两个实现若声明写入同一权威 surface，Claim 冲突会阻止并行。

## 假设与取舍

- 首版先把该逻辑作为专业规划方法和 Runtime 行为 Contract 落地，不新增结构化模块实体。真实使用出现多次漏报或不可解释的并发冲突后，再评估是否把 module/SSOT/ownership 提升为独立领域模型。
- 横纵模块是发现正交边界的思考工具，不是固定目录结构或两层树。
- 先稳定契约、再并行实现比“所有基础实现完成后再做功能”更能提高并发，但前提是 test double 或兼容层足以让消费者独立验证；否则保留真实硬依赖。
