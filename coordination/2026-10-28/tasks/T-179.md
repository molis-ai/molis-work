## 1. 背景

「AI 生成题目」（`form.questions.draft`）把请求与（有的话）回答发给模型，模型回 JSON：

- `{ status: "done", questions }`：`drafted()`（`drafting.ts:46-56`）逐题取标题、类型、选项，任何一题不合格就抛 `form.invalid`「模型没有返回有效题目，请调整提示后重试」，整份不写入；合格的由动作处理函数追加进问卷（`actions.ts:113` 的 `store.update`，再过一遍 `store.ts` 的 `normalizeQuestions`）；
- `{ status: "needs_input", why, questions }`：`asked()`（`:70-87`）取先问的问题，`why` 在 `draft()` 里取（`:136`），连同问题一起返回，宿主画成共享问卷卡。

模型被告知的格式里只有题数和选项个数，没有任何文字长度上限（`prompts.ts:11-15`），所以字数全由这里截或查。三处现在的写法（T-164 头原样）：

```ts
// :51 选项文字
const options = Array.isArray(item.options) ? item.options.filter((label): label is string => typeof label === "string" && !!label.trim()).map(label => ({ label: label.trim().slice(0, 120) })) : [];
// :53 标题
if (!title || title.length > 200 || !type || (choice && (options.length < 2 || options.length > 12))) throw formErrors.invalid("模型没有返回有效题目，请调整提示后重试");
// :136 先问的说明
const why = typeof reply.why === "string" && reply.why.trim() ? reply.why.trim().slice(0, 300) : "生成前想先确认几件事";
```

`.length` 与 `.slice(0, N)` 数 UTF-16 单元；`🟢` 是一个字、两个单元。

每一处下游怎么数：

| 处 | 下游 | 证据 | 结论 |
| --- | --- | --- | --- |
| `:53` 标题 | **数字**。入库：`[...title].length > 200` 抛「题目标题须为 1 到 200 个字」；题目的 schema：`title: { ...text, maxLength: 200 }` | `store.ts:414`；`actions.ts:16`（`questionFields`，记录与输入共用）。AJV 的 `maxLength` 默认数码点（即字）：内核的 AJV 选项（`packages/kernel/src/action-schema.ts:41-42`）没有改它。用 `packages/kernel` 里的 ajv 8.20.0 一次性试过：200 个 `🟢` 通过、201 个不通过（探针没有入库，第 8 节第 4 条） | 按字查。现在 100 个以上 `🟢` 的标题（200 个字以内）就被起草拒掉，库其实收 |
| `:51` 选项文字 | **不数**。入库的选项文字只 `trim()`，没有上限；schema 的 `optionFields` 里 `label` 没有 `maxLength`。填写时答案是选项文字原样，整体按字数查回答（`FORM_ANSWER_LIMIT` 4000），多选的答案是选项文字用 `\n` 连起来再与允许的集合逐个比 | `store.ts:418`；`actions.ts:15`；`store.ts:450-454`；`fillpage.ts:5` | 没人按单元数它。按整字截 120，不劈字 |
| `:136` 说明 | **不数**。合同只说它是「卡片的标题」，没有上限；宿主只查它是字符串，再整段当卡片的问题文字画出来 | `agent-interaction.ts:165`（`InteractionRequest.why`）；`plugin-interaction-answer.ts:12`（只查类型）、`:27`（`prompt: interaction.why`）；`agent-question-card.ts:98`；`packages/design-system/src/interaction.ts:211`（`esc(view.title)`） | 没人按单元数它。按整字截 300，不劈字 |

库里没有长度约束：`database.ts:25`、`:40` 的 `questions_json` 是 `TEXT NOT NULL`，没有 `CHECK`。

## 2. 目标

1. 起草出的标题，200 个字以内（不论含不含两单元字）收；201 个字整份拒收，报错与现在一样（`form.invalid`「模型没有返回有效题目，请调整提示后重试」），不写入。
2. 起草出的选项文字，不超过 120 个字的原样；更长的按整字截到 120 个字，不留半个字。
3. 先问的说明，不超过 300 个字的原样；更长的按整字截到 300 个字，不留半个字。
4. 用例钉住上面三条：改回按单元、上限差一（放宽、收紧）各自都红（第 6 节九个变异）。

2. **`tests/form-draft-questions.test.ts`**：在文件末尾（T-164 头的 `:155` 的 `});` 之后）空一行，原样加下面三个用例。`fixture`、`Drafted`、`assert`、`test` 文件里已有，不加 `import`；`wide` 在每个用例里自己定义（同 RAC-1667、RAC-1699 的写法，不提到文件顶部）。

   ```ts
   test("RAC-1849 a drafted question's title is counted in Unicode characters like the store: 200 are drafted whole, 201 refuse the draft", async t => {
     // The store (src/store.ts normalizeQuestions) and the question schema (src/actions.ts questionFields) count a title in characters; one 🟢 is one character but two
     // UTF-16 units, so `title.length > 200` refused a title of 101 to 200 characters that holds them as "the model returned no valid question".
     const wide = (count: number) => "🟢".repeat(count);
     const f = await fixture(t, [{ status: "done", questions: [{ title: wide(200), type: "text" }] }, { status: "done", questions: [{ title: "b" + wide(200), type: "text" }] }]);
     const done = await f.call({});
     assert.equal(done.status, "done");
     assert.deepEqual(done.form.questions.map((question: { title: string }) => question.title), [wide(200)], "a 200-character title is drafted and kept whole");
     await assert.rejects(f.call({}), { code: "form.invalid", message: "模型没有返回有效题目，请调整提示后重试" }, "201 characters is past the limit, refused by the draft itself");
     assert.equal(f.heard.length, 2, "the second reply did reach the model");
     assert.equal(f.forms.get(f.form.id, "p").questions.length, 1, "and wrote nothing");
   });

   test("RAC-1850 the option labels it drafts are cut in whole characters at 120, and a label of exactly 120 characters is kept whole", async t => {
     // A label is counted nowhere downstream (src/store.ts normalizeQuestions, optionFields in src/actions.ts), so it is cut at 120 characters, not 120 UTF-16 units: one
     // 🟢 is one character but two units, and a cut by units left half of one in the label.
     const wide = (count: number) => "🟢".repeat(count);
     const f = await fixture(t, [{ status: "done", questions: [{ title: "选一个", type: "singleChoice", options: ["a" + wide(130), wide(120), "c"] }] }]);
     const done = await f.call({});
     assert.equal(done.status, "done");
     assert.deepEqual(done.form.questions[0]!.options?.map((option: { label: string }) => option.label), ["a" + wide(119), wide(120), "c"],
       "a label past 120 characters is cut to 120 whole characters; one of exactly 120 and a short one are kept");
   });

   test("RAC-1851 the reason it gives for asking first is cut in whole characters at 300, and a reason of exactly 300 characters is kept whole", async t => {
     // `why` is the shared card's question text (InteractionRequest.why) and counted nowhere downstream, so it is cut at 300 characters, not 300 UTF-16 units.
     const wide = (count: number) => "🟢".repeat(count);
     const reply = (why: string) => ({ status: "needs_input", why, questions: [{ id: "size", prompt: "要几题？", options: [{ label: "3 题" }, { label: "5 题" }] }] });
     const f = await fixture(t, [reply(wide(300)), reply("a" + wide(300))]);
     assert.equal((await f.call({})).interaction.why, wide(300), "a reason of exactly 300 characters is kept whole");
     assert.equal((await f.call({})).interaction.why, "a" + wide(299), "a longer one is cut to 300 whole characters");
   });
   ```

   这三个用例为什么成立（写进【方案】，PR 里也写）：
   - 写法都有先例：`fixture(t, replies)` 按顺序给 `completeText` 回复，`f.call({})` 调处理函数（`:31-42`）；`assert.rejects(…, { code, message })` 与 `f.heard.length`、`f.forms.get(f.form.id, "p")` 是 RAC-1667 的写法（`:129-141`）；局部的 `wide` 与 `needs_input` 回复的写法是 RAC-1699 的（`:143-155`）；`id: "size"` 的问题与 `ASK` 里的一致，过 `asked()` 的完整性检查（`:83`）；
   - 第一个用例的数：
     - `wide(200)` 是 200 个字、400 个单元；`title.length > 200` 拒它，`[...title].length > 200` 收它；入库 `[...title].length` 是 200，收；
     - `"b" + wide(200)` 是 201 个字、401 个单元，两种写法都拒；报错信息是起草自己的，不是入库的「题目标题须为 1 到 200 个字」，所以比较 `message` 能抓住上限放宽（M2）；
     - 第一次调用收下一题，问卷有 1 题；第二次被拒，仍是 1 题；
   - 第二个用例的数：
     - `"a" + wide(130)` 截到 120 个字是 `"a" + wide(119)`；按单元截则是 `"a"` 加 59 个 `🟢`（118 个单元）加一个孤立的高位代理 `"\ud83d"`，共 120 个单元；
     - `wide(120)` 是 120 个字、240 个单元，新写法原样；按单元截则是 `wide(60)`；
     - `"c"` 原样；
     - 三个选项过 12 个以内、2 个以上的检查；
   - 第三个用例的数：
     - `wide(300)` 新写法原样，按单元截是 `wide(150)`；
     - `"a" + wide(300)` 是 301 个字，新写法截成 `"a" + wide(299)`，按单元截是 `"a"` 加 149 个 `🟢` 再加 `"\ud83d"`；
     - 两次调用都不带 `interaction`，各自是一次新的起草，第二次不受第一次留下的待答记录影响；
   - 进程内直接调处理函数，没有内核的输出检查，所以 AJV 数码点这个前提不由这三个用例证明（第 8 节第 4 条）。
