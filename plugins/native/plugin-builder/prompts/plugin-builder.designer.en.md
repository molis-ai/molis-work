## Input and output shorthand

Basic types: string, integer, number, boolean, date, datetime and url. Ranges include string(1..500) or integer(1..5). An explanatory label follows a space, e.g. "string(1..500) Note text". Enum: "unread|reading|read"; list: "string[]"; object: {"title":"string(1..100) Book title","rating?":"integer(1..5) Rating"}; object list: [{"id":"string","title":"string"}]. A question mark after the key makes it optional. Keys use Latin letters, digits and underscores; each record has a plugin-generated string id. Types may also carry constraints or hints such as number(>0), integer(1..5) and string(YYYY-MM).

## Operations in detail and revise

A complete operation looks like {"id":"notes.add","kind":"command","description":"Save a note","input":{…},"output":…,"effects":{"storage":["read","write"]},"errors":[{"code":"not_found","description":"Note not found"}],"examples":[…]}.

- Use query for a read, command for a change. Queries cannot write storage. Use storage ["read"] or ["read","write"] for the plugin's store.
- Use platform capabilities only from capabilities or moreCapabilities. The former contains relevant schemas; the latter lists examples by source. Declare effects.capabilities only where the operation really calls it, e.g. {"storage":["read","write"],"capabilities":["model.generate"]}. An empty capability list means private storage only, without network, model or other plugins.
- model.generate is replaced in examples and UI acceptance by a fixed stand-in: text = "［模型替身］" followed by the first 40 characters of input. Use includes for structure or saved content and check the stand-in in UI acceptance, e.g. expect answers ［模型替身］.
- Each operation needs at least one example; its examples run in sequence on its own empty store. A read on empty storage returns empty data: {"input":{},"output":[]}. For creation use includes when output contains random IDs: {"input":{"text":"Buy milk"},"includes":{"text":"Buy milk"}}. An edit or deletion on empty storage must give a not_found example and declare the error. Test successful edit or delete in acceptance.

## Pages

Use pages such as [{"id":"home","title":"Quick notes","parts":[…]}]. Usually one page is enough; add pages only for actual workflow steps. If records already include the full text, use idField, titleField and textField to show a directory and detail. Do not add a query or part just to read a selected record again. A selection: reference names a real part on the same page, not an operation or a generic word like list.

Valid intents: heading, description, input (entry/edit), action (operate on a selected record), collection (the system chooses a list, cards, table, accordion or calendar), reading, conversation, evidence, schedule and feedback. Example: {"id":"editor","intent":"input","purpose":"Write a note","props":{…},"submit":"notes.add"}.

- collection, reading, evidence and schedule read a query with array output: "read":"query.id". An input submits a query or command and its fields come from the operation input. An action can submit {"op":"notes.remove","input":{"id":"selection:notes.id"}}. An action with all input from one collection appears as a button on each row. Use an action label such as Delete or Mark as read, not Delete selected. Acceptance still selects the record before submit.
- A query after filling fields submits from that same form, without using another form's draft. Text/body/content fields support multiple lines. An empty string is allowed when the contract allows it; required means the key exists. Query shows the complete returned object with labels and preserves input; a later query replaces the result. Use show for one returned field. Acceptance should check visible fields and values, not raw JSON.
- Show command results: {"op":"concepts.ask","show":"question"} displays that result field below its part. To take a result or selection into an editable field, map just that field, e.g. {"op":"concepts.add","input":{"question":"prefill:asker.question"}}. The user fills the rest normally. For a generated question, show the question then prefill it in the answer form; include any related concept in the command result when it must carry forward.
- For totals use a query that returns an object such as {"total":"number Total this month","byCategory":[{"category":"string Category","amount":"number Amount"}]}. Use description for labelled values and small tables for nested lists. Keys remain English. Category values go in records, not keys.
- A collection can bind query input to a control: {"op":"books.list","input":{"status":"form"}}. The filter appears above the list and changing it rereads. Use an optional "status?" field for a selectable “All”. Verify with fill books.status = reading. Do not add a filter part or action.
- The only props are title, description, submitLabel, requiredText, emptyText, idField, titleField, textField and columns. Columns specify field and label; for booleans or enums values may map {"true":"Checked in","false":"Not checked in"}, otherwise booleans use Yes/No. Example collection props: {"idField":"id","titleField":"title","emptyText":"No records yet"}. Give intent only; the system chooses a component from legal catalog candidates.

## Acceptance in detail and revise

Every case starts empty. Its steps contain real browser actions and at least one assertion. Supported string shortcuts: "fill editor.text = Learn spaced repetition", "submit editor", "select notes Learn spaced repetition", "expect notes Learn spaced repetition", "expect-not notes Incorrect", "expect notes New note before Old note", "page home", "reload". To clear a filter use fill list.field = "", never reset or clear.

For fixed UI wording, use {"action":"expectWord","componentId":"notes","word":"emptyText"}. The word value names a declared props property on that component. Use expect strings for record text. A missing-record error belongs in the operation’s examples as {"input":{"id":"missing"},"error":"not_found"}. The browser cannot select a missing record. That object is not a browser step. For a negative form case use {"action":"submitBlocked","componentId":"editor","field":"text","reason":"valueMissing"}. This makes the real click and checks required refusal and no submit call; requiredText is a real hint, not a substitute successful submit. A failure in an isolated acceptance case can use {"action":"faultRead","componentId":"notes"} to fail the next read of the bound query. Verify the shared error, absence of the old empty state and the real {"action":"retry","componentId":"notes"}. Check preserved input with {"action":"expectValue","componentId":"editor","field":"text","value":"Original text"}. Write these actions as JSON objects with an action property. Their exact fields are shown above. They have no string shortcuts and accept no scripts, URLs, error copy or returned values. A description does not inject a fault. Ordinary submit still has to succeed. Reload does not mean upgrade or Host restart.

When input includes uiText, put the complete uiText inside design. Copy each available tag exactly as a locales key. For new designs use the requested tag as default when available, otherwise use the input default. Preserve the default and tags on revision. Finish the pages and bindings first, then give every language the exact slots those declarations need. Bind a list’s filter on the list itself and give it no separate filter part or slots.
