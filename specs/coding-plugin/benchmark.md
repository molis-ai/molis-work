# Coding App 对照清单：参照产品、FlyLeaf 可用能力、我们现在、差距

2026-09-25。为当前目标（§0“当前目标（2026-09-25）”）动手前的对照：每块写参照产品怎么做、FlyLeaf 有什么能直接借用、我们现在做到哪、差距与验收方式，最后按对用户的价值排序。

参照：Claude Code（CLI 与桌面）、Codex（桌面 App 与 CLI）、Cursor（3.x Agents Window）。FlyLeaf（`~/code/flyleaf`，只读）不是完整产品，只看有没有能直接借用的能力。外部产品信息来自公开资料与发布说明，截至 2026-09；个别细节以各产品当前版本为准。

---

## 1. 子代理

**参照产品**
- Claude Code：
  - 子代理有独立上下文、专属提示和工具权限，可以自定义角色；
  - 可以后台并行，结果以摘要回到父任务；
  - Agent Teams 让多个会话直接互发消息、共用任务清单，用户可以用快捷键切到任一成员查看。
- Codex：每个线程配一个 git worktree，多个线程并行；每个线程的 diff 单独审查。
- Cursor：
  - 最多 8 个 Agent 并行，各自在 worktree 或云端；
  - `/multitask` 拆成异步子代理，`/best-of-n` 让同一任务在不同模型上并跑，结果并排对比。

**FlyLeaf 可借用**
- `plugins/coding-agent/src/subagents.ts`：子任务行带 worktree 分支和基线提交，以及"查看变更 / 准备整合"。
- `writers.ts`：并行写入的协调。
- Git 插件：`integrate-worktree` 和 `resolve-conflict`。

**我们现在**
- SDK 子任务分两类：只读，以及独立目录写入（coding-builder）。独立工作树的创建要经宿主审查；同步等待超时已修复。
- 右栏子任务列表有状态、结果、用量，能停止、接受或返工，能"查看成果并整合"，但只能整合选定文本。
- 子任务过程在右栏只是一行行"名称 · 状态"，对话里看不到子任务。

**差距**
1. 对话里没有子任务卡片，看不到每个子任务的实时时间线（工具调用、审查请求）。
2. 不能单独重试。
3. 没有每个子任务的预算。
4. 不能并排对比多个子任务的结果。
5. 工作树成果不能用变更阅读器按文件看，也不能整文件整合；冲突不可见。
6. 父任务汇总质量差：有漏读报告、误述的实例。提示层与界面要把"子任务结论 + 原报告"交到父任务和用户手里。

**验收**：用真实模型拆出 2–3 个子任务并行写入独立工作树。过程中逐个停止、重试、返工；整合时至少遇到一次冲突并在产品里解决。全程不靠外部修正。

## 2. 计划与 TaskBoard

**参照产品**
- Claude Code：
  - Plan 模式只读规划，获批后再执行；
  - 待办清单随执行实时勾选；
  - Agent Teams 的任务清单有依赖、认领、状态，`Ctrl+T` 查看。
- Codex：计划清单实时更新。
- Cursor：Plan 模式先产出可编辑的计划再动手，Agent 面板里的待办实时更新，可以排队追加要求。

**FlyLeaf 可借用**：没有独立的 TaskBoard。

**我们现在**
- 完整路径已实操：计划草稿 → 调整 → 确认并固定 → 按步骤执行 → SDK 任务板回报 → 用户逐步评价 → 返工带入下一版。
- 左栏 TaskBoard 能导航到草稿、原执行、固定计划和子任务评价。
- 执行时模型只能读写本轮的图。

**差距**
1. 对话里看不到步骤进度：没有 Claude 或 Cursor 那样实时勾选的清单。
2. 人不能在执行中插队、跳过、重排并留痕。
3. 阻塞和变更不会回流到计划。
4. 并行子任务和步骤之间没有认领关系。
5. TaskBoard 还只是左栏投影，不是查看和推动长任务的主视图。

**验收**：用真实模型执行一个 4–6 步的计划。中途插队一步、跳过一步；一步失败后返工；重启后继续。各步状态都来自执行事实。

## 3. 中断与恢复

**参照产品**
- Claude Code：`--continue` / `--resume` 续上会话，Esc 中断后可以接着说；检查点可以连同对话一起回退。
- Codex：线程可以恢复；云端任务断网后照常进行。
- Cursor：检查点可以还原；云端 Agent 在电脑合上后继续跑。

**FlyLeaf 可借用**
- `recovery.ts` / `recovery-view.tsx`：核对视图。
- 桌面端 `BackgroundTasks.tsx`：跨工作区的后台任务清单，列出状态（包括"需要核对结果"），能一键跳回原任务或原审查。

**我们现在**
- 强杀或重启后，正文、工具结果、问题和草稿都保留。
- 右栏可以"重新核对 / 结束中断轮次"；结果未知的操作会阻止收口；下一轮历史里带着核实过的事实。
- Esc 可以停止。
- SDK 有暂停相关的阶段。

**差距**
1. 没有"一键从断点继续"。现在要先结束中断轮次，再手动发下一轮，而且模型常把历史理解错。
2. 模型报错、超时、断网后，没有清楚的原因说明和重试入口。
3. 界面没有暂停 / 恢复入口。
4. 没有全局"后台任务"清单：看不到哪些会话在跑或在等你，也不能一键跳过去。

**验收**：六种中断各实测一次——用户停止、模型报错、超时、断网、强杀、重启。每次核对后一键继续：已执行的写入和命令零重复，草稿、问题、审查和成果不丢。长任务暂停后恢复，上下文正确。

## 4. 会话之间互相调用与查看

**参照产品**
- Claude Code：Agent Teams 让会话之间直接发消息、共用任务清单；桌面端能列出本机其他会话并给它们发消息。
- Cursor：可以 @ 引用过去的对话；Agents Window 可以并排查看多个 Agent。
- Codex：以项目和线程组织，线程之间互相引用较弱。

**FlyLeaf 可借用**：Cooperation 协议（`docs/product/architecture.md` §5）。
- 三种关系：引用（只读的固定版本引用，失效时明确显示）、委派、交付。
- 状态机：已收到 → 已送达 → 已接受 → 写入中 → 完成，另有拒绝、失败、取消、过期。三个状态各有回执，"送达 ≠ 接受 ≠ 完成"。
- 接收方有拒绝权；跳数有上限；重启后核对原结果，不重新派发。

**我们现在**
- 会话之间严格隔离：计划和任务图的读写一律拒绝跨会话。
- 固定成果能经 Shelf 副本间接成为材料。
- TaskBoard 下拉可以切换会话。

**差距**：在一个会话里看不到其他会话的进度，不能直接引用其他会话的固定成果，不能委派给另一个会话再收回结果。

**改动方案（需要你拍板，见文末）**
- **A 引用**：在"+ 材料"里选择"其他会话的固定成果"（固定变更、报告、计划），按固定版本冻结进本轮；来源失效时明确不可读。
- **B 查看**：会话里加"相关会话"面板，只读显示其他会话的状态和最近成果。这是宿主投影，不交给模型。
- **C 委派**：在会话 A 选"委派给新会话"，生成一份带来源的任务草稿，不自动执行；对方完成后，把固定成果"交付"回 A，由 A 的用户接受或拒绝。沿用 FlyLeaf 的状态机与回执，全部留痕。
- **D 模型侧**：默认不开放任何跨会话工具。可选：只读取"用户已明确授权的会话成果"。

**验收**：用真实模型完成一个任务：在 A 引用 B 的固定变更，把一个子任务委派给 C，并收回 C 的交付。重启后回执和状态不变。

## 5. 长任务与上下文

**参照产品**
- Claude Code：自动整理、`/compact`，`/context` 查看上下文占用，`/cost` 查看费用。
- Codex：自动整理，显示用量。
- Cursor：显示上下文占用、自动摘要，有费用面板。

**我们现在**
- 上下文整理（Prompt v2，连续整理的问题已修）。
- 用量分输入 / 输出 / 缓存读取显示，未知的不填 0。
- 执行上限固定为 60 轮（计划任务另算），用户不能设。
- 界面约 350ms 读取一次**完整**会话；长会话的性能没测过。

**差距**
1. 读取没有增量或分页，长会话没有虚拟化渲染；几百轮时既卡又费。
2. 看不到上下文占用。
3. 用户不能设预算（轮数 / 费用），到限时也没有说明和继续入口。
4. 没有费用估算（未知时说未知）。

**验收**：造一个 300 轮以上、工具输出很多的会话。首屏加载和滚动流畅（给出实测数字），单次刷新的数据量与会话长度无关。设一个预算，到限后说明清楚并可以继续。

## 6. 工具与工程流程

**参照产品**
- Claude Code：Git 靠命令完成，`gh pr create`；自定义斜杠命令、hooks、MCP、Skills。
- Codex：从 diff 直接建 PR，`/review`。
- Cursor：生成提交说明、源代码管理面板、BugBot 审 PR。

**FlyLeaf 可借用**：Git 插件把以下操作都做成要经审查的操作——建分支、切分支、建工作树、提交、按文件提交、fetch、pull、push、解决冲突、继续合并、整合工作树（`plugins/git/src/host.ts`）。

**我们现在**
- Git：状态、暂存 / 取消暂存（经审查）、固定差异、工作树、未知结果核对。
- 方法 / MCP / Character 可以选择并随本轮冻结。
- 检查点回退经审查。

**差距**
1. 不能提交（含提交说明生成）。
2. 不能建分支、切分支。
3. 不能 push 或建 PR。push 和 PR 要用远端凭据，属于权限决定。
4. 冲突解决不在产品里。

**验收**：在产品里完成"改动 → 暂存 → 生成并确认提交说明 → 提交 → 建分支"，每一步都经审查。push 和 PR 等你决定后再做。

## 7. 体验

**参照产品**：三者都有代码和 diff 高亮、@ 引用文件或符号、斜杠命令、逐字流式输出、完整的快捷键（切换会话、命令面板）。Cursor 和 Codex 能并排看多个 Agent。

**FlyLeaf 可借用**：`CommandMenu.tsx`（命令面板）、`WorkspacePanes.tsx`（分栏）、`desktop-commands.ts`。

**我们现在**（见 §0）：
- 时间线、就地审查、变更侧栏、净变更、结果面板；
- 约 350ms 刷新、书写光标；
- Esc 停止、↵ 批准；
- 深浅色与窄屏已核对。

**差距**
1. 没有语法高亮。
2. 没有 @ 文件引用，也没有斜杠命令菜单。
3. 不是真正的逐字推送。
4. 没有切换会话、命令面板等快捷键。
5. 中文输入法、读屏软件没实测。
6. 没和三者逐项走查。

**验收**：逐项对照走查并留截图；中文输入法与 VoiceOver 实测记录。

## 排序（按对你的价值）

排序依据：你最后的验收任务要同时用到子代理、计划、中断恢复和跨会话引用，所以这四块排在前面。其中恢复是长任务的地基，排第一。

1. **中断与恢复**：一键从断点继续，出错时说明原因并能重试，暂停 / 恢复，全局后台任务清单。
2. **计划与 TaskBoard**：对话里实时显示步骤进度，执行中插队、跳过、重排并留痕，阻塞回流，TaskBoard 作为主视图。
3. **子代理**：对话内子任务卡片和实时时间线，单独重试，预算，工作树成果按文件审查和整合，冲突处理。
4. **长任务与上下文**：增量读取和虚拟化，上下文占用，可设预算。第 1–3 块会让会话变长，这一块要跟上。
5. **会话之间**：方案 A–D，**等你拍板后再做**。
6. **体验差距**：高亮、@ 引用、斜杠命令、快捷键和命令面板、逐字推送、输入法和读屏实测。其中改动小的会穿插在前几块里一起做。
7. **Git 流程**：提交、分支、冲突解决；push 和 PR 等你决定。

## 用户拍板（2026-09-25）

- 顺序：按上面的排序做。
- 跨会话：做方案 A、B、C，不开 D（模型拿不到任何跨会话工具）。委派出去的任务不会自动执行。
- Git：push 和 PR 都在产品里做，每次都经宿主审查。
- 预算：到达上限时只提示，不停下。
- thinking：还没定。

## 当时列出的待拍板事项

1. **跨会话规则**：方案 A–D 是否认可？D（模型读取用户已授权的会话成果）要不要开？委派是否允许自动启动对方执行（会产生费用）？
2. **Git push 与 PR**：是否在产品里接远端操作？用哪种凭据方式？
3. **预算默认值**：新会话默认给多少轮、多少费用上限？到限时是停下来问你，还是只提示？
4. **thinking**：是否为 MiniMax 开启推理（影响费用和速度）？开了"思考"时间线才会有内容。

## 协同：认领、任务图摘要、会话冲突、会话间通信（2026-09-26 你提出，方案待你看过再动手）

你的四项要求：

1. 任何任务都要有认领，看得出是谁在做。
2. 要有任务图摘要。
3. 会话之间的冲突要处理，由主 Agent 或人来协调。
4. 会话之间要能通信。例如 B 发现 A 在做某件事、判断自己依赖它，就把自己挂起，给 A 发请求；A 做完后通过事件唤起 B。其他协同场景也要考虑到。

这会改变"跨会话隔离"的规则（第 5 块定的是"模型没有跨会话工具"），所以先给方案。

### 二、用什么搭：全部用 SDK 已有的零件，不另起一本账

- **项目任务图**：用 SDK 的 TaskBoard，每个项目一张。
  - 每个会话正在做的事是一个节点，负责人记在节点上。
  - 会话之间的依赖是图上的边。前置完成时，图会自动把后面的步骤变成可以开工。
  - 每个会话自己那一轮的计划图照旧，只把"它在做什么"挂到项目图上。
- **认领租约**：用 SDK 的 claim 和宿主已有的租约（Node 宿主已经实现）。
  - 认领的对象可以是事项，也可以是文件范围。
  - 认领人挂了或长时间不动，租约就到期；在"能不能接手"上，沿用 SDK 已有的可重入判断，不自己猜。
- **信封**：用 SDK 的 delivery。
  - 类型有请求、回复、通知、交接、撤回请求、注入。
  - 回执分成已送达、已接受、已完成，也可能被拒、过期或撤回。
  - 被接受的信在对方下一轮最前面带入，并且标明"来自别的会话"。
- **唤醒**：任务图的状态事件，加上 SDK 的队列（到点唤醒、重启后照记录重挂）。
- **需要扩展 SDK 的两处**：
  1. TaskBoard 的负责人现在只能是一个角色，要能记"哪个会话、哪个子任务、还是人"。
  2. 信封现在只存在内存里，重启就没了；要持久化，这样等待和唤醒才能跨重启。
- 现有的委派记录在 Coding 插件自己的账里。最后一期迁到信封上，旧记录保持可读。

### 三、四项要求怎么做

**1. 认领：每件事都有负责人，而且看得见**

- **负责人有三种**：会话、会话里的子任务、人。
  - 计划步骤：默认负责人是这个会话。派出子任务时写明它负责哪几步，那几步的负责人就换成这个子任务，改派会留记录。
  - 你插入的步骤，可以写"由你处理"。
- **在哪里看**：
  - TaskBoard、后台任务清单、会话列表，每一项都显示"谁在做"。
  - 没人认领的事项单独列出来。
- **谁能报**：只有负责人能报这一步的进展。SDK 已经这样限制，别人报会被拒。
- **过期与接手**：认领带租约。会话中断或长时间没有动静，租约到期，事项变成"没人认领"，等主 Agent 或你改派。

**2. 任务图摘要**

- **每一轮开头**：系统提示词里放一份完整摘要，内容是：
  - 我负责的事项和它们的状态；
  - 我在等谁；
  - 谁在等我；
  - 待回复的请求；
  - 别的会话认领的、和我范围重叠的文件。
- **图有变化时**：运行中的这一轮会收到一条简短的变化说明，比如"会话 A 的『改接口』已完成"。沿用现在"已告诉执行中的这一轮"的同一条路。
- **不重复发**：图没变就不发，这样不会每一轮都多花 token，也不会破坏缓存。

**3. 会话冲突：先发现，再由主 Agent 或你来决定**

- **发现**，分三层：
  1. **开工时**：一轮开始时，把它要动的范围登记下来，包括计划里写到的文件和目录，以及派给子任务的目录，并和别人的认领比对。有重叠就先提示，不等写入时才发现。
  2. **写入时**：审查卡上写明"会话 A 正在改这个文件"，这次写入先停住。
  3. **事项层面**：两个会话做同一件事，比如关联同一个 Goal、或者认领了同一个事项，就标成"可能重复"。
- **协调选项**：
  - 让 B 等 A：自动加一条依赖，B 挂起。
  - 调整分工：改认领范围。
  - 照常并行：各用独立工作树，整合时再处理冲突。
  - 取消其中一个。
- **谁来协调**：这一项需要你定，见第六节的第 2 题。

**4. 会话间通信：发现、请求、挂起、按事件唤醒**

- **看得见**：模型多一个只读工具"项目在做的事"。它能看到每个会话的：
  - 标题；
  - 状态；
  - 负责人；
  - 认领的范围；
  - 当前步骤；
  - 公开的成果引用。

  它看不到别的会话的对话原文。
- **发请求**：模型多一个"给会话发信"的工具。
  - 类型有请求、回复、通知、交接、撤回。
  - 每一封都留记录，你随时能看、能撤回。
  - 对方如果正在跑，信在工具调用之间送到；如果空闲，放进对方的收件箱，等你或对方的下一轮处理。
- **挂起**：B 调用"等待"，指明等 A 的哪件事。
  - 项目图上加一条"B 依赖 A"的边。
  - B 这一轮带着"挂起：等会话 A 的『…』"结束，挂起期间不花 token。
  - 会话列表和后台任务清单都显示 B 在等谁。
- **唤醒**：A 的事项变成完成（任务图事件，或 A 把请求标成完成），宿主就唤起 B。唤起时带着"A 已完成，成果是……"开始下一轮，是否自动开始见第六节第 3 题。
- **跨重启**：等待关系在任务图上，信封持久化，唤醒排在队列里。重启后照记录核对：挂起期间 A 已经完成的，照常唤起 B。
- **信任边界**：别的会话发来的内容都当作数据，不是指令；不能代替你批准；不能要求对方做自己被拒绝的事。和 Claude Code 的规则一样。

### 四、其他协同场景

| 场景 | 怎么处理 |
|---|---|
| 依赖等待：B 等 A 做完 | 第三节第 4 项 |
| 提问：B 问 A 一个问题 | 请求信 → A 回复；B 可以挂起等回复，也可以接着做别的 |
| 变更请求：B 要 A 改接口 | A 接受后，在 A 的计划里插入一步（负责人是 A），B 等这一步；A 拒绝要写理由，B 和协调者看得到 |
| 交接：A 把后半交给 B | 交接信加改派负责人，成果引用一并带过去 |
| 重复工作：A、B 在做同一件事 | 事项层面冲突 → 协调者二选一，或者合并分工 |
| 同文件同时改 | 路径认领 → 写入时的冲突卡 → 协调 |
| 广播：公共接口或主分支变了 | 通知信发给认领范围重叠的会话，在它们下一轮开头带入 |
| 失败或取消的传播 | A 失败或取消 → 依赖它的 B 保持挂起，标成"前置失败"，由协调者决定 |
| 循环等待 | 任务图本来就拒绝成环：B 想等 A 而 A（间接）在等 B 时，等待失败，并告诉双方和协调者 |
| 认领了不做：会话挂了或长时间不动 | 租约到期 → 变成没人认领 → 改派 |
| 优先级和抢占 | 你把某件事提前，占用同一范围的会话收到"请让出"，由协调者安排 |
| 人工随时介入 | 你能看所有等待和请求，能代为回复、强制释放认领、改依赖、唤起或取消 |
| 子任务之间 | 同一轮里照旧由父任务协调；冲突检查把子任务的工作树也算进去 |
| 审计 | 认领、改派、信封、唤醒全部留记录；TaskBoard 上能看到时间线 |

### 五、分期与验收（按对你的价值排序）

每一期都做完、测完、真实模型实测过、提交推送后，再开始下一期。

1. **认领 + 任务图摘要**：
   - 内容：同一会话内的步骤和子任务要认领；项目任务图登记每个会话正在做的事；每一轮开头放摘要，图有变化时推送变化。
   - 实测：一个会话派两个子任务，TaskBoard 上每一步都显示负责人；中途改派一次；模型从摘要里说得出谁在做什么。
2. **会话之间看得见 + 冲突检测 + 协调入口**：
   - 内容：开工时比对范围、写入时出冲突卡、事项重复提示；你的协调入口；如果你定了主 Agent，也在这一期。
   - 实测：两个会话都去改 src/label.ts，开工时就收到提示；选"让 B 等 A"后生效。
3. **通信 + 挂起 + 唤醒**：
   - 内容：发信工具；等待和唤醒；信封持久化（SDK）；跨重启核对。
   - 实测：A 改接口，B 做依赖它的调用方。B 发现 A、发请求、挂起；A 完成后 B 被唤起并继续；中间重启一次服务，关系还在。
4. **其余场景 + 委派迁到信封**：交接、广播、租约到期、循环等待提示、优先级；把现有委派迁过来，旧记录可读。

### 六、需要你定

1. **模型能看到别的会话的什么**（改变跨会话隔离规则）：

   - 全部交给你，模型只给建议。
3. **被唤起时是否自动开始下一轮**（费用）：

4. **模型发请求、挂起自己时，要不要每次经你批准**（权限）：
