# 决定中心用户交互稳定性

## 背景与目标

用户在“待决定”中接受风险或应用 Goal 关系调整后，对应卡片会立即消失。权威数据虽然已经写入，但页面只显示一条短暂、笼统的成功提示，没有持续说明具体改了什么，也没有可靠入口去核对结果。用户因此会合理地判断为“保存没有生效”。

本任务让每次风险处理和关系调整都形成可核对的闭环：操作后立即说清结果，刷新页面后仍能看到最近结果，并能直接进入发生变化的 Goal 与具体记录。

本任务同时作为决定中心的稳定性封板：用户从“看懂事项”到“填写、保存、生效、核对、处理后续事项”的路径必须连续可用。任何来自 Runtime 提案的无效内部字段都要在用户提交前被识别；如果问题只是 Molis Work 已有的用户选择（例如风险处理类别），页面必须直接提供选择和保存入口，不能强迫用户退回 Runtime。只有确实需要重新澄清目标或关系的问题才交回 Runtime。

## 当前行为和问题证据

- Footballnia 项目中 `footballnia-risk-ai-variance` 已写为 `accepted`，事件 `risk.accepted` 也已存在，但它从待决定列表消失后，页面没有持久结果。
- 同项目 9 条 Rewire 已写为 `applied`，`impact_json.added_relation_ids` 对应的关系均为 `active`，但待决定页面只把卡片移除，未列出新增了哪些关系。
- 当前客户端回执只存在于本次页面 DOM；刷新、自动同步或重新进入页面后无法复核。
- 当前回执使用“关系已经调整”“风险处理方式已记录”等笼统文案，没有回答“具体改了什么、去哪里看”。
- Hearth 项目的原生 Goal Tree 提案包含 4 条 Risk，把一段具体处理措施写进了只允许 `accept / mitigate / avoid / defer` 的 `treatment` 字段。页面虽然现在能在提交前指出错误，却只允许“退回并要求修正”，没有让用户选择四种处理类别的入口；系统要求用户完成一个界面根本不提供的操作。
- Risk 记录只有枚举式“处理类别”，没有独立的“具体措施”字段。Runtime 因而容易把完整措施误填进类别字段；即使用户修正类别，原本有价值的具体措施也没有可靠保存位置。
- Hearth 这份方案同时缺少顶层 Goal 的完整拆解说明。风险选择应当允许先保存并进入修订版，同时准确保留“仍有 1 项需要 Runtime 补全”，不能把风险选择和其他阻塞混成一个笼统错误。
- 当前页面在已经明确指出方案结构无效后，仍要求用户填写“退回原因”。这是把 Molis Work 已经知道的问题再次交给用户转述，也让修正系统错误变成多余的表单任务。

## 范围

- 在待决定页面增加“最近处理结果”，由现有权威事件、Risk、Rewire 和 Relation 数据派生，不新增第二套状态。
- 覆盖 Goal 方案、目标说明、新发现的工作、Goal 关系、结果确认和风险处理六类用户决定。
- 每项结果显示：处理结果、具体影响、用户理由、处理时间，以及可核对结果的 Goal 入口。
- Rewire 结果列出实际新增/解除的关系；若记录为已应用但没有物化任何关系或风险，明确提示没有产生实际变更。
- 风险结果说明是否仍待处理、是否还会阻塞 Goal，并链接到 Goal 的风险记录。
- 对 `open → open` 的无状态变化使用专门说明：这是“继续待处理”，保存后仍会留在决定中心，不能伪装成已经处理完。
- 在最近一次处理之后新生成的待决定事项标记为“新事项”，避免用户把它误认为刚才没有生效的旧事项。
- 关系记录增加稳定锚点，使结果入口能定位到具体关系。
- 即时成功回执使用服务端返回的实际结果生成具体文案，随后由持久结果区承接。
- 原生 Goal Tree 提案进入决定中心前校验 Risk 的必填事实、处理类别和阻塞方式；未来无效提案在提交阶段直接拒绝，不再进入用户决定队列。
- 对历史已存在且只有处理类别无效的 Risk，确认页在每条风险下直接提供“接受风险、降低风险、避开风险、延后处理”四个选项，并把 Runtime 原先填写的整段文字保留为“具体措施”。
- 用户保存风险选择时，Molis Work 生成包含整份剩余方案的修订版本：风险条目使用用户选择，其他未处理条目原样带入；旧版本保留审计记录但不再继续待处理。保存后页面继续准确显示其他尚未解决的问题。
- Risk 事实把“处理类别”和“具体措施”分开存储；新增、编辑、提案修订、最终写入和详情查看使用同一含义。
- 对无法由用户在当前卡片安全修正的问题，仍自动展开具体条目并提供“退回并要求修正”；页面不得把可自行选择和必须 Runtime 修正的问题混成同一个下一步。
- 当方案因 Molis Work 已经检测到的结构或字段问题而无效时，用户可以一键“退回修正”；Molis Work 自动把页面列出的具体问题写入退回理由，补充说明仅为可选。只有方案本身有效、用户基于意图或偏好主动退回时，才要求用户填写理由。
- 即使客户端页面过期或被绕过，确认 API 也在任何物化写入前拒绝无效条目，返回带条目上下文的人话错误，保证不产生部分写入。
- 对决定中心全部用户动作建立同一交互门槛：问题、影响、输入要求、提交中状态、贴近字段的失败、真实结果和刷新后核对入口。

## 非目标

- 不改变 Risk、Rewire 或 Relation 的状态机和权限。
- 不重放或修补历史决定，不替用户重新选择风险处理方式或关系方向。
- 不实现带筛选和归档的完整历史中心；这里只保留最近 6 项结果，完整审计仍在 Goal 记录中。
- 不新增浏览器本地结果账本。
- 不把决定中心变成任意编辑 Runtime 提案的通用表单；只开放用户本来就应当决定、且 Molis Work 能安全校验的风险字段。

## 用户场景

1. 用户点击“接受风险”，页面明确显示该风险已接受、不再阻塞哪些 Goal，并可直接进入风险记录核对。
2. 用户点击“应用关系调整”，页面列出实际新增或解除的关系，并可直接进入相关 Goal 的关系页核对。
3. 用户刷新或稍后重新进入待决定页面，最近结果仍然存在，不会因待决定卡片消失而误以为保存失败。
4. 若后端返回“已应用”但没有任何实际物化结果，页面明确提示“没有产生实际变更”，而不是声称关系已经调整。
5. 用户明确选择“保持待处理”时，页面说明风险仍会留在决定中心；之后新生成的同类事项带有“新事项”标识。
6. 用户打开处理类别无效的 Goal Tree Risk，直接为每条风险选择处理类别，并看到原有整段文字已作为具体措施保留；保存后不需要重新填写其他方案内容。
7. 同一方案还有拆解问题时，用户保存风险选择后页面明确显示“风险选择已保存，仍有 1 项需要 Runtime 补全”，不会谎称整份方案已可采用。
8. 页面已经指出方案缺少关键路径说明时，用户直接点击“退回修正”即可；系统自动附上这些问题，不要求用户把页面内容再抄一遍。若用户只是觉得一份有效方案不符合真实意图，退回前仍需说明哪里不对。

## 方案与关键决策

### 最终体验标准

- 说人话，但不幼稚化：使用简短、专业、日常能理解的词；不写口号、比喻式产品话术或内部协议名堆叠。
- 路径单一：同一状态只有一个名称、一个权威来源和一个明确下一步；同一操作不在多个位置重复出现不同说法。
- 重点先行：先说明问题、影响和用户要确认的内容，再按需展开完整变化、依据和技术记录。
- 操作精准：按钮写清操作结果，字段说明保存后会发生什么；不可执行的动作在提交前禁用并解释恢复路径。
- 反馈闭环：失败说明具体对象、原因和改法并保留输入；成功说明实际状态变化、下一步和可核对入口。
- 优美高效：保持连续文档和紧凑工作台风格，用层级、间距和细分割线组织内容；不增加卡片墙、装饰性视觉或多余步骤。
- 状态逻辑清晰：待决定、已处理、新事项、冲突和提案无效互斥表达；颜色只辅助文字，不承担唯一语义。

- 权威来源继续是现有 `events`、`rewires.impact`、`risks` 和 `goal_relations`；展示层只做关联和人话解释。
- 最近结果按事件倒序，去除同一对象的旧状态，只展示最近 6 项，避免决定页再次变成长历史页。
- 六类决定共用最近结果区，但每类都显示自己的真实结果和下一步：Goal 方案显示采用、退回和冲突项数；目标说明显示是否成为正式依据；新工作显示是否加入 Goal Tree；结果确认显示用户结论；关系和风险显示具体物化效果。
- Goal 链接进入“关联与约束”中的具体风险或关系；完整审计仍留在 Goal 的“完整记录”。
- 即时回执优先读取 API 返回对象，不能从返回值证明实际变化时使用保守文案。
- “新事项”按决定类型比较：处理风险不会清掉新 Goal 方案的标记，处理 Goal 方案也不会让后来新开的风险失去标记。
- Goal Tree Risk 校验由领域层的单一纯函数提供，提案提交、决定 API 和 Web 渲染复用同一判断，避免三处规则漂移。
- 历史 Risk 修订复用 Goal Tree 已有的版本和 `supersedes` 机制，不原地篡改旧提案；服务端根据旧条目构造完整修订版，客户端只提交风险 ID、处理类别和具体措施，不能伪造 Goal 或关系。
- “处理类别”回答采用哪种策略；“具体措施”回答实际准备怎么做。两者在数据、表单、提案和详情中始终分开。
- 退回理由按责任来源区分：系统校验失败使用校验结果自动生成；用户主观否决使用用户理由。两者都进入原有决定审计，不新增第二套状态，也不让空理由绕过有效方案的确认规则。

## 输入、输出与依赖

- 输入：`MolisWorkWebView.events`、`snapshot.risks`、`snapshot.rewires`、`snapshot.relations`、Goal Tree Risk 提案、用户选择的处理类别与具体措施、Goal 标题及决定 API 返回值。
- 输出：持久的最近处理结果区、可定位链接、具体即时回执。
- 依赖：现有项目作用域链接重写、Goal Detail hash 面板定位、事件账本。

## 文件与模块边界

- `src/web/render.ts`：六类结果派生、HTML、样式、锚点、提交中状态和即时回执文案。
- `src/web/server.ts`：校验风险修订输入，基于权威提案构造完整修订版本，拒绝客户端伪造条目结构。
- `src/v1/store.ts`、`src/v1/types.ts`、`src/v1/coordinator.ts`：持久化并物化独立的风险具体措施。
- `src/v1/goal-tree-proposal-validation.ts`：Goal Tree 提案条目的无副作用语义校验，供提交、决定和展示复用。
- `src/v1/coordinator.ts`：新提案进入队列前校验，历史无效提案在物化前拒绝。
- `src/web/i18n.ts`：新增中英文界面文案。
- `tests/v1.test.ts`、`tests/web.test.ts`、`tests/i18n.test.ts`：提案提交门禁、历史无效提案、持久结果、具体影响、项目作用域链接和文案回归。

## 验收标准

- 接受或解决风险后，待决定页刷新仍显示最近结果，说明风险当前是否还会阻塞，并至少提供一个关联 Goal 入口。
- `open → open` 显示为“继续待处理”且风险卡仍在，不使用完成式成功文案。
- 应用 Rewire 后，待决定页刷新仍列出实际新增/解除关系；入口能定位到 Goal 的具体关系记录。
- 拒绝 Rewire 时明确说明现有关系未改变。
- “已应用但零物化结果”不得显示“关系已经调整”，必须明确没有产生实际变更。
- 最近结果来自权威数据，不因浏览器刷新、自动同步或换标签而丢失。
- 晚于最近处理事件创建的待决定项显示“新事项”，让用户能区分新旧事项。
- “新事项”只和同类决定最近一次处理比较，不受其他类型的处理时间影响。
- 新提交的 Goal Tree 提案只要任一 Risk 缺少必要事实、使用非标准处理类别或无效阻塞方式，就在进入待决定前被拒绝，错误指出条目和字段。
- 历史 Risk 只有处理类别无效时，每条风险直接显示四种处理类别和具体措施；没有选择时不能保存，并把错误放在对应风险旁边。
- 保存风险选择后生成包含所有剩余条目的新提案版本，旧版本不再作为待决定事项；用户无需重新输入未修改内容。
- Runtime 原先误填在处理类别中的整段措施默认迁入“具体措施”，用户可以修改；方案最终采用后该措施仍存在于 Risk 详情和编辑表单。
- 如果修订后仍有拆解、关系或其他问题，页面精确显示剩余数量和唯一下一步，不能显示整份方案已可采用。
- 无效方案的理由框显示为“补充说明（可选）”，留空也能一键退回；服务端用实际校验问题生成非空、可审计的退回理由。风险处理选择同样不要求决定理由。
- 有效方案被用户主动退回时，“决定理由”仍为必填；客户端被绕过时服务端也不得接受空理由。
- 直接调用确认 API 也不能绕过预检；失败时整份事务无任何 Goal、Relation、Risk 或决定记录写入。
- Goal Tree、Contract、Candidate、Rewire、Human Review 和 Risk 六类用户动作均有成功、缺少输入、后端失败和刷新后结果的自动化或可复现验收证据。
- 用户在 5 秒内能指出当前事项的问题、需要自己确认的内容和下一步；首屏不依赖 Contract、Candidate、Rewire、Policy、Claim、Run、Evidence、Review 等内部词才能理解。
- 所有可见状态从一套权威事实派生，同一事项不会同时出现互相矛盾的状态名、按钮或操作说明。
- 桌面与 390px 窄屏下，问题、影响、主操作和错误恢复路径的阅读顺序一致；长标题、长中文说明和英文翻译不挤压或遮挡控件。
- 桌面和窄屏下结果区可读、无横向溢出；新增文案具备中英文覆盖。

## 假设与开放问题

- 现有事件和 Rewire impact 已足够恢复风险与关系的实际结果；不需要数据迁移。
- 最近 6 项作为当前密度的起点；若后续用户需要完整决定历史，再单独设计筛选和归档入口。
