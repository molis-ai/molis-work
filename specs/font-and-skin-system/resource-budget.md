状态：预算方案已定，门禁未改（2026-11-07）。用户选了第 7 节的方案二、不设绝对上限，语言目录「工作台一份、插件按需」；门禁在第 16 批开工前单开 PR 落地。实测已完成，本批未改门禁、CI、页面资源许可和产品代码。这是[决策第 23 项](../post-anticorruption-roadmap/reference/decisions.md#decision-23)其余部分的依据，呼应[实施方案 §12.2](implementation-plan.md)。

## 1. 结论

1. **门禁量的只是一小半，日常访问几乎全在门禁外。** 第一次打开，门禁量到的字节占 36%～66%；再次打开，只占 0.0%～0.1%，因为 HTML 是 `no-store`，每次都整份重发，而门禁量的 `/assets/` 文件只回 304。
2. **英文页每次多发 1.9 MB。** 语言目录内联在 HTML 里（英文 953,817 B，中文 214,759 B）。工作台和到达页都还带一个隐藏的侧栏文档，所以目录每次发两份：英文 1,907,626 B、中文 429,514 B。
3. **主文档第一屏几乎用不到这些目录，但不是完全不用插件的词。** 英文页主文档读了工作台的 23～118 条（共 11,558 条，约 1%），工作台页还同步读了 2～3 条 Goals 的词；中文页主文档一条都没读。隐藏的问题收集文档在第一屏就把整本目录交给它的插件框架，所以 Issues 的词第一屏就要到位（第 3.4 节）。
4. **把目录挪出 HTML 是最大的一笔节省。** 再次打开时，英文工作台从 2,573,362 B 降到 667,040 B（少 74%），中文从 1,093,174 B 降到 663,986 B（少 39%）。第一次打开也少：英文少 1,248,732 B，中文少 424,918 B。这些都是算出来的，前提有两个：插件词的请求带 ETag；中文继续用原文作键。**中文第一次打开的节省只到第 16 批换稳定键之前**：换键后中文也要下载工作台的词文件（估算 46～62 万字节），工作台第一次打开约 3.85～4.0 MB，和今天差不多甚至略多。再次打开和英文的节省不受影响（第 4.2 节）。
5. **令牌去重加删 tray／pill，每张样式表只少 17,443 B（gzip 约 4 KB），也只在第一次打开时省。** 值得做，但不解决预算问题。
6. **现有字体的代价目前看不到。** 这台 Mac 上中文后备字体一次都没下载，因为系统字体够用；Noto Sans SC 只有在缺系统字体时才会多出 1,141,536 B，这种情况没量（第 3.6 节）。
7. **圆润字体已实测（第 6.3 节）。** Nunito 拉丁可变 39,128 B，比 Inter 还小。Resource Han Rounded 简中 Regular：GB2312 一级字单文件 622,512 B，整个 GB2312 单文件 1,113,428 B，按 500 字分 14 片时最大片 108,748 B，中文第一屏估计用 2～3 片。许可是 SIL OFL 1.1，但发行物里没有带许可文件，还有未确认的点（第 6.4 节）。

- **冷**：全新的 Chrome 资料目录，只设语言 Cookie。**热**：同一个 Chrome 里开新标签再开一次，HTTP 缓存还在。
- **字节**：DevTools 的 `encodedDataLength`，含响应头；一次访问里，load 之后、网络静止 1.5 秒（上限 8 秒）之前的请求都算第一屏。
- **压缩**：Host 不压缩。带 `Accept-Encoding: gzip, br` 请求 HTML 和资源，响应都没有 `content-encoding`，所以线上字节就是原始字节。文中的 gzip 列是算出来的对照（`zlib` 第 9 级），不是实际传输。
- **缓存**：HTML 是 `no-store`；`/assets/` 和 `pty-client` 是 `private, max-age=0, must-revalidate` 加 ETag，再次打开每个文件回 304，这次线上约 320～338 B（看的是真实响应，不是常数）。

复现（先 `pnpm build`；全量约 4 分钟，出总数、门禁占比和取词记录）：

```sh
node scripts/machine-slot.mjs run browser --label "first-screen" -- node scripts/first-screen-report.mjs --out <目录>
node scripts/first-screen-report.mjs --summarize <目录>
```

`--http-only` 不用排槽位，约 10 秒，但**出不了总数和占比**：它只读文档和文档里写明的文件，隐藏文档、脚本才加载的文件、启动 JSON 都不含，`--summarize` 对它的目录也没有东西可打。

脚本只报告、不判定、不接 CI。第 3.1 节的门禁占比由 `--summarize` 打出（路径以 `/assets/` 开头的算门禁量到）；第 4 节的节省量是用同一批数据另算的一次性结果，算法写在各小节里。第 3.1～3.3 节、第 3.5、3.6 节和附录量的时候项目 id 还是随机的，脚本现在写死了 id（第 7 节），同一页会差几个字节。

事先的线索，核对结果：CSS 拼接（`page-assets.ts:89,97,102`）、字体路由（`web-assets.ts:83-86`）、缓存头（`:98`）、`--paper:` 每张表 7 处都属实。两处估计偏低或要修正：英文目录不是至少 549 KB，而是 953,817 B（中文作键的部分 589,113 B，接近那个估计）；`VISUAL_FOUNDATION_CLIENT_SCRIPT` 是 77,335 B。另外 7 处 `--paper:` 不是同一张表写 7 遍，七条规则内容各不相同（第 4.1 节）。

### 4.1 令牌表去重

每张样式表有 7 条写 `--paper:` 的顶层规则，共 20,295 B：4 条浅色、3 条深色，内容各不相同，因为分属不同的层，且选择器逐层变宽。

算法：每组以最后一条规则为准，它的选择器覆盖前面所有规则、优先级相同且顺序靠后，所以前面规则里同名的声明不起作用，可以删掉；不同名的保留。这样删掉 358 条声明，保留 28 条。

## 6. 统一资源登记

### 6.1 两张表，各管各的

「第一屏资源都要登记」这个决定不变，但分两处放。一处管随产品分发的文件，一处管门禁要算的第一屏。放不到一起的理由有三条：账按页面和语言算，产品登记表没有这两个字段；隐藏文档、内联块、`/api/...` 没有包路径，放不进必须有 `package`、`path` 的表；每个加启动请求的 PR 都要改设计系统包里的同一个文件，正是并行 PR 冲突的来源。

**产品资源登记表** `packages/design-system/resources/registry.json`。只放随产品分发、有包路径的东西：字体、皮肤、字体方案、共同规格、平台语言目录。字段以 A 段合同设计稿第 3.6 节（#1918，`a-section-contract.md`，未合入）为准，本文不重新定义，也不存字节：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定身份，如 `font.inter-latin-variable` |
| `kind` | `spec`／`skin`／`font-scheme`／`locale`／`font`／`asset` |
| `owner` | 主人，如 `design-system`、`workbench` |
| `package`、`path` | 所在包和包内相对路径 |

门禁要的数字只从清单和真实响应来。一个资源既在登记表又在第一屏下发（比如工作台的语言脚本）时，两边各写一行，互不引用：登记表说它是什么，清单说哪一页要它。

**分片的两笔隐藏代价：**

- **样式要写码位表**：按出现次数排的片不连续，`unicode-range` 很长。500 字分片每字重 46,950 B（gzip 17,601），两个字重 93,900 B，Host 不压缩，所以都要算线上字节。这些规则只能放在方案自己的样式里。
- **按码位顺序分不行**：样式能小到 34,212 B，但第一屏 14 片要碰 13～14 片，等于全下载。

**一级字单文件也有缺口**：产品文字里有 7 个字不在一级字内（浏猹琥珀渲氪矶，语料口径同上），用户文字更多，缺的字会落到系统字体，一段话里混两种字形。

**界面字重。** 现有角色是 `--weight-body: 400`、`--weight-control: 500`、`--weight-title: 600`，并且 `font-synthesis-weight: none`，不能靠合成加粗。Regular、Medium 对得上；600 没有对应字重：只声明 400、500 时标题按 CSS 匹配规则落到 500，比现在轻；声明 Bold 时落到 700，比现在重，并多下载一个字重（一级字单文件 636,680 B）。

**裁法取舍（写手的建议，未定）：** 按 500 字分片、Regular 和 Medium 两个字重。第一屏最省，又保留 GB2312 全部覆盖；代价是请求多、样式多 93,900 B、片的排序要固定下来。200 字分片第一屏字节差不多，请求却多一倍多，不划算。

### 6.4 许可核对

原文读的是 npm 包里的 `LICENSE`、字体文件的 name 表，以及 GitHub 仓库的许可文件。下面是读到的事实，不是法律结论。

| 项 | Nunito | Resource Han Rounded |
| --- | --- | --- |
| 许可名 | SIL Open Font License 1.1（包里 `LICENSE` 全文） | 字体部分 SIL OFL 1.1（name 表 13、14 项；仓库 `LICENSE.txt`、`LICENSE.md`） |
| 版权行 | Copyright 2014 The Nunito Project Authors (https://github.com/googlefonts/nunito) | v0.990 字体内：Copyright © 2018—2019 Cyano Hao. Portions © 2014, 2015, 2018 Adobe (http://www.adobe.com/). |
| 保留字名 | 许可和字体内都没有写 | v0.990 标签的 `LICENSE.txt`：Adobe 部分带 Reserved Font Name 'Source'，并写明 Source 是 Adobe 的商标。Cyano Hao 没有声明自己的保留字名 |
| 发行物带许可吗 | 带 | **`RHR-CN-0.990.7z` 只有 7 个 TTF，没有许可文件**；字体 name 表里有许可说明和网址，版权行里没写保留字名 |
| 裁剪要不要改名 | 许可和字体里没有保留字名，fontsource 发的子集也叫 Nunito | 见下面「未确认」 |

**再分发条件**（两款相同，OFL 1.1）：不能单独售卖字体本身，可以随软件打包；每份都要带版权声明和许可（独立文本，或用户容易看到的元数据）；修改版不能用保留字名；不能用作者名义宣传；修改版和衍生品必须仍用 OFL，字体不能改换许可；用这些字体做出来的文档不受约束。发行时要把许可文本放进产品，Resource Han Rounded 这一份得从仓库取。

**上游关系。** 仓库 README 写「derived from Source Han Sans」。思源黑体仓库的 `LICENSE.txt` 现在写 Copyright 2014-2025 Adobe，带 Reserved Font Name 'Source'，OFL 1.1。v0.990 用的是当时的版本（版权年 2014、2015、2018）。

**GitHub 显示 NOASSERTION。** 这和文件内容并不矛盾：现在的 `LICENSE.md`（2022-05-06「license clarification」提交）把仓库分成三块，代码 MIT、`res/` 公有领域、字体 OFL，GitHub 自动识别不出单一许可。这是推测，不是 GitHub 的说明。该文件写的是 Copyright © 2018—2022 Cyano Hao, Portions © 2014-2021 Adobe，带保留字名 'Source'。

**发布情况。** 不是 2018 年后就没发布：

- v0.990（2018-12-23）是最后一个静态 TTF 发行版，也是这次量的版本。
- **v1.910（2022-04-23）标为预发布**，只有 OpenType/CFF2 可变字体，`RHR-CFF2-CN-1.910.7z` 16,255,241 B。不在批准的下载范围内，**没有下载、没有量**。
- 仓库最后一次提交是 2022-05-06，之后没有更新；未归档。

**未确认：**

- 「Resource Han Rounded」这个名字里含有字母序列 source，它是否算用了 Adobe 的保留字名 'Source'。作者用这个名字发布至今，但我没有找到 Adobe 对此的说法，未确认。
- 产品里裁剪后继续叫这个名字是否合适，取决于上一条；Cyano Hao 没有声明保留字名这一点，只能说明不会因他的声明而要改名。
- v0.990 字体内的版权行不含保留字名，以仓库 `LICENSE.txt` 为准是否足够，未确认。
- 字形质量：圆角是脚本批量处理的（name 表写 round all glyphs），只量了字节，没看过实际效果。

## 7. 预算规则

**已定（用户 2026-11-07）：方案二，真实打开一遍算总数；不设绝对上限。**

**何时做：本批只定方案，不改门禁。第 16 批开工前单开一个门禁 PR 落地，功能不混在里面。**

### 先说清楚：它只看得到多少

不开浏览器，服务只回答被问到的路径。单靠文档和文档里写明的文件，第一次打开能看到的只有这些（实测）：

| 页面 | 中文：看得到／浏览器实际 | 比例 | 英文：看得到／浏览器实际 | 比例 |
| --- | ---: | ---: | ---: | ---: |
| 到达页 | 1,127,863／2,921,408 | 39% | 1,866,990／4,399,587 | 42% |
| 项目选择 | 1,346,620／3,157,053 | 43% | 2,085,922／4,635,419 | 45% |
| 工作台·新项目 | 3,129,308／3,819,824 | 82% | 3,870,444／5,300,012 | 73% |
| 工作台·全部项目插件 | 3,268,288／3,959,380 | 83% | 4,011,378／5,441,522 | 74% |
| 工作台·示例项目 | 3,722,144／4,653,995 | 80% | 4,467,257／6,139,518 | 73% |

也就是 39%～83%。其余的字节要靠人手写的第一屏清单（第 6.1 节）告诉门禁去问。**所以方案二算的「总数」，是文档、文档写明的文件和清单上的路径的总数，不是浏览器实际下载的总数。**

| 看得到 | 看不到 |
| --- | --- |
| 文档的全部字节，含所有内联块 | 不在清单上的东西：脚本发的 `fetch`、脚本才加载的文件、脚本才开的隐藏文档 |
| 文档写明的 `link`、`script` | 第一屏的 POST 启动请求：每一页都有 `host/plugin-pages`，工作台还有 `home/events`，到达页还有 `onboarding/context/<id>/selection`。字节很小，但重放可能有副作用，不进门禁总账，只在报告里看；门禁 PR 要按全部页面核一遍 |
| 清单上每条路径的真实响应 | 带 `unicode-range` 的字体：要不要下载取决于页面文字和系统字体 |
| | 第一屏之外的文档、外部插件包、胶囊窗口、导入字体、安装包（第 5 节） |

**这些改法能让数字变小，门禁还是绿的：**

- 把词典从 HTML 挪到页面脚本发的 `fetch("/api/bootstrap")`，不写进清单。HTML 变小，两本账都下降。这正是第 5 节警告的那条路，方向又反了。
- 从清单删一行。那条路径的字节从账上消失。
- 把字节挪进胶囊窗口、外部插件包这些不在账上的地方。

**看守分两层，都不是硬拦：**

- **删行或改行**：删清单行、缩小路径的 PR 必须附一次浏览器报告。门禁在 CI 摘要里列出被删的行，由评审核对。机器不挡，靠评审。
- **防漏报告**：浏览器真开一遍，把实际请求和清单对比，列出清单没有的路径。脚本今天没有这个功能，门禁 PR 要给 `first-screen-report.mjs` 加。它不进门禁，不挡合并。发现漏项时，归 `tooling/gates/` 的 CODEOWNERS 主人处理：补清单行；如果是有人把字节挪走了，开待办追回去。

防漏报告在哪里跑，**是第 16 批门禁 PR 时要问用户的事，本文不定**：

| 选项 | 怎么跑 | 好处 | 代价 |
| --- | --- | --- | --- |
| 甲（建议） | 放进 `ci.yml` 已有的夜间定时任务（`cron: "0 19 * * *"`），新加一个不挡合并的作业，用 Ubuntu 镜像自带的 Chrome（浏览器冒烟已经这样用） | 不靠人记得，最晚第二天发现，失败能在 Actions 里看到 | 要改 CI；多一个浏览器作业。CI 上要跑多久没量，本机每页每语言一轮的时长见下面的「代价」 |
| 乙 | 不改 CI，每批开工前由统筹在本机经浏览器槽位跑一次，结果写进这批的记录 | 不动 CI | 靠人记得；漏项可能拖一批才发现，那时已经合了好几个 PR |

建议甲：看守这件事本身不该再靠手写的习惯。

### 规则

门禁用固定种子起一个临时 Home 的真实 Host，不开浏览器，按页面和语言算总字节，对照 merge-base，只许变少：

- **按页面、按语言的总账，不按资源。** 要问的路径是文档、文档写明的文件、清单上的路径。只许变少的账收四页：到达页、项目选择、工作台·新项目、工作台·全部项目插件。工作台·示例项目照样量，只报告、不挡合并：它的字节随示例数据变，一改示例内容就要写增长许可；代价是随数据涨的问题（比如 `/api/board/refresh`）门禁拦不到，只能从报告里看。`/settings/appearance` 不收：不带 `sec-fetch-*` 请求头时它回独立文档（中文 610,846 B），用户浏览器里却是 302 到工作台，量的是用户打不开的东西。
- **第一次打开**是这些路径真实响应的字节之和。**再次打开**按响应头真问一次：带 ETag 的发 `If-None-Match`，算实际回应的字节；没有 ETag 的（`no-store`）就是整份再来一遍。不用常数。实测 304 的线上字节因文件而异（Chrome 里 319～338 B），写成「每个文件 326 B」的公式的话，把字节挪进不缓存的文件，算出来还是 326 B，反而放过了最该拦的情况。
- **字节在账上的入口之间搬动时**，第一次打开的总账基本不变；搬到不缓存的入口，再次打开的总账变大，直接被拦。搬到账外，看不出来，见上一小节。
- **第一屏清单之外的**：门禁只认清单，清单里多写的路径回 404 或 500 时失败。清单没写的它不知道。
- **起点**：门禁 PR 合入后的那次实测。之后只比较变化，不设绝对上限。
- **时间不进门禁**：时间随机器负载变化，只在报告里看。

### 合理的增长怎么过

新账沿用 `tooling/gates/page-asset-allowances/` 和[开发手册的规则](../../docs/cli-and-development.md#页面资源体积)，不另开一套：每项任务一份独立 JSON，写理由和评审出处；只消费基点尚未包含的新文件，已采用的不复用；合并组累加。许可文件多一个 `pages` 字段：

```json
{
  "reason": "项目卡片加一句空状态说明，已复用现有样式",
  "review": "PR 评审或需求书中的具体审阅出处",
  "pages": { "workbench-default/zh": { "cold": 120, "warm": 120 } }
}
```

- **这不只是加一个字段。** `scripts/gates/page-assets-policy.mjs` 第 21 行拒绝四个键以外的字段，第 24 行要求 `assets` 非空，所以上面这份 JSON 今天是非法的，门禁 PR 要改这两处（`assets` 改成可选）。门禁也要有两层数字：许可按页面和语言写，问用户的门槛按清单上的行算。
- **要不要问用户**沿用现有门槛：清单上一行净增超过 10,000 B，或者新增一行，先取得用户批准，用 `userApproval` 记录出处。文档算一行；一条词落在两份文档里，两行都涨。
- **第 16 批换稳定键要走这条批准。** 换键本身会让中文第一次打开变大（第 4.2 节，估算），新增的工作台语言文件也是新增一行且超过 10,000 B。这和「第 16 批带实测按类一次批准」合在一起办，否则新账第一次拦的就是它。
- **`page-assets` 留着。** 新账稳定之前两个门禁并存，退不退役本文不定。一个改动同时让 `/assets/` 文件和页面总账变大时，同一份许可里 `assets` 和 `pages` 都写。
- **这条路会比今天频繁。** 今天只有改 `/assets/` 的 PR 要写许可；按页面算之后，改模板或加一条词都让 HTML 变大，这类 PR 都要写一份，直到语言目录挪出 HTML。频率没有量，门禁 PR 应该拿最近合并的 PR 回放一遍再定稿。失败信息要直接打印这份 JSON 的草稿，省掉算数字的功夫。

### 同一提交的字节要稳定

不做处理时，同一提交的 HTML 差 2～4 B：`data-hue` 由随机项目 id 算出（`orange` 和 `blue` 差 2 B），HTML 里还写了 Home 路径。否掉方案三时说过「容差是可以钻的空子」，所以这里也不留容差，把来源去掉。**实测（一次性重放，合并后的提交）：**

| 做法 | 结果 |
| --- | --- |
| 项目 id 写死（`project-onboarding-00000000-0000-4000-8000-000000000001`、`…002`，创建时只接受这个形状；示例项目本来就是 `molis-work-v1-demo`），Home 用同样长度的路径 | 到达页、项目选择、工作台三种的中英文共 10 组，每组连跑 4 次、每次重新建 Home，第一次和再次打开的总数都一个字节不差 |
| Home 路径多 12 个字符 | 工作台 HTML 多 24 B（路径写了两处），示例项目的 `/api/board/refresh` 再多 12 B；到达页和项目选择不变 |

所以门禁要：项目 id 写死；两边的 Home 用同一个前缀建在同一个临时目录下；同一个作业里先后量基点和候选。这组结果只在这台机器上、几分钟内跑过，跨天的相对时间、不同机器都没试。两边是同一时刻量的，时间带来的变化应当相互抵消，这一点也没有实测。

### 代价

- **一边要起 Host 走完所有页面，约 7～8 秒**（实测 5 次：7.2～8.3 秒。写种子约 1.5 秒，起 Host 约 1.2 秒，5 个页面两种语言的文档、文件、启动 JSON 和条件请求约 4.7 秒）。
- **对照 merge-base，基点这边也要跑一遍**，所以至少翻倍，约 15 秒。
- **基点和候选都要先 `pnpm build`。** 今天的 `page-assets` 只用 `pnpm workspace:build`，它直接调资源模块、不起完整服务；方案二要 `dist/web/server.js`，它是根 `pnpm build` 的产物。CI 这一步之前只有 `workspace:verify`，所以要多一次根构建。基点没有可信的现成结果时，还要在临时检出里安装、构建一次（`page-assets-baseline.mjs` 的做法），这段时间没有量；`ci.yml` 另一个作业的注释写着安装加构建约 2 分钟，可作参考。现有的基线缓存要带上新测量器。
- 要加一份固定种子，种子数据一改数字就变。
- 示例数据不代表真实大项目。

只是说明目标，**不是拦人的数**。按「语言目录分法乙（含第一屏的 Issues 和 Goals 词）、删 tray／pill、令牌去重」算：

### 只在选用时加载的字体

不进默认皮肤的首屏总账，单列一本「选用总账」：`选用总账 = 默认总账 + 该方案的字体和字体样式`。同样不设上限，只比较变化。门禁或定期报告核对：**没选这个方案时，第一屏一个字节都不能下载它**，`@font-face` 也不能进基础样式表。

用实测数字重算（工作台·新项目，已按分法乙并算上第一屏的插件词，换稳定键之前；换键后中文各行第一次打开再加第 4.2 节那份文件；Regular＋Medium，加 Nunito；响应头按 358 B、再次打开按 326 B 估算；皮肤文件和皮肤差异未计入）：

| 中文页的裁法 | 文件数 | 第一次打开增加 | 第一次打开总数 | 再次打开总数 |
| --- | ---: | ---: | ---: | ---: |
| 不选 Folio（基准） | 0 | 0 | 3,394,906 | 663,986 |
| 500 字分片，第一屏 2 片（估算） | 6（含样式） | 523,876 | 3,918,782 | 665,942 |
| 500 字分片，第一屏 3 片（估算） | 8（含样式） | 709,040 | 4,103,946 | 666,594 |
| 一级字单文件 | 3 | 1,287,678 | 4,682,584 | 664,964 |
| GB2312 全部单文件 | 3 | 2,274,230 | 5,669,136 | 664,964 |

- 后备字体第一屏可能下载，单列「缺系统字体」的账：今天是默认总账加 1,141,536 B，没实测过。

### 否掉的方案，和否掉的理由

**方案一：只加登记表和内联块门槛。** 静态扫描，几乎不增加门禁时间，也不用起 Host。否掉：只在代码里查名单，查不出网页本身变大；HTML 真实字节、数据块、`/api` 都量不到，换个写法就漏。

**方案三：真实浏览器总账进 CI。** 最准，脚本发的请求、隐藏文档、实际下载的字体都量得到。否掉：每次真开浏览器，慢、易误报。本机 3 轮约 3.5 分钟，浏览器又是 CI 里最不稳定、预算最紧的部分；时序带来字节抖动（设置页冷热两次的 API 请求数就差一个），得加容差，容差又是可以钻的空子。它的量法留作定期报告。

| 门禁在 CI 上的时长、基点隔离构建的时长、防漏作业的时长 | 只量了本机一边约 7～8 秒 |
